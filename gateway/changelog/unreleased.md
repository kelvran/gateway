## Added

- `kelvran.guardrail.fail_open` OTel counter (`{request}`), attributed with `kelvran.virtual_key.id` and a new `kelvran.guardrail.stage` attribute (`precall` / `postcall` / `embeddings`). Incremented at most once per request per stage when a guardrail detector errored or panicked and the request was still allowed through — the guardrail equivalent of the existing `kelvran.ratelimit.fail_open` / `kelvran.budget.fail_open` counters. A Block-tier detector error fails closed and is not counted. Recorded from the dataplane's five `guardrails.Check` call sites (not inside `guardrail.Engine`, which stays an import-free leaf), next to a new `guardrail_fail_open` log line that carries `trace_id`/`key_id`/`stage`; the engine's own `guardrail_detector_error` line is unchanged. Per `docs/upgrade-research/kelvran-deep-research-round3-2026-10-07.md`.
- Upstream error classification by exception name, and upstream `Retry-After` honoured. A non-2xx upstream response's `X-Amzn-ErrorType` header (Bedrock: `ThrottlingException` vs `ModelNotReadyException` under one 429; `ServiceUnavailableException` / `InternalServerException` under 503 / 500), falling back to the body's top-level `__type` / `code` exactly as AWS's own SDK resolves and sanitises it (then, because the value is upstream-authored text headed for a log field, stripped of control characters and cut to 128 runes on a rune boundary), is now captured on `UpstreamHTTPError.ErrorType`, and its `Retry-After` header (delta-seconds or HTTP-date) on `UpstreamHTTPError.RetryAfter`. The `chat_completion` / `embeddings` error log lines gain `upstream_status`, `upstream_error_type` and `upstream_retry_after_ms` (and `upstream_provider` / `upstream_stream_error` for a mid-stream exception frame). The client-facing `Retry-After` is now `max(local backoff, upstream Retry-After capped at 60 s)` — the local backoff is never lowered, and an upstream cannot make Kelvran tell tenants to wait more than a minute. `UpstreamHTTPError.Error()` and `ClientSafeMessage()` are unchanged; the error type never reaches a client body. Per the same research round.
- `deployments.<name>.rate_limit.tpm_accounting` — an optional block that makes a deployment's tokens-per-minute ceiling count tokens the way its provider's quota does: `output_token_multiplier` (Bedrock's output "burndown": 5× for Claude ≤ 4.7, 10× for Sonnet 5 / Opus 5 / Opus 5.5 / Fable 5.1, 15× for Claude 4.8; default 1) and `exclude_cache_read_tokens` (Bedrock's quota does not count cache reads; default false). The weighted count for one call is `PromptTokens − CacheReadTokens (if excluded) + CompletionTokens × multiplier`. A `tpm_accounting` block without a `tpm_capacity` ceiling, or a multiplier below 1, is a load-time error. The per-virtual-key TPM dimension is deliberately left in raw tokens. Per `docs/upgrade-research/kelvran-deep-research-round3-2026-10-07.md` (ranked item 1).

## Changed

- **Deployment-scoped TPM is now enforced.** `deployments.<name>.rate_limit.tpm_capacity` / `tpm_refill_per_second` have been parsed and validated since 2026-09-09 but were deliberately not wired — a config that set them was a silent no-op. They now gate EVERY call to the deployment (hop 1, every `fallback_chains` hop, the router-based single fallback) with the same reserve-then-reconcile bookkeeping the per-key TPM dimension uses: reserved immediately before the upstream call, reconciled to the real (weighted, see `tpm_accounting` above) usage on success, released on failure, so a failed or skipped hop never consumes the bucket. A rejected call is a `DeploymentCapacityError` with `Reason: "tpm"` (HTTP 503, like `rate_limit` / `concurrency`), and inside a fallback chain it simply moves the chain to the next hop. Operators who set these fields before this release should expect them to start limiting. Like the deployment RPM ceiling, the limiter is in-memory per gateway instance. The stale startup warning "TPM is in-memory-only in v1 and will not be enforced" (per-key TPM under Redis has been enforced since the GCRA path landed) is removed.

- `gen_ai.client.token.usage` (Histogram, with a `gen_ai.token.type` enum attribute) is replaced with the current OTel GenAI semantic-conventions token-metrics shape (`open-telemetry/semantic-conventions-genai` PR #374, merged 2026-09-22): 4 new Counters (`gen_ai.client.inference.usage.{input,output,cache_read.input,cache_write.input}_tokens`, each carrying a new `gen_ai.token.modality` attribute) plus 2 new percentile-only Histograms (`gen_ai.client.inference.operation.{input,output}_tokens`). `gen_ai.client.operation.duration` (the separate duration histogram a live Grafana dashboard and Prometheus SLO rules depend on) is unchanged. A 5th new counter in the same spec family, `reasoning.output_tokens`, is deliberately not added yet — Kelvran doesn't track reasoning-token counts anywhere today; adding an always-empty or fabricated-zero instrument would be worse than not adding it. Found via a live end-to-end research pass immediately after the v0.16.0 release.

## Fixed
