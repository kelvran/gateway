## Added
- `POST /v1/messages/count_tokens` on an `anthropic` deployment answers with the deployment's own count: the body is parsed as a Messages body without `max_tokens` and its canonical shadow scanned by the pre-call guardrail (`400` `content_policy_violation` before any upstream byte; a paid detector costs the operator per count, bounded by the virtual key's RPM). It is then forwarded as received — `model` rewritten to `upstream_model`, nothing else touched, no `stream` added — with the client's `anthropic-*` headers to the deployment's `/count_tokens`. The answer comes back byte-for-byte with its `x-should-retry`/`anthropic-ratelimit-unified-*` headers, its own `400`/`422` verbatim and every other failure redacted, exactly as on `/v1/messages`. A body the parser rejects is the parser's `400`, and Kelvran's own request validators run as on `/v1/messages`; an answer over 64 KiB, like a transport failure, is the redacted `502` `upstream_error`. No budget gate stands in front of a count or its guardrail scan (`THREAT_MODEL.md`). No budget moves (Anthropic bills nothing for a count), no cache layer is touched. Every other deployment still answers `404` `count_tokens_unavailable`. Item 11 slice S11c (RFC-1 §9); mock-proven, no live run.
- `POST /v1/messages` on an `anthropic` deployment, streamed: every SSE frame the deployment sends reaches the client exactly as read — event and data lines, comment and `id:` lines, CR LF terminators — before the gateway decodes it for usage, cost, the cache, the post-call audit and the guard cuts; the `x-should-retry` and `anthropic-ratelimit-unified-*` headers travel with the first frame; an upstream `error` frame that follows a relayed frame is relayed as sent and is the stream's single error event, while an error frame, or a frame the gateway cannot decode, that is the very first upstream event is redacted like a pre-stream failure and the hop may fall back; one SSE event is bounded at 4 MiB beside the 1 MiB line cap; a guard cut still ends the stream with `content_block_stop` (the upstream's open block), `message_delta` (`stop_reason: max_tokens`) and `message_stop`; the gateway's own `event: ping` may be interleaved after 15 s or more of upstream silence. The first relayed frame counts as the first byte sent (no fallback hop after it; the turn is billable — a stream that dies after `message_start` is billed the estimated prompt, where before it was unbilled and fell back). A cache hit and an `Idempotency-Key` replay (including a second request on the same key that waited for the first) still stream the re-encoded canonical message, and a stream carrying an event type the gateway does not know before `message_delta` is never cached or replayed (it reached the client; a re-encoded copy would lack it; one arriving after `message_delta` is relayed but not flagged). Translate hops and `/v1/chat/completions` are unchanged. Item 11 slice S11b2 (RFC-1 §9); mock-proven, no live run.
- `POST /v1/messages` on an `anthropic` deployment, buffered: the deployment's own 2xx body is relayed to the client byte-for-byte — Anthropic's id, model and every block, including ones the canonical schema cannot represent — with its `x-should-retry` and `anthropic-ratelimit-unified-*` response headers forwarded unchanged; a cache hit, an `Idempotency-Key` replay or a request de-duplicated against an identical in-flight one is still re-encoded from the canonical response, and a response the shadow cannot represent is now also not stored for replay — the cache already skipped it (slice S6) — so a reused key re-runs the call rather than returning a copy with a block missing. An `anthropic` deployment's own `400` or `422` whose body is Anthropic's error object passes through with its status and body unchanged, so Claude Code's recovery can match Anthropic's wording; every other upstream status, body shape or provider stays the redacted `502`. A streamed turn's pre-stream errors take the same envelope path, so the `400`/`422` exception and the two headers reach a streaming client too; the streamed 2xx relay is the entry above (slice S11b2). Mock-proven; the live run waits for an Anthropic key. Item 11 slice S11b.
- `POST /v1/messages` on an `anthropic` deployment: the request body reaches Anthropic as received — only `model` (→ `upstream_model`) and `stream` are rewritten, on the top level, so unknown members at any depth, member order and the whitespace inside values survive — and every `anthropic-*` request header is forwarded as an open list by prefix, the client's `anthropic-version` taking precedence over the gateway's default; the deployment's own `x-api-key` is the credential and no other client header is forwarded. The forwarded header set is bounded at 16 KiB in total (`400` `invalid_request`). On such a hop `kelvran.ingress.passthrough` is `true` and `dropped_fields` empty. Budgets still price the hop at the deployment's configured rates: betas or server tools that change Anthropic's pricing or add per-call fees are not reflected (`THREAT_MODEL.md`, Tampering row). The buffered response, its relayable headers and Anthropic's own 400/422 are relayed by the entry above; a streamed response is relayed frame by frame by the S11b2 entry. Mock-proven (byte identity of body and headers through a capturing upstream, buffered and streamed); the live passthrough run waits for an Anthropic key. Item 11 slice S11a.
- `POST /v1/messages/count_tokens`: the Anthropic token-counting endpoint is served — authenticated (`x-api-key` or bearer), source-IP- and model-allowlisted, one RPM token per call with the same `Retry-After` rule, no budget, cache or upstream — and answers `404` `not_found_error` with `code` `count_tokens_unavailable` for every deployment but `anthropic` (the `anthropic` branch is the S11c entry above), where Claude Code falls back to its character-based estimate and the Anthropic SDKs raise their not-found error. `kelvran connect claude --check` now reads a `403` `model_not_allowed` as a proven URL and credential (the gateway authenticates and checks `allowed_models` before it routes), so an allowlisted key no longer reports failure. New how-tos: `docs/how-to/clients/claude-code.md` and `anthropic-python.md`. Item 11 slice S10b.
- `POST /v1/messages`: the Anthropic Messages API, buffered and streaming, for the Anthropic SDKs and Claude Code (`ANTHROPIC_BASE_URL` plus one credential variable; `x-api-key` is read as the bearer's alias, `Authorization` wins). The body becomes the same canonical request `/v1/chat/completions` produces, so every pipeline stage — virtual keys, budgets, rate limits, guardrails, the three cache layers, `Idempotency-Key`, routing and fallback, telemetry — applies unchanged; the response is an Anthropic `message` or the Anthropic event stream, with a gateway `ping` after 15 s or more of silence and an `error` event (never a clean end) on a mid-stream failure. Errors before the first byte use Anthropic's envelope with Kelvran's `code` and `param` kept (a mid-stream failure is an `error` event with the type and redacted message), so `kelvran connect claude --check` turns green against this build for a key without `allowed_models` (400 + `model_not_found`; an allowlisted key answers the probe's placeholder model with 403 `model_not_allowed`, which slice S10b (the entry above) reads as proof too); an upstream over-long-prompt rejection carries `capability_rejected: prompt_too_long`. The normalised `anthropic-beta` set is folded into the cache keys and the `Idempotency-Key` fingerprint; `metadata.user_id` fills the end-user cache scope when `X-Kelvran-End-User-Id` is absent. Interim: every deployment was a translate hop until slice S11a (the entry above) relayed the request body to `anthropic` deployments; on every other provider a body with members the schema cannot hold is routed, dropped-and-reported, or refused (`lossy_ingress_rejected`) exactly as the previous entry describes; `POST /v1/messages/count_tokens` is served since slice S10b (the entry above). Item 11 slice S10a.
- An Anthropic Messages request whose body carries members the canonical schema cannot hold is routed only to an `anthropic` deployment or one with `accept_lossy_anthropic_ingress: true` (an `anthropic` hop was shadow-encoded as well until slice S11a, the entry above, relayed the request body; since then nothing is dropped there); when no deployment in the model's pool is eligible it is `400` `invalid_request_error`, code `lossy_ingress_rejected`, `param` the JSON pointers of those members (cut on a pointer boundary at 512 bytes, like `dropped_fields`), with a message that names the config key and `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` and only those top-level members whose name is a plain identifier free of the strings Claude Code matches on for recovery (decision Q5; the rest are counted), before any upstream call. The error-code catalogue row lands with the route. Such a request is never auto-marked with `cache_control`, its `Idempotency-Key` fingerprint is the body as received, and its span and `chat_completion` log line carry `kelvran.ingress.format` / `ingress_format`, `kelvran.ingress.passthrough` / `passthrough` (`false` on a translate hop; `true` on an `anthropic` hop since slice S11a) and `kelvran.ingress.dropped_fields` / `dropped_fields` (sorted pointers, 512 bytes, when a translate dropped members). The route that sets any of this (`/v1/messages`) is not wired yet, so none of it is reachable from any route; `/v1/chat/completions` changes only in the one-time key change (see Changed) and in `ValidateFieldSizes` now bounding a content part's `text` like a message's `content` (8 MiB; before, only the 32 MiB body cap applied). Item 11 slice S9b.

Two deployment keys load and validate ahead of the `/v1/messages` route: `anthropic_beta_policy` (`strip` default; `forward_known`, Bedrock-only, will forward only the live-proven `anthropic-beta` allow-list once the upstream leg (S11) applies it; the route is served since S10a; an `anthropic` hop forwards `anthropic-beta` since slice S11a, every other hop strips it) and `accept_lossy_anthropic_ingress`; `kelvran doctor` warns once per non-`anthropic` chat deployment that leaves the latter `false`. ## Changed
- Every cache key changes once on upgrade: the thinking configuration, the four sampling fields (`top_p`, `top_k`, `stop`, `effort`) and the Anthropic ingress's passthrough fingerprint are folded into the L1 and L2 keys and gated in the L3 check, so entries written by an earlier version become unreachable (a one-time cold cache, exactly as the `tools` fold in `gateway/v0.18.0` was). Two requests that differ only in `stop` or `top_p` — which the gateway now forwards — are different requests and no longer share an entry; the thinking, `top_k` and `effort` folds exist so the ingress, when it lands, can never be served a reply made under another configuration. All three folds the item 11 plan schedules before the ingress ships are in this release (S4 thinking, S5 sampling, S9b passthrough — the members of an Anthropic Messages request the schema cannot hold and its `is_error` tool results, empty for every `/v1/chat/completions` request); a release carrying all three costs one cold cache.
- A `/v1/chat/completions` request that sets `stop` or `top_p` now reaches the provider with them (see Added). Before, both were accepted and dropped, so a client that always sent `stop` got unbounded completions and one that sent `top_p` got the provider's default sampling; the same request now behaves as the client asked. A body whose `stop` is neither a string nor an array of strings is `400` `invalid_json` (it was ignored). A body carrying `stop` or `top_p` also fingerprints differently for `Idempotency-Key` than on the previous build, so a key claimed before the upgrade and reused within its window with it is the `422` mismatch, not a replay.
- A `role: tool` message with image or document `parts` on a model whose pool has no `anthropic` or `bedrock` deployment is `400` `tool_result_parts_unsupported` (was `502` `upstream_error` from the adapter's own rejection on `anthropic`, `bedrock` and `gemini`, and a forwarded `image_url` part the provider rejects on `openai`/`openaicompat`, where a document part was already the adapter's own `502`); with such a deployment in the pool the request is routed to it. Text-only parts on a `gemini`-only pool are likewise `400` (was `502`).
- Two error statuses that were the `502` `upstream_error` default now say what happened (plan gate G16, decided 2026-10-10 together with RFC-1; a MINOR change under `docs/VERSIONING.md` §3: statuses are public surface, and nothing a documented client does stops working — the SDKs still raise an exception, the only `Retry-After` promise in §2 is on 429, and `type`/`code` gain values without losing any): `response_format` on a model pool with no deployment able to enforce it is `400` `invalid_request_error` / `response_format_unsupported` with `param` `response_format`; an `Idempotency-Key` reused within its window with a different body is `422` `invalid_request_error` / `idempotency_key_reused` with `param` `Idempotency-Key`. Neither carries `Retry-After` or bumps the key's retry backoff any more, and the decision event records `OUTCOME_INVALID_REQUEST` instead of `OUTCOME_UPSTREAM_ERROR`. Both are decided before any upstream call, as before.

## Fixed
- `bedrock`: `usage.total_tokens` counted cache tokens twice. Converse's `totalTokens` already includes `cacheReadInputTokens`/`cacheWriteInputTokens` (a live turn on 2026-10-11: input 2, output 4, cache write 35932, total 35938 — the gateway answered 71870) and the adapter added them again, so the TPM limiter debited the doubled figure on every cached Bedrock turn and the `total_tokens` field broke the documented `prompt_tokens + completion_tokens` contract. The adapter now derives the total from its own cache-inclusive prompt count plus the completion count and never reads `totalTokens`; `prompt_tokens`, the cache subsets and the cost were right all along.
- `POST /v1/messages`: a `role: system` entry inside `messages` (Claude Code's mid-conversation system message, sent under its `mid-conversation-system-2026-04-07` beta when the pre-release betas are on) kept its text in content parts that no adapter's system hoist read, so a Bedrock deployment received an empty system block and answered 400 "The system field can't be null" (surfaced as `502` `upstream_error`; Claude Code retried until its own timeout). The ingress now parses such an entry like the top-level `system` array — one system message per text block, `cache_control` kept, a non-text block recorded as untranslatable — and the `bedrock`, `anthropic` and `gemini` adapters hoist a system message's text parts (its plain content first, then each part; `bedrock` and `anthropic` keep the cache markers, Gemini has none), emit nothing for a system message without text, and refuse a non-text part instead of dropping it — `400` `invalid_request_error` `system_parts_unsupported` with `param` `messages`, reachable only through a message's `parts` member on `/v1/chat/completions`, since the Anthropic ingress records such a block as untranslatable before any adapter runs. The `openai` and `openaicompat` adapters already rendered every part and keep the entry in place as a `role: system` message. Found in slice S10b's live Claude Code run.
- A streamed response the gateway cut off (the runaway ceiling or a mid-stream reservation top-up) is no longer written to any cache layer: its canonical response now carries `finish_reason: length`, where before it had no finish reason, so an identical request within the cache TTL was served the truncated answer with an empty `finish_reason` as if complete. The live stream bytes are unchanged; an `Idempotency-Key` replay of such a response now reports `finish_reason: length`. A stream whose final upstream event both crossed the ceiling and carried the finish chunk is complete and is still cached.
- The `publish-image` job no longer tries to attach the image SBOM to the GitHub Release (`release.yml` creates that Release first, and the job deliberately holds `contents: read`); the CycloneDX SBOM and SLSA provenance are attested to the registry only. The job can also be dispatched for an existing `gateway/v*` tag (`workflow_dispatch`, input `release_tag`) to rebuild, push, sign and attest that tag's image from the current workflow definition. The `gateway/v0.18.0` image was re-published this way (index `sha256:acf52ab117fb…`, signed, SBOM and provenance attested; the tag run's first index, `sha256:a68f3eaf…`, stays in GHCR untagged).
