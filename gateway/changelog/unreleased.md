## Added
- The client side of a stream is an interface (`streaming.ChunkSink`), and `HandleChatCompletionStream` shares one core with a sink-taking `HandleChatCompletionStreamSink`; the Anthropic Messages encoder implements it and, through the optional `streaming.Finisher`, ends a message the dataplane cut off (runaway ceiling, reservation top-up) with `stop_reason: max_tokens` and the final usage rather than the `end_turn` a finish-less stream would otherwise get, and gains a keepalive (`KeepAlive`/`StartKeepAlive`) that pings after a tick of silence, flushes every event when the writer can flush, and is terminal after `message_stop` or an error event. Nothing routes to the encoder yet. `/v1/chat/completions` live streaming bytes are unchanged on every path, a guard trip included.
- The Anthropic Messages ingress parser and encoders exist as the leaf package `internal/ingress/anthropicmsgs` (`Parse` into the canonical request plus an `adapter.Passthrough` carrying the raw body, every unconsumed member by JSON pointer, untranslatable content blocks recorded whole, and their pointers; `EncodeResponse`, `EncodeError`, `SSEEncoder`; strings in any member of a message or content block the canonical schema has no home for are surfaced to the guardrail scan). Nothing routes to it yet — `/v1/messages` arrives with a later slice — so no request behaviour changes. A `role: tool` message gains a hidden `ToolResultIsError` flag, which `anthropic` sends as `tool_result.is_error` and `bedrock` as `toolResult.status: "error"`; it is unreachable from `/v1/chat/completions`, whose tool results stay `is_error`-less and `"success"` exactly as before.
- The canonical request carries the caller's thinking configuration: `adapter.ChatRequest.Thinking` (`type` `enabled`/`adaptive`/`disabled`, `budget_tokens`), set only by the Anthropic Messages ingress (its parser exists, no route is wired yet; the field is unreachable from `/v1/chat/completions`). The `anthropic` adapter forwards it verbatim, with Kelvran's non-strict `block_binding` still added on the models that run the prefix check; the `bedrock` adapter forwards it through `additionalModelRequestFields` when the served model's Claude generation accepts the type — live-probed on 2026-10-10: 5.x takes `adaptive`, 4.6 both, 4.5 `enabled` (sonnet-5, sonnet-5-5, fable-5-1, haiku-5-5, sonnet-4-6 and haiku-4-5 proven; every Opus id and sonnet-4-5 placed by their generation, the probe being IAM-denied for Opus) — omits it when the generation is known to reject it, and forwards it to any family outside the table so the upstream's own answer is what the caller sees. Every omission, and a configuration sent to a provider with no thinking support, is a `request_field_dropped` log line naming the deployment, model, `field`, `value` and reason. The `Idempotency-Key` fingerprint folds the configuration in when one is set (a request without one fingerprints exactly as before), so a reused key with a body that differs only in `thinking` is the `422` mismatch, not a replay. Item 11 slice S4.
- `stop` (a string or an array of strings) and `top_p` on `/v1/chat/completions` are forwarded to every provider — Anthropic `stop_sequences`/`top_p`, Bedrock Converse `inferenceConfig.stopSequences`/`topP`, OpenAI and OpenAI-compatible `stop`/`top_p`, Gemini `generationConfig.stopSequences`/`topP` — and a stop that matched surfaces as `finish_reason` `stop` with the native `stop_reason` (`stop_sequence`) beside it and, on `anthropic` deployments only, the matched `stop_sequence` (Converse reports no matched sequence). Provider limits (OpenAI accepts at most four stop sequences; Sonnet 4.5 and Haiku 4.5 reject `temperature` and `top_p` together) stay the provider's own `400`. Item 11 slice S5.
- The canonical request carries `top_k` and `effort` (Anthropic's `output_config.effort`), set only by the Anthropic Messages ingress (its parser exists, no route is wired yet; neither is reachable from `/v1/chat/completions`, and OpenAI's `reasoning_effort` is a different vocabulary that is deliberately not mapped). The `anthropic` adapter forwards both verbatim; `gemini` forwards `top_k`; `bedrock` forwards each only where the served model's Claude generation accepts it — live-probed on 2026-10-10: `top_k` on 4.6 and 4.5 but not 5.x ("deprecated for this model"), `effort` on 5.x and 4.6 but not 4.5 — and forwards both to any family outside the table; `openai` and `openaicompat` ignore both. Every omission is a `request_field_dropped` line (`field` `thinking`, `top_k` or `effort`; `value`; reason). Item 11 slice S5.
- A `role: tool` message may carry `parts` (text, image, document): `anthropic` sends them as a `tool_result` block array and `bedrock` as `toolResult.content` blocks, where before both adapters rejected the message. A request whose tool message carries image or document parts is routed to a deployment in the pool that can carry them (`openai`/`openaicompat` take text parts only, `gemini` none), the same way `response_format` is; when none can, it is `400` `invalid_request_error` / `tool_result_parts_unsupported` with `param` `messages`, before any upstream call. Item 11 slice S6.
- A response carrying a provider content block the canonical schema cannot represent — an Anthropic block type newer than the adapter, such as a server tool use, or a delta type newer than the decoder on a stream — is delivered as before but never written to any cache layer, so a cache hit can never silently lose a block the live client received. Item 11 slice S6.
- The canonical chat response carries the provider's native stop reason beside the canonical `finish_reason`: `stop_reason` and, for Anthropic, the matched `stop_sequence`, on `/v1/chat/completions` responses and on the streaming chunk that sets `finish_reason`, for `anthropic` and `bedrock` deployments (omitted elsewhere; `finish_reason` is unchanged). They round-trip through the cache and the streaming replay. The first canonical-schema gap fill for the Anthropic Messages ingress (item 11 slice S3; the fields RFC-1 §1's `EncodeResponse` reads): an Anthropic-shaped response can then be rendered without guessing the stop reason back from `stop`.

## Changed
- Every cache key changes once on upgrade: the thinking configuration and the four sampling fields (`top_p`, `top_k`, `stop`, `effort`) are folded into the L1 and L2 keys and gated in the L3 check, so entries written by an earlier version become unreachable (a one-time cold cache, exactly as the `tools` fold in `gateway/v0.18.0` was). Two requests that differ only in `stop` or `top_p` — which the gateway now forwards — are different requests and no longer share an entry; the thinking, `top_k` and `effort` folds exist so the ingress, when it lands, can never be served a reply made under another configuration. Two of the three folds the item 11 plan schedules before the ingress ships (S4 thinking, S5 sampling, S9b passthrough); a release carrying all three still costs one cold cache.
- A `/v1/chat/completions` request that sets `stop` or `top_p` now reaches the provider with them (see Added). Before, both were accepted and dropped, so a client that always sent `stop` got unbounded completions and one that sent `top_p` got the provider's default sampling; the same request now behaves as the client asked. A body whose `stop` is neither a string nor an array of strings is `400` `invalid_json` (it was ignored). A body carrying `stop` or `top_p` also fingerprints differently for `Idempotency-Key` than on the previous build, so a key claimed before the upgrade and reused within its window with it is the `422` mismatch, not a replay.
- A `role: tool` message with image or document `parts` on a model whose pool has no `anthropic` or `bedrock` deployment is `400` `tool_result_parts_unsupported` (was `502` `upstream_error` from the adapter's own rejection on `anthropic`, `bedrock` and `gemini`, and a forwarded `image_url` part the provider rejects on `openai`/`openaicompat`, where a document part was already the adapter's own `502`); with such a deployment in the pool the request is routed to it. Text-only parts on a `gemini`-only pool are likewise `400` (was `502`).
- Two error statuses that were the `502` `upstream_error` default now say what happened (plan gate G16, decided 2026-10-10 together with RFC-1; a MINOR change under `docs/VERSIONING.md` §3: statuses are public surface, and nothing a documented client does stops working — the SDKs still raise an exception, the only `Retry-After` promise in §2 is on 429, and `type`/`code` gain values without losing any): `response_format` on a model pool with no deployment able to enforce it is `400` `invalid_request_error` / `response_format_unsupported` with `param` `response_format`; an `Idempotency-Key` reused within its window with a different body is `422` `invalid_request_error` / `idempotency_key_reused` with `param` `Idempotency-Key`. Neither carries `Retry-After` or bumps the key's retry backoff any more, and the decision event records `OUTCOME_INVALID_REQUEST` instead of `OUTCOME_UPSTREAM_ERROR`. Both are decided before any upstream call, as before.

## Fixed
- A streamed response the gateway cut off (the runaway ceiling or a mid-stream reservation top-up) is no longer written to any cache layer: its canonical response now carries `finish_reason: length`, where before it had no finish reason, so an identical request within the cache TTL was served the truncated answer with an empty `finish_reason` as if complete. The live stream bytes are unchanged; an `Idempotency-Key` replay of such a response now reports `finish_reason: length`. A stream whose final upstream event both crossed the ceiling and carried the finish chunk is complete and is still cached.
- The `publish-image` job no longer tries to attach the image SBOM to the GitHub Release (`release.yml` creates that Release first, and the job deliberately holds `contents: read`); the CycloneDX SBOM and SLSA provenance are attested to the registry only. The job can also be dispatched for an existing `gateway/v*` tag (`workflow_dispatch`, input `release_tag`) to rebuild, push, sign and attest that tag's image from the current workflow definition. The `gateway/v0.18.0` image was re-published this way (index `sha256:acf52ab117fb…`, signed, SBOM and provenance attested; the tag run's first index, `sha256:a68f3eaf…`, stays in GHCR untagged).
