# Unreleased

Entries accumulate here under the six [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) categories until the next `gateway` release. At release time this file's content is moved into a new dated `<version>.md` file (e.g. `0.2.0.md`) in this same folder, and this file is reset to empty category headers.

Versioning: [SemVer](https://semver.org/) — load-bearing for the Go module path/tag (`v0.1.0`, `v0.2.0`, ...).

## Added
- `docs/operations/FAILURE-MODES.md`: one table of what the gateway does when each dependency fails — Redis behind the rate limiter, the budget tracker, the identity store and config propagation; the bbolt persistence files; upstream providers; guardrail detectors; credential files; the OTLP collector — with the request-path behaviour, the startup behaviour, the metric and log event that show it, the operator action, and how each row was verified (test, code reading or live). `DEPLOY.md` gains a Redis outage runbook and `TELEMETRY.md` now lists every `kelvran.*` counter the gateway emits (six were missing: `kelvran.budget.fail_open`, `kelvran.budget.threshold_crossed`, `kelvran.streaming.cost_estimated`, `kelvran.streaming.near_duplicate_collision`, `kelvran.persistence.failed`, `kelvran.configpropagation.subscribe_stopped`).
- `kelvran.configpropagation.publish_failed` counter (attributes `kelvran.instance.id`, `kelvran.configpropagation.event_type` = `virtual_key_upsert` / `virtual_key_delete` / `deployment_weight`): a local admin mutation applied but its event never reached Redis, so every other replica is stale until the mutation is re-applied. Recorded next to the existing `configpropagation_publish_failed` log line at all three publish sites; the log line alone was invisible to dashboards and alerts.
- `docs/VERSIONING.md` states what a version number promises: the public surface this policy covers (routes and bodies, the error envelope's `type`/`code`, headers and SSE framing, config keys, CLI flags, OTel names, the container contract, release assets and package paths) and what it does not, the 0.x rules (PATCH never breaks; MINOR breaks only with a `**BREAKING**` entry and an `UPGRADE.md` row, enforced by the release preflight), the 1.0 conditions, deprecation mechanics, and the support window — latest minor all fixes, previous minor security fixes for 90 days — with the current dates. `SECURITY.md`, `SUPPORT.md`, `DEPRECATED.md` and `RELEASE.md` point at it.
- The published image is multi-platform: `ghcr.io/kelvran/gateway` tags are now one index covering `linux/amd64` and `linux/arm64` (the Dockerfile cross-compiles in a builder stage pinned to the build platform, so the arm64 image is a native binary, not an emulated build), signed with `cosign sign --recursive` (index and both manifests; the SBOM and provenance attestations are attached to the index digest), Trivy-scanned per platform, and labelled and annotated with the OCI image labels (`title`, `description`, `source`, `documentation`, `licenses`, `version`, `revision`, `created`, `url`) plus the Artifact Hub labels (`io.artifacthub.package.readme-url|license|category|keywords`) pointing at the new reference card `docs/reference/container-image.md`. Pin the index digest when you deploy; `v0.17.0` and earlier images stay `linux/amd64` only.
- Signed, attested release assets on every `gateway/v*` GitHub Release, built by the new `.github/workflows/release.yml`: `kelvran-gateway_<version>_<os>_<arch>` archives for linux/darwin (amd64, arm64) and windows (amd64) with `LICENSE`, `NOTICE` and `config.example.yaml`; deb/rpm/apk packages for linux amd64 and arm64 that install `/usr/bin/kelvran-gateway`, a hardened systemd unit (`deploy/systemd/kelvran-gateway.service`, never enabled or started by the package) and `/etc/kelvran-gateway/config.example.yaml`; one CycloneDX SBOM per archive and package; `checksums.txt` signed keyless with cosign (`checksums.txt.sigstore.json`) and a SLSA build-provenance attestation over every asset. GoReleaser runs in snapshot mode (`gateway/.goreleaser.yaml`) and the workflow publishes; a release preflight (`scripts/release-preflight.sh`) refuses to build when the changelog or `UPGRADE.md` steps were skipped, and an acceptance job installs the deb on the runner and verifies the unit and the binary before anything is published. The sibling `release-evals.yml` gives `evals/v*` Releases signed sdist/wheel assets. Verification recipe in `RELEASE.md`.
- `GET /v1/models` lists the canonical models the calling virtual key may use: one entry per canonical `model:` name (never per deployment), filtered by the key's `allowed_models` and source-IP allowlist, bearer required (401 envelope without it), no upstream call. The response is one superset document that the OpenAI SDK (`object: list`, `data[].id|object|created|owned_by`), the Anthropic SDK (`data[].type|display_name|created_at`, `first_id`/`last_id`/`has_more` with `limit`/`after_id`/`before_id` pagination) and Claude Code's provider discovery (`data[].id|display_name|description`) all read; each entry also carries Kelvran's `kind` (`chat`/`embedding`). `limit` defaults to every model and is clamped to 1000 (a non-positive or non-integer value is a 400 envelope naming `limit`); `created`/`created_at` are when this instance loaded its catalog, so replicas restarted at different times report different values. The route is registered on the exact path, so `/v1/models/` is a 404 rather than a redirect (Claude Code treats a redirect as a failed provider). A new optional top-level `models:` config section supplies `display_name`/`description` per canonical model (an entry for a model no deployment serves fails to load). Note for Claude Code users: its picker keeps only ids containing `claude` or `anthropic`, and discovery runs only in Anthropic-Messages mode, which Kelvran does not yet serve.
- `gateway -version` prints the build identity on one line and exits 0 (`kelvran-gateway <version> (<commit>, built <date>, <go version>, <os/arch>)`), and every start logs the same fields once as `build_info`. The values are injected at build time through `-ldflags "-X main.version=… -X main.commit=… -X main.date=…"` (`gateway/Dockerfile` now takes `ARG VERSION COMMIT DATE` and builds with `-trimpath -s -w`); a plain `go build`/`go run` identifies itself as `dev (none, built unknown, …)` rather than printing a stale or empty version. Groundwork for release binaries and packages (plan item 4 of `docs/upgrade-research/kelvran-deep-research-round4-discoverability-2026-10-08.md`).

## Changed
- The final telemetry flush at shutdown is bounded to 5 s (`telemetryShutdownTimeout`). It ran under `context.Background()`, so a collector that accepted connections and never answered could hold the process for minutes after the HTTP drain, past systemd's `TimeoutStopSec` and Kubernetes' `terminationGracePeriodSeconds`. The documented worst-case stop is now 30 s + 15 s + 5 s = 50 s; a flush that gives up logs `telemetry_shutdown_failed`.
- **Cache keys now include `tools` and `tool_choice`** (`docs/rfcs/2026-10-08-gateway-cache-key-tools-fingerprint.md`): the L1 and L2 keys fold the canonical JSON of the request's tool definitions and `tool_choice`, and the L3 near-duplicate match gates on it, so identical messages with `tool_choice: "required"` vs `"none"`, or with and without tools, no longer share a cached response at any layer (before, a response that called a tool could be served to a request that offered none — observed while verifying the `tool_choice` fix below). As with every previous key-field addition, every L1/L2 key changes versus an earlier build — for tool-free requests too, because the new field is hashed even when empty — so entries written by an earlier build are unreachable after upgrading (served never, evicted by TTL/LRU): invisible for the default in-process caches, which are empty on every restart anyway; a remote L1 behind the gRPC adapter keeps them until they expire and can be restarted for a clean slate. Nothing to flush by hand.
- Every client-facing error on `/v1/chat/completions` and `/v1/embeddings` is now an OpenAI-shaped JSON envelope, `{"error":{"message","type","param","code"}}` with `Content-Type: application/json`, instead of a `text/plain` body. **Status codes are unchanged** and the message text is the same string the plain body carried (upstream bodies stay redacted to `upstream provider returned status N`), so curl scripts that grep the body still match; the official OpenAI SDKs now populate `.code`/`.type`, and a budget rejection is labelled `type: insufficient_quota` (permanent) rather than looking like a transient `rate_limit_error`. `/healthz` and `/readyz` keep their plain-text bodies. Codes: `invalid_api_key`, `rate_limit_exceeded`, `insufficient_quota`, `concurrency_limit_exceeded`, `deployment_capacity_exceeded`, `model_not_allowed`, `source_ip_not_allowed`, `model_not_found`, `content_policy_violation`, `streaming_not_supported`, `not_an_embedding_model`, `empty_messages`, `invalid_prompt_reference`, `streaming_not_configured`, `embeddings_not_configured`, `upstream_error`, plus `method_not_allowed`, `request_too_large`, `invalid_body`, `invalid_json`, `invalid_request` and `missing_required_parameter` for handler-level validation.

## Fixed
- **Redis budget mode: a client disconnect no longer locks the key at its cap.** The post-response settlement (`budget.Reconcile`, `limiter.ReconcileTPM`) ran under the request's own context; a client that disconnected cancelled it, go-redis failed the `Adjust` fast, and because Redis mode reserves the key's full remaining headroom the reservation stayed debited: every later request got 429 `insufficient_quota` until the window's TTL fired, or for good under a lifetime cap, with Redis perfectly healthy. Settlement now runs under a context that keeps the request's trace values but not its cancellation, bounded to 5 s. A Redis outage during settlement still leaks (see `docs/operations/FAILURE-MODES.md` for the levers); it is now counted under `kelvran.persistence.failed{store_kind=budget}` next to the existing `budget_redis_backend_unavailable op=reconcile` line, which was Warn-only.
- Mid-stream reservation top-ups (TPM and budget) that hit a Redis error still fail open, but are now logged (`ratelimit_tpm_backend_unavailable` / `budget_backend_unavailable` with `op=mid_stream_topup`) and counted under `kelvran.ratelimit.fail_open` / `kelvran.budget.fail_open`, once per stream; both branches were silent. The embeddings rate-limit fail-open line now carries trace ids like its siblings.
- An empty or whitespace-only credential file (`api_key_file`, `access_key_id_file`, `secret_access_key_file`, `session_token_file`, and the Bedrock Guardrails / embed-sim `*_file` fields) is now a read failure: the reload loops keep the last-known-good value and log `credential_reload_read_failed` (or the `bedrockguard_` / `embedsim_` variant) with `credential file is empty`, and at startup the file produces the same warning an unreadable one does. Before, the empty value was stored and logged as a successful `credential_reload_rotated`, which sent every request to that deployment upstream with no credential for up to one reload interval (default 60 s) — a rotation script that truncates before writing, or a volume caught mid-update, could take a deployment down silently.
- Opening a bbolt persistence file (`admin.persist_path`, `budget.persist_path`, `prompt.persist_path`) that another process still holds now fails within one second with `another process holds the file lock` instead of blocking startup forever with no log line and no exit code (bbolt's default lock wait is unbounded). The error wraps bbolt's `ErrTimeout`, which `on_corrupt_store: reset` never treats as corruption, so a merely locked store is never renamed aside.
- Every chat completion now carries the OpenAI envelope: `id`, `object` (`chat.completion` / `chat.completion.chunk`) and `created`, on buffered responses and on every streaming frame. A provider that returns no id — Bedrock's Converse API has no such field — gets a gateway-issued one (`chatcmpl-` + 32 lowercase hex), and streaming frames whose provider sent no `id`/`model` now carry one id for the whole stream plus the canonical `model`; before, Bedrock completions reached clients as `"id": ""` with empty chunk `id`/`model`, and no response of any provider carried `object` or `created` (live defect F7, 2026-10-07/08). Provider-supplied ids (OpenAI, Anthropic, Gemini) pass through unchanged, a cache or `Idempotency-Key` replay returns the id and `created` the completion was stored with, and a response cached before this change is stamped once at replay rather than returned with an empty id. OpenAI streaming chunks keep their upstream snapshot `model`, so buffered and streamed `model` can still differ for that provider (follow-up).
- `/v1/embeddings` now sends the deployment's `upstream_model` on the provider wire, as `/v1/chat/completions` always has. Before, the canonical `model:` name was forwarded unchanged, so an OpenAI-compatible embedding deployment whose `model:` alias differed from its `upstream_model:` (for example `model: fast-embed` → `upstream_model: text-embedding-3-small`) got the provider's "model not found" on every request; deployments where the two names were identical, and every Bedrock Titan deployment (the model is in the InvokeModel URL), were unaffected. The response still reports the canonical name. Found while reviewing the health-probe fix below, which shares the same upstream call (`dataplane.Pipeline.callEmbeddingDeployment`).
- Health probes are shaped for the deployment's kind: a `kind: embedding` deployment is now probed with a one-string embedding request through the same adapter and upstream real `/v1/embeddings` traffic uses (`dataplane.Pipeline.probeDeployment` / `callEmbeddingDeployment`), instead of the 1-token chat completion every deployment received before. With `health_probe` configured, an embedding model rejected the chat-shaped probe, the deployment was marked unhealthy after `unhealthy_threshold` failures and `/readyz` returned `503` for a working embedding deployment (live defect F3, 2026-10-07/08). A provider with no embedding adapter, or a gateway with no embedding upstream, now fails the probe the same way it fails a client request (`ErrEmbeddingsNotConfigured`) rather than being skipped — skipping would have left a broken embedding deployment reading healthy forever because the router defaults a never-probed deployment to healthy. Chat deployments, the router's N-of-M thresholds, the probe timeout and the latency de-weighting are unchanged. `HandleEmbeddings` now calls the extracted `callEmbeddingDeployment` for its upstream step; the extraction kept the error wrapping it had inline, so the messages and status codes clients see from `/v1/embeddings` are unchanged. A deployment of a kind that has no probe shape (none can be configured today) fails its probe with an error naming the kind instead of receiving the chat probe.
- OpenAI's `tool_choice` wire forms are accepted on `/v1/chat/completions`: the bare strings `"auto"`/`"required"`/`"none"` (what every OpenAI SDK sends by default when tools are present) and the function object `{"type":"function","function":{"name":...}}` now decode into the canonical `ToolChoice` (`adapter.ToolChoice.UnmarshalJSON`); before, the string form was a `400 invalid request body` and the object a `502 unknown tool_choice mode ""` (live defect F4, 2026-10-08). Kelvran's canonical `{"mode","tool_name","disable_parallel_tool_use"}` object keeps working; any other shape (Anthropic's `{"type":"auto"}`, OpenAI `allowed_tools`, mixed `mode`+`type`) is a `400` envelope with `code: invalid_tool_choice`, `param: tool_choice`, and a forced tool that `tools[]` does not define is rejected the same way (`adapter.ValidateToolChoice`). `MarshalJSON` is deliberately unchanged (the idempotency fingerprint is `sha256(json.Marshal(req))`). **Operator note:** the response cache keys (L1/L2/L3) do not include `tools` or `tool_choice` (pre-existing), so two requests with identical messages but different `tool_choice` can share a cached response; accepting the OpenAI forms makes that reachable for more clients. Closed the same day by the cache-key change under `## Changed` above.

- **Bedrock structured output on Claude Sonnet 5 is no longer rejected.** The hardcoded Bedrock whitelist that gates `response_format` (`adapter.SupportsStructuredOutput`) was live-verified on 2026-09-10, when Bedrock still rejected `output_config.format` for `claude-sonnet-5`; AWS has since started accepting it (re-verified live 2026-10-08 with a schema-conforming json_schema answer), so the stale entry made every `response_format` request to a Sonnet 5 deployment fail with `ErrStructuredOutputUnsupported` (HTTP 502) whenever no other capable deployment served the same canonical model — including an unmodified OpenAI-compatible client sending `{"type":"json_object"}`, which Kelvran accepts for whitelisted Bedrock Claude models by forwarding the request without any Bedrock-side format field (Converse has no `json_object` equivalent — see `additionalModelRequestFieldsFor`), i.e. accepted but not enforced. Found by routing the real Deep-Research planner through Kelvran. `claude-sonnet-5` is now whitelisted, and the whitelist now matches Claude families at a boundary rather than as a bare substring, so the new entry does not admit Claude Sonnet 5.5 (`claude-sonnet-5-5`), which Bedrock still rejects (live-verified the same day); the whitelist's own comment records every dated verification and the re-check procedure.
- **A local admin mutation can no longer be silently dropped as "stale" — the root cause of the CI-only `TestConcurrentDeleteVirtualKeyRequestsForSameNameNeverBothSucceed` failures first disclosed on 2026-09-22.** `UpsertVirtualKey`, `DeleteVirtualKey`, `RotateVirtualKey` and `UpdateDeploymentWeight` read the wall clock *before* taking the mutation lock, so two concurrent local calls whose clock reads and lock acquisitions inverted made the loser look older than the version already recorded, and the last-writer-wins guard — which exists for late-arriving *remote* events and is correct for them — returned success without applying or publishing anything: two `204`s and two audit entries for one deletion, or a later local upsert / weight update discarded while its caller was told it succeeded. A local mutation now derives its version under the lock and strictly past the newest version this replica has already applied for the same target (`internal/gateway/dataplane/mutation_version.go`), so it can never be stale against the replica's own view, whatever the clock does; the remote-apply paths (`Apply*FromEvent`) still honour the originating replica's own version. Because two lagging replicas can now legitimately publish the *same* token for the same target, the last-writer-wins guard additionally breaks equal-token ties deterministically by the originating instance ID (the same token from the same origin remains the idempotent re-apply that canary promotion relies on), so every replica converges on one value instead of two replicas swapping values. Consequence for operators: the event envelope's `published_at_unix_nano` remains a last-writer-wins ordering token but may now be one nanosecond past a previously applied version rather than the exact wall-clock time — treat it as an ordering token, not as a timestamp to display or window on. Covered by ten deterministic tests: five that inject a clock reading backwards between two sequential local calls (delete twice, later upsert, rotate-then-delete, upsert-then-rotate, later weight update), and five cross-replica tests that simulate several replicas in one process (a local delete and a local weight update bumping past a far-future remote version with the published token checked, equal-token convergence with bystanders receiving in both orders, and the tie-break rules).

## Security
- Transport-level upstream failures (a refused connection, a timeout, a mid-stream decode error) no longer reach clients verbatim. The message carried the deployment's internal `base_url` and `host:port` (`… calling upstream "http://10.0.0.5:8000": … dial tcp 10.0.0.5:8000: connect: connection refused`); every upstream-call failure now wraps `dataplane.ErrUpstreamCallFailed` and, when nothing more specific applies (the 502 `upstream_error` default), the client sees `upstream call failed for model "<model>"`; status, `type` and `code` are unchanged, provider statuses keep `upstream provider returned status N`, and sentinels raised inside the upstream stage (streaming not supported, embeddings not configured) keep their own text and status. Two other messages stop naming the operator's deployment: the 503 `deployment_capacity_exceeded` message is now `deployment at capacity (<reason>)`, and the 400 `not_an_embedding_model` message echoes the requested model instead of the deployment name. The full text still reaches the operator in the `chat_completion` / `embeddings` log line.
