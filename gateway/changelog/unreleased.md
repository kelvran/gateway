## Added

- Bedrock Guardrails (`guardrails.bedrock_guardrails`) and the EmbedSim Bedrock embedder (`guardrails.embed_sim`) now support the same file-based credential hot-reload convention already available for deployments: optional `access_key_id_file`/`secret_access_key_file`/`session_token_file` fields, re-read on the same `credential_reload.interval_seconds` tick as deployment credentials. Previously, either subsystem's AWS credential was resolved once at startup and held for the life of the process — an AWS STS session token expiring, or a Kubernetes projected Secret volume rotation, required a full gateway restart to pick up. New shared `internal/credentialstate` package backs all three now-hot-reloadable subsystems (deployments, Bedrock Guardrails, EmbedSim) with the identical lock-free atomic-swap mechanism. Live-verified end to end against real AWS: rotating the credential file to a bad value produced a real `403` from AWS Bedrock on the very next reload tick, and restoring it recovered cleanly — not just a unit-level proof.
- Guardrail structured logs (`guardrail_verdict_blocked`/`guardrail_verdict_warn` from the engine, and `guardrail_blocked_precall`/`guardrail_blocked_postcall`/`guardrail_blocked_postcall_streaming_audit_only` from the dataplane, buffered and streaming both) now include a `finding_detectors` field alongside the existing `finding_count` — the distinct detector name(s) that actually fired (e.g. `bedrock_guardrails_prompt_attack` vs. this package's own regex-based `promptinjection`), not just an aggregate count. `guardrail.Finding.Detector` was already populated correctly by every detector; this closes the gap where every log call site discarded that detail down to a bare integer, found via a live end-to-end verification pass against real Bedrock traffic.

## Fixed

- Two client request-shape mistakes previously reached a real (upstream-error-status) or misleading (default) `502 Bad Gateway` response instead of an early `400 Bad Request`: (1) naming a model with no configured deployment at all — a pure in-memory routing-table lookup failure that never touches upstream either way, so the 502 default was always wrong for it, not just imprecise; (2) a request resolving to zero messages (`messages: []` with no `prompt_id` set, or a `prompt_id` resolving to an empty template) — previously unvalidated at all, so it reached a REAL, wasted upstream call every time, which then rejected it with the provider's own 400, surfaced to the client as a misleading 502. Both now return 400 immediately; the empty-messages case no longer makes any upstream call. Found via a live end-to-end verification pass against real Bedrock traffic.
- The client-facing chat completion/embedding response's `model` field always echoed the client's originally-requested model, even when a `fallback_chains` hop genuinely served the response with a different model — a client had no way to tell it had been served a different (here, possibly more expensive or less capable) model via fallback. Server-side telemetry (the `gen_ai.response.model` OTel attribute) has reported the true serving model since an earlier fix; this closes the same gap for the response body itself, and for a cached fallback response replayed to a later identical request (buffered and streaming both). Unchanged in every other case — the requested and served model are already identical unless a genuine cross-model fallback occurred.
- The streaming near-duplicate-collision counter (`kelvran.streaming.near_duplicate_collision`) fired on concurrent identical requests that hit an already-warm L1/L2/L3 cache — a false signal, since a cache hit never reaches upstream regardless of this counter, directly undermining the metric's own purpose of measuring genuinely upstream-bound duplication risk. Moved the observation point to after both cache checks miss, mirroring the buffered path's own `runMissPath` scoping.
- `-validate` never actually caught a malformed `allowed_source_cidrs` CIDR string — it only calls `controlplane.Load`, never `cmd/gateway.buildPipeline` (where the real syntax check lived), so a config that would crash the process on real startup could still report "config is valid". `Load` now performs the same `net.ParseCIDR` check itself.

## Security

- A virtual key's `allowed_source_cidrs`, `allowed_models`, or `allowed_regions` restriction was silently, completely disabled if authored as a YAML list (e.g. `allowed_source_cidrs:\n  - "::1/128"`) instead of the required mapping-of-`true` shape — this parser has no YAML list support at all, and the list-shaped line garbled into a value that failed a type check and was silently dropped, with zero error at load, validate, or (for `allowed_source_cidrs`) even real startup time. `Load` now rejects any non-boolean value under these three fields with a loud, named error. Found via a live end-to-end dry run against a real running gateway process — a real IPv4 request to a key restricted to `::1/128` returned `200` instead of the expected `403`. If your own config sets any of these three fields, run `gateway -validate` once against it to confirm it wasn't silently disabled by this shape.
- `resolveClientIP` now fails closed (denies) on an ambiguous, unbracketed IPv6-with-port `RemoteAddr` string (e.g. `"::1:1234"`) instead of passing it through to be misparsed by `net.ParseIP` as a different, valid-looking IPv6 address and checked against the CIDR allowlist under that substituted identity. A real `net/http` `RemoteAddr` for IPv6 is always bracketed, so this never fires against real production traffic — it only closes a theoretical substitution risk for a malformed/hand-constructed input.
- A virtual key's `allowed_regions` (data-residency) restriction could be silently bypassed. Two distinct gaps, both closed: (1) the "legacy" chat-completion fallback path (taken whenever the first-picked deployment has no `fallback_chains` configured — the default for every deployment today) picked its retry target with no region or capability filter at all, unlike the first pick and the explicit `fallback_chains` hop — an ordinary transient upstream error (5xx/timeout/throttle), no attacker action needed, could land a region-restricted key on an out-of-region deployment; now skips an ineligible fallback target entirely rather than selecting it, propagating the original error instead of silently violating the constraint. (2) `HandleEmbeddings`' sole deployment pick never checked `allowed_regions` at all — every embeddings request from a region-restricted key could hit an out-of-region deployment unconditionally, with no error required to trigger it; now best-effort rerouted to an in-region deployment when one exists in the pool.
- `guardrails.category_overrides` had the same "silently drop a config entry whose value doesn't match the expected type" gap as the allowlist fields above, reachable via a different mechanism: category/action values here are colon-free, so the earlier colon-garbling path doesn't apply, but an operator over-nesting the value (`category:\n  action: "block"` instead of `category: "block"` — a plausible mistake, since every sibling section in the same `guardrails:` block legitimately uses nested maps) silently dropped the override with zero error, reverting that category to its coded default. `Load` now rejects a non-string value under this field with a loud, named error.
- A virtual key's `allowed_models` restriction could be silently bypassed by an explicit `fallback_chains` hop naming a different model than the one first requested — a real, already-supported configuration shape (a cheap model falling back to a more capable/expensive one on error), not a strawman: `AllowedModels` was checked once, against the client's originally-requested model, at the top of the request — never re-checked against the fallback target's own canonical model. A key restricted to `gpt-4o-mini` could be served by a `fallback_chains` target running `gpt-4o` with zero enforcement. `attemptFallbackChain` now checks the target's own model against the key's `AllowedModels` immediately before every hop, in both the buffered and streaming paths, skipping a disallowed target exactly like an unhealthy, rate-limited, or out-of-region one. The legacy (no `fallback_chains` configured) fallback branch and `HandleEmbeddings` were independently confirmed NOT to have this gap — both are structurally scoped to the originally-requested model's own deployment pool and can never cross model boundaries.
- Changing `guardrails.category_overrides` without also manually bumping `guardrails.policy_version` left the resulting `guardrail.Engine`'s cache-differentiating version string unchanged — `policy_version` and `category_overrides` are two entirely independent config fields with no code tying a change in one to the other. `guardrail.Engine`'s version string now automatically incorporates a fingerprint of the effective policy's own enforcement state, so ANY resulting change forces a cache-key change, with no operator action required — `policy_version` itself is unchanged and still needed for a detector CODE change (which no config-derived fingerprint can observe), per its own existing convention. **Corrected 2026-09-28, live-verification pass**: not an active-exploit fix today — a category_overrides change requires a full gateway restart, and today's only real cache implementation (`internal/cache/inprocess`) is wiped clean by that same restart regardless, so no stale entry actually survives to be served under the new policy right now. This closes a latent gap that becomes live-reachable the moment the still-design-only Redis-backed L1/L2/L3 cache (`docs/rfcs/2026-09-11-gateway-redis-backed-cache-design.md`) ships — forward-looking hardening, kept because it's a genuine, zero-cost correctness improvement to `Version()`'s own contract regardless. Scope limit: the fingerprint covers `category_overrides` only, not the active detector set — enabling/disabling `guardrails.bedrock_guardrails`/`guardrails.embed_sim` still requires a manual `policy_version` bump, same as before this fix.
