## Added
- The canonical request carries the caller's thinking configuration: `adapter.ChatRequest.Thinking` (`type` `enabled`/`adaptive`/`disabled`, `budget_tokens`), set only by the Anthropic Messages ingress (not yet built; the field is unreachable from `/v1/chat/completions`). The `anthropic` adapter forwards it verbatim, with Kelvran's non-strict `block_binding` still added on the models that run the prefix check; the `bedrock` adapter forwards it through `additionalModelRequestFields` when the served model's Claude generation accepts the type — live-probed on 2026-10-10: 5.x takes `adaptive`, 4.6 both, 4.5 `enabled` (sonnet-5, sonnet-5-5, fable-5-1, haiku-5-5, sonnet-4-6 and haiku-4-5 proven; every Opus id and sonnet-4-5 placed by their generation, the probe being IAM-denied for Opus) — omits it when the generation is known to reject it, and forwards it to any family outside the table so the upstream's own answer is what the caller sees. Every omission, and a configuration sent to a provider with no thinking support, is a `thinking_dropped` log line naming the deployment, model, `thinking_type` and reason. The `Idempotency-Key` fingerprint folds the configuration in when one is set (a request without one fingerprints exactly as before), so a reused key with a body that differs only in `thinking` is the `422` mismatch, not a replay. Item 11 slice S4.
- The canonical chat response carries the provider's native stop reason beside the canonical `finish_reason`: `stop_reason` and, for Anthropic, the matched `stop_sequence`, on `/v1/chat/completions` responses and on the streaming chunk that sets `finish_reason`, for `anthropic` and `bedrock` deployments (omitted elsewhere; `finish_reason` is unchanged). They round-trip through the cache and the streaming replay. The first canonical-schema gap fill for the Anthropic Messages ingress (item 11 slice S3; the fields RFC-1 §1's `EncodeResponse` reads): an Anthropic-shaped response can then be rendered without guessing the stop reason back from `stop`.

## Changed
- Every cache key changes once on upgrade: the thinking configuration is folded into the L1 and L2 keys and gated in the L3 check, so entries written by an earlier version become unreachable (a one-time cold cache, exactly as the `tools` fold in `gateway/v0.18.0` was). Nothing a `/v1/chat/completions` client sends can set the new field, so no two of today's requests are separated by it; the fold exists so the ingress, when it lands, can never be served a reply made under a different thinking configuration. One of three folds the item 11 plan schedules before the ingress ships (S4 thinking, S5 sampling, S9b passthrough); a release carrying all three still costs one cold cache.
- Two error statuses that were the `502` `upstream_error` default now say what happened (plan gate G16, decided 2026-10-10 together with RFC-1; a MINOR change under `docs/VERSIONING.md` §3: statuses are public surface, and nothing a documented client does stops working — the SDKs still raise an exception, the only `Retry-After` promise in §2 is on 429, and `type`/`code` gain values without losing any): `response_format` on a model pool with no deployment able to enforce it is `400` `invalid_request_error` / `response_format_unsupported` with `param` `response_format`; an `Idempotency-Key` reused within its window with a different body is `422` `invalid_request_error` / `idempotency_key_reused` with `param` `Idempotency-Key`. Neither carries `Retry-After` or bumps the key's retry backoff any more, and the decision event records `OUTCOME_INVALID_REQUEST` instead of `OUTCOME_UPSTREAM_ERROR`. Both are decided before any upstream call, as before.
