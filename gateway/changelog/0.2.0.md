# gateway v0.2.0 — 2026-09-09

Entries below are frozen as of this release — see `unreleased.md` for anything added since. [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) categories; [SemVer](https://semver.org/) — load-bearing for the Go module path/tag.

## Added

- Per-deployment concurrency + rate ceiling: a new deployment-scoped `ratelimit.ConcurrencyLimiter`/`ratelimit.KeyLimiter` pair (keyed by `DeploymentConfig.Name`, reused as-is, not new types), acquired/released PER HOP (not per request) at every real call site — hop 1, every `attemptFallbackChain` hop, and the pre-existing single-fallback fallthrough — via new `callDeploymentWithCapacityCheck`/`streamDeploymentWithCapacityCheck`. A new `DeploymentCapacityError` maps to a client-facing 503, kept separate from the existing per-key 429 bucket. New `rate_limit:` schema on `DeploymentConfig` (burst/refill, TPM fields parsed-but-deferred, `max_concurrent_requests`). `probeOneDeployment`/`ProbeDeployments` are deliberately excluded, so a synthetic health probe can't be capacity-rejected into false-unhealthy. Closes a real gap the routing-chaos regression corpus documented (no per-deployment cap existed, only per-key).
- Router-health real-traffic filter/volume-floor primitives, built but deliberately left unwired: `dataplane.isCandidateHealthFailure` (a status-class/origin filter — real 5xx or local/connection-level failure counts, ordinary 4xx and self-throttling rejections never do) and `router.SampleWindow` (a per-deployment rolling candidate-outcome counter against a configurable minimum volume, deliberately clock-free). Zero call sites wired to either — both exist purely as tested, ready building blocks, gated on real production traffic volume Kelvran doesn't have yet to calibrate against.
- PerModel-for-TPM direct-path extension: extends the existing RPM `PerModel` per-model rate-limit override to the TPM dimension, for the direct (non-fallback) path only. `ratelimit.KeyLimiter.ReserveTPM`/`ReconcileTPM` both gain a `model` parameter, resolving to a per-model TPM bucket first (mirroring `AllowForModel`'s existing pattern) before falling back to the key's own default TPM bucket. New optional `rate_limit.per_model.<model>.tpm_capacity`/`tpm_refill_per_second` config fields (must be set together or neither) on both the static YAML surface and the live Admin API. TPM stays scoped out of `checkFallbackTargetRateLimit` — a fallback-hop's own TPM cost still isn't re-targeted mid-chain, matching the already-recorded TPM-fallback-hop deferral.
- New `OUTCOME_DEPLOYMENT_CAPACITY` value (9) on `api/gatewayevents/v1`'s `Outcome` enum — additive, `buf breaking` clean — replacing the generic `OUTCOME_UPSTREAM_ERROR` bucket a deployment-capacity rejection previously fell into. `isRetryStormEligible` was updated in the same change to keep `DeploymentCapacityError` Retry-After-eligible under the new value (it already was under the old generic one).
- Real `bedrock` adapter (buffered/non-streaming only), per `docs/rfcs/2026-09-04-bedrock-adapter.md`, targeting Amazon Bedrock Runtime's provider-agnostic Converse API — a deliberate scope expansion explicitly requested by the user, unlike Gemini's gap-closing pass (`PRD.md`'s v1 line does not name Bedrock). The first adapter needing a genuine `Deployment`/config-schema change: AWS SigV4 request signing has no single bearer-secret shape, so `DeploymentConfig` gains `AccessKeyIDEnv`/`SecretAccessKeyEnv`/`SessionTokenEnv` (env var names, never raw values, matching `APIKeyEnv`'s existing convention) and a plain, non-secret `Region` field, with provider-conditional validation in `Load()` (`api_key_env` required unless `provider == "bedrock"`; the AWS credential fields required only when it is). `setUpstreamAuthHeaders` widened to take the request body (SigV4 signs over a hash of it) and now returns an `error` — the first provider whose auth-header-setting branch can genuinely fail — via a new `case "bedrock"` calling `aws-sdk-go-v2/aws/signer/v4`'s real `Signer.SignHTTP`, the first AWS SDK dependency this project has taken on (deliberately the small, focused signer package, not the full service-client SDK). A real, load-bearing correction found only by reading `aws-sdk-go-v2`'s own current source directly: the SigV4 service-signing name for Bedrock Runtime is `"amazonbedrockfrontendservice"`, confirmed via `service/bedrockruntime/endpoints.go`'s unconditional fallback (zero per-region overrides exist anywhere in that file's endpoint-resolution table) — not `"bedrock"`, a plausible-sounding but wrong value the initial grounding research recommended. Genuinely simpler than Gemini in one real way: a Bedrock `toolResult` block correlates purely by `toolUseId`, with no required `name` field at all, so no name-resolution-from-message-history hazard exists here the way it does for Gemini's `functionResponse`. Real `stopReason` mapping (`end_turn`/`stop_sequence`→`"stop"`, `tool_use`→`"tool_calls"`, `max_tokens`→`"length"`, `guardrail_intervened`/`content_filtered`→`"content_filter"`, `malformed_tool_use`/`malformed_model_output`→ a real typed error, never a fake successful `Choice`). Converse's response has no native response-ID field, unlike every other provider — `ChatResponse.ID` is left empty, an honest absence, never fabricated. Streaming (`ConverseStream`) was deferred to a follow-on RFC at this point and has since shipped — see the dedicated entry below. New end-to-end HTTP integration tests assert a real `AWS4-HMAC-SHA256`-prefixed `Authorization` header and `X-Amz-Date` genuinely reached the upstream call, plus a real two-turn tool-call round trip.
- Real Bedrock `ConverseStream` streaming support, per `docs/rfcs/2026-09-04-bedrock-converse-stream.md` — closes the follow-on deferred by the buffered Bedrock adapter above. ConverseStream's real wire format is AWS's binary `application/vnd.amazon.eventstream` framing, not SSE, so it is decoded by a genuinely separate path rather than a retrofit of `internal/streaming`'s SSE-based `StreamDecoder` contract: `bedrock.StreamDecoder` is a concrete, non-interface type decoding `eventstream.Message` directly (confirmed real event sequence via `aws-sdk-go-v2`'s own `deserializers.go`: `messageStart` → `[contentBlockStart → contentBlockDelta* → contentBlockStop]*` → `messageStop` → `metadata`), and is deliberately stateless (zero fields) — unlike Anthropic's stateful block-tracking decoder, every Bedrock event is self-describing. `dataplane.go`'s `streamDeployment` special-cases `dep.Provider == "bedrock"` at its own top and dispatches to a new sibling, `streamDeploymentBedrock`, which drives `aws-sdk-go-v2/aws/protocol/eventstream`'s real `Decoder.Decode(io.Reader, payloadBuf []byte)` directly in a loop until `io.EOF`, reusing the returned `payloadBuf` backing array per that package's own documented-safe reuse contract. A genuine, load-bearing correction to this feature's own initial task framing (not just the earlier research): Bedrock's streaming URL is a **path-segment** swap (`/converse` → `/converse-stream`, confirmed against `serializers.go`), not a colon-suffix swap the way Gemini's is — `streamUpstreamURL` (in `dataplane.go`) grew a `case "bedrock"` alongside its existing Gemini case, and `NewHTTPUpstreamStreamCaller`'s `Accept` header became provider-conditional (`application/vnd.amazon.eventstream` for Bedrock, `text/event-stream` otherwise). A second real, load-bearing correction: Bedrock's streaming tool-call arguments (`ToolUseBlockDelta.Input *string`) arrive as an accumulating JSON-string *fragment* across chunks, the same contract as OpenAI's/openaicompat's, never a complete object per chunk the way Gemini's streaming is — despite Bedrock's *buffered* tool-call arguments being an already-parsed object. Bedrock's `toolResult`/`metadata` events also confirmed genuinely simpler than every other provider in one way: `metadata` (carrying usage) is the true last event, arriving *after* `messageStop`, so `Decode` never returns a `done` signal at all — the binary decode loop relies purely on `eventstream.Decoder.Decode` returning `io.EOF`, the same pattern Gemini's SSE-based decoder already proved correct. A pure, behavior-identical refactor extracted `streamDeployment`'s provider-agnostic tail (usage-fallback warning, response building, audit-only post-call guardrail check, done-sentinel write) into a shared `finishStreamedResponse` helper, called by both the SSE path and the new binary path — confirmed pure since every pre-existing streaming test passed with zero assertion changes. Two existing tests whose only non-streaming-capable example was `"bedrock"` (already updated once before, when Gemini shipped real streaming) needed a genuinely new, deliberately non-streaming stub fixture (`nonStreamingAdapter`) — every adapter actually registered in `cmd/gateway/main.go` now streams, so `dataplane.ErrStreamingNotSupported`'s generic code path currently has no real production example left, only this test-only one; the equivalent HTTP-level integration test was removed outright rather than faked, since `buildPipeline`'s adapter registry is not test-injectable and modifying production wiring just to keep one stale test alive was rejected. New end-to-end HTTP integration test (`TestIntegrationStreamingRequestSucceedsBedrock`) and two dataplane-level tests build genuinely wire-accurate binary fixtures via `eventstream.Encoder` (the real encode-side counterpart to the decoder under test), including one proving an AWS-side exception frame mid-stream surfaces as a real, typed error rather than truncating silently.
- Real `gemini` adapter (non-streaming + streaming), per `docs/rfcs/2026-09-04-gemini-adapter.md` — closes the last stub adapter `PRD.md`'s v1 scope line names explicitly ("a unified request/response schema across OpenAI, Anthropic, Gemini, and OpenAI-compatible self-hosted runtimes"). A genuine-translation adapter like `anthropic` (not a near-verbatim copy like `openai`/`openaicompat`): Gemini's real API has no "system"/"tool" role (a `role:"system"` message is hoisted into `systemInstruction`; a `role:"tool"` result becomes a `role:"user"` content carrying a `functionResponse` part), and `functionResponse.name` is required but the canonical `role:"tool"` message only carries `ToolCallID` — `ToProvider` resolves the originating call's `Name` from message history before it can honestly build the part, failing loudly (not silently) if no match exists. A real 22-value `finishReason` enum (confirmed against Google's live API discovery document, not assumed) maps onto the canonical vocabulary; the 5 values indicating the model's own tool-call machinery broke (`MALFORMED_FUNCTION_CALL`, `UNEXPECTED_TOOL_CALL`, `TOO_MANY_TOOL_CALLS`, `MISSING_THOUGHT_SIGNATURE`, `MALFORMED_RESPONSE`) surface as a typed error rather than a fake successful `Choice`. Streaming reuses the exact same `Response` schema as the buffered path (confirmed: Gemini has no separate stream-chunk shape) and has no terminal sentinel — `Decode` always returns `done=false`; the dataplane's existing `io.EOF`-driven loop already handles this with zero changes. One real, cross-cutting architectural addition no prior adapter needed: Gemini's streaming endpoint is a genuinely different URL (`:streamGenerateContent?alt=sse`) from the buffered one (`:generateContent`), unlike every other provider's single-URL-plus-body-flag convention — a new `streamUpstreamURL` function in `dataplane.go` derives it from the configured (buffered) `base_url` at call time, with zero config-schema change and zero effect on any other provider. New `case "gemini"` in `setUpstreamAuthHeaders` (`x-goog-api-key` header) and a new `"gemini"` entry in `responseUnmarshalers`. Independently re-verified the single highest-risk claim (whether `FunctionCall`/`FunctionResponse` carry a real `id` field) directly against Google's live API discovery document before writing the RFC — found both do (optional, but real), an improvement over the initial grounding research's more conservative "positional matching only" recommendation. New end-to-end HTTP integration tests, including a real two-turn tool-call round trip proving the `functionResponse.name`-resolution hazard is handled correctly through the full HTTP pipeline, not just the adapter in isolation. `bedrock` remains a stub, deliberately untouched — not named in `PRD.md`'s v1 line the way Gemini is, so not silently bundled into this pass.
- Real `openaicompat` adapter (non-streaming + streaming), per `docs/rfcs/2026-09-04-openaicompat-adapter.md`, for generic self-hosted OpenAI-compatible inference runtimes (vLLM, Ollama, TGI, llama.cpp, LocalAI) — previously a full stub where both `ToProvider`/`FromProvider` unconditionally errored. Implemented as a near-verbatim copy of the working `openai` adapter's types and logic (duplicated, not shared via a common package, matching this codebase's existing "every adapter package is self-contained" convention) — grounded via research confirming the SSE framing, `[DONE]` sentinel, `stream_options.include_usage` mechanics, and tool-call JSON shape are uniformly OpenAI-compatible across every self-hosted runtime surveyed, checked against each runtime's real source code, not just its (often silent) documentation. One required wiring addition outside the adapter package: a `"openaicompat"` entry in `dataplane.go`'s `responseUnmarshalers` map (previously the only gap — `cmd/gateway/main.go`'s adapter registry and the streaming path's `StreamingAdapter` type-assertion were both already fully generic and required zero changes). Real, sourced content-level compatibility differences exist across self-hosted runtimes (vLLM can emit `finish_reason` values like `"abort"`/`"repetition"`; TGI never emits `"tool_calls"` as `finish_reason` even for a genuine tool-call response) — already handled correctly by the existing design with zero extra code (`FinishReason` is a bare string, not a closed enum; unknown response fields are ignored by default), documented explicitly on `Choice`'s doc comment so future callers never gate tool-call detection on `finish_reason`'s value. New end-to-end HTTP integration tests (`TestIntegrationOpenAICompatRequestSucceeds`, `TestIntegrationStreamingRequestSucceedsOpenAICompat`) prove the real wiring, not just the adapter's own unit tests in isolation.
- Weighted deployment routing, per `docs/rfcs/2026-09-04-weighted-routing.md`: a new `internal/router` package replaces `dataplane.Pipeline`'s inline atomic-counter round-robin (`nextDeployment`) with smooth weighted round-robin — the LVS/IPVS `wrr.c` cursor algorithm, real production code, not invented here. This closes the "weighted" half of `PRD.md`'s v1 routing scope line (`"static + weighted routing; a single fallback chain"`) — the one part of that line not yet built; the existing single-fallback mechanism is unchanged. New `weight` key on a `deployments:` entry in `config.yaml` (`DeploymentConfig.Weight`, parsed and validated non-negative in `controlplane.Load`); zero/unset means the default weight of 1. `nextDeployment`'s signature is unchanged (`(Deployment, bool)`) — it is now a thin wrapper delegating to `router.Router.Select`, so `HandleChatCompletion`/`streamDeploymentWithFallback` needed zero call-site changes. Equal weights (including the unset default) provably degrade to byte-identical the old round-robin's exact selection sequence — hand-traced in the RFC and proven in `internal/router/router_test.go`'s `TestSelectDegradesToRoundRobinForEqualWeights`/`TestSelectDegradesToRoundRobinForExplicitEqualWeights`, which is also why every pre-existing dataplane test's exact call-count/order assertions (e.g. `TestHandleChatCompletionFallsBackOnUpstreamError`) needed zero changes to their expectations. Deliberately **not** usage/latency/cost-based routing signals, **not** a circuit breaker or consecutive-failure/cooldown health tracking, and **not** model-*group* fallback chains — none of these are named in `PRD.md`'s v1 allowlist; a grounding research pass (LiteLLM/Portkey/Kong/Envoy precedent, plus Envoy/Hystrix/resilience4j circuit-breaker designs) confirmed real, well-understood designs exist for all three, but this session's own narrowing discipline (mirroring Cache L2/L3-lite/Guardrails) scoped this pass to exactly what PRD.md commits to. `gateway/ARCHITECTURE.md`'s Request Lifecycle section also had its stale "circuit-breaker" mention removed — it never matched the Package Layout section's own, earlier (2026-09-04) doc-honesty correction and doesn't match this feature's actual scope either.
- `api/gatewayevents/v1` enrichment, per `docs/rfcs/2026-09-03-gatewayevents-decision-enrichment.md`: `GatewayDecisionEvent` gains 5 new fields (7–11) closing the exact gap the original contract RFC named and deferred — `rate_limit_fail_open` (bool: the rate limiter's backend errored and the request was let through anyway), `fallback_happened`/`fallback_from_deployment`/`fallback_reason` (whether a request fell back to a second deployment, from which one, and why), and `budget_spent_usd` (the key's real cumulative spend at the moment the budget check ran, decimal-as-string, populated even on a `BUDGET_EXCEEDED` rejection). Purely additive proto change (`buf breaking` confirmed clean under the repo's `FILE` category) — no `UPGRADE.md` entry. `checkRateLimit` widens its return to `(ok, failedOpen bool)`; a new unexported `fallbackInfo` struct threads fallback detail through both the buffered inline fallback block and `streamDeploymentWithFallback`'s return; a new `budget.Tracker.SpentUSD` getter is called at the `budget.Allow` call site (never inside `finalize`) so the captured spend reflects decision-time, not finalize-time.
- Guardrails v1, per `docs/rfcs/2026-09-03-guardrails-pii-regex-classifier.md`: a new `internal/guardrail` package (pure-Go, stdlib-only, zero new `go.mod` entries) runs pre-call and post-call content checks — regex/checksum PII+secrets detection (email, phone, US SSN, IBAN with a real ISO 7064 mod-97 checksum, credit card with a real Luhn checksum, IPv4/IPv6, API-key/secret prefixes gated by Shannon entropy) plus a keyword/hidden-Unicode prompt-injection heuristic. Category-tiered fail-open/fail-closed policy on both the detection and detector-error axes (`credential`/`financial_id`/`government_id` block; `contact_info`/`network_id`/`prompt_injection` warn-with-logging) — never inherited from the rate limiter's own fail-open default. Pre-call runs identically on the buffered and streaming paths, after L1/L2/L3 cache lookup and before the router; post-call is enforcement-capable on the buffered path but **audit-only on streaming** (every chunk is already flushed to the client before a complete response exists to check — a named, accepted residual risk, not silently dropped). A guardrail policy/detector version change forces every existing cache entry to a real miss: `cache.Key`/`cache.NormalizedKey` gained a `guardrailPolicyVersion` hash input (L1/L2 have no metadata envelope to attach a stored field to), and `LexicalCandidate`/`LexicalCache.Put` gained an explicit, checked `GuardrailPolicyVersion` field (L3). New `OUTCOME_GUARDRAIL_BLOCKED` value on `api/gatewayevents/v1`'s `Outcome` enum (purely additive, `buf breaking` confirmed clean) so a guardrail rejection is never misclassified as an upstream error. New optional `guardrails:` config section (`policy_version`, `category_overrides`); a `Config.Guardrails` dependency is hard-required on `dataplane.Pipeline`, never optional. Deliberately **not** NER, **not** an ML/third-party moderation model, **not** CSAM/CBRN detection in this pass — no mature, no-cgo, no-model-file Go NER library exists today, the same class of gap Cache L3-lite already found and narrowed around for real embeddings.
- Added an opt-in `CacheControl{TTL, Key}` marker on `Message`/`ContentPart` in the canonical gateway schema, closing a gap where three of four providers' prompt-caching mechanisms had no field to carry it. Anthropic's adapter restructured `system` from a plain string into `[]SystemBlock` so `cache_control` can attach per-block; Bedrock's adapter gained a standalone `CachePoint` block appended after the content to cache (its own checkpoint shape, distinct from Anthropic's block property); OpenAI's adapter gained a top-level `prompt_cache_key`, populated only from the first caller-supplied `CacheControl.Key` since OpenAI's own caching is automatic and the key only affects routing. Gemini's adapter is left untouched, confirmed by a byte-identical-output test to have no request-level field for either of its caching mechanisms.
- Extended `CacheControl` to `ToolDef` so tool definitions themselves, not just messages/system, can opt into provider-side caching on Anthropic and Bedrock. Anthropic wires `cache_control` as an inline sibling key on the tool object (matching its content-block placement), while Bedrock emits `cachePoint` as a standalone `tools[]` array element rather than an inline field, since AWS's `Tool` union type allows exactly one of `cachePoint`/`systemTool`/`toolSpec` per element — the two providers diverge here even though they converged at the message level. OpenAI, openaicompat, and Gemini remain excluded, re-verified specifically for tool definitions rather than assumed to inherit the message-level finding.
- Virtual keys can now give one specific model its own RPM bucket via `rate_limit.per_model.<model>.{burst,refill_per_second}` (or the Admin API's matching `per_model` field on `POST /admin/virtual_keys/{name}`) — the consumer x model dimension of Kong-style multi-dimensional rate-limit matching. `KeyLimiter.AllowForModel` checks a model's override bucket instead of, never in addition to, the key's default bucket, so keys with no overrides behave byte-identically to before. Enforced in both in-memory and Redis mode; the Redis-mode key uses a NUL-byte-tagged separator (`keyID + "\x00model=" + model`) to avoid the collision hazard of naively `:`-joining two variable-length strings. Provider/header/path matching remain scoped-out future work.
- Added a tokens-per-minute (TPM) rate-limit dimension alongside the existing request-count RPM limit, configurable via `rate_limit.tpm_capacity`/`tpm_refill_per_second` (YAML and Admin API). Since real token usage is only known after the upstream call completes and no tokenizer exists in this codebase, TPM is deliberately retrospective: `KeyLimiter.AllowTPM` checks a per-key balance from past usage only, and `RecordTokens` debits it (allowed to overdraft below zero) once `finalize` reads real usage, gated on the same `billable` flag that prevents double-counting on cache hits/coalesced requests. Scoped to in-memory rate-limit mode only in v1; a startup warning fires if TPM is configured together with Redis mode.
- Added active/synthetic health-probing to the router: `dataplane.Pipeline.RunHealthProbeLoop`/`ProbeDeployments` issue a lightweight synthetic chat-completion request to every deployment on a timer (default 300s, configurable via the new `health_probe:` YAML section), while `router.Router.ReportProbeResult`/`IsHealthy` track each deployment's health via N-of-M consecutive-probe counts (3 consecutive failures to exclude, 2 to re-include, by default) so `Select` skips unhealthy deployments — failing open if every deployment in a model's group is unhealthy at once. Only the traffic-independent active-probe half of health-based routing ships now, per Kong/Envoy/LiteLLM precedent that draws a hard line between it and traffic-derived statistical detection; the latter (Envoy-style outlier detection, LiteLLM-style `allowed_fails` cooldown) stays deferred since Kelvran has no production traffic yet to calibrate a volume floor against.
- Added error-classified, multi-hop fallback chains: a deployment can now configure `fallback_chains` with separate, ordered target-deployment lists per error class — `content_policy`, `context_window_exceeded`, or `generic` — classified via a new `dataplane.UpstreamHTTPError` type using keyword-matching on the upstream response body, since neither Anthropic's nor OpenAI's own docs expose a structured error code for these two conditions. Both the buffered (`runMissPath`) and streaming (`streamDeploymentWithFallback`) paths share the new `attemptFallbackChain` walking logic, with streaming re-checking "no chunk sent yet" before every hop, not just the first. A deployment with no `fallback_chains` configured keeps the exact pre-existing single-fallback-via-router behavior unchanged, and `cmd/gateway`'s `buildPipeline` now validates at startup that every configured fallback target names a real, configured deployment.
- Real OTel Metrics for the first time in this codebase (previously tracing-only), per `docs/rfcs/2026-09-05-gateway-ratelimit-fail-open-metric.md`: `internal/telemetry.Init` now builds a `MeterProvider` alongside the existing `TracerProvider`, sharing the same stdout/otlp/none exporter switch, and a new `kelvran.ratelimit.fail_open` counter (incremented from `dataplane.checkRateLimit`) gives that path's existing per-request log line an aggregate, alertable signal for the first time. Since `sdkmetric.PeriodicReader.Shutdown` unconditionally attempts a final flush even with zero data recorded (unlike the trace pipeline), a metrics-flush failure on shutdown is now logged and treated as non-fatal rather than propagated — matching the same fail-open philosophy the counter itself instruments.
- Added the two OTel GenAI semantic-convention histograms named by Finding 3 of `docs/upgrade-research/gateway-2026-09-06.md` (`docs/rfcs/2026-09-07-gateway-genai-metrics.md`): `gen_ai.client.token.usage`, gated on `billable` so a cache hit or coalesced singleflight follower never replays another call's token count into the aggregate, and `gen_ai.client.operation.duration`, recorded on every request with a conditional `error.type` attribute on failure. Both are wired from `dataplane.finalize`'s existing `ChatCompletionResult` capture point rather than a second, independent data capture.
- Added `otelhttp` middleware for a real outer HTTP-server-level OTel span, per the follow-on `docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md` had explicitly named and deferred: `wrapHTTPServerSpan` wraps the mux via `otelhttp.NewHandler` before `ListenAndServe`, nesting the existing per-request GenAI span inside it using the global `TracerProvider`/`TextMapPropagator` `telemetry.Init` already installs. A new end-to-end test proves real parent/child nesting (shared `TraceID`, inner span's `ParentSpanID` matching the outer span's own `SpanID`), sanity-checked by temporarily disabling the wrap and confirming the test fails.
- Per Finding 5 of `docs/upgrade-research/cache-2026-09-06.md`, added measurement-only infrastructure for cross-instance cache duplicate work ahead of ever building a distributed/shared cache (`docs/rfcs/2026-09-07-cache-cross-instance-telemetry.md`): `telemetry.InstanceID` (`hostname:pid`, stdlib-only), a structured `cache_cross_instance_check` log line at every real L1/L2/L3 cache check (`checkCache`/`checkLexicalCache`), and a standalone, pure `cachecorrelation.Analyze` function that retroactively estimates cross-instance-avoidable misses from a stream of `(tenant, key, instance, hit, timestamp, ttl)` events. No live distributed lookup or correlator process is wired up — the burden is on demonstrating the benefit first, so this only makes the data available once a real multi-instance deployment exists.
- Cache concurrent-miss stampede protection, per THREAT_MODEL.md's Cache Denial-of-Service row: the cache-miss body (guardrail pre-call, router+fallback, upstream call, guardrail post-call, cache write-back) was extracted into a new `runMissPath` and wrapped in `golang.org/x/sync/singleflight.Group` (`Pipeline.missGroup`), keyed on the L1 exact-match cache key. N concurrent identical cache misses now produce exactly one real upstream call instead of N. Keying on `l1Key` (which already bakes in tenant ID) makes cross-tenant coalescing structurally impossible, verified with a dedicated test; coalescing is deliberately narrower than an L2 normalized-equivalent match, and only the leader caller's own context governs the shared guardrail/upstream call. Single-instance-only in v1 — a distributed version is future work.
- Gateway: virtual keys now support `budget_reset_interval_seconds`, turning `budget_usd` into a real rolling window (e.g. a 30-day "monthly" budget) instead of a lifetime-of-the-process cap. `budget.Tracker.Allow`/`SpentUSD`/`Record` check the reset lazily on access (mirroring `ratelimit.TokenBucket`'s lazy-refill design, no new goroutine/ticker); only cumulative spend is persisted, not the reset window's own boundary, so a restart extends the current window by at most one interval — a named, self-limiting gap rather than a new bypass.
- Gateway: virtual keys support a `budget_warn_percent` soft budget-cap threshold — a fraction of `budget_usd` (e.g. 0.8) at which every billable completion logs `budget_warn_threshold_crossed` once spend is at or above that line. Log-only: the request is never rejected or altered, and it's expressed as a percentage of `budget_usd` (not a second absolute dollar value) so it can't drift out of sync if the cap is later changed. Wired into both YAML config and the live Admin API mutation surface, and reuses the existing `billable` gate so a cache hit or coalesced follower can never spuriously re-trigger it.
- Gateway: `buildPipeline` now validates at config-load time that every deployment's `Provider` is a real registered adapter, failing fast at startup instead of only once a request happened to route to an unregistered provider.
- Added an `internal/admin` HTTP surface for the gateway: `GET /admin/config` for read-only config introspection, plus `POST`/`DELETE /admin/virtual_keys/{name}` to add, replace, or remove a virtual key with no config-file edit or process restart. Off by default (enabled via `admin.token_env`), served on its own separate listener and credential space from client-facing virtual keys, defaulting to loopback-only `127.0.0.1:8081`. `dataplane.Pipeline.verifier` is now an `atomic.Pointer[identity.Verifier]` so a live key mutation swaps in a whole new immutable `Verifier` without a lock or partial-update window for in-flight requests.
- The gateway now handles SIGTERM/SIGINT with real graceful shutdown: `run()` uses `signal.NotifyContext` plus `http.Server.Shutdown` (fixed 30s drain) instead of a bare `ListenAndServe`, so the telemetry-flush and `pipeline.Close()` defers now run on every exit path, not just a clean error return. Switched to explicit `net.Listen` + `server.Serve` as a side effect, so a bind failure now surfaces synchronously. Proven with a self-signaling integration test confirming an in-flight request still completes after a real SIGTERM.

## Fixed

- Scoped `isVolatileQuery`'s Cache L3-lite volatility check to `role == "user"` messages only. It previously scanned the entire message history including the system prompt, so a static system prompt merely mentioning a volatility keyword (e.g. "you may discuss current stock prices") permanently disabled L3-lite for every request through that deployment, regardless of what the user actually asked. A pure narrowing — can only make L3 available in more cases, never fewer — so it doesn't touch the entity/freshness hard-gate.
- Closed the streaming budget/TPM concurrent-sibling reservation gap the TOCTOU-fix round (below) had explicitly left open: a long-running stream's real cost can grow well past its own initial reservation over its full duration, silently understating its true claim on a virtual key's headroom to a concurrent sibling for far longer than one HTTP round-trip. New `budget.Tracker.IncreaseReservation`/`ratelimit.TokenBucket.IncreaseReservation`/`KeyLimiter.IncreaseReservationTPM` atomically top up an outstanding reservation to match real-time growth (via the same character-length proxy the runaway-completion guard already tracks per chunk), all-or-nothing — a delta that would exceed the cap/balance is rejected, leaving the existing smaller reservation untouched. Wired into both of `streaming.go`'s decode loops; a rejected top-up stops the stream exactly like a runaway-ceiling trip — gracefully, never as an error.
- Added a mid-stream runaway-completion guard to `HandleChatCompletionStream`, per `docs/rfcs/2026-09-08-gateway-streaming-runaway-completion-guard.md`, closing the "arbitrarily large completion, zero recheck" gap the cost-abuse regression corpus documented as an honest FAIL (`costabuse-streaming-budget-allow-not-rechecked-midstream`) — distinct from the concurrent-request TOCTOU races the `docs/rfcs/2026-09-08-gateway-budget-ratelimit-toctou-fix.md` fix already closed: this bounds ONE already-approved streaming request's own real cost from vastly exceeding its own reservation, not concurrent requests against each other. Since no tokenizer exists anywhere in this codebase (`docs/rfcs/2026-09-05-gateway-tpm-rate-limit.md`), the guard checks a provider-agnostic proxy — accumulated output character length, via `streamaccumulator.go`'s new `totalContentLen()` — against a ceiling computed from `req.MaxTokens` (a generous `*4*10` chars-per-token-and-slack multiplier, named and justified in the RFC) or, if unset, a fixed 750,000-character absolute floor sized comfortably above the largest legitimate single-completion output any configured provider can plausibly produce. Wired into both of `streaming.go`'s real decode loops (`streamDeployment` for SSE-framed providers; `streamDeploymentBedrock` for Bedrock's separate binary `ConverseStream` framing) — each now cancels a new, request-scoped `upstreamCtx` (never the caller's own `ctx`) and cleanly finishes via the existing `finishStreamedResponse` path once the ceiling is crossed, so the client gets a truncated-but-valid stream (never a hang or corrupted frame) and `finalize`'s `Reconcile`/`ReconcileTPM` still run normally afterward. The cache-hit `writeFakeStream` synthesis path is deliberately untouched — it replays an already-complete, already-bounded response with no live upstream connection to guard. New tests (`streamrunaway_test.go`) prove a mock upstream willing to stream far beyond the ceiling is genuinely cut off (verified via the mock's own observed `context.Context` transitioning to canceled, not just "the call returned") on both decode paths, and that an ordinary, well-within-ceiling stream is delivered byte-for-byte unaffected.
- Active health probing (`RunHealthProbeLoop`/`ProbeDeployments`, `gateway/internal/gateway/dataplane/dataplane.go`) now backs off a persistently-unhealthy deployment's own probe cadence instead of probing it at the exact same fixed interval forever — closing the honest FAIL case recorded in `evals/tests/fixtures/regression_corpus_routing_chaos.json`'s `chaos-health-probe-no-backoff-on-repeated-failure` (the AWS-2015-DynamoDB-postmortem-shaped concern that continued fixed-rate probe traffic against an already-degraded dependency is itself a real contributor to sustained overload). A new, unexported `probeDueDeployments` (driven by `RunHealthProbeLoop`; `ProbeDeployments` itself is unchanged — still an unconditional, elapsed-time-independent full-pass primitive tests rely on) tracks each deployment's own next-eligible-probe time; while unhealthy, that interval doubles per consecutive unhealthy reschedule, capped at 8x the configured interval, and resets straight back to the plain interval the instant the deployment is reported healthy again — backoff never applies to a currently-healthy deployment. Deliberately not jittered (unlike `internal/ratelimit`'s client-facing `RetryBackoff`): jitter's value is desynchronizing many independent callers, which doesn't apply to Kelvran's own single per-instance background probe loop. See `docs/rfcs/2026-09-08-gateway-health-probe-backoff.md`.
- Added a post-recovery weight ramp to `internal/router`, closing the real gap `evals/tests/fixtures/regression_corpus_routing_chaos.json`'s `chaos-recovery-instant-full-weight-no-ramp` case documented: the instant a deployment's `HealthyThreshold`-th consecutive successful probe flipped it healthy, `Select` treated it as 100% eligible for its full configured `Weight` immediately, with zero dampening — a known real-world thundering-herd-on-recovery failure mode (Slack's 2021 postmortem: an automated recovery action itself became a second cascading-failure point against a shared dependency). `HealthConfig` gains `RecoveryRampSteps` (<= 0 defaults to 4) and `RecoveryRampInitialPercent` (<= 0 defaults to 20): a just-recovered deployment now starts at `RecoveryRampInitialPercent` of its configured weight and ramps linearly to 100% over `RecoveryRampSteps` further consecutive successful probes, driven by probe outcomes rather than wall-clock time — deliberate, since `router` is I/O-free by design and probe-driven ramping gets "a failure during the ramp restarts it" for free from the same consecutive-counter machinery `UnhealthyThreshold`/`HealthyThreshold` already use, without needing a clock dependency or separate time-window bookkeeping. Implemented as a new `deploymentHealth.ramping`/`rampStep`/`rampCredit` state plus `admitRampedTurn`, a Bresenham-style (rate-limiter) thinning gate applied in `selectHealthy` alongside the existing health-skip check — deliberately layered outside `wrr.go`'s own smooth-WRR cursor math rather than reconstructing `modelState`'s weight-derived fields, so a non-ramping deployment (the overwhelming common case, and every model group with no active recovery) is completely unaffected: zero extra state touched, zero behavior change. A deployment that completes its ramp (or was never unhealthy) is fully indistinguishable from this package's pre-ramp behavior — proven by reusing `TestSelectProportionalForWeightedDeployments`'s own exact-count numbers as the backward-compatibility target. New `health_probe.recovery_ramp_steps`/`recovery_ramp_initial_percent` YAML keys (optional, mirroring `unhealthy_threshold`/`healthy_threshold`'s own resolution convention).
- Widened `internal/guardrail`'s `PromptInjectionDetector` vocabulary — found and honestly documented as two real, hand-curated adversarial regression cases (`evals/tests/fixtures/regression_corpus_guardrail.json` cases 05/06), not invented here: `injectionVerbs` was missing real override-instruction synonyms (`disobey`, `circumvent`, `subvert`), and `injectionTargets`' `"system prompt"` entry had no `"your"`-prefixed form the way `"instructions"`/`"rules"`/`"guidelines"` already did, so a real "disobey **your** system prompt" phrasing still wouldn't have matched with the verb alone added. Both closed together. A third, distinct gap found by the same regression pass (case 13 — a plainly-worded, override-phrasing-free cross-tenant data request) is deliberately left unfixed: override-instruction synonyms are a bounded, enumerable set (a real vocabulary gap), but "ask about another tenant's data" has unbounded natural-language phrasings with no shared lexical anchor — the same class of gap `docs/rfcs/2026-09-03-guardrails-pii-regex-classifier.md`'s Alternatives Considered #1 already declines to solve with a non-semantic, substring-based v1 classifier. Documented as a stated, permanent limitation, not chased further.
- Closed two related `fallback_chains` billing/rate-limit-bypass gaps the cost-abuse regression corpus documented as honest FAILs (`evals/tests/fixtures/regression_corpus_cost_abuse.json`'s `costabuse-crossmodel-fallback-billed-at-requested-not-served-model-price` and `costabuse-permodel-ratelimit-bypassed-via-crossmodel-fallback-chain`): a `fallback_chains` hop that switches to a genuinely different, more expensive model (per `docs/rfcs/2026-09-07-gateway-error-classified-fallback-chains.md`'s own documented cross-model example) was billed at the client's originally-requested, cheaper model's price, and a virtual key's `PerModel` RPM cap on that expensive model was entirely unenforced for traffic reaching it only via a cheaper model's own fallback hop. Fixed at the root: `dataplane.go`'s `finalize` now prices via a new `realServingModel(dep, fallbackModel)` helper, which resolves to `dep.Model` — the `Deployment` that genuinely served the response, after any fallback resolution — whenever one was actually resolved for this response (falling back to the pre-existing `req.Model`/`resp.Model` on a cache hit or any rejection before routing runs, so every other already-verified cost-accounting corpus case, e.g. the cache-hit informational-cost case, is unaffected). `callDeployment`'s deliberate `resp.Model = req.Model` echo for the client-facing HTTP response body is unchanged. The same helper also fixes `telemetry.ChatCompletionResult.ResponseModel` (the `gen_ai.response.model` OTel span attribute), which was previously a silent duplicate of the request model on every request regardless of fallback — an operator can now see a cross-model fallback happened directly on the span. `fallback.go`'s `attemptFallbackChain` gains a new `rateLimitOK func(model string) bool` parameter, consulted with each candidate target's own model immediately before it is actually attempted (mirroring the existing `router.IsHealthy` skip pattern exactly: no `consecutiveFailures`/`realAttempts` increment, no backoff sleep charged for a skipped hop) — both real call sites (`dataplane.go`'s `runMissPath`, `streaming.go`'s `streamDeploymentWithFallback`) supply a new `Pipeline.checkFallbackTargetRateLimit` closure calling `p.limiter.AllowForModel`, RPM only. TPM was investigated and explicitly scoped out: `internal/ratelimit` has no `PerModel` dimension for TPM at all (unlike RPM), so there is nothing for a fallback-hop-aware check to mirror there yet, and retrofitting one would need TPM's own Reserve-then-Reconcile bookkeeping to be re-targeted mid-chain — a materially deeper change than this fix, named as a new honest FAIL (`costabuse-tpm-no-permodel-dimension-crossmodel-fallback-gap`) rather than rushed. Both original corpus cases re-verified against the live fixed code and bumped to revision 2 (`verified_fixed`).
- Fixed the zero-width-space digit-run evasion `evals/tests/fixtures/regression_corpus_guardrail.json`'s `regcorpus-guardrail-23-creditcard-zwsp-evasion-downgrades-block-to-warn` case documented: a single U+200B (or any other `hiddenUnicodeRanges` character, per `promptinjection.go`) inserted mid-digit-run broke `CreditCardDetector`'s contiguous `\b(?:\d[ -]?){12,18}\d\b` match entirely, silently downgrading a real, Luhn-valid card number's `financial_id` Block-tier verdict to a mere `prompt_injection` Warn-tier hit via the unrelated hidden-Unicode scanner. Investigated (via temporary, deleted-before-commit probe tests) whether the same contiguous-run-regex structural gap applied to `SSNDetector`, `IBANDetector`, and `PhoneDetector` — confirmed all three genuinely vulnerable the identical way, and fixed all four with one shared mechanism rather than four separate patches: a new `gateway/internal/guardrail/normalize.go` (`stripHiddenUnicode`/`remapMatch`) strips exactly the same `hiddenUnicodeRanges` set already defined in `promptinjection.go` (never a second, possibly-inconsistent definition) before each vulnerable detector runs its regex, then remaps every match's `[start, end)` back to the ORIGINAL, unstripped text's own byte offsets — preserving `Finding.Start`/`End`'s documented original-text-offset contract exactly. On text with no hidden-Unicode characters (the overwhelming common case), `stripHiddenUnicode` returns an identity mapping, so all four fixed detectors are byte-for-byte behavior-identical to before on every clean input. `EmailDetector` was investigated and confirmed structurally NOT vulnerable the same way (already documented by this same corpus's sibling `regcorpus-guardrail-24` case): an email's local part has no checksum, so the regex engine simply re-anchors one position later and still matches independently — deliberately left unchanged. New tests for every fixed detector (`creditcard_test.go`/`ssn_test.go`/`iban_test.go`/`phone_test.go`) each prove: (1) the exact ZWSP-inside-digit-run evasion is now caught at the correct tier, (2) the clean, no-evasion baseline is byte-for-byte unaffected, and (3) `Finding.Start`/`End` correctly index the ORIGINAL text with the injected character placed well inside the match (not at its first byte), so a naive fix that forgot the offset remap would produce a visibly wrong `End`, not a coincidentally correct one — confirmed by literally breaking `remapMatch` to an identity no-op and observing all four offset tests fail by exactly the injected character's own byte width, then restoring.
- Bounded streaming upstream calls with an idle timeout: `NewHTTPUpstreamStreamCaller` previously used a bare `&http.Client{}` with no timeout and no deadline anywhere in `streaming.go`, so a stalled or slow-to-start streaming upstream hung indefinitely, bounded only by the original client disconnecting. Rather than a single whole-call deadline (which would kill a healthy long-lived SSE stream as readily as a stalled one), added a per-call idle window—a cancelable context plus a timer that `idleTimeoutReader` resets on every real `Read`—bounding both a pre-headers stall and a mid-stream stall without capping total stream duration. A pre-headers timeout now produces a plain error that classifies through the same generic-fallback path the non-streaming caller's 60s timeout already uses.
- `finalize` was re-recording the same notional cost against a virtual key's budget on every repeat cache hit (L1/L2/L3) and every singleflight-coalesced follower from the stampede-protection change above, not just the one genuine upstream call that produced the response. `runMissPath`/`finalize` now thread a `billable` bool, set to true only inside the closure singleflight actually invokes (a coalesced follower's own closure never runs, so its `billable` stays false with no shared state needed) and unconditionally true on the streaming path, which has no coalescing. Cost is still always computed and reported via telemetry; only the budget ledger stops double-counting it. Decided via AskUserQuestion to zero-charge non-billable responses rather than apply a reduced/discounted charge or keep the prior behavior — see docs/rfcs/2026-09-05-gateway-cost-double-counting.md.
- Gateway: the `gen_ai.provider.name` span attribute now remaps `bedrock`/`gemini` to their real OTel semantic-conventions values (`aws.bedrock`/`gcp.gemini`), verified against the registry directly; `openai`/`anthropic` already matched and are unchanged, and `openaicompat` passes through verbatim since it has no well-known registry value of its own. Kelvran's internal provider identifiers (`Deployment.Provider`, adapter registry keys) are untouched — only the OTel-facing attribute differs.
- Fixed a latent hazard in `ratelimit.KeyLimiter.Allow`, uncovered while building the admin API: calling `Allow` for a virtual-key ID with no pre-built bucket nil-pointer-panicked in the default in-memory mode, or silently rate-limited the key to zero forever in Redis mode. Previously unreachable since identity and the rate limiter were always built from the same config in lockstep. Added a thread-safe `KeyLimiter.Register`, called before any `Verifier` swap so a newly-resolvable key ID can never outrun its own rate-limit entry.

## Security

- Closed a real, live documentation-vs-code gap: `THREAT_MODEL.md` and `SECURITY.md` already asserted a "PII/content guardrail pre- and post-call" mitigation for Information Disclosure and Elevation of Privilege (and OWASP LLM01/LLM02 coverage) while zero guardrail code existed anywhere in the repo. Guardrails v1 (see Added, above) makes that claim true.
- Fixed a TOCTOU race that let concurrent requests overspend a virtual key's budget and TPM cap: `budget.Tracker.Allow`/`Record` and `ratelimit`'s `AllowTPM`/`RecordTokens` checked and debited under two separate lock acquisitions, so N simultaneous requests could all pass the check before any committed its debit (verified 20/20 allowed against a $1 cap). Adds `Tracker.Reserve`/`Reconcile` and `TokenBucket.ReserveTPM`/`ReconcileTPM`, which check and provisionally debit atomically under one lock, sized from the key's own historical average cost/tokens once known or the full remaining headroom on a cold start (no pre-call cost estimator exists in this codebase). Every reservation is released or reconciled in `finalize` on every return path including errors; the old `Allow`/`Record`/`AllowTPM`/`RecordTokens` methods are left untouched so existing tests and RPM's already-correct locking are unaffected.
- Added retry-storm-specific DoS mitigations to the gateway: exponential-backoff-with-equal-jitter `Retry-After` headers on rate-limited, concurrency-capped, and final-upstream-failure rejections (deliberately excluded for budget-exceeded, since a budget cap's real recovery time isn't knowable from current `budget.Tracker` state); a new per-virtual-key `max_concurrent_requests` config (`ratelimit.ConcurrencyLimiter`) enforced identically on buffered and streaming paths; and a per-request circuit breaker in `attemptFallbackChain` that stops after 3 consecutive in-chain failures and adds jittered inter-hop delay. The breaker also fixes a real gap where explicitly-named fallback targets bypassed the existing active health-probing check entirely, now skipping any target `router.IsHealthy` already reports as unhealthy.
- Closed `THREAT_MODEL.md`'s Cache Repudiation row (`docs/rfcs/2026-09-05-gateway-cache-hit-provenance.md`): `checkCache` now returns which layer matched (`L1`/`L2`), and `checkLexicalCache` now returns the `Similarity`/write-time age it already computed but was discarding on every hit. Both flow through a new `cacheProvenance` struct, replacing the old bare `cacheHit` bool, into two new OTel span attributes (`kelvran.cache.layer`, plus `kelvran.cache.similarity`/`age_ms` for L3 hits only) and their structured-log equivalents — so a downstream failure can now be traced to which cache decision produced it, not just "this was a cache hit." Deliberately not added to the `gatewayevents` proto, whose own header comment already states it never re-encodes data already real on the span; L1/L2 report layer but not age, since neither cache layer currently captures a write-time timestamp at all.
- Reject `/v1/chat/completions` request bodies over 32MiB (`maxRequestBodyBytes`, enforced via `http.MaxBytesReader` in `gateway/cmd/gateway/main.go`) with a 413, and reject multi-modal content parts whose declared `MediaType` doesn't match the actually-sniffed type of their inline base64 data (`adapter.ValidateContentParts` in `gateway/internal/adapter/validate.go`, via `net/http.DetectContentType`). Both close the Gateway DoS gap THREAT_MODEL.md named: previously `io.ReadAll(r.Body)` had no size limit, and a client-declared Content-Type was trusted outright. The MIME check only flags a definite cross-category mismatch (e.g. declared image vs. detected application) and treats an undetectable `application/octet-stream` result as inconclusive, not a mismatch, to avoid false-positiving on legitimate zip-based document formats.
