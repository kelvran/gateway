# Failure modes

**Status**: written 2026-10-08 against `main` for every row below; each row names how it was verified. This document answers one question per dependency: when it fails, what does the gateway do, how does the operator see it, and what should they do. It is the per-subsystem table behind the Redis outage runbook in [`DEPLOY.md`](DEPLOY.md) and the metric and log catalogue in [`TELEMETRY.md`](TELEMETRY.md).

**How to read a row.** *Request-path behaviour* is what a client and the request see once the gateway is running. *Startup behaviour* is what happens when the dependency is already broken when the process starts. *Metric* and *Log event* name the signals that exist today, and say so when none does. *Verified* is one of: **test** (the named test pins the behaviour), **code-read** (established by reading the code on 2026-10-08, no test exercises it), **live** (observed on a running stack). Line numbers are deliberately absent; search by the identifiers named.

**Two words that mislead.** "Fail-open" means the request proceeds without the control that failed (a rate limit, a budget, a guardrail). "Fail-closed" means the request is refused. The code uses "fail-closed" once for the L3 cache search error; from the client's side that path is fail-open (the request goes upstream), and it is written that way below.

## 1. Redis

All four Redis clients are created lazily: with Redis unreachable the process still starts, except for the identity store (row R10). Nothing pings Redis at startup, `-validate` never dials, and `/healthz` and `/readyz` do not reflect Redis reachability. Two shapes of evidence appear on a dial failure: the gateway's own JSON log line on stdout, and go-redis's plain-text `redis: connection pool: failed to dial after 5 attempts: …` line on **stderr** (the gateway never installs a Redis logger). A log pipeline that reads only the JSON stream misses the second.

## 8. What refuses to start

The process exits 1 before binding a listener when: `admin.token_env` is set but resolves empty; `config_propagation.redis_addr` is set without `signing_secret_env` (or it resolves empty); the identity Redis store cannot be loaded (R10); a bbolt store cannot be opened (P2, P3 under `fail`, P4) or hydrated (P5, and the equivalent `hydrating budget tracker from …`); `admin.audit_log_path` cannot be opened (P7); embed-sim cannot embed its corpus (G1); `telemetry.exporter` is unknown, or `OTEL_EXPORTER_OTLP_INSECURE=true` is combined with an `OTEL_EXPORTER_OTLP_CERTIFICATE` (the exporter refuses that pair); a `fallback_chains` entry names an unknown deployment; or `config.yaml` fails validation. `gateway -validate` catches only the config-shape cases: it never dials Redis, never opens a store or a credential file, and never reads an environment variable.

## 9. Known gaps

Recorded here so the table above does not overstate what exists. Each is a candidate change, not a promise.

- P6: prompt-store write failures have no log line, no metric, and answer 400 (upsert) or 500 (delete) after the in-memory change applied.
- R6: the real cost of a request admitted fail-open in Redis budget mode is never written to the ledger, even after recovery.
- R7, R9: a leaked Redis budget reservation has no automatic reaper and no admin route resets spend without deleting the key.
- G1: a Block-tier detector error is indistinguishable from a finding for the client and is counted by no metric; G2: the streaming post-call case is neither withheld nor counted, and the delivered response is stored by the idempotency store and replayed verbatim to a same-key retry.
- No metric exists for health-probe transitions, fallback hops, export failures, audit-append failures, or credential reload failures; `GatewayDecisionEvent` has no `budget_fail_open` field.
- U5: a client disconnect and a failed cache replay are classified `OUTCOME_UPSTREAM_ERROR`. (gateway/v0.18.0 and earlier cached a stream cut short by the runaway guard or by top-up exhaustion and replayed it with an empty `finish_reason`; since gateway/v0.19.0 it is recorded as `finish_reason: "length"` and never cached.)
- Three local errors (`source_ip_not_allowed`, `streaming_not_supported`, `streaming_not_configured`) fall into the upstream-error outcome, so on the chat routes they carry a `Retry-After` header and count as `error.type=upstream_error`. (**Corrected 2026-10-11**: this sentence also named `model_not_allowed`, which has its own outcome and never carried the header, and the embeddings not-configured error, which `/v1/embeddings` never attaches the header to; `invalid_prompt_reference` left this set the same day — since `gateway/v0.20.0`; `gateway/v0.19.0` still attaches the header to it.)
- A Redis-mode token settlement whose `SettleTokens` call fails (both token dimensions in one script since 2026-10-17; `SettleTPM` per dimension before) is discarded silently (no log, no metric); the over-reservation — the running mean minus the real count, or the full burst minus it for a cold key — decays within `tpm_capacity / tpm_refill_per_second` seconds, and the usage history misses that request. The tokens-per-day bucket (`rate_limit.tokens_per_day`) has the same two leaks — R9 and a failed settle — and they decay within its own refill time, `tokens_per_day / (tokens_per_day/86400)` = 86400 s, a full day rather than seconds; its own `:hist` history misses the request the same way. Like TPM, a Redis-mode settlement re-reads the key's current config: a `tokens_per_day` removed or changed by an admin upsert while a request is in flight settles that request's reservation at the new rate (or not at all when the cap was removed), leaving the day key's arrival time off by the ratio of the two caps — for a cold reservation up to a day of refusals once the cap is re-added, where the minute key's error decays within a minute. The fallback-hop rate-limit check's fail-open is uncounted even when the primary check passed.
- A token settlement whose reply is lost after Redis executed it is applied twice when go-redis retries the call (the history's `HINCRBYFLOAT`/`HINCRBY` and the TAT delta carry no idempotency guard — the budget adjust's epoch guards a window turnover between reserve and adjust, not a retry, so a retried `Adjust` double-applies the same way, R7's family); pre-existing, and unchanged by the paired settle of 2026-10-17 — a single EVAL is retried as a whole exactly as a single command was.
- A Redis-mode budget settlement whose `Adjust` fails (R7 logs and counts it) also loses its history write: the window's mean misses that request and is biased upward by the leak (`spent` keeps the reservation, `billed_count` never counts it), and the leaked reservation is one mean request — or the full remaining headroom when the window had no billed settlement yet — until the window's TTL fires (for good under a lifetime cap). Since 2026-10-16; before, every leaked reservation was the full headroom (R19).
- In both budget modes the reservation mean is `spent / billed_count` with the siblings' in-flight reservations inside `spent`, so each concurrent reservation after the window's first billed settlement is the previous one times `1 + 1/billed_count`: after one settlement each reservation doubles — ten concurrent requests with a 1 USD mean reserve 1, 2, 4 … 256 USD, then the tenth is clamped to the 488 USD left of a 1 000 USD cap in Redis (in memory, which does not clamp, it reserves 512 USD and `spent` reads 1 024 USD) and an eleventh is refused until one of them settles; after ten settlements the same ten-request burst inflates `spent` 2.6× in total (1.1× per reservation), after a hundred 1.1× (1.01×). It self-corrects as the burst settles (every settlement replaces its reservation with the real cost and counts once): `TestTenConcurrentReservesAreAdmittedAfterOneBilledSettlement` pins the arithmetic in Redis, and the in-memory `reservationAmountLocked` is the same formula. Redis-mode TPM does not have this: `gateway/internal/ratelimit/redislimiter/tpm_history.go` keeps a `sum`/`count` of settled tokens. Moving the budget mean to a settled sum in both modes is a design change, not made with R19's fix (parity with memory, 2026-10-16).
- `gateway -validate` cannot detect an unreachable Redis, an unreadable or empty credential file, or an unopenable audit log path.
