# Failure modes

**Status**: written 2026-10-08 against `main` for every row below; each row names how it was verified. This document answers one question per dependency: when it fails, what does the gateway do, how does the operator see it, and what should they do. It is the per-subsystem table behind the Redis outage runbook in [`DEPLOY.md`](DEPLOY.md) and the metric and log catalogue in [`TELEMETRY.md`](TELEMETRY.md).

**How to read a row.** *Request-path behaviour* is what a client and the request see once the gateway is running. *Startup behaviour* is what happens when the dependency is already broken when the process starts. *Metric* and *Log event* name the signals that exist today, and say so when none does. *Verified* is one of: **test** (the named test pins the behaviour), **code-read** (established by reading the code on 2026-10-08, no test exercises it), **live** (observed on a running stack). Line numbers are deliberately absent; search by the identifiers named.

**Two words that mislead.** "Fail-open" means the request proceeds without the control that failed (a rate limit, a budget, a guardrail). "Fail-closed" means the request is refused. The code uses "fail-closed" once for the L3 cache search error; from the client's side that path is fail-open (the request goes upstream), and it is written that way below.

## 1. Redis

All four Redis clients are created lazily: with Redis unreachable the process still starts, except for the identity store (row R10). Nothing pings Redis at startup, `-validate` never dials, and `/healthz` and `/readyz` do not reflect Redis reachability. Two shapes of evidence appear on a dial failure: the gateway's own JSON log line on stdout, and go-redis's plain-text `redis: connection pool: failed to dial after 5 attempts: …` line on **stderr** (the gateway never installs a Redis logger). A log pipeline that reads only the JSON stream misses the second.

## 8. What refuses to start

The process exits 1 before binding a listener when: `admin.token_env` is set but resolves empty; `config_propagation.redis_addr` is set without `signing_secret_env` (or it resolves empty); the identity Redis store cannot be loaded (R10); a bbolt store cannot be opened (P2, P3 under `fail`, P4) or hydrated (P5, and the equivalent `hydrating budget tracker from …`); `admin.audit_log_path` cannot be opened (P7); embed-sim cannot embed its corpus (G1); `telemetry.exporter` is unknown, or `OTEL_EXPORTER_OTLP_INSECURE=true` is combined with an `OTEL_EXPORTER_OTLP_CERTIFICATE` (the exporter refuses that pair); a `fallback_chains` entry names an unknown deployment; or `config.yaml` fails validation. `gateway -validate` catches only the config-shape cases: it never dials Redis, never opens a store or a credential file, and never reads an environment variable.

## 9. Known gaps

Recorded here so the table above does not overstate what exists. Each is a candidate change, not a promise.

- P6: prompt-store write failures have no log line, no metric, and answer 400 (upsert) or 500 (delete) after the in-memory change applied.
- R6: the real cost of a request admitted fail-open in Redis budget mode is never written to the ledger, even after recovery.
- R7, R9: a leaked Redis budget reservation has no automatic reaper and no admin route resets spend without deleting the key.
- G1: a Block-tier detector error is indistinguishable from a finding for the client and is counted by no metric; G2: the streaming post-call case is neither withheld nor counted, and the delivered response is stored by the idempotency store and replayed verbatim to a same-key retry.
- No metric exists for health-probe transitions, fallback hops, export failures, audit-append failures, or credential reload failures; `GatewayDecisionEvent` has no `budget_fail_open` field.
- U5: a stream cut short by the runaway guard or by top-up exhaustion is cached and replayed with an empty `finish_reason`; a client disconnect and a failed cache replay are classified `OUTCOME_UPSTREAM_ERROR`.
- Several local errors (`model_not_allowed`, `source_ip_not_allowed`, the streaming and embeddings not-configured errors) fall into the upstream-error outcome, so they carry a `Retry-After` header and count as `error.type=upstream_error`.
- A Redis-mode TPM settlement whose `AdjustTPM` fails is discarded silently (no log, no metric); the over-reservation decays within `tpm_capacity / tpm_refill_per_second` seconds. The fallback-hop rate-limit check's fail-open is uncounted even when the primary check passed.
- `gateway -validate` cannot detect an unreachable Redis, an unreadable or empty credential file, or an unopenable audit log path.
