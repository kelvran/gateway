Linked from `SECURITY.md`'s Provider & Data-Flow Inventory section for the same reason a threat model needs to know exactly what leaves the system and where.

## Notes

- **Embeddings for semantic caching** are a distinct data flow from the completion call itself — whichever embedding provider/model is used for L3 cache matching must be listed here once chosen (currently unresolved, per `PRD.md`'s open-questions note on the semantic-cache risk model). The offline embedding-gate validation harness (`evals/scripts/validate_embedding_gate.py`, a one-off research script, never production code) does call AWS Bedrock Titan embeddings directly — not listed as its own row since it's not a shipped capability. **Corrected 2026-10-08**: "once chosen" overstates what is pending — the shipped L3 layer is lexical MinHash/Jaccard and uses no embedding provider at all (`gateway/internal/cache/lexical.go`; `PRD.md`'s own 2026-09-05 correction defers embedding-based L3 to a future RFC gated on miss-telemetry that does not exist), so there is no cache-driven embedding flow to list, resolved or otherwise. Two shipped, production embedding flows do exist, neither cache-related: (1) the client-facing `POST /v1/embeddings` pass-through (`dataplane.Pipeline.HandleEmbeddings`, in `gateway/v0.13.0` and every release since) forwards the caller's input text to OpenAI's `/v1/embeddings` or to AWS Bedrock Titan via `InvokeModel` (exactly one input per call, `adapter/bedrock/embeddings.go`; `kind: embedding` is rejected at load for any other provider) — the OpenAI and AWS Bedrock rows above are the credentialed targets, though the Bedrock row's "via `Converse`/`ConverseStream`" wording predates this endpoint; (2) the optional `embedsim` guardrail detector (`gateway/internal/guardrail/embedsim/`, enabled only when `guardrails.embed_sim` is configured, `cmd/gateway/main.go`'s `if es := cfg.EmbedSim; es != nil`) embeds every message text it checks through AWS Bedrock Titan Text Embeddings V2 `InvokeModel`, under its own separately-configured static AWS credentials (`EmbedSimConfig`'s `*_env`/`*_file` fields), so an operator who enables it sends checked prompt text to AWS even when no deployment routes there. The sibling opt-in `bedrockguard` detector (`ApplyGuardrail`) sends the same checked text to AWS Bedrock Guardrails under the same credential shape — not an embedding call, but the same class of "a provider receives data outside the completion call" flow this bullet exists to disclose.
- **No provider receives data it wasn't the target of.** Cache is a lookup-and-serve mechanism only — it returns stored bytes directly to the client, never re-injects a cached response's content into a NEW upstream call to a different provider. **Corrected 2026-09-14**: this bullet previously cited "`THREAT_MODEL.md`'s Cache STRIDE table" for this claim, but no such discussion existed there — a dangling citation, found by a follow-up audit. `THREAT_MODEL.md`'s Cache Information Disclosure row now discusses the related, but distinct, fact this citation was likely reaching for: since `cache.Key`/`cache.NormalizedKey` are built from the client-facing/alias model name, not the serving deployment's real `Provider`, a cache HIT under a virtual model alias (`gateway/ARCHITECTURE.md`'s corrected 2026-09-14 entry) can serve content a *different* real provider originally produced than the one a fresh routing pick would choose — accepted-by-design, since Cache is deliberately provider-agnostic (`AGENTS.md`'s own dependency rule), not a correctness risk this repo has left undocumented.
- **Corrected 2026-09-11**: the "zero entries for Evals by design" claim immediately below this note (in every version of this file until now) was false since `evals/evals/judge/providers.py` first shipped a real, direct provider call (2026-09-04) — this file's own header claims it is "maintained as a manifest kept current," but `git log` shows it was never touched since the initial scaffolding commit. Evals genuinely does call Anthropic/OpenAI/Bedrock directly for LLM-judge scoring, independent of Gateway's own request path entirely — the 3 new rows above are that real data flow, added for the first time.
- **Added 2026-09-14** (`docs/upgrade-research/ai-compliance-regulatory-readiness-2026-09-14.md` Finding 3): the "Cross-border transfer safeguard" column is a deliberately honest, unverified-by-default disclosure, not a compliance claim — this repo has no legal team confirming any provider's current DPA/SCC/adequacy status, and asserting a specific mechanism (e.g. "SCCs in place") without independently verifying it against that provider's own current terms would be worse than disclosing the gap. An operator who needs to represent cross-border transfer safeguards to their own customers must check each listed provider's current DPA directly — this table exists to name exactly which providers that check applies to, not to perform the check on the operator's behalf.
