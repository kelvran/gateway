# Deployment Guide

## Overview

Two independently deployable units — `gateway` (Go) and `evals` (Python) — joined only by the versioned `api/` contract. This document covers operational deployment only; for *why* they're structured this way, see `DESIGN.md` and `docs/decisions/`. **Cache is not a third deployable** — it ships inside the `gateway` binary; nothing here treats it separately.

## Deployment Models

- **Docker Compose** (local/dev) — `gateway` as a Compose service, plus an optional Redis dependency, for local development. `evals` is a Click CLI, not a long-running process — run it directly, not as a Compose service (see below).
- **Kubernetes / production** — `gateway` and `evals` as separate Deployments, scaled and released independently, sharing only the `api/` contract version they were built against. **Corrected 2026-10-08**: only `gateway` has a Deployment. `evals` has no container image and no manifest — `find evals -name 'Dockerfile*'` returns nothing, `deploy/k8s/base/kustomization.yaml` lists only gateway resources, and `docker-compose.yml`'s own header says `evals` is a Click CLI with no Dockerfile. Run `evals` where its data is (a laptop, a CI job, a one-off Job you write yourself); nothing in this repository deploys it as a long-running service. The independent-versioning point stands; the "separate Deployments" shape does not.
- **ECS/Fargate** (added as part of the backlog Phase 7 infra round) — a real alternative to Kubernetes for `gateway` specifically, using Fargate's native secrets injection instead of ESO/IRSA — see below. **Corrected 2026-10-08**: "a real alternative to Kubernetes" overstates what ships. `deploy/ecs/main.tf` provisions one `aws_ecs_task_definition` and its CloudWatch Logs group, nothing else; the ECS cluster, service, VPC/subnets/security groups, load balancer and config-file delivery are all bring-your-own (`deploy/ecs/README.md`, "What this module provisions, and what it deliberately does not"). It is a task-definition module whose one real advantage is Fargate's native secrets injection, not a complete deployment target.

## Prerequisites

- Go 1.26+ runtime for `gateway`, Python 3.12+ for `evals` (per `gateway/ARCHITECTURE.md`/`evals/ARCHITECTURE.md`'s tech-stack tables). **Corrected 2026-10-08**: Go is a build-time requirement, not a runtime one. `gateway/Dockerfile` compiles with `CGO_ENABLED=0` into a static binary and copies it into a `FROM scratch` final stage, so the deployable needs no Go toolchain, libc or shell; the release archives and deb/rpm/apk packages (`gateway/.goreleaser.yaml`, also `CGO_ENABLED=0`; since `gateway/v0.18.0`, the first release to carry them) ship the same static binary. The toolchain floor is `go 1.26.9` (`gateway/go.mod`) and the CI builder image is `golang:1.27.2-alpine` (`gateway/Dockerfile`) — `gateway/ARCHITECTURE.md`'s "Go 1.26+" row describes what you build with, not what you run on. Python 3.12+ remains a true runtime requirement for `evals` (`requires-python = ">=3.12"`, `evals/pyproject.toml`), which ships as source.
- Provider credentials for whichever upstream LLM providers are configured — see `docs/operations/PROVIDERS.md` for exactly which providers exist and what each needs.
- Redis for `gateway`, **only if** `config.yaml`'s `rate_limit.redis_addr` is set (distributed rate limiting across multiple gateway instances, per `docs/rfcs/2026-09-03-distributed-rate-limiting.md`) — omit it entirely for the default, in-memory-only rate limiter. **Corrected 2026-10-08**: `rate_limit.redis_addr` is one of four independent Redis knobs, not the only one — `budget.redis_addr` (Redis-backed budget ledger), `admin.redis_addr` (Redis-backed virtual-key store) and `config_propagation.redis_addr` (cross-replica admin-mutation pub/sub) are each parsed separately in `gateway/internal/gateway/controlplane/config.go` and each opened separately in `cmd/gateway/main.go`. Redis is needed if ANY of the four is set, and a multi-replica deployment needs the last three (see "Redis (Distributed State Backend)" below and `deploy/k8s/README.md`). Setting `config_propagation.redis_addr` additionally requires `config_propagation.signing_secret_env` to name a non-empty environment variable, or startup fails (`resolveConfigPropagationSigningSecret`, `cmd/gateway/main.go`). The `rate_limit.redis_addr`-only wording in the Compose section below is stale in the same way. **Postgres is not used by any shipped code today** — it's a `gateway/ARCHITECTURE.md` Tech Stack *future target* for a control-plane config store, not real yet (config is static YAML, loaded once at startup — see that doc's `/internal/admin` entry).
- Fail-fast on missing required environment variables at startup — never start in a half-configured state, per this project's own security conventions (`SECURITY.md`).

All three, like `redis`, are opt-in and never started by a bare `docker compose up gateway`. **Corrected 2026-10-08**: "currently blocked pending a real bucket/IAM credential" reads as if nothing in the repository could supply one. `terraform/vector-s3-shipper/` provisions exactly that pair — the S3 bucket plus a write-only IAM user (`terraform/README.md`, Modules table) — so the accurate statement is: `vector` requires a bucket and a scoped credential you provision yourself (for example with that module) and place in `.env.vector`; whether anyone has applied the module is not recorded anywhere in this repository, and `docker-compose.yml`'s own comment on the `vector` service still describes the bucket as not existing. Also stale here: "Redis is only needed when `rate_limit.redis_addr` is configured" — any of the four `*.redis_addr` knobs (`rate_limit`, `budget`, `admin`, `config_propagation`) needs the `redis` profile; see Prerequisites.

`gateway/Dockerfile`'s final image also runs as a real non-root user (`USER 65532:65532`, added 2026-09-14) — previously ran as root with a writable root filesystem.

To bring `gateway` up locally:
1. `cp gateway/config.example.yaml gateway/config.yaml` and fill in real values (both files are gitignored except the `.example` one — see `.gitignore`).
2. `cp .env.example .env` and set the real API key(s) your `config.yaml`'s deployments reference.
3. `docker compose up gateway` (add `--profile redis` first if `config.yaml` sets `rate_limit.redis_addr: redis:6379`).

**Corrected 2026-09-11** — this section was stale since 2026-09-07: a real `/healthz` endpoint now exists (`mux.HandleFunc("/healthz", healthzHandler)`, `cmd/gateway/main.go`; since 2026-10-10 registered by `newDataPlaneMux` in `cmd/gateway/mux.go`) — a shallow liveness probe, no auth, returning `200 {"status":"ok"}`, covered by an integration test. Readiness is `GET /healthz` returning `200`, not merely "the container is listening on `:8080`." **Corrected 2026-10-08**: "Readiness is `GET /healthz`" is now true only in the Kubernetes `readinessProbe` sense — `deploy/k8s/base/deployment.yaml` points both probes at `/healthz`, deliberately. Since 2026-09-26 (`87a97739`; the 2026-09-25 paragraph below) the question "can this gateway serve every configured model" is answered by `GET /readyz` (`mux.HandleFunc("/readyz", readyzHandler(pipeline))`, `cmd/gateway/main.go`); the next paragraph explains why the two must stay separate and which one an external monitor should use.

**Updated 2026-09-25** — a second, deliberately separate `/readyz` endpoint now also exists (`readyzHandler`, `cmd/gateway/main.go`; data source: `dataplane.Pipeline.ReadinessSummary`, a pure read of the existing deployment probe loop's own state, zero new upstream calls), per `docs/upgrade-research/production-readiness-security-grounding-2026-09-25.md` Finding 2 — a 2026 LiteLLM-monitoring postmortem found "liveness returns 200 while every routed request fails" to be the single most common real-world LLM-gateway monitoring gap, and `/healthz`'s own deliberate provider-independence (correct, unchanged) left nothing filling that gap. `/readyz` returns `200` with a per-canonical-model health breakdown (`{"ready":true,"models":{"claude-haiku-4-5":true,...}}`) if every configured model has at least one healthy deployment, `503` if any model has none. **Point an external monitor at `/readyz`, not the Kubernetes pod `readinessProbe`** — `deploy/k8s/base/deployment.yaml`'s `readinessProbe` still correctly points at `/healthz` (see that file's own comment, unchanged): `/readyz`'s health verdict is pod-wide across every configured canonical model, so wiring it as the k8s readiness probe would empty the Service's entire `EndpointSlice` the moment even one model (out of potentially several this gateway serves) loses every one of its deployments — cutting off traffic for every OTHER, perfectly healthy model too. That is exactly the same "a readiness probe checking a dependency that can fail in lockstep across every replica, emptying the EndpointSlice, worse than doing nothing" anti-pattern this file's 2026-09-14 correction below already reasons about for a *shared* dependency (Redis/upstream provider) — here the failure mode is per-model rather than per-shared-resource, but the blast-radius risk to unrelated traffic is the same shape.

**Updated 2026-10-08** — `/readyz` with `health_probe` configured and a `kind: embedding` deployment in the config: in `v0.17.0` and earlier the probe sent every deployment a chat-shaped request, an embedding model rejected it, and `/readyz` reported that model not ready (`503`) while real `/v1/embeddings` traffic worked (live defect F3, 2026-10-07/08). Since `gateway/v0.18.0` the probe is shaped for the deployment's kind (`dataplane.Pipeline.probeDeployment`: a one-string embedding through the same adapter and upstream `HandleEmbeddings` uses), so an embedding deployment is healthy when it can embed and unhealthy when it cannot — including the misconfiguration case of a provider with no embedding adapter, which fails the probe the same way it fails a client. If you worked around the old behaviour by disabling `health_probe` or by pointing monitors at `/healthz` only, you can re-enable `/readyz` monitoring once you run a build that includes this fix. See the 2026-10-08 addendum to `docs/rfcs/2026-09-07-gateway-active-health-probing.md`.

## Linux packages (deb/rpm/apk) and systemd

**Added 2026-10-08.** Every `gateway/v*` GitHub Release cut after 2026-10-08 carries `kelvran-gateway_<version>_linux_{amd64,arm64}.{deb,rpm,apk}` built by `.github/workflows/release.yml` from `gateway/.goreleaser.yaml`, plus `.tar.gz`/`.zip` archives for linux, darwin and windows. `gateway/v0.18.0` (2026-10-10) is the first packaged release: `gateway/v0.17.0` (2026-10-07) predates the pipeline, and `release.yml`'s own header says tags at or before it have no `.goreleaser.yaml` in their tree and cannot be rebuilt, so do not look for a `.deb` on `v0.17.0` or earlier. Only the `.deb` install path is exercised by CI (`release.yml`'s `acceptance` job runs `dpkg -i` on the amd64 deb, then `-version`, `-validate` on the shipped example config, and `systemd-analyze verify` on the unit); the `.rpm` and `.apk` come from the same `nfpms` block of `gateway/.goreleaser.yaml` but are not install-tested, and none of the three packages is itself signed (that file has no `signature` configuration) — which is why `apk add` needs `--allow-untrusted`. Verify an asset first (`RELEASE.md`, "Verifying a release binary"). The package installs `/usr/bin/kelvran-gateway` and `/usr/bin/kelvran` (the companion CLI, since `gateway/v0.18.0`), the unit `/usr/lib/systemd/system/kelvran-gateway.service` (source: `deploy/systemd/kelvran-gateway.service`), `/etc/kelvran-gateway/config.example.yaml`, and `LICENSE`/`NOTICE` under `/usr/share/doc/kelvran-gateway/`; its post-install only runs `systemctl daemon-reload` and, on an upgrade, `systemctl try-restart` so an already-running service picks up the new binary. It never enables or starts a stopped service — the gateway has no usable default config and the example's virtual keys are public — so:

```bash
sudo dpkg -i kelvran-gateway_<version>_linux_amd64.deb          # or rpm -i / apk add --allow-untrusted
sudo cp /etc/kelvran-gateway/config.example.yaml /etc/kelvran-gateway/config.yaml
sudoedit /etc/kelvran-gateway/config.yaml                       # deployments, virtual keys, persist paths under /var/lib/kelvran-gateway; keep it 0644 (see below)
sudo install -m 0600 /dev/null /etc/kelvran-gateway/env         # credentials file: root-only, systemd reads it before dropping privileges
sudoedit /etc/kelvran-gateway/env                               # provider credentials, one KEY=value per line (read via EnvironmentFile=)
kelvran-gateway -config /etc/kelvran-gateway/config.yaml -validate      # no sudo: reads only the 0644 config, resolves no env vars (see below)
sudo kelvran doctor --config /etc/kelvran-gateway/config.yaml           # since gateway/v0.18.0: also reads /etc/kelvran-gateway/env and reports the variables, files and paths -validate cannot see
sudo systemctl enable --now kelvran-gateway
```

The unit runs as a `DynamicUser` with `ProtectSystem=strict`: the only writable path is `/var/lib/kelvran-gateway` (`StateDirectory`), so every `persist_path` in the config must live there. `config.yaml` must stay world-readable (0644): the service runs as a `DynamicUser` whose uid is not known in advance, so a `chmod 600` makes `ExecStartPre` fail with permission denied — the file holds only key hashes and environment-variable names, never a secret; the secrets live in the 0600 `env` file, which systemd reads as root. `ExecStartPre` validates the config, `TimeoutStopSec=60s` exceeds the gateway's 50 s worst-case stop (30 s graceful shutdown, 15 s post-shutdown grace, 5 s final telemetry flush), and the capability bounding set is empty, so a listen port below 1024 needs a reverse proxy in front or `CapabilityBoundingSet=CAP_NET_BIND_SERVICE` plus `AmbientCapabilities=CAP_NET_BIND_SERVICE` in a drop-in. `kelvran-gateway -version` prints what is installed. **Corrected 2026-10-08**: the `-validate` line in the block above previously carried `sudo`; it is unnecessary and the line was changed today. `-validate` runs `controlplane.Load` (a plain `os.ReadFile` of the 0644 config; `Load` reads no environment variables) and then `validateConfig`, whose own doc comment states it never opens a file, touches the network or reads an environment variable (`cmd/gateway/main.go`) — which is also why `ExecStartPre` can run the same command as the `DynamicUser`, and why `release.yml`'s acceptance job runs it unprivileged. The "`chmod 600` makes `ExecStartPre` fail" sentence is a direct consequence of `DynamicUser=yes` in `deploy/systemd/kelvran-gateway.service` (the uid is allocated at start, so a root-only file is unreadable to it); no in-repo test exercises that failure — `release.yml`'s acceptance job does `sudo cp` the example config to `/etc/kelvran-gateway/config.yaml` and start the unit, which proves the positive path (a root-owned 0644 file is readable to the `DynamicUser` at `ExecStartPre`), but it never changes the file's mode, so the 0600 refusal itself is undemonstrated.

## Redis (Distributed State Backend)

**Added 2026-09-23**, per `docs/upgrade-research/redis-state-backup-recovery-2026-09-22.md` Findings 1/3/4/6 — this section was previously silent on Redis entirely, a real gap once `rate_limit.redis_addr`/`budget.redis_addr`/`admin.redis_addr`/`config_propagation.redis_addr` moved from a rate-limit-only concern to holding financial-ledger (`redisbudget`) and credential-store (`redisstore`) state.

**Local/dev target**: `docker-compose.yml`'s `redis` service (`redis:7-alpine`, `--profile redis`) now runs with `--appendonly yes --appendfsync everysec` and a named, persistent volume — bounding loss to at most ~1s of writes and surviving container recreation, neither of which was true before this date. This is explicitly a local/dev convenience, never the production target.

**Production target — not yet provisioned, named here for the first time rather than left implicit.** Two real options, in order of preference for this data class:
- **AWS MemoryDB** — durability is structural (a distributed transactional log every write is committed to, not a snapshot cadence someone has to remember to configure): "There is no data loss in this scenario as the data was persisted in the transaction log" for a full Multi-AZ cluster loss/rebuild. Preferred for `redisbudget`/`redisstore` specifically, since both hold state whose loss means either silently under-enforcing a spend cap or silently discarding a live credential — not an ordinary cache-miss cost.
- **ElastiCache with Backup and Restore enabled** — the lower-effort alternative if MemoryDB's cost/API-compatibility tradeoffs (not evaluated here) aren't a fit; snapshot-based (up to 35-day retention), restorable into a new cluster, but its point-in-time-recovery ceiling is bounded by snapshot interval, not a transaction log the way MemoryDB's is.
- Neither has been provisioned yet — this is a documented target for the next real infrastructure pass, not a claim that either exists today. If self-hosting instead of using a managed AWS service, provision a real Redis manifest (StatefulSet + PVC) under `deploy/k8s/` — none exists there today; the config *knobs* are documented, the resource that would provision Redis itself is not.

**RPO/RTO target**: no Kelvran doc anywhere previously set an explicit number for any subsystem. Per AWS's own Well-Architected "Backup and restore" DR tier (the appropriate tier for Kelvran's current single-region, one-pilot-customer stage — not Pilot Light/Warm Standby/active-active, which are unjustified cost/complexity for this stage): **RPO ≤ 5 minutes** (via continuous/frequent backup, not an infrequent manual snapshot), **RTO ≤ 60 minutes** (restore + verify + redeploy). Revisit upward (tighter RPO/RTO, a higher DR tier) only once real production traffic volume and a real customer SLA justify the added cost — mirroring this repo's own established "instrument/decide later" posture for other capacity questions, not a permanent ceiling. A quarterly restore-drill practice (restore a real backup into a scratch instance and verify it) is the recommended way to keep this target honest rather than aspirational — not yet adopted, named here as the next step once a production Redis target is actually provisioned.

**Redis outage runbook (added 2026-10-08).** The per-subsystem table is [`FAILURE-MODES.md`](FAILURE-MODES.md); this is the sequence to run. While Redis is unreachable: per-key rate limits and budgets fail open — requests are admitted, `kelvran.ratelimit.fail_open` / `kelvran.budget.fail_open` count every such admission and the `ratelimit_backend_unavailable` / `budget_backend_unavailable` log lines carry the error; virtual-key authentication is unaffected (verification is in-memory); an admin mutation still applies on the replica that received it, but its persistence write fails (`kelvran.persistence.failed`, `identity_persist_failed`, and `budget_persist_failed` for the budget-state cleanup a key delete, or an upsert that creates a new key id, performs) when the store is Redis and its event never reaches the other replicas (`kelvran.configpropagation.publish_failed`, `configpropagation_publish_failed`). Redis pub/sub does not replay: an event published while a subscriber was disconnected is gone for that subscriber, and go-redis reconnects silently, so once Redis is back the replicas can disagree with no further error — and the one replica that holds the mutation holds it in memory only. Therefore, once Redis is reachable again, **re-apply every admin mutation made during the outage** against any one replica: that re-persists it and re-propagates it. Upserts and deployment-weight changes are idempotent; a delete is not on the replica that already applied it (it answers 404 and writes nothing), so re-apply deletes against a replica that still holds the key, or re-POST the key and DELETE it again. Do not rely on a restart to recover them: a restart reverts the receiving replica to its last persisted state, and deployment weights are never persisted at all (a restart returns them to `config.yaml`). Separately, restart any replica whose `kelvran.configpropagation.subscribe_stopped` is above zero — its subscriber loop has stopped for good and it will miss every future mutation until restarted. This runbook covers Redis being *unreachable*; a healthy Redis holding a budget reservation that a failed settlement left behind (the key answers 429 `insufficient_quota` with no traffic in flight) is row R7 of [`FAILURE-MODES.md`](FAILURE-MODES.md).

## Local Bbolt Persistence: Backup & Restore

**Added 2026-09-26.** `identity`/`budget`/`prompt` can each optionally persist to a local bbolt file (`admin.persist_path`/`budget.persist_path`/`prompt.persist_path` in `config.yaml`) for single-process restart durability — see each `boltstore` package's own doc comment. `POST /admin/backup` (`internal/admin/admin.go`'s `backupHandler`, via `dataplane.Pipeline.BackupStores`) writes a timestamped `<store>-<UTC-timestamp>.bbolt` file per configured, persisted store to `admin.backup_dir` — safe to call while the gateway is actively serving traffic (`internal/backup.CopyFile` uses bbolt's own `Tx.CopyFile`, backed by a read transaction against a consistent MVCC snapshot, per that package's own doc comment).

Until now there was no supported way to actually use one of those backup files again — no `Restore` counterpart existed anywhere in this codebase, and even the informal "stop the process, copy the backup over `persist_path`, restart" workaround had never been proven to work through the real store constructors (`identity`/`budget`/`prompt`'s own `boltstore.Open`) the gateway binary actually calls at startup — `internal/backup`'s own tests previously only ever opened a backup file with a raw, schema-blind `bolt.Open` read-check.

**Restoring from a backup — this is an OFFLINE procedure. Do not skip step 1.**

1. **Stop the gateway process.** Restoring a bbolt file that a running gateway still holds an exclusive lock on (and has already loaded into memory) is a real concurrent-access hazard `internal/backup.Restore` deliberately does not attempt to solve — see that function's own doc comment. Never point the restore step below at a `persist_path` a live gateway process is still serving from.
2. Run the restore flag: `gateway -config config.yaml -restore-store=<identity|budget|prompt> -restore-from=<backup-file-path>`. This is a one-shot operator action — it never starts a listener or the normal server-start path. It resolves the target store's own configured `persist_path` out of the same config file a normal `gateway` invocation would load, validates that the backup file is a well-formed, independently-openable bbolt database (opened read-only via a raw `bolt.Open`) *before* touching anything at the destination, then atomically replaces the destination file (written to a temp file in the same directory first, then moved into place with a single `os.Rename`, so a crash mid-restore never leaves a half-written `persist_path`). Refuses to overwrite an existing destination file unless `-restore-force` is also passed — mirroring `backup.CopyFile`'s own refuses-to-overwrite convention, so a stale or wrong backup can't silently clobber a live `persist_path` by accident.
3. Start the gateway normally (no restore flag). The very next startup loads the now-restored file through that store's exact real constructor (`identity`/`budget`/`prompt`'s `boltstore.Open`), exactly like any other pre-existing `persist_path` file — there is no separate "restored mode" once step 2 completes.

This closes the recovery gap on the OPEN side of `cmd/gateway/main.go`'s `openPersistStoreWithRecovery`/`isCorruptStoreErr`: `admin.on_corrupt_store: reset` (the non-default opt-in) renames a corrupted `persist_path` file aside and starts the store fresh and EMPTY rather than failing startup outright — real data loss if no restore step exists to put a prior backup back in its place. A `.corrupt-<unix-seconds>` file left behind by that reset path is itself a valid `-restore-from` source if it's still a well-formed bbolt file (i.e. the corruption was something `bolt.Open` tolerated enough to be readable at all) — Restore's own validation step will tell you either way before it touches anything.

## Troubleshooting / Health Checks

**Which version is running?** (added 2026-10-08) `gateway -version` prints `kelvran-gateway <version> (<commit>, built <date>, <go>, <os/arch>)` and every start logs the same fields once as a `build_info` JSON record; `docker run --rm ghcr.io/kelvran/gateway:<tag> -version` answers it for an image without starting the server. Replicas reporting different versions is the first thing to check after a rollout.

For deeper diagnosis once something's actually running, see `docs/operations/TELEMETRY.md` — this document covers standing the system up, not debugging it once it's misbehaving.

For what the gateway does when one of its dependencies fails — Redis, a bbolt persistence file, an upstream provider, a guardrail detector, a credential file, the OTLP collector — and what to do about it, see [`FAILURE-MODES.md`](FAILURE-MODES.md) (one row per subsystem: request-path behaviour, startup behaviour, metric, log event, operator action).
