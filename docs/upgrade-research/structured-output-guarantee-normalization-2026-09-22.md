# Kelvran Gateway — Cross-Provider Structured-Output Guarantee-Strength Research

**Date:** 2026-09-22 (Findings 1-6); **extended 2026-09-23** (Findings 7-9, a second pass)
**Scope:** `gateway/internal/adapter/{openai,anthropic,gemini,bedrock,openaicompat}/` and `gateway/internal/adapter/{types.go,capabilities.go}` — specifically the *guarantee-strength* axis of structured-output/tool-calling normalization (which providers/features grammar-guarantee schema-valid output vs. which only bias generation toward it), not general tool-calling feature parity. Distinct from, and does not re-research, `docs/upgrade-research/advanced-tool-calling-structured-output-2026-09-14.md` (parallel tool calls, `tool_choice` forcing-mode normalization, streaming delta shapes, the Bedrock first-attempt structured-output gap) — every finding in that document is treated as current except where explicitly corrected below.
**Method:** Findings 1-6 (2026-09-22): primary-source verification against each provider's own current documentation — Anthropic via the `claude-api` skill's shipped reference (`shared/tool-use-concepts.md`, cached against Anthropic's own docs), OpenAI via direct fetch of `developers.openai.com`'s Structured Outputs and Function Calling guides, Google via direct fetch of `ai.google.dev`'s structured-output and function-calling guides, and AWS Bedrock via two independent tool paths — generic `WebFetch` and the dedicated `aws-mcp` documentation server (`read_documentation`/`search_documentation`) — cross-checking the highest-stakes/most-surprising claims (Bedrock's `ToolSpecification.strict` field, its new top-level `outputConfig` Converse field) against both paths before treating them as real. No multi-agent adversarial vote was run this pass (unlike the sibling `gateway-2026-09-06.md`/`advanced-tool-calling-...` reports); confidence is stated per-finding based on source count and independent cross-checks instead. Findings 7-9 (2026-09-23): a separate, parallel 3-vote adversarial-verification research round (19 claims confirmed, 6 refuted — see the Caveats section for named refutations) against the same four providers' primary docs plus one academic source (arXiv:2608.10137, on the mechanics of grammar-constrained decoding), synthesized here and cross-checked directly against Kelvran's current code rather than taken at face value — this cross-check is what surfaced Finding 7, a correction to this document's own Executive Summary. Grounded throughout against Kelvran's real code (`gateway/internal/adapter/*/`) rather than its own doc comments' self-description — several of those comments are shown below to be stale relative to live provider docs.

## Executive summary

The four providers Kelvran adapts to all now converge on the *same* underlying taxonomy, confirmed independently against each one's own current documentation: **`tool_choice`/`toolChoice`/`tool_choice` forcing (which tool, or whether any tool, gets called) is a strictly orthogonal axis from schema-argument validity (whether the call's arguments are grammar-guaranteed to match the schema).** Every provider exposes two *separate* toggles — one for the final response shape, one for tool-call arguments — and forcing a tool call alone never implies its arguments are schema-valid. OpenAI's own function-calling guide states this most explicitly: `strict: true` "will ensure function calls reliably adhere to the function schema, instead of being best effort," and "Chat Completions requests remain non-strict by default" — non-strict is named, in OpenAI's own words, as *not* a guarantee. Anthropic's `strict: true` on a tool definition is described as a feature genuinely distinct from `tool_choice` forcing ("Strict tool use... Guarantee valid tool parameter schemas" vs. "tool_choice... requests tool-calling forcing behavior"). Gemini names a fourth `tool_choice` mode, `validated`, described in Google's own docs as making the "[m]odel ensure[] function schema adherence" — separate from `auto`/`any`/`none`, which govern only whether/which function is called. And AWS's Bedrock structured-output guide states the same split as two "complementary mechanisms": "JSON Schema output format" for the response, and "Strict tool use" (`toolSpec.strict`) for tool arguments — "These mechanisms can be used independently or together in the same request."

Kelvran's own canonical schema already has the right *shape* for the response-format half of this (`adapter.ResponseFormat`/`JSONSchema.Strict`) and the right shape for the tool-argument half (`adapter.ToolDef.Strict`) — but **both are wired for only 2 of 5 adapters** (OpenAI, openaicompat; see Finding 7 below, which corrects this Executive Summary's own earlier "wired for all 5 adapters" claim). `ToolDef.Strict` is wired for exactly one of five adapters (Anthropic). OpenAI's own native `FunctionDef` wire struct in `openai/openai.go` has no `Strict` field at all to receive it, despite OpenAI being the provider whose docs most explicitly name and describe the mechanism. Gemini's canonical `ToolChoice.Mode` enum has no value for Google's own `validated` mode at all, and Kelvran's Gemini adapter deliberately targets the legacy `functionCallingConfig` surface (`AUTO`/`ANY`/`NONE`) that predates it. Most surprisingly, two live AWS Bedrock Converse API capabilities — `ToolSpecification.strict` and a native top-level `outputConfig.textFormat` request field — directly contradict `bedrock.go`'s own doc comments, which assert (accurate as of Kelvran's last live-verification pass, 2026-09-13) that no such field exists; cross-checked against AWS's current API reference via two independent tool paths, both are now real, documented fields. Separately, Gemini's own adapter comment claiming its dialect has "no `$ref`/`$defs`" is now demonstrably stale: Google's current docs demonstrate a working self-referencing recursive schema via `"$ref": "#"` — meaning Gemini's actual recursion support sits with OpenAI's (both allow it) rather than with Anthropic's/Bedrock's (both explicitly forbid it), inverting the intuitive assumption that Gemini would be the narrowest dialect.

**Extended 2026-09-23** with a second, independent research pass (19 claims, 3-vote adversarial verification against each provider's own primary docs plus one academic source) answering the research question's other half — not "which Kelvran field is unwired" but "what does 'guarantee' actually mean, mechanically, across these four providers, and is a guarantee of schema *validity* the same thing as a guarantee of *unbiased* or *semantically correct* output." Short answer: no. OpenAI's own Structured Outputs guide claims the model "will always" adhere to the schema, in the same document that immediately discloses two named exceptions (safety refusals, `max_tokens` truncation) where the guarantee explicitly does not apply — refusals bypass schema validation entirely via a separate `refusal` field, not merely "close to failing" it. Underneath every provider's constrained-decoding mechanism (Anthropic's grammar-constrained sampling, OpenAI's/Bedrock's/Gemini's structurally equivalent token-masking implementations), a primary academic source proves structural-validity guarantees and distributional-fidelity guarantees are mathematically decoupled properties: masking is guaranteed only with respect to tokens already generated, never evaluates whether a token choice forecloses future grammar conformance, and can measurably distort a model's true output distribution (a worked example shows a uniform 1/17 probability collapsing to a forced ~1/2 for one degenerate output) — meaning "schema-valid, guaranteed" and "quality/probability-preserving" are two different claims every provider's own guarantee language conflates. New Findings 7-10 below cover this.

## Findings, ranked

### 1. Guarantee vs. forcing is a universal, feature-level (not provider-level) split — and Kelvran's per-model whitelist pattern only covers half of it (Foundational)

**What:** Confirmed independently against all four providers' own current docs: `tool_choice` (Anthropic/OpenAI/Bedrock)/`toolChoice` (Bedrock's wire key)/Gemini's `functionCallingConfig` govern *whether/which* tool is called; a *separate* per-tool or per-request flag governs whether the arguments are grammar-guaranteed valid. Neither implies the other. This is the organizing fact behind every other finding below.

**Why it matters for Kelvran specifically:** `adapter.SupportsStructuredOutput`/`BedrockModelSupportsForcedToolChoice`/`AnthropicModelRejectsForcedToolChoice` (`gateway/internal/adapter/capabilities.go`) already give Kelvran a real, working per-provider/per-model whitelist pattern for *forcing* support — but there is no equivalent whitelist for the *guarantee* axis. A caller who sets `ToolChoice: {Mode: "tool", ToolName: "x"}` today gets a guarantee that tool `x` gets called (or a real, typed error if the model can't force it) on every provider — but gets **zero** guarantee that `x`'s arguments are schema-valid on four of five adapters, with no signal that this is even a distinct axis from the caller's perspective.

**Consistent with settled decisions?** Extends, not revisits, `docs/upgrade-research/advanced-tool-calling-structured-output-2026-09-14.md`'s Finding 2 (now shipped, per `docs/rfcs/2026-09-14-gateway-tool-choice-normalization.md` and the real `ToolChoice`/`toolChoiceToProvider` code in all 5 adapters) — that RFC closed the *forcing* half of this gap; this report identifies that the *guarantee* half was never separately scoped.

**2026 primary-source grounding:**
- OpenAI: "Setting strict to true will ensure function calls reliably adhere to the function schema, instead of being best effort... Chat Completions requests remain non-strict by default" (`developers.openai.com/api/docs/guides/function-calling`, Strict mode section, fetched 2026-09-22).
- Anthropic: "Two features are available: JSON outputs (`output_config.format`)... Strict tool use (`strict: true`): Guarantee valid tool parameter schemas" — named as two independently-composable mechanisms, distinct from `tool_choice` (`claude-api` skill, `shared/tool-use-concepts.md` § Structured Outputs, and `shared/tool-use-concepts.md` § Tool Use Patterns: "Strict tool use (no beta): set `strict: true`... Guarantees `tool_use.input` validates exactly").
- Gemini: `tool_choice` mode `validated` — "Model ensures function schema adherence" — named separately from `auto`/`any`/`none`, which govern call occurrence only (`ai.google.dev/gemini-api/docs/function-calling`, fetched 2026-09-22).
- Bedrock: "Structured outputs... You can use structured outputs through two complementary mechanisms" — JSON Schema output format and strict tool use — "These mechanisms can be used independently or together in the same request" (`docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html`, fetched 2026-09-22, cross-checked via `aws-mcp`).

**Concrete next step:** No code change from this finding alone — it's the frame the next three findings hang off. Worth naming explicitly in `gateway/ARCHITECTURE.md` or a follow-on ADR so future work on either axis doesn't accidentally conflate them.

**Effort:** N/A (framing finding).

### 2. OpenAI: `adapter.ToolDef.Strict` is wired for response format but never reaches OpenAI's native tool definitions — and the native wire struct has no field to receive it (Small)

**What:** `adapter.ToolDef.Strict`'s own doc comment (`gateway/internal/adapter/types.go:229-240`) discloses this directly: "Read only by the Anthropic and Bedrock adapters... OpenAI/openaicompat/Gemini never read this field at all in v1, a named scope limit (OpenAI's own per-tool 'strict' flag is deliberately deferred, not wired)." Confirmed by direct grep of `openai/openai.go`: the only `.Strict` reference in the file is `Strict: rf.JSONSchema.Strict` (line 341, the response-format path); the tool-building loop (lines 284-341) never reads `t.Strict`. More fundamentally, OpenAI's own native `FunctionDef` struct (line 137-141) is `{Name, Description, Parameters}` — it doesn't even have a `Strict bool` field to assign into, unlike `ToolDefWire` (Kelvran's own canonical wire shape, which does carry `Strict`) or Anthropic's native `Tool` struct (which does, via `strictPtr`).

**Why it matters for Kelvran specifically:** this is the single most surprising asymmetry in the current codebase — OpenAI is the provider whose docs most explicitly name and describe the strict-tool-use mechanism ("leveraging our structured outputs feature," with a documented fallback-to-best-effort when a schema can't be normalized), and it's the one adapter where Kelvran's own canonical field for exactly this purpose is structurally unreachable, not merely unset.

**Consistent with settled decisions?** A disclosed, not accidental, v1 scope limit per `ToolDef.Strict`'s own comment — this finding confirms the limit is real (not stale) and gives the primary-source grounding for why it's now worth closing.

**2026 primary-source grounding:**
- "Setting `strict` to `true` will ensure function calls reliably adhere to the function schema... strict mode works by leveraging our structured outputs feature (with two schema requirements — `additionalProperties: false` and all properties marked `required`)... [falls back] to non-strict, best-effort function calling if the schema cannot be made compatible with strict mode" (`developers.openai.com/api/docs/guides/function-calling`, fetched 2026-09-22).
- Kelvran's own code: `gateway/internal/adapter/openai/openai.go:130-141` (`Tool`/`FunctionDef` structs, no `Strict` field); `gateway/internal/adapter/types.go:229-240` (`ToolDef.Strict`'s own disclosed scope-limit comment).

**Concrete next step:** add `Strict bool \`json:"strict,omitempty"\`` to `openai.FunctionDef`, and in the tool-building loop (`openai.go` ~line 286) set it from `t.Strict`. Live-verify against a real Chat Completions/Responses call first that OpenAI's `additionalProperties: false`/all-`required` requirements aren't silently violated by existing Kelvran callers' schemas (OpenAI's own SDKs auto-normalize; Kelvran's adapter currently does not) — mirrors the same "verify before wiring" discipline `bedrockEnsureAdditionalPropertiesFalse` already established for Bedrock. `openaicompat` (Ollama/llama.cpp/LocalAI) should stay out of scope for this specific fix — third-party OpenAI-compatible servers are not guaranteed to implement OpenAI's own strict-mode grammar compiler even where they accept the same wire field.

**Effort:** Small — one new struct field, one assignment, one live-verification call.

### 3. Gemini: no canonical path to `validated` mode at all — the legacy adapter surface has nothing to extend (Medium)

**What:** Unlike OpenAI/Bedrock (where the *field* already exists on the canonical schema, just unwired), Gemini has no equivalent at any layer. `adapter.ToolChoice.Mode` (`types.go`) supports only `auto`/`required`/`none`/`tool`. Kelvran's Gemini adapter (`gemini/gemini.go:155-200`) targets — by its own doc comment's admission — "the legacy, well-established `functionCallingConfig` surface (mode/allowedFunctionNames) deliberately, not a newer Interactions-API mode this adapter's own live wire-format target was not confirmed against." `toolChoiceToProvider` (lines 181-199) maps `auto`/`required`/`none`/`tool` to `AUTO`/`ANY`/`NONE`/`ANY`+allow-list — there is no fifth case, and no wire shape exists in `FunctionCallingConfig` (`Mode string`, `AllowedFunctionNames []string`) to carry a `validated` value even if the canonical enum grew one.

**Why it matters for Kelvran specifically:** this directly answers Open Question 3 from `docs/upgrade-research/advanced-tool-calling-structured-output-2026-09-14.md` ("Does Kelvran's Gemini adapter target the older `function_calling_config` ... or the newer Interactions API ... — this determines whether Finding 2's Gemini mapping needs to support the fourth `validated` mode from day one") — confirmed by direct code read: it targets the legacy surface, and the newer mode was never in scope. Of the four providers, Gemini is the only one where Kelvran callers have **no way at all** — not even an unwired field — to request guaranteed-valid tool-call arguments.

**Consistent with settled decisions?** Not a regression — the 2026-09-14 RFC's own "Unresolved Questions" section already flagged this as unconfirmed scope, per `gemini.go`'s comment. This finding closes that open question with a definitive "legacy surface, `validated` never in scope" answer and supplies the primary-source grounding for what closing it would require.

**2026 primary-source grounding:**
- `validated`: "Model ensures function schema adherence" (`ai.google.dev/gemini-api/docs/function-calling`, fetched 2026-09-22) — the only description given; the page doesn't state the underlying mechanism (constrained decoding vs. post-hoc validation/retry).
- `auto`/`any`/`none` carry no argument-validity guarantee language at all in Google's docs — confirmed by the same fetch: "the page gives no explicit guarantee language about argument schema conformance [for these three]... only describes decision behavior."
- Kelvran's own code: `gateway/internal/adapter/gemini/gemini.go:155-200`, doc comment on `ToolConfigWire` explicitly naming the legacy-vs-Interactions-API scope gap.

**Concrete next step:** before any code change, resolve whether Kelvran's Gemini adapter should migrate to the newer Interactions API surface at all (a materially bigger decision than this finding alone justifies — the legacy surface may still be the right choice for other reasons not investigated here). If it does migrate, add a `validated` value to `adapter.ToolChoice.Mode` and the corresponding wire shape; if it doesn't, disclose the gap explicitly (e.g. in `THREAT_MODEL.md`'s existing Gateway Elevation-of-Privilege framing, since a caller believing `tool_choice: "tool"` implies schema-valid arguments — a reasonable inference given Anthropic/OpenAI/Bedrock's own naming — would be wrong for Gemini specifically, with zero error and zero signal).

**Effort:** Medium — genuinely new canonical enum value + wire shape + an adapter-migration decision this report doesn't itself resolve.

### 4. Bedrock Converse: two live AWS API capabilities post-date Kelvran's last live-verification pass and directly falsify `bedrock.go`'s own doc comments (Medium-Large)

**What:** Two independent, current (2026-09-22) AWS API reference facts, each cross-checked via both generic `WebFetch` and the dedicated `aws-mcp` documentation server before being treated as real:

1. **`ToolSpecification.strict` is now a real, documented field.** AWS's own reference: "**strict**: Flag to enable structured output enforcement on a tool usage response. Type: Boolean. Required: No" (`docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolSpecification.html`). This directly contradicts `bedrock.go`'s `ToolSpec` struct's own doc comment: "Deliberately has no Strict field: unlike Anthropic's direct Messages API... no per-tool 'strict' wire shape for Converse's toolSpec is confirmed real... adapter.ToolDef.Strict is therefore read only by the Anthropic adapter in v1; Bedrock is a named scope limit, not an oversight." That comment was accurate as of Kelvran's own stated live-verification date (2026-09-13); it is not accurate today. AWS's structured-output userguide's worked example confirms the real request shape: `toolConfig.tools[].toolSpec.strict: true`, sibling to `name`/`description`/`inputSchema`.
2. **A native, top-level `outputConfig.textFormat` Converse request field now exists**, confirmed against `Converse`'s own real Request Syntax block (`API_runtime_Converse.html`): `"outputConfig": {"textFormat": {"structure": {...}, "type": "string"}}` — a sibling of `toolConfig`/`inferenceConfig`, *not* nested under `additionalModelRequestFields`. AWS's structured-output userguide states the field is API-shape-specific, not old-vs-new: "For InvokeModel API with Anthropic Claude models, use the `output_config.format` request field... For Converse APIs, use the `outputConfig.textFormat` request field." Kelvran's `additionalModelRequestFieldsFor` (`bedrock.go:672-701`) builds `{"output_config": {"format": {...}}}` inside `additionalModelRequestFields` for its Converse-only adapter — the `output_config.format` shape AWS's own current docs say belongs to InvokeModel-against-Anthropic-Claude, not Converse.

**Why it matters for Kelvran specifically:** `bedrock.go` is unusually rigorous about only claiming a wire shape is real once live-verified against an actual Converse call (`bedrockEnsureAdditionalPropertiesFalse`'s own comment: "live-verified 2026-09-13 against a real Converse call"). That discipline is exactly why these two findings matter — they're not speculative, they're the same category of fact that discipline exists to catch, just on the other side of the same 9-day-old verification pass. Item 1 means Kelvran's Bedrock adapter has zero path to schema-guaranteed tool-call arguments today, on a real, live, currently-shipping AWS field. Item 2 means Kelvran's existing structured-output support may be using the wrong Converse-specific field name entirely (not a deprecated fallback — a mismatched-API-shape bug, per AWS's own "for Converse APIs, use..." framing), separate from and worse than the already-disclosed first-attempt-whitelist gap in the 2026-09-14 report.

**Consistent with settled decisions?** Neither item revisits a decision — both are new facts about AWS's own API surface that didn't exist (or weren't documented) as of Kelvran's last verification pass. Item 1 directly extends `docs/rfcs/2026-09-14-gateway-tool-choice-normalization.md`'s own established pattern (per-model whitelist for Bedrock capability gating) to a capability that RFC didn't know existed yet.

**2026 primary-source grounding:**
- `ToolSpecification.strict`: `docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolSpecification.html`, confirmed via `aws-mcp read_documentation` (full field list: `inputSchema`, `name`, `description`, `strict`) — independent of the generic `WebFetch` pass that surfaced the userguide's worked JSON example showing the same field in context.
- `Converse`'s real request syntax including top-level `outputConfig`: `docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html`, confirmed via `aws-mcp read_documentation`'s direct fetch of the page's actual "Request Syntax" code block, and independently via `aws-mcp search_documentation`'s verbatim page-chunk return for the same field.
- `OutputConfig.textFormat` → `OutputFormat` object: `docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_OutputConfig.html`, confirmed via `aws-mcp read_documentation`.
- API-shape-specific field naming ("For Converse APIs, use the `outputConfig.textFormat` request field"): `docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html`, fetched via `WebFetch`.
- Kelvran's own code: `gateway/internal/adapter/bedrock/bedrock.go:339-353` (`ToolSpec`'s "deliberately has no Strict field" comment), `bedrock.go:672-701` (`additionalModelRequestFieldsFor`, the `additionalModelRequestFields`-nested shape).

**Concrete next step:** two independently-shippable fixes, both requiring a real live Converse call to confirm before merging (matching `bedrock.go`'s own established verification bar):
1. Add `Strict bool \`json:"strict,omitempty"\`` to `bedrock.ToolSpec` and wire it from `adapter.ToolDef.Strict`, gated behind a fresh per-model whitelist function (AWS's `ToolSpecification` reference names no model restriction for `strict`, unlike `SpecificToolChoice`'s explicit "Claude 3 and Nova only" — but that *absence* of a stated restriction should not be trusted without a live call, per this codebase's own norm).
2. Live-verify whether migrating `additionalModelRequestFieldsFor` from the `additionalModelRequestFields.output_config.format` shape to a native top-level `outputConfig.textFormat` field changes model-support scope (the userguide no longer names a small whitelist for this field the way `bedrockStructuredOutputModelSubstrings` does — it instead points to a live "models at a glance" page) — if the native field is more broadly supported, the existing 5-substring whitelist may now be needlessly narrow.

**Effort:** Medium-Large — two independent AWS API changes to verify and adopt, one of which (`outputConfig.textFormat`) may also require re-deriving the model-whitelist logic rather than just adding a field.

### 5. Bedrock's `$ref` rejection is a disclosed over-approximation broader than AWS's own stated restriction — worth re-verifying, not yet a confirmed bug (Small)

**What:** `bedrockUnsupportedSchemaFeature` (`bedrock.go:711-770`) rejects **any** `$ref` in a caller's schema, with its own comment explaining why: "`$ref` covers both of AWS's own named 'recursive schemas' and 'external `$ref` references' restrictions — Kelvran has no schema-graph-cycle detector to tell a genuinely-recursive `$ref` apart from a merely-local one, so any `$ref` at all is treated as unsupported." AWS's *current* structured-output userguide states a narrower restriction than what Kelvran enforces: `$ref`, `$def`, and `definitions` are explicitly listed under **Supported** JSON Schema features ("internal references only"), and only "Recursive schemas" and "External `$ref` references" appear under **Not supported** — i.e. AWS's own docs say a purely local, non-recursive `$ref` (e.g. reusing a `$defs` sub-schema twice within the same document) is fine; Kelvran's linter currently rejects it anyway.

**Why it matters for Kelvran specifically:** this is the inverse of Finding 4 — not a missing capability, but a real, disclosed, deliberate *over*-rejection that may now be stricter than necessary. Anthropic's own direct-API dialect (from the `claude-api` skill: "`$ref`/`$def`" listed under Supported) independently corroborates that local `$ref` reuse is a normal, expected pattern across this model family's structured-output tooling, not an edge case.

**Consistent with settled decisions?** The over-approximation was explicit and deliberate ("a real, checkable, narrower subset... Kelvran has no schema-graph-cycle detector"), not an oversight — this finding doesn't dispute that reasoning, only supplies fresh primary-source detail (AWS's own "internal references only" carve-out) that narrows how much rejection is actually justified by AWS's own stated rule.

**2026 primary-source grounding:**
- Bedrock supported: "`$ref`, `$def`, and `definitions` (internal references only)"; not supported: "Recursive schemas... External `$ref` references" (`docs.aws.amazon.com/bedrock/latest/userguide/structured-output.html`, fetched 2026-09-22 — this is an updated, more specific list than the "External `$ref` references" phrasing alone the 2026-09-14 report cited, now explicitly distinguishing internal-vs-external rather than banning `$ref` wholesale).
- Anthropic supported: `enum`, `const`, `anyOf`, `allOf`, `$ref`/`$def` (`claude-api` skill, `shared/tool-use-concepts.md` § JSON Schema Limitations).
- Kelvran's own code: `bedrock.go:711-731` (`bedrockUnsupportedSchemaKeys`/`bedrockUnsupportedSchemaFeature`).

**Concrete next step:** **not** an immediate fix — building a cycle/locality detector to distinguish internal-non-recursive `$ref` from external/recursive `$ref` is real, nontrivial scope (exactly the kind of thing Kelvran's own comment already declined to build without evidence it's needed). The cheap next step is a single live Converse call with a schema using one local, non-recursive `$defs` reference, to confirm AWS's documented "internal references only" carve-out actually behaves as described before investing in the detector — mirrors this codebase's own "verify against a real call before trusting a doc" convention.

**Effort:** Small (verification call) now; Medium-Large (cycle detector) only if the verification confirms real value is being left on the table.

### 6. Gemini's adapter comment claiming "no `$ref`/`$defs`" is stale — Google's current docs demonstrate working recursive schemas (Small)

**What:** `gemini.go`'s `GenerationConfig` doc comment states: "Gemini's own `response_schema` uses an OpenAPI-3.0-SUBSET schema dialect, not full JSON Schema (e.g. no `\"$ref\"`/`\"$defs\"`, a narrower keyword set)." Google's current `ai.google.dev/gemini-api/docs/structured-output` page (fetched twice independently in this pass, once generally and once specifically targeting `$ref` usage) demonstrates a working "Recursive Structures" example: an `Employee` object schema whose `reports` array `items` field is `{"$ref": "#"}` — a self-referencing recursive schema, working today, with no caveat attached to that specific example. The page's only related caveat is a general one ("Not all JSON Schema features are supported... Very large or deeply nested schemas may be rejected"), never naming `$ref`/`$defs` as unsupported.

**Why it matters for Kelvran specifically:** this inverts the intuitive ranking. Kelvran's own comment implies Gemini has the *narrowest* schema dialect of the four providers; on recursion specifically, the opposite is true — Gemini and OpenAI (which documents recursive self-reference via `$ref`) both support it, while Anthropic and Bedrock (both otherwise the more "mature"/explicit structured-output implementations per Finding 1) both explicitly forbid it. A caller schema using recursion that Kelvran's Bedrock linter would reject outright (Finding 5) would actually work unmodified against Gemini today — a real, checkable cross-provider capability asymmetry the current comment obscures rather than reveals.

**Consistent with settled decisions?** A real instance of the doc-vs-code staleness pattern `AGENTS.md`'s own Gotchas section already names as a recurring defect class ("A doc... asserting a capability/status in the present tense after the code it described was deferred, narrowed, or never matched — recurred 6 times by 2026-09-04... Mitigation: when a feature ships/narrows/defers, grep every `*.md` [or comment] for its keyword"). This is the same pattern surfacing in a `.go` doc comment rather than a `.md` file.

**2026 primary-source grounding:**
- Recursive org-chart example using `"items": {"$ref": "#"}`, and the page's only limitation language being a general "not all features supported" caveat with no `$ref`-specific exclusion — `ai.google.dev/gemini-api/docs/structured-output`, fetched twice independently 2026-09-22 (once general, once specifically targeting `$ref` usage, to rule out a fetch-summarization artifact given this session's own prior caution about re-verifying bleeding-edge specifics).
- Kelvran's own code: `gateway/internal/adapter/gemini/gemini.go:136-147` (`GenerationConfig`'s "no `$ref`/`$defs`" comment).

**Concrete next step:** correct the comment (this alone is the fix — the adapter code itself already passes `JSONSchema.Schema` through verbatim, unparsed and unvalidated, per its own "request-shape normalization only" scope, so no behavioral change is needed, only the comment's factual claim). Worth a quick live call with a recursive schema to confirm before editing, given this is exactly the class of claim this report is asking future readers not to trust without verification.

**Effort:** Small — comment correction, optionally preceded by one live-verification call.

### 8. Provider "guarantee" language routinely overstates the guarantee's own documented scope — OpenAI's Structured Outputs guide is the clearest example (Medium)

**What:** OpenAI's own Structured Outputs guide states, in an opening/benefits section, that the feature "ensures the model will always generate responses that adhere to your supplied JSON Schema" — unqualified, framed as a "Reliable type-safety" benefit implying no caller-side retry/validation is needed. The same guide's own "Handle edge cases" section immediately names two real exceptions where this is false: the model refusing to answer for safety reasons, and hitting a `max_tokens` limit mid-generation (truncation). Critically, a refusal is not merely "close to" violating the schema — OpenAI's API surfaces it as a structurally separate `refusal` field/content-block (`type: refusal`), meaning schema enforcement doesn't apply to it *at all*, not that enforcement weakens under refusal. Anthropic's, Google's, and AWS's docs show the identical pattern in miniature: Anthropic's own `tool_choice` "missing required parameters" accordion states model behavior there "is not guaranteed, especially for more ambiguous prompts and for less capable models" (an explicit, named non-guarantee for the *non-strict* default path, contrasted against the same page's `strict: true` guarantee callout one section above); Google's Gemini structured-output docs never claim an unconditional guarantee in the first place, instead disclosing a schema-complexity ceiling ("very large or deeply nested schemas may be rejected") and telling callers to add their own "error handling for schema-compliant but semantically incorrect outputs" — i.e. syntactic validity and semantic correctness are explicitly two different, separately-disclaimed guarantees.

**Why it matters for Kelvran specifically:** Kelvran is itself a place where this exact overstatement risk recurs one layer down — `JSONSchema.Strict`'s and `ToolDef.Strict`'s own doc comments currently describe what `Strict: true` *requests* without stating, per adapter, what happens on the *false*/default path (silently proceeds unconstrained, per-provider best-effort, or errors) — the same "guarantee language undocumented for the non-guaranteed default" gap OpenAI's own docs at least partially close (by naming refusal/truncation explicitly) and Kelvran's comments currently don't. This is a documentation-completeness lesson external to any specific code fix: whichever finding above (2, 4, 7) ends up wiring a `Strict` field further, the accompanying doc comment should name what happens when it's unset/false or unsupported by the target provider/model, not just what happens when it's true.

**Consistent with settled decisions?** New landscape context, not a revisit — no prior Kelvran doc makes an "always"-style overclaim about `Strict`'s guarantee scope today (the existing comments are notably hedged, e.g. `ToolChoice`'s own doc comment already names per-model rejection cases). This finding is preventative: the risk pattern is real across the entire industry, and worth naming before Kelvran's own docs drift toward it as `Strict` wiring expands per Findings 2/4/7.

**2026 primary-source grounding:**
- OpenAI: "the model will always generate responses that adhere to your supplied JSON Schema" (benefits framing) vs. "the model might not generate a valid response that matches the provided JSON schema" / "a refusal does not necessarily follow the schema you have supplied" (edge-case section), `developers.openai.com/api/docs/guides/structured-outputs`, fetched 2026-09-22.
- Anthropic: "This behavior is not guaranteed, especially for more ambiguous prompts and for less capable models," immediately below a `strict: true` guarantee callout, `platform.claude.com/docs/en/agents-and-tools/tool-use/overview`.
- Google: "Very large or deeply nested schemas may be rejected" / "Implement robust error handling for schema-compliant but semantically incorrect outputs," `ai.google.dev/gemini-api/docs/structured-output`.

**Concrete next step:** when next touching `JSONSchema.Strict`/`ToolDef.Strict`'s doc comments (Findings 2, 4, 7), add an explicit "what happens when unset/unsupported" clause per adapter, mirroring the precision OpenAI's own "Handle edge cases" section models (name the specific failure modes, don't just describe the happy path).

**Effort:** Medium — a documentation-discipline change spanning several existing comments, not a single code fix; naturally bundled into Findings 2/4/7's own work rather than a standalone PR.

### 9. The guarantee mechanism itself — grammar-constrained decoding / token-masking — provably guarantees structural validity only, never distributional fidelity; "schema-valid" and "unbiased" are decoupled properties every provider's language conflates (High, informational)

**What:** A primary academic source (Özgü, Wu, Van den Broeck, Kim — UCLA StarAI lab, arXiv:2608.10137, Aug 2026) proves the mechanism underlying every provider's "guarantee" claim (Anthropic's grammar-constrained sampling, and the structurally equivalent token-masking approaches OpenAI/Gemini/Bedrock's own constrained decoding implementations use) has a specific, provable limitation: existing grammar-constrained decoding (GCD) "guarantees grammar conformance only with respect to tokens generated so far, ignoring each token's effect on future grammar conformance" — masking is backward-looking only. This forces real distributional distortion: the paper's own worked example (a 5-bit regular-language grammar with exactly 17 valid strings out of 32 possible, each with a true uniform probability of 1/17) shows a masked decoder can be forced into a single degenerate output with probability ~1/2 instead of the mathematically-correct 1/17, purely as an artifact of masking's backward-looking-only guarantee — every output produced is still schema-valid, but the *distribution* over valid outputs is arbitrarily distorted.

**Why it matters for Kelvran specifically:** this is the mechanistic reason "guaranteed schema-valid" (what `Strict: true`/strict tool use/structured outputs all actually promise, per Finding 1's confirmed cross-provider taxonomy) is not the same claim as "guaranteed unbiased," "guaranteed high-quality," or "guaranteed semantically correct" — three claims no provider reviewed in this report or its sibling makes, and Google's Gemini docs explicitly disclaim ("always validate values in your application" for schema-compliant-but-wrong output). For Kelvran, this means: closing Findings 2/4/7 (wiring `Strict` further) genuinely does deliver on the schema-*validity* promise those fields make — that promise is real and mechanistically sound, not marketing — but callers should not be led to believe (and Kelvran's own docs should not imply) that `Strict: true` additionally protects against a lower-quality or biased-toward-degenerate-output completion; that is a separate, unaddressed axis no provider's `strict`/`json_schema` flag touches.

**Consistent with settled decisions?** New context, no prior Kelvran document conflates these two properties — worth stating explicitly now, before any future doc (e.g. a public-facing description of Kelvran's own `Strict` pass-through) does.

**2026 primary-source grounding:**
- "Existing GCD methods guarantee grammar conformance only with respect to tokens generated so far, ignoring each token's effect on future grammar conformance and distorting the LM's probability distribution by forcing it into a token domain its training never covered" — arXiv:2608.10137, §1/§2 (fetched and PDF-extracted directly, 2026-09-22).
- The 5-bit/17-valid-string worked example (Section 2, "Characterizing the Probability Drift") — same source.
- Corroborating ecosystem evidence that this is a known, designed-around limitation, not a novel claim: Instructor's "reask handlers" (`python.useinstructor.com/concepts/retrying/`) explicitly frame failed-attempt recovery as sending validation errors back to the model for "progressive corrections" — a feedback loop, not a guarantee mechanism, precisely because constrained decoding isn't available/enabled for every model Instructor targets; LiteLLM's `enable_json_schema_validation` (`docs.litellm.ai/docs/completion/json_mode`) is an explicitly opt-in, client-side, post-hoc JSON-schema validator for exactly the models LiteLLM's own docs say lack native `json_schema` support — both tools' own designs tacitly confirm that a provider-side structural guarantee, where it exists at all, is the *only* hard guarantee available; everything else in the ecosystem is best-effort-plus-retry.

**Concrete next step:** none — informational/framing finding, same category as Finding 1. Worth citing if Kelvran ever documents `Strict`'s guarantee scope for external callers (see Finding 8's concrete next step).

**Effort:** N/A (framing finding).
