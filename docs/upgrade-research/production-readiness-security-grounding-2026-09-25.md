# Kelvran Gateway — Production-Readiness & Security Grounding for the 2026-09-25 Live Dry Run

**Date:** 2026-09-25
**Scope:** `gateway/` — grounding the same-day end-to-end live dry run (real AWS Bedrock traffic through the actual running gateway: buffered completions, L1 cache hits, streaming, guardrail blocking, budget enforcement, real concurrent rate-limiting, real WRR fallback-on-503) against current (2026) real-world production-readiness practice and disclosed security incidents in comparable self-hosted LLM gateways.
**Method:** This was **not** run through the repo's own multi-agent `/deep-research` workflow — that skill is locked to explicit user invocation and cannot be triggered programmatically from within a session. Instead: 3 targeted `mcp__exa__web_search_exa` queries (production-readiness checklists for self-hosted LLM gateways; disclosed 2026 security incidents in comparable gateways; fallback/WRR/budget-accounting postmortems), followed by direct verification of every claim worth cross-checking against Kelvran's actual current source (not the search results' own framing) — reading `cmd/gateway/main.go`, `internal/gateway/dataplane/dataplane.go`, `internal/identity/`, and `.github/workflows/ci.yml` directly. Findings below are only the ones that survived that direct-code cross-check; several initial search hits are noted in Caveats as *not* applying once checked against Kelvran's real code.

---

## Executive summary

The single most consequential grounding this round produced is the 2026 LiteLLM incident chain (PyPI supply-chain poisoning via a compromised Trivy CI dependency; a pre-auth SQL injection in bearer-token lookup; an "unauthenticated requests get `PROXY_ADMIN` by default" fail-open bug; an MCP-endpoint auth bypass) — not because Kelvran shares any of these specific bugs, but because it is the clearest evidence available that **AI gateways are now a named, actively-exploited high-value target class**, and every one of LiteLLM's root causes has a direct, checkable analog in Kelvran's own architecture. Checking each analog directly against Kelvran's current code found Kelvran already closes three of the four: CI dependency pinning is full-SHA (not floating-tag) across every GitHub Action including its own use of `trivy-action`, closing the exact vector that compromised LiteLLM's pipeline; there is no SQL anywhere in `internal/identity`, so the SQL-injection vector class is architecturally absent, not merely patched; and the admin API fails *closed*, not open — no `admin.token_env` set means no admin server starts at all (verified live in today's dry run: `404` on every admin route with zero admin log lines). The fourth — MCP-endpoint auth — doesn't yet apply, since Kelvran has no inbound MCP server surface today (only the outbound-credential-brokering RFC scoped 2026-09-25).

The other genuinely new finding is a real, if minor, operational gap: `/healthz` is *deliberately* liveness-only by its own doc comment ("a health check that depends on a third-party API being reachable defeats its own purpose"), which is a defensible design choice — but a 2026 LiteLLM-monitoring postmortem found this exact pattern (liveness returning 200 while every routed request fails) to be the single most common real-world LLM-gateway monitoring blind spot. Kelvran already has the machinery to close this cheaply (the existing deployment probe loop), it just isn't exposed as a separate readiness/smoke signal today.

Two search-surfaced concerns turned out, on direct code inspection, to already be non-issues: gateway-level upstream timeouts (both the non-streaming 60s bound and the streaming idle-timeout were already fixed in a prior session, per `dataplane.go`'s own doc comment citing the chaos-regression corpus that found the original gap) and cache-pinning-under-fallback (Kelvran's fallback is same-canonical-model/different-deployment, not cross-alias, so sharing a cache entry across the working and broken deployment is correct by design, not a leak — a materially different shape from the cross-alias pinning bug the search grounding describes in other gateways).

## Findings, ranked

### 1. AI gateways are a confirmed 2026 high-value attack target — cross-check every LiteLLM root cause against Kelvran's own analog (informational, no action needed on 3 of 4)

**What:** 2026 disclosed a cascading chain of critical LiteLLM vulnerabilities: a March 2026 PyPI supply-chain compromise (CVE-2026-33634, CVSS 9.4 — attackers compromised the Trivy scanner in LiteLLM's own CI/CD pipeline via unpinned tool installation, stole PyPI publish credentials, and shipped a credential-stealing payload in `litellm==1.82.7`/`1.82.8` that ran on every Python interpreter startup via a `.pth` file); a pre-auth SQL injection (CVE-2026-42208, CVSS 9.3 — the bearer-token lookup passed the token directly into an unparameterized SQL query *before* the auth decision was made); an "unauthenticated requests default to `PROXY_ADMIN`" fail-open bug (no CVE, fixed alongside CVE-2026-59821); and an MCP-endpoint auth bypass (CVE-2026-59822) chained with a Starlette host-header bypass (CVE-2026-48710) for unauthenticated RCE (CVSS 10.0, added to CISA's KEV catalog).

**Why it matters for Kelvran specifically:** Kelvran is architecturally similar enough to LiteLLM (centralized multi-provider proxy, holds every upstream provider credential, per-tenant virtual keys, budget enforcement, admin API) that each LiteLLM root cause has a direct analog worth checking — not assuming immunity by architecture difference, but confirming it.

**Direct verification against Kelvran's current code (2026-09-25):**
- **Supply-chain/CI tool pinning** — checked `.github/workflows/ci.yml` directly: every single `uses:` GitHub Action reference is pinned to a full commit SHA with a version comment (e.g. `aquasecurity/trivy-action@ed142fd0673e97e23eac54620cfb913e5ce36c25 # v0.36.0`), never a floating tag. This is the exact mitigation that would have prevented LiteLLM's incident — the attack there depended on force-pushing malicious tags across Trivy's own releases, which has no effect on a consumer pinned to a specific commit SHA. **Already closed, not by accident** — this is standard supply-chain hygiene already in place.
- **SQL injection in auth lookup** — grepped `internal/identity/` for `database/sql`, raw SQL strings, `gorm`, `sqlx`: zero hits. Kelvran's identity/virtual-key storage is `boltstore`/`redisstore` (key-value), not a SQL backend, so this entire vulnerability *class* is architecturally absent for the auth lookup path, not merely defended against.
- **Unauthenticated-admin-by-default** — read `cmd/gateway/main.go`'s admin-server bring-up directly: the admin `*http.Server` is `nil` unless `cfg.Admin.TokenEnv` is set, and if it's set but resolves to an empty env var, startup itself fails with an explicit error ("refusing to start an unauthenticated admin server") rather than falling back to open access. Confirmed live in today's dry run — the pilot config has no `admin:` block at all, and every admin route returned a clean `404` with zero admin-related log lines. **Fails closed, matching the safer of the two designs LiteLLM eventually converged on after its incident.**
- **MCP endpoint auth bypass** — doesn't yet apply: Kelvran has no inbound MCP *server* surface today (searched for `mcp-rest`/`mcp_endpoints`-shaped routes, found none); the only MCP-related work is the outbound-credential-brokering design scoped in `docs/rfcs/2026-09-11-gateway-mcp-outbound-credential-design.md` (design-only, unbuilt). This is a non-issue purely because the relevant surface doesn't exist yet, not because it was defended against — worth re-checking this specific cross-check again if/when that RFC is ever built.

**Concrete next step:** none required right now — this is a today-only confirmation, not a backlog item. Re-run this specific cross-check (CI pinning, identity SQL-absence, admin fail-closed default, MCP auth) any time a new dependency-installing CI step, a new identity backend, or the outbound-MCP RFC gets built, since each is a place a future change could silently reintroduce one of these four root causes.

**Effort:** None (informational confirmation only).

### 2. `/healthz` is deliberately liveness-only — a real, disclosed 2026 monitoring blind spot for exactly this pattern (Small)

**What:** `cmd/gateway/main.go`'s `healthzHandler` has an explicit doc comment: "a shallow liveness/readiness probe — it reports only that this process is up and serving, never upstream provider reachability, per `docs/operations/DEPLOY.md`'s own reasoning: a health check that depends on a third-party API being reachable defeats its own purpose." This is a deliberate, reasoned design choice, not an oversight.

**Why it matters for Kelvran specifically:** a 2026 production-monitoring postmortem for LiteLLM (a directly comparable gateway) found this *exact* pattern — `/health/liveliness` returning `200` while every routed request fails — to be the most common real-world LLM-gateway monitoring gap: "the proxy process is alive; every routed request fails. No monitor checked `/health/readiness` or the backend URL." Kelvran's own reasoning for keeping `/healthz` decoupled from provider reachability is still correct (an unrelated Bedrock outage shouldn't make Kubernetes restart a healthy gateway process) — but the postmortem shows that decoupling only avoids one failure mode (false unhealthy) while leaving the opposite one (false healthy during a real routing failure — e.g. a misconfigured `access_key_id_env`, a revoked IAM credential, or an exhausted rate limit on the AWS side) with zero dedicated signal today.

**Consistent with settled decisions?** Does not contradict `docs/operations/DEPLOY.md`'s existing reasoning — narrows it. The fix is a *second*, separate endpoint, not a change to `/healthz` itself, so the original design's own stated goal (liveness never coupled to a third party) is preserved exactly.

**Concrete next step:** Kelvran already has the raw signal this needs — the existing deployment probe loop (`internal/gateway/dataplane/dataplane.go`'s `ProbeDeployments`/`probeOneDeployment`, which makes a real timed call per configured deployment on a ticker). Expose a new `/readyz` that reports the probe loop's own last-known aggregate health state per canonical model — 200 with a per-model breakdown if every configured model has at least one healthy deployment, 503 if any model has none — with zero new network calls, since the probe loop already makes them. **Built 2026-09-25** (`Pipeline.ReadinessSummary`, `readyzHandler`, `cmd/gateway/main.go`) — point an **external monitor** at this endpoint, matching the search grounding's own recommended split (liveness for restart decisions, a separate smoke/readiness check for "can real traffic actually be served"). Deliberately **not** wired as the Kubernetes pod `readinessProbe` in `deploy/k8s/base/deployment.yaml` (which still correctly points at `/healthz` for both liveness and readiness, per that manifest's own existing comment) — `/readyz`'s "unready if ANY configured canonical model has zero healthy deployments" semantic is pod-wide, so wiring it as the k8s readiness probe would empty the Service's entire `EndpointSlice` the moment even one model (out of potentially many this gateway serves) loses every deployment, cutting off traffic for every OTHER, perfectly healthy model too — precisely the same "shared-dependency-readiness anti-pattern, worse than doing nothing" blast-radius risk that manifest's own comment already warns against, just from a different specific cause. See `docs/operations/DEPLOY.md`'s matching correction for the full reasoning.

**Effort:** Small — one new handler reading existing probe-loop state; no new upstream calls, no config schema change needed if defaulted to always-on.

### 3. Two search-surfaced concerns already resolved in Kelvran's current code — confirmed non-issues, recorded so they aren't re-investigated later

**Gateway-level request timeout, independent of the provider SDK's own timeout** — search grounding (AgentsCamp's 2026 LLM-production checklist, an independent LLM-gateway architecture writeup) both call a missing gateway-level timeout "the most common production incident" for exactly this class of service: a slow/hanging upstream response occupying a connection/thread indefinitely. Checked `dataplane.go` directly: the non-streaming upstream caller already has a 60-second whole-call bound, and the streaming caller has a purpose-built *idle*-timeout (resets on every real chunk of forward progress, rather than a naive whole-call bound that would kill a slow-but-healthy long stream) — both fixed in a prior session specifically because a chaos-regression-corpus test (`evals/tests/fixtures/regression_corpus_routing_chaos.json`'s `"chaos-streaming-no-upstream-timeout-gap"` case) found the original gap. **No action needed** — Kelvran is already ahead of the generic checklist item here, including correctly avoiding the naive fixed-timeout mistake for streaming that the generic advice doesn't distinguish.

**Fallback response cache-pinning** — one search result (an `llm-gateway` project README) documents a real bug class: "a fallback's response is not stored under the primary's key... doing so would serve the stand-in to every later request for that alias until the entry expired, silently pinning traffic to it long after the primary recovered." On inspection this doesn't apply to Kelvran's own fallback shape: Kelvran's WRR fallback (proven live today) routes between deployments that share the *same canonical model* (`claude-haiku-4-5-bedrock` and `claude-haiku-4-5-bedrock-broken` both serve canonical model `claude-haiku-4-5`) — the cache key is already keyed on the canonical model/request content, not on which specific deployment answered, so sharing a cache entry across a fallback is the *intended*, correct behavior for this design, not a leak. The bug the search result describes only applies to gateways whose fallback can cross to a semantically-different alias/model — a shape Kelvran's own WRR design (same-canonical-model deployments only) doesn't have.

**Effort:** None (both are confirmations, not action items).

## Top takeaways

1. Kelvran's supply-chain, auth-lookup-architecture, and admin-fail-closed posture already independently match the fixes LiteLLM was forced to make reactively after real 2026 incidents — worth stating plainly in `SECURITY.md` as a positive, verified claim rather than leaving it undocumented.
2. The one real gap found (`/healthz` liveness-only, no dedicated readiness/smoke signal) is Small effort and has its data source already built (the probe loop) — the lowest-friction real finding from this whole grounding pass.
3. Both of the other search-surfaced "generic best practice" gaps turned out to be already-fixed non-issues once checked against Kelvran's actual current code, not the search results' own framing — reinforcing this project's own repeated lesson (`AGENTS.md`'s Gotchas section) that a claim needs a direct code check, not just a plausible-sounding external source, before being trusted.

## Caveats

- This grounding used ordinary web search (`mcp__exa__web_search_exa`), not the repo's own `/deep-research` multi-agent workflow — that skill explicitly cannot be invoked programmatically from within a session (`disable-model-invocation`), and this document does not attempt to replicate its adversarial multi-source verification methodology. Treat this as a single-pass search-and-verify grounding, not the same rigor as e.g. `gateway-2026-09-06.md`'s 3-vote adversarial `/deep-research` sweep.
- Coverage is necessarily narrow — 3 targeted queries, not an exhaustive sweep. Areas like semantic-cache poisoning, prompt-injection-via-tool-use, and cost-based routing were not re-covered here since they were already grounded in this session's earlier 2026-09-25 5-topic research round.
- The LiteLLM incident chain is the single most load-bearing source in this document; it is well-corroborated across five independently-published sources (Tencent Zhuque Lab, Wiz, Cloud Security Alliance, NVD/CVE records, Ferentin) with consistent CVE numbers and technical detail, which is why it's treated as reliable grounding rather than a single unverified blog claim.
