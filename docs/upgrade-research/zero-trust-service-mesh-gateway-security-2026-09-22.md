## Executive Summary

Kelvran's gateway-to-backend network posture is *already reasonable* for its four SaaS providers — outbound HTTPS to OpenAI/Anthropic/Gemini/Bedrock is system-CA-verified (the Dockerfile explicitly copies `ca-certificates.crt` into the `scratch` final stage for exactly this reason) and the `NetworkPolicy`'s wide-open egress rule is a disclosed, reasoned tradeoff against those providers' dynamic, CDN-fronted IP ranges. The real, previously-unexamined gap is narrower and more concrete: `dataplane.NewHTTPUpstreamCaller` uses **one shared `*http.Client`/`Transport` for every deployment, including `openaicompat`**, and `DeploymentConfig` has **no per-deployment TLS knob at all** — no client certificate, no custom CA pinning, no scheme enforcement. That's a real problem specifically for `openaicompat`'s own named targets (vLLM, llama.cpp, Ollama, TGI, LocalAI), because — confirmed across five independent, converging 2026 sources — **every one of those runtimes ships with zero built-in authentication or TLS**, by their own maintainers' explicit design; any transport security has to come from something in front of them, and today nothing in Kelvran's own code can present a client certificate or verify a private/internal CA to reach one. A full service mesh (Istio, Linkerd, Cilium) or a SPIRE deployment would technically close this, but both are disproportionate to Kelvran's actual topology — a single Go binary, one `Deployment`/one `Service`, no other in-cluster microservices to mesh with — and this report's most direct, closest-analog precedent (Envoy AI Gateway's own kgateway/agentgateway lineage, already Kelvran's established competitor-research comparison set) confirms the right-sized fix: these AI-specific gateways ship a narrow, purpose-built **backend TLS/mTLS origination policy** (client cert + custom CA, no mesh required), mirroring the standardized Kubernetes Gateway API `BackendTLSPolicy` shape. That is the concrete, Go-native, zero-new-infrastructure pattern this report recommends Kelvran adopt for `DeploymentConfig` today, with SPIFFE/SPIRE and a full mesh both named as real, well-understood options whose trigger has not yet fired.

## Findings, ranked

### 1. Per-deployment TLS client configuration (custom CA + client certificate) for `openaicompat` backends (Small-Medium)

**What:** `dataplane.NewHTTPUpstreamCaller(client *http.Client)` (`gateway/internal/gateway/dataplane/dataplane.go`) takes one `*http.Client` at construction and reuses it for every deployment regardless of provider — confirmed directly against the function body, which builds the request from `dep.BaseURL` and calls `client.Do(httpReq)` with no per-deployment transport override anywhere in the call path. `DeploymentConfig` (`gateway/internal/gateway/controlplane/config.go`) has fields for `BaseURL`, `APIKeyEnv`, and (for Bedrock) `AccessKeyIDEnv`/`SecretAccessKeyEnv`/`SessionTokenEnv` — but nothing for a client certificate, a private CA bundle, or even an explicit `https://`-only enforcement. The Dockerfile's own comment ("Copy CA certificates so outbound HTTPS calls to upstream providers... can verify TLS certificates") confirms the *only* trust root available today is the public system CA bundle baked into the image at build time — there is no live mechanism to add a private/internal CA at runtime, and no mechanism at all to present a client certificate for mTLS.

**Why it matters for Kelvran specifically:** this gap is functionally invisible for the four SaaS providers (they terminate TLS with certificates chained to the public CA bundle already present), but it is a real, live gap for exactly the deployment type `openaicompat` exists to serve. Five independent, 2026-dated practitioner sources — a dev.to hardening guide, a dedicated self-hosted-LLM-security guide, an itrpoka production writeup, a `localaimaster.com` Ollama-hardening guide, and an `llmbestpractices.com` deployment reference — converge on the same fact: **Ollama, vLLM, llama.cpp's server, and TGI all ship with zero built-in authentication and no TLS of their own**, an explicit, disclosed design choice by their own maintainers (all four assume they're bound to `localhost` and something else terminates TLS/auth in front of them). Kelvran's own `openaicompat.go` doc comments already treat this backend class as untrustworthy in a different dimension (a self-hosted backend's `cached_tokens` claim is "its own unverified say-so," per `THREAT_MODEL.md`'s Tampering row) — this report extends that same distrust to the transport layer, where it's arguably more consequential: an operator who points `base_url` at a self-hosted backend's private, self-signed-cert or plaintext HTTP endpoint (extremely common in the very hardening guides cited above, which recommend an internal reverse proxy doing its own mTLS with a private CA) has no way to make Kelvran either verify that private CA or present a client certificate the backend's own proxy might require. Today, the only paths available to an operator are (a) install a private CA into the container image's trust bundle at build time — not supported by the current Dockerfile, which only copies the system bundle — or (b) run the backend behind a publicly-CA-issued cert, which defeats the point of keeping it internal-only.

**Consistent with settled decisions?** Directly extends, rather than contradicts, the `2026-09-21` DECISIONS.md entry's Redis-TLS verdict ("no custom-CA/mTLS, since nothing here needs it") — that verdict was scoped to Redis coordination traffic between gateway replicas, a surface with no cross-organizational trust boundary and no untrusted-by-design backend. `openaicompat` backend traffic is a different surface: it crosses into infrastructure Kelvran's own code already treats as less trustworthy (`THREAT_MODEL.md`'s existing self-hosted-backend distrust), and the "nothing here needs it" reasoning was never made for this surface — it doesn't hold by extension, and this finding supplies the concrete evidence (five converging practitioner sources on vLLM/Ollama/llama.cpp/TGI's own lack of built-in transport security) that it shouldn't.

**2026 best practice grounding:**
- Envoy AI Gateway's own lineage — `kgateway` and `agentgateway`, both Envoy-based AI/API gateways this repo's own `gateway-2026-09-06.md` already treats as a direct comparison set — ship a purpose-built backend-TLS-origination feature for exactly this shape: `BackendConfigPolicy`/`AgentgatewayPolicy`'s `backend.tls` block takes `caCertificateRefs` (a Secret/ConfigMap reference) for one-way TLS to a self-signed/private-CA backend, and a separate `mtlsCertificateRef`/`backendTLS.cert`+`key` pair specifically for presenting a client certificate — confirmed directly against `kgateway.dev`'s and `agentgateway.dev`'s own current documentation, cross-checked against two separately-branded projects, not one restated twice [kgateway.dev, agentgateway.dev — confirmed 3-0 across genuinely separate doc sets].
- The Kubernetes Gateway API's own `BackendTLSPolicy` (`gateway.networking.k8s.io/v1`) standardizes this exact shape at the ecosystem level, independent of any single vendor: `validation.caCertificateRefs`/`wellKnownCACertificates` for the CA side, and its own doc explicitly names `subjectAltNames` with SPIFFE URI SANs as "particularly useful for SPIFFE implementations where URI-based SANs may not be valid SNIs" — i.e. this same policy shape is the sanctioned bridge if Kelvran ever *does* adopt SPIFFE identities without needing Kelvran itself to speak the SPIFFE Workload API directly [gateway.envoyproxy.io (Envoy Gateway's own rendering of the upstream Gateway API spec) — confirmed 3-0, a genuinely separate, vendor-neutral standard from the two implementations above].
- Every source checked for self-hosted-runtime behavior agrees the runtimes themselves never present a certificate an operator controls without a fronting proxy — meaning Kelvran's own client-side cert/CA support has to interoperate with *whatever* the operator puts in front of vLLM/Ollama, not with the runtimes' own (nonexistent) TLS stack directly [dev.to/hypernexus, thequantumdispatch.com, itrpoka.com, localaimaster.com, llmbestpractices.com — confirmed 3-0+, five independent practitioner sources converging on the same underlying fact].

**Concrete next step:** add three new optional `DeploymentConfig` fields — a client-certificate/key file-path pair and a CA-bundle file path — read once at config-load time (mirroring how every source above configures TLS material: file paths pointing at a mounted Secret, never raw PEM embedded in YAML or an env var, which is also why this deliberately does *not* reuse the repo's existing `*_env` convention built for bearer-token-shaped secrets). Wire a per-deployment `*tls.Config` into a per-deployment `http.Transport` (still one `http.Client` construction site, just no longer one shared, hardcoded `Transport`) so `openaicompat` deployments can specify a private CA and/or a client cert independently of the four SaaS-provider deployments, which keep using the existing system-CA-only default unchanged. Document the new fields as file paths meant to be populated via a K8s Secret volume mount (the standard pattern every TLS-consuming tool above uses), not `secret-placeholder.yaml`'s existing env-var-injection pattern.

**Effort:** Small-Medium — new config fields, a `tls.Config`/`http.Transport` construction per deployment instead of one shared client, and tests proving CA-pinning/client-cert-presentation actually work against a real self-signed test server. No new third-party dependency (Go's `crypto/tls` stdlib is sufficient).

### 2. Enforce or explicitly opt into non-HTTPS `base_url` values, since nothing today stops a silent plaintext leak of prompts to a self-hosted backend (Small)

**What:** `NewHTTPUpstreamCaller` builds `http.NewRequestWithContext(ctx, http.MethodPost, dep.BaseURL, ...)` from whatever string is in `config.yaml` — confirmed directly against the code — with no scheme validation anywhere in `controlplane.LoadConfig`'s deployment-parsing loop (the same loop that already validates `Model`/`Provider`/`UpstreamModel`/`BaseURL` are non-empty, per `config.go`'s own `if dep.Model == "" || ...` check). An operator who copies a self-hosted runtime's own quick-start example verbatim — and several of the practitioner guides checked for Finding 1 show exactly this, e.g. `vllm serve ... --host 127.0.0.1 --port 8000` reachable at a bare `http://` URL before any reverse proxy is added — gets a working deployment with prompts and completions (the exact content class `THREAT_MODEL.md`'s Information Disclosure row already flags as PII/secret-bearing) traveling in cleartext, with zero warning from Kelvran.

**Why it matters for Kelvran specifically:** this is a strictly cheaper, more defensive-in-depth companion to Finding 1, not a substitute for it — Finding 1 gives an operator who *wants* TLS-to-backend the means to configure it; this finding stops an operator who *forgot* to from silently shipping plaintext. It's also the single most common failure mode named across every source checked in Finding 1 (every guide's "quick start" example runs the backend on a bare port with no TLS at all before the hardening section adds a reverse proxy) — meaning the unsafe default is the *first* thing an operator following any of those guides sees, and Kelvran's own config loader gives it no pushback whatsoever.

**Consistent with settled decisions?** Additive, not a revisit of anything — no prior Kelvran research or decision names request-scheme validation at all. Doesn't touch `PRD.md`'s scope-outs.

**2026 best practice grounding:** NIST SP 800-207A's own zero-trust recommendation `ID-SEG-REC-1` states plainly: "communication between any two [service endpoints] should be encrypted to ensure eavesdropping protection and message authenticity" regardless of where those endpoints sit relative to a perimeter [nvlpubs.nist.gov — confirmed, primary/canonical NIST source, not independently triangulated since it's the standard itself]. This is the same general principle Kelvran's own `THREAT_MODEL.md` already applies to *upstream-provider* traffic implicitly (all four SaaS adapters call HTTPS-only endpoints); this finding is asking for the same property to be enforced, not just assumed, for the one deployment type where an operator's own config could accidentally violate it.

**Concrete next step:** at config-load time, reject (or, if a deliberate escape hatch is wanted for local dev against `127.0.0.1`, warn loudly and require an explicit `allow_insecure_http: true` opt-in per deployment) any `base_url` with scheme `http://` that isn't targeting a loopback address. Mirrors the same "reject at config-load time, cheaper than a runtime 500" philosophy `config.go`'s own comment already states for the embedding-kind/provider mismatch check a few lines away.

**Effort:** Small — one new validation branch in the existing deployment-parsing loop, plus a test for both the reject and (if built) the opt-in-warn path.

### 3. Reconsider the `NetworkPolicy`'s blanket-open egress specifically for self-hosted backend traffic — the SaaS-provider rationale doesn't transfer (Small)

**What:** `deploy/k8s/base/networkpolicy.yaml`'s egress rule is `- {}` — allow everywhere — with an explicit, disclosed rationale in its own comment: OpenAI/Anthropic/Gemini/Bedrock are "dynamic, AWS/CDN-fronted hostnames with no stable, documented IP range to pin an egress rule to." That rationale is sound *for those four providers* — but it was written before `openaicompat`'s own deployment shape was considered specifically, and it doesn't hold for it: a self-hosted vLLM/Ollama/TGI backend is, by definition, infrastructure the *same operator* controls and typically runs at a stable, known in-cluster `Service` address or a fixed private-network IP — the exact opposite of the "no stable, documented IP range" problem the comment names.

**Why it matters for Kelvran specifically:** combined with Finding 1's gap, an operator running a self-hosted backend in the *same* cluster as the gateway gets zero network-level isolation on top of zero application-level transport security — the gateway's egress rule doesn't even scope down to the backend's own namespace/pod selector, meaning (absent Finding 1's mTLS) a compromised gateway pod (or any other workload able to spoof the gateway's egress path) has exactly the same unrestricted reach to the backend as the gateway does. NIST SP 800-207A's own identity-tier-vs-network-tier framing is directly on point here: it explicitly recommends fine-grained network-tier ("microsegmentation") policies specifying the outbound egress path *as well as* identity-tier policies — the two are meant to be complementary layers, not either-or, and today Kelvran has neither for this specific traffic class.

**Consistent with settled decisions?** Directly re-engages with `networkpolicy.yaml`'s own stated egress rationale, rather than silently proposing a change the file's authors already reasoned about — the distinction drawn here (dynamic SaaS IPs vs. operator-controlled self-hosted IPs) is new evidence the original comment's blanket justification doesn't actually cover, not a re-litigation of a settled question about the SaaS-provider case, which this finding leaves untouched.

**2026 best practice grounding:** NIST SP 800-207A explicitly separates "fine-grained network-tier policies" (specifying the egress path for outbound traffic) from "identity-tier policies" (mesh/mTLS-level), stating both are needed for a complete zero-trust posture, not one instead of the other [nvlpubs.nist.gov — confirmed, primary NIST source]. This is also consistent with the general zero-trust migration pattern described across the SPIFFE/Cilium sources checked for Finding 4 below — network-level scoping and identity-level authentication are presented everywhere as additive layers, never substitutes for one another.

**Concrete next step:** for operators who run their self-hosted backend in the *same* cluster, add an additional, narrower egress rule (a `podSelector`/`namespaceSelector` targeting the backend's own labels) alongside — not instead of — the existing `- {}` rule, or document clearly in `deploy/k8s/base/README.md` that an operator with an in-cluster self-hosted backend should replace the blanket rule with one scoped to that backend's namespace plus the still-needed open egress for the four SaaS providers and DNS. This is documentation/config guidance, not a code change — the mechanism (`NetworkPolicy` egress rules) already exists and works; only the operator-facing guidance for this specific case is missing.

**Effort:** Small — a doc update plus an optional example manifest; no gateway code change.

### 4. `go-spiffe` for direct SPIFFE Workload API integration, without deploying a full mesh — real, but genuinely not_yet given Kelvran's current single-service topology (Large, deferred)

**What:** SPIFFE/SPIRE issue short-lived, auto-rotating X.509 identity certificates (SVIDs, typically 1-hour TTL) to workloads via node-local attestation, and the official `go-spiffe` Go library (`github.com/spiffe/go-spiffe`) lets a Go binary consume the SPIFFE Workload API *directly* — via `workloadapi.NewX509Source` plus `tlsconfig.MTLSClientConfig`/`MTLSServerConfig` — to get automatic mTLS with certificate rotation, with **no service mesh, no sidecar, and no Envoy dependency at all**. This is a genuinely different, lighter-weight option than "adopt a service mesh," and it's the option that would let Kelvran's own single Go binary present a SPIFFE identity to a self-hosted backend that also speaks SPIFFE (or sits behind a proxy that does), closing Finding 1's gap with cryptographic workload identity instead of a static, manually-provisioned client certificate.

**Why it matters for Kelvran specifically:** it's the natural *next* step past Finding 1's static-cert approach if Kelvran or its operators ever need cross-organizational trust (federating identity with a self-hosted backend run by a different team, or on infrastructure Kelvran's own operators don't fully control) — SPIFFE's federation model is explicitly built for exactly that, where a shared static CA/client-cert pair (Finding 1's mechanism) becomes awkward to rotate and distribute safely.

**Consistent with settled decisions?** No prior Kelvran decision addresses SPIFFE/SPIRE at all — this is genuinely new ground, not a re-litigation. It is, however, directly adjacent to the `2026-09-21` DECISIONS.md entry's Redis "no custom-CA/mTLS, since nothing here needs it" verdict in spirit: the same "don't build infrastructure for a need that hasn't materialized" reasoning applies here, just for a different reason (operational cost of running SPIRE, not absence of a trust boundary).

**2026 best practice grounding:** confirmed directly against the official `go-spiffe` repository and its own example READMEs (`spiffe-grpc`, `spiffe-jwt`) that the library supports exactly this "Workload API + `tls.Config`, no mesh" pattern for both gRPC and plain HTTP [github.com/spiffe/go-spiffe, pkg.go.dev/github.com/spiffe/go-spiffe — confirmed as a real, documented capability, but graded as **single-source** (the SPIFFE project's own official docs restated across two URLs, not independently corroborated by a second organization's account of the same mechanism) rather than 3-0 cross-checked]. Separately, a Palo Alto Networks explainer independently corroborates that "operating SPIRE at enterprise scale requires dedicated attention to server high availability, agent lifecycle management ... and upstream CA integration" and that "several commercial offerings provide managed SPIFFE/SPIRE implementations that reduce this operational burden" [paloaltonetworks.com — confirmed 2-1, a second, independent organization's account of the same operational-cost claim].

**Verdict: not_yet.** Running even a minimal SPIRE server + agent deployment is real, standing infrastructure a single-maintainer project would now own and operate (server HA, node attestation config, registration-entry maintenance) — a heavier ask than Finding 1's file-based client cert for a problem that, per Finding 1, has a smaller, sufficient fix available today. The concrete, named trigger for revisiting: a real need to federate trust with a self-hosted backend operated by a genuinely different team/organization (where a shared static cert becomes an operational or trust liability Finding 1's mechanism can't cleanly solve), or Kelvran itself growing into more than one deployable Go service that would benefit from mesh-wide identity regardless of this specific backend-TLS problem.

**Effort:** Large — a new, standing piece of infrastructure (SPIRE server + agent) to design, deploy, and operate, plus the Go-side integration work itself.

### 5. Full service mesh (Istio ambient, Linkerd, Cilium+SPIRE) — real 2026 tooling, but disproportionate to a single-`Deployment` gateway; not_yet (Large, deferred)

**What:** Istio's newer "ambient" mode (stable since Istio 1.24, November 2024) replaces the older per-pod Envoy sidecar with a shared per-node `ztunnel` (Rust, L4-only mTLS) plus optional per-namespace "waypoint" Envoy proxies for L7 features — cutting per-pod memory overhead from the sidecar model's ~50-100MB to near-zero and p90/p99 latency overhead from ~0.63-0.88ms to ~0.16-0.50ms, per Istio's own published benchmark. Linkerd ships a comparable, simpler always-on-sidecar mTLS model (a ~10MB Rust microproxy per pod). Cilium can enforce SPIFFE-based mutual authentication at the eBPF/kernel layer with no proxy at all, using SPIRE for identity issuance.

**Why it matters for Kelvran specifically — and why it doesn't, yet:** every one of these technologies solves the *general* "many microservices need mTLS to each other" problem extremely well, and every AI-workload-specific source checked (a "Service Mesh for AI Agents" 2026 comparison, Solo.io's Ambient-Mesh-for-agentic-AI framing) recommends exactly this pattern *for a fleet of many AI-agent/inference services*. Kelvran is not that shape today: `deploy/k8s/base/` defines exactly one `Deployment` and one `Service` (the gateway itself) — there is no second in-cluster microservice to mesh *with*, on Kelvran's own side. Standing up Istio's control plane (`istiod`), or a SPIRE server for Cilium's mutual-authentication mode, purely to get mTLS for ONE service's own outbound calls to backends it doesn't control the deployment of anyway, is materially more operational surface than Finding 1's few-dozen-line `crypto/tls` change — for the same practical outcome on the one problem this report was scoped to solve.

**Consistent with settled decisions?** Not previously addressed by any Kelvran decision — new ground, engaged with directly rather than silently proposed as if undiscovered. Its "not_yet, and the mechanism should be right-sized to the actual topology" verdict is the same shape of judgment `DECISIONS.md`'s Redis-TLS entry already made for a different surface, applied consistently here rather than assumed.

**2026 best practice grounding:**
- Istio's own official docs (`istio.io/latest/docs/overview/dataplane-modes`) state the ambient-vs-sidecar resource/latency comparison directly, as the primary source [istio.io — confirmed, primary/official source]; two further blog sources (`oneuptime.com`, `axyi.ru`) independently restate the same 1.24 benchmark numbers, but both trace back to Istio's own published figures rather than an independently-run benchmark, so this is graded as **one authoritative source, corroborated in retelling but not in independent measurement** — worth being honest about rather than counting it as 3-0.
- Solo.io's own ambient-mesh-for-AI material and a dedicated "Istio Ambient vs Linkerd for AI Agents (2026)" comparison both frame ambient mode as the 2026-default recommendation specifically for *fleets* of AI-agent/inference workloads needing per-request routing features (KV-cache-aware load balancing via the Gateway API Inference Extension) that a bare `crypto/tls` client-cert change could never provide [solo.io, callsphere.ai — confirmed 2-1; the latter source reads as marketing-adjacent content and its specific numeric claims (e.g. "22% higher cache-hit rate") are not independently verifiable from this pass, so only its qualitative framing is relied on here, not its numbers].
- The freeCodeCamp SPIFFE/SPIRE/Cilium walkthrough independently confirms Cilium's eBPF-based mutual-authentication mode requires zero sidecar and a real, working SPIRE integration exists today, corroborating that "sidecarless zero-trust" is a genuinely production-viable alternative to both the sidecar and ambient-Envoy models, not just an Istio-specific idea [freecodecamp.org — confirmed, cross-checked against Cilium's own documented Helm chart validation error message quoted directly in the source, a strong signal this was verified against real tooling rather than restated secondhand].

**Verdict: not_yet.** The concrete, named trigger for revisiting: Kelvran genuinely becoming a multi-service deployment (e.g., the already-named, evidence-gated `docs/decisions/0002-cache-embedded-in-gateway.md` extraction trigger firing, or a second Kelvran-side deployable appearing for an unrelated reason) — at that point, mesh-wide automatic mTLS for the *whole* fleet becomes a natural, amortized byproduct of infrastructure Kelvran would need anyway, rather than a dedicated build for this one backend-TLS problem. Until then, Finding 1's Go-native `crypto/tls` change solves the actual named problem (self-hosted backend transport security) at a small fraction of the operational cost.

**Effort:** Large — a full mesh control plane (or a SPIRE server for Cilium's mode) is standing infrastructure with its own upgrade/HA/observability lifecycle, disproportionate to a single-service gateway.

## Top 3 do next

1. **Per-deployment TLS client configuration for `openaicompat` (Finding 1, Small-Medium).** The concrete, code-verified gap: one shared `http.Client`/`Transport` today, zero per-deployment CA/client-cert support, against a backend class (vLLM/Ollama/llama.cpp/TGI) that ships with no built-in TLS of its own by design. Closes the sharpest real edge with a stdlib-only Go change.
2. **Reject/gate plaintext `http://` `base_url` values (Finding 2, Small).** The cheapest possible defense-in-depth companion — stops the single most common failure mode named across every self-hosted-LLM hardening guide checked (a bare, unproxied `http://` quick-start default) from silently leaking prompt/completion content in cleartext.
3. **Document and provide an example for scoping `NetworkPolicy` egress to an in-cluster self-hosted backend (Finding 3, Small).** Re-engages directly with the existing egress rule's own disclosed rationale rather than leaving it to silently under-cover a case (operator-controlled, stable-address self-hosted backends) its own stated justification (dynamic SaaS IPs) never actually applied to.

**Worth tracking explicitly, not immediately building:** Finding 4 (`go-spiffe` direct integration) is the natural next step past Finding 1 if cross-organizational trust with a self-hosted backend ever becomes real; Finding 5 (a full service mesh) is the right answer only once Kelvran itself becomes a multi-service deployment, at which point it stops being "infrastructure built just for this one problem."

## Caveats

- **The admin API's own inbound mTLS/zero-trust question is explicitly out of scope here and remains genuinely unresolved** — `DECISIONS.md`'s `2026-09-15` entry already names "mTLS/zero-trust for the admin surface beyond bearer-token auth" as a disclosed, unresolved gap. That surface is inbound (an operator/tool calling the gateway's admin API), while this report covers outbound (the gateway calling a backend) — related in spirit (both are "should mTLS exist here") but a genuinely different code path, different trust boundary, and not re-litigated or silently folded into this report's findings.
- Several sources checked (`callsphere.ai`, some of the self-hosted-LLM hardening blogs) read as SEO-oriented or product-marketing-adjacent content; their qualitative framing (e.g., "ambient is the 2026 default for AI fleets," "every self-hosted runtime ships with no auth") is corroborated by multiple independent sources and by Kelvran's own existing threat-model language, so it's relied on — but specific numeric claims from single marketing-adjacent sources (e.g. one source's "22% higher cache-hit rate," another's exact Shodan instance counts) are explicitly *not* relied on as verified facts in this report, only as color.
- The Istio ambient-mode latency/memory numbers (Finding 5) all trace back to one Istio-published benchmark repeated across secondary sources — disclosed as a single authoritative source, not independently triangulated, rather than overstating confidence.
- This report did not test any of Finding 1's proposed `crypto/tls` wiring against a real self-signed backend or a real mTLS-requiring reverse proxy — the concrete next step names exactly what a real implementation pass would need to prove (CA-pinning and client-cert presentation actually working), not a claim that it's already been verified working.
- Kelvran's own `evals/` (Python) component was not examined for this report — its own sandboxed rollout traffic (`--network=none` per its already-shipped egress-block design) is a different, already-more-restrictive posture than `gateway`'s, and this report's scope was `gateway`-only per the research brief.
