# Research: Performance and latency optimization for Kelvran's gateway hot path

**Date:** 2026-09-14
**Scope:** The real request lifecycle in `gateway/internal/gateway/dataplane/dataplane.go`, upstream HTTP client construction across `gateway/internal/adapter/*` (openai, anthropic, bedrock, gemini, openaicompat) and `gateway/cmd/gateway/main.go`, and the SSE writer in `gateway/internal/streaming/`. This round deliberately excludes ground already covered: the multi-layer cache's existence, `singleflight` stampede protection, WRR routing/health-probing, OTel tracing, rate-limit/budget enforcement, and the 90.9% coverage / `-race`-clean baseline are all real and shipped — not re-litigated here.

## Context (Kelvran's own real, current state)

Direct inspection of the live code (not the external research alone) found:

- **HTTP clients are constructed exactly once, at startup, in `cmd/gateway/main.go`** (`&http.Client{Timeout: upstreamHTTPTimeout}` for non-streaming, `&http.Client{}` for streaming, the latter deliberately timeout-free with its own idle-window mechanism), passed into `dataplane.NewHTTPUpstreamCaller`/`NewHTTPUpstreamStreamCaller`, and reused for every request across every deployment/provider. This is the *correct* half of the classic Go gotcha — Kelvran does not construct a fresh client per request.
- **Neither client customizes `http.Transport`** — no `MaxIdleConnsPerHost`, `MaxIdleConns`, or `IdleConnTimeout` is set anywhere in `gateway/internal/adapter/*` or `cmd/gateway/main.go` (`grep`-confirmed, zero matches). Both clients therefore run on `http.DefaultTransport`'s implicit per-host idle-connection cap.
- **`internal/streaming/writer.go`'s `Writer.WriteChunk`/`WriteDone` already call `sw.flusher.Flush()` after every single write** — this is the standard-practice fix, already shipped, not a gap.
- **A real, token-gated, localhost-bound-by-default admin HTTP server already exists** (`internal/admin`, wired in `cmd/gateway/main.go`, off entirely unless `cfg.Admin.TokenEnv` is set, default listen addr `127.0.0.1:8081` per `docs/rfcs/2026-09-05-gateway-admin-api.md`'s "never internet-facing by default" rule). It currently registers only `/admin/config`, `/admin/virtual_keys/*`, and `/admin/prompts/*` routes. **No `net/http/pprof` handler is registered anywhere in the codebase** (`grep -rn pprof` returns zero hits outside this research).
- **No `GOMEMLIMIT`/`GOGC`/`debug.SetGCPercent`/`debug.SetMemoryLimit` call exists anywhere**, and `docker-compose.yml` sets no `mem_limit`/`memory:`/`cpus:` resource ceiling on the gateway service — there is currently no fixed container memory ceiling for a soft memory limit to protect against.
- **Cache L3-lite (`internal/cache/inprocess/lexical.go`) is an explicitly documented, deliberate brute-force per-tenant scan**, not an LSH/ANN index — the type's own doc comment cites `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`'s "no ANN needed at Kelvran's likely scale" research conclusion. Each tenant's candidate set is its own LRU-capped `container/list.List`, scanned linearly via `cache.JaccardEstimate` against a MinHash signature (`cache.MinHashSignature`/`cache.Shingles` in `internal/cache/lexical.go`) — no LSH banding, no Bloom filter, by design.
- **Real `go test -bench` baselines already exist** for hot paths: `internal/cache/inprocess/bench_test.go`, `internal/streaming/bench_test.go`, `internal/ratelimit/bench_test.go` — explicitly tracked as a p50/p95/p99 regression baseline per `docs/testing/TESTING.md` §7, not a pass/fail gate but a recorded `ns/op` trend line.
- Go version: `go 1.26.8` (`gateway/go.mod`).

## Executive Summary

Two findings clear the `build_now` bar with no synthetic load needed to justify them: Kelvran's upstream `http.Client`s are correctly constructed once and reused (avoiding the classic "fresh Transport per request" mistake), but neither customizes `http.Transport`, so every upstream provider host is capped at Go's stdlib default of 2 idle keep-alive connections per host — a well-documented (`golang/go#13801`) source of connection churn and added per-request latency under concurrent bursts to the same host, and a small, targeted, low-risk fix (raise `MaxIdleConnsPerHost`/`MaxIdleConns`/`IdleConnTimeout` on both clients). Separately, Kelvran already has a real, token-gated, localhost-only admin HTTP server that is the natural, zero-risk home for `net/http/pprof` behind an opt-in config flag — mirroring Envoy Gateway's own shipped `enablePprof`-under-`admin` pattern — and today has none at all. Two areas researched turned out to already be correctly implemented and are not gaps: the SSE `Writer` flushes after every chunk, and `go test -bench` baselines already exist for the cache/streaming/rate-limit hot paths. Two areas are honestly `not_yet`: `GOMEMLIMIT`/`GOGC` tuning has no current trigger because no container memory ceiling exists anywhere in today's deployment config, and replacing the L3 lexical cache's brute-force MinHash/Jaccard scan with an LSH/Bloom-filter index is a documented, deliberate non-choice appropriate to Kelvran's per-tenant, LRU-capped candidate-set sizes at current pilot scale — revisiting it has no real trigger until either candidate-set sizes or tenant count grow materially beyond what a linear scan over an LRU-capped list can absorb.

## Findings

### Finding 1 — HTTP clients are correctly reused, but `http.Transport` per-host connection pooling is untuned, capping every upstream provider at 2 idle keep-alive connections

**Confidence: high** (6 claims, 5 unanimous 3-0 + 1 at 2-1, multiple independent primary sources: Go stdlib source, `golang/go#13801`, a reproducible k6 benchmark)

Go's `net/http.Transport` defaults `MaxIdleConnsPerHost` to 2 (claim [0], verified directly against current `golang/go` master source) and its own doc comment explicitly instructs that `Transport`s (and `Client`s) "should be reused instead of created as needed" because they cache connections internally, and are safe for concurrent use by multiple goroutines (claims [1], [2]) — which is exactly the precondition that makes Kelvran's actual pattern (one client, built once in `main.go`, shared across all concurrent request-handling goroutines) both safe and correct. The problem is what happens *after* that correct reuse: once concurrently-open connections to a host exceed `MaxIdleConnsPerHost`, Go closes the excess connections immediately after each request completes rather than keeping them warm for any grace period (claim [3], corroborated directly against `transport.go`'s `tryPutIdleConn`/`putOrCloseIdleConn` source), which under concurrent request bursts to the same upstream host can exhaust ephemeral ports in production — a real, previously-reported operational failure mode, not just a theoretical inefficiency (claim [4]). A reproducible, independently-verified k6 load benchmark shows the concrete shape of this: at the stock default, a spike from 2 to 100 concurrent virtual users drove goroutines from a baseline of ~32 up to 22,416, because each new connection dial spawns at least 4 goroutines under contention (claim [14]) — this specific benchmark's own before/after throughput/latency numbers (7x throughput, 81.8ms→5.7ms p99) were flagged in adversarial re-verification as a single-benchmark data point that shouldn't be read as Kelvran's own expected numbers, so they're cited here only as directional evidence of the mechanism, not as a promised result.

This maps directly onto Kelvran's own code: `dataplane.NewHTTPUpstreamCaller`/`NewHTTPUpstreamStreamCaller` (`gateway/internal/gateway/dataplane/dataplane.go`) each take one shared `*http.Client`, built once in `cmd/gateway/main.go` with no `Transport` field set — meaning both run on `http.DefaultTransport`'s implicit 2-per-host idle cap for every provider (`dep.BaseURL` host) Kelvran calls, across every request. With a real Bedrock pilot already live and other providers configured, any concurrent burst of requests to the same provider host (a plausible shape once traffic exceeds trivial volume) will hit exactly this documented connection-churn pattern.

**build_now:** Construct both `http.Client`s in `cmd/gateway/main.go` with an explicit `&http.Transport{MaxIdleConnsPerHost: N, MaxIdleConns: M, IdleConnTimeout: D}` (N in the tens, not the default 2) instead of the zero-value implicit-`DefaultTransport` client. This is a small, self-contained, low-risk change: no new dependency, no behavior change to request semantics, purely a connection-pool sizing knob, and directly verifiable via the existing `internal/streaming/bench_test.go`-style benchmark pattern or a simple concurrent-request test asserting idle-connection reuse. Recommend pairing with `Transport.CloseIdleConnections` awareness if health-probe-driven deployment churn ever recycles `BaseURL` hosts (not confirmed as a current issue, just a related knob worth setting deliberately rather than leaving implicit).

### Finding 2 — The SSE streaming writer already flushes after every chunk; this is not a gap

**Confidence: high** (claim [15], 3-0, independently corroborated against live Go stdlib buffering behavior)

The general pattern this claim describes — that Go's `http.ResponseWriter` buffers writes (through a 2048-byte `bufio.Writer`, then a `chunkWriter`, then a 4KB connection-level `bufio.Writer`) until either the buffer fills, the handler returns, or `Flush()` is explicitly called — is real, stable, version-independent Go stdlib behavior, and skipping the explicit flush after each SSE event is a documented cause of clients receiving batched chunks instead of a live stream. Kelvran's own `internal/streaming/writer.go` already does this correctly: `Writer.WriteChunk` and `Writer.WriteDone` both call `sw.flusher.Flush()` immediately after their `fmt.Fprintf`/`fmt.Fprint` write, on every single chunk, with no batching path anywhere in the type. `NewWriter` also fails fast (returns an error) if the wrapped `http.ResponseWriter` doesn't implement `http.Flusher`, rather than silently degrading to buffered behavior.

**build_now / not_yet:** Neither — this is a verified non-issue. No action needed; flagged here only so a future contributor doesn't "fix" something that already works.

### Finding 3 — `net/http/pprof` is completely absent, but Kelvran's existing admin server is a ready-made, zero-risk home for it, directly paralleling Envoy Gateway's own shipped design

**Confidence: medium** (2 claims, both 2-1, but independently corroborated against Kelvran's own live code, which raises effective confidence for the *applicability* half even though the external precedent itself had a split vote)

Envoy Gateway's own design doc states its pprof endpoints are exposed by directly reusing Go's standard `net/http/pprof` handler set (not a custom implementation), served under a separate admin server rather than the data-plane API surface (claim [12]) — and, concretely, pprof there is opt-in and gated: disabled by default, only enabled through an explicit `enablePprof` boolean nested under an `admin` config section, with the admin listener's example address bound to `127.0.0.1:19000` rather than a public interface (claim [13]). (An adjacent claim asserting the admin server is *architecturally isolated as a separate component* was refuted 1-2 in adversarial review — the real distinction that survived is narrower: it's a boolean flag under the existing admin config, not a bolted-on-to-the-public-API toggle, which is precisely the applicable half for Kelvran.)

Kelvran already has the exact structural precondition this pattern needs: `internal/admin`'s `Handler` builds its own `http.ServeMux`, served by a separate `*http.Server` in `cmd/gateway/main.go` that is off entirely unless `cfg.Admin.TokenEnv` is set, defaults to `127.0.0.1:8081` (never internet-facing by default, per `docs/rfcs/2026-09-05-gateway-admin-api.md`), and every route it registers already goes through `requireBearerToken`/`requireEitherBearerToken`. Registering `net/http/pprof`'s handlers (`pprof.Index`, `pprof.Profile`, `pprof.Trace`, etc.) onto that same mux, under a path like `/admin/debug/pprof/`, wrapped in the same `requireBearerToken` middleware every other admin route already uses, and gated behind its own new opt-in config bool (e.g. `cfg.Admin.EnablePprof`, mirroring Envoy Gateway's `enablePprof`) reproduces the exact shipped pattern with essentially zero new risk surface — it inherits the existing auth, the existing localhost-by-default bind, and the existing "never wired unless explicitly configured" posture.

**build_now:** Yes. Concretely: add an `EnablePprof bool` field to the admin config struct (default `false`, matching Go's zero value — no explicit default-off logic needed, mirroring Envoy Gateway's own `EnablePprof` field which relies on the same zero-value convention), conditionally register `net/http/pprof`'s package-level handlers onto the admin mux inside `admin.Handler` when set, wrapped in the same bearer-token middleware every other admin route uses. This gives Kelvran real profiling data (heap, goroutine, CPU, block, mutex profiles) the next time a load-driven optimization question comes up, without waiting for a second research round to justify adding it — pprof itself is the mechanism that would generate the evidence any *further* hot-path optimization work should be gated on.

### Finding 4 — `GOMEMLIMIT`/`GOGC` tuning has no current trigger: no container memory ceiling exists anywhere in today's deployment config

**Confidence: medium** (3 claims: [6] 3-0, [7] 3-0, [16] 2-1 — all primary-source-verified, but two adjacent claims narrowing their real-world applicability were refuted, and the "applies to Kelvran today" half is the research agent's own repo-grounded finding, not sourced externally)

Uber's own GC-tuning initiative was triggered by real CPU-profiling data showing GC was the top CPU consumer on their mission-critical services (claim [6]) — but an adjacent claim asserting those measured wins only manifested at thousands-of-cores scale was refuted 1-2, so this precedent's *conditions* for mattering are less sharply bounded than the original claim suggested; regardless, the underlying discipline — profile first, tune second — is sound and is exactly what Finding 3's pprof addition would enable Kelvran to do honestly, rather than tuning speculatively. Separately, `GOMEMLIMIT` combined with `GOGC=-1` under a slow memory leak has a documented, still-open, unresolved Go runtime failure mode: a prolonged (5-8+ hour) spike to ~75% CPU utilization before the process is eventually OOM-killed, rather than a fast, cheap crash (claim [7], verified directly against the still-open `golang/go#58106`, including runtime-maintainer engagement confirming the mechanism and a 2023 proposal to mitigate it that was explicitly closed `NOT_PLANNED`) — a real caveat against blindly setting `GOGC=-1` without also setting a real `GOMEMLIMIT`. And the whole `GOMEMLIMIT`+high-`GOGC` pairing is specifically framed, including in the Go team's own `gc-guide`, as a fix for containerized/Kubernetes deployments with a *fixed* memory ceiling and spiky allocation — a service with a stable live set is described as already cheap under GC defaults regardless of tuning (claim [16]).

Direct inspection of Kelvran's own deployment config found no `mem_limit`/`memory:`/`cpus:` resource ceiling anywhere in `docker-compose.yml`, and no `GOMEMLIMIT`/`GOGC`/`debug.SetGCPercent`/`debug.SetMemoryLimit` call anywhere in the Go source. The precondition every source above requires — a fixed memory ceiling to tune *against* — simply doesn't exist in Kelvran's current deployment today.

**not_yet:** The real trigger is either (a) a production/staging deployment that actually sets a container memory limit (e.g. a future Kubernetes manifest or a `docker-compose.yml` `mem_limit`), at which point `GOMEMLIMIT` set to some margin below that limit becomes directly applicable per the Go team's own guidance, or (b) Finding 3's pprof addition surfacing real CPU-profile evidence that GC is a material cost at Kelvran's actual traffic — neither condition holds today. Tuning GOGC/GOMEMLIMIT before either trigger exists would be speculative, and per claim [7]'s open, unresolved deathspiral risk, `GOGC=-1` specifically should not be reached for without deliberately re-reading that still-open issue first if this is ever revisited.

### Finding 5 — Replacing the L3 lexical cache's brute-force MinHash/Jaccard scan with an LSH/Bloom-filter index is a real, well-documented technique, but Kelvran already made a deliberate, cited decision not to need it at current scale

**Confidence: medium** (4 claims: [10] 3-0, [11] 2-1, [8] 3-0, [9] 3-0 — the algorithmic facts themselves are well-sourced and unanimous/near-unanimous, but the "12x throughput" headline benchmark for the specific Bloom-filter variant was refuted 1-2, and applicability to Kelvran is the research agent's own repo-grounded conclusion)

Exact/brute-force pairwise similarity comparison is O(n²) in time and memory, which is the standard, decades-old justification for LSH-style candidate-bucketing techniques existing at all (claim [10]); MinHash-LSH's concrete banding technique — splitting an n-dimensional signature into b bands of r consecutive values (n = b×r), hashing each band independently, and treating any single-band collision as a similarity candidate — is exactly the mechanism that lets a lexical similarity search skip full-candidate-set scoring (claim [11]). A Bloom-filter-backed variant of this same index (LSHBloom) can reduce disk/memory footprint by 18x versus a standard hashmap/tree-backed MinHashLSH index while keeping F1 accuracy within 1% of baseline (claim [8]) — but it comes with a hard architectural tradeoff confirmed directly against the live `datasketch` source: it can only return a binary duplicate signal (0/1), never *which* stored item matched (claim [9]), which is disqualifying for a cache that needs to retrieve and serve the actual cached response behind a hit, not just confirm one exists. (A closely adjacent claim citing a specific "12x higher throughput" LSHBloom benchmark number was refuted 1-2 in adversarial review and is excluded here as unreliable.)

None of this changes what Kelvran should do today: `internal/cache/inprocess/lexical.go`'s own doc comment already cites `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`'s explicit research conclusion that "no ANN [is] needed at Kelvran's likely scale," and the implementation matches that conclusion exactly — a brute-force scan over a per-tenant, LRU-capped `container/list.List` (bounded by `maxEntries`, never unbounded), not a global index. Crucially, LSHBloom's binary-only limitation (claim [9]) would be a hard blocker even if scale did grow: Cache L3 needs to know *which* entry matched to serve its cached response, which a Bloom-filter-backed index structurally cannot provide — so even a future scale-driven revisit should reach for banded MinHash-LSH (claim [11], which does return real candidates) rather than LSHBloom specifically, if and when a revisit is ever triggered.

**not_yet:** No current trigger. This is already a considered, documented, correct-for-scale decision, not an oversight. The real trigger for revisiting it would be per-tenant candidate-set sizes (bounded today by `maxEntries`) or overall tenant count growing large enough that a linear Jaccard scan measurably shows up in pprof (once Finding 3 exists) as a real hot path — at which point banded MinHash-LSH, not LSHBloom, is the correct candidate technique given the retrieve-the-matched-item requirement.

### Finding 6 — HTTP/2 reverse proxies can withhold SSE response headers for many seconds; whether this applies to Kelvran depends on facts this research did not and could not verify from the code alone

**Confidence: low** (claim [5], 3-0 on the underlying external phenomenon, but its applicability to Kelvran is explicitly unknown, not confirmed)

A real, independently-corroborated GitHub issue documents a measured HTTP/2-specific hazard: behind an HTTP/2-aware reverse proxy, SSE response headers can be withheld until either a timeout tears down the stream (~31s in the reported case) or, with no timeout configured, never delivered at all — because HTTP/2 proxies commonly coalesce/withhold the HEADERS frame until a DATA frame exists to pair it with, a mechanism HTTP/1.1's chunked encoding doesn't have. (A related claim asserting `Flush()` alone is *never* sufficient to force headers through on HTTP/2 was itself refuted 1-2 in adversarial review — the reported fix in the cited issue is an SSE-comment workaround, not a `Flush()`-is-useless claim, so that stronger framing doesn't survive scrutiny.) Kelvran's own `internal/streaming/writer.go` already flushes correctly (Finding 2), which is necessary but, per this external report, not always sufficient if a client sits behind an HTTP/2-terminating proxy that specifically withholds headers pending a body frame.

Whether this is relevant to Kelvran cannot be determined from the gateway's own source: it depends on facts about Kelvran's actual deployment topology (does anything sit between real clients and the gateway that terminates HTTP/2 and coalesces frames this way — a load balancer, an API gateway, a CDN) that this research round did not investigate and that aren't visible from `internal/streaming`/`dataplane.go` alone.

**not_yet (unconfirmed applicability):** Before treating this as actionable, confirm whether Kelvran's real deployment path puts an HTTP/2-terminating proxy in front of streaming responses. If yes, the same SSE-comment-preamble workaround (writing a `: `-prefixed SSE comment line before the first real chunk, forcing an early DATA frame) is a small, low-risk addition to `Writer`'s construction path. If the deployment is HTTP/1.1 end-to-end, or clients connect directly, this finding doesn't apply and needs no action.

### Finding 7 — `go test -bench` baselines already exist for the hot paths that matter; this is not a gap

**Confidence: high** — grounded in direct repo inspection, not an external source, so no adversarial vote applies.

Three real benchmark files already exist and are already framed, per `docs/testing/TESTING.md` §7, as a tracked p50/p95/p99 performance-regression baseline rather than a pass/fail gate: `internal/cache/inprocess/bench_test.go`, `internal/streaming/bench_test.go`, `internal/ratelimit/bench_test.go`. This directly answers research question 5's "is `go test -bench` usage real in this repo today" — yes, and it already covers the cache, streaming, and rate-limiting hot paths this research round was asked to focus on.

**build_now / not_yet:** Neither — already shipped. The one real gap in this area is the *profiling* half (Finding 3's pprof addition), not the *benchmarking* half, which is already adequate.

## Refuted claims (for transparency)

The following claims were investigated but did not survive 3-vote adversarial verification, and are excluded from the findings above:

- "On HTTP/2, calling `Flush()` on an SSE response is never sufficient to force headers through" (refuted 1-2 — the real fix in the cited source is an SSE-comment workaround, a narrower claim than "Flush() is useless").
- "Uber's measured GC wins (65%/30% p99 CPU reduction) only manifest at thousands-of-cores scale" (refuted 1-2 — narrows Finding 4's applicability boundary, but doesn't invalidate the core profile-first discipline).
- "LSHBloom achieves 12x higher throughput than standard MinHashLSH on a 39M-document benchmark" (refuted 1-2 — the 18x disk-footprint claim [8] survived; this specific throughput number did not).
- "Envoy Gateway's admin server (hosting pprof) is architecturally isolated as a separate component from the rest of the control plane" (refuted 1-2 — it's a boolean flag under existing admin config, not a structurally separate component; this is the narrower, applicable-to-Kelvran framing used in Finding 3).
- "Leaving `MaxIdleConnsPerHost` at default is characterized as the *most common* Go microservice connection-pooling misconfiguration" (refuted 0-3 — the underlying default-value fact (claim [0]) is real and used in Finding 1; the superlative framing is not supported).
- "Raising `MaxIdleConnsPerHost` to 100 in one specific load test produced a 7x throughput / 81.8ms→5.7ms p99 latency improvement" (refuted 1-2 as a promise of Kelvran's own expected numbers — used in Finding 1 only as directional mechanism evidence, not as an expected result).
- "A naive fixed-size read buffer for SSE parsing corrupts event framing when an event spans multiple TCP reads" (refuted 0-3 — no evidence this applies to Kelvran's actual SSE reader implementation; not investigated further here).
- "`GOMEMLIMIT` caps GC-driven CPU work at ~50% and only accounts for Go-managed heap, excluding OS thread stacks/cgo/syscall buffers/page cache" (refuted 0-3 — excluded from Finding 4's caveats as unverified).

## Caveats

- **Finding 6 (HTTP/2 SSE header withholding) is genuinely unresolved**, not just low-priority — it hinges on Kelvran's real deployment topology (reverse proxies, load balancers, CDNs in front of the gateway), which this code-only research round has no visibility into. This is the one finding here that needs a fact-check against real infrastructure, not just code, before a build/no-build call can be made.
- **The k6 benchmark numbers cited in Finding 1** (goroutine counts, p99 latency deltas) are from a third-party blog benchmark with a different workload shape than Kelvran's, and adversarial review specifically flagged them as illustrative of the *mechanism*, not a prediction of Kelvran's own numbers after the fix — treat any pre/post comparison Kelvran runs after implementing the fix as the real evidence, not these cited figures.
- **Two of the six research questions in the original brief turned out to already be solved** in Kelvran's own code (SSE flush behavior, benchmark infrastructure) — this is a genuinely positive finding, not a research gap, but it means this document reports "already correct" for those two areas rather than a build recommendation.
- **Source mix is primary-source-heavy but not uniformly so**: Go stdlib source, `golang/go` issue tracker, and Envoy Gateway's own design docs/source are primary; the Uber and randomcommits.com GC-tuning sources and the davidbacisin.com k6 benchmark are reputable but secondary (blog-quality) — confidence ratings above reflect this mix.
