# Gateway Cache Volatility-Bypass Role Scoping — Deep Research (2026-09-09)

## Question

For an LLM-request semantic/lexical caching layer, what's the right role-scoping convention for a "does this query contain volatile/freshness-sensitive content" heuristic — should it ever inspect system-prompt/instruction content, or should it be scoped strictly to user-turn content?

Grounded against Kelvran's own real, current state: `gateway/internal/gateway/dataplane/dataplane.go`'s `isVolatileQuery(messages []adapter.Message) bool` (lines 756-765) iterates over **every** message in the request — including any `role: "system"` entry — and matches each one's `Content` against `volatileQueryPattern` (line 754: `(?i)\b(weather|price|stock|score|today|current|currently|now|latest)\b`) to decide whether to bypass Cache L3-lite entirely for that request. This is checklist item 2 ("volatility bypass") of `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`'s freshness/risk model, one of several hard gates alongside a staleness budget (item 1), a similarity floor (item 3), an entity/number/date hard-gate (item 4, `Fingerprint`), and a model-version exact match (item 5). `adapter.Message.Role` (`gateway/internal/adapter/types.go:20-21`) is documented as one of `"system"`, `"user"`, `"assistant"`, or `"tool"` — the field needed to role-scope this check already exists on the struct `isVolatileQuery` receives; it is simply never read.

**The bug class this confirms**: a static, byte-identical system prompt used across every request through one agent/deployment configuration — e.g. "you may discuss current stock prices with the customer" or "always mention today's date" — will match `volatileQueryPattern` on every single request regardless of what the user actually asked, permanently disabling L3 for that entire deployment. This is exactly the kind of false-positive risk `AGENTS.md`'s explicit rule ("Never ship a semantic-cache (L3) change that removes or weakens the entity/freshness hard-gate in favor of a bare similarity threshold") and `THREAT_MODEL.md` are otherwise built to guard against — except here the failure mode is the opposite of over-permissive matching: silent, total cache unavailability with no error, no log line, and no way for an operator to tell why hit rate collapsed to zero for one tenant's traffic.

## Summary

Every production LLM-caching system surveyed that documents a role-scoping convention at all — Portkey's Semantic Cache (explicit, both directions) and GPTCache's `skip_list` default (`[system, assistant]`, implicit) — independently converges on the same answer: **user-turn content is what should drive a per-request cache-eligibility/similarity decision; system-prompt content should not.** Portkey states this as an explicit product guarantee ("The system prompt is ignored — changing it does not affect cache hits") specifically so that changing a system prompt template never silently invalidates a tenant's cache. Where role-scoping is *not* discussed or enforced — GPTCache's `last_content()` (the library's own default pre-processing function), LangChain core's exact-match cache, and Helicone's cache-key hashing — the omission is a documented, uncontested gap, not a considered alternative design; no source anywhere argues *for* including system-prompt content in a per-request cache/volatility decision. None of the four systems that implement any per-request cache-skip logic at all (GPTCache, LangChain core, Helicone, and Kelvran itself) has a content-based volatility/freshness keyword heuristic comparable to `isVolatileQuery` — Kelvran's volatility bypass is a genuinely novel mechanism in this space, which is exactly why there was no existing role-scoping precedent for it to inherit and why the bug went unnoticed. Separately, OpenAI's own prompt-caching documentation establishes the general principle that dynamic, per-request-varying content must be kept identifiable and separated from static instruction text for a caching mechanism to work correctly — directly applicable to distinguishing "system prompt statically contains the word 'current'" from "system prompt is templated with today's actual date."

## Findings

### Finding 1 — Two production semantic-cache vendors independently converge on user-turn-only scoping for per-request cache decisions (confidence: high, unanimous across primary sources)

**Portkey's Semantic Cache** explicitly and by design excludes the system prompt from its cache-matching logic: *"The system prompt is ignored — changing it does not affect cache hits."* It also requires *"At least one user message must be present"* for the semantic check to apply at all — in Portkey's self-hosted mode, a request containing only system messages is dropped from cache consideration entirely, not silently mismatched. This is a deliberate, stated product contract, not an implementation accident: Portkey's Simple Cache (exact-match mode) is explicitly contrasted as the mode where the full request body — system prompt included — does matter, showing the exclusion in Semantic Cache is a considered choice specific to similarity-based matching. Source: [portkey.ai/docs/product/ai-gateway/cache-simple-and-semantic](https://portkey.ai/docs/product/ai-gateway/cache-simple-and-semantic) (primary, fetched live).

**GPTCache's `Config` class** defaults its `skip_list` parameter to `[system, assistant]` (`gptcache/config.py`; verified against current `main`, stable since a November 2023 commit), documented as being *"for sequence preprocessing, skip those sentences in skip_list."* This default is consumed directly in the library's core pre-processing pipeline: `concat_all_queries()` (`gptcache/processor/pre.py`) iterates a request's `messages` and does `if message["role"] in skip_list: continue` before concatenating what remains into the string used as the cache-key/embedding input. The practical effect matches Portkey's stated design even though GPTCache frames it as an exclusion list rather than an allow-list: by default, only non-system, non-assistant content (in practice, user and any other unlisted role such as `tool`) feeds the similarity computation. Source: [github.com/zilliztech/GPTCache/blob/main/gptcache/config.py](https://github.com/zilliztech/GPTCache/blob/main/gptcache/config.py) and [.../processor/pre.py](https://github.com/zilliztech/GPTCache/blob/main/gptcache/processor/pre.py) (primary, verified live + via commit history).

Two independently-built, unrelated production systems reaching the same design under different mechanisms (an explicit ignore-list vs. an explicit skip-list) is the strongest available signal that user-turn-only scoping is the field's converged-on convention for *this specific class* of decision — even though neither vendor publishes prose naming it as a general principle (see Finding 3).

### Finding 2 — Where role-scoping is absent, it is an undiscussed gap, not a rejected alternative (confidence: high, unanimous)

Three separate systems that build per-request caching logic touching the full message list do **not** scope by role at all, and in each case the omission appears to be an unexamined default rather than a considered decision:

- **GPTCache's own most common pre-processing function, `last_content()`**, is purely positional — `data["messages"][-1]["content"]` — with no role check anywhere in it or its siblings (`last_content_without_prompt`, `last_content_without_template`). It is the library's *default* `pre_embedding_func` (confirmed against `Cache.init()`'s parameter default in `gptcache/core.py`). This coexists in the same library as the role-aware `skip_list`/`concat_all_queries` from Finding 1 — meaning GPTCache itself is internally inconsistent: its default pre-processor ignores role, while its opt-in multi-turn pre-processor role-scopes by default. No changelog or docs explain this inconsistency.
- **LangChain core's built-in exact-match cache** (`BaseChatModel._generate_with_cache()`, `libs/core/langchain_core/language_models/chat_models.py`) serializes the *entire* message list — system, user, assistant alike — via `dumps(normalized_messages)` and uses that as the literal cache lookup key, with zero role-based filtering. A 2024 GitHub issue (#25912) flagged the closely related problem that the cached value itself is a full serialized message object rather than plain content; a follow-up PR proposing an opt-in `cache_text_only` flag was explicitly rejected by a maintainer as adding more complexity than it's worth. LangChain core also has **no content-based volatility/freshness heuristic at all** in this path — the only cache-skip condition is the boolean `self.cache is not False`, confirmed by direct source read and corroborated by a zero-hit GitHub code search for `volatile`/`freshness`/`ttl` in cache-adjacent code across the whole repo.
- **Helicone's cache-key hashing** treats the complete request body (`Complete request payload including all parameters`) as a single undifferentiated blob for hashing — system and user content alike, with *"any change in these components creates a new cache entry."* The only exclusion mechanism is `Helicone-Cache-Ignore-Keys`, which drops specific named JSON fields (e.g. `request_id`) structurally, not by message role. Helicone also documents no content-based volatility heuristic; staleness is governed purely by a `Cache-Control` TTL header (default 7 days).

Sources: [raw.githubusercontent.com/zilliztech/GPTCache/main/gptcache/processor/pre.py](https://raw.githubusercontent.com/zilliztech/GPTCache/main/gptcache/processor/pre.py), [github.com/zilliztech/GPTCache](https://github.com/zilliztech/GPTCache) (README, temperature knob), [github.com/langchain-ai/langchain/blob/main/libs/core/langchain_core/language_models/chat_models.py](https://github.com/langchain-ai/langchain/blob/main/libs/core/langchain_core/language_models/chat_models.py), [github.com/langchain-ai/langchain/issues/25912](https://github.com/langchain-ai/langchain/issues/25912), [docs.helicone.ai/features/advanced-usage/caching](https://docs.helicone.ai/features/advanced-usage/caching) (all primary, all verified live).

This matters directly for Kelvran's fix: **there is no established engineering convention this bug is violating by omission** — role-unaware cache-key/eligibility logic is a common, silent default failure mode across this entire product category, not something only Kelvran got wrong. The two vendors that *do* get it right (Finding 1) did so specifically for semantic/similarity-matching paths, where a system prompt's static boilerplate polluting the match signal is an obvious, visible correctness bug (every request "matches" every other request that shares the same system prompt) — the same shape of bug `isVolatileQuery` has, just inverted (every request bypasses instead of every request hits).

### Finding 3 — No general "user-turn-only by default" principle is documented in the caching or prompt-engineering literature; the closest analog is a security paper about trust, not caching (confidence: medium, 2-1 vote on the closest candidate source)

No source found states a general rule of the form *"any per-request heuristic inspecting message content for a caching/routing/safety decision should default to user-turn-only unless there is a specific stated reason to include system content."* The closest documented analog is OpenAI's "Instruction Hierarchy" paper (Wallace, Xiao, Leike, Weng, Heidecke, Beutel — arXiv:2404.13208), whose core observation is that *"LLMs often consider system prompts... to be the same priority as text from untrusted users and third parties"* — i.e., the industry's documented failure mode is treating system and user content as **equally trusted for behavioral/safety purposes**, which is the mirror-image problem of Kelvran's bug (here, system content is treated as equally *volatile-content-bearing* as user content, when its role in the request is structurally different: static/repeated vs. per-request/varying). This paper is about prompt-injection trust boundaries, not caching, and its proposed fix (a formal system > user > tool priority ordering) does not directly transfer to a caching-eligibility decision — it was checked and specifically rejected as a "closest documented analogue" during adversarial verification of this research. So: the *practice* converges (Finding 1), but the *principle* is not written down anywhere as a named pattern. This is worth naming explicitly in Kelvran's own docs (e.g. as a comment on the fixed `isVolatileQuery`, or a short note in `THREAT_MODEL.md`/`ARCHITECTURE.md`) precisely because no external citation exists to point to — Kelvran would be documenting a real but currently-unnamed convention, not restating an established one.

Source: [arxiv.org/abs/2404.13208](https://arxiv.org/abs/2404.13208) (primary).

### Finding 4 — Dynamic/templated system-prompt content is a real, separately-documented caching hazard — but the industry's fix is positional (where in the prompt), not role-based (which role), and doesn't map cleanly onto a keyword-bypass heuristic (confidence: high for the underlying mechanism, medium for its applicability to Kelvran's specific case)

OpenAI's prompt-caching documentation explicitly instructs developers: *"If developer instructions or shared material contain timestamps, user-specific content, or other dynamic content, place those at the end rather than the beginning"* — specifically because dynamic content early in a prompt invalidates the cached prefix on every request. This confirms that "a system message whose content genuinely varies per request" (e.g., a system prompt templated with `Today's date is {{date}}`) is a real, industry-recognized pattern distinct from "a system message that is static but happens to contain a volatility keyword." However, this guidance solves a **different problem** (prefix-cache reuse for the *prompt itself*, at the token level, keyed on *content stability*) than Kelvran's problem (whether to bypass a *response* cache based on whether the query's *topic* is freshness-sensitive). It does not, by itself, tell you how to distinguish the two cases inside a keyword-bypass heuristic — that distinction has to be engineered specifically for Kelvran's mechanism; no vendor's docs address it because no other surveyed vendor has a content-keyword volatility bypass at all (Finding 2's negative result). Source: [developers.openai.com/api/docs/guides/prompt-caching](https://developers.openai.com/api/docs/guides/prompt-caching) (primary, live-fetched; confirmed as the current canonical URL — the older `platform.openai.com` path 301-redirects here).

Practically, for Kelvran: a system prompt *template* is static across requests (the literal string `"you may discuss current stock prices"` never changes), even when the *rendered* system message differs per request because of an interpolated variable elsewhere in that same message (e.g., a date field). A keyword match against `volatileQueryPattern` cannot tell those two cases apart just from role — it would need to know which *part* of the system message is the static instruction template versus the interpolated variable, which Kelvran's `adapter.Message` (a flat `Content string`) does not currently represent. This is why the smallest safe fix (Finding 5 / Recommendation) is to stop inspecting system content at all for this specific heuristic, rather than to try to teach the heuristic to distinguish "static keyword" from "dynamic keyword" within a system message — that distinction would require new structure Kelvran doesn't have and no surveyed vendor has needed to build for a keyword-bypass mechanism, because no surveyed vendor has one.

## Answering the four questions directly

**1. Do other production caching layers restrict freshness/volatility checks to user-turn content, or is this under-discussed?** Both, depending on the system. It's an explicit, stated design in Portkey's Semantic Cache and an implicit but consistently-applied default in GPTCache's `skip_list` (Finding 1) — genuinely restricted to user-turn content by design in the two systems that do similarity-based cache matching. But it is *silently absent* (not discussed, not defended, not attacked) in every system that does exact-match / hash-based caching (GPTCache's own default pre-processor, LangChain core, Helicone) — an under-discussed gap, not a considered rejection (Finding 2). No surveyed system has a content-keyword volatility heuristic at all, so no direct precedent exists for exactly Kelvran's mechanism.

**2. Is there a broader principle, and is it documented anywhere?** The *practice* (scope to user-turn) is real and converged-upon among the systems that got it right, but no general principle of this shape is documented in caching or prompt-engineering literature under any name (Finding 3). The closest adjacent literature (OpenAI's instruction-hierarchy work) addresses a structurally different problem (behavioral trust, not cache eligibility) and its proposed fix doesn't transfer directly. Kelvran fixing and *naming* this convention in its own docs would be filling a real gap in the field's write-ups, not citing an existing one.

**3. Are there legitimate cases where system-prompt content should affect a freshness decision?** Yes in principle — a system prompt genuinely re-templated per request with live data (Finding 4) is a real pattern OpenAI's own docs treat as a first-class caching hazard. But Kelvran's current `adapter.Message` has no sub-message structure to distinguish "static instruction text" from "per-request-injected variable" within one system message's `Content` field, and no other surveyed vendor's volatility/freshness heuristic needs to make this distinction (because none has a comparable keyword-bypass mechanism). Building that distinction now would be solving a problem with no evidence it currently occurs in Kelvran's traffic (Kelvran has zero production traffic per `STATUS.md`/`DECISIONS.md`, consistent with the "instrument now, decide later" pattern already used elsewhere in this codebase, e.g. `docs/upgrade-research/gateway-routing-scope-2026-09-07.md`'s adaptive-routing deferral) — and no external precedent for how to do it safely inside a keyword-regex heuristic specifically.

**4. Concrete recommendation for Kelvran.** Scope `isVolatileQuery` to `role == "user"` messages only. This is the smallest, safest fix, directly supported by Finding 1's two production precedents (Portkey, GPTCache) and Finding 2's negative result (no vendor argues for including system content in this kind of check). It requires touching one function body (`gateway/internal/gateway/dataplane/dataplane.go:756-765`) and no schema changes, since `adapter.Message.Role` (`gateway/internal/adapter/types.go:20-21`) already carries the value needed — it is simply not read today. It does not attempt to solve the harder, currently-unevidenced problem of dynamic/templated system prompts (Finding 4) — that would require new message-level structure Kelvran doesn't have and no surveyed vendor has needed to build for this specific mechanism, so it should be deferred, not bundled into this fix, consistent with the codebase's existing "don't build ahead of evidence" discipline.

## Recommendation Detail

**Smallest fix**: change `isVolatileQuery`'s loop condition from matching every message to matching only `role == "user"` messages:

```go
func isVolatileQuery(messages []adapter.Message) bool {
	for _, m := range messages {
		if m.Role != "user" {
			continue
		}
		if volatileQueryPattern.MatchString(m.Content) {
			return true
		}
	}
	return false
}
```

This is a pure narrowing of an existing bypass check — it can only make L3 available in *more* cases (where today it was wrongly forced off by static system-prompt boilerplate), never fewer. It does not touch, weaken, or interact with the entity/number/date hard-gate (`Fingerprint`, checklist item 4) or the freshness/risk model (`freshnessRiskModel`, items 1/3/5) — both remain fully independent, unweakened gates on the actual cache hit path, so this does not run afoul of `AGENTS.md`'s rule against weakening L3's hard gates; it only fixes which messages feed a *different*, upstream bypass decision (checklist item 2) that runs before those gates are even reached.

**What this fix deliberately does not attempt**: distinguishing "system prompt statically contains a volatility keyword" from "system prompt is dynamically re-templated with live volatile content per request" (Finding 4). No surveyed production system needs to make this distinction for a keyword-bypass mechanism, because no surveyed system has one; Kelvran has zero production traffic to show whether templated system prompts with per-request-varying freshness-relevant content are even a real pattern in its own usage. If evidence later shows this matters (e.g., an operator reports a templated system prompt causing incorrect L3 behavior in either direction), the fix at that point would need new structure — e.g., distinguishing static template segments from interpolated variables within a message, which is a `docs/rfcs/` -sized design question, not a one-line change — and should be scoped then, against real telemetry, not now.

**Suggested follow-up documentation** (not code): since Finding 3 found no existing external citation for the general principle this fix embodies, consider adding a short comment at `isVolatileQuery`'s definition site naming the convention explicitly — e.g., "scoped to user-role messages only: system-prompt content is static/repeated across requests and must not drive a per-request cache-bypass decision (see `docs/upgrade-research/gateway-cache-volatility-scope-2026-09-09.md`)" — so a future contributor doesn't accidentally revert to scanning all roles under the assumption that "more coverage is safer."

## Caveats

- **No LLM-specific academic or industry literature on this exact failure mode was found.** All Finding-1 evidence is inferred from how two vendors *built* their systems, not from either vendor writing a blog post or doc page that names "role-scoping" as a deliberate defense against this specific bug class. The convergence is real but silent — treat it as strong circumstantial evidence, not a citable best-practice document.
- **GPTCache is internally inconsistent** (Finding 2): its default pre-processor (`last_content`) ignores role entirely while its `skip_list`-driven multi-turn pre-processor (`concat_all_queries`) role-scopes by default. This means "GPTCache does it right" is only true for the specific, not-default, multi-turn path — a nuance that matters if anyone cites GPTCache as an unqualified example.
- **This research did not survey every relevant vendor.** TensorZero, Bifrost, and Anthropic's own (non-caching) prompt-caching guidance were touched only tangentially or refuted during adversarial verification (see refuted-claims list from the underlying research pass) — e.g., a claim that Anthropic's docs name "breakpoint on content that changes every request" as a common mistake analogous to Kelvran's scenario was checked and refuted (0-3 vote), so Anthropic's prompt-caching docs should not be cited as direct support for this report's recommendation, despite surface-level topical similarity.
- **The "legitimate dynamic system prompt" scenario (Finding 4, question 3) is plausible but unconfirmed against Kelvran's actual traffic** — Kelvran has zero production traffic (per `STATUS.md`/`DECISIONS.md`, corroborated independently in `docs/upgrade-research/gateway-routing-scope-2026-09-07.md`'s second-pass reaffirmation), so there is no evidence this pattern occurs in practice for this project specifically; the recommendation to defer it is a judgment call following this codebase's own established "instrument now, decide later" discipline, not a claim that the scenario is impossible or unimportant in general.
- **Time-sensitivity**: all vendor docs/source were fetched live on or around 2026-09-09; GPTCache, LangChain, Portkey, and Helicone's caching mechanisms could change in future releases. The OpenAI Instruction Hierarchy paper is ~2.4 years old (April 2024) but is cited here only as a historical/descriptive claim about what that paper argued, not as a claim about current 2026 model behavior.

- If/when Kelvran gets real production traffic, should the entity/number/date hard-gate (`Fingerprint`) itself also be reconsidered for role-scoping, or is extracting entities from system-prompt content (e.g., a system prompt naming a specific product or currency) actually desirable there, unlike the volatility bypass? This report deliberately did not extend its recommendation to `Fingerprint` — that gate serves a different purpose (exact-match rejection, not bypass) and was out of scope for this question, but the two gates' role-scoping conventions could reasonably diverge and that divergence isn't yet justified in writing anywhere.
- Does Kelvran's `adapter.Message` need a way to represent "this system message contains an interpolated, per-request-varying segment" (Finding 4) for any *other* subsystem (e.g., provider-side prompt caching, if/when Kelvran adds it) — independent of this specific L3 volatility-bypass fix?
