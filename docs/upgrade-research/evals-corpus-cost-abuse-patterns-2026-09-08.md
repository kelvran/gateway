# Real-World Cost-Abuse, Billing-Fraud, and Budget-Bypass Patterns — Eval Corpus Seed Research

**Date:** 2026-09-08
**Scope:** Externally-documented cost-abuse/billing-bypass/EDoS attack patterns against LLM API gateways and comparable financial check-then-act systems, surveyed specifically to seed *additional* `category:cost` cases in `evals/tests/fixtures/regression_corpus_dogfood.json`, distinct from the two cases already mined from this project's own bug history (the `budget_usd` bare-digit boolean-misparse bug and the cache-hit-coalesced-follower double-charge bug). This is 1 of 3 parallel deep-research passes (the other two cover cache attack patterns and routing/chaos patterns) feeding a follow-on regression-corpus-growth round — this document does not touch or reference those two.
**Method:** Adversarial multi-source research (3-vote verification per claim) against real CVEs/GHSAs in comparable LLM gateways (LiteLLM — the only comparable gateway that produced surviving claims; Portkey, Kong AI Gateway, and Bifrost were in scope but returned no verified evidence), a primary academic paper on agentic token-amplification attacks, canonical web-security research on TOCTOU/race-condition limit-overrun exploits, and one independently-disclosed CVE in an unrelated product demonstrating the same root-cause pattern in a financial (wallet-balance) context. 18 claims survived 3-vote adversarial verification; 1 claim was refuted; 6 claims could not be verified due to verifier infrastructure errors (neither confirmed nor refuted — see Caveats). This document adds the Kelvran-specific "why it matters here / how it maps onto `internal/budget`, `internal/costaccounting`, `internal/ratelimit` / concrete case-authoring scenario" layer the raw adversarial verification deliberately does not do.

---

## Executive summary

Real-world cost-abuse against LLM gateways clusters into five distinct, independently-documented attack classes, none of which duplicate Kelvran's own bug history. First, **credential-exfiltration-via-SSRF** is a confirmed, patched CVE in LiteLLM (a client-controlled upstream-endpoint parameter let an attacker redirect a request — and the provider API key riding with it — to their own domain, CVE-2024-6587): the billing-fraud mechanism is stolen-credential reuse, not a logic bug in cost math. Second, **check-then-act race conditions (TOCTOU)** are a well-established, canonically-documented web-security attack class — explicitly including "withdrawing cash in excess of your account balance" and "bypassing a rate limit" as named exploit variants — with a real production incident (a duplicate-bounty-payout bug in HackerOne's own payments code) and a real, independently-disclosed CVE in an unrelated product (a wallet-transfer function with no transactional lock between balance-check and balance-write) providing concrete, reproducible templates; this class maps directly onto Kelvran's own `budget.Tracker.Allow` (check) → `Record` (debit) split and `internal/ratelimit`'s token-bucket check-then-decrement, both of which are exactly the check-then-act shape this research class targets. Third, **token-count/pricing-discrepancy bugs distinct from Kelvran's own Decimal-precision migration history** are real and currently open in LiteLLM: a custom-pricing cost-calculator helper that double-counts cache tokens, and a streaming-response usage-object-discard bug that silently falls back to a local token estimate (losing cache-discount information) and produced a measured 4x single-request overcharge and 3.2x daily-total overcharge in a real deployment. Fourth, **legitimate-mechanism economic-denial-of-sustainability** — SkillBloat, a 2026 academic paper, demonstrates a malicious agent skill inflating a real coding-agent task's token consumption 26.39x (and estimated cost from $0.21 to $5.41) purely by inducing the agent to do more real, legitimately-billed work, with no rate-limit or budget-check circumvention at all. Fifth, a cluster of **privilege-escalation/mass-assignment bugs adjacent to (not squarely inside) cost abuse** — two real LiteLLM CVEs letting an under-privileged caller mutate fields (including a role field) beyond what an endpoint's access check intended — is included because it maps structurally onto Kelvran's own `internal/admin` virtual-key mutation surface, even though the verifier explicitly flagged this cluster as privilege-escalation rather than cost-abuse in kind.

## Findings, ranked

### 1. SSRF-enabled provider-credential theft leading to unauthorized billed usage (High confidence)

**What:** LiteLLM versions prior to 1.44.8 accepted a client-supplied `api_base` parameter on `POST /chat/completions` and used it, unvalidated, as the actual outbound request destination — including the real upstream provider API key riding along with the redirected request (CVE-2024-6587 / GHSA-g26j-5385-hhw3). An attacker sets `api_base` to a domain they control, and the gateway forwards the real credential to them.

**Why it matters for Kelvran specifically:** the mechanism (a client-controlled field that changes where a privileged, server-held credential gets sent) is a general pattern worth testing for defensively even though Kelvran's request schema does not currently expose an equivalent field — the case-authoring value here is a regression guard *against ever adding one without a strict allowlist*, not a bug Kelvran currently has. The downstream consequence — a stolen provider key reused for unauthorized calls billed against the original tenant — is squarely a billing-fraud/cost-abuse outcome even though the entry vector is a credential leak, not a budget-math bug.

**Evidence:** Confirmed 3-0 against the primary GitHub Security Advisory (`github.com/advisories/GHSA-g26j-5385-hhw3`), cross-referenced to NVD, CVSS v4 8.7 (High), with the actual fix commit (`ba1912a`) independently confirmed to add `api_base`/`base_url` to a `banned_params` rejection list. The consequence claim (stolen key reused for unauthorized/billed usage) is a direct, non-speculative reading of the same advisory's own text ("leading to unauthorized access and potential misuse of the API key"), also confirmed 3-0.

### 2. Check-then-act race conditions (TOCTOU) against budget caps and rate limits — a well-established, reproducible exploit class (High confidence)

**What:** A canonical, named web-security vulnerability class ("limit overrun" race conditions, a subtype of time-of-check-to-time-of-use/TOCTOU flaws) exploits the race window between a check (e.g., "is there enough budget/quota left?") and the corresponding state update (e.g., "record this spend") by firing near-simultaneous concurrent requests that all pass the check before any single request's update commits. PortSwigger's canonical reference explicitly names "withdrawing or transferring cash in excess of your account balance" and "bypassing an anti-brute-force rate limit" as documented exploit variants of exactly this pattern — not hypothetical, but a standard, actively-taught class. A dedicated PortSwigger research paper ("Smashing the State Machine") further documents a "single-packet attack" technique that synchronizes 20-30 HTTP/2 requests to arrive within ~1ms of each other (4-10x tighter than prior techniques), specifically engineered to reliably win exactly this kind of race window regardless of ordinary network jitter — meaning a naive check-then-write gate with even a few milliseconds of window is not safe against a motivated attacker. Two independent real-world instances corroborate the class is exploited in practice, not just theorized: HackerOne's own payments code had a race condition letting a reporter receive duplicate payouts for the same bounty; and an unrelated, independently-disclosed 2026 CVE (AVideo, CVE-2026-34368 / GHSA-h54m-c522-h6qr) shows the textbook version of the bug in a financial context — a wallet-transfer function reads the sender's balance, checks sufficiency in application code, then writes the new balance, with no database transaction or row-level lock anywhere in between.

**Why it matters for Kelvran specifically:** this is the single most directly-applicable class in this research. Kelvran's own `budget.Tracker` (`gateway/internal/budget/budget.go`) exposes exactly this shape as two separate methods — `Allow(keyID, capUSD, resetInterval) bool` (the check) and `Record(keyID, costUSD, resetInterval)` (the debit) — called from different points in the request pipeline (the check necessarily happens before the real upstream call completes and its true cost is known; the debit happens after). `internal/ratelimit`'s token-bucket check-then-decrement is structurally the same shape. Whether Kelvran's actual implementation closes this race (e.g., via a lock held across both calls, or an atomic reserve-then-reconcile step) is a real, testable question this research does not itself answer — it establishes that the attack class is real, named, reproducible, and specifically targets check-then-act budget/quota gates, which is exactly what a regression eval case should probe.

**Evidence:** The core PortSwigger claims (check→apply→update TOCTOU sequence; named exploit variants including cash-withdrawal-in-excess-of-balance and rate-limit bypass; the single-packet-attack synchronization technique and its measured 4-10x effectiveness) were each confirmed 3-0 against `portswigger.net/web-security/race-conditions` and `portswigger.net/research/smashing-the-state-machine` directly. The HackerOne duplicate-payout report was confirmed 2-0 against the report's own server-rendered metadata (the full JS comment thread could not be rendered, so some peripheral sub-claims about that report were left unverified — see Caveats). The AVideo TOCTOU root-cause claim was confirmed 3-0 against NVD, the official CVE record, the vendor's own GitHub Security Advisory, and the vendor's own vulnerable/patched code diff. **Note:** a more specific sub-claim describing exactly how an attacker would exploit the AVideo bug via multiple concurrent sessions was put to adversarial vote and refuted (1-2) — the TOCTOU root cause itself is confirmed; the specific multi-session exploitation narrative built on top of it is not, and is excluded from the scenarios below accordingly.

### 3. Real, currently-open token-counting/pricing-discrepancy bugs distinct from Kelvran's own Decimal-migration history (High confidence)

**What:** Two separate, currently-open (as of this research date) LiteLLM GitHub issues document real billing distortions caused by token-count/pricing miscalculation, neither related to the float-vs-Decimal precision class Kelvran's own bug history already covers:

- **Custom-pricing cache-token double-count** (`litellm/issues/40006`): LiteLLM's `cost_per_token()` helper re-adds cache tokens into `prompt_tokens` on the assumption they were not already included — but for providers (confirmed for Anthropic) whose response-transformation layer already folds cache tokens into `prompt_tokens` before the cost calculator runs, the addition happens a second time, but *only* when a deployment uses a custom (non-default) per-model pricing override. Default/public-pricing-table requests are unaffected because they never go through this helper at all.
- **Streaming final-chunk usage discard** (`litellm/issues/36168`): when the final SSE chunk of a streamed response carries the real `usage` object (including `prompt_tokens_details.cached_tokens`) *and* a non-empty `choices` array (rather than the "expected" empty-`choices` shape), LiteLLM's streaming aggregator discards the entire upstream usage object and silently falls back to its own local token-count estimate — which has no cache-hit information at all. The reporter measured a real production consequence: a single request billed $0.12 instead of the correct $0.03 (4x overcharge on that request) and a 3.2x overcharge on that model's entire daily cost total, because every cache-discount-eligible request hitting this code path lost its discount. Two independent third parties reproduced the same root cause against different providers/versions.

**Why it matters for Kelvran specifically:** Kelvran's `internal/costaccounting` computes real Decimal-precision cost from provider-returned usage; the failure mode class here — a cost-calculation path silently substituting a local/fallback estimate for real provider usage data, losing cache-discount or other pricing-relevant fields in the process, specifically under an edge-case wire-format shape (a non-default pricing override, or a streaming final-chunk shape that deviates from the "usual" one) — is a generically real category of billing bug independent of the specific Decimal/float precision issue already in Kelvran's own history. It's directly testable: does Kelvran's own usage-extraction path handle an unusual-but-valid final-chunk shape, or a custom-pricing override with pre-folded cache tokens, without either double-counting or silently discarding real usage data?

**Evidence:** Both issues confirmed 3-0 directly against the primary GitHub issue trackers (`github.com/BerriAI/litellm/issues/40006` and `/issues/36168`), including verbatim reproduction code/output, independent third-party reproduction comments, and (for #40006) a contributor's independent confirmation plus an open draft fix PR with regression tests. Neither issue has been disputed, closed as invalid, or superseded as of the research date.

### 4. Token-amplification / legitimate-mechanism economic denial of sustainability (High confidence)

**What:** SkillBloat (arXiv, Zheng & Chen, submitted 22 Aug 2026) demonstrates a documented case where a malicious or adversarially-rewritten agent "skill" (an injected instruction/context artifact, not a request-shape exploit) causes a coding-agent task's real token consumption to rise from 38,410 to 1,013,561 tokens — a 26.39x amplification — for what remains, to the caller, the same nominal task. The same case study's estimated cost under real model pricing rises from $0.21 (benign baseline) to $5.41 after the attack. Critically, the paper is explicit that this is not achieved by padding document length or any request-shape trick that a size/rate limiter would catch — the agent is genuinely doing more real work (more tool calls, more file edits), each one legitimately priced and billed.

**Why it matters for Kelvran specifically:** this is the cleanest documented example of cost abuse that a rate limiter or a single-request size cap cannot catch by construction, because every individual request in the amplified trajectory is unremarkable — the abuse is only visible in aggregate, across a multi-step agentic run. It is a direct stress test for whether Kelvran's per-key `budget_usd` cap (`budget.Tracker.Allow`) is actually checked before *every* individual completion call in a long agentic run, or only once at session start — and for whether Kelvran has any anomaly signal above the flat budget cap (e.g., cost-per-minute or cost-per-call velocity against an agent_run_id's own historical baseline, distinct from a simple total-spend ceiling).

**Evidence:** Confirmed 3-0 directly against the paper's raw HTML (not a secondary summary), including independent verification of the arithmetic (1,013,561 / 38,410 ≈ 26.39) and confirmation that the paper correctly scopes this as a specific case study (it separately reports a lower ~5.4x-10.4x average range and a higher 75.86x single-run outlier, so the cited figures are neither cherry-picked-as-typical nor an exaggerated extreme). The $0.21→$5.41 cost figure and the "not achieved via document padding, achieved via genuinely more work" mechanism were separately confirmed 3-0 against the same primary source's Table 3.

### 5. Adjacent finding: privilege-escalation / mass-assignment bugs on key-management endpoints (High confidence, explicitly flagged as off-target)

**What:** Two real, patched LiteLLM CVEs concern access control on account/team-management endpoints, not cost-math directly, but both map structurally onto surfaces Kelvran has recently built:

- **GHSA-qqcv-vg9f-5rr3 / CVE-2024-5710** (versions < 1.40.15): improper access control on team-management endpoints let any authenticated attacker create, update, view, delete, block, and unblock *any* team and add/remove members from *any* team — not just their own.
- **GHSA-wpfp-gwwc-vwq6 / CVE-2026-47102** (versions < 1.83.10, CVSS 8.8): the `/user/update` endpoint correctly restricted a caller to updating *only their own account*, but did not restrict *which fields* on that account could be changed — letting a user set their own `user_role` field to `proxy_admin` via ordinary mass assignment, a full privilege escalation despite the endpoint's "own record only" check technically holding.

**Why it matters for Kelvran specifically, despite being outside the cost-abuse category proper:** Kelvran's `internal/admin` (the virtual-key mutation surface added 2026-09-05, per `THREAT_MODEL.md`'s Spoofing/Elevation-of-Privilege rows) is exactly the kind of endpoint this bug class targets — a surface that can live-mutate a virtual key's `budget_usd`, `allowed_models`, and rate-limit fields. The CVE-2026-47102 pattern specifically — "the ownership check is correct, but the field-level allowlist is missing" — is a directly testable question against Kelvran's own admin mutation path: can a caller (even one legitimately scoped to update their own virtual key's metadata, if such a self-service path is ever added) change fields beyond what their scope should permit, such as raising their own `budget_usd` or clearing their own `allowed_models` restriction? The verifier explicitly noted this cluster is privilege-escalation in kind, not cost-abuse — included here, with that caveat stated plainly, because the downstream consequence of exactly this bug shape (an unprivileged caller granting itself unlimited budget) is a budget-bypass outcome even though the root cause is an authorization bug rather than a cost-accounting bug.

**Evidence:** Both CVEs confirmed 3-0 directly against their official GitHub Security Advisory Database records (cross-referenced to NVD, with fix commits/PRs and, for CVE-2026-47102, a corroborating third-party vulnerability blog and bounty listing).

## Concrete scenarios for case authoring

Organized by attack class; each maps to a specific real-world citation from the findings above. These are scenario *descriptions* for a follow-on case-authoring pass to turn into `EvalCase` `task_spec`/`reference` pairs — none of these assert Kelvran currently has the underlying bug; each is a regression/defense-in-depth probe against `internal/budget`, `internal/costaccounting`, `internal/ratelimit`, or `internal/admin`.

**Class 1 — Credential exfiltration → unauthorized billed usage**

1. A request field that would let a caller override the upstream provider endpoint (an `api_base`-equivalent) must never exist unauthenticated/unvalidated in Kelvran's request schema — if one is ever added, it must be server-side-allowlisted, never client-controlled verbatim. *(LiteLLM CVE-2024-6587 / GHSA-g26j-5385-hhw3)*
2. A leaked/stolen provider API key's blast radius should be bounded by the compromised virtual key's own `budget_usd` cap, not by the shared provider credential's full available spend — verify that a virtual key hitting its cap is rejected even mid-stream, regardless of which upstream credential is backing it. *(same CVE, consequence half)*

**Class 2 — Privilege-escalation-enabled budget bypass**

3. A caller with a narrowly-scoped credential (e.g., limited to viewing or rotating their own virtual key) submits a mutation request to `internal/admin`'s virtual-key endpoint that also includes an unrelated field (`budget_usd`, `allowed_models`, or a rate-limit field) — assert the endpoint applies a strict per-role field allowlist, not just an "own record" ownership check. *(LiteLLM CVE-2026-47102 / GHSA-wpfp-gwwc-vwq6)*
4. An authenticated caller without admin scope attempts to create, block/unblock, or view a *different* tenant's virtual key via the admin API — assert per-caller authorization is enforced on every mutation/read, not just bearer-token authentication. *(LiteLLM CVE-2024-5710 / GHSA-qqcv-vg9f-5rr3)*

**Class 3 — Legitimate-mechanism token amplification / EDoS**

5. A single agentic run's completion calls collectively balloon from a nominal ~40K-token trajectory to over 1M tokens (each individual call unremarkable in isolation) — assert `budget.Tracker.Allow` is re-checked before *every* completion call in a multi-step run, so a mid-run blowup is rejected before the cap is exceeded, not just checked once at run start. *(SkillBloat, arxiv.org/html/2608.21929v1)*
6. The same amplification pattern inflates a single agent run's real cost by >25x relative to its own historical/expected baseline for that task shape, while staying within a generously-sized flat `budget_usd` cap — assert Kelvran surfaces a cost-velocity or cost-multiple-of-baseline anomaly signal per `agent_run_id`, not only a binary cap-exceeded/not-exceeded check. *(SkillBloat, same paper)*

**Class 4 — Race-condition (TOCTOU) double-spend against budget and rate-limit caps**

7. A virtual key has exactly enough remaining `budget_usd` headroom for one more request of cost C. N concurrent requests of cost C each are fired against it. Assert exactly one succeeds and N-1 are rejected — not that all N pass the pre-call check before any single request's `Record` call commits. *(PortSwigger "race-conditions" canonical reference: cash-withdrawal-in-excess-of-balance variant; template CVE: AVideo CVE-2026-34368 / GHSA-h54m-c522-h6qr's read-check-write-with-no-lock shape)*
8. The same concurrent-burst pattern targeted at `internal/ratelimit`'s per-key token bucket, timed to land within the same check-then-decrement race window, attempting to push realized RPM/TPM usage above the configured cap. *(PortSwigger race-conditions: "bypassing an anti-brute-force rate limit" named variant)*
9. A tightly-synchronized burst (requests arriving within ~1ms of each other, emulating the "single-packet attack" technique) against either the budget check or the rate-limit check, to verify Kelvran's enforcement holds even when the race window is far narrower than ordinary sequential/loosely-parallel test traffic would ever produce — i.e., the regression guard should not rely on "requests never really arrive this close together in practice." *(PortSwigger "Smashing the State Machine" — 20-30 requests within ~1ms, 4-10x tighter than prior synchronization techniques)*
10. A double-*credit* analogue of Kelvran's own already-fixed double-*charge* bug: if Kelvran ever adds a refund/credit-back path (e.g., reconciling an over-estimated pre-call reservation), assert a race between two concurrent credit events for the same underlying spend cannot double-credit the same refund, mirroring the real production incident where a payments platform's check-then-credit code let a reporter receive duplicate payouts for one bounty. *(HackerOne report 220445)*

**Class 5 — Token-counting/pricing-discrepancy bugs distinct from Kelvran's Decimal-migration history**

11. A provider's usage payload reports `cached_tokens` already folded into `prompt_tokens`, under a non-default (custom) per-model pricing configuration — assert Kelvran's cost calculation applies the cache-read discount exactly once, not twice (once as ordinary input, once again as a separately-added cache-token bucket). *(LiteLLM issue #40006)*
12. A streamed response's final usage-bearing SSE chunk arrives with a non-empty `choices` array (rather than the "typical" empty-`choices` final-usage shape) — assert Kelvran's streaming cost accounting still uses the real provider-reported usage (including any cache-token discount) rather than silently substituting a local token-count estimate that has no cache-hit information. *(LiteLLM issue #36168 — real measured impact: 4x single-request overcharge, $0.12 billed vs. $0.03 correct)*
13. Extending #12 to an aggregate/detection angle: assert Kelvran has some reconciliation or anomaly signal that would surface a systematic per-request overcharge pattern (e.g., a model's daily total cost diverging from an independent token-count-based expectation), not only a per-request unit test — the real-world incident this is modeled on compounded a 4x single-request bug into a 3.2x overcharge on an entire day's cost for one model. *(LiteLLM issue #36168, aggregate-impact half)*
14. A request that legitimately mixes a cache hit (served by Kelvran's own L1/L2/L3 cache, not the provider's) with a genuine, unshared upstream call in the same billing window — assert that Kelvran's own already-shipped fix for cache-hit/coalesced-follower double-charging (the existing `dogfood-cost-cache-hit-coalesced-follower-double-charge` case) is retested against the *token-counting* discrepancy angle specifically: does a cache hit ever get costed using a stale or estimated token count rather than being correctly excluded from provider-usage-based billing entirely? *(synthesis of Finding 3 against Kelvran's own existing dogfood case — not a new external citation, included because it's the natural intersection point a follow-on pass should not miss)*

**Lower-confidence / candidate for a future pass (not included in the 14 above because the underlying claims failed adversarial verification due to infrastructure errors, not because they were refuted):** a multimodal/cached-token-overlap double-counting claim against LiteLLM's `generic_cost_per_token()` (issue #37281) was raised by this research pass but its 3 verifier votes all errored — neither confirmed nor refuted. If a follow-on pass wants a fifteenth scenario in the token-counting class, re-verify that issue directly before authoring a case from it.

## Caveats

- Of the four comparable LLM gateways/proxies explicitly named in the research brief (LiteLLM, Portkey, Kong AI Gateway, Bifrost), surviving verified claims exist only for **LiteLLM**. Portkey, Kong AI Gateway, and Bifrost produced zero surviving cost-abuse-specific claims and remain genuinely unanswered on this specific question, not answered "no" — this mirrors the sibling gateway research report's own finding that several named competitors return no evidence rather than negative evidence.
- One claim was explicitly refuted during adversarial verification (1-2 vote): a specific multi-session exploitation narrative built on top of the AVideo CVE-2026-34368 TOCTOU root cause. The root-cause claim itself (check-then-write with no lock) is confirmed 3-0 and is used in Scenario 7 above; the refuted narrative is deliberately not reflected in any scenario.
- Six claims could not be verified due to verifier infrastructure errors (2 or 3 of 3 votes errored, not disagreed) — genuinely unresolved, not refuted: two sub-claims about the HackerOne duplicate-payout report (whether the exploit required precise timing, and whether the financial loss was absorbed by HackerOne vs. passed through to bounty-sponsoring companies), and four claims describing a purported multimodal/cached-token-overlap double-counting bug in LiteLLM's `generic_cost_per_token()` (issue #37281), including its specific worked-example numbers (a claimed ~2.8x overcharge) and root-cause mechanism. None of these are reflected in the confirmed findings or the 14 scenarios above; the #37281 material is flagged separately as a lower-confidence candidate for a future pass.
- Time-sensitivity: the SkillBloat paper (arXiv, submitted 22 Aug 2026) and both open LiteLLM issues (#40006 filed 2026-09-06, two days before this research; #36168 filed 2026-08-07) are current and, for the two GitHub issues, explicitly *unresolved as of this research date* — a follow-on pass authoring cases from them should note they may be patched by the time cases are written, which would change the case from "documents an open bug in a comparable product" to "documents a since-fixed bug," not invalidate the scenario's value as a regression probe either way. The two LiteLLM CVEs (2024-5710, 2024-6587) and the AVideo CVE (2026-34368) are all patched, historical vulnerabilities in their respective products — cited as real, reproducible attack-pattern templates, not as claims that those products remain vulnerable today.
- The PortSwigger race-condition research ("Smashing the State Machine," Aug 2023) is roughly three years old relative to this research date but is the still-current, actively-cited canonical reference for this vulnerability class industry-wide — no superseding or contradicting research was found.
- This document's Kelvran-specific mapping (which internal package/function a given real-world pattern targets, e.g. `budget.Tracker.Allow`/`Record`) is this document's own synthesis layer, added on top of the adversarially-verified external claims — the raw claims themselves make no assertion about Kelvran's code at all, consistent with the sibling gateway research report's own stated convention for this layer.

## Open questions

- Does Kelvran's `budget.Tracker.Allow`→`Record` split (and `internal/ratelimit`'s check-then-decrement) actually hold a lock, or otherwise serialize, across concurrent requests for the *same* `keyID`, or is there a real, currently-untested race window matching Class 4 above? This research establishes the attack class is real and reproducible elsewhere; it does not itself inspect or claim anything about Kelvran's current concurrency behavior.
- Does Kelvran's agent-run-level cost accounting (the `agent_run_id`/OTel Baggage propagation named in `THREAT_MODEL.md`'s Repudiation row) check `budget.Tracker.Allow` before every individual completion call within a multi-step run, or only once per run/session — the exact question Scenario 5 targets?
- Is there a plausible request shape in Kelvran's own streaming or custom-pricing paths (if/when Kelvran supports per-deployment pricing overrides) that could trigger the same class of usage-object-discard or cache-token double-count bug found in LiteLLM issues #36168 and #40006, even though Kelvran's cost accounting is Decimal-precision (which prevents the *float rounding* class of bug, not the *wrong-field-added-twice* or *fell-back-to-a-different-data-source* class)?
- Should the unverified LiteLLM issue #37281 (multimodal/cached-token overlap double-counting) be re-researched directly in a future pass, given it would add a sixth token-counting-discrepancy scenario if confirmed, and Kelvran already ships multi-modal content support (per `docs/rfcs/2026-09-06-gateway-multimodal-content.md`)?
