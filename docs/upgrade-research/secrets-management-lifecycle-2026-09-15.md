# Secrets Management & Credential-Lifecycle — Upgrade Research (2026-09-15)

> **Supersedes the shallow verdict in `docs/upgrade-research/performance-reliability-edge-hardening-2026-09-14.md`'s RQ4** ("rotate the key now; Vault is disproportionate until the next credential"). That verdict is still true but incomplete — it treats "rotate" as the only lever and doesn't explain why the same leak recurred *three* times (2026-09-13, and twice on 2026-09-14) with zero rotation between occurrences. This report goes one level deeper: it traces the incident to a specific, real Docker Compose tooling gap (no verified drop-in redaction exists), and — going beyond every prior pass on this topic — verifies against Kelvran's **actual, already-shipped Go code** that the long-lived key can be *eliminated*, not just rotated, today, with zero code changes. See `AGENTS.md`'s Gotchas section and `SECURITY.md`'s "Added 2026-09-14" operator disclosure for the incident's own record.

**Scope.** The leaked credential is an AWS IAM access key/secret pair for a Bedrock deployment, referenced by name via `AccessKeyIDEnv`/`SecretAccessKeyEnv`/`SessionTokenEnv` on `gateway`'s `DeploymentConfig` (`gateway/internal/gateway/controlplane/config.go`) and resolved from a local `.env` file that `docker-compose.yml` substitutes into its services — which is exactly what a bare `docker compose config` resolves and prints in cleartext. This report covers: (1) the highest-leverage fix for the print-to-transcript mechanism itself, (2) whether a low-effort rotation-automation pattern exists for a solo-operator Compose deployment, (3) 2026 AWS guidance on eliminating vs. rotating the long-lived key specifically, (4) whether a second future leak is cheaply detectable, and (5) other checkable 2026 credential-hygiene gaps. 17 claims survived 3-vote adversarial verification.

**Already shipped (not re-litigated):** secrets referenced by env-var name only, never a raw value, in any committed file; virtual keys identified by SHA-256 hash (`internal/identity`); `.env`-based Compose variable substitution.

---

## Executive Summary

The single highest-leverage fix for *this exact incident* is not a better redaction tool — no verified, drop-in tool exists that redacts arbitrary command output (`nopeek` explicitly disclaims it; a plausible-sounding hook candidate was investigated and refuted; the one tool that does this is a non-portable extension of a different project's own harness) — it is eliminating the long-lived key itself, and Kelvran's own code already supports this with **zero changes**: `DeploymentConfig.SessionTokenEnv` is a real, wired-through, optional field (`gateway/internal/gateway/controlplane/config.go:64-68`, consumed at `gateway/internal/gateway/dataplane/dataplane.go:3072-3076`) that flows a resolved AWS session token straight into the SigV4 signer alongside the access key ID and secret. Populating that field with a short-lived AWS STS session triple instead of a permanent IAM user's static keypair — AWS's own unambiguous 2026 guidance for exactly this workload shape (a service running outside AWS) — means a future leak of the same kind exposes a credential that expires in hours, not one that stays live and un-rotated for two-plus days as happened three times running. A repo-level "never print a raw `docker compose config`" wrapper is still worth building (Finding 2) as defense in depth, but on its own it only reduces *how often* the leak happens, not *how much it matters* when it happens anyway. Cheap, scheduled rotation-automation tools for long-lived keys exist (`aws-rotate`, a GitHub Action) but are the wrong layer to invest in here, because AWS's own 2026 guidance for this exact credential type is "replace," not "rotate." Detecting a *second* leak into an agent's own transcript remains a genuine, unsolved gap — GitHub secret scanning categorically does not cover it, and the one purpose-built OSS tool found is manual/human-triggered only.

## Findings

### Finding 1 — The real fix is elimination, not rotation, and Kelvran's own schema already supports it with zero code changes
**Confidence: high** (5 merged web claims, all high-confidence primary-source AWS guidance, corroborated directly against Kelvran's own source — not just general advice)

AWS's 2026 guidance for IAM access keys is unambiguous and consistent across every primary source checked: the Well-Architected Framework's own implementation-guidance table labels the suggested strategy for "IAM access keys" as **Replace** ("Use IAM roles... instead"), explicitly distinct from the **Rotate** strategy it assigns to other secret types (OAuth tokens, DB passwords) in the same table — "eliminate, don't just rotate" is the framework's own structure, not an inference. The AWS Startup Security Baseline (guidance explicitly aimed at teams Kelvran's size) offers *zero* rotation-based option for developer/production-data access — its only three paths are `aws login`, IAM Identity Center, or federated IdP access. For the specific topology that matters here — a workload running **outside AWS** (a Docker Compose host, not EC2/Lambda) — AWS names **IAM Roles Anywhere** or **AWS Systems Manager Hybrid Activations** as the temporary-credential mechanism, again framed as a replacement for the access key, not a rotation schedule for it.

Critically, this is not a "someday, if we ever move to AWS-native infra" recommendation for Kelvran specifically: `gateway/internal/gateway/controlplane/config.go` already declares `SessionTokenEnv` on `DeploymentConfig` — "the name of the environment variable holding an AWS session token, for temporary/STS-issued credentials. Optional even for 'bedrock' deployments" — and `gateway/internal/gateway/dataplane/dataplane.go`'s `setUpstreamAuthHeaders` already builds `aws.Credentials{AccessKeyID, SecretAccessKey, SessionToken}` and hands it straight to the AWS SDK v2 SigV4 signer, which natively supports a non-empty session token. The identical pattern — a commented-out `# AWS_SESSION_TOKEN=   # optional, only for temporary/STS creds` — already exists in `docker-compose.yml` for Vector's separate S3-sink credential, confirming this is an established, intentional, repo-wide convention, not a one-off. Nothing in this signing path needs to change; only the *value* the operator puts in `.env` does.

**Verdict: build now.** Concretely: generate a short-lived credential (`aws sts get-session-token` if using the IAM user directly, or `aws sts assume-role` against a scoped role — either produces an access-key-ID/secret/session-token triple with a bounded lifetime measured in hours, not never) and populate `.env`'s three existing variables with it instead of the permanent IAM user keypair; set `session_token_env` in `config.yaml` (already an optional field, no schema change). This closes the *severity* half of the recurring-leak pattern immediately: a credential leaked into a transcript after this change is only live for the remainder of its session, not indefinitely. The heavier architectural version of this fix — standing up IAM Roles Anywhere with a real trust anchor/CA for fully unattended, non-human-refreshed operation — is a genuine, larger investment; its named trigger is Kelvran moving from manually-run/dev-refreshed credentials to an always-on unattended deployment where nobody is available to re-run `aws sts` on a cadence.

### Finding 2 — No verified drop-in tool redacts a raw `docker compose config` dump; the highest-leverage tooling fix is a small repo-owned wrapper, not a dependency
**Confidence: high** (3 merged claims — 2 confirmed at 3-0, 1 confirmed at 2-1 — plus 6 refuted candidate claims that narrow the search space)

Three specific candidate mechanisms were investigated and each falls short of "drop-in":
- **`docker compose config <service>` scoping** — the convention this research question itself proposed — is undermined by a real, currently-unfixed Docker Compose bug: `--no-interpolate` causes `config` to ignore the `[SERVICE...]` filter argument entirely, so a second, unrequested service's config leaks into output meant to be scoped to one service. A maintainer confirmed this is permanent (filtering "will not be supported on these paths") in the merged fix PR, which only added a warning, not a repair. Separately — and more fundamentally for this incident — scoping to *one* service does nothing to protect a leak where the credential of interest belongs to the exact service being inspected, which is what happened here.
- **`nopeek`** — a plausible-sounding candidate for "a wrapper that redacts secrets from output" — explicitly disclaims this use case in its own README: it only controls how secrets are *injected as env vars into a single child process it launches itself*; it does not redact arbitrary command/tool output, and its own threat-model section states outright that it does not protect against a child command that dumps its environment or logs credentials — precisely the `docker compose config` scenario.
- **`pi-redact`**, the one component that *does* filter arbitrary shell/tool output before it reaches model context, is explicitly scoped to a different project's own agent harness (`my-pi`/`Pi`) — it is bundled and enabled by that harness's own tool-result pipeline, not a standalone, harness-agnostic shell wrapper any coding agent could adopt. A separate, more directly-matching candidate (a tool called "redacted," proposed as a Claude Code PostToolUse hook that would intercept all Bash output before it entered context) was investigated and **refuted** on both its core claims (0-3 votes each) — it does not do what its name and README summary suggest.

**Verdict: build now, but the thing to build is in-repo, not a dependency.** Since nothing off-the-shelf closes this gap, the actual highest-leverage, lowest-effort tooling fix is a small (~10-20 line) repo-committed wrapper — a `Makefile` target or shell function that runs `docker compose config`, pipes it through a regex substitution for known secret-shaped variable names (`*_SECRET*`, `*_KEY*`, `*_TOKEN*`, `AWS_*`) before printing, and is what `AGENTS.md`'s own advisory mitigation ("read only the specific value you need") should point at instead of relying on operator/agent discipline alone. This is strictly weaker than Finding 1 as a fix for *this* incident's severity (redaction only helps if the wrapper is actually used every time; a self-expiring credential helps even when it isn't), but is cheap, real, and worth doing as defense in depth regardless.

### Finding 3 — Rotation-automation tooling for long-lived keys is real but is the wrong layer to invest in, given Finding 1
**Confidence: medium** (2 merged claims, 3-0 and 2-1, plus 4 refuted claims that ruled out lower-effort variants)

Two genuinely real, working automation tools were found: `aws-rotate` (a CLI that rotates `~/.aws/credentials` access-key pairs, explicitly skipping assumed-role/STS profiles since "they don't have access keys" — i.e., it's scoped exclusively to the long-lived-key case), and a GitHub Action (`kneemaa/github-action-rotate-aws-secrets`) that fully automates create-new-key → push-to-GitHub-Secrets-across-repos → delete-old-key on a cron schedule (its own README example: weekly, `cron: '27 13 * * 1'`). Both are real and functional, but three candidate "even cheaper" variants were specifically checked and **refuted**: `aws-vault` does *not* ship a built-in `rotate` subcommand a cron job could wrap (1-2 vote against); `aws-rotate` does *not* support a genuinely zero-infrastructure cron pattern beyond what's already described (0-3); and `aws login`'s short-lived sessions were **not** independently confirmed to be AWS's own framing of "the fix for eliminating long-lived keys" beyond what Finding 1 already establishes via other sources (1-2) — i.e., don't double-count `aws login` as a separate rotation-automation finding.

**Verdict: not_yet, and arguably never, given Finding 1.** Both real tools exist for the case where a long-lived key genuinely cannot be eliminated. But AWS's own implementation-guidance table (Finding 1) labels IAM access keys specifically as "Replace," not "Rotate" — investing effort in *automating* rotation of a credential type AWS's own framework says to stop using at all is optimizing the wrong layer. The named trigger for revisiting this finding: a future long-lived AWS credential Kelvran genuinely cannot replace with a session token or role (e.g., a third-party integration that structurally requires a static key) — for that narrow case, `aws-rotate` on a 90-day-or-tighter cadence (Finding 5) is the real, cheap answer, not a new secrets-manager dependency.

### Finding 4 — Detecting a *second* leak into a transcript is a genuinely open gap; no automated tooling covers it today
**Confidence: high** (2 merged claims, both 3-0)

GitHub's secret scanning — the control this repo's own "beast mode" round already relies on — covers **committed files** only; it has no mechanism for scanning a coding agent's own tool-call transcript or an ad-hoc terminal session, which is a fundamentally different threat surface with no established tooling response. The one OSS tool found that's purpose-scoped anywhere near this space (`transcript-sentinel`) is a manually-invoked local CLI/TUI (`go run . -dir /path` or `-tui`) with **no CI/CD integration and no pre-commit hook anywhere in its repo** — confirmed directly against its GitHub Actions config (none exists) and commit history. It provides only after-the-fact, human-triggered auditing of local agent session folders, not continuous or automatic detection the way GitHub's committed-file scanning is. (A stronger claim — that this tool specifically targets the agent-transcript threat surface by design, as opposed to just being a generic local file scanner someone could point at a transcript folder — did not survive verification at strong confidence and is not being relied on here.)

**Verdict: not_yet as automated coverage; build now only as a manual habit.** Nothing found closes this gap with real automation. The closest practical, low-effort partial mitigation available today is not a specific verified tool but a general pattern: periodically pointing any standard secret scanner (the class of tool GitHub's own scanning belongs to) at wherever a coding agent's session transcripts persist on disk, as a manual, scheduled check — genuinely better than nothing, but explicitly after-the-fact detection, not prevention, and this specific sub-recommendation is lower-confidence than the rest of this report since it wasn't itself put through adversarial verification. The named trigger for a real automated version: if transcript-bound leaks recur even after Finding 1 and Finding 2 ship — at that point a dedicated CI-integrated transcript scanner (built, not adopted, since none exists) becomes worth the investment.

### Finding 5 — Two complementary hygiene controls exist for any residual long-lived key, but neither substitutes for Finding 1
**Confidence: high** (2 merged claims, both 3-0)

For whatever long-lived AWS credentials genuinely can't be eliminated (Finding 3's narrow residual case): AWS's own baseline cadence, corroborated across five independent current AWS sources (re:Post, Prescriptive Guidance, Security Hub, AWS Support's own health-check tool, the Security Blog), is rotation **at least every 90 days** — explicitly framed as a floor for residual cases, not the preferred end state. Separately, IAM Access Analyzer's **unused-access analyzer** type generates a distinct, configurable finding (1-365 day window) for IAM user access keys that simply haven't been used recently — a genuinely different signal from "this key leaked," useful for catching *forgotten* keys, not exposed ones, and worth enabling as a standing hygiene check regardless of the rest of this report.

**Verdict: build now, as residual/complementary controls only.** Enable IAM Access Analyzer's unused-access finding type (low effort, native AWS console/API feature, catches a different problem than this incident) and, for any key Finding 1 genuinely can't retire, set a 90-day-or-tighter rotation reminder. Neither replaces eliminating the Bedrock key per Finding 1 — both are what to do for the credentials that structurally can't be eliminated, not a softer alternative for the one that can.

## Options Considered and Ruled Out

For transparency, these plausible-sounding candidates were specifically investigated this round and did not hold up:

- **`redacted` as a Claude Code PostToolUse hook** that intercepts Bash output (including a `docker compose config` dump) before it reaches model context — refuted 0-3; does not do this.
- **`redacted`'s env-var-name keyword matching** (SECRET/TOKEN/PASSWORD/API_KEY/etc.) as a way to catch AWS-key-shaped output — refuted 0-3, same tool.
- **`aws-vault rotate <profile>`** as a primitive a cron job could wrap — refuted 1-2; no such built-in command confirmed.
- **`aws-rotate` supporting a zero-infrastructure cron pattern** beyond its documented CLI invocation — refuted 0-3.
- **`aws login`'s short-lived sessions** as an independently-sourced "eliminate, don't rotate" signal distinct from the AWS Well-Architected/Startup-Baseline sources already cited in Finding 1 — refuted 1-2 (real feature, just not independently corroborated as *this specific* framing).
- **IAM Identity Center "eliminating the need for long-lived keys for individual users"** as a standalone claim beyond what the Well-Architected Framework's own Replace-strategy table already establishes — refuted 1-2 (redundant with, not additive to, Finding 1's stronger sourcing).
- **`transcript-sentinel` as purpose-built for agent-transcript leaks specifically** (vs. a generic local file scanner) — refuted 1-2; its lack of CI integration (Finding 4) is confirmed, but its specific design intent is not.
