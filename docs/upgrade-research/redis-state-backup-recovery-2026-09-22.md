# Redis-Backed Financial State — Backup & Disaster-Recovery Research

**Date:** 2026-09-22
**Scope:** The Redis-backed hot state the gateway now depends on for correctness across replicas — `internal/budget/redisbudget` (per-key USD spend ledger), `internal/identity/redisstore` (admin-API-created/rotated virtual-key records), `internal/ratelimit/redislimiter` (RPM/TPM buckets), and `internal/configpropagation` (the live-mutation pub/sub channel) — specifically their **backup, restore, and disaster-recovery** story: RDB/AOF tuning, point-in-time recovery, cross-region replication *for DR* (as distinct from same-region multi-replica traffic serving), and RPO/RTO targets. Excludes traffic-failover/geo-routing for the gateway itself (`docs/upgrade-research/gateway-multiregion-dr-2026-09-13.md` — correctly `not_yet`, a different problem) and the three bbolt stores' own backup/restore story (`docs/upgrade-research/state-durability-operational-recovery-2026-09-15.md` — thorough, but written before this Redis migration existed and never mentions Redis anywhere in its text).
**Method:** Direct verification against the live repository first (every Kelvran-side claim below cites a real file/line), then primary-source research (Redis's own official docs, the `redis/redis` GitHub repository, AWS's own ElastiCache/MemoryDB/Well-Architected documentation, one real production ledger project's own committed DR runbook, and one DORA-compliance fintech guide) fetched via two independent tool paths and cross-checked against each other for the single most version-sensitive claim (Redis's new `BACKUP` command family). This is a single-pass research-and-code-audit report, not a multi-agent adversarial vote panel — the same disclosed convention the sibling state-durability report already established for exactly this reason (code-side claims are highly confident; external claims are primary-source but single-pass).

`docs/upgrade-research/state-durability-operational-recovery-2026-09-15.md` is thorough on backup/restore for Kelvran's *own* state — but its Ground Truth section describes budget, identity, and prompt state as "three independent, single-instance-only bbolt stores," and its Scope section frames the boundary against multi-region as the only excluded territory. This report's territory — is there anywhere to restore from if this specific Redis instance is lost, corrupted, or needs to survive a real disaster — is untouched by either.

## Executive summary

Kelvran's four Redis-backed subsystems do not all carry the same stakes: `redislimiter`'s RPM/TPM buckets and `configpropagation`'s pub/sub channel are both self-healing or inherently ephemeral by design (a lost rate-limit bucket just refills; a pub/sub message that arrives at zero subscribers was never meant to be durable) — but `redisbudget`'s per-key USD spend ledger and `redisstore`'s admin-API-created virtual-key records are exactly the "financially-sensitive state" and "identity records" this research was asked about, and neither has a backup story of any kind today, anywhere in the repo (Finding 1). This is not a hypothetical gap: unlike the bbolt stores the sibling report analyzed (which at least have *some* local single-instance durability even when unconfigured for backup), choosing Redis mode for budget or identity **completely replaces**, rather than supplements, the bbolt path — `newBudgetTracker`/`mergePersistedVirtualKeys` (`gateway/cmd/gateway/main.go`) never open a bbolt store at all once `RedisAddr` is set, even if `PersistPath` is *also* configured (Finding 2). Layered on top of that, the Redis instance itself — `redis:7-alpine` in `docker-compose.yml`, entirely unprovisioned in `deploy/k8s/` — runs with zero persistence configuration of its own (no AOF, no RDB save-point override from the image default, no volume), so the dataset is one `docker compose down` or container recreation away from total loss regardless of the application-level gap above. Redis's own official guidance is unambiguous that RDB alone or AOF alone each carries a real, named durability gap, and that a real production deployment needs a real backup cadence transferred *off* the host — Kelvran currently has none of that, for the specific data classes (spend ledgers, credential records) whose loss most resembles the kind of quiet financial and identity corruption this research was asked to price out (Findings 3–4). Cross-region replication for disaster recovery is a *third*, genuinely distinct problem from same-region multi-replica correctness (which Kelvran already shipped) — the two real production mechanisms (Redis Enterprise Active-Active, AWS ElastiCache Global Datastore) are both paid/managed add-ons Kelvran has adopted neither of, and — importantly — neither one is a substitute for backup at all, since both replicate a flush or corruption event just as faithfully as a legitimate write (Finding 5). Real financial/ledger-adjacent systems in production target RPO in the single-digit-minutes range at the loose end and near-zero at the tight end (via synchronous replication), with RTO in the tens-of-minutes-to-an-hour range for a plain backup/restore strategy — Kelvran has never written down a target for any of this, for any subsystem, Redis or otherwise (Finding 6).

## Findings, ranked

### 1. Kelvran's Redis instance runs with less persistence than Redis's own out-of-the-box defaults, for data now used as a financial ledger (Small)

**What:** `docker-compose.yml`'s `redis` service (`redis:7-alpine`) sets no `appendonly`, no custom `save` points, and mounts no volume — its own comment block explains *why the service exists* (gated behind a `redis` profile, reached at `redis:6379`) but says nothing about persistence at all. `deploy/k8s/README.md` confirms Redis is entirely bring-your-own in Kubernetes: `budget.redis_addr`/`admin.redis_addr`/`config_propagation.redis_addr` are documented config *knobs*, but no StatefulSet, PVC, or Redis manifest of any kind exists anywhere under `deploy/k8s/` — a grep for "redis" across that directory returns only the two files that *reference* the config keys, never a resource that *provisions* Redis itself.

**Why it matters for Kelvran specifically:** as of `[2026-09-21]`, this Redis instance is where every virtual key's real-time spend against its USD cap lives when Redis mode is chosen — the exact "financially-sensitive state" this research was asked about — and `THREAT_MODEL.md`'s own LLM06/LLM10 crosswalk row already names USD budget caps as *the* mitigation for Unbounded Consumption. A container without a mounted volume loses its entire RDB/AOF working set (whatever the image's own defaults produced) on `docker compose down`, `--build`, or any recreation — the identical Compose-volume gap the sibling state-durability report already found for the bbolt stores (`persist_path` files written into the container's writable layer), now reproduced one layer down, in the exact dependency chosen specifically to be the *durable, cross-replica-consistent* alternative to that bbolt path.

**Consistent with settled decisions?** Yes — this doesn't revisit the 2026-09-21 decision to move budget/identity to Redis (a real, correct fix for a real cross-replica-consistency gap, per `DECISIONS.md`'s own account of *why* the plain `Store`-swap design was rejected mid-implementation). It only asks whether the Redis *deployment* underneath that decision was given the persistence configuration the decision's own stakes require, and the answer today is no.

**2026 best practice grounding:**
- Redis's own official persistence docs state plainly: "Make Sure to Backup Your Database. Disks break, instances in the cloud disappear, and so forth: no backups means huge risk of data disappearing into /dev/null" — and separately, that RDB-only durability means being "prepared to lose the latest minutes of data" on any unclean shutdown, since save points fire on an interval, not per-write [redis.io/docs/latest/operate/oss_and_stack/management/persistence — official docs, fetched directly].
- AWS's own ElastiCache FAQ describes Backup and Restore as a first-class, expected feature for exactly this reason: "ElastiCache will take a snapshot of a specified cache that can later be used for recovery or archiving... You can initiate a backup any time you choose or set a recurring daily backup with retention period of up to 35 days" [aws.amazon.com/elasticache/faqs — official].

**Concrete next step:** at minimum, enable `appendonly yes` (see Finding 3 for the fsync-policy choice) and mount a named volume for `/data` on the Compose `redis` service; for the real production target, either provision a managed, persistence-backed Redis (ElastiCache with Backup and Restore enabled, or MemoryDB — see Finding 4) or, if self-hosting, add a real Redis manifest (StatefulSet + PVC) to `deploy/k8s/` rather than leaving it entirely bring-your-own for state this consequential.

**Effort:** Small — Compose is a few lines; the K8s gap is a genuinely missing manifest, but a plain single-node Redis StatefulSet + PVC is not novel infrastructure for this repo (it already has the analogous PVC-vs-`replicas`-1 tradeoff fully reasoned out for bbolt in the sibling report).

### 2. Choosing Redis mode for budget or identity doesn't add a second copy of the data — it's the *only* copy, with zero local fallback even when `PersistPath` is also configured (Medium)

**What:** `newBudgetTracker` and the identity-store construction path in `gateway/cmd/gateway/main.go` (lines ~1173–1197 and ~734–761) both branch on `cfg.RedisAddr != ""` *first*: if Redis is configured, the corresponding bbolt store is never opened at all — not even as a passive, unused fallback — regardless of whether `PersistPath` is *also* set. The only acknowledgment that both were configured is a single `logger.Warn("...redis_addr_and_persist_path_both_set"...)` line; the bbolt file, if one exists on disk from an earlier bbolt-mode run, is simply never touched again.

**Why it matters for Kelvran specifically:** this is a sharper version of a pattern the sibling state-durability report already flagged for bbolt alone (Finding 3 there: "if an operator's disk, volume, or container is lost... every persisted virtual-key override [and] every dollar of tracked spend... is gone, permanently, with no copy anywhere") — except here there is no *local disk* fallback of any kind to begin with, by design, the moment Redis mode is chosen. If the Redis dataset is lost (Finding 1's Compose-volume gap, a `FLUSHALL`, an operator error, a disk failure on a self-hosted node), the recovery path is not "restart and reload from the bbolt file" — there is no bbolt file being written in the first place. Every tenant's real-time spend against its cap and every admin-API-created or -rotated virtual key (the customer's own live credential) is gone with nothing whatsoever to reload from, config.yaml's bootstrap seed included, since `mergePersistedVirtualKeys`'s own documented design treats an admin mutation as the permanently authoritative version from then on — meaning a config.yaml entry for that same key ID may no longer even reflect its real, now-lost configuration.

**Consistent with settled decisions?** Yes — the Redis-vs-bbolt precedence rule itself is a reasonable, deliberate mirror of `identity.Store`'s own established "one authoritative source, not a merge" pattern (per the sibling report's Finding 6 discussion of the same convention for bbolt-vs-config.yaml). This finding doesn't ask to change that precedence; it asks whether "the only copy of a financial ledger and a credential store lives in a cache-shaped datastore with no backup mechanism wired to it at all" is a risk that decision's own commit history weighed, and nothing in `DECISIONS.md`'s `[2026-09-21]` entries suggests it was.

**2026 best practice grounding:**
- The same Redis persistence page cited in Finding 1 explicitly distinguishes "no persistence... sometimes used when caching" from RDB/AOF/RDB+AOF for anything that isn't disposable cache data [redis.io — official docs]. Kelvran's own architecture doc comments in `redisbudget.go`/`redisstore.go` already frame this Redis instance as *more* durable than the bbolt alternative for cross-replica correctness — but durable-across-replicas-while-all-replicas-share-one-Redis-instance is a different property from durable-against-losing-that-one-instance, and nothing in either file's own extensive doc comments addresses the second property at all.
- LiteLLM's own production deployment docs (already cited by the sibling report) draw exactly this line for a directly comparable gateway: Postgres as "the durable system of record for virtual keys/budgets/spend," Redis explicitly scoped to "rebuildable state" [docs.litellm.ai/docs/proxy/deploy — official]. Kelvran's 2026-09-21 migration inverted that: Redis is now the *only* record of budget/identity in Redis mode, not a rebuildable cache layered in front of one.

**Concrete next step:** the narrowest fix is enabling real Redis-level persistence + backup (Findings 1/3/4) so "the only copy" has at least the same disaster-recovery posture LiteLLM's Postgres-of-record gives that data. A more thorough fix — flagged here as a design question, not a recommendation this report is positioned to settle — is whether budget/identity in Redis mode should *also* write through to a bbolt file as a genuinely passive local backup (accepting that a passive `Store.Load`-once swap was explicitly rejected as *architecturally* insufficient for the cross-replica-correctness problem per `DECISIONS.md`'s Phase 7 account — but a write-through *backup* copy, never read from except during a Redis-loss recovery, is a different proposition than the rejected design, which needed the store to be the live source of truth).

**Effort:** Medium — Finding 1/3/4's fixes are Small on their own; the write-through-backup design question, if pursued, touches the same three call sites the sibling report's Finding 4 already identified for bbolt's own corruption-handling question, plus new code in `redisbudget`/`redisstore` to mirror writes.

### 3. RDB vs. AOF tradeoffs, applied to Kelvran's specific data: AOF (`everysec`) is the right default, RDB/backup is still needed on top, and Redis just shipped a purpose-built online-backup mechanism (Small–Medium)

**What:** Redis's own persistence documentation frames the RDB-vs-AOF choice as a genuine tradeoff, not a solved question: RDB is compact and fast to restart from but can lose "the latest minutes of data" on any unclean shutdown (save points fire on an interval, not per-write); AOF is durable down to at most one second of loss with the default `appendfsync everysec` policy, or effectively zero loss with `always` (at a real, documented performance cost) [redis.io/docs/latest/operate/oss_and_stack/management/persistence — official]. Redis's own stated guidance: "The general indication you should use both persistence methods is if you want a degree of data safety comparable to what PostgreSQL can provide you." Separately, and more consequentially for this specific finding: Redis 8.10.0 shipped a new `BACKUP` command family (`BACKUP START`/`SEAL`/`LIST`/`STATUS`/`CLEANUP`/`ABORT`) that produces a self-contained, restorable, online backup — reusing the multi-part-AOF format — without stopping writes or manually pausing AOF rewrites the way pre-8.10 AOF backups required. This is cross-confirmed across three independent primary sources (the official `redis.io` persistence page, the `BACKUP START` command reference page, and the `redis/redis` GitHub repository's own `8.10/00-RELEASENOTES` file), not a single fetch — the claim was deliberately re-verified via a second, independent tool path given how version-sensitive it is.

**Why it matters for Kelvran specifically:** `budget:<keyID>` (a Hash holding `spent`/`epoch`) and `identity:virtual_keys` (a Hash holding every virtual key's exact JSON encoding) are exactly the shape of data Redis's own "comparable to PostgreSQL" framing is describing — not a cache where losing a second of data is a cache miss, but state whose loss means either silently under-enforcing a spend cap or silently discarding a customer's live credential. Kelvran's Redis instance today (Finding 1) has neither RDB nor AOF configured at all, which is a strictly worse starting point than either option alone, let alone both together.

**Consistent with settled decisions?** Yes — this is additive persistence tuning on infrastructure Kelvran already depends on; it revisits nothing about the 2026-09-21 Redis-migration decision itself, only the configuration of the Redis instance underneath it, exactly as Finding 1.

**2026 best practice grounding:**
- `appendfsync everysec` is Redis's own suggested and default policy specifically because it is "both fast and relatively safe," bounding loss to one second's worth of writes — versus `always` (safest, "very slow in practice") or `no` (fastest, loss bounded only by the OS's own flush interval, typically ~30s) [redis.io — official].
- The `BACKUP` command family's restore path uses a startup-only `preload-file` setting (`aof:<manifest-path>` or `rdb:<path>`) that loads *only* the specified backup and skips normal AOF/RDB directory loading — a clean, first-class restore primitive, not a manual file-copy procedure [redis.io/docs/latest/commands/backup-start — official; corroborated by `redis.io/docs/latest/develop/whats-new/8-10` and GitHub's own `8.10/00-RELEASENOTES`].
- For anyone on a pre-8.10 Redis (which almost certainly includes whatever version `redis:7-alpine` in `docker-compose.yml` resolves to today), the older, still-fully-supported pattern is the one this same page documents: cron-driven RDB snapshots at two retention tiers (hourly for 48h, daily for 1–2 months) plus at least one daily transfer *off the host* (S3, SCP to a separate VPS) — explicitly because "disks break, instances in the cloud disappear."

**Concrete next step:** enable `appendonly yes` with the default `everysec` fsync policy (matching Kelvran's own existing tolerance elsewhere for "lose at most a second" — the same order of magnitude `redisbudget`'s doc comments already accept for cross-replica consistency windows) plus RDB snapshotting left at its default save points; layer a genuine off-host backup on top — either a cron job doing the pre-8.10 RDB-copy-to-S3 pattern, or, once running Redis ≥ 8.10, the new `BACKUP` command family, which is the direct Redis-side analog of the `Tx.WriteTo`-based bbolt-backup recommendation the sibling report already made (Finding 3 there) for the *other* half of Kelvran's persisted state.

**Effort:** Small for the `appendonly`/save-point config change itself; Medium for wiring a real, scheduled, off-host backup job (cron + S3 upload, or an admin-API-triggered equivalent, mirroring the sibling report's own suggested shape for the bbolt case).

### 4. Redis's own point-in-time recovery is snapshot-interval-bounded, not arbitrary-timestamp WAL replay — AWS MemoryDB is the purpose-built managed alternative for exactly this durability class, and Kelvran currently references neither it nor ElastiCache anywhere (Medium)

**What:** Nothing in Redis's official persistence/backup documentation describes a mechanism for restoring to an arbitrary point in time the way Postgres's WAL-replay-based PITR does — the granularity ceiling is "whichever snapshot/backup you took," full stop; AOF replay reconstructs state up to whatever was durably fsynced, not to a caller-chosen timestamp. AWS ElastiCache's Backup and Restore feature is explicitly snapshot-based: manual or scheduled (up to 35-day retention) point-in-time snapshots, each restorable into a *new* cluster [aws.amazon.com/elasticache/faqs; docs.aws.amazon.com/AmazonElastiCache/.../backups-restoring.html — official]. AWS MemoryDB, a separate, Redis-API-compatible managed service, is architected differently at the root: "In addition to storing your entire data set in memory, MemoryDB uses a distributed transactional log to provide data durability, consistency, and recoverability... You can use MemoryDB as a single, primary database service for your workloads requiring low-latency and high throughput instead of separately managing a cache for speed and an additional relational or nonrelational database for reliability" [aws.amazon.com/memorydb/features — official]. MemoryDB additionally supports on-demand/scheduled snapshots on top of that transaction log for point-in-time cluster recreation [docs.aws.amazon.com/memorydb/latest/devguide/snapshots.html — official]. Grepping this repo's Markdown for "ElastiCache" or "MemoryDB" turns up exactly one hit, in an *unrelated* Terraform research doc noting that LiteLLM's own reference Terraform module provisions an encrypted multi-AZ ElastiCache replication group — and explicitly recommending Kelvran *not* adopt that module's infrastructure shape ("no Aurora/ElastiCache need yet"). No Kelvran doc anywhere names either service as the production target for the Redis address `budget.redis_addr`/`admin.redis_addr` now point at.

**Why it matters for Kelvran specifically:** the real Bedrock pilot (per this repo's own `DECISIONS.md`/`LOGS.md` history) runs on AWS, and Kelvran's own `docker-compose.yml` `redis` service is explicitly a *local/dev* convenience (per its own comment: "started only with `docker compose --profile redis up`") — meaning the actual production Redis target for this financially-sensitive state is currently undocumented and unspecified anywhere in this repo, at exactly the moment that gap stopped being low-stakes (rate limiting only) and started being high-stakes (spend ledgers, credential records). Choosing self-hosted `redis:7-alpine`-on-a-node versus ElastiCache-with-Backup-and-Restore versus MemoryDB is not a cosmetic infrastructure detail for this data class — it is the difference between "point-in-time recovery ceiling is whatever snapshot cadence someone remembered to configure" and "durability is structural, by design, before any snapshot is even taken."

**Consistent with settled decisions?** Yes — no Kelvran decision doc anywhere commits to a specific Redis deployment target (self-hosted vs. managed) for production; this finding surfaces that the choice is now higher-stakes than it was, not that an existing decision needs revisiting.

**2026 best practice grounding:**
- MemoryDB's Multi-AZ failure-recovery documentation states plainly: "There is no data loss in this scenario as the data was persisted in the transaction log" — for the specific failure mode of the entire cluster being lost and rebuilt [docs.aws.amazon.com/memorydb/latest/devguide/autofailover.html — official]. This is a structurally different durability guarantee than ElastiCache's own snapshot-based Backup and Restore, which protects against loss only back to the last snapshot taken.
- ElastiCache's own backup-restore documentation is explicit that "for better performance, we recommend taking snapshots on a read replica instead of on the master cache node" [aws.amazon.com/blogs/aws/backup-and-restore-elasticache-redis-nodes — official, AWS News Blog] — a real operational detail a naive "just cron a `BGSAVE`" approach on a single self-hosted node would miss entirely (no replica to offload the snapshot's fork/I/O cost onto).
- Even Redis's own commercial Enterprise Software product doesn't offer anything finer-grained: its scheduled-backup feature produces "compressed (.gz) RDB files," with interval options capped at "Every 24 hours, Every 12 hours, Every 4 hours, and Every hour" and no mention of AOF, continuous backup, or PITR anywhere on that page — confirmed unchanged between the versioned (7.8) and unversioned/latest doc revisions [redis.io/docs/latest/operate/rs/databases/import-export/schedule-backups — official, independently re-verified against both doc versions]. This sets a concrete floor under Finding 6's RPO discussion: even paying for Redis's own most durability-focused product tier does not buy PITR finer than a one-hour snapshot interval — MemoryDB's transaction-log-based durability (not snapshot-based at all) is the one option in this finding that structurally beats that ceiling, not just tunes it.

**Concrete next step:** name a real production Redis target in `docs/operations/DEPLOY.md` (currently silent on this) rather than leaving it implicit — MemoryDB if the "financial-ledger-grade durability, not just cache durability" framing this research was asked to evaluate is taken seriously for `redisbudget`/`redisstore` specifically; ElastiCache-with-scheduled-Backup-and-Restore-enabled as the lower-effort, still-materially-better-than-today option if MemoryDB's cost/API-compatibility tradeoffs (a separate evaluation this report did not attempt) aren't a fit.

**Effort:** Medium — this is a deployment-target decision + `DEPLOY.md` documentation, not a code change; the actual infrastructure provisioning (Terraform/CloudFormation for either AWS service) is genuinely new work this report did not scope in detail.

### 5. Cross-region replication for DR is a distinct, largely paid/managed mechanism from Kelvran's existing same-region multi-replica Redis — and even it does not replace backup (Medium)

**What:** Redis ships exactly one cross-region-capable replication mechanism in its open-source core — ordinary primary-replica replication, which Redis's own docs describe as asynchronous by default, with an explicit, named data-loss window on failover: "because Redis uses asynchronous replication it is not possible to ensure the replica actually received a given write, so there is always a window for data loss" [redis.io/docs/latest/operate/oss_and_stack/management/replication — official]. The `WAIT`/`WAITAOF` commands narrow, but do not close, that window ("`WAIT` does not make Redis a strongly consistent store... acknowledged writes can still be lost during a failover") [redis.io/docs/latest/commands/wait, /waitaof — official]. Genuine geo-distributed, multi-primary replication with automatic conflict resolution — Redis's Active-Active (formerly CRDB), built on CRDTs — is scoped explicitly to Redis Software/Enterprise and Redis Cloud, not open-source Redis: "In Redis Software, Active-Active geo-distribution is based on CRDT technology" [redis.io/docs/latest/operate/rs/databases/active-active — official]. Even Active-Active's own docs are explicit that its cross-cluster replication is *also* asynchronous and can lose writes on failover, identically to plain replication: "Active-Active replication, like Redis replication, is asynchronous. An application that fails over to another replica can miss write operations... [those writes can be] lost forever, if the local replica has an event such as a double failure or loss of persistent files" [redis.io/docs/latest/operate/rs/databases/active-active/develop/app-failover-active-active — official]. AWS's managed equivalent for the plain-replication half is ElastiCache Global Datastore — "typical cross-region replication latency of under 1 second... in the unlikely event of Regional degradation, one of the healthy cross-Region replica clusters can be promoted to become the primary cluster with full read and write capabilities in less than 1 minute" [aws.amazon.com/elasticache/features — official]. Independent third-party corroboration (not primary-sourced, used only to confirm the paid-tier framing rather than as this finding's evidence itself) further notes Active-Active/geo-replication is consistently treated across vendors — Redis Enterprise, Azure Cache for Redis's own Enterprise tier — as the recommended answer for demanding cross-region RPO/RTO, with backup/restore alone explicitly framed as insufficient on its own for that bar.

**Why it matters for Kelvran specifically:** this is the one finding that most directly parallels the already-completed multi-region-DR report's own territory, and it reaches a consistent, not contradictory, conclusion — but reframes *why* it's still `not_yet` in Redis-specific terms. That report correctly found no near-term need for geo-distributed *gateway* availability. This finding adds: even if that changed, the Redis-side mechanism to adopt (Active-Active/CRDB, or ElastiCache Global Datastore) would be a genuinely new, currently-unused capability — not an extension of the same-region, single-Redis-instance multi-replica setup Kelvran already shipped 2026-09-21 for `redisbudget`/`redisstore`/`redislimiter`. And critically: adopting either mechanism, if that day comes, does *not* retire the need for Finding 1–3's backup work — a `FLUSHALL` or corruption event on one participating cluster replicates (or, for Active-Active, syncs and reconciles) to every other cluster just as faithfully as a legitimate write, exactly the same "replication is not backup" principle the sibling state-durability report already established via Vault's and etcd's own documentation (Finding 5 there).

**Consistent with settled decisions?** Yes — reinforces, rather than revisits, the multi-region-DR report's `not_yet` verdict; narrows it specifically to "and if that verdict ever changes, this is the Redis-side decision that comes with it, distinct from anything already shipped."

**2026 best practice grounding:** see inline citations above — all primary-sourced against Redis's and AWS's own official documentation, cross-referenced against each other (plain replication vs. Active-Active vs. Global Datastore) rather than taken from a single page.

**Concrete next step:** none required now — this finding exists to pre-empt a future design doc conflating "we already have multi-replica Redis" with "we have cross-region DR for it," which this research confirms are not the same capability and not even the same *product tier* for Redis specifically.

**Effort:** N/A (informational; not_yet, mirroring the sibling multi-region report's own verdict for the gateway-traffic half of this question).

### 6. Real financial/ledger-adjacent production systems target RPO in single-digit minutes (looser tier) to near-zero (tightest tier, via synchronous replication) and RTO in the tens-of-minutes-to-an-hour range for backup/restore — Kelvran has set neither, for any subsystem (Small–Medium)

**What:** AWS's own Well-Architected Framework names four DR strategy tiers in increasing cost/complexity and decreasing RPO/RTO: **Backup and restore** (RPO in hours, RTO ≤ 24h — "automated or continuous backups will permit point in time recovery (PITR), which can lower RPO to as low as 5 minutes in some cases"), **Pilot light** (RPO in minutes, RTO in tens of minutes), **Warm standby** (RPO in seconds, RTO in minutes), and (implicitly, as the tightest tier) **multi-site active/active** [docs.aws.amazon.com/wellarchitected/.../rel_planning_for_recovery_disaster_recovery — official]. A real, current open-source ledger project's own committed DR runbook sets concrete numbers for exactly this class of state: "RPO (max data loss) ≤ 5 minutes — continuous WAL archiving... RTO (max downtime) ≤ 60 minutes — restore base + replay WAL + verify invariants + redeploy," with an explicit escalation path named in the same document: "If ≤ 5 minutes of journals is not acceptable for your product, use synchronous streaming replication to a standby (RPO ≈ 0) and treat PITR as the second line" [`azex-ai/ledger` — `docs/DR.md`, a real, current GitHub repository]. A 2026 DORA-compliance guide for fintech puts the same shape in regulatory terms: "RTO... Minutes (Core transactional systems)... RPO... Near-Zero / Real-Time (Ledgers & balances)" [tenesys.io — DORA-compliant DR guide, dated 2026-09-04]. Kelvran's own repository has never written down an RPO or RTO number for any subsystem — the sibling state-durability report's own Open Questions section already flags the closely related "should backup run on a schedule or only on-demand" question as unresolved for the bbolt case, and this research found the same absence, now for higher-stakes Redis-backed data.

**Why it matters for Kelvran specifically:** without an explicit target, "how often should the backup in Finding 3 run" and "is a self-hosted Redis with a cron job good enough, or does this need MemoryDB's structural durability (Finding 4)" have no answer to be checked against — the choice becomes vibes, not a number derived from what a lost minute of `redisbudget` spend data or a lost `redisstore` virtual key actually costs. Kelvran's own real stakes (a live Bedrock pilot, per `DECISIONS.md`) plausibly sit at the loose end of the spectrum above (Backup and restore or Pilot light, not Warm standby or synchronous zero-RPO) given a single-region, one-Redis-instance deployment with no production traffic history yet to size the real cost of a lost few minutes of spend-tracking against — but that is this report's own inference, not a verified number, and should be labeled as such if repeated (mirroring how the sibling gateway-2026-09-06 report's own Finding 6 flagged an inference-vs-verified-finding distinction on a different question).

**Consistent with settled decisions?** Yes — purely additive; no existing Kelvran decision doc sets or contradicts an RPO/RTO target today, for any subsystem.

**2026 best practice grounding:** see inline citations above — AWS's own framework (official, primary), one real production ledger project's own committed runbook (a genuine current precedent, not a vendor's marketing framing), and one dated 2026 fintech-compliance guide (used only for the RPO/RTO shape it corroborates, not as a regulatory citation Kelvran is actually subject to).

**Concrete next step:** pick and record an explicit number — a reasonable starting point given Kelvran's own current stage (single-region, `not_yet` on multi-region per Finding 5, one live pilot) is the **Backup and restore** tier's own AWS-cited ceiling (RPO as low as 5 minutes via continuous backup, RTO within an hour) rather than either extreme — and write it into `DECISIONS.md` or a dedicated ops doc the way the sibling report's own "restore-rehearsal discipline" citation (a quarterly drill against a scratch instance, per the same `azex-ai/ledger` runbook) recommends actually *testing* it, not just declaring it.

**Effort:** Small for writing the target down; Medium if a quarterly restore-drill practice (mirroring the cited ledger project's own convention) is adopted alongside it.

## Caveats

- **This is a single-pass research report, not a multi-agent adversarial vote panel**, matching the sibling state-durability report's own disclosed convention for the identical reason: every Kelvran-side claim is verified directly against this repository's own code (file paths cited so they can be re-checked trivially), which is a stronger grounding than any external claim gets here — but each external claim rests on a primary-source fetch, cross-checked a second time only for the single most version-sensitive one (Redis's `BACKUP` command family, confirmed across the official docs page, the command reference page, and the `redis/redis` GitHub repository's own release notes independently).
- **The third-party corroboration cited in Finding 5** (a Redis-DR guide, a 2026-03-31 blog post, an Azure-Redis DR comparison) is secondary-source material used only to confirm that Active-Active/geo-replication being a paid-tier-only capability is consistent, current, third-party-observed framing — not this finding's actual evidence, which rests entirely on Redis's own official Active-Active and replication documentation, fetched directly.
- **This report does not evaluate MemoryDB-vs-ElastiCache-vs-self-hosted on cost, API-compatibility, or migration effort** — Finding 4 names MemoryDB as the structurally-more-durable option and ElastiCache as the lower-effort one, but a real recommendation would need a dedicated pass on Kelvran's actual command usage (Lua scripting via `EVAL`, used extensively by `redisbudget`/`redislimiter`, has historically had caveats on some managed Redis-compatible services worth verifying directly against current MemoryDB/ElastiCache documentation before committing).
- **The RPO/RTO numbers in Finding 6 are benchmarks and precedents, not a verified fit for Kelvran's own actual risk tolerance** — this report explicitly flagged its own "loose end of the spectrum" framing as an inference, not a researched-and-confirmed number, precisely because no one at Kelvran has stated what a lost few minutes of spend data actually costs the business.
- **Time-sensitivity is real and specifically flagged**: Redis 8.10's `BACKUP` command family is very new (this report's own date is within roughly the same window the feature appears to have shipped) — re-verify against whatever Redis version Kelvran actually deploys before relying on it, and confirm `redis:7-alpine`'s pinned version in `docker-compose.yml` predates it (meaning the pre-8.10 manual-RDB-backup pattern in Finding 3 is the one that actually applies to Kelvran's current image, not the new command family, until that image is bumped).

## Open questions

1. Should Redis-mode budget/identity write through to a local bbolt file as a passive backup copy, independent of the Redis instance's own persistence (Finding 2)? This report deliberately did not settle this — it's a real design tradeoff, not a researched verdict, and should be weighed against the specific architectural reason the original passive-`Store`-swap design was rejected during the 2026-09-21 migration.
2. What is Kelvran's actual production Redis target today, for the live Bedrock pilot specifically — self-hosted, ElastiCache, or something else — and does it have backup/persistence enabled right now? This report established the *shipped example* (`docker-compose.yml`) and the *shipped Kubernetes manifests* (`deploy/k8s/`) don't wire this up or document it by default, mirroring the identical caveat the sibling state-durability report already raised for the bbolt case's own Open Question 1 — it did not and could not verify the pilot's actual live Redis configuration.
3. Does `redisbudget`/`redislimiter`'s reliance on server-side Lua scripting (`EVAL`) constrain which managed Redis-compatible service Kelvran can actually adopt (Finding 4's MemoryDB-vs-ElastiCache choice)? Not researched here — a genuinely open question this report's own scope didn't reach.
4. Given Finding 6's target is explicitly an inference, not a verified number: what would a lost 5 minutes (or 60 minutes) of `redisbudget` spend-tracking data actually cost Kelvran's real pilot customer(s) in practice — over-billing risk, under-enforcement risk, or reconciliation effort? This is the concrete business-impact question an explicit RPO/RTO commitment should be derived from, and this report does not have the pilot's real usage data to answer it.
