# Kelvran Gateway — Competitor Gap Research: Portkey, TensorZero, Bifrost, Helicone

**Date:** 2026-09-07
**Scope:** `gateway/` — specifically the cost/governance-accountability differentiation thesis `PRD.md` stakes Kelvran's value on: agent-run-level cost attribution, budget enforcement, virtual keys, rate limiting, audit/decision logging. This is a targeted follow-up to `docs/upgrade-research/gateway-2026-09-06.md`, whose Caveats/Open-questions sections named these four competitors as a genuine research gap — zero surviving claims, not an answered "no."
**Method:** Direct primary-source fetches (`WebFetch` against live vendor documentation, plus `gh api`/`raw.githubusercontent.com` for TensorZero's fully open-source docs tree) against each vendor's current, live documentation — **not** the original report's 3-vote adversarial multi-agent verification pipeline (109 sub-agent calls, 3 votes per claim). Every claim below is a single-source fetch, not cross-voted; confidence framing is calibrated accordingly (see Caveats). 15 documentation pages fetched across the four vendors, cross-referenced against Kelvran's own current source (`gateway/internal/identity/identity.go`, `gateway/internal/budget/budget.go`, `gateway/internal/ratelimit/ratelimit.go`, `gateway/ARCHITECTURE.md`, `DESIGN.md`) for an apples-to-apples comparison, not a generic feature list. `mcp__exa__web_search_exa` (this session's available web-search tool) returned a hard rate-limit error on every one of 4 attempted calls before any fetch succeeded — see Caveats for why this is itself a relevant data point.

## Executive summary

All four vendors ship real, current, substantive features directly on-topic for the exact question the original report couldn't answer — the gap really was an absence of evidence, not evidence of absence, and (see Caveats) plausibly a tooling/method limitation on the original pass rather than these vendors having nothing to say. Once direct documentation fetches worked, every one of the four produced citable material on cost/governance accountability specifically.

The headline result is a confirmation, not a gap: **none of the four unify governance enforcement at the level of a multi-step run**, the exact primitive Kelvran's `agent_run_id` already is. TensorZero comes closest — it ships `episode_id`, a first-class, explicitly-multi-step-workflow grouping concept structurally analogous to an agent run — and even there, its own documentation confirms budget/rate-limit enforcement is scoped to tags or API-key public IDs, never to `episode_id` itself (Finding 3). This is the single most direct piece of external evidence available anywhere in this research effort (original pass or this one) that "agent-run-level cost/governance accountability" is a real, unclaimed differentiator, not a redundant restatement of something already shipped.

The one genuinely new, concrete, adoptable idea is **Bifrost's hierarchical, multi-level budget cascade** (Customer → Team → Virtual Key → Provider Config, each level independently tracked, all applicable levels deducted simultaneously per request, any single level's exhaustion blocks the request) — and it lands with unusual force here specifically because Kelvran's own `DESIGN.md` and `gateway/ARCHITECTURE.md` already sketch this exact shape ("hierarchical scope resolution: org → team → user → key → session") and explicitly mark it **target-only, not built** (Finding 1). Portkey's own migration from "Virtual Keys" to a "Model Catalog" with cascading Integration-level budgets/rate-limits/model-allowlists is independent, convergent evidence for the same pattern from a second vendor (Finding 2). Helicone is the one vendor whose cost/governance surface turns out to be mostly redundant with ground the original report already covered (Kong's cost-based rate limiting), with one architectural data point worth noting rather than adopting: its budget-adjacent feature (Alerts) is explicitly notify-only, never enforcement (Finding 4).

## Findings, ranked

### 1. Bifrost's hierarchical, multi-level budget cascade — real production precedent for a design Kelvran already sketched and deferred (Medium-Large)

**What:** Bifrost (Maxim AI's open-source, Apache-2.0, Go-native LLM gateway) structures budgets as a chain — `Customer → Team → Virtual Key → Provider Config` — where a Customer can also attach directly to a Virtual Key (skipping Team), or a Virtual Key can stand alone with no Customer/Team at all. Each level tracks its own usage/limit independently ("each tracks its own usage and limits"); a single request's cost is deducted from **every applicable level simultaneously** (Provider Config, VK, Team, Customer all drop by the same amount for one request); and enforcement is all-or-nothing — "any single budget failure blocks the request," even if every other level in the chain still has room. Rate limiting is a narrower sibling mechanism restricted to the Provider Config and Virtual Key layers only (Teams/Customers carry no rate limits) [docs.getbifrost.ai/features/governance/budget-and-limits, docs.getbifrost.ai/features/governance/virtual-keys — confirmed by direct fetch, single-source]. Breaching a budget returns a typed `402 budget_exceeded`; breaching a rate limit returns a typed `429` with `rate_limited`/`token_limited`/`request_limited` sub-types. Bifrost is Go, Apache 2.0, with published sustained-5000-RPS overhead benchmarks (11µs/request on a t3.xlarge) [github.com/maximhq/bifrost README — confirmed by direct fetch].

**Why it matters for Kelvran specifically:** Kelvran's own `identity.VirtualKey` (`gateway/internal/identity/identity.go`) and `budget.Tracker` (`gateway/internal/budget/budget.go`) are flat today — one `ID`, one `BudgetUSD` cap, no parent/child relationship at all. But `DESIGN.md` line 69 already names the target shape almost verbatim: *"hierarchical scope resolution: org → team → user → key → session"* — and `gateway/ARCHITECTURE.md` (lines 135-137, 221) confirms this is a deliberate, already-made deferral: *"teams/hierarchical scope (org -> team -> user -> key -> session) remain target-only, per `docs/rfcs/2026-09-02-virtual-keys-budgets.md`'s scope boundary."* This finding is not "here is a competitor idea to consider" — it is real, shipping, production evidence that a design Kelvran already committed to on paper works in practice, from a directly comparable Go-native gateway. Kelvran's own sketched target (5 levels: org/team/user/key/session) is actually more ambitious than Bifrost's shipped 4-level chain (customer/team/VK/provider-config) or Portkey's shipped 2-level chain (Finding 2) — this research de-risks building toward that target, it doesn't reveal a smaller ambition already met elsewhere.

**Consistent with settled decisions?** Directly on-topic for `docs/rfcs/2026-09-02-virtual-keys-budgets.md`'s own named scope boundary and the still-open `PRD.md` bullet ("Exact virtual-key/budget data model (sketched in `DESIGN.md`, not finalized)"). Does not conflict with anything settled — it is external validation for an already-deferred, not-yet-decided item, not a re-litigation.

**Is this already covered by Kong/Envoy/LiteLLM (the original report's 6 findings)?** No. The original report's Finding 5 covered Kong's cost-*computation* formula and *multi-dimensional matching* (consumer × model × provider × header × path, deferred to Phase 3b) — a config-time routing/matching problem, not a parent/child budget-ownership hierarchy. A hierarchical cascade where a Team's cap and a Key's cap are both independently tracked and both must have room is a structurally different mechanism from matching a rate-limit rule to a request's dimensions.

**Effort:** Medium-Large. This is not a bolt-on: it requires a new `Team`/`Customer` (or `org`/`user`/`session`, per Kelvran's own already-sketched naming) data model, a cascading-check algorithm in `budget.Tracker` (all applicable levels checked and deducted per request, not just one), admin API surface to manage the new entities, and its own RFC — it touches two of Kelvran's foundational packages (`identity`, `budget`) directly. Not urgent given zero production multi-tenant demand signal exists yet, but now has a real, concrete, external-evidence-backed design to build against whenever that signal appears — which is a materially different position than "sketched, no precedent."

### 2. Portkey's Virtual-Keys → Model Catalog migration — convergent evidence, not a duplicate of Finding 1 (Small, informational)

**What:** Portkey's own "Virtual Keys" documentation page now states plainly: *"Virtual Keys have been migrated to Model Catalog"* / *"The Virtual Keys feature has been upgraded to the **Model Catalog** system"* [portkey.ai/docs/product/ai-gateway/virtual-keys — confirmed by direct fetch]. Model Catalog restructures the same concern into two entities: an **Integration** (a credential vault — "Think of an Integration as a secure vault for your API keys") which can spawn multiple **AI Providers** (e.g. `@openai-dev`, `@openai-prod` slugs). Budgets (USD or token-based, weekly/monthly resets) and rate limits (RPM/hour/day, concurrent-request caps, burst protection) are set at the **Integration** level and explicitly *cascade down* to every Provider spawned from it — Portkey's own language: *"These limits cascade down to all AI Providers created from that Integration."* A separate "Model Provisioning" layer adds allow/deny-lists per Integration, and "Workspace Provisioning" adds per-team/per-environment access control [portkey.ai/docs/product/model-catalog — confirmed by direct fetch].

**Why it matters for Kelvran specifically:** This is independent, second-vendor evidence for the same pattern as Finding 1 — cascading budget/limit ownership above the level of a single credential — arriving from a different architecture (2-level Integration→Provider, vs. Bifrost's 4-level chain). Two vendors independently converging on "a flat virtual key isn't the whole governance model" is a materially stronger signal than either alone. This is presented as a **reasonable inference, explicitly labeled as such**: the underlying feature facts (what Model Catalog ships) are confirmed by direct fetch; the claim that this represents "a market trend across the sector" is my own inference from two data points, not a verified industry-wide claim — a genuinely different and weaker confidence tier, held apart deliberately per this project's own established research-reporting discipline.

**Caveat on the "deprecated" framing:** Portkey's docs use "migrated"/"upgraded," never the word "deprecated" or "sunset," and no date or version stamp is visible on either fetched page — so this should be read as "Portkey evolved virtual keys into something with more governance depth," not "the industry has abandoned the virtual-key concept." Kelvran's own use of "virtual key" as its core identity primitive is unaffected either way; Portkey's Provider `slug` model and Kelvran's own `VirtualKey.ID` play the same structural role.

**Consistent with settled decisions?** No conflict — informational, reinforces Finding 1's priority rather than adding a separate action item.

**Effort:** N/A (informational; folds into Finding 1's effort estimate, does not add a second implementation item).

### 3. TensorZero's `episode_id` — the closest agent-run analog in this entire research effort, and it is *not* wired to governance (Small effort to confirm; High evidentiary value)

**What:** TensorZero's `episode_id` is defined as *"a sequence of inferences associated with a common downstream outcome"* — created automatically on a client's first inference call (returned in the response, never client-generated by convention) and threaded into every subsequent related call via `extra_body={"tensorzero::episode_id": episode_id}`. The docs frame it explicitly for *"multi-step LLM systems"* where the calling application does arbitrary work between calls (retrieval, tool use, user interaction) — the same shape as an agent run, though the word "agent" itself does not appear in TensorZero's own docs [raw.githubusercontent.com/tensorzero/…/gateway/guides/episodes.mdx — confirmed by direct fetch].

Separately and independently confirmed: TensorZero's cost/usage tracking is documented as attributing to **individual inferences and, in aggregate, per model provider** — with no mention of episode-level attribution anywhere in the cost-tracking docs [raw.githubusercontent.com/…/operations/track-usage-and-cost.mdx — confirmed]. Its rate-limiting system (a genuinely more general design than a flat per-key bucket: rules over `model_inferences`/`tokens`/`cost` resources, a real continuously-refilling token-bucket option, and — the one specific, novel mechanic here — **tag-scoped rules with `tensorzero::each` (a separate limit per distinct tag value) vs. `tensorzero::total` (one limit summed across all values) semantics**) scopes by **user-defined tag or API-key public ID only** — `episode_id` is never named as a scoping dimension anywhere in the rate-limiting docs [raw.githubusercontent.com/…/operations/enforce-custom-rate-limits.mdx — confirmed]. Its auth model is a simple bearer-token API key (create/disable/expire lifecycle) with per-key rate-limit scoping but **no fine-grained per-key permissions and no audit-log feature documented anywhere in the auth docs** [raw.githubusercontent.com/…/operations/set-up-auth-for-tensorzero.mdx — confirmed].

**Why it matters for Kelvran specifically — this is the strongest single piece of evidence in this report:** TensorZero built the one competitor primitive structurally closest to Kelvran's `agent_run_id`, and its own documentation shows governance (cost attribution, rate limiting, budget-style caps) is *not* unified with it. If even the vendor with the closest matching concept doesn't tie enforcement to it, "agent-run-level cost and governance accountability" is confirmed — not merely asserted in `PRD.md`, but externally corroborated by this pass — as a real, still-unclaimed gap rather than something quietly already shipped elsewhere under different terminology.

TensorZero's `each`/`total` tag-scoped rate-limit semantics are also worth a smaller, tactical note: this is a genuinely different design angle on the exact gap the original report's Finding 5 already named (Kong's multi-dimensional matching, deferred to Phase 3b) — a rule scoped dynamically to *any* tag value (which could include `agent_run_id` itself as a tag) rather than a fixed enum of dimensions configured per rule. Worth folding into Phase 3b's eventual design discussion as an alternative shape, not a new standalone item.

One thing this finding explicitly does **not** need: cross-instance shared rate-limit state. TensorZero's rules persist in a shared Valkey/Postgres backend specifically so "multiple gateway instances automatically share the same limits" [same source — confirmed] — but Kelvran already ships this exact property via `internal/ratelimit/redislimiter` (`docs/rfcs/2026-09-03-distributed-rate-limiting.md`, confirmed by reading `gateway/internal/ratelimit/ratelimit.go`'s own package doc directly). Flagging this explicitly so it is not mistakenly logged as a gap: it is not one.

TensorZero also documents a "gateway relay" — a two-tier edge/relay architecture letting many team-run gateway deployments centralize auth/rate-limits/credentials at one relay tier [raw.githubusercontent.com/…/operations/centralize-auth-rate-limits-and-more.mdx — confirmed]. Interesting as a different answer to multi-org governance than Kelvran's single-binary, single-config model, but it presupposes an org/team deployment topology Kelvran doesn't have — noted for completeness, not scoped as an actionable item here.

**Consistent with settled decisions?** Directly reinforces, with new external evidence, the differentiation thesis `PRD.md`'s Competitive Positioning section already asserts. No conflict with any settled decision.

**Is this already covered by Kong/Envoy/LiteLLM?** Partially. The general resource-typed (`tokens`/`cost`/count) rate-limit idea overlaps Kong's cost-based rate limiting (original Finding 5); the `each`/`total` tag semantics are a genuinely new angle on that same already-scoped gap, not a wholly new item. The `episode_id`-vs-governance disjunction is entirely new — none of Kong, Envoy, or LiteLLM have an analogous multi-step-run primitive at all, so this is the one finding in this whole research effort (original pass included) that speaks directly to whether *any* competitor ties governance to a run-level concept.

**Effort:** Small (this finding is evidentiary/confirmatory, not something to build — it strengthens the case for Kelvran's existing `agent_run_id` + budget/rate-limit work, rather than adding a new backlog item itself). The `each`/`total` tag-scoping idea, if pursued, folds into Phase 3b's existing Medium-Large scope rather than adding a new item.

### 4. Helicone — mostly redundant with already-covered ground; one enforcement-posture data point worth noting (Small, low-priority)

**What:** Helicone ships real, current cost/governance-adjacent features, but they land closer to observability than to enforcement. Its **Alerts** feature monitors nine metrics (Error Rate, Cost, Latency, Total/Prompt/Completion Tokens, Prompt Cache Read/Write, Count) against a threshold and time window, with optional grouping (User/Model/Provider/custom property) and Sum/Avg/Min/Max/Percentile aggregation — but the action on breach is **strictly notify-only** (email/Slack): *"there is no mention of blocking, throttling, or otherwise interrupting traffic"* [docs.helicone.ai/features/alerts — confirmed by direct fetch]. Its **Custom Rate Limits** feature is a real enforcement mechanism, distinctly configured via a client-set `Helicone-RateLimit-Policy` request header (`[quota];w=[window];u=[unit];s=[segment]`, following the IETF rate-limit-header convention), segmentable by a global scope, `s=user` (paired with a `Helicone-User-Id` header), or `s=[custom-property]` (paired with a matching `Helicone-Property-*` header) — and setting `u=cents` turns the same policy into a dollar-denominated spend cap enforced with a real `429` on breach, e.g. `500;w=3600;u=cents;s=user` caps one user to $5/hour [docs.helicone.ai/features/advanced-usage/custom-rate-limits — confirmed by direct fetch]. Provider-key handling is either Helicone-managed ("credit" mode, "0% markup" pricing) or bring-your-own-key ("Provider Keys") [docs.helicone.ai quickstart, platform-overview — confirmed by direct fetch].

**Why it matters for Kelvran specifically:** The enforcement-capable feature (cost-based rate limiting via header) is real, current, and does hard-enforce — but it overlaps substantially with ground the original report already named (Kong's cost-based, retrospective rate limiting, Finding 5) rather than opening new territory. The one structurally distinct idea — a **client-declared** policy (the calling application sets its own limit via a request header) rather than an **admin-configured** one — was considered and is judged a poor fit for Kelvran specifically: Kelvran's entire virtual-key/budget model is built on the premise that the *operator*, not the *caller*, sets the cap (`identity.VirtualKey.BudgetUSD`/`RateLimitBurst` are config-file-only, never client-settable), and inverting that trust boundary would be a genuine, considered architectural change, not a drop-in feature — noted here as a deliberately-rejected idea, not an oversight.

The Alerts-are-notify-only finding is one more concrete, externally-sourced data point (alongside Envoy's passive circuit breaker needing a traffic floor, LiteLLM's default aggressive single-failure health check, etc.) that Kelvran's `budget.Tracker`'s hard-blocking enforcement is not automatically the industry default even among vendors whose whole pitch is cost visibility — it reinforces, rather than challenges, Kelvran's own enforcement-first posture.

**Consistent with settled decisions?** No conflict. Confirms rather than revisits anything settled.

**Is this already covered by Kong/Envoy/LiteLLM?** Substantially yes for the enforcement-capable feature (cost-based rate limiting is Kong's Finding 5 territory); no new item is warranted from Helicone specifically.

**Effort:** N/A — no action recommended from this finding beyond the documentation value above.

## Recommendation

**This is a genuinely new, concrete, actionable finding worth adding to a future Kelvran roadmap phase — not a redundant restatement of the original six findings.** Specifically:

1. **Add a new Phase-4-candidate backlog item**: "hierarchical/scoped virtual-key budgets" (org/team/user/key/session, per `DESIGN.md`'s own already-sketched target), citing this research's Finding 1/2 as external production precedent (Bifrost, shipping; Portkey, shipping in a lighter 2-level form) for a design Kelvran had previously only sketched on paper with zero outside validation. This item is Medium-Large, touches `internal/identity` and `internal/budget` directly, and should get its own RFC per this project's established discipline — it also directly resolves `PRD.md`'s still-open "Exact virtual-key/budget data model... not finalized" bullet, so the RFC should explicitly close that Open Question, not just add a feature.
2. **No new item needed from Helicone** — its enforcement-capable feature is redundant with already-scoped ground (Kong, Finding 5/Phase 3b); log this explicitly as a confirmed-redundant outcome, which is exactly as valuable as a new finding per this task's own framing.
3. **Fold TensorZero's `each`/`total` tag-scoped rate-limit semantics into Phase 3b's eventual design discussion** as one alternative shape to consider (a rule scoped to an arbitrary tag value, potentially `agent_run_id` itself, rather than a fixed dimension enum) — not a new standalone item.
4. **TensorZero's `episode_id` finding needs no implementation action** — its value is purely evidentiary, and should be cited directly in any future pitch/positioning material alongside `PRD.md`'s Competitive Positioning section as external, primary-source-verified support for the agent-run-level-accountability thesis.

## Caveats

- **Method is a real, deliberate downgrade from the original report's rigor, not an oversight.** The original `gateway-2026-09-06.md` report used a 3-vote adversarial multi-agent verification pipeline (109 sub-agent calls, 25 claims put to a vote, 3 confirmations required). This pass used single-source direct `WebFetch` calls against each vendor's own live documentation — real primary sources, but not independently cross-voted. Every claim above is labeled "confirmed by direct fetch" rather than "confirmed 3-0" specifically to keep this distinction honest and visible, per this project's own established citation convention.
- **This session's web-search MCP tool (`mcp__exa__web_search_exa`) failed on every one of 4 attempted calls** with a hard rate-limit error before any other tool was tried. Direct `WebFetch` against documentation URLs inferred from vendor naming conventions (and, for TensorZero, browsed via `gh api`'s GitHub Contents API against the fully open-source `tensorzero/tensorzero` repo) was substituted and worked cleanly for all four vendors. This is itself a relevant data point for the original report's stated open question: a rate-limited or otherwise-degraded search tool is a **plausible, concrete explanation** for why the original adversarial pass returned zero surviving claims on these four vendors specifically — not proof (the original pass's exact failure mode wasn't logged in enough detail to confirm this directly), but a real, named alternative to "these vendors have nothing to say," which this pass's substantive results now directly support.
- **No date/version stamps were visible on any of the fetched Portkey or Bifrost documentation pages** — unlike the original report, which could cite Envoy AI Gateway's v1.1 release date and Kong's specific 2026-04-07/2026-07-29 patch dates. Treat Findings 1 and 2 as accurate as of this fetch (2026-09-07) but without the same time-anchoring precision the original report achieved for Envoy/Kong.
- Three fetches 404'd and are reported as genuine absences, not treated as confirming a negative: Portkey's specific migration-guide sub-page, and Bifrost's `features/governance/audit-logs` URL (guessed by analogy to its other `features/governance/*` pages — the 404 is consistent with, but does not independently prove, the "no named audit-log feature" conclusion already reached from the virtual-keys/budget pages' own content).
- **A dedicated separate research pass — not this one — would be needed** to adversarially verify these findings at the same 3-vote confidence level as the original report, or to check whether Helicone, Portkey, or Bifrost have shipped anything materially different since this fetch date.

## Open questions

- Would Kelvran's own hierarchical target (5 levels: org/team/user/key/session) actually need all 5 levels, or would Bifrost's 4-level (customer/team/VK/provider-config) or Portkey's 2-level (integration/provider) shape be sufficient for Kelvran's real, still-nonexistent multi-tenant demand? No production signal exists yet to answer this — genuinely open, not guessable from this research.
- Does any vendor outside this four-vendor set (or a newer feature release from one of these four after this fetch date) tie governance enforcement to a multi-step-run concept the way this report confirms none of Portkey/TensorZero/Bifrost/Helicone currently do? This report only speaks to these four vendors as documented on 2026-09-07 — it cannot rule out a fifth vendor or a future release closing this gap.
- Bifrost's all-or-nothing, simultaneous-multi-level-deduction enforcement model (every applicable level checked and debited per request) has real operational implications (e.g., partial-failure/rollback semantics if one level's deduction succeeds and another's check then fails) that this pass's documentation-only research cannot fully verify — a real implementation attempt would need to read Bifrost's actual source, not just its docs, to confirm the exact transactional behavior.
