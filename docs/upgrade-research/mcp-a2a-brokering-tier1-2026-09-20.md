## Executive summary

The MCP spec's core protocol version is **unchanged** at **2026-07-28** — confirmed directly against the GitHub API's real tag list (no `2026-07-28`-successor tag or RC exists) — so the 2026-09-11 report's central timing claim ("this is a live-churn moment, not a settled target") does not get a clean resolution either way from version-bump evidence alone. But it would be wrong to read the frozen date as settling: a new deprecation-registry entry, **SEP-2577 ("Deprecate Roots, Sampling, and Logging")**, merged **2026-09-15** — five days before this research date — formally starts the spec's own 12-month (or 90-day expedited) removal clock on exactly the features the 07-28 revision had already functionally superseded with the Multi Round-Trip Requests pattern. Separately, this pass surfaced a real gap in *both* prior reports: **SEP-2640, the "Skills Extension,"** was merged back on **2026-04-23** — before either predecessor report was even written — and just crossed into **published status via a docs PR merged 2026-09-18**, two days before this research date. It defines a `SKILL.md`-based resource layer (`skill://<path>/SKILL.md`, a `skill://index.json` discovery resource, an `io.modelcontextprotocol/skills` capability flag) standardizing exactly the Agent-Skills-shaped packaging convention visible directly in this very session's own skill list. It is a real, notable, missed-twice gap — and, on inspection, **orthogonal to Kelvran's brokering thesis**: Kelvran is a request-routing/cost/cache proxy, not an agent runtime that loads or executes skills, so this extension has no natural integration point in Kelvran's architecture today. A2A remains completely stable — still v1.0.1 (2026-05-26), no newer tag — reconfirming the 09-11 report's finding that A2A, not MCP, is the settled side of this space. The OAuth 2.1 IETF draft underlying MCP's own authorization model is still unratified, now at revision **-16** (dated 2026-09-03, expires 2027-03-07) — the "not yet an RFC" blocker from both prior reports is unchanged. On Kelvran's own architecture: a direct read of the real, current code (not a re-quote) confirms every peer-derived prediction from the 09-11 report holds *exactly* against Kelvran's actual implementation — `adapter.Registry` is a bare `map[string]Adapter` with the canonical schema genuinely OpenAI-Chat-Completions-shaped (down to `ToolCall`/`ToolDef` carrying custom `MarshalJSON` specifically to preserve OpenAI's native `tool_calls[].function.{name,arguments}` wire nesting), `identity.Verifier` does exactly one thing — SHA-256-hash-match a bearer token to a `VirtualKey` — with zero extension point for a second, downstream credential, and `costaccounting.Calculate(model string, usage Usage) decimal.Decimal` remains purely token-count-and-`ModelPrice`-shaped with no tool-call cost unit anywhere in it. **Net verdict: unchanged from 09-11 — the architecture's shape (canonical schema, stateless-friendly request handling) is still right for the eventual build, the two hard blockers (credential-delegation layer, tool-call cost unit) are still unbuilt, and — checked directly against `DECISIONS.md`/`docs/agents/LOGS.md` through today's own `[2026-09-20]` entry — there is still no recorded real demand signal.** One genuinely new, actionable data point this pass did find: **SEP-414** (OpenTelemetry trace-context propagation via `_meta` keys `traceparent`/`tracestate`/`baggage`, confirmed live in the current 07-28 changelog) gives Kelvran's already-real, already-shipped `agent_run_id`-scoped OTel tracing (`docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md`) a spec-native mechanism to propagate span context across a future MCP hop — closing a small piece of the tool-call-resilience/observability gap the 09-11 report left as an open question, without touching the cost-accounting or credential blockers at all.

## Findings

### 1. MCP's core spec version is unchanged at 2026-07-28 — confirmed via cross-tool verification specifically to rule out a known sandboxed-fetch content-fidelity risk

**What the research found:** `WebFetch` against `modelcontextprotocol.io/specification/versioning` returned "The current protocol version is **2026-07-28**," including a previously-undocumented detail (a mandatory `server/discover` RPC for version negotiation) that this pass could not find in either predecessor report. Because this session's own memory carries a specific caution that sandboxed fetch tools have previously returned stale or mocked documentation content, that specific new claim was independently re-verified via a second, different tool (`mcp__fetch__fetch`) against the spec's own dedicated changelog page, which confirmed it verbatim — `server/discover` is real, tied to a real SEP (SEP-2575), and documented as a MUST for servers. A third, independent check — the GitHub API's real tag list for `modelcontextprotocol/modelcontextprotocol` — shows the most recent tag is still `2026-07-28` (with only its own `-RC` candidate above it); no successor-dated tag exists.

**Why it matters for Kelvran specifically:** the two-tool-plus-API cross-check is the load-bearing methodology point here, not just the result — it directly answers a standing risk (mocked/stale sandboxed doc content) that this session's own operating context explicitly flags, and the result held up under it. Substantively, this reconfirms the 09-11 report's version claim exactly: seven-plus weeks after the stateless re-architecture, there is still no successor spec revision. That said, "no version bump" is not the same claim as "settled" — see Findings 2 and 3.

**Confidence:** High (three independent primary sources — two doc-fetch tools with different underlying mechanisms, plus GitHub's own tags API — in full agreement).

### 2. A new deprecation-registry entry (SEP-2577) merged five days before this research date, formally starting a real removal clock on features the 07-28 revision had already functionally replaced

**What the research found:** SEP-2577, "Deprecate Roots, Sampling, and Logging," shows as `merged: true` via the GitHub API, with `updated_at: 2026-09-15`. This targets exactly the three server-initiated-request mechanisms (`roots/list`, `sampling/createMessage` — both already functionally superseded by the 07-28 revision's Multi Round-Trip Requests pattern per the 09-11 report's own Finding 1 — plus `logging/setLevel`, whose removal from the core RPC set the current changelog also documents). Per the spec's own versioning page (fetched and confirmed in this pass), a feature marked Deprecated "remains in the specification for at least twelve months, or at least ninety days under the policy's expedited-removal exception... before [it] becomes eligible for removal."

**Why it matters for Kelvran specifically:** this is a concrete, dated data point that the spec is still actively moving *underneath* its own frozen version string, via the Deprecated-Features-Registry mechanism rather than a new dated revision — exactly the kind of continued churn the 09-11 report's Finding 1 warned to expect and set an explicit re-check trigger for. It does not change any of Kelvran's own design conclusions (Roots/Sampling were never something Kelvran's identity/cost/credential blockers depended on), but it is evidence against treating the frozen `2026-07-28` tag as proof the ground has stopped moving.

**Confidence:** High (GitHub API's own PR metadata, primary source, unambiguous merge status and date).

### 3. SEP-2640 ("Skills Extension") is a real gap missed by both predecessor reports — it predates them, and just reached "published" status two days before this research date — but it is orthogonal to Kelvran's own brokering thesis

**What the research found:** GitHub API metadata for PR #2640 shows `created_at: 2026-04-23`, `merged: true` — this SEP predates *both* the 2026-09-07 and 2026-09-11 predecessor reports, neither of which mentions it. A cluster of docs-only follow-up PRs (`#3353` "add Skills extension overview and support tracking," created 2026-09-08; `#3360` "add Sambhav Kothari as Skills Over MCP WG lead," created 2026-09-14; `#3366`, a link-fix after an "ext-skills archive move," created 2026-09-16; and `#3372`, "docs: reflect published Skills extension status," created **2026-09-18** — two days before this research date) show the extension moving from draft tracking into formally **published** status essentially now, with its own named working group ("Skills Over MCP WG"). Substantively, the extension defines a resource-layer convention for packaging and discovering agent capabilities: `skill://<skill-path>/SKILL.md` for a skill's markdown definition, individual files addressable as siblings, a `skill://index.json` discovery resource, and an `io.modelcontextprotocol/skills` capability flag declared at initialization — a `SKILL.md`-centric shape that maps directly onto the Agent-Skills convention visible directly in this session's own available-skills listing (the `gstack`, `bmad-*`, and dozens of other `SKILL.md`-shaped entries), not a coincidence given the shared Anthropic lineage evident in the linked reference implementation's own commit trailers.

**Why it matters for Kelvran specifically:** this is a genuine, previously-unflagged gap in the prior research — worth recording precisely so a future pass doesn't have to rediscover it — but on inspection it does **not** change this report's recommendation. Kelvran is an LLM-request-routing/cost/cache gateway; it has no runtime concept of "loading and executing a skill" the way an agent framework (or a client like Claude Code itself) does, and nothing in `gateway/ARCHITECTURE.md`'s MCP/A2A design intent (inbound: expose Kelvran's own APIs as MCP tools; outbound: broker agent tool calls) names anything resembling a skill-packaging/discovery role. Flagged here as a closed research gap and a "know this exists" data point, not as a build recommendation.

**Confidence:** High (GitHub API PR metadata for all dates/merge status; the extension's own technical shape read directly from the linked reference-implementation diff in PR #2640's own comment thread, a primary artifact, not a secondary summary).

### 6. Kelvran's own architecture, verified directly against its real current code rather than re-quoted from the prior reports — every peer-derived prediction holds exactly

**What the research found, reading the actual files rather than trusting either predecessor report's characterization of them:**

- **`adapter.Registry`** (`gateway/internal/adapter/registry.go`) is a one-line type alias: `type Registry map[string]Adapter` — a bare lookup map keyed by `Adapter.Name()`, deliberately built in `cmd/gateway`, never inside the `adapter` package itself, "to avoid this package importing every concrete adapter package — that would invert the intended dependency direction." Simple, leaf, and already exactly the "adapters register into a canonical vocabulary" shape any future MCP-tool-schema bridge would also need.
- **The canonical schema** (`gateway/internal/adapter/types.go`) is confirmed, in its own package doc comment, to be "OpenAI Chat-Completions-shaped, per `gateway/ARCHITECTURE.md`'s 'Canonical Schema & Provider Adapters' section" — and this is not just a loose description: `ToolCall` and `ToolDef` each carry a hand-written `MarshalJSON`/`UnmarshalJSON` pair whose entire purpose is producing OpenAI's *exact* native `tool_calls[].function.{name,arguments}` / `tools[].function.{name,description,parameters}` wire nesting even though the underlying Go structs are flatter. This matters directly for MCP: every peer gateway surveyed in the 09-07/09-11 reports (LiteLLM, Portkey) converts MCP tool definitions into OpenAI-compatible tool schemas as the interchange format between an MCP server's tool catalog and an LLM's own tool-calling API — which is to say Kelvran's canonical `ToolDef`/`ToolCall` shape is *already* the exact target shape that conversion produces, not something that would need inventing or reshaping.
- **`identity.Verifier`** (`gateway/internal/identity/identity.go`) does exactly one job: `Verify(authorizationHeader string) (*VirtualKey, error)` computes the SHA-256 digest of a presented bearer token and does an O(1) map lookup against configured `VirtualKey`s (plus a grace-period `PreviousKeyHash` check for rotation). There is no OAuth client, no token-exchange logic, no per-downstream-credential concept anywhere in this package — confirmed by reading the whole file, not inferred. This is precisely the "clean mapping for the client→gateway admission leg only" shape the 09-11 report predicted from LiteLLM's/Portkey's own peer patterns (Finding 5 there) — now directly confirmed against Kelvran's real implementation instead of an analogy to someone else's.
- **`costaccounting.Calculator.Calculate(model string, usage Usage) decimal.Decimal`** (confirmed via a fresh read of the package's real exported surface) is unchanged in shape from the 09-07 report's own analysis — still `ModelPrice`/token-count arithmetic, with no tool-call-shaped pricing function, flat-fee table, or per-invocation cost concept anywhere in the package.

**Why it matters for Kelvran specifically:** this is the direct, code-grounded answer to this pass's central question — is Kelvran's architecture still the right shape? **Yes, for the parts that were already right, and no differently than before for the parts that were already missing.** The canonical schema and the adapter-registry pattern need zero redesign to support either an inbound MCP-tool-exposure surface or an outbound MCP-tool-consumption surface — they are already shaped exactly like what such a bridge would produce or consume. But `identity.Verifier` and `costaccounting.Calculator` are, by direct inspection, exactly as narrow as the peer-pattern analysis predicted: neither has an extension seam for a second, downstream-server-scoped credential or a non-token-priced cost unit. Nothing in this pass's spec-freshness findings (SEP-2577, SEP-2640, the still-unratified OAuth draft) changes either of those two verdicts.

**Confidence:** High (direct reads of the real, current source files — the strongest form of evidence this report can offer, stronger than either predecessor report's own reliance on peer-implementation analogy for this specific question).

### 7. Two new, concretely useful spec hooks surfaced this pass that neither predecessor report had — one directly usable today with zero blockers, one speculative

**What the research found:** The current (07-28) changelog, read in full this pass, documents two minor changes not discussed in either predecessor report: **SEP-414** adds documented OpenTelemetry trace-context propagation conventions for MCP's `_meta` field (`traceparent`, `tracestate`, `baggage` keys) — a standardized way to carry a distributed trace across an MCP request boundary. **SEP-2549** requires `ttlMs` and `cacheScope` (`"public"`/`"private"`) fields on list-and-read-shaped results (`tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list`) via a new `CacheableResult` interface — a spec-native freshness/shareability hint for exactly the kind of result a client-side cache would want to key on.

**Why it matters for Kelvran specifically:** these land very differently on the "actionable now" axis. SEP-414 is immediately relevant and low-risk: Kelvran already has real, shipped, `agent_run_id`-scoped OTel tracing with GenAI semantic-convention attributes (`docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md`, confirmed still real per `gateway/ARCHITECTURE.md`'s Tech Stack table) — if Kelvran ever builds either the inbound or outbound MCP surface, SEP-414 means the trace-context-propagation mechanism across that hop is already spec-defined, not something Kelvran would need to invent from scratch the way it would for, say, a bespoke gRPC hop. This directly narrows (without fully closing) the 09-11 report's Finding 7 open question about whether tool-call reliability/observability infrastructure generalizes — it answers the trace-propagation piece specifically, not the broader fallback/circuit-breaker-semantics question, which remains unresolved. SEP-2549's `CacheableResult` pattern is more speculative for Kelvran today: it would only become directly relevant if Kelvran built an *outbound* MCP client that caches a downstream server's `tools/list`/`resources/list` results — which remains blocked behind the same credential-delegation and demand-signal gaps as the rest of outbound brokering — but it is worth naming now since Kelvran's own `internal/cache` package already has a mature TTL/cache-scope convention (L1/L2/L3, per-tenant partitioning) that this SEP's shape would slot into cleanly rather than requiring a new cache-semantics design, if and when that day comes.

**Confidence:** High for the technical existence of both SEPs (read directly from the current, primary changelog). Medium for the "slots in cleanly" framing on SEP-2549 specifically — that is this report's own synthesis against Kelvran's real `internal/cache` conventions, not an independently-verified claim, and is explicitly speculative since outbound brokering itself is not being built.

## Recommendation

**The 2026-09-11 report's core call stands, unrevised: MCP/A2A brokering remains correctly out of scope for v1.** Nothing in this pass's spec-freshness check surfaces new cover to build the full brokering subsystem now — the OAuth 2.1 foundation is still a draft, the spec's own deprecation machinery (SEP-2577) shows it is still actively shedding legacy surface even seven-plus weeks after its last dated revision, and a direct read of Kelvran's own code confirms (rather than merely predicts) that both hard blockers named in the prior reports — a downstream-credential-delegation layer distinct from `identity.Verifier`, and a tool-call-shaped cost-accounting unit distinct from `costaccounting.Calculator`'s token arithmetic — are still entirely unbuilt. `docs/agents/LOGS.md`'s own most recent entries (through `[2026-09-20]`, today) confirm zero recorded demand signal for MCP/A2A of any kind; the gateway's real engineering effort since the 09-11 report has gone into config-propagation, embeddings, sticky routing, and telemetry, none of it MCP-adjacent.

**If a concrete demand signal ever does justify starting this work, this pass sharpens (does not redirect) where to start.** The single most valuable, lowest-risk concrete slice — building directly on the 09-07 report's own suggestion that the *inbound* direction ("expose Kelvran's own APIs as MCP tools") is more tractable than outbound brokering, now confirmed rather than assumed against Kelvran's real code — is: **a minimal inbound MCP server exposing Kelvran's existing chat-completions capability as a single MCP tool, admitting callers through the existing `identity.Verifier` bearer-token check exactly as-is, and pricing every resulting completion through the existing `costaccounting.Calculator` exactly as-is.** Concretely, this needs zero new credential model (the inbound, client-facing leg is the one leg every peer surveyed in the 09-11 report — and now Kelvran's own real `Verifier` — already handles cleanly) and zero new cost-accounting primitive (a chat completion invoked via an MCP tool call still produces the exact same token-priced `Usage` Kelvran already bills today; only the transport calling into the existing dataplane pipeline would be new). The 07-28 revision's stateless, no-handshake request model — unchanged and reconfirmed this pass — makes this a smaller lift than it would have been under the pre-07-28 session-stateful design, since Kelvran's dataplane is already a stateless-per-request Go HTTP pipeline with no sticky-session infrastructure to bridge. SEP-414's OTel `_meta` propagation (Finding 7) means this slice could also carry Kelvran's existing `agent_run_id` trace context across the MCP hop using a spec-defined mechanism rather than inventing one. This is a scoping refinement for **when** a demand signal justifies the work, not a signal that one currently exists — none does.

## Caveats

- **This pass deliberately did not re-survey Kong, Envoy AI Gateway, Portkey, or LiteLLM's competitor MCP-governance depth fresh.** The 09-07 report's Finding 1 (as corrected by its own 2026-09-08 second pass — LiteLLM's flat per-call `default_cost_per_query`/`tool_name_to_cost_per_query` mechanism is the best-known competitor cost baseline) is treated as still-current ground truth here; this pass's scope was spec-version freshness and Kelvran's own code, not a fresh competitor sweep. If a future pass has budget, re-checking whether any competitor has since tied MCP tool-call cost to a multi-step/agent-run-scoped ledger (the specific gap both prior reports identified as still-open) would be the natural next competitor-side check.
- **The sandboxed-fetch mocked-content risk this pass explicitly guarded against (Finding 1) is a real, standing operational caution for this session, not a one-time concern.** The specific claim checked here (the `server/discover` RPC detail) held up under cross-tool verification, but that does not retroactively validate every other unfetched claim in this document — every substantive claim in this report that could be checked against the GitHub API or IETF datatracker directly was checked that way in preference to trusting a single doc-rendering fetch alone.
- **`mcp-go`'s SDK-churn-settlement signal (the 09-11 report's own named trigger: "two consecutive spec-version bumps with zero new Removed/Deprecated entries") could not be fully evaluated this pass.** The SDK has moved from a `v1.0.0` stable cut (explicitly built "to support the 2026-07-28 specification") to `v1.1.0`, but `v1.1.0`'s GitHub release notes came back empty via the API — this pass could not confirm whether that minor bump contains any new version-gate/`Removed`/`Deprecated` machinery of its own. Worth a direct diff against the SDK's source (not just its release notes) in a future pass if the SDK-churn signal specifically becomes load-bearing for a build decision.
- **SEP-2640's "orthogonal to Kelvran" framing (Finding 3) is this report's own architectural judgment, not an externally-sourced claim** — the SEP's technical shape and dates are primary-sourced and high-confidence; whether it stays irrelevant to Kelvran specifically is a judgment call that should be revisited if Kelvran's own product scope ever grows toward agent-runtime concerns rather than staying a pure request-routing/cost/cache gateway.
- **Time-sensitivity remains unusually high for this whole area**, consistent with both predecessor reports' own caveats: the SEP-2577 merge (five days old) and the SEP-2640 published-status docs PR (two days old) at the time of this research both land inside this report's own shelf life, underscoring that "current" here means "current as of 2026-09-20," not a stable, citable target.
