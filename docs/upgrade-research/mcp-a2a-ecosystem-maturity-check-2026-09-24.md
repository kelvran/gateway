# MCP/A2A Ecosystem Maturity Check — Revisiting the Gateway MCP "not_yet" Decision (2026-09-24)

**Date:** 2026-09-24
**Scope:** `gateway/internal/mcp` (zero code, confirmed via grep at the time both RFCs below were written) — specifically, whether the trigger conditions named in `docs/rfcs/2026-09-20-gateway-mcp-inbound-design.md` ("no real demand signal yet") and `docs/rfcs/2026-09-11-gateway-mcp-outbound-credential-design.md` ("MCP's own spec stabilizing" AND "a first real integration") have been met as of this date. Both RFCs are design-only/unbuilt; this document does not itself change that status.
**Method:** Adversarial multi-source research (3-vote verification per claim) against the official MCP spec (modelcontextprotocol.io), the GitHub Advisory Database, and the most-adopted production MCP gateway implementations (AWS Bedrock AgentCore Gateway, Microsoft Foundry Agent Service / Azure OWASP MCP guidance, Cloudflare `workers-oauth-provider`). 25 claims were put to adversarial vote; 13 survived (one at 2-1, the rest at 3-0) and 12 were refuted (0-3 or 1-2). Every surviving claim below is grounded in a primary source (the spec/changelog itself, a vendor's own engineering docs/blog, or a first-party GitHub Security Advisory) — no secondary/blog-only claims survived. This document adds the Kelvran-specific "why it matters here / is this consistent with the RFCs' own stated triggers / confidence" layer the raw adversarial verification deliberately does not do.

---

## Executive summary

The MCP spec's foundational anti-passthrough doctrine — MCP servers **MUST NOT** accept or forward a token not explicitly issued for them — has remained settled, unchanged text across at least three spec revisions (2025-06-18 → 2025-11-25 → 2026-07-28), meaning neither RFC's own open questions are resolved by a *rule change*, because the rule was already stable when both were written. What has changed is the weight of *production precedent*: three of the largest-footprint MCP gateway implementations in the market today — AWS Bedrock AgentCore Gateway, Microsoft's Foundry Agent Service (per its own Azure documentation), and Cloudflare's `workers-oauth-provider` — have all independently shipped a per-hop token-exchange / credential-vault pattern that structurally matches, not merely resembles, the `OutboundCredential` abstraction Kelvran's own outbound RFC sketched from first principles against only two peer gateways (LiteLLM, Portkey). A real, generalizing confused-deputy vulnerability (GHSA-rww4-4w9c-7733, in the widely-used FastMCP framework) also confirms the exact OAuth-proxy risk class the RFC cites is live in production, not theoretical. Against that, this research found **zero** dated, primary-source evidence of real customer/operator demand for MCP support specifically on a self-hosted LLM gateway (as distinct from demand for MCP support in agent frameworks or IDEs) — the third research question came back an honest absence of evidence, not a "no." Net: the *design* half of the "not_yet" decision is now meaningfully de-risked and worth a follow-up implementation RFC informed by AWS/Microsoft's shipped patterns; the *demand* half — is anyone actually asking for this on Kelvran — remains exactly as unresolved as when both RFCs were written.

---

## Findings, ranked

### 1. The spec's core anti-passthrough rule is settled doctrine, not an open question — neither RFC's design is blocked on a rule change (High confidence)

**What:** The MCP spec (`2026-07-28`, the current revision) hard-mandates, in RFC-2119 MUST-NOT language, that an MCP server reject tokens not explicitly issued for it, and separately mandates that when an MCP server itself acts as an OAuth client to an upstream API, it MUST NOT pass through the token it received from its own MCP client. Independent secondary sources trace this exact sentence back through the 2025-06-18 and 2025-11-25 revisions unchanged.

**Why it matters for Kelvran specifically:** Both RFCs cite "MCP's own spec stabilizing" as a trigger condition. This finding shows the *specific piece of the spec both RFCs actually depend on* — the anti-passthrough doctrine — has already been stable for over a year across three revisions. Waiting longer for this particular rule to "stabilize further" is not a real blocker; it already has. What continues to churn is adjacent machinery (see Finding 2), not this core rule.

**Consistent with the RFCs' own stated triggers?** Directly addresses the outbound RFC's "MCP's own spec stabilizing" trigger for the one rule the RFC's Alternatives Considered section actually leans on ("Reuse `VirtualKey` unchanged as the outbound credential" is rejected in part because of this exact doctrine). Does not touch the RFCs' other trigger ("a first real integration") — see Finding 2.

**2026 best-practice grounding:**
- MCP servers **MUST NOT** accept any tokens that were not explicitly issued for the MCP server — and separately, if the MCP server acts as an OAuth client to upstream APIs, it **MUST NOT** pass through the token it received from the MCP client; these are two distinct MUST-NOT rules covering both directions of Kelvran's own inbound/outbound split [modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices and .../basic/authorization/security-considerations — both confirmed 3-0].
- Independent secondary sources (dreaming.press, gethasp.com, blog.logto.io) each confirm this exact prohibition traces back to at least the 2025-06-18 revision and has carried unchanged through 2025-11-25 and 2026-07-28 — three consecutive revisions with no relaxation.
- A real-world deviation exists but is narrow and disclosed: `containers/kubernetes-mcp-server` added an opt-in "pure token passthrough mode" (PR #1160) for a niche topology where the cluster itself is the sole token-validating authority — a documented implementation-level tradeoff, not evidence the spec's own guidance changed.

**Concrete next step:** No RFC change needed on this point — both RFCs' existing framing ("Kelvran's `VirtualKey` cannot simply become the outbound credential," "an MCP tool call goes through the same auth/budget objects as any other request") is already aligned with current spec doctrine and does not need re-litigating when a future implementation RFC is written.

### 2. New spec machinery has shipped since both RFCs' research passes — Mix-Up Attack defenses (RFC 9207 `iss` binding) and DCR→CIMD — both directly relevant to a multi-authorization-server outbound broker (High confidence)

**What:** The current spec revision (2026-07-28) adds a distinct "Mix-Up Attacks" section (citing RFC 9207) requiring authorization responses to be bound to the specific authorization server the client recorded pre-redirect — explicitly noting that PKCE alone and resource indicators alone do **not** prevent this class of multi-authorization-server confusion. The same revision deprecates OAuth 2.0 Dynamic Client Registration (RFC 7591) in favor of Client ID Metadata Documents (CIMD), keeping DCR only for backward compatibility.

**Why it matters for Kelvran specifically:** The outbound RFC's whole premise is a gateway brokering calls to potentially many distinct downstream MCP servers, each with its own authorization server — exactly the topology Mix-Up Attacks describe. This is new, concrete guidance a future `OutboundCredential` implementation would need to fold in (bind each authorization response to the recorded issuer, don't rely on PKCE/resource-indicators alone) that neither RFC's own research pass (2026-09-11 / 2026-09-20) surfaced. The DCR→CIMD shift is a smaller, adjacent client-identity mechanism change worth being aware of if Kelvran ever registers itself as an OAuth client to downstream authorization servers, though neither RFC currently depends on DCR.

**Consistent with the RFCs' own stated triggers?** This is a genuine example of "the spec still churning" (the inbound RFC's own Drawbacks section anticipates this: "the spec's deprecation machinery is still actively shedding legacy surface even at a frozen core version") — evidence *for*, not against, continuing to treat MCP/A2A as design-only until a real implementation forces these details to be resolved concretely. One important caveat: the 2026-07-28 spec revision predates both RFCs (2026-09-11 and 2026-09-20), so strictly speaking this is not "new since the RFCs were written" — it is new material the RFCs' own prior research passes simply did not surface, which is a distinct but related gap worth naming honestly.

**2026 best-practice grounding:**
- The Mix-Up Attacks mitigation text is verbatim: "PKCE alone does not prevent this attack because the client transmits the `code_verifier` to the attacker's token endpoint. Resource indicators do not help when the attacker's authorization server is intercepting requests before they hit the honest authorization server" [modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices — confirmed 3-0]. Corroborated by SEP-2468 (the official proposal introducing MUST-level client-side `iss` validation, cross-referencing implementation PRs across multiple SDKs) and the MCP TypeScript SDK's own `IssuerMismatchError` implementation.
- DCR is formally deprecated in favor of Client ID Metadata Documents as of this revision, "available for backwards compatibility with authorization servers that do not support Client ID Metadata Documents" [modelcontextprotocol.io/specification/2026-07-28/changelog — confirmed 3-0], corroborated by the MCP maintainers' own blog post and a first-party WorkOS engineering writeup dated to the same revision.

**Concrete next step:** When a future implementation RFC is written for the outbound leg, explicitly fold in `iss`-parameter validation (RFC 9207) as a named requirement for any multi-authorization-server `OutboundCredential` design — this is now a documented, spec-mandated defense the 2026-09-11 RFC's own research pass did not have.

### 3. Three of the largest-footprint production MCP gateways now implement exactly the per-hop token-exchange pattern Kelvran's outbound RFC sketched from two smaller peers — the design is now externally validated, not merely internally plausible (High confidence)

**What:** AWS Bedrock AgentCore Gateway implements OAuth 2.0 on-behalf-of (OBO) token exchange through a dedicated AgentCore Identity service (RFC 8693 token exchange or RFC 7523 JWT-bearer grant, GA as of this research), re-scoping a client-issued token into a new, audience-bound token before each downstream MCP-server call and centralizing raw OAuth credentials/client secrets in a "secure token vault" so neither the Gateway nor its MCP servers ever handle them directly. The same AWS product architecturally separates inbound (agent-to-gateway) and outbound (gateway-to-tools) authentication into two independently configured surfaces. Microsoft's Foundry Agent Service blocks Microsoft-Entra-scoped tokens from being forwarded to third-party/custom MCP servers outright, requiring a custom MCP server to be registered under an audience the developer controls. Cloudflare's `workers-oauth-provider` (used to build MCP OAuth proxies) shipped RFC 8693 token-exchange support (narrowed-scope/audience/shorter-TTL re-issuance, off by default) as of v0.2.3, since built on with PKCE enforcement and CIMD alignment through v0.10.4.

**Why it matters for Kelvran specifically:** The outbound RFC's own Motivation section built its design entirely from two peer gateways (LiteLLM, Portkey) and explicitly left open "OBO token exchange (LiteLLM's shape) vs. a simpler injected per-server credential (Portkey's shape)... genuinely undecided." This finding shows the two largest cloud providers building MCP gateway infrastructure today (AWS, Microsoft) have both landed on the OBO/token-exchange shape specifically — not the simpler injected-credential shape — which narrows, with real evidence, one of the RFC's own named open questions. It also independently confirms the RFC's own inbound/outbound conceptual split (AWS's "inbound (agent to gateway) / outbound (gateway to tools)" framing is structurally identical to Kelvran's `ARCHITECTURE.md` naming). This is the single most consequential finding in this report for the "has a first real integration [pattern] emerged" trigger — Kelvran does not need its own first integration to learn this shape; three external, production implementations already demonstrate it converging on the same answer.

**Consistent with the RFCs' own stated triggers?** Directly and substantially advances the outbound RFC's "wait for MCP's own spec stabilizing AND a first real integration" trigger — not by Kelvran having its own integration, but by three independent, GA, large-footprint external integrations converging on the same pattern the RFC already sketched in shape. This is evidence worth weighing even though it does not fully satisfy "Kelvran's own first integration" literally.

**2026 best-practice grounding:**
- AWS AgentCore Gateway's OBO flow: "AgentCore Gateway supports OAuth 2.0 on-behalf-of (OBO) token exchange through AgentCore Identity... It supports standard token exchange (RFC 8693) or JWT authorization grant (RFC 7523)," with the original user's identity preserved end-to-end rather than replaced by a generic service credential [aws.amazon.com/blogs/machine-learning — confirmed 3-0]; GA status confirmed via AWS's own Bedrock AgentCore release notes ("Gateway: 3LO Support for MCP Targets is now GA").
- AgentCore Identity's credential vault: "neither AgentCore Gateway nor MCP servers need to manage credentials directly" [same source — confirmed 2-1, high-confidence].
- AgentCore Gateway's inbound/outbound split: "provides comprehensive authentication for both inbound (agent to gateway) and outbound (gateway to tools) connections," independently corroborated by AWS's own console-help docs and two separate engineering blog posts [docs.aws.amazon.com — confirmed 2-1, high-confidence].
- Microsoft Foundry Agent Service: "Agent Service restricts tokens scoped to a known Microsoft audience from being sent to custom or third-party MCP servers... `Cannot pass Microsoft token to untrusted MCP endpoint`... Your custom MCP server must be registered with an audience that you control" [learn.microsoft.com — confirmed 2-1, high-confidence, dated 2026-09-04/09-11].
- Microsoft's OWASP-MCP-Top-10-aligned Azure guidance recommends redundant, defense-in-depth audience (`aud`) validation at both the API gateway layer and inside the MCP server's own code — "Audience validation must occur in both APIM (first layer) and within the MCP server code (second layer)" [microsoft.github.io/mcp-azure-security-guide — confirmed 3-0 and 3-0 for the two related claims], from a repo actively maintained by named Microsoft security engineers as recently as 2026-09-17.
- A real four-gate Lambda interceptor pattern (AWS Quick Suite MCP gateway) shows post-authentication, pre-business-logic authorization as a concrete, shipped layer distinct from token validation itself — "A request that fails a gate is denied with a 403 and doesn't reach the tool or its data" [aws.amazon.com/blogs/machine-learning — confirmed 2-1, high-confidence].
- Cloudflare `workers-oauth-provider` v0.2.3 (PR #120): "Add OAuth 2.0 Token Exchange (RFC 8693) support... Gated behind the `allowTokenExchangeGrant` option (default `false`)" [github.com/cloudflare/workers-oauth-provider — confirmed 3-0, verified against the live changelog and signed commit].

**Concrete next step (not urgent — informs a future RFC, does not trigger building now):** When/if a future implementation RFC for the outbound leg is written, cite AWS AgentCore Identity's and Microsoft Foundry's shipped patterns as the primary precedent to adapt (token exchange + credential vault + audience-scoped registration), superseding the current RFC's reliance on LiteLLM/Portkey alone as comparables.

**Effort:** N/A for this research pass — the actionable output is "cite this precedent in a future RFC," not an implementation step now.

### 4. The OAuth-proxy confused-deputy vulnerability class the outbound RFC cites has already manifested in a real, widely-used MCP framework — the risk is empirically live, not theoretical (High confidence)

**What:** GHSA-rww4-4w9c-7733 (CVE-2026-27124, CWE-441 Confused Deputy, severity High, published 2026-03-31, patched in FastMCP 3.2.0) documents a real vulnerability in FastMCP's `OAuthProxy._handle_idp_callback` function. GitHub's own advisory states the flaw is not a one-off implementation bug tied to a single identity-provider integration, but generalizes structurally: "a review of the source code... shows that the IdP callback handler does not verify whether the browser sending the state and code has previously consented... This pattern causes all OAuth integrations whose IdP allows skipping the consent page to be vulnerable to this attack."

**Why it matters for Kelvran specifically:** The outbound RFC's own Drawbacks section flags "no real MCP client to validate against yet" as an unavoidable limitation of a design-only RFC. This finding is the closest available substitute: a real, dated, first-party-disclosed vulnerability in a popular MCP server framework's own OAuth-proxy implementation, confirming the exact vulnerability class (OAuth-proxy confused deputy) the RFC's Alternatives Considered section worries about is not a hypothetical risk analysts invented — it is a documented, CVE-tracked defect that shipped in production MCP tooling. A future `OutboundCredential` design should treat browser/session-consent binding as a named requirement, not an afterthought, precisely because this generalizes beyond the one provider it was first found in.

**Consistent with the RFCs' own stated triggers?** Strengthens, rather than resolves, the outbound RFC's "wait for a first real integration" reasoning — it is evidence that when an integration is eventually built, this specific failure mode needs an explicit design answer, not evidence that the wait itself is over.

**2026 best-practice grounding:** Verified directly against GitHub's public Advisory API — real, unwithdrawn, CVE-assigned, with a clear generalization statement in the advisory's own text, independently confirmed via a second, separate fetch of the same page [github.com/advisories/GHSA-rww4-4w9c-7733 — confirmed 3-0].

**Concrete next step:** Name this advisory explicitly in any future outbound-credential implementation RFC's own security-considerations section as the concrete precedent for why browser/session-consent binding (not just token-audience scoping) must be a first-class design requirement.

### 5. No dated, primary-source evidence of operator/customer demand for MCP support specifically on a self-hosted LLM gateway — genuinely unresolved, not answered "no" (Unscoped — needs its own research pass)

**What the research was asked to find:** real, dated evidence of actual customer/operator demand for MCP support on a self-hosted LLM gateway like Kelvran, as distinct from demand for MCP support in agent frameworks or IDEs.

**What the research found:** nothing survived adversarial verification on this specific sub-question. Every surviving claim in this report describes *what vendors have built* (spec text, AWS/Microsoft/Cloudflare product architecture, a CVE) — none describes *who is asking for it on a gateway specifically*, or dates such a request. This is an absence of evidence, not evidence of absence, exactly as the same pattern was flagged in the sibling `gateway-2026-09-06.md` report's Finding 6 for provider-side prompt caching.

**Why this matters for Kelvran specifically:** Both RFCs' own Motivation sections and the underlying research (`docs/upgrade-research/mcp-a2a-brokering-tier1-2026-09-20.md`) already state "no recorded demand signal" as of their own dates — this research pass explicitly re-tested that specific question and did not find grounds to overturn it. The "moot" half of the original "not_yet"/"moot" decision — is anyone asking Kelvran for this — stands exactly where it stood before this research, while the "not_yet" half (is the ecosystem/pattern mature enough to design against) has moved meaningfully, per Findings 1-4 above.

**Effort:** N/A — needs its own dedicated research pass (e.g., a targeted search of LLM-gateway-specific community forums, GitHub issues on comparable OSS gateways like LiteLLM/Portkey/Kong AI Gateway asking for MCP support, or direct operator outreach) before any implementation decision should weigh demand as a factor.

## Top 3 takeaways

1. **Don't reopen the RFCs' core security reasoning — it was already right.** The anti-token-passthrough doctrine both RFCs depend on has been stable spec text for over a year across three revisions; no rule change here changes either RFC's conclusions.

2. **Cite AWS AgentCore Identity and Microsoft Foundry's shipped OBO/token-exchange patterns as the new primary precedent** in any future outbound-credential implementation RFC, superseding the current RFC's LiteLLM/Portkey-only comparables — three independent, GA, large-footprint implementations now converge on the same shape the RFC already sketched, which is real (if indirect) evidence the "first real integration" trigger has been substantially, if not literally, satisfied by the wider ecosystem.

3. **Do not treat this research as resolving the demand question.** No evidence surfaced either way on real customer/operator demand for MCP on a self-hosted gateway specifically — this remains the harder, unanswered half of the original "not_yet"/"moot" framing, and revisiting the RFCs' design should not be conflated with a decision to actually build.

## Caveats

- Two findings (Finding 3's AgentCore Identity/inbound-outbound-split sub-claims, Finding 4's Quick Suite four-gate claim, and Finding 3's Microsoft Foundry claim) rest on 2-1 rather than unanimous 3-0 votes — all still independently corroborated by multiple primary sources and rated high-confidence in the underlying verification, but flagged here for transparency.
- 12 of the 25 claims originally extracted were refuted during adversarial verification, several because they overstated the spec's normative force — specifically, claims asserting the spec *mandates* RFC 8707 audience-restriction as a MUST, or mandates per-client consent for proxy servers with static client IDs, did **not** survive (0-3 / 1-2). This matters: the spec's confirmed MUST-level requirement is narrower than "audience validation is mandatory everywhere" — it is specifically "don't accept/forward a token not issued for you." The broader question of whether Kelvran's future `OutboundCredential` design should adopt RFC 8707 resource indicators remains a genuinely open implementation choice, not a spec mandate either RFC needs to treat as settled.
- A near-duplicate framing of the FastMCP CVE (citing a specific CVSS score and a more granular root-cause mechanism) was refuted 1-2 even though the underlying CVE and its generalization statement (Finding 4) were confirmed 3-0 from the same advisory — this document deliberately omits the specific CVSS figure and the finer root-cause claim since those did not independently survive verification.
- Time-sensitivity: the current MCP spec revision (2026-07-28) predates both of Kelvran's RFCs (2026-09-11, 2026-09-20) — so, strictly, nothing in Finding 1 or 2 is "new since the RFCs were written" in the narrowest chronological sense. What is genuinely new relative to the RFCs' own research passes is that neither RFC's own cited research (`docs/upgrade-research/gateway-mcp-a2a-brokering-2026-09-11.md`, `docs/upgrade-research/mcp-a2a-brokering-tier1-2026-09-20.md`) surfaced the Mix-Up Attack / CIMD material or the AWS/Microsoft/Cloudflare production patterns in Findings 2-3 — this report closes that specific gap, not a chronological one.
- AWS's, Microsoft's, and Cloudflare's own product docs are first-party but are still vendor documentation of their own products, not independent third-party audits of those products' security — appropriate weight for "what large vendors have shipped," not proof those implementations are themselves flawless.
- Question 3 (demand evidence) returned zero surviving claims despite being explicitly asked — treat Finding 5 as a real gap in this research, not a quiet "no."

## Open questions

- Is there any real, current demand signal for MCP support specifically on a self-hosted LLM gateway (Finding 5)? This research explicitly asked and found nothing — needs a dedicated, differently-scoped research pass (e.g., mining GitHub issues on comparable OSS gateways, or direct operator outreach) rather than another spec/vendor-doc sweep.
- Given AWS AgentCore Identity and Microsoft Foundry both landed on OBO/token-exchange (RFC 8693/7523) rather than Portkey's simpler injected-per-server-credential shape, should Kelvran's future `OutboundCredential` design default to OBO now that two independent large vendors have converged on it, or is Portkey's simpler shape still preferable for Kelvran's smaller initial scope (a single MCP tool, per the inbound RFC) given OBO's added complexity (a token-exchange endpoint, two simultaneous credentials)?
- Should a future outbound-credential RFC explicitly adopt RFC 9207 `iss`-parameter validation (Finding 2) as a named requirement given it is not spec-mandated but is now SEP-approved, multi-SDK-implemented guidance directly relevant to Kelvran's own multi-downstream-MCP-server topology?
- Does the FastMCP confused-deputy advisory (Finding 4) change the calculus on whether Kelvran should build any outbound broker at all in-house versus adopting an existing, hardened OAuth-proxy library (e.g. a patched FastMCP, or Cloudflare's `workers-oauth-provider`) rather than re-implementing browser-consent binding from scratch?
