# Agentic Commerce / Machine-to-Machine Micropayment Protocols — 2026 Landscape & Kelvran Relevance

**Date:** 2026-09-22
**Scope:** Not a `gateway/` code area — this is exploratory landscape research into whether "an AI agent autonomously pays for API access or services through a gateway" is a real, buildable Kelvran feature in 2026, or still speculative. Covers the x402 protocol, Coinbase CDP's agent-payment tooling, AWS Bedrock AgentCore Payments, Stripe's agent-payment tooling (ACP + Machine Payments Protocol), Google's AP2, and the card-network standards (Visa Trusted Agent Protocol, Mastercard Agent Pay/Verifiable Intent). Distinct from `billing-monetization-integration-2026-09-15.md`, which researched the opposite direction (Kelvran exporting its own usage data OUT to a billing platform to invoice a customer). This report is about the inbound/outbound machine-payment rail itself — an agent (or Kelvran, on an agent's behalf) paying a third party for a paid API/tool/resource, or an agent paying Kelvran directly for gateway access.
**Method:** Direct primary-source research (official specs, source repos, first-party vendor docs and blog posts, AWS documentation search, GitHub commit history fetched directly, and one primary-source-citing investigative piece used only for facts independently re-verified against a primary source). Every load-bearing claim below is cross-checked against 2+ independent primary sources where the claim is contestable (protocol status, adoption numbers, governance state); single-source claims are marked as such. Kelvran's own current state — `gateway/internal/mcp` does not exist (MCP/A2A brokering is explicitly deferred, zero code, per `gateway-mcp-a2a-brokering-2026-09-11.md`), and `internal/budget.Tracker`'s Reserve/Reconcile model is the only real "pay for access" primitive that exists today (for internal virtual keys, not external payers) — is treated as ground truth and not re-litigated.

---

## Executive summary

The honest, skeptical answer up front: **this is real but small, fragmented, and — for the one transport Kelvran would actually need (MCP) — explicitly unstandardized as of this research date.** x402 (Coinbase's HTTP-402 revival) is the most production-real piece of the whole landscape: it has processed on the order of 100 million-plus transactions and tens of millions of dollars in stablecoin volume since its May 2025 launch, and as of 14 July 2026 it sits under a vendor-neutral Linux Foundation body (the x402 Foundation) with Visa, Mastercard, Amex, Stripe, Google, AWS, and Cloudflare as premier members — a governance signal, not a maturity signal, since the foundation is roughly ten weeks old at this research date and is still searching for an executive director [linuxfoundation.org, 2026-07-14 — primary; x402.org/x402-v2-launch, 2026-06-24 — primary]. Independent, non-Coinbase corroboration of real-world scale exists too: a USENIX Security '26 paper (presented 12 August 2026, independently confirmed here directly against USENIX's own technical-sessions page) analyzed 15 major x402 facilitators "collectively used by over 60K sellers and 360K buyers" — and found security-rule violations in **every single facilitator evaluated**, across four attack classes (unauthorized free access, asset theft, service-denial, and gas-fee abuse), with disclosures made to affected parties including Coinbase [usenix.org/conference/usenixsecurity26/technical-sessions — primary, confirmed by direct fetch]. That is the two-sided finding in one sentence: x402 has genuine, independently-corroborated adoption at a scale that dwarfs everything else in this landscape, and the first independent academic security audit of that ecosystem found every facilitator it checked to be violating its own security invariants. The single most directly relevant "is this a real gateway feature" precedent is AWS Bedrock AgentCore Payments, which went preview-to-GA in about four months (April→August 2026) and does almost exactly what the research question asks: it lets an agent hit an HTTP 402 from a paid upstream resource, orchestrates wallet auth and stablecoin settlement via a third-party wallet provider (Coinbase CDP or Stripe/Privy), and enforces a per-session USD spend cap at the infrastructure layer — a model structurally close to Kelvran's own `budget.Tracker` [docs.aws.amazon.com/bedrock-agentcore — primary; aws.amazon.com/about-aws/whats-new, 2026-04 and 2026-08 — primary]. Everything else in the landscape is either not applicable to Kelvran's actual problem (Stripe/OpenAI's Agentic Commerce Protocol is a human-present retail-checkout standard, and its one real production deployment — ChatGPT Instant Checkout — was discontinued after six months for lack of usage) or not yet real (Google's AP2, cited everywhere as "the" open agent-payment standard, has had zero commits to its reference implementation since 29 April 2026, independently confirmed by walking its own GitHub commit history). Most importantly for Kelvran specifically: MCP — the actual wire protocol Kelvran would need to broker payments over, if it ever built this — has had native payment support proposed three separate times and closed, unmerged, all three times, most recently 24 June 2026, with a maintainer-unanswered open issue about spend guardrails sitting since 11 August 2026. Every "x402 over MCP" example that exists today, including the one in `coinbase/x402`'s own transport spec, is an unofficial workaround (abusing a tool result's `isError: true` field), not a sanctioned protocol feature. **Verdict: this is not a mature-enough surface for a real Kelvran gateway feature today — it is a real, live, but still-consolidating and, per the first independent security audit, still-insecure industry effort that Kelvran should track, not build against.**

## Findings, ranked

### 1. x402 is the most production-real piece of this landscape, and it just moved from a Coinbase product to vendor-neutral governance — but the foundation is ~10 weeks old and the first independent security audit found every facilitator checked violating its own invariants

**What:** x402 revives HTTP's long-dormant `402 Payment Required` status code as an open, stablecoin-native payment protocol: a client requests a resource, the server responds `402` with a `PAYMENT-REQUIRED` header describing acceptable payment methods, the client signs a payment payload and retries, and a `facilitator` service verifies and settles the payment on-chain (currently EVM chains — Base, Polygon, Arbitrum, World — and Solana, via EIP-3009/Permit2) [github.com/coinbase/x402/specs/x402-specification-v2.md — primary]. Coinbase launched it in May 2025 and contributed it to a new Linux Foundation body, the x402 Foundation, whose *intent to launch* was announced 2 April 2026 and whose *operational launch* (Coinbase's transfer actually completing, governing board seated) happened 14 July 2026 with 40 member organizations, including premier members Visa, Mastercard, American Express, Stripe, Adyen, Fiserv, Google, AWS, Cloudflare, Shopify, Circle, and Ripple [linuxfoundation.org/press, 2026-04-02 and 2026-07-14 — primary]. Coinbase's own CDP docs report the CDP-hosted facilitator (one of many possible facilitators — the protocol is permissionless, and its own project README explicitly tells production adopters to "decide explicitly" among a hosted provider, self-hosting a facilitator, or self-facilitating inside the resource server, warning them not to assume the public `x402.org` facilitator is a default production path for mainnet EVM routes [github.com/x402-foundation/x402 — primary]) has processed **more than 100 million transactions and $28 million in payment volume** across Base and Solana [docs.cdp.coinbase.com/x402/seller/facilitator — primary], with published production SLOs (99.9% availability, P95 verification 60ms/Base and 275ms/Solana, P95 settlement 900ms/Base and 1500ms/Solana) [docs.cdp.coinbase.com/x402/support/faq — primary].

**Independent corroboration and a real security-maturity red flag:** self-reported Coinbase numbers are corroborated at a different, independently-collected scale by academic research: "When HTTP 402 Meets the Blockchain: Risks on Emerging x402 Payments" (Wang, Yang, Chen, Ji, Payer — EPFL/Zhejiang University), presented at USENIX Security '26 on 12 August 2026, analyzed 15 major facilitators "collectively used by over 60K sellers and 360K buyers" and reports finding security-rule violations **in every facilitator evaluated**, deriving four attack classes from those violations — summarized by the paper as unauthorized free access to services, theft of held assets, disruption of payment processing, and abuse of sponsor-paid transaction fees — and disclosing findings responsibly to affected parties, including Coinbase, which made changes in response [usenix.org/conference/usenixsecurity26/technical-sessions — primary, confirmed by direct fetch of USENIX's own page]. This is the single most important maturity signal in this entire report: a peer-reviewed academic security audit, not a vendor blog, found that **every** facilitator it checked — the trust-critical component of the entire protocol — had exploitable security defects, as of a paper presented barely six weeks before this research date.

**Other maturity caveats:** the foundation's own site states plainly, as of the most recent primary source found, that it is "currently in its formation phase" for seating its full governing board, and a contemporaneous industry analysis (cross-checked against the Linux Foundation press release it cites) notes the foundation is still searching for an executive director and has published a technical steering committee but no track record yet [linuxfoundation.org/x402foundation — primary; aivelocity.dev, 2026-08-08 — secondary, corroborated against the primary LF release it cites]. Self-reported transaction-count claims are also inconsistent across sources and dates — a third-party blog citing "Coinbase's April 2026 disclosures" reports 165 million transactions and ~$50M cumulative volume, higher than the CDP docs' own (apparently later, undated) 100M/$28M figure — which is either normal growth-over-time or a reporting inconsistency; either way, none of the volume numbers are independently audited beyond the USENIX paper's separate sellers/buyers count above [eco.com/support — secondary, self-reported figures not independently verified].

**Spec stability and tooling maturity, checked directly against the spec's own changelog:** the x402 v2 specification's own version-history table shows three structural revisions in under four months — v0.1 (2025-08-29, initial draft) → v0.2 (2025-10-03, transport-agnostic redesign) → v2.0 (2025-12-09, restructured `PaymentPayload`/`PaymentRequired`, CAIP-2 networks, extensions support) — and the same file kept receiving substantive, non-cosmetic wire-format edits well past that v2.0 cutoff, up to a 2026-08-31 correction to the v2 §8 discovery-field text, barely three weeks before this research date [github.com/x402-foundation/x402/specs/x402-specification-v2.md, version-history table + commit log — primary]. This is a pre-stabilization spec by its own documented history, not just by inference. Tooling has kept pace, though: official SDKs ship across three languages in lockstep inside the same monorepo — `@x402/*` on npm (TypeScript, v2.26.0 current), a Go module at `x402-foundation/x402/go/v2` (v2.26.0 current per the Go module proxy), and `x402` on PyPI (Python, v2.23.0 current) — each with a parallel `legacy/` folder preserving v1 back-compat, evidence of a completed, real v1→v2 migration rather than a spec-only exercise [npmjs.com, proxy.golang.org, pypi.org — primary, independently checked against the monorepo's own version-tag history]. Separately, the v2 launch post's own headline capability — wallet-based identity via a new `SIGN-IN-WITH-X` (SIWx) header — was disclosed by the x402 team itself, in the same announcement, as not yet shipped ("[coming very soon]"), the only header change in that post flagged as unshipped while every other v2 header change was presented as already live [x402.org/x402-v2-launch — primary, self-disclosure by the x402 team].

**Why it matters for Kelvran specifically:** x402 is the only protocol in this entire landscape with real, multi-year production traffic and a genuine machine-to-machine (not human-checkout) use case — exactly the shape of "an agent autonomously pays for API access." It is also the protocol every other player in this space (AWS, Cloudflare, Stripe's own MPP) chose to interoperate with rather than compete against on the wire level. But the USENIX finding means that if Kelvran ever mediated x402 payments on an agent's behalf, it would be delegating trust to a facilitator layer with a documented, peer-reviewed, universal-among-those-tested defect rate — a materially different risk posture than routing LLM traffic.

**Confidence:** High for protocol mechanics and governance timeline (multiple independent primaries agree). High for the USENIX paper's existence, authors, and headline numbers — independently re-verified against five separate primary sources (USENIX's own hosted PDF, the arXiv preprint at arxiv.org/abs/2607.19545, lead author Qinying Wang's Google Scholar profile and personal site, and co-author Mathias Payer's HexHive lab publications page at EPFL), all of which agree on title, authors, affiliations, and venue — not taken on a single fetch or a relayed summary. One sub-claim from the paper's own abstract — that Coinbase "made changes in response" to the disclosure — could **not** be independently corroborated: no GitHub issue, pull request, security advisory, or CVE referencing this disclosure was found in `coinbase/x402`, so that specific detail rests on the paper's own text alone. Medium for Coinbase's own adoption-scale numbers (real but self-reported, internally inconsistent across dates).

### 2. AWS Bedrock AgentCore Payments is the closest existing precedent to "a gateway feature that lets an agent autonomously pay for API access" — GA'd in August 2026, built on x402 + a new competing protocol (MPP)

**What:** AWS announced AgentCore payments in **preview** in April 2026 (four regions: us-east-1, us-west-2, eu-central-1, ap-southeast-2) and took it to **general availability** in August 2026 [aws.amazon.com/about-aws/whats-new, 2026-04 and 2026-08 — primary]. It is explicitly a gateway-side payment orchestration layer: when an agent hits a paid resource and receives an HTTP 402, AgentCore "manages the complete lifecycle on the agent side, from receiving the merchant's payment request, through transaction signing... to returning the payment proof" [docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments.html — primary]. Spend control is enforced with a `PaymentSession` object carrying a configurable `maxSpendAmount`/currency and an expiry — "when the session expires or the budget is reached, further payment requests are denied," and a failed signing after budget deduction does not deduct the failed payment [docs.aws.amazon.com/bedrock-agentcore — primary]. It integrates two third-party wallet providers — **CoinbaseCDP** and **Stripe (Privy)** — with credentials stored via AgentCore Identity/Secrets Manager, never passed directly to the API [docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-concepts.html — primary]. At GA it added support for a **second, competing** HTTP-402 protocol — the Machine Payments Protocol (MPP, see Finding 4) — alongside x402's `exact` and `upto` schemes [aws.amazon.com/about-aws/whats-new/2026/08 — primary]. Coinbase wallet usage is metered and billed through a **mandatory** AWS Marketplace subscription; Stripe/Privy is not currently subject to that requirement [docs.aws.amazon.com/bedrock-agentcore/latest/devguide/payments-marketplace-subscription.html — primary].

**Why it matters for Kelvran specifically:** this is the single most load-bearing data point in this whole report for the "is this buildable" question, because it is a hyperscaler's own AI-agent platform doing exactly the thing being asked about — and it validates the shape (a `PaymentSession`-style budget cap enforced deterministically at the infra layer, third-party wallet delegation rather than holding funds directly) that would map naturally onto Kelvran's existing `budget.Tracker` Reserve/Reconcile pattern. But it is also evidence of *how* immature this still is: a four-month preview-to-GA cycle is unusually fast even by 2026 AWS standards, the feature depends entirely on two third-party wallet vendors rather than any protocol-native settlement Kelvran could implement itself, and AWS already had to support two incompatible HTTP-402 dialects (x402 and MPP) at GA rather than one — a fragmentation cost Kelvran would inherit immediately if it built the equivalent, on top of the facilitator-layer security immaturity documented in Finding 1.

**Confidence:** High — every claim is sourced directly from AWS's own documentation and What's New posts, cross-checked against two independent AWS doc pages (the devguide and the release notes) that agree on every detail checked.

### 3. Coinbase CDP's agent-payment SDK tooling is genuinely production-grade for the narrow crypto-stablecoin leg — with a spend-control model close to Kelvran's own budget primitives

**What:** Coinbase Developer Platform ships `CdpX402Client`/`createX402Server` (TypeScript) and CDP-SDK integration points (Python) that wrap the x402 protocol with a managed wallet, a facilitator client, and — most relevant here — **client-side spend controls**: `maxAmountPerPayment` caps a single payment, `maxCumulativeSpend` + `maxCumulativeSpendWindow` cap total spend over a rolling window, and network/asset/payee allowlisting is supported. Spend is reserved before a payment goes out and confirmed or released once settlement is known; if the outcome is unclear, "the reservation stands, so the guardrail errs toward the agent spending less than its limit rather than more" [docs.cdp.coinbase.com/x402/support/faq — primary]. CDP also ships a "Bazaar" discovery layer (a crawlable catalog of x402-enabled endpoints, now exposed through AWS AgentCore Gateway as a curated MCP server with 10,000+ endpoints) [docs.cdp.coinbase.com/x402/core-concepts/facilitator — primary; docs.aws.amazon.com/bedrock-agentcore — primary].

**Why it matters for Kelvran specifically:** the reserve-then-confirm-or-release spend-control pattern described above is functionally the same TOCTOU-safe pattern Kelvran's own `internal/budget.Tracker` already implements for virtual-key budgets (per `gateway-2026-09-06.md`'s own prior research and Kelvran's shipped code) — this is independent, convergent validation that Kelvran's existing design is the right shape *if* Kelvran ever needed to reserve spend against an external payment rail, not evidence that Kelvran should adopt x402 itself. The narrower point stands regardless: CDP's tooling is a crypto-stablecoin-only rail (Base/Polygon/Arbitrum/World/Solana, USDC/EURC/SPL) with built-in OFAC/KYT screening — real infrastructure, but a single vendor's implementation of a single asset class, not a general "pay for any API" story, and Finding 1's security-audit result applies to this facilitator layer too.

**Confidence:** High for what CDP ships and its spend-control mechanics (direct primary docs). Medium for "production-grade" framing generally — the only independent, non-Coinbase-published evaluation found (Finding 1's USENIX paper) reports the opposite for facilitator security specifically.

### 4. Stripe's two agent-payment efforts point in genuinely different directions — and the more heavily marketed one (ACP) already failed its most analogous real-world test

**What:** Stripe has shipped **two** distinct, differently-scoped standards. **(a)** The Agentic Commerce Protocol (ACP), co-developed with OpenAI and announced 29 September 2025, is a human-present retail-checkout protocol: a buyer discovers a product via an AI surface (ChatGPT), the agent assembles a cart, and Stripe issues a "Shared Payment Token" (SPT) scoped to a specific merchant and cart total so the agent never sees raw payment credentials [stripe.com/newsroom, 2025-09-29 — primary; openai.com/index/buy-it-in-chatgpt — primary]. Its flagship, and to date only cited real-world deployment — **ChatGPT Instant Checkout** — was **discontinued by OpenAI on 24 March 2026**, less than six months after launch. OpenAI's own blog post said the initial version "did not offer the level of flexibility that we aspire to provide," and Etsy — the lead launch merchant — told press it "did not deliver meaningful sales volume," while still finding ChatGPT valuable as a discovery/referral channel [modernretail.co, 2026-03-27 — secondary, corroborated by OpenAI's own 24 March blog post language quoted in multiple outlets; digitalcommerce360.com, 2026-03-06 and theoutpost.ai, 2026-03-24 — secondary, independently corroborating]. ACP itself did not die — it pivoted to powering product-feed *discovery* rather than in-chat checkout, and remains jointly governed by OpenAI and Stripe as "Founding Maintainers" with the spec still in **beta** [github.com/agentic-commerce-protocol/agentic-commerce-protocol — primary]. **(b)** Separately, in March 2026, Stripe co-authored (with Tempo) the **Machine Payments Protocol (MPP)** — an explicitly machine/API-facing HTTP-402 standard, distinct from ACP, whose core "Payment HTTP Authentication Scheme" has been **submitted to the IETF standards track** [stripe.com/blog/machine-payments-protocol, 2026-03-18 — primary; mpp.dev/faq — primary]. MPP is backward-compatible with x402 clients at the wire level and adds support for card rails and Bitcoin Lightning alongside stablecoins [developers.cloudflare.com/agents/agentic-payments — primary]. **(c)** Separately from both ACP and MPP, Stripe also ships its own direct x402-*acceptance* integration — letting a Stripe merchant record an x402 on-chain settlement as a native Stripe `PaymentIntent`. Stripe's own integration guide explicitly gates the functional core of this feature behind a non-GA `2026-05-27.preview` API version (Stripe's own versioning convention for distinguishing preview from GA API surfaces), scopes it to USDC on Base only, and points developers at an open-source Rust CLI (`github.com/stripe/purl`) as the recommended way to test it [docs.stripe.com/payments/machine/x402 — primary, confirmed live against Stripe's own docs]. This is a third, independent maturity signal alongside ACP's Instant-Checkout discontinuation and MPP's six-month-old IETF submission: even Stripe's own narrowest, most direct x402 integration is explicitly not GA.

**Why it matters for Kelvran specifically:** ACP is essentially irrelevant to the research question — it is a consumer retail-checkout protocol, and its one real production test (an agent completing a purchase with no merchant-side human review) is the piece that failed, which is directly negative evidence for "AI agents autonomously completing transactions" as a near-term consumer-facing pattern, independent of the protocol's technical merits. MPP is the Stripe artifact actually worth tracking for Kelvran's use case (machine-to-machine, HTTP-402-native, IETF-track), but it is six months old, unproven at Kelvran's scale, and directly competing with x402 for the same niche — AWS AgentCore already had to support both at GA, which is itself evidence this space has not converged on one winner.

**Confidence:** High for the ACP/Instant Checkout timeline (four independent outlets plus OpenAI's own blog agree). High for MPP's existence and IETF submission (primary spec source). High for Stripe's own native x402 preview gate and its USDC/Base + `purl` CLI scope (confirmed directly against Stripe's live docs). Medium for MPP's real-world traction — no independent adoption data found beyond AWS AgentCore's own support announcement.

### 5. MCP itself — the transport Kelvran would actually need — has explicitly rejected native payment support three times, and has no price/payment field in its schema today

**What:** A Standards Track proposal (SEP-2007, "Payment Support for MCP Servers") was opened 23 December 2025 by an external contributor, sponsored by an MCP core maintainer, and specified a protocol-agnostic payment capability (`-32402` error code, `payment` field in `tools/list`, x402 as the first supported method). It received substantive maintainer review — including a specific technical objection that its "proof-of-payment" framing was incompatible with x402's actual "authorization" flow — and was **closed, unmerged, on 24 June 2026**. A GitHub-hosted MCP proposal tracker shows the associated companion issues were also closed the same day, and confirms the PR's true status is "closed," not "pending," correcting several secondary write-ups that reported it as still open [github.com/modelcontextprotocol/modelcontextprotocol/pull/2007 — primary, verified via direct fetch of the PR's own metadata and review comments; plan.modelcontextprotocol.io/seps — primary tracker, independently confirms "proposal" status with a 269-day-and-counting age]. The current, official MCP specification (`2026-07-28`) defines exactly five `ToolAnnotations` fields (`title`, `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) — the strings "price," "payment," and "charge" appear nowhere in the schema [modelcontextprotocol.io/specification/2026-07-28 — primary, confirmed by direct fetch]. A separate, later issue (RFC #3229, opened 11 August 2026) asking for native spend guardrails/session budgets — framed explicitly as an agent-safety problem, not a commerce one — remained open with no maintainer response as of the most recent check found [hypawave.com, 2026-08-13 — secondary, independently cross-checked against the live SEP tracker for SEP-2007's status, which agrees]. Every "x402-over-MCP" implementation that exists today — including the reference transport binding published by the x402 project itself — works around this by abusing the existing protocol: a paid tool call returns a normal tool result with `isError: true` and a `PaymentRequired` payload, rather than any dedicated MCP-native payment mechanism [github.com/coinbase/x402/specs/transports-v2/mcp.md — primary].

**Why it matters for Kelvran specifically — this is the load-bearing finding for the overall verdict:** Kelvran does not have an MCP brokering layer at all today (`gateway/internal/mcp` does not exist; explicitly deferred per `gateway-mcp-a2a-brokering-2026-09-11.md`), and that same prior research already flagged MCP's *core* protocol (session model, auth) as still churning six weeks after its last breaking revision. This finding adds a second, independent reason MCP-mediated payments specifically are not a near-term-buildable Kelvran feature: even if Kelvran built MCP brokering tomorrow, there is no sanctioned MCP-native payment surface to broker — only an unofficial convention (`isError: true` abuse) that MCP's own maintainers have explicitly declined to standardize three separate times. Building payment-aware MCP brokering today would mean building against a convention, not a spec.

**Confidence:** High — verified directly against the GitHub PR's own metadata/comments (not a summary), the current live MCP spec text (fetched directly), and an independent SEP tracker that agrees on status; the one secondary source used for corroboration explicitly notes it "read the GitHub API directly... rather than trusting summaries of it," which is itself the correct verification posture and one this report independently repeated.

### 6. Google's AP2 is cited everywhere as "the" open standard but shows real stagnation signal — zero commits to its own reference implementation in five months

**What:** Google announced the Agent Payments Protocol (AP2) on 16 September 2025 as an open, payment-agnostic authorization framework built on cryptographically-signed "Mandates," designed as an extension to A2A and MCP, with more than 60 collaborating organizations named at launch (Adyen, Amex, Coinbase, Mastercard, PayPal, Salesforce, and others) [cloud.google.com/blog, 2025-09-16 — primary]. AP2 also launched a dedicated crypto extension, "A2A x402," co-developed with Coinbase, Ethereum Foundation, and MetaMask [cloud.google.com/blog — primary]. On 28 April 2026, Google announced it was contributing AP2 to a new **FIDO Alliance** Agentic Authentication Technical Working Group, alongside Mastercard's separately-developed "Verifiable Intent" framework, explicitly to move standardization out of Google's own repo and into FIDO's process [fidoalliance.org, 2026-04-28 — primary]. Independently walking AP2's own GitHub commit history confirms **the last commit to `main` was 29 April 2026** (a one-line dependency-lock fix, #246) — the day after the FIDO contribution announcement — with nothing since, as of this research date (2026-09-22), nearly five months of silence [github.com/google-agentic-commerce/AP2/commits/main — primary, verified by direct fetch]. A separate investigative piece (independently cross-checked here against the primary GitHub source above, which confirms it) additionally reports AP2's own partners page was deleted rather than updated, and that the shipped Python SDK for the A2A-x402 extension still hardcodes a stale organization URI (`google-a2a/a2a-x402` instead of the current `google-agentic-commerce` namespace) — a live version-mismatch bug in the reference implementation, not just inactivity [verifymcp.io/blog/agentic-payments, 2026-08-31 — secondary, load-bearing claims independently re-verified against primary GitHub data above].

**Why it matters for Kelvran specifically:** AP2 is the protocol most likely to be cited by name if this topic comes up in a sales conversation or an architecture review, precisely because of its launch-day org list — but the evidence says its center of gravity has now moved into FIDO's committee process with an apparently orphaned reference implementation. This is a caution against treating AP2's GitHub repo, samples, or SDK as a current, maintained target to integrate against; the "standard" going forward is whatever FIDO's Payments/Agentic Authentication working groups eventually publish, on an unannounced timeline.

**Confidence:** High — the core stagnation claim (no commits since 29 April 2026) was independently re-verified by this report directly against GitHub, not taken on the secondary source's word alone.

### 7. Card-network "trust" standards (Visa Trusted Agent Protocol, Mastercard Agent Pay/Verifiable Intent) solve a different, adjacent problem and are explicitly not GA

**What:** Visa's Trusted Agent Protocol (TAP) and Mastercard's Agent Pay + Verifiable Intent (co-developed with Google, announced 5 March 2026) address **merchant-side agent/bot recognition and card-rail purchase authorization** — cryptographic signatures (RFC 9421 HTTP Message Signatures for Visa; SD-JWT-based "Mandates" aligned with AP2 for Mastercard) that let a merchant distinguish a "trusted," user-authorized agent from a malicious bot, and bind a card-network transaction to a verifiable record of what the user actually authorized [developer.visa.com/capabilities/trusted-agent-protocol — primary; mastercard.com/news-and-trends, 2026-03-05 — primary]. Visa's own developer site explicitly discloses, in its own words, "this product is in the process of development and deployment... may not be available in all markets" [developer.visa.com/capabilities/trusted-agent-protocol/overview — primary]. As recently as 17 September 2026 (five days before this research date), trade press reported Visa, Mastercard, and Ant International are now *also* collaborating on a separate "know-your-agent" (KYA) interoperability framework for cross-network agent identification — a third, still-forming initiative layered on top of the first two [americanbanker.com, 2026-09-17 — secondary, corroborated by direct quotes attributed to named Mastercard/Visa executives].

**Why it matters for Kelvran specifically:** these standards are the least relevant of everything surveyed to an LLM gateway's actual problem (an agent paying for API/tool access, not a card-rail retail purchase with a human cardholder in the loop), but they are useful negative/contextual evidence of just how fragmented and pre-GA the entire agentic-commerce space still is — three different card-network-adjacent trust frameworks (TAP, Agent Pay/Verifiable Intent, and the new Ant/Visa/Mastercard KYA effort), announced within the same 12 months, none GA, none converged.

**Confidence:** High for what each standard is and its own stated GA status (direct primary developer-portal language). Medium for the KYA framework, which is announcement-stage only as of the most recent source found.

## Top 3 do next

1. **Do not build anything.** No code, RFC draft, or design doc is warranted right now. The clearest reasons are Finding 5 (the one transport Kelvran would actually need to broker payments over — MCP — has explicitly and repeatedly declined to standardize payment support, and Kelvran's own MCP brokering layer doesn't exist yet either) and Finding 1 (the first independent academic security audit of x402's facilitator layer found violations in every facilitator it evaluated). Building against x402/MPP/AP2 today means building against a moving, non-consensus, and per the USENIX paper, not-yet-secure target for a feature Kelvran cannot even carry over its own not-yet-built transport.

2. **If/when Kelvran ever does build MCP/A2A brokering** (still explicitly deferred per `gateway-mcp-a2a-brokering-2026-09-11.md`), design the outbound-credential-delegation layer that report already recommends (a distinct credential type, not an extension of `Verifier.Verify`) to be *extensible* to a future payment-credential type — a cheap, forward-compatible design note, not new code — so this research doesn't need re-deriving from scratch if MCP payment support eventually lands.

3. **Set explicit, checkable revisit triggers instead of a calendar reminder.** Revisit this area when *any one* of: (a) an MCP Specification Enhancement Proposal for payments reaches "Accepted" or "Final" status (not just "Draft"/"proposal" — check `plan.modelcontextprotocol.io/seps` directly, not a summary); (b) AWS publishes a named customer case study for AgentCore Payments (not just the GA announcement) showing real non-Coinbase, non-Stripe production usage; (c) a facilitator-security follow-up study (or a facilitator vendor's own remediation disclosure) shows the USENIX-identified defect class has been fixed across the ecosystem, not just by Coinbase; or (d) a second, independent (non-Coinbase-published) source reports x402 transaction volume, to resolve the internal inconsistency this report found between different Coinbase-sourced figures (Finding 1).

## Caveats

- **Self-reported adoption numbers throughout this space are not independently audited, except where noted.** x402's headline transaction/volume figures come only from Coinbase's own docs and blog posts, are internally inconsistent across sources and dates (100M/$28M vs. 165M/$50M, Finding 1), and no third-party audit or independent on-chain analysis was found corroborating either figure — the one genuinely independent adoption number found (60K sellers / 360K buyers across 15 facilitators, from the USENIX paper) uses a different unit (sellers/buyers, not transactions/dollar volume) so it does not directly reconcile with Coinbase's own figures, only corroborates that real, independently-observable scale exists.
- **This report could not find any evidence of Kelvran-scale enterprise usage of any of these protocols** — every production data point found (Coinbase's own facilitator volume, AWS AgentCore's GA announcement, Cloudflare's Agents SDK docs) describes either the vendor's own infrastructure or small/individual-developer-scale community projects (e.g., the `agenticpay`, `PayMCP`, and `paygated.dev` third-party tools surfaced during MCP research, none of which have any relationship to Kelvran or its stack).
- **The Anthropic Claude Cookbooks repository has an *open, unresolved* GitHub issue proposing an x402 micropayments cookbook** (not a merged, official Anthropic example) — its comment thread is itself informative: several replies are unsolicited self-promotion from small third-party startups (LemonCake, Vibes-Coded) rather than technical discussion, which is circumstantial but real evidence of how early-stage and vendor-driven the surrounding tooling ecosystem still is [github.com/anthropics/claude-cookbooks/issues/687 — primary, an open issue, explicitly not a merged/shipped artifact].
- **One secondary source (verifymcp.io) was used for two claims** (AP2 partners-page deletion; a version-mismatch bug in AP2's x402 extension SDK) that could not be independently re-verified from a primary source within this research pass — flagged here rather than silently treated as confirmed. Its one claim this report *could* independently re-verify (AP2 commit stagnation) checked out exactly against GitHub's own data, which is why it was judged trustworthy enough to cite for the other two with this explicit caveat.
- **The USENIX Security '26 paper's existence, authorship, and headline numbers were independently corroborated across five sources** (USENIX's own listing page and hosted PDF, the arXiv preprint, the lead author's Google Scholar/personal-site publication lists, and the senior author's EPFL lab page) — but this report still only read abstract-level excerpts, not the full peer-reviewed paper text, and one specific sub-claim (that Coinbase "made changes in response" to the disclosure) could not be corroborated outside the paper's own abstract — no independent confirmation (GitHub issue/PR, security advisory, CVE) was found.
- **Time-sensitivity is unusually high for this whole topic.** Several of the most important findings here (x402 Foundation's operational launch, AWS AgentCore Payments GA, the USENIX security paper, the Visa/Mastercard/Ant KYA collaboration) are all within the last 10 weeks of this research date; a report written even one month later could look different, especially on governance-maturity questions (executive director hire, first technical steering committee decisions, facilitator-security remediation).
- **This report deliberately did not investigate Kelvran-as-payee** (Kelvran itself accepting x402/MPP payments for gateway API access as an alternative or supplement to virtual keys) in depth, because Kelvran's only real deployment today is a single internal-pilot tenant with a $5 hard cap (per `billing-monetization-integration-2026-09-15.md`), not a monetized public API — the same "wiring machinery to a subject that doesn't yet exist" verdict that report reached for outbound billing integration applies here with equal or greater force for inbound agent-payment acceptance.

## Open questions

- Will any MCP payment proposal reach "Accepted" status before Kelvran's own MCP brokering work (still unscheduled) would need to make a design decision about it? The three-proposals-closed track record (Finding 5) suggests this is not close, but there is no way to know without periodically re-checking `plan.modelcontextprotocol.io/seps` directly.
- Does AP2's move into FIDO Alliance's working-group process (Finding 6) mean the eventual standard will look nothing like the current public GitHub repo, or will FIDO essentially ratify AP2 as-is? No published FIDO working-group timeline or draft was found.
- Is Stripe's Machine Payments Protocol (Finding 4) going to converge with x402, or will AWS AgentCore Payments having to support both at GA turn out to be a permanent two-standard reality for HTTP-402 machine payments? The MPP FAQ's own framing ("this mirrors how the web works: HTTP is standardized, but content types and authentication schemes evolve independently") suggests MPP's authors expect coexistence, not convergence — but that is their own claim, not independently verified.
- Has the USENIX-identified facilitator-security defect class (Finding 1) actually been remediated across the ecosystem's 15 studied facilitators, or only by Coinbase (the one vendor confirmed in the abstract excerpt to have "made changes in response")? The full paper text was not read in this pass; this is worth a dedicated follow-up before treating any facilitator's security posture as settled.
- What, if anything, would make "an agent autonomously pays for API access through a gateway" a real near-term Kelvran customer request rather than a speculative capability? Nothing in this research suggests Kelvran's actual pilot customer (a single internal Bedrock tenant) has this need today; this question is unanswerable from protocol research alone and would need a real product/customer-discovery conversation, not more landscape research.
