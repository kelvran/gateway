# Redis-Backed Distributed Semaphore Patterns for a Multi-Instance ConcurrencyLimiter — Deep Research (2026-09-09)

## Question

What's the right Redis-backed distributed-semaphore pattern for extending Kelvran's existing single-instance, in-memory per-virtual-key concurrency limiter to a multi-instance deployment — with specific attention to the leaked-slot/orphan-permit problem that a distributed version introduces but a single-instance version doesn't have?

## Context (Kelvran's own real, current state)

`gateway/internal/ratelimit/concurrency.go`'s `ConcurrencyLimiter` bounds how many requests from one virtual key may be simultaneously in-flight (`Acquire(keyID) bool` / `Release(keyID)`, `MaxInFlight <= 0` = unlimited). Its own doc comment already names two facts this research had to take as given, not rediscover:

- It is deliberately in-memory/single-instance only today ("a multi-instance deployment enforces this cap independently per instance, not globally, named explicitly as future work"), following the exact same "single-instance stepping stone" framing `docs/rfcs/2026-09-05-gateway-cache-stampede-protection.md` uses for cache-stampede protection.
- "ConcurrencyLimiter itself has no timeout or leak-detection mechanism; an Acquire without a matching Release permanently consumes one slot" — bounded today only by process restart. In Redis, a leaked slot would persist indefinitely without an explicit TTL/expiry mechanism.

Kelvran already has a working, in-repo precedent for exactly this "single-instance feature gets a second, Redis-backed, interface-compatible implementation" pattern: `gateway/internal/ratelimit/redislimiter/redislimiter.go` runs the token-bucket rate limiter's algorithm atomically via a single Lua script (EVALSHA/EVAL), with a defensive `EXPIRE` on every call (including rejected ones) so an idle key's state auto-expires from Redis, and a Go-supplied clock passed as `ARGV` (never Lua's own `os.time()`) for determinism. That package's own doc comment cites `docs/rfcs/2026-09-03-distributed-rate-limiting.md`'s fail-open policy.

The concurrency limiter is a different problem shape than the rate limiter, though: rate limiting is an atomic increment-and-check with no notion of "holding" anything; a concurrency slot is acquired once and held for the full duration of one gateway request — and `gateway/internal/gateway/dataplane/dataplane.go`'s own streaming path (`idleTimeout`/`idleTimeoutReader`, ~line 1954) shows that a Kelvran request has **no fixed overall duration cap today** — only a per-idle-window timeout that resets on every streamed chunk, by deliberate design, specifically so a slow-but-actively-streaming response isn't killed. Any distributed-semaphore design for Kelvran has to work correctly for a hold that can legitimately last from milliseconds to (in principle) minutes, with no a priori upper bound.

## Summary

Two materially different Redis patterns exist for "many concurrent holders under a cap," and they solve the leaked-permit problem in opposite ways. The older, widely-cited **ZSET+Lua counting-semaphore recipe** (Josiah Carlson, *Redis in Action*) stores each holder as a sorted-set member scored by *acquisition* timestamp, uses no native Redis TTL at all, and only reaps a leaked/crashed holder lazily — as a side effect of some *other* client's next `acquire` call pruning stale scores — so a leak on an idle key can persist indefinitely and correctness leans on cross-client clock agreement. The newer, production-grade pattern used by Redisson's `RPermitExpirableSemaphore`, `goadesign/pulse`'s semaphore package, and (for the closely related single-holder lock case) `bsm/redislock` instead gives each holder an individually-tracked **lease with a native TTL**, renewed by a periodic **heartbeat** at roughly TTL/3 (a convention `bsm/redislock` documents explicitly and `goadesign/pulse` enforces in code as a hard invariant), so a live holder never gets evicted and a dead one expires automatically without needing anyone else to trigger cleanup. For Kelvran's "hold across a whole request, no fixed duration cap" shape, the lease+heartbeat family is the right fit; the recommendation below is to implement it using the same architectural idiom `redislimiter.go` already established (a single atomic Lua script package, Go-supplied clock, defensive `EXPIRE`) applied to a ZSET scored by **absolute expiry time** rather than Carlson's acquisition time — combining the atomicity precedent Kelvran already has with the TTL-lease semantics the hold-duration shape actually needs. A caveat that survives from the distributed-locking literature (Kleppmann's GC-pause argument) applies in a *softened* form here: because a concurrency cap is an admission-control mechanism, not a mutual-exclusion correctness guard, a paused holder wrongly believed-alive causes brief, bounded over-admission — not the double-write hazard fencing tokens exist to prevent — so full Redlock-style multi-node consensus is very likely unnecessary overhead for this feature.

## Findings

### Finding 1 — Two structurally different Redis "many holders under a cap" patterns exist; they are not interchangeable, and the difference is exactly where they put the leak-detection logic (confidence: high)

The **ZSET+Lua** family (Carlson's `acquire_semaphore_lua`/`acquire_fair_semaphore`) atomically prunes any sorted-set member whose *acquisition-time* score has aged past a timeout cutoff (`ZREMRANGEBYSCORE ... -inf now-timeout`), then adds the new holder only if the post-prune cardinality is still under the limit — combining expiry-check and capacity-check in one Lua script. No Redis-native TTL/`EXPIRE` is used anywhere; a plain `ZREM` handles clean release, and a separate `refresh_semaphore`/`refresh_fair_semaphore` call (checking `ZSCORE` before re-`ZADD`-ing a fresh timestamp) is the heartbeat a long-lived holder must call to avoid being pruned. Critically, pruning **only ever runs inside another client's `acquire` call** — there is no background sweeper and no Redis-native expiry, so a leaked slot on an otherwise-idle key persists until somebody else happens to call acquire again. *(Sources: josiahcarlson/redis-in-action ch06 and ch11 listings, primary, multiple independently-verified claims.)*

The **lease+heartbeat** family (Redisson `RPermitExpirableSemaphore`, `goadesign/pulse`) instead gives each holder a Redis-native TTL from the start, tunable per-acquisition, and expects a background renewal loop to keep an active holder's lease alive; a crashed holder's lease lapses and is reclaimed by Redis's own expiry mechanism, not by another client's next call. `goadesign/pulse` exposes this as two independently tunable, code-enforced knobs — `WithLeaseTTL` (crash-recovery bound) and `WithHeartbeatInterval` (renewal frequency), with a hard-enforced invariant that heartbeat must be strictly shorter than lease TTL (`parseOptions` returns an error otherwise). *(Sources: goadesign/pulse README + semaphore.go, primary; redisson.pro docs + Redisson javadoc, primary.)*

A third pattern — `bluele/redis-semaphore`'s plain **LIST-based token pool** (`RPUSH` a fixed set of tokens at init, `BLPOP`/`LPOP` to acquire, `LPUSH` to release) — is a materially simpler data structure than either, but its stale-holder detection writes exactly one timestamp at acquire time with **no renewal method anywhere in the module**, so a long-running-but-alive holder becomes indistinguishable from a dead one once it exceeds a single fixed `stale_client_timeout` and gets its slot reclaimed out from under it. This is a real, named pitfall for Kelvran to avoid, not a pattern to imitate — and the repo itself is a decade-old, 38-star library, a weaker precedent than the other two families. *(Source: bluele/redis-semaphore, primary; low-strength precedent.)*

### Finding 2 — The leaked-permit problem is solved by TTL-based auto-expiry, but the *locus* of the TTL differs by family, and Kelvran's hold-duration shape favors the lease-native version (confidence: high)

For the ZSET+Lua family, "solving" leaks means accepting that a leak lives in Redis until another `acquire` call happens to prune it — fine for a workload where `acquire` calls are frequent and evenly spread across keys, but a poor fit for Kelvran's per-virtual-key structure, where a quiet or low-traffic key could leave a leaked slot uncleaned indefinitely and where correctness depends on every gateway instance's wall clock agreeing closely enough that "now" computed on instance A and instance B don't disagree by more than the timeout window. The Carlson recipe's own source has no mention of clock drift or fencing tokens anywhere in the file. *(Sources: redis-in-action ch06/ch11, primary, multiple claims.)*

For the lease+heartbeat family, the TTL is attached to the specific Redis operation Redis itself already expires natively — `bsm/redislock` documents "run a ticker at roughly `ttl/3` intervals calling `Refresh`; a `Refresh` failure with `ErrNotObtained` signals the lock was lost (expired or stolen) and should typically cancel the protected work via context cancellation" as its recommended pattern, implemented via four embedded Lua scripts (`obtain.lua`, `refresh.lua`, `release.lua`, `pttl.lua`) that make every state transition atomic. `goadesign/pulse` documents the equivalent for its multi-holder semaphore: "Semaphore leases are renewed in the background until `Release` is called or Redis no longer recognizes the holder token," and separately, "Tune `WithLeaseTTL` for the maximum crash-recovery delay and `WithHeartbeatInterval` for how often active holders renew their lease." Redisson's `RPermitExpirableSemaphore` gives each acquired permit its own individually-tracked lease time (`acquire(leaseTime, unit)`, or `tryAcquire(waitTime, leaseTime, unit)` combining a wait-timeout with a lease), confirmed directly against Redisson's own javadoc parameter ordering. *(Sources: bsm/redislock README + repo, primary; goadesign/pulse README + semaphore.go, primary; Redisson javadoc + docs, primary.)* Note: a claim that Redisson's permit-expiry mechanism eliminates the *need* for a separate heartbeat/renewal loop entirely did not survive verification (refuted 0-3) — in practice a fixed lease time set once at acquire still requires the caller to either know the hold duration up front or actively renew it, which is the same operational burden the heartbeat pattern names explicitly rather than hides.

### Finding 3 — TTL/heartbeat interval choice is a documented, not improvised, tradeoff, and Kelvran's own dataplane already removes the easiest wrong answer (confidence: high)

`bsm/redislock`'s own documentation states the tradeoff directly: pick the renewal interval at roughly `ttl/3` "so a single transient redis blip still leaves room to retry before the lock expires." `goadesign/pulse` goes further and makes the same shape a hard, code-enforced invariant (heartbeat interval must be strictly less than lease TTL, or construction fails with an error) rather than just a documentation recommendation. *(Sources: bsm/redislock README, primary; goadesign/pulse semaphore.go, primary.)* Because Kelvran's own dataplane deliberately has **no fixed overall per-request duration cap** — only a per-idle-window streaming timeout that resets on every chunk — the naive answer of "set the lease TTL to the expected request duration" doesn't have a stable value to anchor on. The heartbeat/renewal model is exactly what decouples the crash-recovery bound (a short, fixed lease TTL) from the actual, unbounded work duration: as long as the request-handling goroutine is alive and its heartbeat ticker keeps firing, an arbitrarily long-lived streaming request stays safe, and only an actually-dead holder (crashed process, hung goroutine that stops ticking) is reclaimed, within one lease TTL of its last heartbeat.

### Finding 4 — Mutex-shaped distributed locks (Redsync/Redlock) are the wrong primitive shape for a multi-holder cap (confidence: high)

`go-redsync/redsync` implements a Redis-based distributed **mutual-exclusion lock** per the Redlock algorithm (`redis.io/topics/distlock`) — one holder per named lock, full stop; its README's own usage example states "no one else can obtain the same lock ... until we unlock it." It exposes only `Mutex`/`Lock`/`Unlock`/`Extend` — there is no multi-holder counter or semaphore concept anywhere in the library. This is a genuinely different problem shape from Kelvran's `MaxInFlight > 1`-holders-per-key requirement, and confirms that Redlock-family tooling (built for single-writer coordination, e.g. protecting a critical section) isn't the thing to reach for here — it's solving a different problem than "let up to N requests through, block the (N+1)th." *(Source: go-redsync/redsync README, primary.)*

### Finding 5 — TTL-based schemes have a known, real correctness gap under unbounded process pauses, but its severity for Kelvran's use case is softer than for a mutual-exclusion lock (confidence: high on the underlying mechanism; medium on how much it matters here)

Martin Kleppmann's widely-cited walkthrough demonstrates that a client paused long enough (stop-the-world GC, but generalizable to any unbounded scheduling/network delay) can have its lock/lease TTL expire and be reassigned to a second client, then resume execution still believing it holds the original permit — producing two simultaneous believed-holders. Even Redis's own creator's rebuttal to this critique ("Is Redlock safe?") does not dispute the underlying mechanism, only narrows exactly when the vulnerable window opens, and still recommends mitigations (double time-checks, fencing tokens) rather than denying the problem. *(Sources: martin.kleppmann.com, blog, primary voice on the critique side; corroborated indirectly by Redis's own creator's rebuttal not disputing the core mechanism.)* A related, more specific claim — that a monotonically increasing fencing token checked by the protected resource is "the" standard fix, and that Redlock is "explicitly criticized" for lacking one — did **not** survive verification at the same confidence (1-2 vote); treat the general pause-hazard as solid and the "fencing tokens are the standard/only fix" framing as contested, not settled. For Kelvran specifically, this matters less than it would for a true mutex: a concurrency limiter is an **admission-control cap**, not a correctness guard over shared mutable state. If a paused gateway instance's heartbeat lapses, its lease expires, another request is admitted into what looks like a freed slot, and the paused instance later resumes and (incorrectly) still believes it holds a slot — the consequence is a brief, bounded over-admission of in-flight requests past `MaxInFlight` for at most one lease TTL, not a double-write or a lost-update. That's a real, worth-naming risk, but not one that obviously justifies Redlock's full multi-node-quorum complexity for this specific feature.

## Caveats

- Two adjacent, plausible-sounding claims did **not** survive adversarial verification and are deliberately excluded from the findings above: (1) that Redis's own official docs recommend a generalized "lock extension" heartbeat pattern as *the* mechanism for holders needing more time (0-3 — the official docs describe the single-instance `SET NX PX` + `DELEX`/GET-then-DEL pattern, per Finding-adjacent context, but not a documented "extend" recipe with the same authority); and (2) that `goadesign/pulse` needs "no explicit release required" because of TTL alone (0-3 — its own docs describe TTL as a *crash-recovery backstop* alongside, not instead of, explicit `Release`). Both are noted here so the recommendation below doesn't quietly lean on either.
- The Carlson/*Redis in Action* recipe is roughly a decade old; it remains the standard citation for the ZSET-semaphore shape and its mechanics are static, unchanging code, so age doesn't undermine the *mechanical* claims about it — but it predates, and does not address, the clock-skew and fencing-token concerns the distributed-systems literature raised afterward (Kleppmann, 2016).
- `bluele/redis-semaphore` is a weak precedent on its own merits (last substantive activity ~2016, 38 stars) — it's included here specifically as a documented anti-pattern (fixed single-timestamp staleness with no renewal path), not as a library to adopt.
- None of the verified sources describe a Redis-semaphore implementation tested specifically under Redis Cluster failover or network partition; the partition/failover-safety discussion above is inferred from the general Redlock-safety literature (Kleppmann vs. antirez), not from a source that tested a *semaphore* (as opposed to a *lock*) under partition specifically. Treat that gap as open.

## Recommendation for Kelvran

**Follow the lease+heartbeat family, not the ZSET-lazy-sweep family — but implement it as a single ZSET scored by absolute expiry time, atomically managed via Lua, matching the exact architectural idiom `redislimiter.go` already established.** This gets the atomicity and easy-cardinality-check properties of Carlson's ZSET recipe (a plain `ZCARD` after pruning gives the current in-flight count for free, mirroring `ConcurrencyLimiter.InFlight`) while getting the leak-safety properties of the lease+heartbeat family (a slot expires based on absolute time regardless of whether anyone else calls `acquire`, once the ZSET-key-level `EXPIRE` backstop and a per-holder score comparison are both in place).

Why not a per-holder native-TTL key (`SET concurrency:{keyID}:{holderID} 1 PX leaseTTL`) instead of a ZSET: counting live holders atomically becomes the hard part — either an O(n) `SCAN`/`KEYS` over the key namespace (slow, non-atomic, gets worse as N grows) or a separate counter that must be kept in sync with each key's independent TTL, which reintroduces exactly the leak/desync risk TTLs exist to solve. This is very likely *why* both Carlson's recipe and Redisson's `RPermitExpirableSemaphore` converge on a single sorted/tracked structure rather than N independent keys — a single `ZCARD` after `ZREMRANGEBYSCORE` is the atomic, O(log n) answer to "how many live holders are there right now."

Concrete design, following `redislimiter.go`'s own naming and structure conventions:

```go
// package redisconcurrency (sibling to redislimiter)
type Limiter struct {
    client         *redis.Client
    acquireScript  *redis.Script // ZREMRANGEBYSCORE (prune expired) + ZCARD check + ZADD (score = now+leaseTTL) + EXPIRE
    refreshScript  *redis.Script // ZSCORE existence check + ZADD (score = now+leaseTTL), mirrors Carlson's refresh_semaphore
    releaseScript  *redis.Script // plain ZREM by holderID — no Lua atomicity needed beyond what ZREM itself gives
}

func Open(addr string) (*Limiter, error)

// Acquire mirrors ConcurrencyLimiter.Acquire's "false = at cap" contract,
// but must additionally return a holderID: unlike the in-memory version's
// bare per-key counter (which never needs to know WHICH acquisition a
// Release call corresponds to, since it just decrements), a Redis ZSET
// with potentially many concurrent holders per key needs a per-acquisition
// identity to remove the correct member. This is a deliberate, minimal,
// necessary interface difference from the in-memory type — not a design
// choice made lightly, and it should be called out explicitly to whoever
// signs off on wiring this in, not silently absorbed.
func (l *Limiter) Acquire(ctx context.Context, keyID string, maxInFlight int, leaseTTL time.Duration) (holderID string, ok bool, err error)

// Refresh is the heartbeat call — the caller's own request-handling
// goroutine should run this on a time.Ticker at leaseTTL/3 (bsm/redislock's
// documented rule of thumb; goadesign/pulse enforces the same shape as a
// hard invariant) for as long as the request is in flight, stopping the
// ticker via defer when the request completes. A false return (holder no
// longer present — already pruned by someone else's Acquire) signals the
// caller's slot was already reclaimed and it should treat the request as
// having lost its concurrency admission.
func (l *Limiter) Refresh(ctx context.Context, keyID, holderID string, leaseTTL time.Duration) (stillHeld bool, err error)

// Release mirrors ConcurrencyLimiter.Release's unconditional, error-free
// cleanup contract as closely as Redis allows.
func (l *Limiter) Release(ctx context.Context, keyID, holderID string) error
```

TTL/heartbeat numbers: because Kelvran's dataplane has no fixed overall request-duration cap (only the idle-window streaming timeout), pick a **short, fixed lease TTL decoupled from expected work duration** — on the order of tens of seconds (e.g. 30-60s) — precisely because the heartbeat, not the TTL, is what keeps an arbitrarily long-lived streaming request's slot alive; the TTL only needs to be long enough that a couple of missed heartbeats (a transient Redis blip) don't cause a false eviction, and short enough that a genuinely crashed holder's slot is reclaimed promptly. Set the heartbeat interval to roughly `leaseTTL / 3`, following `bsm/redislock`'s documented convention and the same ratio `goadesign/pulse` enforces as a hard invariant (heartbeat strictly `<` lease TTL) — e.g. a 45s lease with a 15s heartbeat tick gives two full missed-beat retries of margin before eviction. Both values should be operator-configurable (mirroring `ConcurrencyConfig.MaxInFlight`'s own per-key configurability), not hardcoded constants.

Given Finding 5, a single Redis instance (the same trust boundary `redislimiter.go` already accepts, and consistent with `docs/rfcs/2026-09-03-distributed-rate-limiting.md`'s existing fail-open policy) is a reasonable choice for v1 — the failure mode of a paused/partitioned gateway instance is bounded over-admission for at most one lease TTL, not a correctness catastrophe, so Redlock's multi-node quorum machinery is very likely not worth its complexity for this specific feature. This should be named as an explicit, deliberate scope decision in whatever RFC formalizes this change, the same way `docs/rfcs/2026-09-05-gateway-cache-stampede-protection.md` explicitly named "a distributed lock instead of in-process singleflight" as a rejected-for-v1 alternative rather than an unconsidered option.

## Open Questions

- Should `Acquire`'s interface change (returning a `holderID` the caller must thread through to `Refresh`/`Release`) live behind a new package only, or does the existing in-memory `ConcurrencyLimiter.Acquire(keyID) bool` / `Release(keyID)` shape need to change too, for the two implementations to stay swappable via config the way `KeyLimiter`/`redislimiter.Limiter` already are for rate limiting? This research did not resolve which caller (`dataplane.Pipeline`, presumably) would own storing the `holderID` for the lifetime of a request, or whether it belongs on the request's `context.Context`.
- What should happen to a request whose `Refresh` heartbeat reports `stillHeld=false` mid-flight (its slot was already reclaimed by another instance)? Fail the request outright (mirroring `bsm/redislock`'s "cancel the protected work via context cancellation" convention), or let it finish but stop counting it — this is a real product-behavior decision this research didn't investigate.
- No verified source in this research tested a ZSET-based (or any) Redis semaphore specifically under Redis Cluster resharding or a primary/replica failover event — only the general Redlock-safety literature (Kleppmann/antirez) was available, and that's about locks, not semaphores. Worth a dedicated check before shipping if Kelvran's Redis deployment target is clustered rather than single-primary.
- Should the lease TTL be a single global default, or configurable per virtual key the same way `MaxInFlight` already is — e.g. a tenant known to make very long-running agentic calls might legitimately want a longer TTL (at the cost of a slower leak-recovery bound) than a tenant making only short calls?
