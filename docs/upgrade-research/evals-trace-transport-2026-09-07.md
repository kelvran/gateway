# Kelvran Evals — Production-Trace-Ingestion Transport Research

**Date:** 2026-09-07
**Scope:** the one open question `docs/upgrade-research/evals-2026-09-06.md` Finding 6 explicitly deferred — which transport a separate Python `evals/` process should use to sample a subset of `gateway`'s production OTel/request data for online eval purposes. Pure research; no code touched in `gateway/` or `evals/`.
**Method:** direct primary-source retrieval (WebFetch against project docs, OSS READMEs, and vendor docs) plus direct inspection of Kelvran's own repo. This is a **single-pass, single-source-per-claim** research method, not the 3-vote adversarial cross-check the 2026-09-06 reports used — every claim below is cited to one real, fetched, current source, but has not been independently triangulated a second or third time the way the prior reports' claims were. Where a claim rests on Kelvran's own prior internal research (the `gatewayevents` RFC's TensorZero/Portkey/LiteLLM/Kong survey) rather than a fresh fetch in this pass, that's called out explicitly rather than re-presented as freshly confirmed. See Caveats for the specific sources this pass could not reach.

## Grounding: Kelvran's actual current shape (confirmed via direct repo inspection)

- `gateway` emits real OTel spans today — one GenAI span per request (`gen_ai.*` + `kelvran.*` attributes) nested inside an outer `otelhttp`-middleware HTTP-server span, so a Kelvran trace today is a **2-span, single-process** trace, never a multi-service/multi-hop one — confirmed directly against `docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md` and `gateway/internal/telemetry/telemetry.go`.
- `gateway`'s exporter is a 3-way switch — `stdout` (default) / `otlp` / `none` — configured once, driving both the trace and metrics pipelines identically (`gateway/internal/telemetry/telemetry.go`; `docs/operations/TELEMETRY.md`). Sampling is `ParentBased(AlwaysSample())` — **100% of requests are traced today**, an explicit, still-open "Unresolved Question" in the OTel RFC, not yet revisited for cost reasons.
- `gatewayevents_v1` (`docs/rfcs/2026-09-03-api-gatewayevents-contract.md`) is real today: a protobuf-encoded, `protojson`-marshaled `GatewayDecisionEvent` (outcome enum + `trace_id`/`span_id` + virtual key + model), added as a new field on the same structured JSON log line `logRequest` already emits per request. `evals/evals/ingestion/` already has a real, tested decoder for this exact message type (golden-fixture round-trip, per `evals/ARCHITECTURE.md`).
- **Zero cross-service transport of any kind exists today.** Grepped the full `docs/` tree and both `ARCHITECTURE.md`s: no mention of an OTel Collector anywhere in Kelvran's documented deployment topology (`docs/operations/DEPLOY.md` names only `gateway` and `evals` as Kubernetes Deployments/Compose services — no collector, no log-aggregation backend, no queue). `evals` has no exporter wiring at all (`docs/operations/TELEMETRY.md`: "`evals` has no exporter wiring yet").
- `evals` already carries the OTel Python SDK as a real dependency (`evals/tracing.py` — a locally-held `TracerProvider`, zero exporter, self-instrumenting its own sandbox spans, per `docs/rfcs/2026-09-04-evals-trace-span-model.md`). Any future OTLP *receiver* work in `evals` would extend an already-present dependency, not add a new one.
- Production deployment is Kubernetes with **separate, independently-scaled Deployments** for `gateway` and `evals` (`docs/operations/DEPLOY.md`) — i.e., `gateway` is expected to run as multiple replicas behind a Service, not a single pinned process.

## Option 1 — OTel Collector fan-out

**Confirmed, current, cited:**

- The Collector is a real, vendor-neutral "agent or gateway" deployable that receives/processes/exports telemetry to one or more backends [opentelemetry.io/docs/collector/](https://opentelemetry.io/docs/collector/) — confirmed. Two real deployment topologies exist: per-host/sidecar "agent" and cluster-level "gateway" tiers, which can be chained [opentelemetry.io/docs/collector/architecture/](https://opentelemetry.io/docs/collector/architecture/) — confirmed.
- **Tail sampling** (decide per-*trace*, after seeing all its spans) is a real, shipped processor, but is explicitly stateful: "the processor keeps spans in memory while it waits to make a sampling decision," bounded by `num_traces`/`decision_wait`, with a documented risk that a slow decision step or an undersized buffer causes traces to be evicted before a decision is made. Because "All spans for a given trace MUST be received by the same collector instance," the docs prescribe a mandatory **two-tier architecture** — a stateless load-balancing-exporter tier hashing trace IDs to a fixed backend tier that actually holds the tail-sampling state — recommending against combining both roles in one tier "for better failure isolation" [github.com/open-telemetry/opentelemetry-collector-contrib — `tailsamplingprocessor`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/tailsamplingprocessor) — confirmed.
- The Collector's own scaling doc corroborates and extends this: stateless components scale by adding replicas behind an L7 (gRPC-aware) load balancer, but tail-sampling/span-to-metrics processors are named as the specific exception requiring the load-balancing-exporter-plus-consistent-hashing pattern above, with a documented minimum resilience floor (the doc's own example: 3 replicas) and DNS-refresh-interval tuning needed to avoid inconsistent backend-list views across the front tier in elastic environments [opentelemetry.io/docs/collector/scaling/](https://opentelemetry.io/docs/collector/scaling/) — confirmed.
- A materially simpler, **stateless** alternative exists in the same ecosystem: the probabilistic sampler processor makes a per-span (or per-log-record) decision independently, with no buffering, no cross-instance coordination beyond keeping `hash_seed` identical across a tier, and real support for percentage-based sampling on traces (56-bit randomness spec) or logs (hash/attribute-based) [github.com/open-telemetry/opentelemetry-collector-contrib — `probabilisticsamplerprocessor`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/processor/probabilisticsamplerprocessor) — confirmed.
- Fan-out/routing to multiple destinations (e.g., "ship everything to the main backend, plus 5% to `evals`") is a real, shipped capability via the routing connector, which routes by OTTL condition to named pipelines/exporters, with `copy` vs `move` semantics and a documented default-pipeline fallback [github.com/open-telemetry/opentelemetry-collector-contrib — `routingconnector`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/connector/routingconnector) — confirmed.
- Real, current, comparable-system precedent for "OTLP straight to the backend, Collector only when you need to fan out or transform first" exists in Langfuse's own ingestion docs: direct OTLP-to-Langfuse is the default and requires no collector; a collector is only introduced "when consolidating traces from multiple services" or filtering via the collector's own `filterprocessor` before forwarding — with an explicit warning that span-level filtering risks producing incomplete traces if the root span gets dropped [langfuse.com/docs/opentelemetry/get-started](https://langfuse.com/docs/opentelemetry/get-started) — confirmed.

**Reasonable inference (labeled, not confirmed by a citation naming Kelvran):**

- Because Kelvran's real trace shape today is a single-process, 2-span trace (no multi-service hops), tail sampling's core value proposition — deciding on properties only visible once a *whole, multi-span, potentially multi-service* trace has arrived — is currently much weaker for Kelvran than for the typical microservices case the processor's own docs are written for. The stateless probabilistic sampler (which doesn't need the two-tier architecture at all) would very likely capture everything Kelvran's own use case ("sample X% of requests, or requests matching a `kelvran.*` attribute, for eval purposes") actually needs, at a fraction of the operational complexity. This is an inference combining two confirmed facts (Kelvran's own span shape; the processor docs' own stated rationale for statefulness), not a claim any source makes about Kelvran by name.
- Standing up any Collector tier at all — even the simpler, stateless probabilistic-sampler shape — is still a genuinely new piece of infrastructure with its own deployment, scaling, and on-call surface that doesn't exist anywhere in Kelvran's documented topology today (see Grounding above). This is a real cost, not a hypothetical one, given Kelvran currently operates exactly two deployables.

## Option 2 — A dedicated sampling API (gateway exposes an endpoint evals polls)

**Confirmed, current, cited:**

- LiteLLM Proxy — the closest real, currently-maintained analog to Kelvran's own shape (an LLM gateway sitting in front of multiple providers) — is **push-only**: every logging/observability integration (OTel, Langfuse, Datadog, MLflow, Langsmith, Arize, a generic custom-HTTP callback, etc.) is registered as a `success_callback`/`failure_callback` and actively invoked by the proxy at request completion. Nothing in LiteLLM's logging surface is a pull/poll API a separate service queries for a sample of recent requests [docs.litellm.ai/docs/proxy/logging](https://docs.litellm.ai/docs/proxy/logging) — confirmed.
- The one real, general precedent for "an API that returns a sample of recent traces" is Jaeger's Query Service — but it deliberately lives on the **storage/query backend tier** (`jaeger-query`, reading from Cassandra/Elasticsearch), never on an instrumented application itself. Jaeger's own docs even distinguish an internal, UI-only, explicitly "subject to change" JSON API from the stable, versioned `api_v3` gRPC/JSON API meant for external programmatic callers — but both live on the separate query service, not on whatever emitted the spans [jaegertracing.io/docs/latest/apis/](https://www.jaegertracing.io/docs/latest/apis/) — confirmed. No comparable precedent was found anywhere in this pass for a request-serving process exposing a "give me a sample of my own recent requests" endpoint to be polled by a downstream analytics consumer.
- OTLP itself — the wire format Kelvran's own gateway already emits — is architecturally a push protocol: exporters actively construct requests and send them to a configured target endpoint, with retry/backoff semantics that only make sense for an active sender, never a poll target [opentelemetry.io/docs/specs/otel/protocol/exporter/](https://opentelemetry.io/docs/specs/otel/protocol/exporter/) — confirmed. Building a pull API on top of `gateway` would be a genuine deviation from the wire-format convention `gateway` already speaks, not an extension of it.

**Reasonable inference (labeled):**

- Given Kelvran's own real deployment model — `gateway` as multiple, independently-scaled Kubernetes replicas behind a Service (`docs/operations/DEPLOY.md`) — a poll-based sampling endpoint on `gateway` itself would, without additional work, only ever return whatever the polling client's Service-routed connection happened to land on for that particular poll: sampling coverage would be biased toward whichever replica the load balancer picked, not a representative cross-replica sample, unless the endpoint were itself made cluster-aware (aggregating across replicas) — which is a materially harder, statefully-coordinated problem than a single-process buffer, and starts to resemble a hand-built, worse version of the Collector's own load-balancing-exporter tier (Option 1) rather than a simpler alternative to it. This is inference, not a cited claim about Kelvran specifically.
- Buffering "recent requests" in `gateway`'s own process for a poll target to read would add real new statefulness to the hot request-serving path (the same memory-vs-retention tradeoff the tail-sampling processor's README documents explicitly for exactly this problem, see Option 1) and a new authenticated admin surface distinct from `gateway`'s existing per-virtual-key bearer-token model — `SECURITY.md`'s "check auth on every route" rule and `THREAT_MODEL.md`'s cross-tenant-isolation concerns would apply to it like any other route, for a capability Kelvran doesn't have today. This is a real, Kelvran-specific cost inferred from the project's own stated security conventions, not a generic industry warning.

## Option 3 — Log-based ingestion (via the already-real `gatewayevents_v1` field)

**Confirmed, current, cited:**

- `gatewayevents_v1` already exists, already carries `trace_id`/`span_id` (joinable to the real OTel span), and is already decoded end-to-end by a real, tested `evals/ingestion/` module — per direct inspection of `docs/rfcs/2026-09-03-api-gatewayevents-contract.md` and `evals/ARCHITECTURE.md`. The RFC's own "Drawbacks" section already names the honest gap precisely: *"`gatewayevents_v1`'s JSON-log-field transport is explicitly a stopgap, not a real production-events pipeline — genuinely useful for proving the contract works end-to-end, not yet useful for `evals` to actually sample production traffic from."* Nothing in this research pass changes that assessment — the gap named there is still real today.
- The concrete, missing piece is a real log-shipping/centralization mechanism — Kelvran has none today (confirmed absent from `docs/operations/DEPLOY.md`, which names no log-aggregation backend at all). A real, current, primary-sourced tool exists for exactly this role: Vector's file source tails log files with fingerprint-based rotation-safe checkpointing, then a `remap` (parse JSON) → `filter`/`sample`/`route` transform chain can select/sample events on a JSON field (e.g., `gatewayevents_v1.outcome`, or a hash-based percentage sample) before forwarding to a sink [vector.dev/docs/reference/configuration/sources/file/](https://vector.dev/docs/reference/configuration/sources/file/) — confirmed. This is a real, off-the-shelf way to turn "gateway already logs this field" into "evals can read a sampled subset of it," without gateway emitting anything new.
- A genuinely load-bearing caveat, directly relevant to Kelvran's own design (`gatewayevents_v1` joins to the OTel span by `trace_id`/`span_id`, per the RFC): Datadog's own logs-traces-correlation docs confirm this trace-ID-in-a-log-line pattern is a standard, widely-supported technique (documented for 7+ languages plus OTel) — but explicitly warn that "traces and logs are sampled independently," so a log's `trace_id` can point to a trace that was never ingested/retained; this "does not indicate a configuration error," it's an inherent property of decoupling the two pipelines [docs.datadoghq.com/tracing/other_telemetry/connect_logs_and_traces/](https://docs.datadoghq.com/tracing/other_telemetry/connect_logs_and_traces/) — confirmed. **Applied to Kelvran specifically:** this caveat doesn't bite *today*, because `gateway`'s trace sampling is currently `ParentBased(AlwaysSample())` — 100% of requests are traced (per the OTel RFC's own Unresolved Questions) — so every `trace_id` a `gatewayevents_v1` log line carries currently points to a real, retained span. It becomes a real problem only if/when `gateway` ever samples its OTel pipeline down independently of the JSON log line (which logs every request unconditionally) — at that point the log-carried `trace_id` would start pointing to traces that were never kept, exactly Datadog's documented failure mode.

**Reasonable inference (labeled):**

- "Log-based ingestion" is not actually a fully distinct third option from a transport standpoint — it's "ship `gatewayevents_v1already-real payload via a log-shipping tool" vs. "ship OTel spans via a Collector." The genuinely open decision underneath it is the same one underneath Option 1 in different clothing: *some* piece of infrastructure has to move data off `gateway`'s pods and into somewhere `evals` can read it, whether that's an OTel Collector or a log shipper (Vector/Fluent Bit) — Kelvran has picked neither yet. The advantage specific to this option is that the *payload* and its *consumer* (`evals/ingestion/`) already exist and are already tested; only the shipping mechanism is missing — a smaller, narrower gap than Option 1's "build the whole pipeline."

## Recommendation for Kelvran, specifically

**Do not build a dedicated sampling API on `gateway`.** No real precedent for this exact shape exists anywhere surveyed in this pass (the closest LLM-gateway analog, LiteLLM, is push-only; the one general precedent for a trace-sampling API, Jaeger's query service, deliberately lives on a separate storage tier, never the emitting application). Building one would also add new statefulness to `gateway`'s hot request-serving path and a new authenticated admin surface for a capability nothing else in this ecosystem builds this way — and given Kelvran's own multi-replica Kubernetes deployment (`docs/operations/DEPLOY.md`), it would need to solve the same cluster-aware-aggregation problem the Collector's own load-balancing-exporter tier already solves, just reinvented, worse, inside the gateway binary.

**Don't reach for a full OTel Collector deployment yet either** — not because it's wrong in principle (it's real, shipped, and the routing connector genuinely does support "fan out N% to `evals`"), but because it's the most infrastructure for the least immediate payoff given Kelvran's *current* trace shape: a single-process, 2-span trace with no cross-service hops. Tail sampling's entire reason to exist — deciding on a trace only visible once every span from every hop has arrived — isn't yet a problem Kelvran has, and even the cheaper, stateless probabilistic-sampler path still means operating an entirely new deployable that doesn't exist in this project's topology today.

**Ship the smallest real thing: turn `gatewayevents_v1` into an actual pipeline by adding a log shipper (Vector or Fluent Bit), not a new wire format.** This is the only one of the three options where the payload (`gatewayevents_v1`, already carrying `trace_id`/`span_id`/outcome/virtual-key/model) and the consumer (`evals/ingestion/`, already decoding this exact message with a passing golden-fixture test) both already exist and are already tested — the *only* missing piece is a boring, well-understood log-shipping step (tail `gateway`'s structured JSON log line → parse → sample/filter on a field → forward to wherever `evals` reads from), which doesn't touch `gateway`'s request-serving code path at all and doesn't require `evals` to know anything about `gateway`'s replica topology (a log shipper naturally sees every replica's own logs, sidestepping Option 2's sampling-bias problem for free). Concretely, that means: (1) pick a destination `evals` can read on its own schedule — a file/object-storage drop (S3/GCS) is the lowest-ceremony choice given `evals` is a CLI, not a long-running service, per `evals/ARCHITECTURE.md`'s own framing; (2) configure the shipper's field-based sample/filter step now, before volume makes "ship everything" expensive; (3) explicitly do **not** revisit this recommendation just because `gateway`'s OTel span sampling rate changes — as of today it's 100%, so the log/trace-independent-sampling caveat named above is dormant, but it becomes real load-bearing risk (and a legitimate trigger to revisit Option 1's Collector-based approach instead) the moment `gateway` ever samples its OTel pipeline down independently of its JSON logs.

**Concrete revisit triggers, not a speculative timeline:** (a) `gateway` starts sampling its own OTel spans below 100% for cost reasons — the exact moment the log-carried `trace_id` can start pointing to nothing, per Datadog's own documented failure mode; (b) Kelvran's tracing grows a genuine second hop (e.g., the roadmap's MCP/A2A brokering work produces spans that cross a service boundary) — the point at which tail sampling's whole-trace-visibility value actually starts to exist; (c) eval sampling needs outgrow "read a sampled log stream" — e.g., a need to sample specifically on span-level attributes not present in `gatewayevents_v1`'s current (deliberately narrow, v1) schema. None of these conditions hold today.

## Open questions

- Which concrete destination should the recommended log shipper write to — a plain object-storage bucket (S3/GCS) `evals` polls on its own CLI-driven schedule, or a queue (SQS/Pub-Sub) for lower-latency sampling? This report recommends starting with the lower-ceremony object-storage drop given `evals`' own CLI-not-daemon shape, but the actual choice should be made by whoever owns Kelvran's real (not yet built) log-aggregation infrastructure, not decided abstractly here.
- What sampling rate/rule should the shipper's filter/sample step actually apply — a flat percentage, or something scoped to specific `gatewayevents_v1.outcome` values (e.g., always keep `OUTCOME_UPSTREAM_ERROR`/`OUTCOME_BUDGET_EXCEEDED`, sample everything else at a lower rate, mirroring promptfoo's own critical-vs-aggregate gating pattern named in `docs/upgrade-research/evals-2026-09-06.md` Finding 1)? Not decided here — this report resolves the *transport* question Finding 6 asked about, not the sampling *policy* on top of it.
- Once sampled `gatewayevents_v1` records reach `evals`, do they feed the existing manual `evals promote` command unchanged, or does live-traffic sampling warrant its own review path distinct from the current CLI-only promotion flow? `docs/upgrade-research/evals-2026-09-06.md`'s own Open Questions section already named this exact follow-on question — it remains open after this pass, deliberately, since it's a downstream design question this report's narrower scope (transport only) doesn't answer.
