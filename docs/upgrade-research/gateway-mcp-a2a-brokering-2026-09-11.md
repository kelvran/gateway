**Scope:** `gateway/internal/mcp` — confirmed **NOT BUILT** this session (zero code; no such directory exists under `gateway/internal`, which currently holds `adapter`, `admin`, `budget`, `cache`, `costaccounting`, `gateway`, `guardrail`, `identity`, `prompt`, `ratelimit`, `router`, `streaming`, `telemetry`). `PRD.md` lists "MCP/A2A tool brokering" as explicitly out of scope for v1, tracked only as a future `docs/rfcs/` candidate. ## Executive summary

The MCP spec just underwent its largest re-architecture to date (2026-07-28, ~6 weeks before this research date): it dropped session state, the `initialize`/`initialized` handshake, and the `Mcp-Session-Id` header entirely in favor of a stateless, per-request model, with the MCP maintainers themselves calling this a breaking change carrying real migration cost — this is not yet a settled foundation to build a v1 integration against without expecting near-term churn. Auth compounds the instability: MCP authorization remains explicitly **OPTIONAL** and transport-scoped (HTTP servers SHOULD implement it, STDIO servers SHOULD NOT), and even where implemented it still rests on an unratified IETF draft of OAuth 2.1, not a finished RFC. On the credential question, the peer field has already converged on an answer that generalizes beyond any single vendor: nobody extends their existing gateway API key into the tool-call delegation credential — LiteLLM ships five distinct `auth_type` patterns (including RFC 8693 On-Behalf-Of token exchange) and requires the caller's own OAuth bearer token as a second, separate credential alongside its virtual key, while Portkey centralizes a single client-facing key but injects a different, per-server upstream credential (OAuth token, API key, or identity header) behind it — both confirm Kelvran's virtual-key model would need a new, distinct outbound-credential layer, not an extension of `Verifier.Verify`. On result-scanning, the evidence is genuinely thin: LiteLLM's own MCP Guardrails docs show worked examples scanning only outbound tool-call inputs (`pre_mcp_call`), with no documented post-call/result-scanning mode found — suggesting Kelvran's already-verified role-agnostic scan (which structurally covers any message role, including a future "tool" role, via full JSON marshal) is not behind peer practice on this dimension, it may be ahead of what's documented anywhere. On resilience, this research pass turned up **no surviving evidence at all** — neither confirming nor refuting whether fallback/circuit-breaker infrastructure generalizes to tool calls — a genuine gap that should not be assumed away. Finally, on realistic v1 scope: LiteLLM's `require_approval` flag proves the production peer bar is already full bidirectional brokering (auto-execute + feed results back), not merely read-only tool discovery, though LiteLLM's own default is the more conservative "return tool calls to the client for manual execution" — which is the safer real-world v1 target given the spec's own churn and the still-immature guardrail-for-results story.

## Findings

### 1. The MCP spec just underwent its largest, self-acknowledged breaking re-architecture (stateless core, dropped handshake/session), six weeks before this research date — this is a live-churn moment, not a settled target

**What the research found:** The 2026-07-28 MCP spec revision removes the `initialize`/`initialized` handshake and the `Mcp-Session-Id` header entirely, transforming MCP "from a bidirectional stateful protocol into a request/response stateless protocol." Any MCP request can now land on any server instance behind a plain round-robin load balancer — sticky sessions and shared session stores are no longer required, a change AWS's own AgentCore Gateway documentation independently corroborates and has already built production integration against (citing SEP-2575/SEP-2567). The legacy HTTP+SSE transport is formally deprecated with a twelve-month offramp, replaced by Streamable HTTP requiring new `Mcp-Method`/`Mcp-Name` headers (added specifically so intermediaries can route without parsing JSON bodies); server-initiated calls (sampling, elicitation, roots) move to a new "Multi Round-Trip Requests" pattern instead of long-lived bidirectional streams. Critically, the MCP maintainers themselves do not frame this as smooth or additive: "there will be some migration cost, especially for developers that did depend on session identifiers," and a partner quote goes further — "the biggest changes are breaking ones, and the community has chosen to do the hard work rather than paper over the gaps." Independently, the Go `mcp-go` server library's own godoc confirms this is not a one-time cleanup but active, ongoing method-level churn: it ships a dedicated `ErrRemovedInProtocolVersion` error and an `IsModernRequest(ctx)` version-gate specifically for the 2026-07-28 revision, alongside the confirmed removal of server-initiated requests (SEP-2322) and deprecation of the Sampling feature (SEP-2577) in this same revision.

**Why it matters for Kelvran specifically:** this directly answers research question 1's timing half. The stateless re-architecture is *good* news for Kelvran's own routing infrastructure — it means MCP servers, once this revision is the baseline, could sit behind Kelvran's existing weighted-routing/health-probing machinery without inventing sticky-session logic, a genuine simplification versus the pre-2026-07-28 world the 2026-09-07 report's confused-deputy analysis was written against. But the *speed and self-described severity* of this change (whole methods removed, a feature formally deprecated, a maintainer-acknowledged non-trivial migration cost, all within the last spec revision) is a strong signal that the protocol surface a Go implementation would need to track is still moving, not frozen. Building against a six-week-old breaking revision, with a library (`mcp-go`) that is still actively adding version-gate error types for it, is a meaningfully different risk profile than building against a spec that has gone several revisions without a structural change.

**Confidence:** High (primary MCP blog post + changelog + transport spec, independently corroborated by AWS's own technical docs and by `mcp-go`'s real, current source/godoc; unanimous 3-0 votes on every sub-claim).

**Signal:** `not_yet` — for the "should Kelvran build a v1 MCP client/server against the current spec today" question specifically. Trigger to revisit: either (a) the 2026-07-28 revision's twelve-month deprecation window closes with no further structural (non-additive) change to the base protocol, or (b) `mcp-go` (or another mainstream Go SDK) ships two consecutive spec-version bumps with zero new `Removed`/`Deprecated` entries, indicating the churn has settled. Until then, treat any MCP client/server work as needing an explicit re-validation pass before ship, not a one-time build.

### 2. MCP authorization itself is optional, transport-scoped, and built on a still-unratified OAuth 2.1 IETF draft — the auth *foundation*, not just the protocol core, is not fully settled either

**What the research found:** The MCP specification states plainly that "Authorization is **OPTIONAL** for MCP implementations. When supported: Implementations using an HTTP-based transport **SHOULD** conform to this specification. Implementations using an STDIO transport **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment." This exact policy is reproduced verbatim in both the 2025-06-18 and the current 2026-07-28 spec — it has not changed across the stateless re-architecture, so it is a stable design choice, not spec drift. Separately, the authorization mechanism MCP does define is explicitly built on "OAuth 2.1 IETF **DRAFT** (`draft-ietf-oauth-v2-1-13`)" — a still-unratified Internet-Draft, confirmed live on IETF's datatracker as of this research date at revision -16 (up from -13 cited in the MCP spec), with IESG submission only targeted for December 2026 and no RFC number assigned yet.

**Why it matters for Kelvran specifically:** this compounds Finding 1's timing signal from a different angle — even the *parts* of MCP that address authorization (the piece most load-bearing for research question 2) rest on a standard that has not itself finished standardizing. It also means any MCP-auth design decision Kelvran makes must explicitly handle the STDIO-transport carve-out (local/sidecar MCP servers legitimately skip MCP's own auth model and pull credentials from the environment instead) as a first-class case, not an edge case — a gateway-side credential-delegation layer designed only around the HTTP/OAuth path would silently not apply to a meaningful class of MCP servers.

**Confidence:** High (primary spec text, verified identical across two spec revisions; cross-checked against the live IETF datatracker entry for the underlying OAuth 2.1 draft; unanimous 3-0 votes).

**Signal:** `not_yet` for treating MCP's own OAuth 2.1 dependency as a finished target to design permanently against — but this does not block Kelvran from making its *own* auth design decision now (Finding 5), since Kelvran's credential-delegation layer does not need to wait on OAuth 2.1's ratification any more than any other OAuth 2.1-dependent product already shipping today does.

### 3. A2A reached a genuinely stable v1.0 spec with real (not just announced) cloud-platform production integrations — more settled than MCP's own current revision, but adoption numbers are self-reported

**What the research found:** A2A shipped its "first stable specification" (v1.0) in March 2026, adding multi-protocol support, enterprise-grade multi-tenancy, modernized OAuth 2.0 security flows (removing implicit/password grants in favor of device code/PKCE), and "Signed Agent Cards" for cryptographic agent-identity verification — independently corroborated by A2A's own blog post and by GitHub's real, tagged release history (`v1.0.0` tagged 2026-03-12, `v1.0.1` patch 2026-05-26). The Linux Foundation (A2A's governance body) claims more than 150 supporting organizations as of April 2026, up from 50+ a year earlier — a real, dated figure, but self-reported with no cited audit methodology (unlike the same release's separately-verifiable 22,000 GitHub-stars metric), so it should be weighted as adopter-count marketing, not an audited registry. Concretely (not just announced), AWS added A2A support to Amazon Bedrock AgentCore Runtime — confirmed via AWS's own current devguide (a transparent proxy layer with Agent Card discovery, SigV4/OAuth2.0 auth, VPC/PrivateLink support) that has been GA since October 2025 and continued to receive feature investment as recently as March 2026 — and Microsoft built A2A into both Azure AI Foundry and Copilot Studio, confirmed via Microsoft's own current Learn docs, where A2A sits as a first-class shipped connector type alongside other production connectors, not a roadmap placeholder.

**Why it matters for Kelvran specifically:** if Kelvran ever revisits A2A specifically (distinct from MCP), the protocol itself is in a meaningfully more settled state than MCP's six-week-old core re-architecture — a stable v1.0 spec unchanged since March 2026, with two major cloud vendors' production runtimes built against it. This does not by itself justify building A2A support (no demand signal has been established for Kelvran specifically), but it means "A2A is too immature to build against" would be a weaker objection than the equivalent claim about MCP's current spec state.

**Confidence:** Medium-High (press release self-reported adopter count is lower quality on its own, but every specific technical claim — v1.0 stability, Signed Agent Cards, multi-tenancy, AWS/Microsoft integrations — was independently corroborated against each vendor's own primary technical documentation and GitHub's release history; votes ranged 2-1 to 3-0).

**Signal:** N/A for "build now" (no A2A demand signal exists for Kelvran) — but worth noting as a maturity baseline if A2A is ever prioritized: it would not face the same "spec just changed underneath us" risk that MCP does today.

### 4. Peer gateways have already answered the "read-only discovery vs. full brokering" question — production v1 scope is full bidirectional execution, gated behind an opt-in flag, not discovery-only

**What the research found:** LiteLLM's MCP gateway, when `require_approval` is set to `'never'`, "automatically executes the returned tool calls and feeds the results back into the model" before returning the assistant response — a full, provider-agnostic (OpenAI, Azure, Anthropic, Bedrock, Vertex, self-hosted) tool-call execution loop, confirmed directly in LiteLLM's raw docs HTML, not merely an AI-generated summary. This is the default-off, opt-in path: LiteLLM's actual default behavior (`require_approval` omitted or set to anything other than `'never'`) is to return MCP tool calls to the client for manual review and execution — i.e., LiteLLM ships *both* the read-only-discovery mode and the full-brokering mode, with discovery-first as the safer default. Notably, this feature is not labeled beta/experimental in the docs (only a separate, unrelated Python SDK helper carries that label), yet cross-referencing LiteLLM's own GitHub repository turned up multiple real, recent (Jul–Sep 2026) bug-fix PRs specifically targeting this auto-execute loop — duplicate messages in non-streaming follow-ups, suppressed intermediate tool-call turns in streaming, stream-lifecycle issues across auto-execute rounds. That is qualifying evidence the feature is real and hit by production traffic (bugs get filed because it's used), but also that even the most mature, most-documented peer implementation of full bidirectional brokering still has live rough edges roughly a year after MCP tool-calling became mainstream.

**Why it matters for Kelvran specifically:** this is the direct, evidence-backed answer to research question 5. The realistic v1 scope precedent is not "ship read-only tool discovery and stop" — production peers have moved past that and shipped genuine execute-and-feed-back brokering. But the safer, lower-risk entry point precedent is also clear and is what the market leader actually defaults to: ship discovery/return-to-client first (structurally simpler, avoids owning execution-failure semantics and the guardrail-for-results gap identified in Finding 6), and gate full auto-execution behind an explicit opt-in flag once the discovery path is proven, mirroring LiteLLM's own `require_approval` default. Given the rough edges LiteLLM itself still has in its auto-execute loop, a Kelvran v1 that matches LiteLLM's *default* (not its opt-in ceiling) is the defensible, lowest-risk scope — with full brokering as an explicitly flagged v1.1+ target once there's a concrete workload asking for it.

**Confidence:** High (primary vendor docs verified against raw HTML, cross-checked against GitHub's actual current issue/PR history for corroboration and for the "still has rough edges" qualifier).

**Signal:** `build_now` for the *scoping decision* (discovery-first, execution-gated-behind-a-flag is the validated, concrete v1 shape) — `not_yet` for shipping the full auto-execute loop as a default, given even LiteLLM's mature implementation has open bugs in it.

### 5. No peer extends its own gateway API key into the tool-call delegation credential — every implementation surveyed layers a distinct, separate credential-exchange mechanism instead, confirming Kelvran's virtual-key model does not extend cleanly on its own

**What the research found, synthesizing five closely related, independently-verified claims:**

- **LiteLLM** authenticates the caller to the *proxy itself* via its existing virtual key (`x-litellm-api-key`) — that part maps cleanly onto Kelvran's existing model, no new concept needed for admission. But for the *downstream MCP server* leg, LiteLLM layers one of five distinct `auth_type` patterns on top: `authorization_code`/PKCE for interactive user clients, `client_credentials` for machine-to-machine, `oauth2_token_exchange` (On-Behalf-Of, per RFC 8693) for delegated user identity, `true_passthrough` (forward the client's `Authorization` verbatim, no LiteLLM admission), and `oauth_delegate`. This lives in a dedicated `outbound_credentials` module in LiteLLM's own source, structurally separate from the virtual-key/API-key code path — confirmed via LiteLLM's actual GitHub source (`litellm/types/mcp.py`, `litellm/proxy/_experimental/mcp_server/outbound_credentials/adapter.py`), not just docs prose.
- The **OBO (On-Behalf-Of)** flow specifically requires *two* distinct credentials simultaneously on the same MCP call: the LiteLLM virtual key (via the separate `x-litellm-api-key` header, which "plays no role in the OBO exchange") and the end-user's own OAuth bearer token (via `Authorization`, used as the `subject_token` in an RFC 8693 token-exchange call to the identity provider). LiteLLM's own docs anticipate the header-collision problem directly: "If the MCP client can only send one Authorization header, use `x-litellm-api-key` for the LiteLLM key and reserve `Authorization` for the user's token." The explicit design intent is to avoid forwarding the user's raw token to the MCP server at all — LiteLLM "forwards only the exchanged scoped token."
- **Portkey**'s MCP Gateway takes a differently-shaped but structurally analogous approach: a single client-facing API key (or IdP token) authenticates each tool call to Portkey, which then *injects* the appropriate upstream credential for the target server — OAuth tokens for services like GitHub/Slack, API keys for public servers, or identity headers for internal servers — rather than exposing raw upstream credentials to the calling agent at all. Admins configure these per-server credentials centrally; callers never see or supply them directly.

**Why it matters for Kelvran specifically:** this is the direct, now well-corroborated answer to research question 2. Kelvran's existing virtual-key model extends cleanly for exactly one leg — admitting the caller to the gateway — the same way it already does for chat completions. It does **not** extend into the tool-call delegation credential itself; every peer surveyed independently arrived at a *separate* credential concept for the gateway→downstream-MCP-server leg (LiteLLM: five distinct `auth_type`s plus an OBO/RFC-8693 exchange; Portkey: centrally-configured per-server credential injection keyed off, but distinct from, the client-facing key). This converges with — and sharpens — the 2026-09-07 report's spec-level finding that naive token passthrough is normatively forbidden (confused-deputy problem, RFC 8707 audience binding): the *practical* peer-implementation answer to that constraint is consistently "add a credential-mapping/exchange layer," not "route around the constraint," and not "reuse the caller's own gateway key as-is downstream."

**Confidence:** High (LiteLLM's claims verified against both its own docs and its actual, current GitHub source code including dedicated tests; Portkey's claim verified against its own current primary docs with no contradicting evidence found; votes ranged 2-1 to 3-0 across the cluster).

**Signal:** `not_yet` for building the full delegation mechanism (needs a concrete target MCP server / credential type to design against) — but `build_now` for the scoping decision itself: any MCP RFC Kelvran writes should assume from the start that outbound tool-call credentials are a **new, distinct concept** layered alongside (not derived from) the existing virtual-key `Verifier`, matching the unanimous peer pattern. Designing the RFC as if the virtual key would simply "flow through" would contradict every surveyed implementation and the MCP spec's own normative prohibition.

### 6. Guardrail scanning of MCP tool-call *results* is not a documented peer pattern anywhere found — Kelvran's own role-agnostic scan design is not shown to diverge from real-world practice; if anything, peer docs don't show an equivalent capability at all

**What the research found:** LiteLLM's dedicated MCP Guardrails documentation defines exactly two guardrail execution modes for MCP tool calls: `pre_mcp_call` ("Run before MCP call, on input") and `during_mcp_call` ("real-time monitoring and intervention" during execution). The page's only worked configuration and walkthrough examples — PII detection/masking for credit cards, emails, phone numbers, SSNs — apply exclusively to outbound request/tool-call-input content (a user message containing a credit card number, a phone number in a request payload); none of the documented examples demonstrate scanning data *returned by* a tool call before it re-enters the conversation. A raw-HTML grep for `post_mcp_call`, `mcp_response`, `tool.result`, or `tool.output` on the page, and a GitHub code search for `post_mcp_call` in LiteLLM's own source, both returned zero matches.

**Why it matters for Kelvran specifically:** this is the direct answer to research question 3. There is no confirmed peer precedent — positive or negative — for a distinct "scan the tool-call result before feeding it back to the model" guardrail mode; the most detailed MCP-guardrails documentation found describes only input-side scanning. This means Kelvran's own already-verified design (role-agnostic guardrail scanning that operates over the full serialized message set via `serializeMessages`' JSON marshal, and therefore structurally covers a future "tool" role's returned content the same way it covers any other message) is not shown to be behind or diverging from real-world practice — no competitor's *documented* feature set demonstrates doing this explicitly either. If anything, Kelvran's architecture-level answer (one role-agnostic scan layer, not per-role or per-call-type carve-outs) may be ahead of what any surveyed competitor has published, though this should be read cautiously (see caveat below) — absence of a documented mode is not proof no competitor has quietly shipped one.

**Confidence:** Medium. The narrow, precisely-scoped claim (worked examples are input-only) is high-confidence and unanimous (3-0), verified against both raw docs HTML and a GitHub code search. A related but more sweepingly-worded claim — asserting flatly that *no* result-scanning mode exists in LiteLLM's guardrails feature at all — was separately proposed and **refuted** (0-3) in this same research pass; the distinction matters (see caveats) and the weaker, better-scoped claim is what should be relied on.

**Signal:** `build_now` for continuing to trust and rely on Kelvran's existing role-agnostic scan design for this use case — no peer evidence contradicts it, and no re-architecture is indicated by this finding. Re-verify this specific question (peer result-scanning support) once/if MCP-specific tool-call traffic is actually flowing through Kelvral in production, since documentation gaps are weaker evidence than a live product-behavior test.

### 7. Whether existing fallback-chain/circuit-breaker infrastructure generalizes to tool-call reliability is an unanswered question in this research pass — a genuine gap, not a negative finding

**What the research found:** Zero claims addressing tool-call-specific resilience, retry semantics, circuit-breaking, or fallback-chain applicability to MCP tool calls survived adversarial verification in this pass, and none were even proposed and refuted (unlike the A2A gap in the 2026-09-07 report, which had zero proposed claims at all — same shape of gap here for research question 4 specifically).

**Why it matters for Kelvran specifically:** research question 4 asked directly whether Kelvran's existing fallback-chain/circuit-breaker infrastructure (error-classified multi-hop fallback, per-request circuit breaker, backoff/recovery-ramp) generalizes to tool-call reliability, or whether tool-call brokering needs its own distinct resilience model. This pass cannot answer that either way. This is a real, load-bearing open question for any future MCP RFC: a chat-completion fallback (retry against a different model/provider) and a tool-call failure (the specific downstream MCP server is down, or the specific tool errored, or the tool succeeded but returned a semantically-wrong result) are not obviously the same failure class, and it would be a mistake to assume Kelvran's existing router-level fallback logic transfers unmodified without a dedicated research pass or design exercise confirming it.

**Confidence:** N/A — negative/absent finding, not a positive claim with a confidence level.

**Signal:** Explicitly flagged as unresolved — do not build tool-call resilience logic by silently reusing router-fallback code paths without a dedicated design pass first.

## Recommendation, mapped to the five research questions

1. **Spec stability / right time to build?** → **`not_yet`.** The 2026-07-28 stateless re-architecture is six weeks old, self-described by MCP's own maintainers as carrying real breaking-change migration cost, and even a mainstream Go SDK (`mcp-go`) is still actively adding version-gate machinery for it. Authorization itself remains optional, transport-scoped, and dependent on an unratified OAuth 2.1 draft. Trigger to revisit: the 12-month HTTP+SSE deprecation window closing without further structural churn, or two consecutive spec revisions with no new removed/deprecated methods.
2. **Auth/credential model — does the virtual-key model extend cleanly?** → **No, not on its own — `not_yet` for the full mechanism, `build_now` for the scoping decision.** Every peer surveyed (LiteLLM, Portkey) keeps the existing gateway-key/virtual-key model for caller→gateway admission unchanged, but layers a wholly separate, new credential-delegation concept (OAuth token exchange, per-server credential injection, or explicit passthrough) for the gateway→downstream-MCP-server leg. Any Kelvran MCP RFC should be scoped around a new, distinct outbound-credential abstraction from the outset, not an extension of `Verifier.Verify`.
3. **Guardrail scanning of tool-call results — match or diverge from real-world practice?** → **Not shown to diverge — `build_now` (i.e., keep current design, no changes indicated).** No peer documentation demonstrates an explicit result-scanning guardrail mode; Kelvran's existing role-agnostic full-message scan is not contradicted by anything found and may already structurally cover this case ahead of documented peer practice. Re-verify once real MCP traffic exists in Kelvran, since this is a documentation-gap-based finding, not a live-behavior test.
4. **Does existing resilience infrastructure generalize to tool calls?** → **Unresolved — genuine research gap**, not answered either way. Needs its own dedicated research or design pass before any MCP RFC assumes router-fallback code paths transfer to tool-call failures unmodified.
5. **Realistic v1 scope?** → **`build_now` for the scoping decision, `not_yet` for full auto-execution as a default.** The validated peer pattern (LiteLLM) is discovery/return-to-client as the default, with full auto-execute-and-feed-back gated behind an explicit opt-in — and even that mature, opt-in path still has open bugs in production. A Kelvran v1 that mirrors LiteLLM's *default* (not its ceiling) is the defensible scope; full bidirectional brokering is a later, explicitly-flagged target once there is a concrete workload asking for it.

**Overall:** MCP/A2A brokering remains correctly out of scope for v1 per `PRD.md`, and this pass reinforces rather than overturns that call — not because the market thesis is wrong (the 2026-09-07 report's dollar-cost-accounting-for-tool-execution gap is still real and still unsolved by any competitor, and this pass found nothing to contradict that), but because the ground itself (the spec's stateless core, its own OAuth dependency) is still moving underneath any implementation choice, and two of the five research questions this pass was tasked with (tool-call resilience model, and the deeper "should Kelvran build this at all" cost-accounting question from the prior report) remain genuinely open. The one piece of this research that *is* settled enough to act on now, without waiting on spec stability, is the **scoping/design-decision** layer: if and when a concrete demand signal justifies starting an MCP RFC, it should be scoped from day one around (a) a new, distinct outbound-credential-delegation concept, not a virtual-key extension, and (b) discovery-first with execution gated behind an explicit flag, not full bidirectional brokering as the default — both are now evidence-backed, not guesses.

## Caveats

- **Finding 6's evidence has an internal tension worth flagging explicitly.** The narrow claim ("LiteLLM's *worked examples* only cover input-scanning") survived 3-0. A more sweepingly-worded claim asserting flatly that *no* result-scanning mode exists in LiteLLM's guardrails feature *at all* was proposed and refuted 0-3 in the same pass. This is not necessarily a contradiction — it likely reflects that the broader claim overreached into an unverifiable universal negative ("nowhere in the codebase") while the narrower claim about documented examples held up — but it means this report's confidence that "no peer scans tool-call results" should be read as "not demonstrated in the documentation examined," not as a confirmed absence across LiteLLM's entire codebase or config surface.
- **A2A's 150+-organization adoption figure is self-reported** by the Linux Foundation (A2A's own governance body) with no cited audit methodology, unlike the same press release's independently-verifiable GitHub-stars figure. Treat it as a real but promoter-issued number, not an audited registry.
- **Time-sensitivity is unusually high for this report specifically.** The MCP spec moved through a major structural revision only six weeks before this research date, and its own maintainers frame the change as still generating migration-cost feedback from the ecosystem. Any conclusion in this report about "current" spec behavior should be re-checked before actual implementation begins, not treated as a stable target — more so than is typical for a research pass with this report's nominal shelf life.
- **This pass did not re-verify the 2026-09-07 report's core competitor-governance and dollar-cost-accounting findings** (Kong, Envoy AI Gateway, the confused-deputy/RFC 8707 analysis under the 2025-06-18 spec) — those stand as previously verified and are treated as ground truth here, not re-litigated. Where this pass's findings sharpen or extend them (Finding 5 vs. the prior report's Finding 2/3), that relationship is called out explicitly; elsewhere, assume no change.
- **Tavily/Exa web-search rate limits were hit repeatedly during the underlying verification work** (noted across several individual claims), meaning some corroboration relied on primary-source direct fetches and GitHub code search rather than a broader web sweep. This is generally a *stronger* form of evidence for the specific claims it was used on (primary source > secondary aggregator), but it does mean the overall search coverage for contradicting evidence was narrower than an unconstrained sweep would have provided.
- **No claims on Bifrost, TensorZero, Helicone, Kong, or Envoy's MCP support were part of this pass's surviving set** (Kong and Envoy were covered in the 2026-09-07 predecessor report instead) — their absence here reflects this pass's narrower LiteLLM/Portkey/mcp-go/spec focus, not a finding that they lack MCP support.
