# OpenAI API Surface Gap — Tier-1 Comparison and Next-Tier Prioritization

**Date:** 2026-09-20
**Scope:** `gateway/cmd/gateway/main.go` (confirmed data-plane route table), `gateway/internal/gateway/dataplane/dataplane.go` (`Pipeline.HandleChatCompletion`/`Pipeline.HandleEmbeddings`), `gateway/internal/adapter/types.go` (canonical schema + `Adapter`/`EmbeddingAdapter` interfaces), `gateway/internal/costaccounting`, `gateway/ARCHITECTURE.md`. Confirmed by direct code inspection: `cmd/gateway/main.go` registers exactly two data-plane routes — `mux.HandleFunc("/v1/chat/completions", ...)` and `mux.HandleFunc("/v1/embeddings", ...)` — plus `/healthz` and a large `/admin/*` control-plane surface (`internal/admin/admin.go`, 15+ routes: virtual keys, prompts, backup, deployment weights, cache erase, pprof). **This is a material change since `docs/upgrade-research/api-surface-expansion-2026-09-15.md`**, which found zero non-chat routes: `/v1/embeddings` shipped 2026-09-17 (`gateway/ARCHITECTURE.md`'s own "Added 2026-09-17" note, confirmed against `adapter.EmbeddingRequest`/`EmbeddingResponse`/`EmbeddingAdapter` in `types.go` and `Pipeline.HandleEmbeddings` in `dataplane.go`) — via OpenAI and Bedrock adapters only, Gemini deferred, Anthropic skipped (no native embeddings model). This report treats that shipped feature as the concrete precedent/template for ranking the next tier, not as a hypothetical pattern to copy.
**Method:** Primary-source research directly against OpenAI's own current API reference and guides. `platform.openai.com/docs/api-reference/*` now returns HTTP 403 to automated fetches; all primary-source claims below were retrieved after following that host's own 301 redirect to `developers.openai.com/api/docs/...`, confirmed live and current as of this report's date, not from a cached or secondary source. `openai.com/api/pricing/` also 403'd — Moderations pricing is explicitly flagged unverified below, not asserted. Cross-referenced against this repo's own `api-surface-expansion-2026-09-15.md` (Batch/Fine-tuning/Files/Assistants/Responses) and `gateway-batch-api-2026-09-13.md` (Batch architecture) — those reports' architectural conclusions are cited, not re-derived, except where this pass's fresh primary-source fetch corrects or updates a specific factual claim they made.

## Executive Summary

OpenAI's non-chat API surface in 2026 splits cleanly into three buckets relative to Kelvran's now-real Embeddings precedent. **Confirmed dead:** the Assistants API, officially sunset 2026-08-26, with no ambiguity — OpenAI's own migration guide states it plainly and directs new integrations to Responses + Prompts + Conversations instead; any Kelvran roadmap language still mentioning Assistants is stale. **Confirmed active, not deprecated, but architecturally blocked by the same persistent-state gap `gateway-batch-api-2026-09-13.md` already priced out:** Batch, Fine-tuning, and Files — all three are genuinely current products with no sunset signal, and this pass corrects one specific factual gap in that prior report: the 50% Batch discount claim, which an earlier adversarial-verification pass explicitly *refuted* (0-3) as unconfirmed, is now directly confirmed from OpenAI's own current Batch guide ("50% cost discount compared to synchronous APIs") — a real, live economic fact, not evidence of a demand signal. **The one surface whose calculus has genuinely shifted since the 2026-09-15 report:** the Responses API. It is no longer just "OpenAI's eventual successor" in the abstract — OpenAI's own current migration guide states outright that Chat Completions "remains supported" but Responses "is recommended for all new projects," backed by concrete claims (a 3% SWE-bench improvement, 40-80% better cache-hit rates, an agentic multi-tool-call loop) and a hard forward-compatibility wall: starting with GPT-5.4, Chat Completions does not support tool calling with non-default `reasoning_effort` values at all — Responses does. Structurally, a Responses adapter would reuse Kelvran's own real, shipped precedent (`EmbeddingAdapter`'s deliberately-separate-interface, additive-canonical-type, own-pipeline-function pattern) but at a materially larger schema surface than Embeddings' simple vector array, since Responses' output is a polymorphic list of message/function_call/tool_call/computer_use/mcp/code_interpreter/image_generation items — and its stateless (`store: false`) mode maps directly onto infrastructure Kelvran already built and hardened for a different provider's different feature (`adapter.Message.ReasoningBlocks`' opaque `Redacted`/`Data` round-tripping for Anthropic/Bedrock). Moderation and Realtime remain the weakest candidates for the reasons the prior reports already established (duplicative with Kelvran's own guardrail engine; genuinely new persistent bidirectional session-state architecture, respectively) — this pass only refreshes their current-status facts (Moderations: 4 live models, `omni-moderation-latest` primary, pricing still unverified; Realtime: confirmed GA, not beta, as of this fetch) without re-deriving either's settled `not_yet`.

## Findings

### Finding 1 — The gateway's real route surface as of 2026-09-20, and why this report's premise differs from the 2026-09-15 report's
**Confidence: high** (direct code inspection)

`cmd/gateway/main.go` lines 396-398 register exactly `/v1/chat/completions`, `/v1/embeddings`, and `/healthz` as data-plane routes; `internal/admin/admin.go` separately registers the control-plane surface (virtual keys, prompts CRUD + versioning + labels, backup, per-deployment weight updates, cache erase, conditional pprof debug routes) — none of it data-plane traffic in the sense this report cares about. This confirms the task's own premise: Kelvran now proxies `/v1/embeddings` for real (shipped 2026-09-17, three days after `api-surface-expansion-2026-09-15.md` was written and explicitly stated "there is no ... `/v1/embeddings` ... route anywhere in this codebase"), via `openai` and `bedrock` adapters implementing a deliberately separate `adapter.EmbeddingAdapter` interface (`ToEmbeddingProvider`/`FromEmbeddingProvider`), never an extension of the existing `Adapter` interface, per `types.go`'s own doc comment explaining why (Anthropic has no native embeddings model at all; forcing every provider package to implement a capability it doesn't have would mean dummy/panicking implementations).

Reading `Pipeline.HandleEmbeddings` and `ARCHITECTURE.md`'s own 2026-09-17 correction together yields the exact scoping decision this codebase already made once for a non-chat surface, and the template this report uses to evaluate every candidate below: `HandleEmbeddings` reuses only the budget/rate-limit/guardrail primitives and a plain (non-sticky) `nextDeployment` pick — it explicitly does **not** thread through cache, idempotency, the per-identity concurrency cap, fallback chains, or telemetry spans. `costaccounting.Calculator.Calculate` required zero changes, because `EmbeddingResponse.Usage.CompletionTokens` is simply always zero, priced at the model's ordinary `PromptPerToken` rate.

**build_now / not_yet:** N/A — this finding is the report's scope correction and its methodological template, not a build decision on its own.

### Finding 2 — Assistants API: confirmed fully retired, no ambiguity, and its replacement bundle (Responses + Prompts + Conversations) is itself already shedding one piece
**Confidence: high** (primary source, direct fetch of OpenAI's current migration guide)

OpenAI's own migration guide (`developers.openai.com/api/docs/assistants/migration`, reached via `platform.openai.com`'s 301 redirect) states without qualification: "The Assistants API was officially sunset on August 26, 2026, and is no longer available." This matches and reconfirms `api-surface-expansion-2026-09-15.md`'s Finding 6 exactly — no new information here beyond independent reconfirmation five days later. The migration path OpenAI documents: recreate each Assistant's instructions/tools bundle as a **Prompt** (dashboard-only creation now — Prompts can no longer be created via API), store the prompt ID in source control, start new interactions via the **Conversations** API paired with **Responses**, and pull any needed prior thread history from the caller's own application storage since the old thread-message-retrieval endpoint no longer works at all.

One new wrinkle this pass surfaced that the prior report didn't have: OpenAI's own guide flags that the reusable **Prompt** object itself — the very construct it just told developers to migrate Assistants *into* — is separately on its own deprecation timeline, with the guide explicitly recommending developers "check the prompts deprecation timeline before relying on that object type for long-lived integrations." This is a genuinely fast-moving part of OpenAI's surface right now; nothing in this repo should treat "Prompts" as a stable long-term target either, mirroring the same posture the prior report already took toward Assistants itself.

**build_now / not_yet:** N/A — dead API, no build decision applies. Action item: confirm no internal roadmap doc still references Assistants (the prior report already flagged this; this is independent reconfirmation that the correction still holds).

### Finding 3 — The Responses API: the one candidate whose value case has materially strengthened since the last pass, backed by a genuine forward-compatibility pressure point, not just OpenAI's own preference
**Confidence: high** for the primary-source claims (direct fetch of OpenAI's current migration/comparison guide and the Chat Completions reference page's own banner); **medium** for the ReasoningBlocks-reuse and schema-cost synthesis, since that is this report's own architectural read of `types.go`, not an externally-sourced claim

OpenAI's `chat` reference page (`developers.openai.com/api/docs/api-reference/chat`) now carries a banner reading exactly: "Starting a new project? We recommend trying Responses to take advantage of the latest OpenAI platform features." The dedicated migration guide is more explicit still: "While Chat Completions remains supported, Responses is recommended for all new projects," immediately followed by "Chat Completions remains supported, so you can migrate one user flow at a time" — i.e. genuinely not deprecated, but unambiguously steered away from for anything new. Concrete claims backing that steer, all sourced from the same guide: an internal "3% improvement in SWE-bench with same prompt and setup" for reasoning models; a "40% to 80% improvement" in cache utilization versus Chat Completions in OpenAI's own internal testing; an agentic-loop design letting one request chain multiple tool calls (web search, code interpreter, custom functions) server-side; `store: true` plus `previous_response_id` for stateful context chaining without caller-side history management; encrypted-reasoning content enabling a fully stateless (`store: false`) mode compatible with Zero Data Retention; and an `output_text` SDK convenience helper with structured typed streaming events rather than raw deltas.

**The genuinely new pressure point this pass found, not present in the 2026-09-15 report's framing:** the same guide states that starting with GPT-5.4, "Chat Completions does not support tool calling with `reasoning_effort` values other than `none`" — Responses handles this natively. This is not a soft preference; it is a real, model-version-gated functionality gap that only widens as OpenAI ships newer reasoning models. Any Kelvran customer wanting current-generation tool-calling-plus-reasoning behavior from OpenAI specifically will, at some point, need a request shape Chat Completions cannot express at all — a materially stronger version of the "successor" framing than "OpenAI would simply prefer this."

**Structural cost, read against this repo's own shipped Embeddings template (Finding 1):** a Responses adapter would follow the same additive shape — its own canonical request/response type, its own `Adapter`-shaped interface (`ToResponseProvider`/`FromResponseProvider` or equivalent), its own pipeline function alongside (not inside) `HandleChatCompletion` — but the schema itself is categorically larger than Embeddings'. `EmbeddingResponse.Data` is a flat array of float64 vectors; a `Response` object's output is a polymorphic list of item types (message, function_call, tool_call, computer_use action, MCP tool call/approval/list-tools result, code interpreter, image generation) — this is closer in shape and cost to building a second full chat-completions-equivalent canonical schema than to bolting on a narrow additive feature. One genuine cost mitigation this report can state with medium confidence: Responses' stateless (`store: false`) mode requires the caller to store and replay opaque, provider-issued encrypted reasoning content verbatim on the next turn — mechanically the same round-tripping contract `adapter.Message.ReasoningBlocks`' `Redacted`/`Data` fields already implement today for Anthropic/Bedrock's Claude Messages API (per `ARCHITECTURE.md`'s reasoning-content normalization section, independently confirmed in the 2026-09-15 report's own Finding 6) — a real, already-hardened head start for that specific slice of the work, not the whole surface.

What a Kelvran Responses proxy would and would not deliver, honestly scoped: proxying the outer call is feasible and would give real "drop-in existing-SDK compatibility" specifically to callers already using OpenAI's `client.responses.create()` SDK surface — a growing population given the pressure above — but Responses' actual differentiator (server-side agentic tool execution within a single request) happens entirely inside OpenAI's own black box; Kelvran's cache/budget/guardrail checks would wrap the outer request/response exactly as they do today, gaining no additional guarantee over an unproxied direct call — the same "thin passthrough adds centralized auth/audit but no incremental product guarantee" conclusion `gateway-batch-api-2026-09-13.md` reached about Batch.

**build_now / not_yet:** `not_yet` for a full, general Responses adapter (schema cost is real and non-trivial, and this pass still found no confirmed Kelvran customer demand signal). **Escalating toward `build_now`-eligible for a scoped RFC specifically**, more so than the 2026-09-15 report's flat `not_yet` — the GPT-5.4 tool-calling gap is a concrete, dated forward-compatibility trigger, not a hypothetical one, and if pursued the cheapest entry point mirrors Batch's own established precedent: an OpenAI-only, largely-passthrough `/v1/responses` route (auth/routing/budget only, minimal translation) rather than attempting cross-provider Responses-shaped normalization on day one.

### Finding 4 — Batch, Fine-tuning, and Files: all three confirmed current and undeprecated; one specific prior "unverified" claim is now confirmed, but the architectural blocker is unchanged
**Confidence: high** (primary source, direct fetch of OpenAI's current guides/references for all three)

**Batch** (`developers.openai.com/api/docs/guides/batch` and `.../api-reference/batch`): confirmed active with no deprecation language anywhere on either page. Request shape: `input_file_id` (a Files-API upload with `purpose: batch`, up to 50,000 requests / 200 MB), `endpoint` (one of eight targets, explicitly including `"/v1/responses"`, `"/v1/chat/completions"`, and `"/v1/embeddings"` — i.e. OpenAI's own Batch API can batch over the exact same two canonical surfaces Kelvran itself now exposes, plus the one from Finding 3), and a `completion_window` that "can only be set to `24h`" today. Response: a `Batch` object cycling through `validating`/`in_progress`/`finalizing`/`completed`/`expired`/`cancelling`/`cancelled`, with a `usage` object "only populated on batches created after September 7, 2025." **Correction to `gateway-batch-api-2026-09-13.md`'s own stated uncertainty:** that report's Caveats section explicitly logged "a claim that OpenAI's Batch API offers a 50% cost discount was proposed and refuted (0-3)" and its Finding 3 stated the discount figure was "low/unverified — do not cite ... without independent re-verification." This pass did exactly that re-verification, directly against OpenAI's current Batch guide, which states plainly: "50% cost discount compared to synchronous APIs." Record this as a confirmed correction — the discount is real, current, and citable — while noting this changes only the *economic-incentive* half of that report's analysis, not its architectural conclusion (Finding 5 of that report: real gateway-side job tracking without caller-side polling needs a persistent queue/poller Kelvran doesn't have) — that conclusion is unaffected and not re-derived here.

**Fine-tuning** (`.../api-reference/fine-tuning`): confirmed active, no deprecation notice for the API as a whole. Supports supervised, DPO, and reinforcement (grader-scored, still "Alpha") training methods; only the top-level `hyperparameters` field is explicitly marked deprecated in favor of a newer `method` object — a field-level, not API-level, deprecation. Job lifecycle (`create`/`cancel`, list/retrieve referenced by ID) is unchanged from what `api-surface-expansion-2026-09-15.md`'s Finding 5 already characterized as "the same persistent-state cost" as Batch — not re-derived here.

**Files** (`.../api-reference/files`): confirmed active and structurally central — its `purpose` field spans `assistants`/`assistants_output`/`batch`/`batch_output`/`fine-tune`/`fine-tune-results`/`vision`/`user_data`. One fact worth flagging that neither prior report had, since Assistants only sunset three weeks after the 2026-09-15 report: two of those eight `purpose` values (`assistants`/`assistants_output`) now point at a dead API (Finding 2) — any future Files-consuming feature in Kelvran should treat those two purposes as legacy-only, not as a live integration target, leaving `batch`, `fine-tune`/`fine-tune-results`, `vision`, and `user_data` as the only purposes with a real current consumer. Only two metadata *fields* (`status`, `status_details`) are marked deprecated, not the API itself.

**build_now / not_yet:** `not_yet` for all three, unchanged from both prior reports' reasoning (persistent-state cost for Batch/Fine-tuning per `gateway-batch-api-2026-09-13.md`; Files has no standalone value absent a consuming feature per `api-surface-expansion-2026-09-15.md` Finding 5). The one thing this pass changes is confidence in the *economic* case for Batch specifically (50% discount now confirmed, not refuted) — record this fact for whenever a demand signal does appear, but it is not itself a demand signal.

### Finding 5 — Moderations and Realtime: current-status refresh only: confirmed active, current model/transport facts recorded, prior reports' settled `not_yet` verdicts not re-litigated
**Confidence: high** for the primary-source facts; **N/A** for the build verdicts, which this report deliberately does not re-derive

**Moderations** (`.../api-reference/moderations`): confirmed active, accepts a single string, array of strings, or mixed text+image objects; returns `flagged`/`categories` (13 categories)/`category_scores`/`category_applied_input_types`. Four named models: `omni-moderation-latest`, `omni-moderation-2024-09-26` (the current multimodal generation), and legacy `text-moderation-latest`/`text-moderation-stable`. **Pricing remains unverified in this pass** — the API reference page states no cost information at all, and a direct fetch of `openai.com/api/pricing/` returned HTTP 403; this repeats, rather than resolves, `api-surface-expansion-2026-09-15.md`'s identical caveat. This report does not re-derive that prior report's Finding 3 (duplicative with Kelvran's own `guardrail.Engine`, which already takes a plain decoupled string and would generalize to this for free with zero new abstraction) — that reasoning is unchanged and still governs the `not_yet` call.

**Realtime** (`.../api-reference/realtime` and `.../guides/realtime`): confirmed as an event-based (not request/response) API over WebSocket, WebRTC, and SIP transports, supporting audio/text/image multimodal exchange, voice activity detection (including a newer semantic-VAD "turn detection model"), and MCP tool integration with human-in-the-loop approval workflows. **Confirmed GA, not beta** — the current guide has a dedicated section instructing developers to "migrate it to the GA interface before moving forward with new work" and to drop the old beta header, and multiple current-generation transcription models (`gpt-4o-transcribe`, `gpt-realtime-whisper`) are listed as live. Whether this GA status is new since `gateway-realtime-multimodal-2026-09-13.md`'s own research date or was already true then is **not established by this pass** — that report is not re-opened here per this task's own explicit scope instruction, and this fact is recorded as a fresh current-status data point, not as a claimed change. OpenAI's own recommended use case is unchanged from what a realtime-voice feature would always require: "conversational and immediate" speech-to-speech interaction with barge-in and low first-audio latency — a persistent bidirectional session shape, not a synchronous request Kelvran's existing pipeline stages have any precedent for.

**build_now / not_yet:** `not_yet` for both, inherited unchanged from the cited prior reports. No new information in this pass changes either verdict.
