# Kelvran Evals — 2026 Upgrade Research & Prioritized Roadmap

**Date:** 2026-09-06
**Scope:** `evals/` — sandboxed agent-rollout execution, LLM-judge scoring, statistics, harness-transparent reporting. Never sits in the request path.
**Method:** Adversarial multi-source research (3-vote verification per claim) against real 2026 eval-system practice: Inspect AI (UK AISI), DeepEval, Braintrust, promptfoo, plus the PoLL panel-of-judges paper. Every recommendation below is checked against Kelvran's own already-made, already-documented decisions (`PRD.md`, `ARCHITECTURE.md`, `DECISIONS.md`, `STATUS.md`) so this doesn't re-litigate settled calls without new evidence.

---

## Executive summary

The single highest-leverage, lowest-risk move is wiring the CI gate that already exists (`evals report --fail-under`) into `.github/workflows/ci.yml` — verified directly against the live pipeline, the `evals` job today only runs `ruff`, `lint-imports`, and `pytest tests/`; there is no `evals run && evals report --fail-under` step anywhere. Every comparable platform (promptfoo, DeepEval) treats a CI pass/fail gate as first-class, so this isn't a stretch — it's closing Kelvran's own gap between mechanism and deployment. The second-highest-leverage move is designing the judge-panel aggregation interface now, even though building the panel itself is a deliberate v2 non-goal: Inspect AI's `multi_scorer()` (majority/mode reducers, `score.metadata.panel`, `krippendorff_alpha` for inter-judge agreement) is a concrete, battle-tested prior-art design Kelvran can crib from cheaply while the interface is still greenfield — waiting until v2 to think about this means retrofitting `judge()`'s single-`call_model`-callable signature and `Score.scorer_type`'s closed `Literal` later, which is strictly more expensive than typing it correctly once, now. Third: the twice-parked bootstrap/Bayesian-stats backlog item is **reaffirmed, not overturned** — no source found in this research identifies a concrete gap that Wilson CIs + mSPRT leave uncovered for Kelvran's current usage pattern (offline, single-model, per-case regression testing), and the project's own audit language ("no real usage to analyze yet") still matches every comparable platform's actual practice, none of which ship bootstrap/Bayesian eval-stats as a *default* gating mechanism either. Fourth: Kelvran's fully-manual `evals promote` is not an outlier — it matches Braintrust's own documented, human-gated trace-to-dataset workflow, which explicitly names "copying a trace without filling in `expected`" as the single most common anti-pattern; automating that step away would remove exactly the judgment step other platforms deliberately keep human.

## Findings, ranked

### 1. Wire the existing `--fail-under` gate into CI (Small)

**What:** `evals report --fail-under <threshold>` already exists, already gates on the Wilson **lower bound** (not the point estimate — verified via `DECISIONS.md`'s `test_report_fail_under_gates_on_the_lower_bound_not_the_point_estimate`, and via direct inspection of `.github/workflows/ci.yml`, which today runs only `ruff`, `lint-imports`, and `uv run pytest tests/` — no `evals run`/`evals report` step exists in the pipeline at all). This is a real, already-built mechanism with zero engineering left except wiring it into a workflow step.

**Why it matters for Kelvran specifically:** This is explicitly named in the research brief as "a real, easy next step that hasn't been taken." It is the only recommendation in this report requiring no new design work — the gate, its lower-bound semantics, and its test suite already exist and are already documented as correct.

**Consistent with settled decisions?** Yes, directly extends `docs/rfcs/2026-09-05-evals-report-fail-under.md` and closes the exact gap named in `DECISIONS.md`'s 2026-09-05 entry ("mechanism exists and is tested, not yet wired into this repo's own CI").

**2026 best practice grounding:** Both promptfoo and DeepEval treat CI gating as a first-class, documented feature, not an afterthought:
- Promptfoo's documented CI pattern computes `successes / (successes + failures) * 100` and fails the build below a threshold via `jq`/`bc`, or fails on any `stats.failures > 0` (identical logic in both GitHub Actions and Jenkins examples) [promptfoo docs — confirmed 3-0].
- Promptfoo *also* documents gating beyond bare pass-rate: keyword-filtering error content (matching `security`/`injection` substrings) into a `criticalFailures` array that fails the build independently of overall pass rate [promptfoo docs — confirmed 3-0].
- DeepEval ships dedicated, first-class CI/CD tooling (`assert_test()`/`deepeval test run` via pytest/Vitest) explicitly distinct from ad-hoc dashboard review (`evaluate()`), with flaky-test handling (`LLMTestCase(flaky=True)`) so non-deterministic LLM-judge variance doesn't spuriously break builds, and an `--official` flag for marking CI runs as regression baselines [DeepEval docs — confirmed 3-0].

**What Kelvran should adopt cheaply, beyond the bare threshold, given what it already has:**
- **Regression-set-only gating**: since `evals promote --tier regression` already exists, the CI step should default to running against the frozen `regression` tier specifically (not the full case set), mirroring DeepEval's `--official` baseline-marking pattern — Kelvran doesn't need to build anything new for this, just choose which case set the CI invocation targets.
- **Keyword/category-scoped critical gating**: promptfoo's pattern of filtering on error substrings for a *separate*, stricter gate (independent of the bare `--fail-under` threshold) is directly portable to Kelvran's existing `Score`/`Run` schema — e.g., gate harder on cases tagged for safety/security scorers than on the aggregate pass rate.
- **Flaky-judge tolerance**: DeepEval's explicit `flaky=True` escape hatch is a cheap addition given Kelvran's judge is already non-deterministic by design (LLM judge) — worth a config flag before this bites someone in a real CI run.

**Effort:** Small — a workflow YAML step plus (optionally) a `--tier regression` default and a stricter secondary threshold for safety-tagged cases.

### 2. Design the multi-judge-panel *interface* now, even though the panel itself stays v2 (Medium)

**What:** `judge()` currently takes exactly one `call_model` callable; `Score.scorer_type` is a closed `Literal["deterministic", "llm_judge"]`. `PRD.md` itself frames a multi-judge skeptic panel as designed in from the start even though the panel is v2 — but the real code has no such interface today. Building the interface (not the panel) now is materially cheaper than retrofitting it after `judge()`'s signature and `Score`'s schema have more callers depending on the single-callable shape.

**Why it matters for Kelvran specifically:** This directly answers the research brief's open design question (independent-refutation vs. pairwise-comparison, panel-size/quorum rule) with concrete, already-shipped prior art rather than "research favors independent refutation" restated.

**Consistent with settled decisions?** Consistent with, and gives concrete shape to, `PRD.md`'s open item: "Whether the skeptic-panel protocol for Evals should be pairwise-comparison-based or independent-refutation-based (research favors independent refutation; final call deferred to the RFC that accompanies building it)." Does **not** reopen the "skeptic panel as default gate" v2 non-goal — this recommendation is scoped to interface design only, not shipping a panel as v1's default scoring path.

**2026 best practice grounding — concrete, not generic:**
- **PoLL (Panel of LLM evaluators)**: a panel of *smaller, cheaper* models from *disjoint model families* outperforms a single large judge, across three distinct judge settings and six different datasets — not a one-off finding — while being over seven times less expensive [arXiv:2404.18796, Verga et al., Cohere — confirmed 3-0]. This is independent-refutation in spirit: multiple disjoint models score independently and are aggregated, not compared pairwise.
- **Inspect AI's `multi_scorer()`** is the concrete, shipped implementation of exactly this pattern: run several independent LLM-judge scorers on the same sample, reduce via named reducer functions — `mode` (plurality), `majority` (>50% agreement — a literal quorum rule), or `collect` (preserve all values as a list) [inspect.aisi.org.uk/multiple-scorers.html — confirmed 3-0]. `model_graded_qa()` takes `model: list[str | Model] | str | Model | None` built on this same `multi_scorer()` utility, preserves individual votes in `score.metadata.panel`, and has explicit failure-mode handling (unscored sample if too few graders return a valid grade) [inspect.aisi.org.uk/scorers.html — confirmed 3-0].
- **Krippendorff's alpha for judge-panel reliability**: Inspect AI ships `krippendorff_alpha()` (nominal/ordinal/interval levels, compared against Scott's π and Fleiss' κ) specifically to measure agreement across judges when using the `collect` reducer [inspect.aisi.org.uk/metrics.html — confirmed 3-0, same source as `multi_scorer()`].
- **Contrast — DeepEval's Arena is a different problem**: DeepEval's multi-response comparison tooling (`Arena G-Eval`, `Arena Test Case`) is explicitly pairwise/comparative (blinded, randomized-position, n-pairwise judging producing a `winner`, not a score) — this is the *other* pattern PRD.md's open question names, and DeepEval's own docs frame it as an alternative to independent per-output scoring, not a variant of it [deepeval.com/docs/metrics-arena-g-eval — confirmed 3-0]. No independent-multi-judge-with-voting/ensemble feature exists anywhere else in DeepEval's metric catalog — it's Arena (pairwise) or nothing.

**Concrete starting design for Kelvran, if/when the v2 panel gets built:**
- Follow Inspect AI's shape: `judge()` → accepts `list[call_model]`, not one callable. `Score.scorer_type` gains a value (e.g., `"llm_judge_panel"`) rather than trying to overload `"llm_judge"`.
- Default reducer: **majority** (>50% quorum) — matches Inspect's default and gives Kelvran's existing AND-combined per-axis verdict logic (`--judge-axes`) a natural extension: each axis gets its own panel + majority reduction, then axes AND-combine as they do today.
- Preserve individual per-judge votes in metadata (Inspect's `score.metadata.panel` pattern) so disagreement is inspectable after the fact, not just collapsed into a single bit.
- Panel composition: PoLL's finding that *disjoint model families* reduce intra-model bias maps directly onto Kelvran's existing Anthropic+OpenAI dual-provider wiring — the panel's minimum viable size for "disjoint families" is 2 (what Kelvran already has wired), with a 3rd/4th judge from another family as a stretch, not a v2-launch requirement.
- Use `krippendorff_alpha` (or an equivalent lightweight agreement metric) as the drift/reliability signal once a panel exists — this is a natural, cheap companion to recommendation #5's judge-drift-detection idea below.

**Effort:** Medium — this is interface/type design (a widened `judge()` signature, an extended `scorer_type` literal, a metadata field for per-judge votes) plus a short RFC, not an implementation of the panel itself. Building the actual panel remains Large and stays out of scope per the v2 non-goal.

### 3. Bootstrap resampling / Bayesian model comparison: **still not worth it** — verdict reaffirmed, not overturned (n/a — do not build)

**What the research was asked to find:** concrete, real-world evidence that Wilson CIs + mSPRT leave a genuine gap that bootstrap or Bayesian methods would close for Kelvran, specifically.

**What the research found:** none. No source consulted — Inspect AI, DeepEval, Braintrust, promptfoo, or the PoLL paper — treats bootstrap resampling or Bayesian model comparison as a *default* or even commonly-documented gating mechanism for LLM eval CI/CD. The concrete gating mechanisms actually observed in the wild are: bare pass-rate thresholds (promptfoo), bare failure counts (promptfoo), keyword-filtered critical-failure gates (promptfoo), and pytest-style assertion gates with flaky-test tolerance (DeepEval) — none of which required a statistics dependency beyond arithmetic on stored counts. This is consistent with — not contradicting — Kelvran's own architecture-doc aspiration ("no CI/CD gating decision runs without a prior power calculation") being named as exactly that: an aspiration, not something any comparable real system has actually built as a prerequisite to shipping a gate.

**Why this matters for Kelvran specifically:** the research brief was explicit that this exact recommendation has already been rejected twice in this project's backlog ("no real usage to analyze yet" / "no evidence a real need exists") and asked for honesty if the answer is still "not worth it." The answer is still not worth it. `evals report --fail-under`'s existing Wilson-lower-bound gate (recommendation #1) is *already* the narrower, cheaper, real-world-consistent middle ground `DECISIONS.md` chose over the fuller power-calculation machinery — and that choice now has external validation: it's structurally similar to what promptfoo/DeepEval actually ship, not a corner-cutting compromise relative to industry practice.

**When this verdict *would* flip:** if Kelvran ever needs to formally compare two *different* judge configurations or two *different* policy-model versions against each other (not just gate one run's pass rate against a static threshold) — that's a model-comparison problem, which is where Bayesian methods have a genuine, well-established edge over point-estimate CIs. That need does not exist yet in Kelvran's current usage (regression testing against a frozen case set, one model at a time). Track this as the trigger condition, not a reason to build now.

**Consistent with settled decisions?** Reaffirms `STATUS.md`'s 2026-09-05 audit language verbatim ("bootstrap/Bayesian eval stats has no real usage to analyze yet... don't revisit either just to make progress") with new, external evidence behind it rather than just repeating the prior internal judgment call.

**Effort:** N/A — explicitly not recommended at this time.

### 4. Leave `evals promote` manual — do not build an automated production-trace→regression-dataset pipeline (n/a — do not build)

**What the research was asked to find:** whether comparable platforms (Langfuse, Braintrust, DeepEval, Inspect AI, promptfoo) fully automate production-trace→regression-dataset promotion, or deliberately keep a human gate here too.

**What the research found:** every source that documents this workflow keeps it human-gated, and one names *why* in almost the same terms Kelvran's own promotion design implies:
- Braintrust's dataset `input` field can hold a **reference** to a logged trace rather than a copy, rendered via a read-only Trace viewer [braintrust.dev/docs/guides/datasets — confirmed 2-1] — but the actual promotion workflow is explicitly human-initiated: a reviewer picks a "bad" or "interesting" trace worth digging into, copies it into a target dataset, then **a human fills in `expected` from subject-matter expertise** [braintrust.dev/blog/human-review-golden-datasets — confirmed 2-1]. Automated tooling (Topics/Patterns/Loop) only clusters/surfaces *candidates* for review — it never replaces the human promotion step.
- Braintrust's own blog names "copying traces into a dataset but leaving `expected` blank" as **the single most common anti-pattern** in golden-dataset curation, because without a human-authored ground-truth value "the row can't function as a reliable regression test" [braintrust.dev/blog/human-review-golden-datasets — confirmed 2-1]. This is a direct, named argument *against* raw automated trace capture as a substitute for human curation — exactly the failure mode a fully-automated pipeline would risk.
- A second Braintrust post independently confirms the discovery step is also human-driven: regressions are typically first found by "someone scrolling through logs who notices a weird trace," and turning that into a dataset entry is a one-click-but-human-initiated action, not an autonomous background process — the article's own automation is explicitly scoped to *downstream* actions (routing anomalies to alerts/tickets, proposing prompt-fix changes that still require human review) and never to autonomously creating dataset entries without a human noticing [braintrust.dev/blog/traces-and-evals-same-place — confirmed 2-1].
- Braintrust does support a generative/automated dataset-creation *pathway* via a feature called Loop, distinct from the manual pathway (production logs, user feedback, manual curation) [braintrust.dev/docs/guides/datasets — confirmed 3-0] — but this is for generating new synthetic cases, not for autonomously promoting *production* traces into regression sets without review.

**Why this matters for Kelvran specifically:** Kelvran's `evals promote` command is not an outlier relative to real comparable-platform practice — it's the norm. The structural safeguard Kelvran already has (Click's `Choice` type structurally excluding `golden` from rollout-derived promotion, forcing a human through `regression`/`drift_sample` only) is, if anything, a *stronger* guardrail than Braintrust's documented workflow, which relies on human diligence alone to avoid the blank-`expected` anti-pattern.

**Consistent with settled decisions?** Confirms the current manual `evals promote` design is correct as-is; no change recommended. This directly answers (and closes) the research brief's open question #3 rather than surfacing a new gap.

**Effort:** N/A — no build recommended; if anything, this validates keeping the human gate rather than investing in automation here.

### 5. Sandbox isolation pattern is already right; concurrency (Sandbox Pool) should follow asyncio, not Ray — but only once triggered by real concurrent-rollout demand (Medium, deferred)

**What the research was asked to find:** asyncio vs. Ray Core for a future Sandbox Pool, and the real threshold that should trigger building one.

**What the research found:**
- Inspect AI's isolation model matches Kelvran's own current one-Docker-sandbox-per-run design structurally: each sample gets a fresh, isolated sandbox (Docker or local process) specifically to prevent side-effects from contaminating other samples [Inspect AI sandboxing docs, corroborated via a secondary blog source — confirmed 2-1]. Kelvran's `run_in_sandbox()` (`evals/evals/rollout/sandbox.py`) launches exactly one `docker run --rm --network=none --read-only --tmpfs=/tmp` container per call, torn down via `--rm` after each run — the same fresh-sandbox-per-execution-unit pattern, just sequential rather than concurrent today. No change needed to the isolation model itself.
- Inspect AI achieves rollout **concurrency** via an asyncio-style model (AnyIO, asyncio by default with an optional Trio backend), governed by `max_connections`/`max_tasks`/`max_samples` limits — explicitly *not* Ray, multiprocessing, or an actor/distributed framework within the core framework. True cluster-scale execution is delegated to a separate companion package (Inspect Flow), not built into the eval framework's own concurrency primitive [inspect.aisi.org.uk parallelism/eval-sets docs, corroborated against a secondary source — confirmed 2-1].

**Why it matters for Kelvran specifically:** this is real precedent for the exact asyncio-vs-Ray decision Kelvran's own tech-stack table leaves open. A comparable, well-regarded eval framework (built by a national AI safety institute, not a startup optimizing for a sales pitch) chose asyncio/AnyIO for in-process concurrency and only reaches for a *separate* system when it needs cluster-scale (HPC), not for ordinary multi-sample parallelism.

**Consistent with settled decisions?** Consistent with — doesn't reopen — the "massively parallel (10K+) rollouts" v1 non-goal. This recommendation is scoped to *ordinary* concurrency (running more than one sandbox at a time on a single host), not cluster-scale.

**Concrete recommendation:** when a Sandbox Pool is eventually justified, default to asyncio (matching Inspect AI's precedent and avoiding a new heavyweight dependency), gated by a simple `max_concurrent_sandboxes` limit analogous to Inspect's `max_tasks`. Reserve Ray Core only if/when Kelvran needs true multi-host distribution — which the PRD's own 10K+-rollout non-goal suggests is not v1's problem to solve.

**Real trigger threshold:** don't build this speculatively. The concrete, evidence-backed trigger is when sequential rollout wall-clock time becomes the dominant cost in a real CI run that recommendation #1 (the now-wired `--fail-under` gate) actually executes on every PR — i.e., once CI latency from sequential rollouts becomes a felt problem in practice, not before. This is the same "prove real need first" discipline Kelvran already applies to gVisor/Firecracker tiers.

**Effort:** Medium *when* triggered (asyncio refactor of `scheduler.py` plus a concurrency-limit config knob); Small effort right now is simply documenting the trigger condition and the asyncio-over-Ray decision in an RFC so it's not re-litigated from scratch later.

### 6. Production-trace sampling transport: still an open question — no single proven pattern found, so don't guess (Large, deferred)

**What the research was asked to find:** the real, current best-practice transport for a Python eval service to sample a live gateway's OTel traces.

**What the research found:** none of the sources surfaced by this research round (Braintrust, Inspect AI, DeepEval, promptfoo, PoLL) directly and specifically documents "the" production-trace-sampling transport pattern with enough independent corroboration to recommend confidently — the confirmed claims about Braintrust's trace-to-dataset workflow (findings above) describe what happens *after* a trace is already logged into Braintrust's own system, not the wire-level transport by which a separate eval service samples a *live* gateway's OTel pipeline. This is a genuine gap in what this research round could verify, not a finding.

**Why this matters for Kelvran specifically:** the research brief flagged this as "still undecided" in Kelvran's own architecture — this round does not resolve it. Recommend treating it as an open RFC question requiring its own dedicated, narrower research pass (specifically comparing OTel Collector fan-out vs. a dedicated sampling API vs. log-based ingestion against Kelvran's actual gateway topology) rather than accepting a generic, unverified answer here. Given Kelvran's gateway already emits real OTel spans (per `docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md`, confirmed via `DECISIONS.md`), the most promising starting point mentioned in the research brief — an OTel Collector fan-out — deserves a dedicated verification pass before being adopted, not a citation-free recommendation here.

**Effort:** Large, and explicitly not ready to size further — needs its own research/RFC pass first.

## Caveats

- Two findings (Braintrust's trace-reference dataset field, and the Inspect AI/asyncio-concurrency claims) rest on 2-1 votes rather than unanimous 3-0 — treated as high-confidence here because the dissent in each case was a single vote against otherwise-corroborated primary-source evidence, but flagged for transparency.
- The production-trace-transport question (finding #6) is a genuine unresolved gap in this research round, not a soft-pedaled answer — a follow-up research pass scoped specifically to OTel Collector fan-out vs. sampling-API vs. log-based ingestion, evaluated against Kelvran's actual gateway topology, is needed before any transport decision should be made.
- The PoLL paper (arXiv:2404.18796) is from April 2024 — roughly 2.5 years old at the time of this research. Its core empirical finding (diverse-model panels beat a single large judge) is treated as a durable historical result, not a claim about the current SOTA judge models, and nothing in its citing literature refutes it.
- Search tooling (Exa/Tavily) was rate-limited during parts of the underlying research, so several findings rely on direct primary-source fetches rather than independent secondary corroboration; where this occurred, primary-source verification was treated as sufficient given the narrow, factual (not comparative-superiority) nature of the claims involved.

## Open questions

- What panel size and quorum rule should Kelvran actually pick for v2 if/when it's built — majority-of-2 (matching the existing Anthropic+OpenAI wiring) or a 3rd-judge tiebreaker? This report recommends starting at 2 with majority reduction but the RFC in recommendation #2 should make this an explicit, reasoned decision rather than defaulting silently.
- What concrete, measurable threshold should trigger building the Sandbox Pool (recommendation #5) — is "CI wall-clock time exceeds N minutes" the right proxy, or should it be tied to a specific rollout-count-per-PR figure?
- Should the regression-set-only CI gate (recommendation #1) also run against `drift_sample`-tier cases, or is that tier's purpose (per its name) specifically to stay outside the pass/fail gate as an observability-only signal?
- Once a production-trace transport decision is made (recommendation #6), should the resulting sampled traces feed the same manual `evals promote` command unchanged, or does live-traffic sampling warrant its own review UI distinct from the current CLI-only promotion path?
