# Gateway State Durability & Operational Recovery — Research (2026-09-15)

**Scope:** What happens to Kelvran's own operational state — persisted virtual keys (`internal/identity`), budget spend (`internal/budget`), prompt templates (`internal/prompt`), the in-process response cache (`internal/cache`), router/health-probe state (`internal/router`), and `config.yaml` — when things go wrong: process crashes, disk loss, a bad deploy, accidental data loss, or config drift between what an operator declares and what the process actually holds.

**Method:** Direct verification against the live repository first (every code-grounded claim below cites a real file/line, not a doc's own prose), then external research against primary sources (upstream project docs for bbolt/etcd/Vault/Envoy, one real production code-review commit) — **not** the 3-vote adversarial multi-agent panel other reports in this directory used; this is a single-pass research and code-audit report, and confidence levels below distinguish "verified directly against Kelvran's own code" from "primary external source, single fetch" from "one lower-confidence community source." Treat that distinction as load-bearing when deciding what to act on immediately versus verify further.

**Out of scope, already covered elsewhere:** cross-region/geo-distributed availability and data-residency-constrained failover (`docs/upgrade-research/gateway-multiregion-dr-2026-09-13.md` — correctly `not_yet`, and a genuinely different problem from this report's, see Finding 8's framing); the in-process cache's cold-start-after-restart behavior specifically (`docs/upgrade-research/cache-warm-up-cold-start-2026-09-12.md` — correctly `not_yet`, no new evidence found here to revisit that verdict); the bbolt-forces-`replicas:1`-on-Kubernetes mechanics and External-Secrets-Operator recommendation (`docs/upgrade-research/kubernetes-production-deployment-2026-09-14.md`, `deploy/k8s/README.md` — already disclosed in detail); credential rotation/elimination for the leaked AWS keypair (`docs/upgrade-research/secrets-management-lifecycle-2026-09-15.md`). This report's territory is what those don't cover: local-instance data *durability and recoverability* (backup/restore, corruption handling, config-vs-persisted-state drift, silent persistence-layer degradation) — not availability, not multi-region, not the cache specifically, not credential hygiene.

## Ground Truth (Kelvran, confirmed against the live repo, not a research finding)

- Three independent, single-instance-only bbolt stores exist today: `internal/budget/boltstore`, `internal/identity/boltstore`, `internal/prompt/boltstore` — each opened via its own `Open(path)`, each taking bbolt's exclusive file lock, each wired in `gateway/cmd/gateway/main.go` (`newBudgetTracker`, `mergePersistedVirtualKeys`/`identityboltstore.Open`, `newPromptStore`).
- **All three are off by default.** `gateway/config.example.yaml` sets none of `budget.persist_path`, `admin.persist_path`, or `prompt.persist_path` — confirmed by a direct grep returning zero matches. This is also independently confirmed by `deploy/k8s/README.md`'s own disclosure ("`budget.persist_path` is left unset in `config.example.yaml`, so budget state is in-memory-only and resets on every restart"). Every gateway instance run from the shipped example config, including a first Docker Compose bring-up, runs fully in-memory for budget, identity overrides, and prompt templates.
- **The only currently-real deployment shape (Docker Compose) mounts no volume for any of these three paths, even if an operator does set them.** `docker-compose.yml`'s `gateway` service has exactly one volume mount — `./gateway/config.yaml:/config.yaml:ro` — and nothing else. A `persist_path` value written inside the container's writable layer survives a container restart (same container, same layer) but is lost on `docker compose down`, `docker compose up --build`, or any container recreation — and nothing in `docs/operations/DEPLOY.md`'s Compose section discloses this, unlike the Kubernetes README's explicit PVC disclosure for the same underlying gap.
- **Any single corrupted or unopenable bbolt file is a hard, fatal, whole-process startup failure.** `boltstore.Open`'s error return propagates unchanged through `newBudgetTracker`/`mergePersistedVirtualKeys`/`newPromptStore` → `buildPipeline` → `run()` → a non-zero process exit (`gateway/cmd/gateway/main.go:230-232`, `os.Exit(1)` path at line 193). There is no fallback to in-memory, no partial-start, and no repair/inspect tool anywhere in the repo for any of the three files.
- **No backup, restore, snapshot-export, or config-validate tooling exists anywhere in the repo** for any of the three bbolt stores or for `config.yaml` itself — confirmed by grepping `internal/budget`, `internal/identity`, `internal/prompt`, `docs/operations/`, `Makefile`, and `scripts/` for `backup`/`snapshot`/`restore`/`validate`/`dry-run`: the only hits are unrelated doc-comment prose, not real tooling.
- **A persistence write failure is a Warn-level log line only, never a metric.** `budget_persist_failed` (`internal/budget/budget.go:190,277,416`) and `identity_persist_failed` (`internal/gateway/dataplane/dataplane.go:712,725`) are `logger.Warn` calls with no corresponding OTel counter anywhere in `internal/telemetry`, and `/healthz` (`gateway/cmd/gateway/main.go:884`) is a deliberately shallow liveness check that reports only "process is up," never store health.
- **Router health/circuit-breaker state (`internal/router/health.go`'s `deploymentHealth` map) is pure in-memory with zero persistence anywhere**, and every deployment absent from that map is treated as healthy by design (`ReportProbeResult`'s own doc comment) — meaning every deployment starts "healthy" on every process restart, regardless of what its real health was the moment before the restart.
- **The rolling-window budget-reset feature (`VirtualKey.BudgetResetInterval`) and the budget-persistence feature persist different, incomplete slices of the same logical state.** `budget.Store`'s interface (`Load() map[string]decimal.Decimal` / `Save(keyID, spent decimal.Decimal)`) only has room for the cumulative spend total — it cannot represent `periodStart`, `billedCount`, or `periodEpoch`, all of which `resetIfNeeded` (`internal/budget/budget.go:139-178`) keeps in plain in-memory maps with no `Store` counterpart at all.

## Executive Summary

Kelvran's already-shipped restart-durability design (three RFC'd, code-reviewed bbolt stores, each with a clean `Store` interface, each defaulting to today's in-memory behavior when unconfigured) is a genuinely sound piece of engineering for the narrow problem it set out to solve — and this report finds a real, previously-undisclosed correctness gap in exactly that code: the rolling-window budget-reset feature and the budget-persistence feature were built in separate RFCs eleven days apart and never reconciled, so `budget.Store`'s schema persists the spend *total* but not the window's own start time, meaning every process restart silently re-starts every tenant's rolling budget window's clock while keeping its already-accumulated spend — a live, mergeable bug in shipped, opt-in-enabled code (Finding 1). Beyond that specific bug, the bigger pattern this research surfaces is that Kelvran has built real *persistence* but has built essentially none of the operational tooling around it that comparable systems treat as inseparable from persistence itself: bbolt — the exact dependency Kelvran already vendors for all three stores — ships a documented, ready-to-use online hot-backup primitive (`Tx.WriteTo`) that nothing in this repo calls even once (Finding 3); Envoy's decade-old `--mode validate` dry-run pattern has no analog here, so a malformed `config.yaml` is only ever caught by actually trying to start the process (Finding 2); and a corrupted local state file — a real, bbolt-documented failure class, not a hypothetical — currently takes the whole gateway down with no repair path and (per the previous point) nothing to restore from (Finding 4). None of this is exotic: Vault's and etcd's own operator documentation treats "backup/restore protects against corruption and accidental loss; replication/HA protects against availability loss; these are not substitutes for each other" as a stated first principle, which is exactly the distinction this report's territory draws against the already-completed, correctly-scoped multi-region/DR report. The lowest-effort, highest-leverage fix available today doesn't require choosing a new database or building a control plane — it requires finishing the operational half of work Kelvran has already done the hard, correct engineering half of.

## Findings

### Finding 1 — The rolling-window budget reset and budget persistence features were shipped 11 days apart and never reconciled: every restart silently extends every tenant's rolling budget window
**Confidence: high — verified directly against Kelvran's own code, not an external claim.**

`docs/rfcs/2026-09-02-virtual-keys-budgets.md` shipped `BudgetResetInterval` (a rolling window, e.g. "reset every 30 days," tracked via `periodStart`/`billedCount`/`periodEpoch` — all plain `map[string]...` fields on `Tracker` with zero `Store` interaction). `docs/rfcs/2026-09-03-budget-persistence.md` shipped restart-durability exactly one day later, but scoped its own `Store` interface to exactly one value: `Save(ctx, keyID string, spent decimal.Decimal)`. Neither RFC's text acknowledges the other's existence in a way that reconciles this — the persistence RFC's own Motivation section frames the problem purely as "one map, upserted per-key" (the cumulative spend), which was true of the *pre-rolling-window* budget model but stopped being the complete picture the moment `BudgetResetInterval` shipped a day earlier.

**The concrete failure mode:** a virtual key configured with `BudgetResetInterval: 30 * 24h` (a "monthly" cap) and `budget.persist_path` both set survives a restart with its accumulated `spent` correctly intact (persistence does exactly what it promises for that one field) — but `periodStart` for that key is not in the store at all, so `resetIfNeeded`'s own documented behavior for "no `periodStart` yet" (`internal/budget/budget.go:141-142`, explicitly *not* a reset, just starting the clock at `now()`) fires on the very first post-restart access. The key's 30-day window's start-of-period silently jumps forward to the restart time, while the spend it's being measured against is the old window's real, correctly-durable total. A gateway that restarts even occasionally during its own active development cycle (the exact cadence `docs/upgrade-research/cache-warm-up-cold-start-2026-09-12.md` already established is real and frequent for this specific project) will, for every tenant using a rolling budget window, keep pushing that tenant's effective reset date forward on every restart — the opposite of budget enforcement's own purpose, and specifically the class of gap `THREAT_MODEL.md`'s LLM10 Unbounded Consumption row already names budgets as the control for.

**Why this survived two RFCs and hasn't been caught:** `resetIfNeeded`'s doc comment is explicit that a freshly-loaded key with real spend "is not the same as pretending that spend never happened" — correct reasoning for the *value*, but the same code path silently does the period-start equivalent of exactly that "pretend nothing happened before now" move for the *window boundary*, and no test in either RFC's own test suite appears to combine `NewTrackerWithStore` (restart simulation) with a positive `BudgetResetInterval` in the same case — each RFC's tests exercise its own feature in isolation.

**Consistent with settled decisions?** Yes — this is not proposing to change either feature's design, only to close a real gap in how the two already-settled designs compose.

**Concrete next step:** extend `budget.Store`'s schema (or add a small parallel store, mirroring `identity.Store`'s own "deliberately scoped, not everything" precedent) to persist `periodStart` per key alongside `spent`, and add the one missing test class: `NewTrackerWithStore` restart simulation combined with a positive `resetInterval`, asserting the window boundary survives exactly like the spend total does.

**Effort:** Small–Medium — one additional field in an existing bucket's value, or one additional bucket in the existing bbolt file; no new dependency, no new RFC-scale design.

**build_now.**

### Finding 2 — No config-validate/dry-run mode exists; a malformed `config.yaml` is only ever caught by trying to actually start the process
**Confidence: high** (Kelvran side verified directly against code; external precedent from Envoy's own official CLI docs, primary source)

`controlplane.Load(path)` already does real, meaningful validation (`validateFallbackChainTargets`, unregistered-provider checks, the decimal/boolean YAML-parsing fixes `DECISIONS.md`'s `[2026-09-03]` entry documents) — but it only ever runs as step one of actually starting the server. There is no `-validate`/`-check`/`--dry-run` flag on `gateway/cmd/gateway/main.go`'s single `flag.String("config", ...)` definition, and no equivalent exists anywhere else in the repo.

Envoy's own CLI ships exactly this as a first-class, long-standing operating mode: `--mode validate` "Validate the JSON configuration and then exit, printing either an 'OK' message... or any errors generated by the configuration file," explicitly with **no side effects** — "No network traffic is generated, and the hot restart process is not performed, so no other Envoy process on the machine will be disturbed" (envoyproxy.io, official CLI reference) — a pre-deploy config gate a CI pipeline or a pre-rollout hook can call safely against a real, live-adjacent binary, distinct from a human eyeballing YAML.

**Why this matters for Kelvran specifically:** this is the single cheapest available defense against exactly the "bad deploy" half of this report's theme — a config.yaml edit that would fail `validateFallbackChainTargets` or reference an unregistered provider is currently indistinguishable, from a CI/CD or pre-rollout check's perspective, from any other startup failure, and can only be caught by actually attempting a real start (in CI, in a canary, or in production). Kelvran already has every piece of logic this needs; nothing about `controlplane.Load` or `validateFallbackChainTargets` needs to change — only a code path that calls them and exits before touching a listener, a bbolt file, or a real upstream call.

**Consistent with settled decisions?** Yes — purely additive; does not touch config schema, precedence, or any existing validation logic.

**Concrete next step:** add a `-validate` bool flag to `main.go` that calls `controlplane.Load` + `validateFallbackChainTargets` (and ideally also attempts each configured `PersistPath`'s `boltstore.Open`/`Close` round-trip, closing the loop with Finding 4 below) and exits 0/1 without ever calling `ListenAndServe` or holding a bbolt file lock past the check.

**Effort:** Small — the validation logic already exists; this is wiring, not new logic.

**build_now.**

### Finding 3 — bbolt already ships a documented, ready-to-use online hot-backup primitive; Kelvran calls it zero times
**Confidence: high** (bbolt's own upstream README, primary source, fetched directly)

bbolt's own README documents `Tx.WriteTo()` as a built-in mechanism: "You can use the `Tx.WriteTo()` function to write a consistent view of the database to a writer. If you call this from a read-only transaction, it will perform a hot backup" — i.e. a live, currently-open database can be safely snapshotted to any `io.Writer` without stopping the process or blocking writers, and the README explicitly names "backup over HTTP so you can use tools like `cURL`" as a documented, intended use pattern. `Tx.CopyFile()` is named as a to-a-file convenience wrapper over the same mechanism.

Kelvran already depends on `go.etcd.io/bbolt` for all three of its bbolt stores (per the persistence RFC's own stated reasoning — "near-zero *new* transitive dependency weight" was explicitly why bbolt won over SQLite) and calls neither `Tx.WriteTo` nor `Tx.CopyFile` anywhere in the repo. This is the single most direct, lowest-effort, most-precedented gap this report found: the backup mechanism isn't a third-party integration to evaluate or a new dependency to justify — it's a method call away on a library already vendored for exactly this class of data.

**Why this matters for Kelvran specifically:** as things stand, if an operator's disk, volume, or container is lost (accidental `docker compose down -v`, a bad `rm`, a host disk failure — the exact scenarios this report's theme names), every persisted virtual-key override, every dollar of tracked spend, and every prompt-template version history is gone, permanently, with no copy anywhere — even for an operator who *did* correctly configure `persist_path` and mount a volume for it (closing Finding 6 below doesn't help if there's never been a second copy of the data at all).

**Consistent with settled decisions?** Yes — this is additive tooling on top of an existing, settled dependency choice; it does not revisit bbolt-vs-SQLite or embedded-vs-Postgres.

**Concrete next step:** the cheapest version is a new admin-API endpoint (mirroring the existing `/admin/*` surface's own auth pattern) per store — or one unified `/admin/state/export` that streams all three via `db.View(func(tx) error { return tx.WriteTo(w) })` — an operator (or a cron job hitting the admin API) can then redirect that stream to off-host storage. A CLI subcommand on the `gateway` binary itself (`gateway -backup budget.db.bak -config config.yaml`) is a reasonable alternative shape that needs no admin-API auth story at all, closer to `etcdctl snapshot save`'s own shape (see Finding 5's sibling research).

**Effort:** Small — the primitive already exists in the vendored dependency; this is a thin wrapper plus a route or flag.

**build_now.**

### Finding 4 — A single corrupted local state file is a hard, fatal, whole-process outage today, with no fallback and no repair path — and this is a documented real risk, not a hypothetical
**Confidence: high** (Kelvran's fatal-on-`Open`-error behavior verified directly against code; bbolt's own documented corruption classes are a primary source)

`boltstore.Open`'s only two outcomes are "opens cleanly" and "returns an error that is fatal to the whole process" — confirmed by tracing the call chain in the Ground Truth section above. There is no distinction anywhere in that path between "file doesn't exist yet, create it" (already handled correctly — this is the common, safe case) and "file exists but bbolt can't open/read it" (currently indistinguishable from any other startup error, and just as fatal).

This is not a hypothetical failure mode. bbolt's own README documents a real, named corruption class: "bbolt db can be corrupted during the initialization phase due to abrupt power failure" — specifically reproducible "only during the very first initialization phase, when there is no existing data in bolt database," i.e. exactly the moment a fresh `persist_path` file is first created, which for any of Kelvran's three stores is the first time an operator ever turns the feature on. A second, filesystem-specific corruption class is also documented: "bbolt might run into data corruption issue on Linux when the feature ext4: fast commit... is enabled." bbolt's two-phase-commit write design (dirty pages fsync'd, then a checksummed meta page fsync'd) is real crash-safety engineering that correctly prevents a *mid-write* crash from corrupting committed data — but it does not, and does not claim to, protect against these two named classes, or against a corrupted/truncated file arriving by some other means (a bad `docker cp`, a botched manual backup restore, a disk with silent bit-rot).

**The design question this raises, with a real, citable precedent on the other side:** a Rust circuit-breaker-persistence crate built specifically to answer "what should happen when a local state file you depend on turns out to be corrupted or tampered with" makes an explicit, argued choice: **fail open** (discard the bad state, start fresh, log loudly) rather than **fail closed** (refuse to proceed) — with the stated rationale that fail-closed on a corrupted local file "is a self-DoS": "Attacker writes a plausible-but-MAC-invalid file; every circuit trips immediately," versus fail-open's worst case being merely "baseline behaviour *without* [the feature]." Kelvran's own codebase already applies exactly this fail-open reasoning elsewhere by deliberate choice (`internal/ratelimit`'s Redis-backend-error path, `selectHealthy`'s fail-open return, both cited in their own doc comments) — but the bbolt-`Open`-failure path currently does the opposite: fail closed, for state that is explicitly optional and defaults to in-memory when absent.

**This is a real tradeoff, not a slam dunk, and should be presented as one:** failing open on a corrupted budget/identity/prompt file means silently discarding potentially-recoverable data (partial spend history, some virtual-key overrides, some prompt versions) rather than forcing an operator to notice and intervene — which is a worse outcome than fail-closed in a world where a real backup (Finding 3) exists to restore from instead of guessing. The two findings are complementary, not independent: building Finding 3 first makes adopting Finding 4's fail-open recommendation strictly safer (there's now a real "restore from the last good backup" path instead of "silently start empty"), whereas building Finding 4 alone without Finding 3 just trades a loud, honest outage for a silent, undetected data-loss event.

**Consistent with settled decisions?** Consistent with Kelvran's own established fail-open convention elsewhere; this finding proposes extending that convention to a place it currently doesn't reach, not inventing a new one.

**Concrete next step:** distinguish "path absent" (unchanged — create fresh) from "path present but `bolt.Open` or the bucket-ensure step fails" at minimum by making the failure mode an explicit, documented, and ideally configurable choice (e.g. `admin.on_corrupt_store: fail | reset`) rather than the current unexamined default of "fail," and pair any `reset` mode with a loud, high-severity log line and (once Finding 3 exists) an automatic pre-reset backup attempt of the corrupt file itself, so even a "reset" doesn't destroy forensic evidence of what went wrong.

**Effort:** Medium — this touches startup error-handling in three call sites (`newBudgetTracker`, `mergePersistedVirtualKeys`, `newPromptStore`) plus a config knob; the underlying stores themselves need no change.

**build_now** for making the failure mode an explicit, disclosed choice; **not_yet** for picking `reset` as the *default* until Finding 3 (backup) exists to make that default safe.

### Finding 5 — Vault and etcd both treat "backup/restore protects against corruption and accidental loss" as a *different* problem from "replication/HA protects against availability loss" — a distinction this report's territory depends on and the already-completed multi-region report correctly didn't need
**Confidence: high** (Vault and etcd's own official documentation, primary sources, fetched directly)

Vault's own Standard Operating Procedure for snapshot restore states its purpose plainly: restoring from a snapshot is "in response to data corruption or sabotage of which Disaster Recovery Replication might not be able to protect against" (developer.hashicorp.com) — i.e. Vault's own docs explicitly name DR *replication* (an availability mechanism) as insufficient for a corruption/sabotage scenario, which only a point-in-time snapshot can undo. `vault operator raft snapshot save`/`restore` is the mechanism, and Vault Enterprise additionally automates scheduled snapshots to local or cloud storage specifically because a manually-remembered backup is not a real backup policy.

etcd's own recovery docs frame snapshot/restore identically: it exists to rebuild a cluster "without v3 key data loss" after the cluster "disastrously fails, irrevocably losing quorum" — again, a scenario replication/consensus itself cannot recover from once quorum is truly gone. etcd's snapshot mechanism additionally embeds a real integrity hash, checked automatically by the restore tool (`etcdutl snapshot restore`) — copying the raw data directory instead is explicitly documented as unsafe ("might lose data that has not been written yet") and requires an explicit `--skip-hash-check` override specifically because it lacks that hash.

**Why this matters for Kelvran specifically:** it's the reason this report's territory (Findings 1–4, 6–7) is genuinely distinct from — not a re-litigation of — the already-completed multi-region/DR report's `not_yet` verdict. That report correctly asked "does Kelvran need geo-distributed availability yet" and correctly answered no. This report asks a different question — "if Kelvran's one instance's one disk is lost or corrupted, is there anything to recover from" — and the answer today is no, independent of anything multi-region would or wouldn't fix. A future multi-instance/Redis-backed budget store (already named as future work in the persistence RFC's own Unresolved Questions) would improve *availability* of budget data across instances but, per Vault/etcd's own framing, would not by itself be a backup — a shared live store that gets corrupted or accidentally flushed is still gone everywhere at once unless something *else* took a point-in-time copy of it first.

**Consistent with settled decisions?** Yes — reinforces, doesn't revisit, the existing multi-region `not_yet` verdict; clarifies why this report doesn't overlap it.

**Concrete next step:** none — this finding is the conceptual justification for Findings 3/4's `build_now` verdicts and for scoping this report the way its brief asked, not an action item of its own.

**Effort:** N/A (informational).

### Finding 6 — An admin-mutated virtual key silently and permanently overrides any later `config.yaml` edit to the same key ID, with zero startup disclosure of how many overrides were applied
**Confidence: high** — verified directly against `mergePersistedVirtualKeys` (`gateway/cmd/gateway/main.go:692-737`)

`mergePersistedVirtualKeys`'s own doc comment states its design intent plainly and correctly: "a virtual key ever created or rotated via the live admin API is the authoritative version for its ID from then on — `config.yaml` is only ever the BOOTSTRAP/seed state before any admin mutation happens." This is a reasonable, deliberate design — but the merge itself (`virtualKeys[i] = vk`, a full overwrite, no diff, no comparison) runs with **zero logging**: nothing in `buildPipeline` or `mergePersistedVirtualKeys` emits a line stating how many persisted keys were loaded, how many of those overrode a config-declared entry with the same ID, or which fields differed.

**The concrete config-drift scenario this creates:** an operator, weeks after a live admin-API rotation or budget-cap change, edits `config.yaml` to "fix" that same virtual key's `budget_usd` or `allowed_models` — perhaps because they've forgotten the admin API was ever used for it, or because a new operator inherits the deployment with no record of which keys have live overrides. The edit is committed, deployed, and the process restarts cleanly with no error — and the persisted bbolt version silently wins anyway, per the documented (but silent) precedence rule. The "bad deploy" here isn't a crash or a visible failure at all; it's a config change that appears to succeed and quietly does nothing, which is a materially harder class of bug to notice and debug than an outright startup failure.

**Consistent with settled decisions?** Yes — this finding doesn't ask to change the precedence rule (which is a reasonable, deliberate choice, explicitly named in the identity boltstore's own comment as mirroring "this project's proven pattern"), only to make an already-silent, already-real behavior visible.

**Concrete next step:** log a single structured line in `mergePersistedVirtualKeys`'s caller — e.g. `virtual_keys_hydrated_from_store` with `persisted_count`, `overrides_config_count`, and (at Info, not just on request) the specific IDs overridden — so a startup log by itself answers "is this key's config.yaml entry actually live right now," without requiring an operator to already know to distrust it.

**Effort:** Small — a few fields already available at the merge call site, formatted into one log line.

**build_now.**

### Finding 7 — Persistence-layer degradation is invisible: a Warn log line is the only signal, with no metric and no health-check surface
**Confidence: high** — verified directly against code (see Ground Truth)

`budget_persist_failed`/`identity_persist_failed` are the *only* signal emitted when a `Save` call fails — a disk-full condition, a permissions regression, or a filesystem going read-only after a host-level fault would degrade every subsequent write silently from an operator's perspective unless they are actively tailing structured logs at Warn level in real time. There is no OTel counter for persistence failures anywhere in `internal/telemetry` (confirmed by grep), and `/healthz` is deliberately shallow by design (correctly so, per its own doc comment's reasoning about not depending on external services) — but that same design leaves genuinely *local* health (can this process still durably persist its own state) with no home at all, which is a different question from the third-party-dependency question `/healthz` was built to avoid.

**Why this matters for Kelvran specifically:** this is the mechanism by which Finding 1's kind of bug, or a Finding 4-triggering corruption event that happens gradually (a slowly filling disk) rather than abruptly, goes unnoticed until a restart makes the consequence concrete (stale spend, a "lost" virtual-key rotation) — at which point the *original* cause (every write silently failing for however long) is no longer visible in real time, only inferable after the fact from log archives, if retained.

**Consistent with settled decisions?** Yes — purely additive observability; does not change persistence semantics (still synchronous, still non-fatal-to-the-request on failure, per the original RFC's deliberate design).

**Concrete next step:** add a simple monotonic counter metric (e.g. `kelvran.persistence.save_failed`, labeled by store) alongside the existing Warn logs — cheap, and immediately gives an operator's existing metrics/alerting stack (whatever it is — Kelvran's own OTel exporter is already wired) a real signal to alert on, rather than requiring log-based alerting to exist first.

**Effort:** Small — a counter increment at three already-identified call sites.

**build_now.**

### Finding 8 — Router health/circuit-breaker state resets to "every deployment healthy" on every restart; this is a real, named bug class elsewhere, but Kelvran's own probe-driven self-correction likely bounds the damage — genuinely unmeasured either way
**Confidence: medium** (Kelvran's in-memory-only design verified directly against code; the risk framing is corroborated by one real external production commit, not a vendor doc)

`internal/router/health.go`'s `deploymentHealth` map is unconditionally in-memory (see Ground Truth). A real, independently-motivated production fix in an unrelated Rust web server's circuit-breaker code names precisely this failure mode as the reason it added Redis-backed persistence: "CircuitBreaker kept state in a plain in-process HashMap, so a restart or rolling deploy reset every backend back to Closed — a backend that had just tripped the breaker looked healthy again immediately and could cascade the same failures again before anything noticed" (commit `107349a`, `bohdaq/rust-web-server`). Several other real, shipped circuit-breaker libraries (`farzai/breaker-go`, `@reaatech/circuit-breaker-persistence`) exist specifically to close this exact gap via file-based or Redis/DynamoDB/Firestore-backed snapshot persistence.

**Why this doesn't automatically transfer to a `build_now` verdict for Kelvran specifically:** Kelvran's router health state is a *soft* routing preference layered on top of a genuinely independent, per-request safety net — the fallback-chain circuit breaker `docs/upgrade-research/gateway-reliability-resilience-round4-2026-09-11.md` already documents as shipped operates per-request, regardless of what the router's own longer-lived health map currently believes, and `admitTurn`'s own doc comment already characterizes a comparable in-process race window as "rare and self-correcting" by design convention. A restart re-admitting a genuinely-still-down deployment costs, at worst, up to `UnhealthyThreshold`-many wasted probe/request cycles per deployment before the router's own active health-probing loop (already running on a timer, per `dataplane.Pipeline.RunHealthProbeLoop`) re-detects the outage — a bounded, self-correcting cost, not an unbounded one, and structurally similar in shape to other fail-open tradeoffs this codebase has already deliberately accepted elsewhere.

**Consistent with settled decisions?** Consistent with, not contradicting, Kelvran's existing fail-open convention — this finding surfaces a real, externally-corroborated risk class, but does not find Kelvran-specific evidence the current bounded cost is actually a problem at real traffic.

**Concrete next step (measure before building, mirroring this project's own established discipline for exactly this kind of question — see `cache-2026-09-06.md` Finding 5's identical "instrument now, decide later" framing):** once real production traffic exists, measure how many requests actually land on a deployment during the "just-restarted, health-forgotten" window per real restart, and whether that number is materially different from the window a *first-ever* startup already has for every deployment regardless of any past health history (which nothing proposes to fix, since a truly first-boot process has no prior health signal to lose in the first place).

**Effort:** N/A for now (measurement, not a build).

**not_yet** — genuinely unmeasured, not researched-and-dismissed; revisit if/when the measurement above shows real cost.

## Overall Assessment

The pattern across every code-verified finding here is consistent: Kelvran's engineering *of* durable state (the three bbolt RFCs, the decimal-precision work underneath them, the careful `Store` interface boundaries) is genuinely good and holds up under direct code inspection — nothing here found a design flaw in what was actually built. What's missing is almost entirely the *operational* layer around that state: the ability to inspect whether it's actually being written (Finding 7), whether a config change actually took effect over a persisted override (Finding 6), a way to catch a bad config before it reaches a real process (Finding 2), a way to get a second copy of the data anywhere else (Finding 3), and a considered answer — rather than an accidental one — for what happens when the one copy that exists turns out to be unreadable (Finding 4). Finding 1 is the one genuine correctness bug found, and it's a direct, mechanical consequence of the same root pattern: two otherwise-correct features (rolling budget windows, restart durability) were each fully and separately reasoned about, but the seam between them wasn't, because there was no operational practice in place (a restart-plus-rolling-window test case, a schema-completeness check) that would have forced that reconciliation to happen.

## Top 3 — do next

**Do now:**
1. **Fix the rolling-window budget-reset persistence gap** (Finding 1, Small–Medium) — a real, live bug in already-shippable, opt-in-enabled code; every restart currently extends every rolling-budget tenant's window while their spend total stays correct, the opposite of the feature's own purpose.
2. **Wrap bbolt's own `Tx.WriteTo` into a real backup path for all three stores** (Finding 3, Small) — the mechanism already exists in a dependency Kelvran already vendors; today there is no second copy of any persisted spend, virtual-key override, or prompt-version-history data anywhere, for any reason, ever.
3. **Add a `-validate` config dry-run flag** (Finding 2, Small) — Envoy's decades-old, zero-side-effect precedent; the validation logic Kelvran needs already exists in `controlplane.Load`/`validateFallbackChainTargets`, this is purely wiring.

**Instrument/disclose now, decide later:**
4. **Make the corrupted-local-store startup failure mode an explicit, disclosed choice rather than an accidental default** (Finding 4) — pair with Finding 3 before defaulting to fail-open, since fail-open without a backup just trades a loud outage for silent data loss.
5. **Log persisted-vs-config-declared virtual key overrides at startup** (Finding 6, Small) and **add a persistence-failure metric** (Finding 7, Small) — both cheap, both close a real "this silently isn't what the operator thinks it is" gap.

**Not yet — measure first:**
6. Router health-state persistence across restarts (Finding 8) — a real, externally-corroborated risk class, but Kelvran's own per-request fallback circuit breaker and probe-driven self-correction plausibly already bound the cost; measure the actual window before building anything, mirroring this project's own established "instrument now, decide later" discipline from the cache research round.

## Caveats

- **This is a single-pass research report, not the 3-vote adversarial panel other reports in this directory used.** Every Kelvran-side claim above was verified directly against the live repository (file paths and line ranges are cited so they can be re-checked trivially), which is a stronger grounding than most external claims get in any report — but the external claims (bbolt's documented corruption classes, the Rust circuit-breaker commit's rationale, Vault/etcd's stated design philosophy) each rest on one primary-source fetch, not independent multi-source corroboration. Treat the Kelvran-side findings as highly confident and the external framing/precedent as good-quality single-source support, not settled consensus.
- **Exa web search hit its free-tier rate limit partway through this research pass**, which narrowed external coverage on two threads that were not pursued further as a result: a deeper look at Kong AI Gateway's or nginx's own config-dry-run equivalents (Envoy's was fetched directly and is sufficient precedent on its own), and GitOps-style drift-detection tooling (ArgoCD/Flux) as a possible model for Finding 6's "declared vs. actual" visibility gap — the recommendation in Finding 6 is Kelvran-scale (one log line) and doesn't need that heavier precedent to be actionable, but a future pass could still mine that angle for anything more sophisticated worth adopting.
- **Finding 8's severity is presented honestly as unmeasured**, not softened for narrative consistency — the external precedent (a real production commit fixing exactly this bug class) is genuine and should not be discounted, but Kelvran's specific architecture has a mitigating factor (the per-request fallback circuit breaker) that the cited precedent's own codebase may or may not have had, and this report did not verify that comparison — only that Kelvran has *some* independent per-request safety net, which the cited commit's "before" state did not describe having.
- **The Docker Compose volume-mount gap (Ground Truth, third bullet) is stated as a fact about the repository's shipped `docker-compose.yml`, not as a fact about what the real, live Bedrock pilot's actual production configuration does** — this report did not and could not inspect the pilot's real runtime config; it is a repository-level gap that should be checked against the live deployment's actual `persist_path`/volume setup as a direct, cheap next step, separate from any code change.
- **Finding 4's `not_yet`-for-default-behavior verdict is a genuine tradeoff position, not a confident recommendation** — reasonable engineers could land on "fail closed is still correct even after a backup path exists, because silent data loss is worse than an outage that forces investigation" — this report's job is to surface the tradeoff clearly (which side effect is worse, and why the two findings are ordered the way they are), not to declare the debate closed.

## Open Questions

1. Does the real, live Bedrock pilot's actual deployed `config.yaml` set any of the three `persist_path` fields, and if so, is the corresponding file on a volume that survives container/host recreation? This report established the *shipped example* and *shipped Compose file* don't wire this up by default or disclose the gap — it did not and could not verify the pilot's actual live configuration.
2. Should `prompt.Persister`'s "entire version history as one blob per ID" storage shape (`internal/prompt/boltstore`) get any compaction/pruning story before a prompt with many versions makes that blob large enough to matter, mirroring bbolt's own documented freelist-based, never-shrinks-the-file growth model? Not urgent at today's likely scale, but nothing in the current design names a limit or a pruning policy either.
3. If Finding 3's backup mechanism is built, should it run on a schedule (matching Vault Enterprise's automated-snapshot pattern) or only on-demand (matching etcd's manually-triggered `etcdctl snapshot save`)? This report did not find strong evidence either way for Kelvran's likely operator profile (a small, self-hosted, single-operator deployment) and left it as an implementation choice rather than a researched verdict.
4. Would extending `budget.Store`'s schema to include `periodStart` (Finding 1's fix) be cleaner as a breaking change to the existing bucket's value encoding, or as a second bucket in the same bbolt file — and does the answer change once/if `identity.Store`'s own precedent (a single JSON-encoded struct per key, additive-friendly by construction) is deliberately followed instead of `budget.Store`'s current bare-decimal-string encoding?
