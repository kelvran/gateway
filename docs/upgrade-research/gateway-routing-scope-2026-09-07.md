# Gateway Routing Scope Expansion — Deep Research (2026-09-07)

## Question

What is the best design for gateway routing scope expansion (usage/latency/cost-based deployment selection, and automatic model-*group* load balancing) for Kelvran? Grounded against `gateway/internal/router`'s actual current state: a real weighted round-robin selector (smooth-WRR, O(1) per-deployment state, no goroutine/ticker, per `docs/rfcs/2026-09-04-weighted-routing.md`) plus real active/synthetic health-probing (N-of-M consecutive-failure/success thresholds, per `docs/rfcs/2026-09-07-gateway-active-health-probing.md`). `PRD.md`'s v1 scope line is explicitly narrow ("static + weighted routing; a single fallback chain," now multi-hop/error-classified per `docs/rfcs/2026-09-07-gateway-error-classified-fallback-chains.md`) — usage/latency/cost-based selection and model-*group* balancing are named in `gateway/ARCHITECTURE.md` as deliberately unbuilt.

## Summary

Across every gateway whose claims survived 3-vote adversarial verification (LiteLLM, Kong AI Gateway, Portkey), latency/cost-aware routing is uniformly an **opt-in, secondary strategy** layered on top of a production **default that is plain weighted-random distribution over static, human-set weights** — not a unified adaptive algorithm, and not the recommended production default anywhere. Real latency-awareness, where it exists, is built from a smoothed/windowed signal (a TTL-bounded rolling average in LiteLLM, peak EWMA in Kong) plus an explicit anti-thundering-herd mechanism (LiteLLM's `lowest_latency_buffer`, Kong's decaying metrics) — never "always pick the single fastest deployment right now." Cost-aware routing, everywhere it exists, is a simple deterministic lowest-cost lookup against a static cost map, not adaptive. No surveyed gateway has a distinct "model group" abstraction beyond a flat weighted list of equivalent deployments; model-group balancing and fallback/retry chains are explicitly designed as composable, separately-configured layers — not one merged mechanism. Historical infrastructure case studies (Netflix's edge LB, Linkerd/Finagle) independently corroborate the two pitfalls this research anticipated (oscillation from lagging signals; thundering-herd when independent balancers converge on the same "best" target), and confirm the field's standard mitigations (power-of-two-choices, EWMA decay, latency buffers) are old, well-understood techniques, not something Kelvran would need to invent from scratch.

## Findings

### Finding 1 — LiteLLM's production-recommended default is static weighted-random, not adaptive (confidence: high, 3-0)

LiteLLM's `model_name` grouping (the closest analog to a "model group") defaults to `routing_strategy: "simple-shuffle"` — a weighted-random pick off static, human-configured `rpm`/`tpm`/`weight` values, confirmed directly against the live `router.py`/`simple_shuffle.py` source. LiteLLM's own docs state verbatim: *"We recommend using simple-shuffle (default) for best performance in production."* Sources: [docs.litellm.ai/docs/routing](https://docs.litellm.ai/docs/routing), [docs.litellm.ai/docs/proxy/load_balancing](https://docs.litellm.ai/docs/proxy/load_balancing).

### Finding 2 — Where LiteLLM offers adaptive modes, they're discrete opt-in strategies with real anti-herding guards (confidence: high, 3-0)

Latency-based routing scores deployments via a plain **arithmetic mean over a TTL-bounded rolling window** (default ~1hr, configurable) — not a named EWMA/decay formula (confirmed: zero occurrences of ewma/decay/exponential in the actual `lowest_latency.py` source) — plus a `lowest_latency_buffer` percentage that *deliberately widens the candidate pool* to several near-fastest deployments specifically to prevent thundering-herd overload onto whichever deployment currently looks fastest. Usage-based (RPM/TPM-aware) routing is explicitly documented by LiteLLM as **"not recommended for production"** because it depends on Redis round-trips. Cost-based routing is a simple deterministic lowest-cost-from-a-static-map lookup (falling back to $1 for unknown models), filtered to healthy/within-rate-limit deployments — not adaptive or real-time.

### Finding 3 — Kong AI Gateway has genuine EWMA-based latency routing and a separate cost mode (confidence: high, 3-0)

Kong's `lowest-latency` strategy uses **peak EWMA** over TCP-connect-through-body-response latency, governed by a `latency_strategy` parameter (default `tpot` — time-per-output-token — with an `e2e` alternative), with metrics decaying over time. A separate `lowest-usage` algorithm with `tokens_count_strategy: "cost"` explicitly balances model performance against budget targets. Source: [developer.konghq.com/ai-gateway/load-balancing](https://developer.konghq.com/ai-gateway/load-balancing/) (confirmed via 3 independent live fetches).

### Finding 4 — Portkey is purely static weighted-random with a binary health gate, no model-group abstraction (confidence: high, 3-0)

Portkey's load balancing is literal `Math.random()`-based selection over normalized static weights (confirmed against the actual `selectProviderByWeight` implementation in `Portkey-AI/gateway`'s `handlerUtils.ts`) — cost/latency optimization only happens if a human manually sets weights accordingly. The only reactive element is a binary circuit breaker (pass/fail health gate, not latency/cost-scored reweighting). Equivalent deployments are just entries in a generic weighted `targets` array — the same construct used even for spreading load across multiple API keys for one provider's own rate limits. This construct is explicitly composable with fallback chains (nestable either direction).

### Finding 5 — Netflix's real production evidence for the oscillation and thundering-herd pitfalls (confidence: high, 3-0)

Netflix Cloud Gateway replaced round-robin and pure join-shortest-queue with **power-of-two-choices** (randomly sample 2 candidates, score on connection-error health + self-reported utilization + inflight-request count). Netflix explicitly **tried and rejected OS-reported CPU/load-average** as the utilization signal because rolling-average lag caused oscillation — settling instead on simple inflight-request counting. Separately, Netflix found join-shortest-queue alone across many independent load balancers causes real herding (all LBs converge on and overload the same "currently least loaded" server in turn) — mitigated, not eliminated, by combining it with power-of-two-choices random sampling. Source: [Netflix Tech Blog, 2018](https://netflixtechblog.com/netflix-edge-load-balancing-695308b5548c) (verified via Wayback Machine).

### Finding 6 — Linkerd/Finagle's peak-EWMA benchmark, with real caveats (confidence: medium, 2-1)

Peak EWMA maintained fast performance to the 99.9th percentile vs. least-loaded's 99th and round-robin's degradation above the 95th, in an 11-server synthetic simulation with one injected 2s-latency fault — the source itself discloses this is "not a comprehensive analysis." Secondary sources confirm peak-EWMA/power-of-two-choices remains Linkerd's production balancer, but flag real deployment caveats not captured in the original benchmark: per-replica state/memory overhead, a warmup penalty for new/recovering hosts, and oscillation risk under high endpoint churn.

### Finding 7 — No credible LLM-specific benchmark exists quantifying adaptive routing's real benefit (confidence: low)

No public benchmark or case study was found quantifying latency/cost-aware routing's benefit specifically for LLM/AI-gateway traffic (as opposed to generic HTTP microservice load balancing). The one content-farm site that attempted this topic explicitly refused to publish invented figures and had previously *removed* a fabricated "38% latency-based routing beats round-robin" claim from an earlier draft — a negative signal that even motivated low-quality content couldn't find or fabricate credible numbers here.

## Caveats

- **Coverage gap**: TensorZero, Bifrost, and Helicone (3 of the original 7 surveyed gateways) produced zero claims that survived adversarial verification — genuinely unresearched after verification, not confirmed-absent. Envoy AI Gateway's one tested claim (whether its `weight` field does canary splitting vs. model-group balancing) was refuted, leaving that mechanism unconfirmed either way.
- **Historical, not LLM-specific**: the two strongest pitfall case studies (Netflix 2018, Linkerd 2016) are 8-10 years old and describe generic HTTP/microservice load balancing. The underlying control-theory principles (lagging signals → oscillation; independent balancers → herding) are foundational and still cited in production, but no evidence ties them directly to LLM inference traffic's own patterns (e.g., per-request latency variance from streaming token generation).
- **Explicitly refuted, not just unconfirmed**: LiteLLM's "least-busy" strategy tracking live in-flight counts (0-3); Envoy's weight-field purpose (0-3); Prequal's Hot-Cold Lexicographic algorithm's reported p99 gains (0-3) — treat these as open questions, not established facts in either direction.
- This external survey does not itself cover Kelvran's own `internal/router` source — the design sketch and recommendation below were composed separately, grounding the external findings in Kelvran's actual current code.

## Kelvran-Specific Design Sketch & Recommendation

**Kelvran's existing static-weighted default is already the industry-validated choice, not a gap.** Finding 1 and Finding 4 confirm the two most mature, widely-deployed competitors (LiteLLM, Portkey) both default to — and LiteLLM explicitly *recommends* — exactly what Kelvran already ships: static weighted-random/round-robin distribution. This is reassuring evidence that Phase 1's original weighted-routing RFC picked the right production default, not a finding that Kelvran is behind.

**Kelvran already has model-group load balancing, in the exact shape every surveyed competitor implements it.** Finding 4's "no gateway has a distinct model-group abstraction beyond a flat weighted list" describes precisely what `controlplane.Config.Deployments` + `router.Router.Select` already do: multiple `Deployment` entries sharing one `Model` value are already weighted-round-robin-distributed by `Select`, and a separate, already-shipped mechanism (error-classified multi-hop fallback chains) handles cross-model/cross-provider failover — matching Finding 4's own observation that competitors keep load-balancing and fallback as composable, separately-configured layers rather than one merged mechanism. **The real gap `gateway/ARCHITECTURE.md` names is adaptive (latency/cost-driven) *weighting* within that existing group, not the grouping mechanism itself.**

**Recommendation: instrument now, adapt later — do not build a live-signal router yet.** Three independent lines of evidence converge on this:
1. Every mature competitor treats adaptive routing as *secondary and opt-in*, never the default — building it as Kelvran's primary mechanism now would be building ahead of the field's own consensus, not catching up to it.
2. Finding 7's negative result (no credible LLM-specific benchmark exists anywhere) means Kelvran would be tuning blind — there is no external evidence for what smoothing window, buffer percentage, or EWMA decay constant is right for LLM traffic specifically, only decade-old generic-HTTP precedent (Findings 5-6).
3. Kelvran has zero production traffic today — the same reasoning that correctly gated the traffic-derived statistical circuit breaker (`gateway/ARCHITECTURE.md`'s existing deferral) applies identically here, and mirrors the already-established "instrument first, decide later" pattern from cache cross-instance telemetry (`docs/rfcs/2026-09-07-cache-cross-instance-telemetry.md`) and cache L3-lite's per-gate ablation.

**Concrete next step, if any**: extend the already-shipped OTel GenAI metrics (`gen_ai.client.operation.duration`, per-deployment) to be queryable per-`Deployment` at the router level — a small, additive telemetry change, not a routing-behavior change — so that once real traffic exists, an evidence-based adaptive router (following Finding 2/3's proven shape: a smoothed rolling signal + an explicit anti-herding buffer, never naive "always pick fastest now") can be designed from Kelvran's own real data rather than guessed. This is deliberately **not** scheduled as a phase in this pass — it's named here as the concrete trigger-precondition, mirroring how Phase 1b's ablation instrumentation preceded (and was a precondition for) the real-embedding-L3 decision.

## Second-pass reaffirmation (2026-09-08)

Re-examined the 2026-09-07 verdict one day later, per a targeted follow-up (not a full redo). All three checked preconditions are unchanged; the deferral holds.

**1. Competitive landscape — no material change.** LiteLLM's docs/code still default to and recommend `simple-shuffle` for production (`docs.litellm.ai/docs/routing`, `router.py`'s `Router.__init__`); `latency-based-routing`/`cost-based-routing`/usage-based routing remain explicit opt-in `Literal` choices, with usage-based still flagged "not recommended for production." One addition since the original pass: LiteLLM now has a `[BETA] Adaptive Router` (Thompson-sampling/quality-cost bandit for *model selection*, not deployment load-balancing) — still labeled beta, still opt-in, and by its own documented "Known Limitations" does not score latency at all, so it doesn't even compete on the axis this research evaluates. Portkey's docs (load-balancing/conditional-routing/configs/overview) remain purely static-weight-based, with zero occurrence of "adaptive"/"latency-aware"/"EWMA" anywhere. Kong AI Gateway's `lowest-latency` (peak EWMA) is unchanged — still one of seven algorithms, still reference-documented with zero benchmarks or case studies backing how to tune it. Envoy AI Gateway's "latency aware routing for model endpoints" issue (#812) is still open with zero linked PRs/branches, unchanged since the original check. Finding 7's core conclusion — no credible LLM-specific *production* benchmark or postmortem exists — still holds; the one new academic paper surfaced (Lodestar, arXiv, submitted 2026-05-31) is an online-learning router evaluated against a heuristic baseline on synthetic traffic in a provisioned GPU cluster, not a production case study, so it doesn't change the practical conclusion for Kelvran.

**2. Kelvran's own code — the named next step has not been built.** Directly inspected `gateway/internal/telemetry`, `gateway/internal/router`, and `gateway/internal/gateway/dataplane`. `gen_ai.client.operation.duration` (`RecordChatCompletionMetrics`, `telemetry.go`) is real and unconditionally recorded (shipped in Phase 2, 2026-09-07), but its attributes are operation name / provider / `gen_ai.request.model` / `gen_ai.response.model` / `error.type` — model-level, not deployment-level. The `kelvran.deployment.name` attribute exists (`result.go`) but is attached only to trace spans via `RecordChatCompletionResult`, never to the metric histogram. `gateway/internal/router` imports zero telemetry packages (confirmed via grep) — it has no access to any duration/latency signal at all; its only feedback loop is a binary healthy/unhealthy verdict from active synthetic health probes (`ReportProbeResult`/`selectHealthy`), wired through `dataplane`, not through any GenAI metric. A repo-wide grep for "adaptive routing," "latency-aware," "EWMA," and "per-deployment metric[s]" across `DECISIONS.md`, `STATUS.md`, `gateway/ARCHITECTURE.md`, and every `gateway/changelog/*.md` returns zero matches outside this research document itself. The concrete next step was not built as a side effect of any later work — it remains exactly where the original report left it: unscheduled.

**3. Production traffic — still zero.** `STATUS.md` and `DECISIONS.md`, current as of today, independently and repeatedly confirm this directly rather than by inference: `DECISIONS.md` (2026-09-05) describes Kelvran plainly as "a project with zero live traffic"; `STATUS.md`'s Blocked list states the distributed cache work is gated on cross-instance telemetry because "no live multi-instance deployment exists yet to measure"; the Online Eval Service is blocked on "needs production traffic"; and the most recent corpus-growth rounds (through today) still list "whether/how real-traffic failures should feed router health state" as an open, unaddressed item because router health is "fed only by synthetic probes, never real traffic." No `STATUS.md`/`RELEASE.md` section describes any real customer or live deployment — only a public GitHub repo and version tags. This was the single biggest reason adaptive routing was declined, and it is unchanged.

**Verdict: unchanged.** No mature competitor has moved adaptive routing from opt-in to default; no credible LLM-specific production benchmark has appeared; Kelvran's own telemetry still can't distinguish deployments within a model group at the router level; Kelvran still has zero production traffic to tune against. "Instrument now, adapt later — do not build a live-signal router yet" stands. No action item beyond the one already named in the original report (extend `gen_ai.client.operation.duration` to carry a deployment-level attribute, queryable at the router level) — still correctly unscheduled, pending real traffic.
