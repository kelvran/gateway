# Evals Next-Upgrade Scan — Deep Research (2026-09-09)

## Question

Now that `evals/v0.2.0` is tagged and shipped, what are the highest-value next-upgrade candidates for evals specifically — surveying current (2026) production/research practice in Inspect AI, promptfoo, DeepEval, Braintrust, OpenAI Evals, LMSYS/Chatbot-Arena-style pairwise comparison, and agentic-eval harnesses — for: (1) cross-vendor signal for the now-same-vendor judge panel, (2) a real accuracy-vs-designed-label metric for judge/panel quality, (3) dataset/corpus versioning and lineage, (4) human-in-the-loop review patterns, (5) drift detection over time for ingested `drift_sample` cases, (6) cost-aware eval scheduling, (7) `THREAT_MODEL.md`'s Evals rows vs. current eval-harness security survey practice, and (8) anything else a 2026 production eval-framework survey would flag?

## Context (Kelvran's own real, current state)

`evals/v0.2.0` ships: the Rollout Scheduler (`run_suite`, sequential asyncio) + `Run` model + JSONL Results Store; deterministic scoring + a real Anthropic/Bedrock-backed LLM-judge (`--llm-judge`) + a real 2-judge majority-vote panel (`--llm-judge-panel`, fail-closed on a tie, both judges now Claude-via-Bedrock — an explicit, accepted same-vendor-correlation tradeoff for AWS-only operational simplicity) with `--use-score-cache` and `--judge-axes`; a `Score` model with `Decimal`-precision `cost_usd`; a real mixture-SPRT early-stopping rule plus `--use-cache`; a 113+24-case regression corpus (including a dedicated 24-case `judge_accuracy` slice) with a real CI gate (`--fail-under` on the Wilson lower bound); `evals promote`/`evals ingest` (S3+GCS, `drift_sample` tier); `Span`/OTel tracing for sandbox executions; `.importlinter` layer enforcement; a nightly judge-accuracy workflow. Already researched and settled (not re-litigated here): blanket `temperature=0` judge pinning (real "spurious certainty" cost, rejected), a nightly-only `temperature=0`+`seed` experiment (checked — no `seed` parameter exists on either provider API for the models in use), real bootstrap/Bayesian/pass@k statistics (package family not yet installed, Wilson-interval-only is the deliberate interim), Ray Core-based parallel rollout execution (asyncio-only is the deliberate v1 posture).

## Summary

Across the eight research questions, the verified evidence converges on one clear top priority: **close the named judge-accuracy-metric gap by reporting Cohen's kappa and a full 2x2 confusion matrix (not raw exact-match) against the existing 24-case `judge_accuracy` corpus** — pure-Python, needs no new dependency, directly answers RQ2. Two more "build now" items follow closely: a quote-grounded-verdict check added to `llm_judge.py`'s verdict parsing (RQ4), and a same-vendor prompt-debiasing technique (position-swapped combined CoT+rubric prompting, +11.5pp on Claude judges in the cited study) that improves the existing Bedrock-only panel without reopening the OpenAI-cost tradeoff already recorded in `evals/judge/providers.py` (RQ1). Cross-vendor panel reintroduction (RQ1), a formal judge-vs-system drift-attribution method for `drift_sample` cases (RQ5), and a full human-review CLI (RQ4) are all real, well-evidenced 2026 techniques but are "not yet" for Kelvran — each needs a trigger the project doesn't have yet. A first systematic LLM-judge security survey exists and is a legitimate source to cross-check `THREAT_MODEL.md`'s Evals rows against in a future pass (RQ7), though its most specific claim (a bidirectional "judge attacked vs. judge as attack tooling" framing) did not survive verification.

## Findings

### Finding 1 — Cross-vendor judge diversity is not a reliable fix for same-vendor panel bias; a same-vendor prompt-debiasing technique is a real, additive "build now" alternative (confidence: medium) — **debiasing prompt: build now; cross-vendor reintroduction: not yet**

Same-family auditing is confirmed insufficient at catching judge bias, but the effective cross-vendor pairing is bias-specific with no universal answer, and deliberately maximizing vendor diversity can even reduce a panel's effective statistical independence (one cited claim that cross-vendor pairs are never less correlated than same-vendor pairs was explicitly refuted, 0-3). `evals/judge/providers.py`'s own comment already names the Bedrock panel's same-vendor tradeoff as deliberate and accepted; `llm_judge.py` already applies CoT-forcing + reference-guided grading as v1 bias mitigations (`_BIAS_MITIGATIONS_APPLIED`). A "Combined Budget" debiasing technique (a merged CoT+rubric prompt, called twice with position swapped) is shown to produce the largest, most statistically significant accuracy gain specifically for Claude judges (+11.5pp, p<0.0001, Holm-Bonferroni-surviving) and reuses the exact same `call_model` interface at only 2x call cost — no new vendor/credential needed, directly addable to the existing `judge()`/`reduce_panel_votes` path. Reintroducing a real cross-vendor judge (dormant `AsyncOpenAI` wiring already exists in `providers.py`) is "not yet": no single cross-vendor pairing is validated as generally effective, and Kelvran has no labeled data yet identifying which specific bias type(s) its own panel is most exposed to. **Trigger for cross-vendor**: a bias-specific labeled need identified from real data — same-vendor-with-disclosed-limitation remains the pragmatic 2026 answer until that data exists.

### Finding 2 — No chance-corrected judge-accuracy metric exists anywhere in Kelvran's stats code; Cohen's kappa + a full confusion matrix against the existing 24-case corpus closes this with zero new dependencies (confidence: medium) — **build now**

`report_cmd` computes only a Wilson-interval pass rate from raw pass/fail counts. Five commonly-reported correlation statistics (Pearson/Spearman/Kendall-tau_b/phi/MCC) are mathematically identical for binary verdicts and NOT interchangeable with kappa (which is discounted by a marginal-mismatch factor whenever judge/human positive-verdict rates diverge); raw exact-match systematically overstates chance-corrected accuracy by a ~38.6pp mean across studied judges — a naive "percent correct on the 24 cases" number would be badly inflated. Separately, high agreement among Kelvran's 2-judge panel (`quorum_reached`) answers a different question than judge accuracy and must not be mistaken for validation against the corpus. `tests/fixtures/regression_corpus_judge_accuracy.json` already exists (24 cases, each with a `corpus_note` recording the expected/observed unanimous verdict), and `PanelVote` (`scorer_id`, `passed`, `rationale`) is a ready-made input shape for a 2x2 table — this is genuinely additive: the arithmetic needs no new dependency (kappa/phi/MCC on a 2x2 table is a few lines of pure Python), consistent with Kelvran's already-deliberate posture of not yet installing numpy/scipy/scikit-learn. A concrete, sequenced checklist exists in the source literature (chance-correct with kappa, AB/BA position-swap, replicate ≥3 runs, cross-validate on ≥2 label distributions, specifically audit high test-retest against position bias before trusting it) that `report_cmd` could implement incrementally.

### Finding 3 — Two small open-source tools independently converge on the same lightweight HITL pattern; the quote-grounded-verdict half is directly additive to Kelvran today (confidence: medium) — **quote-grounded verdicts: build now; full human-review CLI: not yet**

Two real, tiny (single-owner, low-adoption) open-source tools converge on the same pattern for spot-checking judge disagreement without a full UI build: (a) the AI investigates and quotes evidence while a human makes the final call via a single-keypress terminal loop with per-decision persistence; (b) every judge verdict must cite a verbatim, mechanically string-verified quote from the transcript it's judging, and any verdict whose quote can't be confirmed is discarded before the vote is tallied. The quote-grounded-verdict mechanism is directly buildable: `llm_judge.py`'s `_parse_judge_response(raw_response) -> tuple[bool, str]` already extracts a `(passed, rationale)` pair per panelist, so adding a required verbatim `trigger_quote` field to `build_judge_prompt`'s output contract plus a pure-string substring-in-source-text check before trusting a panelist's `PanelVote` is additive, not a redesign, and needs no new dependency or UI. The full human-review CLI is "not yet" — it needs a trigger Kelvran doesn't have: a real operational volume of promoted regression cases (`evals promote`) or panel ties (`quorum_reached=False`) large enough to justify a dedicated review workflow; neither exists at meaningful scale today.

### Finding 4 — A real, provable anytime-valid drift-attribution method exists but needs two prerequisites Kelvran doesn't have yet (confidence: medium) — **not yet**

A formal method (a frozen human-labeled anchor set + a betting e-process on the judge-vs-human gap + a guard-window rule) attributes an observed quality drift specifically to the JUDGE rather than the system-under-test, with a proven false-alarm bound and a structural proof that system-side drift alone cannot trigger a false judge-drift signal. `evals/ingestion/{decode,mapping,object_store}.py` and `cli.py`'s `promote_cmd` already collect the raw material (S3/GCS `gatewayevents_v1` decoded into `EvalCase`/`Run` at `drift_sample` tier), but nothing consumes those cases over time to actually detect drift — exactly the named gap. This is "not yet" specifically because the method requires (1) a genuinely frozen, human-labeled anchor set that survives across judge/prompt versions, which doesn't exist, and (2) real production `drift_sample` volume accumulating over a monitoring horizon to bet against, which also doesn't exist — consistent with the project's own "no production traffic exists yet to calibrate against" posture. **Recommendation**: record this as a designed-but-deferred RFC to build once `drift_sample` ingestion has real volume, not building it now.

### Finding 5 — A first systematic LLM-judge security survey exists as a legitimate future cross-check for `THREAT_MODEL.md`'s Evals rows, but its most specific claim did not survive verification (confidence: high on existence; the specific framing claim is refuted) — **not actionable yet, flag for a future pass**

A first Systematization-of-Knowledge on LLM-as-a-Judge security exists (863 candidate works filtered to 45 studies, 2020-2026). `THREAT_MODEL.md`'s Evals component already names judge-verdict-flip (Tampering row, CoT-forcing + reference-guided grading + judge≠policy-model as mitigations) and sandbox escape (Elevation of Privilege row, Docker `--network=none`/`--read-only` as real partial mitigations) as live threats. This survey is a legitimate reference to check that taxonomy against for gaps such as judge-call-volume cost-DoS or prompt-injection embedded in task output — but only as an existence/coverage source: the survey's own central bidirectional-attack-surface framing claim (judge attacked vs. judge used as attack tooling) was explicitly refuted (0-3) during verification and must not be cited to justify any specific new mitigation.

## Caveats

- Five of the sixteen confirmed claims underlying these findings were split-vote (2-1) even though sourced from primary arXiv preprints — treat exact effect sizes (+11.5pp, 38.6pp mean) as single-study 2026 point estimates, several from not-yet-peer-reviewed preprints, not settled constants.
- Eight related claims were explicitly refuted during verification and are deliberately excluded: CyclicJudge round-robin variance-optimality, "systematic bias >94% of judge variance," self-preference-bias uniformity across model families, the `hitl-review` threshold-routing tool's specific mechanics, and the SoK survey's bidirectional-framing claim — do not resurface these in a later pass without new evidence.
- The two HITL tools cited (PressF, modelun) are both tiny, low-adoption repos (2 stars/0 stars, single-owner) — verified as real and functioning by direct code inspection, but not battle-tested at scale; treat as design precedent, not tools to adopt wholesale.
- This pass's grounding into Kelvran's own repo was a targeted spot-check, not exhaustive, and did not re-read the full text of the existing `evals-judge-panel-reducer-2026-09-07.md`/`evals-corpus-cost-abuse-patterns-2026-09-08.md` files this task asked to avoid duplicating — only confirmed their topics via directory listing — so residual overlap risk with already-settled research is possible.
- Research questions on cost-aware scheduling (RQ6) and dataset versioning/lineage (RQ3) returned findings that did not survive the top-25 verification cut in this pass's synthesis — treat both as under-researched by this specific run rather than resolved either way; a follow-up pass may be warranted if either becomes a real priority.

## Recommendation for Kelvran

1. **Build now, no new dependency**: report `evals/stats.py`/`report_cmd` gains a Cohen's kappa + confusion-matrix metric against the `judge_accuracy` corpus slice (Finding 2) — this is the single highest-value, lowest-risk item, and directly closes a gap Kelvran has already named but not built.
2. **Build now, additive**: a quote-grounded-verdict check in `llm_judge.py`'s verdict parsing/`PanelVote` (Finding 3), and the position-swapped combined-prompt debiasing technique for the existing Bedrock panel (Finding 1) — both reuse existing interfaces with no redesign.
3. **Not yet, all correctly deferred with a named trigger**: cross-vendor panel reintroduction (needs bias-specific labeled data), formal drift attribution for `drift_sample` cases (needs a frozen human-labeled anchor set + real production volume), a full human-review CLI (needs a real backlog of disagreements/promoted cases at scale).
4. **Flag for a future pass, not actionable today**: cross-check `THREAT_MODEL.md`'s Evals rows against the LLM-judge security SoK survey's taxonomy (Finding 5) — legitimate source, but this pass didn't do the actual gap analysis.
