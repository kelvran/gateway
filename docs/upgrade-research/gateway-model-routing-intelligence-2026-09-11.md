# Cost/Quality-Aware LLM Model-Routing Intelligence for v2 — Deep Research (2026-09-11)

## Question

Beyond Kelvran gateway's current static + weighted round-robin deployment selection, what does real 2026 production LLM-router intelligence look like — cascade routing / model-quality-cost-frontier routing (RouteLLM-style, Martian, Not Diamond, OpenRouter's own routing) — and is "route by predicted quality-cost tradeoff" a well-precedented pattern with real production adoption, or does it remain research-stage with no real production precedent at Kelvran's scale? Specifically: (1) what real signals do production routers use to predict quality before calling a model; (2) is there a real, adopted "cheap model first, escalate on low confidence" cascade standard, and what does escalation cost/latency look like; (3) how do real systems avoid the routing-decision call itself costing more than it saves; (4) given Kelvran's own real per-deployment cost/health data, is there a low-risk build-now version for v2, or is it genuinely not-yet-ready?

## Context (Kelvran's own real, current state)

Already real and shipped: weighted round-robin deployment selection (LVS/IPVS smooth-WRR, `gateway/internal/router`), real active health-probing with N-of-M thresholds + backoff + post-recovery weight ramp, error-classified multi-hop fallback chains (content-policy / context-window / generic, via `classifyFallbackError`), per-deployment concurrency + rate ceilings, real decimal-precision cost accounting with cache-token discounts across all 5 adapters (openai/anthropic/bedrock/gemini/openaicompat), and real per-virtual-key budget/TPM enforcement via Reserve/Reconcile. Explicitly **not** built: usage/latency/cost-based selection signals, automatic model-*group* load-balancing, or traffic-derived statistical circuit breaking — the last of these is a repeatedly-named, deliberate deferral pending a production-traffic volume floor Kelvran does not yet have (see `docs/upgrade-research/gateway-router-health-real-traffic-2026-09-09.md`, which independently confirms the same floor-gated deferral pattern this report also finds industry-wide). This report evaluates whether a *quality-prediction*-based routing layer (as opposed to the health/traffic-derived layer covered by that prior doc) is ready to build now.

## Summary

"Route by predicted quality-cost tradeoff" is a real, well-precedented pattern with genuine production adoption (OpenRouter's Auto Router) and a mature academic literature (RouteLLM, Hybrid LLM, Tryage, AutoMix) — but production and research diverge sharply on mechanism. The one confirmed production system (OpenRouter) does not predict per-request output quality at all: it runs a cheap task-type classifier and then ranks candidates by aggregate community spend share, filtered through a discrete cost-tier band — a market-popularity proxy, not a quality predictor. Academic "quality-cost frontier" routers (RouteLLM, Hybrid LLM, Tryage) instead train a classifier or embedding-similarity model offline on historical human-preference or difficulty-labeled data and apply it before generation; a separate, architecturally distinct line of research (AutoMix) instead calls the cheap model first and escalates only after a post-hoc self-verification step flags likely-incorrect output. All of these avoid the "routing call costs more than it saves" trap the same way — by making the router itself orders of magnitude cheaper than the models it routes between (embeddings/small classifiers, never a second full LLM judge call) — not by any clever amortization trick. For Kelvran specifically, every real-world precedent depends on a training/calibration dataset (historical preference votes, difficulty labels, or aggregate spend data) that Kelvran does not yet have at production scale, so the learned-router feature itself is genuinely not-yet-ready; the one piece that is build-now is OpenRouter's simpler, non-learned discrete cost-tier band filter, which needs no training data and composes directly with Kelvran's already-shipped per-deployment cost data.

## Findings

### Finding 1 — No real production router studied predicts per-request output quality via a live judge/classifier call; the one confirmed production system (OpenRouter) routes on cheap task classification + aggregate market popularity, not quality prediction (confidence: high)

OpenRouter's Auto Router — the only *production*, currently-live system verified in this pass — works in exactly four steps, none of which is a quality-prediction call: (1) a "fast, lightweight classifier" assigns each prompt one of ~30 fine-grained task types, (2) candidates are ranked by trailing-7-day aggregate community spend share for that task type — "the wisdom of the market," explicitly not a per-request quality signal, (3) a discrete `cost_tier` band (low/medium/high/xhigh/max) filters the ranked list, excluding models both above *and* below the band, and (4) the top surviving model plus fallbacks is selected. Nowhere in this pipeline is there an embedding-similarity lookup against past queries or a cheap LLM-judge call predicting output quality. This directly answers research question 1 for the *production* case: the real signal in the field today is a discrete task-type classification feeding a popularity ranking, not quality prediction at all.

**Build now / not yet: not_yet** for the "quality-predicting router" itself — no verified production precedent predicts quality per-request; the closest live system deliberately avoids doing so.

### Finding 2 — Academic "quality-cost frontier" routers use two genuinely different signal families, both trained offline on historical preference/difficulty data, neither a live judge call (confidence: high)

Three independent research systems converge on offline-trained, upfront (pre-generation) quality-prediction signals: **Tryage** trains a "perceptive router" language model to predict downstream expert-model accuracy per prompt, explicitly contrasted with model-card-based heuristics (Gorilla) as *not* a quantitative learned predictor. **RouteLLM** ships four router architectures — similarity-weighted ranking (cosine similarity of the query embedding, via OpenAI `text-embedding-3-small`, to labeled training queries), matrix factorization over query+model embeddings (its strongest, recommended default), a fine-tuned BERT classifier, and a Llama-3-8B causal-LM classifier — all trained on Chatbot Arena preference data with the actual model *responses* explicitly discarded, retaining only which model won. **Hybrid LLM** trains a 300M-parameter DeBERTa-v3-large classifier via binary cross-entropy on BART-scored quality-gap labels to predict per-query "difficulty," again purely from the query text with no live model call at inference. All three are query-only, pre-generation, offline-trained predictors — never a second live LLM call inspecting the actual response.

**Build now / not yet: not_yet.** Trigger: this pattern requires a labeled training set (historical preference votes, human-scored difficulty labels, or a per-query gold-quality signal) at real volume — exactly the "no production traffic yet to calibrate against" gap already named for Kelvran's health/circuit-breaking work. Kelvran's own evals harness (judge panels, regression corpus) is the natural future source of such labels, but does not yet exist at the volume or coverage needed to train a router.

### Finding 3 — Tryage's Pareto-front cost/quality tradeoff and OpenRouter's discrete cost-tier band are two different maturity levels of the same idea; only the discrete-band version is production-proven and needs no trained model (confidence: high)

Tryage frames routing as multi-objective optimization along a Pareto front, trading predicted task accuracy against secondary cost-adjacent proxies (model size, recency, security, verbosity, readability) rather than always picking the single highest-predicted-accuracy model — a continuous, research-stage tradeoff mechanism. OpenRouter's shipped, current mechanism is a much blunter but production-proven version of the same idea: a discrete `cost_tier` band (low/medium/high/xhigh/max) that filters the ranked candidate list, explicitly excluding models both above *and* below the chosen band ("a band, not a ceiling"). Notably, OpenRouter's docs flag a now-deprecated `cost_quality_tradeoff` parameter, implying OpenRouter itself moved *away* from a more continuous-sounding tradeoff mechanism toward the simpler discrete-tier design — a signal that the industry's own production system converged on the cheaper, simpler mechanism over time, not the reverse.

**Build now / not yet: build_now** for the discrete-tier-band pattern specifically. No trigger needed — this requires no trained model and no historical data, only Kelvran's own already-shipped per-deployment cost accounting to bucket deployments into bands and filter the existing WRR/health-based candidate list before or after weight assignment.

### Finding 4 — Cascade/escalation routing (cheap model first, escalate on low confidence) is real and academically well-formed (AutoMix), but is architecturally distinct from — and explicitly rejected by — the predictive-routing systems that have real production adoption (confidence: high)

AutoMix routes to a larger model only *after* generating output from a smaller model and assessing it via a few-shot self-verification prompt (the model judging its own prior output — not an embedding lookup, not a separate trained classifier, and explicitly "we do not train a verifier," unlike baselines FrugalGPT (fine-tuned DistilBERT) and HybridLLM (trained DeBERTa)). Because self-verification is noisy on its own, AutoMix adds a second-stage POMDP-formulated router rather than simply thresholding the raw verification probability — the paper reports the POMDP variant is more robust than plain thresholding. This is a genuinely different architecture from RouteLLM, which explicitly and by design does **not** cascade: RouteLLM's own paper contrasts itself directly against cascading approaches (naming FrugalGPT) as "rely[ing] on multiple LLM queries, which can increase latency," and instead computes a win-probability from the query *alone*, before any generation, routing to exactly one model. The one production system verified (OpenRouter) also does not cascade — its classifier-then-rank pipeline runs once, before generation. So the "cheap model first, escalate on low confidence" cascade pattern is real in the literature but has no verified production adoption in this research pass — the deployed pattern is predictive (decide once, upfront), not cascading (generate, verify, maybe re-generate).

**Build now / not yet: not_yet.** Trigger: cascade routing only makes sense if escalation is rare enough that the wasted small-model call is cheaper than the latency/cost of just calling the strong model directly for every request in that class — this calculation itself requires real query-mix and cost data Kelvran doesn't yet have (the same traffic-volume gap named elsewhere), and no verified quantified real-world escalation-rate/cost numbers survived adversarial verification in this pass (see Caveats) to size the tradeoff even hypothetically.

### Finding 5 — Every studied mechanism avoids the "routing call costs more than it saves" trap by making the router architecturally far cheaper than the models it routes between — never by amortizing a second full LLM call (confidence: medium)

RouteLLM's paper explicitly measured this, rather than assuming it: across all four of its router architectures (embedding-based similarity ranking, matrix factorization, a fine-tuned BERT classifier, and an 8B causal-LM classifier), even the most expensive variant (similarity-weighted ranking) added "no more than 0.4%" additional cost compared to GPT-4-class generation cost, backed by a concrete per-architecture cost/throughput table. The common thread across every real signal-generation mechanism this report verified (Findings 1–2) is architectural, not clever caching or batching: the router is always a small classifier, an embedding lookup, or a matrix-factorization scorer — never a second call to a frontier-class LLM acting as a judge. This is the concrete, verified answer to research question 3: the trap is avoided by construction (router ≪ routed-to model in cost), not by amortization.

**Build now / not yet: build_now as a design constraint, not_yet as a shipped feature.** Kelvran should treat "the router must never be a full LLM call" as a hard constraint for any future routing-intelligence work — cheap to adopt as a principle today — but the router itself still requires the training data named in Finding 2 before it can exist at all.

### Finding 6 — A 2026 paper frames "cold start" (no historical usage data) as its own distinct, real research problem, directly analogous to Kelvran's own no-production-traffic gap, with synthetic data generation as the proposed (not yet broadly adopted) workaround (confidence: medium, split 2-1 vote)

The ACL 2026 paper "Task-Aware LLM Routing with Multi-Level Task-Profile-Guided Data Synthesis for Cold-Start Scenarios" builds its entire contribution around routers generalizing poorly when in-domain training data is unavailable, proposing a hierarchical task taxonomy that synthesizes Q&A pairs to approximate the test-time query distribution — i.e., manufacturing a training set rather than mining real traffic logs. This is a direct structural analog to Kelvran's own situation (no production traffic to calibrate against), but it is a single, very recent (2026) academic paper, not a proven production pattern, and it requires meaningful upfront engineering (a hierarchical taxonomy plus a data-synthesis pipeline) to stand up.

**Build now / not yet: not_yet.** Trigger: worth revisiting only if Kelvran decides the cost of building a synthetic-data-generation pipeline is worth avoiding the wait for real traffic — a scope/cost tradeoff, not a technical blocker, and one this research did not find any production adopter having made yet.

## Caveats

- Quantified real-world payoff numbers for cascade/predictive routing (e.g., "RouteLLM cuts cost >2x," "up to 85% cheaper," "FrugalGPT at 98% lower cost," "AutoMix reaches ~97% of frontier accuracy at ~1/4 cost," "40% fewer large-model calls") were checked adversarially and **did not survive verification** (votes of 0-3 or 1-2 across six separate claims). Treat all such headline savings figures — commonly repeated in blog/marketing coverage of this space — as unverified for this report; only the mechanism descriptions (Findings 1–6) and the specific 0.4%-router-overhead figure (Finding 5) survived at confirmed status.
- Finding 5's underlying claim survived at only a 2-1 (medium-confidence) vote, and a closely related, more sweeping claim ("the routing decision does not eat the savings it creates," as a general conclusion) was separately checked and refuted 0-3 — the *specific measured number* (≤0.4% for RouteLLM's own four architectures) is solid, but do not generalize it into a blanket "routing overhead is always negligible" claim beyond what RouteLLM itself measured.
- Finding 6 rests on a single very recent (2026) paper with a split 2-1 verification vote — treat as the least-settled finding in this report, offered as a structural analogy rather than a load-bearing production precedent.
- No source in this pass discussed Martian or Not Diamond directly (both named in the original research prompt) — this report cannot speak to their specific mechanisms; OpenRouter is the only verified live production router-with-cost-tiers system covered.
- Two claims about RouteLLM's routing signal ("learned from human preference data... baked into a pre-trained router model, not computed live per request") and about the OpenRouter classifier's mechanism being non-embedding/non-judge-based were separately verified in different framings — some redundant claim phrasings were refuted (0-3) even though the underlying mechanism (as stated in Findings 1–2) was independently confirmed via other, more precisely-scoped claims. This reflects claim-phrasing sensitivity, not a real contradiction in the underlying mechanism.

## Recommendation for Kelvran

| Capability | Status | Trigger to revisit |
|---|---|---|
| Discrete cost-tier band filter (OpenRouter-style) over existing WRR/health candidate list | **build_now** | None — needs only existing per-deployment cost data, no training set |
| "Router must be architecturally cheaper than routed-to models" as a design constraint for any future routing feature | **build_now** (as a principle) | None — costs nothing to adopt now, prevents a known trap |
| Learned quality-predicting router (embedding similarity / classifier, RouteLLM/Hybrid-LLM/Tryage-style) | **not_yet** | Real production query + outcome/preference-label data at volume — likely sourced from Kelvran's own evals/judge-panel pipeline once it has enough real traffic and judged outcomes to build a training set |
| Cascade/escalation routing (cheap model first, self-verify, escalate) | **not_yet** | Real query-mix + cost data to size whether escalation rate would actually net-save cost/latency versus Kelvran's existing deterministic fallback chain — same traffic-volume gap named for router-health work |
| Cold-start synthetic-data-generation router (TRouter-style) | **not_yet** | A deliberate scope decision to invest in a data-synthesis pipeline instead of waiting for real traffic — not currently justified by any verified production adoption |

The one concretely actionable v2 item from this research is the discrete cost-tier band: filter Kelvran's existing weighted-round-robin candidate pool by a per-request or per-virtual-key cost tier before applying health/weight selection, using data Kelvran already collects. Everything else in the "quality-cost frontier" space — the actual predictive or cascading routing intelligence the research prompt asked about — remains genuinely not-yet-ready for Kelvran specifically, not because the pattern is unprecedented (it is well-precedented, in both research and, more narrowly, production), but because every real precedent depends on a training/calibration dataset Kelvran does not yet have, mirroring the same production-traffic-volume gap already named and deliberately deferred for Kelvran's traffic-derived health/circuit-breaking work.

## Open Questions

- What would the smallest real dataset look like that Kelvran could use to bootstrap even a simple similarity-weighted or matrix-factorization router (RouteLLM-style) once it has production traffic — could Kelvran's own evals/judge-panel outputs double as the preference-label source, avoiding a separate data-collection effort?
- Is a deterministic, config-driven cost-tier band (Finding 3) sufficient for Kelvran's near-term needs, or will operators want a continuous Pareto-front-style tradeoff (Tryage-style) badly enough to justify the added complexity once traffic exists?
- Given Kelvran already has a deterministic, error-classified fallback chain for reliability, is there real value in also building a quality-based cascade (Finding 4) on top of it, or would that be redundant complexity solving a problem the fallback chain already partially addresses for a different reason?
- Are Martian and Not Diamond (named in the original prompt but not found in this verification pass) doing something meaningfully different from OpenRouter's discrete-tier approach — worth a dedicated follow-up research pass before ruling out a continuous-tradeoff design for Kelvran v2?
