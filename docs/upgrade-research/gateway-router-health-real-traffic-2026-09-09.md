# Blending Real-Traffic Failure Signals into Router Health State — Deep Research (2026-09-09)

## Question

When an LLM gateway has real production traffic (not just synthetic health probes), what's the right way to blend passive (real-request) failure signals into active-probe-based deployment health/routing state, without letting a single client-caused error (a 4xx, a legitimate content-policy rejection) get conflated with a genuine backend health problem?

## Context (Kelvran's own real, current state)

`gateway/internal/router/health.go`'s `Router.ReportProbeResult(name string, success bool) (healthy bool, changed bool)` is already a generic `(name, success)` API with no knowledge of who's calling it — nothing in its signature prevents a real-request outcome from calling it today. In practice it has exactly one call site in the whole codebase: `gateway/internal/gateway/dataplane/dataplane.go`'s synthetic active-probe loop (`Pipeline.ProbeDeployments`/`RunHealthProbeLoop`, per `docs/rfcs/2026-09-07-gateway-active-health-probing.md`).

The health-state machine itself is real and already fairly sophisticated: consecutive-failure/consecutive-success counters against configurable `UnhealthyThreshold`/`HealthyThreshold` (defaults 3/2), a post-recovery weight-ramp (`RecoveryRampSteps`/`RecoveryRampInitialPercent`, defaults 4 steps from 20%→100%, Bresenham-style thinning via `admitRampedTurn`) added specifically to close a documented thundering-herd-on-recovery gap (citing Slack's 2021 postmortem), and probe-interval backoff in `dataplane.Pipeline` (doubles per consecutive unhealthy reschedule, capped at 8x the operator's configured interval, resets on recovery).

This exact question has been named repeatedly across `docs/agents/LOGS.md` as a real, deliberately-deferred gap — most explicitly: "whether/how real-traffic failures should feed router health state (already named as deferred pending a traffic-volume floor)" (LOGS.md line 1455), and earlier: "Router health state is fed only by the synthetic probe loop — real-traffic failures never update it... a concrete pin of `router.go`'s own already-partially-named 'traffic-derived circuit breaker... deferred' scope limit" (LOGS.md line 1445). `health.go`'s own package doc comment states the same reasoning directly: defaults are "deliberately NOT LiteLLM's own aggressive single-failure default, since Kelvran has no production traffic yet to calibrate a more aggressive threshold against."

Kelvran already has a real, reusable error-classification building block elsewhere in the same package: `gateway/internal/gateway/dataplane/fallback.go`'s `classifyFallbackError(err error) string` inspects a (possibly wrapped) `*UpstreamHTTPError`'s status code and body text to bucket a real request failure into `FallbackClassContentPolicy`, `FallbackClassContextWindowExceeded`, or `FallbackClassGeneric` (the catch-all, including rate limits) — proof that "which real-request outcomes indicate a genuine backend problem vs. a client-caused one" is a problem Kelvran's own codebase already solves for a different purpose (fallback-chain routing), not a green-field question.

## Summary

Every production system studied — Envoy, Istio, Linkerd, AWS ALB, Google's SRE book, and the circuit-breaker libraries Hystrix/resilience4j/Polly — draws the same two-part line the research question asks about: (1) a **status-class/error-origin filter** decides which real-request outcomes are even eligible to count as a failure at all (5xx and connection-level failures count; ordinary 4xx does not, by default, everywhere studied), and (2) a **minimum-sample-size ("traffic-volume floor") gate** withholds any statistical action — ejection, circuit-tripping, health-state change — until enough real requests have been observed in the current window, with no separate "low-traffic mode": below the floor, the mechanism simply does nothing, even at 100% observed failure. Google's SRE book independently names the real risk of skipping the floor: routing away from backends that have served errors reduces available capacity and can itself start a load-driven cascading-failure snowball — the mechanism, if not the exact "retry storm" framing, behind the research question's stated worry. For Kelvran specifically, this converges on a concrete, small, and defensible first slice: build the sample-size-gate and status-class filter now (reusing `classifyFallbackError`'s existing types), but do not wire real-traffic outcomes into `ReportProbeResult` at all until Kelvran has real traffic data to set the floor's numeric threshold against — exactly the trigger the deferral itself already names.

## Findings

### Finding 1 — Active (synthetic) and passive (traffic-derived) health signals are treated as genuinely separate mechanisms industry-wide, not two flavors of one thing (confidence: high)

Google's SRE book draws a hard architectural line between "process health checking" (is the binary alive at all — owned by the cluster scheduler) and "service health checking" (can it currently serve this class of request right now — owned by the load balancer). Kelvran's own split mirrors this almost exactly: `router`/`dataplane`'s active-probe loop is a synthetic, traffic-independent signal; a hypothetical passive layer would be the "service health, this class of request" signal the SRE book explicitly assigns to the load-balancer/router layer — i.e., architecturally, `router`/`dataplane` is the *right* place for this, not a layering violation, if/when built. (Vote 2-1 on the underlying primary-source claim — treat with slightly more caution than the unanimous findings below.)

### Finding 2 — The standard filter for "which real-request outcomes are eligible to count as a backend-health signal" is HTTP status class, not "any non-2xx" (confidence: high)

Confirmed independently across three unrelated production meshes/proxies:
- **Envoy** treats only 5xx-class responses (plus connection-level failures) as errors by default — "any other codes are treated as success," explicitly including 4xx.
- **Linkerd**'s circuit-breaking (failure accrual) defines a failure as a 5xx response, or 5xx-or-429 under its "Unified" policy — ordinary 4xx (400, 404, etc., excluding 429) never trips the breaker.
- **Istio**'s `OutlierDetection` exposes separate `consecutiveGatewayErrors` (502/503/504, or TCP connect timeouts/connection failures) and `consecutive5xxErrors` counters, deliberately narrower than "any error."

This is the direct, repeated, cross-vendor precedent for Kelvran filtering by status class rather than treating every non-2xx `UpstreamHTTPError` as health-relevant — a legitimate content-policy rejection or a context-length-exceeded 4xx (both of which `classifyFallbackError` already recognizes and buckets away from generic) must never be eligible to degrade a deployment's health state.

### Finding 3 — A second, orthogonal filter separates connection-level ("local origin") failures from HTTP-response ("external origin") failures (confidence: high)

Envoy's outlier detection explicitly splits errors into "local origin" (connection failures, timeouts — never got a response at all) and "external origin" (an HTTP status code the upstream actually returned) via a `split_external_local_origin_errors` flag, routing to different code paths and, when enabled, different counters. Istio ships the identical concept: `splitExternalLocalOriginErrors` (boolean) plus a distinct `consecutiveLocalOriginFailures` counter (default 5), used only when the flag is set. By default (flag off, in both systems), local- and external-origin failures are folded into one bucket — the split is an opt-in refinement, not a hard requirement everywhere. This maps directly onto Kelvran's own `UpstreamHTTPError` (an external-origin, "we got a response" error type) vs. a network/dial/timeout error from `p.callDeployment` (a local-origin, "never got a response" error) — both are real backend-health-relevant signals, but the precedent shows they are worth keeping conceptually distinct even if Kelvran's first slice doesn't need Envoy's full opt-in split.

### Finding 4 — A minimum-sample-size ("traffic-volume floor") gate is the universal mechanism for keeping low-traffic passive signals from acting at all — not a separate "low-traffic mode" (confidence: high)

This is the single most load-bearing, most repeatedly-confirmed finding, directly answering the research question's #3. Every statistical/passive detector studied enforces a floor below which it simply does not act, regardless of failure rate:

| System | Floor mechanism | Default |
|---|---|---|
| Envoy (Success Rate) | `success_rate_request_volume` (per-host) + `success_rate_minimum_hosts` (cluster-wide) | 100 requests/interval; 5 hosts |
| Envoy (Failure Percentage) | `failure_percentage_request_volume` + `failure_percentage_minimum_hosts` | same shape, separate config |
| Linkerd (Unified policy) | `failure-accrual-success-rate-min-requests` | 5, over a 10s window — documented explicitly as "cold start" protection |
| Hystrix | `circuitBreaker.requestVolumeThreshold` | 20 per rolling window |
| resilience4j | `minimumNumberOfCalls` | 100 per sliding window |
| Polly | `MinimumThroughput` | 100 over a 30s `SamplingDuration` |

Below the floor, the mechanism doesn't switch to a more-cautious alternate mode — it withholds action entirely. Both Hystrix's and resilience4j's own documentation give the identical worked example almost verbatim: 19 (or 9) requests observed, 100% of them failing, and the breaker still does not trip because the request count itself is below the configured floor. This is exactly the shape of Kelvran's own stated deferral reasoning ("no production traffic yet to calibrate... against") — it is not a vague industry norm, it is the specific, named, universally-implemented mechanism for that exact problem.

### Finding 5 — Routing away from backends that have served errors carries a real, named cascading-failure risk if not bounded (confidence: high)

Google's SRE book names the mechanism directly: "Load balancing policies that avoid servers that have served errors can exacerbate problems further... a few backends serve some errors, so they don't contribute to the available capacity for the service. This increases the load on the remaining servers, starting the snowball effect." This is the real-world justification for why every system in Finding 4 gates passive ejection behind a volume floor and (separately) why Kelvran's own `RecoveryRampSteps` weight-ramp exists — both are bounding mechanisms against the same underlying risk (capacity removed from the pool cascading into more load, more errors, more removal). This doesn't literally describe a client-side "retry storm," but it is the closest verified real-world precedent for the research question's stated worry that weighting passive signals too aggressively can amplify a health-state flap.

### Finding 6 — ALB's health-state machine is a real precedent for a bidirectional consecutive-count design, independent of whether a passive component exists (confidence: high, narrowly scoped)

AWS ALB's target-group health uses consecutive-count thresholds in both directions — `UnhealthyThresholdCount` (default 2) consecutive failures to remove a target, `HealthyThresholdCount` (default 5) consecutive successes to restore it — the same N-of-M shape Kelvran's `UnhealthyThreshold`/`HealthyThreshold` already implements. (Note: a broader claim that ALB's mechanism is *exclusively* active-probe-driven with no passive component at all was specifically checked and did not survive verification — treat ALB's passive/active split as genuinely unresolved rather than asserting it either way.)

## Caveats

- Finding 1's underlying claim (SRE book's process/service split as an architectural mandate for *where* this belongs) had a 2-1 verifier vote — directionally solid, but treat with more caution than the unanimous findings.
- A specific claim that ALB has *no* passive/real-traffic health signal at all was checked and refuted — this research draws no conclusion about ALB's passive behavior either way; it is cited here only for its confirmed bidirectional-consecutive-count shape (Finding 6).
- A specific claim about HAProxy drawing an explicit 4xx-vs-5xx classification line in its own configuration manual was checked and refuted — HAProxy is not cited as a source in this report's findings for that reason, even though it is a well-known proxy; do not assume HAProxy precedent beyond what's stated here.
- A claim that AWS's own retry/backoff guidance (Builders' Library) treats HTTP client-vs-server error class as the standard retry-safety signal was checked and refuted, as was a related claim about AWS gating retry amplification on an independent health assessment — do not cite AWS's Builders' Library as a source for this specific mechanism.
- A claim that resilience4j ships a built-in error-classification predicate (`recordExceptions`/`ignoreExceptions`) specifically marketed as the standard way to keep certain error types out of health signals was checked and did not survive verification at the strength claimed — resilience4j's *volume-floor* mechanism (Finding 4) is solidly confirmed; its *error-classification* mechanism is not relied on here.
- All of the confirmed findings are about mature, stable, long-documented mechanisms (Envoy, Istio, Linkerd, ALB, Hystrix, resilience4j, Polly, the SRE book) — low time-sensitivity risk, but Envoy/Istio are still actively-developed projects, so specific default numeric values are worth a quick re-check against current docs before hardcoding them if this is built more than a few months from now.
- No claim in this pass addressed real-world evidence of an actual thundering-herd/retry-storm incident specifically caused by over-aggressive passive-signal weighting in an LLM gateway or general reverse proxy — Finding 5's SRE-book citation is the closest verified precedent, but it describes capacity-reduction cascading, not a literal client-retry-storm mechanism. Treat the retry-storm-specific risk as plausible-by-analogy, not independently verified.

## Recommendation for Kelvran

**Do not wire real-request outcomes into `ReportProbeResult` yet.** The deferral's own stated trigger — a real traffic-volume floor to calibrate against — is not a vague placeholder; it is the exact, named, universally-implemented mechanism (Finding 4) every production system studied uses to keep this class of signal safe, and Kelvran genuinely does not have production traffic to set that floor's numeric value against. Building the wiring without the floor mechanism would reproduce the single failure mode the research question is worried about.

**What would make this safe to build now, if the traffic-volume trigger fires:**

1. **Status-class + origin filter, reusing existing code, not new logic.** Eligibility for a real-request outcome to count as a candidate failure signal at all should be: (a) an `*UpstreamHTTPError` with a 5xx status code, or (b) a local/connection-level failure from `p.callDeployment` (dial error, timeout) — mirroring the unanimous Envoy/Linkerd/Istio precedent (Finding 2) and the local-vs-external-origin distinction (Finding 3). Concretely, this composes with `fallback.go`'s existing `classifyFallbackError`: outcomes it buckets as `FallbackClassContentPolicy` or `FallbackClassContextWindowExceeded` (both necessarily 4xx-shaped, client-caused) must be excluded; only a real 5xx or a local-origin error is even a candidate. This reuses a type (`UpstreamHTTPError`) and a classification path Kelvran already ships and already tests — no new classifier needs inventing.
2. **A minimum-sample-size gate is the mechanism to build, not a specific number to pick yet.** Add a per-deployment rolling window of real-request outcome counts (candidate-eligible outcomes only, per #1), and require it to clear a configurable minimum volume before a passive signal is allowed to influence anything — exactly the Envoy/Linkerd/Hystrix/resilience4j/Polly shape (Finding 4). Given Kelvran has zero production traffic today, the defensible move is to build this gate as a real, tested, inert mechanism now (mirroring how `HealthConfig.normalized()` already resolves conservative defaults for unset config), but default its floor high enough — or require explicit opt-in config — that it cannot fire in practice until an operator has enough real traffic to consciously tune it. This is the same "de-risk the how, wait on the whether/when" pattern already used for hierarchical budgets (`docs/upgrade-research/gateway-hierarchical-budgets-2026-09-07.md`).
3. **Keep passive signals additive, not equally authoritative with active probes, for the first slice.** The safest composition — and the one that best addresses the "avoid a single client-caused error being conflated with backend failure" AND the amplification/snowball risk (Finding 5) in one move — is for a real-request failure that clears both filters above to trigger an out-of-band active probe of that deployment (via the already-shipped `Pipeline.ProbeDeployments`/`probeOneDeployment`) rather than to call `ReportProbeResult` directly itself. This means real traffic can only ever *accelerate* detection of a problem the existing, already-conservative active-probe state machine (N-of-M consecutive, ramp-gated recovery) still has to independently confirm — it never lets a burst of real-traffic 5xxs unilaterally flip health state on its own. This is the orchestrator's own synthesis, not an externally-sourced precedent, but it is a direct, minimal composition of mechanisms this research did verify (status filtering + volume floor + the existing active-probe machinery), and it structurally cannot cause the SRE-book capacity-reduction snowball (Finding 5) since the health *verdict* stays exclusively active-probe-owned.
4. **Watch the interaction with the already-shipped per-request fallback-chain circuit breaker.** `fallback.go`'s `maxConsecutiveChainFailures` (a per-request, ephemeral counter) already reacts to the same real 5xx failures a passive router-health signal would react to, independently, on every single request. Before wiring anything global, explicitly reason about whether these two mechanisms reacting to the same underlying failures at different scopes (per-request vs. cross-request) could interact in a way neither was designed against — this research did not find or verify a specific known failure mode here, but it is a genuinely open question given the two are unaware of each other today.

**Smallest, most defensible first slice:** ship the status-class/origin filter (item 1) and the sample-size-gate primitive (item 2) as real, unit-tested, inert code — not wired to any real call site, exactly like an unused-but-ready mechanism — and leave the actual decision of *when* to connect it to `ReportProbeResult` (or to the out-of-band-probe-trigger design in item 3) gated on the same real traffic-volume signal the existing deferral already names. This mirrors the exact posture the hierarchical-budgets research settled on: refine the "how" now, because it's genuinely cheap and testable to do so, without overturning the "not yet" on the "whether/when."

## Open Questions

- Does Kelvran's per-request fallback-chain circuit breaker (`maxConsecutiveChainFailures`) need to be reasoned about jointly with any future router-level passive signal, or are the two scopes (per-request vs. cross-request) safely independent by construction? Not answered by this research — flagged in Recommendation item 4.
- What is the right numeric floor for Kelvran specifically, once real traffic exists? Every vendor studied picked a different number (20 to 100, over windows from 10s to 30s to unspecified) with no clear cross-vendor consensus on magnitude — this will need Kelvran's own real request-volume data, not a borrowed default.
- Is there real-world evidence, from an LLM-gateway specifically (as opposed to general reverse proxies/meshes), of passive-signal-driven routing amplifying a provider-side outage or rate-limit event into a worse client-facing incident? Not found in this pass — would strengthen or weaken the urgency of the "additive, not authoritative" design choice in Recommendation item 3.
- Should Istio/Envoy's local-origin-vs-external-origin split (Finding 3) be built into Kelvran's filter from day one, or is folding both into one "candidate failure" bucket (as both systems do by default) an acceptable simplification for a first slice? This research surfaces the precedent for both choices but does not resolve which fits Kelvran's own risk tolerance better.
