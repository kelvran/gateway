# Kelvran Gateway — WASM-Based Extensibility for Policy/Plugin Chains (Envoy/Kong/Higress) — 2026 Deep Research

**Date:** 2026-09-22
**Scope:** Evaluating WebAssembly (WASM) as an extensibility mechanism for gateway policy/routing/transform/guardrail logic — specifically the `proxy-wasm` filter-chain ecosystem as implemented by Envoy, Kong Gateway, and Higress — against Kelvran's actual shape (a single-binary, single-maintainer Go LLM gateway). Excludes re-deriving ground already covered by `docs/upgrade-research/guardrail-plugin-extensibility-2026-09-15.md` (that pass answered the narrower "should Kelvran let an outside operator extend `guardrail.Detector` without forking" question via `wazero`/Extism/Starlark/Envoy `ext_authz`); this pass instead evaluates the `proxy-wasm` ABI/filter-chain model specifically — the actual mechanism Envoy, Kong, and Higress use in production — and extends the question to routing-policy and transform logic, not just guardrail detectors.
**Method:** Real external research via `WebSearch`-equivalent (Exa web search) against primary sources — Envoy's own current documentation (envoyproxy.io, `1.40.0-dev` as of this research date), Kong's own engineering blog and GitHub source/PRs, Higress's official docs and its CNCF project page, the `proxy-wasm` spec repo, `wazero`/`proxy-wasm-go-sdk`/`mosn/proxy-wasm-go-host` source and package metadata, and real GitHub issues documenting production failure modes (OOM, body-truncation). Every load-bearing claim below states how many independent primary sources it was cross-checked against; nothing here is asserted as "confirmed" off a single source without saying so.

## Executive summary

The single most consequential finding in this pass is one the original research brief did not anticipate and Kelvran's own prior research (`guardrail-plugin-extensibility-2026-09-15.md`) could not have known at the time: **Kong — one of the three systems this research was explicitly asked to evaluate — removed WASM support from Kong Gateway entirely in version 3.11 (July 2025)**, after two years in beta, replacing it with a native Lua plugin (Datakit) specifically because the new implementation is "considerably more performant and memory efficient" [konghq.com — confirmed 3-0: the vendor's own release blog, its own breaking-changes page, and the GitHub PR that removed the bundled filter]. This is not a hypothetical risk this report is warning about — it is a real, shipped reversal by a production API gateway vendor, on the exact mechanism this research was asked to evaluate, for the exact reason (performance/complexity cost) this report's honesty mandate asked it to weigh honestly. Envoy's own WASM HTTP filter, the ecosystem's oldest and most mature implementation, still carries the label "experimental and is currently under active development" in its current documentation, years after Proxy-Wasm's 2019 introduction [envoyproxy.io — confirmed, current live docs]. The one genuine, thriving counterexample is Higress (Alibaba's Envoy/Istio-based AI-native gateway, CNCF Sandbox since March 2026, real production adopters at 100k+ RPS scale) — but its shape (a multi-tenant plugin marketplace serving many independent application teams, with a console UI, OCI-image plugin distribution, and a dedicated Go/Rust/JS SDK team) is categorically different from Kelvran's (single embedded Go binary, single deployment, single maintainer, per this repo's own settled `DECISIONS.md` framing). Layered onto this is a real, measured performance tax — Google's own estimate puts V8-based Wasm execution at roughly 50% of native performance [solo.io, citing Google's own benchmarks — 1-0, a secondary citation of a primary claim, flagged accordingly below] — and real, documented body/streaming-buffer failure modes (an Envoy OOM bug, a `proxy-wasm-rust-sdk` body-truncation bug reported as recently as August 2025) that would collide directly with Kelvran's own streaming/multi-modal architecture, a capability this repo already treats as a core, shipped differentiator. Taken together, this reinforces — with new, harder evidence than was available on 2026-09-15 — the prior research pass's "not yet" verdict on plugin extensibility generally, and extends it specifically to the `proxy-wasm` filter-chain model: WASM here is solving a problem (safe extensibility for a marketplace of untrusted, polyglot, third-party plugin authors) that Kelvran does not have, at a real, non-hypothetical engineering and performance cost that even Kong itself, a company with a dedicated WASM engineering team, ultimately declined to keep paying.

## Findings, ranked

### 1. Kong removed WASM support from Kong Gateway entirely in 3.11 (July 2025), after two years in beta — the clearest, most concrete real-world data point this research found (Informational — no build action, but load-bearing for the verdict)

**What:** Kong introduced WASM support (the WasmX/`ngx_wasm_module` implementation of the Proxy-Wasm spec) as a beta feature in Gateway 3.4 (August 2023), "Bring Your Own Language with WebAssembly," letting users write filters in Rust, Go, and later JavaScript. It stayed in beta through at least 3.9 (December 2024). In Gateway 3.11 (July 2025), Kong's own release blog states plainly: "we've removed the previous implementation's dependency on WASM. As of 3.11, we're additionally removing WASM support (Beta) from the Gateway as the new implementation addresses the same use cases and is considerably more performant and memory efficient." Kong's own breaking-changes page confirms the same fact under "WASM deprecation": "Support for the beta WASM module has been removed," with the Datakit plugin (the feature that had motivated WASM adoption in the first place) re-implemented as a native Lua plugin instead.

**Why it matters for Kelvran specifically:** Kong is one of the three systems this research's own brief named as the comparators to evaluate WASM against. Finding that one of them tried it in production for two years and then reversed course, citing performance and memory cost, is a direct, checkable answer to the research brief's own honesty requirement ("give an honest verdict... not just 'WASM is cool'"). This is not researcher speculation about hypothetical overhead — it is the vendor's own stated reason for walking away.

**Consistent with settled decisions?** Directly reinforces, with new external evidence unavailable on 2026-09-15, the "not yet" verdict `guardrail-plugin-extensibility-2026-09-15.md` already reached for `wazero`/WASM specifically (that pass's Finding 1 and Recommendation 3). This pass does not overturn anything — it adds a second, harder data point to the same conclusion, from a different angle (a production vendor's real deprecation, not just an unmerged GitHub issue).

**2026 best practice grounding:**
- Kong's own product blog states the removal and its performance/memory rationale in its own words [konghq.com/blog/product-releases/kong-gateway-enterprise-3-11 — primary source, dated 2025-07-09].
- Kong's own breaking-changes documentation independently confirms the same fact in reference-doc form, not just marketing copy: "Support for the beta WASM module has been removed" [developer.konghq.com/gateway/breaking-changes — primary source, current live docs].
- The actual code removal is a real, merged GitHub PR ("chore(wasm): remove bundled datakit filter"), confirming this was an engineering decision executed in the codebase, not just a doc/marketing claim [github.com/Kong/kong/pull/14012 — primary source].
- Cross-checked 3-0 across these three independent primary sources (vendor blog, vendor reference docs, and the actual source-control change) — high confidence.

**Concrete next step:** None — this is evidence to weigh, not an action item. Cite this finding explicitly if the WASM question is ever re-raised for Kelvran, since it directly answers "has anyone actually tried this and regretted it" with a real, named, dated example.

**Effort:** N/A (informational).

### 2. Envoy's own WASM HTTP filter — the ecosystem's oldest, most mature implementation — still self-labels as experimental in its current (2026) documentation, and its stated overhead mechanism (copy-in/copy-out across the VM boundary) is real, not theoretical (Informational)

**What:** Envoy's live documentation for the HTTP Wasm filter (`envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/wasm_filter`, version string `1.40.0-dev` as fetched during this research, i.e. current as of 2026-09-22) states in its own words: "The Wasm filter is experimental and is currently under active development. Capabilities will be expanded over time and the configuration structures are likely to change." Proxy-Wasm as a concept dates to 2019; this caveat has persisted for years, not months.

**Why it matters for Kelvran specifically:** the research brief asked for an honest verdict on "real overhead/complexity tradeoffs, not just 'WASM is cool.'" Reading Envoy's own arch-overview docs directly (not a third-party summary) surfaces the actual mechanism: "Because Wasm is executing in a VM... and that VM does not share memory with Envoy, we have to pay the price of copying the request (including the payload) into and out of the VM for the Wasm program to process it" [Tetrate/Solo.io engineering blog, quoting Envoy's own architecture — 1-0 on the specific framing, but the underlying VM-isolation-implies-copy mechanism is independently corroborated by Envoy's own `arch_overview/advanced/wasm` page describing per-worker-thread VM instances with separate memory]. This is directly relevant to Kelvran, whose gateway already does real per-request body inspection (guardrail detectors run pre-call AND post-call, per `Engine.Check`'s own doc comment, per the prior research pass) — any WASM-hosted equivalent would pay this copy cost on every request, on the hot path, for a Go binary that today does this in-process with zero serialization boundary.

**Consistent with settled decisions?** New evidence, not a re-litigation — the prior guardrail-plugin-extensibility research examined `wazero`'s CPU/memory isolation limits (its Finding 2) but did not examine Envoy's own body-copy overhead framing specifically, since that pass was scoped to detector-plugin extensibility via a bare `wazero` embedding, not the `proxy-wasm` filter-chain model this pass covers.

**2026 best practice grounding:**
- Envoy's own current wasm_filter docs state the "experimental... under active development" caveat verbatim [envoyproxy.io — confirmed, live primary source, current version string].
- Envoy's own arch-overview page confirms the VM-per-worker-thread isolation model that necessitates the copy cost: "the worker threads operate independently and do not share the Wasm execution instances and their runtime memory" [envoyproxy.io/docs/envoy/latest/intro/arch_overview/advanced/wasm — primary source].
- Google's own benchmark estimate that V8-based Wasm execution runs at roughly 50% of native performance is cited via a third-party engineering blog (Solo.io), not fetched directly from a Google-published benchmark in this pass — flagged as **1-0, a secondary citation of a claimed primary source**, not independently re-verified against Google's own benchmark data here.
- A separate, directly-measured data point corroborates real (if smaller) overhead specifically for Go-compiled Wasm plugins: Higress's own contributor-run benchmark (`higress-group/higress` GitHub issue #1768, dated mid-2025) compared TinyGo-compiled vs. native-Go-1.24-compiled `proxy-wasm` plugins under `wrk` load and found the Go-1.24 plugin's average latency 5–27% higher than TinyGo's, depending on concurrency (e.g. 722µs vs. 685µs at concurrency 1, rising to 2.33ms vs. 1.84ms at concurrency 5), with the compiled binary itself ~4x larger (2.46MB vs. 637KB) [github.com/higress-group/higress issue #1768 — a single contributor's own benchmark, not independently reproduced elsewhere in this research pass, so graded **1-0** rather than cross-confirmed, but it is a real, numbers-backed, primary-source benchmark, not a marketing claim].

**Concrete next step:** None — informational context for the overhead half of the "is this worth it" question.

**Effort:** N/A (informational).

### 3. Higress is the one real, thriving, CNCF-recognized WASM-plugin ecosystem found in this research — and it is also the clearest illustration of why WASM's value proposition doesn't transfer to Kelvran's actual shape (Informational; confirms a shape-mismatch, not a build item)

**What:** Higress is a real, production-grade, Envoy/Istio-based "AI-native API gateway," accepted into the CNCF as a Sandbox project on March 15, 2026. Its own CNCF announcement names real enterprise adopters (Alibaba Group, Ant Group, BOSS Zhipin, Cathay Insurance, Ctrip, DJI, Kuaishou, Sealos, Vipshop) and states the project "supports large-scale scenarios with hundreds of thousands of requests per second" in production at Alibaba. It ships 41 official WASM plugins across 5 categories (including AI-specific ones: AI Proxy, AI Agent, AI Search, AI Transformer), supports authoring plugins in Go, Rust, and JavaScript, and — as of Higress gateway v2.1.5+ — migrated its Go plugin toolchain from TinyGo to native Go 1.24 WASM compilation, explicitly to avoid the TinyGo dependency.

**Why it matters for Kelvran specifically:** this is the one genuine, checkable counter-data-point to Finding 1 — it proves WASM-for-gateway-extensibility is not a dead pattern in 2026, just a pattern with a specific shape that fits. That shape, read directly from Higress's own docs, is: a gateway operated as shared infrastructure for many independent internal teams/tenants (a console UI with global/domain-level/route-level plugin configuration precedence, OCI-image-based plugin distribution and versioning, "lossless hot updates" specifically framed as a multi-tenant operability feature) — i.e., exactly the "genuine multi-tenant/untrusted-third-party plugin marketplace" shape the prior guardrail-plugin-extensibility research (its Finding 1) already identified as the real precedent-fit for WASM adoption, and explicitly contrasted against Kelvran's actual shape: single deployment, single maintainer, zero external operators identified.

**Consistent with settled decisions?** Directly confirms, from a second and much stronger real-world example than the closed Envoy AI Gateway GitHub issue the prior pass found, that the prior pass's shape-mismatch reasoning was correct: WASM's value shows up when a gateway operator is serving other people's plugin code, not when a single team owns end-to-end all the logic running in its own gateway.

**2026 best practice grounding:**
- Higress's CNCF Sandbox acceptance and production-adopter list are stated directly on CNCF's own project page and CNCF's own blog post — not just Higress's self-description [cncf.io/projects/higress and cncf.io/blog/2026/03/25/... — confirmed 2-0 across two independent CNCF-authored sources, both dated March 2026].
- The 41-plugin marketplace, AI-specific plugin categories, and multi-language SDK support are read directly from Higress's own official plugin marketplace and "What is Higress" pages [higress.ai/en/plugins and higress.ai/en/docs/latest/overview/what-is-higress — primary source, though single-source since only Higress's own docs were checked for these specific counts].
- The TinyGo→Go-1.24 migration and its stated motivation (avoiding TinyGo as a toolchain dependency) are confirmed via Alibaba Cloud's own AI Gateway documentation and a real Higress GitHub issue discussing the migration and its benchmark tradeoffs [alibabacloud.com/help/en/api-gateway/ai-gateway and github.com/higress-group/higress issue #1768 — 2-0, independently corroborating the same migration from two different Alibaba-affiliated sources].

**Concrete next step:** None for Kelvran directly — this is context, not a mechanism to adopt (see Finding 5 on why "adopt Higress's model" isn't actually available to Kelvran as a lightweight option).

### 4. `proxy-wasm`'s body/streaming-buffer handling has real, recent, documented failure modes that would collide directly with Kelvran's own streaming/multi-modal architecture (Informational — a genuine risk factor, not yet a triggered concern)

**What:** Three independent, real GitHub issues/PRs, spanning 2021–2025, document recurring problems in exactly the area Kelvran's own gateway treats as a core capability (streaming responses across all 5 adapters including tool calls and reasoning blocks, plus multi-modal inline-base64 content already flagged in `gateway-2026-09-06.md`'s Finding 1 as a real, sizeable-payload attack surface): (a) an Envoy Wasm-VM OOM crash when processing larger request/response bodies through a Go/TinyGo-compiled filter, root-caused to a TinyGo heap-growth bug and fixed upstream in TinyGo itself, not in Envoy or the spec (2021); (b) a documented, breaking change in how `body_size` semantics work across repeated `on_http_request_body` callbacks, which caused real double-processing and "not found" buffer-read errors in a production WASM-based WAF (`coraza-proxy-wasm`) until explicitly fixed in a 2023 PR; (c) a live, still-open `proxy-wasm-rust-sdk` issue (filed August 2025) reporting that the `http_body` example silently loses the final chunk of a body larger than roughly 65,500 bytes — a real, current, unresolved data-loss bug in the ecosystem's own example code.

**Why it matters for Kelvran specifically:** Kelvran's own `PRD.md` differentiation thesis and its already-shipped adapter layer both center on real streaming (SSE) and multi-modal content handling — this is not a hypothetical edge case for this specific gateway, it's squarely in the traffic shape Kelvran was built to handle well. If Kelvran ever did adopt a `proxy-wasm`-hosted mechanism for any body-touching concern (a transform plugin, a response-guard, a body-size-aware policy), it would be adopting a subsystem whose own ecosystem has repeatedly shipped and only-eventually-fixed real body-handling bugs, in the exact traffic pattern (large and/or streamed bodies) Kelvran cares most about getting right.

**Consistent with settled decisions?** New finding, not previously examined — the prior guardrail-plugin-extensibility research's `wazero` findings concerned CPU/memory sandbox isolation generically, not `proxy-wasm`'s specific HTTP-body-callback semantics, since that pass evaluated a bare `wazero` embedding for detector plugins, not the full `proxy-wasm` ABI's body-streaming contract.

**2026 best practice grounding:**
- The 2021 Envoy OOM issue and its TinyGo-heap-growth root cause are documented directly in the Envoy GitHub issue thread, including confirmation from a `proxy-wasm-go-sdk` maintainer and the actual TinyGo PR that fixed it [github.com/envoyproxy/envoy issue #14856 and the linked tinygo-org/tinygo PR #1567 — confirmed 2-0, cross-referencing the bug report and its actual upstream fix].
- The `body_size`/chunking semantics bug and its fix are documented directly in a real, merged `coraza-proxy-wasm` PR with detailed before/after logs [github.com/corazawaf/coraza-proxy-wasm PR #252, and its own linked reference to a `proxy-wasm-go-sdk` PR #418 discussing the semantics change — confirmed 2-0].
- The August 2025 body-truncation bug is a single, currently-open issue, not yet confirmed fixed — graded **1-0, and explicitly currently unresolved**, not a closed/historical data point like the other two [github.com/proxy-wasm/proxy-wasm-rust-sdk issue #326].

**Concrete next step:** None today — no trigger exists for adopting a body-touching WASM mechanism at all (see Finding 5). Worth re-surfacing explicitly if that trigger ever arrives, since "the ecosystem's own body-handling semantics have a real bug history" is a genuine, checkable design input at that point, not FUD.

**Effort:** N/A (informational risk factor).

### 5. There is no viable path to host `proxy-wasm` filters directly inside Kelvran's own Go binary without also adopting Envoy or nginx underneath it — the one Go-native host implementation (`mosn/proxy-wasm-go-host`) is stale and ABI-incompatible with the rest of the ecosystem (Informational — closes off a specific architecture option the research brief's framing implied might exist)

**What:** The research brief's framing ("Envoy/Kong/Higress WASM filters... versus whatever Kelvran's existing guardrail-extensibility research already recommends") could be read as implying Kelvran might adopt the `proxy-wasm` filter-chain *model* — reusing its ABI, its SDK ecosystem, its filter-ordering semantics — inside Kelvran's own single Go binary, without actually running Envoy/nginx as a sidecar or replacing Kelvran's own HTTP layer. Checking whether that's a real, available option: the only Go-native (non-Envoy, non-nginx) host implementation of the `proxy-wasm` ABI found in this research is `mosn/proxy-wasm-go-host`, and it is not a viable adoption path today. Its own GitHub issue thread (from its own original author) states directly: "this ABI is intentionally incompatible with other things, in order to support Ant Group" — it is a fork maintained for MOSN's (Ant Group's own service mesh data plane) internal ABI needs, not a general-purpose, spec-compliant `proxy-wasm` host. Its package metadata shows Go 1.14 as the target, 66 GitHub stars, and its most recent tagged release (`v0.2.0`) dates to October 2022 — three years stale as of this research date, with no evidence of active maintenance since.

**Why it matters for Kelvran specifically:** this closes off, with a real checked answer, an architecture option Kelvran might otherwise have assumed existed ("surely someone has built a lightweight, embeddable, Go-native `proxy-wasm` host by now"). It hasn't, in any actively-maintained, spec-compliant form. The real options for "get `proxy-wasm`'s specific filter-chain model into Kelvran" reduce to either (a) putting a real Envoy or nginx/`ngx_wasm_module` instance in front of or beside Kelvran's own gateway as a sidecar — a materially bigger architectural change than "add a plugin mechanism," and one that duplicates request-handling responsibility Kelvran's own Go binary already owns end-to-end — or (b) using `wazero` directly as a bare Wasm-VM embedding without the `proxy-wasm` ABI/ecosystem at all, which is exactly the option the prior guardrail-plugin-extensibility research already evaluated and deferred (its Finding 1), just without the `proxy-wasm`-specific filter-chain/SDK-reuse benefit the research brief was hoping to unlock.

**Consistent with settled decisions?** New finding — directly answers a question the prior research pass didn't need to ask, since it was scoped to a bare `wazero` embedding rather than "can Kelvran reuse the actual Envoy/Kong/Higress plugin ecosystem."

**2026 best practice grounding:**
- `mosn/proxy-wasm-go-host`'s own maintainer, in its own GitHub issue thread, states the ABI-incompatibility fact directly, in the maintainer's own words [github.com/mosn/proxy-wasm-go-host issue #10 — primary source, the project's own author].
- The project's staleness (Go 1.14 target, last tag 2022-10-10, 66 stars) is read directly from its `pkg.go.dev` package page and GitHub repo metadata [pkg.go.dev/mosn.io/proxy-wasm-go-host and github.com/mosn/proxy-wasm-go-host — confirmed 2-0 across the package registry and the repo itself, both showing consistent staleness signals].
- No second, actively-maintained, general-purpose Go-native `proxy-wasm` host was found in this research pass despite explicit searching for one — an absence-of-evidence result, disclosed as such rather than treated as a confirmed "none exists anywhere."

**Concrete next step:** None — this closes an option, it doesn't open one.

**Effort:** N/A (informational).

### 6. Routing/transform policy has zero same-repo extension point today (unlike guardrails' `Detector` interface) — but this is a continuation of Kelvran's existing "not yet" pattern for adjacent asks, not a newly-discovered gap needing WASM or anything else (Small, if a real trigger ever arrives — and it would be a Go interface, not WASM)

**What:** The research brief specifically asked this pass to extend beyond guardrails into "routing-policy/transform logic." Checked directly: Kelvran's router (`gateway/internal/router`, per `DECISIONS.md`'s own framing) and its virtual-key/deployment-config surfaces are entirely declarative today — `AllowedModels`, `AllowedRegions`, cost-tier filtering, sticky/canary hashing, and fallback chains are all config fields an operator sets, not a programmable policy-logic extension point of any kind (no Go interface analogous to `guardrail.Detector` exists for "write custom routing logic"). This is a genuinely different starting position than guardrails, where the prior research found an already-adequate `Detector` interface (its Finding 7) — for routing, there is no interface to compare WASM against at all, same-repo or otherwise.

**Why it matters for Kelvran specifically:** this could be read as a bigger gap than the guardrail one, since there isn't even an in-repo escape hatch today. But `DECISIONS.md`'s own settled deferrals for structurally similar asks — model-provider expansion ("`not_yet` across the board, pending an actual customer ask — no verified urgency trigger exists"), hierarchical org/team-scoped budgets ("repeatedly reaffirmed, no demand signal") — establish a clear, consistent pattern: Kelvran defers config/policy surface-area expansion until a real, named trigger exists, not preemptively. Nothing in this research found a real trigger for programmable (as opposed to declarative) routing policy either.

**Consistent with settled decisions?** Directly continues the pattern named above, rather than reopening it — this finding does not argue routing policy needs a plugin mechanism now; it explicitly declines to, on the same evidentiary standard `DECISIONS.md` already applies elsewhere.

**2026 best practice grounding:** No 2026 external precedent changes this calculus — Envoy, Kong, and Higress all built their WASM routing/transform hooks to serve their own multi-tenant plugin-marketplace shape (Findings 1–3 above), which remains the mismatch, independent of whether the extension point in question is a guardrail detector or a routing rule.

**Concrete next step (only if a real trigger arrives):** a same-repo, Go-interface-based routing-policy hook (mirroring `guardrail.Detector`'s own successful shape) would be the right-sized answer for a same-repo/same-organization extension need — not WASM, for the same reasons Findings 1–5 already establish. This is explicitly a "not yet," matching the prior research pass's own framing for the guardrail side.

**Effort:** Small, if a trigger ever appears — a narrow Go interface is a small, well-precedented addition (see `bedrockguard`'s existing sibling-package pattern) — but there is no trigger today, so no work is proposed.

### 7. Kelvran's existing Redis pub/sub, HMAC-signed config-propagation mechanism already delivers the specific "hot-reload without a restart" benefit WASM's dynamic-loading model is prized for at Envoy/Kong/Higress — for the config surface Kelvran actually has today (Informational; a genuine non-gap)

**What:** A recurring, explicitly-named virtue of the `proxy-wasm` model across all three surveyed systems is hot-swappable logic without a process restart: Envoy Gateway's `EnvoyExtensionPolicy` CRD fetches and reloads WASM modules from an OCI registry or HTTP URL; Kong's (now-removed) filter-chain model rebuilt filter execution plans on config change without a worker restart; Higress's own docs state its Wasm plugin model achieves "lossless hot updates of gateway logic" specifically framed as a headline capability. Checked against Kelvran's own actual architecture: `gateway/internal/gateway/controlplane`'s Redis pub/sub, HMAC-signed config propagation across replicas — already shipped, already covering guardrail policy, virtual-key config (including the region-allowlist fix shipped 2026-09-15), and rate-limit/budget settings — already delivers config changes to every running Kelvran replica without a restart, for exactly the kind of policy/config surface Kelvran actually has today.

**Why it matters for Kelvran specifically:** this is a direct, checkable non-gap. The "hot-reloadable" virtue the research brief asked this pass to weigh as one of WASM's selling points is something Kelvran's existing, already-built mechanism already provides — for config, not for turing-complete plugin *code* — but Kelvran's actual extension points today (guardrail detector selection/policy tiers, virtual-key allowlists, budget caps) are exactly config, not code that needs hot-swapping. WASM's hot-reload benefit is solving for hot-swapping *logic* (a compiled plugin binary), which only matters once there's a real need for operator-authored logic in the first place — which, per Findings 1–6, Kelvran does not have evidence of yet.

**Consistent with settled decisions?** Directly builds on, without contradicting, the real, shipped 2026-09-15 config-propagation work already in this repo — this finding is pointing out that an existing capability already substantially covers one of the stated motivations for the new one being evaluated.

**2026 best practice grounding:**
- Envoy Gateway's `EnvoyExtensionPolicy` CRD and its OCI-image/HTTP-URL WASM fetch mechanism are documented directly on Envoy Gateway's own current docs site [gateway.envoyproxy.io/docs/tasks/extensibility/wasm — primary source].
- Higress's "lossless hot updates" framing is stated directly on its own "What is Higress" page as a named capability [higress.ai/en/docs/latest/overview/what-is-higress — primary source, single-source for this specific phrase].
- Kong's now-removed filter-chain rebuild-on-config-change model is documented in its own `runloop/wasm.lua` source (`rebuild_state`, hashing old vs. new filter-chain state to decide whether to recompile) [github.com/Kong/kong — primary source, direct source read].
- Kelvran's own existing Redis pub/sub config-propagation mechanism is asserted from this repo's own `DECISIONS.md` `[2026-09-15]` entry (second entry) — not independently re-verified against source in this research pass, since it is describing this repo's own already-documented, already-shipped capability rather than an external claim.

**Concrete next step:** None — documenting a genuine non-gap, not proposing work.

**Effort:** N/A (informational non-gap).

## Top 3 do next

Given this is a "not yet, and here's new evidence for why" research pass, there is no build item to prioritize as a top-3 action. The three most decision-relevant things to actually *do* with this research are:

1. **Treat Finding 1 (Kong's own 2025 WASM removal) as the reference data point if this question is ever re-raised.** It is more persuasive than the closed Envoy AI Gateway GitHub issue the 2026-09-15 research found, because it is a real, shipped, vendor-executed reversal with a stated performance/complexity rationale — not an unimplemented feature request.
2. **If a real external-operator trigger for guardrail *or* routing extensibility ever does arrive** (per both this pass's Finding 6 and the 2026-09-15 pass's own open question — "has any real external party ever actually asked to extend Kelvran... without forking?"), route straight to that prior research's recommendation (`canonical/starlark`-style embedded scripting) rather than re-opening the `proxy-wasm`/WASM question — this pass adds confirmation, not a reason to reconsider that recommendation.
3. **Do not adopt any `proxy-wasm`-ecosystem mechanism for body-touching logic** (Finding 4) without first re-checking whether the specific bugs cited here have been resolved upstream — they may well be fixed by the time a real trigger exists, but as of this research date, the most recent one (the Rust SDK body-truncation issue) is still open.

## Caveats

- Several claims in this pass rest on a single primary source rather than 2+ independently cross-checked sources, and are explicitly flagged as such inline: the specific 5–27% Go-1.24-vs-TinyGo latency numbers (a single contributor's own benchmark, not reproduced elsewhere); the "V8 Wasm ≈ 50% of native" estimate (a secondary citation of a claimed Google benchmark, not independently re-verified against Google's own published numbers in this pass); Higress's specific 41-plugin/5-category marketplace count (read only from Higress's own docs).
- The absence of a second, actively-maintained Go-native `proxy-wasm` host (Finding 5) is reported as an absence-of-evidence result from this pass's own searching, not as a definitive claim that no such project exists anywhere — a narrower, more targeted search specifically for very recent (2026) entrants could not be fully ruled out.
- This pass did not examine Cloudflare Workers, AssemblyScript-specific tooling, or any dedicated "AI-gateway WASM plugin marketplace" product beyond Higress in depth — several lower-traffic/smaller vendor blog posts surfaced during this research (e.g. independent projects positioning themselves against Kong/LiteLLM/Portkey with WASM-composable middleware claims) were not verified against primary product documentation or real production adoption evidence strong enough to cite as confirmed findings here, and are deliberately omitted rather than cited on thin evidence.
- Envoy's Null VM mode (Wasm code compiled natively and statically linked into the Envoy binary, per `envoyproxy.io`'s own arch-overview page) is a real, distinct deployment mode that sidesteps the interpreted/JIT-VM overhead discussed in Finding 2 — it was not evaluated as a serious option for Kelvran in this pass because it requires building and shipping a custom Envoy-equivalent binary per plugin change, which reintroduces exactly the "must recompile the host to add a plugin" friction WASM's dynamic-loading model exists to avoid in the first place; noted here for completeness, not pursued further.
- This is a fast-moving space (Kong's own WASM feature went from beta-launch to full removal in under 2 years) — the specific version numbers and dates cited here (Kong 3.4→3.11, Higress's CNCF acceptance date, the Go-1.24 SDK migration) are structural, dated facts as of this research date and are unlikely to reverse, but a "is this still true" spot-check is warranted if this document is read materially later than 2026-09-22.

## Open questions

- Does the specific `proxy-wasm-rust-sdk` body-truncation bug (Finding 4, filed August 2025) get fixed upstream, and if so, does the same underlying issue also affect the Go SDK path Kelvran would actually use if this were ever adopted? Not resolved in this pass — the issue was open, unresolved, at research time.
- Has Kong published (or will it publish) a retrospective explaining the WASM removal in more technical depth than the one paragraph in its 3.11 release blog? A deeper post-mortem, if one exists, would likely contain more specific, reusable lessons than the single paragraph found in this pass.
- Is there a real, load-bearing reason Higress's shape (multi-tenant plugin marketplace) could ever become Kelvran's shape — e.g., if Kelvran itself were ever offered as shared infrastructure to multiple independent internal teams rather than operated single-tenant? This pass found no evidence that's a live possibility, but it's the one condition under which this entire verdict would need to be re-run, not just re-confirmed.
- Would Envoy's Null VM mode's "recompile the host per plugin change" friction actually be worse than Kelvran's own current "recompile the Go binary per detector change" friction (today's actual same-repo-contributor cost, per the 2026-09-15 research's Finding 7)? Not evaluated head-to-head in this pass — flagged only as a caveat, not resolved.
