# Kelvran Gateway — Streaming Transport Protocol Evolution Beyond SSE (2026 Research)

**Date:** 2026-09-22
**Scope:** `gateway/internal/streaming/` — the *transport layer* underneath Kelvran's existing unidirectional token-streaming implementation (real SSE writer/reader, mid-stream runaway guard, mid-stream budget/TPM top-up, streaming timeout, per-request circuit breaker). This is deliberately narrower than the sibling 2026-09-11 report: that report asked "does Kelvran need bidirectional/duplex streaming" (a *feature* question, answered NOT YET for general text-completion, scoped OUT for voice); this report asks "should the existing one-way token stream ride a different wire protocol" (a *transport* question) — WebTransport/HTTP/3/QUIC, gRPC server-streaming, and whether any major LLM provider or gateway has actually moved production traffic off SSE, versus SSE's own real, still-current advantages.
**Method:** Real external research via web search and primary-source fetches (W3C/IETF specs, MDN, Google's own `google-cloud-go` generated gRPC/REST client source, Google AI Developer Forum, an IETF HotRFC slide deck, a live IETF Internet-Draft, and ~12 independent 2026-dated practitioner/vendor sources) cross-checked against Kelvran's own committed code (`gateway/internal/streaming/writer.go`, `gateway/cmd/gateway/main.go`'s server/transport construction, `deploy/k8s/base/`). Grounded first against this repo's own prior streaming research and `DECISIONS.md` before treating anything below as a genuinely new angle.

---

## Executive Summary

Nothing found in this pass changes Kelvran's transport choice: **every major LLM provider (OpenAI, Anthropic, Google Gemini, Cohere, Mistral) still streams tokens over SSE in 2026, and no production LLM gateway (Kong, Envoy AI Gateway, LiteLLM, Portkey) has moved its default token-delivery path off SSE.** The one genuinely new 2026 fact this report surfaces — WebTransport reaching W3C/browser "Baseline" status in March 2026 when Safari 26.4 shipped it — does not change that picture, because WebTransport solves problems (bidirectional low-latency channels, unreliable datagrams, connection migration across network changes) that a one-way, ordered, text token stream simply does not have; multiple independent 2026 sources explicitly reason through this and land on the same "wrong tool" conclusion for LLM token delivery specifically, while recommending WebTransport for genuinely different workloads (cloud gaming, live video, collaborative cursors). gRPC server-streaming for LLM completions is real, shipping infrastructure — not vaporware — but it lives on a different plane than Kelvran's client-facing surface: Google's own `generativelanguage.googleapis.com` ships a real protobuf `GenerativeService.StreamGenerateContent` RPC and a generated Go gRPC client, and Vertex AI's dedicated-endpoint docs explicitly support gRPC + `StreamRawPredict`, but the *public, API-key-authenticated* consumer surface that Kelvran's adapters actually call is REST+SSE (`:streamGenerateContent?alt=sse`), and a real developer-forum thread shows gRPC access to the public endpoint failing outright (dial timeout on the wrong port, no clear public gRPC endpoint documented for API-key auth). The pattern that emerges — SSE for the browser/API-key-facing edge, gRPC reserved for GCP-IAM-authenticated service-to-service traffic — is exactly the split Kelvran itself would need if it ever added gRPC, and there is no signal any provider intends to change that split. One adjacent, code-grounded (not speculative) fact is worth naming even though it doesn't change the SSE-vs-alternatives verdict: Kelvran's own client-facing `*http.Server` (`cmd/gateway/main.go`) calls plain `ListenAndServe()` with no `TLSConfig` and no h2c wiring, meaning the Go process itself only ever speaks HTTP/1.1 — whatever HTTP/2 or HTTP/3 a real client sees today depends entirely on an ingress/load-balancer this repo does not commit a manifest for (`deploy/k8s/base/` has no `Ingress` resource; the one comment referencing "ingress-nginx's own real production default" in `poddisruptionbudget.yaml` describes an assumption about the *deployment environment*, not a resource this repo controls). This is a real, previously-undocumented fact about Kelvran's own listener, but it does not, by itself, justify a change — it means the case for it (if any) belongs at the ingress layer, not inside `gateway/internal/streaming/`.

## Findings, ranked

### 1. No major LLM provider or gateway has moved off SSE for token streaming, and this is not inertia — it is a repeatedly-reaffirmed, load-bearing design choice (Small — documentation only)

**What:** OpenAI, Anthropic, and Google Gemini all deliver streaming completions as `text/event-stream` in 2026 — confirmed directly against Google's own current API docs (`ai.google.dev/api/generate-content`, showing `streamGenerateContent?alt=sse` with a literal `curl -N ... alt=sse` example) and independently corroborated by at least three independent practitioner sources (Zylos Research's 2026-03-28 streaming-architecture report, an IETF HotRFC slide deck, and a 2026-04-19 protocol-decision retrospective) that all list the same provider set using the same transport. Kelvran's own `gateway/internal/streaming/writer.go` already implements exactly this shape (`data: <json>\n\n` frames, a literal `data: [DONE]\n\n` terminal sentinel) — matching, not diverging from, the ecosystem norm.

**Why it matters for Kelvran specifically:** this is the single most important fact for a v2 upgrade-research pass to get right — it means there is no upstream provider protocol change pulling Kelvran toward a transport migration, and no competitor-parity pressure either (unlike the sibling 2026-09-11 report's bidirectional-voice finding, where LiteLLM/Portkey did ship something Kelvran hadn't). A transport migration here would be speculative engineering with no external pull, the same trap the PRD's own "wait for a concrete trigger" philosophy exists to avoid.

**Consistent with settled decisions?** Directly reinforces, rather than revisits, `gateway/ARCHITECTURE.md`'s existing SSE-only design and the sibling 2026-09-11 report's Finding 3 (Anthropic's Messages API is "exclusively unidirectional SSE, including at the error-recovery layer"). No `DECISIONS.md` entry names transport protocol directly, so there is nothing to reopen — this finding closes an open question the prior report's framing left implicit rather than reversing a decision.

**2026 best practice grounding:**
- Google AI for Developers' current live docs show the public Gemini streaming endpoint is `POST /v1beta/{model}:streamGenerateContent` with `alt=sse`, `Content-Type: text/event-stream` — a primary source, not a secondary summary [ai.google.dev — confirmed, primary source].
- Independently, three 2026-dated practitioner/research sources (Zylos Research 2026-03-28, an IETF HotRFC AI-inference-streaming slide deck, tianpan.co's 2026-04-19 protocol retrospective) each independently list the identical provider-transport table (OpenAI/Anthropic/Gemini all on HTTP+SSE) with no disagreement between them [zylos.ai, datatracker.ietf.org, tianpan.co — confirmed 3-0, cross-checked against each other and against Google's own primary docs].
- A live IETF Internet-Draft (`draft-spk-agentproto-llm-stream`, fetched directly) makes the explicit, reasoned argument for *keeping* SSE as transport while standardizing only the JSON payload inside it, citing gRPC's HTTP/2-only requirement as a real proxy-compatibility cost SSE avoids: "SSE degrades gracefully to HTTP/1.1; gRPC and Connect+proto break under HTTP/1-only" [datatracker.ietf.org / santoshpallagatti.github.io — confirmed, primary source, though this is one author's proposal, not a ratified standard — treat the *reasoning* as well-grounded, the *draft's future adoption* as unknown].
- The Model Context Protocol's own maintainers directly debated WebSocket/gRPC vs. SSE and picked SSE specifically because "SSE exists within standard HTTP, and we figured that adopting websockets on average would probably be a bigger lift than supporting SSE for existing web stacks" — a direct quote from an Anthropic MCP maintainer in the protocol's own public design discussion [github.com/modelcontextprotocol/modelcontextprotocol discussion #102 — confirmed, primary source, direct maintainer statement]. This corroborates, from a second independent protocol-design process, the same reasoning Kelvran's own sibling 2026-09-11 report already found in MCP's transport evolution (Finding 4: MCP moved *away* from persistent bidirectional connections, not toward them).

**Concrete next step:** none — this finding's action is to explicitly close the "should we track SSE-successor adoption" open question with a documented NOT YET / re-check trigger (a major provider or gateway announcing a default-path transport change), rather than leaving it implicitly open.

**Effort:** Small — a documentation-only close-out, identical in kind to the sibling report's Finding 5 treatment of voice/multimodal scope.

### 2. WebTransport reached browser Baseline in March 2026 — a genuinely new 2026 fact — but it solves a different problem than LLM token delivery has (Small — documentation only)

**What:** WebTransport (a browser API for multiplexed, optionally-unreliable communication over HTTP/3/QUIC) crossed W3C/browser "Baseline" status when Safari 26.4 shipped support on 2026-03-24, joining Chrome/Edge/Firefox — closing the one real cross-browser gap that previously made it a non-starter for production web use. This is a real, dated, cross-checked fact (independently confirmed by MDN's WebTransport API page, the W3C's own 2026-02-04 Working Draft, and three independent 2026-dated blog/guide sources describing the same Safari-26.4/March-2026 milestone).

**Why it matters for Kelvran specifically:** this is the one transport-layer development in this research area that is genuinely new since Kelvran's last relevant research pass (2026-09-11) — but every source that discusses WebTransport for AI/LLM use cases specifically frames it around **bidirectional, low-latency, partially-unreliable** workloads (cloud gaming frame pushes, live video, collaborative cursors, real-time multimodal *input* streaming) — not one-way text token delivery. One source's own worked example of "AI inference streaming" over WebTransport uses *datagrams* for intermediate/lossy predictions (object-detection bounding boxes, partial transcripts) precisely because losing an intermediate result is tolerable — a property that does not describe LLM chat-completion tokens, where every token must arrive, in order, exactly once. Kelvran's own existing SSE implementation already provides ordered, reliable delivery; WebTransport's headline advantages (no head-of-line blocking across independent streams, unreliable datagrams, connection migration) are not problems Kelvran's single-stream-per-request token delivery has.

**Consistent with settled decisions?** Extends, rather than contradicts, the sibling 2026-09-11 report's verdict structure — that report scoped bidirectional/voice work OUT for lack of an upstream trigger; this finding does the same for WebTransport specifically, for a different but complementary reason (no upstream trigger *and* a structural mismatch between what WebTransport offers and what token streaming needs).

**2026 best practice grounding:**
- MDN's WebTransport API page and the W3C's 2026-02-04 Working Draft both confirm the spec/API is still evolving ("preliminary proposal... likely to change significantly") even after reaching browser Baseline — a real caveat on top of the "Baseline" milestone itself, not just a formality [developer.mozilla.org, w3.org — confirmed 3-0 across MDN/W3C/independent blog].
- Independent 2026-dated sources (laramateo.com 2026-06-25, calmops.com 2026-03-11, kmcd.dev 2026-09-01) all converge on the same guidance: ship WebTransport with a WebSocket/SSE fallback because it rides UDP on port 443, which "plenty of corporate and public networks block," and because server-side tooling/DevTools support still lags the WebSocket ecosystem [confirmed 3-0, independent sources agreeing on the same caveat].
- A 2026-03-28 research report (Zylos) explicitly estimates WebTransport's "expected viable window" for production LLM-adjacent use at "2-3 years" from a 2026 baseline, specifically citing that "no major browser/server ships RFC 9220 (WebSocket-over-HTTP/3) production support as of early 2026" [zylos.ai — one source, treat as a reasoned estimate, not a confirmed fact — lower confidence than the browser-Baseline milestone itself, which is independently 3-0 confirmed].

**Concrete next step:** document this as an explicit, dated NOT YET in the same place the sibling report's voice/multimodal scope-out lives, with a stated re-check trigger: WebTransport is worth revisiting only if Kelvran ever needs to carry something genuinely tolerant of loss/reordering alongside or instead of text tokens (e.g., a future audio/video multimodal *streaming input* path) — not for the existing text-completion token-delivery path, which has no such need today.

**Effort:** Small — a documentation-only close-out.

### 3. gRPC server-streaming for LLM completions is real, shipping, and even Google-native — but it lives behind GCP-IAM auth on a different endpoint than the one Kelvran's Gemini adapter actually calls (Medium — investigation, not implementation)

**What:** Google's `generativelanguage.googleapis.com` service — the same host Kelvran's Gemini adapter targets — has a real, committed `.proto` definition (`google/ai/generativelanguage/v1beta/generative_service.proto`) with `rpc StreamGenerateContent(GenerateContentRequest) returns (stream GenerateContentResponse)`, and Google's own `google-cloud-go` repository ships a fully generated Go gRPC client (`generativeGRPCClient`) alongside the REST client Kelvran presumably already uses — both real, both maintained, confirmed by reading the generated source directly. Separately, Vertex AI's "dedicated public endpoints" docs explicitly state dedicated endpoints support gRPC with a `StreamRawPredict` method and are described as "Generative AI-ready: Streaming and gRPC are supported."

**Why it matters for Kelvran specifically:** this is the most consequential nuance in this report, because the naive version of "does gRPC exist for LLM streaming" is YES, but the naive follow-on "should Kelvran's gateway speak gRPC to Gemini instead of REST+SSE" does not follow from that YES. A real Google AI Developer Forum thread (2025-02-28, still current) shows a developer attempting exactly this — calling `generativelanguage.googleapis.com` over gRPC with an API key — and hitting a connection failure (`dial tcp ...:50051: i/o timeout`), with Google's own forum response redirecting them back to the REST API as "the best source" for this integration. This is consistent with the gRPC surface being real but oriented at GCP-IAM-authenticated, Vertex-AI-style callers (service accounts, dedicated endpoints), not the simple API-key auth flow Kelvran's adapter and most third-party gateways use. It also means switching Kelvran's Gemini adapter to gRPC would trade a working, documented, API-key-authenticated REST+SSE integration for an less-documented gRPC surface with a different auth model — a real cost with no demonstrated latency/throughput benefit specific to Kelvran's own workload, since Kelvran is not the "50 agents making 10 requests/minute against a single persistent connection" service-mesh pattern gRPC's advantages are framed around; it is a per-end-user, per-request proxy.

**Consistent with settled decisions?** No existing `DECISIONS.md` or upgrade-research entry addresses gRPC-vs-REST for upstream adapter calls specifically — this is a genuinely new angle, not a re-litigation, and it lands on NOT YET for the same reason Finding 1 does: no concrete Kelvran-specific problem (latency, cost, or a customer requirement) that gRPC would solve and REST+SSE does not.

**2026 best practice grounding:**
- The `.proto` definition and generated Go gRPC client are primary source, read directly from `googleapis/googleapis` and `googleapis/google-cloud-go` — not a secondary claim [github.com/googleapis — confirmed, primary source].
- Vertex AI's dedicated-endpoint gRPC/streaming support is documented directly on Google Cloud's own docs site [docs.cloud.google.com — confirmed, primary source].
- The forum thread showing a real, unresolved gRPC-connection failure against the public API-key surface is a single data point (one developer, one thread) — real and primary-source, but not independently cross-checked against a second failure report, so treat "gRPC is not practically usable against the public Gemini API-key surface" as **medium confidence**, not 3-0 confirmed, even though the underlying forum post itself is genuine [discuss.ai.google.dev — one source, lower confidence on the generalization].
- A 2026-03-28 research synthesis (Zylos) independently recommends the identical architectural split this finding lands on without prompting: "SSE for browser-facing token delivery; gRPC for internal service mesh (orchestrator ↔ model backend, orchestrator ↔ vector DB)" — corroborating the split from a second, independent source [zylos.ai — confirmed, second independent source agreeing with the forum-thread-derived inference].

**Concrete next step:** none for implementation. If a future concrete trigger appears (e.g., Kelvran itself starts running its own inference backend, or a customer specifically requests a gRPC-native integration path for internal service-mesh use rather than public gateway use), the investigation starting point is Vertex AI's dedicated-endpoint gRPC path (GCP-IAM-authenticated), not a direct gRPC call to the public `generativelanguage.googleapis.com` API-key surface, which the forum evidence suggests is not the intended integration path for third-party callers.

**Effort:** Medium if ever pursued (new auth model per-provider, new adapter code path, no existing Kelvran precedent) — not being pursued now for lack of a trigger.

### 4. Kelvran's own client-facing `http.Server` is HTTP/1.1-only at the Go process level — a real, code-confirmed, previously-undocumented fact, but not something this report can respons­ibly recommend changing without first confirming the deployment environment (Small — investigation only)

**What:** `gateway/cmd/gateway/main.go` constructs the client-facing server as a plain `&http.Server{Addr: cfg.ListenAddr, Handler: ..., ReadHeaderTimeout: 10*time.Second}` and starts it with `server.ListenAndServe()` (no `ListenAndServeTLS`, no `TLSConfig` set on this server, no `golang.org/x/net/http2/h2c` wiring found anywhere in `gateway/`). Go's `net/http` package only negotiates HTTP/2 automatically via TLS ALPN (`ListenAndServeTLS`) or explicit h2c wiring for cleartext — neither is present here, so the Go process itself speaks HTTP/1.1 only. Separately, `newUpstreamTransport()` clones `http.DefaultTransport`, which has HTTP/2 negotiation enabled by default for TLS connections — meaning Kelvran's *outbound* calls to OpenAI/Anthropic/Gemini (all TLS) already get HTTP/2 for free, at zero extra engineering cost, while the *inbound*, client-facing leg does not.

**Why it matters for Kelvran specifically:** several of the SSE-infrastructure concerns this research surfaced (the historical "6 connections per origin" HTTP/1.1 browser limit; TCP head-of-line blocking across concurrent streams on one connection) are specifically *solved* by HTTP/2 multiplexing, per multiple independent 2026 sources — but only if the connection between the actual client and *something* actually negotiates HTTP/2. Whether that happens for Kelvran today is an operational fact this repo cannot answer on its own: `deploy/k8s/base/` contains no `Ingress` resource (only `Namespace`/`Deployment`/`Service`/`PodDisruptionBudget`/`NetworkPolicy`), and the one related comment in `poddisruptionbudget.yaml` references "ingress-nginx's own real production default" as an *assumption about the deployment environment*, not a committed configuration. This means Kelvran genuinely does not know, from its own repo, whether real end users hit an HTTP/2-terminating ingress in front of the pod (in which case this finding is moot for them) or connect over HTTP/1.1 all the way through (in which case the historical per-origin connection-limit concern is real for direct, non-ingress deployments). This is exactly the kind of fact this research brief's own convention asks to be surfaced rather than assumed either way.

**Consistent with settled decisions?** Genuinely new — no `DECISIONS.md` entry, `ARCHITECTURE.md` section, or prior upgrade-research doc addresses the client-facing listener's own HTTP version, as distinct from the many existing documents about SSE *framing* itself.

**2026 best practice grounding:**
- Go's own `net/http` package behavior (TLS-ALPN-only HTTP/2 negotiation absent explicit h2c) is stdlib-documented behavior, verifiable directly from the code read in this pass [pkg.go.dev/net/http — confirmed, direct code+doc read, not a secondary claim].
- Multiple independent 2026 sources (tianpan.co 2026-04-19, speedtesthq.com 2026-05-25) each make the same claim — that HTTP/2 multiplexing already eliminates the historical WebSocket-driven "escape the 6-connection limit" argument for SSE specifically — without prompting each other, since they're written from different angles (a protocol-decision retrospective and an SSE/WebSocket/long-polling comparison guide respectively) [confirmed 2-0, independent sources reaching the same conclusion].

**Concrete next step:** a narrow, low-effort investigation (not a code change) — confirm with whoever operates Kelvran's actual production ingress (this is explicitly outside this repo's own committed manifests) whether TLS/HTTP-2 termination happens there. If it does, this finding is fully mitigated already and needs no further action. If Kelvran is ever deployed without a terminating ingress in front of it (e.g., a bare `LoadBalancer`-type Service, or a minimal/local deployment), enabling h2c (`golang.org/x/net/http2/h2c`) on the client-facing listener would let it multiplex client connections without needing an ingress to do it — but this is speculative until the actual deployment topology is confirmed, and should not be built preemptively per this project's own YAGNI-flavored deferral conventions.

**Effort:** Small for the investigation; Small-Medium for the h2c change itself, if the investigation confirms it's warranted — not undertaken now for lack of that confirmation.

## Caveats

- This report's Finding 2 (WebTransport Baseline) rests on independent confirmation from MDN, the W3C's own spec draft, and three practitioner blogs all dated 2026 — strong corroboration for the *milestone itself* — but the *practical production-readiness* framing ("2-3 years," "server tooling lags," "DevTools can't inspect the traffic") comes from fewer, more loosely-corroborated sources and should be read as a directional consensus estimate, not a hard fact with the same confidence as the Safari-26.4 milestone.
- Finding 3's forum-thread evidence (gRPC dial failure against the public Gemini endpoint) is a single data point from one developer's single thread — real and primary-source, but not independently reproduced or cross-checked against a second failure report in this pass. The broader claim it supports ("the public API-key gRPC path isn't the intended integration route") is corroborated by a second, independent source (Zylos's SSE-for-browser/gRPC-for-mesh recommendation) reaching the same conclusion from architecture-first reasoning rather than the same forum evidence — but neither source is Google stating this policy explicitly in its own docs, so label this **medium confidence**, not confirmed-by-primary-source-statement.
- Finding 4 is deliberately scoped as an investigation, not a recommendation to change anything, specifically because this repo's own committed manifests (`deploy/k8s/base/`) do not include an `Ingress` resource — this report cannot see Kelvran's real production network topology and says so rather than guessing in either direction.
- The IETF Internet-Draft cited in Finding 1 (`draft-spk-agentproto-llm-stream`) is a single author's proposal, not a ratified standard, working group output, or adopted RFC — its reasoning is well-grounded and independently corroborated by other sources reaching the same SSE-over-alternatives conclusion, but its own *future adoption* is unknown and shouldn't be conflated with the underlying reasoning being sound.
- Time-sensitivity: the Safari 26.4 / WebTransport-Baseline milestone (2026-03-24) and the gRPC forum thread (2025-02-28, still live/unresolved as far as this pass could tell) are both real dated data points as of this research's date (2026-09-22), but both areas — browser API maturation and provider auth-surface documentation — are exactly the kind of fast-moving ground worth re-verifying before treating either as permanently settled.
