# Cache Semantic-Embedding Readiness — Deep Research, Round 4 (2026-09-11)

## Question

Is there fresh 2026 evidence that changes the "not yet" verdict on real embedding-based semantic L3 caching — specifically: (1) can Kelvran validate a candidate embedding-similarity gate's value *without* waiting for production traffic, using its own existing static regression corpus or a synthetic paraphrase harness; (2) is there now a genuinely lightweight, Go-embeddable embedding-generation option that didn't exist or wasn't practical before; (3) is there a genuinely lightweight, embeddable ANN library that fits Kelvran's "leaf, provider-agnostic, zero heavy deps" constraint; (4) has 2026 research found a cheap, inline-runnable hard-gate mechanism (e.g. NLI-based contradiction detection) that's better than entity/number/date extraction; and (5) does a 2026 survey of production semantic-caching practice (GPTCache, vLLM, LangChain/LlamaIndex, Portkey, Helicone) surface anything Kelvran hasn't considered? Cache round 3 (2026-09-11, `cache-next-upgrade-round3-2026-09-11.md`) returned a clean negative result on a different, broader set of angles (KV-cache-aware routing, sub-completion caching, budget/SLO linkage, proactive invalidation) — this round checks a narrower, different question the earlier round did not examine at all.

## Context (Kelvran's own real, current state)

L1 exact-match; L2 normalized-match (narrow allowlist: outer whitespace/NFC/trailing-punctuation only); L3-lite pure-stdlib lexical near-duplicate matching (MinHash/Jaccard shingling, `hash/fnv`, zero new `go.mod` entries) behind a hard entity/number/date fingerprint gate, a 24h staleness budget + exact model-ID match, a Jaccard floor of 0.9, and a volatility-keyword bypass scoped to `role=="user"` only — all per-tenant-partitioned, TTL-jittered, guardrail-policy-version cache-busting, with cross-instance duplicate-work telemetry (measurement only). `PRD.md` (line 27) and `AGENTS.md`'s Boundaries section make the hard-gate requirement non-negotiable: "never ship a similarity-based cache layer without the hard-gate," specifically because of the CacheAttack/KeyPooling findings in `THREAT_MODEL.md`. Real embedding-based semantic L3 remains explicitly deferred (`docs/decisions/` via the L3-lite RFC, `STATUS.md`), gated on two things that don't exist yet: production miss-telemetry, and the already-shipped per-gate ablation instrumentation (`kelvran.cache.l3.gate_outcome`) running against real traffic. `evals/tests/fixtures/regression_corpus_cache_adversarial.json` is a real, already-committed 17-case adversarial corpus (part of a 137-case total regression corpus across all categories — verified by direct count, not the research question's approximate figure alone), built and used for eval-gate purposes but not yet used as an offline embedding-gate validation harness.

## Summary

This round is **not a repeat of round 3's clean negative** — it asked a narrower, different question (semantic-L3 readiness specifically) that round 3 never examined, and it surfaces one genuinely new, buildable-now item plus one important reinforcing result that should update Kelvran's own reasoning even though the production feature stays correctly deferred. First, offline/synthetic validation of a candidate embedding-similarity gate — using Kelvran's own static regression corpus extended via LLM-driven paraphrase generation — is a real, already-precedented 2026 technique (FreshCache-Bench, Redis LangCache) that is genuinely buildable now, as a one-off Python analysis script outside the Go binary, with zero dependency on production traffic (Finding 1, **build now**). Second, a rigorous 2026 audit shows a bare cosine-similarity gate catastrophically approves meaning-reversing negation flips (0/56 caught) and — critically — that an NLI-based contradiction-detection drop-in, the most obvious "smarter gate" candidate for research question 4, was tested and performed no better than chance on held-out data; this is new, direct evidence that should be recorded as "evaluated and rejected," not merely "not yet considered" (Finding 2, **not a validated win — record as considered-and-rejected**). Third, the Go-embeddable embedding-generation landscape did not improve in 2026 and arguably narrowed: the one candidate that looked like a pure-Go wrapper (fastembed-go) was archived/abandoned in January 2026, and the two remaining serious options both require a native shared library reached via CGo, unbundled for most platform/arch combinations (Finding 3, **still not yet — reinforced, not overturned**). Fourth, at Kelvran's realistic per-tenant cache scale, no ANN library is actually needed even if real embeddings were ever built — brute-force cosine similarity in pure Go is proven, zero-dependency, and adequate well past Kelvran's likely per-tenant volume, so the real blocker is specifically embedding *generation*, not similarity *search* (Finding 4, **structural clarification, not a blocker resolved**). Fifth, this round found no confirmed primary evidence specifically about GPTCache's, vLLM's, LangChain/LlamaIndex's, or Portkey's/Helicone's own semantic-cache internals — this is reported as an honest gap, not folded into a false negative or false positive (Finding 5, **unanswered — flag, don't fabricate**).

## Findings

### Finding 1 — BUILD NOW: offline/synthetic validation of a candidate embedding gate against Kelvran's own static corpus is real, precedented, and needs zero production traffic

Two independent, primary, 2026-dated sources establish this as a mature, already-executed technique, not a speculative idea: FreshCache (arXiv:2607.04281, Jul 2026) scaled a static, offline benchmark from 8,072 base queries to 31,201 via LLM-driven paraphrase generation, used entirely offline (a precomputed similarity matrix) to score five different semantic-cache-gating strategies against each other with zero live traffic. Redis's LangCache paper (arXiv:2504.02268) went further: it validated embedding-similarity duplicate-detection purely against static, held-out datasets (Quora Question Pairs, a medical Q&A set) with precision/recall/F1 scoring, and — for a domain with scarce real labeled data — built an LLM-driven synthetic pipeline (a paraphrase generator plus a "distinct but related" negative generator, via Qwen2.5-32B) that produced ~35,000 synthetic pairs and, on fine-tuning purely on that synthetic set, delivered a 9-point precision gain and matched/beat OpenAI's own embedding model on a real held-out medical test set — a fully worked, reproducible example of exactly the "cheaply validate the idea before building the production feature" step this research question asks about.

Applied to Kelvran directly: the existing `evals/tests/fixtures/regression_corpus_cache_adversarial.json` (17 cases, part of the 137-case regression corpus) is a ready-made seed set. A one-off, out-of-band Python script (not a `gateway/` runtime dependency — see Finding 3's constraint, which does not apply here since this never ships in the Go binary) can: (a) expand the seed set via an LLM-driven paraphrase-generator + "distinct-but-related" negative-generator pair, mirroring LangCache's own prompt pattern; (b) score a candidate embedding-similarity threshold's precision/recall against that expanded, held-out static set; and (c) — this is the load-bearing part for Kelvran's specific hard-gate requirement — separately score how much of the precision loss a bare threshold produces is actually recovered by layering the *existing* entity/number/date fingerprint gate on top, replicating the audit methodology of Finding 2 directly against Kelvran's own adversarial corpus rather than a generic one. This produces real numbers Kelvran currently has zero of (would a real embedding layer even catch meaningfully more paraphrases than the existing Jaccard/MinHash L3-lite already does, at what precision cost) — genuinely distinct from, and cheaper than, the currently-blocking need for production miss-telemetry to size cache capacity/hit-rate ROI. It does not, and must not, replace the entity/freshness hard gate in the live system either way — it is a design-validation step, not a production build.

**Confidence: high** (two independent, primary, 2026 sources with released methodology and — in LangCache's case — a verified, reproduced results table).

### Finding 2 — Record as "evaluated and rejected," not "unconsidered": NLI-based contradiction detection is not a validated better hard-gate, and the failure mode it would need to catch is empirically severe

A rigorous 2026 audit (arXiv:2608.10216, *Similarity Gates Approve Reversals*, with a released reproducible artifact) found that a production-grade cosine-similarity drift guard caught **0 of 56** meaning-breaking mutations, including a negation/polarity-flip pair — "withhold the study drug" → "administer the study drug" — that scored cosine 0.9608, i.e. would sail through almost any plausible bare-similarity threshold. This is the exact failure class Kelvran's PRD names as the reason a bare similarity threshold must never substitute for the entity/freshness hard gate, and the exact adversarial pattern already present in this session's own `v-adversarial-cache-negation-polarity-flip-drug-administration` test. Critically for research question 4: the same paper tested an NLI-based drop-in as one of several "obvious repairs" to the cosine gate, and it performed **no better** — landing at chance on separately-authored held-out data, the same as an encoder swap and an overlap-conditioned gate. A separate, independent 2025 paper on contradiction detection in RAG systems (arXiv:2504.00180) reinforces this from the other direction: its own proposed approach abandons lightweight NLI/entailment classifiers entirely in favor of full LLM-prompted context validators, explicitly because two-text-at-a-time NLI models can't handle self-contradictions or cross-document conditional contradictions — and its own cost analysis shows the LLM-prompting alternative is *not* cheap or latency-friendly (O(N²)/O(N³) LLM-call blowup even at 20 retrieved documents), i.e. not a candidate for an inline, per-request cache gate either.

Net effect on Kelvran: this is genuinely new evidence this round found (round 3 never examined hard-gate mechanisms at all), and it should change how the "why not NLI" question is documented — not as an unexamined possibility, but as a specific, cited, evaluated-and-rejected option, matching the same "state it plainly rather than smoothing it over" discipline `DECISIONS.md`'s own L3-lite entry already uses for the entity/number/date gate's own lack of formal validation. It also strengthens (does not weaken) the case for Finding 1's offline harness: if Kelvran ever validates a candidate similarity gate, the harness's own held-out set should specifically include negation/polarity-flip pairs like the one this paper surfaces, since a naive precision/recall score on paraphrase-only pairs would miss this exact failure mode entirely.

**Confidence: high** (primary arXiv sources with released corpora/artifacts, corroborating rather than contradicting each other, both directly on-topic for Kelvran's exact adversarial scenario).

### Finding 3 — Still NOT YET, reinforced by fresh evidence: no practical, low-dependency Go-native embedding-generation option exists in Sept 2026, and the option set narrowed rather than improved

Checked three concrete 2026 candidates against Kelvran's static-binary, zero-heavy-deps constraint (the same constraint the original L3-lite RFC cited when it rejected real embeddings for lack of "a mature, statically-linkable Go ML runtime"): (1) **fastembed-go**, the one library that looked like a plausible pure-Go wrapper, was archived by its owner on 2026-01-15 and is now permanently read-only/unmaintained — and even while it was alive, it required the external ONNX Runtime shared library (a separate native C++ dependency, with a manual `ONNX_PATH` env-var fallback), never a pure-Go, zero-dependency solution. (2) **onnxruntime_go** requires CGo and manually loads the ONNX Runtime shared library at runtime (no Python dependency, which is a real plus) — but the module bundles that shared library for only three platform combos (AMD64 Windows, ARM64 Linux, ARM64 Darwin); every other target (including AMD64/i386 Linux and x86 macOS) requires the operator to separately obtain and ship the correct native `.so`/`.dll`/`.dylib`. (3) **ONNX-GoMLX** genuinely avoids both Python and the C++ ONNX Runtime, and does support the standard `all-MiniLM-L6-v2` sentence-embedding model directly — but achieves this via GoMLX's XLA backend, itself a CGo-driven, dynamically-linked, per-platform PJRT plugin (`.so`) that must be downloaded/managed separately, and GPU variants need a separately-installed CUDA toolkit. None of the three is a genuinely zero-heavy-dependency, pure-Go option; the field's one real "just a Go package" candidate died in the exact window this round is checking. This directly reinforces — rather than overturns — the original L3-lite RFC's rejection of real embeddings, now with fresh, dated 2026 evidence rather than an assumption carried forward from 2026-09-03.

The already-documented mitigation (named in `docs/upgrade-research/cache-next-upgrade-2026-09-09.md`, not new this round) remains the correct shape if this is ever built: a co-located gRPC sidecar for embedding generation, matching Kelvran's own dormant `grpcserver`/`grpcclient` Cache-extraction adapters structurally even though they weren't built for this purpose — isolating the native/CGo dependency in a separate process so a bad embedding model can only crash the sidecar, never the main gateway binary.

**Confidence: high** for fastembed-go's archived status and onnxruntime_go's bundling gaps (3-0, direct primary-source + live API verification); **medium-high** for ONNX-GoMLX's own no-Python/no-ONNX-Runtime claim (2-1 vote — the dissent centers on whether avoiding Python/ONNX-Runtime specifically still counts as "heavy" given the XLA/PJRT native dependency, not on the underlying fact pattern).

### Finding 4 — Structural clarification: at Kelvran's realistic scale, no ANN library is needed even if real embeddings were built — the blocker is generation, not search

Three 2026-current, embeddable (non-server) vector-similarity options were checked against Kelvran's "leaf, zero heavy deps" constraint: **chromem-go** is a genuinely pure-Go, zero-third-party-dependency, in-process (SQLite-like, no client-server) vector store — but its only implemented similarity search is exhaustive/brute-force cosine comparison; HNSW/IVFFlat ANN indexing is roadmap-only, unimplemented as of the current HEAD (commit from 2026-09-06). **sqlite-vec** is pure C, zero dependencies, runs anywhere SQLite runs including via a pure-Go CGO-free WASM driver — but its own documented default usage pattern is brute-force `ORDER BY distance LIMIT N`, with real ANN indexing (IVF, DiskANN) still experimental/not enabled in its 2026 releases. **kelindar/search** is explicit and self-documented about the real ceiling for this pattern: its own README states brute-force search is appropriate up to roughly 100,000 entries, past which it recommends switching to a real ANN algorithm.

The implication for Kelvran: L3's cache is already per-tenant-partitioned and LRU-bounded (per `gateway/ARCHITECTURE.md`'s Cache Subsystem section) — a per-tenant candidate set for a similarity search is highly unlikely to approach anywhere near a 100,000-entry ceiling in realistic usage. This means that *if* a real embedding-based L3 is ever built, it would not need a genuine ANN library or vector database at all — a pure-Go, zero-dependency brute-force cosine-similarity loop (chromem-go's own proven pattern, or a hand-rolled equivalent using the same SIMD-dot-product approach kelindar/search already demonstrates) is sufficient and fits the "zero heavy deps" constraint cleanly. This narrows, rather than resolves, the real blocker identified in Finding 3: the dependency cost that killed real embeddings in the original L3-lite RFC is specifically about turning text into a vector (embedding *generation*), not about comparing vectors once they exist (embedding *search*) — a distinction the original RFC's research did not have separated out this cleanly.

**Confidence: high** (3-0 votes on chromem-go's brute-force-only status and kelindar/search's documented ceiling; 2-1 on the precise bundled-binary detail of one supporting source, which doesn't affect this finding's core claim).

### Finding 5 — Open gap, not a negative result: no confirmed 2026 evidence surfaced on GPTCache's, vLLM's, LangChain/LlamaIndex's, or Portkey's/Helicone's own semantic-cache internals specifically

The adversarial verification pass produced primary-source-confirmed evidence on Redis's LangCache (a direct current-generation GPTCache-class competitor/successor, Finding 1) and on FreshCache-Bench's own baseline comparison set, which name-checks "SemanticTTL/GPTCache-style" caching as one of five baselines it benchmarks against — but nothing was confirmed this round about GPTCache's own current (2026) architecture, vLLM's own semantic-caching layer (if any exists at the inference-engine level, distinct from KV-cache reuse already ruled out of scope by round 3), or LangChain/LlamaIndex's or Portkey's/Helicone's own semantic-cache feature implementations specifically. This is reported honestly as an unanswered research question rather than folded into either a false "nothing else exists" conclusion or a fabricated finding.

**Confidence: n/a — explicitly unanswered this round.**

## Verdict vs. Round 3

This is **not** a repeat of round 3's clean negative result. Round 3 checked a different set of angles entirely (KV-cache-aware routing, sub-completion caching, cache-aware budget/SLO linkage, proactive invalidation) and correctly found every one of them either structurally inapplicable to a hosted-API gateway or exploratory-only — that verdict is untouched by this round and still holds. This round asked the narrower question of semantic-L3 embedding readiness specifically, which round 3 never examined, and found: one genuinely new, concrete, buildable-now item (Finding 1 — an offline validation harness using Kelvran's own regression corpus, needing zero production traffic, and zero changes to the Go binary's dependency footprint); one important piece of new reinforcing evidence that changes how an already-correct decision should be documented (Finding 2 — NLI is now evaluated-and-rejected, not merely unconsidered); and confirmation, with fresh dated 2026 sources, that the underlying dependency-cost blocker (Finding 3) not only persists but narrowed (fastembed-go's death), while a previously-conflated concern (needing an ANN library) turns out not to be a real blocker at all (Finding 4). The production feature itself — real embedding-based semantic L3 — remains correctly deferred, gated on production miss-telemetry and per-gate ablation data that still don't exist; nothing here overturns that.

## Caveats

- Finding 1's offline harness produces precision/recall numbers on a *synthetic/static* corpus, not real production traffic — it validates whether the *idea* is worth production investment (and calibrates what a candidate threshold/architecture might look like), it does not replace the production miss-telemetry trigger that's still required before building the feature itself, and does not by itself resolve the cache-capacity/ROI sizing question (a separate, traffic-dependent concern).
- The `Similarity Gates Approve Reversals` paper (Finding 2) is a single-author preprint about one month old at research time — real, with a released artifact and internally consistent, rigorous methodology, but not yet independently replicated or peer-reviewed.
- ONNX-GoMLX's "no Python/no ONNX-Runtime" claim (Finding 3) is accurate as far as it goes but should not be read as "no heavy native dependency" — it substitutes a CGo-driven XLA/PJRT native shared library for the ONNX Runtime one, which is a different, not necessarily lighter, dependency shape; this was the one 2-1 vote in this round's evidence.
- Finding 4's scale argument (no ANN needed) is an inference from Kelvran's own architecture docs (per-tenant, LRU-bounded L3) combined with third-party libraries' self-documented ceilings — it is not validated against Kelvran's own real per-tenant cache-size distribution, which doesn't exist as production data yet (the same underlying gap this whole feature is blocked on).
- Finding 5 is a genuine gap in this round's coverage, not evidence that nothing exists at GPTCache/vLLM/LangChain/LlamaIndex/Portkey/Helicone — a dedicated follow-up pass targeting those five names specifically would be needed to close it.

## Recommendation for Kelvran

1. **Build now (low-cost, no production-traffic dependency, no PRD-gate risk)**: a one-off, out-of-band Python analysis script (lives in `evals/` or a scratch/research location, never in `gateway/`'s Go dependency graph) that extends `evals/tests/fixtures/regression_corpus_cache_adversarial.json` via an LLM-driven paraphrase+negative-generator pair (following LangCache's own prompt pattern), then scores a candidate embedding-similarity threshold's precision/recall on that held-out set both bare and layered with the existing entity/freshness fingerprint gate — explicitly including negation/polarity-flip adversarial pairs per Finding 2. This produces real numbers Kelvran currently lacks, without touching production code, without needing production traffic, and without weakening the hard gate at any point.
2. **Update the decision record, not the code**: document NLI-based contradiction detection as "evaluated in the 2026 literature and found no better than the existing bare-similarity failure mode it would replace" (Finding 2) rather than leaving it as an unexamined future option — this is a documentation-only action with no runtime change.
3. **No action on the embedding-generation dependency question**: the "no mature, statically-linkable Go ML runtime" conclusion from the original L3-lite RFC is reinforced, not overturned, by fresh 2026 evidence — the field narrowed (fastembed-go's death) rather than improved. If/when the production-telemetry trigger ever fires, the already-documented gRPC-sidecar mitigation (matching Kelvran's own dormant Cache-extraction adapters) remains the right shape — nothing new to design here.
4. **Drop "ANN library" from the future-feature's dependency-cost concern**: if real embedding-based L3 is ever built, Finding 4 shows a genuine embeddable ANN library isn't needed at Kelvran's realistic per-tenant scale — a pure-Go, zero-dependency brute-force cosine-similarity comparison (chromem-go's proven pattern) is adequate. This simplifies, rather than adds to, the eventual design's dependency footprint.
5. **Open, not closed**: a dedicated follow-up pass specifically targeting GPTCache's, vLLM's, LangChain/LlamaIndex's, and Portkey's/Helicone's own current semantic-cache architectures (Finding 5) would be needed before claiming a complete 2026 competitive survey on this specific sub-topic.
