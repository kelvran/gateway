# Security Posture Beyond Supply-Chain — Research (2026-09-13)

**Scope:** Kelvran's supply-chain-security work (`govulncheck`/`pip-audit` dependency scanning, SHA-pinned Actions, cosign-signed/SBOM-attested/SLSA-L2-provenance-attested `ghcr.io/kelvran/gateway` images, admin-API audit logging, Bedrock Guardrails `PROMPT_ATTACK`) is already real and shipped — see `docs/upgrade-research/supply-chain-security-2026-09-13.md` and is **not** re-litigated here. This report covers the four adjacent, currently-unaddressed control surfaces named in the research brief: (1) code-level SAST, (2) secret scanning, (3) container image hardening, and (4) branch protection / OpenSSF Scorecard — each checked directly against the live repo and its config, not assumed.

**Ground truth verified live this pass (not carried over from the source research):**
- `gh api repos/kelvran/gateway/branches/main/protection` → `404 Branch not protected`. `main` has **zero** branch protection today.
- `gh api repos/kelvran/gateway --jq .security_and_analysis` → `secret_scanning: disabled`, `secret_scanning_push_protection: disabled`, `dependabot_security_updates: disabled` (repo `visibility: public`, confirmed in the same payload).
- `grep -niE "codeql|semgrep|sast" .github/workflows/*.yml` → no matches. No code-level static scanner runs anywhere in CI today; only `govulncheck`/`pip-audit` (dependency/CVE-database scanners, not source-code scanners).
- `gateway/Dockerfile` read directly: multi-stage build, final stage `FROM scratch`, no `USER` instruction, no `HEALTHCHECK`, `ENTRYPOINT`/`CMD` already in exec (JSON-array) form. `docker-compose.yml`'s `gateway` service sets no `user:` or `read_only:` key either. Container runs as root with a writable root filesystem, and nothing anywhere sets otherwise.
- Grep for raw SQL / DB drivers in `gateway/` source turned up nothing real (only false-positive matches on Go's `select` statement keyword) — consistent with `AGENTS.md`'s disclosed "Postgres not used by any shipped code today." Classic SQL-injection is not a live attack surface here.

## Executive Summary

Three of the four control surfaces researched are real, checkable, **zero-cost, zero-dependency gaps that can be closed today**: GitHub's native secret scanning + push protection is free for public repos but is currently *disabled* on `kelvran/gateway` despite the repo being public since 2026-09-03; no code-level SAST scanner (CodeQL is the natural, native-Go+Python, free-for-public-repos fit) runs anywhere in CI; and `gateway/Dockerfile`/`docker-compose.yml` run the container as root with a writable filesystem, which a `USER`/`--read-only` addition would fix without touching the already-correct exec-form `ENTRYPOINT`/`CMD`. Branch protection on `main` is genuinely unprotected (confirmed via a live `404`) and OpenSSF Scorecard would flag this as a High-risk finding — but full PR-required-review ceremony is defensible to defer for a single-maintainer project with no external contributors yet; a minimal Tier-1 protection (block force-push/deletion) costs nothing and closes the sharpest edge of that gap regardless. Adding `ossf/scorecard-action` (free, Apache-2.0, one workflow file, auto-updating README badge) would both surface all of the above in one standardized score and specifically reward CodeQL/SonarCloud — not plain Semgrep — on its SAST subcheck, which matters for tool choice if the score itself is a goal.

## Findings

### Finding 1 — No code-level SAST scanner exists in CI; CodeQL is the free, native-fit choice now that the repo is public
**Confidence: high** (4 merged claims: [0] 3-0, [1] 2-1, [2] 2-1, [14] 3-0)

Grep-confirmed: `.github/workflows/ci.yml` and `evals-judge-nightly.yml` run `govulncheck` and `pip-audit` only — both are dependency/CVE-database scanners (they compare manifest versions against advisory data), not source-code analyzers. CodeQL is a genuinely different, complementary layer: it "treats code like data" and analyzes the source itself for vulnerability *patterns*, and it natively supports both Go and Python (plus GitHub Actions workflow files as a scannable target) — no separate tool needed per language for this polyglot repo. Cost is the deciding factor for tool choice: CodeQL is free to run on public repositories but requires a paid GitHub Code Security license (~$30/committer/month, the successor to the old bundled GHAS price) on private ones; Semgrep is free/OSS-capable everywhere regardless of repo visibility. Since `kelvran/gateway` is confirmed public today, that cost distinction doesn't currently bite — CodeQL is fully free to adopt right now via a native, one-click GitHub Actions setup.

Classic SQL-injection detection — the most commonly cited CodeQL/Semgrep win — is not relevant here: this codebase has no raw SQL or DB driver usage (confirmed by grep, consistent with `AGENTS.md`'s disclosed non-use of Postgres). What a source-level scanner *would* still catch that `golangci-lint`/`ruff` don't: taint-tracking of secrets/credentials into logs or responses, SSRF-shaped patterns in the gateway's upstream-URL handling, unsafe deserialization, and — notably — CodeQL's dedicated Actions-workflow query pack, which analyzes `.github/workflows/*.yml` for the exact script-injection class this project already found and hand-fixed once this week (binding `github.*` context through `env:`). A standing CodeQL Actions scan would catch that class proactively rather than requiring a human/security-review pass to notice it.

**Verdict: build now.** Add `github/codeql-action` with `languages: go, python` (plus the default `actions` query pack) as a new CI job. Zero cost on this public repo, no build-system changes required beyond what `go build`/`pip install` already does for the existing jobs, and it directly covers a gap `govulncheck`/`pip-audit` structurally cannot.

### Finding 2 — GitHub's native secret scanning + push protection is free and available, but is currently *disabled* on this now-public repo
**Confidence: high** (claim [3], 3-0, cross-checked against a live `gh api` call, not just documentation)

Secret scanning covers a repo's *entire* Git history across *all* branches for known secret-type patterns (API keys, tokens, passwords), not just new commits on the default branch. It's a free feature for public repositories — but, confirmed directly via `gh api repos/kelvran/gateway --jq .security_and_analysis`, it is **not automatically on**: `secret_scanning`, `secret_scanning_push_protection`, and `secret_scanning_validity_checks` all show `status: disabled` on `kelvran/gateway` right now, despite the repo having been public since 2026-09-03. This isn't a hypothetical gap flagged by a general claim about GitHub's feature set — it's the literal, current, live setting on this exact repo. `dependabot_security_updates` is also shown `disabled` in the same payload, a closely-related free control worth flipping on in the same pass even though it's outside this brief's four named surfaces.

Whether to *additionally* stack a dedicated CI-run scanner (gitleaks/trufflehog) on top of GitHub's native full-history coverage is a weaker claim — the specific "OWASP recommends a dedicated tool as a distinct control from native scanning" claim split 1-2 on adversarial review and shouldn't be treated as settled guidance. Given native secret scanning already covers full history on all branches for free, a second CI-run scanner is a genuine but lower-priority addition, not an urgent one.

**Verdict: build now** (enabling native secret scanning, push protection, and Dependabot security updates — one `gh api`/Settings-page toggle each, zero cost, zero CI changes, zero dependency). **Not yet** for a dedicated CI-run secret scanner (gitleaks/trufflehog) stacked on top — the case for it is weaker evidence and native coverage is already comprehensive; revisit if a real secret-exposure incident recurs.

### Finding 3 — `gateway/Dockerfile` runs as root with a writable filesystem; both are real, fixable-without-breaking-anything gaps
**Confidence: high** (5 merged claims: [4] 2-1, [5] 3-0, [6] 3-0, [7] 3-0, [8] 3-0)

Directly confirmed by reading `gateway/Dockerfile` and `docker-compose.yml`: the final stage is `FROM scratch` with no `USER` instruction anywhere (so the container runs as root/UID 0, Docker's default) and no `read_only`/`--read-only` setting in either the Dockerfile or the compose file's `gateway` service (so the root filesystem is writable). OWASP's Docker Security Cheat Sheet names an unprivileged user as "the best way to prevent privilege escalation attacks" (via `USER` in the Dockerfile, `-u` at `docker run`, or Kubernetes `runAsUser`) and a read-only root filesystem (`--read-only` + `--tmpfs` for any genuinely-needed scratch space) as a second, independent hardening rule; Docker's own official Dockerfile best-practices guide states the same non-root recommendation directly ("if a service can run without privileges, use `USER` to change to a non-root user").

Neither fix requires a base-image change or breaks anything currently relied on: `ENTRYPOINT ["/gateway"]` / `CMD ["-config", "/config.yaml"]` are already in exec (JSON-array) form, and there is no `HEALTHCHECK` directive at all — so there is no shell-dependent instruction anywhere in this Dockerfile that a non-root/read-only switch could break. `scratch` itself has no `/etc/passwd`, but Linux only needs a numeric UID/GID at the kernel level (no passwd entry required) — `USER 65532:65532` (the same "nonroot" convention distroless images use) works directly on `scratch` today. Separately: `scratch` is already more minimal than even the smallest distroless base (`gcr.io/distroless/static-debian13`, ~2 MiB, itself ~50% of Alpine's size and <2% of full Debian) — so the base-image choice here is not the gap; distroless would be a *lateral* move (same minimality, but adds a `:debug` shell variant if one is ever needed for troubleshooting), not an upgrade. A generic Docker "use `scratch` for compiled binaries" best-practices claim was checked and did **not** survive verification as something Docker's own docs assert (0-3, refuted) — so this Dockerfile's `scratch` choice should be credited to Kelvran's own `ARCHITECTURE.md`-driven design decision, not to a Docker-endorsed pattern; either way it doesn't need to change.

**Verdict: build now.** Add a numeric `USER 65532:65532` (or similar) to the Dockerfile's final stage — likely requires creating the binary with correct ownership in the builder stage first — and add `read_only: true` (plus a `tmpfs:` mount if the gateway process needs any writable path, e.g. for temp files) to `docker-compose.yml`'s `gateway` service and to any production deploy manifest. Neither change touches the existing exec-form `ENTRYPOINT`/`CMD` or requires a base-image swap.

### Finding 4 — `main` has zero branch protection (confirmed live); a minimal Tier-1 rule is a real, no-ceremony win today, but full PR-gating is fair to defer
**Confidence: high on the mechanism, medium on the recommended scope** (claims [9]+[12] merged, both 3-0 — same Scorecard Branch-Protection check described from two source pages)

`gh api repos/kelvran/gateway/branches/main/protection` returns a live `404 Branch not protected` — this is not an assumption, it's the actual current state. OpenSSF Scorecard has a dedicated **Branch-Protection** check rated **High** risk that specifically evaluates this: its tiers run from blocking force-push/branch-deletion (Tier 1, the cheapest, lowest-ceremony rule) up through required reviewer approval, required status checks, 2+ reviewers/code-owner review, and admin-only settings (Tiers 2-5). A repo with today's literal zero-protection setting would score 0/10 on this High-weighted check if Scorecard were run against it.

However, the stronger framing claims around this — that enabling protection *automatically* disables force-push/deletion as a baseline effect, that "require pull request reviews" alone is what actually converts a direct-push workflow into a PR-gated one, and that OWASP treats a mandatory non-bypassable PR gate as a baseline SCM control — all **failed** adversarial verification (1-2, 0-3, 0-3 respectively). Concretely: GitHub's branch protection settings are independent toggles, not a package deal with sensible defaults, and "require pull request reviews" does not by itself block a repo admin from pushing directly unless "do not allow bypassing the above settings" is *also* explicitly checked. This matters for Kelvran specifically, since the single maintainer's entire workflow today is direct pushes to `main` — a naively-configured "require PR reviews" rule could either do nothing (if bypass is allowed for admins, the status quo continues unaffected) or immediately block the maintainer's own workflow (if bypass is disallowed), depending on a setting easy to get wrong without testing it.

**Verdict: split.** **Build now:** a Tier-1-only rule (block force-push, block branch deletion on `main`) — this closes the sharpest, cheapest edge of the gap (accidental/malicious history rewrite) without touching anyone's workflow, given CI already holds `packages:write`/`id-token:write`/`attestations:write` on every push to `main` and the repo is now public. **Not yet:** required-review/required-status-check PR gating (Tier 2+) — genuinely reasonable to defer for a single-maintainer project with no external contributors, but disclosed as a real, live, currently-unmitigated risk rather than an assumed non-issue; named trigger: onboarding a second committer, or opening the repo to external PRs.

### Finding 5 — OpenSSF Scorecard is a free, zero-infrastructure addition that would surface Findings 1-4 in one standardized score, and specifically rewards CodeQL/SonarCloud (not Semgrep) on its SAST subcheck
**Confidence: high** (claims [9]/[12] SAST+Branch-Protection weighting, [10] cost/mechanics, [11] SAST detection logic, [13] structured results — all 3-0)

`ossf/scorecard` is Apache-2.0 licensed with no paid tier, runnable as a GitHub Action, standalone CLI, or REST API; enabling `publish_results: true` in the Action produces a README badge that updates on every push-triggered run. Its **SAST** check (Medium risk) and **Branch-Protection** check (High risk) map directly onto Findings 1 and 4 above — running Scorecard today would independently confirm both gaps in a standardized, externally-recognized score rather than this report's own ad hoc grep/API checks. One concrete, actionable nuance for tool choice: Scorecard's SAST check detection logic specifically looks for the `github-code-scanning` app (i.e., CodeQL), the SonarCloud app, or `github/codeql-action` in workflow files or recent merged PRs — a claim asserting this same check would credit a plain Semgrep CI run was **refuted** (0-3). If Kelvran wants Finding 1's SAST addition to also move its Scorecard score, that means CodeQL (or wiring Semgrep's SARIF output through GitHub's code-scanning integration) is what counts — a bare `semgrep ci` step alone would not register. Scorecard also exposes granular, probe-level ("Structured Results," 44 probes as of the source article) JSON beyond the aggregate 0-10 score, intended for piping into a custom policy engine (OPA/Rego) for accept/reject decisions — a more advanced capability than Kelvran's current single-maintainer scale needs today.

**Verdict: build now** for adopting `ossf/scorecard-action` + README badge (zero cost, one workflow file, directly surfaces Findings 1-4 in a standard external format). **Not yet** for building custom OPA/Rego policy enforcement on top of Scorecard's structured probe results — genuinely useful only once there's a policy to enforce beyond "read the badge."

## Caveats

- Several plausible-sounding claims failed adversarial verification and are deliberately excluded from the findings above rather than smuggled in as soft caveats: CodeQL requiring a build step vs. Semgrep not (0-3); GitHub secret scanning being "automatic" on public repos (0-3 — it's free but opt-in, confirmed by this repo's own live `disabled` state); Docker's own docs specifically recommending `scratch` for compiled binaries (0-3); branch protection auto-disabling force-push as a baseline effect (1-2); "require PR reviews" alone converting a direct-push workflow to PR-gated (0-3); OWASP treating protected branches + mandatory PR review as a baseline SCM control (0-3); Scorecard crediting a bare Semgrep run on its SAST check (0-3); and CodeQL's native GHAS integration (Copilot Autofix, Security Overview) being unambiguously superior UX to Semgrep (1-2). Where relevant, the corrected/weaker reading is folded into the finding text above rather than treated as settled.
- Finding 4's split verdict rests partly on general GitHub branch-protection mechanics (independent toggles, admin-bypass interacting with "require reviews") that are stable, uncontroversial platform behavior, not fast-moving — but the *specific configuration* that would suit Kelvral's single-maintainer workflow without accidentally locking the maintainer out was not itself tested live against this repo in this pass; treat the Tier-1-only recommendation as the low-risk subset, and test any Tier 2+ change in a scratch repo first before applying it to `kelvran/gateway`.
- The research brief's item (6) — "anything else a 2026 AI-infra-gateway-specific survey would flag" — did not surface any additional confirmed claim beyond the five findings above (prompt-injection defenses were explicitly out of scope per the brief and are already covered in `THREAT_MODEL.md`). This is reported as a negative result, not as proof no further gap exists — it means this specific research pass's sourcing didn't surface one, not that a more targeted future pass couldn't.
- The `dependabot_security_updates: disabled` finding was discovered via the same live `gh api` call used to verify secret scanning, not from a sourced/voted claim in the original research corpus — it's included because it's directly checkable, free, and adjacent to Finding 2, but it wasn't independently adversarially verified the way the other findings were.
