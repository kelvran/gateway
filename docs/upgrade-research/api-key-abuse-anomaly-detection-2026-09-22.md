# Kelvran Gateway — Real-Time API-Key Abuse/Fraud/Anomaly Detection Research (2026-09-22)

**Date:** 2026-09-22
**Scope:** `gateway/internal/identity/` — the virtual-key identity/verification layer (`identity.go`, `boltstore/`, `redisstore/`) and its live-mutation surface in `gateway/internal/gateway/dataplane/dataplane.go` (`RotateVirtualKey`, `UpsertVirtualKey`, `DeleteVirtualKey`, `checkRateLimit`, `checkConcurrency`) and `gateway/internal/admin/admin.go` (`POST/DELETE /admin/virtual_keys/{name}`, `POST /admin/virtual_keys/{name}/rotate`). This is explicitly **distinct** from Kelvran's existing content-focused Guardrails (`internal/guardrail`'s PII/prompt-injection regex+embedding/ML detection, already covered in `THREAT_MODEL.md` and `docs/upgrade-research/ai-security-hardening-tier1-2026-09-20.md`) — the question here is detecting anomalous **usage patterns** of a legitimate-looking but compromised or abused credential: sudden new geography/IP, credential leakage into public code, and spend/volume spikes distinct from content scanning.
**Method:** Direct primary-source research — official vendor documentation (GitHub, Anthropic, OpenAI, AWS, Google Cloud, Microsoft Azure, LiteLLM, Portkey, Okta, Auth0, Ping Identity, Cloudflare) plus named security-research firms' own original incident writeups (Sysdig, Permiso, Wiz, Palo Alto Networks Unit 42, GitGuardian, Truffle Security, FortiGuard Labs) and Anthropic's own first-party threat-intelligence disclosure. Every claim below is cross-checked against at least 2 independent sources where the topic allows it (noted per finding); grounded against Kelvran's own current `internal/identity` code, `THREAT_MODEL.md`, and the prior `docs/upgrade-research/gateway-security-threatmodel-round4-2026-09-11.md` Finding 4 (which already asked a narrower version of this question — "anomaly-triggered key suspension" — and found only Kong's rate-limiting docs, concluding "NOT YET, industry-wide gap"). This report re-asks the question with a wider net (GitHub's partner ecosystem, AWS GuardDuty, Google Cloud, Azure, and the IAM/CIAM world's own established anomaly patterns) and finds the prior "NOT YET, industry-wide" verdict was **too broad** — it is now false for at least three named providers.

**2026-09-22 addendum (this revision):** the findings and incident record below were extended in a second pass run as part of a 10-way parallel adversarial research sweep (each claim independently voted 3x before inclusion; 13 of the sweep's claims survived unanimous or 2-1 verification and are folded in below — Findings 7-8, the Finding 1/6 enrichments, and two new Real-incident-record entries). Nothing from the original pass was removed; additions are marked inline. 11 additional claims from the same sweep were explicitly refuted on re-verification (a $46k/day Bedrock-quota cost-spike figure, an AntiBotGW impossible-travel/geo-denylist feature that does not actually exist in that project, unverified LiteLLM-supply-chain-compromise specifics, and others) and are deliberately excluded rather than cited — see Caveats.

## Executive summary

The prior round's verdict — that automatic anomaly-triggered key suspension is an unshipped, industry-wide gap — does not survive a wider search. **Three concrete, currently-shipping mechanisms exist that Kelvran's own `identity` package has zero equivalent of.** First, GitHub's secret-scanning partner program is a mature (since 2018, OpenAI/Anthropic since 2021), 40+-partner pipeline that detects a leaked LLM-provider API key in a public repo and reports it to the issuing provider within seconds, and both Anthropic and OpenAI have their own documented auto-revocation response to it — this is the "credential leaked to a public repo" half of the question, answered definitively, not speculatively. Second, AWS GuardDuty AI Protection (GA 2026-07-14) ships a real ML-based anomaly baseline *per IAM identity* for Bedrock/SageMaker model invocations — flagging "invocation from an unusual IP address, an unusual API, or an unusual model" as `Impact:IAMUser/AnomalousModelInvocation`, and anomalous token-volume spikes as a separate `Impact:IAMUser/CostHarvesting` finding — which is precisely the "sudden new geography/IP pattern" and "spend/volume spike distinct from content scanning" detection this research was asked to find, shipped by a major cloud provider, not a research prototype. Third, both OpenAI and Google Cloud ship **automatic, provider-triggered credential quarantine/disablement** the moment a key is confirmed leaked or behaving anomalously (AWS's `AWSCompromisedKeyQuarantine` family; Google Cloud's `iam.serviceAccountKeyExposureResponse` org policy, default-on since 2024-06-16), independent of and prior to any content check.

The real incident record is extensive and unambiguous that this is a live, monetized threat class, not a theoretical one: "LLMjacking" (Sysdig's own term, coined May 2024) has grown from an opportunistic $46,000/day cost-harvesting technique against stolen AWS credentials into, per a 2026 Cloud Security Alliance research note citing Pillar Security Research, a structured criminal marketplace ("Operation Bizarre Bazaar") averaging ~972 attacks/day between 2025 and January 2026. GitGuardian's own 2026 "State of Secrets Sprawl" report — the entity that does the scanning, not a secondary summary — measured 1,275,105 AI-service secrets leaked on public GitHub in 2025 alone (+81% YoY), a category growing faster than any other secret type they track.

Against this backdrop, Kelvran's `internal/identity.VirtualKey` has genuine, concrete, and currently-real gaps: no IP/geography field anywhere in the struct or the dataplane request path (confirmed by a repo-wide grep — `RemoteAddr`/`X-Forwarded-For`/`geo`/`ClientIP` appear nowhere outside two unrelated PII-regex country-code comments in `internal/guardrail`), no per-key usage baseline of any kind, and no automated-suspension trigger distinct from the existing static `BudgetUSD`/`RateLimitBurst`/`MaxConcurrentRequests` caps. Everything that exists today (`BudgetWarnPercent`'s log-only warning, `PreviousKeyHash`'s grace-period rotation, the admin API's manual `POST /admin/virtual_keys/{name}/rotate`) is either a static, operator-declared threshold or a manually-triggered action — never something the gateway itself notices and reacts to from the shape of live traffic. This is a real, currently-open, and now well-precedented gap, not a speculative one — three separate named providers (AWS, OpenAI/Anthropic via GitHub, Google Cloud) ship a version of exactly this for their own first-party credentials.

## Findings, ranked

### 1. GitHub's secret-scanning partner program: mature, fast, and already covers every major LLM provider (Small-Medium — a Kelvran-side integration, not new infrastructure)

**What:** GitHub partners with 40+ token issuers (as of a 2021 changelog entry; the roster has only grown since) to scan every public-repo commit for a leaked credential and forward it directly to the issuing provider for automatic revocation — end-to-end, GitHub's own 2021 blog post states this "takes just a few seconds." The current supported-patterns table (`docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns`, confirmed live) lists Anthropic (both `anthropic_api_key` and a separate `anthropic_admin_api_key` pattern), OpenAI (`openai_api_key`, with token-version support), Google (`google_api_key`, plus a newly-added `google_gemini_api_key` pattern per GitHub's own September 2025 changelog), Cohere, Mistral AI, and Hugging Face — all marked as Partner=✓ with push-protection and, for several, live validity checks and extended metadata (leaked-key owner name/email, added 2025-10-28).

**Why it matters for Kelvran specifically:** this is the direct, provider-side answer to "credential-leakage detection... GitHub secret-scanning partnerships that detect leaked API keys in public repos" named explicitly in this research's brief — and it already exists, today, for every upstream provider credential Kelvran's adapters call out to (OpenAI, Anthropic, Google/Bedrock's third-party models). What it does **not** cover is the layer directly below it: Kelvran's own `VirtualKey.KeyHash` is a credential Kelvran itself issues (per `identity.go`'s own package doc comment), and no external partner program scans for *that* — a leaked Kelvran virtual key would need to be caught by Kelvran itself, or not at all.

**Consistent with settled decisions?** Additive. `THREAT_MODEL.md`'s Value Chain/Information Security row already credits "GitHub-native secret scanning + push protection" as enabled on the repo itself (protecting Kelvran's *own* source, e.g. the AWS credential that leaked into an agent transcript per `AGENTS.md`'s Gotchas) — this finding is about a structurally different thing: the partner program protecting *third-party callers'* virtual keys and upstream provider keys, which is a product capability question, not a repo-hygiene one, and has no existing row anywhere in `THREAT_MODEL.md` or `SECURITY.md`.

**2026 evidence, cross-checked 3 ways:**
- GitHub's own docs (`docs.github.com`, "Secret scanning" concept page, confirmed live 2026-09-22): *"When a partner secret is detected, we notify the provider so they can take action, such as revoking the credential... if a secret matching one of GitHub's supported partner patterns is leaked in a public repository, GitHub automatically reports the leak to the secret provider, who may immediately revoke the secret."*
- Anthropic's own support article (`support.claude.com/en/articles/9767949-api-key-best-practices-keeping-your-keys-safe-and-secure`, confirmed live): *"Anthropic has partnered directly with GitHub to provide an extra layer of protection for our users through GitHub's Secret scanning partner program... If a Claude API key is detected in a public GitHub repository, GitHub immediately notifies Anthropic. To prevent potential abuse, Anthropic automatically deactivates the exposed API key. The affected user receives a detailed email notification."*
- OpenAI's own GitHub-changelog-era confirmation (github.blog, 2021-06-08, "RubyGems, Adobe and OpenAI are now GitHub secret scanning integrators"): *"From today, GitHub will scan every commit to a public repository for exposed... OpenAI API keys. We will forward any keys we find to the relevant service, who will automatically disable them and notify their owners."* Independently, OpenAI's own current Help Center article on API key safety confirms the live-usage side of the same posture: rotate immediately if leaked, and (see Finding 3) offers IP allowlisting as a complementary control.
- Google Cloud runs a structurally identical mechanism for its own service-account keys, confirmed directly on Google's own blog (see Finding 2) — "working in close partnership with secret-scanning programs at public repositories including Github and Gitlab."
- **(Added 2026-09-22)** GitHub's partner-secret path is explicitly separate from its user-facing alert UI: GitHub's own current secret-scanning docs (`docs.github.com/code-security/secret-scanning/about-secret-scanning`) state partner secrets "are reported directly to the provider and aren't displayed in your repository alerts" — the notify-the-issuer pipeline is a silent, out-of-band channel, not something a repo owner sees first. GitHub's coverage of this pipeline is still actively growing month over month: an August 7 2026 changelog entry (`github.blog/changelog/2026-08-07-secret-scanning-coverage-updates`, live-verified) added **Lovable Labs** as a new partner (secret type `lovable_api_key`, same detect-and-forward mechanic) and simultaneously expanded **push-protection-by-default** — real-time, block-on-commit enforcement, not just after-the-fact detection — to four more secret patterns including an LLM-adjacent one, Mistral AI's `mistral_ai_api_key`, extending automatic commit-blocking to free public repos for all four.
- **(Added 2026-09-22)** GitHub separately ships a **Credential Revocation REST API** (GA 2025-04-29, still current and unauthenticated as of this research date per `docs.github.com/rest/credentials/revoke`) that lets *anyone* — not just the token's owner — submit an exposed GitHub personal access token (found in a public repo or anywhere else) for revocation, unauthenticated, in bulk (up to 1,000 tokens per request, 60 requests/hour). On a valid submission GitHub automatically revokes the token, writes an `oauth_access.revoke` entry to the *owner's* audit log, and emails the owner at their account's primary address — full detect-report-revoke-notify closure with zero owner action required, and critically, the reporter does not need to own or even authenticate as the affected credential. This is GitHub's own PAT-specific analog of the same "report-and-auto-revoke" shape that GitHub relies on partner providers (Finding 1's Anthropic/OpenAI quotes) to build for LLM-provider keys — no equivalent public, unauthenticated "someone else can report my leaked virtual key for auto-revocation" surface exists anywhere in Kelvran's own `internal/identity`/admin API today, nor could it, since `POST /admin/virtual_keys/{name}/rotate` and `DELETE /admin/virtual_keys/{name}` are both gated behind the Admin credential per `admin.go` — a deliberate, correct design choice for a self-hosted gateway (there is no public GitHub-style ecosystem to receive third-party reports from), but worth naming explicitly as the reason this specific GitHub mechanism has no portable equivalent for Kelvran, unlike Findings 2/3/4 below.

**Concrete next step:** this finding does not change what upstream-provider keys need — GitHub/Anthropic/OpenAI/Google already do this. What it motivates for Kelvran is the missing mirror-image capability for Kelvran's own virtual keys: an operator-facing, Kelvran-native equivalent of "scan for my own issued credential leaking somewhere, and auto-revoke." Since `VirtualKey.KeyHash` is the SHA-256 digest of a Kelvran-issued secret (never a third-party format GitHub's regex patterns would recognize), this cannot be outsourced to GitHub's program the way an OpenAI key can — it would need either (a) a documented recommendation that operators run a generic secret-scanner (Gitleaks, TruffleHog) against their own repos for the virtual-key prefix/shape Kelvran issues, or (b) if virtual keys are ever minted with a recognizable static prefix (e.g. `kelvran_vk_...`, mirroring `sk-ant-...`/`sk-...`), a path to Kelvran running its own outward secret-scanning sweep (GitHub code search API, or a TruffleHog-style public-commit crawl) for that prefix — a real, non-trivial build, not proposed as urgent here.

**Effort:** Small for documenting the "your virtual keys are not covered by any third-party partner program, use Gitleaks/TruffleHog on your own repos" operator guidance; Large/Unscoped for Kelvran running its own outward GitHub-scanning sweep.

### 2. AWS GuardDuty AI Protection: a real, shipping ML anomaly baseline per IAM identity for LLM invocations — the closest thing to "answered yes" in this entire research pass (Large, but a strong design template)

**What:** GuardDuty AI Protection (general availability 2026-07-14, per AWS's own "What's New" post) analyzes CloudTrail data events from Bedrock/Bedrock AgentCore/SageMaker AI and generates three finding types. Two of the three are genuine usage-pattern anomaly detectors, not content scanners:
- `Impact:IAMUser/AnomalousModelInvocation` — GuardDuty "establishes a baseline of normal model invocation activity for each IAM identity and AWS account," profiling features including (per AWS's own finding-type documentation, quoted verbatim) *"invocations from a previously unseen IP address, a previously unseen user agent, or a model that the identity has never invoked."* This is the exact "virtual key suddenly used from a new geography/IP pattern" scenario named in this research's brief, shipped as a production ML detector, not a proposal.
- `Impact:IAMUser/CostHarvesting` — a separate baseline of average input/output token volume per identity/account; GuardDuty fires when observed token counts deviate significantly, "correlated with other unusual signals" — the "sudden spend/volume spike" half of the brief, explicitly distinguished by AWS's own docs from content-based detection.
The third finding type, `Impact:IAMUser/PromptInjection.Direct`, is content-based (requires Bedrock Guardrails) and is the one AWS capability that overlaps Kelvran's existing Guardrails scope — correctly excluded from this report's focus.

**Why it matters for Kelvran specifically:** this is a full, working reference architecture for exactly the capability class this research was commissioned to investigate, built by the single largest cloud LLM-hosting provider, live as of two months before this research date. It directly falsifies the prior round's "NOT YET, industry-wide gap" verdict (`gateway-security-threatmodel-round4-2026-09-11.md` Finding 4) — that finding checked only Kong's product marketing pages for the keywords "anomaly, suspend, abuse, compromised" and found nothing; it never checked AWS's own security-service documentation, which is where this capability actually lives (as an adjacent cloud-security product, not a feature of the LLM gateway product line itself). The prior finding's own "named trigger to revisit: ...6-12 months" has effectively already fired, 11 days after that round's publication date.

**Consistent with settled decisions?** New — no existing row in `THREAT_MODEL.md` or `SECURITY.md` addresses per-identity behavioral baselining of Kelvran's own virtual-key traffic. `internal/identity.VirtualKey.AllowedRegions` is the closest existing concept, and it is a fundamentally different mechanism: an *operator-declared, static* allow-list checked against a deployment's own `Region` field (fails closed when unknown, per that field's own doc comment) — not an *observed, per-key baseline* of which IPs/geographies a given key has actually been used from historically. AllowedRegions answers "is this deployment allowed for this key," never "does this request's origin look like this key's normal origin."

**2026 evidence, cross-checked 2 ways (both AWS's own docs, independently confirming the mechanism at two different documentation layers):**
- AWS GuardDuty AI Protection overview page (`docs.aws.amazon.com/guardduty/latest/ug/ai-protection.html`, confirmed live): *"GuardDuty uses an anomaly detection machine learning (ML) model to analyze the collected events and establish a baseline of normal model invocation activity for each IAM identity and AWS account. GuardDuty generates a finding when it detects activity that deviates significantly from this baseline."*
- AWS GuardDuty AI Protection finding-types reference page (`docs.aws.amazon.com/guardduty/latest/ug/findings-ai-protection.html`, confirmed live, quoted above) — independently corroborates the mechanism at the per-finding-type level, including the explicit remediation guidance: *"If the activity is unexpected for the associated identity, the credentials might have been compromised... You can also restrict access to the Amazon Bedrock invocation APIs for the affected identity."*
- Independently, an AWS-Samples GitHub-hosted "Threat Technique Catalog for AWS" (`aws-samples.github.io`, a semi-official AWS reference, not the GuardDuty docs themselves) separately describes GuardDuty as containing "integrated detections for LLM Abuse based on anomalous behavior" — a third, independent confirmation that this is a named, documented AWS capability rather than a single doc page's overstatement.

**Concrete next step (not proposed as immediate — Large effort, needs its own design pass):** the transferable design pattern for Kelvran's own `internal/identity`/`internal/gateway/dataplane` is a per-`VirtualKey.ID` behavioral baseline (recent-IP set, recent-user-agent set, per-model invocation history, rolling token-volume average) computed from data Kelvran's dataplane already has at every request (the same request path that already resolves `vk *identity.VirtualKey` in `checkRateLimit`/`checkConcurrency` has access to the inbound `http.Request`, which today is never inspected for `RemoteAddr`/`X-Forwarded-For` anywhere in the codebase — confirmed by a repo-wide grep returning zero matches outside two unrelated PII-regex comments). A finding that deviates from that baseline could feed the *existing* `dataplane.Pipeline.RotateVirtualKey`/`DeleteVirtualKey` machinery (already wired to the admin API's `POST /admin/virtual_keys/{name}/rotate` and `DELETE /admin/virtual_keys/{name}` routes) rather than requiring new revocation plumbing — the mutation path already exists; only the trigger does not.

**Effort:** Large — a new baselining subsystem (per-key IP/UA/model/token-volume history, a genuinely new kind of state Kelvran does not currently track anywhere), plus a policy decision on false-positive tolerance (AWS's own docs concede "the credentials *might* have been compromised" — probabilistic, not certain). Not proposed for immediate build; named here as the single most concrete, best-precedented design template surfaced by this research.

### 3. IP allowlisting: the one usage-pattern control OpenAI ships today that Kelvran's own virtual keys have no equivalent of (Small — directly portable)

**What:** OpenAI ships IP allowlisting as a first-party, documented feature (`help.openai.com/en/articles/20001201-ip-allowlisting-for-the-openai-api` and the newer `developers.openai.com/api/docs/guides/ip-allowlist`, both confirmed live and consistent with each other): an organization or project can restrict which source IPs/CIDR ranges may present a given API key at all — *"Requests from IPs not on the allowlist are rejected, even if they include a valid API key"* — returning `401`/`ip_not_authorized`. OpenAI's own docs are explicit about what this is and isn't: *"IP allowlisting can help reduce risk by restricting where API requests originate, but it does not fully prevent all forms of misuse. It should be used alongside other security best practices."* This is a preventive control, not a detector — it does not "notice" an anomaly, it structurally forecloses one entire class (a leaked key used from an IP the legitimate caller never uses).

**Why it matters for Kelvran specifically:** Kelvran's `VirtualKey` struct already has the identical shape of control for two other dimensions — `AllowedModels` (model allow-list) and `AllowedRegions` (deployment-region allow-list) — both empty-means-unrestricted, both enforced at request time in the dataplane. An IP/CIDR allow-list on `VirtualKey` would be the same pattern applied to a third dimension Kelvran currently has zero code touching at all (per Finding 2's grep result). Unlike Finding 2's ML baseline (which requires new observational infrastructure and tolerates false positives), an IP allowlist is operator-declared and deterministic — the same posture `AllowedModels`/`AllowedRegions` already use — making it the lowest-effort, most architecturally-consistent gap to close of everything in this report.

**Consistent with settled decisions?** Directly analogous to, and a natural sibling of, `AllowedRegions`'s own fail-closed design (added per `docs/upgrade-research/data-residency-regional-routing-2026-09-15.md`'s finding) — no existing decision or scope-out in `PRD.md`/`DECISIONS.md` touches source-IP restriction specifically, so this is a new capability, not a revisit.

**2026 evidence, cross-checked 2 ways:** OpenAI's Help Center article and the newer `developers.openai.com` guide independently describe the identical mechanism (CIDR-range allowlist, per-project or per-org scope, up to 15-minute propagation delay, `ip_not_authorized` error code) — consistent cross-referencing within OpenAI's own documentation set at two different URLs/eras, not a single unverified page. The same Help Center's "Best Practices for API Key Safety" article separately cross-links to it as control #7 in an ordered list of key-safety measures, alongside key rotation and secret-manager usage — confirming it is treated by OpenAI as a standing, current recommendation, not a deprecated or beta feature.

**Concrete next step:** add an optional `AllowedSourceCIDRs []string` (or equivalent) field to `identity.VirtualKey`, enforced in the same dataplane request path that already resolves the caller's `vk *identity.VirtualKey` — checked against `r.RemoteAddr`/the trusted-proxy-adjusted `X-Forwarded-For` value (the latter needs its own trust-boundary decision: which upstream proxies, if any, Kelvran trusts to set that header, since it is trivially spoofable by an untrusted client otherwise). Empty/nil means unrestricted, mirroring `AllowedModels`/`AllowedRegions` exactly.

**Effort:** Small-Medium — the `VirtualKey` field and dataplane check itself is small; the `X-Forwarded-For` trust-boundary decision (does Kelvran sit behind a load balancer/reverse proxy that sets this header, and is that infrastructure itself trusted) is the one piece requiring a real design decision, not just code.

### 4. Provider-triggered automatic key quarantine (AWS, Google Cloud) — the "leaked key gets disabled before a human acts" pattern, with real speed data (Medium — informs *policy*, not directly portable code)

**What:** Two major providers automatically disable a credential the moment it's confirmed leaked, with no human step in between detection and action:
- AWS's `AWSCompromisedKeyQuarantine`/`V2`/`V3` managed policies (confirmed directly via `docs.aws.amazon.com`) are auto-attached to an IAM user's credentials when AWS's own detection (which includes, but is not limited to, GitHub/GitLab secret-scanning notifications) flags them — denying a broad set of actions (by V3: EC2 launch, IAM privilege changes, S3 bucket/policy mutation, several Bedrock/SageMaker actions, KMS key deletion, and more) while leaving existing resources running. Palo Alto Networks' Unit 42 ran a controlled experiment (their own "EleKtra-Leak" research, `unit42.paloaltonetworks.com`, cross-checked against the AWS quarantine-policy docs themselves) and measured this directly: **AWS applied the quarantine policy within 2 minutes of an intentionally-leaked key appearing in a public GitHub repo**, and a real threat actor began reconnaissance against the (still-quarantined) credential 2 minutes after that — a from-the-source empirical timing measurement, not a vendor marketing claim.
- Google Cloud's `iam.serviceAccountKeyExposureResponse` organization policy constraint (Google's own Cloud Security blog, `cloud.google.com/blog/products/identity-security/automatically-disabling-leaked-service-account-keys-what-you-need-to-know`, 2024-05-15) defaults new and existing organizations to `DISABLE_KEY` (auto-disable on detected exposure) as of 2024-06-16, replacing an opt-in `WAIT_FOR_ABUSE` posture — Google's own framing: *"Google Cloud might detect a particular service account key has been exposed in a public repository and you can rely on this new capability to automatically disable the leaked key."*

**Why it matters for Kelvran specifically:** this is the automated-response half of the question, distinct from Finding 1's detection half — both AWS and Google demonstrate that once a leak (or, per Finding 2, an anomaly) is detected, the credible 2026 posture is to act automatically and notify after, not to alert-and-wait-for-a-human. Kelvran's own admin API already has the exact mechanical hook for this (`DELETE /admin/virtual_keys/{name}`, `POST /admin/virtual_keys/{name}/rotate`, both already wired end-to-end) — what's missing is any automated caller of that hook; today both routes are exclusively human/operator-triggered via the Admin credential.

**Consistent with settled decisions?** New. Nothing in `THREAT_MODEL.md`'s Elevation-of-Privilege row (which already extensively documents what a *compromised admin credential* can do) addresses the opposite direction: what happens when a *virtual key* is compromised, today the answer is "nothing, until an operator notices and manually calls the rotate/delete endpoint."

**Effort:** Medium — this finding's own concrete artifact (the quarantine *policy content*, e.g. AWS's specific denied-action list) isn't portable to Kelvran's very different threat surface; what's portable is the *design decision* — automate the revoke/quarantine step once a trigger fires (whether that trigger is Finding 2's ML baseline, Finding 3's IP-allowlist violation, or a much simpler heuristic like "spend velocity crossed N× the historical rate in under a minute") rather than only ever alerting. Sizing depends entirely on which trigger is chosen; not itself a build item without Finding 2 or an equivalent simpler trigger built first.

### 5. Usage-pattern spend/volume alerting distinct from content guardrails: real in LiteLLM, absent as automated action anywhere surveyed except AWS/Azure (Small — Kelvran already has half of this)

**What:** LiteLLM (a direct, currently-shipping competitor gateway) ships budget-threshold alerting on virtual keys/teams/users as a first-class, well-documented feature (`docs.litellm.ai/docs/proxy/alerting`, cross-checked against LiteLLM's own GitHub PR #31618/issue #32597 implementing the most recent iteration): configurable Slack/webhook notifications fire at `threshold_crossed` events (default `[0.8, 0.85, 0.95]` of `max_budget`) and `budget_crossed`/`projected_limit_exceeded` events, per-key/team/user, entirely independent of any content check. Azure OpenAI Service's "Risks & Safety monitoring" / "potentially abusive user detection" feature (Microsoft's own docs, `learn.microsoft.com/en-us/azure/ai-foundry/openai/how-to/risks-safety-monitor`) is explicitly, per Microsoft's own clarifying note, **not** the same thing as Azure's separate content-only "Abuse Monitoring" — it scores per-user request *volume and frequency* combined with harmful-content signals into an "abuse score," a genuine (if content-adjacent, not purely usage-pattern) hybrid.

**Why it matters for Kelvran specifically:** Kelvran's own `VirtualKey.BudgetWarnPercent` (per its own doc comment, "log-only... the request is never rejected or altered") is directly analogous in spirit to LiteLLM's `threshold_crossed` — both are a static percentage-of-budget warning. The gap versus LiteLLM specifically is narrower than it looks: Kelvran already has the *threshold concept*; what LiteLLM has and Kelvran does not is (a) an *outbound notification* (Slack/webhook) rather than a log line only, and (b) the same mechanism generalized to *velocity* (LiteLLM's `projected_limit_exceeded` event, which fires when *projected* spend — not just current spend — would exceed budget, i.e. a rate-of-spend signal, not merely an absolute-spend one).

**Consistent with settled decisions?** Additive/bounded extension of the existing, already-shipped `BudgetWarnPercent` design — not a reopening of `docs/rfcs/2026-09-05-gateway-budget-warn-threshold.md`'s "log-only, no new API surface" decision, since adding an outbound webhook is a new capability layered on the same trigger condition, not a change to what triggers it.

**2026 evidence, cross-checked 2 ways:** LiteLLM's own hosted docs and its own GitHub repository's recent PR/issue (a second, independent primary source — the actual shipping implementation, not just a docs page) agree on the mechanism and default thresholds. Separately, Microsoft's own two Azure docs pages (`techcommunity.microsoft.com` announcement blog and the current `learn.microsoft.com` how-to) independently corroborate that "potentially abusive user detection" is a distinct feature from base "Abuse Monitoring," at two different documentation layers (announcement + current reference).

**Concrete next step:** add an outbound webhook/Slack notification fired from the same code path that already computes `BudgetWarnPercent`'s log line (per that field's own doc comment, in the dataplane's billable-completion finalize path) — a small, additive change reusing an existing trigger, not a new detector. A `projected_spend`-style velocity signal (LiteLLM's `projected_limit_exceeded`) would be a separate, slightly larger follow-on requiring a rolling-rate calculation Kelvran doesn't currently compute.

**Effort:** Small for the webhook notification (reuses the existing `BudgetWarnPercent` trigger); Small-Medium follow-on for a velocity/projected-spend signal.

### 6. The IAM/CIAM world's own established pattern (Okta, Auth0) is the clearest evidence that "new geography" detection is a solved, generalizable problem outside the LLM-gateway space specifically (context, not a direct build item)

**What:** Okta's "Behavior Detection" (`help.okta.com`, confirmed live) and Auth0's "Adaptive MFA" (`auth0.com/docs`, confirmed live) both ship, as standard product features (not research prototypes), the exact primitives named in this research's brief: `NewDevice`, `ImpossibleTravel` (computed as a hypothetical travel velocity between two successive sign-ins, compared against a plausible-travel threshold), `UntrustedIP` (IP-reputation intelligence), and `Velocity` (Okta's own term, default threshold 805 km/h / 500 mph). Both compute a risk score from these signals and gate a *step-up* action (require MFA) rather than an outright block — Auth0's own docs note the design constraint explicitly: *"You can't deny access to users based on behavior conditions... They're only denied access if multifactor authentication fails."*

**Why it matters for Kelvran specifically:** this is the closest well-established analog to "a virtual key suddenly used from a new geography/IP pattern" named in the research brief — and it demonstrates the concept is decades-mature in the adjacent CIAM space, just not (per Findings 1-5) broadly ported into LLM-gateway products yet, AWS GuardDuty AI Protection being the one clear exception. It also surfaces a real design constraint Kelvran would inherit if it built an equivalent: Okta/Auth0's step-up-to-MFA response has no clean analog for a machine-to-machine API key (there is no human to challenge) — the only available response for a bearer-token credential is allow, deny, or rate-limit-more-aggressively, which is a strictly harder-to-tune lever than "ask for a second factor."

**Consistent with settled decisions?** Context only — no existing Kelvran decision touches this. Not itself a finding requiring action; included because it directly answers "is credential-geography anomaly detection a real, provenpattern" (yes, extensively, in an adjacent domain) while also explaining *why* it hasn't ported cleanly into the LLM-gateway product category yet (the step-up-challenge response doesn't translate to bearer tokens).

**(Added 2026-09-22 — third independent vendor confirmation):** Ping Identity's PingID ships the identical "impossible travel" primitive under the name **geovelocity anomaly rule** (`docs.pingidentity.com/pingid/pingid_service_management/pid_configuring_geovelocity_anomaly_rule.html`, live-verified): it compares the elapsed time between a user's current and immediately-previous sign-on locations against the physical travel time required between them (PingID's own worked example: New York at 12:00pm followed by a London sign-on two hours later triggers the rule, since commercial travel cannot cover that distance that fast) — and, unlike Okta/Auth0's step-up-to-MFA framing, PingID's documented default *rule action* is **Deny**, an outright block rather than a second-factor challenge. This is a third, independently-documented vendor (distinct company, distinct docs) confirming the same pattern, and its default-deny posture is a closer behavioral analog to what a machine-to-machine bearer-token gateway would actually need (no human to challenge, so "deny" is the only lever available, exactly per this finding's own point about MFA not translating to API keys) — strengthening, not just repeating, the design-pattern case already made above.

**2026 evidence, cross-checked 2 ways:** Okta's and Auth0's own documentation (different companies, independently confirming the same three-signal pattern — new device, impossible travel, untrusted IP/velocity — under different product names) is about as close to independent 2-source confirmation as this space offers, since both are primary vendor docs for the feature they each ship. PingID's own docs (a third company) independently confirm the same underlying geovelocity mechanic and, notably, its default-deny (not default-challenge) action.

**Effort:** N/A — not a build item, included for design-pattern grounding only.

### 7. Cloudflare's session-based Volumetric Abuse Detection — a second, independent real-world design template for per-endpoint usage-pattern baselining, from the API/WAF layer rather than the cloud-IAM layer (context + design template, not a direct build item)

**What:** Cloudflare's API Shield ships **Volumetric Abuse Detection** (`developers.cloudflare.com/api-shield/security/volumetric-abuse-detection/`, live-verified, last updated 2026-08-03) — an unsupervised-learning system that builds an independent traffic baseline **per API endpoint**, then rate-limits on a **per-session basis** (a session identifier defined as an authorization token, available as a request header or cookie) rather than per source IP, specifically because, per Cloudflare's own docs, tracking by session instead of IP "reduces false positives when traffic to your API increases, because rate limits track individual sessions rather than shared IP addresses" — i.e., many legitimate callers sharing one IP/NAT/corporate egress don't get lumped into one anomaly signal. The system imposes a concrete minimum-sample-size gate before it will produce a recommendation for a given endpoint: at least 50 distinct sessions observed in any 24-hour window during the trailing seven days.

**Why it matters for Kelvran specifically:** this is a second, structurally different real-world precedent for exactly the same class of capability Finding 2 (AWS GuardDuty) already established — per-identity/per-endpoint behavioral baselining distinct from content scanning — but built at the API-gateway/WAF layer using an authorization-token-scoped session concept, not a cloud-account IAM identity. That is a much closer architectural match to Kelvran's own `VirtualKey`-centric model than GuardDuty's IAM-identity model is: a Kelvran `VirtualKey.ID` (or `KeyHash`) is already the natural session-identifier equivalent Cloudflare's mechanism keys on, meaning the *shape* of a future Kelvran baselining subsystem (Finding 2's "Large effort" design template) has a second, independently-arrived-at industry precedent confirming per-credential (not per-IP) baselining is the right unit, not merely AWS's own single opinion.

**Consistent with settled decisions?** New — no existing row in `THREAT_MODEL.md` addresses per-endpoint/per-key volumetric baselining; additive context for the same open question Finding 2 already raises, not a new decision by itself.

**2026 evidence:** Cloudflare's own current developer documentation, directly fetched and cross-checked (page content matches almost verbatim between an AI-summarized fetch and a raw HTML fetch), including disclosed real caveats rather than pure marketing framing — it requires a configured session identifier to work at all, JWT claims can still be miscounted if invalid JWTs aren't blocked upstream or a non-unique claim is chosen as the identifier, it is an Enterprise-only feature, and it will not generate a recommendation for a given endpoint below the 50-distinct-session/24h floor.

**Concrete next step:** not proposed as an immediate build (this is Large effort exactly like Finding 2, and the two should likely be designed together, not separately) — named here specifically because it independently corroborates that a per-credential (session-token-keyed) baseline, not a per-source-IP one, is the correct unit for any future Kelvran equivalent, and because its documented minimum-sample-size gate (50 sessions/24h) is a concrete, borrowable starting heuristic for how much traffic history Kelvran's own future baseline would need before trusting it — directly relevant to the open question already raised in Finding 2 about needing real production traffic data first.

**Effort:** N/A directly (not a Kelvran build item on its own) — folds into Finding 2's existing Large-effort design question as corroborating evidence, not a separate line item.

### 8. FortiGuard Labs' September 2026 AWS Bedrock LLMjacking incident: a documented technique for evading single-credential monitoring by minting a *second*, service-specific credential (Small-Medium — a concrete, currently-open detection gap distinct from anything else in this report)

**What:** FortiGuard Labs (Fortinet's threat-research team) published a real, dated incident writeup (`fortinet.com/blog/threat-research/someone-else-is-using-your-ai`, 2026-09-03 — 19 days before this research date) describing an intrusion in which a leaked, long-lived AWS IAM access key with `AdministratorAccess` was used to (1) create a brand-new IAM identity, (2) subscribe that identity to premium foundation models via AWS Marketplace (`CreateAgreementRequest`/`AcceptAgreementRequest`), and (3) run inference requests against those models, with all resulting charges billed to the victim's account (independently corroborated by cybersecuritynews.com and gbhackers.com's own coverage of the same incident, both published within days of the Fortinet original). The genuinely new detail for this research question: FortiGuard separately observed the attacker **issuing Bedrock-specific service credentials to the newly-created identity** — a distinct credential type from a standard IAM access key — explicitly creating a **second, parallel access path** that "may make the activity less obvious to teams focused only on the original exposed key" (FortiGuard's own framing). AWS's own Security Blog (`aws.amazon.com/blogs/security`, "Securing Amazon Bedrock API keys," 2025-10-17) independently confirms Bedrock service-specific credentials are a real, documented AWS mechanism distinct from IAM access keys — the technical premise isn't a misreading of an obscure feature.

**Why it matters for Kelvran specifically:** this is a concrete, real-world **evasion technique against exactly the kind of single-credential-focused monitoring this whole report otherwise recommends** (Findings 2/3/4's per-key baselines, IP allowlists, and quarantine hooks are all scoped to *one* virtual key/identity). It surfaces a genuine, previously-unconsidered gap for any future Kelvran anomaly/quarantine design: if a compromised admin credential (Kelvran's own `THREAT_MODEL.md` Elevation-of-Privilege row already covers this attack surface) is used to mint an *additional* virtual key rather than abusing the original one, a detection/response system watching only the originally-flagged key's traffic would miss it entirely. Kelvran's own admin API (`POST /admin/virtual_keys/{name}` create/upsert) is the direct structural analog of AWS's "issue a second, service-specific credential" step — an attacker with Admin-credential access could mint a fresh Kelvran virtual key the same way, and nothing in `internal/identity` today correlates "a new virtual key was just created shortly after this other key started behaving anomalously" as a signal.

**Consistent with settled decisions?** New — extends `THREAT_MODEL.md`'s existing Elevation-of-Privilege row (which already covers what a compromised Admin credential can do to *existing* keys via `rotate`/`delete`) with a specific, previously-undocumented sub-case: an Admin-credential compromise being used to *create* a new key as a monitoring-evasion step, not just to mutate an existing one.

**2026 evidence, cross-checked 2 ways:** the FortiGuard primary source plus two independent outlets' (cybersecuritynews.com, gbhackers.com) contemporaneous coverage of the same named incident, all agreeing on the attack chain and the secondary-credential detail; AWS's own security-blog documentation independently confirms Bedrock service-specific credentials are a real, distinct mechanism (not an invented detail).

**Concrete next step:** when any future automated-response trigger (Finding 4) is eventually built, its scope should explicitly include "flag/correlate new virtual-key creation events that occur in unusually close temporal proximity to an anomaly finding or an Admin-credential action" — a cheap addition to whatever audit/event log already exists once one exists at all, and worth naming now precisely because it's the kind of gap that's easy to omit if a future design only thinks in terms of "monitor the flagged key more closely."

**Effort:** Small-Medium once any baseline/quarantine trigger (Finding 2 or 4) exists — this is a scoping note for that future design, not a standalone detector; effort is dominated by whichever trigger mechanism it rides on.

## Real incident record (grounding "is this a live threat," not a hypothetical)

Cross-checked across 5 independent named-firm sources, plus one directly-verified GitHub issue, not a single vendor's marketing claim (plus two further incidents added 2026-09-22, below):

- **(Added 2026-09-22) Anthropic's own September 2026 threat-intelligence report** (`anthropic.com/threat-intelligence-report-september-2026`, live-verified directly, not taken from a summary) — a first-party admission from the exact provider Kelvran's own adapter layer calls out to, not a third-party researcher's inference. Two separate, named case studies are directly on-point for this research question: **GTG-50014** ("ShinyHunters smash-and-grab opportunists") — Anthropic attributes a roughly three-week campaign to a ShinyHunters-affiliated actor who used AI API keys **stolen from the victims' own enterprise software vendors**, not from any Anthropic-side compromise; Anthropic's report is explicit and repeats this framing verbatim across multiple unrelated case studies in the same document: *"In every instance, the API keys involved were stolen from Anthropic customers' environments. Anthropic's own systems were not compromised."* **GTG-50021** — a distinct, named group ran a fraudulent AI-reseller operation advertising cheap Claude access that was "neither cheap nor actually Claude": customer traffic was silently proxied to a different model while the reseller's own tooling installed a credential harvester that stole the customers' *real* Anthropic account credentials for resale to other AI-proxy resellers — i.e., a credential-theft operation that itself masquerades as a legitimate low-cost LLM-gateway/reseller product, a direct cautionary data point for any product occupying that exact market category. Both case studies include concrete IOCs (domains, e.g. `awstore[.]cloud`, `kiro[.]cheap`) in the source report.
- **(Added 2026-09-22) FortiGuard Labs' AWS Bedrock LLMjacking incident** (2026-09-03, ~19 days before this research date) — see Finding 8 above for the full technical detail (leaked `AdministratorAccess` IAM key → new IAM identity → AWS Marketplace foundation-model subscription → inference billed to the victim, plus a secondary Bedrock-specific-credential evasion step) — independently corroborated by cybersecuritynews.com and gbhackers.com's contemporaneous coverage of the same named incident. Included here specifically as the single most recent dated incident in this report (weeks, not months, old), demonstrating LLMjacking-via-stolen-cloud-credentials is not a 2024-era phenomenon that has since been fully mitigated — it is still an active technique as of a few weeks before this research date.

- **A confirmed credential-theft incident inside a named LLM-gateway competitor's own supply chain** (`github.com/BerriAI/litellm/issues/24512`, independently fetched and confirmed directly, not taken on a secondary report's word): PyPI package `litellm==1.82.8` shipped a malicious `litellm_init.pth` file inside its wheel — a `.pth` file in `site-packages/` executes automatically at Python interpreter startup, with no `import` required — that harvested environment variables (including API keys/secrets), SSH keys, and AWS/GCP/Azure/Kubernetes/Docker/git credentials, encrypted the haul with AES-256 under a hardcoded 4096-bit RSA public key, and exfiltrated it to `models.litellm.cloud` — a lookalike domain, not LiteLLM's real `litellm.ai`. Discovered 2026-03-24. This is a different attack vector than everything else in this section (a compromised software-supply-chain artifact, not a leaked/stolen credential or a usage-pattern anomaly) — included specifically because it is a real, dated, first-party-confirmable incident of credential theft against the exact category of product (an LLM gateway) this report is about, in the exact competitor (LiteLLM) this report cites repeatedly for its own feature comparisons elsewhere.

- **Sysdig** (`sysdig.com/blog`, coined the term "LLMjacking," May 2024): the original documented campaign — stolen cloud credentials (via a vulnerable Laravel install, CVE-2021-3129) tested against **ten** distinct AI platforms (AI21 Labs, Anthropic, AWS Bedrock, Azure, ElevenLabs, MakerSuite, Mistral, OpenAI, OpenRouter, GCP Vertex AI) using an open-source reverse-proxy tool (`oai-reverse-proxy`) specifically built to pool and resell stolen credential access; Sysdig's own worst-case cost projection was **$46,000/day** against a single victim's AWS Bedrock quota. Sysdig's own reconnaissance-detection detail is worth citing exactly since it's a genuinely distinctive technique: attackers sent `max_tokens_to_sample: -1` (an intentionally invalid parameter) to `InvokeModel` purely to distinguish a `ValidationException` (credential has Bedrock access, benign-looking error) from an `AccessDenied` error (no access) — probing without ever generating a real completion or triggering an obvious abuse signal.
- **Permiso** (`permiso.io/blog`, October 2024, independently confirmed by their own honeypot telemetry, not a re-report of Sysdig's finding): documented a distinct, later evolution — attackers hijacking AWS Bedrock access (predominantly targeting Anthropic Claude models) specifically to host unfiltered AI roleplay/chat services and pass the compute cost to the victim, capturing over 75,000 real model invocations from a single attacker IP over two days via honeypot invocation logging.
- **Wiz** (`wiz.io/blog`, December 2024, tracking a threat actor they name "JINX-2401" — again, independent telemetry, not a re-citation of Sysdig/Permiso): documented compromised IAM access keys used specifically to attempt Bedrock model invocation, with a consistent IAM-username regex pattern (`^[A-Z][a-z]{5}[0-9]{3}$`) recurring across multiple, separately-compromised victim AWS environments — evidence of an automated, repeatable attacker toolchain, not one-off manual abuse.
- **Sysdig, follow-up** (`sysdig.com/blog`, dated 2026-02-03 in this research — i.e., roughly seven weeks before this report): a newer incident showing the technique's continued evolution — a threat actor reached AWS administrative privileges in under 10 minutes via stolen credentials found in a public S3 bucket, then specifically pivoted to Bedrock (13 separate model invocations across Claude Sonnet 4/Opus 4/3.5 Sonnet/3 Haiku, DeepSeek R1, Llama 4 Scout, and others) as one stage of a broader intrusion — LLMjacking as a component of, not the sole goal of, a modern cloud intrusion.
- **Cloud Security Alliance research note** (`labs.cloudsecurityalliance.org`, 2026, citing Pillar Security Research's own "Operation Bizarre Bazaar" findings as its primary evidence — flagged here as a research-note synthesis rather than the original discovering entity, lower confidence than the four sources above but independently corroborating the trend's direction): describes the threat class's maturation into a structured criminal marketplace (`silver.inc`) averaging an estimated ~972 attacks/day across a measurement window between 2025 and January 2026, with a documented reconnaissance-to-validation pipeline (2-8 hour lag between public endpoint scanning and monetization attempts).
- **GitGuardian** (`gitguardian.com`, "State of Secrets Sprawl 2026," the entity that performs the scanning itself, not a summarizer): 1,275,105 AI-service secrets found leaked on public GitHub in 2025 (+81% YoY, the fastest-growing secret category they track), including 113,000 leaked DeepSeek API keys and 24,008 secrets found specifically in MCP configuration files (a newer, adjacent leak surface this research's brief did not name but is directly relevant to any future Kelvran MCP/A2A work per `THREAT_MODEL.md`'s own MCP rows). Separately and soberly: GitGuardian's own remediation-rate data shows **64% of secrets confirmed valid in 2022 were still valid/unrotated in 2026** — detection existing does not imply remediation happens.
- **Google Cloud incident detail** (a real user-reported forum thread, `discuss.google.dev`, 2026-03, lower confidence — anecdotal, not vendor-authored, but directly on-point): a customer's own account describes Google's internal fraud/billing team confirming via written statement that "an API key associated with your project has been leaked and there is a high probability that this key was used for unauthorized activity," with the customer citing geographic mismatch (100% of fraudulent Gemini API calls originating from a region where the customer had zero infrastructure) as corroborating evidence Google's own support process did not initially act on consistently. Included not as an authoritative claim about Google's detection capability (Finding 2's Google Cloud citation is the authoritative one) but as real-world evidence that even where usage-pattern/geo-anomaly detection fires internally, the human remediation/billing-dispute process downstream of it can still be inconsistent — a caveat worth carrying into any future Kelvran design that pairs automated detection with a human-facing dispute path.

## Caveats

- The prior research round's Finding 4 (`gateway-security-threatmodel-round4-2026-09-11.md`) checked only Kong's own product-marketing pages for this exact question and reached a defensible "NOT YET, industry-wide" verdict *given the sources it checked* — this report does not contradict that round's methodology, only extends its scope. Kong, Portkey, and LiteLLM were re-checked in this pass specifically for IP-allowlisting/geo-anomaly features on their own virtual-key equivalents and still show no such capability (Portkey's `TRUSTED_CUSTOM_HOSTS`/custom-host SSRF validation is a structurally different control — it protects against a key being used to route to an internal network target, not against a key itself being used from an unexpected external origin); this remains a genuine gap versus AWS/OpenAI/Google specifically, not versus the LLM-gateway product category as a whole.
- Finding 2 (AWS GuardDuty AI Protection) is the single newest capability cited in this report (GA barely two months before this research date) — both AWS documentation pages cited were fetched and cross-checked against each other and against a third, AWS-Samples-hosted community reference, but this report could not independently verify GuardDuty AI Protection's real-world false-positive rate or detection latency the way Unit 42's own controlled experiment did for the older `AWSCompromisedKeyQuarantine` mechanism (Finding 4) — treat the *existence and mechanism* of the GuardDuty finding types as solidly confirmed, and any claim about their practical accuracy in production as unverified.
- The Cloud Security Alliance research note's "~972 attacks/day" figure (Real incident record section) is a research-note synthesis citing Pillar Security Research as its primary source, not independently re-derived by this research pass from Pillar's own original publication — flagged at lower confidence than the four named-firm-original sources (Sysdig ×2, Permiso, Wiz) it sits alongside.
- The Google Developer forum incident (Real incident record section) is a single, unverified customer account, not a vendor statement or independent security-research writeup — included only as directional color on the human-process gap between automated detection and remediation, explicitly not as evidence about Google's detection *capability*, which Finding 2's `iam.serviceAccountKeyExposureResponse` citation (a genuine primary source) already covers on its own.
- This research did not find any evidence — positive or negative — of Anthropic, OpenAI, or Google shipping a GuardDuty-AI-Protection-equivalent per-API-key behavioral baseline for their own *first-party* API keys (as opposed to AWS's IAM-identity-level baseline for Bedrock access specifically, which is a different credential layer). OpenAI's `safety_identifier`/`cyber_policy` mechanism (`developers.openai.com/api/docs/guides/safety-checks`) is the closest first-party analog found, and it is explicitly scoped to *cybersecurity-capability* risk thresholds on specific newer models, not a general-purpose usage-pattern anomaly detector — this is a real, disclosed absence-of-evidence, not a confirmed "no."
- **(Added 2026-09-22)** This addendum's own 10-way parallel sweep explicitly refuted several claims that looked plausible but did not survive verification, and they are deliberately *not* cited above: a specific "$46,000/day at 500K tokens/min across 4 regions" cost-spike figure attributed to Sysdig (the real Sysdig post gives $46k/day as a general worst-case, not that specific per-minute-quota derivation); a claimed "AntiBotGW" open-source gateway feature performing GeoLite2-based impossible-travel detection and a country-denylist (the underlying deepwiki page describes MaxMind GeoLite2 integration for ASN/city lookup, but the specific impossible-travel and denylist claims did not hold up against the source); an unverified March-2026 LiteLLM PyPI supply-chain compromise ("434,000 CI/CD credentials," a specific attributed threat-actor name) distinct from the *separately-confirmed* `litellm==1.82.8` malicious-`.pth`-file incident already cited above (that one *is* independently confirmed directly from `github.com/BerriAI/litellm/issues/24512` and remains fully valid); and a claimed GitHub secret-scanning "March 2026 Vercel six-token-type expansion." None of these appear anywhere in this report's findings or incident record — they are named here only so a future reader doesn't rediscover and re-cite them as if they were new.
