# Semantic (Embedding-Based) L3 Cache — Reconsidered Against Kelvran's Own Shipped `/v1/embeddings` Endpoint

**Date:** 2026-09-20
**Scope:** Whether Kelvran's now-live `POST /v1/embeddings` endpoint (`Pipeline.HandleEmbeddings`, `gateway/internal/gateway/dataplane/dataplane.go:1977`; `adapter.EmbeddingAdapter` implemented by `gateway/internal/adapter/bedrock/embeddings.go` for Titan V2 and `gateway/internal/adapter/openai/embeddings.go` for OpenAI's `text-embedding-3-*` family) changes the buildability/cost/latency calculus for a real vector-similarity L3 cache tier, versus the shipped lexical (MinHash/Jaccard) `LexicalCache` in `gateway/internal/cache/inprocess/lexical.go`. This is a direct, dated follow-up to two prior reports that predate the endpoint shipping — `cache-semantic-embedding-reconsideration-2026-09-13.md` and `cache-production-semantic-caching-2026-09-11.md` — and it also directly answers Open Question 2 already posed in `api-surface-expansion-2026-09-15.md`, written the day the embeddings feature was first scoped (before it shipped): *"do [the client-facing embeddings feature] and the cache subsystem's own semantic-L3 question share enough plumbing that scoping them together would be cheaper than sequencing them independently?"*
**Method:** Direct code inspection of the shipped embeddings pipeline, the shipped `LexicalCache`/`LexicalCandidate` design, `AGENTS.md`'s dependency-boundary rules, and `THREAT_MODEL.md`'s Cache STRIDE row — cross-referenced against `DECISIONS.md`'s `[2026-09-17]`/`[2026-09-19]` entries confirming ship date and live-traffic proof. Fresh primary-source fetches this round: AWS's own Titan-embeddings model-card docs and ML blog (pricing), OpenAI's own pricing page, Portkey's own current documentation, and GPTCache's own GitHub README — re-verifying, not merely inheriting, three of the five vendor claims the 2026-09-13 report already made. Redis LangCache's dedicated docs page 404'd on direct fetch this round (a live URL-structure change since the prior reports cited it); its arXiv paper (arXiv:2504.02268) and landing page remain the citation trail, carried forward from the prior report rather than re-fetched.

---

## Context (Kelvran's own real, current state, as of this round)

The embeddings endpoint did not exist when either predecessor report was written. It shipped 2026-09-17 (`DECISIONS.md`'s fourth post-`v0.12.0` round, Phase 4: commits `4c7652e5`..`d86e01dc`) as a deliberately narrow v1 — `HandleEmbeddings` is its own pipeline function, reusing only the already-decoupled generic subsystems (auth, per-key RPM rate-limiting, budget reserve/reconcile, guardrail scanning, cost accounting), explicitly **not** threading through Cache, idempotency, or fallback chains (`dataplane.go:1950-1963`'s own doc comment). It was proven against real, live Bedrock traffic in the 2026-09-19 end-to-end dry-run (`DECISIONS.md`'s fourth same-day entry: "Bedrock Titan V2 embeddings" in the list of things "live-proved, for the first time ever against real Bedrock traffic"). A `Dimensions` field (256/512/1024 for Titan V2; provider-default passthrough for OpenAI) was added the same dry-run round (commit `c00ca9b6`), and completion-outcome logging + spend metrics were added the same round (commit `9337f133`) after being found missing during the dry-run.

The cache-embedding question this endpoint's existence reopens was itself explicitly flagged, in advance, by `api-surface-expansion-2026-09-15.md`'s own Finding 2 — which drew a sharp line that this report now tests directly: *"[the]'no Go-native ML runtime' blocker... is about computing embeddings locally in-process inside the Go binary — it has no bearing on a client-facing proxy route, which is network-bound provider translation exactly like every existing chat adapter, not local inference. Do not let that blocker leak into this feature's analysis by association."* This report's central finding is that this warning was exactly correct, and its implication cuts against a naive reading of the research question.

## Executive Summary

**The embeddings endpoint changes the *engineering-effort* side of the calculus to essentially zero, and the *dollar-cost* side to a rounding error — but it does not touch the two things that actually gated the feature: the "cache lookup never touches an upstream" architectural guarantee, and the real, previously-measured ~350-380ms per-call network latency.** Kelvran now has production-grade, tested `adapter.EmbeddingAdapter` implementations for Bedrock Titan V2 and OpenAI `text-embedding-3-*`, wired through a real HTTP upstream caller (`NewHTTPEmbeddingUpstreamCaller`) — this retires the *build-it* cost of embedding generation entirely; a future cache feature would call the same adapter pattern, not invent one. Fresh pricing checked directly against AWS's and OpenAI's own pages confirms embedding calls are commodity-cheap regardless of provider (Titan V2 and `text-embedding-3-small` are both $0.02/1M input tokens; `text-embedding-3-large` is $0.13/1M) — two to three orders of magnitude below what a chat completion this cache exists to avoid typically costs, so a real embedding-L3 tier's marginal *dollar* cost, even at meaningful traffic, is not the binding constraint. What is unchanged is that `/v1/embeddings` is a network-bound proxy to the exact same external provider APIs the 2026-09-13 report already measured at 350-380ms steady-state — calling it (or its underlying adapter functions) on a cache *read* is architecturally indistinguishable from the "calling an upstream on every lookup" pattern the original L3-lite RFC rejected specifically to preserve that guarantee. The buildable, genuinely new design this endpoint unlocks is a **write-path/read-path split**: generate and store the embedding asynchronously after the response is already returned to the client (a real, near-zero-marginal-cost addition to an already multi-second completion), and pay the real synchronous tax only on read, only for the subset of traffic that already missed the free, sub-millisecond L1/L2/lexical-L3 checks — which is also, not coincidentally, exactly the traffic this tier is meant to add coverage for. The entity/number/date hard-gate, freshness/risk model, and every existing `LexicalCandidate` provenance field must carry over unchanged, per `AGENTS.md`'s non-negotiable "never weaken the hard-gate" rule — this round's fresh Portkey/GPTCache verification reconfirms that no production vendor has a better answer to that requirement than what Kelvran already ships.

## Findings

### Finding 1 — The embeddings endpoint resolves the *supply-side* engineering blocker completely, but resolves *none* of the two blockers that actually gated the cache feature — this is a real, load-bearing distinction, not a technicality
**Classification: not_yet (as a green light) — the correct reading is "one of three blockers closed, two open"** · **Confidence: high** (direct code inspection)

The original L3-lite RFC (`docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`, "Why not real embeddings yet") named two independent reasons real embeddings were deferred: (1) no mature, statically-linkable Go-native ML runtime existed to compute embeddings *in-process*, and cgo/ONNX options broke the `scratch`-image static-binary story; (2) calling an embedding API on every L3 lookup **is** an upstream call, which "silently voids the one architectural guarantee this whole subsystem exists to provide" (per `gateway/ARCHITECTURE.md`'s Request Lifecycle: a cache lookup happens before the router/provider call *so a hit never touches an upstream*). `cache-semantic-embedding-readiness-round4-2026-09-11.md`'s Finding 3 reconfirmed blocker (1) with fresh 2026 evidence eight days before the embeddings endpoint shipped, finding the Go-native-embedding-runtime field had *narrowed* (fastembed-go archived 2026-01-15), not improved.

`/v1/embeddings` resolves neither (1) nor (2) directly: reading `bedrock/embeddings.go` and `openai/embeddings.go` confirms both are thin translation layers (`ToEmbeddingProvider`/`FromEmbeddingProvider`) around a real `p.embeddingUpstream(ctx, dep, providerReq)` HTTP call (`dataplane.go:2056`, via `NewHTTPEmbeddingUpstreamCaller`, `dataplane.go:3718`) — this is network-bound provider translation, structurally identical to every existing chat adapter, never local inference. It does not run a model in-process; it proxies to the same Bedrock/OpenAI APIs the original RFC's blocker (2) was about. What it *does* resolve is a third, distinct cost this round's research isolates for the first time: the **engineering effort of building and hardening embedding-generation code at all**. Before this endpoint, the only embedding-generation code in the repo was `evals/scripts/validate_embedding_gate.py` (a one-off Python research script, explicitly scoped as living "OUTSIDE the `evals` Python package... never a permanent CLI feature" per `api-surface-expansion-2026-09-15.md` Finding 2) plus a throwaway Go program for one latency measurement. Today there is a real, tested, production adapter interface (`embeddings_test.go` exists for both providers), a real wire-format contract (`EmbeddingRequest`/`EmbeddingResponseWire` for both Titan V2 and OpenAI), a real `Dimensions` knob, and a real cost-accounting path (`costaccounting.Calculator` already prices `Usage{PromptTokens, TotalTokens}` for embeddings with zero new code, per `api-surface-expansion-2026-09-15.md` Finding 2). A future cache-embedding feature does not need to build any of this from scratch — it needs to *call* it, from `dataplane.go` (never from `internal/cache`, per the boundary discussed in Finding 3 below).

**Verdict:** treat this as closing exactly one of three real blockers (engineering effort), not as a green light for the feature as a whole. The remaining two — the architectural "hit never touches upstream" guarantee, and the real measured latency — are addressed in Findings 2-3 below, not resolved by this endpoint's mere existence.

### Finding 2 — Cost is now a settled non-issue with fresh, live numbers; latency is unchanged and remains the real constraint
**Classification: build_now (the cost conclusion) / not_yet (the latency conclusion, unless architecturally isolated per Finding 3)** · **Confidence: high** (live pricing fetched directly from AWS's and OpenAI's own pages this round)

Fresh, primary-source pricing, fetched directly this round rather than inherited: Amazon Titan Text Embeddings V2 (`amazon.titan-embed-text-v2:0`, max 8,192 input tokens / 50,000 characters, 1,024/512/256-dimension output — confirmed against AWS's own Bedrock user-guide page, `docs.aws.amazon.com/bedrock/latest/userguide/titan-embedding-models.html`) prices at **$0.02 per million input tokens**, per AWS's own ML blog post's worked cost example (`aws.amazon.com/blogs/machine-learning/get-started-with-amazon-titan-text-embeddings-v2...`, "Price per million tokens: $0.02" — also confirming V1 was 5x more expensive at $0.10/million, since superseded by V2). OpenAI's own current pricing page (`developers.openai.com/api/docs/pricing`, redirected from `platform.openai.com/docs/pricing`) confirms `text-embedding-3-small` at **$0.02/1M tokens** — identical to Titan V2 — and `text-embedding-3-large` at **$0.13/1M tokens**. For a typical short, cache-checkable conversational query (order of 50-300 input tokens), the per-call dollar cost is on the order of $0.00001 or less — two to three orders of magnitude below what the completion this cache exists to avoid typically costs (Finding 6 of the 2026-09-13 report cites "1-3 seconds for a fast/cheap model (Haiku)" as the completion this cache aims to short-circuit; Haiku-class pricing is materially higher per token than $0.02/million). **Cost is not, and was never going to be, the reason to defer this feature** — this round's contribution is replacing an assumption with a checked number.

Latency is a different story, and nothing about the new endpoint changes it: the 2026-09-13 report's Finding 6 measured real, live Bedrock Titan V2 calls (via a throwaway Go program mirroring `bedrockguard.go`'s exact SigV4 pattern) at 350-382ms steady-state (p50 369ms) against the pilot's own real AWS account. `/v1/embeddings` calls the identical underlying Bedrock `InvokeModel` operation on `amazon.titan-embed-text-v2:0` — same provider, same model, same network path — so there is no reason to expect this number to have materially changed, and this round did not re-measure it (see Caveats: this is a real, cheap, one-line follow-up now that `Dimensions` is a live config field, since a smaller 256-dim request is a strictly smaller response payload than the 1,024-dim default the original measurement used, though model *compute* time, not payload size, is more likely to dominate). The endpoint's existence does not shrink this number; it only makes the *call itself* production-grade and reusable rather than a bespoke script.

### Finding 3 — The one genuinely new, concrete design this endpoint unlocks: a write-path/read-path split that confines the real latency tax to exactly the traffic that needs it, using storage and boundary patterns Kelvran already has
**Classification: build_now (design), not_yet (ship on the request path without this split)** · **Confidence: high** (direct code inspection of the existing `LexicalCache`/`AGENTS.md` boundary rules; the specific architecture below is this report's own synthesis, not independently vendor-sourced)

`AGENTS.md`'s "Never" list is explicit and non-negotiable: *"Let Cache call a provider directly, or let it depend on `internal/adapter`."* This means an embedding-cache feature's actual embedding-generation call can never live inside `internal/cache` — it must live in `dataplane.go`, mirroring the exact precedent `Fingerprint()` (`dataplane/entities.go`) and `normalizeMessages`/`serializeMessages` already set for schema-aware, `adapter.Message`-touching logic that the cache package itself is architecturally barred from. Concretely, this means reusing `p.adapters[dep.Provider].(adapter.EmbeddingAdapter)` and a caller-side upstream invocation *from `dataplane.go`*, passing only the resulting `[]float64` vector into a new `internal/cache` interface — never letting `internal/cache` see an `adapter.EmbeddingRequest` or call a provider itself. This is structurally the same split `LexicalCandidate`'s own doc comment already documents for the entity fingerprint (`cache.LexicalCandidate`'s `Fingerprint`/`ModelID`/etc. fields are provenance *checked by the caller*, never inside the `cache` package).

The genuinely new element this round's research adds: **the embedding call does not need to happen on the synchronous read path at all for the write half of the round-trip.** A cache write (`Put`) already happens *after* a full chat completion has computed and is about to be cached — the response has already been generated; nothing about generating an additional embedding of the (already-normalized) query text needs to block the client's own response. Fired in a background goroutine after the response is written (the same "fire-and-forget, `context.WithoutCancel`" pattern this repo's own new `internal/alerting` package already established for webhook delivery, per `DECISIONS.md`'s `[2026-09-18]` Item 13), the real ~350-380ms cost lands entirely off any client-visible latency. This builds up an embedding-indexed candidate set over time at zero request-latency cost. The **read** side is where the real, unavoidable tax lives: a new incoming query still needs its own real-time embedding call to search that index, and that is a genuine ~350-380ms addition to every cache-checkable request that reaches this stage — but by design, it should only ever be reached *after* L1 (exact-match), L2 (normalized-match), and L3-lite (lexical Jaccard) have all already missed, and only when the query isn't marked volatile. All three of those checks are sub-millisecond in-process computation (per `lexical.go`'s own package doc, "no ANN needed... a brute-force scan over an LRU-capped candidate set is cheap"), so gating the embedding call behind them confines the real cost to exactly the fraction of traffic where Kelvran actually wants the extra paraphrase coverage — the same class of traffic the 2026-09-13 report's own confirmed ~0.0078-Jaccard clean-miss case represents.

At Kelvran's storage scale, no new infrastructure is needed for the search side either: `cache-semantic-embedding-readiness-round4-2026-09-11.md`'s Finding 4 already established (checked against chromem-go's pure-Go brute-force design and `kelindar/search`'s own documented ~100,000-entry brute-force ceiling) that a per-tenant-partitioned, LRU-capped candidate set — the identical shape `inprocess.LexicalCache`'s `tenantBucket`/`list.List` already implements for the lexical tier — never realistically approaches a scale where brute-force cosine similarity becomes a real CPU cost. An `EmbeddingCache` mirroring `LexicalCache`'s exact structure (a `[]float32` vector instead of a `[]uint64` MinHash signature, cosine similarity instead of `JaccardEstimate`, identical per-tenant `tenantBucket` isolation for `THREAT_MODEL.md`'s KeyPooling mitigation) is the right shape — no pgvector, no HNSW, no external vector database, consistent with this repo's own established "leaf, zero heavy deps" discipline.

### Finding 4 — Fresh vendor verification this round reconfirms the hard-gate requirement is non-negotiable and unimproved-upon anywhere in production practice — with one new nuance on Portkey specifically
**Classification: not_yet (bare similarity, unchanged) / build_now (gated variant, unchanged)** · **Confidence: high** (Portkey's and GPTCache's own current docs fetched directly this round; Redis LangCache and TrueFoundry claims carried forward from the 2026-09-13 report, not independently re-verified this round)

Portkey's own current documentation (fetched live this round) confirms and sharpens the 2026-09-13 report's Finding 5: Portkey's semantic cache runs simple (exact-match) cache first and *only* falls back to embedding similarity on a miss; even in the semantic path, `model`, `temperature`, `max_tokens`, and "any other body parameter" plus `x-portkey-metadata` must still match **exactly**, cosine similarity is checked only against the user-message text at a default threshold of 0.95, and at least one user-role message must be present. One nuance this round's direct fetch surfaces that the prior report's characterization did not make explicit: Portkey's docs state the **system prompt is excluded from matching entirely** — "changing it does not affect cache hits." This is a real design choice Kelvran should not copy: `LexicalCandidate`'s own `PromptFingerprint`/`ReasoningBlocksFingerprint`/`GuardrailPolicyVersion` fields exist specifically because Kelvran's threat model treats prompt-template and reasoning-history differences as cache-key-relevant (per `docs/rfcs/2026-09-12-gateway-reasoning-content-canonical-schema.md`'s cache-key decision, cited in `lexical.go` itself) — Portkey's narrower gate is evidence of the "hard-gate design space," not a bar to clear or lower.

GPTCache's own GitHub README, re-fetched live this round, confirms unchanged from the prior report: still explicitly in limited-maintenance mode ("we no longer add support for new API or models"), still offers no entity/number/date-equivalent content gate across any of its nine similarity-evaluation modules (embedding distance, an ONNX duplicate-detector model, exact-match, numpy-distance, planned BM25) — reconfirming Finding B of the 2026-09-11 report rather than overturning it. FreshCache's conjunctive `sim(q,q′) ≥ θ ∧ P(stale) ≤ ε` formula and its own adversarial result (20/20 bare-cosine false-approvals on crafted false-entity pairs, 15/20 blocked once an NER-equivalent entity gate is added) stand as previously reported — not independently re-verified this round, carried forward as still the strongest available blueprint. **Net: nothing in this round's fresh vendor check changes the standing requirement that any embedding-similarity candidate must clear the exact same entity/number/date fingerprint, freshness/risk model, `ModelID` match, `GuardrailPolicyVersion` match, `ResponseFormatFingerprint`/`PromptFingerprint`/`NegationFingerprint`/`ReasoningBlocksFingerprint` checks `LexicalCandidate` already enforces — an `EmbeddingCandidate` should carry every one of these fields unchanged, per `AGENTS.md`'s "never weaken the hard-gate" rule.**

One additional, real, currently-shipped precedent worth adopting regardless of the embedding-L3 timeline, surfaced by cross-referencing `cache-l3-lite-threshold-calibration-2026-09-12.md`: LiteLLM ships `similarity_threshold` as a documented, tunable YAML config field (`cache_params`, confirmed live in `litellm/caching/{qdrant,redis,valkey}_semantic_cache.py`) and emits a per-response `x-litellm-semantic-similarity` header carrying the raw computed score on every decision, hit or miss (verified against merged PR #37742, including a defined `0.0` sentinel on embedding-timeout misses). Kelvran already has the `X-Kelvran-Overhead-Duration-Ms` precedent (`THREAT_MODEL.md`'s 2026-09-14 addition) for disclosing server-computed signals to callers — a `X-Kelvran-Cache-Similarity`-shaped header, populated for L3-lite today and extendable to any future embedding tier, would be a small, precedented, non-security-sensitive addition independent of the larger embedding-L3 decision.

### Finding 5 — A live compliance trigger, specific to this exact moment: `THREAT_MODEL.md`'s own EU AI Act scoping note names "the semantic cache moves from future work to an active RFC" as the condition to revisit — this round's research is arguably that trigger
**Classification: build_now (a short scoping-rationale note, cheap)** · **Confidence: high** (direct citation of Kelvran's own already-written compliance research)

`ai-compliance-regulatory-readiness-2026-09-14.md`'s Finding 1 already concluded Kelvran's *current* routing/caching (deterministic WRR/health-based routing, lexical Jaccard/MinHash L3) falls within the EU AI Act's "basic data processing" exclusion from the Article 3(1) "AI system" definition — but flagged one live residual conditional: *"[this] doesn't currently bite since nothing shipped exercises 'inference' in the Act's sense, but it would need re-asking if the deferred real-embedding L3 semantic cache... ever ships, since embedding-similarity scoring sits closer to 'inference' than lexical shingling does."* `THREAT_MODEL.md` itself (line 89) repeats this verbatim and specifically instructs: *"Revisit this note... immediately if the semantic cache moves from future work to an active RFC."* This round's research — triggered by a real, shipped embeddings endpoint that makes an embedding-based L3 concretely buildable with existing code for the first time — is a reasonable candidate for exactly that trigger event, even though no embedding-L3 RFC has been written yet. This is a cheap, `build_now`-eligible documentation action (the compliance report already named the 5-10 line fix), not a call to accelerate the underlying feature decision.

### Finding 6 — The already-disclosed cache-erasure gap would extend unchanged to any embedding tier, unless designed against from day one
**Classification: not_yet (design precondition, not a blocker)** · **Confidence: high** (direct citation of `DECISIONS.md`'s own disclosed limitation)

`DECISIONS.md`'s `[2026-09-18]` entry, Item 10, discloses a real, already-shipped and already-tested limitation: the new `POST /admin/cache/erase` endpoint gives `cache.Cache.Delete` (L1/L2) a real caller, but its own test suite "empirically proves and prominently discloses" that erasing L1/L2 does not prevent an identical follow-up request from still hitting L3, "since L3's own similarity-based lookup was never plumbed through this path." An `EmbeddingCache` tier, being a second similarity-based lookup structurally identical in this respect to the lexical one, would inherit the exact same gap by default. This is a named, disclosed precondition for any future embedding-L3 RFC — the erasure path needs to be designed to reach every similarity-based cache tier from day one, not discovered as a gap after a second tier ships the way the first one was.

## Synthesis: what changed and what didn't, versus the two prior reports

| Question | 2026-09-11/13 answer | This round's answer, given the shipped endpoint |
|---|---|---|
| Does a mature embedding-generation path exist? | No — no Go-native ML runtime, only a throwaway script | **Different question answered instead**: a production-grade *external-API* embedding path now exists and is reusable, but it was never the in-process runtime the original blocker was about (Finding 1) |
| Is embedding-call cost a real concern? | Assumed real, not measured | **Settled: no.** $0.02-0.13/1M tokens, live-verified against AWS's and OpenAI's own pricing — negligible relative to the completion cost this cache avoids (Finding 2) |
| Is embedding-call latency a real concern? | Measured once: 350-382ms steady-state | **Unchanged.** Same provider, same model, same network path — this round did not re-measure and has no reason to expect a different number (Finding 2) |
| Does calling an embedding API on every lookup still void the "hit never touches upstream" guarantee? | Yes, named explicitly in the original RFC | **Still yes, on the read path** — but a write-path/read-path split, newly concretely buildable with the shipped adapter code, confines the real cost to lexical-L3-miss traffic only (Finding 3) |
| Does the hard-gate requirement still stand, unweakened? | Yes — FreshCache, TrueFoundry, GPTCache, Portkey all surveyed | **Reconfirmed with fresh Portkey/GPTCache verification** — no vendor has a better answer; Portkey's system-prompt exclusion is a design choice to avoid, not adopt (Finding 4) |
| Any new consideration this round surfaces that neither prior report examined? | — | EU AI Act "active RFC" trigger (Finding 5); erasure-path gap inherited from the existing L1/L2-vs-L3 disclosure (Finding 6) |

**Overall verdict, unchanged from both prior reports: still `not_yet` for shipping a live embedding-based L3 on the request path.** The trigger conditions named by the 2026-09-11 report (real production miss-telemetry; a genuinely lightweight embedding-generation path) are only partially advanced — the embeddings endpoint answers "is embedding generation now cheap and easy to call," not "does Kelvran have production traffic to size this against," which remains the binding gate. What *is* newly `build_now`-eligible, specifically because of this endpoint's existence: a design RFC for the write-path/read-path split (Finding 3), the compliance-note update (Finding 5), and — independent of the embedding-L3 decision entirely — the LiteLLM-style similarity-score response header (Finding 4).

## Caveats

- **Latency was not re-measured this round.** The 350-382ms figure is carried forward from the 2026-09-13 report's own live measurement against the same Bedrock Titan V2 model. Re-running that measurement *through* the now-shipped `/v1/embeddings` endpoint itself (rather than a bespoke SigV4 script) — and specifically testing whether the new `Dimensions=256` option measurably reduces it versus the 1,024-dimension default the original measurement used — is a real, cheap, concrete follow-up this round identifies but does not perform.
- **Redis LangCache's dedicated docs page returned HTTP 404 on direct fetch this round** (`redis.io/docs/latest/develop/ai/langcache/`), a live change since the prior reports cited it (they may have used a since-moved URL, or the docs restructured). This round's Redis LangCache claims lean on the landing page (`redis.io/langcache/`, fetched successfully) plus the arXiv paper (arXiv:2504.02268) already cited by the 2026-09-11 report — not an independent re-fetch of Redis's own detailed technical docs. Treat Redis-specific architectural claims in this report as inherited, not freshly re-verified.
- **This round did not run a multi-angle adversarial-verification research pass** (the 3-vote/6-angle methodology the 2026-09-13 report used) — it is a direct, single-pass code-and-primary-source verification exercise, scoped tightly to "what changed since the endpoint shipped." Confidence levels above reflect direct-verification-vs-inherited-citation, not a formal vote count.
- **FreshCache's, CacheAttack's, and the NDSS 2026 paper's own headline numbers were not independently re-fetched this round** — they are cited exactly as the 2026-09-13 report already verified them, which itself notes some (SAFE-CACHE, TrueFoundry) were split 2-1 votes rather than unanimous.
- **No real production traffic or miss-telemetry exists yet** — this remains true today exactly as both prior reports state, and is the actual binding gate on shipping the feature, independent of anything this round found about the embeddings endpoint.
- **Whether cache-generated embedding calls should be billed to the requesting tenant's own budget, or treated as unbilled gateway operating overhead, is a real, undecided product question this report does not resolve** — `HandleEmbeddings`' own cost-accounting path bills the *caller* of a client-facing `/v1/embeddings` request; an internal, cache-triggered embedding call has no natural caller to bill in the same way, and this asymmetry needs an explicit decision before any write-path embedding generation ships, not a default assumed silently.

## Open Questions

1. Does requesting `Dimensions=256` (now a live, one-line config choice on the Titan V2 adapter) measurably reduce the real per-call latency versus the 1,024-dimension default the 2026-09-13 measurement used, or does embedding-model compute time dominate regardless of output size? Untested; cheap to check with the now-shipped endpoint itself.
2. Should an internal, cache-triggered embedding call reuse `HandleEmbeddings`' full customer-facing pipeline (auth, per-key rate-limit, budget reserve, guardrail scan) or bypass it entirely as a lighter-weight internal call directly against the adapter/upstream — and if bypassed, what internal-only auditing/rate-limiting, if any, should replace it, given this call would run on every tenant's traffic continuously rather than only when a customer explicitly asks for embeddings?
3. Should cache-generated embedding cost be attributed to the requesting tenant's own budget (since it's serving their request) or treated as unbilled gateway infrastructure overhead? No decision exists yet either way.
4. Does the write-path (async, post-response) embedding generation this report proposes actually need Cache's own `Put` call to move to a background goroutine, or does the existing synchronous write path already run late enough (after the response has been serialized to the client) that this is a non-issue? Needs a direct read of the exact call site in the response-finalization path before design, not assumed here.
5. `cache-semantic-embedding-readiness-round4-2026-09-11.md`'s own Open Question about whether Kelvran's real per-tenant cache population would ever approach the ~100,000-entry brute-force ceiling remains exactly as open as it was — this round adds no new traffic data.
