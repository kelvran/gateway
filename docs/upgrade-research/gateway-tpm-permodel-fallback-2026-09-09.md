# TPM Has No Per-Model Dimension — Multi-Hop Fallback Gap — Deep Research (2026-09-09)

## Question

Kelvran's TPM (tokens-per-minute) rate-limit dimension has no per-model concept at all, unlike RPM. Specifically for requests that traverse a multi-hop fallback chain: how should Kelvran handle this? Grounded against Kelvran's own actual current state:

- `gateway/internal/ratelimit/limiter.go`'s `KeyConfig.PerModel` gives RPM a real per-model override map (`map[string]ModelRateLimit`). TPM has no equivalent construct anywhere in that package — `TPMCapacity`/`TPMRefillPerSecond` are single, key-scoped fields.
- RPM's fallback-hop-aware check is already fixed: `Pipeline.checkFallbackTargetRateLimit` (`dataplane.go` ~line 577) is called by `attemptFallbackChain`'s `rateLimitOK` closure (wired at ~lines 1066-1069) immediately before each candidate fallback target is attempted — skipping a rate-limited target exactly like an unhealthy one (no `consecutiveFailures` increment, no backoff charged), fail-open on a limiter backend error.
- TPM already has a real reserve-then-reconcile mechanism for its own key-level bucket: `KeyLimiter.ReserveTPM`/`ReconcileTPM` (`limiter.go` ~line 267/287) backed by `TokenBucket.ReserveTPM`/`ReconcileTPM` (`ratelimit.go` ~line 125/175) — the TOCTOU-safe pattern RPM's `Allow` also uses.
- The gap is documented as an honest, deliberately-unfixed FAIL case in Kelvran's own eval corpus: `evals/tests/fixtures/regression_corpus_cost_abuse.json`'s `costabuse-tpm-no-permodel-dimension-crossmodel-fallback-gap` (`verdict: verified_real_gap`), whose `corpus_note` explains why this is materially harder than the RPM fix: a TPM reservation made against the originally-requested model's bucket would need to be released and re-reserved against whatever model the fallback hop actually targets — a stateful, multi-step bookkeeping problem, not RPM's stateless per-attempt check.

## Summary

No surveyed production LLM gateway — LiteLLM, Kong AI Gateway, Envoy AI Gateway, Bifrost, TensorZero, Helicone — has solved "reserve a token budget against target A, release it, re-reserve against target B" for a fallback/failover hop. The field converges on one of two structurally simpler patterns instead: either (a) account tokens **retrospectively**, debiting the real usage only after the response completes with no pre-call reservation at all (Envoy AI Gateway, Kong's `cost` strategy, Bifrost), or (b) **document the gap as a known limitation** rather than solve it (Kong explicitly says a request "may succeed even if the final model has reached its limit" after a failover; Envoy's QuotaPolicy and Provider-Fallback docs never cross-reference each other; TensorZero's rate-limiting and retries/fallback docs are mutually silent). Two gateways — Bifrost and Envoy — do have a genuine per-model TPM-equivalent construct (Bifrost's `token_max_limit`/`token_reset_duration` per model-scoped config; Envoy's `perModelQuotas`), proving per-model TPM itself is a solved, shippable feature — but neither pairs it with fallback-hop-aware re-targeting. Kong is the closest direct precedent for Kelvran's exact shape: it has a per-model rate-limit construct AND a documented, named, unfixed failover gap identical in kind (though not in cause) to Kelvran's. The retrospective/debit-after-usage alternative is real and shipped in production (Envoy, Kong `cost` strategy, Bifrost) but trades a concrete, named cost: a burst of concurrent requests can all pass an admission check against an under-protected target before any of them reconciles (Envoy's own docs candidly describe an admitted stream being allowed to overshoot its bucket before the post-hoc charge lands). Given that (1) no production precedent exists for mid-chain reservation-transfer bookkeeping, (2) the exposure is bounded by RPM's now-fixed per-model cap plus the global key-level TPM bucket (both already enforced on every fallback hop), and (3) Kelvran has zero production traffic, the recommendation is to defer the fallback-hop TPM fix a second time with this research as the explicit justification, and if any change ships now, restrict it to documentation/telemetry rather than reservation-transfer plumbing.

## Findings

### Finding 1 — Per-model TPM is a solved, shipped feature in at least two production gateways (confidence: high, 3-0)

Bifrost's model-level `rate_limit` config carries `token_max_limit`/`token_reset_duration` as fields fully parallel to and independent of `request_max_limit`/`request_reset_duration`, attached to a `model_configs` entry via `rate_limit_id` — confirmed not just in docs but in the actual Go source (`framework/configstore/tables/ratelimit.go`'s `TableRateLimit` struct, validated and reset separately for each dimension) and a dedicated governance UI (`ui/app/workspace/model-limits/`). Envoy AI Gateway's `QuotaPolicy` natively supports `perModelQuotas`, assigning distinct token budgets to individual models (e.g. 10,000/1h for `gpt-4` vs 100,000/1h for `gpt-3.5-turbo`) — confirmed shipped (not aspirational) in the released v1.1.0 CR D type `PerModelQuotas []PerModelQuota`, not just main-branch docs. This establishes that Kelvran's RPM-shaped `PerModel` map is not an unusual ask to extend to TPM in isolation — the *mechanism* (per-model token bucket) has real precedent. Sources: [github.com/maximhq/bifrost/blob/main/docs/features/governance/model-limits.mdx](https://github.com/maximhq/bifrost/blob/main/docs/features/governance/model-limits.mdx), [github.com/maximhq/bifrost/blob/main/docs/features/governance/budget-and-limits.mdx](https://github.com/maximhq/bifrost/blob/main/docs/features/governance/budget-and-limits.mdx), [raw.githubusercontent.com/envoyproxy/ai-gateway/main/site/docs/capabilities/traffic/quota-policy.md](https://raw.githubusercontent.com/envoyproxy/ai-gateway/main/site/docs/capabilities/traffic/quota-policy.md).

### Finding 2 — No surveyed gateway does pre-call reservation for TPM at all; the dominant production pattern is retrospective, post-response debiting (confidence: high, 3-0)

Envoy AI Gateway charges token usage **after the response completes**: "Token usage is charged after the response completes... AI Gateway extracts token usage from the completed response and charges it towards the total," and admission checks for the *next* request use only already-charged history — never an estimate of the current request. It candidly documents the resulting weakness: an already-admitted stream is never interrupted even if it later pushes the bucket over budget (a concrete 1,000-token-bucket-pushed-200-over example). Kong's token-based `cost` strategy is identical in shape: "The cost for the AI Proxy or AI Proxy Advanced is only reflected during the next request" — cost can only be computed after the provider responds, so enforcement is inherently one-request-lagged, not a live reservation. Bifrost's own Go source confirms the same at the code level, not just doc level: `CheckRateLimits(ctx, rateLimits, nil, nil)` passes `nil` for both token and request baselines at every production call site (test-only code passes real values), `UpdateUsage` is gated on `update.TokensUsed > 0` (post-response only), and grepping the governance package for `inflight`/`pending`/`provisional`/`optimistic` returns zero hits. **No gateway in this survey implements a reserve-then-release-then-reconcile transaction for TPM the way Kelvran's own `ReserveTPM`/`ReconcileTPM` already does for its key-level bucket** — Kelvran's existing mechanism is, if anything, more sophisticated than any competitor's *baseline* token-accounting design, before even considering the fallback-transfer extension. Sources: [raw.githubusercontent.com/envoyproxy/ai-gateway/.../usage-based-ratelimiting.md](https://raw.githubusercontent.com/envoyproxy/ai-gateway/main/site/docs/capabilities/traffic/usage-based-ratelimiting.md), [developer.konghq.com/plugins/ai-rate-limiting-advanced/](https://developer.konghq.com/plugins/ai-rate-limiting-advanced/), [github.com/maximhq/bifrost/blob/main/docs/features/governance/budget-and-limits.mdx](https://github.com/maximhq/bifrost/blob/main/docs/features/governance/budget-and-limits.mdx).

### Finding 3 — Kong is the closest direct precedent for Kelvran's exact gap shape, and documents it as an accepted limitation rather than a solved problem (confidence: high, 3-0)

Kong's AI Rate Limiting Advanced plugin supports per-model policy-based limits (including token-count metrics via `tokens_count_strategy`), and its own docs state the caveat verbatim: **"these limits apply to the requested model. If a request is redirected to a different model after a failover, the request may succeed even if the final model has reached its limit."** This is a named, first-party admission of pre-failover-check/no-post-failover-recheck behavior — structurally the same failure mode as Kelvran's gap, though the root cause differs: Kong *has* a per-model construct and simply doesn't re-check it after failover, whereas Kelvran has no per-model TPM construct to re-check in the first place. No changelog entry (checked through the current release) ties any fix to reversing this caveat — it remains live in Kong's current documentation. This is direct evidence that even a mature, widely-deployed commercial AI gateway ships this exact class of gap into production and documents it rather than engineering around it with reservation-transfer logic. Source: [developer.konghq.com/plugins/ai-rate-limiting-advanced/](https://developer.konghq.com/plugins/ai-rate-limiting-advanced/).

### Finding 4 — Every gateway with both a token/quota construct and a fallback/retry mechanism keeps the two completely undocumented with respect to each other (confidence: high, 3-0)

Envoy AI Gateway's `QuotaPolicy` doc explicitly frames token quotas ("total consumption budget") as **distinct from** usage-based rate limiting ("controls request velocity"), and its only mention of fallback is a bare, unexplained cross-reference to a separate Provider Fallback doc — which, independently fetched, contains zero mention of `QuotaPolicy`, token quotas, or any accounting interaction with a fallback hop; its scope is limited to `backendRefs` prioritization and retry mechanics. TensorZero's rate-limiting doc (resource types `tokens`/`model_inferences`/`cost`, scoped only by tag or API key — no native per-model scoping at all, would require a manual tag bolt-on) contains no mention of retries or fallback; its separate retries/fallbacks doc (model-provider `routing`, variant `retries`, variant `fallbacks`) contains zero mentions of rate limits, tokens, or TPM anywhere — confirmed further by a repo-wide GitHub code search for `rate_limit` returning 0 results across TensorZero's entire codebase. This is a consistent pattern, not an isolated doc gap: **the entire surveyed field treats token-rate accounting and fallback/retry routing as orthogonal subsystems that are never jointly specified**, which is itself evidence that Kelvran's gap is a field-wide open problem, not something Kelvran uniquely failed to anticipate. Sources: [raw.githubusercontent.com/envoyproxy/ai-gateway/.../quota-policy.md](https://raw.githubusercontent.com/envoyproxy/ai-gateway/main/site/docs/capabilities/traffic/quota-policy.md), [github.com/tensorzero/tensorzero/blob/main/docs/operations/enforce-custom-rate-limits.mdx](https://github.com/tensorzero/tensorzero/blob/main/docs/operations/enforce-custom-rate-limits.mdx), [github.com/tensorzero/tensorzero/blob/main/docs/gateway/guides/retries-fallbacks.mdx](https://github.com/tensorzero/tensorzero/blob/main/docs/gateway/guides/retries-fallbacks.mdx).

### Finding 5 — Bifrost's fallback IS rate-limit-state-driven, but at provider granularity via retrospective accounting, not model-granular reservation transfer (confidence: high, 3-0)

Bifrost explicitly ties fallback to rate-limit state: "If a provider config exceeds its rate limits, that provider is excluded from routing, but other providers within the same virtual key remain available" — confirmed live in `docs/features/governance/budget-and-limits.mdx` and in the actual `PreLLMHook` implementation (`plugins/governance/main.go`), which is tested (`TestPreLLMHook_ProviderRateLimitExceeded_NoVirtualKey`). Every provider in the fallback set, including fallback targets, carries its own independently-enforced rate limits — the fallback target is not unlimited. But this operates at **provider** granularity (OpenAI vs. Anthropic), not per-model, and the underlying token accounting behind it is the same purely retrospective, no-reservation design from Finding 2 — so Bifrost's fallback-aware rate limiting sidesteps the reservation-transfer problem entirely by never reserving in the first place. This is the single closest real-world analog to "rate-limit state gates fallback progression" that Kelvran's own RPM fix already implements (`checkFallbackTargetRateLimit`), and it confirms Kelvran's RPM fix's *shape* (a non-reserving, stateless per-attempt check) is the production-proven pattern — while confirming that pattern has never been extended to a reserving dimension like TPM anywhere in this survey. Source: [github.com/maximhq/bifrost/blob/main/docs/features/governance/budget-and-limits.mdx](https://github.com/maximhq/bifrost/blob/main/docs/features/governance/budget-and-limits.mdx).

### Finding 6 — Helicone has no TPM dimension at all, at any scope, confirming this is a genuinely hard/low-priority feature industry-wide, not just for the fallback case (confidence: high, 3-0)

Helicone's rate-limiting docs list "Token-based rate limiting" explicitly under **"Coming Soon"** — unreleased, planned, not shipped — with only request-count and cost-in-cents limits live today, and only three scopes exist at all (Global, Per-User, Per-Property), none of them per-model. This is useful negative evidence: even the base case (any TPM limiting, ignoring fallback entirely) is still unshipped in at least one actively-maintained gateway, which contextualizes Kelvran's gap as sitting on a spectrum of "how much of TPM governance has this gateway built" rather than being an anomalous omission. Source: [docs.helicone.ai/features/advanced-usage/custom-rate-limits](https://docs.helicone.ai/features/advanced-usage/custom-rate-limits).

## Answers to the Four Research Sub-Questions

**1. Is there real precedent for "reserve against A, release, re-reserve against B" bookkeeping across a fallback hop?** No. Across all six gateways surveyed, zero implement a reservation-transfer mechanism for token-rate limiting across a fallback/retry chain. Production systems structurally avoid the problem, not solve it — either by never reserving pre-call at all (Envoy, Kong, Bifrost's retrospective debit model, Finding 2) or by keeping rate-limit granularity at a level (provider, not model — Finding 5) or a scope (tag/key, not model — Finding 4) where the transfer problem doesn't arise, or by simply documenting the gap as a known limitation (Kong, Finding 3). Kelvran's own `ReserveTPM`/`ReconcileTPM` key-level mechanism is already more advanced than any competitor's token-accounting design surveyed here.

**2. Is retrospective (debit-after-actual-usage, no pre-call reservation) a safer/simpler alternative, and what's the real tradeoff?** Yes, it is simpler, and it is the field's actual dominant pattern (Finding 2) — but the tradeoff is real and openly documented by its own implementers, not hypothetical: Envoy's docs state directly that an admitted stream is never interrupted even after it's known to have overshot the bucket, and enforcement of the *next* request depends on usage from *already-completed* prior requests, meaning any concurrent burst against the same target is admitted essentially unmetered until each individual response completes and reconciles. This is exactly the "burst of concurrent requests all reserving against the same under-protected fallback target before any of them reconciles" tradeoff the question anticipated — it is not merely theoretical, it is the documented, accepted behavior of at least two production gateways (Envoy, Kong) today. For Kelvran specifically, adopting pure retrospective TPM accounting for the fallback path only would be a *regression* relative to Kelvran's own existing pre-call `ReserveTPM` design for the direct path — trading a known TOCTOU race Kelvran already solved for RPM/TPM at the key level for a reintroduced one, scoped narrowly to fallback hops.

**3. Is this a genuinely exploitable attack, or a narrower/lower-severity gap than the now-fixed RPM one?** Narrower and lower-severity, for two concrete, code-grounded reasons. First, the now-fixed RPM gap (`costabuse-permodel-ratelimit-bypassed-via-crossmodel-fallback-chain`) was a complete bypass of an operator-configured control — an expensive model's RPM cap was *entirely unenforced* for any request that reached it via a fallback hop, with no other RPM-shaped control catching it. The TPM gap is different in kind: there is no PerModel TPM control anywhere for ANY access path (direct or via fallback) to bypass — this is a feature absence, not a broken enforcement point, so there's nothing being "bypassed" in the sense of a control silently failing to fire. Second, and more importantly for real exposure: Kelvran's already-fixed RPM per-model check (`checkFallbackTargetRateLimit`) already gates every fallback hop by request count, and the pre-existing key-level `TPMCapacity` global bucket (reserved once, pre-routing, via `ReserveTPM(vk.ID)`) already bounds the aggregate token throughput for the *whole* virtual key across all models it might fall back to — an adversary cannot drive unbounded token throughput through a fallback chain even without per-model TPM, because the coarser key-level TPM ceiling and the now-fixed per-model RPM ceiling both still apply on every hop. What's missing is *only* the ability for an operator to cap one specific model's token throughput independently of the key's aggregate cap and other models' RPM — a real gap in operator cost-governance granularity, not an open door to unbounded adversarial cost/DoS.

**4. Concrete recommendation for Kelvran.** See below.

## Kelvran-Specific Design Sketch & Recommendation

**Do not build mid-chain TPM reservation-transfer now.** Finding 1 confirms per-model TPM as a static construct is easy and well-precedented to build; the hard part the eval corpus's own `corpus_note` identifies — release a reservation against the originally-requested model's bucket, re-reserve against whichever model a fallback hop actually lands on, and thread that final `(bucket key, reservedTokens)` pair back out through `attemptFallbackChain → runMissPath/streamDeploymentWithFallback → HandleChatCompletion/HandleChatCompletionStream → finalize`'s `ReconcileTPM` call — has **zero production precedent anywhere in this survey**. Building it now means designing blind, ahead of the field, for a threat this research (sub-question 3) shows is bounded, not urgent, given Kelvran's existing key-level TPM ceiling and now-fixed per-model RPM ceiling.

**Extending `PerModel` to TPM for the direct (non-fallback) path only is a reasonable, low-risk interim step — but is not free, and should be sized honestly.** Finding 1's precedent (Bifrost, Envoy) is for a *static* per-model bucket checked at request time, structurally similar to how Kelvran's existing `AllowForModel`/`PerModel` RPM check already works for the direct path. However, unlike RPM's `Allow` (non-reserving, stateless), TPM's own dimension is inherently reserving (Kelvran's `ReserveTPM`/`ReconcileTPM`), so a `PerModel` TPM bucket would need its own reserve/reconcile pair per model, mirroring the key-level pattern — a real but bounded, single-call-site change (`checkRateLimit`'s existing `ReserveTPM(vk.ID)` call becomes `ReserveTPM(vk.ID, req.Model)`-shaped, plus the matching `ReconcileTPM` in `finalize`), entirely on the direct/pre-fallback path Kelvran already fully controls today. This does **not** extend to fallback hops — a fallback candidate's `PerModel` TPM bucket, if one existed, still could not be safely checked without first solving the reservation-transfer problem, so it would need to be explicitly excluded from `checkFallbackTargetRateLimit`'s mirror, exactly as the eval corpus's `corpus_note` already anticipates.

**Recommendation: defer the fallback-hop TPM fix a second time, explicitly, with this research as the justification — and treat "extend `PerModel` to TPM for the direct path" as a separate, smaller, optional follow-up, not a substitute fix for the fallback gap.** Three things converge on this:
1. No production gateway surveyed (LiteLLM's TPM-per-deployment config, Bifrost, Envoy, Kong, TensorZero, Helicone) has solved fallback-hop-aware token-rate reservation transfer — Kelvran would be building a genuinely novel mechanism, not catching up to an established pattern (Findings 1-5).
2. The real-world exposure is already bounded by two controls that already run on every fallback hop today — the now-fixed per-model RPM check and the pre-existing key-level TPM ceiling — so the marginal adversarial cost/DoS risk of leaving this specific gap open a while longer is genuinely lower-severity than the RPM gap was before its own fix (sub-question 3).
3. Kelvran has zero production traffic (consistent with this repo's existing "instrument now, adapt later" pattern used to defer other traffic-dependent decisions, e.g. `docs/upgrade-research/gateway-routing-scope-2026-09-07.md`'s adaptive-routing deferral) — there is no live signal yet to validate that a reservation-transfer design, invented from scratch with no precedent, would even be correctly shaped.

**Concrete next step, if any is taken now:** update `costabuse-tpm-no-permodel-dimension-crossmodel-fallback-gap`'s `corpus_note` (or a new RFC) to record this research's finding that the gap is industry-wide and structurally hard, not a Kelvran-specific oversight — and, only as an optional, clearly-separate follow-up, extend `KeyConfig.PerModel`'s TPM-equivalent to the direct (non-fallback) path alone, explicitly scoping fallback hops out of that check's coverage the same way the RPM fix's own `checkFallbackTargetRateLimit` is explicitly scoped IN to fallback hops today — so operators reading the two features side by side understand the asymmetry is deliberate, not a bug.

## Caveats

- **Coverage is uneven across the six surveyed gateways.** LiteLLM's per-deployment TPM config (Claim 0) and its fallback-mapping structure (Claim 1) were confirmed, but no claim about LiteLLM's specific *fallback-triggered* TPM-accounting behavior survived verification (the two LiteLLM claims attempting this — reactive-fallback-only triggering, and provider-error-text-sourced TPM signals — were refuted 0-3). This means LiteLLM, despite being named in the original research question, contributes essentially nothing to the fallback-TPM-interaction question specifically, beyond confirming per-deployment TPM config exists.
- **A LiteLLM bug report (Claim 2) about repeated fallback re-triggering is real but off-topic** — it documents a since-patched (v1.80.15, fixed within days) terminal-state bug in fallback looping, unrelated to TPM/token accounting, and is included here only as background on LiteLLM's fallback engine's general maturity, not as evidence about token-rate behavior.
- **Kong's precedent (Finding 3) is analogous, not identical.** Kong's gap is "has a per-model construct, doesn't re-check it post-failover"; Kelvran's gap is "has no per-model TPM construct at all." The lesson (ship a documented limitation rather than a partial fix) transfers; the specific remediation path does not.
- **No claim in this research addresses whether any gateway's own internal engineering teams *attempted and rejected* reservation-transfer as a design** — the survey found only that no gateway *shipped* it, and that the two gateways with the clearest adjacent mechanism (Envoy's QuotaPolicy, Bifrost's provider-level fallback gating) documented it as out of scope or simply never mentioned the interaction, which is suggestive but not proof that the idea was considered and rejected on its merits elsewhere.
- **Time-sensitivity**: all sources were fetched live on 2026-09-09 against currently-maintained repos/docs (Bifrost HEAD commit dated 2026-09-07, Envoy AI Gateway v1.1.0 released 2026-08-21, Kong's docs current). This is a fast-moving space — a per-model TPM-aware fallback re-check could ship in any of these projects without much notice; this report reflects the field's state as of this date, not a permanent absence.

## Open Questions

- Would a *narrower* fallback-aware TPM check — e.g., checking the fallback target's per-model TPM bucket's `HasBalance`-equivalent read-only, without reserving anything, purely to *skip* an obviously-exhausted target the same way RPM's `AllowForModel` does — be safe enough to ship without the full reserve/release/re-target bookkeeping? This sidesteps reservation-transfer entirely (no reservation is made until the final serving model is known) but was not evaluated by any surveyed gateway's documented design, so its own correctness (e.g., interaction with `ReconcileTPM`'s existing key-level accounting) would need to be worked out from first principles, not from precedent.
- Do any of the surveyed gateways' *paid/enterprise* tiers (as opposed to the OSS docs surveyed here) implement fallback-aware token accounting that isn't publicly documented? Not checked in this pass.
- What does LiteLLM's per-deployment TPM config (Claim 0) actually do when a `fallbacks`-triggered switch lands on a deployment whose own TPM bucket is already exhausted — is it silently ignored (mirroring Kong's documented gap), enforced via some undocumented mechanism, or untested/undefined? This is the single most directly relevant unanswered question and was not resolved despite being the closest structural analog to Kelvran's own `PerModel` design; the two claims attempting to establish LiteLLM's fallback-TPM interaction behavior were both refuted on verification.
- Kelvran's own eval corpus_note proposes a specific multi-hop threading design (release pre-routing reservation → reserve against actually-served hop's bucket → thread final `(bucket key, reservedTokens)` back through `finalize`). Given that no external precedent exists to validate this shape, would a smaller experiment (e.g., a feature-flagged, metrics-only "shadow" reservation-transfer that logs what it *would* have done without affecting real admission decisions) be a viable way to gain real-traffic evidence before committing to the full design — mirroring Envoy QuotaPolicy's own `shadowMode` field?
