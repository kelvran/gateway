# Model Cascading / Cost-Aware Routing, Re-Evaluated Against Real Pilot Traffic and a New Contract — Deep Research (2026-09-20)

## Question

Kelvran now has real production traffic (a live Bedrock pilot account, dry-run-proven 2026-09-19), a `GatewayDecisionEvent` contract carrying `agent_run_id`/`cost_usd`/`outcome` per request (`api/gatewayevents/v1/gatewayevents.proto`), and `evals cost-report --agent-run-id`. Does this change the `not_yet` verdict recorded in `DECISIONS.md`'s `[2026-09-14]` (fourth entry) — "Kelvran has no request-level confidence/refusal/complexity signal today to drive a cascade decision at all," citing LLMRouterBench/ACL Findings 2026's finding that OpenRouter's own commercial auto-router underperforms simply picking the best model by -24.7%? This report independently re-verifies that claim against its primary source rather than trusting the prior report's summary, and surveys the current (2026) state of production routing/cascading tooling (RouteLLM, Martian, Not Diamond, Unify.ai, semantic-router) for what input signal each actually requires — specifically whether any avoids a pre-trained classifier.

## Context (Kelvran's own real, current state)

`GatewayDecisionEvent` (`api/gatewayevents/v1/gatewayevents.proto`) is real and shipping: one message per `HandleChatCompletion`/`HandleChatCompletionStream` call, carrying `trace_id`/`span_id`, `outcome` (a 10-value enum: OK plus 9 rejection/failure categories — auth, model-not-allowed, rate-limited, budget-exceeded, no-deployment, upstream-error, guardrail-blocked, deployment-capacity), `agent_run_id`, `cost_usd`, `savings_usd`, `cost_is_estimated`, and `billing_subject_id`. `evals cost-report --agent-run-id` (`evals/evals/cli.py:1690`) is real and does exactly what its name says: lists ingested `gatewayevents_v1` objects, filters to one `agent_run_id`, sums `cost_usd`/`savings_usd` as Decimal. Confirmed directly against both files, not assumed from an architecture doc. The Bedrock pilot is real — `DECISIONS.md`'s `[2026-09-19]` (fourth entry) describes an actual end-to-end dry-run against the real pilot AWS/Bedrock account (a temp copy of the real `config.yaml`, never the live file) exercising golden-path chat, WRR fallback, distributed rate limiting, embeddings, sticky routing, budget rejection, real Bedrock Guardrails, and cache write/hit/erase.

## Summary

The prior `not_yet` verdict is still correct, but for a narrower reason than originally stated, and one piece of its evidence needs a correction. First, the correction: LLMRouterBench's `-24.7%` figure is real — independently re-extracted from the ACL Anthology PDF itself (`aclanthology.org/2026.findings-acl.1881.pdf`), not just the prior report's summary — but it measures a specific, now-superseded version of OpenRouter's Auto Router (the paper's own citation is dated 2025/early-2026, and OpenRouter replaced that mechanism with a market-spend-based router on 2026-08-10). Citing it as evidence about OpenRouter's *current* commercial auto-router, in the present tense, is stale. The paper's other, more load-bearing finding — that the dominant driver of the remaining gap to an Oracle router is "model-recall failure," confirmed at Recall@3 of only 46.1%/50.6% for two tested baselines — is unaffected by this correction and remains the strongest reason not to build a classifier/embedding router regardless of Kelvran's own data situation. Second, on Kelvran's own signal gap: `GatewayDecisionEvent` itself still carries no quality/confidence signal — its `Outcome` enum distinguishes *why a request was rejected*, never *whether a completed response was good*. But two real, already-parsed per-response primitives exist in the canonical adapter schema (`gateway/internal/adapter/types.go`) that neither the 2026-09-11 nor 2026-09-13 nor 2026-09-14 research passes named: `Message.Refusal` (added 2026-09-12, response-only, only populated by 2 of 5 adapters) and `Choice.FinishReason` (present since day one, normalized across all 5 adapters, but today used only to gate cache writes against truncated responses). Neither is wired to any decision, and neither reaches `GatewayDecisionEvent`. The accurate framing is "no signal wired to any decision" — a real gap, but smaller than "no signal exists at all." Separately, the 2026 production landscape has one genuinely new, real, live example beyond Ramp: Databricks' Unity Gateway "Smart Routing," now in beta inside Claude Code and Codex, which routes at session-start via a lightweight task-classifier and validates itself through the same evaluation-layer/production-trace pattern Kelvran's own `evals` subsystem already is — except Kelvran's evals-to-gateway link today is a one-way, offline, human-triggered report, never a live feedback loop into a routing decision.

## Findings

### Finding 1 — The LLMRouterBench `-24.7%` figure is real, independently confirmed word-for-word against the primary-source PDF, but it measures OpenRouter's Auto Router as it existed before OpenRouter's own 2026-08-10 rewrite, not the router live today (confidence: high)

Downloaded and text-extracted `aclanthology.org/2026.findings-acl.1881.pdf` directly (`pdftotext -layout`, cross-checked byte-level against a grep false-negative caused by embedded null bytes). The paper (Li et al., *LLMRouterBench: A Massive Benchmark and Unified Framework for LLM Routing*, Findings of ACL 2026, pp. 37733–37754, also `arXiv:2601.07206`, submitted 2026-01-12 per alphaXiv) states verbatim: "the commercial router OpenRouter yields the smallest (indeed, negative) performance improvement (-24.7%) relative to the Best Single model and fails to match its performance, despite operating over a much larger candidate pool," with a footnote that "OpenRouter uses a platform-defined model pool that differs from ours and is not user-configurable (OpenRouter, Inc., 2025a)." The paper's own bibliography cites `OpenRouter, Inc. 2025a. Auto router - api, providers, stats. https://openrouter.ai/openrouter/auto`, and separately dates OpenRouter latency data used elsewhere in the paper to "Jan. 2026." Independently fetching OpenRouter's *own* current documentation (`openrouter.ai/docs/guides/routing/routers/auto-router`) and blog (`openrouter.ai/blog/announcements/introducing-the-new-auto-router`, dated 8/10/2026) shows OpenRouter shipped "a major update to our Auto router" on that date, moving from a per-request quality-prediction mechanism to a "wisdom of the market" design: a ~30-way task classifier feeding a ranking by trailing-7-day aggregate community spend share, explicitly "no retraining or manual curation" needed as the market shifts, no embeddings, no LLM-as-judge. A third-party comparison source (morphllm.com) independently corroborates that the *prior* Auto Router "powers OpenRouter's Auto mode" via Not Diamond's trained meta-model classifier ("You supply prompts, candidate model responses, and evaluation scores"). Taken together: LLMRouterBench measured the Not-Diamond-powered, pre-rewrite Auto Router (accessed circa late 2025/January 2026), which OpenRouter itself discontinued roughly seven months later. The `-24.7%` figure is a real, rigorously-obtained number about a real product — just not the product currently live.

**Build now / not yet: not_yet**, unchanged — but the citation itself needs correcting wherever it's repeated in present tense. Trigger to re-verify: if this figure is cited again, re-check it against OpenRouter's *current* router, not the one this paper measured.

### Finding 2 — LLMRouterBench's single most load-bearing finding — "model-recall failure" as the dominant driver of the remaining Oracle gap — is independently confirmed and is NOT specific to OpenRouter or to any data-volume gap; it holds across the full field the paper tested (confidence: high)

Directly from the extracted text: "A key contributor is model-recall failure: when only one or a few candidate models produce the correct answer, current routers often fail to select them... on queries where at most three experts answer correctly (410 queries, 11.9% of the test set), Avengers and EmbedLLM achieve low accuracy (24.6% and 23.2%, respectively)." The paper's own Recall@k table (Table 5) confirms: "even with k=3, Recall remains limited for both Avengers (50.6%) and EmbedLLM (46.1%), meaning the correct model is not ranked among the top candidates." This is the same number the prior 2026-09-13 Kelvran report cited (46–51% at k=3), now confirmed directly against the primary source rather than the prior report's paraphrase. Separately, the paper found leading routing methods achieve "up to a 4% average accuracy gain" and "up to a 31.7% cost reduction" over Best Single, but "several routers fail to outperform the Best Single, and some (especially binary routers, such as HybridLLM and FrugalGPT) struggle." This is a field-wide result across 10 baselines (RouterDC, EmbedLLM, MODEL-SAT, GraphRouter, Avengers, HybridLLM, FrugalGPT, RouteLLM, Avengers-Pro, OpenRouter), not an artifact of OpenRouter's specific (now-superseded) mechanism — Finding 1's correction narrows only the OpenRouter-specific headline number, not this broader, still-current conclusion.

**Build now / not yet: not_yet**, and this is the finding that should carry the most weight in any future re-evaluation — it means even a hypothetical future Kelvran router built on richer signals than Kelvran has today would face a real, currently-unsolved industry bottleneck, not merely a data-availability problem that more traffic would fix on its own.

### Finding 3 — `GatewayDecisionEvent` is a real, shipping outcome/cost/attribution ledger, not a quality signal; Kelvran's own durable contract still discards the one dimension a cascade decision would need (confidence: high)

Read directly against `api/gatewayevents/v1/gatewayevents.proto`: every field added since the message's creation (`agent_run_id`, `cost_usd`, `savings_usd`, `cost_is_estimated`, `billing_subject_id`) is about *spend attribution*, and `Outcome`'s 9 non-OK values are all *rejection reasons* determined before or at the point of calling a model (auth failure, budget exceeded, rate limited, no deployment, guardrail blocked, deployment capacity) or a generic upstream failure — never a judgment about whether an `OUTCOME_OK` response was actually good. This confirms the core of the 2026-09-14 verdict is still accurate for this specific contract: nothing here can drive a cascade "was the cheap model's answer good enough" decision.

**Build now / not yet: not_yet** for adding a quality dimension to this contract specifically — see Finding 4 for what's separately, already available elsewhere in the codebase.

### Finding 4 — Two real, already-computed per-response signal primitives exist elsewhere in the canonical schema that no prior research pass named, though both are unused for any decision and neither reaches `GatewayDecisionEvent` (confidence: high)

`gateway/internal/adapter/types.go`'s `Message.Refusal` field (added 2026-09-12, confirmed via `git log -S`, predating the 2026-09-14 "no signal at all" research pass by two days) is populated from OpenAI's real `ChatCompletionMessage.refusal` field and openaicompat's equivalent — "the model's own explanation for declining to comply with the request" — but the comment explicitly documents it as response-only, read by no adapter on the request path, and populated by only 2 of 5 adapters (Anthropic/Gemini/Bedrock signal the analogous condition through `finish_reason` instead and leave `Refusal` permanently empty). Separately, `Choice.FinishReason` is a canonical field normalized across *all five* adapters (confirmed present since the repo's initial scaffolding commit), and is a real, already-computed per-response signal today — but its only current consumer is `dataplane.responseWasTruncated` (`dataplane.go:3276`), which gates cache writes against replaying a truncated response, not any routing/escalation decision. Neither field is threaded into `GatewayDecisionEvent`, neither is inspected by `dataplane`'s existing deterministic, error-classified fallback chain (`attemptFallbackChain`), and no retry/cascade/escalation code path exists anywhere in `gateway/internal/router` or `gateway/internal/gateway/dataplane` that could consume either signal even if it were exposed. This directly narrows (without fully overturning) the 2026-09-14 verdict's claim: the raw post-hoc signal Kelvran would need for an AutoMix-style "generate cheap, then check a refusal/verification signal, escalate if it fails" cascade is not absent from the codebase — it's unused and incompletely covered, which is a real but smaller and cheaper-to-close gap than "the signal doesn't exist."

**Build now / not yet: not_yet** for a cascade decision itself (no escalation infrastructure exists to consume the signal, and Finding 2's model-recall-failure bottleneck means even a working escalation loop might not pay off) — but **build_now-sized** as a much narrower, disclosure-only step: threading the already-computed, already-universal `FinishReason` onto `GatewayDecisionEvent` as a new additive field (mirroring the `cost_is_estimated` precedent's own non-breaking pattern) would cost near-zero new engineering and stop discarding a signal Kelvran already produces on every single request, independent of whether or when any cascade logic is ever built on top of it.

### Finding 5 — Surveyed against Kelvran's actual question ("does any 2026 production/OSS router avoid a pre-trained classifier"): every commercial router checked requires either a trained model or an offline, vendor-controlled profiling process; exactly one open-source library (semantic-router) is genuinely training-free, but it solves a different problem (confidence: high)

Not Diamond's own current docs (`docs.notdiamond.ai/docs/router-training-quickstart`, `/docs/key-concepts`) are explicit: both its "pre-trained" and "custom" router types are trained meta-models — a custom router needs "prompts, candidate model responses, and evaluation scores" (minimum 15 samples, up to 10,000 samples/5MB per job, independently confirmed via a third-party comparison source). Martian's "Model Mapping" is a proprietary, vendor-run interpretability process that converts each candidate model into an internal representation used to predict its performance on a prompt without running it — real and distinctive, but not something Kelvran (or any customer) can compute itself from its own traffic; it is Martian's own offline artifact, not a zero-data mechanism. Unify.ai uses "a neural scoring function to estimate how well each model would respond to a specific prompt" (per an independent third-party summary) — also a trained model. The one architecture found in this pass that requires neither historical traffic nor a trained classifier is Aurelio Labs' `semantic-router` (open source, ~3.7k GitHub stars): routes are defined as a handful of hand-authored example utterances per route, encoded once via an off-the-shelf embedder (OpenAI/Cohere/etc.), and a query is routed by nearest-neighbor cosine similarity — "a vector lookup rather than a generation," explicitly zero training. This is architecturally close to RouteLLM's similarity-weighted-ranking router, but bootstrapped from a small hand-curated exemplar set instead of a large historical preference dataset. It is designed and evaluated for intent/tool routing (e.g., "politics" vs. "chitchat" branches for a chatbot), not for quality-cost model selection, and no source in this pass evaluated it in that role at production scale.

**Build now / not yet: not_yet** for adopting semantic-router's mechanism as Kelvran's cost-aware model router specifically — it would still require someone to hand-author which model each exemplar utterance should route to, which is a real, human-authored ground-truth requirement, just a much smaller one (a curated utterance list, not a production-scale labeled query corpus) than every other option surveyed. Worth naming as the cheapest bootstrap path if Kelvran ever revisits this space, not as something to build today.

### Finding 6 — A new, real, live 2026 production deployment beyond Ramp exists (Databricks Unity Gateway's "Smart Routing," beta, live inside Claude Code and Codex today) and it validates itself via the same evaluation-layer pattern Kelvran's own `evals` subsystem already is — except Kelvran's own evals-to-gateway link is one-way and offline (confidence: high)

Databricks' own blog post (`databricks.com/blog/smart-routing-unity-ai-gateway...`) describes a real, beta-production system, not a research prototype: "Smart Routing is now available in Beta through Unity Gateway," live "inside Claude Code and Codex today." Its mechanism is deliberately session-start, not per-request: a cheap, low-latency model reads the task description at the start of a session and labels it with semantic fields (code area, evidence present, how localized the fix appears), from which the router derives a task-type/language-family and picks a model tier — explicitly rejecting per-request classification because "consecutive turns" need to hit the same model to preserve prompt-cache hit rate, which the post states dominates real cost. Reported production numbers: "at just 65% of the cost per task of a leading model" on internal workloads, "less than half the cost" at matched quality on public benchmarks, 35%/56% cost savings respectively. Critically, Databricks validates routing *changes* (not each individual routing decision) by "analyz[ing] traces" via "AI models and human review" — an evaluation layer over production traces, exactly the shape `braintrust.dev`'s own 2026 taxonomy of routing (`best-llm-routers-2026`) names as the hard requirement for "quality routing": "evaluation results, production traces, and scorer outputs," stating flatly that this category "requires an evaluation layer underneath the gateway to produce reliable scores" and finding no method in its own survey that achieves quality-based routing without one. Kelvran's `evals` subsystem is architecturally exactly this kind of evaluation layer (judge panels, regression corpus, now joinable to real gateway spend via `agent_run_id`) — but today the join is a one-way, offline, human-triggered CLI report (`cost-report --agent-run-id`), never a live signal feeding back into a routing decision the way Databricks' trace-analysis loop does.

**Build now / not yet: not_yet** for building an online eval-feedback routing loop at Kelvran — but this is the clearest concrete precedent yet found for what Kelvran's own evals-gateway boundary would need to grow into if it ever pursues this, and it reframes the right comparison: Kelvran is missing the *live feedback loop*, not the *evaluation layer* itself, which already exists in a different (offline) shape.

### Finding 7 — Kelvran's "real pilot" is a dry-run-proven live AWS/Bedrock account, not a demonstrated sustained-volume production workload; no requests/day or per-deployment volume figure exists anywhere in this repo's own record to check against the traffic-volume floor every prior research pass named as the actual blocker (confidence: medium)

`DECISIONS.md`'s `[2026-09-19]` (fourth) entry describes a single end-to-end dry-run session against the real pilot AWS/Bedrock account, using a temp config with a deliberately-diverse traffic mix constructed for test coverage (a broken WRR-fallback sibling, a sticky-canary sibling, an embeddings deployment) — this proves the pilot account and gateway work correctly together, not that sustained customer query volume now exists. No entry in `DECISIONS.md` or `docs/agents/LOGS.md` reviewed in this pass states a requests/day, QPS, or per-deployment sample count for the pilot. The 2026-09-09 router-health research and the 2026-09-13 adaptive-routing research both named a minimum-sample-size volume floor (mirroring Envoy/Linkerd/Hystrix) as the actual trigger for wiring any traffic-derived signal, health or otherwise — that same floor would apply to a bandit-style cost/quality re-weighting layer (the one build_now-adjacent recommendation from the 2026-09-13 report) exactly as much as to a classifier-based router, and this pass found no evidence the floor has been crossed, only that a live account now exists to eventually cross it.

**Build now / not yet: not_yet**, and specifically: do not treat "the pilot account is live" as equivalent to "the traffic-volume floor is met" — those are different claims, and only the first is currently supported by this repo's own record.

## Caveats

- The OpenRouter blog post's date (8/10/2026) is read as US-style MM/DD/YYYY (2026-08-10) per the vendor's own byline formatting convention; this was not independently cross-checked against a web archive snapshot, only against the vendor's own currently-live page and a third-party comparison article's independent corroboration that Not Diamond previously powered OpenRouter's Auto mode.
- The OpenRouter blog's "over 55T in weekly token spend" figure is quoted as-is from the vendor's own post; it was not independently verified and may refer to token *volume* rather than a dollar figure — treat as an unverified vendor claim, consistent with this repo's own prior finding (`llm-cost-optimization-finops-2026-09-14.md` Finding 2) that vendor headline routing/cost numbers routinely fail independent verification.
- Martian's and Unify.ai's mechanisms are described here from third-party summaries and comparison sites (siliconangle.com, hpcwire.com, a Perplexity-generated summary), not each vendor's own current first-party technical documentation, which was not found to describe the underlying mechanism in comparable technical depth to Not Diamond's or OpenRouter's own docs — confidence in the specific mechanism descriptions for these two is correspondingly lower than for OpenRouter, Not Diamond, semantic-router, and Databricks.
- Finding 7's "no evidence the floor has been crossed" is an absence-of-evidence finding from this repo's own written record, not a live check against the actual pilot account's real traffic — this report did not query any live metrics endpoint or dashboard; it is scoped to what `DECISIONS.md`/`docs/agents/LOGS.md` themselves disclose.
- Databricks' Smart Routing numbers (35%/56%/65%-of-cost) are the vendor's own self-reported figures from its own blog post, not independently audited — flagged with the same skepticism this repo's own prior research applies to all vendor-reported routing savings figures, even though the deployment's existence and beta-production status are independently plausible (visible inside two named, real products — Claude Code and Codex).
