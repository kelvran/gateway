# Load Testing and Capacity Planning for LLM-Gateway Traffic Shapes — Deep Research (2026-09-14)

## Question

Load testing and capacity-planning methodology for Kelvran, tailored to real LLM-gateway traffic shapes (bursty, long-tail latency, streaming, cache-hit-skewed) — distinct from the separate chaos-engineering/resilience-testing research pass (fault injection, concurrency-race testing). This pass covers throughput/capacity/latency-under-load methodology specifically: (1) tool choice for a gateway proxying real, costly, rate-limited upstream providers; (2) realistic traffic-shape generation (Poisson/bursty arrivals, cache-hit-skewed repeat traffic); (3) capacity-planning metrics that matter for Kelvran's own architecture; (4) whether a cheap, CI-integrated smoke-level load tier is worth adding today; (5) gaps flagged by a 2026 survey of LLM-gateway-specific load-testing practice.

## Context (Kelvran's own real, current state)

Already real and shipped, out of scope to re-litigate: per-key RPM/TPM rate limiting (`gateway/internal/ratelimit/limiter.go`, including per-model overrides and an optional in-memory-only TPM dimension) and per-key concurrency caps (`ConcurrencyLimiter.MaxInFlight`, `gateway/internal/ratelimit/concurrency.go`, single-instance in v1 by explicit design); Redis-backed distributed rate limiting proven across 2 real instances; a real, live-verified 20-request concurrent burst test methodology already run manually this week that found a real WRR fallback race bug, but not yet promoted to a permanent, repeatable load-test suite; real coverage/CI gates for functional correctness (not load/throughput).

`docs/testing/TESTING.md` §7 ("Load/Performance Tests") already establishes the load-testing tier's shape: mocked upstream only ("a real provider's rate limits would throttle the test itself, not measure Kelvran"), `k6` or `vegeta` named as the Go-side tool options, a tiny PR-blocking smoke test plus a full nightly/pre-release profile, and p50/p95/p99 latency + memory tracked as trend lines rather than pass/fail thresholds only. This confirms a load-testing tier already exists in the documented strategy — what does **not** yet exist is: an actual implemented mock-upstream harness, any traffic-shape-aware (Poisson/bursty/cache-skewed) load generation, or a defined capacity-planning scorecard. A prior, adjacent research pass (`docs/upgrade-research/gateway-load-testing-methodology-2026-09-12.md`) already covered gateway-overhead benchmarking methodology in depth (mock-upstream isolation is the universal vendor pattern, k6/Locust as generic tools, LiteLLM's `x-litellm-overhead-duration-ms` header as a concrete overhead metric, Go-specific bottleneck mechanics as an open gap) — this pass extends that with the traffic-shape and capacity-planning-metrics angle specifically, and should be read alongside it rather than as a duplicate.

## Summary

The validated, unanimous pattern across every LLM-gateway vendor and every purpose-built LLM load-testing tool surveyed is to load-test against a mock/stub upstream, never a real provider — LiteLLM's own official benchmark docs and its `BerriAI/Automated_Perf_Tests` repo (Locust + FastAPI, no k6/Gatling/vegeta) are the clearest concrete precedent, and this exactly matches what `TESTING.md` §7 already commits Kelvran to. For realistic bursty arrival-shape generation specifically, three actively-maintained, purpose-built tools — `inference-perf` (kubernetes-sigs, 240 stars), `llm-perf` (iopsystems), and NVIDIA's `AIPerf` (ai-dynamo, 661 stars) — have first-class, code-verified Poisson (and in AIPerf's case, gamma-distributed/burstiness-tunable) arrival-process generation plus built-in LLM-specific metrics (TTFT, TPOT, ITL, goodput, context-length-bucketed percentiles) out of the box, meaning Kelvran does not need to build a bespoke arrival-shape harness from scratch — it can adopt or crib from one of these rather than reinvent Poisson sampling. `ray-project/llmperf`, the older and better-known name in this space, is archived (Dec 2025) and has zero arrival-rate modeling of any kind — a dead end to avoid. Cache-hit-skewed traffic (a small share of prompts accounting for most repeat hits, a large one-time-only tail) is a well-established, decades-old phenomenon in the adjacent CDN-caching literature (JEDI, TRAGEN), which supports building a simple Zipfian-weighted synthetic prompt-repeat generator for Kelvran's cache load tests now, without needing a full academic trace-synthesis tool or a real production trace to calibrate against.

## Findings

### Finding 1 — Mock/stub upstream, not a real provider, is the unanimous, validated industry pattern for LLM-gateway load testing — directly confirming Kelvran's own already-documented TESTING.md policy (confidence: high)

LiteLLM's official benchmark documentation states plainly it tests "the Gateway/Proxy against a fake OpenAI endpoint," offering both a free hosted fake endpoint and a self-hostable one (`github.com/BerriAI/example_openai_endpoint`), plus an in-process mock model that intercepts requests at the httpx transport layer — explicitly to strip out real provider cost and provider latency while keeping the gateway's own request path active. LiteLLM's separate, dedicated load-testing repo, `BerriAI/Automated_Perf_Tests`, independently confirms the tool choice: Locust scenarios orchestrated via a FastAPI server (`fastapi==0.115.0`, `locust==2.40.5`), with no k6, Gatling, or vegeta anywhere in the repo. NVIDIA's own benchmarking docs go further and explicitly recommend running *both* a generic load tester (K6/Locust, for capacity/autoscaling/resource-utilization questions) and an LLM-specific benchmarking tool (GenAI-Perf/LLMPerf, for token-level throughput/latency questions) together, since each answers a different capacity question — not a either/or choice. This directly validates `TESTING.md` §7's existing "mocked upstream only" policy and its k6/vegeta tool naming; no new decision is required here, only implementation.

**build_now.** This requires no real upstream spend and no production traffic — a small deterministic mock upstream (already scoped as a prerequisite in the 2026-09-12 companion doc's Finding 1) plus either k6, vegeta, or Locust against it is buildable today. One nuance worth adopting alongside the tool choice: LiteLLM's docs explicitly warn that latency numbers are meaningless without disclosing the concurrency/think-time model used to generate them (see Finding 4) — Kelvran's own load-test output should document this alongside any number it publishes.

### Finding 2 — Purpose-built LLM load-testing tools (inference-perf, llm-perf, AIPerf) already have first-class Poisson/gamma arrival-process modeling and LLM-specific long-tail latency metrics built in — Kelvran does not need a custom harness for traffic-shape generation (confidence: high)

Three independently-verified, currently-maintained tools solve this directly, none requiring bespoke development:

- **`inference-perf`** (kubernetes-sigs org, 240 stars, pushed today as of this research date) ships `Constant rate, Poisson arrival, and concurrent user simulation` as named load patterns, backed by a real `PoissonLoadTimer` class that draws per-second request counts from `numpy`'s Poisson distribution (not just a README claim — confirmed in source). It also natively reports TTFT, TPOT, ITL, Normalized TPOT, token throughput, and **goodput** (rate of requests meeting SLO constraints) as first-class outputs, backed by dedicated test files (`test_calculate_goodput_metrics.py`) rather than requiring a custom harness to derive these from raw percentiles.
- **`llm-perf`** (iopsystems) offers a named `arrival_distribution = poisson` config knob (vs. `uniform`) applicable in QPS mode, and separately reports TTFT via SSE streaming, TPOT, and ITL with context-length-aware percentile buckets across five tiers (0-200, 200-500, 500-2K, 2K-8K, 8K+ tokens) — directly relevant to the "long-tail latency from streaming, small number of very expensive requests" shape called out in the research question.
- **NVIDIA's `AIPerf`** (ai-dynamo org, 661 stars, actively released monthly) exposes a `--arrival-pattern` flag with three modes — `constant`, `poisson` (default), and `gamma` (paired with `--arrival-smoothness`, where <1.0 = bursty, 1.0 = Poisson, >1.0 = smooth) — explicitly compatible with vLLM's own `--burstiness` parameter for cross-tool comparability, and reports avg/min/max/p50/p90/p99/std for every timing metric (TTFT, inter-token latency, request latency) as a standard output table, not an afterthought.

Notably, no surviving evidence confirms `vegeta` itself (the tool `TESTING.md` names as a Go-side option) has any Poisson/arrival-process modeling built in — the research found this capability only in these three LLM-specific tools, not in generic HTTP load testers. This is a real, unresolved gap worth checking directly against vegeta's own docs (see Open Questions) before assuming it can produce this traffic shape unaided.

**build_now.** Kelvran can adopt `inference-perf` or `AIPerf` directly against its mock upstream today (both speak OpenAI-compatible wire formats, matching Kelvran's own gateway surface), or crib the arrival-distribution/goodput-metric design patterns into a lightweight Go harness if a Python dependency in the load-test tier is undesirable. Either path is available now, without production traffic.

### Finding 3 — `ray-project/llmperf` is archived and has no arrival-rate modeling of any kind — a legacy name to explicitly avoid (confidence: high)

`ray-project/llmperf` — the older, more commonly-referenced name in this space — was archived by its owner on 2025-12-17 and is now read-only; it had already been inactive for over a year before archival. A full source-tree grep confirms zero references to `poisson`, `arrival`, `qps`, `rate limit`, or `traffic shape` anywhere in its codebase: its load generation is Ray-actor-based concurrency (`--num-concurrent-requests`) with configurable mean/stddev input/output token counts, but no arrival-process modeling whatsoever. No actively-maintained fork or successor exists under the same name.

**not_yet — do not adopt.** This is a dead-end tool for the traffic-shape question this research targets; Finding 2's three alternatives supersede it entirely. Flagged here only so a future search for "llmperf" doesn't waste time re-evaluating an archived project.

### Finding 4 — LiteLLM's own concrete methodology is a directly reusable template for Kelvran's load-test scorecard: a named concurrency/think-time model, published alongside a dedicated gateway-overhead metric distinct from total latency (confidence: high)

LiteLLM's official benchmark docs disclose their exact load-generation configuration: Locust, 1000 simulated users, 500-user ramp-up, `wait_time = between(0.5, 1)` (each simulated user sleeps 0.5-1s between requests) — and explicitly warn that this configuration holds roughly 130 requests in flight at any instant, so **comparing latency numbers without matching this think-time/concurrency model (or at minimum disclosing your own in-flight count) is invalid**. Separately, LiteLLM instruments and publishes a dedicated `LiteLLM Overhead Duration (ms)` benchmark stat, surfaced live in production via the `x-litellm-overhead-duration-ms` response header — a genuine, standing, general-purpose header (independently confirmed on LiteLLM's separate response-headers reference page, not just the benchmark page), isolating proxy-added latency from total end-to-end/upstream latency. This directly extends the 2026-09-12 companion doc's Finding 4 (which already surfaced the header and its 12/29/43ms → 2/8/13ms overhead numbers) with the concurrency-model disclosure requirement as an additional, separate methodology lesson.

**build_now.** Two concrete, low-cost artifacts to add to Kelvran's own load-test harness today: (1) a documented concurrency/think-time model (e.g., "N simulated agents, each issuing a request every X-Y seconds" or "N requests held in flight") published alongside every latency number Kelvran reports, so future comparisons are apples-to-apples; (2) a dedicated `x-kelvran-overhead-duration-ms`-style response header (or equivalent internal metric) isolating gateway-added latency from total request latency, mirroring LiteLLM's pattern and reusing the mock-upstream harness from Finding 1 to compute `total_latency − direct_to_mock_latency`.

### Finding 5 — Cache-hit-skewed repeat traffic (a small share of objects dominating hits, a large one-time-only tail) is a well-established, decades-old phenomenon in the adjacent CDN-caching literature — supporting a cheap, buildable-now Zipfian synthetic generator for Kelvran's own cache load tests, without needing a real production trace (confidence: medium — high on the underlying CDN facts, medium on direct applicability to LLM-gateway traffic specifically)

Two peer-reviewed CDN-caching papers (Akamai-affiliated, IMC 2021/2022) independently document and quantitatively measure this exact traffic shape in real production traces: a small number of very popular objects account for a disproportionate share of requests (up to 15% of requests from "a few" objects in one traffic class), while a large fraction of objects — 55% in one measured trace — are accessed only once ("one-hit-wonders"), with the degree of skew varying by traffic class. Purpose-built statistical trace generators (TRAGEN's "footprint descriptor" / "byte-weighted footprint descriptor" model, later extended by JEDI) can synthesize traffic matching a target cache-hit-rate profile, and can compose multiple traffic classes at a target mix (e.g., "10 Gbps of video traffic mixed with 5 Gbps of download traffic"), all without transporting a sensitive real production trace. This is CDN-domain evidence, not LLM-gateway-specific evidence — its applicability to Kelvran's semantic cache is a reasonable analogy (the researcher's framing), not a verified transfer. Two related, more specific claims (that these tools reproduce hit-rate curves with near-perfect numeric fidelity, and that this validates synthetic traffic generally for cache-hit-skewed *load testing* as a category) were checked adversarially and did **not** survive verification — treat those two specific extensions as unconfirmed.

**build_now for a simplified version; not_yet for a full footprint-descriptor-based tool.** A lightweight Zipfian-weighted (or similarly power-law-weighted) synthetic prompt-repeat generator — parameterized by target cache hit-rate and one-hit-wonder fraction, not by a real trace — is cheap to build today and gives Kelvran's cache load tests a non-uniform, cache-hit-skewed access pattern instead of either fully-uniform or fully-repeated synthetic traffic. Adopting a full academic trace-synthesis tool (TRAGEN/JEDI-style footprint descriptors) is explicitly `not_yet`: it is real "boil the ocean" scope for a capability a simple Zipfian generator already covers adequately, and the trigger for revisiting it would be a real production trace to calibrate a footprint-descriptor model against — which does not exist yet.

### Finding 6 — A purpose-built, provider-accurate rate-limit mock exists (`mocklimit`) that could stand in as Kelvran's mock upstream specifically for testing 429/backoff behavior under simulated throttling — a real option, but unproven by independent adoption (confidence: medium — single primary source, 0-star/no-adoption project, one vote against in adversarial review)

`mocklimit` implements three real rate-limiting algorithms (fixed window, sliding window, token bucket — confirmed as actual source files, not just doc claims) and produces 429 error bodies matching the real, distinct shapes OpenAI, Anthropic, and Google actually return (confirmed against the tool's own `error_templates.py` source). This is directly relevant to load-testing Kelvran's own `gateway/internal/ratelimit` and fallback-chain behavior under a simulated partially-throttled upstream, rather than only a happy-path mock. However, it has zero stars and no independent adoption found, and a related, more specific claim (that it supports fully in-process ASGI-test-client use for a zero-cost CI smoke test) was checked and refuted (0-3) — so its integration ergonomics for a CI-integrated tier are unconfirmed.

**build_now, but scoped narrowly.** Worth a cheap spike to see if it (or a much smaller hand-rolled equivalent returning the same three providers' real 429 shapes) fits as one mode of Kelvran's mock upstream — specifically to load-test the fallback/backoff paths under simulated rate-limit pressure — but treat it as an unproven, single-source option to evaluate hands-on before committing to it as a dependency, not as a settled recommendation.

## Load-Test Scorecard — a concrete shape to define now (synthesizing Findings 1-5)

Even without real production traffic to calibrate numeric targets against, the surviving research supports defining the *shape* of a scorecard now:

- **Gateway-added overhead** (not total latency): p50/p95/p99, isolated via `total_latency − direct_to_mock_latency` (Finding 1/4), reported through a dedicated header/metric analogous to `x-litellm-overhead-duration-ms`.
- **Disclosed concurrency/think-time model** alongside every number (Finding 4) — without this, Kelvran's own numbers are as incomparable across runs as the cross-vendor numbers this research found unreliable.
- **Streaming-specific metrics**: TTFT, inter-token latency (ITL/TPOT), not just end-to-end latency (Finding 2) — directly matches the research question's "long-tail latency from streaming" traffic-shape characteristic.
- **Goodput** (requests meeting an SLO, not just raw throughput) as a first-class metric (Finding 2) — more informative under Kelvran's own WRR fallback-chain and rate-limiter architecture than raw RPS alone, since a request that succeeds only after multiple fallback hops may still miss a latency SLO even though it "succeeded."
- **Cache-hit-rate as a load parameter, not just an output**: run the same load profile at multiple target hit-rates (via the Finding-5 Zipfian generator) to see how effective capacity changes as hit-rate varies — this is the one metric in this scorecard genuinely specific to Kelvran's own semantic-cache architecture rather than generic to any LLM gateway.
- **Rate-limiter/Redis round-trip overhead in distributed mode**, isolated the same way as gateway overhead (in-memory vs. Redis-backed `KeyLimiter` runs, same load profile, difference = Redis round-trip cost) — not directly sourced from a surviving claim this pass, but a direct, low-cost extension of Finding 1/4's isolation technique to Kelvran's own already-shipped Redis-backed rate limiter.

## Caveats

- This pass found no surviving claim directly addressing research question 4 (a CI-integrated, cheap, no-real-upstream-cost smoke-level load tier as a permanent regression guard for the WRR-race-bug class). `TESTING.md` §7 already commits to "tiny smoke-only load test on PR," but whether/how that should specifically target the WRR fallback race this week's manual dry run found is a Kelvran-specific implementation decision this research does not answer — treat it as open (see Open Questions).
- Whether `vegeta` itself (named as an option in `TESTING.md`) has any first-class Poisson/burst-arrival support was not confirmed either way in this pass — the surviving evidence only confirms three *other*, LLM-specific tools have this. Verify vegeta's own docs directly before assuming parity or gap.
- One refuted claim is worth flagging explicitly: a claim that `BerriAI/Automated_Perf_Tests` is configured to hit a real, live upstream host (implying LiteLLM's own practice diverges from the mock-upstream pattern) was checked and refuted (0-3) — but this only means that specific "real host" framing is unsupported, not that the repo is proven to be mock-only either. Net position: LiteLLM's *documented benchmark methodology* (Finding 1) is confirmed mock-based; the separate `Automated_Perf_Tests` repo's exact upstream target in practice remains ambiguous.
- Several DVARA "mock provider" claims (a built-in `mock/` model prefix with configurable per-call/per-token latency knobs) were checked and refuted (1-2 and 0-3) — do not treat DVARA as a validated reference for configurable synthetic latency injection; if Kelvran wants that capability, it needs its own design, not a borrowed one.
- GenAI-Perf-specific claims (a hard load-testing-vs-performance-testing line, and OpenAI-compatible-endpoint support via `--service-kind openai`) were both refuted (0-3 and 1-2 respectively) — do not cite GenAI-Perf capabilities from this research pass without re-verifying directly against its current docs.
- The CDN-caching evidence (Finding 5) is strong on its own terms (peer-reviewed, primary-source-verified) but is a cross-domain analogy applied to LLM-gateway cache traffic, not direct evidence about LLM traffic itself — treat the "build a Zipfian generator" recommendation as a reasonable inference, not an industry-standard practice for LLM gateways specifically.
- Time-sensitivity: `inference-perf` and `AIPerf` are both actively released (pushed/released within days of this research date) — their exact CLI flag names/defaults should be re-checked against current docs before implementation, not copied verbatim from this snapshot.
