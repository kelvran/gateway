# Continuous Evaluation / Production-Traffic-Sampling Patterns for Evals v2

**Date:** 2026-09-11
**Status:** Research synthesis (23 claims, 3-vote adversarial verification)
**Scope:** How Braintrust, Langfuse, Arize AX, and W&B Weave wire live production traffic into continuous quality monitoring + alerting in 2026, and whether that maps onto Kelvran evals' existing `ingest` / `promote` / `flag-candidates` / `TrendSnapshot` primitives.

## Executive Summary

Mature eval platforms split roughly in two: Langfuse and Weave run **event-driven, per-trace LLM-as-a-judge scoring** (async queues/serverless inference triggered on ingestion, with sampling-rate as the cost lever), while Arize AX runs **explicit scheduled/batch monitors** (default hourly for production monitors, default every 6h for its "Signal" agent, configurable from minutes to months) — both are legitimate, currently-shipping 2026 production patterns, not one superseding the other. Critically, **none** of the four platforms use statistical/DDM-style drift detection for alerting; all four use simple, tunable numeric thresholds (static, or "automatic" thresholds derived from historical data) evaluated over a rolling window, wired to a notification channel (Slack/webhook) — the human is always the one who acts. Classical DDM-family drift detectors structurally require an immediately-available ground-truth correctness label per example, which is a different kind of field than the operational metadata (`occurred_at`, `fallback_happened`, `budget_spent_usd`) `mapping.py` now persists — so the DDM deferral trigger is **not** satisfied by this session's change; unsupervised/semi-supervised variants exist precisely to route around this constraint by substituting predicted labels for true ones, not by accumulating more metadata. Kelvran's own batch shape (`ingest` from S3/GCS → `promote`/`flag-candidates` on a schedule + nightly CI) already matches Arize's validated production pattern, and the human-gated promote/flag-candidates split mirrors what every platform researched actually does at the point of action (notify a human, don't auto-act) — so no genuinely new "always-on" component is required for v2's continuous-eval story; the concrete gap is a threshold+window+severity alerting layer on top of the existing `TrendSnapshot` series.

## Confirmed Findings

### Finding 1 — Production continuous-monitoring architecture: event-driven queues AND scheduled batch are both mature 2026 patterns; Kelvran's batch shape is not a stopgap
**Confidence: high** (multiple primary sources per platform, unanimous votes; corroborated by public source code for Langfuse)

- Langfuse's online/production evaluation is **event-driven, not periodic batch**: a "rule" (filters + sampling rate + evaluator) scores new observations as they arrive; a separate, explicitly manual "batch evaluation" mode exists only for re-scoring selected historical data. Verified against docs and Langfuse's own public repo, which shows a real BullMQ/Redis `EvalExecutionQueue` enqueued from trace-upsert ingestion events (`worker/src/features/evaluation/evalService.ts::createEvalJobs()`) — genuine queue/event-driven architecture, not a cron scan. [Langfuse docs: /docs/evaluation/get-started/online, /docs/scores/model-based-evals]
- Sampling rate is a first-class, explicit cost-control lever on Langfuse rules ("evaluate a percentage of traces... choosing cost-effective judge models"), with UI guidance to review 7-day matching volume and estimated cost before activating. [Langfuse docs]
- Langfuse explicitly frames "Observations" (continuous production scoring) as the recommended target for live-traffic monitoring, versus "Experiments" (one-off dataset evaluation) for pre-deployment dev work. [Langfuse docs]
- Weave's built-in "signals" **automatically score every incoming production trace** as it arrives via serverless-inference LLM-as-a-judge binary classification (hallucination, low-quality, jailbreak, etc.) — an event-triggered-per-trace model, not a scheduled batch pull. Custom monitors (beyond the presets) use the same LLM-judge-passive-scoring mechanism. A self-hosted-only `WEAVE_INGEST_SAMPLE_RATE` knob is an opt-in cost dial, not evidence of a default batch pipeline. [weave-docs.wandb.ai/guides/evaluation/guardrails_and_monitors]
- Arize AX's "Signal" feature and its general production monitors are **scheduled batch workers**: Signal defaults to running every 6 hours (configurable 3 hours to monthly); production monitors default to hourly (configurable to 5/10/15/30-minute intervals or longer). The docs' "Continuously monitor" language is marketing framing for background coverage, not a technical claim of a real-time streaming daemon — the actual mechanism is schedule/poll-based re-evaluation of a rolling window. [arize.com/docs/ax/observe/signal, /observe/production-monitoring]
- Braintrust's dashboards are a **pull/re-aggregation model**: they aggregate metrics (counts, latency, tokens, cost, scores, topics, custom metrics — multiple independent series, not a fused composite) across logs/experiments; live refresh is an opt-in toggle, otherwise a manual refresh button reloads charts. No streaming/websocket infrastructure is documented for this surface. [braintrust.dev/docs/guides/monitor]

**Implication for Kelvran:** Kelvran's `ingest` (S3/GCS batch decode) → `flag-candidates`/`auto_flag.py` (rule-based candidate surfacing) → nightly CI judge-accuracy run → human-gated `promote` shape is architecturally the same family as Arize AX's scheduled-monitor pattern — the most directly analogous of the four platforms, since Arize is also polling accumulated event data on a cadence rather than scoring a live request stream inline. Langfuse/Weave's event-driven per-trace judge-scoring is a different, complementary pattern (continuous *quality scoring* of traffic as it lands) that Kelvran has not built and does not need in order to claim a legitimate "continuous eval" story — both patterns coexist in the market in 2026.

**build_now / not_yet:** `not_yet` for an event-driven per-trace scoring daemon. Trigger to revisit: only if Kelvran needs sub-hour-latency quality signal on individual live requests (e.g., a synchronous judge call gating a response) rather than trend-level drift/regression visibility — no such requirement exists in the current spec.

### Finding 2 — DDM's deferral trigger is NOT satisfied by mapping.py persisting occurred_at/fallback_happened/budget_spent_usd
**Confidence: high** (peer-reviewed primary sources: the canonical concept-drift survey plus three DDM-lineage papers, unanimous votes)

- DDM-family statistical/SPC drift detectors work by comparing each prediction to its **true label** and monitoring the resulting error rate's confidence interval — this requires a ground-truth correctness label available immediately after each example, not just contextual/operational metadata about the example. [Gama et al., ACM Computing Surveys 46(4), 2014, DOI 10.1145/2523813]
- The same survey draws a hard line between **real concept drift** (change in p(y|X) — the decision boundary itself, which needs adaptation and requires labeled feedback to detect) and **virtual drift** (change in p(X) alone — detectable from input data without labels, and explicitly out of scope for feedback-dependent detectors like DDM). [same source]
- This immediate-ground-truth requirement is independently confirmed as "unrealistic in several practical problems" by a 2020 survey of unsupervised drift detection, and by a 2017 IEICE paper naming DDM specifically as relying on the assumption "that class labels become available immediately after a data sample arrives." [DOI 10.1002/widm.1381; DOI 10.1587/transinf.2017EDP7091]
- Because of this, a distinct research line (unsupervised/semi-supervised drift detection) exists specifically to avoid the label dependency — but it does so by **substituting predicted labels from a classifier, or a "virtual classifier," for true labels**, not by relying on richer input/operational metadata. It still requires *some* labeling mechanism (even a synthetic one), just not continuous ground truth. [DOI 10.1587/transinf.2017EDP7091]

**Implication for Kelvran:** `occurred_at`, `fallback_happened`, and `budget_spent_usd` are timestamp/operational-outcome fields — useful for windowing and for the existing `gateway-failure-outcome` auto-flag rule — but none of them is a quality-correctness ground-truth label ("was this response good/correct?"). DDM needs the latter, immediately, per example. Persisting these fields does not close DDM's deferral gap.

**build_now / not_yet:** `not_yet`. Exact trigger: either (a) a synchronous/near-synchronous automated-judge call producing a per-request correctness proxy label at ingestion time (analogous to the "virtual classifier" substitution in the literature), which would make an unsupervised/semi-supervised drift detector viable — not classical DDM; or (b) the human-gated `promote` pipeline accumulating a labeled (judge-scored) corpus large enough for a supervised detector to be statistically meaningful. (Note: a specific "~30 labeled observations" minimum-sample claim was checked and refuted — do not cite a precise threshold number; the literature only supports "needs enough labeled points for the binomial CI math to be meaningful," not a fixed constant.)

### Finding 3 — Alerting-threshold methodology across all four platforms is simple/tunable thresholds, not statistical drift detection, and maps directly onto TrendSnapshot
**Confidence: high** (primary vendor docs for all four platforms, unanimous votes)

- **Braintrust:** alerts fire when a SQL-computed scalar over a time window crosses a fixed numeric bound (e.g. `{type: threshold, operator: gt, threshold: 100}`); docs explicitly tell users to build their own external system if they want spike/anomaly detection — Braintrust doesn't ship that. [braintrust.dev/docs/observe/alerts]
- **Weave:** automations = Event (a monitor/scorer metric) + Metric Threshold (comparator + value) + Window + Aggregation (mean/median/min) → Action (Slack/webhook). Even Weave's "regression detection" use case runs through this same threshold+window+aggregation primitive — no ADWIN/DDM/PSI/KS-test language anywhere in the docs. [weave-docs.wandb.ai/guides/evaluation/guardrails_and_monitors, /automations]
- **Langfuse:** alerts are a recurring scheduled evaluation (schedules its first evaluation on save, re-evaluates over a configurable lookback window like "1 hour / 1 day / 1 week") with a two-tier static-threshold severity model: a required ALERT threshold and an optional WARNING threshold crossed before it. No percentage-change or baseline-relative logic. [langfuse.com/docs/metrics/features/alerts]
- **Arize AX:** two threshold methods — "Automatic" (Arize computes a threshold from historical data, with an adjustable sensitivity dial) and "Static" (user sets an exact number, e.g. "alert if accuracy drops below 85%"). The "Automatic" mode is the closest any platform gets to a statistically-informed baseline, but it is still a threshold-crossing alert, not a DDM/CUSUM-style sequential detector. [arize.com/docs/ax/observe/production-monitoring]

**Implication for Kelvran:** This is the most directly actionable finding. Kelvran already persists exactly the kind of independently-trended series (judge-accuracy-kappa, quote-grounding-rate, audit-corpus-defect-rate, judge-panel-tie-rate, cost) that every platform above turns into an alert. The missing piece is not a new detection algorithm — it's a threshold + window + severity-tier object per series, wired to a notification channel, mirroring Langfuse's two-tier WARNING/ALERT model or Arize's static-vs-automatic-threshold choice. None of the platforms researched fuse these into one composite/health score for alerting purposes either — confirming Kelvran's "5 independently-trended series, never fused" design is consistent with the field, not a gap.

**build_now / not_yet:** `build_now`. Exact trigger: already satisfied — `TrendSnapshot` persistence for all 5 series exists today; adding a per-series threshold (static or simple rolling-baseline "automatic") + window + WARNING/ALERT severity + notification hook is buildable immediately without any new data pipeline, mirroring the mechanism (not the vendor) of Langfuse/Weave/Arize/Braintrust.

### Finding 4 — Human-gated promote/flag-candidates is consistent with, not behind, mature-platform practice (lower confidence — synthesis, not a directly sourced claim)
**Confidence: medium** (inferred from Findings 1 and 3 rather than a single directly-verified claim; no claim in the vote set directly addresses auto-promotion vs human-gating)

Every alerting mechanism surfaced above terminates in a **notification to a human** (Slack, webhook, dashboard) — none of the four platforms auto-promotes a flagged trace into a training/eval corpus, auto-adjusts a model, or auto-rolls back a deployment purely from a quality-metric threshold crossing. The "action" in every documented mechanism is "tell a person," which is exactly Kelvran's existing shape: `auto_flag.py`/`flag-candidates` surfaces candidates automatically (the "notify" step), and `promote` requires a human to join a Run+Score back to its source EvalCase (the "act" step). No evidence surfaced in this research that continuous-eval maturity at scale requires collapsing that human gate.

**build_now / not_yet:** `not_yet` / no architectural change needed. Exact trigger to revisit: not a maturity-of-methodology trigger but a *volume* trigger — if/when the rate of auto-flagged candidates exceeds what a human can triage, the next increment (if any) would be auto-triage assistance/prioritization of the flag queue, not auto-promotion itself.

## Refuted Claims (excluded from findings above)
- "Braintrust's alerting is built directly on top of a batch-style scheduled evaluation over recent production log data (via `project_logs()` queries)" — rejected 1-2 on verification; do not assert a specific polling mechanism for Braintrust alerts, only that they are threshold-based (Finding 3) and that the dashboard surface is pull/manual-refresh by default (Finding 1).
- "SPC/DDM-style detectors only become statistically meaningful once at least ~30 labeled observations have accumulated" — rejected 1-2; do not cite a specific minimum-sample-size number for DDM viability (Finding 2).

## Caveats
- Corroboration relied heavily on each vendor's own current documentation (appropriately primary for "how does vendor X's shipped feature work," but not independently audited against their production source code except for Langfuse, where public-repo code was cross-checked).
- Search tooling (Exa/Tavily) was rate-limited during parts of verification; several findings rest on a single, if authoritative and directly-quoted, primary source rather than triangulated third-party corroboration. This is flagged per-claim above but does not change any finding's direction.
- All vendor docs were fetched live on 2026-09-11 (today); vendor UI/feature details can change without notice, so treat specific numeric defaults (e.g., Arize's "every 6 hours," "hourly") as current-as-of-today rather than permanent.
- The concept-drift/DDM literature (Finding 2) is foundational and date-stable (2014-2020 sources describing 2004-era DDM mechanics that are unchanged), so its age does not weaken it — but it does not by itself establish 2026 state-of-the-art for *unsupervised* drift detection; only that DDM specifically remains label-dependent.

2. What is Kelvran's actual current alert/notification channel (if any) for TrendSnapshot regressions today — is Finding 3's "build_now" threshold layer starting from zero, or is there partial plumbing (e.g., the nightly CI workflow failing a build) that already serves as a crude static-threshold alert?
3. Would an "automatic" (historical-baseline-derived) threshold per TrendSnapshot series, à la Arize, actually behave sensibly given Kelvran's judge-accuracy-kappa and cost series' known volatility/seasonality, or does it need a minimum-history warm-up period before being trustworthy?
4. If Kelvran later wants Langfuse/Weave-style live per-request judge scoring (Finding 1's "not_yet" item), what's the expected production request volume, and does the gateway have a place to hang an async scoring hook without adding latency to the response path?
