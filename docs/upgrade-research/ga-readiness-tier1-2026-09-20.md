# GA-Readiness / Tier-1 Enterprise Trust Posture — Research Report

**Date:** 2026-09-20
**Scope:** What genuine GA-readiness / tier-1 enterprise trust posture requires for an LLM gateway beyond pilot stage, specifically: SLA commitments, incident-response/on-call maturity, a public status page, versioned API stability + deprecation guarantees, and support tiering. Checked directly against Kelvran's live repo state (not assumed from prior research docs), and against primary-source documentation from OpenAI, Anthropic, Cloudflare AI Gateway, Kong, and Portkey.
**Method:** Direct inspection of Kelvran's live files (`SUPPORT.md`, `SECURITY.md`, `UPGRADE.md`, `gateway/cmd/gateway/main.go`, `gateway/internal/admin/admin.go`, `docs/operations/grafana/alertmanager/alertmanager.yml`, `git log`) — not a re-read of a prior research doc's claims. External claims are grounded in primary sources fetched directly this round: `status.openai.com`, `developers.openai.com/api/docs/deprecations`, `status.claude.com`, `status.portkey.ai`, `konghq.com/pricing`, `www.cloudflarestatus.com`, `developers.cloudflare.com/ai-gateway/`.

---

## Executive Summary

Kelvran today is honestly self-described as pre-GA and has zero tier-1 trust-posture mechanisms live: `SUPPORT.md` states "Best-effort, no SLA, at the current solo-maintainer stage," no status page of any kind exists, the gateway's HTTP API has shipped a second `v1` endpoint (`/v1/embeddings`, added since the prior versioning report) without ever adding a deprecation mechanism, and the on-call/alerting path terminates in a `placeholder-webhook` that the alertmanager config itself documents as fake ("no real Slack/PagerDuty/Opsgenie credential exists for this pilot yet"). This is not a gap unique to Kelvran — this round's live re-check of `docs/upgrade-research/api-versioning-deprecation-policy-2026-09-15.md`'s recommendations confirms **none were operationalized in the 5 days since that report was written**: the route table, `UPGRADE.md`, and RFC corpus are unchanged on every claim that report made. What *is* new since 2026-09-15 is a live, unflagged contradiction between two of Kelvran's own docs: `SECURITY.md` was edited to declare its acknowledgement/resolution targets "real and contractual" now that `gateway/v0.1.0` shipped, while `SUPPORT.md` — untouched since the initial scaffolding commit — still says those same targets are "explicitly marked aspirational until the project's first real release." One of these two statements is now stale, and this is exactly the doc-vs-code (here, doc-vs-doc) staleness class `AGENTS.md`'s own Gotchas section already tracks.

On the external-precedent side, five real vendors show five different maturity postures, not one uniform bar: OpenAI publishes a precise, tiered deprecation-notice policy (6 months GA / 3 months specialized / 2 weeks preview) but its status page reports historical uptime percentages rather than a forward-looking contractual SLA; Anthropic's status page is a stock Atlassian Statuspage instance with no published numeric SLA visible on the page itself; Cloudflare has no AI-Gateway-specific SLA or status component at all — AI Gateway inherits whatever general Cloudflare terms apply, undifferentiated; Kong is the only one of the five with a fully worked support-tiering-to-SLA mapping (named tiers, each with an explicit response-time number, plus a separate 99.9%-per-month platform SLA); and Portkey — the closest peer to Kelvran in shape and stage — has a real status page (on BetterStack, not a bespoke build) but no formal contractual SLA document, just a marketing-stated uptime statistic. The practical implication for Kelvran: a public status page and a written deprecation policy are both cheap, precedented, and buildable well before any tenant volume argues for them; a numeric, credit-backed SLA and true 24x7 on-call are the two items every source treats as gated on having a real paying customer base and a team larger than one, and none of the five vendors examined extend either to their free/self-serve tier.

## Findings

### Finding 1 — None of the prior versioning-policy report's recommendations were operationalized in the 5 days since it was written; the gap it identified is unchanged and one new instance of it has shipped
**Classification: not_yet (mechanism), build_now (the cheap parts, per Finding 2 below)** · **Confidence: high** (direct code re-inspection, not inherited from the prior report)

Re-checking `docs/upgrade-research/api-versioning-deprecation-policy-2026-09-15.md` (dated 2026-09-15) directly against the live repo, 5 days later:

- **The data-plane route table now has *two* `v1` endpoints, not one, and neither carries any real version negotiation.** `gateway/cmd/gateway/main.go:396-398` registers `mux.HandleFunc("/v1/chat/completions", ...)`, `mux.HandleFunc("/v1/embeddings", ...)` (new since the prior report — added in commit `766b4fb4`, "feat(gateway): add an embeddings endpoint for OpenAI and Bedrock Titan"), and `/healthz`. The new endpoint reuses the same unversioned `v1` path literal the prior report flagged as "not a real version" — confirming the pattern is now load-bearing across two routes instead of one, making a future migration to real versioning strictly harder than when the report was written.
- **`UPGRADE.md` is still exactly the empty table** the prior report described: `| Version | Breaking Change | Migration Steps |` with a single `| — | — | — |` row. No breaking-change definition or safe-change allowlist (Finding 3 of the prior report) has been added to it, `AGENTS.md`'s Conventions section, or any `docs/decisions/` entry — `ls docs/decisions/` still shows only the same 3 ADRs (`0001-monorepo-two-deployables.md`, `0002-cache-embedded-in-gateway.md`, `0003-go-python-split.md`) as before.
- **No `Deprecation`/`Sunset` response header, no `Stripe-Version`-style request header, and no `/v2/` path exist anywhere.** A direct grep for `Stripe-Version|API-Version|Deprecation:|Sunset:|/v2/` across `gateway/internal`, `gateway/cmd`, `api/`, and `docs/rfcs` returns exactly one hit, and it's not Kelvran's own HTTP contract — it's a *different* RFC (`docs/rfcs/2026-09-07-evals-trace-ingestion-object-storage.md:35`) describing the **already-existing** `api/gatewayevents/v1/` → `v2/` directory-versioning convention for the internal proto contract, the same internal/external asymmetry Finding 6 of the prior report already named.
- Admin routes grew substantially in the same window (`POST /admin/backup`, `POST /admin/deployments/{name}/weight`, `POST /admin/cache/erase`, per `gateway/internal/admin/admin.go:206-213` — all added since 2026-09-15) — every one of them unversioned, same as before, widening the surface the prior report's Finding 6 already flagged as ungoverned relative to the proto contract.

**Recommendation:** Unchanged from the prior report — this is not a new problem, but it is measurably a slightly worse one (two live `v1` routes now instead of one, plus three more unversioned admin routes) precisely because nothing was done about it. Treat Finding 3 of the prior report (the written breaking-change definition + allowlist, costing zero code) as the one item that should not still be missing at the *next* 5-day check-in.

### Finding 2 — A public status page is cheap, low-risk, and has a real precedent even for a single-tenant/near-zero-traffic project — Portkey and Kong both run theirs on third-party platforms, not custom infrastructure
**Classification: build_now** · **Confidence: high**

None of the three status pages fetched this round for peer/incumbent comparison are custom-built infrastructure:

- **OpenAI's status page** (`status.openai.com`) runs on **incident.io** — confirmed by the page's own "Powered by" footer credit — and tracks 12 API components, 15 ChatGPT components, and separate Codex/FedRAMP/Ads groupings, each with a reported historical uptime percentage (e.g. "99.93% uptime" for a Jun–Sep 2026 window) rather than a forward SLA number. The page states explicitly that these percentages are "reported at an aggregate level across all tiers, models and error types" and that "individual results may vary depending on their subscription tier" — i.e., the public number is a retrospective transparency signal, not the contractual SLA text itself.
- **Anthropic's Claude status page** (`status.claude.com`, redirected from the legacy `status.anthropic.com`) runs on **Atlassian Statuspage** — confirmed by the "Powered by Atlassian Statuspage" footer — tracking six components (`claude.ai`, Claude Console, Claude API, Claude Code, Claude Cowork, Claude for Government), with a real incident timeline (Investigating → Identified → Monitoring → Resolved) going back at least to 2026-09-05, and multi-channel subscription (email, SMS, Slack, Teams webhook, generic webhook, Atom/RSS). No numeric SLA percentage is shown on the page itself — it is purely an operational-transparency tool, same posture as OpenAI's.
- **Portkey's status page** (`status.portkey.ai`) — the closest peer to Kelvran in both product shape (LLM gateway) and company stage — runs on **BetterStack**, tracking two components ("Saas Control Plane" and "AI Gateway"; the fetched page's own component descriptions appear internally swapped/mislabeled between the two, a live documentation bug on Portkey's own status page, not a Kelvran finding but worth noting as evidence that even a funded competitor's status-page hygiene isn't perfect), showing "100% uptime" over the visible window with two real incident entries in August 2026 (a 40-minute JWKS-URL-inaccessible event and a ~2-hour control-plane-slowness event), and the same multi-channel subscription options (email, RSS/Atom, JSON feed, webhook, Slack).

Cloudflare is the one negative data point among the five: `www.cloudflarestatus.com` has **no AI-Gateway-specific component at all** — it tracks general Cloudflare products/locations (WARP, Workers KV, Durable Objects, Hyperdrive, per-datacenter network health) with no numeric uptime shown anywhere on the page, only incident/maintenance timelines. AI Gateway inherits Cloudflare's general platform status, undifferentiated — confirmed by `developers.cloudflare.com/ai-gateway/`'s own docs, which contain zero mention of an SLA, uptime guarantee, or dedicated status component for AI Gateway specifically.

**Applied to Kelvran:** the pattern across every real status page examined is a hosted third-party product (incident.io, Atlassian Statuspage, BetterStack), not custom-built monitoring infrastructure — meaning the cost of adopting one is integration time, not engineering a new system. Kelvran already has the one prerequisite a status page needs to be non-fake — real uptime/error telemetry via the `grafana/otel-lgtm` stack (`gateway/internal/telemetry/telemetry.go`) — so a status page here would not be inventing data, only publishing a summary of data that already exists. This is the single cheapest, most purely-additive item in this report: it requires no change to Kelvran's actual reliability, only a decision to make existing internal signal externally visible.

**Recommendation:** Adopt a hosted status-page product (BetterStack's free tier is the closest-precedent, lowest-cost option given Portkey's own choice) once there is a second real consumer of the gateway besides Kelvran's own pilot traffic — publishing a status page with zero historical incidents and zero subscribers is honest but has negative signaling value before that point. This is a **build-now-the-mechanism, publish-later-in-practice** item, not a fully deferred one.

### Finding 3 — A numeric, credit-backed SLA is the one item every source examined gates on real paying-customer volume and contractual relationship — none of the five vendors extend one to a free/self-serve tier
**Classification: not_yet** · **Confidence: high**

- **Kong** is the most structured of the five: its pricing page (`konghq.com/pricing`) names three support tiers with explicit response-time SLAs — **Diamond** (24×7, 30-minute SLA), **Platinum** (24×7, 1-hour SLA), and **Business** (regional business hours, 2-hour SLA) — plus a **Trial/Plus** tier at "2 business days" email-only support, and a separate **99.9%-per-calendar-month** platform availability target for Kong Konnect specifically, referenced via a linked "Support and Maintenance Policy" document. Every one of these SLA numbers is tied to a paid tier; the entry-level tier gets a multi-day response window, not a percentage guarantee at all.
- **Portkey** publishes a marketing uptime statistic — "over 25M requests daily with a 99.99% uptime" — but its own FAQ confirms this is not backed by a contractual SLA document, credit terms, or differentiated support tiers; the only support channel named is a generic `support@portkey.ai` email, with enterprise-tier language limited to private-cloud managed hosting for security/compliance reasons, not response-time commitments.
- **OpenAI** and **Anthropic** both show retrospective uptime transparency (status-page percentages, incident timelines) but neither page surfaces a forward-looking, credit-backed SLA number publicly — OpenAI's own page explicitly caveats that individual results vary by subscription tier, implying the real SLA (if any) is a contractual term gated behind an enterprise agreement, not a page any anonymous visitor can read.
- **Cloudflare** could not be confirmed either way this round — the general Cloudflare SLA page (`cloudflare.com/service-level-agreement/`) and Kong's own detailed Support and Maintenance Policy document both returned HTTP errors (403/404) when fetched directly this round, so their exact credit/remedy language is not independently confirmed here (see Caveats) — but no source found treats AI Gateway as having its own SLA distinct from whatever general-platform terms apply.

**Applied to Kelvran:** `SECURITY.md`'s acknowledgement/resolution targets (3 business days acknowledgement, 14 days for a Critical/High fix-or-mitigation plan) are the closest thing Kelvran has to an SLA today, and they cover *security response*, not general availability/uptime — there is no uptime percentage, credit, or remedy of any kind committed anywhere in the repo. This is consistent with every source examined: a real uptime SLA is a late-stage, paid-tier, contractual artifact, not something built ahead of a real customer base. Kong's structure — tiered response-time-by-severity, separate from a platform-wide percentage target — is the clearest template to eventually copy, but doing so today, with a solo maintainer and zero paying tenants, would be exactly the "reliability theater" risk `docs/upgrade-research/slo-error-budget-observability-2026-09-15.md`'s Finding 3 already named for the adjacent SLO-target question.

**Recommendation:** Do not write a numeric SLA yet. The trigger that should end this `not_yet` classification is the same one Kong's and Portkey's own tier structures imply: a real second party paying for, or contractually depending on, Kelvran's uptime — not a calendar date or a traffic-volume threshold in isolation.

### Finding 4 — Kelvran's on-call/incident-response path is honestly labeled as fake by its own config, and this is the correct interim state, not a gap to rush past
**Classification: not_yet (real on-call), but the current placeholder is itself a build_now-quality pattern worth keeping** · **Confidence: high** (direct file inspection)

`docs/operations/grafana/alertmanager/alertmanager.yml` routes every alert to a `placeholder-webhook` receiver pointed at `http://placeholder-receiver.invalid/kelvran-alerts`, with a comment block explicitly stating: "no real Slack/PagerDuty/Opsgenie credential exists for this pilot yet, and inventing one here would be indistinguishable from a real, working integration to a future reader." The same comment explains a real design choice — it deliberately avoids Alertmanager's `null` receiver type specifically because that would "silently swallow every alert with no visible effect at all," preferring a fake-but-observable endpoint whose failed-delivery attempts are still visible in request logs.

This is a genuinely good pattern for a pre-GA project, not merely an acceptable gap: it means Kelvran's own alerting pipeline (4 real MWMB SLO alert rules already defined per `docs/upgrade-research/slo-error-budget-observability-2026-09-15.md`, evaluated by Prometheus) is exercised end-to-end today, and a future real PagerDuty/Opsgenie integration is a one-line receiver swap, not new pipeline plumbing. No comparable vendor documentation examined this round discusses this specific "honest placeholder over silent null" design choice — it's Kelvran's own judgment call, not an externally precedented practice, but it is consistent with the general principle (visible in Kong's tiered response-time SLAs and OpenAI's "immediately becomes deprecated" hard-cutover language) that every mature source treats ambiguity about operational state as worse than an explicit, even unflattering, label.

**Recommendation:** Keep the placeholder-webhook pattern exactly as-is until there's a real on-call rotation (which, for a solo maintainer, may never make sense to build as a formal "rotation" at all — a personal phone/Slack notification may be the honest end state, not a 24×7 PagerDuty tier). The `not_yet` classification here is about *true on-call coverage* (someone reachable outside normal hours with an escalation path), not about the alerting *mechanism*, which is already real.

### Finding 5 — The SUPPORT.md / SECURITY.md contradiction is a live, unflagged instance of the exact doc-staleness class `AGENTS.md` already tracks — and it directly concerns this report's own subject matter
**Classification: build_now (a one-line fix)** · **Confidence: high** (direct file + git-history inspection)

`git log --oneline -- SECURITY.md` shows five edits, the most recent chain culminating in a change that added: *"Acknowledgement / resolution targets (real and contractual as of `gateway/v0.1.0`/`evals/v0.1.0`, tagged 2026-09-03 — the 'first real release' condition below has been met): acknowledgement within 3 business days; a fix or mitigation plan communicated within 14 days for Critical/High severity."*

`git log --oneline -- SUPPORT.md` shows exactly **one** commit — `0f10464f`, "chore: initial documentation set and code scaffolding" — meaning `SUPPORT.md` has never been touched since the repo's initial scaffold. It still reads: *"Best-effort, no SLA, at the current solo-maintainer stage. `SECURITY.md`'s acknowledgement/resolution targets are the one place with numeric targets, and those are explicitly marked aspirational until the project's first real release — this document points there rather than inventing separate numbers."*

These two documents now directly contradict each other on the exact question this report was asked to investigate: `SECURITY.md` says the "first real release" condition is met and the targets are real; `SUPPORT.md`, which explicitly defers to `SECURITY.md` for the numbers, still asserts they're aspirational pending that same condition. `docs/operations/TELEMETRY.md:50` independently repeats the stale framing — "explicitly **not** an SLA (see `SECURITY.md`'s acknowledgement/resolution targets, which are similarly marked aspirational pre-release)" — so this is now a three-file inconsistency (`SUPPORT.md`, `TELEMETRY.md` both stale; `SECURITY.md` current), not a two-file one. This is precisely the failure mode `AGENTS.md`'s own Gotchas section names as having "recurred 6 times by 2026-09-04" and instructs to fix by grepping every `*.md` for the relevant keyword once a status changes — that grep was evidently not run when `SECURITY.md` was corrected.

**Recommendation:** Update `SUPPORT.md`'s "Response Time Expectations" section (and the parenthetical in `docs/operations/TELEMETRY.md:50`) to match `SECURITY.md`'s current "real and contractual" language, or — if the "real and contractual" framing itself was too strong for a project that still describes itself elsewhere as solo-maintainer/pre-GA — correct `SECURITY.md` instead and treat this report's own use of it as provisional pending that decision. Either direction is a small, purely-editorial fix; the risk is only in leaving the three files disagreeing, which is exactly the kind of untrustworthy-docs signal that undermines tier-1 trust posture on its own, independent of whether the underlying targets are actually met in practice.

### Finding 6 — "Support tiering" for a pre-GA, no-tenant gateway means having an honest single tier, not building multiple tiers prematurely
**Classification: not_yet** · **Confidence: high**

`SUPPORT.md`'s own current structure is, in fact, the right shape for this stage: a single "Getting Help" path (GitHub issues, pointing to `docs/users/USER_GUIDE.md` first), an explicit "Commercial/Enterprise Support: Not offered. Stated as a current fact, not a permanent policy" line, and no invented tiers. This matches every vendor examined in spirit if not in scale — Kong's own lowest tier (Trial/Plus) is still a real, named tier with a real (if slow) response commitment, and Portkey's is a single generic support email exactly like Kelvran's, differentiated only by a 99.99%-uptime marketing claim Kelvran doesn't yet have the traffic history to make honestly.

The one live inconsistency worth flagging (distinct from Finding 5's SUPPORT.md/SECURITY.md contradiction): `SECURITY.md`'s vulnerability-reporting channel names `security@kelvran.dev`, annotated "(to be activated once the domain is registered — see `DECISIONS.md`'s open naming action)" — meaning the primary non-GitHub security contact channel is not actually live today. A tier-1 trust posture requires every published contact channel to actually work; an unregistered domain behind a security-contact email is a small but real gap in the same spirit as the placeholder webhook (Finding 4), except this one isn't labeled with the same "no real value here yet" clarity `alertmanager.yml`'s comment gives its own placeholder.

**Recommendation:** No new support tier is needed yet — the single-tier, honestly-labeled "not offered" structure is correct for this stage and matches Portkey's own comparable posture. The concrete, cheap fix is narrower: either register the `kelvran.dev` domain and activate `security@kelvran.dev`, or update `SECURITY.md` to name the GitHub Security Advisories channel as the sole real channel until the domain exists, removing the dangling "to be activated" email as a currently-non-functional contact path.

## Synthesis: What's actually gating GA/tier-1 posture vs. what's cheap and available now

| Item | Kelvran today | Cheapest precedented next step | Classification |
|---|---|---|---|
| Written breaking-change definition + safe-change allowlist for the HTTP API | Nonexistent (Finding 1) | Add to `UPGRADE.md`/`AGENTS.md`, zero code | **build_now** |
| Public status page | Nonexistent | Hosted product (BetterStack/incident.io), publish once a 2nd real consumer exists | **build_now (mechanism), defer publish** |
| Numeric, credit-backed uptime SLA | Nonexistent | Kong's tiered-by-severity model, once real paying tenants exist | **not_yet** |
| Real (non-placeholder) on-call/paging | Explicitly placeholder, honestly labeled | Swap `placeholder-webhook` for a real receiver once a rotation (even informal) exists | **not_yet**, mechanism already real |
| SUPPORT.md/SECURITY.md/TELEMETRY.md consistency on response-time targets | Actively contradictory across 3 files | One-line doc fix | **build_now** |
| `security@kelvran.dev` as a live channel | Named but inactive (domain unregistered) | Register domain or remove the dangling reference | **build_now (cheap half); not_yet (domain purchase, an operator action)** |
| Support tiering beyond a single honest tier | Single tier, correctly scoped for this stage | No action — matches Portkey's comparable posture | **not_yet, correctly so** |

The pattern across every "not_yet" row is the same one Finding 3 and Finding 6 both surface: every real vendor examined gates numeric SLA commitments and multi-tier support behind an actual paying/contractual relationship, never behind a calendar date or a feature checklist. The "build_now" rows are, without exception, either pure documentation (zero code) or a cheap integration against telemetry Kelvran already has — nothing in this report requires new instrumentation, matching this report's own scope discipline of not proposing engineering work disguised as trust-posture work.

## Caveats

- **Two fetches central to fully substantiating Finding 3 failed this round**: `cloudflare.com/service-level-agreement/` returned HTTP 403, and Kong's own detailed "Support and Maintenance Policy" document (linked from `konghq.com/pricing` but not fetched at its own URL, which 403'd under a guessed path) was not independently confirmed — the tier names, response-time numbers, and 99.9% Konnect figure quoted above come from Kong's pricing-page FAQ text directly, which is a real primary source, but the more detailed legal remedy/credit language in the referenced policy document itself is not confirmed here.
- **OpenAI's specific enterprise-tier contractual SLA number (if one exists) was not directly retrieved** — `openai.com/policies/service-level-agreement/` returned 403, and `openai.com/enterprise-privacy/` (which covers privacy, not SLA terms, and was the wrong page for this question in retrospect) also 403'd. What's confirmed instead is the *public, retrospective* uptime-percentage framing on `status.openai.com`, which is a different artifact than a forward SLA commitment; this report does not claim OpenAI lacks an enterprise SLA, only that it wasn't independently verified this round.
- **This report treats Portkey as the closest shape-and-stage peer to Kelvran**, but Portkey is a funded, multi-tenant SaaS company with real daily request volume (25M/day, per its own marketing) — a materially different traffic and funding profile than Kelvran's single-pilot-tenant stage. Its posture (real status page, no formal SLA, single support email) is a floor worth matching, not a ceiling Kelvran should assume is sufficient once it has real paying tenants of its own.
- **This report did not re-verify `docs/upgrade-research/slo-error-budget-observability-2026-09-15.md`'s or `admin-operator-experience-2026-09-14.md`'s own findings** beyond the specific cross-references made above (the 4 MWMB alert rules, the audit-log/credential-tier work) — those are cited as established context, not independently re-checked this round.
- **The Finding 5 contradiction's correct resolution (update `SUPPORT.md`/`TELEMETRY.md` to match `SECURITY.md`, vs. the reverse) is a judgment call this report does not make** — it depends on whether `gateway/v0.1.0`/`evals/v0.1.0`'s tagging genuinely constitutes "the project's first real release" in the sense `SUPPORT.md`'s own conditional was written to mean, which is a project-maturity judgment, not a fact this research can settle from the repo alone.

## Open Questions

1. **Does `gateway/v0.1.0`/`evals/v0.1.0` (tagged 2026-09-03) actually satisfy the "first real release" condition `SUPPORT.md` and `TELEMETRY.md` both still gate their "aspirational" framing on**, the same condition `SECURITY.md` already declared met? Resolving this settles Finding 5 in one direction or the other.
2. **What real-world signal — beyond "a second real consumer exists" — should gate publishing (as opposed to building) a status page?** Portkey and OpenAI both clearly publish before achieving anything like GA maturity; the risk this report flagged (a zero-incident, zero-subscriber page reading as hollow) may be overstated relative to actual practice, and is worth revisiting against Kelvran's own actual pilot-tenant count.
3. **Should `security@kelvran.dev` be removed from `SECURITY.md` now, or is domain registration imminent enough that leaving the dangling reference is fine short-term?** This report found no repo evidence either way beyond the existing `DECISIONS.md` open action `SECURITY.md` itself already references.
4. **Is a solo-maintainer project the right shape to ever build a "rotation" at all**, or does Finding 4's honest-placeholder pattern actually represent the correct long-term end state (a personal notification channel, never a formal PagerDuty/Opsgenie tier) until Kelvran has more than one person capable of responding? No source examined this round directly addresses solo-maintainer on-call design, since none of the five vendors compared are solo-maintainer projects.
