# Research: Cache L3-lite lexical similarity-threshold calibration & monitoring methodology

**Date:** 2026-09-12
**Scope:** Calibration/monitoring methodology for the hard-coded `l3MinSimilarity = 0.9` Jaccard/MinHash threshold in `gateway/internal/gateway/dataplane/dataplane.go` (per `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`), which sits alongside the already-shipped entity/number/date hard-gate and negation-particle gate. This is narrower than, and does not revisit, `docs/upgrade-research/cache-production-semantic-caching-2026-09-11.md`'s conclusion that lexical-only is the honest current state of the art at Kelvran's scale — this round asks only how to calibrate and monitor the threshold value Kelvran already committed to.

## Context (Kelvran's own real, current state)

`l3MinSimilarity = 0.9` is applied to a Jaccard estimate computed by `cache.JaccardEstimate` over 128-value MinHash signatures (`cache.MinHashSignature`, `k=3` word shingles via `cache.Shingles` — all in `gateway/internal/cache/lexical.go`), inside `freshnessRiskModel()` (`dataplane.go:1145`). The RFC's own Unresolved Questions section states plainly that this ~0.9 floor was specified in `THREAT_MODEL.md` for **embedding-cosine** similarity and transferred to **Jaccard** similarity without independent validation, and that no production traffic exists yet to validate it. `gateway/internal/gateway/dataplane/lexical_cache_test.go` already contains one real, code-comment-documented empirical Jaccard measurement — a single "can"→"cannot" swap inside a ~70-word passage scored similarity=0.90625, just above the floor — computed via "a throwaway scratch computation using `cache.MinHashSignature`/`JaccardEstimate` directly," confirming ad hoc sensitivity probing has already happened informally but was never formalized into a reusable tool. Separately, this session's embedding-gate research (`cache-production-semantic-caching-2026-09-11.md`) built and ran a real offline validation harness, `evals/scripts/validate_embedding_gate.py`, against a 12-pair labeled set (4 seeds × {1 corpus-negative, 1 LLM-generated paraphrase-positive, 1 LLM-generated negative}) drawn from `evals/tests/fixtures/regression_corpus_cache_adversarial.json`, finding bare cosine@0.90 = precision 0.667/recall 1.0 — but that experiment measured **embedding cosine**, not the shipped **lexical Jaccard** threshold.

## Executive Summary

Standard IR/ML practice has two genuinely distinct answers depending on whether labeled data exists. With zero labeled production data (Kelvran's actual current state), the only real precedent is **analytic/offline calibration**: LSH implementations (datasketch, data-juicer) already solve an adjacent but different problem — computing optimal MinHash band/row parameters for a *given* threshold via closed-form false-positive/false-negative integrals — while the threshold *value* itself has no equivalent analytic derivation and must instead come from an offline labeled benchmark, exactly like `validate_embedding_gate.py` already did for the embedding case; the same 12-pair corpus and methodology transfers directly to Jaccard with no new data collection, since Kelvran's own Go code (`cache.MinHashSignature`/`JaccardEstimate`) can compute the sensitivity table natively. Once real production traffic exists, label-free drift monitoring is a mainstream, well-precedented technique (gate-rate week-over-week delta, KL divergence / PSI between score-histogram windows), but it detects *distributional* drift, not threshold *correctness* — it cannot substitute for ground-truth precision/recall without either proxy labels or a periodic human-labeled sample. A recent EMNLP 2026 paper further complicates any future ranking-based tuning: it argues PR-AUC-style model/threshold selection is the wrong frame for semantic caching because it ignores whether scores are usable at the one fixed threshold actually deployed — a caution equally applicable if Kelvran ever tunes the Jaccard threshold by ranking quality alone. Exposing the threshold as a documented, tunable config field (LiteLLM's `similarity_threshold`) and emitting a per-response similarity-score header (LiteLLM's `x-litellm-semantic-similarity`) are both real, currently-shipped precedents Kelvran could adopt regardless of when real traffic arrives, since the header requires no ground truth and is buildable from telemetry Kelvran already has hooks for.

## Findings

### Finding 1 — With no labeled data, LSH tooling optimizes *implementation* parameters for a threshold, not the threshold *value* itself; only an offline labeled benchmark calibrates the value

**Confidence: high** (4 unanimous, primary-source-verified claims: [0], [4], [5], plus the refutation record below)

datasketch's `MinHashLSH` and data-juicer's ported `optimal_param` function both frame "threshold calibration" as: given a chosen Jaccard threshold, analytically compute the `(b, r)` band/row split that minimizes a weighted sum of false-positive/false-negative collision probabilities via closed-form integration of the LSH S-curve — a decades-old, foundational technique (Rajaraman/Ullman) requiring no labeled data, no traffic, only `threshold`, `num_perm`, and two arbitrary weight floats. Three adjacent claims proposing to extend this same math to produce a retrospective sensitivity comparison *across* candidate threshold values (e.g., evaluating the FP/FN integrals at 0.85 vs. 0.90 vs. 0.95 purely offline) were explicitly **refuted 0-3 by adversarial verification** in this round — the verifiers found the functions are parameterized by threshold as an input to solve for `(b,r)`, not a general-purpose evaluator of arbitrary candidate thresholds' real-world precision/recall. This is a load-bearing distinction for Kelvran: Kelvran's own architecture doesn't use LSH banding at all (`l3SearchK = 5`, a linear-ish top-k search per `dataplane.go`, not bucketed LSH), so even the *legitimate* half of this technique (tuning `b`/`r` for a chosen threshold) doesn't directly apply — Kelvran's actual gap is calibrating the threshold **value**, for which the datasketch/data-juicer precedent offers no shortcut. GPTCache, a directly comparable production semantic-cache library, exposes `similarity_threshold` (default 0.8) as a bare numeric config field with explicitly **no** documented statistical calibration methodology, benchmark procedure, or sensitivity-report tooling on its own reference page or in its GitHub repo beyond a generic sample benchmark — corroborating that "ship a threshold with no calibration story" is the actual production norm Kelvran is already at parity with, not behind.

**build_now:** Nothing runnable falls out of the LSH-optimization literature directly (it solves a different problem for a different architecture). What **is** build_now, and is the correct next step per this finding, is Finding 4 below.

### Finding 2 — Cross-validated threshold tuning is a real, standard ML technique, but it presupposes exactly the labeled ground truth Kelvran's research question says doesn't exist yet

**Confidence: high** (primary source: scikit-learn's own docs, claim [3], 3-0)

scikit-learn's `TunedThresholdClassifierCV`, run under `RepeatedStratifiedKFold`, both selects an optimal decision threshold and quantifies how much that optimum varies across folds (a documented example found ~0.32 optimal vs. the naive 0.5 default; a cost-sensitive variant found ~0.02 vs. 0.5) — a genuine, rigorous, currently-shipped technique for threshold selection *and* variance-quantification. The verifier's own flagged caveat is the operative finding here: this method tunes against labeled binary-classification ground truth via cross-validation, which presupposes the exact kind of labeled data research question 1 states does not exist for Kelvran yet. It answers "how do I tune a threshold once labeled data exists" — directly useful once Kelvran has either production feedback signal or a larger labeled corpus (see Finding 4's N=12 limitation) — not "how do I calibrate with zero labeled data."

**not_yet:** Requires a labeled dataset of (query pair, is-this-actually-a-safe-cache-hit) ground truth large enough to k-fold split meaningfully — Kelvran's existing 12-pair harness is a plausible seed but was explicitly sized as a first pass, not large enough to cross-validate a variance estimate from (`cache-production-semantic-caching-2026-09-11.md`'s own Open Questions flags the N=6 corpus-negative subset as "explicitly too small to generalize from"). Trigger: either (a) real production miss/hit telemetry with enough volume to sample-and-label, or (b) deliberately growing the offline harness's N well past 12 pairs per seed-scenario.

### Finding 3 — Once real traffic exists, label-free drift monitoring (gate-rate delta, KL divergence, PSI) is mainstream and well-precedented — but it detects *distributional shift*, not threshold *correctness*, and needs a labeled or proxy-labeled sample to close the gap

**Confidence: high** (4 corroborating sources: [7], [8], [9], all unanimous or independently cross-verified against a second authoritative source)

A concrete, numerically-specified playbook (zeroentropy.dev) defines threshold-drift detection from two label-free production signals — week-over-week change in "gate rate" (fraction of inputs the threshold lets through) and KL divergence between score histograms across time windows — with explicit bands: healthy (<2pp gate-rate change AND KL<0.05), suspect (2-5pp OR KL 0.05-0.15), confirmed drift (>5pp OR KL>0.15) against a trailing 4-week baseline. Population Stability Index (PSI), a decades-old credit-scoring formula (`SUM((actual% - expected%) * ln(actual%/expected%))`), is the standard alternative distribution-comparison metric, independently corroborated across multiple sources and endorsed in AWS's own ML Well-Architected guidance alongside KL and Jensen-Shannon divergence. And per mainstream MLOps doctrine (independently corroborated via metricgate.com and, more authoritatively, Evidently AI's ML-in-production guide), true concept drift is formally a change in P(Y|X) that cannot be measured without label feedback at all — so input/prediction-distribution monitoring (gate-rate delta, KL, PSI) is explicitly a **proxy**, not a measurement of whether the threshold is still *correct*, only whether the traffic *feeding* it has changed shape. One adjacent claim asserting PSI can specifically miss real degradation (staying flat while Gini/rank-power measurably declines) was correctly **refuted 1-2** in adversarial review, but the refutation doesn't overturn the underlying proxy-not-ground-truth caveat above, which comes from the primary MLOps sources directly, not the refuted claim.

**not_yet:** Requires real production request volume through Cache L3-lite with per-request Jaccard-similarity values logged over time — specifically, at minimum: (a) a per-response similarity score (Finding 5 below shows exactly how to emit this at zero marginal engineering cost once traffic exists), (b) enough sustained volume to compute a meaningful week-over-week gate-rate and a non-degenerate score histogram per window, and (c) a periodic small human-labeled sample of served L3 hits (stratified by score band, per the now-refuted-but-directionally-consistent Medium-post claim this round's verifiers rejected on citation grounds, not on the underlying stratified-sampling idea) to close the P(Y|X) gap that pure distribution-monitoring cannot close alone.

### Finding 4 — Kelvran's own `validate_embedding_gate.py` methodology is directly, mechanically portable to the shipped Jaccard threshold, using data and code Kelvran already has — this is the one clear build_now answer to research question 4

**Confidence: high** — grounded in direct repo inspection, not an external source, so no adversarial vote applies; stated as fact-checked against live files in this session.

`evals/scripts/validate_embedding_gate.py` already built exactly this kind of offline sensitivity harness for the *embedding* cosine threshold: 12 labeled pairs (4 real seed scenarios from `regression_corpus_cache_adversarial.json`'s known negatives, each paired with one LLM-generated genuine paraphrase-positive and one LLM-generated distinct-negative), scored bare and gate-layered at multiple candidate thresholds, producing the precision=0.667/recall=1.0 @ 0.90 result research question 4 references. The exact same 12 labeled pairs are directly reusable for the Jaccard case with no new labeling and no LLM calls needed (the pairs already exist as text): compute `cache.Shingles` → `cache.MinHashSignature` → `cache.JaccardEstimate` (all already-exported Go functions in `gateway/internal/cache/lexical.go`) over each pair, sweep candidate thresholds (0.85/0.90/0.95, matching the research question's own framing), and produce a precision/recall table exactly analogous to the embedding one — either as a small Go test/script alongside `lexical_cache_test.go` (no Python port needed, unlike the embedding case, since the real MinHash/Jaccard implementation is already native Go) or reusing the Python harness's pair data with a Python MinHash re-implementation if a single cross-language report is preferred. `lexical_cache_test.go`'s own code comment already proves this is mechanically trivial — one specific pair (a "can"/"cannot" swap) was already hand-computed this way ("a throwaway scratch computation using `cache.MinHashSignature`/`JaccardEstimate` directly: similarity=0.90625") to justify a single test fixture; formalizing that into a reusable sweep across the existing 12-pair (or larger) corpus is a small, mechanical, same-day task.

**build_now:** Yes — this is the single concrete, immediately actionable deliverable this research round surfaces. Concretely: a Go test/script that (a) loads the same seed scenario pairs already used by `validate_embedding_gate.py` (or its underlying `regression_corpus_cache_adversarial.json` entries directly), (b) computes Jaccard similarity for each pair via the existing exported `cache` package functions, (c) sweeps l3MinSimilarity candidates (e.g. 0.85, 0.90, 0.95) and reports precision/recall at each, matching the embedding harness's output format for direct side-by-side comparison. No production traffic, no new labeling, no new dependencies required — everything needed already exists in the repo as of this session.

### Finding 5 — Exposing the threshold as a documented tunable config field, and emitting a per-response similarity score, are both real, low-cost, currently-shipped production precedents Kelvran could adopt independent of when real traffic arrives

**Confidence: high** (2 primary-source-verified, code-corroborated claims: [0], [1], both 3-0)

LiteLLM Proxy ships `similarity_threshold` as an explicit, documented YAML config field under `cache_params` (default example 0.8), applied identically across its Qdrant/Valkey/Redis-semantic backends, and additionally exposes it through its admin dashboard and API — confirmed live in `litellm/caching/{qdrant,redis,valkey}_semantic_cache.py` with dedicated tests, not merely aspirational docs. Separately, LiteLLM emits a per-response `x-litellm-semantic-similarity` header carrying the actual computed similarity score behind every cache decision (hit or miss), including a defined `0.0` sentinel specifically on embedding-timeout misses (verified against a real merged PR, #37742, with before/after examples) — giving per-request observability into "how close was this match" with zero ground-truth labels required, since it's just the raw computed score. Both are mechanically simple, already-proven patterns: making `l3MinSimilarity` a named, documented constant with a comment explaining its provenance is already partially done (`dataplane.go`'s own comments already narrate the RFC's uncertainty); the harder-but-still-cheap step is emitting the computed Jaccard similarity value alongside each L3 decision in Kelvran's existing telemetry/trace pipeline (per `v2-dogfood-telemetry-cache-similarity-l3`-flavored work already tracked among this session's active agents), which is exactly the raw signal Finding 3's monitoring bands would need once real traffic exists.

**build_now (partial):** Making the threshold a clearly-labeled, documented constant is already effectively done in `dataplane.go`. Emitting the per-decision Jaccard similarity value into telemetry (the header/log-field analog of LiteLLM's `x-litellm-semantic-similarity`) is buildable now against existing code paths — `checkLexicalCache` already computes the similarity value before comparing it to the floor, so surfacing it costs a field addition, not new instrumentation infrastructure. Turning that log field into the Finding 3 monitoring bands is **not_yet**, gated on real traffic volume as stated there.

### Finding 6 (caution for future work) — If Kelvran ever tunes the Jaccard threshold by ranking-quality metrics, a 2026 EMNLP paper's central thesis warns that's the wrong frame for a fixed-threshold production cache

**Confidence: medium** (1 primary-source-verified claim [6], vote 2-1; several adjacent claims from the same paper about specific numeric findings were refuted 0-3 and are excluded here)

The paper's own abstract states that standard practice evaluates semantic-caching-adjacent models using PR-AUC — a ranking-quality metric — while ignoring whether scores are usable at the one fixed threshold actually deployed, and that this mismatch produces systematically poor deployment choices. This doesn't change Kelvran's current lexical-only, hard-gated design (which the prior research round already concluded is the honest state of the art), but it is a direct, relevant caution for *any* future work that might try to select or re-tune the Jaccard threshold by ranking quality (e.g., AUC over the sensitivity table from Finding 4) rather than by precision/recall *at* the specific threshold that will actually ship. Note the paper's authors are Redis-affiliated (building on their own LangCache product) — a mild vendor-interest flag noted but not disqualifying, since the thesis is echoed independently by the plain precision/recall framing already used in Kelvran's own `validate_embedding_gate.py`.

**not_yet (informational only):** No action required now; flag for whoever eventually builds Finding 4's sensitivity table to report precision/recall at each candidate threshold directly (which Finding 4 already specifies), not a single aggregate ranking score, so this caution is satisfied by construction.

## Caveats

- The scikit-learn CV-tuning technique (Finding 2) and the general LSH band-optimization technique (Finding 1) are both real and well-sourced, but neither directly solves Kelvran's zero-labeled-data problem — they were the closest adjacent standard-practice techniques found, not a perfect match, and this is flagged explicitly in both findings rather than glossed over.
- Several plausible-sounding claims from this round's initial pass were adversarially refuted (13 total, listed in the source synthesis) — notably, that LSH's FP/FN integrals can evaluate arbitrary candidate thresholds' real precision/recall (they can't; they optimize `(b,r)` for a *given* threshold), and several EMNLP-paper claims beyond the core PR-AUC-vs-calibration thesis. These are excluded from findings above per the verification record.
- The zeroentropy.dev playbook (Finding 3) and metricgate.com blog (Finding 3) are blog-tier sources; both are treated as medium-to-high confidence only because their specific claims were either independently cross-verified against a more authoritative source (Evidently AI for the P(Y|X) point) or state mainstream, uncontroversial numeric bands that no contradicting evidence was found for — not because blog sourcing alone would normally clear this bar.
- Finding 4's build_now claim is based on direct repo inspection during this research session (existence of `cache.Shingles`/`MinHashSignature`/`JaccardEstimate` as exported functions, the 12-pair corpus, and the `lexical_cache_test.go` code comment), not an external adversarially-voted source — it is asserted with high confidence because it is independently verifiable by reading the cited files, not because it went through the 3-vote process applied to the web-sourced claims above.
