# Prompt Template Lifecycle — Versioning, Experimentation, Rollback — Deep Research (2026-09-15)

## Question

Kelvran recently shipped bbolt-backed persistence for admin-managed prompt templates (`gateway/internal/prompt/`, `gateway/internal/admin/`). What upgrade/best-practice opportunities exist for prompt template lifecycle management on top of this — versioning, A/B testing/experimentation between prompt variants, safe rollback — and how do comparable production LLM platforms (LiteLLM, Portkey, LangSmith/Langfuse prompt management, PromptLayer, PostHog) structure this?

## Context (Kelvran's own real, current state)

`gateway/internal/prompt/prompt.go`'s package doc comment states prompt templates are "operator-managed, versioned message templates" and that "every prompt ID has its own append-only version history: Upsert always creates a NEW version, never edits an existing one in place." `Prompt` (`prompt.go:35-40`) is exactly four fields — `ID`, `Version`, `Messages`, `CreatedAt` — no label, alias, comment, `CreatedBy`, or status field of any kind. `Store.Upsert` computes `Version = len(existing versions for id) + 1` inside a `CompareAndSwap` retry loop (never a plain Load-then-Store), so two concurrent `Upsert(id, ...)` calls for the same `id` always produce distinct, sequential versions with no lost write (`TestConcurrentUpsertGetResolveUnderRace`); `Store.Get(id, version)` treats `version <= 0` as "latest" (the highest existing version number for that id) and any positive `version` as an exact pin. `gateway/internal/prompt/boltstore/boltstore.go` persists each id's *entire* version slice as one JSON blob under a single bbolt bucket, mirroring `internal/identity/boltstore` and `internal/budget/boltstore` file-for-file; `Persister.Save(ctx, id, nil)` is the documented deletion signal, and `TestPersistsAcrossReopen` proves durability survives a real process restart. `gateway/internal/admin/admin.go` exposes exactly five Admin-API routes for prompts: `GET /admin/prompts` (list latest-per-id), `GET /admin/prompts/{id}` (latest), `GET /admin/prompts/{id}/versions/{version}` (exact pin), `POST /admin/prompts/{id}` (Upsert = always a new version, Admin-token-gated), `DELETE /admin/prompts/{id}` (removes *every* version for that id — there is no single-version delete). `dataplane.resolvePromptIfSet` (`gateway/internal/gateway/dataplane/dataplane.go:875-920`) resolves `req.PromptID`/`req.PromptVersion`/`req.PromptVariables` into real `[]adapter.Message` content via `prompt.Store.Resolve`, then overwrites `req.PromptVersion` with the *real* resolved version number (a round-3 backlog-audit fix, so "latest" resolution is always traceable after the fact) — this resolved `PromptID`/`PromptVersion` pair is recorded as real OTel span attributes (`telemetry/result.go`'s `AttrKelvranPromptID`/`AttrKelvranPromptVersion`, set on every `ChatCompletionResult` where `PromptID != ""`) alongside cost/token/latency data already captured for every request. `substitute` (`prompt.go:307-327`) is a deliberately minimal `{{name}}`-only allowlist substitution, explicitly not Go's `text/template`, to avoid handing operator-authored prompt content a template-injection surface. There is no `Persister`-level or `Store`-level concept of a named pointer ("production"/"staging"/a percentage split) anywhere in this package or in `admin.go`'s routes.

## Summary

Kelvran's prompt store already implements the exact same immutable, append-only, sequentially-numbered versioning model that Langfuse, LangSmith, and PromptLayer all converge on as the industry-standard foundation — and, notably, Kelvran's request path already emits per-version OTel telemetry (`AttrKelvranPromptID`/`AttrKelvranPromptVersion` alongside cost/latency/tokens), which is the exact substrate PostHog's and PromptLayer's variant-comparison dashboards are built on, so the hardest infrastructure precondition for experimentation is already shipped, just not surfaced. The one real, concrete gap every comparable platform's rollback and deployment-promotion story depends on and Kelvran's does not have is a **named, mutable pointer decoupled from the version-number-and-content itself** — Langfuse's `production` label, PromptLayer's release label, LangSmith's environment/commit-tag — without which "rollback" in Kelvran today means either re-`Upsert`-ing old content as a brand-new version number (a copy, not a repoint) or requiring every caller to hold and pass an exact `PromptVersion` integer (which does work as a pin, but couples deployment state to caller code rather than decoupling it, the opposite of what every comparable platform optimizes for). None of the platforms surveyed run true server-side traffic-splitting for prompt A/B tests either — Langfuse and PromptLayer both document the split as happening in the caller's own application code (Langfuse explicitly, `Math.random() < 0.5`; PromptLayer via percentage/segment-based release-label routing that is still evaluated inside the calling app's SDK) — but Kelvran is structurally positioned to do genuinely better than either, since it already sits as the actual request-serving gateway between every caller and the provider, not merely an SDK inside the caller's process; a caller-supplied stable identifier (session/user ID) hashed with a per-prompt salt (the deterministic-bucketing pattern real feature-flag services use) could let Kelvran assign and log a variant server-side, something no surveyed SDK-shaped competitor can do as natively.

## Findings

### Finding 1 — Kelvran's version model already matches the industry-standard immutable/sequential/append-only shape Langfuse, LangSmith, and PromptLayer all ship (confidence: high) — **non-gap, already correct**

`prompt.go`'s own package doc states versions are append-only and Upsert "never edits an existing one in place" — matching Langfuse's documented model exactly ("Versions provide an immutable history of every prompt change. Each update creates a new version (1, 2, 3...)") and LangSmith's commit model (each `push_prompt` creates a new, addressable commit). `Store.Upsert`'s `Version = len(existing) + 1` inside a CAS retry loop is the correct concurrency-safe implementation of that model — proven by `TestConcurrentUpsertGetResolveUnderRace`, not merely asserted. There is genuinely nothing to change here; Kelvran picked the same foundation every comparable platform converges on, independently.

### Finding 2 — Kelvran has no named, mutable deployment pointer (a "label"/"environment"/"release label") decoupled from the version number; "latest" is the only pointer, and it moves automatically on every `Upsert` with no separate promotion step (confidence: high) — **real, concrete gap**

Langfuse: "To deploy a prompt version, you have to assign the label `production`... your code references the labels" so "updates and rollbacks happen by moving the label pointer rather than editing code." LangSmith: "environments... named deployment targets... assign to specific commits," with `client.pull_prompt(name:production)` documented as literally equivalent to pulling by the commit hash the tag currently resolves to. PromptLayer: "release labels such as `prod` and `staging` that each point to a specific version... moving the `prod` release label back to the known-good version — a rollback measured in seconds, not a hotfix deploy." Kelvran's `Store.Get(id, version<=0)` returns whatever the highest version number happens to be — there is no distinct "this is the one marked live" concept, so promoting a new version is *identical* to creating it (there's no separate "and now serve it" step to gate), and there's no way to have "staging" point at version 7 while "production" stays pinned to version 5 without every caller for each environment separately memorizing and passing an exact `PromptVersion` integer.

### Finding 3 — Rollback in Kelvran today means one of two options, and neither is the decoupled label-repoint every comparable platform treats as the standard: (a) re-`Upsert` old content, which allocates a brand-new version number rather than repointing to the old one, or (b) require every caller to pass an exact `PromptVersion`, which does work as a pin but couples the caller's own request to a specific integer rather than to a name (confidence: high) — **direct consequence of Finding 2, real gap**

Langfuse's own rollback: "Simply reassign the `production` label back to a previous version... this happens without changing code." PromptLayer: rollback is "measured in seconds, not a hotfix deploy," via the same label-move mechanism. LangSmith's environments maintain "an ordered history of which commits were assigned to it and when," with a UI "rollback icon" reading that history to let an operator pick an earlier commit and repoint the environment pointer — a first-class, auditable rollback action distinct from creating a new commit. Kelvall's `DELETE /admin/prompts/{id}` only removes *every* version for an id (a destructive nuke, not a rollback), and there is no `PATCH`/promote-style route that says "make version N the one 'latest' resolves to without copying its content into a new version N+1." Re-`Upsert`-ing old content as a workaround also has a real, subtle side effect worth naming: because `Upsert` always allocates `len(existing)+1`, "rolling back" this way permanently changes what integer any caller pinned to the *new* highest version will get if they ever start requesting "latest" again, and it inflates the version-count history with a duplicate of already-existing content rather than genuinely reusing it.

### Finding 4 — None of Langfuse, PromptLayer, or PostHog's A/B-testing feature actually performs server-side traffic splitting inside the platform itself; all three (as A/B testing is currently understood in this space) push the random-assignment decision into the *calling application's own code or SDK*, which Kelvran — as the actual request-serving gateway, not an SDK — is structurally better positioned to do natively (confidence: high on the citation; the "Kelvran is better positioned" clause is this report's own reasoned recommendation, not a claim about any surveyed vendor) — **real opportunity, not merely a gap**

Langfuse's own docs state plainly: "label different versions of a prompt (e.g., `prod-a` and `prod-b`)... your application can randomly alternate between these versions," with the actual code sample being `Math.random() < 0.5 ? promptA : promptB` — the randomization is explicitly application code, not a Langfuse server-side feature. PromptLayer's marketing and docs describe percentage/segment-based routing via "release labels," but the mechanism is still evaluated by the caller's own SDK resolving a label at fetch time inside the calling application's process, the same shape as Langfuse's, just with more built-in percentage bookkeeping. PostHog's implementation is the most server-side of the three, but it achieves this by piggy-backing on PostHog's own separately-hosted feature-flag/experiment product ("PostHog creates a feature flag with one variant per prompt version") — i.e. PostHog's *prompt* layer still has no bespoke experiment engine; it reuses a wholly separate control-plane product. Kelvran is different from all three in one structural way that matters here: Kelvran's gateway *is* the thing serving every request between the caller and the provider (per `resolvePromptIfSet`'s own position in the request pipeline, immediately after auth and before rate-limiting), so a percentage-based or hash-bucketed variant assignment could be computed and enforced entirely inside `prompt.Store.Resolve` itself, with zero caller-side code — something none of the three surveyed platforms' actual mechanics achieve today (Langfuse/PromptLayer require caller-side logic; PostHog requires wiring to a second product).

### Finding 5 — A real, checkable prior-art algorithm exists for the specific mechanism a future server-side split would need (deterministic, sticky, per-experiment-decorrelated bucketing), and it is a well-precedented pattern, not a novel design problem (confidence: medium — secondary source, but its citation chain bottoms out in a named vendor's public docs and open-source SDK) — **actionable technical input for if/when Finding 4's opportunity is pursued**

The documented pattern is `bucket = SHA256(salt + unit_id) mod 10000`, compared against a rollout-percentage threshold, where the salt is **per-flag/per-experiment**, not merely per-user — "if you hash on `user_id` alone, the same user lands in the same bucket for every flag... including a per-flag salt decorrelates assignments across flags." Mapped onto Kelvran's own shape: `unit_id` would be a caller-supplied stable identifier (e.g. a session or end-user ID passed alongside `PromptID`), and the salt would naturally be the `prompt_id` itself (or `prompt_id` + an experiment identifier) — giving a deterministic, sticky assignment (the same caller-supplied ID always lands on the same variant for a given prompt experiment) that requires no server-side session storage at all, consistent with `prompt.Store`'s existing stateless, pure-function `Resolve` design.

### Finding 6 — Kelvran already emits the exact telemetry substrate (`AttrKelvranPromptID`/`AttrKelvranPromptVersion` on every `ChatCompletionResult`, alongside cost/latency/token data) that every surveyed platform's variant-comparison feature is built on top of — this is a shipped, verified precondition for experimentation, not a future dependency (confidence: high, read directly from source and its own test) — **non-gap; understated existing asset**

`telemetry/result.go`'s `RecordChatCompletionResult` appends `AttrKelvranPromptID`/`AttrKelvranPromptVersion` to the span whenever `r.PromptID != ""` (`TestRecordChatCompletionResultEmitsPromptIDAndVersionOnlyWhenSet` proves this, not just documents it), and `dataplane.resolvePromptIfSet` deliberately overwrites `req.PromptVersion` with the real resolved version — explicitly so that "latest" resolution is traceable after the fact even though the caller never specified a concrete number. This is functionally identical in purpose to PostHog's `$ai_prompt_name`/`$ai_prompt_version` event tagging and PromptLayer's per-version metrics tracking — the mechanism that lets an operator later ask "how did version 5 perform vs. version 6 on cost/latency," which is the actual analytical payoff every comparable platform's A/B-testing feature ultimately delivers. Kelvran already has this half of the feature; only the "assign a variant and let an operator declare a winner" half (Findings 2-4) is missing.

### Finding 7 — etcd's per-key `version` concept (starts at 1, increments per mutation, reset on delete) is the same primitive Kelvran's own per-`id` `Version` field already implements correctly — but etcd's separate, global, monotonically-increasing `revision` counter across the *entire* keyspace has no analog in Kelvran's prompt store, meaning there is no single, total-ordered way to answer "what changed across every prompt in this deploy window" (confidence: high on etcd's own mechanics; the "Kelvran has no analog" half is a direct read of `prompt.go`, not inferred) — **minor, low-priority gap**

etcd's docs describe exactly two counters: a per-key `version` ("creating a key increments the version of that key, starting at 1... updating a key increments its version") and a wholly separate, global `revision` that increases on *every* atomic mutation across the whole keyspace, giving total ordering across all keys, not just one. Kelvran's `Prompt.Version` is a correct implementation of etcd's *first* concept, scoped correctly per-`id` — but there is no equivalent of etcd's second concept anywhere in `prompt.Store`: nothing timestamps or orders mutations *across different prompt IDs* into a single, queryable sequence (`CreatedAt` exists per-`Prompt`, but is wall-clock time, not a tamper-evident monotonic counter, and nothing indexes by it). This is a real, checkable structural gap, but a low-priority one — it matters for cross-prompt audit/compliance questions ("show me every prompt change between deploy X and deploy Y"), not for the versioning/rollback/experimentation questions this research was scoped to answer.

## Caveats

- Every comparable-platform claim above is grounded in each vendor's own current documentation (Langfuse, LangSmith, PromptLayer, PostHog, etcd) as of this research pass, not in an independent hands-on trial of any of those products against Kelvran's own workload — the *mechanics* described (label-repoint rollback, application-side A/B randomization, feature-flag-flag-based experiments) are verified against primary sources, but real-world operator friction with any of them is not something this pass tested directly.
- The "Kelvran is structurally better positioned for server-side splitting" framing in Finding 4 is this report's own reasoned inference from where `resolvePromptIfSet` sits in the request pipeline, not a claim that any surveyed vendor lacks this capability elsewhere in their own product — Langfuse/PromptLayer are SDK-first by design choice, not by technical limitation, and could in principle add a server-side split too.
- The deterministic-bucketing algorithm in Finding 5 traces through a secondary (curriculum-style) source rather than being read directly from a single, unambiguous first-party spec; its citation chain does bottom out in a named vendor's public docs and open-source SDK, but the exact byte-level hash-to-integer folding is an SDK implementation detail, not something guaranteed identical across every implementation of the pattern — treat the *shape* (salted SHA-256, per-experiment salt, modulo bucket count, threshold compare) as the reusable takeaway, not a byte-exact spec to copy verbatim.
- This research did not examine LiteLLM's or Portkey's prompt-management surfaces directly — no verified claim about either survived this pass's citation set, so neither is represented in the Findings above; treat their absence as "not examined," not as "found to have nothing relevant."
- Kelvran's own `Persister` interface has shipped unimplemented (per its own doc comment) for a full RFC cycle before `boltstore` existed, and `NewStoreWithPersister` currently has "no real caller anywhere in this codebase yet" per that constructor's own doc comment — any label/pointer or experiment-assignment feature proposed above would need to account for whether it is wired through the in-memory `Store` only, or also needs a `boltstore` schema change (a new bucket, most naturally) to survive a restart.

## Recommendation for Kelvran

1. **Add a named, mutable label/pointer layer decoupled from `Version` and content** (closes Findings 2 and 3) — the single highest-leverage change, since every comparable platform's rollback and staged-promotion story depends on exactly this primitive, and Kelvran is currently the outlier for not having it. Concretely: a small `labels map[string][]string` (or a dedicated `Labels map[id]map[label]version` structure) alongside the existing `versions map[string][]Prompt` in `storeState`, mutated with the same rebuild-whole-then-swap CAS convention `Upsert`/`Delete` already use, persisted via a new bbolt bucket in `boltstore` (or an extension to the existing one) mirroring the existing `Save(ctx, id, nil)`-means-delete convention. `Resolve` would need a way to accept a label name in addition to (or as an alternative to) an integer `version` — the exact shape LangSmith's `pull_prompt(name:production)` already validates as "resolves to whichever commit the tag currently points to."
2. **Add an explicit promote/rollback Admin API action, distinct from `Upsert`** (closes Finding 3) — e.g. `PUT /admin/prompts/{id}/labels/{label}` with a body naming the target version, so "roll back production to version 5" is a single, auditable, non-content-duplicating operation, not a re-`Upsert` of version 5's content as a new version 8.
3. **If/when A/B experimentation is actually requested, prefer a server-side, hash-bucketed variant assignment inside `Resolve` over copying any surveyed vendor's application-side-randomization pattern** (Findings 4-5) — this is Kelvran's real structural advantage over Langfuse/PromptLayer/PostHog for this specific feature, and the deterministic `SHA256(salt + caller_supplied_id) mod N` pattern is a real, precedented, low-risk mechanism to implement it with, keyed by `prompt_id` (or `prompt_id` + an explicit experiment id) as the salt. This is explicitly a "when triggered," not a "build now" — no evidence surfaced in this pass that Kelvran has a real caller asking for prompt A/B testing today; build the label/rollback primitive from recommendation 1 first, since experimentation depends on it (a variant needs a name to be assigned to) but rollback does not depend on experimentation.
4. **Low priority, no urgency**: consider whether `docs/agents/LOGS.md`/`DECISIONS.md`-style cross-prompt audit questions ("what changed across all prompts between two points in time") ever become a real operational need — if so, Finding 7's etcd-style global-revision-counter gap is the concrete mechanism to close it; nothing suggests this is needed today.

## Open Questions

- Does any real caller of Kelvran's Admin API today actually need "staging" vs. "production" as distinct pointers, or is a single mutable "latest-that-serves-live-traffic" pointer (with the current `Get(id, version<=0)`-is-always-truly-latest behavior demoted to "highest version number that exists," a separate, less load-bearing query) sufficient for the platform's actual current user base? This research pass found no evidence of a real multi-environment caller today.
- If a label/pointer layer is added, should moving a label be gated behind the same Admin-token tier `POST`/`DELETE /admin/prompts/{id}` already require, or would a lighter-weight "operator" tier (distinct from full Admin) make sense for routine promote/rollback actions specifically, since it's a lower-risk action than an arbitrary content `Upsert`? Not addressed by any surveyed platform's docs in a way that maps cleanly onto Kelvran's own existing two-tier (`Admin`/read-only) credential model (`admin.go`'s own doc comment on credential tiers).
- Would a future server-side experiment feature need its own persisted "which variant did this caller see last time" state to guarantee sticky assignment across a caller's own retries/reconnects, or is a pure hash-of-caller-supplied-ID-with-no-storage (Finding 5) sufficient in practice? The stateless approach is simpler and consistent with `Resolve`'s current pure-function design, but was not validated against any real Kelvran traffic pattern in this pass.
- LiteLLM's and Portkey's own prompt-management feature sets were not examined in this pass (see Caveats) — a follow-up research pass scoped specifically to those two platforms could either surface additional patterns or confirm the findings above already cover the relevant design space.
