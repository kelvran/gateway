# Kelvran Evals Corpus — Cache Attack Pattern Research for Regression Case Authoring (2026-09-08)

**Date:** 2026-09-08
**Scope:** External, documented cache-poisoning/hijacking/correctness attack patterns against LLM-gateway/proxy semantic and lexical response caches — sourced specifically to seed *new* `category:cache` cases in `evals/tests/fixtures/regression_corpus_dogfood.json`, distinct from the two existing `category:cache` cases already mined from this project's own bug history (the L3-lite entity-fingerprint bug and the L1/L2 key-layer-collision bug). This is one of three parallel research passes (cache attack patterns, cost-abuse patterns, routing/chaos patterns) feeding a follow-on regression-corpus-growth round; it does not touch or reference the other two.
**Method:** Adversarial multi-source research (3-vote verification per claim) against real CVEs/GHSAs in named LLM-gateway/proxy/cache products (ckan-mcp-server, LiteLLM, Open WebUI, GPTCache, vllm-project/semantic-router) and 2026 academic literature on semantic-cache safety, prompt-cache timing side channels, and cosine-similarity-gate failure modes. This pass deliberately does not re-derive ground already covered by the sibling report `docs/upgrade-research/cache-2026-09-06.md` — CacheAttack's `"Neglect:"` mechanism, KeyPooling's defense contract, GroundedCache's per-gate ablation methodology, cache ROI reporting, and singleflight coalescing are treated as settled prior art there and only re-surface here where a *new* fact (e.g. a specific quantified freshness-exploitation number, or a second paper's independent corroboration) earns its place. 18 claims confirmed (13 unanimous 3-0, 3 at 2-0 on a two-voter paper, 2 at 2-1); 3 claims explicitly refuted; 4 claims returned unverifiable due to verifier infrastructure errors (neither confirmed nor refuted) — all three categories are accounted for in the Caveats section below, not silently dropped.

---

## Executive summary

Real-world, CVE-documented cache-poisoning and cache-hijacking incidents against LLM-gateway-adjacent products in 2026 cluster into two structurally distinct classes, both directly relevant to Kelvran's L1/L2/L3-lite design: **exact-key collisions** caused by unescaped serialization, truncated hashes, or misconfigured caching decorators (ckan-mcp-server, LiteLLM, Open WebUI ×2, GPTCache — five independent CVEs/GHSAs across five real products), and **semantic near-duplicate false-positives** caused by embedding-space or lexical-similarity gates that are either too permissive (a diluted per-user namespace token in vllm-project/semantic-router) or fundamentally blind to meaning-reversing edits (a documented 0.9608-cosine negation flip that beats every deployed semantic-cache threshold surveyed in a 2026 audit paper). A third class — timing side-channel leakage from a *shared* cache, independent of any key collision — was empirically measured across seven real commercial LLM API providers including OpenAI in a peer-reviewed ICML 2025 paper, establishing that even a perfectly-partitioned cache can leak cross-tenant signal through response latency alone. On freshness/staleness, the sibling report already covers GroundedCache's headline 51.5%→1.5% document-drift number; this pass adds one materially new design pattern (FreshCache's per-tier staleness-probability budget, distinct epsilons for answer/URL-list/page-content reuse) that is directly portable to Kelvran's own freshness/risk model. Fifteen of the confirmed findings below translate directly into concrete, citable eval-case scenarios in the dedicated section at the end of this report.

## Findings, ranked

### 1. Delimiter-injection and type-ambiguity cache-key collisions are a real, CVE-documented cache-poisoning vector in a production MCP server (High confidence)

**What:** ckan-mcp-server's `canonicalizeParams` function (GHSA-78x9-fhhx-v2g6 / CVE-2026-73846, CVSS 6.5) joins sorted `key=value` pairs with `&` without escaping `&`, `=`, or the `|` field separator used elsewhere in `buildCacheKey`. Two different logical parameter sets can serialize to the identical cache key — e.g. `{q:'budget', rows:10}` and `{q:'budget&rows=10'}` both canonicalize to `q=budget&rows=10`. The advisory documents two independent confirmed collision vectors: delimiter injection (the example above) and object-vs-string type ambiguity (a parameter passed as a string that JSON-round-trips indistinguishably from an object representation). Because the collision is general — an attacker can reproduce *any* target canonical string by injecting it into the alphabetically-first parameter — and caching is shared/default-on, an attacker can prime a colliding entry so that another client's genuinely different query receives the attacker-chosen cached response. A working PoC demonstrates a victim served an attacker-primed cache entry.

**Why it matters for Kelvran specifically:** this is a direct, real-world instance of the exact structural risk class Kelvran's L1/L2 key builder must avoid — a hash-input serialization that isn't collision-resistant to adversarial input containing the serializer's own delimiter characters. Kelvran's `gateway/internal/cache/key.go` already closed one collision class in this family (the L1-vs-L2 same-hash-input bug, now a regression case in the corpus) but that bug was about *layer* discrimination, not *delimiter*-injection within a single layer's own serialized input — this is a distinct, still-untested risk shape.

**Confidence:** High — two independently GitHub-reviewed, CVE-numbered primary advisories for the same real product, cross-verified via `gh api`, unanimous 3-0 and 3-0 votes on the two component claims (one delimiter-injection description at 2-1, the general-collision/cross-client-confusion consequence at 3-0).

**Caveat:** ckan-mcp-server is an MCP tool server, not an LLM-gateway response cache per se — the analogy is to Kelvran's key-serialization mechanism specifically (any place a hash input is built by joining structured fields with a delimiter), not to Kelvran's product category as a whole.

### 2. Truncated-hash cache keys enable cross-identity hijacking, not just cache incorrectness — a real CRITICAL CVE in a named LLM gateway (High confidence)

**What:** LiteLLM's OIDC userinfo cache used `token[:20]` (the first 20 characters of a JWT) as its cache key (GHSA-jjhc-v7c2-5hh6 / CVE-2026-35030, CVSS4 9.4 Critical). Because JWT headers produced by the same signing algorithm are frequently identical, different tokens can produce colliding truncated keys. An unauthenticated attacker can craft a token whose first 20 characters match a legitimate cached victim's token; on a cache hit, the attacker inherits that victim's identity and permissions — a full authentication bypass mediated entirely through the cache layer, not through any flaw in the auth logic itself.

**Why it matters for Kelvran specifically:** LiteLLM is a real, named LLM gateway product (the same category as Kelvran), and this is the clearest documented case of "cache-key truncation/weak-hashing causes cross-identity leakage" in that exact product category. It is a scoping caveat, not a disqualifier, that this is LiteLLM's *auth* cache rather than its semantic response cache — but the truncated-key-causes-collision mechanism is identical in shape to any place Kelvran might ever key a cache entry off a prefix or truncated hash of a longer identifier (tenant ID, session token, request signature) rather than the full value or a full-strength hash.

**Confidence:** High — primary vendor GHSA with an assigned CVE, GitHub-reviewed, cross-checked against the independent GitHub Advisory Database mirror; both component claims unanimous 3-0.

**Caveat:** this is a cache-key-collision-as-authn-bypass pattern in LiteLLM's identity/auth cache, not a semantic-cache poisoning of LLM *responses* — cite it as a structural-collision analogy, not as a semantic-cache-specific incident.

### 3. Missing tenant/instance namespace on a shared-backend cache key enables real cross-instance poisoning and data exfiltration, not just leakage (High confidence)

**What:** Open WebUI's Redis cache keys for `tool_servers` and `terminal_servers` omit the `REDIS_KEY_PREFIX` namespacing used by nearly every other cache key in the codebase (GHSA-3x8w-4f7p-xxc2 / CVE-2026-44552, CVSS 8.7 High). When multiple Open WebUI instances share one Redis backend — an explicitly documented and supported deployment pattern for multi-region, blue-green, or cluster topologies — the bare, unprefixed keys collide across instances: a write on Instance A is later read as valid cache by Instance B. The full documented attack chain requires admin access on only *one* instance (not the victim instance): the attacker configures a malicious tool-server URL on Instance A, which is cached under the unprefixed key; Instance B's users then unknowingly fetch and invoke Instance A's poisoned tool-server list, sending chat content, user identity, and OAuth tokens to the attacker-controlled server, which returns arbitrary attacker-controlled responses fed back into Instance B's users' LLM context as "trusted tool output."

**Why it matters for Kelvran specifically:** this is the single most complete, real, documented "cache-key namespace omission → cross-boundary poisoning → data exfiltration" chain found in this research pass, and it validates from the *failure* side exactly what KeyPooling's defense contract (already covered in the sibling report) validates from the *success* side: a namespace/discriminator must survive every write and every read, and "we prefix almost everything" is not the same guarantee as "we prefix everything." Kelvran's own tenant-namespace-in-every-key design is the correct shape per this incident, but the incident is a concrete demonstration of exactly how a single omitted discriminator on an otherwise-correct design turns into a full poisoning chain — good source material for a case testing "does every cache write path include the tenant discriminator," not just the happy-path ones.

**Confidence:** High — primary, CVE-assigned, GitHub-reviewed advisory with named file/line and an explicit attack-scenario writeup; both component claims unanimous 3-0.

**Caveat:** this is cross-*instance* leakage under a shared-backend deployment topology, not cross-*tenant* leakage within a single instance in the SaaS multi-tenancy sense — relevant to Kelvran only if/when a distributed cache backend is ever built (named as deferred future work in the sibling report), or as a general "namespace must be on every key" test pattern regardless of topology.

### 4. A cache-decorator library misconfiguration (`key=` vs `key_builder=`) silently collapses per-user cache isolation into a single shared entry — a real, reproducible CVE with concrete repro steps (High confidence)

**What:** Open WebUI's `get_all_models` caching decorator used `aiocache`'s `key=` parameter (evaluated once, as a static/constant key) instead of `key_builder=` (invoked per-call) (GHSA-3wp3-xxj9-5jqq / CVE-2026-59213, CVSS 3.1 Low). Because `key=` in the pinned aiocache version is a static cache key rather than a per-call callable, the intended per-user namespacing via `user.id` never actually took effect — every caller collided onto one shared cache entry within the TTL window (default 1 second, `MODELS_CACHE_TTL`). Whichever user's request first populates the cache within that window determines what every other caller receives, regardless of their own actual permissions — exposing the existence and naming of models the receiving user is not authorized to see. The advisory's own reproduction: configure two users with differing model-access permissions; User A requests the model list (populating the shared cache); within the 1-second TTL, User B requests the model list and receives User A's filtered list, including unauthorized models.

**Why it matters for Kelvran specifically:** this is the clearest available real-world example of "per-key namespacing was *intended* in the code but a library-level API misuse silently defeated it" — a subtler and more insidious failure mode than an omitted namespace (Finding 3), because the code visibly *tries* to scope by user and appears correct on casual reading. This is exactly the shape of bug a code-review checklist or a static test alone might miss, and exactly the shape a concrete eval regression case (feed two permission-differentiated identities through the same cache path within a TTL window, assert no cross-leak) is well-suited to catch.

**Confidence:** High — primary, CVE-assigned, GitHub-reviewed advisory with named file/line, exact root cause, and a step-by-step reproduction; all three component claims unanimous 3-0.

**Caveat:** severity is rated Low (CVSS 3.1, 3.5) because the attacker cannot select which victim they collide with and the leak is model *existence/naming* only, not model outputs — treat this as a correctness/isolation-discipline case, not a high-severity exploit template.

### 5. Deriving a cache key from only a buffered prefix of file/image content — not the full content — causes real prefix-collision cache poisoning in a named semantic-cache library (Medium-High confidence)

**What:** GPTCache (Zilliztech), a widely-used semantic caching library for LLM applications, derived cache keys for file/image inputs from `BufferedReader.peek()`, which returns only the currently-buffered prefix (commonly ~8192 bytes) rather than the full file content (GHSA-xfqj-4cr9-9gr5 / CVE-2026-10812, CWE-327, CVSS 3.1 3.6 Low/AC:H). Two different files sharing the same initial ~8KB prefix but differing in later content produce the same cache key/pre-embedding input — an attacker who controls a file's later bytes (while matching a target's leading bytes) can cause their submission to be treated as identical to another file, retrieving its cached response.

**Why it matters for Kelvran specifically:** this is a named, real semantic-cache product (not an analogy) with a documented cache-poisoning bug from exactly the failure mode a hasty performance optimization tends to introduce — "we only need to look at the start of the input to build a fast key" — and it generalizes directly to any future Kelvran cache-key derivation over long inputs (e.g. large conversation histories, uploaded documents/attachments referenced by `Message.Parts`) if a similar shortcut were ever taken instead of hashing full content.

**Confidence:** Medium-High — primary, GitHub-reviewed, CVE-assigned advisory cross-verified against the linked GitHub issue/PR containing a runnable repro; both component claims unanimous 3-0. Real-world blast radius is limited (AV:L, attacker needs local-equivalent access, and CWE-327's "broken crypto algorithm" classification is an imprecise auto-tag for what is really a truncated-input-hashing bug) — the claims themselves flag this, so it is not overstated here.

### 6. A shared prompt cache leaks cross-user signal through response-timing alone, independent of any key collision — empirically measured across seven real commercial LLM API providers (Medium-High confidence)

**What:** *Auditing Prompt Caching in Language Model APIs* (Gu, Li, Kuditipudi, Liang, Hashimoto; ICML 2025, arXiv:2502.07776) documents a real, exploitable timing side channel: because cached prompts process measurably faster than non-cached ones, an attacker sharing a cache with other users can infer information about other users' submitted prompts purely from API response latency (fast response = cache hit = someone else already submitted that or a similar prompt). Using statistical timing audits, the authors empirically detected — not merely theorized about — global (cross-user) cache sharing in seven real commercial API providers, including OpenAI, and used the same technique to infer non-public architectural details of a provider's embedding model.

**Why it matters for Kelvran specifically:** this is a distinct leakage channel from every other finding in this report — it requires no key collision, no misconfiguration, and no false-positive semantic match at all. Even a cache with perfect per-tenant partitioning at the key level can still leak "did tenant X already ask something like this" to an attacker who can time responses, if the *timing* itself isn't also partitioned or normalized (e.g. constant-time responses regardless of hit/miss, or timing-noise injection). Kelvran's per-tenant key partitioning defends against the *response-content* leak this channel could otherwise exploit as a stepping stone, but does not by itself defend against the *existence-inference* leak (learning that a hit occurred at all, and how fast) unless response timing is also normalized across hit/miss paths — worth naming explicitly as a residual risk even where content isolation is correct.

**Confidence:** Medium-High — peer-reviewed ICML paper from credible authors (Percy Liang, Tatsunori Hashimoto among them), but both component claims registered only 2 votes (unanimous 2-0, not the full 3-0 bar) due to a verifier infrastructure gap, not a substantive disagreement.

**Caveat:** the paper's measured "global cache sharing" finding is about *providers'* own caches (e.g. OpenAI's), not about a gateway sitting in front of them like Kelvran — the timing-side-channel *mechanism* is what transfers to Kelvran's threat model, not a claim that Kelvran's own cache was measured.

### 7. A per-user namespace token prepended to query text before embedding/hashing can be diluted to near-irrelevance for realistic-length queries, silently degrading tenant isolation to "hope similarity doesn't exceed threshold" (High confidence, narrowly scoped)

**What:** vllm-project/semantic-router's `ScopeQueryToUser` mitigation prepends an HMAC-derived namespace token, repeated three times, to the query text before it is embedded, intending to make each user's embeddings distinguishable. A maintainer-filed issue (#2134, merged fix PR #2135, both primary sources on a real, substantial open-source LLM-routing project with a real semantic cache) documents the flaw: for anything but very short queries, a 16-hex-character prefix (×3) is a tiny fraction of the total embedded text, so two users asking the same or similar question embed almost identically regardless of the namespace token — isolation degrades to "hope the embedding distance exceeds the threshold," which the issue's own analysis shows it does not reliably do. The fix replaced the diluted-token approach with a hard namespace-equality gate independent of embedding distance.

**Why it matters for Kelvran specifically:** this is a directly on-point, real "we thought we had tenant isolation via an embedding-space trick, and it degraded silently as query length grew" incident in a real LLM-routing product with a real semantic cache — precisely the kind of subtle failure Kelvran's L3-lite must avoid if it ever moves from pure lexical shingling toward real embeddings (named explicitly as future work in the sibling report). It is independent confirmation, from a different codebase and a different mechanism, of the same underlying principle KeyPooling's "survive every lookup and write" contract already established: tenant/user isolation must be a hard, structural partition (a separate index/namespace), never a soft signal (a token folded into the same similarity computation used for matching).

**Confidence:** High — primary GitHub issue + merged fix PR, both directly retrieved and cross-checked, unanimous 3-0.

**Caveat:** treat the specific numeric reproduction figures mentioned in the issue's own text (a cross-user cosine similarity of 0.9085 against an 0.8 deployed threshold) as descriptive color from the primary source, not as an independently re-confirmed exploit — a claim asserting this exact reproduction as the demonstrated vulnerability did not clear the 3-vote bar (1-2 split) in this pass, even though the broader structural-dilution claim above did clear it unanimously.

### 8. A documented meaning-reversing edit (negation/polarity flip) scores near the top of the observed similarity range and exceeds every commonly-deployed semantic-cache threshold surveyed — a concrete adversarial-paraphrase attack shape against fuzzy-match gates (Medium-High confidence)

**What:** A 2026 audit of cosine-similarity threshold gates (arXiv:2608.10216) found that a specific meaning-reversing edit to a drug-administration instruction — flipping "withhold the study drug" to "administer the study drug" — scored cosine similarity 0.9608 against the original. This single pair exceeded every one of five commonly-deployed operating thresholds the paper surveyed (0.30/0.40/0.80/0.85/0.95), meaning a real fuzzy-match cache gate at any of those thresholds (comparable to e.g. GPTCache's 0.7–0.8 or LangChain's 0.95 defaults) would treat this reversal as a near-duplicate/hit. The paper explicitly frames semantic caches, alongside deduplication filters, drift guards, and answer-grader gates, as the class of production mechanism relying on the assumption this finding challenges. This is independently corroborated by prior peer-reviewed work (Blagec et al. 2019, cited in the same paper) finding negation/antonym pairs scoring 0.93–0.999 across every sentence-embedding model tested — this is not a one-off cherry-pick but a recurring, cross-model phenomenon.

**Why it matters for Kelvran specifically:** this is the single most directly actionable adversarial-correctness finding in this report for Kelvran's L3-lite gate specifically. L3-lite's entity/number/date hard-gate defends against the case where entities/numbers/dates *themselves* differ, but a negation/polarity flip ("withhold" → "administer", "approved" → "not approved", "increase" → "decrease") may leave every entity, number, and date in a query byte-identical while completely reversing the correct answer — a Jaccard/shingle-based lexical similarity score would likely also score such a pair very highly, since only one or two tokens differ, and nothing in the described entity/date gate structurally catches a same-entities-different-polarity pair. This is a genuine, previously-unflagged gap distinct from anything the sibling cache report or Kelvran's own bug history identified.

**Confidence:** Medium-High — primary, recent (Aug 2026), methodologically detailed arXiv preprint, not yet peer-reviewed, but corroborated by an independent peer-reviewed 2019 source for the general phenomenon; the core numeric claim cleared 3-0.

**Caveat:** two adjacent, more sweeping claims from the same paper — that the audited system's gates caught *zero* of 56 meaning-breaking mutations, and that the paper explicitly names semantic caches by name as sharing this exact failure mode — were both explicitly refuted (0-3) in this pass's verification and must not be cited; only the specific 0.9608 negation-flip example and its corroboration by Blagec et al. are load-bearing here.

### 9. GroundedCache's own citation of adversarial collision attacks reinforces — but does not add new information beyond — the sibling report's existing CacheAttack finding (High confidence, explicitly non-novel)

**What:** GroundedCache (arXiv:2605.27494, already the subject of Finding 1 in the sibling `cache-2026-09-06.md` report) explicitly names "adversarial collision attacks" as one of three failure modes (alongside referent shift and retrieval drift) motivating its four-gate design, citing CacheAttack's up-to-86% response-hijacking rate via key-collision — the same CacheAttack paper the sibling report already covers in full (Finding 2 there).

**Why it matters for Kelvran specifically:** nothing new for Kelvran's cache-gate design — this is recorded here only to close the loop on this pass's own source material and to introduce one genuinely new detail the sibling report did not surface: GroundedCache names a *second* failure mode, "referent shift" (a cached answer's referent — e.g. which specific drug, patient, or account a pronoun/short-form reference resolves to — silently changing between the cached query and a new near-duplicate query), which is a distinct correctness risk from both adversarial collision and document drift and is not yet named anywhere in Kelvran's own threat model or bug history.

**Confidence:** High for the citation fact itself (3-0, primary source); the "referent shift" detail is a direct quote from the same primary source, not independently re-verified beyond that source.

**Caveat:** do not treat this finding as new evidence for the roadmap decisions already closed in the sibling report (per-gate ablation, hard-gate validation) — it is included solely to surface the "referent shift" failure mode as a candidate for a new eval scenario (see scenario 11 below), which the sibling report's own text did not enumerate.

### 10. Freshness/staleness exploitation is quantifiable and severe under naive semantic caching — a specific document-drift regime already named in the sibling report, re-confirmed here to anchor a concrete eval scenario (Medium confidence, explicitly overlapping)

**What:** Under GroundedCache's document-drift evaluation regime (re-issuing a prior query after the underlying retrieved source documents have been mutated), naive similarity-only semantic caching answers from cache 56.5% of the time with a wrong-cached-answer rate of 51.5%; GroundedCache's four-gate design answers from cache only 2.0% of the time, with a wrong-cached-answer rate of 1.5% — a 97.1% relative reduction.

**Why it matters for Kelvran specifically:** this exact 51.5%/1.5% figure already appears in the sibling `cache-2026-09-06.md` report's Finding 1 (quoted there as "51.5%... cut to 1.5%") — it is reproduced here not as new information but specifically because it is the cleanest available quantified real-number anchor for authoring a concrete freshness-exploitation eval case (a query whose correct answer changed after the underlying facts changed, served stale from cache), which the sibling report's roadmap-oriented framing did not translate into a case-authoring artifact.

**Confidence:** Medium — single, non-peer-reviewed arXiv preprint (3 months old at time of this pass), the figures come from the authors' own synthetic six-regime benchmark built to showcase their own method (not an independently audited benchmark or a real production incident), and the underlying scenario is RAG evidence-retrieval staleness rather than Kelvran's own hash/lexical gateway cache directly — cite as directly analogous, not as an attack proven against a system like Kelvran's.

### 11. A risk-constrained, per-tier staleness-probability budget is a materially different (and more portable) freshness-gating design than a flat TTL, and is new relative to both this pass and the sibling report (Medium confidence)

**What:** FreshCache (arXiv:2607.04281, Jul 2026) treats semantic-cache reuse as a risk-constrained temporal inference problem: rather than a flat TTL, it estimates the probability that a cached result is stale using a fitted exponential decay model enhanced by a learned MLP, and approves reuse only when that estimated staleness probability falls below a per-tier error budget — epsilon=0.10 for cached answers, epsilon=0.20 for cached URL lists, epsilon=0.35 for cached page content. Tiers with a higher cost-of-being-wrong (a final answer) get a tighter budget than tiers with a lower cost (raw page content that will still be further processed).

**Why it matters for Kelvran specifically:** this is a genuinely new design pattern relative to both this pass's other findings and the sibling report — it gives Kelvran's own "freshness/risk model" (already named in `THREAT_MODEL.md`'s Cache Elevation-of-Privilege row, already gating L3-lite hits) a concrete, portable structure: instead of (or alongside) a single age-based freshness threshold, different classes of cached content within the same cache could carry different acceptable-staleness-probability budgets, with the budget itself tied to the downstream cost of being wrong rather than to a single global TTL. This maps cleanly onto a future eval case: verify the freshness/risk model's actual behavior degrades staleness tolerance as a function of content criticality, not just entry age.

**Confidence:** Medium — single, non-peer-reviewed arXiv preprint (2 months old), but the descriptive/methodological claim (what the paper's design *is*) is fully supported by the primary source and cross-checked against independent mirrors; both component claims unanimous 3-0.

## Caveats

- **Refuted claims, explicitly not used:** three claims were refuted at the 3-vote bar and are excluded from every finding and scenario above: (1) the specific vllm-project/semantic-router bob/alice 0.9085-cosine reproduction as an independently-confirmed exploit (Finding 7's caveat addresses this directly); (2) the claim that the audited agent system's cosine gates caught 0 of 56 meaning-breaking mutations; (3) the claim that the same paper explicitly names semantic caches by name as sharing the meaning-reversal failure mode. All three came from sources otherwise used elsewhere in this report (Findings 7 and 8) — the refutation is scoped to the specific over-claim, not to the paper/issue as a whole.
- **Unverified claims (infrastructure errors, not content disputes):** four claims could not be confirmed or refuted because verifier agents errored on all attempts: a KeyPooling-style cross-tenant leakage claim about OpenRouter-pooled credentials (arXiv:2605.30613); a hubness-poisoning claim about embedding-retrieval "hub" items (arXiv:2602.22427); a GPTCache 37.9%-accuracy-on-agent-benchmarks claim (arXiv:2602.18922); and a claim asserting a documented vllm-project/semantic-router production vulnerability in general terms (overlapping with, but broader than, the confirmed Finding 7). None of these are used as evidence anywhere above; they are named here only so a future research pass knows they remain open, not settled either way.
- **Source-quality gradient:** the CVE/GHSA-sourced findings (1–5) are the strongest evidence in this report — primary, vendor-published, GitHub-reviewed, CVE-numbered advisories against real named products. The academic-paper-sourced findings (6, 8, 10, 11) are single, mostly non-peer-reviewed 2026 arXiv preprints (the timing side-channel paper, Finding 6, is the one peer-reviewed exception, ICML 2025) — treat their specific numbers as illustrative and methodologically sound, not as industry-audited consensus.
- **Time-sensitivity:** all CVEs cited are from 2026 (April–July), all still current relative to this report's date; all arXiv preprints are from May–August 2026. Nothing here is stale, but the academic papers in particular are recent enough that they have not yet accumulated independent citation/replication history.

## Concrete scenarios for case authoring

Fifteen specific, realistic adversarial or edge-case cache scenarios, organized by attack class, each with its real-world citation. These are written to be directly convertible into `EvalCase` `task_spec`/`reference` pairs testing Kelvran's real L1/L2/L3-lite cache-gating logic in a follow-on case-authoring pass — each names the concrete query/attack shape, not just the general category.

**Class 1 — Structural cache-key collision (exact-match layers, L1/L2)**

1. **Delimiter-injection key collision:** a request whose serialized parameters contain the cache key builder's own field-separator character(s) (e.g. a message field literally containing `&` or `|` sequences resembling key-value syntax) produces the same L1/L2 hash as a different, unrelated request whose parameters happen to canonicalize to the same string. *(ckan-mcp-server GHSA-78x9-fhhx-v2g6.)*
2. **Object/string type-ambiguity key collision:** a request field passed as a plain string that JSON-serializes indistinguishably from an equivalent object/array representation produces the same cache key as a semantically different request using the other representation. *(Same source, second confirmed PoC vector.)*
3. **Truncated-identifier key collision:** if any Kelvran cache-key component is ever derived from a prefix or truncated hash of a longer identifier (tenant ID, session token, idempotency key) rather than the identifier's full value or a full-strength hash, two distinct identifiers sharing that prefix must never collide to the same cache partition or served response. *(LiteLLM GHSA-jjhc-v7c2-5hh6, token[:20] OIDC cache collision → identity hijack.)*
4. **Prefix-only hash collision on long inputs:** two requests with long message histories or attached content (e.g. two different multi-turn conversations, or two different document/file `Parts`) that share an identical leading ~8KB but diverge materially afterward must not collide to the same cache key if any future Kelvran cache-key derivation ever hashes only a prefix of a large input for performance. *(GPTCache GHSA-xfqj-4cr9-9gr5 / CVE-2026-10812.)*

**Class 2 — Namespace/discriminator omission (tenant, user, permission-scope)**

5. **Missing-discriminator write path:** a regression/property test that walks every code path touching the cache (lookup, write, singleflight-coalesced write, retry, fallback) across at least two tenants and asserts the tenant-derived namespace component is present and correctly scoped on *every one* — directly modeled on the real Open WebUI failure where two specific cache keys (`tool_servers`, `terminal_servers`) were accidentally omitted from an otherwise-consistent namespacing scheme used everywhere else in the codebase. *(Open WebUI GHSA-3x8w-4f7p-xxc2 / CVE-2026-44552.)*
6. **Static-key decorator/helper regression:** if Kelvran ever wraps a cache-lookup helper in a decorator- or higher-order-function-based caching pattern, a test asserting that the cache key genuinely varies per distinguishing input (e.g. per user/tenant) rather than being silently evaluated once and reused as a constant — modeled on a real library-API misuse (`key=` vs a per-call `key_builder=`) that caused two permission-differentiated users to receive the identical shared cache entry within a short TTL window. *(Open WebUI GHSA-3wp3-xxj9-5jqq / CVE-2026-59213.)*
7. **Diluted namespace-token embedding collision:** if Kelvran's L3 ever adopts real embeddings with a token-based tenant-scoping mitigation (prepending a short per-tenant token to text before embedding), a long/realistic-length query from tenant A and a similarly-long query from tenant B asking a related question must not collide above the similarity threshold merely because the fixed-length namespace token becomes a smaller and smaller fraction of the total embedded text as query length grows. *(vllm-project/semantic-router issue #2134.)*

**Class 3 — Timing/existence side channels**

8. **Cache-hit timing side channel:** an attacker issuing a candidate query and measuring gateway response latency should not be able to reliably distinguish "this exact/near-duplicate query was already cached by another tenant" (fast response) from "this is genuinely novel" (slow response, real upstream call) — i.e., verify that hit/miss latency difference is bounded or normalized rather than leaking cross-tenant existence signal. *(Auditing Prompt Caching in Language Model APIs, arXiv:2502.07776, measured across seven real API providers including OpenAI.)*

**Class 4 — Adversarial paraphrase / meaning-flip near-duplicates**

9. **Negation/polarity-flip near-duplicate:** a query differing from a previously-cached query by a single negation or polarity-reversing edit (e.g. "withhold the study drug" vs. "administer the study drug"; "the refund was approved" vs. "the refund was not approved"; "increase the dosage" vs. "decrease the dosage") must not be served the original's cached answer even though lexical/Jaccard similarity would likely score the pair very highly, since the edit changes none of the entities, numbers, or dates the existing hard-gate checks. *(arXiv:2608.10216, 0.9608 cosine on the drug-administration example, exceeding every deployed threshold surveyed; corroborated by Blagec et al. 2019's 0.93–0.999 range for antonym/negation pairs.)*
10. **Referent-shift near-duplicate:** a query that is lexically near-identical to a cached query except for which specific entity a short-form/pronoun reference resolves to (e.g. "Is it safe for adults?" cached from a conversation about Drug X, then reused verbatim in a new conversation where "it" now refers to Drug Y) must not be served the original's cached answer merely because the surface text matches. *(GroundedCache, arXiv:2605.27494, "referent shift" named as a distinct failure mode from adversarial collision and document drift.)*
11. **Gradient/adversarial-suffix embedding collision (regression, not new-build):** a crafted query containing an adversarial suffix designed to force a lexical-shingle or (future) embedding-space match against a targeted victim query, while leaving the visible entities/numbers/dates unchanged from the attacker's actual intended (different) request, must still be rejected by the existing hard entity/date gate regardless of how high the underlying similarity score is. *(CacheAttack, arXiv:2601.23088, already named in the sibling report; included here as a directly testable regression case for the existing gate, not a new gap.)*

**Class 5 — Freshness/staleness exploitation**

12. **Document-drift stale reuse:** a query whose correct answer depends on an underlying fact that has since changed (e.g. "What is the current published rate for X?" asked once, cached, then the underlying source value changes, then the same or a near-duplicate query is asked again before the cache entry's freshness gate would reject it) must not be served the pre-change cached answer past the point the underlying fact changed. *(GroundedCache mtRAG document-drift regime: 51.5% wrong-cached-answer rate under naive caching vs. 1.5% under a four-gate design — already the quantified anchor in the sibling report, reused here specifically as a case-authoring seed.)*
13. **Tier-differentiated staleness-budget violation:** if Kelvran's freshness/risk model is ever extended to distinguish content criticality (e.g. a final synthesized answer vs. a raw retrieved snippet), a case verifying that the *same* elapsed age is treated as acceptable for a low-criticality tier but rejected for a high-criticality tier, rather than one flat age threshold applied uniformly regardless of what's being reused. *(FreshCache, arXiv:2607.04281, per-tier epsilon budgets of 0.10/0.20/0.35.)*

**Class 6 — Cross-instance/shared-backend poisoning (deployment-topology-specific)**

14. **Cross-instance config poisoning via missing namespace, full chain:** in a (currently-hypothetical, for Kelvran) shared-Redis-backend multi-instance deployment, an admin-level actor on one instance writes a malicious configuration value (analogous to Open WebUI's poisoned tool-server URL) under a cache key that is missing its instance/tenant discriminator; a second instance's users then read and act on the poisoned value, with downstream effects including sending sensitive request data to an attacker-controlled endpoint and receiving arbitrary attacker-controlled content back into their own request context. *(Open WebUI GHSA-3x8w-4f7p-xxc2 / CVE-2026-44552, full attack scenario — distinct from scenario 5's narrower "is the discriminator present" structural test.)*
15. **KeyPooling-contract violation test, generalized:** a single property-style test asserting the "survive every lookup and write" contract holds simultaneously across *all* of Kelvran's cache write/read paths for *all* discriminators that should be present (tenant, and any future user- or permission-scope-level discriminator), directly modeled on the fact that five separate real-world incidents in this report (Findings 1, 2, 3, 4, 7) each independently arose from exactly one discriminator being omitted or diluted on exactly one code path while the rest of the system correctly enforced it — i.e., the recurring real-world failure mode is *partial* correctness, not *total* absence of a namespacing scheme.
