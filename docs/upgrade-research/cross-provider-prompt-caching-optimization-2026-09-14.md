# Cross-Provider Prompt-Caching Optimization and Arbitrage — Deep Research (2026-09-14)

## Question

Going deeper than what's already shipped (`docs/rfcs/2026-09-07-gateway-provider-prompt-caching.md` + same-day tool-definition addendum, and `docs/rfcs/2026-09-07-gateway-cache-control-auto-populate.md` — automatic `cache_control`/`cachePoint` marker population for Anthropic/Bedrock, default-on, extended to tool definitions, with a `SharedAcrossTenants` cross-tenant-timing-leak override and real `CacheReadTokens`/`CacheCreationTokens` cost accounting): does Kelvran's routing layer have any real awareness of upstream cache warmth (research question 1, deferred to a sibling report — see Finding 3)? Does Kelvran's OpenAI adapter structure requests for automatic caching (question 2)? Does Kelvran's cost/savings accounting correctly handle per-provider minimum-cacheable-token thresholds (question 3)? Is there a validated 2026 pattern for cache-locality-aware instance routing, and does it conflict with Kelvran's fail-open/stateless design (question 4, deferred to the same sibling report)? What else would a 2026 survey of production prompt-caching optimization flag as a concrete, checkable gap (question 5)?

**Method:** 21 claims survived 3-vote adversarial verification against primary vendor sources (Anthropic, AWS Bedrock, OpenAI, Google Gemini/Vertex AI docs, all fetched live). This report merges semantic duplicates, cross-checks every claim against Kelvran's own current source (`gateway/internal/adapter/{anthropic,bedrock,openai}/*.go`, `gateway/internal/costaccounting/costaccounting.go`, `gateway/internal/router/router.go`), and states a build-now/not-yet call per finding. Research question 1 and 4 (routing awareness / cache-locality-aware instance routing) were already the subject of a dedicated, thorough prior pass — `docs/upgrade-research/cache-prompt-caching-aware-routing-2026-09-12.md` (20 claims, 3-vote verified, `not_yet` with two named triggers) — so this report does not re-litigate them; it cross-references that report's verdict and adds only what's new (the TTL/threshold mechanics that make the routing problem concrete). The most actionable output of this pass is not from the external claim set at all: a direct read of `gateway/internal/adapter/bedrock/bedrock.go` found a real, verified doc-vs-code gap in Kelvran's own already-shipped caching code (Finding 1).

---

## Executive summary

Every provider's prompt-caching mechanics are real, current (2026), and more heterogeneous than Kelvran's schema currently models in one place: Anthropic and Bedrock share a 5-minute-default/1-hour-opt-in TTL shape with per-model minimum-token thresholds (512–4,096 tokens), OpenAI has three different TTL regimes depending on model generation and retention tier (5–10 min, 30 min–24h, or a fixed 30-min-resetting window for GPT-5.6+) plus a hard 1,024-token minimum on GPT-5.6+ only, and Gemini has two entirely separate caching systems (automatic implicit caching with a 2,048–6,144-token model-tiered minimum and no documented TTL, versus an explicit, out-of-band `CachedContent` API with a 60-minute default TTL and no maximum bound) — confirming Kelvran's RFC was correct to exclude Gemini from the marker-based schema entirely, since Gemini has no request-level field for either mechanism. Kelvran's cost accounting is provably safe against the "assumes any marker implies eligibility" accuracy gap named in research question 3, because it is post-hoc — driven entirely by the provider's own reported `CacheReadTokens`/`CacheCreationTokens`, which providers themselves report as zero below their minimum threshold — not a predictive pre-call estimate; the gap only becomes real if Kelvran ever ships a pre-call savings estimator, which does not exist today. Research question 2 (OpenAI-specific prompt shaping) resolves to "not applicable by design": Kelvran's adapters are architecturally byte-faithful pass-throughs with zero message-reordering logic anywhere in the codebase, and actively reordering a caller's conversation content to front-load static text would violate the same "adapters are pure functions, never mutate or reorder" invariant the 2026-09-07 RFC's own byte-fidelity findings already rely on — this is correctly a `not_yet`/never-appropriate item, not an unexploited opportunity. The one concrete, validated, build-now-scale finding this pass surfaces that no prior report caught: Kelvran's own `bedrock.CachePoint{Type string}` struct has no `TTL` field and `bedrock.go` never reads `CacheControl.TTL` anywhere, directly contradicting the canonical `CacheControl.TTL` field's own doc comment ("Only Anthropic (direct, and Bedrock's Anthropic-family cachePoint) reads this") — a caller who sets `TTL: "1h"` on a Bedrock-routed request today gets it silently dropped, with no error, even though AWS's real Converse API genuinely supports `cachePoint: {type: "default", ttl: "5m"|"1h"}` for exactly the Claude model family Kelvran targets.

## Findings

### Finding 1 — A real, verified doc-vs-code gap: Bedrock's `CachePoint` never carries the caller-supplied `TTL`, contradicting the canonical field's own doc comment (confidence: high — direct code read + AWS primary docs)

AWS Bedrock's Converse API genuinely supports a caller-selectable `ttl` field on `cachePoint` (`5m` or `1h`) for a specific, named subset of Claude models (Sonnet 5/4.6/4.5, Opus 5/4.8/4.7/4.6/4.5, Haiku 4.5, and newer) — this is not a hypothetical extension, it is documented, current AWS API surface (`docs.aws.amazon.com/bedrock/latest/userguide/prompt-caching.html`), confirmed by AWS's own What's New announcement (2026-01-26) and API reference for `CachePointBlock`.

Kelvran's canonical `adapter.CacheControl.TTL` field's own doc comment (added in `docs/rfcs/2026-09-07-gateway-provider-prompt-caching.md`) states: *"Only Anthropic (direct, and Bedrock's Anthropic-family cachePoint) reads this."* Direct inspection of `gateway/internal/adapter/bedrock/bedrock.go` shows this is false as shipped:

```go
// gateway/internal/adapter/bedrock/bedrock.go:112-114
type CachePoint struct {
	Type string `json:"type"`
}
```

`CachePoint` has no `TTL` field at all, and `appendCachePointIfNeeded`/`appendSystemCachePointIfNeeded` (the only two constructors of a `CachePoint` value in the file) both hardcode `&CachePoint{Type: "default"}` unconditionally. A repo-wide check (`grep -n '\.TTL\b' gateway/internal/adapter/bedrock/*.go gateway/internal/adapter/anthropic/*.go`, excluding tests) confirms `cc.TTL` is read exactly once in the entire codebase — `anthropic.go:101` — and never in `bedrock.go`. A caller who sets `Message.CacheControl.TTL = "1h"` on a request routed to a Bedrock deployment gets it silently dropped: no error, no warning, and the resulting cache checkpoint always uses Bedrock's own 5-minute default, even though the caller explicitly asked for the 1-hour tier and the underlying AWS API would honor it if asked correctly.

This is a narrowly-scoped, well-understood fix: add `TTL string `json:"ttl,omitempty"`` to `bedrock.CachePoint`, and change the two hardcoded `&CachePoint{Type: "default"}` constructions to set `TTL: cc.TTL` (empty string omits the field, matching AWS's own "if not specified, defaults to 5 minutes" behavior) — gated, per AWS's own docs, to only emit `ttl` for the Claude-model subset that supports it (the same kind of per-model capability table the minimum-token-threshold findings below already establish AWS requires).

**Build now** — this is a real, verified regression against Kelvran's own documented design, not a speculative enhancement; the fix is small (one struct field, two call sites, a per-model capability check) and directly closes a gap between what the schema's own doc comment promises and what the code delivers.

### Finding 2 — Minimum-cacheable-token thresholds are real, provider- and model-specific, and vary by 2-8x within a single vendor's own model lineup — but Kelvran's cost accounting is already immune to the "assumes eligibility" accuracy gap by construction (confidence: high)

Every provider enforces a real, silent-no-error minimum token count below which a `cache_control`/`cachePoint` marker (or an automatic-caching model's own internal trigger) simply does not engage:

| Provider | Minimum threshold | Varies by |
|---|---|---|
| **Anthropic** | 512 tokens (Claude Opus 5/Fable 5.1 family) to 4,096 tokens (Haiku 4.5); Sonnet 5 specifically = 1,024 | Model tier |
| **Bedrock** | 512 tokens (Opus 5) to 4,096 tokens (Haiku 4.5); GPT-5.6 models hosted on Bedrock = 1,024 | Model, cumulative across `tools → system → messages` |
| **OpenAI** | 1,024 tokens hard minimum for GPT-5.6+; variable (1,024–2,048, depends on tools/images/output schema/reasoning effort/verbosity) for earlier models | Model generation + request shape |
| **Gemini implicit** | 2,048 tokens (2.5 Flash/Pro) to 6,144 tokens (3.0/3.1/3.7/3.8 Flash-tier previews); 4,096 for the general Gemini 3 family | Model generation |

In every case, a request below the threshold succeeds normally with **no error**, and the provider's own usage response reports the cache-token fields as genuinely zero (`cache_creation_input_tokens`/`cache_read_input_tokens` = 0 for Anthropic; Bedrock's cache-write/cache-read fields likewise; OpenAI's `cached_tokens` = 0) rather than raising any signal that a marker was ignored.

Direct inspection of `gateway/internal/costaccounting/costaccounting.go` confirms Kelvran's cost/savings accounting is **not** exposed to the "any `cache_control` marker implies eligibility" failure mode research question 3 asks about, because it never makes that assumption in the first place — it derives cache cost entirely from `usage.CacheReadTokens`/`usage.CacheCreationTokens`, the provider's own post-hoc reported values (`Calculate`, lines ~94-101), with an explicit defensive fallback (lines 94-98) that zeroes both fields out entirely if they're negative or their sum exceeds `PromptTokens` — i.e. the code already treats provider-reported cache usage as the sole source of truth, never Kelvran's own guess about whether a marker "should have" produced a cache write/read. Since every provider reports zero cache tokens for a sub-threshold request, Kelvran's existing accounting already, correctly, attributes zero cache savings to that request — with no threshold-awareness code needed at all. A further repo-wide check (`grep -rn -i estimat gateway/internal/costaccounting gateway/internal/cache`) confirms Kelvran has no pre-call, predictive cost/savings estimator anywhere today (the only "estimate" logic in the codebase, `JaccardEstimate`, belongs to the unrelated L3 lexical semantic-cache, not provider prompt caching) — so there is no code path where a threshold-unaware savings claim could currently be surfaced to an operator or client.

**Not yet** — there is no accuracy gap in what Kelvran ships today; the gap research question 3 anticipates only becomes real if Kelvran ever builds a pre-call/predictive cache-savings estimator (e.g., a dry-run cost projection feature), at which point that estimator would need this per-model threshold table to avoid over-promising savings on short requests. Trigger: a concrete product requirement for pre-call cost estimation or a "would this request be cache-eligible" dry-run endpoint.

### Finding 3 — Cross-instance/cross-region cache-locality loss is real and AWS-documented, and Kelvran's WRR router has zero locality awareness — but this is already a dedicated, deeply-researched `not_yet` finding in a sibling report (confidence: high, deferring verdict)

AWS's own Bedrock docs state plainly that cross-region inference — automatic routing to whichever region has capacity — "may lead to increased cache writes" under high demand, i.e. it can and does route a request away from the region holding its warm cache. This is real, vendor-acknowledged behavior, not a theoretical edge case, and it is structurally the same failure mode as Kelvran's own weighted-round-robin router: a direct read of `gateway/internal/router/router.go` confirms `Router.Select` groups deployments strictly `byModel` (canonical model name → list of weighted deployments) and performs smooth weighted round-robin with health-based skipping — there is no session, conversation, or prefix-affinity concept anywhere in the type or its selection logic. Two back-to-back requests sharing an identical long system prompt, routed to two different same-model deployment replicas, would each pay a full cache-creation charge on the upstream provider instead of the second one getting a cache-read discount.

This exact scenario, its production precedent (LiteLLM's three independently-shipped fixes, OpenRouter's default sticky routing, AWS SageMaker's `PREFIX_AWARE` strategy), the two real mechanism families (stateless prefix-hash routing vs. stateful session affinity), and the fail-open/stateless design tension research question 4 asks about were already the subject of a dedicated prior deep-research pass: `docs/upgrade-research/cache-prompt-caching-aware-routing-2026-09-12.md`. That report's verdict — **not_yet**, gated on two concrete triggers (real production traffic demonstrating measurable cache-locality cost, or a second concrete signal named in that report) rather than "more data" in the abstract — stands unchanged by this pass's findings. This report adds no new evidence that would move that verdict; it only confirms, via the TTL/threshold mechanics above, that the underlying provider behavior driving the problem (short cache windows, model-specific eligibility, and AWS's own documented cross-region cache-defeat) is real and current as of 2026-09-14, not stale.

**Not yet** (unchanged from the 2026-09-12 report) — see that report for the full build-now/not-yet analysis and named triggers; this pass does not re-open it.

### Finding 4 — OpenAI's own "static content first" guidance is real and provider-endorsed, but is not a gap in Kelvran — Kelvran's adapters are architecturally byte-faithful pass-throughs with no message-reordering logic anywhere (confidence: high)

OpenAI's current documentation explicitly recommends structuring prompts with stable/shared content first and dynamic/user-specific content last, specifically to preserve a stable prefix for its own automatic caching — this is real, current, provider-first-party guidance, not folklore. Google's Gemini docs independently confirm the identical principle for implicit caching ("try putting large and common contents at the beginning of your prompt").

However, a direct check of Kelvran's OpenAI adapter (`gateway/internal/adapter/openai/openai.go`) finds no message-reordering, sorting, or content-restructuring logic of any kind — a targeted grep for `sort`/`reorder`/`order` inside the adapter returns nothing, consistent with the 2026-09-07 research pass's own byte-fidelity finding that `normalizeMessages` operates on a copy and every adapter's `ToProvider` is a byte-faithful translation of whatever the client actually sent. This is not an oversight: `gateway/internal/adapter/types.go`'s own doc comment requires adapters to be "pure functions: no network calls, no hidden state beyond what's passed in," and reordering a caller's conversation content — even in service of cache-friendliness — would be a semantic mutation of message order that risks breaking tool-call sequencing, conversation meaning, or client expectations about response correlation to specific turns. The "put static content first" lever is real, but it is the **calling client's** responsibility to structure its own prompt correctly (exactly as it would be calling OpenAI directly, with no gateway in between) — Kelvran forwarding the client's own byte-exact ordering is the correct behavior, not a missed optimization.

**Not applicable / never-appropriate-here**, not simply `not_yet` — this is not a capability gated on a future trigger; it is a deliberate architectural boundary (adapters as pure, non-mutating functions) that this research confirms is correctly upheld today, and building automatic content-reordering would work against that boundary rather than complete it.

### Finding 5 — Gemini's exclusion from the 2026-09-07 RFC's marker-based schema is fully validated by current (2026-09-14) provider documentation; no action needed (confidence: high)

The original RFC excluded Gemini from `CacheControl` entirely, reasoning that Gemini has no request-level field for either of its two caching mechanisms. This pass's independent re-verification against Google's current docs confirms that reasoning holds, and sharpens it: Gemini implicit caching is fully automatic, default-on for Gemini 2.5+ models, requires no marker of any kind, and carries no cost-savings guarantee (Google's own docs candidly disclose this — "no cost saving guarantee"); Gemini explicit caching is a wholly separate, out-of-band `CachedContent` object created via its own API call (`client.caches.create()`) with a distinct 60-minute default TTL and no documented maximum bound, referenced by a later `generate_content` call via a returned name rather than any per-request marker on the content being cached. Neither mechanism has anything resembling Anthropic's `cache_control` or Bedrock's `cachePoint` for a marker-based schema to attach to. One caveat surfaced in adversarial verification: a claim asserting Gemini's implicit caching gives "a 90% discount... with no storage cost, directly analogous to OpenAI's automatic caching" was refuted (1-2 vote) — the discount percentage and no-storage-cost framing are not confirmed by the primary source for implicit caching specifically (only "we automatically pass on cost savings," no percentage stated); do not treat that specific figure as validated.

**No action needed** — this finding validates an already-shipped design decision rather than surfacing new work.

## Direct answers to the five research questions

1. **Routing awareness of upstream cache warmth:** No — `Router.Select` groups purely `byModel`, with zero session/prefix-affinity logic, confirmed by direct code read. This is a real, model-level-only WRR gap, but it is the exact subject of `docs/upgrade-research/cache-prompt-caching-aware-routing-2026-09-12.md`, whose `not_yet` verdict and named triggers stand unchanged (Finding 3 above).
2. **OpenAI-specific prompt shaping:** Kelvran does nothing special, by design — no reordering logic exists in any adapter, and adding any would violate the adapters'-are-pure-functions architectural invariant. Not a missed opportunity; the responsibility correctly sits with the calling client (Finding 4).
3. **Minimum cacheable prefix length and cost-accounting accuracy:** Real, model-specific thresholds exist for all four providers (512–6,144 tokens depending on provider/model), but Kelvran's cost accounting is immune to the feared accuracy gap today because it is post-hoc and driven entirely by provider-reported usage fields, not a predictive assumption (Finding 2). The gap becomes real only if a pre-call estimator is ever built.
4. **Cache-locality-aware instance routing pattern:** A real, validated 2026 pattern exists (LiteLLM's three shipped fixes, OpenRouter's default sticky routing, AWS SageMaker's `PREFIX_AWARE`), and it would indeed sit in tension with a hard-stateless fail-open design — but this is fully covered by the sibling 2026-09-12 report, whose `not_yet` verdict this pass does not disturb (Finding 3).
5. **Anything else a 2026 survey would flag:** Yes — a real, verified, build-now-scale gap: Kelvran's Bedrock adapter silently drops a caller's `CacheControl.TTL` instead of forwarding it to AWS's real `cachePoint.ttl` field, contradicting the canonical field's own doc comment (Finding 1). This was found by direct code inspection during this research pass, not by the external adversarial-claim panel.

## Caveats

- Finding 1 (the Bedrock TTL wiring gap) is an author-verified code finding from this research session, not one of the 21 adversarially-voted claims — it is grounded in a direct read of `gateway/internal/adapter/bedrock/bedrock.go` and AWS's primary docs, but did not go through the 3-vote panel process the other findings did. It should be spot-checked against the current file (line numbers may drift as the codebase changes) before acting on it.
- Two claims were refuted during adversarial verification and are explicitly excluded from this report's findings: (a) that Bedrock's 1-hour TTL is restricted to only three specific Claude model families (the real model list is broader and growing); (b) that Gemini implicit caching gives a flat 90% discount with no storage cost, directly analogous to OpenAI (not confirmed for implicit caching specifically — only explicit caching's separate storage-billing mechanics are documented with concrete numbers). Do not cite either figure as validated.
- All per-model token thresholds and TTL figures are current as of live fetches on 2026-09-14; every provider has changed these figures within 2026 already (Bedrock's 1-hour TTL only shipped 2026-01-26; OpenAI's GPT-5.6 tier shipped 2026-07-09) — treat any of these numbers as subject to change on a provider's own roadmap, not as permanent constants to hardcode without a re-check cadence.
- Research questions 1 and 4 are deliberately not re-researched in depth here; this report defers entirely to `docs/upgrade-research/cache-prompt-caching-aware-routing-2026-09-12.md` for those two questions rather than duplicating that report's own (already thorough, already 3-vote-verified) analysis.
- No real production traffic exists yet for Kelvran (repeated caveat from every prior prompt-caching research pass in this repo) — every "not_yet" verdict above is gated on triggers that require production-scale evidence Kelvran does not yet have, not on any technical blocker.

## Open questions

- Should Bedrock's `cachePoint.ttl` support (Finding 1's fix) be gated to only the specific Claude model subset AWS documents as supporting it, or should Kelvran forward it unconditionally and let AWS's own API reject/ignore an unsupported value — i.e., does Kelvran's adapter need its own per-model capability table for this, mirroring the minimum-token-threshold tables in Finding 2, or can it rely on AWS's own validation?
- Should OpenAI's `prompt_cache_key` (already wired per the original RFC, caller-supplied only via `CacheControl.Key`) ever be auto-populated from Kelvran's own stable tenant/virtual-key identity, the way the 2026-09-07 RFC's own "Alternatives Considered" section named as a legitimate, smaller, complementary future extension distinct from that RFC's scope — and would that require the same "thread identity through the adapter interface" architectural change that RFC explicitly deferred?
- Does AWS's documented cross-region-inference cache-defeat behavior (Finding 3) interact with Kelvran's own multi-region DR plans (`docs/upgrade-research/gateway-multiregion-dr-2026-09-13.md`)? Neither report currently cross-references the other, and a future multi-region Kelvran deployment could compound both problems (Kelvran's own WRR spreading a conversation across replicas, and AWS's own cross-region inference spreading it further within a single replica's calls).
- Real measured cache-hit-rate and cost impact from any of this remains unmeasurable today — the same caveat every prior prompt-caching RFC and research pass in this repo has already named repeatedly, for the same reason (no production traffic exists yet).
