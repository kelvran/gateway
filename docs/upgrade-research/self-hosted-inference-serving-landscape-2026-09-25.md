# Self-Hosted Inference-Serving Landscape — Queue-Depth, Speculative Decoding, KV-Cache Coordination (2026-09-25 Refresh)

**Date:** 2026-09-25
**Scope:** `gateway/internal/router/` (`router.go`'s and `health.go`'s already-shipped `SetLatencyFactor`/`activeCostTier` mechanisms) and `gateway/internal/adapter/openaicompat/` (the generic self-hosted-backend adapter targeting vLLM, SGLang, TGI, Ollama, llama.cpp, LocalAI) — specifically the router's own already-named, deliberately-deferred future work: scraping an upstream engine's own `/metrics` Prometheus endpoint for a true queue-depth signal, instead of the currently-shipped soft latency-de-weighting derived from active health-probe timing alone (`router.go`'s 2026-09-24 correction; `gateway/ARCHITECTURE.md`'s adapter section, added 2026-09-23). Excludes the deepest KV-cache-coordination tier (precise KV-cache-event-driven prefix-cache routing, disaggregated prefill/decode orchestration) — `gateway/ARCHITECTURE.md` already places that tier out of scope, one architectural layer down, in dedicated sidecar/ext-proc systems.
**Method:** Adversarial multi-source research (3-vote verification per claim) against primary sources only — vLLM's, SGLang's, TGI's (Hugging Face), and Ollama's own docs, GitHub repositories, merged/open pull requests, and live source code, cross-checked via `gh api`/`gh search` where a claim rested on a PR or repo-metadata assertion rather than a docs page. 12 claims survived 3-vote adversarial verification; 13 near-duplicate, overreaching, or already-covered claims were explicitly refuted in the same pass (listed for transparency in Caveats). This document adds the Kelvran-specific "is this actually new relative to `router.go`/`health.go`'s own doc comments and `gateway/ARCHITECTURE.md`'s already-drawn scope boundary" judgment layer the raw adversarial verification deliberately does not do — mirroring `docs/upgrade-research/gateway-2026-09-06.md`'s own stated convention.

---

## Executive summary

Of the four named engines, only vLLM produced genuinely new findings relative to Kelvran's own already-documented scope boundary — and the single most consequential one is that vLLM v0.29.0 (merged 2026-08-31) now ships a synchronous, in-process admission-control mechanism (`--max-num-queued-reqs`/`--max-num-queued-tokens`) that self-rejects overloaded requests with HTTP 503 before they ever enter the engine, giving Kelvran's router a real, already-wire-visible overload signal that needs no `/metrics` scrape at all. A second, separately-merged (2026-08-20) vLLM feature puts per-request speculative-decoding acceptance stats directly in the OpenAI-compatible response body (opt-in, off by default) — this corrects Kelvran's own prior "zero wire-visible signal" verdict on speculative decoding, which was accurate when written (2026-09-22) but is now, at six weeks old, stale for this one specific opt-in path. vLLM's `/metrics` endpoint itself remains richer in scraping detail than previously catalogued (a by-reason queue-depth breakdown, per-position speculative-decoding acceptance counters, NIXL disaggregated-KV-transfer histograms), but this only refines, not expands, the deferred-future-work scope Kelvran already named — a near-duplicate claim asserting vLLM's aggregate `vllm:num_requests_waiting` gauge itself was a *new* finding was independently re-checked and explicitly refuted, since `gateway/ARCHITECTURE.md` already cites that exact metric name verbatim. TGI is now archived (since 2026-03-21, ~6 months frozen as of this research date) and should be deprioritized as an active "what's new" target; Ollama — also a named `openaicompat` runtime — still ships zero native Prometheus metrics today, with its two competing, unmerged proposals split on whether queue-depth is even included in the design. SGLang produced zero surviving claims of any kind after adversarial verification and remains a genuinely open question, not a "no." Finally, real production cross-replica KV-cache coordination (Mooncake Store, NIXL) is confirmed to exist and to work exactly the way Kelvran's own scope boundary already assumes — as a dedicated layer beside the inference engine — reinforcing, rather than expanding, the already-drawn "one architectural layer down" line.

## Findings, ranked

### 1. vLLM's own admission-control rejection (HTTP 503) is a real, wire-visible overload signal that needs no `/metrics` scrape at all (Medium)

**What:** vLLM v0.29.0 (PR #49445, merged 2026-08-31) added two admission-control flags — `--max-num-queued-reqs` and `--max-num-queued-tokens` — checked synchronously in `AsyncLLM.add_request` before a request enters the engine. When exceeded, the request is rejected with a plain HTTP 503 (Service Unavailable). The signal driving this check is not a metrics scrape or an IPC round-trip: it comes from the `OutputProcessor`'s own existing in-process `request_states`/`is_prefiling` tracking — a pure in-process dict scan (`get_num_queued_tokens()` sums `req.prompt_len` for every request where `is_prefilling` is true), confirmed against the actual diff, which touches zero Prometheus/metrics source files.

**Why it matters for Kelvran specifically:** this is a genuinely new, low-effort alternative to the heavier "scrape `/metrics` for a queue-depth number" path `gateway/ARCHITECTURE.md` already names as future work. Kelvran's `dataplane.Pipeline` already sees every upstream HTTP status code on the request path today — a 503 from an `openaicompat` backend running vLLM ≥0.29.0 (with these flags enabled) is a real-time, per-request overload signal Kelvran can react to (e.g. feed into the existing `SetLatencyFactor` de-weighting mechanism, or trigger `ReportProbeResult`-style unhealthy marking) without building any Prometheus client, scraper, or new I/O dependency inside `router` at all.

**Consistent with settled decisions?** Complementary to, not a reopening of, the deferred `/metrics`-scraping RFC named in `gateway/ARCHITECTURE.md` (added 2026-09-23) — that RFC is about a *pre-filter* signal fed into the same latency-de-weighting mechanism `SetLatencyFactor` already implements (per `health.go`'s own doc comment: "Callers (dataplane's health probe loop) compute this from each deployment's own rolling-average probe latency... this method has no opinion on how the percentage was derived"). A 503-driven signal is a different, cheaper input into that same existing mechanism, not a new mechanism of its own — `router` package boundaries (adapter-agnostic, I/O-free; see `router.go`'s own package doc comment) are untouched either way, since `dataplane` already owns response-status handling.

**2026 best practice grounding:**
- vLLM PR #49445's own body, verified live via `gh api`/`gh pr view` (not a secondary blog): "Two independent admission control flags, checked synchronously in `AsyncLLM.add_request` before the request enters the engine... When exceeded, requests are rejected with HTTP 503 (Service Unavailable)." Shipped in the v0.29.0 release (published 2026-09-09) [github.com/vllm-project/vllm/pull/49445 — confirmed 3-0].
- The queued-token/queued-request count itself comes from the `OutputProcessor`'s existing in-process state, not a metrics/Prometheus code path — confirmed against the real file diff (18 files, none in `vllm/v1/metrics/`) and the actual patch (`get_num_queued_tokens()`'s in-process dict scan). The PR author's own post-merge comment ("we don't have metrics right now which is the biggest observability signal we need") independently corroborates that no metrics-endpoint exposure of this signal exists yet [github.com/vllm-project/vllm/pull/49445 — confirmed 3-0].

**Concrete next step:** a bounded design note (not a build) on whether `dataplane.Pipeline` should treat a 503 from an `openaicompat` deployment as an input to `router.SetLatencyFactor`/health-probe state — distinct from, and cheaper than, the already-named `/metrics`-scraping RFC, and worth writing before that heavier RFC, not instead of it, since it only fires once an operator is already overloaded rather than pre-emptively load-balancing away from rising queue depth.

**Effort:** Medium — no new external dependency; reuses `dataplane`'s existing response-handling and `router`'s existing `SetLatencyFactor` entry point. The flags themselves are an operator-side vLLM config change with zero code changes to Kelvran to start observing them.

### 2. vLLM's per-request speculative-decoding acceptance stats are now wire-visible in the OpenAI-compatible response body — corrects Kelvran's own six-week-old "not applicable" verdict (Small)

**What:** vLLM PR #48915 ("[Frontend][Core][Spec Decode] Per-request acceptance stats in OpenAI API responses"), merged 2026-08-20, adds a `metrics.speculative_decoding` object (fields: `mean_acceptance_length`, `draft_acceptance_rate`, `acceptance_histogram`, `num_spec_steps`, `num_accepted_draft_tokens`, `num_draft_tokens`, `num_spec_tokens`) directly to the OpenAI-compatible chat-completion response, gated behind a server-startup flag (`--per-request-spec-decode-metrics summary`/`detailed`), off by default — when off, the response is byte-identical to today.

**Why it matters for Kelvran specifically:** `gateway/ARCHITECTURE.md`'s adapter section (added 2026-09-23, citing `docs/upgrade-research/self-hosted-inference-server-integration-depth-2026-09-22.md`) resolves token-level speculative decoding to **NOT APPLICABLE** for router coordination specifically because "the client-facing response is identical whether or not the backend used it internally, so there is nothing for this router to coordinate on" — a verdict that report's own Finding 4 states as "zero wire-visible signal." That verdict was accurate when written (2026-09-22) but PR #48915 had already merged a month earlier (2026-08-20); the 2026-09-22 report's own research pass appears to have missed this already-shipped, if opt-in and low-visibility, feature. This does not overturn the NOT_APPLICABLE verdict's practical conclusion (the feature is off by default, and no Kelvran code today reads or forwards it), but the doc's absolute "zero wire-visible signal" framing is now inaccurate for this one specific, opt-in vLLM path and should be corrected rather than silently left stale.

**Consistent with settled decisions?** A correction to, not a reopening of, `gateway/ARCHITECTURE.md`'s existing NOT_APPLICABLE verdict — the underlying reasoning (no gateway-facing surface for engine-internal speculative decoding, as a *general* engine-configuration concern) still holds for SGLang and for vLLM when the flag is unset; only the specific "zero wire-visible signal, full stop" phrasing needs a footnote naming this one opt-in exception.

**2026 best practice grounding:**
- vLLM PR #48915, verified via `mcp__plugin_github_github__pull_request_read` directly against the GitHub API (state=closed, merged=true, merged 2026-08-20, merged by WoosukKwon, a genuine senior vLLM maintainer; 798 additions/76 deletions across 25 files, 6 commits, E2E-tested on real H100 hardware). PR body verbatim: "Today you can only see this as a server-wide average on `/metrics`. You can't tell how any single request did... This PR reports it in the response. It's off by default; turn it on at server start with `--per-request-spec-decode-metrics summary` (or `detailed`). When it's off, the response is unchanged." [github.com/vllm-project/vllm/pull/48915 — confirmed 3-0].

**Concrete next step:** a one-paragraph doc correction to `gateway/ARCHITECTURE.md`'s router section (mirroring the prior report's own recommended pattern for scope-boundary notes): name PR #48915 as a real, opt-in exception to the "zero wire-visible signal" framing, without changing the underlying NOT_APPLICABLE-for-routing-coordination conclusion, since the feature is off by default and no Kelvran adapter reads or forwards `metrics.speculative_decoding` today.

**Effort:** Small — a documentation correction only; no code change is implied unless Kelvran later decides to surface `metrics.speculative_decoding` through its own API, which is a separate, unscoped question this finding does not answer.

### 3. vLLM's `/metrics` catalog is richer than a single scalar gauge — refines, but does not expand, the already-deferred scraping target (Small, cluster)

**What:** Three related, narrower vLLM `/metrics` findings, all confirmed against the live docs and source code:
- `vllm:num_requests_waiting_by_reason` (Gauge) breaks the aggregate `vllm:num_requests_waiting` queue-depth gauge down by cause (e.g. a `capacity` label for requests waiting on scheduling capacity, `deferred` for transient constraints like LoRA budget/KV transfer/blocked status) — per-reason values sum to the aggregate.
- `vllm:spec_decode_num_accepted_tokens_per_pos` (Counter) — a dedicated "Speculative Decoding Metrics" table entry tracking accepted draft tokens per speculative position, on the `/metrics` endpoint (distinct from Finding 2's per-request, opt-in, response-body signal).
- A "NIXL KV Connector Metrics" table (`vllm:nixl_xfer_time_seconds` histogram, plus `vllm:nixl_num_failed_transfers`/`vllm:nixl_num_failed_notifications` counters) tracking KV-cache transfer duration and failures between disaggregated prefill/decode replicas.

**Why it matters for Kelvran specifically:** these add real implementation detail for whenever Kelvran's already-named, deliberately-deferred `/metrics`-scraping RFC (Finding 1's design note, above, or a heavier follow-on) actually gets written — a more granular `capacity`-reason breakdown is a better pre-filter input than the bare aggregate gauge already cited in `gateway/ARCHITECTURE.md`, and the speculative-decoding/NIXL counters are additional health signals beyond pure queue depth. None of this changes the scope-boundary verdict itself: the aggregate gauge's mere existence is not new information (see below), and the deepest KV-cache-coordination tier NIXL's metrics describe remains correctly out of scope per Finding 6.

**Consistent with settled decisions?** A near-duplicate claim asserting that vLLM's `/metrics` endpoint already exposes `vllm:num_requests_waiting` as "exactly the upstream engine's own `/metrics` Prometheus endpoint queue-depth signal that Kelvran's router names as deferred future work" was explicitly **refuted 0-3** during this same adversarial pass — correctly, since `gateway/ARCHITECTURE.md` (added 2026-09-23) already cites `vllm:num_requests_waiting`/`vllm:kv_cache_usage_perc` by name. The three items above are additive detail on top of an already-known metric family, not a newly-discovered category.

**2026 best practice grounding:**
- `vllm:num_requests_waiting_by_reason`'s docstring, confirmed against both vLLM's own docs and its live source (`vllm/v1/metrics/loggers.py`): "Sum of all reasons equals `vllm:num_requests_waiting`." [docs.vllm.ai/en/latest/usage/metrics/ — confirmed 3-0].
- `vllm:spec_decode_num_accepted_tokens_per_pos`, confirmed against the docs table and `vllm/v1/spec_decode/metrics.py`'s actual `Counter` instantiation (per-position, incremented from `spec_decoding_stats.num_accepted_tokens_per_pos[pos]`) — this metric's core implementation dates to PR #24127 (merged 2025-09-11), i.e. roughly a year old, not itself new, though a doc/PromQL-example fix landed as recently as 2026-09-14 [docs.vllm.ai — confirmed 3-0].
- NIXL KV Connector Metrics, confirmed against both the docs table and the `NixlPromMetrics` class in `vllm/distributed/kv_transfer/kv_connector/v1/nixl/stats.py` [docs.vllm.ai — confirmed 3-0].

**Concrete next step:** fold the `capacity`-reason breakdown and the NIXL failure counters into the scope/design section of Kelvran's already-named `/metrics`-scraping RFC when it is eventually written; no immediate action.

**Effort:** N/A now — a Small addition to a not-yet-written RFC's scope, not a standalone build item.

### 4. Ollama — a named `openaicompat` target — ships zero native Prometheus metrics today, and even the leading unmerged proposal omits queue-depth (Small)

**What:** As of this research date, Ollama has no shipped `/metrics` endpoint of any kind. The most recent proposal, PR #18508 (open, unmerged, created 2026-09-17), gates the entire feature behind an `OLLAMA_METRICS` environment variable, off by default, with a documented zero-runtime-cost-when-unset design (nil-pointer no-op counters). Critically, per the PR author's own side-by-side comparison table, PR #18508 itself ships **no** scheduler/queue-depth metrics ("scheduler metrics | queued requests, queue capacity, loaded models, peak memory | none") — that data exists only in a separate, also-unmerged, competing proposal, PR #16998 (open since 2026-07-01), which defines `ollama_requests_queued` and `ollama_queue_capacity` gauges. An umbrella tracking issue (#3144) for a `/metrics` endpoint remains open.

**Why it matters for Kelvran specifically:** Ollama is a named `openaicompat` target (`docs/rfcs/2026-09-04-openaicompat-adapter.md`'s own list: "vLLM, Ollama, TGI, llama.cpp, LocalAI"), so any future `/metrics`-scraping design must account for the fact that Ollama, unlike vLLM, currently offers nothing to scrape at all — and even once a metrics endpoint ships, queue-depth specifically is not guaranteed to be part of it, since the two competing PRs disagree on that point. This is genuinely new information not covered by Kelvran's existing scope-boundary text, which names vLLM/SGLang/TGI/llama.cpp's telemetry but does not currently address Ollama's metrics posture at all.

**Consistent with settled decisions?** Narrows, rather than reopens, the deferred `/metrics`-scraping future work — confirms that any such RFC would need an explicit "Ollama has no signal to scrape yet" carve-out, or a fallback to Kelvran's own existing active-probe latency mechanism for that one runtime specifically, rather than assuming feature parity across all five `openaicompat` targets.

**2026 best practice grounding:**
- PR #18508's body, verified live via `gh api` (state=open, merged=false, created 2026-09-17): "Off by default. The route only exists when `OLLAMA_METRICS` is set. When it is unset the counters are a nil pointer whose methods return immediately, so the inference path pays nothing for a feature nobody asked for." [github.com/ollama/ollama/pull/18508 — confirmed 3-0].
- The same PR's own comparison table and a direct diff of PR #16998, both confirmed live: `scheduler metrics | queued requests, queue capacity, loaded models, peak memory | none` for #18508; `ollama_requests_queued`/`ollama_queue_capacity` gauges genuinely present only in #16998's diff. Both PRs independently confirmed still open/unmerged as of this research date [github.com/ollama/ollama/pull/18508, github.com/ollama/ollama/pull/16998 — confirmed 3-0].

**Concrete next step:** none urgent — track both PRs (#18508, #16998) and issue #3144; revisit Ollama's specific carve-out in the `/metrics`-scraping RFC once either merges, since the shape of what becomes scrapable is still genuinely undecided upstream.

**Effort:** N/A — tracking only; nothing to build against a moving, unmerged upstream target.

### 6. Cross-replica KV-cache coordination (Mooncake Store, NIXL) is real and production-proven — and confirms, rather than expands, Kelvran's own already-drawn architectural boundary (Confirmatory — no action)

**What:** Multiple vLLM instances can embed Mooncake clients that share a single, cluster-wide Mooncake Store — turning what would otherwise be isolated per-instance KV caches into a shared, cluster-level pool, cutting redundant prefill computation for repeated-prefix (agentic/multi-turn) workloads across replicas. This sits alongside, and is chained via `MultiConnector` with, vLLM's pre-existing `MooncakeConnector` for prefill/decode (PD) disaggregation (shipped ~Feb–Mar 2026, well before this Mooncake Store integration).

**Why it matters for Kelvran specifically:** this is exactly the "KV-cache coordination across replicas" mechanism the research question named — and it is real, live, and production-oriented. But `gateway/ARCHITECTURE.md`'s adapter section (added 2026-09-23) already, explicitly, places this entire class of mechanism out of scope for Kelvran's own router: "The deepest coordination tier for this signal (precise KV-cache-event-driven prefix-cache routing, disaggregated prefill/decode orchestration) is deliberately out of scope — that tier is real and production-proven, but lives one architectural layer down, in dedicated sidecar/ext-proc systems... that Kelvran's own single-process, provider-agnostic shape was never designed to replicate." Mooncake Store/`MooncakeConnector` is a second, concrete real-world instance of exactly that already-named class of system (alongside the doc's existing Gateway API Inference Extension/llm-d example) — it reinforces the existing boundary rather than identifying anything Kelvran's router itself should now do differently.

**Consistent with settled decisions?** Fully consistent — no revisit needed. Several closely related claims covering the same ground (Mooncake's disaggregated prefill/decode clustering, LMCache's engine-independent daemon architecture and pluggable storage backends, llm-d's globally-indexed KV-cache view and hierarchical-offloading benchmarks) were explicitly **refuted** (0-3 or 1-2 votes) during this same adversarial pass on the grounds that they restate, rather than extend, this same already-documented scope boundary — see Caveats for the full refuted list. The two Mooncake claims that did survive 3-0 add corroborating factual detail but land on the identical conclusion.

**2026 best practice grounding:**
- vLLM's own blog post, cross-checked against the independent upstream Mooncake GitHub repository (`kvcache-ai/Mooncake`), both confirming multiple vLLM instances share a cluster-wide Mooncake Store rather than isolated per-instance caches [vllm.ai/blog/2026-05-06-mooncake-store — confirmed 3-0].
- Live GitHub commit history confirms `MooncakeConnector` (PD disaggregation) predates the Mooncake Store blog post by roughly 2-3 months (Feb 2026 vs. May 2026), and `MultiConnector`'s chaining mechanism predates both (May 2025) — confirming the "already adopted, now extended" framing rather than a from-scratch build [github.com/vllm-project/vllm — confirmed 3-0].

**Concrete next step:** none. Optionally, the next time `gateway/ARCHITECTURE.md`'s router section is touched, name Mooncake Store alongside its existing Gateway API Inference Extension/llm-d example as a second concrete instance of the already-excluded system class — a documentation nicety, not a scope change.

**Effort:** None — this finding's entire value is confirming that no Kelvran-side work is warranted here.
