# Guardrail/Detector Plugin Extensibility — Deep Research (2026-09-15)

## Question

Comparing against how comparable 2026 production LLM gateways/API gateways handle third-party or operator-authored extensibility (Envoy's WASM filter model, Kong's plugin architecture, Cloudflare Workers, promptfoo's plugin taxonomy already cited in this repo's own `DECISIONS.md` `[2026-09-13]` entry): (1) is a WASM-based detector-plugin system (e.g. via `wazero`) a real, well-precedented 2026 pattern for letting an operator add a custom detector without forking Kelvran's Go source and rebuilding — or is that premature complexity for a single-deployment, single-maintainer project? (2) Is there a lighter-weight alternative already common in 2026 API-gateway practice — an HTTP/gRPC sidecar-callout pattern, a shell-subprocess escape hatch, or a Lua/Starlark embedded-scripting layer — and how does each tradeoff against `wazero`/WASM for this codebase's own constraints (no cgo, no new heavy runtime dependency)? (3) Does the existing `Detector` Go interface already give a same-repo contributor everything needed to add a new detector with minimal friction, or is the real gap "no way for an outside operator to extend this without forking"? (4) Anything else a 2026 survey of guardrail/middleware extensibility patterns flags as a real, checkable gap — or a real, checkable non-gap.

## Context (Kelvran's own real, current state)

`gateway/internal/guardrail/types.go`'s package doc comment states this package is "Pure-Go, stdlib-only in this pass" and "never imports adapter, cache, or any provider-specific package — text in, Verdict out." `gateway/.go-arch-lint.yml` enforces this at the architecture level, not just in prose: `guardrail` is a deliberate "pure leaf" — absent from the `deps:` map entirely, which (per that file's own comment, "verified against go-arch-lint's own source") means `checker_imports.go` denies *any* project-internal import for `guardrail`, not merely provider-specific ones. `Detector` (`types.go:52-56`) is a 3-method interface — `Name() string`, `Category() Category`, `Detect(ctx context.Context, text string) ([]Finding, error)` — explicitly designed context-aware and erroring from day one "so that detector's error-handling doesn't need retrofitting later," anticipating exactly the kind of networked, third-party-backed detector that `bedrockguard` later became. `guardrail/engine.go`'s `DefaultDetectors()` returns eight in-tree, pure-regex/checksum detectors (`EmailDetector`, `PhoneDetector`, `SSNDetector`, `IBANDetector`, `CreditCardDetector`, `IPAddressDetector`, `SecretKeyDetector`, `PromptInjectionDetector`). `guardrail/bedrockguard/bedrockguard.go` is the one opt-in, provider-specific `Detector` implementation — its own doc comment states it "lives OUTSIDE `internal/guardrail` deliberately" because that package "never imports adapter, cache, or any provider-specific package," and `.go-arch-lint.yml` backs this with a real rule (`bedrockguard: { mayDependOn: [guardrail] }`, one-directional). `bedrockguard.Detector` is appended to the `Engine`'s detector slice "only when an operator opts in via `GuardrailsConfig.BedrockGuardrails`" — i.e. wiring happens at `cmd/gateway`, not inside `guardrail` itself. `policy.go`'s `DefaultPolicy()` already ships a category-tiered Block/Warn table (credential/financial_id/government_id → Block; contact_info/network_id/prompt_injection → Warn), independently for both `Actions` (on detection) and `ErrorActions` (on detector failure). `DECISIONS.md`'s `[2026-09-13]` entry documents a real, completed adversarial-probe pass against the live gateway "mirroring promptfoo's own public plugin taxonomy" — Kelvran already treats promptfoo's taxonomy as a probe-authoring reference, not (yet) as a plugin-architecture precedent to imitate.

## Summary

No comparable 2026 production LLM/API gateway examined actually ships a WASM plugin runtime for this exact use case, and the one adjacent real-world attempt found — an Envoy AI Gateway GitHub issue proposing an external governance-policy-hook mechanism — was closed by its own non-maintainer author with zero implementation and zero maintainer engagement, which is itself evidence against urgency, not for it. Reading `guardrail`'s actual interface and `bedrockguard`'s actual implementation answers question 3 directly: there is no real gap for a same-repo contributor today — the `Detector` interface is already minimal (3 methods), already error/context-aware for networked detectors, and `bedrockguard` is a working, `go-arch-lint`-enforced demonstration of exactly the sibling-package pattern any future in-repo detector (Kelvran-authored or same-repo-contributor-authored) would follow. The only extensibility gap that exists is the one explicitly named in the research brief itself: a true external operator with no repo access and no ability to rebuild the Go binary. Nothing in this research surfaced evidence that anyone is actually asking for that today — Kelvran is single-deployment, single-maintainer, and its own `DECISIONS.md` entry treats promptfoo as a taxonomy reference for hand-crafted probes, not as a signal that third-party plugin authors are waiting at the door. If that trigger ever fires, a Lua/Starlark-style embedded-scripting escape hatch (specifically `canonical/starlark`, whose fork adds memory- and CPU-budget enforcement upstream Starlark lacks) is the better-fitting lightweight mechanism for Kelvran's stated no-cgo/no-heavy-runtime posture than a `wazero`/WASM plugin ABI — and even that is a "not yet," not a "build now."

## Findings

### Finding 1 — A pure-Go WASM plugin runtime (`wazero`) is a real, well-precedented 2026 pattern for letting a host Go application load operator-authored plugins without recompiling — but it is precedented for genuine multi-tenant/untrusted-third-party plugin marketplaces, not for Kelvran's current shape (confidence: high) — **not yet**

Extism's Go SDK (`github.com/extism/go-sdk`, real, actively maintained, "Imported by: 44" per pkg.go.dev, migrated from a cgo-based runtime to `wazero` specifically to drop the C dependency) is a genuine, production-grade precedent for "embed a pure-Go WASM runtime in a Go host so operators can load plugins without rebuilding the host binary." Its own README states this use case explicitly: "You want to be able to execute arbitrary, untrusted code from your users? Extism makes this safe and practical to do." This is real precedent, not manufactured — but the precedent's actual shape (a host serving many third-party plugin authors it doesn't control) does not match Kelvran's actual current shape (single deployment, single maintainer, zero external operators identified). The pattern exists and works; the trigger for adopting it at Kelvran — a real external party asking to extend `guardrail` without forking — does not exist yet.

### Finding 2 — `wazero`'s own isolation model has real, checkable limits that any future adoption would need to account for: memory is hard-capped, but CPU-time is only checked at operation/loop-iteration boundaries via `context.Context`, not per-instruction (confidence: high) — **informational, not a blocker, but corrects an over-simplified "WASM sandboxes CPU too" assumption**

`wazero`'s `RuntimeConfig.WithMemoryLimitPages` is a genuine hard ceiling — `internal/wasm/memory.go`'s `Memory.Validate` rejects any module whose declared max exceeds the configured limit at compile/instantiation time, not just as an unenforced default (e.g. 1024 pages = exactly 64 MiB, verified against `wazero`'s own source). CPU-time bounding, however, has no fuel/step-metering equivalent — a `feat: experimental Fuel API support` PR (#2500) was opened and abandoned upstream — and the only real mechanism is `context.Context` cancellation via `WithCloseOnContextDone(true)`, checked at compiler-inserted "periodic checks" (an open upstream issue, #2466, confirms this means every native loop iteration, not per-instruction, with a documented "very large performance impact" when enabled). This is a real, checkable technical caveat for any future `wazero` adoption at Kelvran — memory isolation is solid, CPU isolation is coarser than the word "sandbox" implies — but it does not change the "not yet" verdict on its own; it would matter at design time if/when this is ever actually built.

### Finding 3 — Cloudflare Workers for Platforms, cited in the research brief as a WASM-precedent comparator, is not actually a WASM-isolation precedent at all — its real isolation primitive is V8-isolate "untrusted mode," with no WASM/container/VM sandboxing described anywhere in its own architecture docs (confidence: high) — **corrects a premise; genuine non-gap for the WASM question specifically**

Cloudflare's own "How Workers for Platforms works" page states the isolation mechanism plainly: each user Worker runs in "untrusted mode," meaning "user Workers never share a cache... and cannot access the `request.cf` object" — a V8-isolate-level restriction, independently corroborated by a third-party technical reference describing "separate V8 isolates with memory limits and CPU time constraints." The word WASM does not appear anywhere on that page. This matters because the research brief listed Cloudflare Workers alongside Envoy WASM filters and Kong as 2026 third-party-extensibility precedent — but Workers' actual production isolation story for "run someone else's code safely" is a JS-isolate sandbox, not a WASM plugin ABI. This doesn't argue for or against Kelvran adopting WASM; it just means Workers isn't evidence *for* WASM specifically, and should be dropped from any future "WASM is how everyone does this" argument.

### Finding 4 — The one comparable-gateway precedent found for "let operators plug in custom policy/governance logic without forking" (Envoy AI Gateway) was proposed, discussed, and closed with zero implementation and zero maintainer buy-in — real evidence that this exact ask, even when raised on a comparable production LLM gateway, has not yet cleared the bar for actually getting built (confidence: high) — **reinforces "not yet" from an external data point, not just an internal one**

A GitHub issue on Envoy AI Gateway (now `theagentrouter/agent-router`, formerly under the `envoyproxy` org) proposing an external governance-policy-hook mechanism was closed by its own author — who was never a maintainer (`authorAssociation: NONE` on every comment in the thread, including the closing one) — with the comment "Closing — no follow-through on this end." No PR ever implemented it; the only labels applied were from an automated bot, not a human; the one maintainer-adjacent account that touched the issue only "subscribed," with zero comment or design feedback. This is a genuine, checkable data point that a structurally similar extensibility ask, raised on a comparable production gateway, did not generate enough real demand to get built — which is exactly the kind of external signal the research brief asked to be honest about, and it points toward "not yet" rather than "there's a wave of demand Kelvran is behind on."

### Finding 5 — Envoy's `ext_authz` sidecar-callout pattern is real, lightweight (a single-RPC gRPC contract), and — critically — is structurally the same shape Kelvran's own `bedrockguard.Detector` already implements today; Kelvran does not need a new mechanism to get "callout to an external service for a verdict," because it already has one (confidence: high) — **non-gap: already adequately served by the existing `Detector` interface + sibling-package pattern**

Envoy's `ext_authz` filter "calls an external gRPC or HTTP service to determine whether an incoming HTTP request is authorized," with a `failure_mode_allow` toggle so operators explicitly choose fail-open vs. fail-closed behavior on a check-service error — and the gRPC variant's contract is a single-method `AuthorizationServer.Check(context.Context, *CheckRequest) (*CheckResponse, error)` interface, deliberately narrow compared to a full plugin ABI. This is architecturally identical, method-for-method, to what `bedrockguard.Detector` already does inside Kelvran: `Detect(ctx, text) ([]Finding, error)` makes an external HTTP call (AWS Bedrock's `ApplyGuardrail`) and returns a verdict-shaped result, with fail-open/fail-closed already handled — per `bedrockguard.go`'s own doc comment — by the *existing* `Engine.Check`/`Policy.ErrorActions` mechanism, explicitly "no new per-detector failure-policy surface." A same-repo (or even a network-callout-authoring) contributor who wants "call some external service and turn its answer into a `Finding`" does not need Envoy's pattern *imported* — Kelvran's `Detector` interface already generalizes it. This is the clearest non-gap finding in this research pass.

### Finding 6 — If a lighter-weight, in-process "operator-authored custom logic" escape hatch is ever pursued instead of a full WASM plugin runtime, `canonical/starlark` is a better-fitting 2026 candidate for Kelvran's specific no-cgo/no-heavy-runtime constraint than `wazero`/WASM, GopherLua, or go-lua — but this remains gated on an actual trigger, not built now (confidence: high on the technical comparison; the "should Kelvran build this" verdict is unavoidably a should, not a fact) — **not yet, but names the right candidate for whenever the trigger arrives**

`canonical/starlark` is a fork of Google's `starlark-go` that adds `MemSafe` (memory-budget enforcement) and `CPUSafe` (CPU-time-budget enforcement) safety constraints explicitly "not present upstream," motivated in its own `doc/safety.md` by exactly the untrusted/resource-constrained host scenario a detector escape hatch would be: "allowing users unlimited access to run code on the host can be problematic." Starlark's embedding shape (`starlark.Thread` + `ExecFile`/`Call`, with `NewBuiltin(name, fn)` wrapping a Go function of signature `func(thread *Thread, fn *Builtin, args Tuple, kwargs []Tuple) (Value, error)` as a callable script value) is exactly the integration shape a host would need to expose, say, a `guardrail.Finding` constructor or an existing regex helper into an operator-authored script, with no plugin runtime and no cgo. GopherLua and go-lua are also real pure-Go, no-cgo alternatives (confirmed via source/`go.mod` inspection — zero `import "C"`, zero `#cgo` pragmas in either), but neither ships `canonical/starlark`'s built-in memory/CPU budget enforcement, making Starlark the stronger fit specifically *because* Kelvran would be running this on a hot path (pre-call AND post-call, per `Engine.Check`'s own doc comment) where a runaway or malicious script is a real availability concern, not just a theoretical one. None of this changes the verdict: this is a "candidate shape for later," not something to build now, since no real trigger (an actual operator wanting to extend detection logic without forking) has surfaced.

### Finding 7 — The existing `Detector` interface already gives a same-repo contributor everything needed to add a new detector with minimal friction; there is no real gap at this project's current maturity stage for that audience (confidence: high, read directly from source, not inferred) — **non-gap; honest "nothing to build" answer to question 3**

Read directly, not assumed: `Detector` is 3 methods, `Detect` is `context.Context`-aware and can return an error (built that way *specifically* to anticipate a future networked detector, per the interface's own doc comment — a design decision that paid off exactly as intended when `bedrockguard` was built later), category assignment is a single method returning one of six fixed `Category` constants, and wiring a new detector in requires only appending it to the slice `DefaultDetectors()` returns (for an always-on, in-tree detector) or following `bedrockguard`'s pattern of a sibling package + opt-in wiring at `cmd/gateway` (for anything provider-specific or optional). `go-arch-lint.yml`'s enforced "pure leaf" rule for `guardrail` and its one-directional `bedrockguard mayDependOn guardrail` rule mean this pattern isn't just documented convention that could silently rot — CI would fail a same-repo contributor's PR if they violated the boundary by mistake. There is genuinely no friction here worth fixing. The real and only extensibility gap is the one the research brief itself already named honestly: a true external operator with no repository access and no ability to compile a new binary. This research pass found no evidence that operator exists yet for Kelvran.

## Caveats

- Several claims in this pass (Envoy `ext_authz`'s core behavior, its `failure_mode_allow` toggle) landed at 2-1 rather than unanimous 3-0 votes on the first pass but were independently re-verified live against Envoy's own current docs during verification — treated as high confidence here because the re-verification, not just the original vote, is what closed the gap.
- `canonical/starlark`'s specific claim of novelty over upstream ("not present upstream") is real for the memory-budget half but has a real nuance for the CPU-budget half: upstream `starlark-go` already has a coarser `SetMaxExecutionSteps`/`ExecutionSteps` mechanism (added 2020, extended 2022) that is a rougher analog to `CPUSafe`. This doesn't overturn the finding — the fork's own maintainers, who know upstream's code, still list `CPUSafe` as a real difference, implying finer/more-comprehensive enforcement — but it means "zero CPU-limiting exists upstream" would be an overstatement; "meaningfully better CPU-limiting exists in the fork" is the accurate framing used above.
- The Envoy AI Gateway issue (Finding 4) is one data point, not a survey of every comparable gateway's issue tracker — it is real, live-verified, and directly on-point, but it should be read as "one real, checkable non-adoption data point," not as proof that no comparable gateway has ever shipped operator-pluggable governance hooks anywhere.
- No source in this pass claims Kong's plugin architecture or a promptfoo-native plugin-loading mechanism was directly examined against Kelvran's own code — the research brief named them as comparators, but the surviving verified claims cluster around Extism/wazero, Cloudflare Workers, Envoy `ext_authz`/AI-Gateway, and Starlark/Lua; Kong specifically doesn't appear in the confirmed-claims list, so no Kong-specific finding is reported here rather than filling the gap with speculation.
- This is a fast-moving-adjacent area (WASM tooling, `wazero` releases) but the load-bearing technical facts checked here (API shapes, safety-constraint existence, isolation primitives) are structural/architectural, not benchmark numbers likely to be stale by the time this is read.

## Recommendation for Kelvran

1. **No action needed on the `Detector` interface itself** (Finding 7) — it already serves same-repo/same-organization extension with minimal friction, and this is validated by reading the actual interface plus `bedrockguard`'s real, working, `go-arch-lint`-enforced implementation of it. This research question is closed.
2. **No new "callout" mechanism needed** (Finding 5) — `bedrockguard.Detector` already demonstrates the external-HTTP-verdict pattern Envoy's `ext_authz` exemplifies industry-wide; Kelvran already has this, generalized through the existing interface, not through a separate mechanism.
3. **Not yet, all correctly deferred, with an explicit trigger to watch for**: a WASM plugin runtime (Finding 1) and an embedded-scripting escape hatch (Finding 6) are both real, buildable, well-precedented mechanisms — but neither has a real trigger today. The trigger to watch for is unchanged from the research brief's own framing: a real third-party or external operator actually asking to extend `guardrail` without forking Kelvran's Go source. If and when that happens, this research pass's honest recommendation is Starlark-style embedded scripting (specifically `canonical/starlark`, for its memory/CPU safety constraints) over a full `wazero`/WASM plugin ABI, given Kelvran's own established no-cgo/no-heavy-runtime posture — WASM becomes the better fit only if true untrusted/adversarial third-party plugin authors (not just "an operator who trusts their own script") become a real requirement, since WASM's sandboxing story is stronger than Starlark's for that specific threat model.
4. **Document, don't build**: Finding 2's `wazero` CPU-isolation caveat (coarse, context-cancellation-based, not per-instruction fuel metering) is worth remembering as design context for whenever WASM adoption is actually triggered — it is not itself an action item today.

## Open Questions

- Has any real external party — a customer, an integrator, a community contributor without repo write access — ever actually asked to extend Kelvran's guardrail detection without forking? This research pass found no evidence either way inside Kelvran's own docs; it is the single fact that would flip Findings 1 and 6 from "not yet" to "build now."
- If/when a scripting escape hatch is pursued, would Kelvran expose it as a per-tenant/per-deployment operator setting (config-driven script path) or as a build-time-only extension point — this affects whether `canonical/starlark`'s sandboxing is even load-bearing (an operator's own trusted script vs. a genuinely adversarial third party change the threat model significantly).
- Does Kong's plugin architecture (named in the original research brief but absent from the surviving verified-claims set) offer a meaningfully different lesson than Envoy's `ext_authz`/WASM-filter model? Not answered in this pass — no verified claim addressed it directly.
- Would a future `bedrockguard`-style sibling package for a *second* third-party ML moderation provider (e.g., a non-AWS content-safety API) surface any friction the current pattern doesn't already handle cleanly? Untested — `bedrockguard` is currently the only real example of the pattern in the repo, so "does this generalize to a second instance" is unverified in practice.
