# API Versioning & Deprecation Policy for the Gateway HTTP API — Research Report

**Date:** 2026-09-15
**Scope:** Kelvran's **public-facing gateway HTTP API** — the data-plane route (`gateway/cmd/gateway/main.go`) and the control-plane Admin API (`gateway/internal/admin/admin.go`) — as distinct from the internal cross-language `api/gatewayevents/v1` protobuf contract, which already has real governance (`buf breaking` in CI, package/directory versioning, an `UPGRADE.md` table) per `api/README.md` and `docs/rfcs/2026-09-03-api-gatewayevents-contract.md`. This report does not re-litigate that contract's mechanism; it treats it as the internal baseline Kelvran's *external* HTTP surface currently has no equivalent of.
**Method:** Direct inspection of Kelvran's live route table and related RFCs/docs, cross-checked against primary-source versioning/deprecation policy documentation from OpenAI, Stripe, LiteLLM Proxy, and LLM Gateway (llmgateway.io) — the closest direct peer, since it is itself an LLM gateway proxying multiple providers behind one HTTP contract, the same shape as Kelvran's own gateway. 20 claims survived 3-vote adversarial verification across these four sources.

---

## Executive Summary

Kelvran's gateway HTTP API — `POST /v1/chat/completions` and the entire `/admin/*` control-plane surface — has **no versioning scheme, no deprecation policy, and no breaking-change definition of any kind today**, confirmed directly against the live route table: the `v1` in `/v1/chat/completions` is a hardcoded path literal chosen for OpenAI drop-in compatibility, not a negotiated or incrementable version (an RFC in this same repo says so explicitly — see Finding 1), and `/admin/*` has no version segment at all. This is a real, unaddressed gap distinct from — and currently ungoverned unlike — the internal `api/` proto contract, which already has `buf breaking` CI enforcement and a documented migration table. Three structurally different, all-legitimate models exist among comparable systems: URL-path versioning with an explicit "new path version = breaking" rule (LLM Gateway, the closest direct peer); header-based, account-pinned dated versions with per-request override (Stripe); and no endpoint-level versioning at all, instead relying on immutable dated model-snapshot names plus tiered notice windows (OpenAI). The cheapest, most universally-adopted practice across every source examined — and the one that slots most directly into a mechanism Kelvran already has (`UPGRADE.md`'s existing, currently-empty breaking-change table) — is a precise written definition of "breaking change" paired with a mandatory release-note callout and an explicit allowlist of what counts as safe/additive. Kelvran's gateway has shipped zero breaking changes to date (`UPGRADE.md`'s own table is empty), which makes this the ideal moment to adopt a policy proactively rather than retrofitting one after the first real break.

## Findings

### Finding 1 — Kelvran's gateway HTTP API has no versioning or deprecation policy today, and the `v1` in its data-plane route is not a real version at all
**Confidence: high** (direct code and RFC inspection — not an externally-sourced claim)

The live route table, read directly: the data-plane listener registers exactly one route, `mux.HandleFunc("/v1/chat/completions", chatCompletionsHandler(pipeline))`, plus `/healthz` (`gateway/cmd/gateway/main.go`). The control-plane Admin API — a second, separate `http.Server` on its own loopback-default listener (`127.0.0.1:8081`), per `docs/rfcs/2026-09-05-gateway-admin-api.md` — registers `GET /admin/config`, `POST /admin/virtual_keys/{name}`, `DELETE /admin/virtual_keys/{name}`, `POST /admin/virtual_keys/{name}/rotate`, `GET /admin/virtual_keys/{name}/spend`, `GET /admin/prompts`, `GET /admin/prompts/{id}`, `GET /admin/prompts/{id}/versions/{version}`, `POST /admin/prompts/{id}`, `DELETE /admin/prompts/{id}`, plus debug-only `pprof` routes (`gateway/internal/admin/admin.go`). **None of these routes carry a version segment except the data-plane one, and that one is not a real version**: a separate, same-repo RFC (`docs/rfcs/2026-09-07-gateway-ratelimit-provider-header-path-dimensions.md`) states this plainly while discussing path-matching design: *"Path matching is, today, vacuous. `main.go` registers exactly one route... There is no second path to distinguish a request by."* There is no `/v2/`, no `API-Version`/`Stripe-Version`-style request header, no `Deprecation`/`Sunset` response header, and no documented breaking-change policy anywhere in `gateway/internal`, `gateway/cmd`, or the RFC corpus that this research's grep of the codebase for those terms found — confirmed by a direct search that returned zero hits. `UPGRADE.md` exists and has a real, structured table for breaking changes, but its own header text confirms it has recorded exactly zero to date, and its scope as currently used is the `api/` proto contract and the deployables' own SemVer, not this HTTP surface specifically.

**Recommendation:** Adopt a policy now, before the first breaking change — this repo's own `UPGRADE.md` table is empty today specifically because nothing has broken yet, which is the correct moment to write the rule down rather than after.

### Finding 2 — Three structurally different versioning mechanisms exist among comparable systems; Kelvran must choose one deliberately, not default into whichever is easiest to bolt on later
**Confidence: high** (multiple unanimous primary sources per mechanism)

1. **URL-path versioning, breaking change = new path segment.** LLM Gateway (llmgateway.io) — the closest direct peer to Kelvran, itself an LLM gateway proxying multiple providers behind one contract — versions its REST API via the URL path (`https://api.llmgateway.io/v1`); breaking changes to the REST contract require a new path version rather than modifying the current one in place, while additive changes (new fields/endpoints/model mappings) ship within the existing version and callers are told to tolerate unknown response fields. This is the same shape Kelvran's `/v1/chat/completions` path literal already superficially resembles — the gap is that Kelvran's `v1` isn't wired to anything: there is no code path that would ever produce a `/v2/chat/completions` route today, and no rule stating what would trigger cutting one.
2. **Header-based, account-pinned dated versions with per-request override.** Stripe resolves the effective API version per request from a priority chain: an explicit `Stripe-Version` header (highest precedence) → the version tied to an authorizing OAuth application, if the request is made on a user's behalf → the account's own pinned version, set automatically the first time that account ever calls the API and otherwise stable indefinitely. This decouples "what version does this specific request run against" from "what's the latest version" entirely — an integration written years ago keeps working against its original pinned behavior even as Stripe ships new dated versions, without the caller doing anything.
3. **No endpoint-level versioning at all — versionless contract, versioned model names instead.** OpenAI's API surface itself has no `/v2/` and no version header; the "versioning" that exists lives entirely in *model naming* — dated snapshots (`gpt-5-2025-08-07`), `-latest` rolling aliases that get deprecated as a category, and a `-preview` suffix that signals a shorter, less stable notice window — layered under a flat, unversioned REST path.

Kelvran's current shape is closest to (3) by accident (a flat, unversioned-in-practice path) but has none of (3)'s compensating structure (no dated-snapshot equivalent, no alias/preview naming convention for its own routes) and none of (1)'s or (2)'s explicit machinery either. Any of the three is a legitimate, real-world-proven choice; picking none, which is the status quo, is the one option none of the sources examined actually use in production.

**Recommendation:** Given Kelvran's `/v1/chat/completions` path literal already visually implies path-versioning (option 1) to any caller familiar with OpenAI's own convention, adopting LLM Gateway's explicit rule — a new path segment (`/v2/chat/completions`) if and when a genuinely breaking change is needed, current path stays additive-only in between — is the lowest-surprise choice; it matches what the existing URL already implies rather than introducing a header mechanism (option 2) callers have no reason to expect from a path that already says `v1`.

### Finding 3 — A precise written definition of "breaking change," a mandatory release-note callout, and an explicit backward-compatible-change allowlist is the cheapest, most portable practice found — and slots directly into a mechanism Kelvran already has
**Confidence: high** (multiple unanimous primary sources, cross-corroborated)

LiteLLM Proxy defines a breaking change precisely: *"anything that removes or renames a field, changes a default, tightens who may call an endpoint, or otherwise requires action to keep prior behavior"* — with additive changes (new endpoints, new optional request fields, new response fields) explicitly carved out as non-breaking and shippable in any release. It requires breaking changes to be called out in a dedicated "Breaking Changes" section at the top of the release notes for the version that ships them. Stripe's own documentation goes further and publishes a concrete, enumerated allowlist of exactly what counts as backward-compatible: adding new API resources; adding new optional request parameters to existing methods; adding new response properties; reordering properties in responses; changing the length or format of opaque strings (object IDs, error messages); and adding new event types. Stripe pairs this with a durable claim about its own track record — it states it has maintained compatibility with every version of its API since the company's 2011 founding — which is only credible *because* the definition behind it is this specific, not a vague "we try not to break things."

Both of these — the precise breaking-change definition and the enumerated safe-change allowlist — are pure documentation practices with zero code changes required, and both map directly onto a mechanism Kelvran's own repo already has and already uses for a *different* contract: `UPGRADE.md`'s existing `Version | Breaking Change | Migration Steps` table (currently empty, used today for the `api/` proto contract per `RELEASE.md`'s "Contract-Version Bump-and-Validate Procedure"). Extending that same table's scope — or adding a clearly-labeled sibling section — to cover the gateway HTTP API specifically, backed by a written definition of "breaking" for HTTP endpoints (field removal/rename, default-value change, new required field, tightened auth, changed status code semantics) and an explicit "additive is always safe" allowlist, costs nothing structurally new and immediately gives both Kelvran's own team and any future API consumer a citable, enforceable rule rather than an implicit one.

**Recommendation:** Adopt this first, independent of which versioning *mechanism* (Finding 2) Kelvran eventually picks — the definition and the documentation habit are valuable even before any version-negotiation code exists, and this is the one finding in this report with no implementation cost at all.

### Finding 4 — Release-cadence models for breaking vs. non-breaking changes: SemVer-major-only-breaking (LiteLLM) vs. named, twice-yearly major releases with monthly backward-compatible-only releases (Stripe) — and Stripe's own history of abandoning an ad-hoc predecessor is directly instructive for Kelvran's current state
**Confidence: high** (unanimous primary sources for the current-state claims; **medium** for LiteLLM's specific weekly-release-day claim, which was corroborated with one day's slippage against a single sampled release)

LiteLLM Proxy uses SemVer where only a major bump (`1.x.x` → `2.x.x`) is permitted to break backward compatibility; minor bumps ship on a regular weekly cadence (typically Sunday, per a Tue/Thu/Sat dev-build → release-candidate → promotion pipeline) and are explicitly scoped to backward-compatible feature additions only; patch bumps are reserved for hotfixes. Stripe runs a structurally different but equally deliberate cadence: named, dated **major** releases roughly every six months (Acacia → Basil → Clover → Dahlia, confirmed live as of this research pass) that carry the only breaking changes Stripe ships, paired with **monthly** dated sub-releases that are backward-compatible-only and deliberately keep the same major-release name specifically to signal to integrators that upgrading within a name is always safe. Critically, Stripe's own engineering blog is explicit that this replaced an earlier, worse model: prior to this cadence, Stripe *"released new API features as soon as they're ready for production — regardless of whether they're backward-compatible or not,"* i.e. breaking changes could land at any time with no predictable schedule at all.

This last point is the one most directly relevant to Kelvran's present state: Kelvran's gateway today ships breaking changes exactly the way pre-2024 Stripe did — whenever a change happens to land, governed only by the deployable's own ad-hoc SemVer tag (`gateway/v0.1.0`, per `RELEASE.md`), with no fixed cadence and no rule about which kinds of changes require which kind of version bump for the *HTTP contract specifically* (as opposed to the Go module or container image). Stripe's own retrospective on why it moved away from that model — unpredictability for integrators, not any specific incident — applies to Kelvran's current gateway HTTP surface without modification.

**Recommendation:** Kelvran doesn't need Stripe's exact twice-yearly-named-release machinery on day one — that's disproportionate for a pre-1.0 gateway with a small, still-forming integrator base — but the underlying principle (a fixed, named rule for what triggers a breaking release vs. what's safe to ship anytime) is exactly the gap Finding 1 identified, and is cheap to state even before it's operationally enforced.

### Finding 5 — Deprecation notice-window and enforcement models: OpenAI's tiered fixed minimums with a hard cutoff vs. LLM Gateway's per-endpoint notice with no blanket minimum vs. LiteLLM's narrower approach of limiting what's covered by any guarantee at all
**Confidence: high** for OpenAI's and LLM Gateway's specific policies (unanimous primary sources); **high** for LiteLLM's public/private scoping (unanimous primary source)

OpenAI runs the most structured deprecation-notice policy examined: generally-available models get **at least 6 months** notice; specialized variants (chat/Codex/deep-research variants of a GA model) get **at least 3 months**; preview models may get as little as **2 weeks**, with explicit warnings against production use of preview models for exactly this reason. Enforcement is a hard binary, not a soft degradation: the moment a deprecation is announced it "immediately becomes deprecated," and once the published shutdown date passes, the model or endpoint "will no longer be accessible" — there is no rate-limited or degraded-service intermediate state. OpenAI also maintains a dedicated deprecations page, separate from its changelog, with concrete historical examples: the Assistants API got roughly a year's notice before being fully sunset (2026-08-26) in favor of the Responses/Conversations APIs, and a batch of transcription models got almost exactly the policy's 6-month floor.

LLM Gateway takes a deliberately looser approach for its REST endpoints specifically: rather than a blanket minimum notice period, *"the specific deprecation notice for each endpoint defines its own transition window"* — model availability can also change independently of API versioning, on the upstream provider's own schedule, a distinction LLM Gateway's docs draw explicitly since it proxies multiple providers, the same position Kelvran's gateway is in. LiteLLM sidesteps the notice-window question for a subset of its surface entirely by narrowing what's covered by any compatibility promise at all: only endpoints that appear in the proxy's own OpenAPI spec are considered public and covered by *any* stability guarantee; everything else (LiteLLM names `/login`, `/v2/login`, `/fallback/login` as examples) is explicitly private, can change or be removed in any release with no notice, and is excluded from the breaking-change/release-notes process entirely.

This last point is directly actionable for Kelvran today, independent of the versioning-mechanism question: Kelvran's Admin API already has a real, if implicit, public/private-shaped split — the debug-only `pprof` routes under `/admin/debug/pprof/*` (gated behind a build flag per `admin.go`) are clearly not meant to carry the same stability promise as `GET /admin/config` or the virtual-key CRUD routes, but nothing in the repo currently states that distinction as a rule the way LiteLLM's OpenAPI-spec-scoping does.

**Recommendation:** Given Kelvran's gateway serves both multi-provider LLM traffic (where, per LLM Gateway's own framing, upstream-provider model churn is already a variable Kelvran doesn't control) and an Admin API with genuinely different stability tiers already implicit in its route names, a **hybrid** is the best fit: adopt LiteLLM's public/private scoping now (name `pprof` and any future debug-only route explicitly private, no-notice-required) at zero cost, and adopt something closer to OpenAI's tiered fixed minimums (e.g., a stated minimum notice period for the stable `/v1/chat/completions` and core Admin CRUD routes) once Kelvran has external integrators whose breakage would actually matter — LLM Gateway's looser per-endpoint model is reasonable but offers less concrete protection to callers than a stated floor does, and Kelvran has no existing customer base yet whose current behavior would argue for the extra flexibility over the extra certainty.

---

### Finding 6 — The central gap is not any single missing mechanism, but that Kelvran governs its internal cross-language contract more rigorously than its external HTTP contract, which every comparable system in this research governs at least as strictly
**Confidence: high** (synthesis of Findings 1–5, each independently high-confidence; direct code/doc cross-reference, not an external claim)

Kelvran's `api/gatewayevents/v1` proto contract already has real, CI-enforced governance: `buf breaking` runs automatically and fails the build on an unintentional incompatible change; a breaking change requires an `UPGRADE.md` entry and a version bump *independent of either deployable's own version*; and `RELEASE.md`'s own procedure explicitly forbids "letting one deployable release against a contract version the other hasn't caught up to." None of that — not the CI gate, not the independent version identifier, not the required migration-note entry — exists today for `/v1/chat/completions` or `/admin/*`, the surface actual external callers and operators depend on. Every comparable system examined in this research (LiteLLM, LLM Gateway, OpenAI, Stripe) governs precisely the surface Kelvran currently leaves ungoverned — the public REST contract — and none of them were found to apply a comparably strict mechanism to some *other*, more internal contract instead. In other words, Kelvran has the governance instinct and the tooling pattern already proven out (buf breaking + independent version ID + required migration doc), just pointed at the wrong contract for a research question about the *public-facing* API's own compatibility promise.

**Recommendation:** The fastest way to close this gap is not to invent a new mechanism, but to extend the pattern Kelvran already trusts: (1) write the breaking-change definition and safe-change allowlist (Finding 3) directly into `AGENTS.md`'s Conventions section or a new `docs/decisions/` entry, mirroring how the proto contract's rule already lives in `RELEASE.md`; (2) decide the versioning mechanism (Finding 2) — this research's own recommendation is path-versioning, since `/v1` already implies it; (3) decide what's public vs. private for notice purposes (Finding 5's LiteLLM-style scoping, cheapest first step); (4) only then decide a notice-window number, once Kelvran has real external integrators to calibrate it against.

## Caveats

- **This report found zero external (real customer/integrator) demand signal for a specific versioning mechanism** — every recommendation above is a relative-cost-and-precedent ranking among proven external models, not evidence that Kelvran's current lack of a policy has caused a real incident yet (Kelvran's gateway has shipped zero breaking changes to date, per `UPGRADE.md`'s own empty table).
- **LiteLLM's specific weekly-release-day claim (Finding 4) was corroborated with a one-day discrepancy** against a single sampled GitHub release tag (a Monday publish against a "typically Sunday" policy) — treat the *cadence structure* (weekly, with a Tue/Thu/Sat dev→RC→stable pipeline) as solid, but the exact day-of-week as approximate.
- **OpenAI's model-naming conventions (Finding 2, item 3) were corroborated at 2-1**, not unanimous — the core tiered-notice-window and hard-cutoff claims (Finding 5) are separately unanimous and should be weighted more heavily than the naming-scheme framing.
- **This research did not find any comparable system that versions an Admin/control-plane API separately from its data-plane API** — every source examined (LiteLLM, LLM Gateway, Stripe, OpenAI) discusses REST API versioning in the context of a single unified public surface, not a data-plane/control-plane split the way Kelvran's `/v1/chat/completions` vs. `/admin/*` (deliberately separate listeners, separate credential schemes, per `docs/rfcs/2026-09-05-gateway-admin-api.md`) already is. Finding 5's recommendation to treat them with different notice-tier policies is this report's own synthesis, not something directly precedented in any source found.
- **Two claims were refuted during verification and are omitted above rather than silently dropped**: a claimed LiteLLM 90-day grace window tied specifically to major-version transitions, and a claimed "OpenAI has no formal backward-compatibility guarantee at all" framing — both were checked and did not hold up against the primary sources on a second pass.

## Open Questions

1. **Does Kelvran have, or expect to soon have, external (non-Kelvran-operated) integrators calling `/v1/chat/completions` or `/admin/*` directly**, as opposed to only Kelvran's own `evals` package and any future first-party client SDK (`client-sdk-strategy-2026-09-13.md`)? Every notice-window recommendation in Finding 5 is contingent on this — a policy calibrated for third-party integrators is over-engineering if every caller today is first-party and redeployed in lockstep with the gateway itself.
2. **Should the HTTP contract's version identifier be tied to the Go module/container SemVer tag (`gateway/v<version>`) that `RELEASE.md` already manages, or be independent of it**, the way the `api/` proto contract's version is explicitly independent of either deployable's version? Stripe and LiteLLM both decouple their API version from any client-library or binary release number; Kelvran's `gateway/v<version>` tag today conflates "the binary changed" with "the wire contract changed," and this report did not resolve which coupling Kelvran should choose.
3. **Does the Admin API's already-implicit stability tiers (CRUD routes vs. `pprof` debug routes) need a formally separate policy from the data-plane API**, given no comparable system examined splits data-plane and control-plane versioning this way — is this a genuine architectural difference worth a distinct policy, or would applying one uniform policy to both surfaces be simpler and equally correct?
4. **If Kelvran adopts path-versioning (`/v2/chat/completions`) per Finding 2's recommendation, how would that interact with the OpenAI-drop-in-compatibility goal** that appears to be the actual reason `/v1/chat/completions` uses that exact path today (mirroring OpenAI's own route) — would a hypothetical `/v2` diverge from what OpenAI-compatible client SDKs expect, and is that an acceptable tradeoff, or does OpenAI-compatibility itself argue for never moving off `/v1` and instead versioning some other way?
