## Ground Truth (Kelvran, confirmed real, not a research finding)

- Kelvran's gateway runs as a single-instance, single-region deployment (`docker-compose.yml`; `deploy/k8s/` per `kubernetes-production-deployment-2026-09-14.md`).
- The client-facing listener is plain HTTP/1.1, un-TLS'd, with **no Ingress, LoadBalancer, WAF, or CDN of any kind** in front of it today (confirmed by `performance-reliability-edge-hardening-2026-09-14.md` RQ3, independently by this report's own grep of `deploy/k8s/`).
- Kelvran already has a real, shipped, in-process multi-layer cache (L1 exact, L2 normalized, L3-lite lexical near-duplicate with a hard entity/freshness gate) and `singleflight`-based cache-stampede protection — both are single-instance/in-memory today, not edge- or cross-replica-distributed.
- Kelvran's rate limiting is in-memory per-instance with an optional Redis/GCRA-backed cross-replica mode (`internal/ratelimit/redislimiter`) — i.e., Kelvran's own design already optimizes for *global accuracy across replicas*, the opposite tradeoff edge-native rate limiting makes (Finding 4).

## Findings, ranked

### 1. Network latency to the end user is a small, usually single-digit-to-low-double-digit percentage of total LLM request latency — provider-side queueing and decode dominate, and edge placement cannot fix either (Informational — grounds the overall verdict)

**What:** The research brief asked to verify, not assume, whether "latency to end-user" or "latency to the LLM provider itself" dominates total LLM-gateway request latency. It does — decisively, and by a wide margin — in favor of the provider side.

**Why it matters for Kelvran specifically:** this is the load-bearing fact underneath every other finding in this report. If network transit time to the end user were a large fraction of total latency, moving Kelvran's proxy logic to 300+ edge PoPs would be a straightforward, high-value win. It is not: the measured evidence below shows edge placement would shave milliseconds off a request whose total latency is dominated by seconds of provider-side queueing/inference, which happens at whatever single region the provider itself runs in — a distance edge deployment cannot shorten, because Kelvran (or any gateway) still has to make one long-haul hop to the provider's own infrastructure regardless of where the gateway's own logic executes.

**Consistent with settled decisions?** No prior Kelvran decision addressed this directly (see "Prior research checked" above) — this is new ground, and it independently arrives at the same directional conclusion the multi-region-DR report reached for a different reason (diurnal-demand economics), reinforcing rather than merely repeating it.

**2026 best practice grounding:**
- A public, dated (updated 2026-09-11) real-world measurement site, llmlatency.dev, publishes a live table decomposing TTFT into TTFB (network floor: DNS+TCP+TLS+first byte, no model involved) and the remainder (queueing + model prefill), measured from 5 real geographic client locations against real provider endpoints. The network share of TTFT ranges from **3% to 33%** across the measured combinations — e.g., calling Groq from São Paulo has network at 32% of TTFT, but calling Google from US-Central has network at only 3% — with the *rest* (67–97%) being queueing/prefill, not network [llmlatency.dev — single primary measurement source, but methodologically transparent and directly on-point; not independently re-run by this research pass, so treat the exact percentages as illustrative of the mechanism rather than Kelvran's own expected numbers].
- An independent "seven hops" analysis (Mango Developer, citing a Multigrid engineering write-up) decomposes LLM request latency into `connect + rtt_up + gateway + queue + prefill + decode_1 + rtt_down` and states explicitly that of these seven hops, only two (`rtt_up`/`rtt_down`, the one-way network trips) are reducible by moving closer to the user — and even those are "bounded below by the speed of light in fiber. No amount of engineering removes it. Only moving closer does." The same source identifies the **queue** hop — provider-side, driven by other tenants' traffic on a continuous-batching scheduler — as having "the highest variance by a wide margin" and states bluntly: "you cannot fix queueing from the client. You can only avoid it, by having somewhere else to send the request" [mangodeveloper.com — independent, corroborates llmlatency.dev's structural finding via a different, non-vendor source].
- Redis's own engineering blog and packet.ai's LLM-metrics guide both independently describe the same TTFT/TPOT/E2E decomposition and both identify prefill (compute-bound) and decode (memory-bandwidth-bound) — not network transit — as the dominant, controllable-only-server-side terms, with network/delivery explicitly named as one of several *smaller* contributors rather than the dominant one [redis.io, packet.ai — two more independent sources, same structural conclusion, different vendors with no shared incentive to agree].
- A disaggregated-LLM-serving study (cited via a 2026 secondary write-up, daily.dev, of primary academic-style research) found that in a production-style A100 cluster, **prefill compute accounts for only 2–23% of P95 TTFT, while queuing and KV-cache transfer between prefill/decode nodes account for 77–98%** — reinforcing that even the *provider's own* internal architecture, not just the network hop to reach it, is dominated by scheduling/queueing effects that have nothing to do with where the calling gateway is physically located [daily.dev summarizing a cited disaggregated-serving study — secondary source, one step removed from the primary paper, treated as directional rather than a promised number].

**Read on the research question:** all four independently-sourced analyses agree on the same structural point via different methodologies (live cross-region measurement, hop-by-hop latency-identity decomposition, serving-engine metric taxonomy, and disaggregated-serving profiling) — network transit to the end user is real but small, and the dominant terms (provider-side queueing, prefill, decode) are fixed by *where the model runs and how loaded it is*, not by where the calling gateway's own proxy logic executes. Kelvran's request path already makes exactly one round trip to whichever region the destination provider (OpenAI, Anthropic, Bedrock, Gemini, or a self-hosted openaicompat runtime) has decided to run in — edge-deploying Kelvran's own logic does not change that hop, it can only ever shorten the separate, smaller hop between the *end user* and Kelvran itself.

**Concrete next step:** none — this finding is a verdict input, not a build item. See Finding 6 for the one concrete, narrow action this report does recommend.

**Effort:** N/A (informational/verdict-grounding).

### 2. Where edge deployment genuinely helps an LLM proxy — co-location with the model's *own* hosting infrastructure — is a narrow case that does not transfer to Kelvran's multi-provider, BYOK architecture (Informational)

**What:** Cloudflare's own materials are explicit that AI Gateway's edge placement pays off specifically when the *inference itself* also runs on Cloudflare's network (Workers AI): "there's no extra hop over the public Internet since your code and inference run on the same global network" [developers.cloudflare.com/ai-gateway (Overview, Features) and blog.cloudflare.com/ai-platform — 2 primary Cloudflare sources, consistent with each other, though both are vendor self-description of Cloudflare's own product, not independently verified].

**Why it matters for Kelvran specifically:** this is the actual mechanism behind "edge is good for AI gateways" in vendor marketing, and it does not apply to Kelvran. Kelvran is explicitly a multi-provider, BYOK gateway (OpenAI, Anthropic, Bedrock, Gemini, openaicompat) that never hosts the inference itself — every real request still crosses the public Internet (or a customer's own VPC peering, for Bedrock) to reach a third-party provider's own infrastructure, wherever that provider has chosen to run it, regardless of where Kelvran's own proxy logic sits. The "same global network, zero extra hop" benefit is real, but it is a benefit of *vertically integrating gateway + inference on one vendor's network*, not of edge placement per se — and Kelvran's whole value proposition (per `PRD.md`) is provider-agnostic routing, which is structurally incompatible with that specific optimization.

**Consistent with settled decisions?** Reinforces, with new evidence, the existing multi-provider/BYOK architecture rather than revisiting anything.

**2026 best practice grounding:** as cited above — 2 consistent primary Cloudflare sources on the mechanism, cross-checked against Fastly's own AI Accelerator materials, which make the same category distinction implicitly by positioning their edge semantic cache as valuable specifically *because* it avoids a trip to *any* backend LLM provider, not because Fastly hosts the models itself [fastly.com/products/ai, fastly.com/ai-hub — 2 more primary vendor sources, independently corroborating the "avoiding the trip to the provider is the win, not proximity to the provider" framing from a competitor with a different business model].

**Concrete next step:** none — documents why this category of edge benefit is structurally inapplicable to Kelvran's architecture, so it isn't rediscovered and misapplied later.

**Effort:** N/A (informational).

### 3. Cloudflare AI Gateway's edge caching semantics are exact-match-only and *less* sophisticated than Kelvran's own already-shipped L1/L2/L3-lite cache — no gap found (Informational)

**What:** Cloudflare AI Gateway's caching, read directly from its own current docs, works by hashing (SHA-256) the concatenation of provider, endpoint, model, and the provider auth header — an **exact-match cache key** over the whole request. Any difference in the request body (including messages, tools, or parameters) produces a separate cache entry; Cloudflare's own docs state plainly: "We plan on adding semantic search for caching in the future to improve cache hit rates" — i.e., semantic caching is not yet shipped there, as of this research date. The docs also disclose the cache is "volatile": under simultaneous identical requests, the first may not finish caching before the second requests it, so the second can still miss and hit the origin provider [developers.cloudflare.com/ai-gateway/features/caching — primary, confirmed via direct doc read].

**Why it matters for Kelvran specifically:** this is a direct, apples-to-apples comparison point against Kelvran's own cache, and the comparison favors Kelvran, not the flagship vendor. Kelvran already ships an L1 exact-match layer (conceptually equivalent to Cloudflare's whole caching feature), *plus* an L2 normalized layer and an L3-lite lexical near-duplicate layer with a hard entity/freshness gate — none of which Cloudflare's edge cache has. Moving Kelvran's cache "to the edge" in Cloudflare's own image would be a regression from Kelvran's current cache sophistication, not an upgrade. Fastly's AI Accelerator does ship semantic (embedding-based) caching at the edge today, ahead of Cloudflare on this specific axis [fastly.com/products/ai — primary vendor source] — but Kelvran's own `PRD.md` deliberately defers a real semantic/embedding L3 pending production miss-telemetry (per the task briefing's own "already shipped/deferred" ground truth), a decision this finding does not disturb: Fastly having semantic caching says nothing new about whether Kelvran's own traffic volume justifies building one yet, which is a volume-and-telemetry question, not an edge-placement question.

**Consistent with settled decisions?** Does not touch the semantic-L3 deferral (that trigger — production miss-telemetry — is unrelated to whether the cache sits at the edge or in-process) and does not touch `AGENTS.md`'s hard entity/freshness-gate requirement, which no competitor's caching docs mention at all — worth flagging as a genuine differentiator Kelvran has that none of the three vendors researched here (Cloudflare, Fastly, Vercel) publicly document an equivalent to.

**2026 best practice grounding:** Cloudflare's caching docs and Fastly's AI Accelerator/AI Hub materials are the two primary sources; both are vendor self-description (appropriate for descriptive "how does X work" claims, as the template's own convention notes) and are consistent with each other in describing edge caching as a proxy-layer response cache, not a semantic replacement for Kelvran's own layered design [developers.cloudflare.com — confirmed via direct doc read; fastly.com — 2 pages, consistent with each other].

**Concrete next step:** none — this is a verified non-gap, flagged so a future contributor doesn't assume "the big CDN vendors must have a more advanced cache than we do" without checking.

**Effort:** N/A (informational/non-gap).

### 4. Edge-native rate limiting is deliberately per-PoP/local and eventually consistent — the opposite accuracy tradeoff from Kelvran's own Redis-backed cross-replica design, not an upgrade to it (Medium — genuine finding, no build recommended)

**What:** Cloudflare's own Workers Rate Limiting API documentation discloses, in its own words, that the underlying counters are "cached on the same machine that your Worker runs in, and updated asynchronously in the background," that "Rate limits that you define and enforce in your Worker are local to the Cloudflare location that your Worker runs in" (a request rate-limited to zero in Sydney is not counted at all against the same key's limit in any other Cloudflare location), and that the API is explicitly "permissive, eventually consistent, and intentionally designed to not be used as an accurate accounting system" [developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit — primary, confirmed via direct doc read]. Cloudflare's separate WAF-layer rate limiting (a different product from the Workers binding) does support global counting, but its own docs disclose "there may be a delay of up to a few seconds between detecting a request and updating rate counters," so "excess requests could still reach the origin before Cloudflare enforces a mitigation action" [developers.cloudflare.com/waf/rate-limiting-rules — primary, confirmed via direct doc read, independently corroborating the same "not exact" characteristic from a second Cloudflare product].

**Why it matters for Kelvran specifically:** this directly inverts the naive assumption that "edge-native" rate limiting is strictly more advanced than Kelvran's own. Kelvran's `internal/ratelimit` already supports a Redis/GCRA-backed cross-replica mode specifically to get *globally accurate* per-key limits across however many gateway instances are running — the exact property edge-native, per-PoP rate limiting explicitly does *not* provide by design, because global consistency at true edge scale (hundreds of PoPs, no shared low-latency store) is a genuinely different, harder problem that these vendors have chosen to trade away for speed ("You are not waiting on a network request," per Cloudflare's own docs on why the Workers binding is local-only). If Kelvran ever moved rate-limit enforcement to an edge layer in front of itself, it would be *trading down* on rate-limit accuracy relative to what it can already do today with Redis, not trading up — a real, non-obvious finding worth recording explicitly so it isn't rediscovered the hard way during a future edge/CDN evaluation.

**Consistent with settled decisions?** Reinforces the existing Redis/GCRA-backed cross-replica design (`gateway-distributed-concurrency-limiter-2026-09-09.md`, `gateway-tpm-permodel-fallback-2026-09-09.md`) rather than revisiting it — this is new evidence that the current design's own tradeoff (a shared low-latency store, at the cost of not being literally co-located with every possible ingress point) is the *correct* choice for accuracy, not a compromise edge deployment would improve on.

**2026 best practice grounding:** 2 independent primary Cloudflare sources (Workers Rate Limiting API docs, WAF rate-limiting-rules docs), both disclosing the same class of consistency tradeoff for two different Cloudflare products — internally consistent, not merely restated once. Vercel's own WAF rate-limiting docs corroborate the same pattern from a second vendor: "Rate limit counters are tracked on a per-region basis; traffic matching a given rate limit key in multiple regions can exceed the limit you configure for any single region" [vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting — primary, independently confirms the same structural tradeoff exists at a different vendor with a different underlying implementation, raising confidence this is a general property of edge/regional rate limiting, not a Cloudflare-specific quirk].

**Concrete next step:** none — no build recommended. Worth a one-line addition to `gateway/ARCHITECTURE.md`'s router/rate-limit section the next time it's touched, noting explicitly that edge-native rate limiting was evaluated and found to be a *less* globally-accurate model than Kelvran's current Redis-backed design, so this doesn't need re-litigating from scratch later.

**Effort:** N/A (informational; the doc-note itself would be trivial/Small if done).

### 5. Edge-native request collapsing (Fastly's "waiting list," Vercel's two-level distributed lock) is the same mechanism Kelvran already ships via `singleflight` — no edge-specific advantage found for Kelvran's current single-instance deployment (Informational)

**What:** Both Fastly and Vercel document real, production request-collapsing mechanisms at their respective edges to prevent cache-stampede/thundering-herd effects: Fastly's is a per-object "waiting list" with a `hit-for-pass` marker for non-cacheable responses, escalated across up to two tiers (clustering + shielding) for extra collapsing opportunities [fastly.com/documentation/guides/concepts/cache/request-collapsing — primary, confirmed via direct doc read]. Vercel's CDN implements a two-level (node, then region) distributed lock with double-checked-locking semantics and a hedging timeout, explicitly built to bound the number of concurrent waiters as traffic scales, and reports collapsing "over 3M requests per day on cache miss, on top of the 90M collapsed requests from background revalidations" in production [vercel.com/blog/cdn-request-collapsing — primary, confirmed via direct doc read].

**Why it matters for Kelvran specifically:** the *mechanism* — a leader/follower pattern where the first concurrent identical request executes and the rest wait on its result rather than each firing an independent duplicate call — is identical in kind to what Kelvran's own cache already does via Go's `singleflight` package for cache-stampede protection (per `AGENTS.md`'s own already-disclosed ground truth). The edge-specific engineering in both vendors' implementations (multi-tier collapsing across clustering/shielding POPs, or node-then-region distributed locks) exists specifically to solve collapsing *across many physically distinct machines with no shared memory* — a problem Kelvran's current single-instance deployment does not have, since one process with one in-memory `singleflight` group already achieves the same *effective* outcome (one in-flight call per key, followers wait) without needing any distributed-locking machinery at all. This changes if/when Kelvran becomes genuinely multi-instance (per the multi-region-DR report's own `not_yet` framing) — at that point, a Redis-backed or equivalent distributed single-flight (the same pattern an independent open-source LLM-gateway project, `uncle-voh-max/semantic-cache`, implements today for exactly this reason [github.com — a working OSS reference implementation, not a vendor, corroborating the *pattern* independently of both CDN vendors]) would become the relevant precedent — not edge deployment itself.

**Consistent with settled decisions?** Confirms, rather than revisits, that Kelvran's current single-instance `singleflight` approach is fit for purpose at its current single-instance scale — the trigger for anything more (a distributed single-flight layer) is the same "genuinely multi-instance" trigger the multi-region-DR report already named as `not_yet`, not a distinct edge-specific trigger.

**2026 best practice grounding:** 2 independent primary vendor sources (Fastly, Vercel) plus 1 independent OSS reference implementation, all describing the same underlying leader/follower single-flight pattern, cross-checked against a fourth, non-vendor educational source (ai-tldr.dev) that explicitly names "an LLM gateway or a proxy in front of the model" as the correct place to put this pattern — which is exactly where Kelvran already has it [ai-tldr.dev/learn/production-llmops/cost-latency-optimization/request-coalescing-llm — independent, corroborates the architectural placement, not just the mechanism].

**Concrete next step:** none for today. Worth remembering as the *specific* pattern to reach for (Redis-backed distributed single-flight, not edge deployment) if/when Kelvran becomes multi-instance and its current in-process `singleflight` stops being sufficient.

**Effort:** N/A (informational).

### 6. The one concrete, actionable gap: Kelvran has zero DDoS/WAF/bot-mitigation layer in front of its exposed, un-TLS'd listener today — a real gap, but the fix is a reverse-proxy/WAF layer in front of the existing single-region deployment, not an edge redeploy of the gateway itself (Small–Medium)

**What:** Every vendor researched here ships automatic, effectively-free, always-on DDoS mitigation as a baseline platform property, independent of and prior to any of their AI-specific features: Cloudflare's WAF rate-limiting docs describe protecting "REST APIs from resource exhaustion (targeted DDoS attacks)" as a named use case; Vercel's own Firewall docs state "Vercel provides automated DDoS mitigation for all deployments, regardless of the plan that you are on," layered before any custom WAF rule; Fastly's AI-specific press materials name "DDoS Protection" and "Next-Gen WAF" as existing platform capabilities its new AI Firewall/AI Runtime Control products build on top of, not new inventions [developers.cloudflare.com/waf/rate-limiting-rules/best-practices, vercel.com/docs/vercel-firewall, fastly.com/press/press-releases/fastly-launches-ai-firewall-and-ai-runtime-control-to-secure-and-scale-ai — 3 independent primary vendor sources, all naming DDoS mitigation as a baseline, table-stakes platform property]. Kelvran, by contrast, has confirmed (per `performance-reliability-edge-hardening-2026-09-14.md`'s RQ3, independently reconfirmed by this report's own read of `deploy/k8s/`) **no reverse proxy, load balancer, Ingress, WAF, or TLS termination of any kind** in front of its client-facing listener — meaning today, if Kelvran's gateway were exposed to the public Internet at all, it would have literally none of the DDoS/rate-limiting/bot-mitigation protections every competitor treats as a free, automatic baseline.

**Why it matters for Kelvran specifically:** this is a genuinely different question from "should Kelvran deploy at the edge for latency," and this report's own Finding 1 verdict (`not_yet` on latency grounds) does not answer it — DDoS/WAF protection is a security-posture question, not a performance one, and the case for it does not depend on whether edge placement helps LLM-proxy latency at all. Vercel's own guidance on this exact topology is directly applicable and reassuring on the "does this create a second-CDN latency penalty" concern: putting a CDN in front of a non-CDN-hosted origin in reverse-proxy mode is the standard, named pattern for exactly this situation, with the explicit caveat that doing so adds "a hop of latency" on cache misses and creates two client-IP/TLS-fingerprint visibility complications worth being aware of, not disqualifying ones [vercel.com/kb/guide/vercel-waf-vs-cloudflare-waf — primary, directly names "protecting origins that don't run on Vercel/Cloudflare" as a first-class use case for exactly this topology].

**Consistent with settled decisions?** Directly extends, with new evidence, the still-open gap `performance-reliability-edge-hardening-2026-09-14.md`'s RQ3 and RQ5 already named (no TLS, no mTLS/zero-trust for admin) — this finding narrows *why* it matters (DDoS/WAF exposure, not just HTTP/2/3 protocol features) and gives it a concrete, minimal-risk shape (a reverse-proxy WAF layer, not a rearchitecture). It does not reopen or contradict the multi-region-DR report's `not_yet` verdict on geo-distributed gateway *compute* — a WAF/CDN layer in front of a single-region origin is orthogonal to whether the origin itself is single- or multi-region.

**2026 best practice grounding:** 3 independent primary vendor sources on DDoS-mitigation-as-baseline (above), plus the direct, load-bearing chain back to this repo's own confirmed ground truth (`performance-reliability-edge-hardening-2026-09-14.md` RQ3) that TLS termination — the actual prerequisite for *any* reverse-proxy/WAF layer, edge or otherwise — does not exist yet on Kelvran's client-facing surface. This means the real, honestly-scoped next step is smaller than "adopt a CDN": it is "decide on TLS termination for the client-facing listener," a decision that was already `not_yet` for HTTP/2/3 reasons and is now *additionally* motivated by this finding's DDoS/WAF angle, without needing edge deployment or any of Findings 1–5's tradeoffs to be relevant at all.

**Concrete next step:** not a build item today (per RQ3's own already-correct `not_yet`, which this finding does not overturn) — but the next time TLS termination is scoped for Kelvran's client-facing listener (whenever that trigger fires), the design should default-assume a CDN/WAF layer in reverse-proxy mode (Cloudflare, Vercel, or equivalent, in front of Kelvran's existing single-region K8s origin) as the mechanism, rather than terminating TLS bare on the gateway itself with no DDoS/WAF layer at all — this is a "when you build it, build it this way" note, not a standalone RFC to write now.

**Effort:** Small–Medium *if and when* TLS termination is scoped (adds one well-precedented topology decision to that future work, not new scope of its own); N/A today, since the TLS prerequisite itself remains `not_yet` per the already-settled RQ3 finding.

This directly supports a `not_yet` verdict for edge-deploying Kelvran's gateway logic itself.
2. **Add a one-line note to `gateway/ARCHITECTURE.md`'s router/rate-limit section** (Finding 4) recording that edge-native rate limiting was evaluated and found to be a *less* globally-accurate model than Kelvran's existing Redis-backed cross-replica design — cheap, prevents this specific tradeoff from being rediscovered the hard way in a future evaluation.
3. **When TLS termination for the client-facing listener is eventually scoped** (the still-open, already-`not_yet` prerequisite from `performance-reliability-edge-hardening-2026-09-14.md` RQ3), default-assume a reverse-proxy CDN/WAF layer (Cloudflare, Vercel, or equivalent) as the mechanism, given every vendor researched here treats DDoS/WAF protection as an automatic, near-zero-cost baseline once any reverse proxy exists in front of an origin (Finding 6). This is not a standalone action item — it's guidance for that future, separately-triggered decision.

**Overall verdict:** `not_yet` on edge-deploying Kelvran's own gateway/proxy logic, for latency reasons — a real, defensible, evidence-backed verdict, not a default. The one adjacent, genuinely open gap (no DDoS/WAF layer at all, Finding 6) is real but distinct from the edge-latency question, has its own separate trigger (TLS termination being scoped), and does not require reversing the edge-latency verdict to address.

## Caveats

- **"Edge AI gateway" is itself a nascent, unsettled product category as of this research date, not table stakes.** Fastly's own architecture blog post describing an AI Gateway built on Fastly Compute is explicitly framed as a proof-of-concept the author built to "see what it would look like" — closing with "We're exploring what it would look like to make this a native Fastly capability," not announcing a shipped product [fastly.com/blog/building-an-ai-gateway-on-fastly-compute]. Fastly's separately-announced, actually-shipped "AI Runtime Control" (2026-09-20/21) is a different, narrower product (virtual keys, spend tracking, failover) that does not itself claim edge-executed proxy logic in the way the POC blog post does. Treat Fastly's edge-AI-gateway pattern as illustrative of what's technically possible on Compute, not as evidence of a mature, battle-tested competitor architecture to benchmark against.
- **Vercel's own "AI Gateway," despite the branding, is explicitly *not* edge-executed** — Vercel's own engineering blog states plainly it "runs across the Vercel distributed infrastructure in multiple AWS regions" on "Fluid compute" (a regional, server-like runtime), and only uses Vercel's global anycast/PoP delivery network for *ingress routing* to the nearest compute region, not for executing the gateway's own routing/auth/quota logic at the edge itself [vercel.com/blog/how-ai-gateway-runs-on-fluid-compute]. This is a genuinely useful, somewhat counter-intuitive finding: even a major, actively-marketed "AI Gateway" product from an edge/CDN-native company keeps its actual proxy compute regional, not edge-distributed — independent evidence, from inside the industry itself, that edge-executing an LLM-proxy's control logic is not the obvious or default choice its own vendor's brand name might suggest.
- **Source mix is vendor-documentation-heavy for the caching/rate-limiting/DDoS descriptive claims** (Cloudflare, Fastly, Vercel self-describing their own products) — appropriate for "how does X work" claims (this directory's own established convention, per `gateway-2026-09-06.md`'s Caveats section), but none of these vendors' own performance/latency marketing claims (e.g., Cloudflare's "reducing latency by up to 90%" for cache hits, or Fastly's "boosts... performance... by 9x") were independently re-benchmarked by this research pass — treat these specific numbers as vendor-reported, not independently verified, even though the underlying *mechanisms* they describe are confirmed via direct doc reads.
- **The network-latency-share table (Finding 1) is one measurement site's own methodology and dataset**, not independently reproduced by this research pass — its directional conclusion (network share is small, 3–33%) is corroborated structurally by three other independent sources using different methods, but the exact percentages should be treated as illustrative, the same caution `performance-latency-optimization-2026-09-14.md` already applied to its own cited k6 benchmark numbers.
- **This report used single-agent iterative web search and doc-fetch, not the multi-agent adversarial-vote process** some earlier reports in this directory (`gateway-2026-09-06.md`) used — confidence language above describes source-count agreement, not a formal vote tally, and should be read accordingly.
- **Time-sensitivity is real and non-trivial**: several sources cited are dated within the last few weeks of this report (Fastly's AI Runtime Control launch, 2026-09-20/21; Fastly's Compute AI Gateway POC blog, 2026-03-10; Cloudflare's Workers-AI/AI-Gateway unification blog, 2026-08-07) — this entire competitive space is visibly moving fast, and specific vendor feature sets should be re-verified before being cited in a design doc more than a few months from this date.

## Open questions

1. **This report did not investigate whether any of Kelvran's actual client applications sit behind a CDN of their own today** (a fact this repo's own code cannot answer, per `performance-latency-optimization-2026-09-14.md`'s own identical caveat on its Finding 6) — if a customer's own frontend already routes through Cloudflare/Vercel/Fastly before reaching Kelvran, that changes the practical urgency of Finding 6's WAF/DDoS gap, independent of anything Kelvran itself does.
2. **If Kelvran ever does host or co-locate with a specific provider's own inference infrastructure** (e.g., a future dedicated Bedrock VPC-peered deployment), does Finding 2's "co-location, not edge placement, is the real mechanism" framing change the calculus for that one provider specifically, even while the general multi-provider case (this report's main verdict) stays `not_yet`? Not investigated here — a narrower, provider-specific follow-up question if that scenario ever becomes concrete.
3. **Fastly's stateless MCP-at-the-edge pattern** (tied to the MCP spec's 2026-07-28 stateless revision) is a genuinely interesting adjacent pattern for a future inbound MCP server — but Kelvran's own inbound-MCP-server RFC is explicitly not yet built (per this task's own briefing), so whether edge deployment matters *specifically for an MCP broker* (a different traffic shape than chat-completion proxying — more tool-catalog/discovery calls, which Fastly's own writeup notes are cacheable and rarely change) is a distinct question this report did not investigate in depth, and shouldn't be conflated with this report's main chat-completion-proxy verdict if/when the MCP RFC is picked up.
4. **What would actually change this report's `not_yet` verdict?** By analogy to the multi-region-DR report's own named trigger (real production traffic at geographic/volume scale), the concrete trigger here would be: (a) Kelvran acquiring end users in regions where the *network* hop specifically (not provider queueing) is measured to be a material fraction of their experienced latency — the llmlatency.dev-style measurement this report leaned on, but run against Kelvran's own real traffic and geography, not a third party's — or (b) a customer requirement for DDoS/WAF protection materializing independent of the latency question (Finding 6), which has its own separate, already-named trigger (TLS termination being scoped).
