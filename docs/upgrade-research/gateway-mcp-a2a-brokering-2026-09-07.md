# Kelvran Gateway — MCP/A2A Tool-Call Brokering: Is It a Real Differentiator? (2026-09-07)

**Date:** 2026-09-07
**Scope:** `gateway/internal/mcp` — currently **NOT BUILT** (zero code; no such directory exists under `gateway/internal` as of this research date). Named in `gateway/ARCHITECTURE.md`'s "MCP/A2A Subsystem" section as a design intent ("inbound... + outbound... brokering — shares identity/costaccounting, not a second gateway") and explicitly listed in `PRD.md` as **out of scope for v1**. This report evaluates whether to build it next, not how to build it today.
**Method:** Adversarial multi-source research (3-vote verification per claim) against real, currently-shipping 2026 AI-gateway MCP support (Portkey, Envoy AI Gateway, Kong AI Gateway, LiteLLM) plus the current, primary MCP specification itself (2026-07-28 revision, cross-checked against 2025-06-18). 18 claims survived adversarial verification; 7 were refuted and are logged below for transparency. This is 1 of 4 parallel deep-research passes (routing scope, MCP/A2A brokering, hierarchical budgets, evals judge-panel reducer) — cross-references to the sibling `gateway-2026-09-06.md` report are noted where relevant, but this document stands alone.

---

## Executive summary

Real, shipping precedent for gateway-brokered MCP tool calls exists and is more mature than expected: Kong AI Gateway ships a GA, enterprise-licensed plugin that routes MCP traffic through its existing consumer/auth/rate-limit/observability stack, Envoy AI Gateway multiplexes multiple MCP servers behind OAuth-gated routes with tracing, and LiteLLM's proxy auto-executes MCP tool calls end-to-end behind the same virtual-key header used for chat completions — so question 1 (does anyone actually do this) is a clear **yes**, at least for governance dimensions other than dollar-cost. But every one of these products stops short of exactly the piece that would make MCP brokering interesting for Kelvran specifically: none of them extend **dollar-denominated cost accounting** to MCP tool-call execution — Portkey's own docs show its cost-based Usage Limit Policies structurally exclude an `mcp_tools`/`mcp_server` target, leaving only request-count/token-count rate limiting for MCP, and Envoy's MCP docs mention no cost/billing/spend concept at all, only tracing and metrics. Separately, the MCP specification itself (2026-07-28, current) turns out to impose a materially different trust model than Kelvran's virtual keys: OAuth 2.1 three-party roles, RFC 8707 audience-bound per-server tokens, and an explicit, spec-level prohibition on token passthrough (a broker cannot forward one internal credential to arbitrary downstream MCP servers) — though this friction is real only for implementations that opt into MCP's HTTP-transport authorization at all, since the spec labels authorization OPTIONAL. A2A's relevance to this research question could not be established either way — no surviving claims addressed A2A adoption/maturity at all, a real gap in this pass. The honest recommendation: **outbound MCP brokering is a genuine, differentiated extension of Kelvran's own agent-run-level cost/governance thesis on paper, but no shipping competitor has solved the specific hard problem (dollar-costing non-token tool execution) that would make Kelvran's entry non-redundant — building it now is premature relative to a demand signal, and the real prerequisite work (a tool-call cost-accounting unit distinct from per-token Decimal pricing) has not been designed anywhere yet.**

## Findings

### 1. Real, shipping gateways DO broker MCP tool calls through their own governance layer today — but the depth of that governance is uneven, and dollar-cost is the one dimension none of them cover

**What the research found:** Three independently-verified, currently-shipping products broker MCP tool calls through an existing gateway control plane, not a bolted-on side system:

- **Kong AI Gateway**'s `AI MCP Proxy` plugin is GA (no beta/preview badge, unlike the adjacent MCP Registry feature which Kong does label `tech preview`), enterprise-licensed, minimum Kong Gateway 3.12, with a multi-version changelog running through 2026-07-02. It has four modes — passthrough-listener, passthrough-proxy to upstream MCP servers, and two REST→MCP conversion modes — and Kong explicitly documents that its existing plugin ecosystem (OpenID Connect/Key Auth, Rate Limiting/Rate Limiting Advanced, logging/tracing, ACL) applies to MCP traffic the same way it applies to LLM traffic, including MCP client "pings" counting toward AI Gateway usage totals.
- **Envoy AI Gateway** runs a transparent proxy between MCP clients and backend MCP servers, aggregating multiple backend MCP servers into one unified endpoint with backend-prefixed tool names (`github__issue_read`, `context7__resolve-library-id`) to route calls correctly — real server multiplexing and tool routing, not just pass-through.
- **LiteLLM**'s proxy, when configured as the MCP endpoint (`server_url=litellm_proxy` + `require_approval:never`), fetches MCP tools, converts them to OpenAI-compatible tool definitions, and on a returned tool call automatically parses arguments, routes to the correct MCP server, executes the tool, retrieves results, and feeds them back to the LLM for a final response — the full outbound-brokering loop the task's research question 4 asks about, already shipping.

**Why it matters for Kelvran specifically:** this directly answers research question 1 — brokering MCP tool calls through a gateway's own control plane is not a hypothetical, it is Kong's, Envoy's, and LiteLLM's current shipped reality, and `gateway/ARCHITECTURE.md`'s own framing ("shares identity/costaccounting, not a second gateway") is exactly the architecture Kong (existing plugin/consumer stack) and LiteLLM (same virtual-key header) already chose independently. **But** every one of these products' governance for MCP tool calls, on inspection, is narrower than their governance for LLM completions: Portkey's MCP Gateway rate-limits by request count or token consumption only (no `cost` rate-limit type exists for the `mcp_tools` target, even though Portkey's separate Usage Limit Policies *do* support dollar-cost — just scoped to LLM-specific fields like `provider`/`model`/`endpoint_type`, with no MCP equivalent), and Envoy's MCP docs list observability as OpenTelemetry tracing + Prometheus metrics only, with no cost/billing/spend/token-metering concept anywhere on the page. This is the load-bearing gap for Kelvran's differentiation thesis: **the brokering mechanism is solved and precedented; the dollar-cost-accounting-for-tool-execution problem is not, anywhere.**

**Confidence:** High (multiple primary sources — Kong's own plugin docs + changelog, Envoy's own docs + blog, LiteLLM's own docs — unanimous 3-0 votes on every sub-claim in this cluster).

### 2. Gateway auth models for MCP brokering reuse the gateway's existing identity system for the *client-facing* leg, but none of them extend it into a virtual-key-shaped credential for the *downstream MCP server* leg — that leg follows MCP's own OAuth model instead

**What the research found:** LiteLLM's MCP client-facing authentication is literally the same virtual-key/bearer-token mechanism used for chat completions (`x-litellm-api-key: Bearer $LITELLM_API_KEY`, and the docs state explicitly that "a LiteLLM API key used for gateway admission is not copied to the upstream [MCP] server" — the LiteLLM-to-upstream-MCP-server leg is a *separate*, distinct hop with its own `auth_type`/`auth_value`). Envoy AI Gateway's inbound/client-facing MCP authentication is OAuth-only (authorization code flow + PKCE, `securityPolicy.oauth` with `issuer`/`protectedResourceMetadata`/`scopesSupported`) — Envoy's own MCP docs contain no mention of "virtual key" at all — while its *upstream*-facing leg (Envoy-to-backend-MCP-server) uses a completely different mechanism, per-backend API-key injection via a Kubernetes Secret, plus selective client-header forwarding for per-user passthrough. Kong's MCP proxy similarly layers its existing OpenID Connect/Key Auth plugins onto the client-facing leg without literally reusing its LLM-traffic-specific plugins (the OAuth2 plugin is explicitly documented as *not* invoked as part of an LLM completion request flow — it is new, MCP-specific).

**Why it matters for Kelvran specifically:** this is the direct answer to research question 2's "clean mapping or real friction point" ask, refined with more precision than a single yes/no. There is a clean mapping for the *client → Kelvran* leg (Kelvran's existing virtual-key `Verifier.Verify(authorizationHeader)` already does exactly what LiteLLM does — one bearer credential admits the caller to the gateway, no change needed there). The friction is entirely on the *Kelvran → downstream MCP server* leg, and it is not merely a "different auth scheme" annoyance — it is a structural mismatch, detailed in Finding 3.

**Confidence:** High (primary vendor docs for all three products, unanimous or 2-1 high-confidence votes, cross-checked against the products' own negative-evidence — e.g., confirmed "virtual key" does not appear anywhere on Envoy's MCP page).

### 3. The MCP spec's own authorization model is structurally incompatible with naively forwarding a single internal credential downstream — this is a real, spec-mandated constraint, not a design preference Kelvran could route around

**What the research found, synthesizing several tightly related, spec-verified claims:**

- MCP defines three distinct OAuth 2.1 roles — the MCP server as **resource server**, the MCP client as **OAuth client**, and a separate **authorization server** that issues tokens — a three-party model, versus a virtual-key gateway where the gateway itself is the sole trust/issuance point (collapsing what MCP treats as separate roles into one entity).
- MCP **mandates RFC 8707 Resource Indicators**: every token request must include a `resource` parameter bound to the *canonical URI of the specific target MCP server* — tokens are audience-scoped per downstream server, not a single reusable caller-scoped bearer credential the way Kelvran's virtual keys are.
- MCP **explicitly prohibits token passthrough** at the spec level, in the strongest normative language available: "MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server... MCP servers **MUST NOT** accept or transit any other tokens." The spec's own Security Considerations section extends this to a broker/proxy scenario directly on point for Kelvran's outbound-brokering design: "If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server **MUST NOT** pass through the token it received from the MCP client." This rule is stable across at least two spec revisions (2025-06-18 and current 2026-07-28), so it is not a fringe draft-only provision.
- MCP names this exact failure mode a "**confused deputy problem**" — a named attack class specifically for MCP servers/proxies brokering to third-party APIs on a user's behalf, mandating per-dynamically-registered-client user consent before forwarding to third-party authorization servers.
- Full OAuth-flow MCP servers must additionally act as a complete RFC 9728 protected resource: returning `401` + `WWW-Authenticate` challenges pointing to a self-hosted Protected Resource Metadata document, then delegating to a separate authorization server for a real, browser-based, per-user login/consent flow — not a bearer-header check.

**Why it matters for Kelvran specifically:** research question 2 asked whether MCP's auth model assumes a different trust boundary than a gateway's virtual-key-per-caller model — the answer is an unambiguous, spec-verified **yes**, and the specific shape of the mismatch matters for design: Kelvran cannot simply take a caller's virtual key, attach it to an outbound MCP tool call, and forward it to whichever downstream MCP server the agent wants to reach. It would need to either (a) mint/broker a separate, audience-scoped, per-downstream-server OAuth token per outbound tool call — real new machinery, structurally analogous to what Envoy does with its per-backend API-key-injection Secrets, not a virtual-key extension — or (b) restrict outbound brokering to MCP servers configured with static, gateway-managed API keys (a narrower, more tractable v1 scope, closer to Kong's/Envoy's own upstream-auth pattern than to MCP's own OAuth-native design).

**Important qualifier, load-bearing for scope decisions:** MCP's spec formally labels authorization **OPTIONAL** for MCP implementations overall ("strongly recommended" only for specific scenarios like per-user data access, audit requirements, or per-user rate limiting) — so all of this OAuth/RFC 8707/confused-deputy machinery is a real constraint only for MCP servers that *choose* to implement HTTP-transport authorization in the first place. STDIO-transport/local MCP servers, and any HTTP server that skips auth, sidestep this entirely — for better or worse (skipping auth is itself a real risk Kelvran's own brokering design would need to account for, not a clean escape hatch).

**Confidence:** High (primary MCP specification itself, cross-checked across the 2025-06-18 and 2026-07-28 revisions with identical substantive text; unanimous 3-0 votes on every sub-claim in this cluster except the general "OAuth 2.1 conventions, not one proprietary system" framing claim, which was 2-1 but still corroborated directly against the normative spec text).

### 5. The tool-call cost-accounting problem is real, unsolved by any competitor, and probably cannot reuse Kelvran's per-token Decimal ledger unmodified

**What the research found:** No competitor's MCP governance extends to dollar-cost accounting for tool execution (Finding 1). Kelvran's own `internal/costaccounting.Calculator.Calculate(model string, usage Usage) decimal.Decimal` is built around a `Usage`/`ModelPrice` shape that is fundamentally about *token counts × per-million-token price* — a unit that has no natural referent for a tool call. An MCP tool call is a request/response pair over JSON-RPC-shaped MCP semantics (`tools/call` with arguments, returning content blocks or an error) — not a token-metered LLM completion. Some tool calls have zero marginal cost to Kelvran (a local filesystem read); some have a real but non-token cost (a paid third-party API called by the MCP server, a metered compute-heavy operation, a per-invocation SaaS fee); none of this maps onto "prompt tokens × input price + completion tokens × output price." This is not a claim independently verified by a primary source in this pass (it is this report's own analysis of the shape mismatch, cross-referencing verified competitor behavior against Kelvran's actual current code) — flagged as such rather than presented as an adversarially-verified finding.

**Why it matters for Kelvran specifically:** this is the direct answer to research question 4's "what NEW cost-accounting problem does this introduce." If Kelvran wants outbound MCP brokering to serve its own differentiation thesis (agent-run-level cost/governance accountability tied to `agent_run_id`), it cannot simply pipe tool-call events through the existing `costaccounting.Calculator` — it would need either (a) a per-tool-call flat/metered price table (closer to Kong's cost-based rate-limiting formula from the sibling gateway report, adapted to a per-invocation unit instead of per-token) or (b) a two-tier model where token-priced LLM calls and unit-priced tool calls both roll up into the same `agent_run_id`-scoped ledger but via genuinely different pricing functions. Neither shape has been designed anywhere in this codebase yet — this is real, uncharted design work, not a reuse of existing infrastructure.

**Confidence:** Low-Medium — the "no competitor solves this" half is high-confidence (Finding 1's primary-source evidence); the "here's what Kelvran would need to build instead" half is this report's own synthesis against Kelvran's real code, not an independently-verified external claim.

## Recommendation

**MCP outbound brokering is a genuine extension of Kelvran's differentiation thesis on paper — but it is premature to build now, for two independent reasons, not one:**

1. **The one thing that would make Kelvran's MCP brokering non-redundant with Kong/Envoy/LiteLLM — dollar-cost accounting for tool execution tied to `agent_run_id` — has not been designed by Kelvran or solved by any competitor.** Building the brokering mechanics first (which is comparatively well-precedented — Kong, Envoy, and LiteLLM all show workable patterns) without first designing the cost-accounting unit would ship a fourth "yet another MCP proxy," not the "agent-run-level cost/governance accountability that no one else has" story `PRD.md` and the competitor-gaps research already stake out as Kelvran's actual thesis. The inbound side (exposing Kelvran's own APIs as MCP tools) is a smaller, more tractable, more clearly-scoped piece that does not have this problem — it is a request/response shape translation, not a new cost unit — and could reasonably be decoupled from outbound brokering as an earlier, lower-risk slice if there is real demand for it specifically.
2. **The spec-mandated auth mismatch (Finding 3) is a real, non-trivial design cost, not a paperwork detail.** Naive token passthrough is explicitly forbidden by the spec itself, so outbound brokering cannot be a thin proxy layer over the existing virtual-key `Verifier` the way `/v1/chat/completions` is — it requires new per-downstream-server credential-management machinery (closer in shape to Envoy's per-backend API-key-injection Secrets than to anything Kelvran has today), *or* a deliberately narrowed v1 that only brokers to MCP servers using simple, gateway-managed static API keys and defers full OAuth-flow MCP servers — itself a real scope decision that hasn't been made.

**Compared to the alternatives being researched in parallel:** routing-scope-expansion and hierarchical-budgets both extend infrastructure Kelvran already has working end-to-end (the router, `internal/budget.Tracker`) with comparatively well-precedented next steps (per the sibling `gateway-2026-09-06.md` report, e.g. active health-probing, OTel GenAI metrics). MCP/A2A brokering, by contrast, requires inventing a new cost-accounting primitive *and* new credential-management machinery before the "genuinely differentiated" version of it can exist — it is not a next-increment of existing work the way the other two tracks are. This is a legitimate reason to sequence it later, not a reason to abandon it: the underlying thesis (agent-run-level accountability extended to tool calls) is sound and consistent with what Kelvran is already building toward, and the market gap (no competitor ties MCP governance to a multi-step-run or dollar-cost concept) is real and durably confirmed by both this report and the separate competitor-gaps research it context-loads from. **Genuinely needs a demand signal** (a real user wanting to broker MCP tool calls through Kelvran specifically, not a speculative "agents will need this" bet) **before it displaces routing/budget work that is a more direct extension of what already exists and works.**

## Caveats

- **A2A (research question 3) is entirely unanswered**, not answered "stalled" or "still active" — zero surviving claims either way. Do not treat this report's silence on A2A as evidence of anything about A2A's real status; it reflects only this pass's search coverage.
- **Portkey's MCP Gateway claim was largely refuted, not confirmed** — an earlier draft claim asserted Portkey ships full inbound+outbound MCP brokering with a virtual-key-analogous auth model; adversarial verification found this claim's specific framing (virtual-key-*analogous*, built-for-MCP) did not hold up, though Portkey does ship *some* MCP governance (confirmed narrowly in Finding 1, rate-limiting only). Treat any prior informal claims about Portkey's MCP depth as unverified.
- **Envoy AI Gateway's "existing cost/quota layer extends to MCP" framing was explicitly refuted** (voted 1-2) — Envoy's MCP-specific governance is narrower (auth + observability, not cost/quota) than its general LLM-traffic governance; do not conflate the two.
- **Kong's "no Consumer/Consumer-Group scoping for MCP" claim was refuted** (voted 0-3) — the verification did not find clean evidence either way on this specific sub-point; it should not be treated as a confirmed friction point, just an unresolved detail.
- Time-sensitivity: Kong's MCP plugin changelog runs through 2026-07-02, Envoy AI Gateway's MCP docs are dated to its 1.1 release — both are current relative to this research date (2026-09-07), not stale, but this is a fast-moving area (the MCP spec itself moved from 2025-06-18 to 2025-11-25 to 2026-07-28 within roughly a year) and should be re-checked before any actual implementation, not treated as permanently settled.
- Finding 5's "what Kelvran would need to build" half is this report's own synthesis against Kelvran's actual `costaccounting` code, not an independently adversarially-verified external claim — flagged at low-medium confidence accordingly, distinct from the high-confidence competitor-evidence half of the same finding.
- This report did not investigate Bifrost, TensorZero, or Helicone's MCP support specifically (no claims on these three survived verification in this pass) — their absence here is analogous to the sibling `gateway-2026-09-06.md` report's own caveat about incomplete competitor coverage: absence of evidence, not evidence of absence.

## Open questions

- Is A2A still an active, evolving spec with real production adopters, or has it stalled/merged into MCP-adjacent tooling? Needs its own dedicated research pass — nothing here answers it.
- What would a per-tool-call pricing model actually look like in practice — flat per-invocation price, metered by downstream-reported cost, or something else — and should it live in `internal/costaccounting` as a second pricing function, or as a genuinely separate package, given `cache`'s existing "provider-agnostic, never imports adapter" dependency-direction discipline suggests Kelvran already has precedent for keeping cost-relevant concerns cleanly separated by concern rather than bolted onto one calculator?
- If Kelvran narrows outbound brokering to "static-API-key MCP servers only" as a smaller v1 (Finding 3's option b), does that scope still deliver enough of the differentiation thesis to be worth building, or does it mostly just replicate Kong's/Envoy's existing narrow-auth pattern without the cost-accounting piece that would make it distinctive?
- Is there any real, current user demand signal for MCP tool-call brokering specifically through Kelvran, as opposed to a speculative "agents will need this eventually" argument — and if not, what would that signal concretely look like before this moves off the backlog?
