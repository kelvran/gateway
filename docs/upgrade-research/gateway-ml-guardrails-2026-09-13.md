# ML/Classifier-Based Guardrails as a Complement to the Regex Guardrail Engine — Deep Research (2026-09-13)

## Question

Every detector in `gateway/internal/guardrail/` (`creditcard.go`, `email.go`, `iban.go`, `ipaddress.go`, `phone.go`, `promptinjection.go`, `secretkey.go`, `ssn.go`) is purely regex/pattern-based — no ML classifier of any kind exists anywhere in Kelvran. Kelvran already integrates with AWS Bedrock as a real, live provider adapter (`gateway/internal/adapter/bedrock/`). What does current (2026) practice for ML-classifier-based content moderation / prompt-injection defense look like — Meta's Llama Guard 4 and Prompt Guard 2, Anthropic's own safety classifiers, Azure AI Content Safety, and specifically AWS Bedrock Guardrails — and how do their latency/cost/accuracy tradeoffs compare against Kelvran's zero-added-latency regex engine and against `THREAT_MODEL.md`'s own OWASP LLM01 framing? For each option: is it `build_now` (wrap an existing integration) or `not_yet` (needs a bigger architectural commitment, e.g. self-hosting a model)?

## Context (Kelvran's own real, current state)

`gateway/internal/guardrail/` is exclusively regex/pattern matching — `policy.go`'s three Block-tier and three Warn-tier categories (`CategoryCredential`, `CategoryFinancialID`, `CategoryGovernmentID`, `CategoryContactInfo`, `CategoryNetworkID`, `CategoryPromptInjection`) are all detected by hand-written patterns, at zero added inference latency and zero per-request marginal cost. `THREAT_MODEL.md` itself already states this scope boundary explicitly: the detector set "was never intended to be a general content-moderation layer," and building one "would be a large, separately-scoped effort, not a natural extension of the PII/injection detectors that exist today." Kelvran has a real, live Bedrock adapter (`gateway/internal/adapter/bedrock/`) already in production use — no equivalent Azure or standalone-classifier-hosting integration exists.

## Summary

AWS Bedrock Guardrails is the one option in this research that is a genuinely low-activation-cost fit for Kelvran: it is a managed, API-configurable, model-agnostic service (not a model Kelvran would have to host) with a dedicated `PROMPT_ATTACK` filter and a metered, per-text-unit pricing model ($0.08–$0.15 per 1,000 units depending on filter type), directly reachable through the Bedrock integration Kelvran already has. Meta's Llama Guard 4 (12B, dense, single-GPU-runnable) and Prompt Guard 2 (86M/22M, binary jailbreak classifier) demonstrate a real, measurable accuracy ceiling above pure regex — Prompt Guard 2's Recall@1%FPR jump from 21.2% to 97.5% is the single most concrete accuracy data point found — but both ship only as open weights for self-hosted GPU inference, not as a managed API, making them a materially bigger architectural commitment than wrapping Bedrock. Anthropic's own Constitutional Classifiers confirm that even a maximally cost-optimized in-house ML safety layer still carries nonzero compute overhead (~1% after a cascaded linear-probe pre-filter, vs. 50% for the classifier alone) and, critically, is not offered as an external product Kelvran could call at all. Azure AI Content Safety's Prompt Shields is a second real, managed-API alternative directly mapping to OWASP LLM01's direct/indirect split, but it is a net-new cloud dependency Kelvran doesn't have today, unlike Bedrock. Across every vendor and OWASP's own 2026 Top 10, the consistent caveat is that no ML classifier — Bedrock's, Azure's, or Meta's — is positioned as a complete, standalone defense; all are meant to layer on top of existing controls, which is consistent with (not a threat to) keeping the regex engine as the zero-latency first line.

## Findings

### Finding 1 — AWS Bedrock Guardrails is a managed, model-agnostic, already-reachable service with a dedicated OWASP-LLM01 prompt-attack filter, priced per text unit rather than Kelvran's zero-marginal-cost regex model (confidence: high)

Bedrock Guardrails attaches to any Bedrock text/image foundation model simply by referencing the guardrail at inference time — no per-model hosted classifier is required, and policy checks run in parallel per configured policy specifically to minimize added latency. Its `PROMPT_ATTACK` filter type (`CreateGuardrail`'s `contentPolicyConfig.filtersConfig`) is configurable with `inputStrength` (`NONE`/`LOW`/`MEDIUM`/`HIGH`) and `inputAction` (`BLOCK`/`NONE`), and is exposed as its own billable SKU via the `InvokeGuardrailChecks` API at **$0.08 per 1,000 text units** — separate from, and cheaper than, the standard content-filter/denied-topic rate of **$0.15 per 1,000 text units**. AWS additionally makes regex-based PII detection *free* inside Guardrails while charging **$0.10 per 1,000 text units** for its ML/probabilistic PII detector — meaning Kelvran's existing regex detectors (`ssn.go`, `creditcard.go`, `email.go`, `iban.go`, `phone.go`, `secretkey.go`) already sit in the free tier of that exact tradeoff, and only an upgrade to Bedrock's ML PII detection would add per-unit cost. All of this is metered, per-request billing — a real cost-model shift from Kelvran's regex engine's zero marginal cost, but a small one at $0.08–$0.15/1K text units.

**Build now / not yet: build_now.** This is the lowest-activation-cost option in the whole research set: Kelvran already has a live Bedrock adapter, and wrapping the `PROMPT_ATTACK` filter as an additional, optional guardrail-engine backend (behind the same interface `promptinjection.go` implements) requires no new cloud account, no new SDK, and no self-hosted inference.

### Finding 2 — The prompt-attack filter has a real integration gotcha that any Bedrock-backed wrapper must account for (confidence: high)

When Bedrock Guardrails are used with `InvokeModel`/`InvokeModelWithResponseStream` (as opposed to the `Converse` API's separate `guardrailConfiguration` mechanism), the caller **must** wrap user-supplied content in explicit input tags to mark it apart from developer/system content. If no tags are present, the prompt-attack filter silently does not run at all for that call — every other Guardrails filter falls back to scanning the whole untagged prompt, but prompt-attack detection is the one exception that requires tagging to fire. Any Kelvran wrapper that proxies raw `InvokeModel` calls to Bedrock needs to either add this tagging itself or route prompt-attack checks through the decoupled `InvokeGuardrailChecks` API instead.

**Build now / not yet: build_now-adjacent** — not a blocker, but a concrete design requirement for Finding 1's wrapper, not an afterthought.

### Finding 3 — Meta's Llama Guard 4 and Prompt Guard 2 quantify a real accuracy ceiling above regex-only detection, but ship only as self-hosted, GPU-run open weights — not a managed API (confidence: high)

Llama Prompt Guard 2 is a purpose-built jailbreak/prompt-injection binary classifier (benign vs. malicious) shipped in two sizes: 86M and a smaller/faster 22M parameter variant. On Meta's own private jailbreak-detection benchmark, the 86M model's Recall@1%FPR jumped from **21.2%** (Prompt Guard 1) to **97.5%**, with AUC improving from .987 to .998 — a concrete, vendor-published accuracy gain no regex pattern set can claim. That accuracy has a latency cost: 92.4ms per classification on an A100 GPU (512 tokens) for the 86M model, dropping to 19.3ms for the 22M variant (a ~75% latency/compute reduction per Meta's own framing), with the 22M model trading some accuracy for that speed (Recall@1%FPR 88.7% vs. 97.5%). Llama Guard 4 is a broader, dense 12B-parameter multimodal moderation model (pruned from Llama 4 Scout, explicitly not a Mixture-of-Experts model) using an early-fusion architecture "to keep the overall size small" specifically so it "can be run on a single GPU" — i.e. self-hostable, but still real GPU-bound inference, unlike regex pattern matching which adds no inference latency at all. Both models are distributed as Hugging Face model-card weights for local/self-hosted inference, not as a hosted API endpoint.

**Build now / not yet: not_yet.** Adopting either model means Kelvran would need to stand up and operate a GPU-backed inference service — a materially bigger architectural commitment than wrapping an integration Kelvran already has (Bedrock). The accuracy numbers are real and compelling, but the self-hosting requirement is the blocking gap, not the model quality.

### Finding 4 — Anthropic's own production Constitutional Classifiers confirm that even a heavily cost-optimized in-house ML safety layer carries nonzero compute overhead, and isn't offered as an external product at all (confidence: high)

Anthropic's next-generation Constitutional Classifiers cascade a lightweight linear probe (screening all traffic) into a heavier "exchange classifier" only for flagged exchanges — the exchange classifier alone adds a **50% increase in compute** versus baseline inference, which the cascade design brings down to roughly **1% overhead** by only running the expensive component on pre-filtered traffic. Anthropic's own published follow-up work reports the resulting production system achieves a **0.05% flag rate** on real Claude Opus/Sonnet traffic with over **40x** lower compute overhead than the uncascaded exchange classifier. These figures illustrate that full ML-classifier moderation is genuinely far from Kelvran's zero-added-latency regex profile even in Anthropic's best-optimized, production-hardened form — and, separately, this system is described only as Anthropic's own internal safeguard applied to Claude traffic, with no mention anywhere of a standalone hostable model or public API Kelvran (or anyone) could call.

**Build now / not yet: not_yet — and not applicable regardless of cost/latency, since there is no external product to wrap.** Useful as a benchmark for what "as good as it gets" ML-classifier overhead looks like, not as an adoptable option today.

### Finding 5 — Azure AI Content Safety's Prompt Shields is a second real, managed-API alternative for OWASP LLM01, but is a net-new cloud dependency Kelvran doesn't already have (confidence: high, with one supporting claim at 2-1 vote)

Prompt Shields is a unified Azure AI Content Safety API that detects and blocks both direct (user-prompt) and indirect (document/third-party-content) prompt-injection attacks — a clean map onto OWASP LLM01's own direct/indirect split, and, like Bedrock Guardrails, offered as a managed cloud API rather than a model Kelvran would host. Microsoft's own documentation is explicit that the classifier "may not catch all attack vectors or may flag legitimate prompts" and instructs users to "always implement additional validation layers" — the same complement-not-replace framing AWS gives its own Guardrails.

**Build now / not yet: not_yet.** Architecturally this is the same shape as Finding 1 (managed API, no self-hosting), but Kelvran has no existing Azure integration to reuse — adopting it means standing up a brand-new cloud dependency, a real activation cost Bedrock Guardrails doesn't carry given Kelvran's existing adapter.

### Finding 6 — OWASP's own 2026 Top 10 states no reliable prompt-injection prevention mechanism exists today, and that defense must be architectural rather than interceptive — a framing constraint on how any ML-classifier guardrail should be positioned (confidence: high)

OWASP's Top 10 for LLM Applications 2026 states directly, under LLM01's mitigation section: "Prompt injection is intrinsic to current generative AI: LLMs make no architectural distinction between instructions and data, and their behavior is stochastic, so no reliable prevention mechanism exists today... Defense is therefore architectural rather than interceptive." The same section lists "filter at every modality boundary... run modality-specific classifiers" as one mitigation control among several in a mandatory defense-in-depth stack, explicitly noting "semantic filters are evadable by rephrasing or encoding." This is consistent with, not contradicted by, every vendor caveat found in this research (Finding 5's Azure quote; AWS's own guidance to layer Guardrails with other controls) — no ML classifier, including Bedrock Guardrails, should be treated as a complete or primary prompt-injection defense on its own.

**Build now / not yet: not applicable as a build item — this is a scoping constraint on Findings 1 and 5, not an option to adopt.** Any Bedrock-Guardrails wrapper should be framed and documented as one additional layer alongside the existing regex engine and Kelvran's other architectural controls (schema validation, tool-call argument scanning per `THREAT_MODEL.md`), never as a replacement for them.

## Caveats

- Bedrock Guardrails' content filters and denied-topics filter (Finding 1's $0.15/1K SKU) are broader content moderation, not prompt-injection-specific — `THREAT_MODEL.md` already states general content moderation is explicitly out of the guardrail package's current scope ("a large, separately-scoped effort, not a natural extension"). This research treats only the `PROMPT_ATTACK` filter and the PII filters as in-scope extensions of what `promptinjection.go`/PII detectors already do; the broader content-filter SKU is a scope-expansion decision for the user, not assumed here.
- The input-tagging gotcha (Finding 2) is documented specifically for `InvokeModel`/`InvokeModelWithResponseStream`; whether it also applies when calling the decoupled `InvokeGuardrailChecks` API directly (rather than through model-invocation-time attachment) was not independently confirmed in this research pass and should be verified against Kelvran's actual adapter call shape before implementation.
- Two verified claims (Bedrock's regex-vs-ML PII pricing split, and Azure's "complement not replace" framing) landed at a 2-1 vote rather than unanimous — both were still judged high-confidence on verification, but are flagged here for transparency.
- Several plausible-sounding claims about Meta's models did **not** survive adversarial verification and are deliberately excluded from the findings above: that Prompt Guard 2 or Llama Guard 4 require a *specific* VRAM figure (e.g. 24GB) to self-host, and Anthropic's specific red-teaming vulnerability-rate and prior-generation-overhead figures. The general, confirmed fact that both Meta models are self-hosted, GPU-run open weights (not a managed API) still stands on other, verified claims (the A100-latency benchmarks and Llama Guard 4's "single GPU" framing) — only the specific unverified numbers were dropped.
- Every pricing figure cited here (AWS Bedrock's $0.08/$0.10/$0.15 per 1,000 text units) reflects an August 2024/December 2024 rate cut confirmed still current as of multiple 2026 sources; AWS could change this at any time, and cost estimates for wrapping Bedrock Guardrails should be re-verified against the live pricing page before committing to a budget line.

## Recommendation for Kelvran

| Capability | Status | Trigger to revisit |
|---|---|---|
| AWS Bedrock Guardrails `PROMPT_ATTACK` filter as an optional guardrail-engine backend, reusing the existing Bedrock adapter | **build_now** | None — lowest-activation-cost option found; needs a design pass for the input-tagging integration detail (Finding 2), not new infrastructure |
| Bedrock Guardrails ML PII filter (`$0.10`/1K units) as an optional, opt-in backend alongside the existing free regex PII detectors | **build_now-adjacent** | Same wrap as above, different filter type; only worth it if regex false-negative rate on PII is measured and found wanting |
| Bedrock Guardrails content filters / denied topics (general content moderation, `$0.15`/1K units) | **not_yet / out of current scope** | A deliberate scope-expansion decision by the user — `THREAT_MODEL.md` already documents this as intentionally unbuilt, not an oversight |
| Meta Llama Guard 4 / Prompt Guard 2 (self-hosted, GPU-run open-weight classifiers) | **not_yet** | Would need a self-hosted GPU inference service as a new architectural component — revisit only if Bedrock Guardrails' accuracy/cost proves insufficient after real production data |
| Anthropic Constitutional Classifiers | **not_yet (not applicable)** | Would need Anthropic to ship this as an external product; no such product exists today |
| Azure AI Content Safety Prompt Shields | **not_yet** | Same managed-API shape as Bedrock Guardrails, but no existing Azure integration to reuse — revisit only if Kelvran adds a broader Azure dependency for other reasons first |
| "No ML classifier is a complete/standalone defense — always layer with existing architectural controls" (OWASP's own 2026 stance) | **build_now (as a documentation/framing principle)** | None — costs nothing to adopt now; should be stated explicitly wherever a Bedrock Guardrails wrapper is documented |

The one concretely low-risk next step is wrapping AWS Bedrock Guardrails' `PROMPT_ATTACK` filter (via the `$0.08`/1,000-text-unit `InvokeGuardrailChecks` SKU) as an additional, optional backend behind the existing guardrail-engine interface — it reuses an integration Kelvran already has in production, requires no new cloud account or self-hosted model, and directly extends `promptinjection.go`'s OWASP LLM01 coverage with a real ML accuracy gain. Everything that requires self-hosting a classifier model (Llama Guard 4, Prompt Guard 2) or doesn't exist as an external product at all (Anthropic's classifiers) remains not-yet-ready, independent of how compelling their accuracy numbers are.

## Open Questions

- Does Kelvran's actual Bedrock adapter call shape use `InvokeModel`/`InvokeModelWithResponseStream`, `Converse`, or the decoupled `InvokeGuardrailChecks` API — and does the input-tagging requirement from Finding 2 apply to whichever path is chosen?
- What is Kelvran's current measured false-negative rate for regex-based prompt-injection and PII detection in production traffic? Without that baseline, it's hard to know whether Bedrock Guardrails' ML accuracy gain (Finding 3's 21.2%→97.5% recall jump, for a different but related model) would move the needle enough to justify the per-unit cost.
- If a Bedrock Guardrails backend is added, should it run in parallel with the regex engine (defense-in-depth, per Finding 6) or as a fallback only when regex flags nothing — and does that choice change the effective per-request cost profile at Kelvran's real traffic volume?
- Is there any appetite to expand guardrail scope beyond PII/secrets/prompt-injection into general content moderation (Bedrock's content filters / denied topics, or Azure's broader Content Safety product), given `THREAT_MODEL.md` currently treats that as a deliberately unbuilt, separately-scoped gap?
