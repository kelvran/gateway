# Observability & Monitoring Stack Maturity — Beyond stdout-only OTel

Date: 2026-09-13 (synthesis written 2026-09-14) · 19 claims survived 3-vote adversarial verification

## Ground truth (re-verified directly against this repo before synthesis)

- `gateway/internal/telemetry/telemetry.go`'s `Config.Exporter` already accepts three values — `"stdout"`, `"otlp"`, or `"none"` — and the `"otlp"` branch is fully implemented: `otlptracehttp.New(ctx, otlptracehttp.WithEndpoint(cfg.OTLPEndpoint))` and `otlpmetrichttp.New(ctx, otlpmetrichttp.WithEndpoint(cfg.OTLPEndpoint))`. **The OTLP code path is not a gap — it is already written and only needs `exporter: "otlp"` + an `otlp_endpoint` value in `gateway/config.yaml` to activate.** `gateway/config.yaml` currently pins `telemetry.exporter: "stdout"` with the comment `# stdout is fine for a first pilot — no OTLP collector deployed yet.` This reframes the whole research question: the only real gap is a running collector to point at, not gateway code.
- `docker-compose.yml` already defines a `vector` service (image `timberio/vector:0.58.0-debian`, mounted against `docs/operations/vector-gatewayevents-s3-compose.yaml`, read-only Docker-socket bind-mount, a named `vector-data` volume) gated behind `profiles: ["vector-s3"]` — i.e. it is real, wired, and never started by a bare `docker compose up`. Its `env_file: .env.vector` is required and documented (`KELVRAN_GATEWAYEVENTS_BUCKET`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) but that file has never been created — confirming the task's disclosed "blocked, no bucket, no IAM creds" status.
- `docker-compose.yml` also defines `gateway`, `redis` (profile-gated), and `gateway2` (the multi-instance test rig), matching the task's ground truth.

These three facts anchor every recommendation below in what Kelvran's Compose file and Go code can already do without any new code.

## Executive summary

Kelvran's telemetry code is materially ahead of its deployed infrastructure: the OTLP exporter path is already implemented and inert, so the entire Q1 answer reduces to "add one Compose service and flip one config line" rather than any gateway change. The lowest-friction real backend for that role is `grafana/docker-otel-lgtm` — a single pre-built image bundling the OTel Collector, Prometheus, Tempo, Loki, Pyroscope, and Grafana — which the vendor explicitly scopes to dev/demo/test (not production), a scope that is a genuine match, not a mismatch, for Kelvran's disclosed single-pilot-tenant stage; SigNoz was evaluated and rejected for now because its install path changed to a CLI-generated multi-container (5+ services) stack, heavier than a pilot needs. Grafana's own file-based provisioning system is a real, native dashboards-as-code mechanism fitting Kelvran's "config as code" discipline, and LiteLLM's public repo ships a committed, importable Grafana dashboard JSON for the same OTel `gen_ai.*` metric namespace Kelvran's histograms already use, giving a concrete adaptable starting point. Vector's `aws_s3` sink can point at a local MinIO instead of real AWS S3 via a config-only `endpoint`/`force_path_style` change — a real unblocking path for the stalled Vector→S3 pipeline — but MinIO's community edition was archived by its maintainer in April 2026 and no longer ships pre-built binaries or Docker images, turning what used to be a one-line `docker pull` into a build-from-source step with an unmaintained dependency. Finally, formal burn-rate/SLO alerting is explicitly not a good fit yet per Grafana's own guidance (1-hour-minimum windows are unreliable for low/spiky traffic without synthetic load), so the existing report-only evals-trend check remains right-sized; only the *practice* of tiering future alerts by urgency is cheap enough to adopt now.

## Findings

### F1 — The OTLP switch-over is a config flip, not an engineering task (build_now)
**Confidence: high** (direct repo verification, not a web claim)

`telemetry.go` already implements the `"otlp"` exporter branch end-to-end (trace + metric exporters via `otlptracehttp`/`otlpmetrichttp`). The only missing piece is something to point `OTLPEndpoint` at. This means every downstream recommendation in this report is gated on standing up *a receiver*, not on writing Go code.

### F2 — `grafana/docker-otel-lgtm` is the lowest-friction real backend for this Compose shape, and its "dev/demo/test only" scoping matches Kelvran's actual pilot stage rather than disqualifying it (build_now)
**Confidence: high** (2 primary-source claims, votes 3-0 and 2-1)

A single image (`docker pull grafana/otel-lgtm:latest`) bundles the OTel Collector, Prometheus, Tempo, Loki, Pyroscope, *and* Grafana — addable as one more service in `docker-compose.yml` alongside `gateway`/`gateway2`/`redis`, with no separate wiring of storage components. The project's own README explicitly states this image "is intended for development, demo, and testing environments" and points production use cases at a paid Grafana Cloud product instead. Read against Kelvran's own disclosed status — a single real Bedrock pilot tenant, no SRE team, no committed cloud observability budget — this disclaimer describes exactly the use case Kelvran is in today, not a mismatch to route around. Recommendation: add it as an Compose service, set `telemetry.exporter: "otlp"` + `otlp_endpoint: "http://otel-lgtm:4318"` in `gateway/config.yaml`, and revisit graduating to a production backend (managed Grafana Cloud, or a hardened SigNoz/Alloy+Mimir stack) only once real multi-tenant production traffic exists.

### F3 — SigNoz was evaluated and is heavier than this pilot needs right now (not_yet — trigger: real multi-tenant traffic volume + appetite for operating a 5-container stack)
**Confidence: high** (2 primary-source claims, both 3-0)

As of SigNoz v0.130.0, the old `docker-compose.yml`-based install (`install.sh` + bundled `deploy/`) is deprecated; installation now goes through a new `foundryctl` CLI that generates Compose files from a `casting.yaml` config. The resulting stack is not a single container either way — a real self-hosted deployment comprises at least 5 components (ClickHouse server, PostgreSQL metastore, ClickHouse Keeper, `signoz-otel-collector`, and the combined `signoz/signoz` app), plus an optional `signoz-mcp` add-on. This is real operational surface area (more moving parts than `docker-otel-lgtm`'s single image) for a project with no dedicated SRE function; defer unless SigNoz's specific feature set (e.g. its native trace-to-log correlation UX) becomes a hard requirement.

### F4 — Grafana Alloy is a real single-binary multi-signal *collector*, but it is not a full backend and has its own durability gotcha, and two of the strongest framing claims about it did not survive verification (not_yet — needs its own follow-up verification pass before adoption)
**Confidence: medium** (1 confirmed claim 3-0, 1 confirmed claim 3-0, but 2 adjacent claims about Alloy were refuted 0-3 and 1-2 in the same research round)

Alloy genuinely has native pipelines for OpenTelemetry, Prometheus, Loki, and Pyroscope in one process — it could ingest Kelvran's OTel metrics, structured JSON logs, and traces without separate collector binaries. But it is a *collector*, not a storage/query backend: Alloy still needs something downstream (self-hosted Loki/Tempo/Prometheus, or Grafana Cloud) to actually store and query the data, so on its own it does not answer Q1 the way `docker-otel-lgtm` does. It also uses a Write-Ahead Log for metrics that defaults to an ephemeral directory — buffered data is lost on restart unless `--storage.path` is explicitly pointed at a mounted volume, a real Compose-deployment requirement if adopted. Two broader claims this research round tried to establish about Alloy — that it is officially framed as "a vendor-neutral distribution of the OpenTelemetry Collector," and that its officially-documented platform support confirms Linux-container/Compose viability — were both **refuted** on verification (votes 1-2 and 0-3). Treat Alloy as a plausible future piece, not a validated one; a dedicated verification pass (does it actually run cleanly in this repo's Compose shape, paired with what backend) is the concrete next step, not adoption.

### F5 — Grafana's file-based provisioning is Kelvran's real dashboards-as-code mechanism, no custom tooling needed (build_now)
**Confidence: high** (2 primary-source claims, both 3-0)

Grafana natively supports declaring datasources, dashboards, and plugins via YAML/JSON files under `provisioning/datasources`, `provisioning/dashboards`, `provisioning/plugins` — no UI clicking, no third-party wrapper. Grafana's own docs frame this explicitly as designed for version control, "making GitOps more natural." This slots directly into this repo's existing discipline (config as code, gitignored secrets only): a `docs/operations/grafana/provisioning/` directory committed to the repo, mounted into whichever Grafana container is chosen (F2 or F3), is the correct shape.

### F6 — Concrete first-dashboard panels have real peer precedent to copy rather than invent from scratch (build_now for 3 of 4 panels; one panel — fallback-hop frequency — has no confirmed peer precedent)
**Confidence: high** for the LiteLLM precedents (3 primary-source claims: 2-1, 3-0, 3-0); **flagged gap** for fallback-hop frequency

- **Cache hit rate by layer**: Kelvran already emits `kelvran.cache.lookup`/`.hit`/`.savings_usd`/`.l3.gate_outcome` — this panel needs no new instrumentation, only a Grafana panel definition.
- **Budget burn**: LiteLLM's own Prometheus integration exposes per-scope (team/API-key/user/org) budget gauges — max budget, remaining budget, remaining hours — and documents a `prometheus_initialize_budget_metrics: true` flag that runs a periodic DB-poll cron so these gauges stay populated even without live traffic. This is a directly comparable, checkable pattern against Kelvran's own budget-spend metrics for a "budget burn" panel, including the detail that a pilot with sparse traffic needs a poll-based (not purely request-driven) update path.
- **Guardrail verdict rate**: LiteLLM emits guardrail metrics *only when a guardrail actually runs*, using exactly three low-cardinality metrics (`requests_total`, `errors_total`, a `latency_seconds` histogram) labeled by `guardrail_name`/`status`/`hook_type` — never per-request unbounded labels. This is a validated peer precedent for building a guardrail-verdict panel off Kelvran's existing guardrail verdict logs without a cardinality blowup, matching this project's own stated discipline of avoiding unbounded-cardinality metric attributes (the same reasoning already applied to `cache_cross_instance_check`).
- **A literal starting template**: LiteLLM's repo ships a *committed, ready-to-import* Grafana dashboard JSON at `cookbook/litellm_proxy_server/grafana_dashboard/dashboard_genai_otel/grafana_dashboard.json`, charting `gen_ai.*` OTel metrics — spend, tokens, request rate, latency percentiles by model. Kelvran's own histograms already follow OTel GenAI semantic-convention naming (per `telemetry.go`'s comments), so this file is a realistic fork-and-adapt starting point rather than a from-scratch build.
- **Fallback-chain hop frequency** (the fourth panel named in the research question) has **no confirmed peer precedent** in this research round — a claim that LiteLLM exposes standard fallback counters (`cooled_down`/`successful_fallbacks`/`failed_fallbacks`) was checked and **refuted 0-3**. Kelvran's existing approach (span events on fallback hops) remains a bespoke design choice with no external validation either way; flagged as an open question below rather than asserted as either right or wrong.

### F7 — MinIO can technically unblock the stalled Vector→S3 pipeline with a config-only change, but the specific dependency now carries a real, newly-relevant maintenance risk (build_now, with a disclosed caveat that changes the risk calculus)
**Confidence: high** (4 primary-source claims: 3-0, 2-1, 3-0, 2-1)

Vector's `aws_s3` sink has a first-class `endpoint` option (paired with `force_path_style`, default `true`) explicitly documented for AWS-compatible services — pointing Vector at a local MinIO container instead of real AWS S3 needs zero code change, only a config value in `docs/operations/vector-gatewayevents-s3-compose.yaml`'s sink block plus a `.env.vector` filled with MinIO's local credentials instead of real AWS ones. MinIO's S3-API compatibility for exactly this kind of drop-in use is real and independently corroborated (not just MinIO's own marketing) by Vector's own sink schema. **However**, `minio/minio` was archived by its own maintainer on 2026-04-25 ("THIS REPOSITORY IS NO LONGER MAINTAINED," redirecting to a paid "AIStor Free"/"AIStor Enterprise" successor), and the community edition is now source-only — no new pre-compiled binaries or convenient Docker images are being published going forward, so what used to be a `docker pull minio/minio` one-liner now requires either building from source (`go install` or a local `docker build`) or deliberately pinning to an old, no-longer-patched image. This is still zero-cloud-cost and does not require the blocked real S3 bucket/IAM setup, so it remains the right *category* of interim fix — but the specific tool has gotten meaningfully less turnkey and now carries an unpatched-dependency risk that should be weighed (e.g. against evaluating the AIStor Free successor, which this research round did not independently verify) before committing engineering time to it.

### F8 — Formal burn-rate/SLO alerting is explicitly a poor fit at current traffic; only alert *tiering as a practice* is cheap enough to adopt now (not_yet for SLO tooling — trigger: real sustained multi-tenant production traffic large enough that hour-scale failure counts are a reliable signal; build_now for tiering as a lightweight practice)
**Confidence: high** (4 primary-source claims, all 3-0 except one 2-1)

Grafana's own SLO best-practices guidance recommends splitting burn-rate alerts into two tiers — fast-burn to on-call/escalation, slow-burn to a team channel reviewed during business hours — specifically to prevent alert fatigue; Kelvran's current single, flat, non-blocking `evals trend alert` (a report-only Wilson-interval check) has no such tiering today. But the same vendor guidance states burn-rate windows bottom out at 1 hour, and for low-traffic or spiky-traffic services its own stated "ideal solution" is to supplement with *synthetic* traffic rather than lean on a Minimum-Failures-count workaround — i.e. Grafana's own vendor guidance says hour-scale burn-rate SLO alerting is a poor fit for exactly Kelvran's current single-pilot-tenant traffic profile. Two lighter-weight tools exist in this space if a Prometheus backend materializes (F2/F3) and traffic grows — Sloth (a Prometheus-native SLO *rule generator*, not a backend, presupposing Prometheus+Grafana already exist) and SLO-Tracker (a minimal error-budget tracker explicitly positioned as a downstream companion to — not a replacement for — a full alerting stack, with an explicit warning against feeding it every raw alert) — but both solve a problem premature at current scale. The one genuinely cheap, no-new-infra move available now is adopting the fast/slow *routing convention* itself (which alerts are urgent-escalation vs. review-later) as a practice, independent of any burn-rate math or new tooling.

## Answers to the five research questions

1. **Lowest-friction real OTLP collector+backend for Compose today?** `grafana/docker-otel-lgtm` as one added Compose service (F2), paired with the already-implemented `otlp` exporter branch in `telemetry.go` (F1). Not premature — the vendor's own dev/demo/test scoping matches Kelvran's real current stage. SigNoz (F3) and Alloy (F4) are real but heavier or under-verified for this exact step.
2. **What's a genuinely useful first dashboard, and is dashboards-as-code real here?** Yes — Grafana's native file-based provisioning (F5) is a real, committable mechanism. Three of four requested panels (cache hit rate, budget burn, guardrail verdict rate) have real peer precedent to copy (F6), including a literally importable LiteLLM dashboard JSON for the same OTel `gen_ai.*` namespace; fallback-chain hop frequency has no confirmed peer precedent and remains an open design question.
3. **Can MinIO unblock the Vector→S3 pipeline without waiting on real S3+IAM?** Technically yes, config-only (F7) — but MinIO's community edition was archived and de-binaried in 2026, so the "interim" option is no longer as frictionless as it was when this pattern became popular; weigh a from-source build or the AIStor successor before committing.
4. **Is anything beyond the report-only evals-trend-alert worth adding now?** No formal SLO/burn-rate tooling yet (F8) — Grafana's own guidance says it's a poor fit for current traffic. Adopting a fast/slow alert-routing convention as a cheap practice is the one available "now" move.
5. **Anything else a 2026 survey would flag as a concrete next step?** The single most important finding is F1: this project already wrote the OTLP code path and never flipped it on — the "no backend yet" framing undersells how close this already is. The MinIO maintenance-status shift (F7) is itself worth flagging as a checkable fact for anyone about to reach for MinIO by habit/precedent without checking its current repo status first.

## Caveats

- Several of the strongest-sounding claims about Grafana Alloy's positioning and platform support were checked and **refuted** in this same research round (votes 1-2 and 0-3) — Alloy is included here only for its two claims that *did* survive verification (multi-signal pipelines, WAL durability gotcha); do not treat it as validated as a drop-in Compose service without a dedicated follow-up check.
- The LiteLLM fallback-counter claim (which would have given fallback-chain-hop-frequency a peer precedent, matching the other three dashboard panels) was refuted 0-3 — this is a real gap, not an oversight, in this research round's coverage.
- Two RAM/resource-footprint comparisons between SigNoz and the Grafana LGTM stack, sourced from a single third-party blog, were refuted (0-3 and 1-2) and are deliberately excluded from F2/F3 above — the "SigNoz is heavier" conclusion rests only on install-mechanism and container-count facts confirmed directly against SigNoz's own current docs, not on any resource-usage number.
- MinIO's post-archival landscape (AIStor Free's actual licensing/cost/setup friction as a substitute) was not independently verified this round — flagged as an open question below rather than asserted.
- This report's F1 ground-truth check (the already-implemented OTLP exporter) came from directly reading `gateway/internal/telemetry/telemetry.go` and `gateway/config.yaml` in this session, not from the prior adversarially-verified claim set — it is high-confidence direct repo evidence, but is called out separately from the 19 web-sourced claims for that reason.
