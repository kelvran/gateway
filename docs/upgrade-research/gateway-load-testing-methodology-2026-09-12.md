# Load-Testing and Performance-Benchmarking Methodology for LLM Gateways — Deep Research (2026-09-12)

## Question

What real, published methodology do comparable LLM gateway products (LiteLLM, Portkey, Kong AI Gateway, Cloudflare AI Gateway, Envoy AI Gateway) use to measure and publish their own request-path overhead (added latency, max sustainable throughput, memory/CPU under load), and what real numbers (if any) have they published? What load-testing tools/patterns are actually used in practice — generic HTTP load testers (k6, vegeta, locust) against a mocked/stubbed upstream, or something LLM-specific that accounts for streaming and variable response times? What are the real, known bottlenecks in a Go-based reverse-proxy-style gateway under load (connection pooling, goroutine/memory overhead, GC pressure from JSON marshaling) that a load test should specifically target? Is there a real, standard set of SLIs (p50/p95/p99 added latency, requests/sec ceiling, error rate under saturation) a gateway product should commit to before calling itself "production ready," and what do comparable products actually commit to?

## Context (Kelvran's own real, current state)

Already shipped and out of scope to re-litigate: per-deployment/per-key concurrency caps, weighted round-robin + health-probing + cost-tier routing, and real Docker-sandboxed evals execution (a separate subsystem from the gateway's own request path). What is **not** yet done, and is the real gap this research targets: Kelvran's own gateway has never been load-tested or benchmarked for its own latency/throughput overhead versus calling providers directly. This is a genuine, unaddressed prerequisite before real production traffic could safely be onboarded — every finding below is evaluated specifically against "can Kelvran build this now, without production traffic, since it tests the gateway's own overhead rather than real usage patterns."

## Summary

Every comparable gateway benchmark surveyed — Kong, LiteLLM, Portkey, Bifrost, TensorZero, and the cross-vendor AIGatewayBench/AI Gateway Bench project — uses the identical isolation technique: point the gateway at a local, deterministic mock/stubbed upstream (WireMock, a purpose-built Rust mock, or a "fake OpenAI endpoint") instead of a real provider, then compute overhead as gateway-mediated latency minus direct-to-mock latency, explicitly to strip out provider latency and network variance and leave only the gateway's own added cost. The load generators are uniformly generic, off-the-shelf HTTP tools — k6 (Kong) and Locust (AIGatewayBench, LiteLLM's older benchmarks) — not bespoke LLM-specific harnesses; where streaming needs to be measured, the pattern is to extend the generic tool with a purpose-built plugin (e.g. `locust-sse`) that adds a Time-To-First-Token metric on top of Locust's existing SSE support, rather than replacing the load tool itself. On the SLI side, Google's SRE literature supplies the standard, industry-wide vocabulary (the four golden signals — latency, traffic, errors, saturation — and multi-percentile latency SLO targets, e.g. p90 and p99 together), and LiteLLM is the one vendor found to publish a concrete, disclosed overhead number via a dedicated `x-litellm-overhead-duration-ms` response header (median/p95/p99 overhead shrinking from 12/29/43ms at 2 proxy instances to 2/8/13ms at 4 instances, with total request latency roughly halving). No comparable product was found publicly committing to a specific SLI bar (e.g. "p99 added latency < X ms") as a formal "production ready" contract — vendors publish raw self-run numbers instead, and those comparative rankings are unreliable across vendors (self-serving benchmarks produce contradictory orderings). The research surfaced essentially no confirmed evidence on Go-specific reverse-proxy bottleneck mechanics (connection pooling, goroutine overhead, GC pressure from JSON marshaling) — this remains a real open gap in the public record, not something this report can answer with verified sources.

## Findings

### Finding 1 — The universal published methodology across LLM gateway vendors is to benchmark against a deterministic mock/stubbed upstream, never a real provider, specifically to isolate the gateway's own added overhead (confidence: high)

Every vendor benchmark examined uses the same core technique. Kong's own benchmark (GitHub repo `Kong/kong_ai_gateway-portkey-litellm-benchmark` and its companion engineering blog post) mocks the LLM with WireMock exposing OpenAI-compatible endpoints "to have better control over the AI Gateways and remove the native LLM infrastructure variables, such as latency time and throughput" — testing Kong AI Gateway against Portkey and LiteLLM. The cross-vendor AIGatewayBench / AI Gateway Bench project (BerriAI's `ai-gateway-bench`, its `howardjohn` fork, and LiteLLM's own `litellm.ai/ai-gateway` marketing page, all describing the same tool) points every gateway under test — LiteLLM Rust, LiteLLM Python, Portkey, and Bifrost — at the same local, deterministic Rust mock-upstream service, computing `overhead = latency(client→gateway→mock) − latency(client→mock directly)` so that "provider latency and network noise are removed and what's left is the gateway's own overhead." LiteLLM's own documented benchmarks separately use an in-process "mock model" that intercepts requests at the httpx transport layer, plus a standalone "fake OpenAI endpoint," for the same isolation purpose, explicitly stating the mock "removes provider cost and provider latency while keeping the gateway request path active." TensorZero's and Bifrost's own benchmark docs independently confirm the identical pattern ("all benchmarks are on mocked OpenAI calls"). A cross-vendor blog (DeepInspect) independently corroborates, via each vendor's own primary docs, that LiteLLM, Bifrost, and Kong all benchmark against mocks and flags this as a shared methodology limitation across the industry, not an isolated choice by one vendor.

**Build now / not yet: build_now.** This requires no production traffic and no historical data — only a small deterministic mock upstream service (a stub that returns canned OpenAI/Anthropic-shaped responses, ideally with configurable simulated latency and both streaming and non-streaming modes) that Kelvran's gateway is pointed at during the load test. Overhead is then computed exactly as the surveyed vendors do: gateway-mediated latency minus direct-to-mock latency. This is the single most directly actionable, best-precedented finding in this report and should be the first piece Kelvran builds.

### Finding 2 — Load generation uses generic, off-the-shelf HTTP load testers (k6, Locust) — not bespoke LLM-specific harnesses — with streaming handled via a plugin extension rather than a replacement tool (confidence: high)

Kong's benchmark uses k6 as the load generator, run from an EC2 instance in the same VPC as the EKS cluster under test, with a fixed, disclosed load profile: 400 virtual users (each representing a distinct consumer), sustained for 3-minute runs (10-minute runs specifically when visualizing CPU), each request carrying 1000 prompt tokens, on gateway and mock-LLM nodes deliberately split across separate c5.4xlarge EKS nodes (16 vCPU/32GiB) with all gateways capped at 12 CPUs and no caching/auth policies enabled (pure proxy overhead only). The BerriAI/AIGatewayBench project instead standardizes on Locust for its load/streaming scenarios specifically, with non-load scenarios handled by plain Python scripts and concurrency/throughput charts driven by a separate persistent Rust `reqwest` client. Neither project reaches for an LLM-specific load tool as the primary driver. Where streaming responses specifically need first-token-level measurement, the pattern found is to extend Locust with a purpose-built plugin — `locust-sse` (Aleph Alpha) — which subclasses Locust's existing `SSEUser` class rather than building a new harness from scratch, and adds a Time-To-First-Token (TTFT) metric defined precisely as the latency from request start until the first SSE "append" event is received, reported as its own distinct row in Locust's stats output (`{request_name}_ttft`) alongside the normal per-request latency metric.

**Build now / not yet: build_now.** Kelvran can adopt k6 or Locust directly today against the mock upstream from Finding 1 — both are mature, well-documented, zero-cost-to-adopt tools with no dependency on real traffic. If/when Kelvran's gateway streaming path needs first-token-level measurement, the concrete, low-effort pattern to copy is a Locust (or k6) extension that timestamps the first streamed chunk separately from the final chunk, exactly as `locust-sse` does — this is a small, buildable addition, not a research-stage capability.

### Finding 3 — Google's SRE literature (four golden signals + multi-percentile latency SLOs) is the real, standard SLI/SLO vocabulary the industry uses, but no surveyed gateway vendor was found publicly committing to a specific numeric SLI bar as a "production ready" gate (confidence: high for the SRE framework itself; the "no vendor commits to a bar" observation is an absence-of-evidence finding, not independently falsifiable)

Google's SRE book defines the four golden signals — latency, traffic, errors, and saturation — as the canonical minimal monitoring set: "if you can only measure four metrics of your user-facing system, focus on these four." The companion SRE Workbook gives the standard mechanism for turning latency measurements into commitments: use multiple percentile thresholds together (not a single number) to capture both typical and tail behavior, illustrated with a worked example converting measured p90/p99 latencies into rounded SLO targets (e.g., 90% of requests under 450ms, 99% under 900ms). This is the vocabulary every gateway benchmark in this report implicitly reports against (p50/p90/p95/p99 style breakdowns), even though none of the surveyed vendors was found publishing a formal "we commit to p99 added latency under X ms before calling ourselves production-ready" statement — instead, each vendor publishes its own raw benchmark numbers (see Finding 4) without a standardized public commitment format across the industry.

**Build now / not yet: build_now.** Adopting the four-golden-signals framing and multi-percentile latency SLIs (p50/p95/p99 *added* overhead specifically, RPS ceiling, error rate under saturation) as Kelvran's internal quality bar requires no production traffic and no vendor coordination — it is a documentation and dashboarding exercise applied to the load test results from Findings 1–2. The open question is what numeric bar Kelvran should commit to; since no comparable vendor was found publishing a standardized public commitment, Kelvran would be setting its own bar rather than copying an industry number (see Open Questions).

### Finding 4 — LiteLLM is the one vendor found publishing concrete, disclosed gateway-overhead numbers via a dedicated response header, separate from total request latency; comparative rankings across vendors are not reliable (confidence: high on the LiteLLM numbers themselves; explicitly low/refuted on any cross-vendor ranking)

LiteLLM instruments proxy overhead per-response via a dedicated `x-litellm-overhead-duration-ms` header, reported separately from total `/chat/completions` latency, and publishes concrete numbers: at 2 proxy instances, median/p95/p99 overhead is 12/29/43ms; at 4 instances, 2/8/13ms; total median chat-completion latency roughly halves (200ms → 100ms) when doubling from 2 to 4 instances. This is a genuinely disclosed, methodologically-described number (Locust load generator, 1000 users, fake-OpenAI mock upstream, 4 CPU/8GB machines) — the strongest concrete overhead figure to survive verification in this pass. However, comparative rankings across vendors should be treated with real skepticism: multiple specific comparative claims (Bifrost's ~1ms vs LiteLLM Python's ~40ms/257ms p99; LiteLLM Rust's 0.66ms p99 as "3.5x lower than the next-best gateway"; TensorZero's sub-millisecond p99 at 10,000 QPS contrasted with LiteLLM failing at 1,000 QPS; Envoy AI Gateway's claimed real-GPU H100 endurance test) were all checked adversarially and did **not** survive verification (each vote-refuted). Separately, LiteLLM's own AIGatewayBench numbers and a competing MLflow self-published benchmark using a similar mocked-delay methodology report opposite rankings for the same comparison — a recurring pattern of each vendor's self-run benchmark favoring itself.

**Build now / not yet: build_now for the instrumentation pattern (a dedicated overhead header, separate from total latency); not_yet / do-not-trust for treating any single vendor's comparative ranking as ground truth.** Kelvran should add its own equivalent (e.g. `x-kelvran-overhead-duration-ms`) as part of the load-test harness output — this is copyable today with zero dependency on production traffic — but should not use any competitor's published ranking numbers as a target to beat, since none of those specific numbers survived independent verification.

### Finding 5 — Go-specific reverse-proxy bottleneck mechanics (connection pooling, goroutine/memory overhead per request, GC pressure from JSON marshaling) are a real gap in the public record this research could not confirm (confidence: n/a — no surviving evidence)

No claim addressing this research question survived adversarial verification. The one source that raised Go-vs-interpreted-language framing directly (a requesty.ai blog post arguing gateways should be built in Go) had its specific numeric comparisons (Bifrost ~1ms/500 RPS vs LiteLLM Python ~40ms average/~257ms p99, a cited 9.5x throughput / 54x p99 latency / 3x peak memory gap, and TensorZero's claimed sub-ms p99 at 10,000 QPS) refuted 0-3 on verification. The only part of that source that survived was its confirmation of the mock-upstream methodology (folded into Finding 1), not any bottleneck-specific claim. This means research question 3 — what a load test should specifically target inside a Go reverse-proxy gateway (connection-pool exhaustion to upstream providers, per-request goroutine/memory overhead, GC pauses from JSON marshaling under sustained concurrency) — remains genuinely open; this report found no vendor publishing verified data on these specific internal mechanisms, only end-to-end overhead numbers that don't decompose into cause.

**Build now / not yet: not_yet, but for a different reason than "no trigger exists" — the trigger is Kelvran running its own load test (Findings 1–2) and then profiling with Go's own tooling (`pprof` for CPU/goroutine/heap, `go test -bench` with `-benchmem` for allocation counts, GC trace via `GODEBUG=gctrace=1`) against the results.** This is not gated on production traffic at all — it is gated only on having a running load test to profile during. Once Findings 1–2 are built, this becomes immediately actionable using Go's standard profiling toolchain; no external precedent is needed because this is Kelvran instrumenting its own binary, not adopting an industry practice.

## Caveats

- The "no comparable vendor commits to a public SLI bar for production-readiness" observation in Finding 3 is an absence-of-evidence finding from this research pass, not a proven negative — it's possible such a commitment exists in a source this pass didn't surface (e.g., an enterprise SLA document behind a sales wall) rather than in public benchmark blogs/docs.
- Nearly every source in this report is vendor self-published (Kong's own blog/repo about itself vs. competitors, LiteLLM's own docs about itself, BerriAI/LiteLLM's own "open standard" framing of AIGatewayBench). Methodology descriptions (mock-upstream isolation, tool choice) were independently corroborated across multiple unrelated vendors and are trustworthy; comparative performance rankings were not, and several specific ranking claims were explicitly refuted during adversarial verification (see Refuted claims below) — treat any vendor's "we're faster than X" number as marketing until independently reproduced.
- `locust-sse` (Aleph Alpha) is a small, now-archived (as of Aug 2026), zero-adoption side project (0 stars/forks, 3 days of commit activity) — it demonstrates the generic-tool-plus-plugin pattern for streaming/TTFT correctly, but is evidence of a viable pattern, not of a widely-adopted industry-standard tool. Kelvran should treat it as a design reference to reimplement the pattern from, not as a dependency to adopt wholesale.
- A specific claim that Envoy AI Gateway was benchmarked against real H100 GPU infrastructure (rather than a mock) for 3 hours at ~2ms overhead was refuted on verification (vote 1-2) — this report cannot confirm any surveyed vendor benchmarked against real provider/GPU infrastructure end-to-end; the mock-upstream methodology in Finding 1 appears to be the practical industry default specifically because no one found a workable alternative, not because real-infrastructure testing was tried and rejected.
- Time-sensitivity: several primary sources (BerriAI/AIGatewayBench, LiteLLM's Rust-gateway blog post, Kong's benchmark repo) are from mid-2026 and describe fast-moving, actively-developed tools; specific version numbers and absolute performance figures should be expected to shift and were not re-verified as of this report's date.

## Refuted claims (not usable — for transparency)

- Envoy AI Gateway benchmarked with real H100 GPUs (3-hour endurance test, ~2ms overhead) — refuted 1-2.
- LiteLLM Rust gateway "0.66ms p99, 3.5x lower than next-best" — refuted 0-3.
- Bifrost vs LiteLLM Python specific throughput/latency/memory gap numbers — refuted 0-3.
- TensorZero sub-ms p99 at 10,000 QPS vs LiteLLM failing at 1,000 QPS — refuted 0-3.
- k6 allegedly has no concept of streaming and conflates TTFT with total generation time — refuted 0-3 (the `locust-sse`-style plugin pattern in Finding 2 is the confirmed counter-evidence: streaming-aware measurement is achievable, just via a plugin, and this specific claim about k6's limitations did not itself survive verification).
- p99 inter-chunk latency as gateways' single most important ("moat") metric — refuted 0-3.
- SRE Workbook rounding guidance ("round to nearest 50ms") as a stated explicit rule — refuted 0-3.
- LiteLLM's load tool described as "distributed mode, one master/multiple workers" — refuted 1-2 (Locust usage itself is confirmed; this specific operational detail is not).
