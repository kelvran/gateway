**Scope:** Kelvran ships two Docker images (`gateway/`, `evals/`) built by plain GitHub-hosted Actions runners, with no dedicated/hermetic build system. CI (`.github/workflows/ci.yml`) already runs `govulncheck` (gateway) and `pip-audit` (evals) for dependency CVE scanning as of 2026-09-11. There is currently **no SBOM generation, no container image signing, and no provenance attestation** anywhere in CI or either service's Dockerfile. This research covers 2026 practice for SBOM generation (SPDX vs CycloneDX, Syft/Trivy), container signing (cosign/Sigstore keyless via GitHub Actions OIDC), and SLSA provenance levels realistically reachable on stock GitHub Actions — then sorts findings into `build_now` (concrete, low-effort CI additions) vs `not_yet` (needs an external trigger before it's worth the cost). 17 claims survived 3-vote adversarial verification across 3 independent primary/near-primary source sets (Sigstore/cosign official docs, GitHub's own docs, and three real-world example workflows: `j-dahl7/container-sbom-signing-attestation`, `tracelane/tracelane`, `this-is-tobi/github-workflows`).

**Already shipped (not re-litigated):** `govulncheck` (gateway), `pip-audit` (evals) dependency CVE scanning in CI, 2026-09-11.

## Executive Summary

For a project at Kelvran's size — two Docker images, GitHub-hosted Actions, no dedicated build system — the right-sized, low-effort stack is: **Syft or Trivy for SBOM generation** (either format works; GitHub's own tooling accepts both SPDX and CycloneDX), **cosign keyless signing via GitHub Actions OIDC** for image signing (no key management at all — Sigstore's Fulcio/Rekor issue short-lived certs off the workflow's own OIDC token), and **GitHub's first-party `actions/attest` / `actions/attest-sbom` actions** to wrap both into signed attestations, which reaches **SLSA Build Level 2 "by default"** with zero extra architecture. All three additions slot into the existing image-build job and need only workflow-level permission grants (`id-token: write`, `attestations: write`, `packages: write`) — no secrets, no external key vault, no new infrastructure. **SLSA Build Level 3** (provenance non-forgeability via a reusable-workflow isolation boundary) and the now-deprecated `slsa-github-generator` project are correctly out of scope today: L3's specific value — proving the build pipeline itself wasn't tampered with by whoever authored the calling workflow — matters most once external consumers are demanding verifiable provenance, which is not yet a Kelvran requirement. Full SLSA L3 hermetic/dedicated-builder setups (the kind used by large multi-team orgs) are genuine enterprise overkill for a single-maintainer-shaped, ~2-image project and should stay out of scope indefinitely absent a specific trigger.

## Findings

### Finding 1 — Container image signing: cosign keyless via GitHub Actions OIDC is the unambiguous 2026 default, and it requires zero long-lived key management
**Confidence: high** (7 merged claims, all 3-0 or 2-1 votes, corroborated by 2 independent real-world CI examples plus official Sigstore/GitHub docs)

Cosign's default signing mode since ~2021-2022 (still current, unchanged practice in 2026) is **keyless signing**: the workflow authenticates to an OIDC provider (GitHub Actions' own token qualifies out of the box), Sigstore's public-good **Fulcio** certificate authority issues a short-lived certificate bound to that OIDC identity, the signing event is recorded to the public **Rekor** transparency log, and the ephemeral private key is discarded immediately after use. There is no `cosign.key`, no `COSIGN_PRIVATE_KEY`/`COSIGN_PASSWORD` secret, and no key rotation/storage burden anywhere in this flow — confirmed against the official `sigstore/cosign` README, `docs.sigstore.dev`, and two independently-verified real GitHub Actions workflows (`tracelane/tracelane`'s `release-container.yml` and `j-dahl7/container-sbom-signing-attestation`'s `supply-chain.yml`), both of which sign with a bare `cosign sign --yes <image>@<digest>` step and carry no key-material secrets at all.

The only workflow-level requirement is the `id-token: write` permission (to let the job mint the OIDC token cosign exchanges for the Fulcio cert) — both `gh-action-sigstore-python` and `cosign-installer`-based flows need exactly this, nothing more, per Sigstore's own quickstart-ci guide.

**Verdict: build now.** This is the textbook "syft + cosign in the existing build-images CI job" addition named in the research prompt. Concretely: add `sigstore/cosign-installer`, then `cosign sign --yes ${REGISTRY}/${IMAGE}@${DIGEST}` as a step in the job that already builds and pushes each of Kelvran's two images, gated to `id-token: write` + `packages: write`, running only on the push-to-main/tag paths that currently publish images. No new secrets, no new infrastructure, ~10 lines of YAML per image.

### Finding 2 — SBOM generation: mature, low-effort tooling; GitHub's own attestation format accepts either SPDX or CycloneDX, so the format choice is a preference, not a constraint
**Confidence: high** (4 merged claims, all 3-0, cross-checked against 3 independent real workflow examples showing all 3 common tool/format combinations in production)

SBOM generation from a built container image is a solved, one-step CI operation. Three real, currently-maintained example workflows demonstrate the space: (1) `j-dahl7/container-sbom-signing-attestation`'s workflow runs **Syft twice against the same image digest** in one step, producing both `sbom.spdx.json` and `sbom.cdx.json` — i.e., generating *both* formats costs one extra CLI invocation, not a format decision; (2) `tracelane/tracelane` uses **Anchore's `sbom-action`** (a wrapper around Syft) to emit CycloneDX JSON, then attaches it via `cosign attest --type cyclonedx`; (3) `this-is-tobi/github-workflows`'s reusable `attest-docker.yml` uses **Trivy** to emit an SPDX-only SBOM, attached via `cosign attest --type spdxjson`. GitHub's own native attestation tooling (`actions/attest-sbom`, wrapping `actions/attest`) explicitly supports **either** SPDX or CycloneDX predicate — it does not mandate one, confirmed directly against `docs.github.com`'s artifact-attestations page and the `actions/attest-sbom` repo.

**Verdict: build now.** Format choice is genuinely low-stakes for Kelvran's scale — CycloneDX has stronger tooling momentum in the container-signing ecosystem (2 of 3 examples above use or attach it), but SPDX is equally valid and is what Trivy defaults to. Given Kelvran already needs a vulnerability scanner (it doesn't currently have one in the image-build path — `govulncheck`/`pip-audit` run against source dependencies, not the built image), **Trivy is worth considering as a single tool that covers both container CVE scanning and SBOM generation in one step**, though Syft is the more SBOM-purpose-built option if a dedicated image scanner isn't wanted yet. Either way: one CI step, no new secrets, attach the output as a cosign/GitHub attestation.

### Finding 3 — SLSA Build Level 2 is reachable "by default" with GitHub's native attestations on GitHub-hosted runners — no special architecture needed
**Confidence: high** (4 merged claims, 3-0 and 2-1 votes, corroborated independently against the SLSA v1.0 spec itself, not just GitHub's own framing)

GitHub's own docs state plainly: "Artifact attestations by itself provides SLSA v1.0 Build Level 2" — using GitHub Artifact Attestations (the `actions/attest` family) on GitHub-hosted runners reaches SLSA Build L2 **by default**, with no reusable-workflow isolation or other architectural change required. This is independently corroborated by the SLSA v1.0 spec's own Build Level requirements table: L2 = a hosted build platform (GitHub-hosted runners satisfy "hosted, not an individual's workstation") + signed, consumer-verifiable provenance (Sigstore-backed attestations satisfy this) — with no isolation requirement at that level. The only setup cost is the same few lines of YAML already covered under Findings 1-2 (permissions block + the `attest`/`attest-build-provenance` action call); GitHub Artifact Attestations use Sigstore for keyless signing, and public repos use the shared Sigstore Public Good Instance with signing events written to a public, readable transparency log — so, again, no long-lived keys to manage.

**Verdict: build now, but frame as a byproduct, not a separate initiative.** Once Findings 1 and 2 are implemented (image signing + SBOM attestation via `actions/attest`), SLSA L2 provenance is a natural extension of the same job: add an `actions/attest-build-provenance@v4` (or the container-image variant) call alongside the SBOM/signing steps, requiring only `id-token: write`, `contents: read`, `attestations: write`, plus `packages: write` for container images specifically. This is the "free" tier of provenance — do not build a bespoke provenance mechanism when GitHub's native action reaches the same standardized level in a few lines.

### Finding 4 — SLSA Build Level 3 requires architectural isolation (a reusable workflow) that a single-maintainer project without a dedicated build system should defer
**Confidence: high** (2 merged claims, 3-0 and 2-1 votes; one closely-related claim about "no infrastructure overhaul" was refuted 1-2 and is excluded)

The specific mechanism that elevates provenance from L2 to L3 is architectural: converting the attestation/signing step into a **reusable workflow** so it executes in a build context (VM/runner) controlled by the reusable-workflow's own identity, not by the calling workflow's author — this is what makes the resulting provenance *non-forgeable* (a compromised build step in the calling workflow cannot impersonate the identity that produced the provenance). GitHub's own guidance and the official SLSA spec agree this is the load-bearing difference between L2 and L3, not a documentation/formatting nicety. However, a claim asserting this is reachable "via one additional step, not a major infrastructure overhaul" was specifically **refuted** on adversarial review (1-2) — the surviving evidence supports the *mechanism* (reusable-workflow isolation) but not the framing that it's trivially cheap to adopt; it is a real architectural change to how the build pipeline is structured, not a copy-paste addition.

**Verdict: not yet.** L3 exists specifically to defend against a threat model — a compromised or malicious calling-workflow author forging provenance — that isn't a live concern for a single-maintainer-shaped project without external build contributors to a trust boundary. **Named trigger:** an external consumer or downstream integrator explicitly requiring L3-grade, non-forgeable provenance before they'll consume Kelvran's images, or Kelvran onboarding outside contributors with write access to workflow files (at which point the calling-workflow-author trust boundary becomes real). Until then, L2 (Finding 3) already gives Kelvran a standards-recognized, signed, verifiable provenance baseline at near-zero incremental cost — jumping to L3 pre-emptively would be solving a threat that doesn't exist yet.

### Finding 5 — `slsa-github-generator` is deprecated; don't reach for it — GitHub's native `actions/attest` is the maintained path
**Confidence: high** (1 claim, 3-0, directly confirmed by the project's own README deprecation notice)

The SLSA project's own `slsa-github-generator` tool — historically the way to bolt SLSA provenance onto a GitHub Actions build — is **no longer actively maintained**. Its maintainers' own README states they are "working on guidance and simpler tooling to replace it" and explicitly names **GitHub artifact attestations** (`gh attestation verify` / `actions/attest`) as that replacement. Provenance already generated by the old tool remains valid, and existing workflows using it continue to function, but they should not be assumed to receive updates (including for GitHub Actions runtime deprecations).

**Verdict: not yet — actively avoid.** This isn't a "maybe later" item; it's a steer-away finding. Kelvran should build directly on `actions/attest`/`actions/attest-sbom` (Findings 2-3) rather than evaluating or adopting `slsa-github-generator`, since the latter is a lower-maintenance, soon-to-be-legacy path to the same L2 outcome GitHub's native tooling already covers.

## Synthesis: build_now vs not_yet

| Item | Verdict | Effort | Why |
|---|---|---|---|
| SBOM generation (Syft or Trivy, SPDX or CycloneDX) | **build_now** | ~1 CI step per image | Mature, one-command, no new secrets; format choice is low-stakes |
| Cosign keyless image signing via GitHub OIDC | **build_now** | ~10 lines YAML per image | Zero key management; only needs `id-token: write` |
| SLSA Build Level 2 via `actions/attest`/`attest-build-provenance` | **build_now** | ~1 more step, same job | "By default" on GitHub-hosted runners; byproduct of the two items above |
| SLSA Build Level 3 (reusable-workflow isolation) | **not_yet** | Architectural change to CI structure | Defends against a calling-workflow-author trust boundary that doesn't exist yet for a single-maintainer project |
| `slsa-github-generator` adoption | **not_yet (avoid)** | N/A | Deprecated by its own maintainers in favor of GitHub's native attestations |
| Full SLSA L3 hermetic/dedicated-builder infra | **not_yet** | Large — new build system | Enterprise-scale overkill; no GitHub-Actions-only path reaches this without a dedicated build platform |

## Caveats

- Two closely-related but stronger claims were refuted on adversarial review and are deliberately excluded from the findings above: (1) that GitHub's attestation mechanism can natively *bundle* an SBOM together with a provenance attestation as one artifact (refuted 0-3 — they remain two separate attestation calls/artifacts, even though both use the same underlying `actions/attest` action); (2) that reaching SLSA L3 on GitHub-hosted runners is "one additional step, not a major infrastructure overhaul" (refuted 1-2 — the isolation mechanism is real, but the framing of its adoption cost is not supported).
- A `slsa-github-generator` "Container Generator" claim (dedicated container-image provenance generator, cosign-attestation-compatible, stable since v1.4.0) was refuted 0-3 — do not assume such a component exists or is production-stable; this reinforces Finding 5's "avoid this project" verdict rather than contradicting it.
- Two workflow examples (`j-dahl7/container-sbom-signing-attestation`, `tracelane/tracelane`) combining `docker/build-push-action`'s built-in `provenance:`/`sbom:` flags with a separately-run `actions/attest-build-provenance` step, described as jointly reaching "SLSA Build Level 3," were both refuted 0-3 — treat any workflow claiming L3 from Docker Buildx's built-in flags plus a bare attest-build-provenance call as unverified marketing-level framing, not a confirmed L3 path. This matters directly for Finding 4: the *only* verified L2→L3 mechanism found this round is reusable-workflow isolation, not a Buildx-flag shortcut.
- All Sigstore/cosign mechanism claims (Findings 1, 3) describe long-stable (since ~2021-2022), unchanged-in-2026 behavior — low time-sensitivity. The SLSA deprecation finding (Finding 5) is comparatively fresher (the migration guidance is actively being written per the maintainers' own README) and worth re-checking if this research is revisited more than a few months out.
- General web search (Google/Bing/DuckDuckGo) was blocked by robots.txt/bot-challenges during verification for several claims, and Exa MCP hit rate limits repeatedly — several high-confidence findings above rest on direct primary-source fetches (official docs, live GitHub repos/workflows) rather than a broad adversarial web sweep for dissenting opinions. This is noted per-claim above where it occurred; it did not prevent verification, since primary-source fetches are the strongest evidence tier anyway, but a broader sweep was not exhaustively possible.

## Open Questions

1. Should Kelvran standardize on CycloneDX or SPDX for its SBOMs, given GitHub's tooling accepts either? (No technical blocker either way — this is a preference/ecosystem-fit decision, not something this research resolved.)
2. If Trivy is adopted for SBOM generation, should it also be turned on as a container-image CVE scanner (distinct from the existing source-dependency `govulncheck`/`pip-audit` scans), given it can do both in one tool? Not evaluated this round.
3. What is the actual named trigger that would justify SLSA L3 investment — a specific customer/integrator requirement, a compliance mandate, or simply onboarding external contributors with workflow-file write access? This research identified the *mechanism* but not a concrete Kelvran-specific trigger condition beyond the generic "external consumer demands it."
4. Does Kelvran want signed attestations verified anywhere downstream (e.g., a `cosign verify`/`gh attestation verify` gate before deploy), or is generating them sufficient for now? This research covered generation only, not consumption/enforcement.
