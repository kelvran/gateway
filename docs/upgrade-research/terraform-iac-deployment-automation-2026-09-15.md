# Terraform / IaC Deployment Automation — Upgrade Research (2026-09-15)

> **Builds on, does not re-litigate:** `docs/upgrade-research/kubernetes-production-deployment-2026-09-14.md` (the Kustomize manifests at `deploy/k8s/`, the documented-but-not-live External Secrets Operator decision) and `docs/upgrade-research/secrets-management-lifecycle-2026-09-15.md` (the `SessionTokenEnv`/STS-over-static-key finding, `make config-safe`). Those reports cover the Kubernetes workload layer and the credential-lifecycle layer respectively; this report covers the one layer neither touched — provisioning the underlying cloud resources (IAM, S3, networking, secrets infrastructure) those workloads actually run against, which today has zero automation of any kind.

**Scope.** Kelvran deploys today via Docker Compose only (`docker-compose.yml`, real) plus a set of Kustomize manifests (`deploy/k8s/`, real but never applied to a live cluster). Neither artifact provisions any actual cloud infrastructure — there is no Terraform, Pulumi, CloudFormation, or other IaC anywhere in this repo (`find . -iname '*.tf'` returns nothing). Two concrete, already-documented gaps this blocks: (1) `evals`' Bedrock-judge path (`judge/providers.py`) needs a scoped AWS IAM identity for `bedrock:InvokeModel`, currently satisfied only by hand-issued static keys (the exact credential type that leaked three times per the secrets-management report); (2) the `vector`/`vector-s3` Compose profile that ships `gatewayevents_v1` to S3 is explicitly `docs/operations/DEPLOY.md`-documented as "blocked pending a real bucket and a real, minimally-scoped IAM credential that don't exist yet." This report surveys how comparable self-hosted LLM gateway/infra projects structure their official Terraform, and identifies concrete, low-risk automation Kelvran could adopt to close both gaps. 20 claims survived 3-vote adversarial verification.

**Already shipped (not re-litigated):** Docker Compose as the only live deployment shape; Kustomize K8s manifests at `deploy/k8s/` (never applied to a real cluster, `replicas: 1` deliberate, ESO named but not deployed); `gateway/internal/gateway/controlplane/config.go`'s `SessionTokenEnv` field (STS session-token support already wired end-to-end, per the secrets-management report); `make config-safe` secret-redaction wrapper.

---

## Executive Summary

Kelvran has no Terraform or other IaC today, and the two comparable self-hosted LLM gateway projects surveyed both do — LiteLLM ships two official, actively-maintained Terraform Registry modules (AWS and GCP) that provision the entire stack a gateway needs (compute, database, cache, object storage, secrets, networking, load balancer) in one apply, while Portkey ships a purpose-built multi-cloud IaC repo (ECS + Azure Container Apps) with production deployment strategies (blue/green, canary, automatic rollback) far beyond Compose's single-node shape. The consistent structural pattern across both projects and AWS's own official reference architecture is to split Terraform by concern — one root module per resource domain (IAM, network, S3, secrets, compute, load balancer) rather than one monolith — and to keep secrets-management infrastructure and PR-gated plan/apply automation as separate, deliberately bolted-on layers rather than folding everything into a single tool. For Kelvran specifically, the highest-leverage, lowest-risk first module is narrow: an IAM role scoped to `bedrock:InvokeModel`/`InvokeModelWithResponseStream` against a specific foundation-model ARN (not a wildcard) plus the one S3 bucket the `vector-s3` profile is already blocked on — both are self-contained, don't require a live Kubernetes cluster to be useful, and directly unblock two gaps this repo's own docs already flag as open. PR-gated plan/apply automation (Atlantis, or a GitHub Actions apply-on-main-push gate) is a real, well-established next step but should follow, not precede, the first working module, since there's nothing to gate yet.

## Findings

### Finding 1 — Comparable self-hosted LLM gateways ship official, actively-maintained Terraform modules that provision the full stack, not just compute
**Confidence: high** (5 merged claims, 3 unanimous / 2 at 2-1, all against primary sources — the actual Terraform source, not marketing pages)

LiteLLM — the most directly comparable OSS self-hosted LLM gateway to Kelvran — publishes two official modules on the public Terraform Registry, `BerriAI/litellm/aws` and `BerriAI/litellm/google`, maintained in-repo at `github.com/BerriAI/litellm/tree/main/terraform/litellm/{aws,google}` (confirmed live via `gh api`, pushed within 24 hours of this research date). Both provision the *entire* microservices stack in one apply, not just the compute layer: the AWS module stands up three ECS Fargate services (gateway/backend/UI), an Aurora Postgres cluster with IAM database authentication enabled, an encrypted multi-AZ ElastiCache Redis replication group, a versioned S3 bucket, Secrets Manager entries for the master key and DB password, and an Application Load Balancer with path-based routing (`/v1/chat/*` → gateway, `/_next/*` → UI, everything else → backend) — plus a one-off ECS migration task that runs before the services start. The GCP module provisions the direct equivalent (Cloud SQL Postgres, Memorystore Redis, GCS, Secret Manager, Cloud Run, HTTPS load balancer). Every category of resource these modules provision — IAM, object storage, secrets, networking — is a category Kelvran's own docs already flag as needed and unautomated: `evals`' Bedrock IAM identity, the `vector-s3` bucket, and the ESO secrets-backend decision from the Kubernetes report.

**Verdict: build now** — not by adopting LiteLLM's module wholesale (Kelvran's shape differs: no Aurora/ElastiCache need yet, single Go binary not three services), but by treating "one apply provisions the categories of resource the workload actually needs" as the target shape for Kelvran's own first module, scoped down to what's actually blocked today (IAM + S3, not a full VPC/RDS/ALB stack Kelvran has no present use for).

### Finding 2 — AWS's own reference architecture splits Terraform into narrow, single-purpose modules rather than one monolith, including a standalone module for exactly the kind of S3 bucket Kelvran needs
**Confidence: high** (3 merged claims, all unanimous, verified directly against the live repo's file tree, not just its README prose)

The AWS Solutions Library's official multi-provider generative-AI-gateway guidance (`aws-solutions-library-samples/guidance-for-multi-provider-generative-ai-gateway-on-aws`) does not ship one Terraform stack — it ships four independent root modules, each with its own state: `litellm-terraform-stack` (the main deployment), `litellm-private-load-balancer-ec2-terraform`, `litellm-s3-log-bucket-terraform`, and `litellm-fake-llm-load-testing-server-terraform`. Direct inspection of the repo confirms `litellm-s3-log-bucket-terraform` is a genuinely separate, standalone root module (its own `provider.tf`/`s3.tf`/`variables.tf`/`outputs.tf` and its own remote-state key), deployed *before* the main stack, which then consumes its bucket ARN as an input variable for downstream IAM permissions — this is architecturally the same shape as Kelvran's own `vector-s3` gap: a log/event bucket that needs to exist and have a scoped IAM credential *before* the workload that writes to it can run. The same reference architecture also provisions distinct, persona-scoped IAM roles (`litellm-stack-developers`, `litellm-stack-operators`, `litellm-stack-eks-nodegroup-role`) rather than one broad role, explicitly framed as least-privilege.

**Verdict: build now.** The direct, narrow takeaway for Kelvran: a standalone `terraform/s3-gatewayevents/` root module (its own state, deployed independently of any future compute module) that provisions exactly the bucket the `vector-s3` Compose profile is blocked on, plus a minimally-scoped IAM policy/role for it — mirroring this pattern is lower-risk than bundling it into a larger, not-yet-needed stack.

### Finding 3 — Least-privilege Bedrock IAM scoping to a specific model ARN is a documented, real Terraform pattern — directly closes `evals`' Bedrock-judge credential gap
**Confidence: high** (1 claim, unanimous, verified against the actual module source, not just its docs page)

A published AWS AgentCore Terraform module's production-configuration example scopes `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` to one specific foundation-model ARN (e.g. `arn:aws:bedrock:us-east-1::foundation-model/anthropic.claude-3-5-sonnet-20241022-v2:0`), not a wildcard `Resource: *`, and the module's own security-notes section states this as the recommended pattern explicitly. (A related, broader claim — that this specific module's *default*, out-of-the-box policy grants wildcard Bedrock access unless a flag is flipped — did not survive verification and should not be relied on; treat the wildcard-vs-scoped question as module-specific, not a general default.) This directly matches `evals/docs/operations/DEPLOY.md`'s own documented need: `judge/providers.py`'s `make_bedrock_call_model` currently reads `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_REGION` via boto3's standard credential chain, with no IaC-defined scoping at all today.

**Verdict: build now.** A small, self-contained `terraform/iam-bedrock-judge/` module — one IAM role/policy scoped to the two Bedrock model ARNs `evals`' judge panel actually calls (Sonnet 5 + Haiku 4.5, per `docs/operations/DEPLOY.md`'s env-var table) — is buildable today, independent of any cluster or larger stack, and is a direct root-cause fix rather than a rotation band-aid for the credential class the secrets-management report already flagged as recurringly leaking.

### Finding 4 — Portkey's official multi-cloud Terraform IaC demonstrates production deployment automation (HA, blue/green, automatic rollback) well beyond Compose, deliberately splits secrets out of Terraform, and supports both direct-run and version-pinned-module consumption
**Confidence: high** (4 merged claims, all unanimous, verified against live repo + actual `.tf`/README content, not marketing copy)

Portkey-AI publishes `portkey-gateway-infrastructure`, an official IaC repo (org-owned, not a fork) whose stated purpose is deploying their self-hosted gateway "across multiple cloud platforms" — live modules exist for AWS ECS and Azure Container Apps. The ECS module's Terraform variables genuinely implement high availability across multiple AZs and four deployment strategies (Rolling, Blue/Green, Canary, Linear) plus a deployment circuit breaker with automatic rollback (`gateway_deployment_circuit_breaker`/`dataservice_deployment_circuit_breaker` variables) — a level of deployment automation Kelvran's single-node Compose setup and `replicas: 1` Kustomize manifest don't attempt. Two structural details are directly relevant to how Kelvran should organize its own future Terraform: (1) the repo deliberately keeps secrets management in a *separate* tool from compute/networking — `cloudformation/secrets.yaml` (a CloudFormation template) defines the actual `AWS::SecretsManager::Secret` resources, while the Terraform tree only ever *consumes* secret ARNs by reference, never creates them — an explicit compute/networking-vs-secrets split, not an accident; (2) the module supports two consumption paths — a directly-run example deployment (`environments/dev/dev.tfvars`) for getting started, and a version-pinned reusable module (`source = ".../terraform/ecs?ref=v2.0.0"`) referenced from a consumer's own Terraform project, documented in a dedicated `ModuleUsage.md`.

**Verdict: not_yet for the HA/blue-green/rollback automation itself** — Kelvran has no live cluster or multi-instance production deployment to justify that investment yet (the Kubernetes report's own `replicas: 1` verdict still holds). **Build now, as a structural convention**, is the secrets-split pattern: whatever Terraform Kelvran writes for IAM/S3 (Findings 2-3) should only ever *reference* secrets by ARN, never define `SecretsManager`/`Secret` resources inline in the same module — consistent with this repo's own existing rule (`AGENTS.md`: "never store... any secret in a committed file").

### Finding 5 — The consistent structural best practice across every source surveyed is many small, single-concern modules with a `main.tf`/`variables.tf`/`outputs.tf` convention, plus separating cluster-provisioning state from in-cluster-resource state
**Confidence: medium-high** (4 merged claims — 2 unanimous, 2 at 2-1 — spanning the official LiteLLM module's own file layout, a GKE example repo, and HashiCorp's own Kubernetes-provider tutorial)

The official LiteLLM AWS module itself is a flat root module (no nested `modules/` subfolder) with one `.tf` file per resource domain (`alb.tf`, `ecs.tf`, `iam.tf`, `network.tf`, `rds.tf`, `redis.tf`, `s3.tf`, `secrets.tf`, plus `autoscaling.tf`/`bootstrap.tf`/`locals.tf`/`migrations.tf`), an `examples/default` directory, and a `tests/` directory — confirmed directly against the live repo tree. A separate example (an author's own GKE quick-start repo) splits provisioning into three independent modules (cluster, ingress controller, cert manager), each following the same `main.tf`/`variables.tf`/`outputs.tf` convention. Independently, HashiCorp's own official Terraform Kubernetes-provider tutorial explicitly recommends splitting cluster/infrastructure provisioning and in-cluster Kubernetes-resource management into *separate* Terraform workspaces/state, specifically so "changes in one repository doesn't affect the other" and so different permissions can be scoped to each — directly relevant to Kelvran's own future EKS-or-equivalent decision, since it means the IAM/S3/networking module (Findings 1-3) should stay a separate state from any future Terraform that manages in-cluster resources (which today are Kustomize-managed anyway, per the Kubernetes report, so this separation already exists by construction).

**Verdict: build now**, as the organizing convention for whatever Terraform Kelvran writes: one file per resource domain inside a flat module (no premature submodule nesting), a dedicated `examples/` directory, and — when a real cluster eventually exists — cloud-resource-provisioning state kept separate from any in-cluster-resource state, never merged into one workspace.

### Finding 6 — External Secrets Operator's zero-static-key authentication chain (IRSA/kiam/kube2iam) is the standard mechanism a future Kubernetes-deployed Kelvran would need Terraform to provision the IAM side of, and ESO supports per-store role scoping via `sts:AssumeRole`
**Confidence: high** (2 merged claims, both unanimous, verified against ESO's own current docs)

External Secrets Operator — already the Kubernetes report's *documented but not yet live* decision for Kelvran's secrets-management gap — supports a "zero-configuration" authentication method that inherits credentials from the AWS SDK's default credential chain, with a role attachable via IRSA, kiam, or kube2iam (all three named explicitly in ESO's own docs), meaning no static AWS keys are baked into the cluster at all. Separately, ESO supports scoping access per `SecretStore` via an explicit `role` field (documented as "the recommended way to scope access") plus an `additionalRoles` list for sequential cross-account role-chaining. This is the concrete missing piece between "ESO is the documented decision" (Kubernetes report) and "ESO is actually running": someone has to provision the IRSA trust relationship (an OIDC-federated IAM role trusting the cluster's service account) as IaC — that role, and the `SecretStore.role` it's paired with, is exactly the kind of narrow, well-scoped Terraform resource Finding 3's Bedrock-IAM module pattern would extend to.

**Verdict: not_yet** — this is real, well-documented, and directly actionable, but genuinely requires a live EKS-or-equivalent cluster with an OIDC provider to attach IRSA to, which doesn't exist yet (per the Kubernetes report, `deploy/k8s/` has never been applied to a real cluster). Worth designing the Terraform module's shape now (a parameterized IAM role + trust policy taking a cluster OIDC provider ARN as input) so it's ready the day a real cluster exists, rather than a "someday" with no concrete plan.

### Finding 7 — Terraform's conventional scope (IAM, networking, managed services) matches exactly the categories Kelvran's own docs already flag as unautomated
**Confidence: medium** (1 claim, 2-1 split vote — general IaC scope guidance, not project-specific, but independently corroborated against Kelvran's own real docs)

General Terraform/Kubernetes-boundary guidance draws the line at Terraform owning cloud infrastructure — IAM roles/policies/service accounts, networking (VPCs, subnets, NAT gateways), and managed services (RDS, S3, Pub/Sub-equivalents) — while workload-layer resources (Deployments, ConfigMaps, application Secrets) stay with Kubernetes-native tooling. (A stronger, more prescriptive version of this claim — that Kelvran's own app containers/config specifically should therefore stay entirely out of Terraform — was checked and did **not** survive verification at strong confidence; treat the general infra/workload split as a reasonable default, not a hard rule this research established for Kelvran specifically.) The categories on the "Terraform owns this" side of that line are precisely the three gaps named in this report's Scope section: IAM (Bedrock judge credential), networking (not yet a blocker, but relevant the moment a real VPC/cluster exists), and a managed service (the S3 bucket). Kelvran's existing Kustomize manifests already only touch the workload layer (Deployment/Service/Secret-placeholder) — so this split isn't a change Kelvran would need to make, it's already the shape its two existing IaC-adjacent artifacts (Compose, Kustomize) fall into; Terraform would fill the one layer neither currently touches at all.

**Verdict: build now**, as validation of scope, not a new task — confirms Findings 2-3-6's proposed modules (IAM, S3, IRSA trust) are the correct category of resource to hand to Terraform rather than trying to express them in Kustomize/Compose instead.

### Finding 8 — PR-gated Terraform plan/apply automation (Atlantis or a GitHub Actions equivalent) is a real, well-established next layer, but has nothing to gate until a first module exists
**Confidence: high** (3 merged claims, all unanimous — one corroborated independently against Atlantis's own README, not just a vendor blog)

Atlantis is a real, widely-used, self-hosted tool that moves `terraform plan`/`apply` out of local terminals and into GitHub pull requests via webhooks, posting plan output as PR comments — independently confirmed against Atlantis's own README, not just the (vendor-adjacent) blog post that first described it. A simpler, dependency-free alternative pattern — a GitHub Actions workflow where `plan` runs on both `pull_request` and `push` but the `apply` job is gated behind an explicit `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` conditional — achieves the same PR-review-before-apply property with no additional infrastructure, and is a well-known, HashiCorp-corroborated pattern (`terraform plan -out=tfplan` then `terraform apply tfplan`, applying the *exact* plan artifact a human reviewed rather than a fresh plan that might have drifted). Kelvran's existing CI (`.github/workflows/ci.yml`: `ci.yml`, `codeql.yml`, `scorecard.yml`, `evals-judge-nightly.yml`) has no Terraform-aware job today — confirmed by direct inspection, not inference.

**Verdict: not_yet.** This is the right next step *after* Findings 2/3/6 produce actual `.tf` files worth reviewing in a PR — introducing Atlantis or a plan/apply-gated GitHub Actions workflow before any module exists has nothing to automate. When a first module ships, the GitHub-Actions-native pattern (plan-on-PR, gated-apply-on-main-push, applying the saved `tfplan` artifact) is the lower-overhead choice for a single-maintainer project — matching this report's own recommendation in Finding 1 to start narrow — over standing up a separate Atlantis service.

## Options Considered and Ruled Out

For transparency, these plausible-sounding candidates were specifically investigated this round and did not hold up under adversarial verification:

- **"The official LiteLLM AWS module's documented secrets pattern (Secrets Manager, ARN-referenced injection) is the specific mechanism"** — refuted 0-3. The module does use Secrets Manager, but this specific framing of it as *the* documented pattern (vs. one of several valid approaches) did not survive verification; don't cite this module's secrets handling as a settled best-practice endorsement beyond what Finding 4's Portkey-sourced secrets-split pattern already establishes independently.
- **"The LiteLLM AWS module's default resource set maps almost one-to-one onto Kelvran's actual needs"** — refuted 0-3. The module's Aurora/ElastiCache/ALB/three-ECS-service shape is significantly larger than what Kelvran's Go-binary-plus-optional-Redis shape needs; do not treat it as a template to copy wholesale, only as a structural (Finding 5) and scope (Finding 1) reference.
- **"The AgentCore module's out-of-the-box default grants wildcard `bedrock:InvokeModel` access unless explicitly narrowed"** — refuted 1-2. Don't assume any specific module defaults to a wildcard; verify each module's actual default before trusting Finding 3's scoped-ARN pattern is automatic.
- **"ESO's IRSA pattern is *the* specific mechanism Kelvran's own future Terraform module would need to implement"** — refuted 0-3 (as an overly specific, prescriptive framing — the general IRSA/kiam/kube2iam chain in Finding 6 is real and verified, but this stronger "Kelvran must implement exactly this" framing did not hold up).
- **"Kubernetes-native tooling, not Terraform, should own Kelvran's own app containers/config even after Terraform provisions the underlying infra"** — refuted 1-2. The general infra/workload split (Finding 7) is real; this Kelvran-specific extension of it is not independently established by this research and shouldn't be over-cited as settled.

## Open Questions

- **AWS vs. multi-cloud from day one?** Every module surveyed (LiteLLM, Portkey, the AWS reference architecture) supports at least AWS; several also support GCP or Azure. `evals`' Bedrock judge path and the `vector-s3` gap are both AWS-specific today — does Kelvran's own self-hosted, deploy-anywhere positioning (referenced in the Kubernetes report) require a multi-cloud-ready module shape from the start, or is an AWS-only first module (matching what's actually blocked today) the right initial scope?
- **Who owns the Terraform state, and where?** None of the sources surveyed answer this for a single-maintainer OSS project specifically — S3+DynamoDB remote state (the conventional AWS answer) requires its own bootstrap problem (the classic "what provisions the state bucket" chicken-and-egg). Worth a dedicated follow-up before writing the first `.tf` file.
- **Does the EKS-vs-ECS-vs-self-managed-Kubernetes decision need to happen before the IRSA-shaped Finding 6 module can be designed concretely?** IRSA specifically requires an EKS OIDC provider; a self-managed cluster or ECS would need a different mechanism (kiam/kube2iam, or ECS task roles respectively) — this report didn't resolve which compute target Kelvran will actually use.
- **Is Atlantis vs. a bare GitHub Actions gate a decision worth making now, or truly deferred until Finding 8's "nothing to gate yet" blocker clears?** The report's own verdict is not_yet, but a lightweight now-vs-later comparison (maintenance burden of a self-hosted Atlantis instance vs. a same-repo GitHub Actions workflow) wasn't itself put through verification this round.
