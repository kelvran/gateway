# Cache Production Semantic-Caching Benchmarks — Deep Research (2026-09-11)

## Question

Kelvran's current L3-lite is deliberately LEXICAL-similarity-only (Jaccard/MinHash), never embedding-based, per `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md` — gated by an entity/number/date hard-match fingerprint plus a freshness-risk model, specifically to avoid semantic-similarity false positives (negation/polarity flips like "withhold" vs "administer" a drug). This round asks whether 2026 production semantic-cache systems (Redis LangCache, GPTCache, Portkey, Momento, LiteLLM, vLLM's semantic-router) have a genuinely *better* precision/recall solution than what Kelvran already tried and found wanting, or whether Kelvran's own findings match the honest state of the art: (1) what real precision/recall numbers do production caches report for negation/polarity-flip false positives specifically; (2) do any combine embedding similarity with a structured hard-gate, and how does the gate design differ from Kelvran's; (3) is there a 2026-era cheap classifier / structured extraction / LLM-as-judge technique that changes the calculus, and at what cost per cache-check; (4) is an embedding-based L3 upgrade justified for v2, or should Kelvran stay lexical-only and document this as considered-and-rejected.

## Context (Kelvran's own real, current state)

L3-lite catches near-duplicate phrasing via pure-stdlib MinHash/Jaccard shingling, gated by an entity/number/date fingerprint (exact-set-equality, no partial credit) plus a freshness/risk model (staleness budget, model-ID match, volatility-keyword bypass). Real embedding-based semantic L3 is explicitly deferred pending production miss-telemetry and a mature Go-native embedding path (neither exists yet — reconfirmed as recently as `cache-semantic-embedding-readiness-round4-2026-09-11.md`, same date as this round). This session Kelvran built and ran a real offline validation harness (`evals/scripts/validate_embedding_gate.py`) against real AWS Bedrock Titan-v2 embeddings: at cosine threshold=0.90, bare embedding similarity gets precision=0.667/recall=1.0 (2 of 6 negatives wrongly approved); layering the *same* entity-fingerprint hard-gate on top does not improve precision at that threshold and costs recall to 0.5 (also rejects true paraphrases). Only at threshold=0.95 does the gated version reach precision=1.0 at recall=0.25. Already cited: arXiv:2608.10216 found NLI-based contradiction detection performs no better than chance as a cosine-gate repair, and a bare-similarity gate catches 0/56 meaning-reversing mutations in that paper's own test set.

## Summary

No production semantic-cache vendor surveyed (LiteLLM, Portkey, GPTCache, Redis LangCache) publishes real precision/recall numbers for negation/polarity-flip false positives, and where a structured "hard gate" exists at all, none matches Kelvran's entity/number/date fingerprint design — Portkey's gate matches request *parameters* (not content), GPTCache has no content-level gate at all, and Redis's own evaluation methodology substitutes an LLM-judge shipped with a literally empty default prompt rather than structured extraction. The single production system found with a real negation-targeted defense, vLLM's semantic-router, independently validates Kelvran's design philosophy rather than superseding it: it runs a cheap, deterministic, always-on lexical negation-cue/antonym tier as its trustworthy default, and relegates the "smarter" NLI-based option to an optional layer that fails open specifically because its own engineers don't trust it to gate reliably — matching a 2026 academic audit's own finding that NLI-based contradiction detection repairs a cosine gate no better than chance on held-out data. Given this, Kelvran's own offline numbers (precision=0.667 bare at threshold=0.90, gated version reaching precision=1.0 only at recall=0.25) are not a compromise but the honest state of the art for this failure class in 2026 — no surveyed production system or academic technique reports a genuinely better precision/recall tradeoff for negation-flip false positives. The one concrete, buildable-now item to fall out of this research is narrow and additive: a cheap lexical negation-cue/antonym-swap tier (mirroring vLLM's model-free default), layered alongside Kelvran's existing entity/number/date gate to close the specific "same entity, flipped verb" gap the fingerprint alone cannot catch — independent of, and not a substitute for, the still-not_yet decision on real embedding-based L3.

## Findings

### Finding A — Q1: No production vendor publishes real precision/recall numbers on negation/polarity-flip false positives; the only concrete numbers anywhere come from independent academic audits, and they are damning

A production-grade cosine-similarity drift guard, independently audited, caught **0 of 56** meaning-breaking mutations in its test set, and one approved item — "withhold the study drug" → "administer the study drug" — scored cosine 0.9608, the exact failure class Kelvran is probing. Redis's own official LangCache customer-evaluation repo publishes **no** precision/recall benchmark numbers of its own at all — it is only a runnable scoring harness customers must execute against their own dataset, and even then it substitutes an LLM-as-a-Judge for ground-truth labeling (shipped with a literally empty default prompt out of the box, no entity/number/date logic anywhere in its codebase) rather than disclosing Redis's own measured accuracy. GPTCache's own documentation openly acknowledges false positives as an inherent, unresolved risk of semantic caching, but the three metrics it offers to gauge performance are Hit Ratio, Latency, and Recall — notably not Precision or any measured false-positive rate.

**Confidence: high** (multiple independent primary sources — arXiv:2608.10216, Redis's own repo, GPTCache's own README — unanimous or near-unanimous votes).

**Verdict: not_yet.** No vendor will supply this number for Kelvran's own risk profile; the only path to a real number is Kelvran's own harness (already built and run this session). Trigger to revisit: none from vendor disclosure — Redis's own "ship a harness, not a number" pattern suggests this won't change. The only real trigger is (a) production miss-telemetry quantifying what the current lexical L3 is actually missing, plus (b) Kelvran's own harness re-run at a larger, independently-labeled N (the current N=6 negatives is explicitly too small to generalize from).

### Finding B — Q2: Structured hard-gates on top of embedding similarity are the exception, not the rule, among production systems — and where they exist, none matches Kelvran's design

LiteLLM's semantic cache validates hits using *only* cosine similarity against a configurable threshold — no entity/number/date matching or any other content-level gate, only tenant/key scoping. Portkey layers a hard-gate on top of its 0.95-default cosine check, but that gate is an exact-match on request *parameters* (model, temperature, max_tokens, metadata) — structurally incapable of catching negation/polarity flips or entity substitutions in the user's text, since those parameters are untouched by such edits. GPTCache's similarity-evaluation layer offers only embedding-distance, a generic duplicate-detector model, exact-match, and (planned) BM25 — no entity/number/date extraction anywhere in its source across all nine evaluator modules inspected. Redis's LangCache evaluation methodology substitutes an LLM-as-a-Judge for structured extraction entirely.

**Confidence: high.**

**Verdict: not_yet** (as a reason to build embeddings). This absence, across every major vendor surveyed, reads as evidence for the "honest state of the art" interpretation — not as evidence Kelvran is missing an established, provably-better pattern it should adopt.

### Finding C — Q2/Q3, BUILD NOW: the one production system with a real structural analog to Kelvran's gate independently validates Kelvran's design philosophy, and surfaces a genuine, narrow gap Kelvran can close today

vLLM's semantic-router ships a mandatory, model-free lexical negation-cue/antonym-swap tier as the *default*, always-on layer on top of bi-encoder similarity — explicitly because "bi-encoder similarity cannot tell 'turn on dark mode' from 'turn off dark mode': opposite-meaning queries often score above `similarity_threshold` while genuine paraphrases score below it, so raising the threshold does not fix the false hit." This independently reproduces Kelvran's own threshold=0.90-vs-0.95 precision/recall tradeoff finding in a live production system. Its *optional* secondary NLI tier fails **open** (serves the cache hit) when the contradiction verifier is missing or errors, with the code comment stating this is explicitly so "a model hiccup never turns into a cache outage" — i.e., the production engineering team trusts the cheap lexical tier as load-bearing and treats the ML-based option as best-effort, not authoritative, matching Kelvran's own instinct to prefer a deterministic gate over an ML classifier.

The gap: vLLM's gate targets negation *cues* and antonym *swaps*, a different signal from Kelvran's entity/number/date fingerprint — neither alone catches everything the other catches. "Withhold the study drug" vs. "administer the study drug" would likely be caught by vLLM's negation/antonym tier but is **not** caught by Kelvran's entity fingerprint as currently designed (same entity "study drug," no number/date delta — a real, already-flagged gap per this session's own `v-adversarial-cache-negation-polarity-flip-drug-administration` adversarial test).

**Confidence: high** (3-0 votes across four independent primary-source checks: docs, PR history, and direct source-code inspection of `inmemory_cache_polarity.go`).

**Verdict: BUILD_NOW (narrow, additive).** A cheap lexical negation-cue/antonym-detection tier — pure regex/word-list, no embeddings, no new `go.mod` entries, modeled on vLLM's model-free design — layered alongside Kelvran's existing entity/number/date fingerprint gate. No trigger required: this is buildable today, independent of and orthogonal to the embedding-based-L3 v2 decision, and it closes a real, already-named gap in the *current* lexical L3-lite (verb-polarity flips sharing an identical entity fingerprint), not merely a hypothetical future-embedding gap.

### Finding D — Q3: the one dedicated "smarter gate" attempted in 2026 — NLI-based contradiction detection — was tested by both academia and production engineering, and both independently concluded it is not a repair

A rigorous audit (arXiv:2608.10216) tested an NLI drop-in as a repair for the cosine gate: it scored AUROC 0.831 in-sample but collapsed to 0.533 (chance-level, CI [0.36, 0.71]) on separately-authored held-out data — no better than the flawed baseline it was meant to fix. vLLM's own production team reached a compatible conclusion by an independent, practical route: they ship NLI only as an optional bonus tier that fails open, never as the load-bearing gate — i.e., they don't trust it to gate reliably either, for different (engineering-risk) reasons than the paper's (statistical-generalization) reasons. No production system surveyed publishes a cost-per-cache-check figure for LLM-as-judge cache validation; the closest thing to a reference implementation — Redis's own LangCache evaluation harness — ships with a literally empty default judge prompt that the operator must hand-author before it produces any signal, which is itself weak evidence that LLM-as-judge is not yet a mature, off-the-shelf, cost-known technique for this specific use case in 2026.

**Confidence: high** on NLI-fails-as-a-repair (three independent, convergent sources: the audit paper, its own GitHub artifact, and vLLM's fail-open design). **Confidence: medium** on "no cost figures published" — this is an absence-of-evidence finding, not a directly benchmarked negative result.

**Verdict: not_yet.** No cheap dedicated classifier or LLM-as-judge technique surveyed changes the calculus. Trigger to revisit: a future NLI/contradiction model demonstrating materially strong (e.g., >0.85 AUROC) performance on genuinely out-of-domain held-out data — not just in-sample — in a peer-reviewed or independently-reproduced benchmark. Nothing in the 2026 evidence surveyed meets that bar.

### Finding E — theoretical grounding: this is a structural property of embeddings, not an implementation gap "better engineering" or "a better model" is likely to fix

Contrastive training objectives push dissimilar content apart in embedding space, but negated statement pairs are close in surface content while conveying opposite information — a documented, fundamental mismatch between the training objective and the negation-detection task. Empirically, across universal text-embedding models, a sentence's negated version is rated *more* similar to the original than a true dissimilar paraphrase in 99.27% of cases on average, and negated-pair similarity scores never drop below 0.6 even in the human-annotated group with the lowest similarity. A clinical-domain paper independently corroborates the exact structural analog to Kelvran's scenario: "patient has chest pain" vs. "patient denies chest pain" can receive high similarity scores despite opposite clinical meaning.

**Confidence: high** (three independent primary sources, unanimous votes).

**Verdict: not_yet.** This is why "wait for a better embedding model" is also not a real trigger — the failure is architectural to contrastive bi-encoder training, not a model-quality gap current or near-future embedding models are likely to close on their own.

### Finding F — Q4, the verdict: Kelvran's own numbers match the honest 2026 state of the art; lexical-only + hard entity gate is the more defensible choice at Kelvran's scale, not a compromise

Every production system surveyed either (a) has no content-level hard gate at all and openly documents unresolved false-positive risk (LiteLLM, GPTCache, Redis's LLM-judge substitute), (b) uses a gate structurally different from and no more capable than what Kelvran already has (Portkey's request-parameter match), or (c) is the one system with a real negation-targeted gate and deliberately keeps it cheap/deterministic/mandatory while treating the ML option as optional and fail-open (vLLM) — reproducing Kelvran's own design philosophy rather than superseding it. No surveyed system reports precision/recall numbers on negation-flip false positives that beat Kelvran's own harness result (precision=1.0 achievable only at recall=0.25 — the same brutal tradeoff, not a better one).

**Confidence: high.**

**Verdict: NOT_YET for embedding-based L3 in v2.** Exact trigger to revisit, all three required: (1) real production miss-telemetry showing the current lexical/Jaccard L3-lite is leaving a materially large, *quantified* paraphrase-miss rate on the table (the trigger the original L3-lite RFC already named); (2) a genuinely lightweight, statically-linkable Go-native embedding-generation path existing at that time (per the separate round-4 readiness research run the same day — still not_yet as of 2026-09-11, and the field narrowed rather than improved); and (3) Kelvran's own offline harness, re-run at a larger, independently-labeled N (current N=6 negatives is too small to generalize from), confirming the precision/recall ceiling found this session holds or improves at scale. Absent all three, ship v2 with lexical-only L3 + the existing hard gate (plus Finding C's cheap negation-cue addition), and document real embedding-based L3 in `DECISIONS.md` as a considered-and-rejected path with this research as the citation trail.

## Caveats

- Kelvran's own harness this session used N=6 negative test cases — a real, honest result, but too small to generalize a precise precision/recall number from; Finding A's "not_yet" verdict depends partly on this being re-run at a larger N before being treated as final.
- arXiv:2608.10216 (the 0/56 audit, the NLI-fails-as-repair result) is a single-author preprint about one month old at research time — real, with a released reproducible artifact, but not yet independently replicated or peer-reviewed.
- Two related claims were checked and refuted, not merely unconfirmed: Portkey's 0.95 default threshold is **not** evidence it independently converged on Kelvran's own found-necessary threshold (the claim linking them was voted down 0-3), and a claim that plain contextual embeddings score at exact chance (33.32%) on a negation benchmark was also refuted (0-3) — both are excluded from the findings above rather than folded in as false corroboration.
- The research question named Momento specifically as a system to check; no claim about Momento's semantic-cache design (if one exists) survived verification this round — this is a real, honest gap, not a "Momento has no such issue" finding.
- LangChain/LlamaIndex's and Helicone's own semantic-cache internals also remain unconfirmed by this round (consistent with the prior round-4 readiness doc's own open gap on the same names) — absence of evidence here, not evidence of absence.
- vLLM's negation-cue `polarity_guard` tier is very recent (PR #3075 landed 2026-08-28, ~2 weeks before this research) — real and live in the current main branch, but not yet battle-tested at scale in long-running production, so treat it as a strong design signal rather than a proven-at-scale outcome.

## Recommendation for Kelvran

1. **Not yet** — do not build real embedding-based semantic L3 for v2. Kelvran's own harness numbers are not an outlier or a compromise; they match (and in the gated-at-0.95 case, slightly exceed) the best precision/recall tradeoff found anywhere in 2026 production or academic sources for this exact failure class. Document this research (and the original harness run) in `DECISIONS.md` as considered-and-rejected, citing arXiv:2608.10216, arXiv:2504.00584, and vLLM's own `polarity_guard` design rationale alongside Kelvran's own numbers.
2. **Build now (narrow, low-cost, independent of the embedding decision)** — add a cheap lexical negation-cue/antonym-swap tier to the existing entity/number/date hard gate, modeled on vLLM's model-free `polarity_guard` default tier. This closes a real, already-flagged gap (verb-polarity flips sharing an identical entity fingerprint, e.g. withhold/administer) that the current fingerprint gate cannot catch on its own, using pure regex/word-list logic — no embeddings, no new dependencies, no production-traffic gate needed.
3. **No action** on NLI/LLM-as-judge as a gate mechanism — both the academic audit and vLLM's own production engineering independently concluded it is not reliable enough to be load-bearing; treat this as evaluated-and-rejected in the decision record, not as an open future option.
4. **Re-run the harness at scale before finalizing the "not yet" verdict long-term** — extend the current N=6-negative offline harness (per the already-recommended, not-yet-built pattern from `cache-semantic-embedding-readiness-round4-2026-09-11.md`) via an LLM-driven paraphrase+negative-generator pair, and confirm the precision ceiling holds at N=50+ before treating this round's numbers as final for the v2 decision record.
