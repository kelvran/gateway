# Cache Warm-Up & Cold-Start Mitigation — Research (2026-09-12)

**Scope:** Kelvran's L1(exact)/L2(normalized)/L3-lite(lexical, entity+negation-gated) response cache is entirely in-process and in-memory, and starts empty on every process restart/deploy — a frequent event for an actively-developed product. This round asks whether real-world cache warm-up / cold-start-mitigation practice (general web-cache/CDN/database-cache, and LLM-gateway-specific where it exists) offers a precedented, worth-adopting pattern, and whether the problem is even real at Kelvran's likely scale. Four research questions; findings below are the claims that survived 3-vote adversarial verification, merged and organized by question. "build_now" / "not_yet" verdicts are given only where the surviving evidence actually supports one.

**Already shipped (not re-litigated):** the L1(exact)/L2(normalized)/L3-lite(lexical, entity+negation-gated) three-layer cache design itself; the Redis-backed L1/L2 distributed-cache design RFC (already written, deferred pending multi-instance deployment); `kelvran.cache.savings_usd` / `kelvran.cache.lookup` cost-observability metrics.

---

## Executive Summary

General cache-warming practice recognizes two well-established strategies — eager (pre-load before serving traffic) vs. lazy/cache-aside (let real requests fill it) — but the strongest empirical evidence found (a peer-reviewed CDN/storage-trace study) shows organic refill often reaches near-parity hit rate well before the cache is even close to full, which cuts against reflexively building a snapshot/replay warm-up mechanism. On the LLM-gateway-specific question, real precedent for a *simpler-than-Redis* local persistence layer clearly exists and is shipped, not vaporware: LiteLLM's disk-cache backend, GPTCache's SQLite+FAISS local data-manager pairing, and omnicache-ai's `diskcache`-backed `DiskBackend` all persist an LLM response cache to local disk across restarts with no external service required, and omnicache-ai additionally ships a dedicated `CacheWarmer` component for bulk pre-population from a known query list — directly matching the "pre-populate from a snapshot" pattern this research asked about. A time-to-cache-warm SLI has a real qualitative shape to watch for now (a post-deploy dip-and-recovery in the hit-ratio time series, using metrics Kelvran already emits) but no quantitative template (warm-threshold ε, target duration) survived scrutiny as reusable off-the-shelf, and calibrating one requires production traffic Kelvran doesn't yet have. Critically, no evidence surfaced either way on whether cold-cache is actually a costly problem at Kelvran's specific traffic shape (agent-governance gateway, likely low request volume) — this remains a genuinely open question, not a researched-and-dismissed one.

---

## Findings

### Finding 1 — Real, shipped LLM-cache-specific local-disk persistence precedent exists, and is simpler than Redis
**Confidence: high** (3 independent primary sources, all 3-0, verified against actual source code not just docs)

Three independent, real, shipped projects persist an LLM response cache to local disk without requiring Redis or any external service, directly answering research question 2 (is there a simpler-than-Redis pattern for snapshotting L1/L2 across restarts):

- **LiteLLM's disk-cache backend** (`Cache(type=disk)`, built on the third-party `diskcache` library, merged via PR #3266 in May 2024) persists cached LLM responses to a local cache file; LiteLLM's own docs confirm explicitly that "if you run the code two times, response1 will use the cache from the first run that was stored in a cache file" — i.e., survival across separate process runs. It's also exposed as a first-class proxy config option (`cache_params: {type: disk, disk_cache_dir: ...}`), not an experimental corner case.
- **GPTCache** pairs a disk-based relational store (SQLite, via `CacheBase(sqlite)`) with a disk-based vector index (FAISS, via `VectorBase(faiss, dimension=...)`) as its documented local-persistence layer for a *semantic* (embedding-based) LLM response cache — `get_data_manager(CacheBase(sqlite), VectorBase(faiss, dimension=onnx.dimension))`. Both components are inherently disk-backed/local; GPTCache separately supports Redis as an alternative backend, confirming this is a real documented choice among backends, not an improvised one.
- **omnicache-ai**'s `DiskBackend` wraps `diskcache.Cache(directory, size_limit=size_limit)` directly in its source (`omnicache_ai/backends/disk_backend.py`), with the module docstring stating it "survives process restarts" and is "safe for multi-process use (SQLite locking)." `diskcache` ships as a core dependency (always available), unlike its `RedisBackend` which requires an install extra.

**Verdict: not_yet.** The pattern is real and would apply even in Kelvran's current single-instance-only deployment model — it requires no multi-instance coordination, unlike the already-deferred Redis RFC. But building it now would be solving a problem whose actual cost at Kelvran's scale is unmeasured (see Finding 5), and Finding 3's empirical evidence suggests organic refill may already be fast enough that persistence buys little. **Named trigger:** production traffic + deploy-frequency data (via the already-shipped `kelvran.cache.savings_usd`/`kelvran.cache.lookup` metrics) showing a measurable, recurring dollar or latency cost during the post-deploy window that a disk snapshot would eliminate — i.e., evidence from Finding 5 resolving in the "costly" direction.

### Finding 2 — A real precedent for explicit "pre-populate from a known query list/snapshot" warm-up exists in an LLM-caching library
**Confidence: medium** (1 primary source, 3-0 vote, but single-source — verified at the source-code level, not just docs)

omnicache-ai ships a dedicated `CacheWarmer` component (`omnicache_ai/core/warmer.py`, added in the real v0.3.0 release, June 2026) with `warm_from_queries()` and `warm_from_file()` (CSV) methods. Its docstring states the purpose explicitly: "warming a cold cache on startup using known high-traffic queries, reducing the number of live LLM calls in production" — this is a direct, working implementation of exactly the "pre-populate from a snapshot/known list" pattern research question 1 asked about, not just a described intention.

**Verdict: not_yet.** The mechanism is real and buildable, but it presupposes a "known high-traffic queries" list — which Kelvran cannot construct without production traffic to observe what's actually high-traffic. Building this ahead of having that data would mean guessing the seed set. **Named trigger:** enough production request volume to derive a genuine top-N query/prompt-shape list (the same traffic data needed to resolve Finding 5), at which point this becomes a low-effort addition given Finding 1's persistence layer.

### Finding 3 — Organic cache refill often outpaces full capacity in production CDN/storage traces, weakening the default case for proactive snapshot/replay warm-up
**Confidence: medium** (1 peer-reviewed primary source, 2-1 vote; general eager-vs-lazy framing corroborated by a separate 3-0 source)

A HotCloud 2020 (USENIX) paper measuring production CDN and storage cache traces found that caches reach "warm" (interval hit ratio within 1% of steady-state) well *before* they are even capacity-full after a restart — by 39.1%/36.8% of the way to full for two CDN workloads and 16.6%/23.8% for two storage workloads. In other words, across all four real traces studied, organic traffic refill converged to near-parity hit rate long before the cache filled up, undercutting the assumption that a cold cache *needs* to be pre-filled or snapshotted to become useful quickly. Separately, the general industry framing of "eager" (pre-load everything before serving traffic) vs. "lazy"/cache-aside (let it fill from real requests) warming as the two baseline strategies is well-established, uncontroversial practice, not a novel claim.

**Verdict: not_yet** — this finding is a *caution against* building proactive warm-up reflexively, not a recommendation to build one. The paper's traces are classical high-volume CDN/storage LRU caches, a different shape from Kelvran's likely-lower-volume semantic/exact-match gateway cache, so the transfer isn't guaranteed to hold — but absent evidence to the contrary, it's the closest empirical data point available. **Named trigger:** Kelvran's own post-deploy hit-ratio time series (once real traffic exists) showing organic refill takes materially longer to reach near-steady-state than the paper's traces would predict, relative to how often Kelvran actually deploys.

### Finding 4 — A time-to-cache-warm SLI has a real qualitative signature to watch for now, but no ready-made quantitative template survived scrutiny
**Confidence: medium** (1 source, 2-1 vote; a candidate formal template from a separate primary source was explicitly rejected by adversarial review)

A recognizable cold-cache-after-deploy signature exists in cache-hit-ratio monitored as a time series (not a snapshot): a dip immediately following deployment, followed by organic recovery as traffic repopulates the cache — "if your cache hit ratio regularly dips after deployment, for example, and climbs back up again, you might have a cold cache issue." This is exactly the shape a "time-to-cache-warm" SLI would need to detect, and it requires no new instrumentation to start watching — Kelvran's already-shipped `kelvran.cache.savings_usd`/`kelvran.cache.lookup` metrics, viewed as a time series across deploys, already carry this signal. Separately, the same HotCloud 2020 paper (Finding 3) does define a formal, operational "warmup time" (convergence of interval hit ratio to within tolerance ε of a never-restarted baseline) — but a claim that this formal definition is "a directly reusable template for a Kelvran time-to-cache-warm SLI" did not survive adversarial verification (0-3): the panel rejected treating it as ready-to-adopt without adaptation.

**Verdict: build_now** for simply defining what to watch (the qualitative dip-then-recovery pattern, plotted from existing metrics across deploy boundaries) — this costs nothing new to instrument and gives operators an early diagnostic even with today's traffic volume. **not_yet** for picking a formal numeric SLI (a specific ε / target-duration threshold) — that requires real production traffic to calibrate, and the one candidate formal template found in the literature was judged not directly transferable without adaptation work. **Named trigger for the formal SLI:** enough production deploy-cycle data to observe what "recovered" actually looks like for Kelvran's own workload, so an ε and target duration can be chosen from evidence rather than borrowed from a differently-shaped (classical LRU, high-volume) workload.

### Finding 5 — Whether this is a real, costly problem at Kelvran's specific scale remains unanswered — not researched-and-dismissed, genuinely open
**Confidence: low** (no claim survived verification either way on this specific question)

No confirmed claim in this research round directly establishes whether cold-cache is a costly problem for an agent-governance gateway at Kelvran's likely (lower-than-consumer-chat) request volume. Two claims that would have supported "this doesn't matter much" were explicitly refuted: a claim that Lambda-style cold starts affect under 1% of requests in typical production workloads (0-3 — and note that claim is about container/runtime cold-start latency, a different mechanism from cache-fill economics, so it wasn't even on-topic), and a claim that "most serverless functions don't need proactive warm-up at all" (1-2). Their refutation does not, however, establish the opposite — it only means the specific sources arguing "not a problem" didn't hold up. No source arguing "this is definitely costly at low volume" was found or survived either.

**Verdict: not_yet**, purely by absence of evidence in either direction. **Named trigger:** real production traffic once Kelvran has live deployments with meaningful request volume — at which point the already-shipped `kelvran.cache.savings_usd`/`kelvran.cache.lookup` metrics can directly measure the dollar/latency cost of the post-deploy cold window (per Finding 4's qualitative signature) and settle this question with Kelvran's own data rather than borrowed intuition from higher-volume systems.

## Caveats

- Several intuitively-plausible general patterns did not survive verification this round and are deliberately omitted above rather than presented as confirmed precedent: gradual/weighted traffic-shift warm-up, Facebook-TAO-style shadow-traffic warm-up, blue-green cache-cluster cutover, a "replay_last_n" traffic-replay strategy, and a threshold-based (~90% hit-ratio) build trigger were all refuted (0-3 or 1-2) as specifically-cited precedents. This doesn't mean these techniques don't exist in practice anywhere — only that the specific sources claiming them as named, citable precedents this round did not hold up to adversarial scrutiny. Treat the space of "traffic-shifting / shadow-traffic warm-up" as folklore-level, not yet evidence-backed, pending a source that survives verification.
- A Trident (Varnish-alternative) periodic-snapshot-plus-reload-on-startup pattern, and a "dump cache to file, restore on next startup" strategy from a cache-warming blog, were both refuted at 1-2 (split, not unanimous) — there's a real possibility these patterns do exist as described, but the evidence presented this round wasn't strong enough to confirm; worth a second look with fresher sourcing if the disk-persistence direction (Finding 1) is ever pursued.
- Finding 3's empirical data (organic refill outpacing fillup) comes from classical CDN/storage LRU caches at high volume — a materially different shape from Kelvran's likely lower-volume, semantic/gating-heavy cache. The transfer is explicitly a hypothesis to test against Kelvran's own data, not an established fact about Kelvran specifically.
- Finding 5 is the most important caveat of all: this entire research round could not establish that cold-cache mitigation is worth building at Kelvran's scale. Every "build_now"/"not_yet" verdict above is contingent on that question resolving in the "costly enough to matter" direction once real traffic exists — treat this report as pre-work for that future decision, not a mandate to build any of it now.
- Search tooling (Exa/Tavily) hit rate limits during portions of this research round; several findings rest on direct primary-source WebFetch/GitHub-API verification alone rather than broader corroborating web search.

## Open Questions

1. Once Kelvran has production traffic, what does "warm" actually look like for its own workload — should the SLI's tolerance (ε) and target duration be derived from Kelvran's L1 (exact-match) and L3-lite (lexical/semantic) layers separately, given they likely have very different natural refill speeds?
2. If disk persistence (Finding 1) is ever built, should it snapshot L1/L2 only, or also attempt to persist L3-lite's entity/negation-gate state — and does persisting gate state across restarts introduce any staleness risk the live in-memory gate doesn't have?
3. Is there a non-LLM-specific reference case closer to Kelvran's actual shape — a low-volume, correctness-gated cache (rather than a high-volume classical LRU CDN/storage cache) — worth a dedicated follow-up search, since Finding 3's only empirical data point is from a workload shape that may not transfer?
4. Should the "known high-traffic queries" seed list for `CacheWarmer`-style pre-population (Finding 2) be derived automatically from production logs, or does Kelvran's governance/agent context make a curated, reviewed seed list (rather than raw traffic replay) the safer choice given the entity/freshness hard-gate's existing security rationale in `THREAT_MODEL.md`?
