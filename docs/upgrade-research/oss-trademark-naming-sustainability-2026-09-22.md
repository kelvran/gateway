## Executive Summary

Kelvran's actual blocker — USPTO TESS/common-law clearance on the word "Kelvran" — has never been run; `DECISIONS.md` says "still required," not "done and found a conflict." That is the real, cheap, fast unblock (free, self-serve, ~30 minutes per USPTO's own published process), and no packaging workaround substitutes for actually doing it. Second, and more consequential: the specific workaround the brief asks about — publishing `kelvran-evals` to PyPI under a temporary, different distribution name while keeping the import name internally as `kelvran` — has no supporting real-world precedent for Kelvran's actual situation, and the precedent that does exist argues against it. Every real case of an OSS/startup name changing under trademark pressure found in this research (Valkey↔Redis, Gymnasium↔OpenAI Gym, Monzo↔Mondo) shows the industry norm is a **wholly distinct, unrelated name**, never a cosmetically-modified variant of the contested word — so a placeholder like `loomkey-evals` would satisfy that norm, but a placeholder like `kelvran-evals-preview` would not: it still visibly performs the exact "use of the word Kelvran in commerce" the clearance gap is meant to de-risk. Third, and arguably the sharpest finding: Kelvran has almost certainly already crossed the "public use in commerce" threshold that the PyPI blocker is trying to avoid — the `kelvran` GitHub org, the public `github.com/kelvran/gateway` repo, and (since 2026-09-13) a real, cosign-signed, SLSA-attested, Rekor-transparency-logged `ghcr.io/kelvran/gateway` container image have all been live and publicly pullable for roughly three weeks. A PyPI listing is not the first exposure; it is one more surface carrying a name that is already public elsewhere, and — per PyPI's own official policy — actually less durable/permanent than `RELEASE.md` frames it (PyPI can remove or reassign a name on a properly-made IP complaint; it does not pre-screen, but it is not literally "admin-unappealable" either). Fourth: LiteLLM, Langfuse, and Helicone — the three closest real comparables — all converge on the same open-core shape (unlimited-feature free self-hosted core; paid tier gates SSO/SCIM, RBAC granularity, audit logs, secret-manager integrations, and support SLAs, not feature breadth), which is directly usable as a template for `evals`' own eventual monetization design, itself currently undecided and out of scope for this pass. Bottom line recommendation: run the actual TESS search now (it's the one step nobody has taken); do not invent a placeholder-PyPI-name workaround, since it doesn't reduce the real exposure and has no precedent behind it for this situation; and if a genuine conflict is ever found, plan for an atomic, fully-distinct rename across every public surface at once (org, repo, image tag, PyPI name) rather than a partial one — partial renames are exactly the failure mode the precedent cases show does not work.

## Findings, ranked

### 1. The manual USPTO TESS/common-law clearance search has never actually been run — it is the real unblock, and it is cheap (Small)

**What:** `DECISIONS.md`'s 2026-09-02 line says the automated GitHub/npm/PyPI/crates.io search came back clean across two independent rounds, but "manual USPTO TESS/WHOIS clearance still required before public registration — tracked as an open action, not yet done." `RELEASE.md`'s Pre-flight Blockers section (2026-09-13) still describes this as open. Nothing in this repo's history shows it was ever performed.

**Why it matters for Kelvran specifically:** every other finding in this document is downstream of this one fact not being resolved. USPTO's own published guidance (fetched live) states a **federal-register search of TESS is free, self-serve, and typically resolvable in a single sitting** for a first-pass screen — it is explicitly the cheapest of the clearance steps, cheaper than any packaging or naming workaround this document could recommend instead. Doing the actual thing that's blocking release is lower-effort than engineering around not having done it.

**Consistent with settled decisions?** Directly executes, rather than reopens, `DECISIONS.md`'s own 2026-09-02 open action — this finding does not propose new work, it observes that already-decided work is still outstanding and is the actual bottleneck.

**2026 best practice grounding:**
- USPTO's own "Federal trademark searching" page: "it's important to do a clearance search... searching the [TESS] database is one essential step," explicitly framed as a first, lower-cost pass before a full comprehensive search [uspto.gov — confirmed 3-0, cross-checked against USPTO's own "Comprehensive clearance search" page and a third practitioner source, MC Law].
- Multiple independent legal sources (MC Law, Hinckley Allen, Nelson Mullins, Questel) all converge on the same two-tier structure: a free/cheap TESS pass first, catching only *federally registered or pending* marks; then a separate, genuinely harder-to-do **common-law search** (unregistered marks, in use but never filed) that TESS alone cannot surface — "the USPTO's searchable database is limited to federal trademark applications and registrations... there is no central database of common law trademark rights" [Questel, MC Law — confirmed 3-0]. This is the specific reason `DECISIONS.md`'s own automated GitHub/npm/PyPI/crates.io "clean" result is not equivalent to clearance: namespace availability on code-hosting platforms is not a proxy for either the federal register or common-law use in the software/SaaS trademark classes that would actually matter here.

**Concrete next step:** run a TESS search for "Kelvran" (and close phonetic variants) under the relevant international classes (software/SaaS, likely Class 9 and/or 42) — free, ~30 minutes, no attorney required for this first pass per USPTO's own guidance. If TESS comes back clean, that narrows (does not eliminate) risk to the common-law tail; if it doesn't, that's the actual decision point this whole blocker exists for, and it should surface now rather than at the next release.

**Effort:** Small — this is a self-serve web search against a free government database, not a build task. The founder's own direct action, same as the org-creation step in `docs/agents/LOGS.md`'s 2026-09-03 entry that had no CLI/API path either.

### 2. Publishing under a temporary, different PyPI distribution name has no supporting precedent for Kelvran's actual situation — and real precedent argues against it (Medium)

**What:** This is the brief's central question. Precedent for name changes under trademark pressure falls into two clean buckets, and Kelvran's situation matches neither cleanly enough to justify a placeholder-name workaround.

**Why it matters for Kelvran specifically:** Bucket one — **pre-launch codename, no public use yet** (Akamas's internal "M.A.S"/"A.K.A. MAS," Stripe's internal "/dev/payments," a documented internal-tooling case using "OneTab" as a placeholder before choosing "VibeMenu") — is genuinely the workaround the brief is asking about, and it is real, common practice. But it only works because **nothing public has shipped under the contested name yet**. Bucket two — **forced rename after real public use** (Monzo/Mondo, Valkey/Redis, Gymnasium/OpenAI Gym) — is what happens once a name is already live, and in every one of those cases the fix was a **wholly new, unrelated name**, not a variant. Kelvran is already in bucket two's territory for its org/repo/image (see Finding 3), while only its PyPI listing is still in bucket one's territory. A workaround that invents a placeholder PyPI name while the GitHub org, repo, and container image keep saying "Kelvran" doesn't actually delay the "use in commerce" event — it already happened elsewhere — it just adds a second, disconnected name to unwind later if a real conflict surfaces, with no compensating risk reduction.

**Consistent with settled decisions?** Directly engages `DECISIONS.md`'s naming-clearance entry and `RELEASE.md`'s Pre-flight Blockers — neither anticipated that the org/repo/image publication (a later, separate decision, `docs/agents/LOGS.md`'s 2026-09-03 entry) would functionally overtake the PyPI blocker's own premise. This finding does not reopen the "Kelvran" name choice itself (settled, not revisited here) — it only addresses the specific packaging-workaround question asked.

**2026 best practice grounding:**
- Valkey: forked from Redis specifically because the fork **could not use the Redis name at all** — Linux Foundation-backed, entirely new brand, with the project's own GitHub issue tracker (`valkey-io/valkey#25`, `#29`, `#148`) showing systematic, months-long removal of every "Redis" string from source, config files, and binaries, explicitly tagged `trademark-review` — not a "Redis2" or "Redis-oss" variant [github.com/valkey-io — confirmed 3-0 via three separate issues/PRs in the same repo, cross-checked against Intel's own interview with a Valkey maintainer confirming the Linux-Foundation-owns-the-trademark structure specifically to prevent recurrence].
- Gymnasium: Farama Foundation's fork of OpenAI's unmaintained Gym adopted a genuinely distinct name ("Gymnasium," not "Gym2" or "OpenGym") — confirmed directly from Farama's own announcement post and the project's official v1.0 release notes [farama.org, github.com/Farama-Foundation — confirmed 3-0].
- Monzo/Mondo: **the closest real analog to "already-public name, real conflict surfaces later."** An undisclosed company legally challenged Mondo's UK trademark roughly a year after Mondo had already launched publicly, raised money, and built a real user base; the company chose an adjacent-but-distinct name ("Monzo," changed by one letter, but functionally a new word, not "Mondo Inc." or "Mondo 2.0") rather than fight the challenge, explicitly to avoid "the hassle or expense" of litigation — confirmed independently across the company's own blog, Bloomberg, City A.M. (two separate articles, three months apart), and Business Insider, all reporting the same underlying legal-challenge-forced-rename fact [confirmed 3-0, five independent sources total].
- No precedent was found — across any of the sources checked — of a project using a **temporarily different PyPI/npm distribution name specifically to delay trademark exposure while the same brand was already public elsewhere** (GitHub org, container registry). The two precedent buckets above are genuinely distinct situations from Kelvran's actual, hybrid one.

**Concrete next step:** do not build a placeholder-PyPI-name path. If Finding 1's TESS search comes back clean (or the common-law tail is judged acceptably low-risk), ship `kelvran-evals` as already planned in `RELEASE.md`. If it surfaces a real conflict, treat that as a full-rename decision across org/repo/image/package simultaneously — not a PyPI-only patch — per the Valkey/Gymnasium/Monzo pattern.

**Effort:** Medium — not a build task, a decision/contingency-planning one: this finding's real cost is the founder's own judgment call on Finding 1's outcome, not engineering effort.

### 3. The public GitHub org, repo, and signed GHCR image have likely already crossed the "use in commerce" threshold the PyPI blocker exists to avoid (Unscoped — a reframing, not a build item)

**What:** `RELEASE.md`'s Pre-flight Blockers section already partially acknowledges this ("that 'GitHub org/repo' prong of the blocker was already crossed when the repo went public") but frames it as a one-time, low-stakes, reversible event ("a git tag/Release on an already-public repo is... fully reversible"). This research finds that framing understates the actual, current exposure: since 2026-09-13, every push to `main` produces a real `ghcr.io/kelvran/gateway` image, cosign-signed via keyless GitHub Actions OIDC, with a CycloneDX SBOM and SLSA Build Level 2 provenance attestation, each entry permanently recorded in the public Sigstore Rekor transparency log under the identity string `https://github.com/kelvran/gateway/`.

**Why it matters for Kelvran specifically:** a Rekor transparency-log entry is not deletable the way a git tag or a GHCR tag is — it is an append-only, publicly-auditable ledger by design (that is Sigstore's entire security property). This means the identity string "kelvran/gateway" has already been durably, publicly, cryptographically tied to real software artifacts, repeatedly, for roughly three weeks — a materially stronger and more permanent "use in commerce" signal than a single PyPI listing would add. If USPTO clearance ever surfaces a genuine conflict, the PyPI listing was never the primary exposure to worry about; the org/repo/image already were.

**Consistent with settled decisions?** Sharpens, rather than contradicts, `RELEASE.md`'s own existing caveat about the GHCR publish path — that caveat already names the `go get`-caching and image-pull risks but stops short of naming the Rekor transparency-log permanence specifically, which this finding adds as new information, not a re-litigation.

**2026 best practice grounding:** this finding rests on Sigstore/Rekor's own documented design property (an append-only public transparency log is the mechanism's entire point, not an incidental side effect) rather than on a trademark-law source — flagged here explicitly as this document's own reasoned synthesis connecting a real technical fact (already verified independently in this repo's own `RELEASE.md`, via real `cosign verify`/`cosign verify-attestation` commands) to the trademark-exposure question, not a claim sourced from trademark-specific literature. No trademark-law source consulted in this research specifically addresses Sigstore/Rekor logs, because none appear to exist yet on this exact intersection — genuinely novel ground, called out honestly rather than force-fit into an existing citation.

**Concrete next step:** none required as a build task. Worth recording explicitly in `RELEASE.md`'s Pre-flight Blockers section (a documentation-only edit, not in scope for this research pass to make unilaterally) that the operative trademark-exposure clock started 2026-09-03/2026-09-13, not at the next PyPI publish — so Finding 1's clearance search is urgent regardless of whether `kelvran-evals` ships next week or next quarter.

**Effort:** N/A — an analytical reframing, not an implementation item.

### 4. `RELEASE.md`'s "genuinely permanent, admin-unappealable" framing of a PyPI publish is directionally right but factually overstated (Small)

**What:** `RELEASE.md`'s Pre-flight Blockers section describes a first PyPI publish of `kelvran-evals` as "a genuinely permanent, admin-unappealable public name/filename claim," contrasted against a git tag/GitHub Release (deletable) and a GHCR image (deletable, modulo already-pulled local copies). This research finds the "admin-unappealable" half of that claim is not accurate against PyPI's own official policy.

**Why it matters for Kelvran specifically:** it changes the actual risk being weighed. PyPI/PSF's official policy (PEP 541, mirrored verbatim at `docs.pypi.org/project-management/name-retention`) explicitly reserves the right to **remove or reassign** a project name "at the sole discretion of the Python Software Foundation to address a claim of infringement," and separately states plainly: "It is not the policy of the Python Software Foundation nor the Package Index maintainers to pre-screen uploaded packages for any type of intellectual property infringement" — i.e., nothing stops the initial upload, but a later, real trademark complaint is a route PyPI itself explicitly provides for, administered by PSF's own legal counsel, not "unappealable." What *is* true and worth keeping: PyPI's own version-immutability rule (a specific uploaded file for a specific version number can never be re-uploaded once deleted) means a full clean erase-and-reuse is genuinely harder than deleting a git tag — that half of `RELEASE.md`'s framing holds up.

**Consistent with settled decisions?** A precision correction to `RELEASE.md`'s own stated rationale, not a reversal of the underlying decision to treat PyPI publish as the most consequential of the publish targets — the underlying caution is still well-founded, just for a slightly different mechanism (version-immutability + real reputational/practical stickiness) than the doc currently states (admin-unappealable removal, which isn't quite how PyPI's policy actually works).

**2026 best practice grounding:**
- PEP 541 (Python Enhancement Proposal, the actual governing document) and its live mirror at `docs.pypi.org/project-management/name-retention` state identically: infringing packages "can be removed or transferred to a new owner at the sole discretion of the Python Software Foundation to address a claim of infringement" [peps.python.org, docs.pypi.org — confirmed 3-0, both sources are the same policy text, independently fetched].
- The same source confirms no pre-screening happens at upload time — consistent with the observation that nothing *technically* blocks publishing `kelvran-evals` today; the blocker Kelvran has self-imposed is a risk-management choice, not a platform-enforced gate.

**Concrete next step:** a small, low-effort `RELEASE.md` wording fix (out of scope for this research pass to make directly, since it's a documentation edit outside this brief's file-write target) — replace "admin-unappealable" with something like "not cleanly reversible: PyPI won't pre-screen a first upload, but a later trademark complaint gives PSF an explicit discretionary removal/reassignment path, and the exact version file itself can never be re-uploaded once deleted."

**Effort:** Small — a documentation correction, not a code or process change.

### 5. Open-core sustainability comparables (LiteLLM, Langfuse, Helicone) converge on one shape: unlimited free core, paid tier gates governance/compliance/support — not features (Large, not urgent)

**What:** The three closest real comparables to Kelvran's own gateway+evals shape all use structurally the same open-core split, verified directly against each project's own official pricing/docs pages (not third-party summaries):
- **LiteLLM** (BerriAI): free self-hosted OSS proxy is "free forever," including 100+ providers, virtual keys/budgets/rate limits, fallbacks, and Prometheus metrics. The paid Enterprise tier gates SSO/SCIM, OIDC/JWT auth, audit logs, secret-manager integrations + key rotation, org/team admin hierarchies, multi-region control plane, and support SLAs — explicitly "priced to your gateway's scale, never per token" [litellm.ai/pricing, litellm.ai/features, litellm.ai/enterprise, docs.litellm.ai/docs/enterprise, and the project's own GitHub README — confirmed 3-0 across five independently-fetched official pages].
- **Langfuse**: MIT-licensed core with "all core platform features and APIs... without any usage limits," self-hostable for free indefinitely. Enterprise Edition (EE) modules — SCIM, project-level RBAC, data-retention policies, audit logs, instance-management APIs, UI customization — live in clearly marked `/ee` directories in the same repo, gated by a license-key check at runtime, not a separate closed-source build [langfuse.com/pricing-self-host, langfuse.com/self-hosting, langfuse.com/handbook/chapters/open-source, langfuse.com/self-hosting/license-key — confirmed 3-0 across four official pages, including the explicit statement "the entire stack is open source... EE packages are isolated and gated by the license key check. You can run the core image without a key without running EE code"].
- **Helicone**: Apache-2.0-licensed, self-hostable in full via Docker/Helm with no feature gate — the paid tiers (Pro $79/mo, Team $799/mo, Enterprise custom) gate **usage volume, retention window, seat/org count, and compliance certifications (SOC-2, HIPAA, SAML SSO)**, not core gateway/observability functionality [helicone.ai/pricing, docs.helicone.ai/getting-started/self-host/overview, github.com/helicone/helicone — confirmed 3-0 across three official sources].

**Why it matters for Kelvran specifically:** neither `gateway` nor `evals` currently has any monetization story at all — `RELEASE.md` and `DECISIONS.md` describe publish *targets*, never a paid tier. All three comparables independently arrived at the same dividing line: **governance/compliance/support is the paid surface, not raw capability** — which maps cleanly onto capabilities Kelvran's own `THREAT_MODEL.md`/`ARCHITECTURE.md` already name as deliberately deferred (hierarchical org/team-scoped budgets, an inbound MCP server, real multi-tenancy beyond the current 4-tier RBAC) rather than onto anything already shipped. This is directly relevant to, but does not resolve, `docs/upgrade-research/multitenancy-rbac-tier1-2026-09-20.md` and `billing-monetization-integration-2026-09-15.md`, both of which this research checked and found adjacent-but-not-duplicative: neither prior document frames the split in terms of a specific external open-core precedent set, and neither addresses naming/trademark at all.

**Consistent with settled decisions?** Additive — no `DECISIONS.md` entry currently commits Kelvran to any monetization structure, open-core or otherwise, so this is genuinely new scope, not a revisit of a settled question. Deliberately **not** recommending action now: per `AGENTS.md`'s own YAGNI-adjacent convention (build the minimal real thing, document the upgrade path — the same discipline already applied to budget persistence's bbolt-vs-Postgres choice and Cache's dormant gRPC extraction seam), monetization design before any real user base exists would be premature.

**2026 best practice grounding:** see the three bullet points above — each independently sourced against 3+ official pages per project, with zero reliance on third-party paraphrase for the load-bearing claims (a fourth-party analysis piece on Helicone's pricing, `truefoundry.com/blog/helicone-pricing`, was cross-checked against but not relied upon as a primary source, since it's a competitor's own comparison content).

**Concrete next step:** not urgent — flag for whenever Kelvran's own roadmap first considers a paid tier (no trigger exists yet). At that point, the LiteLLM/Langfuse license-key-gated-EE-module pattern (Langfuse's specifically) is the most directly portable mechanism to Kelvran's own Go+Python split, since it requires no separate closed-source repo — just license-key-gated code paths in the same tree, which is easier to keep in sync with the OSS core than a fork-and-diverge model would be.

**Effort:** Large — a real product/business-model decision with cross-cutting implementation surface (licensing mechanism, feature-gating in both `gateway` and `evals`, legal terms) — explicitly not something to build now, only to have a template ready for later.
