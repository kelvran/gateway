## Executive Summary

This pass answers a real, previously-flagged gap head-on: Kelvran's own `evals-corpus-routing-chaos-patterns-2026-09-08.md` explicitly noted that every incident it mined (AWS DynamoDB 2015, Slack 2021, Twilio/Segment 2018, Cloudflare/Facebook 2021) was generic-HTTP/DNS infrastructure, not LLM-specific, and asked whether LLM-specific traffic patterns would change the realistic failure shape. The answer, from real 2025-2026 incidents, is **yes, in three distinct ways no generic-HTTP postmortem would predict**: (1) LLM inference has a silent-degradation failure mode with no HTTP-level signal at all — Anthropic's own September 2025 postmortem describes three infrastructure bugs that degraded Claude's *output quality* for a month while every request kept returning `200 OK`, a failure class invisible to any of Kelvran's current health/routing/circuit-breaker machinery, all of which key off HTTP status and latency, never output correctness; (2) token/cost accounting has its own dedicated failure class (tokenizer-version skew, hidden provider-side tokens, streaming-usage-frame omission) that doesn't exist for generic request/response HTTP traffic at all, because "how much did this cost" isn't a question generic infra has to answer per-request; (3) the OSS LLM-gateway comparable closest to Kelvran (LiteLLM) has hit, in real production, almost every one of the concurrency/Redis-failure-mode bug *shapes* Kelvran's own architecture already defends against by design — which is a genuinely useful cross-check: several LiteLLM incidents **validate** decisions Kelvran already made (fail-open on Redis unavailability, atomic single-Lua-script token-bucket operations, `defer`-based concurrency-slot release), while one class (Redis connection-pool storms on concurrent cold-start) has no confirmed Kelvran-side mitigation and is a genuine, previously-unexamined open question.

Kelvran's own recent audit history (`DECISIONS.md`'s 2026-09-08/09-20 entries) already closed several of the classic failure-taxonomy gaps a generic postmortem survey would surface — the budget/TPM check-then-debit TOCTOU race, the Slack-2021-style recovery thundering herd, the streaming-upstream zero-timeout gap, and the per-deployment concurrency-cap gap are all real, already-fixed, verified-against-live-code closures, not open items this report re-raises. What is genuinely new here, verified against real 2025-2026 incidents rather than re-derived from first principles: production-quality/silent-degradation monitoring (Finding 1, the highest-priority genuinely open gap), config-propagation blast-radius/staged-rollout (Finding 2), and the Redis-connection-storm-on-cold-start open question (Finding 4). Findings 3, 5, and 6 are deliberately framed as **external validation of existing decisions**, not new gaps — a real incident taxonomy pass should say so honestly when the evidence points that way, rather than manufacturing symmetric "gaps" for every finding.

## Findings, ranked

### 1. Silent model-quality degradation is a real, documented LLM-specific failure class with zero HTTP-level signal — and Kelvran has no production-facing detector for it (Large)

**What:** Anthropic's own September 2025 postmortem (`anthropic.com/engineering/a-postmortem-of-three-recent-issues`) describes three overlapping infrastructure bugs — a context-window routing error misrouting up to 16% of Sonnet 4 requests to the wrong server pool at peak, a TPU misconfiguration causing random non-English characters to appear in English responses, and an XLA:TPU compiler miscompilation in the approximate top-k sampling operation that silently dropped the highest-probability token in certain batch configurations — that degraded Claude's output *quality* for roughly a month (Aug 5–Sep 12, 2025) while every affected request still returned a normal `200 OK` with a normal-looking (if wrong) completion. Anthropic's own retrospective is explicit about why this class of failure evaded detection: "We never reduce model quality due to demand, time of day, or server load... [but] the evaluations we ran simply didn't capture the degradation users were reporting... we relied too heavily on noisy evaluations," and their concrete fix was to "run [quality] evaluations continuously on true production systems," not merely offline/pre-deploy.

**Why it matters for Kelvran specifically:** every one of Kelvran's health/routing/circuit-breaker mechanisms — active synthetic probing (`gateway/internal/router/health.go`), the per-request fallback-chain circuit breaker (`maxConsecutiveChainFailures = 3`, `gateway/internal/gateway/dataplane/fallback.go:280`), the passive-health-signal research already correctly deferred — key off HTTP status codes, connection failures, and latency. None of them, and nothing else in the gateway, would notice a deployment silently returning subtly-wrong-but-syntactically-valid completions the way Anthropic's own infrastructure did to its own users for a month. `evals`' online-eval sampling (per the briefing's own summary) is "rule-filtered, LLM-judge scoring explicitly deferred pending a content-carrying event source" — i.e. Kelvran already has the *transport* for production samples (the `gatewayevents` contract, per `api/gatewayevents/v1`) but not the *quality-judging* half that would actually catch an Anthropic-style silent-degradation incident happening to one of Kelvran's own configured upstream deployments.

**Consistent with settled decisions?** This does not contradict anything — it sharpens the existing, already-named "online-eval LLM-judge scoring deferred pending a content-carrying event source" deferral by giving it a concrete, real-world trigger this report supplies: this is exactly the kind of production incident that deferral was implicitly betting wouldn't matter yet. It doesn't reopen the deferral (the blocking reason — no content-carrying event source — is still real and unresolved), but it does argue the deferral's priority should rise, since the alternative (Kelvran has zero way to detect an Anthropic-style event happening upstream of it) is now a demonstrated real-world failure mode, not a hypothetical one.

**2026 best practice grounding:**
- Anthropic's own postmortem is a primary source, directly on-topic (an LLM provider's own infrastructure bugs degrading model output quality in production for a month) [anthropic.com/engineering — primary source, confirmed independently by InfoQ's and Rootly's third-party writeups covering the same postmortem, both citing the same underlying facts — 3-0 confirmed].
- Anthropic's own stated remediation ("run quality evaluations continuously on true production systems," "more sensitive evaluations that can more reliably differentiate between working and broken implementations") is the concrete 2026 best-practice pattern this finding recommends Kelvran move toward — not a third-party's opinion about what Anthropic should have done, but what Anthropic itself now does [anthropic.com/engineering — same primary source].
- Caveat: this is a single incident (well-documented, high-confidence as *a real thing that happened*, but only one data point on *how common* this failure class is industry-wide) — no second, independently-sourced LLM-provider postmortem describing an analogous silent-quality-degradation incident was found in this pass; treat "this failure class is common" as a reasoned inference from one strong data point, not a 3-0 confirmed cross-vendor pattern.

**Concrete next step:** this is not "build online LLM-judge scoring now" (that remains blocked on the same real, correctly-named prerequisite) — it's narrower and immediately actionable: a lightweight, rule-based **output-shape anomaly detector** on the existing `gatewayevents` stream (unexpected-script/non-target-language character detection in a response expected to be English — directly matching Anthropic's own "สวัสดี" symptom; a repeated-token or empty-completion detector; a per-deployment rolling anomaly-rate metric) that requires no LLM judge and no new content-carrying event source beyond what already flows through `gatewayevents` today, giving Kelvran a first, cheap tripwire for exactly the symptom class Anthropic's own incident actually produced, while the harder LLM-judge-on-production-samples work stays correctly deferred.

**Effort:** Large overall (full production-quality monitoring), but the concrete next step above is Medium — a new rule-based detector consuming the existing `gatewayevents` stream, no new transport, no LLM-judge dependency.

### 2. Admin/config-propagation has no staged-rollout blast-radius control — two real, independent OpenAI incidents show why this matters at gateway scale (Medium)

**What:** Two separate, real OpenAI postmortems name the identical structural failure: a change applied instantly and uniformly across the whole fleet, with no canary/staged gate, causing a fleet-wide incident. (a) Feb 26, 2025 (`status.openai.com/incidents/01JN2BQN4N618RG49BPMBDQGWZ`): an account-migration script intended for a limited subset of users "inadvertently impacted a broader group," incorrectly changing billing configuration and causing mass false `429` "usage exceeding quota" errors — a **rate-limit/budget-enforcement configuration change with an uncontrolled blast radius**, not a code bug. (b) July 15, 2025 (`status.openai.com/incidents/01K08JJK77JF5D2NN636SDY9WD`): "an internal engineer applied a configuration change with an invalid value... read by multiple services which expanded the blast radius... quickly propagated, causing pods to enter crash loops." OpenAI's own stated fix for (b) is structural: "future critical configuration changes... will roll out to a single cluster first with automated health guards that halt further rollout if availability degrades."

**Why it matters for Kelvran specifically:** Kelvran's own config-propagation mechanism (`internal/configpropagation`, per the briefing) is Redis pub/sub, HMAC-signed, explicitly designed to push an admin-API config change (a virtual-key's budget cap, a rate-limit override, a deployment's weight/health config) to every replica simultaneously. That is precisely the "instant, uniform, whole-fleet" propagation shape both OpenAI incidents show can turn an operator/admin-API mistake into a fleet-wide incident — for OpenAI, a rate-limit/budget config error (directly analogous to Kelvran's own `internal/budget`/`internal/ratelimit` config surface) and a fleet-wide crash-loop (directly analogous to what an invalid `configpropagation` payload reaching every Kelvran replica at once could do, if the payload passed HMAC verification but contained a value downstream code doesn't validate before acting on).

**Consistent with settled decisions?** Additive — does not contradict `docs/rfcs/2026-09-03-distributed-rate-limiting.md`'s or `configpropagation`'s own design, which correctly solved *consistency* (every replica converges to the same config) but never claimed to solve *blast-radius control* (a bad config value converging correctly and instantly everywhere is the actual OpenAI failure mode). No existing Kelvran RFC or `DECISIONS.md` entry currently names a staged/canary rollout requirement for admin-API-driven config changes; this is a genuinely new, real-incident-grounded finding, not a re-litigation of a prior deferral.

**2026 best practice grounding:**
- Both incidents are OpenAI's own first-party status-page write-ups, the highest-confidence source type available (the operator's own admitted root cause and remediation, not third-party speculation) [status.openai.com — primary source, 2 independent incidents, each individually a 1-0 primary-source citation rather than a 3-vote cross-checked claim, since there is exactly one authoritative source for each incident by construction — no second vendor witnessed OpenAI's own internal rollout].
- The remediation pattern named ("single cluster first," "automated health guards that halt further rollout if availability degrades") is the same canary/staged-rollout pattern already well-established in general SRE practice (progressive delivery, canary analysis) — this report did not re-derive that general pattern from a separate source in this pass, so treat the *general* canary-rollout best-practice framing as reasoned synthesis grounded in OpenAI's own stated fix, not independently re-verified against a third canary-specific source this round.

**Concrete next step:** add an opt-in staged-propagation mode to `configpropagation` — a config change first applies to a small, operator-designated subset of replicas (or a single canary replica, mirroring OpenAI's own "single cluster first" language) with a short observation window before the HMAC-signed pub/sub broadcast reaches the full fleet, at minimum for the highest-blast-radius config classes (virtual-key budget/rate-limit overrides, deployment weight/health config) — not required for every admin-API write on day one.

**Effort:** Medium — `configpropagation`'s existing pub/sub mechanism and HMAC-signing stay unchanged; this adds a staged-subset-first delivery mode and an operator-facing opt-in flag, not a redesign.

### 3. LiteLLM's real production regression on rate-limiter fail-open behavior externally validates Kelvran's own existing decision — recommend only a regression test, not a design change (Small)

**What:** A real, closed GitHub issue in `BerriAI/litellm` (#14820, filed 2025-09-23): LiteLLM's newer "V3" rate-limiting implementation changed behavior so that when Redis becomes unreachable, in-flight LLM requests now **fail** (`redis.exceptions.RedisClusterException` propagates to the client) — a regression from LiteLLM's own prior, explicitly-preferred behavior ("in the previous rate limiting implementation, when redis is down an error is logged, but the user LLM request is still handled... I assume most proxy users would prefer that if redis goes down, requests are still handled without rate limiting"). The issue was fixed by `v1.77.5-stable`.

**Why it matters for Kelvran specifically:** this is a real, independent confirmation — from the closest OSS comparable to Kelvran, hit in real production, reported by a real operator — that Kelvran's own `[2026-09-03]` decision ("a Redis backend error fails open (logged, request allowed) rather than rejecting — defensible specifically because `internal/budget.Tracker`'s per-key USD cap is a second, independent control that never touches Redis") is the correct default, and that even a mature, widely-deployed comparable gateway can regress *away* from it without noticing until a real operator hits it in production.

**Consistent with settled decisions?** Fully consistent — this finding does not propose changing Kelvran's design at all. It is included specifically because a real incident taxonomy pass should report validating evidence honestly, not manufacture a "gap" to fill a slot. The actionable value is defensive: LiteLLM's own regression shows this specific fail-open/fail-closed policy is the kind of behavior a future refactor can silently flip without any test catching it (LiteLLM apparently shipped V3 without a regression test for this exact property).

**2026 best practice grounding:**
- Primary source: the GitHub issue itself, including the reporter's reproduction steps (`docker kill` the Redis container, observe request failure) and the maintainer confirmation that it was "fixed since `1.77.5-stable`" [github.com/BerriAI/litellm/issues/14820 — primary source, single-source since this is a first-party bug report/fix in the exact repository being cited, not a claim requiring independent cross-vendor confirmation].

**Concrete next step:** confirm (or add, if genuinely absent) a real `internal/ratelimit/redislimiter` test that kills/blocks the Redis connection mid-test and asserts the request is still allowed through (fail-open), specifically named/commented so a future refactor touching this path re-reads the LiteLLM incident before "fixing" it into fail-closed by accident — the exact regression LiteLLM itself shipped once already.

**Effort:** Small — one regression test (or a doc-comment strengthening an existing one) tied to already-shipped behavior; no production code change anticipated.

### 4. Redis connection-pool storms on concurrent cold-start are a real, quantified LiteLLM production incident — Kelvran's own equivalent code path is unverified this pass (Medium, open question)

**What:** A real, closed GitHub issue in `BerriAI/litellm` (#19724): `RedisCache.init_async_client()` had a check-then-create race where multiple concurrent requests hitting a cold cache simultaneously each created their own new Redis connection pool before any could populate a shared cache — the reporter's own production telemetry showed connections jump from ~14 (normal) to a **peak of 746** across 2 pods during a rollout, plateauing at 600-700 for ten minutes because the orphaned pools were never garbage-collected, only released by a full pod restart. Fixed via double-checked locking (`init_async_client()`) in PR #20852.

**Why it matters for Kelvran specifically:** Kelvran has multiple independent Redis-backed subsystems that each maintain their own client (`internal/ratelimit/redislimiter`, `internal/budget/redisbudget`, `internal/configpropagation`, per the briefing's shipped-capability list) — a rolling deployment or a fleet-wide restart is exactly the "many replicas cold-starting against the same Redis endpoint simultaneously" shape that triggered LiteLLM's incident. This pass did **not** verify Kelvran's own Redis-client initialization code for the equivalent race (whether client/pool construction is idempotent per-process, whether it uses a `sync.Once`-equivalent, or whether a concurrent-connection burst on cold start is even structurally possible given Go's `redis/go-redis/v9` client's own connection-pool semantics, which differ meaningfully from the Python `redis.asyncio` per-event-loop client-caching model LiteLLM's bug was specific to) — this is flagged honestly as a real, external-incident-grounded open question, not a confirmed Kelvran gap, because the verification was not completed this pass.

**Consistent with settled decisions?** No existing Kelvran RFC or `DECISIONS.md` entry addresses Redis client connection-pool initialization races specifically — this is a genuinely unexamined area, not a re-litigation.

**2026 best practice grounding:**
- Primary source: the GitHub issue's own reporter-supplied production telemetry table (connection counts by timestamp) and the linked fix PR (#20852, double-checked locking) [github.com/BerriAI/litellm/issues/19724 — primary source, single-vendor, but with concrete first-party production data (a real before/after connection-count timeline), not speculative].
- Note: this is specific to `litellm`'s Python `redis.asyncio` client, whose per-event-loop connection-pool caching model (see also Finding 5 below, PR #31501, a *different* LiteLLM bug in the same subsystem) is architecturally different from Go's `redis/go-redis/v9` — the underlying *general* lesson (concurrent cold-start against a shared Redis endpoint can create a connection-count spike if pool construction isn't synchronized) is language-agnostic, but the specific reproduction mechanism does not automatically transfer to Kelvran's Go client without direct verification.

**Concrete next step:** a direct, targeted code read of each of Kelvran's three Redis-backed subsystems' client-construction call sites (confirm whether `redis.NewClient`/pool construction happens once per process at startup — the normal Go pattern — versus lazily per-request, which would be the only shape that could reproduce this bug class in Go) — a half-hour verification task, not a design change, likely to close this as "not applicable to Go's client model" but worth confirming rather than assuming.

**Effort:** Medium for the verification pass; Small-if-confirmed-safe, Medium-if-a-real-gap-is-found for any resulting fix.

### 5. LiteLLM's Redis Sentinel-failover permanent-counter-poisoning bug is structurally prevented by Kelvran's existing atomic single-Lua-script design — external validation, not a gap (Small)

**What:** A real, closed GitHub issue in `BerriAI/litellm` (#38987): LiteLLM's Redis-backed rate-limit counters were updated via **two separate Redis commands** (`INCRBYFLOAT` then a conditional `EXPIRE`) — if a Sentinel failover promoted a new master between those two commands, the counter's increment would survive but its expiry would not, leaving a permanent (`TTL=-1`) counter that (because some window keys use only `HH-MM`, not a full date) would then cause **recurring false rate-limit saturation on the same clock minute every subsequent day** until an operator manually deleted the poisoned key. Fixed in PR #39250 by combining the increment and expiry-repair into one atomic Lua `EVAL`.

**Why it matters for Kelvran specifically:** this is directly analogous to Kelvran's own Redis-backed distributed rate-limiter — but Kelvran's `[2026-09-03]` design decision already chose "a hand-rolled Lua token-bucket script running the exact same math as the existing in-memory `TokenBucket`, atomically via EVALSHA," i.e. a **single** atomic Lua operation for the whole token-bucket update, not two separate increment-then-expire commands. LiteLLM's specific bug requires exactly the two-command split Kelvran's design never had.

**Consistent with settled decisions?** Fully consistent — this externally validates the `[2026-09-03]` Lua/EVALSHA design choice as having correctly avoided this exact bug class, not by luck but by the deliberate "atomically via EVALSHA" framing already recorded. No design change is proposed.

**2026 best practice grounding:**
- Primary source: the GitHub issue's own detailed root-cause writeup (naming the exact split-command pattern and its Sentinel-failover interaction) plus its own fix PR #39250's before/after Lua-script diff [github.com/BerriAI/litellm/issues/38987 and PR #39250 — primary source, single-vendor but with a concrete before/after code diff, not speculative].

**Concrete next step:** a small, cheap regression test specifically simulating a Redis master-failover (or connection interruption) *mid-Lua-script-execution* against Kelvran's own token-bucket script, asserting the whole operation is atomic (no observable half-applied state) — since Kelvran's design should already pass this by construction, this is a confirmatory test, not a design change, closing the loop the same way Finding 3 recommends for fail-open behavior.

**Effort:** Small — one new test using the same fault-injection technique (`testcontainers-go` + a forced connection interruption, or a Toxiproxy-style cut, per `chaos-engineering-resilience-testing-2026-09-14.md`'s already-adopted tooling) already available in this repo's test infrastructure.

### 6. Non-2xx upstream responses cached and replayed as success is a real, named LLM-gateway cache-poisoning bug class — Kelvran's error-as-Go-error (not error-as-response) design already structurally avoids it (Small)

**What:** A real, closed GitHub issue in `vllm-project/semantic-router` (#2130), a maintained OSS LLM gateway with a semantic response cache: the cache's `updateResponseCache` call unconditionally stored whatever the upstream returned — including a transient (429/502/503/504) or permanent (400/500) **error response** — and then replayed that cached error as an HTTP `200` to every subsequent semantically-similar request for the full TTL, even after the real upstream had recovered. The root cause: the HTTP status code was computed at the response-header phase but discarded (used only for metrics), never propagated to the response-body/cache-write phase, which had no way to gate on it. Fixed in PR #2131 by threading the upstream status code through to the cache-write gate and skipping the write on any non-2xx status.

**Why it matters for Kelvran specifically:** this is a real, concrete example of the exact bug class Kelvran's own `THREAT_MODEL.md`/`AGENTS.md` treat as highest-priority for the `cache` subsystem — but a direct code read this pass (`gateway/internal/gateway/dataplane/dataplane.go:4286`/`4360`/`4504`, the three upstream-call-response sites) confirms Kelvran's Go adapters return a non-2xx upstream status as a Go `error` value (`&UpstreamHTTPError{...}`), never as a populated `adapter.ChatResponse` — and `runMissPath`'s cache-write calls (`dataplane.go:2081`, `:2122`) only execute in the success path once a real `adapter.ChatResponse` exists. Structurally, an error return can never reach the cache-write call sites at all in Kelvran's current code, unlike `semantic-router`'s Go code (a different codebase, coincidentally also Go), where the HTTP status was tracked as a separate field on a response object that always got constructed regardless of status, and the cache-write path had no independent gate on it.

**Consistent with settled decisions?** Fully consistent — reinforces, does not reopen, `AGENTS.md`'s "never ship a semantic-cache change that removes... the entity/freshness hard-gate" rule and the cache's general design. No gap found; the "why" (idiomatic Go error-as-value propagation, not a deliberate cache-specific defense) is a happy structural consequence worth naming explicitly rather than assuming.

**2026 best practice grounding:**
- Primary source: the GitHub issue's own detailed technical root-cause section (naming the exact code path, `pkg/extproc/processor_res_cache.go`, and the exact asymmetry between the streaming path's incidental protection and the non-streaming path's total lack of one) plus the linked fix PR #2131 [github.com/vllm-project/semantic-router/issues/2130 — primary source, single-vendor, but a detailed, code-level root-cause writeup rather than a shallow bug title].
- Broader academic corroboration that LLM response-cache poisoning is a real, current (2026) research area with cross-cloud-validated attacks (AWS/Azure/Alibaba semantic caches, 82-89% attack success rates) exists in NDSS 2026's "When Cache Poisoning Meets LLM Systems" and "Cache Me, Catch You" papers, and a separate 2026 arXiv paper on semantic-cache key-collision attacks — none of these are specific to the non-2xx-caching bug class this finding centers on (they target semantic-similarity-threshold exploitation, which Kelvran's own hard entity/freshness gate is already specifically designed against per `AGENTS.md`), but they corroborate that cache-poisoning against LLM-serving caches generally is an active, real 2026 threat class worth Kelvran continuing to take seriously, not a stale 2023-era concern [ndss-symposium.org (two papers) + arxiv.org/html/2601.23088 — 3 independent sources on the general threat class, though 0 of them specifically address the non-2xx-caching sub-class this finding is about].

**Concrete next step:** add one explicit regression test asserting a non-2xx upstream response is never written to L1/L2/L3 under any code path — a cheap, high-value confirmatory test given the bug class is real and recently (2026) hit a comparable OSS gateway, even though Kelvran's current design appears to avoid it structurally already.

**Effort:** Small — one regression test; no production code change anticipated pending that test's result.

### 7. Token-counting/billing drift is a distinct, LLM-specific failure class with no generic-HTTP analogue — Kelvran's provider-usage-as-ground-truth design already follows the correct 2026 pattern, with one known, already-disclosed exception (Small)

**What:** Multiple independently-published 2025-2026 sources (a real `openai/tiktoken` GitHub issue showing a 3x local-vs-API token-count mismatch on tool-call-heavy payloads; a real OpenAI community-forum thread showing a `reasoning_tokens` discrepancy nearly 5x the visible completion; and two independently-authored technical deep-dives) converge on the same structural finding: any system that estimates token counts **locally** (a bundled tokenizer library) rather than reconciling against the provider's own **returned** `usage` field will silently drift from the real bill — via tokenizer-version skew (a provider can ship a new tokenizer counting up to ~35% more tokens for identical text, ahead of the client library's next release), un-modeled overhead (tool-call schema serialization, chat-template framing tokens, reasoning tokens, multimodal tile-based image billing), and streaming-usage-frame omission (many SDKs require an explicit opt-in flag to receive the final usage frame in a streamed response, silently under-reporting output tokens if that flag was never set). The universally-recommended 2026 fix in both deep-dives: treat the provider's own returned `usage` as the sole ground truth for cost/budget accounting, never the local estimate, and reconcile continuously against it.

**Why it matters for Kelvran specifically:** a direct code read this pass (`gateway/internal/costaccounting/costaccounting.go`) confirms Kelvran's `Calculator.Calculate` already takes a `Usage` struct sourced from the real upstream provider response (mirroring `internal/adapter.Usage`'s own shape) — Kelvran was never built with a local/bundled tokenizer estimating cost pre-call at all; `internal/budget`'s `Record`/`Reserve`/`Reconcile` machinery is entirely usage-driven, matching the exact best-practice pattern these sources independently converge on. The one documented exception, already correctly named in Kelvran's own prior research (`gateway-2026-09-06.md` Finding 4): the TPM rate-limit dimension is retrospective-only ("always one request behind," per `docs/rfcs/2026-09-05-gateway-tpm-rate-limit.md`'s own explicit rejection of pre-call reservation, "no tokenizer/estimator exists anywhere in this codebase") — which is precisely the state these sources' own recommended fix (use the provider's own pre-flight `count_tokens` endpoint, not a local tokenizer, when a pre-call estimate is genuinely needed) would unblock, exactly matching `gateway-2026-09-06.md`'s own already-flagged "most consequential finding in this report," now independently re-confirmed by a second, unrelated set of 2026 sources rather than resting on Envoy's precedent alone.

**Consistent with settled decisions?** Fully consistent, and doubly confirms two already-recorded positions: (1) Kelvran's decision to use Decimal-precision, provider-usage-sourced cost accounting (`docs/rfcs/2026-09-02-decimal-cost-accounting.md`) rather than any local estimate was already the right call per this fresh, independent source set; (2) `gateway-2026-09-06.md`'s already-flagged pre-completion-token-counting follow-on (provider-side `count_tokens` endpoints to unblock pre-call TPM reservation) is reinforced, not reopened — this pass adds no new argument for building it now, only independent corroboration that the underlying tension is real and correctly already tracked.
