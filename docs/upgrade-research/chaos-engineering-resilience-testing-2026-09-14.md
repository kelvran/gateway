**Scope:** Motivated directly by this week's own real finding — a live concurrent-load production dry run found a WRR same-model-fallback race condition (`router.Select`'s shared cursor could re-select a deployment that had just failed under concurrency), now fixed with a deterministic unit test, but with no systematic *methodology* in this repo for the whole bug class (concurrency-only failure modes) beyond ad-hoc tests written after the fact.

## Findings

1. **No lightweight, production-ready tool exists today for systematically testing concurrency-only failure modes (data races on shared mutable state) — Kelvran's `-race` + hand-written interleaving tests are already the state of the art, not a gap to fill from elsewhere.** The two closest research prototypes target adjacent-but-distinct problems: AdvocateGo (record/replay/fuzzing for concurrency bugs) and GoCR (a resource-aware tracer targeting *blocking* bugs — deadlocks, stuck channels — explicitly not data races). Go's own `gomutants` mutation tester has zero mutators for concurrency primitives (mutex/channel/goroutine/atomic — confirmed via source grep). Go's `synctest` package's fake-clock mechanism explicitly does not treat mutex acquisition as durably blocking and provides no synchronization guarantee on its own — the race detector still has to independently catch races even inside a synctest bubble. **`build_now`** — but the "build" here is Kelvran's own dedicated regression test (Finding 4 below), not adopting a third-party tool.

2. **Go's 2026 runtime investment in concurrency-bug detection targets a different bug class entirely.** The accepted proposal shipping experimentally in Go 1.26 (`GOEXPERIMENT=goroutineleakprofile`) detects goroutine leaks / partial deadlocks via a GC-reachability trick — never data races on live, reachable shared state like a mutex-protected WRR cursor. It also can't catch goroutines blocked on I/O, held in a global channel variable, or stuck in an infinite CPU loop. The design doc never once mentions "race" — it explicitly contrasts itself with the pre-existing race detector as solving a different problem. **Not relevant to Kelvran's bug class.**

3. **Toxiproxy (Shopify) is a strong, real `build_now` match for infrastructure-level network fault injection.** A mature, actively-maintained, test/CI/dev-purpose-built (explicitly not production) client-server TCP proxy — a Go binary intercepts real gateway↔upstream traffic, controlled via a dynamic HTTP API (port 8474), no root access needed. Ships toxics directly matching what Kelvran would want: latency+jitter, timeout, `reset_peer` (simulated TCP RST), bandwidth throttling, packet loss, slow close — addable/removable mid-test without a proxy restart. A new `toxiproxy` Compose profile would follow the exact same profile-gated pattern already established (`redis`, `multi-instance`, `vector-s3`, `observability`). **`build_now`.**

4. **A real, repeatable "concurrent burst against a known-bad deployment" CI regression test is a genuine, build_now gap — and the bug class is proven to recur in this exact domain, not hypothetical.** LiteLLM — the most directly comparable adjacent LLM gateway — recently fixed a near-identical shared-counter race in its own `max_parallel_requests` limiter: a sliding-window reset re-admitted fresh capacity on top of in-flight requests, and forgotten decrements drove the counter negative, admitting far more over-limit traffic than configured (a real, reproducible load-test showed backend concurrency reach 60 against a configured limit of 5, before the fix). Separately confirmed: LiteLLM's own flagship reliability test (`test_oai_azure_release.py`, a 3-hour default soak) is strictly sequential with zero concurrency anywhere in its control flow — even this comparable project has no dedicated concurrency-race testing methodology today. Building this at Kelvran would put it ahead of the curve, not behind it. **`build_now`.**

5. **A genuine Docker-Compose-native chaos orchestrator beyond simple network faults exists (Entropy), but its maturity doesn't support real adoption yet.** Entropy (`ibrahimkizilarslan/entropy`) supports both `docker-compose` and Kubernetes behind one `--runtime` flag, with real auto-detection and a `ContainerRuntime` interface dispatching to real Docker or `k8s.io/client-go` backends plus `tc`/`netem`-based fault injection — verified at the source level, not just a README claim. But it's single-maintainer, 7 stars, ~5 months old — real production-readiness risk is unverified. **`not_yet`** — trigger: the project matures, or a real need for Compose-native chaos beyond plain network faults (which Toxiproxy already covers) emerges. Heavier K8s-native tools (Chaos Mesh, LitmusChaos) remain premature — Kelvran has no K8s deployment at all yet (see the separate Kubernetes-deployment research pass).

## Caveats

This is a synthesis over an already-verified web-research claim set, with light local grounding (confirmed `docker-compose.yml`'s real profile list and `maxConsecutiveChainFailures = 3` directly against the repo) but not a full line-by-line cross-check of `health.go`'s active-probing design or `docs/testing/TESTING.md`'s complete strategy before writing this synthesis — worth a quick cross-check before implementing Finding 3/4. A candidate claim about a static mutex-inference linter (`golintmu`) was explicitly refuted under adversarial verification and is not included above — meaning "static analysis for mutex-guarded fields" remains a genuine, unfilled gap, not a found-and-rejected tool. Go 1.26's `goroutineleakprofile` is still experimental and could change before a stable release. Entropy's "worth watching" framing is weaker than its factual description — the adoption-risk caveat is real, not boilerplate hedging.
