# Cache Next-Upgrade Scan — Deep Research (2026-09-09)

## Question

Now that `gateway/v0.2.0` is tagged and shipped, what are the highest-value next-upgrade candidates for Kelvran's Cache subsystem specifically — extending `cache-2026-09-06.md`'s prior pass, comparing against current (2026) production practice in GPTCache, Redis semantic caching/LangCache, Portkey's semantic cache, LiteLLM's caching layer, and vector-DB-backed LLM caches — for: (1) bootstrapping a semantic cache without production traffic, (2) embedding-model shape for a future semantic L3, (3) TTL/eviction policy vs. LRU/LFU/TinyLFU/ARC practice, (4) negative caching, (5) cache warming, (6) `THREAT_MODEL.md`'s Cache rows vs. current cache-poisoning/hijacking practice, (7) cross-tenant isolation hardening, and (8) anything else a 2026 production semantic/LLM-cache survey would flag?

## Context (Kelvran's own real, current state)

Cache ships embedded inside `gateway/` (`docs/decisions/0002-cache-embedded-in-gateway.md`): L1 in-process exact-match; L2 normalized-match; L3-lite lexical near-duplicate matching with an entity/freshness hard-gate (a `PRD.md` HARD requirement — never weakened in favor of a bare similarity threshold, per `AGENTS.md`'s Never-boundary); `isVolatileQuery` scoped to user-role messages only; guardrail-policy-version-aware cache keys; cache-hit provenance (layer, L3 similarity/age) on OTel spans; N-concurrent-miss stampede protection via `singleflight`, tenant-scoped; per-gate outcome OTel instrumentation for L3-lite's three gates; cross-instance duplicate-work measurement-only infrastructure (`cachecorrelation.Analyze`); provider-side `CacheControl` prompt-caching markers (Anthropic/Bedrock/OpenAI pass-through, not Kelvran's own Cache). Already researched and settled (not re-litigated here): real embedding-based semantic L3 and a distributed/Redis-backed shared cache — both blocked on real production traffic that doesn't exist yet.

## Summary

Grounding the 17 confirmed claims against the live repo (not just the claims in isolation) turned up the most valuable outcome of this pass: **the research brief's own TTL/eviction premise is stale**. Kelvran's L1/L2 already ship bounded LRU (`container/list`, 10k-entry default, MoveToFront-on-hit) + TTL + write-time age tracking, shipped 2026-09-03/09-06 — exceeding the comparable-system baseline (GoModel ships TTL+hourly-sweep only, no LRU at all). A claim that LFU/TinyLFU/ARC would meaningfully outperform LRU was explicitly refuted, so there is no case to add them. The single genuinely new, previously-undocumented finding this pass surfaced: **Kelvran's `Deployment.APIKey` is shared across tenants by the Router's own design, and `CacheControl` auto-populates by default with no tenant-namespacing signal sent upstream** — structurally identical to a real, measured shared-org-credential cross-tenant provider-cache-leakage mechanism a 2026 paper found live against OpenRouter. This sits outside `THREAT_MODEL.md`'s existing Cache-component Information-Disclosure row (which only covers Kelvran's own L1/L2/L3, not provider pass-through) and is cheap to document/decide now — no traffic required. For the two already-deferred items, this pass sharpens rather than changes the calculus. Cache warming and "bootstrap without traffic" both reconfirm "wait for traffic" as still the right call industry-wide. Negative caching remains a genuine open question with no evidence found either way.

## Findings

### Finding 1 — Kelvran's L1/L2 eviction/TTL gap is already closed, not open; the existing LRU implementation exceeds the comparable-system baseline (confidence: high) — **no action needed; premise was stale**

`gateway/internal/cache/inprocess/inprocess.go` ships bounded LRU (`container/list`, `defaultMaxEntries=10_000`, MoveToFront on `Get`) + TTL (`expiresAt` checked at read) + write-time age tracking (`writtenAt`), shipped 2026-09-03 and 2026-09-06 respectively, per `DECISIONS.md` and the code's own comments. GoModel — a real, comparable Go LLM gateway — ships a weaker baseline: `expires_at` TTL + hourly sweep only, no LRU/size bound at all, with advanced eviction explicitly deferred out of v1 (verified 3-0 against its own ADR at a tagged release and current HEAD). A claim that LFU/TinyLFU/ARC would outperform other eviction policies by more than a trivial margin across 18 workload settings was explicitly refuted (0-3) — there is no surviving evidence that switching Kelvran's LRU to LFU/TinyLFU/ARC would be worth the complexity. This research question is fully answered: nothing to build here.

### Finding 2 — Kelvran's `Deployment.APIKey`/`CacheControl` auto-populate design carries a real, previously-undocumented cross-tenant provider-cache-leakage risk analogous to a measured OpenRouter vulnerability (confidence: high on the structural analogy; medium on live exploitability) — **new finding, needs a decision, not a code fix yet**

`Deployment` has one `APIKey`/credential per deployment, and the Router pools requests from potentially multiple tenants onto the same deployment by design. `docs/rfcs/2026-09-07-gateway-cache-control-auto-populate.md`'s `CacheControl` auto-populate ships default-ON with no tenant-namespacing key sent upstream. A 2026 paper (CacheProbe, SAGAI'26/IEEE S&P) measured this exact mechanism live against OpenRouter across 3 providers: when multiple tenants share one org-level provider credential, the *provider's own* prompt cache can leak cache hits/timing across tenants sharing that credential — root-caused specifically to shared credentials, not to any routing-logic bug, and fixed by BYOK (bring-your-own-key), after which the leak signal dropped to noise (p>>0.16). This is structurally identical to Kelvran's own shape: any deployment shared by more than one tenant, with `CacheControl` auto-populated, has the same shared-credential precondition. This sits **outside** `THREAT_MODEL.md`'s existing Cache-component Information-Disclosure row, which only covers Kelvran's own L1/L2/L3 cache, not the provider's own pass-through cache. **This is not a "build now" code fix** — it's a real gap in threat-model coverage that's cheap to document and decide on now, without needing production traffic: does any real Kelvran deployment config actually share one credential across more than one tenant today? If yes, either BYOK-per-tenant or disabling `CacheControl` auto-populate for shared-credential deployments closes it; if no tenant ever shares a deployment credential, the risk is latent/config-dependent and worth naming as a documented constraint rather than building anything.

### Finding 3 — Two comparable systems diverge on future-embedding-L3 architecture; Kelvran's own dormant gRPC adapter already matches the safer pattern (confidence: high) — **sharpens the deferred item, doesn't change the "not yet" verdict**

GoModel went API-only for embeddings (rejected in-process ONNX specifically to avoid native/cgo dependencies, keeping one code path) — the simpler fallback, consistent with Kelvran's own established no-cgo/no-model-file preference for L3-lite/NER. sbproxy instead recommends a co-located sidecar over gRPC specifically so a bad embedding model can only crash the sidecar, not the main proxy process. Kelvran's own dormant `grpcserver`/`grpcclient` adapter (built for a different reason — whole-Cache extraction, per `docs/decisions/0002-cache-embedded-in-gateway.md`) already matches sbproxy's recommended shape structurally, even though it wasn't built for this purpose. This is useful design context for whenever the real embedding-L3 trigger fires (real production miss-telemetry + per-gate ablation data) — it does not change the "not yet" verdict, since that trigger still doesn't exist.

### Finding 4 — Cache warming and bootstrap-without-traffic both reconfirm "wait for traffic" as the correct industry-wide posture (confidence: medium) — **not yet, same blocker as before, reconfirmed**

GoModel explicitly scoped cache warming out of v1. A candidate claim recommending a minimum ~25-30% query-repetition-rate floor (via a one-week embedding-similarity sample) before building a semantic cache at all was refuted (1-2) — no clear external minimum-repetition threshold survived verification. LiteLLM's own posture is default-off/opt-in for semantic caching — an adjacent but non-identical rollout-safety pattern (ship it disabled, let the operator turn it on), not a true "bootstrap without real traffic" answer. No counter-evidence survived verification for skipping the traffic prerequisite Kelvran's own deferral already names. **Trigger**: unchanged — real production traffic sufficient to measure genuine miss/repetition patterns.

### Finding 5 — Kelvran's existing tenant-key + hard-gate design is already stricter than real comparable systems (confidence: high) — **no action needed, validates existing design**

LiteLLM's semantic-cache scoping defaults to key/team/org (matching Kelvran's tenant granularity, verified 3-0 directly against source). Portkey's exact-match cache key is `SHA-256(requestBody+url)` with an `organisationId` field accepted but never actually used in the key — i.e. no tenant identity folded in at all (verified via direct primary-source code read, upgraded from an initial 2-1 vote) — and its semantic match has no entity/freshness gate documented beyond a bare 0.95 cosine threshold. Kelvran's tenant-scoped keys (L1/L2/L3) plus the entity/freshness hard-gate are already stricter than both comparators studied. No action needed — this is a validation of existing design, not a gap.

## Caveats

- Several confirmed claims split 2-1 rather than unanimous 3-0 (Redis's TTL+LRU/LFU framing, the CacheProbe generalization-beyond-OpenRouter clause, the OpenRouter cross-account leakage claim itself before independent code-level verification, and the initial Portkey no-tenant-key claim) — treated as medium confidence and flagged as such.
- GroundedCache/KVGov/CacheAttack/CacheProbe are all single-author-or-recent (2026) arXiv preprints, some not yet peer-reviewed beyond workshop/conference acceptance — real and independently verifiable, but not settled multi-year consensus.
- KVGov's timing-side-channel finding is currently **not applicable** to Kelvran's architecture (no self-hosted vLLM/SGLang backend) — noted as informational-only, not a real gap.
- The refuted-claims list is load-bearing: it rules out LFU/TinyLFU/ARC adoption, rules out treating Redis's own docs as validating Kelvran's hard-gate specifically (that specific claim was refuted, even though the hard-gate design itself is independently confirmed correct by other means), and rules out KVGov's specific per-principal-salt mitigation as an externally-validated pattern to cite (the general direction — per-tenant key salting — is consistent with Kelvran's own already-existing tenant-baked-key design, but that's Kelvran's own reasoning, not an externally-validated mitigation).
- Cache ROI/savings reporting methodology has no confirmed external source (unchanged from the 2026-09-06 pass).

## Recommendation for Kelvran

1. **No code changes needed** for TTL/eviction (Finding 1) or tenant-key/hard-gate design (Finding 5) — both already exceed comparable-system practice; this research question is closed.
2. **Decide, don't necessarily build**: the `Deployment.APIKey`/`CacheControl` cross-tenant leakage risk (Finding 2) needs a real answer to one question — does any current Kelvran deployment config share one credential across more than one tenant? — before deciding whether this is live risk needing a fix (BYOK-per-tenant, or disabling auto-populate for shared-credential deployments) or a documented, currently-latent constraint. Either way, this belongs as a new row or an addendum to `THREAT_MODEL.md`'s existing Cache Information-Disclosure coverage, since today's row only covers Kelvran's own L1/L2/L3, not provider pass-through caching.
3. **Not yet, all correctly deferred with an unchanged trigger**: real embedding-based semantic L3 and cache warming/bootstrap (both need real production traffic); distributed/Redis-backed shared cache (needs a real, quantified duplicate-work cost from an actual multi-instance deployment).
