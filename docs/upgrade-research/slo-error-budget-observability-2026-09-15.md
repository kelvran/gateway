# SLO / Error-Budget Observability — Research Synthesis (2026-09-15)

## Kelvran ground truth (read before any external precedent)

- `gateway/ARCHITECTURE.md` (Observability section, lines ~501-509): confirms a real, live `grafana/otel-lgtm` backend (OTel Collector + Prometheus + Tempo + Grafana) proven with genuine Bedrock pilot traffic, but **no SLO, error-budget, or burn-rate alerting mechanism of any kind exists yet**. ClickHouse remains the eventual production sink target, not a burn-rate layer.
- `gateway/internal/telemetry/telemetry.go` and `gateway/internal/telemetry/result.go`: the raw ingredients for both an availability SLI and per-provider/per-model segmentation **already exist**:
  - `gen_ai.client.operation.duration` (Float64Histogram, unit `"s"`) is recorded **unconditionally on every request** (`telemetry.go`), making it a ready-made numerator/denominator source for an availability or latency SLI.
  - `AttrErrorType = "error.type"` (`result.go:66`) is attached per the OTel GenAI semantic-conventions spec whenever a request fails — giving a real success/failure signal (`error.type` absent = success) without new instrumentation.
  - `AttrGenAIProviderName = "gen_ai.provider.name"`, `AttrGenAIRequestModel = "gen_ai.request.model"`, `AttrGenAIResponseModel = "gen_ai.response.model"` (`result.go:22-25`) are already attached to both `gen_ai.client.operation.duration` and `gen_ai.client.token.usage` — so per-provider/per-model segmentation data is already flowing; nothing downstream (a recording rule, a dashboard panel, an alert) currently slices on it.
  - `kelvran.ratelimit.fail_open` and `kelvran.budget.threshold_crossed` counters, and `kelvran.cache.hit`/`kelvran.cache.lookup`, `kelvran.llm.spend_usd`/`kelvran.cache.savings_usd` counters, are all real and already shipped, per the task's own disclosed baseline.
- No existing code path in `gateway/internal/gateway/dataplane/dataplane.go` (`attemptFallbackChain`, `errorTypeFor`) computes anything error-budget- or burn-rate-shaped — fallback/circuit-breaker logic is per-request, not a rolling-window budget.

Net: **the missing piece is entirely the SLO/burn-rate rule layer on top of already-existing metrics and attributes** — not new instrumentation.

## Executive summary

The multiwindow multi-burn-rate (MWMB) alerting *mechanism* — the Google SRE Workbook algorithm, mirrored by the OSS generator Sloth — is a **build-now** item for Kelvran regardless of its near-zero pilot-tenant traffic: it is a static spec-to-Prometheus-YAML transformation that can be authored and proven correct against synthetic or test traffic today, and a real-world precedent (a homelab MWMB deployment driven purely by synthetic blackbox-probe traffic) shows this is not a theoretical claim. Per-provider/per-model SLO segmentation — so a Bedrock outage doesn't blow the same error budget as an OpenAI blip — is likewise **build-now**: Kelvran's own spans and metrics already carry `gen_ai.provider.name`, `gen_ai.request.model`, and `gen_ai.response.model` (`gateway/internal/telemetry/result.go`), so the segmentation dimension already exists in the data; only the SLO rules that slice on it are missing. What remains genuinely uncertain is narrower than prior framing suggested: the specific numeric SLO *target* for a single-pilot-tenant service is best treated with caution per a Goodhart's-Law/surrogation risk lens (a provisional target risks becoming "reliability theater" rather than a real signal) — but several sharper claims asserting a hard rule ("wait N days for real traffic before setting any target") were checked this round and did **not** survive verification. A 2026 survey of practitioner writeups also shows that even gateways with genuine, sustained production traffic commonly ship nothing beyond static-threshold alerting — no SLO or error-budget concept at all — so building the MWMB mechanism now, against an explicitly-labeled-provisional target, would put Kelvran ahead of common practice rather than behind it.

## Findings

### Finding 1 — The MWMB alerting mechanism itself is build-now, independent of real traffic volume
**Classification: build_now** · **Confidence: high**

Sloth (github.com/slok/sloth, sloth.dev) is a real, actively maintained OSS tool that autogenerates Prometheus SLI recording rules, SLO metadata rules, and multiwindow multi-burn-rate alert rules (page + warning severity) from a single YAML SLO spec, explicitly built on Google's SRE Workbook MWMB framework. Critically, Sloth itself never fires alerts — it emits static rule YAML that Prometheus/Alertmanager evaluates later — meaning generation and validation (`sloth generate`/`sloth validate`) is a pure, stateless spec-to-YAML compile step, agnostic to whether the embedded PromQL queries point at real or synthetic/test metrics. This is independently proven in production-adjacent practice: a documented real-world deployment (woitzik.dev) implements the exact Google SRE Workbook two-tier scheme (30x burn / 1h+2h windows / `for:2m` / page; 6x burn / 30m+6h windows / `for:15m` / warning) as a working `PrometheusRule` CRD, driven entirely by synthetic blackbox-probe traffic on a homelab cluster — not real production load. Separately, the documented rationale for the short (confirmation) window in MWMB alerting is to prevent stale/false alerts by re-confirming the long-window signal is still active (a "reset-time" fix), not to calibrate against real traffic volume — reinforcing that the mechanism's design is orthogonal to traffic volume.

Applied to Kelvran: since `gen_ai.client.operation.duration` and `error.type` already exist unconditionally (`gateway/internal/telemetry/telemetry.go`, `gateway/internal/telemetry/result.go`), a Sloth-style (or hand-authored) MWMB rule set could be written, generated, and even test-fired against synthetic traffic in Kelvran's existing `grafana/otel-lgtm` stack today, with zero dependency on real pilot-tenant volume increasing.

Sources: github.com/slok/sloth (primary, 3-0 ×3 merged claims), sloth.dev/introduction/architecture (primary, 3-0), wasilzafar.com Prometheus/SLOs part 14 (secondary, corroborated against Google's own SRE Workbook, 3-0), woitzik.dev homelab k3s writeup (blog, 3-0, verbatim-verified against live article).

### Finding 2 — Per-provider/per-model SLO segmentation is build-now; Kelvran already emits the labels it needs
**Classification: build_now** · **Confidence: high**

Per-provider (and per-model) segmentation of both error rate and latency is standard, precedented practice for LLM/AI gateways in 2026, not a novel idea: Kong AI Gateway's own OTel documentation confirms its `gen_ai.client.operation.duration` histogram ships with `gen_ai.provider.name`, `gen_ai.request.model`, `gen_ai.response.model`, and `error.type` attributes out of the box, and a companion Kong how-to shows a live Grafana panel breaking down request counts by provider. Independent corroboration (futureagi.com's LLM-gateway glossary, several OSS gateway projects) confirms per-provider error-rate and latency-percentile breakdowns are treated as baseline LLM-gateway observability, not an advanced feature. A blog-level illustrative example makes the underlying rationale concrete: averaging a 99.9%-healthy provider with a 92%-degraded provider into a blended 96% aggregate SLI hides the failing provider entirely — exactly the "Bedrock outage vs. OpenAI blip" scenario the research question raises.

Applied to Kelvran: this is not a future instrumentation project. `gateway/internal/telemetry/result.go` already attaches `gen_ai.provider.name` (validated against a real well-known-enum per `docs/rfcs/2026-09-05-gateway-gen-ai-provider-name-validation.md`, confirmed value `"aws.bedrock"` in `result_test.go`), `gen_ai.request.model`, and `gen_ai.response.model` to every `gen_ai.client.operation.duration` and `gen_ai.client.token.usage` record. The gap is purely a missing SLO/recording-rule layer that groups by these existing attributes — a pure Prometheus/Sloth-config change, not new Go instrumentation.

Sources: developer.konghq.com/ai-gateway/ai-otel-metrics (primary, 3-0), developer.konghq.com/how-to/visualize-llm-metrics-with-grafana (primary, corroborating), futureagi.com/glossary/llm-gateway (blog, 3-0, full-page-verified), majiafan.hashnode.dev LLM-gateway observability post (blog, 3-0, verbatim-verified illustrative example).

### Finding 3 — The specific numeric SLO target is where caution is warranted, but the evidence for a hard traffic-volume gate is weaker than prior framing assumed
**Classification: not_yet (softer than previously stated)** · **Confidence: medium**

The one claim that survived 3-0 verification on this side of the question is a conceptual risk framework, not a hard technical rule: SLO metrics are vulnerable to Goodhart's-Law-style surrogation, where the proxy measure (the target number) drifts from and replaces the underlying goal it represents — the USENIX ;login: piece "Avoiding the SLO Reliability-Theater Trap" names this explicitly for SLOs specifically, not just metrics generally. This is directly relevant to judging whether a provisional SLO number for Kelvran's real single-pilot-tenant, near-zero-volume traffic profile would be meaningful or merely performative — but it is a caution about interpretation and governance, not a rule that blocks building the mechanism.

Notably, several sharper claims that would have supported a hard "wait for N days/30 days of real traffic before setting *any* target" rule were checked this round and **did not survive verification** (0-3 or 1-2 votes): a claim that Google's own SRE Workbook names low-traffic services as a persistent burn-rate failure mode, a claim that a named source recommends 90-day/30-day historical baselining before picking a target, and a claim that "leading teams" set internal SLOs 1-2% tighter than observed historical uptime. None of these held up under verification this round. This means the "SLO target is traffic-gated" framing carried forward from prior rounds should be treated as a live inference from general SRE practice and the Goodhart's-Law risk lens — reasonable to keep operating on — rather than as separately re-confirmed by new primary-source evidence this round.

Sources: usenix.org/publications/loginonline/avoiding-slos-reliability-theater-trap (secondary, credible SRE-practitioner venue, 3-0, primary-quote-verified).

### Finding 4 — Even gateways with real production traffic commonly skip SLO/error-budget concepts entirely, making early MWMB adoption a genuine differentiator
**Classification: build_now (opportunity framing)** · **Confidence: medium**

A detailed, current (2026) practitioner writeup on running an LLM gateway in production (mdsanwarhossain.me) devotes an entire "Observability: Tracing, Metrics & Alerts" section to alerting, and uses **only** static numeric thresholds (`llm_gateway_error_rate > 1% over 5 minutes → PagerDuty`, plus p99 latency, fallback rate, cache-hit rate, cost/hour, and budget thresholds) — a full-text sweep confirms the terms "SLO," "error budget," and "multi-window" appear nowhere in the piece, and "burn rate" appears exactly once, referring to dollar-spend burn, not SRE-style error-budget burn. This is one concrete, verified data point that a fairly sophisticated, real-production LLM-gateway operational writeup in 2026 still does not reach for error-budget/burn-rate alerting at all — consistent with the research question's framing that this maturity level is uncommon even where real traffic exists.

Implication for Kelvran: adopting even a provisional MWMB mechanism now (Finding 1) — clearly labeled as provisional per the Finding 3 caution — would place Kelvran's observability maturity ahead of at least this documented real-traffic comparator, independent of Kelvran's own traffic volume.

Sources: mdsanwarhossain.me/blog-llm-gateway-production.html (blog, 3-0, full-article-terminology-swept and verbatim-verified).

## Answers to the four research questions

1. **SLO target vs. alerting mechanism — which is traffic-gated?** The mechanism (MWMB Prometheus rule generation/validation, e.g. via Sloth or hand-authored rules) is not traffic-gated — Finding 1 shows it is a static generator that can be built and tested with synthetic traffic today. The target number is where caution applies, but per Finding 3 the strongest surviving evidence for that caution is a conceptual Goodhart's-Law/surrogation risk, not a settled quantitative rule (e.g. "wait 30 days") — several claims asserting such a hard rule did not survive verification this round.
2. **Is the MWMB algorithm itself a real `build_now` item?** Yes — Finding 1, high confidence, corroborated by a live homelab deployment run entirely on synthetic/blackbox-probe traffic.
3. **What's commonly missing even with real traffic?** Per-provider/per-model SLO segmentation is standard/precedented and immediately buildable in Kelvran on data it already emits (Finding 2). Separately, even sophisticated real-production LLM-gateway writeups often skip SLO/error-budget concepts entirely in favor of static thresholds (Finding 4) — so the SLO/burn-rate layer itself is the more common industry-wide gap, not per-provider segmentation specifically.
4. **Guardrail-block-rate / cache-hit-rate as their own signals?** Not confirmed this round. A claim that LLM-gateway metrics explicitly track guardrail-block-rate and fallback-trigger-rate as distinct per-route signals was checked and refuted (0-3). Cache-hit-rate degradation as a leading indicator was not separately confirmed or refuted this round — open question below.

## Caveats

- Several claims specifically underpinning a **hard** "SLO target must wait for real traffic" rule were checked this round and refuted (0-3 or 1-2 votes): Google's SRE Workbook allegedly naming low-traffic services as a burn-rate failure mode, a 90-day/30-day historical-baseline recommendation, and a "-1-2% tighter than historical uptime" precedent. Treat the traffic-gating of the SLO target as a reasonable inference from general SRE practice and the Goodhart's-Law risk lens (Finding 3), not as freshly re-confirmed primary-source fact.
- Source quality is mixed: Sloth's and Kong's own docs/README are strong primary sources; several other sources (majiafan.hashnode.dev, mdsanwarhossain.me, woitzik.dev, wasilzafar.com) are individual practitioner blogs — lower authority tier individually, but each was independently fetched and verbatim-verified against its live page content rather than taken on the excerpted quote alone.
- Time-sensitivity: the underlying MWMB technique is Google's ~2018-era SRE Workbook methodology and is stable/non-time-sensitive. Sloth and Kong AI Gateway are both confirmed actively maintained as of 2026, but exact CLI/config syntax should be re-verified at adoption time.
- This synthesis is entirely about external precedent to adopt — ground-truth checks against `gateway/ARCHITECTURE.md` and `gateway/internal/telemetry/telemetry.go`/`result.go` confirm Kelvran has zero existing SLO/error-budget/burn-rate mechanism today, consistent with the task's framing.
- Per the task's own settled context, a fleet-wide/global retry budget remains explicitly gated on a real production-traffic-volume floor Kelvran doesn't have — that finding is unrelated to and not contradicted by anything here; the MWMB *alerting* mechanism researched in this report is a different mechanism (observability/alerting, not a resilience/retry-budget control) and this report's own findings show it is not subject to the same traffic-volume gate.
