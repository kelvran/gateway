# Kelvran Gateway — Plugin Marketplace / Ecosystem-Strategy Models (Kong Plugin Hub, Envoy Gateway, Higress) — 2026 Research

**Date:** 2026-09-22
**Scope:** The ECOSYSTEM/BUSINESS-MODEL side of third-party gateway-plugin extensibility — how third-party plugins get discovered, vetted, distributed, and monetized in production 2026 API/AI gateways (Kong Plugin Hub, Envoy Gateway's extension ecosystem, Higress's plugin marketplace) — deliberately excluding the technical extensibility mechanism itself (WASM ABIs, `wazero`, Starlark, `proxy-wasm`), which is already covered by this repo's own `docs/upgrade-research/guardrail-plugin-extensibility-2026-09-15.md` and `docs/upgrade-research/wasm-plugin-extensibility-2026-09-22.md`. This pass asks a different question than either of those: even if a technical extension point existed, is there a *marketplace/ecosystem-governance* model worth building around it, and is now the right time?
**Method:** Real external research via `web_search_exa`/`web_fetch_exa` against primary sources — Kong's own Plugin Hub (`developer.konghq.com/plugins/`), Kong's pricing page, Kong's own blog and press release announcing its Premium Technology Partner Program, Kong's docs-repo README, a Kong Nation community thread, Envoy Gateway's own community design docs and extension-server task docs (`gateway.envoyproxy.io`), core Envoy's `EXTENSION_POLICY.md`/`REPO_LAYOUT.md`, Higress's own plugin-image spec, `CONTRIBUTING_EN.md`, `AGENTS.md`, and a live GitHub issue documenting its MCP-marketplace review SLA — plus, via a parallel research pass on the same question, Tetrate's own "Built on Envoy" marketplace repository (`github.com/tetratelabs/built-on-envoy`), its `CONTRIBUTING.md`, its launch press release, and independent trade-press coverage (The New Stack, TFiR). Every load-bearing claim below states how many independent primary sources it was cross-checked against.

---

## Executive summary

The systems named in the research brief turn out not to be variations on one model — they are categorically different answers to "should this project run a plugin marketplace at all," and the research brief's framing (grouping Kong, Envoy Gateway, and Higress as comparable "ecosystem strategies") obscures that. **Kong runs the only real commercial, in-project marketplace of the three**: a partner-application-gated Plugin Hub with an explicit two-tier certification ladder (a base "Technical Partner" tier, and a "Premium Technology Partner" tier launched 2024-09-11 that adds "rigorous validation against the latest releases" plus dedicated Kong engineering support), and Kong's own docs state plainly that submissions are accepted "from trusted technical partners, on a limited basis" — an invite/approval funnel, not an open self-serve app-store listing flow [confirmed 3-0: `developer.konghq.com/plugins/`, Kong's own 2024 partner-program blog post, and Kong's own press release, cross-checked against a fourth source — Kong's docs-repo README's own submission-policy line]. **Higress runs a real, working plugin-marketplace *UI*, but its actual governance is just Higress's own ordinary open-source PR/maintainer-review process** — official marketplace plugins live inside the same monorepo as core code, reviewed by the same maintainers under the same `CONTRIBUTING_EN.md`/`AGENTS.md` rules as any other change, with zero certification tier, zero partner-application step, and zero monetization mechanism [confirmed 2-0: Higress's own `CONTRIBUTING_EN.md`/`AGENTS.md`, and a maintainer's own comment on a live GitHub issue]. **The Envoy Gateway *project* itself has no plugin marketplace at all** — its own community design document states, twice, in its own words, that its extensibility goal is to "provide a common foundation for vendors to build value-added products without having to re-engineer fundamental interactions" [confirmed 2-0 across two `gateway.envoyproxy.io` pages stating the identical line], deliberately delegating discovery/vetting/distribution/monetization to the vendor layer one level up.

That delegation is not hypothetical: a parallel research pass run alongside this one found that a vendor **did** build a real marketplace on top of Envoy — Tetrate's **"Built on Envoy"** (`builtonenvoy.io`), launched 2026-03-11, an Apache-2.0, GitHub-PR-based catalog of Envoy extensions (Cedar Auth, SAML Auth, AWS Bedrock guardrails, Azure Content Safety, and others) that Tetrate seeded and explicitly frames as aiming to become "a community-sustained ecosystem," not a Tetrate-only catalog [confirmed 3-0: Tetrate's own press release, The New Stack's launch coverage, and Tetrate's own `CONTRIBUTING.md`/extension-guidelines in the `tetratelabs/built-on-envoy` repository]. Its governance, read directly from Tetrate's own contribution guide, is ordinary GitHub PR review with no distinct security-audit, code-scanning, or formal approval pipeline described for marketplace submissions specifically — CNCF is not a governing party (the repo lives under `tetratelabs`, not `envoyproxy` or `cncf`; a supportive CNCF-CTO quote in the launch press release is not a governance role). This is genuinely useful, on-point evidence: it confirms Envoy's own "let vendors build the marketplace" strategy really did produce a marketplace eventually — just a young one (barely six months old at this research date), run by a single vendor, with the *lightest*-weight governance of any system in this research (lighter even than Higress's in-tree PR model, since Tetrate's guidelines describe no distinct plugin-specific review criteria beyond standard code review).

The second, more consequential finding is that **the monetization half of the research brief's own question has a thin, largely negative answer across every system examined — Kong included**. No revenue-share, listing-fee, or plugin-transaction mechanism was found anywhere in Kong's, Higress's, Envoy Gateway's, or Tetrate's "Built on Envoy" documentation. Kong monetizes its *own* first-party AI Gateway plugins by paywalling them inside its Konnect/Enterprise subscription tiers (a platform-subscription model, not a marketplace-transaction model) and describes third-party partner benefit only vaguely as "new revenue opportunities" with no defined mechanism [confirmed 2-0: `konghq.com/pricing`'s "AI Gateway Paid Plugins" table, and Kong's own Premium Technology Partner blog post]. Higress, Envoy Gateway, and Tetrate's marketplace are all free/open-source with no plugin-marketplace monetization mechanism of any kind. If Kelvran were ever looking for a proven "third-party plugin marketplace revenue model" to imitate, none of the systems this research examined actually has one to copy.

Grounded against Kelvran's own real, current state — pre-1.0 (`gateway/v0.9.0`/`evals/v0.8.0`), explicitly "a pre-1.0, zero-external-consumer project" per `STATUS.md`'s own words, self-hosted-only by deliberate `PRD.md` non-goal, no partner/BD/sales organization, and — critically — **no plugin API surface of any kind exists today**, confirmed by both of this repo's own prior research passes reaching independent "not yet" verdicts on the underlying technical extension point itself — the honest verdict is that a plugin marketplace/ecosystem strategy is not merely unbuilt but categorically premature at Kelvran's current maturity stage. This is not a generic "marketplaces take time" argument; it is that every real-world sequencing pattern found in this research (Kong's partner-tier apparatus, Higress's curated-contribution UI, even Tetrate's lightweight vendor-seeded catalog) was built only after or alongside real demand — either a commercial-vendor relationship or a standing open-source contributor community — layered on top of a stable, external-facing plugin ABI. Kelvran has neither the demand signal nor the ABI.

## Findings, ranked

### 1. Kong Plugin Hub is a real commercial marketplace with an invite-gated, two-tier partner-certification ladder — not a self-serve app store (Informational)

**What:** Kong's own docs-repository README states the submission policy in its own words: "We are currently accepting plugin submissions to our plugin hub from trusted technical partners, on a limited basis." This is the base tier. On top of it, Kong launched a formal "Premium Technology Partner Program" at API Summit 2024 (2024-09-11): premium-tier plugins "undergo rigorous validation against the latest releases and get dedicated support from Kong's engineering team," with a "streamlined pathway for community plugins to transition to the premium tier." The live Plugin Hub itself (`developer.konghq.com/plugins/`) visibly separates first-party bundled plugins (filterable by license: Free / Kong Gateway Enterprise) from a distinct "3rd Party Plugins" section, each carrying a "Support by: `<vendor>`" line (e.g. AWS Request Signing — "Support by: The LEGO Group"; DataDome, Salt Security, Wallarm, etc.) — an older archived version of the same hub page shows the underlying filter taxonomy explicitly: `All / Kong / Technical partner / Premium partner / Support by 3rd party`.

**Why it matters for Kelvran specifically:** this is the single clearest, most checkable data point that "plugin marketplace" in 2026 production practice does not mean "anyone can submit a plugin" — it means a business-development relationship (become a Kong Partner, apply, get accepted on a limited basis, optionally graduate to a premium, more deeply validated tier) layered on top of the technical plugin mechanism. Running a marketplace like Kong's requires an organization capable of running a partner program — reviewing applications, maintaining a partner portal, doing "rigorous validation against the latest releases" on an ongoing basis, providing "dedicated support" — none of which exists at Kelvran today (single maintainer, no BD/partner function of any kind).

**Consistent with settled decisions?** No prior Kelvran decision addresses this directly — `DECISIONS.md` has no partner-program or marketplace entry to be consistent or inconsistent with. It is, however, consistent with `DECISIONS.md`'s and `PRD.md`'s repeatedly-demonstrated pattern of deferring organizational/commercial capability expansion (hierarchical org-scoped budgets, a hosted/SaaS offering, billing/monetization integration for Kelvran's *own* product) until a real, named trigger exists — this finding shows a plugin marketplace belongs in that same deferred bucket, for the same reason: the organizational capability to run it does not exist yet.

**2026 best practice grounding:**
- Kong's own docs-repo README states the "trusted technical partners, on a limited basis" submission policy verbatim [`github.com/Kong/docs.konghq.com`'s `README.md` — primary source, Kong's own repository].
- Kong's own blog post and its own press release both independently confirm the Premium Technology Partner Program's launch date, its "rigorous validation against the latest releases" claim, and the "streamlined pathway... to the premium tier" line, in near-identical wording across two separately-published Kong-authored documents [`konghq.com/blog/news/premium-technology-partner` and `konghq.com/company/press-room/press-release/...` — confirmed 2-0, both Kong-authored primary sources, independently worded but stating the same facts].
- The live Plugin Hub's "3rd Party Plugins" section and its "Support by: `<vendor>`" convention are read directly from the current, live `developer.konghq.com/plugins/` page [primary source, live as of this research date] and corroborated by an archived legacy version of the same page showing the explicit tier-filter taxonomy (`Kong / Technical partner / Premium partner / Support by 3rd party`) [`legacy-gateway--kongdocs.netlify.app/hub/` — a second, independent Kong-authored snapshot, confirmed 2-0].

A follow-up check (run in parallel, specifically to stress-test this finding) re-fetched `developer.konghq.com/plugins/` directly and confirmed the page organizes plugins into categories including a "Monetization" category, and found one concrete, unambiguous example of Konnect-gating within the Hub itself: the "Metering & Billing" plugin is labeled "A licensed add-on through Konnect Metering & Billing," i.e. not available to open-source Kong Gateway users without a Konnect license (see also Finding 5). Beyond that one plugin, the Hub page itself does not state a general rule for which plugins are open-source-Gateway-accessible versus Konnect/Enterprise-only — so this document does not claim a blanket "OSS excluded" rule, only this one concrete, named example. The same follow-up re-fetched the Premium Technology Partner blog post directly and confirmed its date (2024-09-11) and its "Kong Konnect and Kong Gateway Enterprise" framing are unchanged from what this document already cites; no newer (2025/2026) update to that specific program was found, though the check's own search tooling was rate-limited, so "no newer update found" should be read as "not yet exhaustively searched," not as a confirmed absence of one.

**Concrete next step:** None for Kelvran today — cite this finding if a partner-program question is ever raised, as the concrete shape a Kong-style program would require (application review, a certification tier, ongoing validation capacity) before deciding whether to build one.

**Effort:** N/A (informational).

### 2. Higress's "marketplace" is really Higress's ordinary open-source contribution pipeline wearing a discovery UI — not a distinct plugin-marketplace governance process (Informational)

**What:** Higress's Console ships a real "Plugin Market" UI (with global / domain-level / route-level configuration entry points), and `higress.ai/en/plugins` lists dozens of official plugins across categories including AI-specific ones (AI Proxy, AI Agent, AI Search, AI Transformer). But the plugins behind that UI are not independently vetted artifacts from arbitrary third parties — they live inside the same `alibaba/higress` monorepo as core gateway code (`plugins/wasm-go/extensions/`, `plugins/wasm-rust/`), and getting one merged follows the *exact same* PR process as any other Higress code change: fork, branch, PR against `main`, reviewed and merged by a Higress maintainer, per `CONTRIBUTING_EN.md`. `AGENTS.md` layers a further, stricter gate specifically for AI-assisted contributions (a maintainer-approved "Design Issue" required before implementation begins, full command-level verification evidence required before claiming success) — a governance bar aimed at code-contribution quality, not at plugin-marketplace certification. A separate, distinct, and materially faster-turnaround process exists for Higress's sibling MCP-server marketplace (`mcp.higress.ai`): a maintainer's own comment on a live GitHub issue states plugins are reviewed and, once merged, published "within one day" — using an auto-generated YAML from existing API docs, with explicitly no staging environment yet ("Currently, there is no stage environment, but we will test according to your README as soon as it goes live"). A follow-up check (run in parallel, specifically to stress-test the "zero monetization" half of this claim) fetched the official `higress.io/plugins` marketplace page directly and confirmed it as "purely a free/open listing with no monetization or paid-listing mechanism described": the page self-describes as the "官方插件库" (official plugin library), states its documentation is "Distributed under CC-BY-4.0," identifies the project as a "CNCF Sandbox 项目" (CNCF Sandbox project), and frames contribution as "贡献插件到社区" (contribute plugins to the community) via GitHub PR — consistent with the mechanism already described above. A repository-wide grep of `higress-group/higress` for price/paid/commercial terms surfaced nothing relevant (only unrelated code matches on words like "store" inside variable names). The one commercial-adjacent link found anywhere on the Higress site is a separate Alibaba Cloud "AI 网关企业版" (AI Gateway Enterprise Edition) product page — outside the plugin marketplace itself, and not a transaction mechanism for individual plugins.

**Why it matters for Kelvran specifically:** this is the clearest illustration that "marketplace" in Higress's case does not imply a separate certification/vetting apparatus distinct from ordinary code review — it implies a curated, in-tree catalog with a nice UI on top, governed by exactly the same open-source contributor pipeline (fork → PR → maintainer review → merge) any Higress code change goes through. This is a materially different, and materially *cheaper*, model than Kong's partner-application ladder — but it still presupposes something Kelvran does not have: a standing pool of external contributors making PRs against the repo, and maintainers with spare review bandwidth to evaluate plugin-shaped PRs specifically (as opposed to Kelvran's own core-feature PRs).

**Consistent with settled decisions?** New finding — no prior Kelvran decision addresses an in-tree-contribution-as-marketplace model. It is directly relevant context for the prior `guardrail-plugin-extensibility-2026-09-15.md` research's own open question ("has any real external party... ever actually asked to extend Kelvran's guardrail detection without forking?") — Higress's model shows that even the *lightest-weight* in-project "marketplace" still assumes external contributors already exist; it does not manufacture them.

**2026 best practice grounding:**
- `CONTRIBUTING_EN.md`'s fork/branch/PR workflow and its own statement that "PR is the only way to make change to Higress project files" describe the mechanism directly, from Higress's own repository [`github.com/alibaba/higress`'s `CONTRIBUTING_EN.md` — primary source].
- `AGENTS.md`'s "Mandatory issue-spec gate for agent-assisted changes" — requiring maintainer-approved Proposal and Design Issues before implementation, and disclosure of AI-agent participation — is read directly from the same repository's own current governance file [`github.com/higress-group/higress`'s `AGENTS.md` — primary source], independently corroborating that plugin contributions and core contributions share one governance path (plugins live under `plugins/`, which `AGENTS.md` explicitly documents as subject to the same gate).
- The MCP-marketplace's same-day review SLA and "no stage environment yet" caveat are a maintainer's own words on a live, real GitHub issue [`github.com/alibaba/higress` issue #2113 — primary source, direct maintainer comment].
- Cross-checked 2-0 across two independently-published Higress-owned documents (`CONTRIBUTING_EN.md`/`AGENTS.md` describing the general mechanism, and the GitHub issue describing the specific MCP-marketplace SLA) — high confidence on the "in-tree contribution, not a separate certification process" claim.
- The zero-monetization confirmation is a direct fetch of `higress.io/plugins` itself (the official Chinese-language marketplace page, self-describing as CC-BY-4.0-licensed and a CNCF Sandbox project) plus a repository-wide grep of `higress-group/higress` for commercial/pricing terms that turned up nothing relevant — two independent checks against the same conclusion [confirmed 2-0].

**Concrete next step:** None for Kelvran today — informational precedent for what the cheapest real-world in-project "marketplace" actually looks like, should a real external-contributor trigger ever arrive.

**Effort:** N/A (informational).

### 3. The Envoy Gateway *project* itself deliberately runs no plugin marketplace — its own design docs state, twice, that its ecosystem strategy is to let vendors build the product/marketplace layer independently (Informational)

**What:** Envoy Gateway's own community design document for extensibility states the project's goal in its own words: to "provide a common foundation for vendors to build value-added products without having to re-engineer fundamental interactions." The exact same sentence, framed as one of the project's stated goals, is repeated verbatim on the separate, current Extension Server task page. Both documents describe the technical mechanism (a vendor-run gRPC Extension Server hooking into Envoy Gateway's xDS translation pipeline) but neither describes, links to, or references any marketplace, plugin registry, listing site, certification tier, or discovery UI run by the Envoy Gateway project itself — and no search conducted in this pass found one anywhere on `gateway.envoyproxy.io`. Separately, *core* Envoy (not Envoy Gateway) has its own real, well-documented governance process for extensions landing inside the Envoy binary itself (`EXTENSION_POLICY.md`): every core extension needs an existing-maintainer sponsor and two named reviewers, is held to the full Envoy code-quality bar, and can be removed by maintainer vote if unmaintained; a lower-barrier `contrib/` path exists for extensions not held to that same bar, with an explicit, named trade-off ("Contrib extensions are not eligible for Envoy security team coverage"). This is real vetting machinery — but it governs code landing inside Envoy's own repository and binary, not the distribution of independent third-party artifacts through any marketplace the *project* runs.

**Why it matters for Kelvran specifically:** Envoy Gateway's own explicit design-doc framing is the strongest direct evidence in this research that "we are infrastructure vendors build on top of, we deliberately are not ourselves a marketplace" is a legitimate, real, currently-shipping 2026 ecosystem strategy for a project at Envoy Gateway's own scale — not a gap or an oversight. Whether that strategy actually produces a marketplace eventually (it does — see Finding 4) is a separate question from whether the *project itself* needs to run one.

A second, independent check (run in parallel, specifically to stress-test this finding) confirmed the "no centralized catalog" claim two further ways: a GitHub issue search inside `envoyproxy/gateway` for a marketplace/catalog/registry proposal returned zero results — no roadmap item, issue, or discussion proposing one exists in that repository at all — and no de facto community-maintained registry (an "awesome-envoy-gateway"-style list) was found on GitHub either. That same check also surfaced a relevant historical data point: Solo.io's **WebAssembly Hub** (`webassemblyhub.io`), a real, older, Envoy-*core* (pre-dating Envoy Gateway's own extension-server mechanism) WASM-filter distribution point, is now defunct — `getenvoy.io` (its companion install-docs domain) silently 301-redirects to Envoy's own generic install docs with no deprecation notice, and `webassemblyhub.io` itself currently shows only a bare "Coming Soon" placeholder with no stated relaunch date, reading as a lapsed/parked domain rather than an actively-managed service. This is a fourth-ish data point in the same direction as this finding, from a different vendor (Solo.io, not Tetrate) and a different Envoy-ecosystem layer (core Envoy WASM filters, not Envoy Gateway's extension server): a centralized Envoy-plugin marketplace has been *tried* before, by a real, resourced vendor, and did not survive — independent of whether Tetrate's newer attempt (Finding 4) will fare differently.

**Consistent with settled decisions?** New finding, and it reinforces — from an external, independent angle — the "not yet" verdict both of this repo's own prior extensibility research passes already reached on the underlying technical mechanism.

**2026 best practice grounding:**
- The "common foundation for vendors to build value-added products" goal is stated identically on two separate, current `gateway.envoyproxy.io` pages (the community extensibility design doc and the Extension Server task doc) [confirmed 2-0, both primary Envoy Gateway-authored documentation].
- The absence of any marketplace/registry/listing mechanism *run by the Envoy Gateway project itself* is an absence-of-evidence result from this pass's own explicit searching, not a claim independently verified as "provably does not exist anywhere" — disclosed as such, consistent with this repo's own research-documentation convention for negative results. A follow-up GitHub issue search inside `envoyproxy/gateway` (a separate check, done specifically to stress-test this claim) corroborates it: zero issues/discussions proposing a marketplace/catalog/registry were found, and no community "awesome-list"-style registry exists either.
- Core Envoy's `EXTENSION_POLICY.md` (sponsor + two reviewers + removability-by-maintainer-vote for core extensions; the `contrib/` lower-barrier path and its explicit "not eligible for Envoy security team coverage" trade-off) is read directly from Envoy's own repository [`github.com/envoyproxy/envoy`'s `EXTENSION_POLICY.md` — primary source], corroborated by `REPO_LAYOUT.md`'s description of the `contrib/` directory's structure and purpose [same repository, a second file — confirmed 2-0 within Envoy's own repo].
- Solo.io's now-defunct WebAssembly Hub is confirmed via a direct, live check of both its domains: `getenvoy.io` 301-redirecting to Envoy's own generic docs with no deprecation banner, and `webassemblyhub.io` itself showing a bare "Coming Soon" placeholder [direct site checks, primary-source in the sense of observing the live pages themselves; no independent second source corroborates an exact retirement date, so this is graded as a single-check observation, not a 2-0 cross-confirmed claim].

**Concrete next step:** None — this closes off, with a real checked answer, an implicit assumption the research brief's framing could otherwise have carried (that all three named systems run comparable, project-run marketplaces). They do not; see Finding 4 for what actually filled that gap, one layer up, and for why a newer attempt (Tetrate's) coexists with an older one (Solo.io's) that already failed.

**Effort:** N/A (informational).

### 4. The vendor layer Envoy Gateway delegates to *did* eventually build a real marketplace — Tetrate's "Built on Envoy," launched 2026-03-11 — but it is the lightest-weight, least-formally-governed marketplace of any system in this research (Informational)

**What:** A parallel research pass run alongside this one, specifically checking whether Envoy's vendor layer produced a real marketplace, found one: **Tetrate's "Built on Envoy"** (`builtonenvoy.io`, GitHub: `tetratelabs/built-on-envoy`), announced via PRNewswire and Tetrate's own press release on 2026-03-11, described as "a community-driven marketplace for Envoy Proxy extensions" that is "free to use" (Apache 2.0). Tetrate's own CTO is quoted framing it explicitly as community-first, not vendor-curated: "We built this for the ecosystem, and we are inviting everyone to come use it and contribute back." The New Stack's independent launch coverage confirms the same framing in its own words: "Tetrate has seeded the marketplace, but the long-term vision is a community-sustained ecosystem where organizations across industries share what they have built." The initial seeded catalog includes real, named extensions (Cedar Auth, SAML Auth, an AWS Bedrock guardrails integration, an Azure Content Safety integration, a Databricks file-server contribution). Read directly from the repository's own `CONTRIBUTING.md` and its `extensions/` "Extension Guidelines," the actual governance is ordinary GitHub PR review — fork, add files, document, open a PR — with guidelines limited to "single responsibility," "comprehensive documentation," "working examples," and "follow Envoy best practices"; **no distinct security-audit, code-scanning, or formal approval pipeline is described for marketplace submissions specifically**, beyond the same maintainer PR review any GitHub project uses. The repository lives under Tetrate's own `tetratelabs` GitHub org, not `envoyproxy` or `cncf` — CNCF's CTO gave a supportive quote in the launch press release, but no source describes CNCF as governing, vetting, or formally endorsing the extension catalog.

**Why it matters for Kelvran specifically:** this is directly on-point, corrective evidence for Finding 3's own framing — Envoy's "let vendors build it" strategy really did eventually produce a marketplace, confirming that strategy is viable at Envoy's scale (a large, CNCF-adjacent, multi-vendor ecosystem). But the marketplace that resulted, six months old at this research date and run by a single vendor company with real engineering resources, still has *no* certification tier (unlike Kong), no in-monorepo maintainer-review integration with a broader project's own core-contribution pipeline (unlike Higress — it's a standalone repo, not folded into `envoyproxy/gateway` itself), and no monetization mechanism of any kind. If even a well-resourced vendor company building a marketplace from scratch for an ecosystem as large as Envoy's chose the lightest-weight possible governance (plain PR review, no formal vetting), that is a real, checkable data point against reaching for anything heavier than that as a starting point — and Kelvran, with zero vendor resources and zero existing plugin population, has even less reason to start heavier than Tetrate did.

**Consistent with settled decisions?** New finding — refines, rather than contradicts, this document's own Finding 3 and Finding 5's sequencing observation: Tetrate built "Built on Envoy" once Envoy's own ecosystem had grown large enough (years of Envoy/Envoy Gateway adoption) to make seeding a marketplace worthwhile for Tetrate's own commercial positioning — it is not evidence that marketplace machinery should be built speculatively, ahead of any comparable ecosystem size, at a project the size of Kelvran.

**2026 best practice grounding:**
- The launch date, Apache-2.0 licensing, and "free to use"/"community-sustained ecosystem" framing are confirmed across Tetrate's own press release and The New Stack's independent coverage [PRNewswire/`tetrate.io/press` and `thenewstack.io/tetrate-built-on-envoy` — confirmed 2-0, one vendor-authored and one independent trade-press source, both dated 2026-03-11 and stating consistent facts].
- The seeded initial extension catalog (Cedar Auth, SAML Auth, AWS Bedrock guardrails, Azure Content Safety, Databricks file-server) is corroborated by a third, independent source [`tfir.io/built-on-envoy-tetrate-extension-marketplace` — a second independent trade-press outlet, confirmed 2-0 against The New Stack's coverage].
- The absence of a formal vetting/security-scanning process, and the ordinary-PR-review governance model, are read directly from Tetrate's own repository artifacts — `CONTRIBUTING.md` and the `extensions/` directory's own guidelines document [`github.com/tetratelabs/built-on-envoy` — primary source, the project's own governance documents, not inferred].
- The CNCF-non-governance point (repo under `tetratelabs`, not `envoyproxy`/`cncf`; a supportive-but-non-governing CTO quote) is a direct reading of the repository's own organizational home plus the press release's own attribution — not an inference from silence alone, since the press release explicitly quotes CNCF's CTO in a general-supportive capacity without describing any CNCF role in the marketplace's operation.
- This finding should not be confused with Tetrate's separate CVE-scanning tool for Istio/Envoy *core* (Tetrate Vulnerability Scanner, per a Tetrate blog post) — that tool was not found described anywhere as applying to Built on Envoy marketplace *extension* submissions specifically, and this distinction is deliberately preserved rather than blurred.

**Concrete next step:** None for Kelvran today — but this is the single most relevant precedent in this document if Kelvran's own ecosystem ever grows large enough for the question to become live: even then, a Tetrate-style "seed it, invite contribution, review by plain PR" model — not a Kong-style certification ladder — is the closest-fitting real analog to what Kelvran's own scale (small team, no dedicated partner org) could plausibly run.

**Effort:** N/A (informational).

### 5. None of the systems examined has a demonstrated third-party-plugin-marketplace *monetization* mechanism — the research brief's monetization question has a thin answer everywhere, not just at Kelvran (Informational — directly answers the research brief's own explicit ask)

**What:** Searched specifically for revenue-share, listing-fee, or plugin-transaction mechanisms across Kong, Higress, Envoy Gateway, and Tetrate's Built on Envoy. None was found anywhere. Kong's own pricing page lists "AI Gateway Paid Plugins" (AI AWS Guardrails, AI Semantic Cache, AI Proxy Advanced, and others) as *Kong's own first-party plugins*, gated behind Konnect's Plus/Enterprise subscription tiers (e.g. "$100/month per model" on the lower self-serve tier, "no costs for 30 days" trial, "custom, volume discounts available" on Enterprise) — this is Kong monetizing its own product's feature set via subscription, not taking a cut of third-party plugin sales. Kong separately sells a distinct add-on product, "Konnect Metering & Billing" ("requires a separate purchase... contact Sales"), which lets *Kong's customers* meter and bill *their own* API/AI usage to *their own* end customers — a real monetization capability, but aimed at Kong's customers monetizing their APIs, not at Kong monetizing its plugin marketplace. The Premium Technology Partner Program's stated partner benefit is "new revenue opportunities" with no defined mechanism specified anywhere found (read most plausibly as co-sell/lead-generation access, not a listing fee or revenue share). Higress, Envoy Gateway, and Tetrate's Built on Envoy are all free/open-source (Apache 2.0 in Tetrate's case) with zero monetization mechanism for their plugin/extension ecosystems.

**Why it matters for Kelvran specifically:** the research brief explicitly asked how third-party plugins get monetized in these systems. The honest, checkable answer is: they mostly don't, at the marketplace layer itself, anywhere this research looked. The one system with a real commercial marketplace (Kong) monetizes by paywalling its *own* plugins inside a platform subscription, not by taking a cut of what third parties build — meaning even the strongest available precedent doesn't validate "build a marketplace, take a revenue share" as a proven pattern to imitate. This removes one entire category of reason someone might otherwise reach for to justify building a marketplace speculatively ("it's how gateways make money off their ecosystem") — that reason does not hold up against the actual, checked 2026 evidence.

**Consistent with settled decisions?** Complements, without contradicting, `DECISIONS.md`'s existing "billing/monetization integration" line item — that line refers to Kelvran's *own* customer-facing billing/monetization (per `docs/upgrade-research/billing-monetization-integration-2026-09-15.md`, a different document with a different scope), explicitly deferred in the third post-research value-add round (`[2026-09-16]` entry). This finding is a distinct, narrower claim about third-party *plugin-marketplace* monetization specifically, and should not be conflated with that broader, already-tracked item.

**2026 best practice grounding:**
- The "AI Gateway Paid Plugins" list and its per-tier pricing (including the "$100/month per model" self-serve figure) are read directly from Kong's own live pricing page [`konghq.com/pricing` — primary source, live as of this research date].
- The Metering & Billing add-on's separate-purchase requirement and its actual scope (metering/billing for Kong's *customers'* own downstream usage, not plugin-marketplace transactions) are read directly from Kong's own product page and plugin doc, cross-checked against each other [`developer.konghq.com/metering-and-billing/` and `developer.konghq.com/plugins/metering-and-billing/` — confirmed 2-0, both Kong-authored].
- The vague, mechanism-undefined "new revenue opportunities" partner-benefit phrasing is Kong's own words, from the same blog post cited in Finding 1 [`konghq.com/blog/news/premium-technology-partner` — primary source].
- The absence of any monetization mechanism at Higress, Envoy Gateway, and Tetrate's Built on Envoy is an absence-of-evidence result from this pass's (and the parallel pass's) own searching across each project's documentation, disclosed as such rather than asserted as definitively proven nonexistent.

**Concrete next step:** None — this is evidence to weigh, and it directly undercuts one common speculative justification ("marketplaces are how ecosystems monetize") for building a plugin marketplace ahead of real demand.

### 6. Every real ecosystem examined built (or explicitly declined to build) marketplace/certification machinery only in relation to real, already-existing plugin volume or vendor demand — never speculatively ahead of it (Informational — the sequencing lesson underlying the verdict below)

**What:** Reading the findings above together surfaces a consistent sequencing pattern. Kong's Plugin Hub existed as a listing surface for its own bundled plugins long before the Premium Technology Partner Program was introduced in 2024 specifically to formalize and deepen vetting for an *already-growing* population of third-party integrations (the program's own framing explicitly offers "a streamlined pathway for community plugins to transition to the premium tier" — i.e., it retrofits deeper certification onto plugins that already exist and are already listed). Higress's marketplace UI sits on top of a monorepo that already contains dozens of officially-authored plugins, with the same review bar as any other code — the "marketplace" is a discoverability layer added over an existing, actively-growing catalog. Tetrate did not build "Built on Envoy" until Envoy/Envoy Gateway had years of real, large-scale, multi-vendor adoption behind it — and even then chose the lightest-weight governance available (plain PR review), seeding an initial catalog itself rather than waiting for volunteers, precisely because a marketplace with zero listings at launch would have nothing to demonstrate value with. Envoy Gateway itself, facing the identical question at the project level, answered explicitly and in writing: no, that is the vendor layer's job.

**Why it matters for Kelvran specifically:** none of the real precedents this research examined built marketplace/certification machinery *ahead of* demand. Kong deepened its vetting only once a partner-plugin population already existed to vet more rigorously; Higress's catalog grew inside its normal contribution pipeline before anyone built a dedicated "Plugin Market" UI over it; Tetrate seeded its own initial catalog rather than launching an empty shell and waiting, but only did so after years of ecosystem growth made that seeding worthwhile; Envoy Gateway looked at the same choice Kelvran now faces and declined outright, by design. There is no real-world model in this research where a marketplace/ecosystem-governance layer was stood up speculatively, in true advance of an actual population of third-party plugin authors, vendors, or (at minimum, per Tetrate) a large enough existing user base to make self-seeding worthwhile.

**Consistent with settled decisions?** Directly reinforces `DECISIONS.md`'s own repeatedly-demonstrated house discipline — visible across the hierarchical-budget deferral, the model-provider-expansion deferral (both cited in `wasm-plugin-extensibility-2026-09-22.md`'s Finding 6), and the CI version-matrix decision explicitly reasoned from Kelvran being "a pre-1.0, zero-external-consumer project" (`STATUS.md`, item 6-13 of the fresh backlog audit) — of not building organizational or governance capability ahead of a real, named trigger. This finding shows the same discipline, applied by every real external system examined, to the same class of decision Kelvran now faces.

**2026 best practice grounding:** Synthesizes Findings 1–5 above; no new primary source beyond those already cited.

**Concrete next step:** None — this is the load-bearing sequencing argument for the verdict below, not a separate action item.

**Effort:** N/A (informational).

### 7. Verdict for Kelvran: a plugin marketplace/ecosystem strategy is not merely unbuilt, it is categorically premature at Kelvran's current, real maturity stage (Informational — the honest answer the research brief asked for)

**What:** Grounding the verdict in Kelvran's own real, current state rather than generic "marketplaces are good" reasoning: `STATUS.md` describes Kelvran as, in its own words, "a pre-1.0, zero-external-consumer project" (used to justify *declining* a CI version-matrix expansion for the identical reason this finding relies on). `PRD.md`'s own Non-Goals section states self-hosting is "the only supported deployment model until there's a real signal otherwise" — Kelvran is not even a managed/hosted product yet, let alone one with a partner ecosystem or a vendor layer analogous to Tetrate's. There is no plugin API surface for a marketplace to sit on top of at all: `guardrail-plugin-extensibility-2026-09-15.md`'s Finding 7 confirmed the *same-repo* contributor path (the `Detector` interface) already works well, but that no real external operator has ever asked to extend Kelvran without forking; `wasm-plugin-extensibility-2026-09-22.md`'s Finding 6 confirmed routing/transform policy has *zero* extension point of any kind today, same-repo or otherwise. Both of those research passes — asking the narrower "should we even build the technical extension mechanism" question — independently reached "not yet" verdicts for lack of a real trigger. A marketplace/ecosystem-governance layer (partner applications, certification tiers, a listing UI, distribution/signing infrastructure, a monetization model) is a materially larger, and strictly *later*, commitment than the technical extension point itself — per every one of Findings 1–6 above, real-world marketplace machinery (even Tetrate's deliberately lightweight version) is only ever built on top of an already-large, already-real user/ecosystem base, none of which exists at Kelvran.

**Why it matters for Kelvran specifically:** this is the direct answer the research task asked for — not "is a marketplace model theoretically relevant to gateways in 2026" (it clearly is, for Kong, Higress, and Tetrate/Envoy), but "is it relevant to Kelvran, right now, given what Kelvran actually is." The honest answer is no, for reasons specific to Kelvran's real state: no commercial vendor/partner organization exists to run a Kong-style certification ladder; no standing external-contributor community exists to run a Higress-style curated-PR marketplace; and Kelvran has no comparable ecosystem size or vendor layer for a Tetrate-style seeded catalog to make sense of yet. Building marketplace governance now would mean building certification/vetting/distribution/monetization machinery years ahead of the plugin population, contributor base, or ecosystem scale any of it would exist to serve.

**Consistent with settled decisions?** Directly extends the "not yet" verdict both prior extensibility research passes already reached, one layer up the stack — those passes examined whether to build the technical mechanism; this pass examines whether to build the governance/business-model layer on top of one, and reaches the same verdict for a compounding reason: the layer below (a stable, external-facing plugin ABI) doesn't exist either, so there is nothing yet for a marketplace to organize.

**2026 best practice grounding:** Synthesizes Findings 1–6 above against Kelvran's own documented state (`STATUS.md`, `PRD.md`, `guardrail-plugin-extensibility-2026-09-15.md`, `wasm-plugin-extensibility-2026-09-22.md`); no new external primary source beyond those already cited in this document.

**Concrete next step:** None today. If this question is ever re-raised, check first whether the trigger both prior extensibility passes named ("has a real external party ever actually asked to extend Kelvran without forking?") has fired — and even then, per those passes' own recommendations, the right next step is a same-repo Go interface or a Starlark-style scripting escape hatch for that *one* operator, not marketplace-grade governance built for a population that still wouldn't exist yet. Marketplace machinery only becomes a reasonable question once there is real plugin *volume* — multiple independent third-party authors, or an ecosystem large enough for a Tetrate-style self-seeded catalog to be worth the effort — which is a categorically higher bar than "one operator wants in."

## Top 3 do next

This is a "should we build this" honest-assessment pass, not a roadmap — there is no build item to prioritize. The three most decision-relevant things to actually *do* with this research:

1. **Do not build any plugin-marketplace governance (partner tiers, a listing UI, certification, distribution signing, or a monetization mechanism) until the trigger named in both prior extensibility research passes fires** — a real external party asking to extend Kelvran without forking. That trigger has not fired as of this research date, per those passes' own open questions.
2. **If/when that trigger does fire, resist the temptation to reach for marketplace machinery at all** — per Finding 6, no real-world system examined here built marketplace governance for a single plugin author; each built it only once real *volume* or ecosystem scale already existed (a growing partner-plugin population at Kong, an actively-growing in-tree catalog at Higress, years of multi-vendor Envoy adoption before Tetrate seeded Built on Envoy). The right first move at that point is still the technical extension point (a same-repo interface, or Starlark-style scripting per the prior research's own recommendation) — not a partner program or a seeded catalog.
3. **If Kelvran's plugin-ecosystem question is ever revisited for a monetization angle specifically, weigh Finding 5 honestly**: none of Kong, Higress, Envoy Gateway, or Tetrate's Built on Envoy has a demonstrated third-party-plugin revenue-share model to imitate.
