# Provider-Side Prompt Caching vs. Kelvran's Own Cache — 2026-09-07 Research

**Date:** 2026-09-07
**Scope:** Whether OpenAI's, Anthropic's, Gemini's, and Bedrock's own provider-side prompt/context-caching mechanisms are complementary to or redundant with Kelvran's own embedded multi-layer cache (`gateway/internal/cache/` — L1 exact match, L2 normalized match, L3-lite lexical near-duplicate). This is the dedicated follow-up research pass named as an open item in `docs/upgrade-research/gateway-2026-09-06.md` Finding 6 ("genuinely unresolved, not a 'no'"), scoped exactly as that finding's own "Concrete next step" specifies.
**Method:** Direct primary-source retrieval (live `WebFetch` against each vendor's own current official documentation — Anthropic's `platform.claude.com`, OpenAI's `developers.openai.com`, Google's `ai.google.dev`, AWS's `docs.aws.amazon.com`) cross-checked against Kelvran's own real source code (`grep`/`Read` against `gateway/internal/adapter/`, `gateway/internal/gateway/dataplane/`, `gateway/internal/cache/`) — not the sibling reports' 3-vote adversarial-multi-agent method, since this question is resolvable by reading each vendor's own documentation of its own product directly, and Kelvran's own behavior is resolvable by reading Kelvran's own code directly, rather than by adjudicating between competing secondary sources. Every claim below is either a direct quote/paraphrase of a fetched vendor doc (cited with the exact URL fetched) or a direct reference to a specific Kelvran source file/line, with vendor-documentation claims and Kelvran-code claims kept visibly separate throughout — never blended into a single unlabeled sentence.

## Executive summary

The original research's a priori inference — that provider-side caching and Kelvran's own cache are complementary rather than redundant, because a Kelvran cache hit skips the upstream call entirely while a Kelvran cache miss still benefits from whatever the resulting real call's provider does with prefix caching — is **confirmed, not merely repeated**, by direct inspection of Kelvran's own code: `normalizeMessages` (used to compute the L2/L3 cache keys) operates on a copy of the message slice and never touches `req.Messages` itself (`gateway/internal/gateway/dataplane/dataplane.go:1352-1373`); `guardrails.Check` is read-only (block-or-pass, never a redact-in-place) on both the pre-call and post-call paths (`dataplane.go:857`, `:899`); and each adapter's `ToProvider` is a byte-faithful translation of the canonical schema, confirmed for the plain-text case by a dedicated existing test (`internal/adapter/openai/openai_test.go`'s `TestToProviderTextOnlyContentIsByteIdenticalToPlainString`). So on a genuine Kelvran cache miss, the exact bytes the client sent are what reaches the provider adapter — nothing about Kelvran's own caching layer mutates, reorders, or normalizes the request that actually goes upstream, which is the precondition every one of the four providers' own caching mechanisms needs to have any chance of matching a prefix.

The more consequential, previously-undiscovered finding is narrower and more actionable than "they're complementary": **Kelvran's canonical `ChatRequest`/`Message`/`ContentPart` schema (`gateway/internal/adapter/types.go`) carries no field for Anthropic's `cache_control`, Bedrock's `cachePoint`/`prompt_cache_breakpoint`, or OpenAI's Bedrock-hosted GPT-5.6 explicit breakpoint mechanism — confirmed by a repo-wide `grep` for `cache_control`, `cachePoint`, and `prompt_cache_key` across `internal/adapter/`, which returns zero matches.** Every one of those three mechanisms is documented by its own vendor as requiring an explicit, opt-in marker on a specific content block (see the per-provider findings below) — a marker Kelvran's client-facing wire format has no way to carry, and that none of Kelvran's four adapters currently emit on their own initiative. This means explicit, opt-in provider-side prompt caching is not merely "not yet exploited" through Kelvran today — it is **structurally unreachable** for Anthropic-direct traffic and for Bedrock's explicit-caching model families, regardless of what the origin client wants, because the opt-in signal has nowhere to travel through Kelvran's own schema. The three providers/paths whose caching is fully automatic with no required field — OpenAI's pre-GPT-5.6 implicit caching, Gemini's implicit caching, and Bedrock's own implicit caching for Anthropic/Nova models — are unaffected by this gap and should continue to fire transparently through Kelvran's miss-path traffic exactly as they would for a direct client, per the byte-fidelity findings above.

A second, smaller, genuinely-open finding: OpenAI's own documentation states cache entries "live on specific machines rather than being globally shared," and that its optional `prompt_cache_key` request field "influences routing" toward the machine most likely to hold a warm cache — a field Kelvran also never sets today (confirmed by the same `grep`). This is not a regression Kelvran introduces (a client calling OpenAI directly without setting this field gets the identical un-hinted routing), but it is a concrete, low-cost, complementary opportunity Kelvran is currently leaving on the table specifically because Kelvran already has a piece of stable identity (tenant/virtual-key ID) that would make a reasonable `prompt_cache_key` value, and no client calling through Kelvran with Kelvran's own canonical schema has any way to supply one itself.

### Kelvran's own code confirms the "miss forwards unchanged bytes" precondition

- `normalizeMessages(messages []adapter.Message) string` (`gateway/internal/gateway/dataplane/dataplane.go:1352`) explicitly `copy(normalized, messages)`s before mutating — the function's *return value* feeds L2/L3 key computation only; the caller's own `req.Messages` (the value later passed into `adapter.Adapter.ToProvider`) is never touched by this function.
- `p.guardrails.Check(ctx, serializeMessages(req.Messages))` (`dataplane.go:857`, pre-call) and `p.guardrails.Check(ctx, serializeResponse(resp))` (`dataplane.go:899`, post-call) both take a read-only serialized copy and return a block/allow `Verdict` — a `grep` for any assignment into `req.Messages[` anywhere in `internal/gateway/dataplane/` returns zero matches, confirming there is no redact-in-place step between arrival and the upstream call.
- `internal/adapter/openai/openai_test.go`'s `TestToProviderTextOnlyContentIsByteIdenticalToPlainString` is an existing, already-passing test that names and proves exactly this property for the plain-text case on the OpenAI adapter.
- Cache lookup structurally happens *before* the router/provider call (`gateway/ARCHITECTURE.md`'s Request Lifecycle section, unchanged by this research): "a hit never touches an upstream" — meaning on an L1/L2/L3 hit there is categorically no upstream request for any provider-side cache to have participated in.

Taken together, these four facts are what actually *prove* (rather than merely restate as a plausible guess) the complementary relationship the prior research round could only infer: Kelvran's cache operates entirely upstream of, and independently of, whatever a provider does with the request Kelvran forwards on a miss.

### Kelvran's canonical schema has no field for any provider's opt-in caching signal

- `gateway/internal/adapter/types.go`'s `Message`, `ContentPart`, and `ChatRequest` types carry `Role`, `Content`, `Parts`, `ToolCalls`, `ToolCallID`, `Model`, `Temperature`, `MaxTokens`, `Tools`, `Stream` — no `CacheControl`, `CacheBreakpoint`, or equivalent field anywhere.
- A repo-wide `grep -rn "cache_control\|cachePoint\|prompt_cache_key\|prompt_cache_breakpoint" gateway/internal/adapter/` returns **zero matches** — none of the four adapters (`anthropic`, `openai`, `gemini`, `bedrock`) reads, writes, or passes through any such field today.
- `gateway/ARCHITECTURE.md`'s own claim that "each adapter offers an `additionalModelRequestFields`-style escape hatch... so a new provider's quirk never requires touching the core pipeline" does not correspond to any real code: a repo-wide `grep -rn "additionalModelRequestFields\|AdditionalModelRequestFields"` across `internal/adapter/` and `internal/gateway/` also returns zero matches. This is the same doc-vs-code staleness class `AGENTS.md`'s own promoted Gotcha already names — flagged here as a direct, confirmed instance, not a hypothetical one; not fixed by this research pass, since this is a research-only item that must not touch gateway source, but worth a follow-up doc correction.
- The providers' own adapters are at different starting distances from being able to carry such a field if one were added: Bedrock's `System` field is already `[]SystemContentBlock` (`internal/adapter/bedrock/bedrock.go:156`, an array of blocks — the shape Anthropic's/Bedrock's own `cache_control`/`cachePoint` needs to attach to), while Anthropic's own adapter's `System` field is a plain `string` and Gemini's `SystemInstruction` is a single `*Content` object, not a per-block array (`internal/adapter/gemini/gemini.go:123`) — so wiring an opt-in breakpoint through the `system` position specifically would be a smaller structural change for Bedrock's adapter than for Anthropic's or Gemini's own, independent of the shared canonical-schema change every adapter would need regardless.

### The three fully-automatic mechanisms are unaffected by the schema gap

OpenAI pre-GPT-5.6 implicit caching, Gemini implicit caching, and Bedrock's own implicit caching for Anthropic/Nova models all require *no* request field at all per their own vendor documentation (see table above) — so the missing `cache_control`/`cachePoint` field in Kelvran's schema is irrelevant to these three paths specifically. Given the confirmed byte-fidelity findings above, Kelvran's miss-path traffic to these should continue to receive whatever automatic caching benefit the provider is willing to give, exactly as if the client called the provider directly — this is a real, positive finding, not just an absence of a negative one.

## Tier 2 — Reasoned inference (labeled as such, not dressed up as confirmed)

- **OpenAI's per-machine cache locality is a live, unexploited opportunity for Kelvran specifically, but its real-world magnitude for Kelvran's traffic is not something this research measured.** OpenAI's own doc states cache entries "live on specific machines rather than being globally shared" and that `prompt_cache_key` "influence[s] routing" without guaranteeing a hit. Kelvran already has stable per-request identity (`vk.ID`, the virtual-key/tenant ID already used as the cache-key tenant namespace) that would be a natural `prompt_cache_key` value — but whether adding it would produce a *measurable* hit-rate improvement for Kelvran's actual traffic shape (call volume per tenant, request cadence, how "hot" a given system prompt stays) is inferred from OpenAI's own general guidance, not verified against Kelvran's own production data, which does not yet exist (mirroring the sibling cache report's own repeated "instrument before building" framing for its unrelated findings).
- **Weighted multi-deployment routing *could* reduce provider-side cache warmth if two "deployments" for the same logical model are actually distinct underlying endpoints/credentials for the same provider (e.g., two Azure OpenAI resources in different regions) rather than the same endpoint declared twice for weight-shaping.** This is a plausible mechanical consequence of `router`'s weighted round-robin spreading otherwise-identical repeated-prefix requests across multiple deployment targets (`gateway/internal/router/wrr.go`), combined with OpenAI's own stated per-machine cache locality — but this research did not determine how Kelvran operators actually configure multi-deployment groups in practice (same-endpoint-duplicated-for-weight vs. genuinely-distinct-endpoints), so the real-world frequency and severity of this effect is inferred, not measured.
- **The a priori "complementary, not redundant" framing from the original Finding 6 is directionally correct but incomplete on its own** — it correctly separates "Kelvran hit skips upstream entirely" from "Kelvran miss still benefits from the provider's own caching," but by itself it did not anticipate the schema-gap finding above (that three of the four providers' *opt-in* mechanisms are currently unreachable through Kelvran regardless of complementarity in principle). This report's Tier 1 findings supersede the prior inference with something more specific and more directly actionable, without contradicting its core direction.

## Tier 3 — Genuinely unresolved (reported honestly, not guessed)

- **No documented, named interaction between an LLM gateway/proxy and provider-side prompt caching was found anywhere in the vendor documentation fetched.** None of the four providers' docs mention gateways, proxies, or third-party routers at all in the context of prompt caching — the "gotchas" this report surfaces (the schema gap, the routing-locality gap) are derived by cross-referencing each vendor's own documented mechanics against Kelvran's own code, not by finding a vendor or third party naming this exact interaction as a known class of problem. If such prior art exists (e.g., a LiteLLM/Portkey/Kong blog post specifically about preserving provider prompt-cache eligibility through a proxy), this research pass did not surface it, and it should not be assumed absent just because it wasn't found in this pass's specific searches.
- **Exact percentage/pricing discount for Gemini's implicit and explicit caching read rate.** The mechanics page states only "we automatically pass on cost savings" with no number; the separate pricing page gives the *context-caching* per-token rate directly (e.g., $0.125/MTok for Gemini 2.5 Pro at ≤200k tokens) but this research did not cross-derive that as a percentage-off-base-input-rate the way Anthropic's and OpenAI's own docs state their multipliers directly — a reader wanting an exact "X% off" figure for Gemini specifically would need a follow-up pass against Gemini's base input pricing row on the same page.
- **Whether Kelvran's own multi-deployment configs in practice declare the same endpoint twice (weight-shaping only) or genuinely distinct endpoints (the Tier 2 inference above's precondition) was not determined** — this would require reading actual `gateway/config.example.yaml`-style deployment configs or real operator configs, which this research pass did not do, since it falls outside "what does each provider's caching do" and into "how do Kelvran operators actually configure deployments," a materially different question this pass did not scope.
- **Real production measurement of any of the above** does not exist yet for the same reason the sibling `cache-2026-09-06.md` report's Finding 5/7 name repeatedly: Kelvran has no production traffic yet. Every claim in this report about *Kelvran's own* behavior is either a direct code-read (Tier 1) or a reasoned inference from that code plus vendor docs (Tier 2) — none of it is a measured hit-rate or cost-savings number, because none exists yet to measure.

## Direct answer to the research question

**Complementary, not redundant — and now confirmed by Kelvran's own code, not just inferred a priori.** A full Kelvran cache hit (L1/L2/L3) means zero bytes reach any provider, so provider-side caching plays no role at all in that case — there's no call for it to apply to. A Kelvran cache miss forwards the client's original request byte-for-byte to the provider adapter (confirmed: `normalizeMessages` operates on a copy, `guardrails.Check` is read-only, `ToProvider` is byte-faithful for the plain-text case per an existing passing test) — so whatever caching a provider is willing to do automatically on that resulting real call proceeds exactly as it would for a direct client. The two systems solve genuinely different problems at genuinely different points in the request path (whether to call upstream at all, vs. how cheaply to process the upstream call once it happens) and there is no evidence, in either the vendor documentation or Kelvran's own code, of the two mechanisms conflicting, competing for the same resource, or requiring a choice between them — using both is not wasted complexity.

**The real, actionable finding is narrower: three of the four providers' *opt-in* caching mechanisms (Anthropic's `cache_control`, Bedrock's explicit `cachePoint`, and GPT-5.6-on-Bedrock's `prompt_cache_breakpoint`) cannot currently be triggered through Kelvran at all**, because Kelvran's canonical wire format has no field to carry the opt-in signal and no adapter emits one on its own initiative — not a conflict, but a missed opportunity distinct from "the two systems are compatible." The three fully-automatic mechanisms (OpenAI pre-GPT-5.6, Gemini implicit, Bedrock implicit) are unaffected by this gap and should already be working transparently on Kelvran's miss-path traffic today, with no code change needed.

## Recommendation for Kelvran

1. **Document this finding now — no code change required for this item.** Add a short paragraph to `gateway/ARCHITECTURE.md`'s Cache Subsystem section (or a new "Interaction with provider-side caching" subsection) stating plainly what this report confirms: Kelvran's own cache and each provider's own caching are complementary by construction (hit = no upstream call at all; miss = unmodified bytes forwarded, so automatic provider caching still applies), and that Kelvran's canonical schema does not yet carry any provider's opt-in cache-control signal. This closes the open question from `docs/upgrade-research/gateway-2026-09-06.md` Finding 6 with a real answer instead of leaving it marked unresolved, and gives the next engineer who wonders "should we build something here" a concrete starting point instead of re-deriving this from scratch.

2. **Correct the stale `additionalModelRequestFields`-escape-hatch claim in `gateway/ARCHITECTURE.md`** while documenting the above — this research pass confirmed it describes no code that exists today (zero matches repo-wide), which is exactly the doc-vs-code staleness class `AGENTS.md`'s own Gotchas section already tracks. (This report does not make the edit itself, per this item's explicit research-only, no-gateway-source-changes scope — flagging it here for whoever picks up the next implementation item.)

3. **A future, separate implementation item — not urgent, and explicitly not this research pass's job to build — would be:** adding an opt-in `CacheControl`/`CacheBreakpoint`-style field to the canonical `Message`/`ContentPart`/`ChatRequest` schema, threading it through to Anthropic's `cache_control`, Bedrock's `cachePoint`/`cache_control`, and GPT-5.6's `prompt_cache_breakpoint` in their respective `ToProvider` implementations, and setting a stable `prompt_cache_key` (e.g., derived from `vk.ID`) on OpenAI/Bedrock-GPT-5.6 requests to improve machine-affinity cache locality. This is real, cross-adapter work (touches the shared canonical schema plus up to three adapters differently, per the differing `System` field shapes this report already found) and should get its own RFC weighing the benefit (provider-side cost/latency savings on cache-miss traffic specifically) against the cost (schema change touching every adapter, plus deciding whether Kelvran's own client-facing API should expose this as a pass-through knob at all, which is a product-scope question this research does not answer) — not a rushed addition here. Flagging it as a legitimate, evidence-backed candidate for a future roadmap item, distinct from "should be built now."

4. **Do not build anything to make Kelvran's own cache and provider-side caching "aware" of each other, or to disable one when the other is active.** No evidence — vendor-documented or Kelvran-code-derived — suggests they interfere with, override, or need coordination against each other. The two systems being unaware of each other is the correct, low-complexity steady state; the only real gap this research found is the unreachable opt-in signal (recommendation 3), not a conflict needing resolution.
