## Executive summary

The `not_yet` verdict holds, and — because only two days separate this pass from the prior `[2026-09-20]` re-verification — the honest framing is that this pass mostly widens the evidence base rather than detects a change that occurred in 48 hours. Three independently-published 2026 routing benchmarks found in this pass (`LLMRouter`/`xRouteBench`, `TwinRouterBench`, and `LLMRouterBench`'s own GitHub "Recent Updates" note) all reconfirm, from different angles, that **model-recall failure remains the field's dominant, unresolved bottleneck** — the same conclusion the 2026-09-20 report already established from the ACL Anthology PDF itself. Separately, three brand-new 2026 papers (UCCI, RACER, Signed Rescue Routing) describe genuinely cheaper escalation-signal mechanisms than a full trained classifier — but every one of them requires either per-token output logprobs (which none of Kelvran's five adapters currently expose — confirmed by `grep`, zero hits) or a labeled calibration set with ground-truth correctness labels (which Kelvran still does not have). This sharpens the trigger for revisiting cascade routing into something more concrete than "wait for a training set": specifically, "wait for logprobs exposure, not just wait for traffic." Two commercial-landscape developments are genuinely new and worth recording even though neither changes the verdict: **Not Diamond has pivoted its flagship product to session-level, cache-aware agentic routing** ("Not Diamond Code," live inside Claude Code and Codex since August 2026) — a second real production precedent for the same "session-start, not per-request" pattern the 2026-09-20 report named for Databricks' Unity Gateway, strengthening that framing rather than contradicting it. And **Martian has abandoned model routing as a product entirely**, pivoting to interpretability research; its team's new production offering (`Ship`, via an incubated lab called Thesean AI) is an inference-time compute-allocation endpoint with a quality SLA — architecturally a different category from a multi-model router, and not something Kelvran could adopt patterns from for this specific problem. This closes a real, previously-open question from the 2026-09-11 research pass ("what does Martian specifically do") with a genuinely surprising answer: not routing, not anymore.

## Findings, ranked

### 1. Model-recall failure is independently reconfirmed as the field's dominant bottleneck by three additional, genuinely new 2026 benchmarks — the `not_yet` verdict's core justification gets stronger, not weaker, with fresh evidence (Small — no action, documentation only)

**What:** The 2026-09-20 report re-verified LLMRouterBench's own finding (Recall@3 of 46.1%/50.6% for two tested baselines) directly against the ACL Anthology PDF. This pass found three additional, independent sources published in 2026 that were not read by any prior Kelvran research pass, and all three reach the same structural conclusion from different benchmark constructions:
- `LLMRouterBench`'s own GitHub repository (`ynulihao/LLMRouterBench`) lists "Recent Updates" — three newly-integrated benchmarks (FrontierScience, SGIBench, SFE) and extended multimodal-routing support added after the paper's original ACL submission — and its README states the same conclusion in its own words: "a significant Gap@O remains due to **model-recall failures** — when only a few models answer correctly, routers often fail to select them," explicitly noting that even Avengers (a leading router that requires no neural-network training at all) cannot close this gap.
- `LLMRouter`/`xRouteBench` (arXiv:2608.06867, a newer, broader benchmark spanning generic-LLM, memory-augmented, vision, time-series, and personalized-routing tracks across 18 candidate models) independently finds that "learned routers achieve a 14.6% relative improvement over the strongest fixed-model baseline" — a real, positive signal for the *field*, but one earned only by training on router-specific supervision the paper's own pipeline constructs by exhaustively running every candidate model against every benchmark query first, exactly the kind of labeled-outcome dataset Kelvran does not have.
- `TwinRouterBench` (arXiv:2605.18859), a step-level agentic-routing benchmark built specifically because prior benchmarks (RouterBench, LLMRouterBench, RouterArena) only evaluate one-shot prompts, not intermediate calls inside a multi-turn agent trajectory — closer to Kelvran's own real workload shape than any benchmark named in prior Kelvran research. It reports "a logistic router trained on the static labels achieves a 53% cost reduction at matched resolve rate on the dynamic track" — a genuinely strong number, but again explicitly contingent on training a router from execution-verified labels a live SWE-bench harness produced, which required running the full task to completion once per step to generate ground truth.

**Why it matters for Kelvran specifically:** all three sources converge on the same shape of answer LLMRouterBench itself gave: routing intelligence *can* work, but every mechanism that works requires a labeled outcome dataset Kelvran has never had the ability to generate (it would need to run every candidate model against every real request and score the results, which is neither Kelvran's current architecture nor a low-cost thing to add). This is not new information changing the verdict — it is the same conclusion, now independently reconfirmed by three more benchmarks than were checked two days ago, which is itself a real and honest finding: the prior verdict was not a fluke of one paper's framing.

**Consistent with settled decisions?** Directly reconfirms, rather than revisits, `DECISIONS.md`'s `[2026-09-14]`/`[2026-09-20]` `not_yet` verdicts and `docs/rfcs/2026-09-20-gateway-cost-aware-model-cascading.md`'s Alternatives Considered section (which already named "a trained classifier or embedding router" as rejected per the recall-failure finding).

**2026 best practice grounding:**
- `ynulihao/LLMRouterBench`'s own GitHub README (fetched directly) — self-reported by the benchmark's own authors, not a third-party summary — confirmed model-recall failure remains the stated conclusion after the benchmark's own post-publication extensions [github.com/ynulihao/LLMRouterBench — single primary source, the benchmark authors' own repository, not independently cross-checked against a second source, but this is the authoritative first-party source for its own conclusion].
- `LLMRouter`/`xRouteBench` (arXiv:2608.06867) — read directly from the paper's own abstract and body text [arxiv.org — single primary source, not independently cross-checked against a second source describing the same paper].
- `TwinRouterBench` (arXiv:2605.18859) — read directly from the paper's own abstract and body text, including its own explicit positioning against LLMRouterBench/RouterBench/RouterArena as the reason for its existence [arxiv.org — single primary source, not independently cross-checked].
- None of these three sources' headline savings/improvement numbers (14.6%, 53%) were independently cross-checked against a second, unaffiliated source — treat as the paper authors' own reported figures, consistent with this repo's own established skepticism toward unverified headline routing-savings numbers (`docs/upgrade-research/gateway-model-routing-intelligence-2026-09-11.md`'s Caveats section, which explicitly refused to cite RouteLLM/FrugalGPT/AutoMix headline numbers that failed adversarial verification).

**Concrete next step:** none — this finding closes a research question (does newer benchmark evidence change the verdict) with "no," which is itself the deliverable. If Kelvran's `evals` subsystem ever grows a live feedback loop into gateway routing (per the 2026-09-20 report's Finding 6/Open Questions), `TwinRouterBench`'s step-level, execution-verified-label methodology is the closest published precedent to what Kelvran's own agentic workloads would need — worth returning to at that point, not now.

### 2. Three new 2026 papers (UCCI, RACER, Signed Rescue Routing) describe cheaper-than-classifier escalation signals — but every one requires infrastructure or data Kelvran does not have, sharpening the trigger without meeting it (Medium — for the infrastructure precondition; not_yet for any routing feature built on top of it)

**What:** This pass searched specifically for the brief's core question — "a new, cheaper confidence/uncertainty signal" — and found three genuinely new 2026 papers not named in any prior Kelvran research pass:
- **UCCI** (arXiv:2605.18796, "Calibrated Uncertainty for Cost-Optimal LLM Cascade Routing") maps **token-level margin uncertainty** (the gap between the top-1 and top-2 token probabilities during generation) to a calibrated per-query error probability via isotonic regression, then picks an escalation threshold by cost minimization. On a real production NER workload (75,000 queries, 4B/12B instruction-tuned models on H100 GPUs — a real, disclosed deployment, not a public academic benchmark), it reports a 31% cost reduction (95% CI: [27%, 35%]) at matched quality, beating entropy thresholding, split-conformal routing, and a FrugalGPT-style learned threshold at the same operating point.
- **RACER** (arXiv:2603.06616, "Risk-Aware Calibrated Efficient Routing") is a **post-hoc, model-agnostic** calibration layer that sits on top of *any* existing base router (it does not require retraining the router itself) and converts single-model selection into a calibrated candidate *set* with a distribution-free, statistically-proven risk bound on "the correct model was excluded from the set." This is architecturally interesting — it doesn't require building a new router from scratch — but it still requires a calibration dataset of `(query, ground-truth-correct-model-set)` pairs to calibrate its threshold, which is exactly the labeled-outcome data Kelvran does not have.
- **Signed Rescue Routing / SRR** (arXiv:2609.07786, submitted 2026-09-07 — the most recent paper found in this pass) makes a sharper conceptual point than either: most cascade routers escalate based on "is the small model uncertain," but escalation is only *useful* when the large model would actually *fix* a wrong small-model answer, and is actively *harmful* when it would *replace a correct small-model answer with a wrong one*. SRR trains a lightweight two-head router to predict these two probabilities separately and ranks by their signed difference, which the paper proves is the Bayes-optimal routing score under a fixed escalation budget. This is conceptually the most sophisticated framing of "when should Kelvran's `escalationSignal` actually fire" found anywhere in this research lineage — but it still needs training data (paired small-model/large-model correctness labels), and the paper's own evaluation (Qwen3-4B/8B on MMLU/HellaSwag/ARC-Challenge, with results explicitly marked "TBD" in the abstract as of this fetch) is not yet a completed, citable result.

**Why it matters for Kelvran specifically:** this directly answers the brief's question about whether a new, cheaper signal exists — and the honest answer is "yes, but 'cheaper' means cheaper than training a full classifier, not cheaper than what Kelvran already has." UCCI is the most concrete: its precondition is **per-token output logprobs**, a real, checkable, and — importantly — **infrastructure** gap rather than a **data** gap. Confirmed directly against Kelvran's own code: `grep -rn "logprobs\|LogProbs" gateway/internal/adapter/types.go` returns zero hits, and no adapter file in `gateway/internal/adapter/` references logprobs at all. This means UCCI's mechanism is not adoptable today for a reason distinct from the "no labeled training set" reason that blocks RouteLLM/Not-Diamond/Martian-style routers — it's a wiring gap, not a data-science gap, and (unlike a labeled dataset, which requires real production volume to accumulate) it is something Kelvran could close unilaterally, at any time, for the one adapter that already supports it natively (OpenAI's Chat Completions API has shipped `logprobs`/`top_logprobs` since 2023; Anthropic, Gemini, and Bedrock Converse have no directly equivalent parameter as of this research, mirroring the same uneven-adapter-coverage pattern the 2026-09-20 report already disclosed for `Message.Refusal`).

**Consistent with settled decisions?** Directly engages with, and does not overturn, `docs/rfcs/2026-09-20-gateway-cost-aware-model-cascading.md`'s "Trigger to revisit" (re-verify Finding 2/model-recall-failure against any *newer* routing benchmark before starting implementation — done in Finding 1 above, verdict unchanged) and its Detailed Design's own escalation-signal function, which explicitly said the design deliberately avoids "a trained classifier... no network call, no LLM-as-judge, no trained model." UCCI/RACER/SRR do not contradict that constraint — if anything, UCCI's isotonic-regression calibration layer is architecturally closer to "cheap" than the RFC's own hand-written `escalationSignal` function assumed was the *only* cheap option (`Message.Refusal`/`Choice.FinishReason`-based heuristics), but it needs a signal (logprobs) those two fields cannot substitute for.

**2026 best practice grounding:**
- UCCI (arXiv:2605.18796) — abstract and body read directly [arxiv.org — single primary source, not independently cross-checked against a second source; its own reported 31% figure with a stated 95% CI is a real, disclosed production result, but from the paper's own single deployment, not independently audited].
- RACER (arXiv:2603.06616) — abstract and body read directly [arxiv.org — single primary source, not independently cross-checked].
- Signed Rescue Routing (arXiv:2609.07786) — abstract read directly, noting the paper's own results table contains literal "TBD" placeholders as of this fetch, meaning its headline comparison numbers are not yet available to cite at all [arxiv.org — single primary source, explicitly incomplete as published].
- Kelvran's own logprobs-exposure status — confirmed by direct `grep` against `gateway/internal/adapter/types.go` and all files in `gateway/internal/adapter/`, zero matches [live repo — first-party, definitive for this specific claim].

**Concrete next step:** none as a routing feature (this remains `not_yet`, per the field-wide recall-failure bottleneck Finding 1 reconfirms). If Kelvran ever wants to *prepare* for revisiting cascade routing before a labeled dataset exists, the narrowly-scoped, low-risk preparatory step this finding surfaces — not proposed for immediate implementation, flagged for a future RFC's own consideration — would be threading OpenAI's already-available `logprobs` field through to `adapter.ChatResponse` for the one adapter that supports it, mirroring `Message.Refusal`'s own precedent of accepting uneven coverage rather than blocking on full adapter parity.

**Effort:** Medium if the logprobs-exposure step above is ever taken (a new field on `adapter.ChatResponse`, populated by 1 of 5 adapters, disclosed uneven exactly like `Message.Refusal`); not_yet / N/A for any cascade or calibration logic built on top of it, since Finding 1's recall-failure bottleneck and the missing labeled calibration set are both still unresolved.

### 3. Not Diamond has pivoted its flagship product to session-level, cache-aware agentic routing — a second real, live 2026 production precedent for the "session-start, not per-request" pattern, strengthening (not contradicting) the 2026-09-20 report's Finding 6 (Unscoped — informational, no Kelvran action implied)

**What:** The 2026-09-20 report's Finding 5 described Not Diamond's routing mechanism strictly as a pre-trained, per-request meta-model classifier (`docs.notdiamond.ai`'s "pre-trained"/"custom" router types). This pass found that Not Diamond has since (as of a 2026-08-04 blog post) launched a materially different product, "Not Diamond Code," aimed specifically at long-horizon coding agents, and followed it with a 2026-09-01 blog post reporting concrete benchmark results. The new mechanism is explicitly **not** a per-request classifier: it "predicts future rewards and costs for a given model and reasoning effort **at each step of an agent sequence**," is "cache-aware" (it accounts for the cost of breaking a warm KV-cache mid-session and will deliberately stay on a pricier model to preserve cache locality even when a cheaper model could technically handle a given turn), and "continuously updates in real-time based on developer feedback signals." It is live today inside Claude Code (the same harness this research is being written from) and is reported, in Not Diamond's own 2026-09-01 post, as "Pareto dominant" against Opus-class quality on three coding-agent benchmarks (SWE-Interact, SWE-Together, Dialogue SWE-Bench-Pro) at a 20-80% cost reduction, with an internal ablation showing that adding GLM 5.2 and DeepSeek V4 Flash to the candidate pool improved accuracy by 3.6% and increased savings from 39% to 66% relative to Opus xhigh on a separate benchmark (Poly-SWE-Bench).

**Why it matters for Kelvran specifically:** the 2026-09-20 report's Finding 6 named Databricks' Unity Gateway "Smart Routing" as "a new, real, live 2026 production deployment beyond Ramp," explicitly session-start rather than per-request, "because 'consecutive turns' need to hit the same model to preserve prompt-cache hit rate." Not Diamond Code is a second, independently-arrived-at production system converging on the identical design constraint (cache-aware, session/trajectory-level, not per-request) — this is exactly the kind of corroborating, independent evidence that turns a single data point into a real pattern. It directly reinforces, rather than reopens, `docs/rfcs/2026-09-20-gateway-cost-aware-model-cascading.md`'s own explicit scoping decision to exclude "session-start task classification... a different problem" from its per-request cascade design. If Kelvran ever does pursue routing intelligence, this finding is evidence that the field's own production consensus by September 2026 has moved decisively toward session/trajectory-level, cache-aware routing — not per-request classifiers (RouteLLM's original framing) and not per-request cascades (AutoMix's framing, and this repo's own deferred RFC's framing) — which should inform *which* of the three architectural families gets picked first, if and when the trigger for building anything in this space ever fires.

**Consistent with settled decisions?** Additive to, not a revisit of, the 2026-09-20 report's Finding 6 and the cascade RFC's own "Explicitly out of scope" list, which already named session-start task classification as a different problem it deliberately excluded. No decision needs updating — this strengthens the existing framing with a second real-world example.

**2026 best practice grounding:**
- Not Diamond's own 2026-08-04 blog post ("Not Diamond Code: intelligent model routing for coding agents") and 2026-09-01 blog post ("Interactive benchmarks: evaluating model routing for AI agents") — both read directly from the vendor's own site [notdiamond.ai — first-party vendor source, not independently cross-checked against a third party; the specific percentage figures (20%+, 20-80%, 3.6%, 39%→66%) are the vendor's own self-reported numbers from its own early-access program and internal evaluations, not independently audited, consistent with this repo's own established skepticism toward vendor-reported routing savings — see `llm-cost-optimization-finops-2026-09-14.md` Finding 2 and the 2026-09-20 report's own Caveats section, both of which apply the identical standard to Databricks' numbers].
- Not Diamond's own current pricing/docs pages (`notdiamond.ai/pricing`, `docs.notdiamond.ai`) confirm the older, simpler pre-trained/custom chat router (per-request, `tradeoff="cost"/"latency"/None`) still exists as a separate, live product alongside the new Code router — Not Diamond has not deprecated its original mechanism, it has added a second one for a different workload shape [notdiamond.ai — first-party, directly confirms both products coexist].

**Concrete next step:** none for Kelvran directly — this is a landscape-tracking finding, not an actionable build. Worth citing the next time Kelvran's own cascade/routing RFC is revisited, as independent corroboration for prioritizing a session/trajectory-level design over a per-request one if that RFC's trigger ever fires.

**Effort:** Unscoped — informational only.

### 4. Martian has abandoned model routing as a product entirely; its successor offering ("Ship," via Thesean AI) is an inference-time compute-allocation black box, not a multi-model router — resolves a real, previously-open question from the 2026-09-11 research pass (N/A — informational, closes an open question)

**What:** `docs/upgrade-research/gateway-model-routing-intelligence-2026-09-11.md`'s own Caveats and Open Questions explicitly flagged "no source in this pass discussed Martian or Not Diamond directly (both named in the original research prompt)" and asked "are Martian and Not Diamond... doing something meaningfully different from OpenRouter's discrete-tier approach — worth a dedicated follow-up research pass." ## Caveats

- **The two-day gap between this pass and the prior `[2026-09-20]` re-verification is the single most important caveat for this entire document.** The brief's own framing — "find out whether anything has genuinely changed" — is honestly answered "no, not materially, because 48 hours is not enough time for the underlying research landscape to shift" for most of what this pass checked. Where this pass does add value, it is by reading sources the 2026-09-20 pass did not have time to find (three new benchmark papers, three new escalation-signal papers, Not Diamond's and Martian's most recent product moves), not by detecting change that occurred *during* those 48 hours.
- **UCCI, RACER, and Signed Rescue Routing are all single-source findings in this pass** — each read from its own arXiv abstract/body, none independently cross-checked against a second description of the same paper (e.g., a citing paper, a blog summary, or an independent reproduction). Treat the specific mechanism descriptions as accurately reported from the primary source, but treat the *quality* of that source's own claims (especially UCCI's 31% figure and its 95% CI) with the same single-deployment caution this repo already applies to every other vendor- or paper-self-reported savings number.
- **Signed Rescue Routing's own results section contains literal "TBD" placeholders** as of the version fetched in this pass (submitted 2026-09-07) — its headline comparison numbers against entropy routing and a learned small-model error predictor do not yet exist to cite, only the paper's conceptual framing (signed conditional gain as the Bayes-optimal routing score) does.
- **Not Diamond's and Martian's own reported figures (20-80% cost reduction, 3.6%/39%→66%, 50%/50.2%) are vendor- and single-customer-self-reported**, not independently audited by any source in this pass — consistent with, and explicitly cross-referencing, this repo's own established standard for treating vendor routing-savings claims (`llm-cost-optimization-finops-2026-09-14.md` Finding 2; `cost-aware-cascading-tier1-2026-09-20.md`'s Caveats on Databricks' numbers).
- **This pass did not re-run the ACL Anthology PDF re-extraction** the 2026-09-20 report already performed for LLMRouterBench's core `-24.7%`/Recall@3 figures — it treats that primary-source verification as already-settled and builds on top of it rather than duplicating it, per the brief's own instruction to find a genuinely fresh angle rather than blindly re-researching settled ground.
- **The `grep` confirming zero logprobs references in Kelvran's adapter code checked only `gateway/internal/adapter/`** (the canonical adapter schema and implementation directory) — it did not exhaustively search the entire `gateway/` module for every possible reference to per-token probabilities under a different name, though this is the correct and complete location for this specific claim per `AGENTS.md`'s own description of where adapter-level response fields live.
- **This pass found no update to OpenRouter's own current market-spend-based Auto Router** (the mechanism the 2026-09-20 report already described as superseding the Not-Diamond-powered version LLMRouterBench measured) — no evidence of a further OpenRouter routing-mechanism change was found or specifically searched for as a dedicated question in this pass beyond what surfaced incidentally in the Not Diamond and RouteLLM searches.

## Open questions

- Would exposing per-token logprobs (where a provider supports it — OpenAI's Chat Completions API does; Anthropic, Gemini, and Bedrock Converse have no direct equivalent as of this research) be worth an `adapter.ChatResponse` schema change on its own, given only 1 of Kelvran's 5 adapters could populate it — mirroring `Message.Refusal`'s own already-disclosed 2-of-5-adapter coverage gap, and would that unevenness make a UCCI-style calibrated signal too noisy to trust across Kelvran's actual multi-provider deployments?
- Now that two independent production systems (Databricks Unity Gateway, Not Diamond Code) have converged on session-level, cache-aware routing rather than per-request classification or per-request cascading, should any future Kelvran routing RFC start from that architectural family first, rather than the per-request cascade design `docs/rfcs/2026-09-20-gateway-cost-aware-model-cascading.md` already sketched — and would that require the same live eval-feedback loop from `evals` back into `gateway` that report's Finding 6 already named as Kelvran's real missing piece (not the evaluation layer itself, which exists offline, but the live wiring)?
- Is Martian's "Ship" (inference-time compute allocation with a quality SLA) worth its own dedicated research pass as a *distinct* category from model routing — e.g., as a comparison point for Kelvran's own future guardrails/cost work — or is it definitionally out of reach for Kelvran specifically, since it requires trusting a third-party vendor to execute the actual model call rather than Kelvran's own gateway proxying directly to the provider?
- Do UCCI's, RACER's, and Signed Rescue Routing's calibration-based approaches generalize from the classification-style or short-answer workloads each was evaluated on (real-world NER; MMLU/HellaSwag/ARC-Challenge) to Kelvran's actual, open-ended chat/agentic generation workload, where "correctness" is not a clean binary label the way it is in a named-entity-recognition or multiple-choice task — none of the three papers found in this pass tested that harder, more Kelvran-relevant setting, and this remains genuinely unanswered rather than assumed either way.
