## Findings

1. **Zero dependency-update automation exists today.** Directly verified: `.github/` contains only `ci.yml` and `evals-judge-nightly.yml` — no `dependabot.yml`, no `renovate.json`, no CODEOWNERS, no PR template, no issue templates, no stale-bot workflow. **`build_now`.**

2. **`main` has zero branch protection, and the repo has zero PRs in its entire history.** Directly verified live: `gh api repos/kelvran/gateway/branches/main/protection` returns 404 ("Branch not protected"); `gh pr list --state all` returns zero results; every commit in `git log` is a direct push. A real, checkable gap for a now-public repo, independent of whether external contributors exist yet.

3. **No test-coverage instrumentation exists anywhere in CI.** Directly verified via grep of both workflow files — no `-cover`/`-coverprofile`/`pytest --cov` flag anywhere; the only "cover" matches are incidental English words in unrelated comments.

4. **The dual-stream release structure is real at the filesystem level.** `gateway/changelog/` and `evals/changelog/` both exist as separate directories with dated version files (`gateway/changelog/` has 0.1.0.md through 0.10.1.md plus `unreleased.md`), confirming the manual per-deployable flow described in `RELEASE.md` is real and currently unautomated — no release workflow file exists in `.github/workflows/`.

5. **Dependabot is the right first move over Renovate, but only for now.** Dependabot is a zero-install, config-file-only native GitHub feature; Renovate needs a GitHub App install or self-hosting, in exchange for materially better default grouping (`config:recommended` bundles pre-built grouping Dependabot has no equivalent of) and finer-grained per-dependency scheduling. For a solo maintainer with no appetite yet for an extra GitHub App, Dependabot's zero-install footprint is the more proportionate starting point. **`build_now`** (Dependabot) / **`not_yet`** (Renovate — trigger: "dependency-PR volume becomes unmanageable under Dependabot's defaults").

6. **Comparable-scale AI-infra repos show no consensus on dependency automation, but `envoyproxy/ai-gateway` is the closest usable template.** LiteLLM's `dependabot.yaml` configures only the `github-actions` ecosystem despite being a Python+TypeScript project. `Portkey-AI/gateway` (~13k stars) has no Dependabot/Renovate config at all (verified via API listing, direct 404 fetches, and a code search returning `total_count:0`). `envoyproxy/ai-gateway` — the closest structural analog (a Go-based "gateway" project) — configures exactly 3 ecosystems (`github-actions`, `npm` scoped to `site/`, `gomod`), each grouped via a wildcard pattern into a single PR, weekly, with a **14-day `cooldown.default-days`** delay before a new dependency version is even proposed. For Kelvran this template translates directly to `gomod` (root, for `gateway/`), `pip` (for `evals/`), and `github-actions` — each grouped and cooldown-delayed so a newly-released dependency doesn't trigger a same-day, Bedrock-spend-incurring CI run before the community has flagged problems with it. **`build_now`** — config-only, no external trigger required, and a directly comparable, verified precedent exists.

7. **Release Please's manifest-releaser mode could in principle automate the dual-stream release flow, but forcing it onto Kelvran's exact tag format is a real integration project, not a drop-in.** The manifest mechanism itself (a `packages` object where each key is an independently-versioned artifact, with `separate-pull-requests: true`) is real and verified against Release Please's own docs. A more specific claim — that its release-type conventions out-of-the-box match Kelvran's changelog-file-per-version + non-standard `gateway/vX.Y.Z` tag format — was explicitly refuted under adversarial verification. **`not_yet`** — needs a scoped spike to confirm the tag-format customization (or a custom Action) can reproduce `gateway/vX.Y.Z`/`evals/vX.Y.Z` exactly before it's worth adopting over the current, working manual flow.

8. **CODEOWNERS would have zero enforcement effect today.** CODEOWNERS entries are only valid for users who already have write access, and even when valid, they only auto-request reviewers — they never block a merge unless branch protection separately enables "Require review from Code Owners." Since Kelvran has zero branch protection configured (Finding 2) and is a solo-maintainer repo (only one person to name as owner anyway), adding CODEOWNERS today would be pure inert documentation. **`not_yet`** — trigger: a second reviewer/maintainer joins AND branch protection gets turned on.

9. **A stale-issue bot is premature; a PR/issue template is cheap enough to be worth adding as forward-positioning.** LiteLLM runs a real, SHA-pinned, daily-cron `actions/stale` bot (`days-before-stale: 90`, `days-before-close: 7`) plus CODEOWNERS and a top-level PR template — but that presumes an existing flow of external issues/PRs to triage, which Kelvran (zero PRs, likely zero/near-zero open issues) does not have. **`not_yet`** (stale bot — trigger: a real backlog of external issues/PRs accumulates) / a minimal PR template and issue template are cheap enough (a few minutes, no external trigger) to reasonably be **`build_now`** as forward-positioning for the now-public-repo transition, even though the stale-bot itself should wait.

10. **For coverage tooling, a same-runner tool beats a third-party SaaS upload for this project's specific risk profile.** Because Kelvran is public, both Codecov's and Coveralls' unlimited free-for-OSS tiers would technically apply — negating the "private repo cost" concern. The real deciding factor instead: uploading a coverage profile to any third-party SaaS enumerates the full source-tree structure to that third party, an unnecessary exposure for a project with real Bedrock spend and internal structure worth not casually exposing. `go-test-coverage` (Go) and `python-coverage-comment-action` (Python) both compute and gate entirely from a local coverage profile inside the GitHub Actions runner itself, with zero external account/service dependency — the correctly-shaped tools for this project's risk profile over Codecov/Coveralls (better fits only once genuinely open to external contributors wanting a public badge). Note: Coveralls also has a live, open GitHub issue reporting Actions-upload 503 errors under load — a real, unresolved reliability signal worth weighing. **`build_now`** (`go-test-coverage` + `python-coverage-comment-action`) / **`not_yet`** (Codecov/Coveralls — trigger: "genuine desire for a public coverage badge/social proof for external contributors").

11. **`python-coverage-comment-action` does not natively gate a PR on coverage — that requires an explicit extra step.** It only exposes numeric outputs (`new_percent_covered`, `reference_percent_covered`); the consuming workflow must wire those into its own conditional `if:` step (with `exit 1`) to actually enforce a threshold. The `MINIMUM_GREEN`/`MINIMUM_ORANGE` inputs control only visual badge color, not CI pass/fail. Important implementation detail: adopting this action alone adds a coverage comment/badge but **not** a real gate unless Kelvran's own `ci.yml` adds that explicit step.

## Caveats

This synthesis combines externally-sourced, adversarially-verified web claims (Dependabot, Renovate, Release Please, CODEOWNERS, Codecov, Coveralls, `go-test-coverage`, `python-coverage-comment-action`, and the comparable repos) with live, first-hand verification against the real local Kelvran checkout and the real `kelvran/gateway` GitHub repo. Two claims were explicitly refuted after adversarial verification (Release Please's Go/Python release-type fit, and a fuller claim about LiteLLM's dependabot cooldown/auto-merge/labels config) — a reminder that even primary-sourced claims can be wrong on first pass. Branch-protection and PR-count checks are point-in-time (2026-09-14) and go stale the moment any PR or protection rule is added. GitHub Actions cost/CI-minutes impact data for Dependabot vs. Renovate specifically at Kelvran's real usage was not independently verified.

- Would a scoped 1-day spike actually get Release Please's manifest-releaser mode to emit tags in the exact `gateway/vX.Y.Z`/`evals/vX.Y.Z` format, or does its tag-template config fall short and require a custom Action instead?
- What is Kelvran's real current Go and Python test-coverage percentage — without a baseline number, any coverage-gate threshold chosen is a guess, not a data-driven starting point.
- Is there appetite to add a minimal, cooldown-free `dependabot.yml` immediately (even before deciding on Renovate long-term) simply to close the "zero dependency-CVE-bump automation" gap?
