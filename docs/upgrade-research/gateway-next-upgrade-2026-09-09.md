# Gateway Next-Upgrade Scan — Deep Research (2026-09-09)

## Question

Now that `gateway/v0.2.0` is tagged and shipped, what are the highest-value next-upgrade candidates for the gateway specifically — surveying current (2026) production practice across LiteLLM, Kong AI Gateway, Envoy AI Gateway/agent-router, agentgateway, Portkey, Bifrost, TensorZero, Helicone, Barbacane, and Cloudflare AI Gateway — for: (1) an MCP/A2A minimum viable slice, (2) cost/quality/latency-based routing signals beyond static weights, (3) rate-limit dimension gaps (per-provider/per-header/per-path), (4) Admin API hardening (OAuth/OIDC, mTLS, audit logging, RBAC), (5) Guardrails maturity beyond regex/checksum/keyword, (6) secrets/credential rotation, (7) tool-calling security, (8) batch/async API support, and (9) anything else a 2026 production-gateway survey would flag?

## Context (Kelvran's own real, current state)

`gateway/v0.2.0` ships: multi-provider adapters (OpenAI/Anthropic/Gemini/Bedrock/openaicompat, buffered+streaming), weighted round-robin routing with active health-probing (N-of-M consecutive, backoff, post-recovery ramp) and error-classified multi-hop fallback chains, per-deployment concurrency+RPM ceilings, virtual-key budgets and RPM/TPM rate limiting (per-key, per-model, TOCTOU-safe reserve/reconcile, mid-stream reservation top-up), a mid-stream runaway-completion guard, Guardrails v1 (regex/checksum PII+secrets, keyword/hidden-Unicode prompt-injection, category-tiered fail-open/closed, pre+post-call), OTel tracing+metrics, Admin API v1 (bearer-token-gated, loopback-only by default), graceful shutdown, `/healthz`. Already researched and settled (not re-litigated here): real-traffic health-signal wiring (needs a traffic-volume floor Kelvran doesn't have), a distributed `ConcurrencyLimiter` (no multi-instance deployment yet), TPM reservation-transfer across fallback hops (no production precedent found anywhere).

## Summary

Cross-referencing 20 adversarially-verified claims about 2026 production gateway practice against Kelvran's own real code turned up **one real, code-verified security defect** rather than a new-feature gap: the post-call Guardrails scan only inspects `Message.Content` and silently skips `Message.ToolCalls[].ArgumentsJSON`, unlike the pre-call scan, which correctly covers tool_calls via a full JSON marshal. This is a genuine asymmetry in already-shipped security surface, not a speculative feature request — see Finding 1. Beyond that, exactly two small, low-risk "build now" feature candidates survive contact with real code (a per-provider rate-limit dimension; an Admin API viewer/full-admin RBAC split), though neither has a recorded demand signal. Every other researched area is a well-precedented "not yet": cost/latency-based routing is explicitly deferred in Kelvran's own `router.go` pending a traffic-volume floor (and the health-probe loop doesn't even instrument latency yet); per-header/per-path rate limiting has no target given the gateway's single `/v1/chat/completions` route; full OIDC/SAML Admin-API SSO and MCP/A2A tool-call brokering are both industry-wide premium-tier or genuinely unsolved even among the strongest comparators; batch/async API support remains unshipped in the most comparable OSS gateway seven-plus months after its own design proposal; and NER-based guardrails remain correctly deferred, now confirmed by a second independent 2026 vendor. Secrets/credential rotation (research question 6) returned zero surviving claims and remains genuinely unresolved.

## Findings

### Finding 1 — Kelvran's own post-call Guardrails check has a real, checkable asymmetry with its pre-call check: it never scans model-generated tool-call arguments (confidence: high) — **BUILD NOW, security defect**

The pre-call check calls `p.guardrails.Check(ctx, serializeMessages(req.Messages))`, and `serializeMessages` does a full `json.Marshal(messages)` — since `adapter.Message.ToolCalls []ToolCall` is a real JSON field, tool_calls ARE covered on the request side. The post-call check instead calls a deliberately narrower `serializeResponse(resp)`, whose own doc comment says it extracts "every choice's message content, newline-joined, not a full JSON re-encoding" — its body does `contents = append(contents, c.Message.Content)` for each choice, never touching `c.Message.ToolCalls[i].ArgumentsJSON`. A model that emits PII, a leaked secret, or attacker-exfiltrated data inside a tool call's arguments (e.g. a hijacked `send_email(body=...)` call following a successful prompt injection) produces a response whose `Message.Content` is typically empty — Guardrails' post-call detectors never see that payload at all. This lands squarely in OWASP LLM06:2025 Excessive Agency's framing ("damaging actions... due to unexpected, ambiguous, or manipulated LLM outputs"), though Kelvran's actual exposure is narrower than OWASP's general tool-execution guidance implies: Kelvran's adapter layer is a pure wire-format pass-through for tool_calls, it never executes a tool itself — Kelvran's own responsibility is the narrower, concrete one this finding identifies: scan everything it lets through, symmetrically, on both call directions.

**Fix**: extend `serializeResponse` to also append each choice's `ToolCalls[].ArgumentsJSON` — small, low-risk, no new detectors required, mirroring what the pre-call path already does correctly. Arguably urgent since it is a gap in already-committed security surface, not a speculative new capability. Worth checking whether the same asymmetry exists on the audit-only streaming post-call path too — not checked by this pass.

### Finding 2 — A per-provider rate-limit dimension is a real, narrow, low-risk gap; per-header/per-path have no current target (confidence: medium) — **per-provider: build-now candidate, no demand signal; per-header/per-path: not yet**

Kong's `ai-rate-limiting-advanced` policy and agentgateway's CEL-expression-based global rate limiting both let one policy AND-combine provider + consumer + header + path + IP + JWT dimensions — real, current, unanimous-vote-confirmed patterns. Kelvran's `ratelimit.KeyConfig`/`KeyConfig.PerModel` has exactly two dimensions today: per-key and per-key×per-model, both RPM+TPM. There is no per-provider, per-header, or per-path dimension. Per-provider is the one gap with a real use case: today a virtual key can cap one exact model name (`PerModel`) but has no way to cap its own aggregate spend against, e.g., "all Anthropic models" without enumerating every model name — the existing `buildPerModelBuckets`/`buildPerModelTPMBuckets` pattern could be generalized to close this with low risk (same proven bucket-per-dimension-value shape). Per-header and per-path have no current target: `cmd/gateway/main.go` registers exactly one data-plane route (`/v1/chat/completions`, plus `/healthz`), and the only caller-identifying signal is the virtual-key bearer token — there is no second path or header-based caller-identification need to scope a limit against. **Trigger for per-header/per-path**: a second distinct HTTP path with a materially different risk/cost profile (e.g. a future batch or MCP endpoint), or a genuine multi-header caller-identification need — neither exists today.

### Finding 3 — Kelvran's flat bearer-secret Admin API sits below even the free-tier RBAC rung comparable vendors ship; only that free rung fits to build now (confidence: high) — **viewer-role split: build-now candidate, no demand signal; SSO/mTLS: not yet**

LiteLLM ships four RBAC roles free/open-source (`proxy_admin`, `proxy_admin_viewer` — view-only, can't create/delete keys or add users — `internal_user`, deprecated `internal_user_viewer`). Org/team-scoped roles AND full Admin-UI SSO (OIDC/SAML) are both Enterprise-license-gated industry-wide, with SSO free only up to 5 users beyond which a paid license is required — full SSO is a monetized premium tier, not a self-hosted OSS baseline, at the leading comparator. Kong AI Gateway secures its control-plane/data-plane trust boundary with mTLS + per-node X.509 certificates — but this specifically addresses a distributed, multi-node control-plane/data-plane split, a topology Kelvran doesn't have (consistent with the already-decided-against distributed `ConcurrencyLimiter`). Today `gateway/internal/admin/admin.go`'s `requireBearerToken` wraps the entire mux with one `subtle.ConstantTimeCompare` check — `GET /admin/config`, `POST/DELETE /admin/virtual_keys/{name}` all require the identical secret; there is no read-only/mutate split, and neither handler writes an audit log entry on create/delete (a separate, directly-observed gap not covered by any external source this pass). **Fix**: a second, GET-only viewer secret mirroring LiteLLM's free `proxy_admin_viewer` — small, low-risk, matches an OSS-tier pattern, reuses the existing "separate credential space, never delegates to `identity.Verifier`" architecture. **Trigger for OIDC/SAML SSO**: a deliberate Enterprise-tier product decision or genuine multi-human-operator need (today's admin surface is explicitly single-secret, loopback-only, off-by-default, zero recorded demand for multiple human operators). **Trigger for mTLS/X.509 CP-DP registration**: same trigger as the distributed-concurrency-limiter deferral — no multi-instance/distributed deployment topology exists yet.

### Finding 4 — Cost/latency-based routing precedent is real and mature (LiteLLM), but Kelvran's own router.go already, correctly, defers this pending a traffic-volume floor it doesn't have (confidence: high) — **not yet**

LiteLLM's `latency-based-routing` strategy picks the lowest-response-time deployment via a rolling cache with tunable `ttl`/`lowest_latency_buffer` — a real, currently-shipping, non-deprecated strategy. `router/router.go`'s own package doc comment already names this exact signal class and defers it: "Deliberately out of scope... usage/latency/cost-based routing signals... that class genuinely needs a traffic-volume floor Kelvran doesn't have production data for yet." Checked whether the underlying mechanism could at least be seeded today: `Router.ReportProbeResult(name string, success bool)` takes only a boolean — no duration/latency parameter exists anywhere in the active-probing subsystem, so latency-based routing isn't just a wiring change on top of existing data; it would need new instrumentation too. A specific claim about LiteLLM's cost-based-routing (a claimed $1 placeholder-cost risk) did NOT survive verification (0-3) — cost-based routing is simply unresearched-with-confidence this pass, not confirmed safe or unsafe either way. **Trigger**: real production traffic volume sufficient to calibrate a rolling average/error-rate floor (identical trigger to the already-made router-health-real-traffic decision), plus, for latency specifically, adding duration capture to the probe path.

### Finding 5 — MCP outbound brokering remains correctly deferred; Barbacane's OpenAPI-to-MCP pattern is a genuinely smaller, lower-risk template specifically for a decoupled inbound slice, still gated on demand (confidence: medium) — **not yet, unchanged trigger**

This does not overturn the more thoroughly-researched sibling findings (`gateway-mcp-a2a-brokering-2026-09-07.md` and its 2026-09-08 follow-up): outbound MCP brokering is still blocked on a missing tool-call cost-accounting primitive (Kelvran's per-token `Decimal` ledger has no natural unit for a non-token tool invocation) and has zero recorded demand signal. What this pass adds: Barbacane (a real, actively-committed OSS project) compiles an existing OpenAPI spec directly into an MCP tool server and dispatches every resulting tool call through the identical HTTP-request middleware chain (auth/rate-limit/validation/observability) already used for ordinary requests — confirmed in its own source, not just marketing copy. Applied to Kelvran, this is the concrete shape an inbound MCP slice (e.g. exposing the Admin API as MCP tools) could take without inventing any new cost unit. This sharpens WHICH slice would be cheapest if demand ever appears; it does not manufacture a demand signal that doesn't exist. **Trigger**: unchanged — a real user asking to broker/expose tool calls through Kelvran specifically.

### Finding 6 — NER-based guardrails remain correctly unbuilt, now confirmed by a second independent 2026 vendor; hosted-moderation-API adapters are the nearest genuinely-actionable next step, but need a deliberate RFC first (confidence: high) — **NER: not yet, same trigger; hosted moderation: not yet, needs an RFC**

agentgateway (a real, active, Linux Foundation-governed 2026 project) explicitly routes NER use cases (people/orgs/places) to a "custom webhook" integration point, stating built-in options don't cover NER models — this reconfirms, from an independent second source, the prior finding that no mature no-cgo Go NER library exists anywhere. Kelvran punting on native NER remains the right call, not a gap to close. Separately, agentgateway's ML/moderation capability for hate-speech/violence/harmful-content is not a self-hosted classifier — it is first-class adapters to hosted provider APIs (OpenAI Moderation, AWS Bedrock Guardrails, Google Model Armor, Microsoft Purview DLP), explicitly contrasted against its own native regex tier. A related claim that agentgateway frames these as a deliberate, staged two-tier progression was explicitly refuted (0-3) — it would be an overreach to say agentgateway "recommends" hosted moderation as Kelvran's necessary next step; it is simply the two capability tiers that vendor ships. Kelvran's current guardrails already match agentgateway's own first (native, in-process, deterministic) tier exactly. **Trigger for hosted moderation-API adapters**: a deliberate Guardrails-v2 RFC that makes the new latency/cost/fail-open-vs-closed tradeoffs explicit up front — this is a product decision Kelvran hasn't made, not merely an integration task.

### Finding 7 — Batch/async API support remains a clear not-yet, reinforced rather than weakened by fresh evidence (confidence: high) — **not yet**

Envoy AI Gateway (renamed "agent-router") merged only a 624-line design PROPOSAL for batch processing on 2026-02-03 — zero implementation code — and the proposal itself explicitly flags rate-limiting/token-usage tracking for batch APIs as unresolved and hard (token usage is only known after async result retrieval, creating double-counting/never-retrieved edge cases), recommending deferring the whole problem to "a future proposal." A follow-up implementation PR remains open/draft as of 2026-09-09 — more than seven months after the design proposal, the most comparable OSS gateway still hasn't shipped batch support. Separately, Portkey — a leading commercial comparator that does ship batch — gates it entirely behind Enterprise hybrid/self-hosted plans requiring direct sales contact; it is absent from every self-serve tier. **Trigger**: a real recorded user demand signal (none exists) AND someone actually solving the delayed-token-usage-accounting/rate-limiting design problem even Envoy's own reference proposal punted on — building this today would be genuinely unprecedented design work, not adoption of a settled industry pattern.

## Caveats

- Research question 6 (secrets/credential rotation for provider API keys) returned zero surviving claims — this is an absence of evidence, not a finding that Kelvran's current practice is adequate or inadequate. Treat as a genuine open item for a future pass, not silently assumed away.
- Several of the strongest "industry practice" claims (LiteLLM's RBAC/SSO tiering) come from a vendor that itself monetizes the exact features being cited as "standard practice" — what a commercial vendor chooses to paywall is a business decision, not proof of technical necessity. Kelvran's much leaner single-secret/single-tenant admin model may remain adequate far longer than the vendor-tiering pattern implies.
- Three claims were explicitly refuted during adversarial verification and support none of the findings above: LiteLLM's cost-based-routing "$1 placeholder" risk (0-3), agentgateway's claimed deliberate regex-vs-hosted-ML staged-tier narrative (0-3), and Kong Admin API loopback-default parity with Kelvran (1-2).
- Finding 1 (the tool-call guardrail scanning gap) came from direct inspection of Kelvran's own code, not from the pre-verified 20-claim vote-tallied set — high-confidence because it's a straightforward two-function code read, but evidentially a different category from the externally-sourced, multi-vote-verified findings.
- Time-sensitivity: all vendor docs cited (LiteLLM, Kong, agentgateway, Envoy/agent-router, Barbacane, Portkey) are current as of 2026-09-09, but this space moves fast — re-verify before implementing anything.

## Recommendation for Kelvran

1. **Fix the post-call Guardrails tool-call scanning gap now** (Finding 1) — this is a defect in already-shipped security surface, not a new feature, and should be filed and fixed independent of this broader research cadence. Also check whether the same asymmetry exists on the audit-only streaming post-call path.
2. **Optional, low-risk, no recorded demand yet**: a per-provider rate-limit dimension (Finding 2) and an Admin API viewer-role split (Finding 3) — both small, both reuse existing proven patterns, neither urgent without a real demand signal.
3. **Not yet, all correctly deferred with a named trigger**: cost/latency-based routing (needs traffic volume + latency instrumentation), MCP/A2A outbound brokering (needs a cost-accounting primitive + real demand), full Admin-API SSO/mTLS (needs a product decision or multi-instance topology), batch/async API support (needs a demand signal + solving an industry-wide unsolved accounting problem), NER-based guardrails (needs a mature Go library that doesn't exist).

## Open Questions

- Secrets/credential rotation for the AWS/provider API keys is entirely unresearched by this pass — what does real 2026 production practice actually require (automated rotation via a secrets manager, short-TTL/STS-style credentials) that Kelvran might be missing?
- Is there any real user/demand signal for Admin-API multi-operator use or batch-API support — or does Kelvran remain genuinely single-operator/single-tenant-shaped for the foreseeable future? This directly determines whether the two build-now-but-no-demand-signal candidates (per-provider rate limiting, Admin viewer role) are worth doing opportunistically now versus deferred indefinitely.
- Does the tool-call-arguments guardrail scanning gap (Finding 1) exist anywhere else Guardrails is invoked that this pass didn't check?
- Now that Barbacane demonstrates a concrete, low-risk "same-middleware, no shadow stack" pattern for exposing an OpenAPI surface as MCP tools, does that materially change the calculus for decoupling a small inbound-only MCP slice as a nearer-term item — or does the absence of any recorded demand signal make this moot regardless of how cheap the slice has become?
