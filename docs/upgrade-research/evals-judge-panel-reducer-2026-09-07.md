# Kelvran Evals — Judge-Panel Reducer/Voting Mechanism Research

**Date:** 2026-09-07
**Scope:** `evals/evals/judge/llm_judge.py`'s `judge()` and `evals/evals/models.py`'s `Score`, specifically the reducer/voting algorithm that would combine `N > 1` independent LLM-judge verdicts into one final `Score` — the exact gap `docs/rfcs/2026-09-07-evals-judge-panel-interface.md` left as a deliberate, honest `NotImplementedError`.
**Method:** Adversarial multi-source research (3-vote verification per claim) against real production/academic 2026 multi-judge-aggregation practice: Inspect AI (UK AISI), Braintrust, Langfuse, PoLL (Cohere), and four 2026 academic papers specifically studying LLM-judge-panel correlation and aggregation (Apple ML Research/Kohli, CARE/Wisconsin-SprocketLab, an Ising-model dependence-aware aggregator from UC Davis/AWS, and a pivotal-vote margin-analysis paper). This is one of four parallel deep-research passes (routing scope, MCP/A2A brokering, hierarchical budgets, evals judge-panel reducer); it does not touch or reference implementation work on the other three.

---

## Context this research does not re-litigate

`docs/rfcs/2026-09-07-evals-judge-panel-interface.md` (accepted, implemented 2026-09-07) already shipped the **interface**, not the panel behavior:

- `evals/evals/judge/llm_judge.py`'s `judge()` accepts `CallModel | list[CallModel]`. A list of exactly one is scored identically to a bare callable. **A list of length > 1 raises `NotImplementedError`** — the majority-reducer aggregation this research report is about is explicitly named in that error message as unbuilt.
- `evals/evals/models.py`'s `ScorerType` gained `"llm_judge_panel"` alongside `"deterministic"`/`"llm_judge"`. No scorer constructs a `Score` with this value yet.
- That RFC already decided, as "a reasoned decision, not a silent default": independent-refutation (not pairwise comparison), a **majority (>50% quorum)** default reducer, and panel composition starting at **2 disjoint model families** (Kelvran's already-shipped Anthropic + OpenAI `CallModel` wiring in `evals/evals/judge/providers.py`). It explicitly deferred `Score.metadata`/per-judge-vote storage, since no real writer existed yet.

This report's job is the one thing that RFC deliberately left open: **the actual reducer algorithm** — how N independent judge verdicts become one final `Score`, and how that `Score` composes with the CI-gate machinery `docs/rfcs/2026-09-07-evals-cigate-refinements.md` just shipped on top of `Score` (`--fail-under`, `--category-fail-under`, flaky exclusion — all read via `evals/evals/cli.py:1285-1299`'s `for scorer_type in sorted(...)` loop, which sums `s.value: bool` per group and feeds `(successes, total)` into `evals.stats.wilson_interval`).

## Findings, ranked

### 1. Real, shipped multi-judge reducers exist — but only one framework (Inspect AI) actually ships one; two other real eval platforms surveyed (Braintrust, Langfuse) ship none at all

**What:** Inspect AI's `src/inspect_ai/scorer/_reducer/reducer.py` ships two, deliberately *distinct*, named reducer strategies for combining a panel's per-judge scores: `mode_score()` (plurality — the most frequent value wins, ties broken by the order judges were declared) and `majority_score()` (a **strict majority**: a value wins only if `count * 2 > panel_size`; if nothing clears that bar — including an exact even-panel tie — the result is `NaN`/unscored, *not* decided by declaration order). Critically, unscored/`NaN` judge outputs still count toward `panel_size` (the denominator) even though they contribute nothing to any candidate's count — an abstaining judge makes majority *harder* to reach, never easier.

Braintrust's Autoevals reference docs describe no multi-judge/ensemble feature at all: each evaluator (e.g. `Factuality`) is instantiated with exactly one model at a time; its `Score` primitive is a continuous float in `[0,1]` (or a categorical mapped to a number), architecturally different from Kelvran's boolean `Score.value` + Wilson-interval-on-a-boolean-success-rate gate. Langfuse's model-based-evals feature runs multiple *independent* evaluators over a trace (toxicity, relevance, accuracy) but each writes its own separate score with **zero** aggregation/voting logic anywhere in its docs or source (confirmed via `gh search code` across Langfuse's own repos — the only aggregation code found is a generic mean/value-counts UI display helper, not a judging decision mechanism).

**Confidence:** High — Inspect AI claims verified directly against live source code (not docs alone) via raw GitHub fetch; Braintrust/Langfuse negative claims each verified against primary docs plus (for Langfuse) a source-code search, all 3-0.

### 2. PoLL's abstract establishes the panel-beats-single-large-judge *result*, but does not itself specify majority vote as the aggregation mechanism — don't over-cite it for the "how," only the "whether panels can help"

**What:** PoLL (arXiv:2404.18796) demonstrates a panel of smaller, cheaper LLM judges from disjoint model families outperforming a single large judge (GPT-4-class), across three distinct judge settings and six datasets. The abstract itself, verified directly, never mentions majority vote, mean, or any other specific aggregation mechanic. The already-shipped interface RFC's own citation of PoLL is therefore correctly scoped to the *disjoint-model-families* and *panel-vs-single-judge* framing, not to majority vote's specific algorithm — that association came from Inspect AI's own `multi_scorer()` prior art, not from PoLL itself. (A commonly-repeated secondary claim that PoLL is "over 7x cheaper" was checked directly against the primary abstract in this pass and did **not** independently re-confirm at the rigor this report requires — treat the qualitative "smaller disjoint panel can match/beat one large judge" finding as solid, but do not cite a specific cost multiplier without re-deriving it from the paper body.)

**Confidence:** High for what PoLL's abstract does say (3-0); the cost-multiplier figure is explicitly flagged here as unverified in this pass and should not be repeated as a load-bearing number.

### 3. New, sobering evidence directly bears on whether *any* small panel + majority vote reliably beats a single well-chosen judge: a 9-judge, 7-disjoint-family panel provided only ~2 effective independent votes, and majority vote did not meaningfully beat the best single judge on any tested dataset — was measurably *worse* on one

**What:** "Nine Judges, Two Effective Votes: Correlated Errors Undermine LLM Evaluation Panels" (Apple ML Research / Kohli, arXiv:2605.29800, May 2026) tested 9 frontier LLM judges from 7 disjoint model families on three NLI datasets (MNLI/SNLI/AlphaNLI, all with real ground-truth crowd labels) plus RewardBench. Using plain, unweighted majority vote as the headline aggregator, the panel did not meaningfully outperform the best individual judge on any dataset: MNLI panel 72.0% vs. best single judge 71.8% (within noise); **SNLI panel 77.7% vs. best single judge 84.2% — the panel was genuinely worse than just using the single best judge**; AlphaNLI 88.7% vs. 91.2% (again worse). The paper's own Kish effective-sample-size analysis found the 9 nominally-independent judges carry the statistical information of only ~2 truly independent votes — roughly three-quarters of the panel's nominal independence is lost because the judges make the same mistakes on the same items (shared pretraining, architectures, and failure modes), not independent noise that averaging can wash out.

**Why this matters for Kelvran specifically:** this is the single most important caution for the exact design question this report was asked to answer. It directly undercuts the assumption baked into "start a 2-judge disjoint panel + majority vote" as a mechanism that will *reliably* improve on Kelvran's current single-judge (Haiku 4.5) scoring. **Caveat, stated honestly:** the study's smallest tested disjoint-family configuration used 7 judges/families, not Kelvran's target 2–3; and the task is closed-set NLI classification against ground-truth crowd labels, not Kelvran's open-ended reference-guided judge grading. Both are real differences in kind, not just scale — this is directionally relevant, corroborating evidence, not a controlled measurement of Kelvran's exact 2-judge, open-ended-grading setup.

**Confidence:** High for the paper's own reported numbers and mechanism (verified directly against the primary arXiv source, 3-0); medium for its direct applicability to Kelvran's smaller/different panel, which this report flags rather than asserts.

### 4. The theoretical reason majority vote can fail for LLM-judge panels: correlated errors from shared confounders, not independent noise — and this is a provable, not just empirical, gap under a formal model

**What:** Two independent 2026 papers formalize *why* Finding 3's empirical result happens. CARE (arXiv:2603.00039, Feb 2026, Wisconsin/SprocketLab) states its motivating premise directly: standard aggregation (majority vote or averaging) implicitly assumes judges are conditionally independent given the true label, but real LLM judges share correlated errors from verbosity/stylistic preference/training artifacts, "causing standard aggregation rules like majority vote or averaging to provide little gain or even amplify systematic mistakes." A second paper (arXiv:2601.22336, UC Davis/AWS, Jan 2026) proves a formal separation result under a class-dependent correlation (Ising) model: there exist regimes where every individual judge is better than random, yet a conditional-independence-based majority/weighted-majority predictor keeps making a constant fraction of errors no matter how many judges are added, by misreading correlated "wrong-mode" agreement as independent corroborating evidence — while a dependence-aware Bayes-optimal aggregator's error vanishes as panel size grows. (A refinement worth noting: under class-*independent* correlation specifically, the Bayes-optimal rule is still a linear/weighted-vote form with correlation-adjusted weights — it's the class-*dependent* correlation case where the optimal rule becomes genuinely non-vote-shaped. Naive CI-based majority is provably suboptimal in the harder, class-dependent case, not merely "less than perfect" in the easier one.)

**Why this matters for Kelvran specifically:** this supplies the mechanism behind Finding 3's numbers and explains why "just add a second disjoint-family judge and vote" is not automatically a free accuracy win, even with genuinely different model families.

**Confidence:** High for both papers' own stated claims (each verified directly against primary-source PDF/abstract text, 3-0); this is a characterization of what each paper argues/proves, not an independent empirical replication by this research pass.

### 5. Sophisticated dependence-aware aggregation *does* measurably beat both uniform and weighted majority vote on real judges and real datasets — but every real validation of this used a training/fitting step and panels far larger than Kelvran's target 2–3

**What:** CARE's own 12-benchmark empirical results show its confounder-aware aggregator reduces error substantially vs. both majority-vote and averaging baselines — but its tested panels were 11–20 judges (0.6B–14B params), not Kelvran's 2–3-judge target. The Ising-model paper ran real six-judge experiments (Claude Sonnet 4.5, Claude Haiku 4.5, OpenAI gpt-oss-120b, Llama 4 Maverick, Llama 4 Scout, DeepSeek-R1 — closer to Kelvran's real judge scale) on three real-world tasks (WikiQA relevance, Jigsaw toxicity, a Phoenix-benchmark CNN/DailyMail summarization variant) and found its dependence-aware (Ising) aggregator clearly beating both weighted and uniform majority vote: relevance 0.90 (Ising) vs. 0.82 (weighted-MV) vs. 0.80 (uniform-MV); toxicity 0.79 vs. 0.72 vs. 0.69. Both results are real and methodologically solid — but both required a model-fitting/EM step over (at least partially) labeled data, not a zero-shot drop-in reducer like plain majority vote, and both are self-evaluations by the papers' own authors on their own proposed methods (a standard, real caveat, not a disqualifying one).

**Why this matters for Kelvran specifically:** a genuinely more accurate reducer than majority vote exists and has real evidence behind it — but adopting it means adding a calibration/fitting step with a data-labeling requirement, a materially larger and more operationally novel piece of infrastructure than a stateless majority function, and one with zero validated evidence at Kelvran's actual 2-judge panel size.

**Confidence:** High for both papers' own reported numbers (each verified directly against primary-source text, 3-0); the applicability of a training-requiring aggregator to Kelvran's current, offline, no-labeled-corpus regression-testing usage pattern is a real open question this report does not resolve.

### 6. The one place additional judges/tie-breakers demonstrably help is decisions with a one-vote margin — population-averaged accuracy metrics hide this

**What:** A separate 2026 paper (arXiv:2608.06940) shows, via elementary majority arithmetic, that substituting or adding a single verification signal (or, by direct mathematical extension, a single additional judge vote in a majority scheme) can only change a decision that sits at a one-vote margin — a pivotal vote. The accuracy gain from that extra signal concentrates entirely on those pivotal, near-tie decisions (the paper measures +10.4 to +23.3 percentage points there) and is exactly zero everywhere else; a population-wide independence/accuracy metric averages over both the affected and unaffected cases and therefore obscures a real, large, conditional effect.

**Why this matters for Kelvran specifically:** this reframes what a 2-judge panel's majority reducer is actually for. It will not move the needle on cases the two judges already agree on (the vast majority, if the judges are any good) — its entire value is concentrated on the disagreement cases, which for a 2-judge panel are exactly the tied (1-1) cases this report's design section below has to give an explicit disposition to. This makes the tie-break policy the single highest-leverage design decision in the whole reducer, not an afterthought.

**Confidence:** High for the paper's own stated mechanism (verified directly against primary source, 3-0); the extension from "an added verification signal" to "an added judge vote" is an explicitly-hedged, mathematically sound generalization of a source-agnostic single-ballot-substitution argument, not a claim the cited paper tested with LLM judges specifically.

### 7. Confirms the interface RFC's own choices were reasonable, ties them to Kelvran's precedent correctly, and clarifies which existing Kelvran pattern is (and is not) the closest analog

**What:** Inspect AI's `majority_score()` (Finding 1) is a real, concrete precedent for exactly the reducer shape the interface RFC already committed to (`>50%` quorum, majority default). Kelvran's own **multi-axis judging** pattern (`docs/rfcs/2026-09-05-evals-multi-axis-judging.md`'s `--judge-axes`: each axis independently PASS/FAIL, then AND-combined into one case verdict) is the correct internal analog the interface RFC already cited — a panel's majority-reduction would happen *within* one axis, then axes AND-combine exactly as today. The research brief's suggested alternate analog — the **guardrails/PII classifier's** category-tiered fail-open/fail-closed verdict combination (`docs/rfcs/2026-09-03-guardrails-pii-regex-classifier.md`) — is, on direct inspection, a *materially different* combination pattern: it is a worst-of/severity-tiered policy across *distinct detector categories* (credential detection always blocks, contact-info detection always warns), not a same-question, same-axis vote-counting problem across *interchangeable* judges. It is a real and useful precedent for Kelvran's general "never silently default to permissive" ethos (directly informing this report's tie-break recommendation below), but it is not the multi-judge-voting analog the research brief speculated it might be — the multi-axis AND-combine pattern is.

**Confidence:** High — both Kelvran-internal claims verified by direct reading of the cited RFCs and the live `evals/evals/cli.py` code (lines 1285–1338 for the AND-combine/category-gate machinery), not secondhand summary.

## Concrete reducer design for Kelvran

### The structural tension the interface RFC's own choices create, and why this report resolves it rather than restating "majority, >50%"

The interface RFC already decided "majority (>50% quorum)" and "panel starts at 2, disjoint families." Those two decisions, taken together, have a consequence worth naming explicitly rather than leaving implicit: **with an even-sized, 2-judge panel, a strict `count * 2 > panel_size` majority can only ever be reached when the two judges agree.** Any 1–1 split is *guaranteed*, not merely possible, to fail the majority threshold every time it occurs — this is not a rare edge case to handle defensively, it is the structurally-certain outcome of every single disagreement a 2-judge panel will ever produce. Inspect AI's own design (Finding 1) handles this by returning `NaN`/unscored — a real, honest option in an offline research tool. Kelvran's `Score.value` is a non-optional `bool` that feeds directly into `evals.cli.report_cmd`'s Wilson-interval gate math (`evals/evals/cli.py:1285-1299`), so "unscored" is not representable without either widening the schema or picking a concrete disposition. This report picks the latter, deliberately, rather than deferring it again.

### Function signature

`judge()`'s existing `NotImplementedError` branch (`len(panel) > 1`) is replaced with: `await asyncio.gather(*(call(prompt) for call in panel))` (independent-refutation — every judge sees the identical prompt, none sees another's output or verdict, matching the already-decided design), parse each response with the existing `_parse_judge_response`, then call `reduce_panel_votes`.

### Majority rule and tie-break — the one real new policy decision

- **Majority rule, unchanged from the interface RFC's decision and Inspect AI's exact formula:** count votes for `True` and `False` among `votes`; a value wins iff `count * 2 > len(votes)`.
- **Tie-break for a panel with no strict majority (the guaranteed 1–1 case at panel size 2, and any exact split at a larger even panel): `quorum_reached=False`, `passed=False` — fail-closed, not an implicit declaration-order pick.** This is a deliberate policy choice, not a default picked by omission, and it follows Kelvran's own existing convention directly: `docs/rfcs/2026-09-03-guardrails-pii-regex-classifier.md`'s fail-closed tiers already establish, for this exact codebase, that when a verdict mechanism can't produce a confident answer, the safe direction is to withhold a pass, not grant one ("Any security mechanism should be designed... so that when it fails, it fails closed"). Applying the identical philosophy here — a panel that couldn't agree gets treated as a fail, not a pass — is consistency with an existing Kelvran decision, not a new invention. It is also the more conservative reading of Finding 6: since the entire accuracy value of a second judge is concentrated on exactly these disagreement cases, silently defaulting a tie to `passed=True` would mean the panel adds a judge specifically to identify contested cases and then discards that signal by rubber-stamping them.
- **Alternative considered and rejected for the first cut: auto-escalate to a 3rd, tie-breaking judge only on a 1–1 split.** This is the mechanism Finding 6's own evidence would most directly justify (pay for a 3rd judge only exactly where a 3rd judge's marginal value is real), and is worth documenting as the natural next iteration if real production disagreement rates justify it. Rejected for v2's first cut because: (a) it directly contradicts the interface RFC's own already-decided scope, which named a 3rd/4th judge as a stretch goal, not a v2-launch mechanism; (b) it turns `judge()`'s clean, static `panel = call_model if isinstance(call_model, list) else [call_model]` shape into a variable-size, conditional-second-round call graph, a real complexity increase with zero production evidence yet that Kelvran's specific 2-judge configuration disagrees often enough to matter; (c) the fail-closed default is not a dead end — it can be revisited exactly if real telemetry (a real, computed `quorum_reached=False` rate, cheap to measure since it's already a field on `PanelVerdict`) shows disagreement is common enough to be worth a 3rd judge's cost.
- **Alternative considered and rejected: default a tie to `passed=True` (fail-open).** Rejected for the same reason the guardrails RFC rejected inheriting the rate limiter's blanket fail-open default without a second, independent control backing it up — a judge panel that can't agree has no analogous second control (there's no `budget.Tracker`-equivalent safety net here), so there is no justification for defaulting to permissive.

### Composition with the CI-gate machinery — zero changes required to `report_cmd`

The reducer emits exactly **one** `Score` per case per axis, with `scorer_type="llm_judge_panel"` and `value=panel_verdict.passed` (a plain `bool`). This is the load-bearing design property: re-reading `evals/evals/cli.py:1285-1299` confirms `report_cmd`'s entire gate/report loop only ever reads `s.scorer_type`, `s.value` (as a boolean success/failure), `s.tags`, `s.flaky`, and `s.tier` — all of which a panel-produced `Score` already has, unchanged, via the exact same construction path `run_cmd`/`rollout_cmd` already use for `llm_judge` scores today. **The Wilson-interval `--fail-under` gate needs no code change whatsoever** — it treats a fail-closed tie exactly like a genuine 2/2 `FAIL`: both simply fail to contribute a success to the group's pass rate. `--category-fail-under` and flaky-exclusion (`docs/rfcs/2026-09-07-evals-cigate-refinements.md`) compose identically, for the same reason.

- `Score.cost_usd` for the one emitted panel `Score` is the **`Decimal` sum of every panelist's real per-call cost** (not `None`, not just the first judge's cost) — this is a real, exactly-computable fact given Kelvran's existing `providers.py` cost-tracking side channel for both Anthropic and OpenAI calls, not an estimate, so it should follow the same "exact fact, not `None`" convention `Score.cost_usd`'s own docstring already establishes for a `deterministic` score's `Decimal("0")`.
- **Per-judge vote audit trail:** this is the moment the interface RFC's deferred `Score.metadata` question gets a real answer, because — unlike when that RFC was written — a real writer now exists. Recommend a narrow, typed field over an untyped dict, consistent with this codebase's existing preference for honest, specific schemas over speculative generic ones (the same preference `Run`'s and `Score`'s own docstrings state explicitly): `Score.panel_votes: list[PanelVote] | None = None` (populated only for `scorer_type="llm_judge_panel"`, `None` — not `[]` — for every other scorer type, matching `Score`'s existing "`None` means not applicable" convention) plus `Score.quorum_reached: bool | None = None`, so `report_cmd`/audit tooling can distinguish "unanimous PASS", "unanimous FAIL", and "fail-closed tie-defaulted-to-FAIL" without re-deriving it from raw votes after the fact.

### Panel-size/quorum policy this design commits to (superseding nothing, resolving what was left open)

- Reaffirms the interface RFC's "2 disjoint families, majority (>50%) reducer" starting point — this research found no evidence strong enough to overturn it, only evidence (Finding 3) that it should not be assumed to be a free accuracy win, which the fail-closed tie-break and the honest `quorum_reached` audit field both directly address by making disagreement visible rather than papering over it with a wrong-but-plausible pass.
- Does **not** adopt CARE's or the Ising-model paper's dependence-aware aggregation (Finding 5) for the first cut — both require a fitting/calibration step over labeled data that Kelvran's current offline, small-fixture regression testing has no infrastructure or labeled corpus to support yet, and both were validated at panel sizes (6–20 judges) well beyond Kelvran's 2–3-judge target. Track this as a real, evidence-backed future option, not a rejected idea — revisit if/when Kelvran has enough real judge-disagreement data to fit one.

## Is this the right next evals investment? — honest recommendation

**Recommendation: do not build the panel reducer next.** Leave the interface RFC's `NotImplementedError` in place for now. The concrete design above is ready to implement without further research whenever it is prioritized, but this research pass's own findings argue against prioritizing it ahead of the regression-tier curated-dataset gap named in `docs/upgrade-research/evals-2026-09-06.md` and still explicitly unscoped since Phase 1e.

**Why, concretely:**

1. **The core accuracy premise is now in real doubt, not just theoretically arguable.** Finding 3's own numbers — a 9-judge, 7-disjoint-family panel *failing* to beat the single best judge on any tested dataset, and doing measurably worse on one (SNLI, 77.7% vs. 84.2%) — is exactly the failure mode Kelvran's own 2-judge design is most exposed to, precisely because a 2-judge panel structurally guarantees the hardest case (a genuine tie) whenever the judges disagree at all. This does not prove Kelvran's specific panel would underperform its current single-judge (Haiku 4.5) scoring, but it removes the presumption that "add a second disjoint judge and vote" is a safe, low-risk accuracy improvement — it is a real behavior change to every existing `--fail-under` gate the moment it ships, since a second judge disagreeing on any case Haiku alone currently passes now flips that case to fail-closed.
2. **The genuinely more accurate alternative (dependence-aware aggregation, Finding 5) requires infrastructure Kelvran doesn't have yet** — a labeled/partially-labeled fitting corpus — and has zero validation at Kelvran's target panel size. Building plain majority vote now, only to replace it once real disagreement data justifies the more sophisticated approach, is a plausible path but is itself an argument for waiting until there is real production disagreement data to justify either investment, rather than building the simpler version speculatively.
3. **A judge-panel reducer refines *how* existing cases are scored; it does nothing to fix *what* is being scored against.** Kelvran's CI gate today runs against tiny, hand-built fixtures (`tests/fixtures/golden_example.json`, `tests/fixtures/ci_gate_example.json`), not a real curated regression corpus. `docs/upgrade-research/evals-2026-09-06.md`'s own Finding 4 already established — and this pass finds nothing to contradict — that every comparable real platform treats a *human-curated, human-authored-`expected`* regression dataset as the actual load-bearing quality lever, not a more sophisticated scoring mechanism layered on top of a thin case set. Investing in the reducer before the underlying case set is real is optimizing the measurement of a signal that is not yet the thing worth trusting — the same pattern this project has already twice, correctly, declined to over-invest in for the bootstrap/Bayesian-stats backlog item (`docs/upgrade-research/evals-2026-09-06.md`'s Finding 3, and `STATUS.md`'s 2026-09-05 audit language, both reaffirmed rather than overturned by that same research pass).
4. **The engineering cost is genuinely Medium, not trivial**, and — unlike the interface RFC's own "typing it correctly once" framing — building the reducer now is not simply retrofit-avoidance, because the interface already exists and absorbs a future implementation cleanly (`judge()`'s signature and `Score.scorer_type` need zero further changes; only `Score` gains two new optional fields, and `report_cmd` needs zero changes at all, per this report's own composition analysis above). There is no "typing it correctly once, now, or pay more later" argument pulling this forward the way there was for the interface itself — the cost of waiting for real disagreement data before committing to a tie-break policy and a reducer algorithm is genuinely low.

**When this verdict would flip:** if Kelvran's regression-tier case set grows into something real enough that judge-scoring noise (not case-set thinness) becomes the dominant source of gate flakiness or disputed verdicts — or if a second judge becomes available at effectively zero marginal cost and cheap telemetry shows a non-trivial real disagreement rate on real cases — either is a concrete, observable trigger condition, in the same spirit as this project's own Sandbox-Pool and bootstrap/Bayesian-stats trigger-condition precedents, rather than a reason to build speculatively now.

**Relative to the other three parallel research passes (routing-scope-expansion, MCP/A2A brokering, hierarchical budgets):** this report does not have visibility into those passes' findings and does not assume a ranking against them — that comparison is for whoever consolidates all four. What this report can say with confidence, scoped to evals alone, is that **the regression-tier curated dataset is very likely a higher-value use of comparable effort within `evals/` specifically** than building the judge-panel reducer right now, for the four reasons above.

## Caveats

- Finding 3's most directly relevant evidence (the Apple ML Research / Kohli correlated-panel study) used a 7-judge-family, closed-set NLI classification setup, not Kelvran's exact 2–3-judge, open-ended reference-guided grading setup. Treated throughout this report as directionally relevant, corroborating evidence, not a controlled measurement of Kelvran's precise configuration — flagged explicitly wherever it's cited, not smoothed over.
- CARE's and the Ising-model paper's strongest empirical results (Finding 5) are self-evaluations by each paper's own authors of their own proposed methods — a normal, real caveat for any single-paper result, not a disqualifying one, but worth remembering before treating either number as an external, independently-replicated ceiling.
- A previously-circulated "PoLL is >7x cheaper" figure did not independently re-verify to this report's standard in this pass (Finding 2) — do not repeat that specific number without re-deriving it from the paper body directly.
- Both of the "sophisticated aggregation beats majority vote" results (Finding 5) were validated at panel sizes (6–20 judges) larger than Kelvran's 2–3-judge target; their applicability at Kelvran's exact scale is inferred, not directly tested by either paper.
- All primary sources are current as of this research date (2026-09-07); the correlated-judge-panel literature (Findings 3, 4, 6) is itself only weeks to a few months old and largely single-author/small-team preprints not yet subject to independent replication or peer review — treated as the best currently-available evidence, not as settled science.

## Open questions
