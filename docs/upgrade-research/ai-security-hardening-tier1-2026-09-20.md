# AI Security Hardening, Tier 1 — Research (2026-09-20)

**Scope.** Two independent questions, both checked against primary sources and Kelvran's live code, never a secondary write-up: (1) does the *current* OWASP Top 10 for LLM Applications still validate `THREAT_MODEL.md`'s existing crosswalk and Kelvran's real prompt-injection defenses (`gateway/internal/guardrail`'s regex/checksum detectors and the hidden-Unicode heuristic, confirmed by reading `promptinjection.go`/`engine.go`/`policy.go`/`bedrockguard.go` directly — genuinely regex/heuristic-based with zero ML by default, exactly as claimed), and has the state of the art moved meaningfully; (2) has the STS/short-lived-credential rotation work named in `AGENTS.md`'s Gotchas section (`SessionTokenEnv`) actually been operationalized — a real STS session generated/rotated — or does `.env` still hold a long-lived static key.

**Already shipped (not re-litigated):** `internal/guardrail`'s PII/secret checksum-validated detectors (email/phone/SSN/IBAN/credit-card/IP/secret-key); `internal/guardrail/bedrockguard`'s opt-in AWS Bedrock Guardrails `PROMPT_ATTACK` ML detector, live in the pilot (`guardrail_id: "ao7so1e2qocp"`, `inputStrength: MEDIUM`); `DeploymentConfig.SessionTokenEnv`, wired through to the SigV4 signer in both `dataplane.go` and `bedrockguard.go` with zero further code needed.

## Executive Summary

OWASP published a real **2026** edition of the Top 10 for LLM Applications on 2026-09-01 (v1.0, dated 2026-08-04) — this is not a hypothetical; the full 122-page PDF was fetched and read directly. It confirms `THREAT_MODEL.md`'s own 2026-09-10 Addendum claim (Excessive Agency moved from rank 6 to rank 3) is **correct and grounded**, not fabricated — but the Addendum only patched two rows' prose and never actually renumbered the crosswalk table to the real 2026 IDs, which reshuffled five of ten categories and renamed one outright (System Prompt Leakage → the broader **Hidden Context Exposure**). Separately, OWASP's own 2026 edition — citing real 2025 adaptive-attack research (Nasr et al.) showing static defenses succeed near-0% while adaptive attacks succeed >90% against most recent defenses — states flatly that **no reliable input-side prevention mechanism exists today for prompt injection, regex or ML, and defense must be architectural, not interceptive.** This reframes the team lead's question: the state of the art hasn't moved toward "ML classifiers solve this" — real, affordable production ML classifiers (AWS Bedrock Guardrails, Lakera, Azure AI Content Safety Prompt Shields, Google Model Armor) are now a commodity, pluggable-guardrail-provider layer at peer gateways including LiteLLM (the exact project Kelvran's own regex detector cites as precedent) — but OWASP's own primary source explicitly warns against treating any single detector, ML included, as sufficient. Kelvran already has one such real ML classifier wired in (`bedrockguard`), opt-in and off by default; the regex detector's own commit history (two vocabulary-widening patches after confirmed bypasses) is a live instance of the exact static-patch treadmill OWASP's cited research says fails under adaptive testing. Separately, and unambiguously: the STS/short-lived-credential elimination path is real, wired code with **zero operational adoption** — `.env` holds only `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` today, no `AWS_SESSION_TOKEN` line exists anywhere, and the same static key has been repeatedly flagged as leaked and never rotated across at least six documented session rounds (`DECISIONS.md`/`docs/agents/LOGS.md`, 2026-09-13 through 2026-09-18+), every time deferred as "the operator's own AWS IAM console action."

## Findings

### Finding 1 — OWASP's 2026 Top 10 is real, published, and confirms `THREAT_MODEL.md`'s rank-reshuffle claim, but the crosswalk table itself was never renumbered and now has real gaps
**Confidence: high** — verified by fetching and reading the actual OWASP GenAI Security Project 2026 PDF (`genai.owasp.org/resource/owasp-genai-llm-top-10-2026/`, "Version 2026," dated 2026-08-04, publicly announced 2026-09-01), not a secondary source.

The real 2025→2026 rank migration, per the report's own bump chart and prose (pages 6-7):

| 2025 rank/name | 2026 rank/name | Movement |
|---|---|---|
| LLM01 Prompt Injection | LLM01 Prompt Injection | unchanged — "held the top spot" |
| LLM02 Sensitive Information Disclosure | LLM02 Sensitive Information Disclosure | unchanged — "the one place... belief and evidence simply agree" |
| LLM03 Supply Chain | LLM04 Supply Chain | down 1 |
| LLM04 Data and Model Poisoning | LLM05 Data and Model Poisoning | down 1 |
| LLM05 Improper Output Handling | **LLM10** Improper Output Handling | down 5 — "fell the furthest, from fifth to tenth" |
| LLM06 Excessive Agency | **LLM03** Excessive Agency | **up 3 — "the most consequential move on the list"** |
| LLM07 System Prompt Leakage | **LLM08 Hidden Context Exposure** | renamed/re-scoped, down 1 — "a broader framework for the same failure to trust information that should have stayed out of reach" |
| LLM08 Vector and Embedding Weaknesses | LLM09 Vector and Embedding Weaknesses | down 1 |
| LLM09 Misinformation | LLM07 Misinformation | up 2 |
| LLM10 Unbounded Consumption | LLM06 Unbounded Consumption | up 4 |

`THREAT_MODEL.md`'s 2026-09-10 Addendum ("OWASP's 2026 revision reordered category ranks, most notably moving LLM06 Excessive Agency from rank 6 to rank 3... Category IDs (LLM01–LLM10) are unchanged") is **half right, half wrong**: the Excessive Agency rank-3 claim is exactly correct (confirmed via a direct quote from Michael Bargury/Zenity in OWASP's own announcement: Excessive Agency is "now number three"), but the IDs are **not** unchanged — five categories got new numbers, and the crosswalk table below it still uses the stale 2025 IDs/names throughout (`LLM06 Excessive Agency`, `LLM07 System Prompt Leakage`, `LLM08 Vector and Embedding Weaknesses`, `LLM09 Misinformation`, `LLM10 Unbounded Consumption`). Two categories — 2025's Supply Chain and Improper Output Handling — have **no row at all** in `THREAT_MODEL.md`'s OWASP crosswalk table today (Supply Chain is credited elsewhere, under the NIST Value Chain row, but never in the actual OWASP table itself).

The LLM07→LLM08 rename is substantive, not cosmetic: OWASP's own 2026 section (not yet read in full detail this pass, but its renaming rationale is stated on page 7) broadens "System Prompt Leakage" into "Hidden Context Exposure" — a wider frame for "the same failure to trust information that should have stayed out of reach." `THREAT_MODEL.md`'s current LLM07 row ("Adapter-level system-prompt handling isolated per provider; never cached across tenants") is scoped to the old, narrower System Prompt Leakage definition and has not been re-evaluated against the broader 2026 scope.

**Verdict: build now (documentation).** Renumber `THREAT_MODEL.md`'s OWASP crosswalk table to the real 2026 IDs, add the two missing rows (Supply Chain, Improper Output Handling — both already have real, shippable mitigations elsewhere in the document to cite, just never cross-referenced in this specific table), and re-evaluate the LLM07→LLM08 row against the broader Hidden Context Exposure scope rather than leaving it framed as the narrower 2025 System Prompt Leakage definition.

### Finding 2 — Kelvran's default guardrail detector is confirmed, by direct code read, to be exactly what it claims: regex/heuristic, zero ML — but a real ML detector already exists in the same package tree, opt-in
**Confidence: high** — verified directly against `gateway/internal/guardrail/promptinjection.go`, `engine.go`, `policy.go`, and `gateway/internal/guardrail/bedrockguard/bedrockguard.go`.

`PromptInjectionDetector.Detect` (`promptinjection.go:89-112`) runs exactly two checks, both pure Go stdlib: (1) a case-insensitive substring match against a combinatoric verb×target phrase list (9 verbs × 11 targets = 99 phrases, e.g. `"ignore your system prompt"`), and (2) a rune-range scan for four hidden-Unicode blocks. No model call, no embedding, no fuzzy/edit-distance matching anywhere in this file — `DefaultDetectors()` (`engine.go:113-124`) includes it unconditionally alongside six checksum-validated PII detectors. This confirms the team lead's premise for the **default** detector set exactly.

But a second, genuinely ML-based detector already exists and is live in the pilot today: `bedrockguard.Detector` (`bedrockguard/bedrockguard.go`) calls AWS Bedrock's standalone `ApplyGuardrail` API with a real guardrail ID (`ao7so1e2qocp`, per `config.yaml`), which AWS's own documentation (`docs.aws.amazon.com/bedrock/latest/userguide/guardrails-prompt-attack.html`, fetched directly) describes as detecting three distinct attack categories — Jailbreaks, Prompt Injection, and Prompt Leakage (Standard tier only) — via a purpose-built classifier, not pattern matching. `Engine.Check` runs every configured `Detector` identically (`engine.go:46-77`), so when `guardrails.bedrock_guardrails` is configured, both the regex detector and the ML detector run on every request; when it isn't, only the regex detector runs. This is an **opt-in, off-by-default** posture, confirmed by `THREAT_MODEL.md`'s own Elevation-of-Privilege row.

**One AWS-documented limitation worth flagging, not yet independently confirmed against Kelvran's specific call pattern**: AWS's docs state "the prompt attack filter does not evaluate tool results" for the native Converse/InvokeModel `guardrailConfig` integration, which structurally skips `messages[].content[].toolResult` blocks. Kelvran's `bedrockguard.Detector` instead calls the *standalone* `ApplyGuardrail` API with Kelvran's own pre-serialized JSON blob (from `serializeMessages`) passed as one opaque text block — a different call shape than the one AWS's documented exclusion describes, so it's not confirmed whether that same exclusion silently applies here too. This matters because `THREAT_MODEL.md`'s own 2026-09-11 entry proves the regex detector *does* scan `role:"tool"` fed-back content (a dedicated regression test exists for exactly this). Not resolved this pass — worth a direct empirical check (a tool-result message containing a known attack phrase, run through `bedrockguard.Detector` specifically) before assuming the ML detector's tool-result coverage matches or exceeds the regex detector's.

**Verdict: confirmed as asked — regex-only by default, real ML detector exists but is opt-in.** Not a `build_now`/`not_yet` item on its own; feeds Finding 3's recommendation.

### Finding 3 — The state of the art has moved, but not in the direction of "switch to an ML classifier" — OWASP's own 2026 edition says no input-side detector, regex or ML, is a reliable prevention mechanism
**Confidence: high** — direct primary-source read of OWASP's 2026 LLM01 section (pages 10-17), not inferred.

OWASP's LLM01:2026 Prevention and Mitigation Strategies section opens with: "Prompt injection is intrinsic to current generative AI: LLMs make no architectural distinction between instructions and data, and their behavior is stochastic, so **no reliable prevention mechanism exists today**, a position consistent with NIST (2025), NCSC (2025), and Debenedetti et al. (2025). Defense is therefore architectural rather than interceptive." Its Control #3 explicitly names semantic/ML filters as evadable: "Semantic filters are evadable by rephrasing or encoding, and low-resource and code-mixed inputs degrade their accuracy (Hackett et al., 2025)." Its Control #11 is the sharpest primary-source evidence for this finding: "Test against adaptive attackers who have read the deployed defense, and reject static-only attack-success claims... Nasr et al. (2025) found static attack success near zero while adaptive attack success exceeded 90% for most of 12 recent defenses." OWASP's own 11-point control list is dominated by architectural/blast-radius controls (constrain system-prompt-declared capabilities, validate output against a strict schema in trusted code, filter at every modality boundary, hold credentials in application code with least privilege, strip specific invisible-Unicode ranges, provenance-tag external content, require human confirmation before privileged actions, pin/sign MCP servers and tool packages) — detection (regex or ML) is one control among eleven, not the centerpiece.

Separately, real production ML-based prompt-injection classifiers genuinely are now a commodity, affordable layer — this half of the team lead's premise is also correct, just not OWASP's own recommended centerpiece. LiteLLM's proxy — the exact project Kelvran's `promptinjection.go` doc comment cites as precedent for its regex approach — now supports a whole ecosystem of pluggable third-party guardrail providers beyond its own bare regex heuristic: Lakera, Aporia, Pillar Security, DynamoAI, Javelin, Lasso, Pangea, Google Model Armor, Azure Content Safety hooks, AIM, and AWS Bedrock Guardrails itself (confirmed directly against `docs.litellm.ai/docs/proxy/guardrails/quick_start`). Kelvran already has exactly one of these real ML classifiers wired in (Bedrock Guardrails via `bedrockguard`) — it is not behind the state of the art on this axis, it is opt-in-off-by-default on it.

A live, confirmed instance of the exact static-patch treadmill OWASP's cited research warns about already exists in Kelvran's own commit history: `promptinjection.go`'s doc comments disclose that its verb/target vocabulary was widened twice after specific documented bypasses were found (adding `"disobey"`/`"circumvent"`/`"subvert"` and `"your system prompt"` to defeat two exact regression-corpus cases). This is real, working defense against the *specific* bypasses found — but it is definitionally the "static defense, patched after each disclosed failure" pattern Nasr et al. (2025), as cited by OWASP itself, found succeeds against adaptive attackers at near-zero rates regardless of how many rounds of patching precede the test.

**Verdict: not_yet for "add more ML," build_now for "stop treating regex-vs-ML as the axis that matters."** The regex detector doesn't need replacing — per OWASP's own framing it and the Bedrock ML detector are both interceptive controls of comparable (limited) reliability against a motivated adaptive attacker; Kelvran's real, actionable levers are the architectural ones OWASP's list emphasizes that Kelvran can uniquely still add at the gateway layer without needing MCP/A2A to exist first — see Finding 5.

### Finding 4 — Kelvran's hidden-Unicode range list is close to, but measurably narrower than, OWASP 2026's own named smuggling ranges
**Confidence: high** — direct comparison of `promptinjection.go:61-66`'s `hiddenUnicodeRanges` against OWASP's LLM01:2026 Control #5 (page 14).

OWASP names three specific ranges as live 2026 smuggling vectors, each independently sourced: "tag-block (U+E0000 to E007F), variation-selector (U+FE00 to FE0F), and zero-width (U+200B, U+200C, U+200D, U+2060) characters" — citing Rehberger (2025c) specifically for variation-selector smuggling of arbitrary bytes. Kelvran's own `hiddenUnicodeRanges` covers: `{0x200B, 0x200D}` (zero-width space/non-joiner/joiner — matches three of OWASP's four zero-width points), `{0xFEFF, 0xFEFF}` (BOM only — a single code point, not OWASP's 16-point `U+FE00–FE0F` variation-selector block), `{0x202A, 0x202E}` (bidirectional control — not named by OWASP's list at all, an extra Kelvran already covers beyond OWASP's own three), and `{0xE0020, 0xE007F}` (tag characters — a narrower start than OWASP's `U+E0000`, though the functional tag-character range used by real attacks starts at `U+E0020` per Unicode's own tag-block layout, so this is likely not a real gap). Two concrete, real gaps: **U+2060** (word joiner, one of OWASP's four named zero-width points, absent from Kelvran's range) and the **full U+FE00–FE0F variation-selector block** (Kelvran has only the unrelated BOM code point `U+FEFF`, not this block at all) — the latter is the more consequential gap, since OWASP cites a specific, named 2025 technique (Rehberger) demonstrating this exact block smuggles arbitrary bytes invisibly.

**Verdict: build now.** Add `{0x2060, 0x2060}` and `{0xFE00, 0xFE0F}` to `hiddenUnicodeRanges` — a two-line change with the same shape as the four existing entries, closing a gap against a named, cited, real 2026 technique rather than a hypothetical one.

### Finding 5 — Kelvran's own architecture already has real headroom against OWASP 2026's blast-radius controls, but MCP/A2A's "moot" status means the highest-leverage 2026 controls target a subsystem Kelvran doesn't have yet
**Confidence: medium** — synthesis, not a single verified claim; grounded in `THREAT_MODEL.md`'s own confirmed MCP/A2A-moot status plus OWASP's 2026 control list.

OWASP's LLM01:2026 controls most emphasized as "load-bearing" for agentic deployments (#4 credential/least-privilege mediation, #7 human confirmation before privileged actions, #8 the "Rule of Two," #10 MCP/tool-package pinning) are explicitly agent/tool-execution controls — the doc's own cross-reference states "LLM03:2026 [Excessive Agency] carries the full agency-side treatment." Kelvran has no tool-execution surface of its own (`internal/mcp` confirmed to not exist, per `THREAT_MODEL.md`'s Cross-Component table), so most of these controls apply to whatever agent sits on top of Kelvran, not to Kelvran itself — consistent with `THREAT_MODEL.md`'s own existing "moot today" framing for LLM06(old)/LLM03(new) Excessive Agency. What Kelvran *does* already have that maps onto OWASP's remaining, gateway-applicable controls: Control #2 (strict output-schema validation in trusted code, not a second LLM call) is a real match for Kelvran's structured-output normalization work; Controls #8/#9-adjacent (rate limiting, circuit breakers) are real, shipped (`ratelimit`, `budget`, `attemptFallbackChain`'s circuit breaker) — this is genuinely one of the better-covered axes in this whole report. What's genuinely still open, per Finding 3: Control #3's "filter at every modality boundary, not just text" — Kelvran's multi-modal guardrail coverage (per `THREAT_MODEL.md`'s 2026-09-06 entry) scans `Message.Parts[].Text` but never runs OCR over an image part or transcription over an audio part before scanning, and OWASP's own Common Example #4/Scenario #6 names multimodal steganographic injection (sub-perceptual image/audio/video perturbations) as a real, demonstrated 2026 attack class against four frontier vision-language models (Clusmann et al., 2025) — distinct from, and unaddressed by, the existing text-only Parts scan.

**Verdict: not_yet, named explicitly rather than silently absent.** OCR/transcription-before-scan for non-text modality parts is a real, larger feature (a new dependency, likely a hosted moderation/transcription call, not a code-only fix) — correctly out of scope for a "Tier 1" pass, but should be named in `THREAT_MODEL.md`'s Information Disclosure row as a live, unaddressed 2026-dated attack class rather than left implicit in the existing "Parts[].Text" framing, which could otherwise be misread as full multimodal coverage.

### Finding 6 — STS/short-lived-credential elimination is real, wired code with zero operational adoption; the credential in `.env` is confirmed still a long-lived static IAM key
**Confidence: high** — direct read of `.env` (names only, no values exposed), `config.yaml`, and a full history search across `DECISIONS.md`/`docs/agents/LOGS.md`.

`.env` today contains exactly two AWS-credential lines: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. No `AWS_SESSION_TOKEN` line exists in `.env` or `.env.example`. `config.yaml`'s real Bedrock deployment and its `bedrock_guardrails` block both reference only `access_key_id_env`/`secret_access_key_env` — neither declares a `session_token_env`, though the field is real and optional on `DeploymentConfig` (confirmed in `AGENTS.md`'s own Gotchas entry, itself verified against `gateway/internal/gateway/controlplane/config.go` and `dataplane.go`). This is the code capability the team lead asked about — it is genuinely real and requires zero further Kelvran code changes to use.

Whether it has been *operationalized* — a real STS session actually generated for this account — is answered unambiguously by the session history: the same live AWS access key (prefix `AKIAUXDE...`, IAM user `AAVA_Bedrock_Non_Prod`, account `324481424504`) leaked into an AI coding agent's own transcript via an unredacted `docker compose config` dump on at least three separate, dated occasions (2026-09-13, and twice more by 2026-09-14), was flagged for rotation every time, and — per `DECISIONS.md`'s own `[2026-09-15]` (second) entry — was explicitly named as "the one operator-action item this round could not itself close... still the user's own action on a live credential, not something buildable in code." Every subsequent round through at least 2026-09-18 lists "AWS key rotation" as a permanently user-blocked open item, never closed. No entry anywhere in `DECISIONS.md` or `docs/agents/LOGS.md` records an `aws sts get-session-token`/`assume-role` call ever having been run against this account, or `.env` ever having held a session token.

**Verdict: confirmed as asked.** The `SessionTokenEnv` capability is real and ready; the credential in `.env` remains, today, the same permanent IAM user's static keypair it has been since 2026-09-13, never rotated and never replaced with a short-lived session. This is an operator action outside any agent's authority to perform (it requires the user's own AWS IAM console access), not a code gap — consistent with every prior round's own disclosure, re-confirmed rather than newly discovered by this pass.
