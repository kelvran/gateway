# Prompt-Caching-Locality-Aware Deployment Routing — Deep Research (2026-09-12)

## Question

A DIFFERENT angle from cost-tier routing (already shipped: `Deployment.CostTier`) and from semantic/negation cache research (already done). Anthropic/Bedrock/OpenAI/Gemini all offer provider-side prompt caching — a discount for repeated identical-prefix content within a short TTL window — which Kelvran's cost accounting already tracks (`adapter.Usage.CacheReadTokens`/`CacheCreationTokens`) but Kelvran's routing layer has zero awareness of. Weighted round-robin can send two back-to-back requests sharing an identical long system prompt to two *different* deployment replicas of the same canonical model, each incurring a full cache-creation charge instead of the second one getting a cache-read discount, because provider-side prompt caches are scoped to the specific upstream account/region/instance a request actually lands on, not shared across Kelvran's own replicas.

1. Is this a real, documented problem for any production LLM gateway that load-balances across multiple deployments/replicas of the same model — do LiteLLM, Portkey, or OpenRouter implement session/prefix-affinity routing specifically to preserve provider-side cache locality, and how?
2. What's the real mechanism (consistent hashing on a cache-relevant prefix, sticky sessions keyed by virtual-key/conversation ID, etc.) that would let Kelvran route "this looks like a continuation of a recent conversation with a long shared system prompt" to the same deployment it last used, without undermining the existing weighted-round-robin/health-probing design?
3. How would this interact with Kelvran's already-shipped fallback chains and health-probing — a cache-affinity-preferred deployment that's currently unhealthy must still fail over correctly?
4. Given Kelvran has zero real production traffic yet, is this genuinely worth building now, or does it need real traffic data first to size the actual savings opportunity?

**Method:** 20 claims survived 3-vote adversarial verification against primary sources (vendor docs, live GitHub PRs/issues/source code). This report merges semantic duplicates, groups the survivors into findings that directly answer the four research questions above, and states a build-now/not-yet call with a named trigger for each.

---

## Executive summary

Yes — this is a real, repeatedly-solved production problem, not a hypothetical: **LiteLLM independently built and merged three separate, increasingly sophisticated fixes for exactly this failure mode** (a 2024 prefix-hash "remember which deployment served this cacheable prefix" check, a 2026 general-purpose deployment-affinity callback keyed on `previous_response_id`/user-key, and a 2026 fix decoupling deployment stickiness from model-tier stickiness after discovering an auto-router still spread one conversation's turns across a fanned-out model group), and **OpenRouter ships provider-sticky-routing by default** for exactly this purpose across every one of the caching styles Kelvran already tracks. The real mechanism bifurcates into two families — stateless prefix/content-hash routing (OpenRouter's default, sglang's `prefix_hash` policy, AWS SageMaker's `PREFIX_AWARE` routing) and stateful store-then-recall session/key affinity (OpenRouter's `session_id` override, LiteLLM's `DeploymentAffinityCheck`) — and every production implementation found treats affinity as a **soft pre-filter that degrades to full-healthy-set failover**, never a hard pin, specifically because naive always-honor-affinity routing causes hot-spotting under concurrent similar-prompt load. None of the surviving evidence, however, is about Kelvran's own traffic: every precedent cited was built by a project that already had production traffic demonstrating the cost impact (LiteLLM's issue was filed by a real user; its later PR's author confirms "running in prod for weeks"), so the honest answer to research question 4 is **not_yet**, gated on two concrete, checkable triggers rather than on vague "more data" — see Finding 4.

## Findings

### Finding 1 — This is a real, repeatedly-solved production problem, not a hypothetical one; three independent gateways/routers have shipped dedicated fixes for exactly Kelvran's scenario (confidence: high)

**LiteLLM** built and merged this fix *three separate times*, at increasing sophistication, as real production usage kept exposing new gaps:
1. **2024** — issue [#6784](https://github.com/BerriAI/litellm/issues/6784) (*"Prompt caching friendly routing strategy"*) names the exact scenario: *"Prompt caching is harder to trigger when litellm load balances across several deployments... On subsequent calls with the same first 1024 tokens... litellm would route the request to the same cached model-id."* The merged fix, PR [#7086](https://github.com/BerriAI/litellm/pull/7086) ("support routing prompt caching enabled models to previous deployments"), shipped `PromptCachingDeploymentCheck`: it hashes the cacheable prefix (everything up to and including the last `cache_control` checkpoint) via `extract_cacheable_prefix()`, stores `{model_id}` against that hash with a 300s TTL (matching Anthropic's cache window), and on a later request with a matching hash narrows the healthy-deployment set down to that one deployment. Still live on `main` today, confirmed by direct code read.
2. **2026** — PR [#19143](https://github.com/BerriAI/litellm/pull/19143) ("Add deployment affinity routing callback") adds `DeploymentAffinityCheck`, explicitly motivated by three reasons including *"to ensure context cache is always reused"* and *"to avoid inconsistent behavior across deployments that are nominally the same model."* A reviewer on that same PR pointed out the team's own pre-existing `prompt_caching_cache.py` module (item 1 above) already did a version of this — i.e., LiteLLM's own maintainers recognized this as a recurring class of problem worth two separate mechanisms, not one.
3. **2026** — PR [#36146](https://github.com/BerriAI/litellm/pull/36146) fixes a *third*, more subtle instance surfaced by its own new Auto-Router feature: *"An auto-router picks a model group, never a deployment, so a group fanned across several deployments spreads one conversation's turns across them and the provider prompt cache goes cold roughly every other turn."* This is nearly a verbatim restatement of Kelvran's own research question.

**OpenRouter** ships *provider sticky routing* as an on-by-default mechanism: *"OpenRouter uses provider sticky routing to route your subsequent requests to the same provider endpoint after a cached request... keeping your cache warm."* Its own docs state this works automatically for both caching styles Kelvran already distinguishes — implicit (OpenAI, DeepSeek, Gemini) and explicit `cache_control`-based (Anthropic) — confirming the mechanism is caching-style-agnostic, not Anthropic-specific.

**AWS SageMaker** shipped `PREFIX_AWARE` as a first-class, GA `RoutingStrategy` for real-time inference endpoints (announced 2026-09-10) specifically to preserve KV-cache locality across a multi-instance fleet — an adjacent but distinct caching layer (engine-side KV cache, not a provider-billed prompt cache), included here because it independently corroborates the general pattern (naive load-balancing spreads a shared prefix across replicas, defeating whatever cache each replica holds) and because its production-shipped mechanism is directly reusable as a design reference for Finding 2.

**Build now / not yet:** N/A (this finding establishes precedent exists; see Finding 4 for Kelvran's own build call).

### Finding 2 — The real mechanism bifurcates into two families: stateless content-hash routing, and stateful sticky-session/key affinity; a hybrid store-then-recall pattern (LiteLLM's) sits between them (confidence: high)

**Family A — stateless prefix/content hashing → deterministic worker selection (true consistent hashing, no stored record needed):**
- **OpenRouter's default** identifies a conversation by hashing the first system/developer message plus the first non-system message; matching hashes route to the same provider. Overridable with an explicit `session_id` (request body or `x-session-id` header), falling back further to an OpenAI-style `prompt_cache_key` if neither is set.
- **sglang's `prefix_hash` policy** (`sgl-model-gateway/src/policies/prefix_hash.rs`) truncates each request to a configurable prefix (default 256 tokens, "~1 paragraph"), hashes it with xxhash, and looks up the destination via a **consistent-hash ring** — the most literal, working implementation of "consistent hashing on a cache-relevant prefix" found in this research, explicitly positioned as *"a lightweight alternative to the full radix tree cache_aware policy."*
- **AWS SageMaker's `PREFIX_AWARE`** inspects a configurable byte/char prefix length (1024–65536, tunable via `PrefixLength`) and consistently maps matching prefixes to the same instance, with the documented scale-stability property (only a small fraction of traffic remaps when the fleet resizes) that is consistent hashing's defining signature.

**Family B — stateful sticky-session/key affinity (store-then-recall, not a deterministic hash→node function):**
- **OpenRouter's `session_id` override** — when present, used directly as the sticky-routing key instead of the derived hash.
- **LiteLLM's `DeploymentAffinityCheck`** — a strict two-tier priority: (1) if `previous_response_id` is present, pin to the exact deployment that produced that prior response (highest priority); else (2) fall back to a TTL-cached (default 3600s) user-key→deployment mapping. Its own module docstring is explicit that the only hashing present (`_hash_user_key`, SHA-256) is applied to the API key purely to avoid storing raw keys in Redis — **not** a hash of prompt/prefix content, confirming this branch is genuinely ID-based sticky routing, not content-hash routing.
- **LiteLLM's `session_affinity` flag** additionally couples deployment stickiness to *model-tier* stickiness (pins both together so an escalated session can never de-escalate); a later fix decoupled this into an independent, default-on `deployment_affinity` flag specifically so per-turn tier classification and deployment stickiness could coexist — a real, shipped example of exactly the tension Kelvran would hit combining cache-affinity with its own cost-tier routing.

**The hybrid in between:** LiteLLM's older `PromptCachingDeploymentCheck` (Finding 1, item 1) uses a hash of the cacheable prefix only as a *lookup key* into a `{hash: model_id}` store — it is store-then-recall (like Family B) using a content fingerprint as the key (like Family A), not a deterministic hash-ring mapping. This is the closest real-world analog to Kelvran's own `CacheReadTokens`/`CacheCreationTokens`-aware scenario, since it keys off the literal cacheable content rather than a client-supplied session identifier — useful because Kelvran's own clients will not reliably supply a `session_id`.

**A necessary design constraint, not optional:** llm-d's own documentation names the failure mode any of the above risks without a load-balancing counterweight: *"using prefix-cache-scorer with max-score-picker causes hot-spotting[,] concurrent similar-prompt requests overload a single endpoint, while pairing it with weighted-random-picker avoids hot-spotting but dilutes cache affinity."* Every production system in this research avoids this by making affinity a **preference that expires or yields**, never an unconditional pin — TTL expiry (LiteLLM: 300s/3600s; OpenRouter: 10 min inactivity), or explicit overload escape valves (AWS SageMaker's `ConcurrencyThreshold`, see Finding 3).

**Build now / not yet:** not_yet as a standalone feature; see Finding 4. If/when built, the design should default to **Family A (content-hash keyed lookup, LiteLLM's hybrid pattern)** rather than requiring an explicit client-supplied session ID, since Kelvran cannot assume its clients will supply one — and must pair it with a TTL and a hot-spotting escape valve from day one, per this finding's constraint, not as a later hardening pass.

### Finding 3 — Every production implementation treats cache-affinity as a soft pre-filter that degrades to full failover, never a hard pin — directly answering how this interacts with Kelvran's existing fallback chains and health-probing (confidence: medium — underlying votes split 2-1 across all three constituent claims, though independently corroborated by real merged test code)

**LiteLLM's `DeploymentAffinityCheck`** has a merged, real test (`test_async_filter_deployments_falls_back_when_cached_deployment_is_unhealthy`) whose docstring states: *"If affinity cache points to a deployment that's no longer healthy, callback should return all healthy deployments so router can pick an available one."* The implementation mocks an affinity-pinned deployment absent from the current healthy set, calls `async_filter_deployments`, and asserts the **full healthy list** is returned unfiltered — i.e., the affinity check narrows candidates only when its pinned choice is actually present among the healthy set; otherwise it is a no-op that hands control back to normal routing/failover.

**AWS SageMaker's `PREFIX_AWARE`** applies the same yield-under-load principle in the orthogonal direction (overload, not unhealthy): a `ConcurrencyThreshold` (1–1024 in-flight requests) causes the router to deliberately route to a less-busy instance instead of the cache-affine one when the affine target is saturated — *"You might miss a cache hit on that one request, but you avoid overwhelming a single machine."*

**The generalizable pattern for Kelvran:** cache-affinity should sit as a pre-filter stage that runs *before* Kelvran's existing weighted-round-robin/health-selection logic, narrowing the candidate pool to the affinity-preferred deployment **only if** that deployment is currently in the healthy (and, per Finding 2's hot-spotting constraint, not-overloaded) set already produced by the existing health-probing layer — never bypassing or racing against it. This composes cleanly with Kelvran's already-shipped fallback chains without requiring any change to their error-classification or backoff logic; the affinity check simply changes which member of the *already-healthy* candidate set is tried first.

**Build now / not yet:** not_yet as a standalone feature (same gate as Finding 4); build_now as a **design constraint** to record now for whenever the feature is built — "soft pre-filter over the existing healthy set, never a hard pin" costs nothing to write down today and prevents a known, previously-hit-by-others failure mode (a stale/unhealthy affinity target blocking requests) from being reintroduced later.

### Finding 4 — Not yet buildable in good conscience; every real precedent was built in response to real production traffic Kelvran does not yet have, and two concrete, checkable prerequisites are missing (confidence: medium — this is a reasoned inference from Findings 1–3, not itself a separately sourced claim)

Every piece of real-world precedent surfaced in this research was built by a project that *already had* the production traffic exposing the problem, not preemptively: LiteLLM's original issue (#6784) was filed by a real user hitting the exact symptom; the deployment-affinity PR's author states *"I have this code running in prod for weeks and works fine"* as validation, not a design assumption; and the third LiteLLM fix (#36146) was itself only discovered as a gap *after* shipping a related feature (Auto Routing) and observing it in practice. Kelvran has no equivalent signal yet. Two concrete prerequisites — not vague "wait for more data" — gate build_now status:

1. **Confirm operators actually run ≥2 deployments of the same canonical model against the same upstream account/region** (the precondition for the whole problem to exist at all) rather than declaring the same endpoint twice purely for weight-shaping. Kelvran's own prior research (`docs/upgrade-research/gateway-provider-prompt-caching-2026-09-07.md`, Tier 2) already named this exact unresolved question for a closely related finding and did not resolve it — this report does not resolve it either; it remains open.
2. **Real traffic showing a `CacheCreationTokens`-to-`CacheReadTokens` ratio worse than expected specifically across deployments of the same canonical model**, isolating routing-induced cache misses from ordinary cold-start misses (a new conversation, a genuinely-changed prefix, or normal TTL expiry) — without this, there's no way to size whether the savings opportunity is real dollars or a theoretical curiosity, and no way to tell a routing-caused miss from an unavoidable one using data Kelvran does not yet collect in a distinguishable form.

**Build now / not yet: not_yet.** Named triggers to revisit: (a) an operator configures, or a support/GitHub issue reports, ≥2 deployments genuinely pointing at distinct upstream accounts/regions for the same canonical model — the same condition that triggered LiteLLM's original 2024 issue; or (b) once any production traffic exists, a dashboard pass over real `CacheCreationTokens`/`CacheReadTokens` data (already collected today, just not yet cross-referenced against deployment identity) shows a measurable, non-trivial creation-charge inflation attributable to routing rather than to genuine conversation cold-starts. This mirrors, rather than contradicts, the exact "instrument before building" deferral pattern Kelvran's own prior research has already and repeatedly established for the adjacent traffic-derived health/circuit-breaking work (`gateway-router-health-real-traffic-2026-09-09.md`) and for the closely related provider-prompt-caching schema gap (`gateway-provider-prompt-caching-2026-09-07.md`).

## Caveats

- **All 20 surviving claims are about precedent set by other systems (LiteLLM, OpenRouter, AWS SageMaker, sglang, llm-d) — none measure or even estimate Kelvran's own exposure to this problem.** Finding 4's not_yet call is a reasoned inference from that pattern, not itself independently sourced the way Findings 1–3 are.
- Several claims about **AWS SageMaker's `PREFIX_AWARE` routing** were checked and refuted (0-3 or 1-2 votes) when framed as directly proving Kelvran's exact problem is "already-solved" — the correct, surviving framing (used in Findings 1–3 above) is that SageMaker solves engine-side **KV-cache locality** for self-hosted inference, a related but distinct caching layer from the provider-side **billing/prompt cache** (Anthropic/OpenAI/Bedrock/Gemini-managed) that Kelvran's `CacheReadTokens`/`CacheCreationTokens` actually track. Treat SageMaker/llm-d/sglang evidence as strong *mechanism* precedent (the routing pattern transfers) but not as direct proof of the *billing-cache* problem specifically — only LiteLLM's and OpenRouter's evidence is about that exact caching layer.
- A related claim about **llm-d's Prefix Cache Affinity Filter being a clean pre-filter/no-op design pattern directly reusable for Kelvran** was refuted at 1-2 for over-claiming direct applicability; the surviving, narrower version of this evidence (used in Finding 2) is limited to the hot-spotting *risk* llm-d's own docs name, not an endorsement of its filter as a ready-made template.
- A claim asserting LiteLLM users had *already documented* Kelvran's exact scenario as a known community pain point was refuted (0-3) — the surviving evidence is that LiteLLM's own *maintainers* built and merged the fix (Finding 1), not that a broad community consensus about the problem's cost impact exists independent of LiteLLM's own engineering response.
- A claim about a dedicated `vllm-router` cache-aware radix-tree routing policy was refuted (0-3) — do not cite `vllm-router` as precedent; sglang's `prefix_hash`/`cache_aware` policies (Finding 2) are the verified self-hosted-inference-router precedent instead.
- Finding 3's three constituent claims (LiteLLM's fallback test, LiteLLM's stated cache-reuse motivation, AWS's concurrency-threshold overflow) each individually survived only a 2-1 vote — treat Finding 3 as directionally solid (independently corroborated by real, merged, inspectable code in LiteLLM's case) but not unanimous-consensus-strength.

## Open Questions

- Does any Kelvran operator today actually configure ≥2 deployments of the same canonical model against distinct upstream accounts/regions (the precondition for this problem to exist at all), or does Kelvran's `Deployment.CostTier` feature mean multi-deployment groups in practice are usually *different* models/tiers rather than replicas of the *same* model — in which case this entire problem class may not apply to Kelvran's actual configuration patterns regardless of traffic volume?
- If/when Kelvran does build this, should the affinity key be derived purely from request content (LiteLLM's hybrid pattern, no client cooperation needed) or should Kelvran also expose an explicit session/conversation-ID field in its own canonical schema (mirroring OpenRouter's `session_id`/`x-session-id` override) for clients who want a stronger guarantee than a hash-based heuristic can offer?
- How would cache-locality affinity interact with the already-shipped `Deployment.CostTier` cheapest-tier-first preference specifically — e.g., LiteLLM had to build a dedicated fix (`session_affinity` vs. `deployment_affinity` decoupling) after discovering tier-escalation and deployment-stickiness fought each other; does Kelvran's cost-tier logic have an analogous latent conflict waiting to surface once both features exist?
- Would Kelvran's own evals/regression-corpus traffic (synthetic but structured) be enough to approximate a "does this pattern happen and how often" signal before real production traffic exists, the way LiteLLM's and OpenRouter's real users provided that signal for them — or is synthetic traffic too different in shape (repeated benchmark prompts vs. organic conversational continuations) to be a trustworthy proxy here?
