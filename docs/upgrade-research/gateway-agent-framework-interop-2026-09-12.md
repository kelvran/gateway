# Kelvran Gateway — Agent-Orchestration-Framework Interop Requirements (2026-09-12)

**Date:** 2026-09-12
**Scope:** `gateway/internal/adapter` (canonical `ChatRequest`/`ChatResponse` shape, SSE streaming, tool-call support across all five adapters) and the framework-facing edge of the gateway (OpenAI-compatible `base_url` surface). This report does **not** re-litigate what's already shipped: the OpenAI-compatible request/response shape, SSE streaming, `kelvran.agent_run_id` propagation via W3C Baggage, per-virtual-key budget/rate-limit/concurrency enforcement, or tool-call support across all 5 adapters — all treated as ground truth. Instead it asks, for the first time, what real agent-orchestration frameworks (LangChain, LangGraph, CrewAI, AutoGen/AG2, OpenAI's Agents SDK, Anthropic's Claude Agent SDK) actually expect from a gateway sitting in front of them, and where third-party gateways/proxies (LiteLLM, OpenRouter, LangSmith's own gateway) have already hit real compatibility gaps.
**Method:** Adversarial multi-source research (3-vote verification per claim) against primary sources — framework source code (LangChain/langchain-openai, AutoGen, OpenAI Agents SDK), official API documentation (Anthropic, OpenAI, Google Gemini), and real GitHub issues/PRs showing reproduced failures. 15 claims survived; 10 were proposed and refuted, logged below for transparency. No claim in this pass touches Kelvran's own code — this is pure external-requirements research; every recommendation below is a candidate for Kelvran's canonical schema and adapter layer, not yet cross-checked against what Kelvran's adapters currently do.

---

## Executive summary

Agent frameworks calling through an OpenAI-compatible `base_url` are less forgiving than the base Chat Completions spec suggests: LangChain's `ChatOpenAI` deliberately drops any non-standard response field a gateway might add and silently disables streaming-usage auto-detection the moment a custom `base_url` is set, while OpenAI's own Agents SDK defaults to a fundamentally different, stateful Responses-API model that Kelvran's Chat-Completions-shaped `ChatRequest`/`ChatResponse` does not address at all. The real, hard-enforced multi-turn tool-call contract lives one level below any single provider's REST spec: Anthropic's API rejects (with a specific 400) any replayed assistant message that reorders, rebuilds, or strips `thinking`/`redacted_thinking` blocks relative to what it originally returned, and Gemini 3 enforces an equivalent `thoughtSignature` contract on `functionCall` parts — both are documented, reproducible failure modes that a normalizing gateway could inadvertently trigger by touching content it doesn't recognize. Third-party gateways already have real, live compatibility bugs distinct from calling providers directly — AutoGen crashes with an unhandled `TypeError` on OpenRouter's non-standard error shape, and a widely-used agentic follow-up pattern (a "reflection" call that omits `tools` while message history still contains prior `tool_use`/`tool_result` blocks) passes on OpenAI's own API but is rejected by other providers when proxied through OpenRouter — both are unresolved upstream as of this research date. No adopted standard for gateway capability discovery/negotiation (prompt caching, structured outputs, extended thinking) was found anywhere in this pass; that question remains open.

## Findings

### 1. LangChain's `ChatOpenAI` is deliberately scoped to the *official* OpenAI spec — it silently drops gateway-added fields and disables its own streaming-usage detection the moment a custom `base_url` is configured

**What the research found:** LangChain's `langchain_openai.chat_models.base` module docstring states plainly that `ChatOpenAI` targets official OpenAI API specifications only, and that non-standard response fields added by third-party providers (its own examples: `reasoning_content`, `reasoning_details`) are **not** extracted or preserved — verified directly against the pinned source and reconfirmed unchanged against the current `master` branch as of this research date. Separately, and mechanically distinct: `stream_usage` (LangChain's flag for parsing token-usage data out of the final SSE chunk) is auto-enabled only when `openai_api_base`/`base_url` and any custom HTTP client are all unset; the moment any of them is set — which is true for every Kelvran integration by definition — `stream_usage` silently falls back to `False` unless the caller explicitly re-enables it.

**Why it matters for Kelvran specifically:** this is a direct, evidence-backed answer to research question 1. Two consequences follow. First, any provider-specific extension field Kelvran's adapters might want to surface through the OpenAI-compatible shape (reasoning content, thinking summaries, cache-hit markers) will be silently invisible to any LangChain user on `ChatOpenAI` regardless of what Kelvran does — this is a LangChain-side ceiling, not a Kelvran defect, and no gateway-side workaround changes it (a LangChain user would need a provider-specific chat-model class, which doesn't exist for a generic gateway). Second, and more actionable: any LangChain user pointing at Kelvran's `base_url` will get **silently disabled** streaming-usage parsing unless they know to set `stream_usage=True` explicitly — this is a real, likely-to-recur support question ("why is `usage` missing from my streamed response?") that has nothing to do with whether Kelvran actually sends usage data in the final chunk.

**Confidence:** High (primary source: LangChain's own shipped docstrings and `validate_environment` logic, verified against a pinned commit and reconfirmed unchanged on the current branch; unanimous 3-0 on both sub-claims).

**Signal:** `build_now` — add a short, explicit note to Kelvran's integration docs for LangChain users: pass `stream_usage=True` on `ChatOpenAI` to get streamed token-usage data back, since the library disables this by default for any non-default `base_url`. This is a documentation fix, not a protocol change, and removes a predictable support burden at zero engineering cost.

### 2. Provider-specific `base_url` environment variables silently take precedence over a configured gateway routing variable — a documented multi-gateway interaction hazard Kelvran should anticipate in its own setup docs

**What the research found:** LangChain's own LLM Gateway documentation states explicitly that provider-specific base-URL environment variables (`OPENAI_API_BASE` in Python, `OPENAI_BASE_URL` in TypeScript) take precedence over LangSmith's own gateway-routing variable — so with the gateway enabled, setting `OPENAI_API_BASE` routes OpenAI calls to that URL directly while every other provider continues through the gateway. This precedence is codified in LangChain's actual source (`_gateway.py`: `base_url: explicit base_url > base_url_env > LangSmith gateway > default_base_url`) and enforced by unit tests, not just documentation.

**Why it matters for Kelvran specifically:** this is evidence of a real, general `base_url`-override interaction pattern, not a LangSmith-only quirk — any framework or SDK that reads a provider-specific `*_API_BASE`/`*_BASE_URL` environment variable independently of an explicit client constructor argument creates the same silent-partial-bypass risk for Kelvran. A user who sets Kelvran's `base_url` on their `ChatOpenAI` client constructor is safe, but a user who also has `OPENAI_API_BASE` set in their environment (common in multi-tool setups) could have OpenAI-specific calls silently skip Kelvran entirely while Anthropic/Gemini calls still route through it — a support/debugging trap ("why isn't OpenAI usage showing up in Kelvran's dashboard?") that has nothing to do with Kelvran's own correctness.

**Confidence:** High (primary LangChain docs, cross-checked against actual source code and unit tests; 3-0 vote). Scope caveat: directly confirmed for LangChain/LangSmith specifically; treated here as an illustrative instance of a general env-var-precedence hazard rather than a claim that every framework behaves identically.

**Signal:** `build_now` — document this precedence hazard explicitly in Kelvran's setup guide (e.g., "if you use LangChain and have `OPENAI_API_BASE` set anywhere in your environment, it will silently override Kelvran's `base_url` for OpenAI-routed calls specifically — unset it or use the client-constructor `base_url` argument instead").

### 3. OpenAI's own Agents SDK defaults to a stateful Responses-API model (`previous_response_id` + a durable Conversations object) that has no equivalent in the Chat-Completions shape Kelvran's adapter targets

**What the research found:** OpenAI's Responses API supports server-side conversation chaining via a `previous_response_id` parameter, plus a separate Conversations API that persists messages, tool calls, and tool outputs as a long-running object with its own durable identifier — a state model Chat Completions has no equivalent for (Chat Completions is fully stateless; the client resends the full message array every turn). Corroborating this beyond the API docs themselves: OpenAI's own Agents SDK python library defaults to `OpenAIResponsesModel` ("Recommended and default"), with `OpenAIChatCompletionsModel` offered only as an explicit, non-default alternative.

**Why it matters for Kelvran specifically:** this is a direct answer to research question 1's "do frameworks depend on provider-specific behavior a Chat-Completions-normalizing gateway doesn't offer" half — and the answer, for one of the six named frameworks, is yes, by default. A developer who installs OpenAI's Agents SDK and points its default configuration at Kelvran's `base_url` is implicitly assuming a Responses-API-shaped backend; Kelvran's Chat-Completions-only surface would not satisfy that default without the developer explicitly opting into `OpenAIChatCompletionsModel` first. This is not an urgent build item — it's a scope boundary Kelvran should be aware it has, and can choose to document rather than close.

**Confidence:** Medium (2-1 vote; the core factual claims — `previous_response_id`, the Conversations API's stored-item shape, and the Agents SDK's default model — were independently confirmed against live OpenAI docs and the Agents SDK's own docs page; the split vote reflects disagreement over how far the inferential "frameworks depend on this" conclusion should extend, not disagreement over the underlying facts).

**Signal:** `not_yet` — building a Responses-API-compatible surface is a real scope expansion with no demand signal yet. Trigger: a concrete user report of "the OpenAI Agents SDK doesn't work against Kelvran's `base_url` without extra configuration," or an explicit product decision to target OpenAI-Agents-SDK users as a named integration. Until then, document the limitation (Kelvran targets Chat-Completions-shaped clients; OpenAI Agents SDK users must explicitly select `OpenAIChatCompletionsModel`) so it's a known boundary, not a silent gap.

### 4. Anthropic's API enforces a strict, reproducible multi-turn replay contract for `thinking`/`redacted_thinking` blocks — reordering, rebuilding, or filtering them produces a hard 400, not a soft degradation, and real frameworks have hit this in production

**What the research found, synthesizing five closely related claims:** Anthropic's docs state the requirement in exact, mechanical terms: when a tool result is returned, the `thinking` blocks from the preceding assistant message must come back with it, complete and unmodified; rebuilding the message or filtering out `redacted_thinking` blocks triggers a documented 400 error. Separately, when extended/manual thinking is enabled and tool calls are present, the final assistant turn's content must *begin* with a `thinking`/`redacted_thinking` block before any `tool_use`/`tool_result` blocks — a requirement OpenAI's own Agents SDK originally violated, producing a literal, reproduced `BadRequestError` (`Expected thinking or redacted_thinking, but found text`) that was fixed in PR #openai-agents-python#1744 after two independent user bug reports (#765, #678). A third, independently-enforced ordering rule: every `tool_result` block must be preceded, in the immediately prior message, by its matching `tool_use` block — violating this produces a distinct, separately-reproduced Anthropic error (confirmed via `openai-agents-python#1797`). Finally, with interleaved thinking enabled, a single assistant turn can legitimately contain *multiple* separate `thinking` blocks interspersed between successive tool-call/tool-result exchanges, not just one block at the turn's start — so a canonical schema modeling "at most one reasoning block per turn" is already insufficient for Anthropic's current interleaved-thinking mode.

**Why it matters for Kelvran specifically:** this is the direct, most load-bearing answer to research question 2. The practical risk for Kelvran is specifically in the normalization boundary: if Kelvran's canonical `ChatResponse`/`ChatRequest` schema (or the adapter code that converts to/from it) ever filters an assistant message's content blocks down to "known" types (text, tool_use) when passing a message through — the exact failure mode that hit OpenAI's own Agents SDK — any multi-turn tool-call conversation with Anthropic thinking enabled that round-trips through Kelvran would 400. This applies regardless of whether Kelvran itself understands or uses the thinking content; it only needs to pass it through byte-for-byte, in the same position, when the same provider/model handles both turns of the exchange.

**Confidence:** High (Anthropic's own current, live API documentation for the core contract, cross-corroborated by a second Anthropic doc page and by independently-reproduced GitHub issues from real users; the PR fix and its two linked bug reports are primary, verified-merged sources; votes ranged 2-1 to 3-0 across the cluster, with all but one sub-claim unanimous).

**Signal:** `build_now` — audit Kelvran's Anthropic adapter and canonical schema conversion path specifically for whether it preserves unknown/opaque content-block types (particularly `thinking` and `redacted_thinking`) in their original position when converting a message to and from the canonical shape, rather than filtering to a fixed known-type allowlist. This is a concrete, scoped code-review action with a known failure signature (a specific Anthropic 400 error text) to test against, not a speculative hardening exercise.

### 5. A real OSS canonical/IR schema needed three new lossless fields — beyond any single provider's own spec — to survive Anthropic + Gemini 3 multi-turn round trips, and Gemini's signature field lives at the message-part level, not nested inside the tool call

**What the research found:** A merged PR in a real, active multi-agent framework repo (`open-multi-agent/open-multi-agent#205`, 756/756 tests passing) added three fields to its canonical intermediate representation specifically to survive provider round trips: `ReasoningBlock.signature` (Anthropic's `thinking.signature` and Gemini 3's `thoughtSignature`, required to echo back unchanged on Anthropic, recommended on Gemini), `ReasoningBlock.redactedData` (Anthropic's `redacted_thinking.data`, which must still be echoed on later turns even though its content is opaque/encrypted), and `ToolUseBlock.signature` (Gemini's `thoughtSignature` attached to `functionCall` parts, required by Gemini 3+ to continue tool calling — confirmed as a live, currently-enforced 400-erroring constraint via real, current issues in Google's own official `js-genai`/`python-genai` SDK repos). Independently verified against the actual current `@google/genai` npm package type definitions: `thoughtSignature` is declared as a sibling field directly on the `Part` interface, not nested inside the `FunctionCall` interface — so a schema that only models signature data as a property of the function-call payload itself (rather than of the enclosing message part) would structurally misplace or drop it.

**Why it matters for Kelvran specifically:** this is the most concrete, actionable answer to research question 2 — a real, independently-built framework converged on exactly three extra lossless fields to make multi-turn tool-call+reasoning state survive a round trip across two providers, and this is corroborated by both providers' own current official documentation warning about exactly this failure mode if the fields are dropped or filtered. For Kelvran's own canonical schema, this is a direct design input: any `ReasoningBlock`/thinking representation needs an opaque `signature` and (for Anthropic specifically) an opaque `redactedData` field that gets echoed back verbatim on later turns without inspection; and any `ToolUseBlock`/tool-call representation needs its own opaque `signature` field modeled as a sibling of the tool-call data (matching Gemini's `Part`-level placement), not nested inside it — getting this structural placement wrong is a concrete, documented way to silently drop the field during a schema conversion.

**Confidence:** High for the three-field requirement itself (3-0, corroborated independently by live Anthropic docs, live Gemini docs, and real current GitHub issues in Google's own SDKs going beyond the single cited PR). Medium for the specific structural detail of *where* in Google's schema the field lives (2-1; independently re-verified in this pass by downloading and inspecting the actual current `@google/genai` package type definitions directly, which confirms the structural claim, though the PR's own cited line number had already drifted from the current npm-latest version — a version-drift caveat on the citation, not on the underlying fact).

**Signal:** `build_now` — this is a concrete, scoped canonical-schema change candidate: add opaque `signature` and `redactedData` fields to Kelvran's reasoning/thinking representation and an opaque `signature` field to its tool-call representation (modeled at the message-part level, not nested inside the tool-call payload), populated and echoed verbatim without inspection. This directly de-risks Finding 4's failure mode for both Anthropic and Gemini simultaneously.

### 6. Third-party gateways already have real, reproducible compatibility bugs that don't occur when frameworks call providers directly — distinct from any single-provider spec gap

**What the research found, synthesizing two related claims:** AutoGen's OpenAI-compatible client (`autogen_ext.models.openai`) throws an unhandled Python `TypeError` — not a graceful, parsed error — when a third-party gateway (OpenRouter) returns a provider error nested inside a non-standard `model_extra` field with `choices=None`, instead of a normal `ChatCompletion` object; this is still live and unfixed in AutoGen's current `main` branch as of this research date, and was independently reproduced by multiple users including an AutoGen core maintainer, across both Claude and Gemini models routed through OpenRouter. The underlying trigger for the malformed response was itself a distinct, common agentic pattern: the conversation history contained prior `tool_use`/`tool_result` blocks, but AutoGen's follow-up "reflection" call omitted the `tools` field — behavior OpenAI's own API tolerates, but which the downstream provider (accessed via OpenRouter) rejected outright with `Requests which include tool_use or tool_result blocks must define tools`; OpenRouter surfaced that as a raw passthrough error buried in `model_extra` rather than translating it into a clean, top-level OpenAI-shaped error. An open PR (`#7402`, still pending as of March 2026, over a year after the original report) aims to fix this by keeping the same tool schemas available during the reflection pass.

**Why it matters for Kelvran specifically:** this is the direct answer to research question 3, and it surfaces two distinct, independently addressable gaps Kelvran should anticipate. First, an error-shape guarantee: whatever a downstream provider returns, Kelvran's own OpenAI-compatible response must never surface as an HTTP 200 with a null/malformed `choices` field and the real error buried in an extension field — this is exactly the shape that crashes AutoGen's client with an unhandled exception, and Kelvran, as the OpenAI-compatible-shape-emitting layer, is the one place positioned to prevent it regardless of what any individual downstream provider does. Second, a specific reproducible trigger pattern: a multi-turn agentic follow-up call with `tool_use`/`tool_result` history but no `tools` field is a real, documented agentic-framework behavior (not a hypothetical edge case) that some providers reject and others don't — Kelvran's adapters should have a clear, deliberate answer for what happens when a client sends this shape (reject with a clear error before forwarding, strip the tool-call history, or pass the provider's native rejection through cleanly), rather than an accidental behavior inherited from whichever adapter happens to handle it.

**Confidence:** High for the AutoGen crash mechanism and its still-live status (3-0, verified against AutoGen's actual current source plus multiple independently-reproducing bug reports). Medium for the "reflection call omits `tools`" root-cause framing specifically (2-1; the mechanism itself is confirmed via reproduced provider error text and corroborated by a still-open, mechanism-matching fix PR over a year later, but the split vote reflects some hesitation about generalizing from one provider's specific error message to the broader pattern).

**Signal:** `build_now` for the error-shape guarantee (verify/harden that Kelvran's adapters always return a proper OpenAI-shaped error object with a correct non-2xx HTTP status when a downstream provider errors, never a 200 with a null `choices` and the real error hidden elsewhere — a concrete, testable invariant). `not_yet` for building special-case handling of the "tool history without `tools` field" pattern specifically — needs a trigger: a real user report of this exact shape failing through Kelvran with a specific adapter/provider pair, since the right fix (reject early vs. strip history vs. pass through) depends on which provider and what the calling framework actually expects.

### 7. A separate third-party gateway (LiteLLM) shipped a real request-mangling bug from naively merging caller-supplied passthrough fields over its own already-normalized request — a directly analogous risk for Kelvran's own adapter code

**What the research found:** In LiteLLM's OpenRouter adapter, a client-supplied `extra_body` dict was merged over the gateway's own already-processed request via a plain `dict.update()` call (`response.update(extra_body)`) — confirmed directly against LiteLLM's live current source (`litellm/llms/openrouter/chat/transformation.py`). If a caller's `extra_body` happened to contain a stale or malformed `tools` key, that call would silently clobber the correctly normalized `tools` array LiteLLM had just built, with no warning. This is confirmed still present/unpatched in LiteLLM's current `main` branch as of this research date; both fix PRs for it are closed/unmerged and the tracking issue was auto-closed as "not planned" by a stale-bot, not resolved by a maintainer.

**Why it matters for Kelvran specifically:** this is a second, independent answer to research question 3 — a concrete bug class (naive last-write-wins merge of caller-supplied "extra"/passthrough parameters over a gateway's own normalized fields) that has already caused a real, shipped defect in a comparable production gateway. This is directly actionable as a Kelvran-internal code-review item: anywhere Kelvran's adapters accept a passthrough/extra-fields escape hatch (for provider-specific parameters the canonical schema doesn't model) and merge it over already-normalized request fields, the merge order and key-collision behavior should be deliberate (e.g., reject/ignore passthrough keys that collide with canonical fields like `tools`, rather than let them silently win).

**Confidence:** High (3-0; verified not just against the PR's own description but independently against LiteLLM's actual live current source code and both fix PRs' regression-test diffs, which reproduce the exact clobbering scenario).

**Signal:** `build_now` — audit Kelvran's own adapter code for any place accepting a caller-supplied passthrough/extra-parameters field, and confirm the merge behavior against canonical fields (especially `tools`) is deliberate, not a naive object-spread/`dict.update()`-style last-write-wins. This is a narrowly scoped, cheap code-review action directly motivated by a real, documented peer-gateway defect.

### 8. No adopted standard or convention for gateway capability discovery/negotiation was found anywhere in this research pass

**What the research found:** Despite explicitly researching this question, no claim addressing a real, adopted mechanism for an agent framework to discover or negotiate gateway-specific capabilities (prompt caching support, structured-output support, extended-thinking support, etc.) survived — none were even proposed and refuted; the search simply came back empty for this sub-question, in contrast to research questions 1–3 which each produced multiple verified findings.

**Why it matters for Kelvran specifically:** this is a genuine, honest gap rather than a soft negative. Research question 4 asked directly whether such a standard exists that Kelvran should expose; this pass cannot answer that question either way, and it would be a mistake to either (a) assume no such need exists, or (b) invent a bespoke capability-negotiation protocol speculatively without evidence any framework would consume it. The closest adjacent, verified pattern from this same research pass is implicit rather than a negotiation protocol: frameworks like LangChain's `ChatOpenAI` detect `base_url` presence itself as a signal to change default behavior (Finding 1's `stream_usage` auto-disable) — i.e., the one real "capability signal" found in this pass is a client-side heuristic based on configuration, not a gateway-exposed discovery endpoint.

**Confidence:** N/A — absent finding, not a positive claim with a confidence level.

**Signal:** `not_yet` — explicitly flagged as unresolved. Trigger to revisit: either (a) a concrete user/framework integration request that needs to know per-model capability support before making a call (e.g., a LangGraph or CrewAI user asking "how do I know if this Kelvran-routed model supports prompt caching before I try it"), or (b) an emerging real-world convention from a peer gateway or a framework itself that this pass didn't surface — worth a dedicated, narrower follow-up research pass specifically on this question before building anything speculative.

## Recommendation, mapped to the four research questions

1. **Do frameworks depend on provider-specific fields/headers/behaviors a normalizing gateway might break?** → Yes, in two concrete, documented ways: LangChain's `ChatOpenAI` silently disables streaming-usage auto-detection for any custom `base_url` (Finding 1 — `build_now`: document the `stream_usage=True` workaround), and OpenAI's own Agents SDK defaults to a stateful Responses-API model with no Chat-Completions equivalent (Finding 3 — `not_yet`: document the boundary, wait for real demand before building a Responses-API surface). Separately, `base_url`-override environment-variable precedence is a documented, generalizable multi-gateway interaction hazard worth calling out in Kelvran's own setup docs (Finding 2 — `build_now`, docs only).
2. **Is there a common multi-turn tool-call state pattern Kelvran's canonical schema needs beyond any single provider's spec?** → Yes, and it's concrete: Anthropic enforces a strict, reproducible replay contract for `thinking`/`redacted_thinking` blocks and tool-call ordering that a filtering/normalizing gateway can inadvertently violate (Finding 4 — `build_now`: audit the Anthropic adapter's content-block handling against this exact failure signature), and a real OSS framework's canonical schema needed three specific opaque fields (`ReasoningBlock.signature`, `ReasoningBlock.redactedData`, `ToolUseBlock.signature`, the latter modeled at the message-part level) to survive Anthropic+Gemini round trips (Finding 5 — `build_now`: concrete schema-field addition candidate).
3. **Do frameworks have documented third-party-gateway-specific compatibility gaps Kelvran should anticipate?** → Yes, two independent real bug classes: AutoGen crashes on OpenRouter's non-standard error response shape, driven by a common "reflection call omits `tools` with prior tool-call history" agentic pattern that some providers reject (Finding 6 — `build_now` for Kelvran's own error-shape guarantee; `not_yet` for special-casing the specific tools-omission pattern until a real report surfaces), and LiteLLM shipped a real, still-unpatched request-clobbering bug from naively merging caller passthrough fields over normalized request fields (Finding 7 — `build_now`: audit Kelvran's own passthrough-merge behavior).
4. **Is there an adopted capability-discovery/negotiation standard Kelvran should expose?** → No evidence found either way (Finding 8 — `not_yet`, genuinely unresolved). Needs either a concrete integration request or a dedicated, narrower follow-up pass before building anything.

**Overall:** this pass's most actionable output is not a new feature but a short, concrete audit list against Kelvran's *existing* adapter and canonical-schema code: (a) confirm unknown/opaque content-block types survive a round trip through the Anthropic adapter's normalization path unfiltered (Finding 4), (b) add opaque `signature`/`redactedData` fields to the canonical reasoning/tool-call representation, with the tool-call signature modeled at the message-part level (Finding 5), (c) confirm error responses from any downstream provider always surface as a proper OpenAI-shaped error object with a correct status code, never a 200 with a malformed body (Finding 6), and (d) confirm any passthrough/extra-parameters escape hatch in Kelvran's adapters doesn't naively clobber normalized fields like `tools` (Finding 7). Two documentation-only items (Findings 1 and 2) close out predictable LangChain-specific support questions at effectively zero engineering cost. Two items remain deliberately deferred pending real signal: a Responses-API-compatible surface for OpenAI Agents SDK users (Finding 3), and any form of capability discovery/negotiation (Finding 8).

## Caveats

- **Several claims in this pass had split 2-1 votes** (Findings 3, 5's structural sub-claim, 6's root-cause framing) rather than unanimous 3-0 — these should be read as "the core mechanism is confirmed, but the inferential reach of the claim was debated," not as weak evidence. Each is called out individually above.
- **Anthropic's thinking-block contract (Finding 4) is scoped to manual/extended thinking mode specifically.** Anthropic's own current docs note that its newer "adaptive thinking" mode (rolled out on newer models) drops the "final assistant turn must begin with a thinking block" requirement — the underlying signature/redacted-data echo-back contract (Finding 5) appears unchanged across both modes based on current docs, but Kelvran should track which thinking mode is in play per-model rather than assuming one fixed rule applies everywhere.
- **A meaningful number of plausible-sounding claims were proposed in this pass and did not survive verification** (10 of 25 total): the depth of LangSmith's own gateway translation for tool-call state, the specific internal storage mechanism the OpenAI Agents SDK PR used to fix its thinking-block bug, a claimed ordering bug in the Agents SDK's own history serializer, a claimed 400 error from routing Anthropic-via-OpenRouter through `ChatOpenAI`, a claimed structured-output incompatibility with OpenRouter, a claimed centralized reasoning-field-normalization PR in LangChain, a claim that AutoGen's OpenRouter bug is isolated from direct-provider calls, a claimed type-mismatch bug in LangChain's streaming-delta parser, and a claimed GPT-5.4-specific LiteLLM/OpenRouter tools bug. These are logged for transparency (see the source material) but should not be treated as either confirmed or as reliable signal that the underlying systems are gap-free — absence of surviving evidence is not evidence of absence.
- **This is a fast-moving area.** Gemini 3's `thoughtSignature` requirement, Anthropic's adaptive-vs-manual thinking split, and OpenAI's Agents SDK default-model choice are all recent (2025–2026) and could shift with the next SDK/model release. Treat this report's findings as needing re-validation before any Finding-5-derived schema change ships, not as a permanently settled target.

## Open questions

1. **Does Kelvran's Anthropic adapter currently preserve unknown/opaque content-block types (`thinking`, `redacted_thinking`, and any future block type) unfiltered through its canonical-schema conversion, or does it filter to a known-type allowlist?** This is a direct code-audit question this research pass could not answer (it researched external requirements only) but that Finding 4's `build_now` signal depends on.
2. **What should Kelvran's adapters do when a client's follow-up request omits `tools` but message history contains prior `tool_use`/`tool_result` blocks, given providers disagree on whether this is valid?** Finding 6 flags this as a real, recurring agentic-framework pattern but deliberately does not prescribe a fix pending a concrete failure report.
3. **Is there real, current demand from Kelvran's actual or prospective users for an OpenAI-Agents-SDK-compatible (Responses API) surface, or do all realistic framework integrations (LangChain, LangGraph, CrewAI, AutoGen) stay within the Chat-Completions shape Kelvran already targets?** Finding 3 identifies the gap but has no evidence either way on actual demand.
4. **Should Kelvran define its own capability-discovery convention (e.g., a per-model capabilities endpoint) proactively, or wait for either a concrete integration request or an external convention to emerge?** Finding 8 found no existing standard to align with either way.
