# Kelvran Gateway — 2026 Upgrade Research & Prioritized Roadmap

**Date:** 2026-09-06
**Scope:** `gateway/` — the Go LLM proxy/router (routing, adapters, rate limiting/budgets, guardrails, telemetry, admin API). Excludes the embedded Cache and the separate Python `evals` service — see the sibling reports in this directory.
**Method:** Adversarial multi-source research (3-vote verification per claim) against real, currently-shipping 2026 gateway practice: Kong AI Gateway, Envoy AI Gateway, LiteLLM, plus Go stdlib docs and OWASP standards. 109 sub-agent calls, 26 sources fetched, 112 claims extracted, 25 put to adversarial vote, 22 confirmed, 3 refuted, 10 survived synthesis. Full per-claim evidence and vote counts are preserved in this session's workflow journal; this document adds the Kelvran-specific "why it matters here / is this consistent with `PRD.md`'s own scope-outs / effort tier" layer the raw adversarial verification deliberately does not do.

---

## Executive summary

The research converges on three concrete, low-ambiguity findings and one important nuance to Kelvran's own stated deferral. First: Kelvran's "wait for real production traffic before building circuit-breaker routing" deferral is **half right, not fully right** — Kong, Envoy, and LiteLLM all confirm that *active/synthetic* health-probing (a background loop that pings deployments itself) is a traffic-independent mechanism real gateways ship today, while only the *statistical/passive* circuit-breaker class (Envoy's Success-Rate/Failure-Percentage outlier detection, LiteLLM's `allowed_fails` traffic-derived cooldown) genuinely requires a traffic-volume floor to mean anything. Kelvran's deferral is correct for the second class and unnecessarily conservative for the first. Second: the newly-discovered, currently-open request-body-size gap from the multi-modal-content work has a specific, low-effort, standards-documented fix (`http.MaxBytesReader`, not a generic `io.LimitReader`) plus a second, distinct control worth adding at the same time (client-declared MIME type on inline-base64 `Parts` cannot be trusted per OWASP's File Upload guidance — magic-byte/signature validation is the real control). Third: Kelvran's OTel Metrics surface (exactly one counter, added days ago) falls well short of the OTel GenAI semantic-conventions instruments that Envoy AI Gateway already ships with a ready-made Grafana dashboard — and these instruments map directly onto Kelvran's own stated cost/governance-accountability differentiation thesis, not onto breadth-for-breadth's-sake.

A fourth cluster of findings (Kong's cost-based rate limiting, LiteLLM's error-type-specific and multi-hop fallback chains, Envoy's pre-completion token-counting APIs) is real and valuable but more involved — one item within it (provider-side pre-completion token counting) is flagged below as a genuinely high-value follow-on because it directly unblocks a design alternative this project's own TPM rate-limit RFC explicitly rejected for lack of a tokenizer. Coverage is uneven: of the seven competitors named in the research brief, only Kong, Envoy AI Gateway, and LiteLLM produced surviving claims — Portkey, TensorZero, Bifrost, and Helicone, plus the entire provider-side-prompt-caching question, returned no verified evidence and remain genuinely open, not answered "no."

## Findings, ranked

### 1. Request body-size limit + MIME-type validation for multi-modal content (Small)

**What:** `chatCompletionsHandler`'s `io.ReadAll(r.Body)` has no size limit anywhere in this codebase — already identified as a real, open gap while shipping multi-modal content (`docs/rfcs/2026-09-06-gateway-multimodal-content.md`, `THREAT_MODEL.md`'s DoS row). This research confirms the concrete fix and adds one more control worth bundling into the same change.

**Why it matters for Kelvran specifically:** this is the single most actionable, lowest-risk item in this report — it closes an already-named, already-tracked gap, not a speculative new one, and multi-modal payloads (inline base64 images/documents, naturally tens of MB) make the existing gap dramatically more exploitable than it was for text-only prompts.

**Consistent with settled decisions?** Directly closes the adjacent finding named in `THREAT_MODEL.md`'s Gateway DoS row and `docs/rfcs/2026-09-06-gateway-multimodal-content.md`'s own "genuinely new, adjacent finding" section. No PRD.md scope-out touched.

**2026 best practice grounding:**
- Go's own `http.MaxBytesReader` (stdlib, added a typed `*MaxBytesError` in Go 1.19) is the purpose-built mechanism for this — distinct from a generic `io.LimitReader`, it also cascades `Close()` to the underlying reader and is explicitly documented as existing "for limiting the size of incoming request bodies" to prevent resource exhaustion [pkg.go.dev/net/http — confirmed 3-0].
- OWASP API4:2023 (Unrestricted Resource Consumption) mandates enforcing a maximum size on **all** incoming payloads and parameters — not just uploaded files, and explicitly including string length and array counts [owasp.org — confirmed 3-0].
- Separately: a client-declared `Content-Type`/MIME-type field "cannot be trusted... it is trivial to spoof" and "should not be relied upon for security" per OWASP's File Upload Cheat Sheet, which recommends magic-byte/file-signature validation as the real control [OWASP — confirmed 3-0]. This is directly analogous to Kelvran's new `ContentPart.MediaType` field (client-supplied, currently trusted verbatim) — a distinct, second control from the body-size cap, worth adding in the same pass since both concern the same new attack surface.

**Concrete next step:** wrap the request body read in `http.MaxBytesReader(w, r.Body, <limit>)` (a sensible starting limit — e.g. 25-50MB, large enough for a real multi-modal request, small enough to bound worst-case memory) and add a lightweight magic-byte check (or at minimum, a declared-vs-detected MIME-type mismatch warning) for inline `Parts[].Data`.

**Effort:** Small — a stdlib wrapper at the one HTTP-body-read call site, plus an optional, bounded magic-byte check for `ContentPart.Data`.

### 2. Active/synthetic health-probing for routing — ship now; the traffic-derived circuit breaker correctly stays deferred (Medium)

**What:** Kelvran's router (`internal/router`) has exactly one fallback attempt on error, no health/cooldown tracking at all. The prior backlog framing treated "circuit-breaker routing" as one deferred item, blocked on production traffic. This research shows that framing conflates two genuinely different mechanisms with different traffic preconditions.

**Why it matters for Kelvran specifically:** this directly revises (narrows, not overturns) a real, previously-made deferral decision — it says the deferral was right for the harder half of the problem and unnecessarily conservative for the easier half.

**Consistent with settled decisions?** Partially revisits — with new evidence, not just re-litigating — `gateway/ARCHITECTURE.md`'s router section ("Still not built, deliberately: usage/latency/cost-based selection signals, consecutive-failure/cooldown circuit-breaker tracking... none of these are named in PRD.md's v1 allowlist"). This finding does not argue for building the traffic-derived, statistical half now — only the traffic-independent, active-probing half.

**2026 best practice grounding:**
- Kong explicitly distinguishes active checks (synthetic HTTP/HTTPS/TCP probes Kong itself issues on a timer, independently of real traffic) from passive checks (derived from real proxied traffic) — only active checks can automatically re-enable a target [developer.konghq.com — confirmed 3-0, with a 2-1 sub-claim on independence still rated high-confidence].
- Envoy documents active health checking as a separate, complementary mechanism to passive outlier detection, explicitly recommending both together for a comprehensive solution — active checking itself carries no traffic-volume precondition [envoyproxy.io — confirmed, with a 2-1 sub-vote].
- LiteLLM's `GET /health` runs a real synthetic test request against every configured model and supports `background_health_checks` on a configurable timer (default 300s), fully decoupled from production request volume. LiteLLM further ships a **distinct, currently-shipping "Health Check Driven Routing" feature** that removes a deployment from the routing pool purely on synthetic-probe failure — as aggressive as a single failed probe by default, unless an `allowed_fails_policy` is configured [docs.litellm.ai — confirmed 3-0 on both].
- By contrast, Envoy's own docs confirm its *statistical* passive detectors (Success Rate / Failure Percentage outlier detection) will not activate below a configured request-volume floor — this is the one class of health signal for which "wait for real traffic" is technically correct, not health-checking as a whole [envoyproxy.io — confirmed 3-0]. LiteLLM's traffic-derived `allowed_fails`-based cooldown is the same category.

**Concrete next step:** add a background synthetic-probe loop (a lightweight periodic request per configured deployment, on a timer, with a small cached-result window) that can remove a deployment from `router.Router`'s selection pool — deliberately *not* the statistical/passive failure-counting class, which should stay deferred exactly as `gateway/ARCHITECTURE.md` already says.

**Effort:** Medium — a new background goroutine/ticker, a per-deployment health-state cache, and a `router.Router.Select` change to skip unhealthy deployments. No new external dependency needed.

### 3. OTel Metrics: add the GenAI semantic-convention token-usage and operation-duration histograms (Medium)

**What:** Kelvran's OTel Metrics surface, added 2026-09-05, has exactly one counter (`kelvran.ratelimit.fail_open`). No latency histogram, no token-usage histogram, no request-count metric exists.

**Why it matters for Kelvran specifically:** this maps directly onto `PRD.md`'s own stated differentiation thesis — "cost savings attributable and explainable down to the individual agent run" and agent-run-level cost/governance accountability are observability claims, and Kelvran currently has almost no aggregate metrics to back them beyond the one rate-limit counter and the per-request OTel span attributes.

**Consistent with settled decisions?** Additive to, not a revisit of, `docs/rfcs/2026-09-05-gateway-ratelimit-fail-open-metric.md` (the RFC that stood up the OTel Metrics pipeline in the first place, explicitly naming this as the *first* metric, not the only one).

**2026 best practice grounding:**
- The canonical OTel GenAI semantic-conventions spec (fetched live) defines `gen_ai.client.token.usage` (Histogram, unit `{token}`, Recommended, with a required `gen_ai.token.type` attribute distinguishing input/output) and `gen_ai.client.operation.duration` (Histogram, unit `s`, Recommended, with a conditionally-required `error.type` attribute on failure) [github.com/open-telemetry/semantic-conventions-genai — confirmed 3-0].
- Envoy AI Gateway v1.1 already ships both of these plus two latency variants (time-to-first-token, time-per-output-token) and a ready-made Grafana dashboard JSON file as concrete precedent [aigateway.envoyproxy.io — confirmed, dashboard/tracing framing 2-1 but high-confidence].
- **Caveat worth weighing before committing**: `gen_ai.client.token.usage`'s spec stability badge is explicitly "Development," not "Stable," as of this research — a real consideration if Kelvran wants to treat this as a long-term public contract rather than an internal-only metric name that might still rename before the spec stabilizes.

**Concrete next step:** add `gen_ai.client.token.usage` and `gen_ai.client.operation.duration` as new instruments in `internal/telemetry`, recorded from the same `finalize` call site that already computes cost/usage — reusing the existing per-request data, not a new capture point.

**Effort:** Medium — two new histogram instruments plus wiring at the existing `finalize` call site; no new dependency (same OTel Metrics SDK already stood up for the fail-open counter).

### 4. Pre-completion token counting — a real path to unblock the TPM RFC's own rejected alternative (Large, high-value follow-on)

**What:** Envoy AI Gateway v1.1 ships pre-completion token-counting APIs across many providers (vLLM, Vertex Gemini, GCP Anthropic, Bedrock Converse, AWS Anthropic, Anthropic's native `count_tokens`, OpenAI/Azure OpenAI's `input_tokens` endpoint) — letting a caller estimate token cost *before* generating a completion.

**Why it matters for Kelvran specifically — this is the most consequential finding in this report:** `docs/rfcs/2026-09-05-gateway-tpm-rate-limit.md` explicitly rejected a "pre-call reserve+reconcile" design (estimate cost before the call, reserve it, refund the delta after) specifically because "no tokenizer/estimator exists anywhere in this codebase" — and shipped a retrospective-only, always-one-request-behind TPM dimension instead, naming the tokenizer gap as the reason. Provider-supplied token-counting **endpoints** (not a locally-built tokenizer Kelvran would have to maintain per-provider) are a real, externally-verified way to close exactly that gap without Kelvran building or vendoring a tokenizer at all.

**Consistent with settled decisions?** Directly revisits — with new, concrete evidence — the TPM RFC's own named Alternative Considered and its stated reason for rejection. This is not free: it would mean an extra upstream call (or reuse of a provider's own pre-call estimate) before the real completion call, a real latency/complexity tradeoff the original RFC didn't have available to weigh.

**2026 best practice grounding:** confirmed verbatim against Envoy's v1.1 release notes and independently cross-checked against the official GitHub release page — the feature counts tokens for a prompt without generating a completion, across the named providers/endpoints [aigateway.envoyproxy.io — confirmed 3-0].

**Concrete next step (not urgent — a follow-on RFC, not an immediate build):** a dedicated research/design pass on whether provider-side token-counting endpoints are fast/cheap enough (latency, and whether they count against rate limits themselves) to make pre-call TPM reservation viable for Kelvran's 5 adapters, given each provider's own endpoint has a different shape and availability.

**Effort:** Large — touches all 5 adapters, needs its own RFC, and the original TPM RFC's retrospective-debit design remains real and working in the meantime. Not urgent, but worth tracking explicitly rather than letting the original rejection reason go stale now that it may no longer be fully accurate.

### 5. Richer routing/cost governance primitives from Kong and LiteLLM (Medium, cluster of smaller items)

**What:** Three related but independent gaps, all real:
- **Kong's cost-based rate limiting**: retrospective, post-response, computed from the provider's own returned token counts and per-model prices — `(prompt_tokens × input_cost + completion_tokens × output_cost) / 1,000,000` — plus multi-dimensional rate-limit matching (consumer × model, provider, header, path, with AND logic) [developer.konghq.com — confirmed 3-0]. **Nuance**: Kelvran's `internal/budget.Tracker` already does something conceptually similar (real Decimal-precision cost tracking against a per-key USD cap, from real provider usage) — the genuinely missing piece is the *multi-dimensional matching* (per-model, not just per-key), not the cost-computation idea itself, which Kelvran already has in a different form.
- **LiteLLM's error-type-specific fallback chains**: separate, coexisting fallback lists for content-policy violations, context-window-exceeded errors, and generic errors (rate limits, etc.), plus in-order multi-hop chains (more than one fallback attempt) and a deployment-ID-specific fallback that explicitly bypasses the normal cooldown check [docs.litellm.ai — confirmed 3-0, cross-checked against source]. Kelvran currently has exactly one undifferentiated fallback attempt regardless of error type.

**Why it matters for Kelvran specifically:** the fallback-chain gap is the more clear-cut one — a context-window-exceeded error and a rate-limit error arguably warrant genuinely different fallback targets (e.g., a larger-context model vs. any available capacity), and Kelvran's router has no way to express that distinction today.

**Consistent with settled decisions?** The multi-hop/error-type fallback chain is a bounded extension of the existing "single fallback chain" v1 scope line in `PRD.md`, not a reopening of it. Multi-dimensional rate-limit matching would be a real, new capability, not currently scoped anywhere.

**Effort:** Medium for error-type-specific + multi-hop fallback chains (a router/dataplane change, bounded); Medium-Large for multi-dimensional rate-limit matching (touches `internal/ratelimit`'s key shape).

### 6. Provider-side prompt caching vs. Kelvran's own cache — genuinely unresolved, not a "no" (Unscoped — needs its own research pass)

**What the research was asked to find:** whether Anthropic's prompt caching or Bedrock's `cachePoint` are complementary to or redundant with Kelvran's own multi-layer cache.

**What the research found:** nothing — zero claims on this sub-question survived adversarial verification. This is an absence of evidence, not evidence of absence.

**Why this matters for Kelvran specifically:** this is a real, still-open question the research brief asked directly and could not answer — recommend a dedicated, narrower follow-up pass rather than guessing. The a priori reasoning (provider-side prompt caching discounts *repeated prefix tokens within a single provider's own pricing*, whereas Kelvran's cache avoids the upstream call *entirely*) suggests they are likely complementary, not redundant — but this is an inference, not a verified finding, and should be labeled as such if repeated.

**Effort:** N/A — needs its own research pass before any implementation decision.

## Top 3 do next

1. **Add the request body-size limit + MIME-type-mismatch check** (Small). Closes an already-tracked, currently-open security gap with a specific stdlib mechanism (`http.MaxBytesReader`) — zero design risk, directly actionable today.

2. **Ship active/synthetic health-probing for routing** (Medium). This is not a reopening of the router deferral — it's a correction to an overly-broad framing of it. The statistical/traffic-derived circuit breaker correctly stays deferred; the traffic-independent active-probe loop does not need to wait for production data, per Kong/Envoy/LiteLLM's own concrete, currently-shipping precedent.

3. **Add `gen_ai.client.token.usage`/`gen_ai.client.operation.duration` OTel Metrics instruments** (Medium). Directly serves `PRD.md`'s own cost/governance-accountability differentiation thesis with concrete, spec-backed instrument names and a real competitor's (Envoy) ready-made dashboard to model against — not observability for its own sake.

**Worth tracking explicitly, not immediately building:** the pre-completion token-counting finding (item 4) is the most consequential single discovery in this report — it's a real, externally-verified way to unblock the TPM RFC's own previously-rejected pre-call design — but it's Large effort and deserves its own RFC, not a rushed addition here.

## Caveats

- Of the seven competitors named in the original research brief (LiteLLM, Portkey, TensorZero, Bifrost, Kong AI Gateway, Envoy AI Gateway, Helicone), surviving verified claims exist only for **Kong, Envoy AI Gateway, and LiteLLM**. Portkey, TensorZero, Bifrost, and Helicone produced zero surviving claims and remain genuinely unanswered, not answered "no."
- Two claims rest on split 2-1 votes rather than unanimous 3-0 (Kong's active-probe traffic-independence claim; Envoy's dashboard/tracing-as-self-observability framing) — both still rated high-confidence on direct primary-source grounds, flagged here for transparency.
- Three claims were explicitly refuted during adversarial verification: (a) an OWASP "batched-upload-bypasses-per-request-limits" analogy specifically framed around GraphQL array mutations (voted 1-2 — the underlying body-size-cap need in Finding 1 stands on its own independent evidence regardless); (b) a near-duplicate wording of Envoy's active-health-checking-needs-no-traffic claim (voted 1-2, superseded by the higher-confidence phrasing in Finding 2); (c) a claim that LiteLLM's cooldown is derived *only* from traffic data (voted 0-3 — correctly refuted, since LiteLLM has both a traffic-derived cooldown AND a separate synthetic-probe mechanism, per Finding 2).
- Time-sensitivity: Envoy AI Gateway's v1.1 release (metrics/dashboard/token-counting) dates to August 2025 — about a year old relative to this research date. Kong's policy-based rate limiting shipped 2026-04-07 with patches through 2026-07-29. Both are additive feature sets unlikely to have been reversed, but neither is brand-new.
- `gen_ai.client.token.usage`'s OTel spec maturity is explicitly "Development," not "Stable" — worth weighing before treating it as a long-term public metric name.
- This document's "why it matters for Kelvran" / "consistent with settled decisions" / effort-tier framing was authored by synthesizing the raw adversarially-verified claims (which do not themselves make Kelvran-specific judgment calls) — the underlying evidence quality is as described per-finding above; the prioritization judgment is a layer added on top, same as the sibling evals report's own stated convention.

## Open questions

- Does provider-side prompt caching complement or duplicate Kelvran's own multi-layer cache (Finding 6)? Needs dedicated re-research — zero claims survived on this despite being explicitly asked.
- What do Portkey, TensorZero, Bifrost, and Helicone specifically ship for cost/governance accountability that Kong/Envoy/LiteLLM don't already cover? None of the surviving claims touched these four competitors at all, despite being named explicitly in the brief.
- Given LiteLLM's default health-check-driven routing excludes a deployment after a single synthetic-probe failure, what failure threshold/quorum should Kelvran's own active-probing implementation (item 2) default to — LiteLLM's aggressive single-failure behavior, or something more conservative given Kelvran has no production experience yet to calibrate against?
- Is it worth committing to the OTel GenAI metrics instruments now given `gen_ai.client.token.usage`'s "Development" (not "Stable") spec maturity, or should Kelvran wait for the spec to stabilize before treating these as a long-term public contract rather than an internal-only metric?
- Are provider-side token-counting endpoints (item 4) fast/cheap enough in practice to make pre-call TPM reservation viable, given each of Kelvran's 5 adapters would need its own integration with a differently-shaped endpoint?
