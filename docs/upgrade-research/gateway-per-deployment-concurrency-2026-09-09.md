# Per-Deployment Concurrency/Rate Ceilings — Deep Research (2026-09-09)

## Question

Kelvran's every existing rate-limit and concurrency control (`gateway/internal/ratelimit`'s `KeyLimiter` RPM/TPM, and `ConcurrencyLimiter`'s in-flight cap) is scoped exclusively to the calling virtual key, never to the shared upstream deployment those keys route through. What's the right design for a per-deployment (per-upstream-backend) concurrency/rate ceiling — enforced independently of, and on top of, per-caller limits? What's the right mental model (circuit breaker, queueing/backpressure, something else), what should happen when the cap is hit (reject distinctly vs. silently reroute), and does this need a new mechanism or can it reuse `ConcurrencyLimiter`'s existing shape?

## Context (Kelvran's own real, current state)

`gateway/internal/ratelimit/limiter.go`'s `KeyLimiter` (RPM/TPM, optionally × model) and `gateway/internal/ratelimit/concurrency.go`'s `ConcurrencyLimiter` (in-flight cap) are both keyed *exclusively* by virtual-key ID — confirmed directly: `ConcurrencyLimiter.Acquire`/`Release`/`Register` all take a bare `keyID string`, `checkConcurrency`/`releaseConcurrency` in `dataplane.go` call them with `vk.ID`, never a deployment identifier. `ConcurrencyLimiter`'s own doc comment already names two real, self-acknowledged v1 scope limits worth carrying into any deployment-scoped extension: it is deliberately scoped to virtual-key ID only (never the unverified, client-supplied `agent_run_id`), and "has no timeout or leak-detection mechanism; an Acquire without a matching Release permanently consumes one slot," with no distributed (multi-instance) counterpart.

`docs/agents/LOGS.md` (2026-09-08) names the exact gap this research addresses as new, not previously documented in either package's own doc comments: "Zero per-deployment rate-limit/concurrency-cap construct exists anywhere ... A Slack-2021-style convergence of many *different* virtual keys onto one fallback-target deployment is bounded only by each key's own independent limits, with nothing capping that deployment's own aggregate load." This matters concretely because Kelvran already ships multi-hop, error-classified fallback chains (`gateway/internal/gateway/dataplane/fallback.go`'s `attemptFallbackChain`, per `docs/rfcs/2026-09-07-gateway-error-classified-fallback-chains.md`): many independently-configured virtual keys, each comfortably under their own RPM/TPM/concurrency caps, can each independently decide — on a provider outage, a content-policy rejection, or a context-window error — to fall back onto the exact same shared `DeploymentConfig.Name`-identified deployment, with nothing today capping that deployment's own aggregate in-flight or per-minute load. Deployment identity is already a single, stable string used consistently across the codebase (`router.IsHealthy(name)`, `p.deploymentsByName`, `DeploymentConfig.Name`), which matters for how cheaply a deployment-scoped limiter can key off the same identifier every other deployment-aware mechanism already uses.

## Summary

Every production system studied — LiteLLM, Envoy, Kong, Stripe, and Google's own SRE book — independently converges on the same two-part answer: a deployment/backend-scoped ceiling belongs *alongside*, never merged into, per-caller limits, and it needs **two different mechanisms, not one**, because a shared backend's real constraint is usually throughput (RPM/TPM) as much as raw concurrency. Envoy's circuit breakers (per-cluster/per-priority, fail-fast, distinct stat counters, no silent reroute) are the cleanest architectural analog to "cap the shared backend independent of caller identity," and Stripe's own production architecture — a bare in-flight-count "Concurrent Requests Limiter" kept as a genuinely separate control from its per-second rate limiter — is the strongest direct precedent that Kelvran's `ConcurrencyLimiter` (a bare in-flight cap) and `KeyLimiter` (RPM/TPM) should each get a deployment-scoped sibling instance rather than being redesigned into one merged mechanism. AWS's 2015 DynamoDB US-East disruption, not Slack's 2021 outage, is the well-documented real-world precedent that actually matches Kelvran's named worry (many independent callers converging on one under-provisioned shared backend, fixed only by an explicit load-shed/pause action) — Slack 2021 turns out to be a materially different failure (Slack's own autoscaler overwhelming an internal provisioning service), and a specific claim attributing that outage to raw AWS network-capacity limits was checked and did not hold up either. On the reject-vs-reroute question, HTTP semantics (503 vs. 429) and Kong's own upstream-health design both support rejecting distinctly from a per-key rate-limit error, and Kelvran's own already-shipped fallback-chain machinery is the natural place to let a deployment-capacity rejection fall through to the next configured hop rather than failing the whole request outright.

## Findings

### Finding 1 — LiteLLM proves the "deployment-scoped ceiling shared dynamically across many callers, on top of per-caller limits" model is real, shipped production behavior, and its enforcement mechanism is a usage-ratio, not a bare in-flight count (confidence: high)

LiteLLM's Dynamic TPM/RPM Allocation feature (`docs/proxy/dynamic_rate_limit`, corroborated directly against its source, `dynamic_rate_limiter.py`) tracks a per-model/per-deployment capacity pool shared across whichever virtual keys/teams are currently calling that model — a base "Quick Start" tier is a simple shared model-wide TPM/RPM counter that 429s every key once the pool is exhausted regardless of any individual key's own limits, with a more granular Beta/Enterprise priority-reservation mode reserving fixed percentage floors per tier once a **saturation ratio** — `max(current_rpm/max_rpm, current_tpm/max_tpm)` against the deployment's configured max, explicitly *not* a count of active connections or keys — crosses a configurable threshold. Separately, LiteLLM's Router ships a plainer, non-dynamic version of the same idea: each deployment entry carries its own static `rpm` value under `litellm_params`, and with `enable_pre_call_checks: true` the Router enforces the *sum* of per-deployment caps as the aggregate ceiling regardless of how much load callers actually send — the docs' own worked example sends 600 requests/minute against two 100-rpm deployments (200/min aggregate) and explicitly expects only 200/min to succeed, the rest rejected. Both mechanisms are real, current, shipped features, not aspirational docs.

### Finding 2 — Envoy's circuit breakers are the cleanest architectural analog for "cap the shared backend, independent of caller identity" — cluster/priority-scoped, fail-fast, and explicitly distinguishable from a client-facing rate-limit rejection (confidence: high)

Envoy tracks five independently-configurable concurrent-resource thresholds (max connections, pending requests, active requests, retries, connection pools) **per upstream cluster and per priority** — never per calling client — confirmed directly against Envoy's own architecture-overview docs. This is a purely threshold-based, fail-fast model (not a Hystrix-style error-rate/time-window trip-and-recover state machine — that closer analog is Envoy's separately-documented Outlier Detection feature, a different mechanism entirely). When a breaker trips, Envoy does not silently reroute: it fails the request immediately, increments a distinct stat counter per breaker type (`upstream_cx_overflow`, `upstream_rq_pending_overflow`, `upstream_rq_active_overflow`, `upstream_rq_retry_overflow`, `upstream_cx_pool_overflow`), and for HTTP requests sets the `x-envoy-overloaded` response header — giving operators and callers a way to distinguish this rejection from any other failure type. Worth noting as a scoping caveat: Envoy's separate Overload Manager (a global/memory-pressure-triggered subsystem, never using the term "circuit breaker" anywhere in its own docs) is a materially different mechanism that should not be conflated with circuit breaking when building a mental model — its closest connection-cap analog, the `connection_pool_new_connection` load-shed point, is triggered by global resource pressure rather than a fixed per-backend ceiling, and on rejection simply fails the downstream request outright with no rerouting, same as circuit breaking's own behavior.

### Finding 3 — Kong's upstream-level health cap shows a two-tier model: keep rerouting among healthy replicas while some capacity remains, but fail closed with a distinct, uniform error only once the whole upstream's aggregate capacity is truly exhausted (confidence: medium — 2-1 vote)

Kong distinguishes Target-level health (one backend replica) from Upstream-level health (the aggregate % of total Target weight still healthy, against a configurable `healthchecks.threshold`). Below that aggregate threshold, Kong keeps routing normally to whichever healthy Targets remain — ordinary graceful degradation, not a deployment-cap rejection. Only when the healthy-capacity percentage crosses the configured threshold does the *entire* Upstream flip to unhealthy, at which point Kong deliberately fails closed: "the Upstream will only return errors," a uniform 503 for every request to that upstream, explicitly to let the struggling Targets recover rather than continuing to drain traffic onto insufficient capacity. This is a genuinely different shape from Envoy's per-request threshold check (Finding 2) — it's an aggregate-capacity gate that only engages once the shared resource is functionally gone, not a per-request concurrency/rate counter — but it reinforces the same reject-distinctly, don't-silently-reroute posture.

### Finding 4 — By contrast, a real production LLM gateway (Portkey) ships caller-facing load balancing with *zero* deployment-side protection at all — a live example of the exact gap Kelvran has (confidence: medium — 2-1 vote)

Portkey's AI Gateway load-balancing docs describe pure proportional-weight traffic splitting across providers/targets (define targets + weights → normalize → probabilistically distribute), with no mention anywhere of per-target concurrency/rate limits, circuit-breaker behavior, or health-based conditional routing. Its adjacent, composable features are equally reactive/static rather than proactive: Conditional Routing matches static request metadata (never real-time target health), and Fallbacks fire only reactively per-request on a non-2xx status code, with no circuit-breaker state or proactive health probing. This is useful negative evidence: it's not just that a per-backend cap is *possible* to omit — a real, shipping LLM gateway competitor has, at least in this documented feature, actually omitted it, which is the same gap Kelvran's own `LOGS.md` finding names.

### Finding 5 — The real-world precedent that actually matches Kelvran's stated worry is AWS's 2015 DynamoDB disruption, not Slack's 2021 outage — and the fix was an explicit load-shed action, not per-caller limits grinding the problem down (confidence: high)

AWS's own postmortem (`aws.amazon.com/message/5467D2/`) for the September 20, 2015 DynamoDB US-East disruption is a clean match for "many independent callers converging on one shared, under-protected backend": a brief network blip caused many storage servers to simultaneously request membership data from one internal, capacity-constrained metadata service; failed servers' retries kept load high ("Unavailable servers continued to retry requests for membership data, maintaining high load on the metadata service"), which then degraded response times for healthy, uninvolved servers too, causing them to flap between healthy and unavailable in a cascading, oscillating pattern (error rates climbing to ~55%). Critically, the fix that broke the cycle was an explicit, deliberate backpressure action — AWS "decided to pause requests to the metadata service" entirely, which relieved load enough to add real capacity, after which normal traffic resumed and error rates recovered. **Slack's 2021 outage is a weaker match than it's often invoked as being.** Verified directly against Slack's own postmortem: the load that overwhelmed an internal provisioning service was Slack's *own* autoscaling automation attempting to add 1,200 servers in 14 minutes after a network-induced CPU-utilization swing — internally generated automation load, not externally-driven caller traffic converging on a shared dependency. A further specific claim — that the Slack incident's actual root cause was AWS Transit Gateway network-capacity scaling failing to keep up with a post-holiday traffic surge — was separately checked and did not survive verification either. Recommendation: cite DynamoDB-2015 as the grounded precedent going forward; treat "Slack-2021-style convergence" (as currently phrased in `LOGS.md`) as directionally-right shorthand for the failure *pattern*, not a verified description of that specific incident's actual mechanism.

### Finding 6 — Google's SRE book independently confirms the same "shared backend, oversubscribed per-caller quotas" topology, and names why a bare backend-side gate alone isn't sufficient (confidence: high)

The SRE book's Per-Customer Limits pattern (Gmail/Calendar/Android/Google+ each granted a fixed CPU-second quota against one shared backend) explicitly allows per-customer quotas to sum to *more* than the backend's real total capacity (10,000 CPUs), on the documented assumption that not all customers peak simultaneously — the same many-callers/one-backend topology, and the same oversubscription logic LiteLLM's shared-pool and Router-sum-of-per-deployment-caps designs (Finding 1) both echo. Separately, the book's client-side adaptive throttling mechanism (each client tracks its own rolling requests-vs-accepts ratio and self-limits via a computed rejection probability, multiplier K, default 2x) exists specifically because "the backend can become overloaded even though the vast majority of its CPU is spent just rejecting requests" — i.e., a bare backend-side reject-at-the-gate mechanism is necessary but, on its own, can still let a large enough caller surge degrade the backend purely through the cost of saying no.

### Finding 7 — The SRE book's own concrete recommended mechanisms map almost exactly onto `ConcurrencyLimiter`'s existing shape, extended to a new scope (confidence: high)

Two distinct, complementary patterns, both directly quoted from the same chapter: (a) a **per-task (per-backend-instance) in-flight-request cap**, independent of caller identity, rejecting overflow with HTTP 503 — "return an HTTP 503 ... when there are more than a given number of client requests in flight" — which is structurally identical to `ConcurrencyLimiter`'s existing `MaxInFlight`/`Acquire`/`Release` design, just keyed by backend rather than by caller; and (b) a **fairness cap layered on top**, limiting how much of one shared server's resources any single caller/keyspace may consume even while the aggregate cap holds — "you might consider only allowing 25% of your threads to be occupied by any one client" — which is the missing piece that keeps one heavy or misbehaving virtual key from starving every other key routed to the same deployment even after a deployment-level cap exists.

### Finding 8 — Stripe's own production architecture is the strongest direct precedent for keeping concurrency and rate as two separate controls rather than merging them (confidence: high)

Stripe runs a distinct "Concurrent Requests Limiter" — a bare cap on simultaneously in-flight requests per user — as a genuinely separate mechanism from its per-second Request Rate Limiter, explicitly built because, before it existed, "we regularly dealt with resource contention on our most expensive endpoints caused by users making too many requests at one time." This is not a stale 2017 design either: Stripe's current, live API docs independently confirm the same two-control architecture still ships today, with distinct 429 sub-reasons (`global-concurrency`/`endpoint-concurrency` vs. `global-rate`/`endpoint-rate`) and a concrete worked example (a 30-concurrent-request cap alongside a separately-configured 15-requests/second rate cap on the same endpoint). This directly validates that Kelvran's existing `ConcurrencyLimiter` + `KeyLimiter` split at the per-key scope is the right shape to mirror at the deployment scope too, rather than collapsing concurrency and throughput into one merged deployment-level primitive.

### Finding 9 — HTTP semantics already draw the exact reject-distinctly line this design needs (confidence: high)

MDN's documented, standards-aligned semantics (matching RFC 9110/RFC 6585) draw a clean, uncontroversial line: 503 Service Unavailable is the correct code when a server-side resource threshold (memory, CPU, connection-pool limits) is met and the server wants to shed load and create backpressure; 429 Too Many Requests is specifically for restricting a particular client via rate limiting. This gives Kelvran an existing, industry-standard vocabulary for making a deployment-capacity rejection visibly different from a per-key rate-limit/concurrency rejection, on top of whatever internal Kelvran-specific error type or `gatewayevents` outcome value is used to draw the same distinction internally.

## Caveats

- Findings 3 and 4 (Kong, Portkey) each rest on a 2-1 verifier vote — directionally solid, treat with slightly more caution than the unanimous findings.
- A claim that Kong's upstream-wide capacity circuit breaker is "architecturally distinct from any per-consumer rate-limiting plugin" (i.e., precisely the mental model this research was asking about) was checked and did **not** survive verification at the strength claimed — Finding 3 is scoped narrowly to what was actually confirmed (the two-tier reroute-then-fail-closed shape), not to a broader claim about Kong's overall architecture.
- A claim that the deployment-level RPM ceiling on LiteLLM's Router is specifically enforced *before dispatch* via `enable_pre_call_checks`, and that this is "the mechanism that separates how-much-this-backend-can-take from how-much-any-caller-is-sending," was checked and refuted — do not cite LiteLLM for a specific claim about *when* in its request lifecycle the check runs, only for the aggregate-cap-sums-per-deployment behavior itself (Finding 1).
- A claim that uncoordinated per-caller retries against an already-overloaded shared backend cause runaway load amplification (the mechanistic core of "why per-caller limits alone are not enough") was checked against the SRE book and did not survive verification at the strength claimed — treat the retry-amplification mechanism as plausible-by-analogy (Finding 6's CPU-cost-of-rejection point is the closest verified adjacent mechanism), not as an independently confirmed SRE-book claim.
- A claim that Stripe added its concurrency limiter *specifically* because rate-limiter rejections were provoking client retries that worsened an outage was checked and refuted — Finding 8's actual verified rationale is resource contention on expensive endpoints from simultaneous in-flight requests, not a documented retry-storm-avoidance motive.
- Slack's 2021 postmortem is the one incident this research spent the most effort re-checking against the codebase's own framing (`LOGS.md`'s "Slack-2021-style convergence" phrase) — see Finding 5. Treat that phrase in `LOGS.md` as a naming shorthand worth correcting in future references, not as a settled factual citation.
- All Envoy/Kong/LiteLLM specifics were verified against live, current documentation/source (not cached/outdated pages) as of this research date, but Envoy, Kong, and LiteLLM are all actively-developed projects — re-check exact config keys/defaults before hardcoding them if this is built more than a few months out.

## Kelvran-Specific Recommendation

**Build two parallel, deployment-scoped instances of mechanisms Kelvran already has, keyed by `DeploymentConfig.Name` — do not try to fold a deployment dimension into the existing per-key `ConcurrencyLimiter`/`KeyLimiter` instances themselves.**

1. **A deployment-scoped `ConcurrencyLimiter` (reuse the type as-is).** `ConcurrencyLimiter`'s `Acquire(id)`/`Release(id)`/`Register(cfg)` shape is generic over its ID space already — nothing about it is virtual-key-specific except the call sites. Construct a second instance keyed by deployment name and `Acquire`/`Release` it around every dial attempt in `callDeployment`, at **every hop of `attemptFallbackChain`**, not just the first deployment the router selects — the whole point of the named gap is that fallback hops are exactly where many different keys converge on the same deployment, so a check only at hop 1 would leave the gap open at hop 2+. This is a near-zero-new-design change: same type, same "`MaxInFlight <= 0` means unlimited" convention, new config surface on `controlplane.DeploymentConfig` (a property of the shared backend, set by whoever owns deployment config — an operator — not by a virtual key owner) rather than on `identity.VirtualKey`. Finding 7's SRE-book precedent (per-task in-flight cap, reject with 503) and Finding 8's Stripe precedent (concurrency as its own control) both directly support this as sufficient and correct for the "too many simultaneously open requests" dimension.

2. **A deployment-scoped `KeyLimiter`-shaped RPM/TPM ceiling (reuse the mechanism, not necessarily the same instance).** A bare in-flight cap alone is not the right model for a deployment's *real* constraint, which for most upstream LLM providers is throughput, not raw concurrency — a deployment could have many slow streaming connections open without approaching its provider-side rate limit, or conversely a handful of short, high-token bursts could saturate TPM well under any reasonable concurrency ceiling (Finding 1, Finding 6). Construct a second `KeyLimiter`-shaped instance (reusing `TokenBucket`, and the already-Redis-capable `redislimiter/` backend for multi-instance deployments) keyed by deployment name, with per-deployment RPM/TPM caps configured on `DeploymentConfig` — directly mirroring LiteLLM's own precedent (Finding 1) of a per-deployment static `rpm` cap, and the SRE book's oversubscription logic (Finding 6) for how to size it relative to caller-side limits. This is the piece a bare-concurrency-only design (option 1 alone) would miss.

3. **Reject distinctly, mapped through Kelvran's existing fallback-chain machinery rather than a wholesale new architecture.** When either deployment-scoped cap is hit, this is a server/backend-capacity condition, not a per-caller rate-limit condition — per Finding 9's confirmed 503-vs-429 line, it should surface as a distinct outcome from `ErrRateLimited`/`ErrConcurrencyLimitExceeded` (both already deliberately bucketed together as client-facing 429s), not folded into the same bucket. But it should **not** always fail the whole request outright: Kelvran already has `attemptFallbackChain` and `classifyFallbackError`'s `FallbackClass*` bucketing built for exactly the "try the next configured target" shape. The cleanest design is to let a deployment-cap rejection participate in the same chain-walking logic a provider-returned 5xx/429 already does today — try the next configured fallback hop first, and only surface a client-facing 503 (Findings 2, 3, 9) if the entire chain is exhausted. This composes naturally with the existing pre-selection filter `router.IsHealthy(name)` already provides (skip deployments known-unhealthy before dispatch) — a deployment at its own concurrency/RPM/TPM ceiling is a different-but-analogous "not eligible for this request right now" signal that fits the same call-site shape, not a new one. No vendor studied described silently rerouting past a full backend to another one as an *automatic, invisible* substitution (Envoy/Kong/Overload-manager all just fail the individual request) — the "try the next hop" behavior recommended here is Kelvran's own already-shipped fallback-chain mechanism doing what it already does for other error classes, not a novel reroute-on-overload design being invented from scratch.

4. **Carry `ConcurrencyLimiter`'s existing self-documented gaps forward deliberately, don't silently inherit them.** The existing type's own doc comment already names "no timeout or leak-detection mechanism" and "no distributed counterpart" as real v1 limits at the per-key scope. Both become more consequential at deployment scope: a leaked Acquire-without-Release at the deployment level throttles *every* virtual key routed to that deployment, not just one caller, and a shared deployment is precisely the resource multiple gateway instances would independently converge on if Kelvran is ever deployed multi-instance — worse, not better, than the per-key case these gaps were originally accepted for.

## Open Questions

- Does the deployment-scoped RPM/TPM limiter need Redis-backed (multi-instance) enforcement from day one, given a shared deployment is exactly the resource multiple gateway instances would all independently hit — sooner than the per-key case ever needed it? Not resolved by this research; `redislimiter/` already exists as prior art but wiring a deployment-scoped instance to it wasn't investigated.
- What should the actual default per-deployment RPM/TPM/concurrency numbers be, and should they come directly from each provider's own published account-level rate limits rather than an arbitrary Kelvran-chosen default? Not investigated in this pass.
- Should a deployment nearing its own cap proactively lower its effective weighted-routing share (extending the existing weighted round-robin + health recovery-ramp mechanism) rather than only hard-rejecting once the cap is fully hit? No source studied described this kind of graduated, pre-emptive load-shedding at the deployment-cap layer specifically — worth a follow-up pass if Kelvran wants sub-100%-utilization behavior, not just a hard ceiling.
- Should `ConcurrencyLimiter`'s known leak-detection/timeout gap be fixed *before* a deployment-scoped instance is built, given the blast radius of a leaked slot is categorically larger at deployment scope (every key routed there) than at key scope (one caller)? This research surfaced the existing gap as more consequential at the new scope but did not evaluate concrete leak-detection designs from other vendors beyond Envoy's stat-counter observability (which detects/reports overflow, but doesn't itself prevent or clean up a leaked reservation).
