# Regression-Corpus Growth: Routing/Failover/Chaos Patterns — Deep Research (2026-09-08)

## Question

What are real, documented chaos-engineering-style routing/failover/rate-limit-bypass failure scenarios for LLM API gateways or general HTTP load-balancing/proxy systems, that could seed concrete regression eval test cases for Kelvran's evals corpus? Grounded against Kelvran's actual shipped mechanisms: real weighted round-robin routing (`gateway/internal/router`, smooth-WRR per `docs/rfcs/2026-09-04-weighted-routing.md`), active/synthetic health-probing (`docs/rfcs/2026-09-07-gateway-active-health-probing.md`), error-classified multi-hop fallback chains (`docs/rfcs/2026-09-07-gateway-error-classified-fallback-chains.md`), per-key/per-model rate limiting (`gateway/internal/ratelimit`), and retry-storm mitigation shipped 2026-09-07 (equal-jitter backoff, per-key concurrency caps, per-request fallback-chain circuit breaker, per `docs/rfcs/2026-09-07-gateway-retry-storm-mitigation.md`). This is explicitly a scenario-mining pass, not new design work — the deliverable is a citable seed list for `evals/tests/fixtures/regression_corpus_dogfood.json`'s `category:routing` cases, distinct from the 3 cases already mined from this project's own bug history (nil-TokenBucket panic, Admin API PerModel-never-wired gap, fallback-chain-bypasses-health-probe gap).

## Summary

Real chaos-engineering practice and real production postmortems converge on four failure classes directly relevant to Kelvran's router/fallback/rate-limit stack, and all four are backed by primary-source evidence, not speculation. First, **partial and degraded (not hard-down) backend failure is the normal operating condition at scale**, not an edge case — Netflix's Chaos Gorilla and Latency Monkey precedents (zone-outage rebalancing, delay-injection-as-outage-simulation) and Segment/Twilio's own statistical argument (dozens of endpoints failing "at any point in time" at 200+-integration scale) both argue for treating partial failure as a steady-state condition to test continuously, not a rare edge case. Second, **retry storms and cascading failure are named-canon chaos-engineering failure classes** with three independent, primary-sourced production postmortems (AWS DynamoDB 2015, Slack 2021, Twilio/Segment Centrifuge 2018) each showing a different concrete mechanism: client-retry-driven metadata-service overload, autoscaling-driven self-inflicted provisioning collapse, and degraded-success-rate-plus-retry-amplification happening simultaneously. Third, **DNS/resolution-layer thundering herds are measurable at 30x baseline volume** (Cloudflare's Oct 2021 Facebook-outage data), giving a concrete, citable request-volume multiplier for retry-storm regression scenarios. Fourth, **rate-limit bypass under concurrency is a named, demonstrated attack class** (PortSwigger's "limit-overrun" race-condition category, with a documented sub-1ms 20-30-request burst technique) with independent evidence that even Cloudflare's own production sliding-window approximation quantifiably let traffic ~15% over threshold through via a structural async-increment TOCTOU gap — directly relevant to Kelvran's per-key/per-model token bucket under concurrent load.

## Findings

### Finding 1 — Zone/AZ-level and delay-injected partial failure is the canonical chaos-engineering precedent for "rebalance to healthy backends without user-visible impact" (confidence: high, 3-0)

Netflix's Chaos Gorilla simulates the outage of an entire AWS availability zone specifically to verify that services automatically re-balance traffic to the remaining healthy zones with no user-visible impact and no manual intervention. Netflix's Latency Monkey establishes a distinct, complementary technique: injecting artificial delay into the client-server communication layer to simulate degraded service, and using very large delays to simulate a full node or service outage *without* physically killing instances — i.e., latency-injection is a documented, real chaos technique for testing fallback/timeout behavior against a dependency, not just hard-kill testing. Both are 2011-era Netflix Simian Army tools; the specific tools were later superseded internally, but the pattern (zone-level correlated failure; delay-as-outage-proxy) remains the standard reference point cited across chaos-engineering literature today. Source: [netflixtechblog.com/the-netflix-simian-army-16e57fbab116](https://netflixtechblog.com/the-netflix-simian-army-16e57fbab116).

### Finding 2 — Retry storms and cascading single-point-of-failure are explicitly named in the chaos-engineering canon as the exact systemic weaknesses the practice exists to surface (confidence: high, 2-1)

The Principles of Chaos Engineering manifesto explicitly lists "improperly tuned timeouts causing retry storms," "downstream dependencies receiving too much traffic," and "cascading failures when a single point of failure crashes" among the canonical example failure classes chaos engineering targets. This is a direct, named match to Kelvran's own already-shipped retry-storm mitigation (equal-jitter backoff, per-key concurrency caps) and per-request fallback-chain circuit breaker — i.e., these are not hypothetical concerns invented for this research pass, they are named industry-standard chaos targets. Source: [principlesofchaos.org](https://principlesofchaos.org/).

### Finding 3 — AWS's 2015 DynamoDB outage is a fully-documented, primary-sourced case study of partial-failure-to-cascading-retry-storm, with the mitigation being exactly a circuit breaker (confidence: high, 3-0)

AWS's own postmortem describes the complete causal chain in detail: a brief network blip affecting a *subset* of storage servers (partial backend failure) caused those servers to retry membership-data requests against a shared metadata service; that service's per-request processing time was already near its allotted limit due to unmonitored growth in membership-list size from GSI adoption; the resulting retry load pushed *previously-healthy* servers into failure too (error rate reached ~55%, "far beyond any level experienced in the last 3 years"); and the load from continued automatic retries by unavailable servers is what maintained the overload — a genuine self-reinforcing retry-storm/thundering-herd dynamic, not a single-shot failure. AWS's actual fix was an operator-triggered pause of all requests to the metadata service — functionally a circuit breaker — specifically because the retry storm's own load was preventing them from making the administrative requests needed to add capacity; only after pausing traffic (relieving retry pressure) could they add capacity and recover. Source: [aws.amazon.com/message/5467D2/](https://aws.amazon.com/message/5467D2/).

### Finding 4 — Slack's 2021 outage shows a distinct thundering-herd mechanism: an *automated recovery action itself* overwhelming a shared provisioning dependency (confidence: high, 3-0)

Unlike the AWS case (client retries drive the storm), Slack's autoscaling system attempted to add 1,200 new servers to its web tier within a single 14-minute window (7:01-7:15am PST) as an automated response to network-driven saturation — and this mass scale-up attempt itself overwhelmed `provision-service`, hitting a Linux open-files limit and an AWS quota limit, so most of the 1,200 instances were never fully provisioned. The broken instances then hit pre-configured autoscaling-group size limits and blocked spin-up of monitoring-dashboard instances, turning the recovery mechanism into a second cascading-failure point that had to be fixed (~8:15am) before capacity could actually be restored (~9:15am). This is a documented case of a *recovery* mechanism — not client retry behavior — causing a thundering herd against a shared internal dependency, directly relevant to testing Kelvran's own fallback-chain/health-probe recovery paths under simultaneous multi-deployment failure. Source: [slack.engineering/slacks-outage-on-january-4th-2021/](https://slack.engineering/slacks-outage-on-january-4th-2021/).

### Finding 5 — Twilio/Segment's Centrifuge postmortem gives a concrete, quantified shape for "degraded, not hard-down" partial failure plus simultaneous retry amplification (confidence: high, 3-0)

During a real production incident, successful call throughput to a failing downstream endpoint dropped to about 15% of its normal 16,000 req/s baseline while retry-storm volume to that same endpoint simultaneously spiked to roughly 100,000 req/s (~6x baseline) as Centrifuge's backoff logic reacted to the failing endpoint — demonstrating the concrete shape of partial-backend-failure (degraded success rate + retry amplification happening together) rather than a clean hard-down failure. Separately, Segment's own statistical argument for *why* this must be treated as continuous rather than rare: at 200+ downstream integrations, even endpoints individually rated at 99.9% uptime guarantee that "dozens" of endpoints are in a failing state at any given moment, and an hour-long outage occurs roughly once per day system-wide — a documented argument that partial/flapping backend failure is the steady-state condition for any system routing across many backends, directly applicable to Kelvran's multi-deployment router. Source: [twilio.com/en-us/blog/archive/2018/introducing-centrifuge/](https://www.twilio.com/en-us/blog/archive/2018/introducing-centrifuge/).

### Finding 6 — The Oct 2021 Facebook DNS outage gives a concrete, quantified request-volume multiplier for retry-storm regression scenarios: ~30x baseline, driven by compounding app-level and human-level retries (confidence: high, 3-0)

Cloudflare's own telemetry during the Oct 4, 2021 Facebook outage shows DNS resolvers worldwide (including its own 1.1.1.1) handling 30x more queries than usual. Cloudflare's own analysis attributes this to two compounding retry mechanisms stacking on top of each other: application-level retries ("apps won't accept an error for an answer and start retrying, sometimes aggressively") plus human-level retries (end-users reloading pages or killing/relaunching apps after hitting errors) — a concrete, citable mechanism for how naive client retry logic amplifies a single backend outage into a load spike on the resolution/routing layer. This gives a real-world request-volume multiplier (~30x sustained through the outage window) that a regression test's synthetic retry-storm load pattern could target instead of an arbitrary number. Source: [blog.cloudflare.com/october-2021-facebook-outage/](https://blog.cloudflare.com/october-2021-facebook-outage/).

### Finding 7 — Rate-limit bypass via race condition is a named, demonstrated attack category, not a theoretical TOCTOU concern (confidence: high, 3-0)

PortSwigger's "Smashing the State Machine" research (James Kettle, 2023 Top 10 web hacking technique) names "limit-overrun" as a distinct race-condition attack category — exploiting the time-gap between a security check and the protected action — with "bypassing an anti-bruteforce rate-limit" as its canonical worked example, complete with a dedicated hands-on lab. The concrete mechanism that makes this reliably reproducible (rather than flaky/timing-dependent) is the "single-packet attack," implemented in the open-source Turbo Intruder extension: it can land 20-30 near-simultaneous HTTP/2-multiplexed requests within a sub-1ms arrival window at the server, regardless of network jitter — 4-10x more effective than the older "last-byte sync" technique. This is the concrete mechanism a regression/chaos test would need to reproduce to exercise a TOCTOU race against Kelvran's per-key/per-model token bucket or concurrency cap reliably. Source: [portswigger.net/research/smashing-the-state-machine](https://portswigger.net/research/smashing-the-state-machine).

### Finding 8 — Real production rate limiters already exhibit a structural async-increment TOCTOU lag window, with Cloudflare's own quantified data on how much traffic it lets through (confidence: high, 2-1 / 3-0)

Cloudflare's own engineering writeup on its production rate limiter confirms that counter increments are processed asynchronously relative to the request path ("the increment jobs are run asynchronously without slowing down the requests") — meaning a request is structurally allowed through *before* its own contribution to the count is durably recorded, and only a separately-cached mitigation flag (not a live count) is checked during request processing. Cloudflare quantifies the real-world impact of this design: in an internal analysis of 400M requests from 270K distinct sources, 0.003% of requests were wrongly allowed or rate-limited, with an average 6% divergence between approximate and real rate, and specific cases where actual traffic was allowed up to 15% above the configured threshold before mitigation engaged (3 sources total exhibited this false-negative pattern; zero false positives). This is a genuine, measured production artifact of an async-counting design under concurrent load — directly relevant as a citable "how much bypass is realistic/tolerable" baseline for a Kelvran token-bucket race-condition regression case, though note this specific data point is a sliding-window-approximation artifact rather than a pure concurrency race, so it should be cited for the *magnitude* (single-digit-percent to ~15% overrun) rather than as a TOCTOU race per se. Source: [blog.cloudflare.com/counting-things-a-lot-of-different-things/](https://blog.cloudflare.com/counting-things-a-lot-of-different-things/).

## Concrete scenarios for case authoring

Each scenario below is stated as a one-or-two-sentence concrete regression-test premise with its real-world citation, organized by failure class, for a follow-on pass to turn into `EvalCase` `task_spec`/`reference` pairs against Kelvran's real `gateway/internal/router`, `gateway/internal/ratelimit`, and fallback-chain/circuit-breaker code.

**Partial backend failure (some but not all replicas of a model group failing):**

1. A model group has N weighted deployments; 1 of N starts failing health probes while the rest stay healthy — assert the router's WRR selection converges to zero-weight/skip for the failing deployment without affecting the healthy deployments' relative weight ratios (grounded in Chaos Gorilla's "rebalance to healthy without user-visible impact" pattern, Finding 1).
2. A downstream deployment's success rate degrades to ~15% of baseline (not 0%) while request volume to it simultaneously spikes via retries — assert Kelvran's per-request fallback circuit breaker trips on the *degraded success rate*, not just on hard connection failure, matching the Centrifuge incident's "degraded, not hard-down" shape (Finding 5).
3. At a model-group size representative of Kelvran's largest configured group, simulate the Segment/Twilio statistical argument directly: inject continuous low-level flapping across a subset of deployments (each individually "healthy most of the time") and assert the router treats this as steady-state load-shedding rather than triggering unbounded fallback-chain retries (Finding 5).
4. Inject an artificial fixed delay (not a hard failure) on one deployment large enough to simulate a full outage without killing the connection — assert the router's timeout/fallback path activates correctly on delay-as-outage, per Latency Monkey's precedent that large injected delays are a valid outage-simulation technique distinct from hard kills (Finding 1).

**Flapping health (a backend that intermittently passes/fails health checks):**

5. A single deployment's active health probe alternates pass/fail across consecutive probe cycles (e.g., fail-pass-fail-pass) at a rate below the N-of-M consecutive-failure threshold — assert the deployment is never incorrectly marked permanently unhealthy nor incorrectly kept fully healthy, exercising the exact boundary condition of the N-of-M threshold design (grounded in Finding 5's "dozens of endpoints in a failing state at any given moment" steady-state framing).
6. A deployment fails health checks, gets ejected from routing, then recovers — assert the fallback chain does not bypass the health probe's re-admission logic when re-including a recovered deployment (this exercises the same class of gap as the project's own already-mined "fallback-chain-bypasses-health-probe" bug, but from the recovery/flapping direction rather than the failure direction).

**Cascading failure (one backend's failure increasing load/failure-rate on the remaining ones):**

7. Simulate the AWS DynamoDB pattern directly: a shared dependency used by multiple routing decisions (e.g., a shared health-probe target or shared rate-limit counter store) becomes slow under load from retries of an already-failing deployment — assert Kelvran's retry-storm mitigation (equal-jitter backoff, per-key concurrency caps) prevents the retry load itself from degrading the shared dependency further, i.e., the retries don't create a second point of failure (Finding 3).
8. Simulate the Slack pattern: trigger simultaneous fallback-chain activation across many concurrent requests when a widely-shared first-hop deployment fails, and assert the resulting surge of fallback requests onto the second-hop deployment doesn't itself trip that deployment's own rate limits/circuit breaker in a way that cascades further down the chain (Finding 4).
9. Assert that Kelvran's per-request fallback-chain circuit breaker, once tripped for a given request's chain, does not independently re-attempt the same failed hop from a *different* concurrent request in a way that compounds load on the already-struggling deployment — i.e., the circuit breaker's scope (per-request vs. shared) is tested under concurrent load, not just single-request load (Finding 3 + Finding 4 combined).

**Retry storm / thundering herd (request volume/timing patterns grounded in real incidents):**

10. Reproduce the Cloudflare/Facebook-outage volume shape: sustain ~30x normal request volume against a single failing upstream for the duration of a simulated outage window, and assert Kelvall's equal-jitter backoff plus per-key concurrency cap bounds the *actual* outbound retry volume well below a naive 30x multiplier (Finding 6).
11. Reproduce the Centrifuge incident's specific numeric shape: baseline 16,000 req/s to a deployment, success rate drops to ~15% of baseline, retry volume to that same deployment spikes toward ~6x baseline — assert the fallback/backoff logic converges rather than continuing to amplify over a sustained multi-minute window (Finding 5).
12. Simulate a Slack-style "recovery-triggered herd": many concurrent requests independently detect the same deployment as newly-healthy (post-recovery) within a narrow time window and all route back to it simultaneously — assert there's no unbounded simultaneous-reconvergence spike analogous to Slack's 1,200-server-in-14-minutes provisioning collapse (Finding 4).

**Rate-limit bypass / TOCTOU race under concurrent load:**

13. Fire a burst of concurrent requests against a single API key's token bucket sized to land within a sub-millisecond arrival window (per the PortSwigger single-packet-attack technique) at a point where the bucket has capacity for exactly 1 more request — assert exactly 1 request is admitted, not N, closing the exact race window the "limit-overrun" attack category exploits (Finding 7).
14. Run concurrent requests against a per-key concurrency cap at the boundary (cap = K, fire K+several concurrently) and assert the cap is enforced atomically rather than allowing a burst of K+delta through during the check-then-increment gap (Finding 7 + Finding 8).
15. Using Cloudflare's own measured tolerance as a ceiling, assert Kelvran's token bucket under sustained concurrent load never lets actual admitted traffic exceed roughly 15% above the configured per-key/per-model limit — i.e., treat "≤15% overrun under race conditions" as a concrete, citable regression bound rather than requiring mathematically perfect enforcement under all concurrency (Finding 8).
16. Combine a rate-limit race with a fallback chain: fire a race-condition burst against a key's rate limit at the exact moment its primary deployment also fails health checks, and assert the two mechanisms (rate limiter admission, fallback-chain routing) don't interact to produce a compounded bypass (e.g., rejected-then-retried requests silently re-entering the bucket via a different fallback hop's own, separately-tracked limit) (Finding 7 + Finding 3 combined).

## Caveats

- **6 claims from the underlying verification pass could not be verified due to infrastructure/tooling errors** (verifier agents errored rather than confirming or refuting), covering: the "First Sequence Sync" IP-fragmentation race technique and its 10,000-requests-in-166ms benchmark and 1,000-attempt login-rate-limit bypass (flatt.tech); an Envoy AI Gateway rate-limit/ext_proc metadata race condition and its reproducible error signature (GitHub issue #1786); and Cloudflare's claimed avoidance of atomic CAS transactions for counting. These are not refuted — they remain open leads worth re-verifying in a follow-on pass, particularly the Envoy AI Gateway issue, which if confirmed would be a second, LLM-gateway-specific (not generic-HTTP) documented rate-limit race.
- **One claim was refuted on verification**: Envoy's outlier-ejection duration does not scale geometrically for repeat offenders in the way an earlier draft claim asserted (vote 0-3) — do not cite this as a "flapping health" mitigation pattern without re-checking the actual Envoy source directly.
- **A related claim was also refuted**: the "Vary Real-world Events" taxonomy framing (hardware/software/non-failure-load-event injection categories from principlesofchaos.org) did not survive verification (vote 0-3) — Finding 2's narrower "retry storms + cascading failure are named canon targets" claim did survive and should be used instead.
- **A Twilio/Segment-specific "6x spike over 90 minutes" claim was refuted as an independent claim** (vote 1-2) but the underlying, better-supported version — the same 16,000 req/s baseline, ~15% success rate, and ~100,000 req/s retry-storm peak, all within the same March 17 incident window — did survive (Finding 5) and is used instead; do not separately cite a "90-minute" duration or treat the 6x figure as independently verified beyond what Finding 5 states.
- **Time-sensitivity**: the AWS (2015), Twilio/Segment (2018), and Netflix Simian Army (2011) sources are historically dated incidents/tools, cited here as documented case studies establishing realistic failure *shapes* and *magnitudes* for test design — not as claims about current production architecture at those companies. The Cloudflare rate-limiter source (2017) describes an architecture Cloudflare has since migrated off internally (to Pingora), but independent 2026 sources confirm the same async-increment/approximate-counting design philosophy persists conceptually — the magnitude data (Finding 8) is treated as a durable reference point, not as Cloudflare's current live numbers.
- **Source-type note**: Findings 1, 3, 4, 5, 6, 7, and 8 all rest on primary sources (the operator's own engineering blog/postmortem, or the original security researcher's own publication) — this is a stronger evidentiary basis than the routing-scope-expansion research's competitor-survey findings, which relied more heavily on reading vendor source code and docs. Finding 2's manifesto-canon claim is the one split-vote (2-1) finding, though the underlying quote was independently re-verified against the raw source HTML.
