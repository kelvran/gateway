# Kelvran Gateway — Batch API Proxying: Peer Gateway Architecture Survey and Stateless-Proxy Cost Assessment (2026-09-13)

**Date:** 2026-09-13
**Scope:** `gateway/internal/adapter/{openai,anthropic,bedrock,gemini,openaicompat}` — confirmed **NOT BUILT**: every adapter is synchronous request/response or SSE-streaming only; there is no batch/async job concept, no queue, and no polling mechanism anywhere in this codebase, and no persistent job/state store exists anywhere in Kelvran's gateway (config is static YAML loaded once at startup, no database). This report asks whether peer LLM gateways (LiteLLM, Portkey, Helicone) proxy or wrap the native Batch APIs of OpenAI, Anthropic, and AWS Bedrock today, what a gateway-level batch-proxying architecture actually looks like in production (job submission, status polling, result retrieval, cost tracking), and what batch support would cost Kelvran architecturally given its current fully-stateless, single-request design.
**Method:** Adversarial multi-source research (3-vote verification per claim) against primary vendor documentation (LiteLLM, Portkey, Anthropic, OpenAI) and primary source code (LiteLLM's `BerriAI/litellm` GitHub repo, Portkey's open-source Python SDK, `llm-d/llm-d-batch-gateway`, `linto-ai/llm-gateway`). 20 claims survived; 5 were proposed and refuted (0-3 or 1-2) and are logged below for transparency. Helicone was in scope for the research question but no claim about it survived verification — see Caveats and Open Questions.

---

## Executive summary

Gateway-level batch proxying of native provider Batch APIs is now mainstream peer practice: LiteLLM ships `/batches` as a first-class, free (non-Enterprise) proxy endpoint category spanning OpenAI, Azure, Vertex AI, and Bedrock, and Portkey wraps Bedrock's native batch job lifecycle behind its own SDK. But every peer implementation studied draws a hard line between two very different things — a cheap, stateless *passthrough* of the native API shape (LiteLLM's Anthropic integration, Portkey's default "Provider Batch API" mode) versus real gateway-side job tracking with no caller-side polling, which every vendor treats as a separate, heavier, explicitly bolted-on subsystem (Portkey's "Managed Batching" mode requires an additional "Data Service"; LiteLLM gates automated cost tracking behind its paid Enterprise tier). Batch support is also inherently a config-time, per-model registration concept, not something a stateless per-request proxy can infer dynamically — LiteLLM requires each Bedrock batch model to be pre-declared in static YAML with `mode: batch`, which is structurally compatible with how Kelvran already declares synchronous deployments. The one thing no peer solves for free is state: real job tracking costs a persistent queue plus crash-recovery logic (concretely demonstrated by `llm-d-batch-gateway`'s Redis-backed sorted-set/list queue pair, in a different but architecturally analogous domain), and Kelvran currently has zero persistent state anywhere. The net conclusion: a thin, Anthropic-style zero-translation passthrough (auth/routing only, caller polls the provider directly) is a cheap, buildable-on-demand addition that mirrors exactly what mature peers ship as their *default*, low tier; anything beyond that — unified job tracking, cost attribution, Bedrock-style S3/IAM-mediated translation — requires a genuinely new persistent-state subsystem that is disproportionate to build speculatively.

## Findings

### 1. Gateway-level batch proxying of native provider Batch APIs is now mainstream peer practice, not a novel or speculative capability

**What the research found:** LiteLLM markets `/batches` as one of its unified, standard proxy endpoint categories alongside `/chat/completions`, `/embeddings`, and `/responses` (claim 0), and its proxy layer ships a dedicated, free (`No Enterprise license is required`) Managed Batches feature spanning OpenAI, Azure, Vertex AI, and Bedrock (claim 16) — confirmed as actively developed as recently as the day before this research date via live GitHub PR/issue activity, not a stale or abandoned feature. Portkey ships two operating modes wrapping native provider Batch APIs specifically for Bedrock (cheapest/native "Provider Batch API" vs. faster/provider-agnostic "Portkey Batch API"), with dedicated SDK methods (`create`/`list`/`retrieve`/`cancel`/`output`) confirmed both in Portkey's docs and independently in Portkey's own open-source Python SDK source code (claims 1, 17, 18).

**Why it matters for Kelvran specifically:** this directly answers the "do peer gateways proxy these APIs today" half of the research question — yes, and by two separate, mature vendors, with real code behind the claims (not just marketing copy). This establishes that a validated market pattern exists to follow if/when Kelvran decides to build, but the mere existence of peer support is not itself a build trigger absent Kelvran-specific customer demand (see Finding 7).

**Confidence:** High (multiple primary sources, independently corroborated by GitHub source code for both vendors; unanimous or near-unanimous votes).

**Signal:** N/A — informational landscape finding; feeds the go/no-go decision in Finding 7 rather than being a build decision on its own.

### 2. Two structurally different proxying patterns exist, with very different cost profiles: format-translating wrapper vs. zero-translation passthrough

**What the research found:** LiteLLM's Bedrock batch integration is a genuine translating wrapper — it exposes OpenAI-compatible endpoints (`POST /v1/files`, `POST /v1/batches`, `GET /v1/batches/{id}`, `GET /v1/files/{id}/content`) but internally converts OpenAI-shaped JSONL into Bedrock's Converse-request shape on a per-model-family basis (claim 3), and requires S3 as a mandatory intermediary for both input and output plus a dedicated `aws_batch_role_arn` IAM role letting Bedrock invoke models and access the bucket (claim 4). By contrast, LiteLLM's Anthropic integration is a pure passthrough: it forwards the native `/v1/messages/batches` shape verbatim with zero request/response translation (claim 6), functioning as generic provider-specific route-forwarding rather than a gateway-abstracted job model.

**Why it matters for Kelvran specifically:** this is the key architectural fork for any future Kelvran batch work. Passthrough-style proxying (Anthropic pattern) is architecturally cheap — a thin route reusing existing auth/routing, no format translation, no S3/IAM provisioning. A translating wrapper (Bedrock pattern) is a materially heavier, provider-specific lift requiring cloud-resource provisioning (S3 bucket, IAM role) and per-model transformation logic that has nothing to do with Kelvran's existing adapter code.

**Confidence:** High (both patterns confirmed against live, current primary vendor docs with exact endpoint/config detail).

**Signal:** `build_now`-eligible pattern to copy *if and only if* Kelvran ever builds anything here: passthrough-first (Anthropic-style) is the defensible cheap entry point. `not_yet` for a Bedrock-style translating wrapper under any currently known precondition — the S3 + IAM + per-model-translation lift is disproportionate without a concrete Bedrock-specific customer commitment large enough to justify provisioning and maintaining that cloud-resource surface.

### 3. All three providers' native batch APIs are async submit/poll/retrieve job models with a real, verified economic incentive — not a sync/streaming variant

**What the research found:** Anthropic's Message Batches API charges exactly 50% of standard synchronous pricing across input, output, and special tokens (claim 8), follows a documented three-step model — create batch, process asynchronously per-request, poll status and retrieve results once processing ends (claim 9) — with most batches finishing under 1 hour but a hard 24-hour expiry ceiling (claim 10). OpenAI's Batch API requires uploading a `.jsonl` file where each line is an independent request carrying its own `custom_id`/`method`/`url`/`body`, then creating a batch referencing that `file_id` and polling status asynchronously — the guide documents no synchronous request/response coupling anywhere (claim 11). Two related claims did **not** survive verification and are flagged for caution: a claim asserting OpenAI's Batch API also offers a 50% discount was proposed and refuted (0-3), as was a claim about OpenAI's output-ordering/`custom_id`-mapping requirement (0-3) — see Caveats.

**Why it matters for Kelvran specifically:** this confirms the research question's premise that these are genuinely async, hours-long-SLA job models incompatible with a stateless per-request proxy's normal request lifecycle, and establishes the demand-side economic case (a verified 50% cost reduction for Anthropic; OpenAI's discount figure specifically is unverified in this pass) that would need to exist among Kelvran's own customers before batch support is worth building at all.

**Confidence:** High for Anthropic's pricing and mechanics and for OpenAI's async mechanics; **low/unverified** for an OpenAI-specific discount percentage — do not cite a specific OpenAI batch discount figure without independent re-verification.

**Signal:** N/A — this describes provider-side behavior Kelvran does not control. It is the economic precondition input to Finding 7's build/no-build call, not a build decision in itself.

### 4. Batch proxying is fundamentally a config-time, per-provider/per-model registration concept — not something a stateless per-request proxy can infer dynamically

**What the research found:** LiteLLM requires each Bedrock batch-capable model to be explicitly pre-declared in static `config.yaml` with `model_info: mode: batch` (claim 5) before any request can target it as a batch model — an admin-time registration step, not a request-time inference. LiteLLM's Anthropic passthrough similarly requires the target model to be defined in `proxy_config.yaml` for cost-tracking to function correctly at all (claim 7), tying even the "no translation" passthrough path to a config-time model registry.

**Why it matters for Kelvran specifically:** this is good news for the *declaration* half of any future Kelvran batch design — Kelvran already declares synchronous model deployments in static YAML loaded once at startup, so a new `mode: batch` (or equivalent) field per deployment entry is structurally compatible with the existing config model and does not itself require new infrastructure. The harder problem peer gateways all push into a *separate* subsystem is what happens after a batch request is accepted (Finding 5), not how the model is declared.

**Confidence:** High (both sub-claims verified directly against live, current primary docs with exact config-field detail).

**Signal:** `build_now`-relevant precondition if Kelvran ever adds batch support at all: model it as a new, explicit per-deployment config field (parallel to existing static YAML deployment declarations), not as something inferred per-request. This specific piece carries no meaningful cost and is not itself a reason to defer.

### 5. Real gateway-side job tracking (no caller-side polling) requires a persistent state store bolted onto the gateway — this is the concrete, unavoidable architectural cost, and every peer treats it as a separate subsystem, not a byproduct of proxying

**What the research found:** Portkey's own documentation explicitly discloses that its default "Provider Batch API" mode is stateless and does **not** poll for completion status on the provider's side — the caller must poll a Retrieve Batch endpoint manually, with the same signature across all supported providers (claim 1). Real gateway-side tracking without caller-side polling exists only in a separate "Portkey Managed Batching" mode that requires enabling an additional "Data Service" component (claim 2) — i.e., even a funded commercial gateway treats genuine job-state tracking as an optional, heavier add-on layered on top of a stateless core, not something proxying gives you for free. The concrete shape of what that add-on costs is independently visible in `llm-d-batch-gateway`'s real, current, actively-maintained open-source design: async dispatch requires an external Redis instance implementing two distinct queues (a sorted set for pending requests, a list for results), an in-memory `PendingRequests` map keyed by request ID, and an acknowledged, tracked gap around recovering results after a processor pod is lost (claim 13). This is architecturally the closest available concrete precedent for "add a job/queue layer to a gateway," though it is important to note precisely: `llm-d`'s Batch Gateway sits in front of `llm-d`'s own internal router for self-hosted vLLM/SGLang model serving — it does **not** proxy or wrap OpenAI's, Anthropic's, or Bedrock's native Batch APIs (claims 12, 14). It is evidence that a job-store-plus-queue-plus-worker-fanout architecture on top of a stateless synchronous backend is real and production-viable, not evidence of a peer wrapping the specific provider APIs this research is about.

**Why it matters for Kelvran specifically:** this is the load-bearing finding for the cost-assessment half of the research question. No peer solves job-state tracking as a free byproduct of a stateless proxy design — Portkey's own core gateway explicitly does not, and the closest available concrete engineering precedent for what solving it *would* cost (Redis-backed dual-queue design, in-memory pending-request tracking, unresolved crash-recovery edge cases) confirms it is a genuinely separate, non-trivial subsystem, not incremental plumbing on Kelvran's existing per-request adapter code.

**Confidence:** High for the Portkey stateless-by-default disclosure and for the `llm-d-batch-gateway` Redis design detail (verified against the actual byte-for-byte design doc source, not a summary); the `llm-d` citation is directionally relevant as an architectural analog but explicitly not an example of proxying the providers this research targets — treat accordingly.

**Signal:** `not_yet`. Precondition to revisit: Kelvran already has (or is independently building, for reasons unrelated to batch — e.g. a usage/billing ledger, multi-tenant key management requiring a database) a persistent datastore that a batch job/queue subsystem could piggyback onto. Building a database + queue + poller + crash-recovery subsystem *solely* to enable "no caller-side polling" batch tracking, when even Portkey — a funded commercial product — treats that as a separate, heavier mode on top of its own stateless core, is a disproportionate lift for Kelvran's current zero-persistence architecture absent that precondition.

### 6. Batch cost/spend tracking is commonly a paid/Enterprise-gated feature even among peers who do proxy batch APIs, and even there it still requires an internal polling subsystem

**What the research found:** LiteLLM explicitly gates automated batch cost tracking behind its paid Enterprise tier — the open-source proxy gets creation/upload/list/retrieve/rate-limiting and generic logging-integration visibility for batches, but not aggregated cost/spend accounting per user/key/team/tag (claim 19). Where cost tracking *is* offered at all (LiteLLM's Anthropic passthrough), it requires the model to be pre-registered in static config **and** relies on an internal polling mechanism that retrieves batch status purely to compute cost (claim 7) — i.e., cost attribution alone requires bolting on the same category of polling infrastructure Finding 5 describes, even without delivering full job-state UX to the caller.

**Why it matters for Kelvran specifically:** cost/budget accounting is one of Kelvran's existing gateway responsibilities for synchronous calls, so it is tempting to assume batch cost tracking is "just more of the same." The evidence says otherwise: even the market-leading OSS proxy treats it as a commercially-gated, infrastructurally-separate feature requiring its own polling loop, not something that falls out of the existing per-request cost-accounting path.

**Confidence:** High (both sub-claims verified directly against current primary vendor docs, with the Enterprise-gating claim additionally cross-checked against a GitHub issue/PR search finding no evidence of the feature having been open-sourced).

**Signal:** `not_yet`. Precondition: do not build a bespoke batch-status poller solely to attribute cost for a feature that doesn't otherwise exist yet — defer until/unless Kelvran is already building a general usage-aggregation or billing-ledger subsystem (see Finding 5) that a batch-status poller could hook into as an incremental addition rather than a standalone build.

### 7. Net architectural cost to Kelvran, and the "just tell callers to hit the batch API directly" alternative

**What the research found, synthesizing Findings 1–6:** Given Kelvran's adapters are uniformly synchronous request/response or SSE-streaming with zero persistent state, batch support is not an incremental adapter change — it introduces a categorically different code path regardless of which tier is chosen. The cheapest defensible version (an Anthropic-style, zero-translation passthrough per Finding 2) requires: a new route that forwards native-shaped batch requests, reusing Kelvran's existing auth/routing for admission, but explicitly **not** attempting job tracking, cost aggregation, or a unified cross-provider schema — the caller polls the provider directly through the passthrough, exactly as LiteLLM's own Anthropic passthrough and Portkey's default "Provider Batch API" mode already ship as their baseline tier (Findings 1, 2, 5). That tier is meaningfully cheaper than bypassing Kelvran and hitting the provider's batch API directly *only* insofar as it preserves centralized auth, routing, and audit logging — it does not solve state tracking, which mature peers explicitly disclose they don't solve at this tier either. Anything beyond that — true job tracking without caller-side polling, cost attribution, Bedrock-style S3/IAM-mediated translation — requires a genuinely new persistent subsystem (database + queue + poller + crash recovery) that no current Kelvran component provides and that even Portkey ships only as a separate, heavier, explicitly-gated mode.

**Why it matters for Kelvran specifically:** this is the direct answer to "what would batch support cost Kelvran architecturally." The honest answer has two tiers with very different costs: a thin passthrough is cheap and buildable on demand; a real managed-batch subsystem is a multi-week, new-infrastructure undertaking (persistent datastore, queue, poller, crash-recovery logic, per-provider config registration, and — separately — cost-attribution plumbing) that should not be built speculatively.

**Confidence:** High (synthesized directly from Findings 1–6, each independently high-confidence; no claim in this synthesis extends beyond what those findings individually support).

**Signal:** `not_yet` for any tier beyond a thin passthrough. `build_now` trigger for the passthrough tier specifically: a concrete paying customer requests batch access to a specific provider (Anthropic first, given the zero-translation cost profile from Finding 2) routed through Kelvran, explicitly for centralized-auth/audit/routing reasons, and explicitly accepts caller-side polling with no unified job schema and no cost tracking as the initial cut — mirroring exactly what LiteLLM's Anthropic passthrough and Portkey's default mode already ship. Absent that concrete ask, `build_now` is not justified for *any* tier: this research pass found no evidence of Kelvran-specific customer demand for batch access, and a passthrough that provides no additional job-state guarantee over calling the provider directly is not obviously a better customer experience — only a better *operational* one (single auth surface, unified audit trail) for Kelvran's existing customers.

## Recommendation, mapped to the research question

1. **Do peer gateways proxy native provider Batch APIs today?** → **Yes**, both LiteLLM and Portkey do, as a mainstream, actively-maintained (not deprecated or abandoned) feature — but Helicone's practice is unestablished in this pass (see Caveats/Open Questions), and neither peer solves state tracking "for free."
2. **What does gateway-level batch-proxying architecture look like in production?** → Two tiers, not one: (a) a cheap, stateless passthrough of the native API shape with caller-side polling (the default/baseline everywhere it was found), and (b) a separate, heavier, explicitly-bolted-on job-tracking subsystem (persistent queue, poller, crash recovery, often commercially gated) that no peer treats as inherent to proxying itself.
3. **What would batch support cost Kelvran architecturally?** → A thin passthrough tier is cheap and structurally compatible with Kelvran's existing static-YAML-declared, stateless design (Finding 4). A real managed-batch tier (unified job tracking, cost attribution, Bedrock-style translation) requires Kelvran's first persistent datastore and a queue/poller/crash-recovery subsystem — a genuinely new category of infrastructure, not an adapter extension.
4. **Overall:** `not_yet` for building anything beyond a thin, on-demand passthrough absent a concrete customer ask; `build_now` is reserved for the specific, narrow passthrough trigger in Finding 7, and explicitly `not_yet` for any tier requiring persistent state until that state is justified by something other than batch support alone.

## Caveats

- **Two claims specifically about OpenAI's Batch API were proposed and refuted (0-3) in this pass**: a claim that OpenAI's Batch API offers a 50% cost discount, and a claim about OpenAI's fixed 24-hour completion window plus output-ordering/`custom_id`-mapping requirements. The surviving claim about OpenAI (claim 11, async submit/poll/retrieve mechanics) held up, but do not assume OpenAI's specific discount percentage or ordering/window guarantees without independent re-verification — this report deliberately does not state a specific OpenAI discount figure for this reason.
- **A claim that LiteLLM's managed batches require a persistent Postgres database and that this is unsupported in "stateless SDK usage mode" was refuted (0-3)**, as was a claim about a specific "batch cost poller" default interval (3600s, refuted 1-2). Treat LiteLLM's exact persistence/polling internals as less certain than the claims that did survive (the Enterprise cost-tracking gate itself, and the general existence of a polling mechanism for cost calculation).
- **A claim that llm-d's Batch Gateway "requires persistent state that a stateless per-request proxy does not have" (framed generically) was refuted (0-3)** even though the more specific, code-verified claim about its Redis-backed dual-queue design (claim 13, used in Finding 5) survived 3-0. The lesson: the general architectural principle ("adding batch requires new state") is best supported by the specific, code-verified detail, not by a broadly-worded restatement of it — this report leans on the narrower, surviving claim only.
- **Helicone was explicitly in scope for this research question but no claim about it survived adversarial verification.** This is a genuine research gap, not a confirmed absence of Helicone batch support — do not read this report as evidence Helicone lacks batch proxying.
- **`llm-d-batch-gateway` and `linto-ai/llm-gateway` are architecturally adjacent analogs, not actual examples of proxying OpenAI/Anthropic/Bedrock's native Batch APIs.** `llm-d` wraps its own self-hosted model-serving router; `linto-ai/llm-gateway`'s "jobs" are its own internal document-processing task queue (Celery/Redis) and its adapters make only synchronous `chat.completions.create` calls, never touching any provider's `/v1/batches` endpoint (claim 15). Both were cited in this report only as evidence of what a real job/queue layer costs to build, never as evidence of provider-Batch-API wrapping.
- **Time-sensitivity is meaningfully high for LiteLLM's Managed Batches feature specifically** — it is explicitly labeled `[BETA]` and was under very active development as of the day before this research date (multiple real PRs/issues in the preceding two weeks touching custom-endpoint support and Bedrock file deletion). Treat its exact feature surface as a moving target, not a settled reference architecture.
- **Portkey's Bedrock batch wrapper is gated to Enterprise hybrid/self-hosted plans** per the verifier's supplementary check — this qualifies availability of the feature discussed in Findings 1 and 2 but does not contradict the underlying technical architecture claims.

## Open questions

1. **Does any Kelvran customer actually want batch API access today, and for which provider first?** No demand signal was found in this research pass — this report establishes feasibility and cost, not need. The `build_now` trigger in Finding 7 is conditional on this being answered externally.
2. **Does Helicone proxy or wrap native provider Batch APIs?** Unestablished in this pass (see Caveats) — worth a dedicated, narrower follow-up specifically targeting Helicone's own docs/source before this report's peer-landscape claim in Finding 1 is treated as exhaustive across all three named competitors.
3. **If Kelvran ever adds a persistent datastore for an unrelated reason (billing ledger, multi-tenant key management), does that change Finding 5/6's `not_yet` calculus enough to flip to `build_now` for batch job tracking specifically?** Worth revisiting the moment such a datastore decision is made, rather than waiting for a separate batch-specific trigger.
4. **What is OpenAI's actual current batch discount rate and completion-window/ordering guarantee?** Two related claims were refuted in this pass (see Caveats) — before any future report leans on an OpenAI-specific economic or SLA figure, it should be independently re-verified against OpenAI's own current pricing/docs pages rather than reused from this report.
