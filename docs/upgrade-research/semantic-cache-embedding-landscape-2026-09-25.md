# Kelvran Cache — Semantic-Cache Embedding Landscape Research (2026-09-25)

**Date:** 2026-09-25
**Scope:** The deferred "real-embedding L3 semantic cache," named explicitly as future work in `PRD.md` and `gateway/ARCHITECTURE.md`'s Cache Subsystem section, gated on real production miss-telemetry that does not exist yet (`docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`'s Unresolved Questions: *"the trigger is concrete miss-telemetry showing lexical matching's real paraphrase-miss volume, not a fixed timeline"*). **This report does not propose building the upgrade now.** It asks whether the *landscape* — vector DB/ANN-index options, entity/freshness-safety techniques beyond lexical shingling, and any real, dated production example of a gateway safely shipping a semantic (not lexical) response cache — has moved in a way worth knowing about for when `PRD.md`'s own gating criterion is eventually met, and whether any new safety technique beyond an entity/freshness hard-gate has emerged that `AGENTS.md`'s non-negotiable rule ("never ship a semantic-cache change that removes or weakens the entity/freshness hard-gate in favor of a bare similarity threshold") should be aware of. Findings are grounded first against `THREAT_MODEL.md`'s CacheAttack/near-duplicate-hijacking row — which already measures and documents that Kelvran's current L3-lite uses lexical shingle-Jaccard/MinHash similarity with a ~0.9 floor, **never** embedding-cosine similarity — and second against `PRD.md`'s own stated gating criteria. This is a direct follow-up to `semantic-cache-embeddings-tier1-2026-09-20.md`, `cache-semantic-embedding-reconsideration-2026-09-13.md`, `cache-production-semantic-caching-2026-09-11.md`, `cache-semantic-embedding-readiness-round4-2026-09-11.md`, and `cache-l3-lite-threshold-calibration-2026-09-12.md` — those reports covered buildability/cost/latency and prior vendor-safety-model surveys; this report is scoped narrowly to what's *new* in the landscape since, plus the vector-DB/ANN and academic-safety-technique angles those reports touched less directly.
**Method:** Adversarial multi-source research (3-vote verification per claim) against current (2026-09-25) production and academic semantic-caching practice: Milvus, Qdrant, LiteLLM, Azure API Management, and Portkey (vendor docs), plus LaCache, Krites, the CacheAttack-lineage "From Similarity to Vulnerability" paper, the "Early Bird" timing-side-channel paper, vCache, and FreshCache (academic preprints), plus GPTCache's own repository — 12 distinct primary sources, 25 claims put to adversarial vote, 17 confirmed (3-0 or 2-1), 8 refuted. Full per-claim evidence and vote counts are preserved in this session's workflow journal; this document adds the Kelvran-specific "why it matters here / is this consistent with `PRD.md`'s own gating criteria / does this touch the `AGENTS.md` hard-gate rule" layer the raw adversarial verification deliberately does not do.

## Executive summary

The landscape has moved incrementally, not radically, and nothing found here changes the calculus of *whether* to build the real-embedding L3 now — only what to remember for *when* `PRD.md`'s gating trigger fires. Mainstream production gateways (Azure API Management, GA as of 2026-08-18; LiteLLM; Portkey) now ship genuine embedding-cosine semantic caching as a real, dated, currently-shipping feature — but every one of them still gates hits on a bare similarity threshold plus exact secondary-parameter matching and a TTL, with no entity- or freshness-aware hard gate anywhere in their own documentation; Kelvran's hard-gate requirement remains, if anything, ahead of mainstream production practice, not behind it. Two genuinely new 2026 academic techniques are worth tracking: Krites' asynchronous LLM-judge verification for borderline near-threshold matches (whose own judge design independently re-derives entity+freshness checks, reinforcing rather than replacing Kelvran's hard-gate philosophy) and vCache's formal per-prompt calibrated-threshold framework (a different axis — statistical threshold calibration, not a substitute for a hard gate). Vector-DB infrastructure (Qdrant's native payload-filter/ACORN engine, Milvus's dedicated MinHash-LSH index type) has matured enough that entity/freshness-style hard filters could in principle be enforced natively inside a real ANN index rather than only as today's caller-side post-hoc check — a concrete architectural option for the eventual RFC, not a reason to change anything now. New 2026 academic research (LaCache, a CacheAttack-lineage paper, and a peer-reviewed timing-side-channel paper) confirms cache-collision/poisoning and cache-timing leakage against embedding-based semantic caches remain active, unsolved attack surfaces, and — notably — that none of the defenses these papers themselves propose (response-token consistency checks, key salting, perplexity screening, per-user namespacing) include an entity/freshness hard-gate, meaning the literature has not superseded Kelvran's own approach.

Coverage is uneven, consistent with prior reports' own disclosed convention: of the vendors and systems implied by the original research brief, only Milvus, Qdrant, LiteLLM, Azure API Management, and Portkey (plus GPTCache, whose specific claims here were refuted rather than confirmed) produced surviving evidence. Redis LangCache, TrueFoundry, and Bedrock's/OpenSearch Serverless's own native semantic-cache internals returned zero surviving claims this round and remain genuinely open, not answered "no" — the same disclosed-gap pattern the sibling `gateway-2026-09-06.md` report already established as this directory's convention.

## Findings, ranked

### 1. Mainstream production gateways now ship genuine embedding-cosine semantic caching as a real, dated feature — but every one still gates hits on a bare similarity threshold, validating rather than challenging Kelvran's own hard-gate rule (Awareness only — no build now)

**What:** Three real, currently-documented production/near-production semantic caches were checked directly against their own docs. Azure API Management's `llm-semantic-cache-lookup` policy is GA across **all** APIM tiers (page dated `ms.date: 2026-08-18`), performs lookup based on "vector proximity of the prompt to previous requests and a specified score threshold," and supports OpenAI, Anthropic Messages (API Management v2 tiers), and Google Vertex AI backends. LiteLLM's semantic-cache backends (Qdrant, Valkey, Redis) all ship genuine cosine-similarity scoring against real embedding models (default `text-embedding-ada-002`), gated by a configurable `similarity_threshold` — all three documented backend examples use `0.8`. Portkey's self-hosted semantic cache matches on cosine similarity (default threshold 0.95) via a configurable embedding provider (OpenAI/Azure/Google/Vertex, example default `text-embedding-3-small`) and a vector store (Milvus or Pinecone), running only after an exact-match cache miss. All three are genuine embedding-cosine implementations — the representation Kelvran's own L3-lite deliberately does not use yet.

**Why it matters for Kelvran specifically:** `PRD.md`'s own founding thesis — *"every semantic cache surveyed (GPTCache, Redis LangCache, Portkey's semantic mode) gates reuse on a single similarity threshold — 'close enough' — not on whether the cached answer is still true"* — is not stale as of this research date; it is the accurate, current description of all three real, documented systems checked here. None of the three has shipped an entity- or freshness-aware hard gate on top of the bare threshold: Portkey's own docs (re-verified this round, and cross-checked against its Guardrails product docs and its open-source gateway cookbook, all independently agreeing) describe exactly threshold + exact-match on `model`/`temperature`/`max_tokens`/metadata + a TTL, with zero mention of entity verification or hijacking detection anywhere; LiteLLM's caching backends key their safety purely on the numeric threshold; Azure's policy reference names only the score threshold and the caller-supplied embeddings backend. Note a deliberate scoping distinction: a stronger claim that Azure's docs affirmatively *disclose* "no safeguard beyond the threshold exists" did not survive adversarial vote (0-3) — Azure's docs simply do not discuss additional safeguards either way, which is a weaker, different claim than "confirmed absent," and this finding states only the weaker, verified version.

**Consistent with settled decisions?** Directly reconfirms, does not contradict, `AGENTS.md`'s non-negotiable rule and `THREAT_MODEL.md`'s CacheAttack row (entity/number/date hard-gate + freshness/risk model, similarity threshold never below ~0.9 for open-ended traffic, but never similarity alone). If Kelvran ever builds a real-embedding L3, the bare-threshold pattern these three vendors ship today is the floor to exceed, not a design to imitate.

**2026 landscape grounding:**
- Azure API Management's `llm-semantic-cache-lookup` policy: GA on all APIM tiers, "based on vector proximity of the prompt to previous requests and a specified score threshold," supporting OpenAI, Anthropic Messages, and Google Vertex AI backends [learn.microsoft.com — confirmed 3-0].
- LiteLLM: "embeds the prompt and serves the closest cached response whose cosine similarity clears `similarity_threshold`"; all three documented backends (Qdrant/Valkey/Redis) use `similarity_threshold: 0.8`, confirmed against LiteLLM's own source (`qdrant_semantic_cache.py`'s Qdrant collection config `distance: Cosine`) [docs.litellm.ai — confirmed 3-0].
- Portkey: "matches requests with similar meaning using cosine similarity, not just identical text" (default threshold 0.95), configurable embedding provider and vector store (Milvus/Pinecone), running only after an exact-match miss [portkey.ai — confirmed 3-0].
- Portkey's documented safety model beyond the threshold is exact-match on `model`/`temperature`/`max_tokens`/body params/metadata plus a `max_age` TTL (60s-90-day range) — no entity-verification or hijacking-detection layer is documented anywhere in Portkey's docs, its Guardrails product, or its OSS gateway cookbook [portkey.ai — confirmed 3-0].

**Concrete next step:** none now. When the real-embedding L3 RFC is eventually written (gated per `PRD.md` on real miss-telemetry), cite this finding directly in that RFC's motivation section — evidence that mainstream production practice has not solved this problem is useful ammunition against a future reviewer suggesting "just copy LiteLLM/Portkey's bare-threshold design."

**Effort:** N/A — landscape confirmation only; no code or design change proposed. Revisit only once `PRD.md`'s gating criterion (real miss-telemetry) is met.

### 2. Two genuinely new 2026 academic safety techniques exist beyond "raise the threshold" — neither replaces the entity/freshness hard-gate, and one independently re-derives it (Awareness only — no build now)

**What:** Krites (arXiv:2602.13165, "Asynchronous Verified Semantic Caching for Tiered LLM Architectures," Feb-Mar 2026) proposes an asynchronous LLM-judge verification step that fires only for borderline matches just below the static similarity threshold, stays off the request's critical path, and gates promotion into a reusable "dynamic cache" tier on judge approval. Separately, vCache (arXiv:2502.03771, accepted ICLR 2026) proposes the first semantic cache with a formal, user-defined error-rate guarantee, replacing a single global threshold with an online-learned, per-cached-prompt calibrated threshold requiring no additional training step.

**Why it matters for Kelvran specifically:** Krites' own LLM-judge task specification explicitly checks "intent alignment, entity/constraint consistency (names, locations, time, quantities), and freshness/personalization requirements" — the academic community's own independent answer to "beyond bare threshold" converges on checking entity and freshness signals, the same two axes Kelvran's hard-gate already enforces. This is reinforcement, not a reason to reconsider the hard-gate's design. vCache's contribution is orthogonal: it's about *how the threshold itself is calibrated* (per-prompt, statistically bounded), not about *what else gets checked alongside it* — it doesn't compete with or substitute for an entity/freshness gate; it would, if ever adopted, sit underneath a hard-gate the same way a fixed 0.9 floor does today.

**Consistent with settled decisions?** Neither technique argues for weakening `AGENTS.md`'s hard-gate rule — Krites' judge design is independent external validation that entity+freshness checking is the right axis, not something Kelvran invented in isolation. Caveat: a claim that Krites offers a *formal, provable* security guarantee against collision/hijacking did not survive adversarial vote (0-3). Krites' own validation is a 100-pair spot-check against a real Claude Opus 4.5 judge (99/100 agreement with human labels) plus a trace-driven simulation against a benchmark-derived oracle judge — not a cryptographic or worst-case adversarial bound, and not a disclosed live production deployment. Treat Krites as a promising design idea, not a solved, deployed system.

**2026 landscape grounding:**
- Krites: "When the nearest static neighbor of the prompt falls just below the static threshold, Krites asynchronously invokes an LLM judge to verify whether the static response is acceptable for the new prompt. Approved matches are promoted into the dynamic cache..." [arxiv.org/abs/2602.13165 — confirmed 3-0].
- Krites' own problem framing: "both tiers are commonly governed by a single embedding similarity threshold, which induces a hard tradeoff: conservative thresholds miss safe reuse opportunities, while aggressive thresholds risk serving semantically incorrect responses" [arxiv.org/abs/2602.13165 — confirmed 3-0] — an academic validation of exactly the bare-threshold weakness `PRD.md` already names as the reason this project exists.
- vCache: "the first verified semantic cache with user-defined error rate guarantees for predictable performance," employing "an online learning algorithm to estimate an optimal threshold for each cached prompt" requiring "no additional training step" [arxiv.org/abs/2502.03771 — confirmed 3-0, ICLR 2026-accepted].

**Concrete next step:** none now. Worth a one-line pointer in a future real-embedding L3 RFC's "Alternatives Considered" section — Krites-style async judge as a possible *complement* to (never a replacement for) the hard-gate; vCache-style per-prompt calibration as a possible refinement to a fixed 0.9-equivalent floor. Not worth prototyping before real miss-telemetry exists per `PRD.md`'s own gating rule.

**Effort:** N/A — tracked for a future RFC's literature section, not actionable today.

### 3. Vector-DB/ANN infrastructure has matured enough to enforce entity/freshness-style hard filters natively inside the index itself — a concrete architectural option for whenever the gate is met, not required by today's lexical L3-lite (Awareness only — no build now)

**What:** Qdrant's Filterable HNSW extends the HNSW graph with additional edges based on indexed payload, and its ACORN algorithm (shipped v1.16.0) traverses to second-hop neighbors when a point's direct neighbors are excluded by a payload filter — explicitly documented as the fix for combined strict filters or heavy soft-deletion causing disconnected graph components (a cited benchmark shows 97.20% accuracy at 13.86ms with ACORN vs. 53-71% without, on a 5M-vector/2-filter test). Qdrant payload indexes natively support `datetime` (range filtering, since v1.8.0) and `keyword`/`uuid` (match filtering, since v1.11.0) field types, combined with vector search rather than applied as a post-hoc full-scan filter. Separately, Milvus's native `MINHASH_LSH` index requires `metric_type: MHJACCARD` on a `BINARY_VECTOR` field and explicitly documents that MinHash-signature similarity is architecturally incompatible with standard `JACCARD`/`L2`/`COSINE` metrics.

**Why it matters for Kelvran specifically:** if a real-embedding L3 is ever built, entity-identity and freshness/timestamp constraints could in principle be expressed as index-accelerated structured filters evaluated *during* the same ANN traversal that finds similarity candidates — a genuinely different implementation shape from today's caller-side, post-hoc hard-gate check (`LexicalCandidate`'s fields, checked in `dataplane.go` after `LexicalCache.Search` returns candidates, per `AGENTS.md`'s "Cache must never import `adapter`" boundary). This is worth knowing about, not a reason to prefer it over the current design, and not something today's lexical L3-lite needs at all (it doesn't use an ANN index). Milvus's own MinHash-LSH documentation independently corroborates, from the vendor side, the same structural distinction `THREAT_MODEL.md`'s 2026-09-13 correction already established from real measurement: lexical/set-based similarity (MinHash/Jaccard) and embedding-cosine similarity are different representations requiring different index families entirely — not the same representation at different thresholds. This reinforces why `l3MinSimilarity`'s "~0.9 floor calibrated against lexical Jaccard, never embedding-cosine" caveat is the right caution to keep, not an oversight to paper over by reusing the same number against a future embedding metric.

**Consistent with settled decisions?** No conflict — Kelvran's cache remains in-process/no-ANN by design at today's scale (`docs/decisions/0002-cache-embedded-in-gateway.md`), and this finding does not argue for changing that. Recorded purely because the research brief asked about vector DB/ANN-index options specifically.

**2026 landscape grounding:**
- Qdrant ACORN: "During traversal, it looks beyond direct neighbors to neighbors of neighbors (second hop) when direct neighbors are filtered out — trading some performance for improved accuracy," available as of v1.16.0, for combined strict filters or heavy soft-deletion [qdrant.tech — confirmed 3-0].
- Qdrant payload indexes: support `keyword`, `integer`, `float`, `bool`, `geo`, `datetime`, `text`, and `uuid` field types, with `datetime` affecting range filtering and `keyword`/`uuid` affecting match filtering, combined with vector search via the Filterable HNSW extension rather than post-hoc filtering [qdrant.tech — confirmed 3-0].
- Milvus MINHASH_LSH: "standard metrics such as JACCARD, L2, or COSINE cannot be directly applied to compare" MinHash signatures; `metric_type: MHJACCARD` on a `BINARY_VECTOR` field is required [milvus.io — confirmed 2-1].

**Concrete next step:** none now. Worth citing in a future RFC's Detailed Design section as one candidate implementation shape for entity/freshness enforcement (index-native filter vs. today's caller-side check) — a design-space note, not a recommendation to adopt either shape yet.

**Effort:** N/A — infrastructure-maturity awareness only.

### 4. Cache-collision/poisoning attacks against embedding-based semantic caches remain an active, unsolved 2026 academic threat — and none of the proposed defenses include an entity/freshness hard-gate, reinforcing rather than reducing the case for Kelvran's own requirement (Awareness only — no build now)

**What:** LaCache (arXiv:2608.01718, Aug 2026) frames its target vulnerability explicitly as "cache-collision attacks, wherein an adversary pollutes the cache by injecting crafted queries, corrupting responses to subsequent legitimate requests" against embedding-based semantic caches — the same general attack shape as `THREAT_MODEL.md`'s CacheAttack/near-duplicate-hijacking row. LaCache's own defense is structural, not gate-based: it additionally checks whether a small number of speculatively decoded *output* tokens match, not just whether the query embedding is close. Separately, "From Similarity to Vulnerability: Key Collision Attack on LLM Semantic Caching" (arXiv:2601.23088) — a paper in the same CacheAttack lineage `THREAT_MODEL.md` already cites — evaluates exactly three defenses (key salting, perplexity screening at cache-insertion time, per-user/per-session cache namespacing) and finds none of them inspects entities or content freshness at all; its best-performing lightweight defense (salting) is explicitly described as only "consistent with its role as a lightweight mitigation rather than a complete defense."

**Why it matters for Kelvran specifically:** this is direct, dated confirmation that the threat class `THREAT_MODEL.md`'s CacheAttack row already treats seriously remains an open academic problem in 2026 — and, importantly, that none of the field's own proposed defenses have converged on an entity/freshness hard-gate as a mitigation. That is not evidence the hard-gate is unnecessary; it's evidence the hard-gate is Kelvran's own contribution to a problem the literature has not yet solved from a different angle (response-consistency checks, salting, namespacing) — consistent with `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`'s own honest admission that "none of the three papers [cited in `THREAT_MODEL.md`] propose or test entity/number/date extraction as their defense... [it] is real and used in industry practice... layered onto `THREAT_MODEL.md`'s own requirement." This sweep found two additional, more recent papers and the same pattern holds.

**Consistent with settled decisions?** Directly reconfirms `AGENTS.md`'s hard-gate rule and `THREAT_MODEL.md`'s CacheAttack row; adds two new dated academic citations to the evidence base `docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md` already assembled from CacheAttack/KeyPooling/"When Cache Poisoning Meets LLM Systems." Two important scoping caveats: a claim that the 2601.23088 paper validated its attack against real, currently-marketed AWS Bedrock and Azure API Management production services did **not** survive adversarial vote (1-2) — treat the attack's real-world applicability against those named commercial services as unconfirmed by this pass, not proven. A claim that sweeping the similarity threshold from 0.75-0.90 fails to close the vulnerability also did not survive vote (1-2) — this document does not assert that raising the threshold is proven ineffective, only that the paper's own tested defenses (salting/perplexity/namespacing) don't touch entities or freshness.

**2026 landscape grounding:**
- LaCache: "existing schemes are fundamentally vulnerable to cache-collision attacks, wherein an adversary pollutes the cache by injecting crafted queries, corrupting responses to subsequent legitimate requests"; its fix "additionally checks the cache hit of its first k (speculatively) decoded tokens" rather than only the query [arxiv.org/abs/2608.01718 — confirmed 3-0, both claims].
- "From Similarity to Vulnerability" (arXiv:2601.23088): exactly three evaluated defenses (key salting §7.1, perplexity screening at insertion §7.2, per-user cache isolation §7.3), zero mentions of "entity" or "freshness"/"staleness" anywhere in the full paper text; salting "slightly reduces HR and ISR, consistent with its role as a lightweight mitigation rather than a complete defense" [arxiv.org/abs/2601.23088 — confirmed 3-0].

**Concrete next step:** none now. Cite both papers alongside the existing CacheAttack/KeyPooling/NDSS trio in the eventual real-embedding L3 RFC's "cited papers, verified" section, updating the "none of the papers propose entity extraction as their defense" observation with these two additional, more recent confirmations.

**Effort:** N/A — literature-tracking only.

### 5. A distinct, newer attack surface for embedding-based caches specifically: timing side-channels can leak cross-tenant prompt content via the cache hit/miss signal itself (Awareness only — no build now)

**What:** "The Early Bird Catches the Leak" (arXiv:2409.20002, peer-reviewed, accepted to IEEE Transactions on Information Forensics and Security) demonstrates timing side channels in LLM serving systems "specifically targeting the Key-Value (KV) cache and semantic cache widely used to enhance LLM inference performance... [that] can be exploited to infer both confidential system prompts and those issued by other users." Its "Peeping Neighbor Attack" measures response-latency differences between cache hits and misses to recover other tenants' cached requests/system prompts with 81.4% accuracy after one attack request, rising to 95.4% after five. The paper studies GPTCache (an embedding-based semantic cache) directly and names Azure OpenAI Service, Amazon Bedrock, and Alibaba PAI as real production offerings that natively support semantic caching.

**Why it matters for Kelvran specifically:** this is a genuinely new risk category — orthogonal to CacheAttack-style similarity-collision hijacking — concerning the response-timing signature of a semantic-cache lookup, which is architecturally different for a real embedding-based lookup (a network round-trip to an embedding API, or a vector-index traversal, each with its own timing profile) than for today's in-process lexical MinHash/Jaccard scan. Important scoping caveat: an attempt to generalize this finding as applying equally, "independent of whether the cache's similarity metric is lexical or embedding-cosine," to Kelvran's *current* L3-lite did **not** survive adversarial vote (0-3) — this document therefore does not claim the finding transfers to today's shipped lexical L3-lite as-is. (Kelvran already has a related but distinct, already-tracked, low-severity consideration — `X-Kelvran-Overhead-Duration-Ms`, per `THREAT_MODEL.md`'s 2026-09-14 CacheAttack-row addition.) What this finding does establish, confirmed, is that a real embedding-based L3 would introduce its *own* additional timing-side-channel surface (an embedding-generation call and/or vector-index search, each with a measurable, potentially cache-hit-correlated timing signature) that today's lexical L3-lite does not have in the same form — worth a dedicated timing-analysis pass in the eventual RFC, not an assumption that the existing header-disclosure mitigation automatically covers it.

**Consistent with settled decisions?** Additive — a new consideration for the eventual real-embedding L3 RFC's threat-model section. Does not touch, or require any change to, today's shipped lexical L3-lite or its existing `X-Kelvran-Overhead-Duration-Ms` disclosure.

**2026 landscape grounding:**
- "Timing side channels in LLM serving systems... specifically targeting the Key-Value (KV) cache and semantic cache widely used to enhance LLM inference performance... can be exploited to infer both confidential system prompts and those issued by other users" [arxiv.org/abs/2409.20002 — confirmed 3-0]. Studies GPTCache (embedding similarity via `albert-duplicate-onnx`, 0.8 cosine threshold) directly; names Azure OpenAI Service, Amazon Bedrock, and Alibaba PAI (EAS) as real production semantic-caching offerings.

**Concrete next step:** none now. Add a one-line forward-pointer in the eventual real-embedding L3 RFC's threat-model section noting that the embedding-generation/vector-search call itself needs its own timing-side-channel review, separate from and in addition to the existing lexical-L3 `X-Kelvran-Overhead-Duration-Ms` disclosure.

**Effort:** N/A — new threat-model consideration for a future RFC, not actionable today.

### 6. FreshCache's probabilistic, per-content-type error-budget freshness model is a genuinely different paradigm from a binary fresh/stale gate — worth knowing about, not urgent (Awareness only — no build now)

**What:** FreshCache (arXiv:2607.04281, July 2026) reframes semantic-cache reuse as a probabilistic, risk-constrained decision rather than a hard fresh/stale binary: it estimates the probability that a cached result is stale via a fitted exponential-decay model enhanced by a learned MLP, and approves a cache hit only when that probability falls under a per-content-type error budget (ε=0.10 for answers, ε=0.20 for URL lists, ε=0.35 for page content).

**Why it matters for Kelvran specifically:** `gateway/ARCHITECTURE.md`'s Cache Subsystem description names "a freshness/risk model, and a hard bypass for volatile queries" for L3-lite, but at a materially coarser grain than FreshCache's continuous, per-content-type probabilistic error budget. This is worth remembering as a possible refinement (a probabilistic staleness estimate supplementing a binary volatile/not-volatile bypass) for whenever the real-embedding L3 gate is met. It does not bear on, or argue against, the entity/freshness hard-gate itself — FreshCache's mechanism is a *freshness* model specifically, not a substitute for entity verification, and its per-tier error budgets are calibrated for open-web retrieval content types (answers/URL lists/page content), not necessarily Kelvran's own traffic shape.

**Consistent with settled decisions?** No conflict — purely additive design-space awareness for a future RFC's freshness-model section.

**2026 landscape grounding:**
- "Before approving a cache hit, FreshCache estimates the probability that the cached result is stale using a fitted exponential decay model enhanced by a learned MLP, and approves reuse only when that probability falls below a per-tier error budget across answers (ε=0.10), URL lists (ε=0.20), and page content (ε=0.35)" [arxiv.org/abs/2607.04281 — confirmed 3-0].

**Concrete next step:** none now. Worth a one-line mention in a future RFC's freshness-model design alternatives.

**Effort:** N/A — design-space awareness only.

## Caveats

- Eight claims were explicitly refuted during adversarial verification and are excluded from the findings above, but are worth naming for transparency. Two GPTCache claims (its `similarity_threshold` configuration pattern, and its use of real dense embeddings) both refuted 0-3 — this sweep found no reliable confirmation of GPTCache's current tooling maturity one way or the other, so it should be treated as an open question, not settled by either the confirmed or refuted framing. A claim that the CacheAttack-lineage paper (2601.23088) validated its attack against real, currently-marketed AWS Bedrock and Azure production services (1-2) and a claim that sweeping the similarity threshold 0.75-0.90 fails to close the vulnerability (1-2) both fell short of the 3-vote bar — treat the paper's real-world applicability and the threshold-sweep conclusion as unconfirmed, not proven. A claim generalizing the timing-side-channel finding as metric-independent and equally applicable to Kelvran's current lexical L3-lite was refuted 0-3 (see Finding 5).
