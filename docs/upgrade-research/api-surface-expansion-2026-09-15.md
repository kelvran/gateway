# API Surface Expansion Beyond Chat Completions — Research Report

**Date:** 2026-09-15
**Scope:** `gateway/internal/adapter/*` (canonical schema + per-provider `ToProvider`/`FromProvider` pairs), `gateway/internal/gateway/dataplane/dataplane.go` (`Pipeline.HandleChatCompletion`), `gateway/cmd/gateway/main.go` (HTTP route table), `gateway/internal/costaccounting`, `gateway/internal/guardrail`. Confirmed by direct code inspection: the gateway registers exactly one data-plane route, `mux.HandleFunc("/v1/chat/completions", ...)`, plus `/healthz` and an `/admin/*` control-plane surface (`internal/admin/admin.go`) — there is no `/v1/embeddings`, `/v1/moderations`, `/v1/rerank`, `/v1/images/*`, `/v1/audio/*`, `/v1/fine_tuning/*`, `/v1/files`, or `/v1/assistants`/`/v1/responses` route anywhere in this codebase. `adapter.Adapter`'s two methods (`ToProvider(ChatRequest) (any, error)` / `FromProvider(any) (ChatResponse, error)`) are hardcoded to the chat-completions canonical schema, not generic. Explicitly **not** re-researched here — already deeply covered and both settled `not_yet`: realtime/bidirectional voice WebSocket APIs (`docs/upgrade-research/gateway-realtime-multimodal-2026-09-13.md`) and native provider Batch APIs (`docs/upgrade-research/gateway-batch-api-2026-09-13.md`). Guardrail/detector plugin extensibility (a different question — how server-side `Detector`s plug into `guardrail.Engine`) was independently settled the same day this report was written (`docs/upgrade-research/guardrail-plugin-extensibility-2026-09-15.md`) and is cited, not re-litigated.
**Method:** Primary-source research against current (2026) vendor API references (OpenAI, Anthropic/Claude, Google Gemini, AWS Bedrock, Cohere, Voyage AI) and peer-gateway documentation (LiteLLM, Portkey, Kong AI Gateway), cross-checked against this repo's own code, `ARCHITECTURE.md`, `DECISIONS.md`, and prior upgrade-research reports. Several vendor pages 301-redirected to new canonical domains mid-fetch (`platform.openai.com` → `developers.openai.com`; `docs.anthropic.com` → `platform.claude.com`) — followed and fetched at the redirect target, noted inline where the redirect itself is informative (e.g. it independently corroborates how fast this API surface is still moving in 2026).

## Executive Summary

The non-chat LLM API landscape is large, real, and unevenly proxied by peer gateways in 2026: embeddings (OpenAI/Gemini/Bedrock, but **not** Anthropic, which has no native embeddings model and officially recommends third-party Voyage AI), reranking (Cohere/Bedrock/Voyage, but **not** OpenAI or Gemini), moderation/content-safety (OpenAI has a dedicated endpoint; Gemini and Anthropic do not), fine-tuning + Files APIs (control-plane job/asset management, not per-request traffic), and OpenAI's Assistants API (confirmed **sunset 2026-08-26**, replaced by the Responses API). LiteLLM proxies nearly all of these as first-class unified endpoints; Portkey and Kong cover a real but uneven subset, and Kong's own marketing notably treats embeddings as *infrastructure for its own semantic cache* rather than as a client-facing endpoint to proxy — the same two-different-uses-of-embeddings split this research independently found inside Kelvran's own codebase. Of everything examined, **embeddings is the standout build_now-eligible candidate**: it is the single closest structural match to Kelvran's existing chat-completions pipeline (synchronous JSON request/response, no streaming, purely input-token billing that `costaccounting.Calculator` already prices correctly with zero code changes), and — unlike every other surface in this report — it already has a concrete, if narrow, internal demand signal: `evals/scripts/validate_embedding_gate.py` calls AWS Bedrock's Titan-v2 embedding model directly via `boto3`, entirely bypassing Kelvran's own gateway. Reranking is the second most defensible candidate but requires a genuinely new pricing unit (`search_units`, not tokens) and, for Cohere/Voyage specifically, provider relationships Kelvran has never built. Moderation, fine-tuning, Files, images, and non-realtime audio are all real and current but each has a specific, named reason to stay `not_yet` — weak/duplicate rationale (moderation vs. Kelvran's own guardrail engine), the same persistent-state cost the Batch report already priced out (fine-tuning/Files), or a canonical-schema/wire-format mismatch (images' binary output, audio's multipart upload) that none of the cheaper candidates share. No surface in this report has a confirmed *paying-customer* demand signal — this report establishes feasibility and relative cost ranking, not need.

## Findings

### Finding 1 — The 2026 non-chat LLM API landscape is real and broad, but peer-gateway coverage of it is uneven and often page-scoped, not universal
**Confidence: high** (multiple primary + peer-gateway sources, cross-corroborated)

LiteLLM's own docs confirm the richest coverage found in this pass: unified `/embeddings`, `/moderations`, `/rerank`, `/images/{edits,generations,variations}`, `/audio/{transcriptions,speech}`, `/fine_tuning`, and `/files` endpoints, each fanning out to multiple real providers (e.g. `/embeddings` alone spans OpenAI, Bedrock's Titan/Cohere/TwelveLabs, Cohere direct, NVIDIA NIM, HuggingFace, Mistral, Gemini, Vertex AI, Voyage, and Nebius). Portkey's own AI Gateway docs confirm Images, Audio, Fine-tuning, Batch, Files, Moderations, and OpenAI-specific Assistants as supported unified endpoints — but that same page made no mention of embeddings or rerank at all, which this report treats as a page-scope gap, not a confirmed absence (Portkey is independently known, including from this repo's own `gateway-batch-api-2026-09-13.md` Finding 1, to wrap provider-native APIs broadly). Kong AI Gateway's own marketing page is the most telling asymmetry: it explicitly ships "AI Semantic Cache" — an embeddings-*consuming* feature — and multiple named content-safety guardrail policies (AI Prompt Guard, AI Sanitizer, AI AWS/Azure/GCP-native guardrail integrations), but never mentions proxying an embeddings or rerank *endpoint* itself anywhere on that page. This exact split — embeddings/moderation-as-internal-infrastructure vs. embeddings/moderation-as-proxied-client-facing-endpoint — is not a peer-gateway-only phenomenon; it recurs inside Kelvran's own codebase (Findings 2 and 3 below) and is the organizing distinction this whole report uses.

**build_now / not_yet:** N/A — landscape/framing finding, feeds every finding below rather than being a build decision on its own.

### Finding 2 — Embeddings: the strongest build_now-eligible candidate — closest structural match to Kelvran's existing pipeline, and Kelvran's own evals subsystem already needs one today
**Confidence: high** (primary vendor sources for API shape/billing; direct code inspection for the internal-demand and cost-accounting claims)

OpenAI's `/embeddings` endpoint (`text-embedding-3-small`/`-large`, legacy `ada-002`) is a single synchronous `POST`, JSON in/out, no streaming, with a response `usage` object carrying only `prompt_tokens`/`total_tokens` — there is no completion-token concept at all, since an embedding call generates a vector, not text. Google's Gemini embeddings (`gemini-embedding-2`, current as of April 2026) go further: genuinely multimodal input (text, image, audio, video, PDF in a single `embedContent` call), plus a separate async Batch variant priced at "50% of the default Embedding price" — but still a synchronous `embedContent` call for the interactive path. AWS Bedrock exposes embedding models (Titan, Cohere) via the same `InvokeModel` primitive Kelvran already authenticates against for Bedrock chat, just a different operation than the `Converse` API `bedrock.go` targets today. **Anthropic has no native embeddings model at all** — its own docs state this plainly ("Anthropic does not offer its own embedding model") and officially recommend Voyage AI, a third party, whose HTTP API happens to mirror OpenAI's response shape almost exactly (`object: "list"`, `data[].embedding`, `usage.total_tokens`). This is a real structural asymmetry an embeddings feature would inherit that chat completions never had: every one of Kelvran's four existing chat adapters implements the same interface, but an embeddings feature would only ever have three real "native" adapters (OpenAI, Gemini, Bedrock) plus, if pursued, a wholly new Voyage-direct integration for Anthropic-style callers — not a gap in Kelvran's engineering, a gap in Anthropic's own product.

**Why this is the cheapest candidate in this report, concretely:** `costaccounting.Calculator.Calculate(model, usage)` (confirmed by reading `costaccounting.go`) already computes `cost = freshPromptTokens*PromptPerToken + CompletionTokens*CompletionPerToken` — an embeddings `Usage{PromptTokens: N, CompletionTokens: 0}` prices correctly against the *existing* `PriceTable` type with **zero changes to that package**. Embeddings calls are also a strictly better cache-fit than chat completions: they are pure, deterministic functions of (model, input) with no sampling temperature, so an exact-match L1 cache hit is *more* trustworthy for embeddings than for a chat completion, not less. The real cost lives elsewhere: `adapter.Adapter`'s two methods are hardcoded to `ChatRequest`/`ChatResponse` (confirmed in `types.go`), so embeddings needs its own additive interface and canonical request/response types (e.g. `EmbeddingRequest{Model, Input, ...}`/`EmbeddingResponse{Data, Usage}`) — cheap and precedented (this codebase has added `Parts`, `CacheControl`, `ReasoningBlocks`, and `ToolChoice` to the canonical schema additively before, per `ARCHITECTURE.md`'s own normalization-point history), but real, non-zero work. `dataplane.HandleChatCompletion` is a single ~1,600-line function (confirmed by direct reading) whose cache-key derivation, guardrail scan, and finalize/telemetry logic are all written directly against `ChatRequest.Messages` — an embeddings path needs its **own** pipeline function, not a retrofit of that one, though it can reuse the same underlying generic sub-packages (`identity` verifier, `budget.Tracker`, `router.Router`, `ratelimit`, `costaccounting.Calculator`) that `HandleChatCompletion` itself calls, none of which are chat-schema-specific.

**Internal demand signal, honestly scoped:** `evals/scripts/validate_embedding_gate.py` calls `amazon.titan-embed-text-v2:0` directly via a raw `boto3.invoke_model` call, entirely outside Kelvran's own gateway — no centralized auth, budget, audit trail, or cache. This is real, current, and concrete, but it is explicitly a one-off research script (its own doc comment: "lives OUTSIDE the `evals` Python package... never a permanent CLI feature"), not production customer traffic — treat it as evidence that *when Kelvran's own team needs embeddings, the gateway is not where they reach for them today*, not as a confirmed customer-demand trigger. Separately, `docs/upgrade-research/cache-semantic-embedding-reconsideration-2026-09-13.md`'s own "no Go-native ML runtime" blocker (which keeps a real embedding-based cache L3 `not_yet`) is about computing embeddings **locally in-process inside the Go binary** — it has no bearing on a client-facing proxy route, which is network-bound provider translation exactly like every existing chat adapter, not local inference. Do not let that blocker leak into this feature's analysis by association.

**build_now / not_yet:** `build_now`-eligible for a scoped RFC + adapter-interface prototype (cheap, additive, real internal signal, zero blast radius to the existing chat path); `not_yet` for general customer availability absent a confirmed external demand signal, which this research pass did not find.

### Finding 3 — Moderation/content-safety endpoints: real and current, but only one of Kelvran's four adapters even has one, and Kelvran already ships a materially more capable in-gateway alternative for a different integration shape
**Confidence: high** (primary vendor sources; direct code inspection for Kelvran's existing guardrail architecture)

OpenAI's `/moderations` endpoint (`omni-moderation-latest`, multimodal text+image input) is a synchronous, single-call classifier returning `flagged`/`categories`/`category_scores` — this pass could not confirm its pricing from the fetched docs (flag this as unverified, not "free," pending independent re-check). Google's Gemini API has no standalone moderation endpoint at all — safety signals are embedded *inside* `generateContent` responses (`PromptFeedback`, already handled by `gateway/internal/adapter/gemini/gemini.go` per that file's own comment), never a separately callable classifier. Anthropic has no standalone moderation endpoint either. AWS Bedrock's `ApplyGuardrail` operation *is* a real, standalone moderation-shaped call — and Kelvran already integrates it, but as a server-side `guardrail.bedrockguard.Detector` plugged into `guardrail.Engine`'s pre/post-call scan (per `ARCHITECTURE.md`'s Guardrails Subsystem section and the same-day `guardrail-plugin-extensibility-2026-09-15.md` report), never as a client-facing proxied endpoint. This is a materially different, and for Kelvran's own product positioning arguably more valuable, integration shape: a Detector runs on *every* real chat-completion request Kelvran already routes, not on a standalone classification call a caller would have to remember to make separately. Notably, `guardrail.Engine.Check(ctx, text string) Verdict` (confirmed in `engine.go`) already takes a plain string, decoupled from `ChatRequest` entirely — so if Kelvran ever did add embeddings/rerank input scanning, the *existing* guardrail engine would generalize to it for free, no new abstraction needed; this is a genuine non-gap worth naming even though it isn't this finding's main subject.

Proxying OpenAI's `/moderations` as a new client-facing Kelvran route is a different, narrower question than either of the above: it would only ever serve one of Kelvran's four provider relationships (OpenAI), duplicates a capability Kelvran already ships in a different, arguably-better shape (guardrails), and this research pass found no demand signal — internal or external — for a standalone moderation-classification proxy independent of an actual chat completion.

**build_now / not_yet:** `not_yet`. Structurally cheap in isolation (sync request/response, no cache/cost-accounting complexity since there's no generation), but weak, largely-duplicative rationale and asymmetric provider coverage (1 of 4 adapters). Trigger: a concrete customer ask for standalone content classification independent of any chat completion Kelvran routes — none found today.

### Finding 4 — Reranking (Cohere/Bedrock/Voyage): a real, growing RAG-adjacent pattern, but its billing unit doesn't fit `costaccounting`'s existing model, and two of its three providers are new relationships Kelvran has never built
**Confidence: high** (primary vendor sources for API shape/billing; direct code inspection for the cost-accounting mismatch)

Cohere's Rerank v2 (`POST https://api.cohere.com/v2/rerank`) takes a `query` and a `documents` list and returns an ordered `results` array of `{index, relevance_score}` — a single synchronous call, no streaming, billed via `meta.billed_units.search_units`, **not** input/output tokens. AWS Bedrock ships a genuinely standalone `Rerank` operation (in the `agent-runtime` API namespace, text-only, usable directly or from inside Knowledge Bases' `Retrieve`/`RetrieveAndGenerate`) — this reuses the *same* AWS/Bedrock auth relationship Kelvran's existing `bedrock` adapter already has, just a different operation than `Converse`, making it the cheapest of the three provider paths if this is ever pursued. Voyage AI — Anthropic's own recommended embeddings partner — also ships `rerank-2.5`/`rerank-2.5-lite` rerankers, called via `rerank()` in the same SDK as its embeddings. Neither OpenAI nor Gemini ships a rerank endpoint of any kind, so unlike embeddings (3 of 4 existing adapters have a native path), rerank has genuinely no home in two of Kelvran's four existing provider adapters and would need Cohere-direct and/or Voyage-direct as wholly new provider integrations — the same category of new-relationship cost as onboarding a brand-new chat provider, just for a narrower capability.

The concrete architectural mismatch this report's cost-accounting reading surfaced: `costaccounting.PriceTable`/`Calculator` (per Finding 2's same code reading) is hardcoded to a per-token `PromptPerToken`/`CompletionPerToken` shape — Cohere's `search_units` billing doesn't decompose into that shape at all; a rerank feature would need a genuinely new pricing *dimension* inside `costaccounting`, not just a new `PriceTable` row, unlike embeddings which slots into the existing shape for free. LiteLLM ships `/rerank` as a first-class unified endpoint (confirmed directly); Portkey's own docs page fetched in this pass did not surface rerank (page-scope gap, per Finding 1, not confirmed absence); Kong's fetched marketing page did not mention it at all. No demand signal, internal or external, was found in Kelvran's own corpus.

**build_now / not_yet:** `not_yet`. If ever pursued, start with Bedrock's `Rerank` operation specifically (reuses an existing provider relationship, mirroring `gateway-batch-api-2026-09-13.md`'s own "passthrough-first, cheapest provider first" precedent) rather than Cohere/Voyage-direct, and treat the new pricing-dimension work in `costaccounting` as a named precondition, not an afterthought.

### Finding 5 — Fine-tuning management and Files APIs: the same persistent-state cost `gateway-batch-api-2026-09-13.md` already priced out, plus a control-plane-vs-data-plane mismatch that weakens the case even further for fine-tuning specifically
**Confidence: high** (direct cross-reference to this repo's own prior settled research, plus primary-source confirmation of Anthropic's Files API mechanics)

This report deliberately does not re-derive `gateway-batch-api-2026-09-13.md`'s Finding 5 (real job-state tracking without caller-side polling requires a persistent queue/poller/crash-recovery subsystem Kelvran's zero-persistence architecture doesn't have) — fine-tuning job management (create/list/cancel/retrieve against OpenAI/Bedrock/Vertex fine-tuning APIs) is architecturally the *same* async submit/poll/retrieve job shape Batch already is, and that report's cost analysis applies unchanged. Files APIs (OpenAI `/v1/files`, Anthropic's now-GA Files API) are a shared *dependency* of fine-tuning, batch, and (per Anthropic's own docs) the code-execution tool and vision/document inputs — standalone, a Files proxy has no value; it only matters as input plumbing for a consuming feature this report otherwise finds `not_yet`.

One new, non-obvious wrinkle beyond what the Batch report already covered: fine-tuning is inherently an infrequent, off-hot-path *control-plane* action — train a custom model once, then serve production traffic against it for months — not a repeated per-request data-plane call. The operational argument the Batch report used to justify even a "thin passthrough" tier (centralized auth/audit across *many* repeated calls, Finding 7 of that report) is much weaker here, since there's comparatively little ongoing call volume to centralize for an action a given customer might take a handful of times total. Separately, Anthropic's Files API (confirmed GA as of this pass, out of its `files-api-2025-04-14` beta) has a real, specific security wrinkle worth recording now even though the feature itself is deferred: **files are scoped to an entire workspace, not to an end user, conversation, or virtual key** — Anthropic's own docs state plainly "any API key with access to a workspace can access any files uploaded to that workspace" and explicitly warn "never accept `file_id` values from end users." This collides directly with Kelvran's own per-virtual-key multi-tenant isolation model (the same category of concern `THREAT_MODEL.md` already tracks for cache cross-tenant isolation) — if a Files-consuming feature (fine-tuning, or a future Anthropic-code-execution proxy) is ever pursued, this workspace-vs-tenant mismatch is a named precondition to design around, not a detail to discover live.

**build_now / not_yet:** `not_yet` for both, for the same reasoning `gateway-batch-api-2026-09-13.md` already established for Batch, doubly so for fine-tuning given the low call-frequency argument above. Precondition to revisit: same as Batch's — if Kelvran ever builds a persistent datastore for an unrelated reason, re-evaluate.

### Finding 6 — OpenAI's Assistants API is confirmed dead (sunset 2026-08-26); its replacement, the Responses API, is a genuinely mixed case whose *stateless* mode already resembles infrastructure Kelvran has built for a different provider's different feature
**Confidence: high** for the sunset date and Responses API mechanics (primary source, direct fetch); **medium** for the ReasoningBlocks-reuse observation, since that is this report's own architectural synthesis, not an externally-sourced claim

OpenAI's own migration guide states plainly: "The Assistants API was officially sunset on August 26, 2026, and is no longer available" — any internal notes, roadmap assumptions, or prior research anywhere in this repo that still reference a future Assistants API integration are stale as of three weeks before this report and should be treated as such. Its replacement, the Responses API, is structurally a mixed case rather than a clean "compatible" or "incompatible" verdict: at the wire level, a single basic call still resembles Chat Completions (one request, one generation — parallel `n`-completions were removed), but state handling is a genuine three-way choice the caller makes per request: (a) `previous_response_id` lets OpenAI manage prior context server-side (this does **not** reduce cost — "all previous input tokens for responses in the chain are billed as input tokens" every time); (b) the caller replays prior `output` items itself, fully client-managed; or (c) `store: false` disables server-side storage entirely, and to preserve reasoning quality in that mode the API returns **encrypted reasoning content the caller stores and replays verbatim** on the next turn.

Option (c) is the interesting structural finding: it is, mechanically, the same opaque-ciphertext round-tripping pattern Kelvran **already ships today** for a different provider's different feature — `adapter.Message.ReasoningBlocks`' `Redacted`/`Data` fields (per `ARCHITECTURE.md`'s reasoning-content normalization section) already require callers to echo an opaque, provider-issued, never-interpreted blob back on subsequent turns for Anthropic/Bedrock's Claude Messages API. If Kelvran ever builds an OpenAI Responses adapter, its stateless mode maps onto infrastructure Kelvran has already built and hardened for an unrelated reason — a real head start, not a hypothetical one. What this does **not** solve: Responses' actual differentiator — the reason anyone would reach for it over Chat Completions at all — is its "agentic by default" bundle of hosted tools (web search, code interpreter, file search, computer use, image generation, remote MCP connectors) executing *server-side, within the span of one API request*. Kelvran's value-add (cache/budget/guardrail checks on the request and response) never sees inside that server-side execution loop; proxying the outer call is easy, but Kelvran gains no additional guarantee over what a bare, unproxied call to OpenAI would already provide — the same "thin passthrough adds centralized auth/audit but no incremental product guarantee" conclusion `gateway-batch-api-2026-09-13.md` already reached about Batch passthroughs.

**build_now / not_yet:** `not_yet`. No adapter, RFC, or demand signal exists for Responses today. Record the Assistants-sunset fact now as a real, actionable correction (stop citing/planning around Assistants API anywhere in this repo), and record the ReasoningBlocks-reuse observation as a concrete design head start for whenever a Responses adapter is actually proposed.

### Finding 7 — Image generation and non-realtime audio (transcription/TTS): real, current, peer-proxied surfaces that break Kelvran's canonical-schema and wire-format assumptions in ways embeddings/rerank don't
**Confidence: medium** (provider/model names and general shape confirmed via peer-gateway sources; this pass could not independently verify per-model billing mechanics for images, flagged honestly below)

LiteLLM confirms unified `/images/{generations,edits,variations}` spanning OpenAI (DALL-E, `gpt-image-1`), Gemini (Imagen), and Stable Diffusion, and `/audio/{transcriptions,speech}` for speech-to-text/text-to-speech; Portkey's own docs independently corroborate both as supported unified endpoints (naming DALL-E/`gpt-image-1`/Stable Diffusion for images explicitly). These are explicitly **distinct** from the already-settled realtime-voice WebSocket surface (`gateway-realtime-multimodal-2026-09-13.md`) — image generation and non-realtime transcription/TTS are ordinary synchronous REST calls, not persistent bidirectional sessions, so none of that report's session-state/resumption-token findings apply here.

Two separate structural mismatches, neither shared with embeddings/rerank:

1. **Canonical response schema.** `adapter.ChatResponse.Choices[].Message.Content` is a string. Kelvran's canonical schema already has a multimodal *input* type (`ContentPart`, per the multimodal-content RFC `gateway-realtime-multimodal-2026-09-13.md`'s Finding 4 already confirmed on the input side), but no multimodal *output* type — an image-generation response (base64 or URL image data) has nowhere to live in the existing `ChatResponse` shape and would need a wholly new canonical response type, not an additive field the way `ReasoningBlocks`/`Parts` were.
2. **Wire format.** `chatCompletionsHandler` (confirmed in `main.go`) unconditionally does `json.Unmarshal(body, &req)` — every existing Kelvran route assumes a JSON body. Audio transcription/TTS's native shape is `multipart/form-data` file upload, a different HTTP-layer parsing concern the existing handler doesn't have any precedent for at all, smaller in scope than the schema question but still real, non-zero engineering.

This pass could not independently confirm the specific billing mechanism for image models (token-based for some OpenAI models vs. flat-per-image-by-resolution/quality for others is the commonly cited 2026 pattern, but this report did not verify it against a primary source this pass — treat as an open item, not a confirmed claim). No demand signal, internal or external, was found for either surface.

**build_now / not_yet:** `not_yet` for both. Lower priority than embeddings/rerank even under a hypothetical customer ask, given the canonical-schema and wire-format work required on top of the same demand-signal gap every other `not_yet` finding in this report shares.

### Finding 8 — Cross-cutting: every candidate in this report needs the same two additive extension points, and the guardrail engine already generalizes to all of them for free
**Confidence: high** (direct code inspection; this is the report's own architectural synthesis grounded in Findings 2–7, not an independently-sourced external claim)

Reading `adapter/types.go`, `dataplane.go`, and `guardrail/engine.go` together yields one structural conclusion that applies uniformly to every surface examined above: none of them can be added by retrofitting `adapter.Adapter` or `Pipeline.HandleChatCompletion` — both are hardcoded to the chat-completions canonical schema, by design, the same way this codebase has always kept provider-specific and feature-specific concerns in additive sibling types/packages rather than widening an existing interface's signature (`ReasoningBlocks`, `CacheControl`, `ToolChoice`, and `bedrockguard.Detector` all follow this same convention, per `ARCHITECTURE.md` and the same-day `guardrail-plugin-extensibility-2026-09-15.md` report's Finding 7). Concretely, any surface in this report would need: (a) its own canonical request/response type (cheap for embeddings/rerank/moderation — simple string/list-of-strings shapes; genuinely new for images' binary output); (b) its own `Adapter`-shaped interface, since `ToProvider(ChatRequest)`/`FromProvider(any) ChatResponse` cannot be reused as-is; and (c) its own pipeline function alongside (not inside) `HandleChatCompletion`, reusing the generic, already-schema-agnostic sub-packages (`identity`, `budget`, `router`, `ratelimit`) but not that function itself. One genuine, verified non-gap worth naming positively rather than as a cost: `guardrail.Engine.Check(ctx, text string) Verdict` already takes a plain string, fully decoupled from `ChatRequest` — any future embeddings/rerank/moderation input-scanning need would work against the *existing* guardrail engine with zero new abstraction, the cheapest part of this entire cross-cutting picture.

**build_now / not_yet:** N/A — architectural synthesis informing every other finding's cost estimate, not a build decision on its own.

## Caveats

- **OpenAI moderation pricing was not confirmed in this pass.** The fetched API reference did not state whether `/moderations` is free or billed, and this report deliberately does not assert a specific figure without independent re-verification (mirroring this repo's own established convention, per `gateway-batch-api-2026-09-13.md`'s refusal to cite an unverified OpenAI batch-discount percentage).
- **Image-generation billing mechanics (token-based vs. flat-per-image) were not independently verified against a primary source this pass** — Finding 7 flags this honestly rather than asserting a specific mechanism; before any future report or design leans on a specific image-pricing claim, verify it directly against OpenAI's/Google's current pricing pages.
- **Portkey and Kong's endpoint coverage claims in Findings 1 and 4 are scoped to the specific pages fetched in this pass**, which is a real limitation, not a confirmed absence — both vendors' documentation is large and this research did not exhaustively crawl either. Treat "not mentioned on the fetched page" as a research gap, matching the same caveat pattern `gateway-batch-api-2026-09-13.md` used for Helicone.
- **This report found zero confirmed external (paying-customer) demand signal for any surface examined.** The one internal signal found (Finding 2's `validate_embedding_gate.py`) is real but is explicitly a one-off research script outside production traffic — every `build_now`/`not_yet` call above should be read with that honestly-scoped distinction in mind, not as evidence of product-market pull.
- **Redirects encountered mid-research** (`platform.openai.com` → `developers.openai.com`; `docs.anthropic.com` → `platform.claude.com`) were followed to their target and fetched successfully, but are themselves a live signal that even the *documentation URLs* for this exact API surface are still being reorganized in 2026 — treat every specific endpoint path and model name in this report as current as of 2026-09-15, not as permanently stable.

## Open Questions
