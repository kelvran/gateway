# Hierarchical Virtual-Key Budgets — Deep Research, Round 2 (2026-09-07)

## Question

Should Kelvran build hierarchical virtual-key budgets (org→team→user→key→session cascading spend caps), and if so, what is the concrete implementation design? This is the **third** pass on this exact question — `docs/rfcs/2026-09-02-virtual-keys-budgets.md` originally rejected it at ship time ("nothing in the codebase has more than one level of scope to resolve yet"), and `docs/upgrade-research/gateway-competitor-gaps-2026-09-07.md` found real Bifrost/Portkey precedent that led to the decision being **deferred twice** (`DECISIONS.md`, 2026-09-07 x2), both times with an explicit revisit trigger: "a real multi-tenant demand signal, not calendar time." This pass's mandate was to go deeper than the competitor-gap pass, not re-derive it — either surface genuinely new evidence that changes the calculus, or honestly confirm the deferral remains correct.

## Summary

Bifrost and LiteLLM both provide real, production, primary-source-verifiable evidence for how a hierarchical budget cascade is implemented under concurrency: **neither uses distributed locks or cross-level atomic transactions** — both use independent per-level counters (Bifrost: lock-free CAS retry loop on a `sync.Map`, single-node in-memory, RAFT only in paid Enterprise for multi-node; LiteLLM: cost-reservation against a Redis cross-pod counter with saga-style compensating rollback). Bifrost confirmed has **no session-scoped budget level** anywhere in its shipped code or docs (hierarchy tops out at Customer→Team→VK→Provider Config), but **LiteLLM — a third vendor outside the prior research pass's scope — does ship a genuine session-scoped budget** (`max_budget_per_session`) tied to its Agent Gateway and trace-ID correlation, meaning Kelvran's org→team→user→key→session sketch is not novel, just not precedented by the two vendors previously studied. Critically, this pass found **zero verified evidence** on Portkey's mechanics, **zero verified evidence** of real customer demand/pain, and **zero verified evidence** on concrete Kelvran-specific Go implementation design — three of the five original research questions returned no claims that survived adversarial verification. The technical findings are new and useful (a concrete, de-risked concurrency pattern to copy if/when Kelvran builds this) but **do not surface a demand signal**, so they do not overturn the twice-deferred decision — they refine "how," not "whether now."

## Findings

### Finding 1 — Bifrost's hierarchy is exactly 4 levels, with independent-check-then-independent-deduct (not atomic cross-level), and no session level (confidence: high)

Bifrost's shipped hierarchy is Customer → Team → Virtual Key → Provider Config. The same request cost is deducted from every applicable level, and any single level's failure blocks the request — but this is **not** a pre-check-then-atomic-commit across levels: Bifrost's own worked example shows a charge pushing a level over its limit in the same transaction that applied it, with enforcement blocking only the *next* request. Sources: [Bifrost governance docs](https://bifrost.mintlify.app/features/governance/budget-and-limits), `store.go`/`tracker.go` source.

### Finding 2 — Bifrost's real concurrency mechanism is lock-free CAS on a `sync.Map`, single-node, with an explicitly accepted at-least-once DB-settlement gap (confidence: high)

Confirmed at the source level: `store.go`'s `BumpBudgetUsage` uses `sync.Map.CompareAndSwap` per budget entry (one CAS loop per hierarchy level — VK, Team, Customer, Provider, Model, User — inside a single synchronous `UpdateUsage` call), not a mutex or a database transaction. OSS Bifrost is strictly single-node in-memory (never re-reads state from Postgres after startup); real-time cross-node sync exists only in paid Enterprise via a modified RAFT protocol. There's an explicitly accepted "at-least-once, not exactly-once" gap for durable DB settlement, separate from the per-request in-memory increment path.

### Finding 3 — Bifrost has zero session-scoping concept anywhere (confidence: high)

Confirmed directly: the `GovernanceData` struct, the `GovernanceStore` interface (66 methods), and two separate governance PRs (#3937, #3998) contain zero mentions of "session." The closest adjacent feature — Enterprise-only customer scoping via `x-bf-customer-id` headers — is a per-request attribution mechanism for multi-customer teams, not a session/conversation-state budget, and doesn't replace the team/VK/provider-config budgets.

### Finding 4 — NEW: LiteLLM (a fourth vendor, outside the prior pass's scope) ships a real session-scoped budget (confidence: high)

LiteLLM's Agent Gateway feature ships `max_budget_per_session` plus session rate limits (`session_tpm_limit`, `session_rpm_limit`) and iteration caps (`max_iterations`), gated behind trace-ID correlation (`require_trace_id_on_calls_by_agent`). Confirmed at the source level: a real pre-call hook (`_PROXY_MaxBudgetPerSessionHandler`) accumulates response cost per `session_id`/`x-litellm-trace-id` via an atomic Redis Lua `INCRBYFLOAT` script, rejecting with 429 once exceeded. **This directly answers the original research brief's question 2: Kelvran's session-level ambition is not unprecedented — it just wasn't precedented by the two vendors (Bifrost, Portkey) the prior competitor-gap pass examined.**

### Finding 5 — LiteLLM's concurrency mechanism is reservation + saga-style rollback, not a cross-level transaction either (confidence: high)

LiteLLM pre-reserves the request's estimated max cost against each applicable hierarchy level (Key, Team, TeamMember, User, EndUser, Tag, Model-access-group, Organization), rejects before calling the provider if any reservation would exceed budget, then replaces the reservation with the actual priced cost after the response. Confirmed at the source level (`budget_reservation.py`'s `reserve_budget_for_request`): a plain sequential `for` loop over `_BudgetCounter` objects, each with its own try/except and a best-effort compensating rollback (`_release_applied_entries_best_effort`) if a later counter fails — a saga pattern, not a Lua script or `MULTI`/`EXEC` spanning multiple hierarchy keys.

### Finding 6 — Synthesis: new technical evidence, zero new demand evidence (confidence: medium — this is a synthesis, not an independently sourced claim)

Two independent production vendors converge on the same shape (independent per-level counters, never a cross-level atomic transaction), and a third vendor confirms session-scoped budgets are real precedent, not novel ambition. But no claims about Portkey's mechanics, real-world demand/pain evidence, or Kelvran-specific Go implementation design survived verification in this pass — these three of the original five research questions remain genuinely open, not answered negatively.

## Caveats

- Three of the five original research questions (Portkey's mechanics; real-world demand evidence; concrete Kelvran-specific Go design) have **zero verified claims** — treat as open gaps, not resolved negatives.
- Several plausible-sounding Bifrost claims were explicitly **refuted** during verification (a claimed billing-bypass risk from "co-payers"; a claim about PR #6311's terminology; an "architectural drift-prevention" claim; a "richer lattice of limit-holder kinds" claim) — do not rely on these even though they surfaced during research.
- Three underlying claims had 2-1 vote splits (still counted as confirmed, but with mild residual verifier disagreement) — treat with slightly more caution than the unanimous 3-0 claims.
- Bifrost is a fast-moving OSS repo (code/PRs referenced as recent as 2026-09-05, days before this research) — re-check `plugins/governance/store.go`/`tracker.go` before treating mechanism details as current if acted on more than a few months out.

## Kelvran-Specific Implementation Design (composed by the orchestrator — this pass's own external research did not verify Kelvran-code-specific claims, so this section is separate synthesis, not adversarially-verified research)

Both confirmed concurrency patterns (Bifrost's CAS-per-level, LiteLLM's reserve-per-level) map cleanly onto Kelvran's existing single-key `budget.Tracker.Record` call — extending it to a hierarchy would mean calling `Record` independently against each applicable scope ID (key, team, org, session) rather than needing a heavier transactional design across scopes. **This is genuinely good news for effort estimation on the concurrency mechanism specifically** — it validates that Kelvran's existing "one flat counter, one `Record` call" shape scales to "N independent counters, N `Record` calls" without a redesign of the underlying counter primitive itself.

The harder, more architecturally invasive part is unchanged from the original 2026-09-02 RFC's own reasoning: `identity.VirtualKey` has zero concept of team/org/session today, so building this needs (a) new hierarchy-identifier fields on `VirtualKey` (or a separate resolution table mapping key→team→org), (b) new scope-resolution logic in the request path *before* `budget.Tracker` is ever called, (c) new config/admin-API surface for defining and mutating org/team-level budgets (extending the already-shipped live virtual-key mutation surface, `dataplane.Pipeline.UpsertVirtualKey`), and (d) a decision on how this composes with the already-shipped `ratelimit.KeyConfig.PerModel` per-model override (does a per-model override apply within one hierarchy level only, or across all levels simultaneously — genuinely unresolved by any research pass so far). Effort estimate: the concurrency/counter layer itself is now credibly Small-Medium (per the converging vendor evidence above), but the hierarchy-resolution and config-surface work remains Medium-Large, unchanged from the original RFC's own assessment — this research refines confidence in *one part* of the estimate, not the whole.

## Recommendation

**This research does not surface a real multi-tenant demand signal — the deferral's own explicit revisit trigger — so it should remain deferred.** What it does provide, genuinely new and worth keeping: (1) a de-risked, evidence-backed concurrency design (independent per-level counters, never a cross-level transaction) to use directly if/when the trigger fires, removing what would otherwise be a real open design question at build time; (2) confirmation that Kelvran's session-level ambition is real, precedented industry practice (LiteLLM), not speculative over-scoping — worth keeping in the target design rather than trimming it for lack of precedent. Compared to the two alternatives researched in parallel: routing-scope-expansion and MCP/A2A-brokering both also lack a current demand signal, but routing-scope-expansion's core mechanism (model-group load balancing) is arguably already partially built (see the sibling `gateway-routing-scope-2026-09-07.md` report), making it lower-risk to extend now; hierarchical budgets and MCP brokering both genuinely need net-new subsystems and both are correctly waiting on the same missing ingredient — real customer demand — that no research pass, however deep, can manufacture.

## Second-pass reaffirmation (2026-09-08)

**Verdict unchanged: still deferred.** This targeted follow-up re-ran the demand-signal search from genuinely new angles, re-checked whether Bifrost/LiteLLM/Portkey changed their concurrency mechanism, and directly re-inspected Kelvran's own code. Nothing found moves the needle — this is an honest null result, not a padded one.

**1. Demand signal — still none.** Fresh searches (Langfuse's LLM cost-management engineering post, an 8-tool cost-observability roundup covering Opslyft/Helicone/Langfuse/Portkey/LiteLLM/Datadog/Arize/CloudZero, StackSpend's OpenAI cost-monitoring page, an OpenAI community-forum thread, and a fresh HN Show-HN — "Prism," a proxy built specifically to track Claude API costs by team) surfaced zero case studies, forum threads, or named-customer complaints about flat LLM-gateway budgets causing real pain in a multi-team org — the same gap the original report named as "the single most decision-relevant gap." Two adjacent-but-not-equivalent signals are worth recording honestly: (a) StackSpend names a real *attribution* gap in OpenAI's native flat org billing ("multiple teams share one org with no per-team attribution") — but that's a visibility/reporting complaint, not a request for cascading budget *enforcement*, and it's marketing copy, not a customer case study; (b) even a tool purpose-built to solve "track AI costs by team" (Prism) ships only a single flat `department` tag today, with per-user attribution still on its stated roadmap — weak but real evidence that the market itself treats full hierarchy as v2+, not table stakes, which is mildly supportive of staying deferred rather than building speculatively. One genuinely new, more substantive data point: LiteLLM's issue #33871 shows a real user, on a real deployed proxy with real billed traffic, actively relying on LiteLLM's already-shipped `org > team > project > key` hierarchy and hitting a bug in it (project-level spend is checked but never written, so project budgets silently never enforce). This proves people who already have hierarchy available use it in earnest — but it's demand for a bug fix in an existing feature, not a report that Kelvran's own flat model is hurting a real customer. It does not meet the deferral's own bar.

**2. Vendor concurrency mechanism — unchanged, recommendation stands, with one refinement worth keeping.** Direct re-inspection of Bifrost's live `plugins/governance/store.go` (HEAD as of 2026-09-08) confirms `BumpBudgetUsage`/`ChargeBudgets` are still independent `sync.Map.CompareAndSwap` retry loops per budget ID — one CAS per hierarchy level touched, never one cross-level atomic update. Two Bifrost PRs merged 2026-09-07 don't change this: #6932 is a budget-*edit* state-loss fix confined to the admin-API reconciliation path (never touches `store.go`/`tracker.go`); #6896 (a new enterprise "Projects" feature with project/provider/model budget tiers and per-member split policies) is documentation-only in this PR — no backend code shipped yet, so its concurrency mechanism isn't verifiable and is worth a re-check once Bifrost actually ships the implementation. LiteLLM's reservation pattern (`budget_reservation.py`) for Key/Team/TeamMember/User/EndUser/Tag/Organization is also unchanged. The one real refinement: LiteLLM's *session*-level budget (`max_budget_per_session`) turns out to use a materially weaker mechanism than the other levels — a plain check-then-increment with no reservation at all (confirmed live in current `main`), with an open, unfixed, maintainer-unreviewed race (issue #34732, fix PR #34742 still open after 6+ weeks, a bot review flagging a security gap in the proposed fix itself). Lesson for Kelvran, not a reversal: "independent per-level counters" is the right shape, but each level still needs its own reservation-safe implementation verified individually — a hierarchy is only as race-free as its weakest level, and even mature vendors ship some levels (session) less safely than others (key/team). Useful, coincidental validation: Kelvran's own `budget.Tracker` gained a `Reserve`/`Reconcile` pair on 2026-09-08 (`docs/rfcs/2026-09-08-gateway-budget-ratelimit-toctou-fix.md`) to close a real TOCTOU race in its existing *flat* budget — i.e. Kelvran has now independently built, for one level, exactly the reservation-safe pattern this research would recommend replicating per-level if/when hierarchy is ever built. That's a proof point already sitting in the codebase, not just an external one.

**3. Kelvran's own code — still fully flat, confirmed by direct inspection today.** `gateway/internal/identity/identity.go`'s `VirtualKey` struct has exactly seven fields (`ID`, `KeyHash`, `BudgetUSD`, `BudgetResetInterval`, `BudgetWarnPercent`, `AllowedModels`, `RateLimitBurst`/`RateLimitRefill`, `MaxConcurrentRequests`) — zero `Team`/`Org`/`Session` concept anywhere. `grep -rni "team|org|session"` across `gateway/internal/identity/` and `gateway/internal/budget/` returns hits only in test fixtures using opaque string IDs like `"team-alpha"` as ordinary `VirtualKey.ID`/tracker-key values (e.g. `identity_test.go`, `budget_test.go`, `reset_test.go`, `toctou_fix_test.go`) — never a real hierarchy field. `budget.Tracker` is still a flat `map[string]decimal.Decimal` keyed by one opaque string per key, exactly as the original research found.

**4. DECISIONS.md — no new demand signal logged since the second deferral.** `DECISIONS.md` line 106 (2026-09-07, "deferral reaffirmed a second time") remains the most recent entry mentioning hierarchical budgets, demand signals, or multi-tenancy. Every entry since then (18 entries through 2026-09-08, lines 107-129) covers unrelated work — eval multi-axis judging, retry-storm mitigation, regression-corpus growth (7→113 cases across four research-fed rounds), two real TOCTOU race fixes, a streaming-timeout fix, a health-probe-recovery-ramp fix, a fallback-chain cross-model billing/rate-limit bypass fix, and a guardrail zero-width-space evasion fix. None reference a customer, a team/org/multi-tenant complaint, or hierarchical budgets at all. The deferral is uncontradicted by everything that has shipped since it was last reaffirmed.

**Net: this is now the third time this exact decision has been examined and reaffirmed (2026-09-07 x2, this pass 2026-09-08), each time from a different angle (competitor-precedent research, deep concurrency-design research, and now a targeted fresh demand-signal sweep), and each time landing on the same unresolved gap.** The concurrency design from the prior pass (independent per-level counters, `budget.Tracker.Record`-per-scope, never a cross-level transaction) remains correct and is now further de-risked — keep it on file for if/when the trigger fires. Revisit only on a real multi-tenant demand signal, not calendar time or further research passes; further research alone cannot manufacture a customer that doesn't exist yet.
