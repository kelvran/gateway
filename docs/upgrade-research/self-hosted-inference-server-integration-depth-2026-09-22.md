## Executive Summary

Kelvran's `openaicompat` adapter already gets the *wire-format* layer right — its own doc comments already disclose, correctly and specifically, the real per-runtime unevenness in `finish_reason` values, tool-call support, reasoning-field names, and `prompt_tokens_details.cached_tokens` cache-token reporting, all independently verified against each runtime's real source in prior rounds. What none of that touches is a materially different signal family this research confirms is real, currently-shipping, and unused by Kelvran today: every one of the five runtimes `openaicompat` targets exposes its own native load/capacity telemetry — vLLM's `vllm:num_requests_waiting`/`vllm:kv_cache_usage_perc`, SGLang's `sglang:num_queue_reqs`/`sglang:kv_cache_usage_perc`, TGI's `tgi_queue_size`/`tgi_batch_current_size`, and llama.cpp's `llamacpp:requests_processing`/`requests_deferred` (plus a separate `/slots` endpoint) — none of which Kelvran's router ever reads. The research question of whether the gateway should read this and use it for routing has a two-part, evidence-backed answer, not a single yes/no: the *deepest* form of this coordination (precise, ZMQ-KV-event-driven prefix-cache-aware routing, disaggregated prefill/decode orchestration, LoRA-adapter-aware scheduling) is real, production-proven (GKE Inference Gateway is a GA product; an AWS reference benchmark shows up to 69% p90 TTFT improvement under sustained load; Snap Inc. reports 75-80% prefix-cache hit rates in production), **and is deliberately built as a separate architectural layer** — the Kubernetes Gateway API Inference Extension's Endpoint Picker (EPP), a sidecar/ext-proc service that sits *between* a general-purpose AI gateway and the self-hosted fleet, not inside one. The Gateway API Inference Extension's own docs name exactly this composition: "integrate your self-hosted models alongside model-as-a-service providers in a higher level AI Gateways like LiteLLM, Gloo AI Gateway, or Apigee." Kelvran is architecturally in that "higher level AI Gateway" category (a single-process, provider-agnostic Go proxy with no Kubernetes-pod-discovery, no per-runtime tokenizer, no ZMQ event bus) — the deepest coordination tier is genuinely out of scope for what Kelvran is, not merely unbuilt. But a much shallower, low-effort tier is a real, evidence-backed gap: LiteLLM — the closest production analog to Kelvran's own shape — ships a "least-busy" strategy that tracks only its *own* in-flight request count, and a live, reproducible GitHub issue (#37622) shows this diverging sharply from a self-hosted backend's actual state (one vLLM instance logging `Running: 31 reqs, Waiting: 48 reqs, GPU KV cache usage: 98.8%` while a sibling deployment sat fully idle) purely because LiteLLM never looks at the backend's own real signal. Kelvran's active-probe loop already makes an out-of-band HTTP call to every `openaicompat` deployment on a timer — extending that existing mechanism (not the pure-function `Adapter` interface) to also read the runtime's own `/metrics` gauge as a soft, LiteLLM/GKE-precedented pre-filter is a real, bounded, currently-missing capability worth naming, even though the precise KV-cache-event-routing tier stays out of scope.

## Findings, ranked

### 1. The gap is real: every self-hosted runtime `openaicompat` targets exposes native queue-depth/KV-cache-utilization telemetry Kelvran never reads, and the landscape is unevenly shaped across runtimes in a way the existing adapter design already has a precedent for handling (Small — documentation/design-constraint only)

**What:** `openaicompat.go`'s own package doc comment (and the `docs/upgrade-research/cache-provider-native-caching-audit-round4-2026-09-11.md` research it cites) already discloses, per-runtime, which of vLLM/Ollama/llama.cpp/TGI genuinely populate `prompt_tokens_details.cached_tokens` — but that is a *billing/cost-accounting* signal riding inside the OpenAI-compatible chat-completion response body. This research confirms a *separate*, currently entirely-unread signal family: each runtime's own out-of-band Prometheus `/metrics` endpoint (or, for llama.cpp, an additional non-Prometheus `/slots` endpoint), carrying real-time queue depth and GPU/KV-cache utilization:

| Runtime | Queue-depth signal | KV-cache/GPU-utilization signal | Gating |
|---|---|---|---|
| vLLM | `vllm:num_requests_waiting`, `vllm:num_requests_running` | `vllm:kv_cache_usage_perc` (renamed from `gpu_cache_usage_perc` across versions studied), `vllm:gpu_prefix_cache_hit_rate` | On by default with `/metrics`; distinct from the opt-in `enable_prompt_tokens_details` flag that gates the cache-token *response-body* field |
| SGLang | `sglang:num_queue_reqs`, `sglang:num_running_reqs` | `sglang:kv_cache_usage_perc` (added recently, PR #34714 — `max(full, swa)` excluding Mamba pools), `sglang:cache_hit_rate` | Requires `--enable-metrics` at server launch |
| TGI | `tgi_queue_size` | `tgi_batch_current_size`, `tgi_batch_current_max_tokens` — no KV-cache-percent-style gauge exists (consistent with TGI's already-disclosed zero cache-token support) | On by default once `/metrics` is scraped |
| llama.cpp server | `llamacpp:requests_processing`, `llamacpp:requests_deferred` | A separate `/slots` endpoint (not Prometheus-formatted) with per-slot state and, per a 2026 PR (#25813), realtime prefill/decode progress | Requires `--metrics` (Prometheus) or `--slots` (default-enabled) flags respectively |
| Ollama | Inherits from its llama.cpp-backed/MLX legacy runners only; its newer pure-Go engine path has no equivalent exposed | Same split | Not independently re-verified this round beyond the already-disclosed cache-token split |

**Why it matters for Kelvran specifically:** the research brief's framing ("should the gateway read vLLM's own queue-depth/utilization metrics to inform routing, rather than treating it as an opaque OpenAI-compatible backend") presupposes a single yes/no answer; the real landscape is exactly as uneven as the cache-token-field question Kelvran already researched and disclosed for a different field family — the right response is the same "best-effort, runtime-dependent, harmlessly absent" disclosure pattern `openaicompat.go` already uses, not a uniform assumption either way.

**Consistent with settled decisions?** Directly extends, rather than contradicts, `docs/upgrade-research/cache-provider-native-caching-audit-round4-2026-09-11.md` Finding 2's already-established convention for this exact adapter package — same "verify per runtime, disclose the split, never assume uniformity" discipline, applied to a new metric family the prior round didn't cover (that round was scoped to the response-body cache-token field, not the out-of-band `/metrics` endpoint).

**2026 best practice grounding:**
- vLLM's own docs (`docs.vllm.ai/en/stable/usage/metrics/`, `docs.vllm.ai/en/stable/design/metrics/`, and the `v0.19.1`/`v0.9.2` historical versions, plus the GitHub-hosted `docs/design/metrics.md`) consistently confirm `num_requests_running`/`num_requests_waiting`/`kv_cache_usage_perc` as real, currently-documented Prometheus gauges across every version checked [docs.vllm.ai + github.com/vllm-project/vllm — confirmed 4-0 across 4 independently-dated doc versions].
- SGLang's own docs (`docs.sglang.ai/references/production_metrics.html`) and its GitHub source (`metrics_collector.py`, PR #34714 adding `kv_cache_usage_perc`) confirm the same shape, with the recent PR explicitly motivated by "users migrating from vLLM expect a Prometheus gauge for KV cache utilization" [docs.sglang.ai + github.com/sgl-project/sglang — confirmed 2-0, both official].
- TGI's own HF docs (`huggingface.co/docs/text-generation-inference/reference/metrics`, both the versioned and `main` pages) plus a GitHub discussion (#1127) and a K8s-serving-WG feature request (#1977, still open as of this research, proposing *more* metrics TGI doesn't yet have) confirm `tgi_queue_size`/`tgi_batch_current_size` are real and shipping, and that the WG-requested superset (e.g. `total_tokens_in_current_batch`, `estimated_max_batch_before_compute_saturation`) is explicitly not yet implemented [huggingface.co + github.com/huggingface/text-generation-inference — confirmed 3-0].
- llama.cpp's own GitHub (`tools/server/README.md`'s `--metrics`/`--slots` flag table, PR #5708 introducing `/metrics`, PR #25813 from 2026 adding realtime per-slot stats to `/slots`) confirms both endpoints are real and actively maintained [github.com/ggml-org/llama.cpp — confirmed 3-0, all from the project's own repository].

**Concrete next step:** none — this finding is the factual foundation for Findings 2 and 3 below, not itself an implementation task.

**Effort:** Small (a documentation/design-constraint finding only).

### 2. Precise, KV-cache-event-driven prefix-cache-aware and disaggregated-serving coordination is real, production-proven, and deliberately built as a *separate architectural layer* Kelvran should not attempt to replicate inside a provider-agnostic gateway (Large if attempted — but the correct call is Not Built, a scope boundary, not a backlog item)

**What:** The deepest tier of self-hosted-inference coordination — precise prefix/KV-cache locality routing, disaggregated prefill/decode orchestration, LoRA-adapter-aware scheduling, priority-based flow control with in-flight eviction — is real and production-grade, but it lives in the **Kubernetes Gateway API Inference Extension (GIE)** project's **Endpoint Picker (EPP)**, most visibly packaged as **llm-d** and, as a managed product, **GKE Inference Gateway**. The mechanism: vLLM pods publish real-time KV-cache block allocation/eviction events over ZeroMQ; the EPP subscribes per-pod, builds a global prefix-block index by tokenizing each incoming prompt with the *same* hash algorithm and block size vLLM itself uses (`--prefix-caching-hash-algo`, `--block-size`, `PYTHONHASHSEED` must match exactly between vLLM and the EPP config), and scores candidate pods via a pluggable pipeline (`precise-prefix-cache-producer` + `prefix-cache-scorer` + `kv-cache-utilization-scorer` + `queue-scorer`) before an Envoy (or equivalent) proxy forwards the request to the winning pod over the `ext-proc` protocol.

**Why it matters for Kelvran specifically:** this directly and precisely answers the research brief's core question — "should the gateway read vLLM's own queue-depth/utilization metrics to inform routing, rather than treating it as an opaque OpenAI-compatible backend, versus is that coordination depth genuinely out of scope for a provider-agnostic gateway." The evidence says both halves of that question are correct for different slices: the *coordination itself* is real and valuable in production (not a niche or hypothetical optimization — GKE Inference Gateway is a shipping GA product; an independent AWS reference implementation measured p90 TTFT dropping from 4.4s to 1.4s — a 69% improvement — under sustained multi-turn load versus plain round-robin; Snap Inc.'s own engineering leadership is quoted reporting 75-80% production prefix-cache hit rates), but the *precise* form of it requires infrastructure Kelvran does not have and, per `docs/decisions/0003-go-python-split.md`'s and `AGENTS.md`'s own stated bar against adding new languages/runtimes preemptively, should not casually acquire: Kubernetes-native pod discovery, a persistent ZeroMQ subscriber per backend pod, a tokenizer that byte-for-byte matches vLLM's own block-hashing scheme, and — critically — the GIE project's own docs state outright that this layer is meant to sit *underneath* exactly the kind of gateway Kelvran is: "integrate your self-hosted models alongside model-as-a-service providers in a higher level AI Gateways like LiteLLM, Gloo AI Gateway, or Apigee." Kelvran already reuses this same "the right layer for X already exists elsewhere and Kelvran should compose with it, not rebuild it" reasoning for the K8s manifests it ships today (`deploy/k8s/`).

**Consistent with settled decisions?** Not previously researched — no existing `docs/upgrade-research/*.md` file or `DECISIONS.md` entry addresses the Kubernetes Gateway API Inference Extension / llm-d ecosystem at all (confirmed via the grep sweep in the Method section above). This finding does not contradict any prior decision; it establishes a new, explicit scope boundary that is consistent with the project's existing "provider-agnostic, single-process gateway" self-description in `PRD.md`/`gateway/ARCHITECTURE.md`.

**2026 best practice grounding:**
- The Gateway API Inference Extension's own site (`gateway-api-inference-extension.sigs.k8s.io`) and the `llm-d-router` GitHub repo/docs (`llm-d.ai/docs/architecture`) both independently describe the EPP/ext-proc architecture identically — an Endpoint Picker consulted by a conformant L7 proxy (typically Envoy) per request, scoring pods on KV-cache locality, queue depth, and LoRA-adapter affinity [gateway-api-inference-extension.sigs.k8s.io + llm-d.ai + github.com/llm-d — confirmed 3-0, cross-organizational: this is a CNCF-sandbox project with Google/Red Hat/IBM contributors, not one vendor's marketing].
- Google Cloud's own docs (`docs.cloud.google.com/kubernetes-engine/.../about-gke-inference-gateway`) and blog (`cloud.google.com/blog/.../gke-inference-gateway-prefix-caching...`) confirm GKE Inference Gateway is GA, built on llm-d's EPP, with the Snap Inc. testimonial quoted directly and attributed [cloud.google.com — confirmed, single-vendor source for the specific 75-80% figure, but the underlying mechanism claim is independently corroborated by the AWS sample below].
- An independent, vendor-neutral primary source — `github.com/aws-samples/sample-eks-cache-aware-llm-routing` (an AWS solutions-architecture sample repo, not marketing copy) — reproduces the identical architecture (Envoy Gateway + llm-d EPP + vLLM with `--kv-events-config`) end to end on EKS and reports its own measured benchmark numbers (p90 TTFT: 649ms→288ms at 0-30s, degrading to 4443ms→1370ms by 150-180s under sustained load, a 69% improvement at the worst-case bucket) [github.com/aws-samples — confirmed 1-0 as a standalone measurement, but independently corroborates the mechanism Google's own docs describe, making the *mechanism* claim 2-0 even though this specific number is single-sourced].
- The GIE project's own introduction page explicitly names the composition-not-replacement relationship with general-purpose AI gateways (LiteLLM, Gloo AI Gateway, Apigee) [gateway-api-inference-extension.sigs.k8s.io — confirmed, single canonical source, but this is the project's own self-description, the strongest possible source for a scope-boundary claim about itself].

**Concrete next step:** none as a build task. If Kelvran ever needs this tier (i.e., an operator specifically deploys ≥2-4 self-hosted GPU replicas of the same model under sustained multi-turn conversational load, the precondition under which the AWS benchmark's gains actually materialize), the correct recommendation is to document that Kelvran composes with a Gateway API Inference Extension deployment placed in front of the self-hosted fleet (Kelvran's `openaicompat` deployment's `BaseURL` simply points at the Inference Gateway's own endpoint instead of directly at a single vLLM pod) rather than to build any of this inside `gateway/internal/router` or `gateway/internal/adapter/openaicompat`. This mirrors the same "the deeper layer already exists, integrate rather than rebuild" posture the K8s deployment manifests already take, and costs zero code today — it is worth a short note in `gateway/ARCHITECTURE.md`'s Router section the next time that section is touched, so a future operator or contributor doesn't independently propose rebuilding this.

**Effort:** Large if attempted inside Kelvran directly (a new persistent-connection subsystem, a tokenizer dependency, a hash-algorithm-compatibility contract with every target runtime) — but the actual recommendation is Not Built / documented scope boundary, which is effectively zero engineering effort.

### 3. A genuinely lower-effort, evidence-backed partial win exists within Kelvran's own existing architecture: extend the already-shipped active-probe loop to read a coarse load signal as a soft pre-filter — a real gap, not a speculative one, with a live production failure mode as direct evidence (Medium)

**What:** `dataplane.RunHealthProbeLoop`/`ProbeDeployments` already makes a real, out-of-band HTTP call to every configured deployment on a timer (a synthetic chat-completion request, per `docs/rfcs/2026-09-07-gateway-active-health-probing.md`) and already updates `router.Router`'s health state from the result. That loop currently asks each deployment exactly one question — "is this healthy at all" — and nothing about *how loaded* it currently is. Given Finding 1's confirmed metric surface, the same loop could, for `openaicompat` deployments specifically (optionally, per-deployment, since not every self-hosted deployment runs a metrics-exposing runtime — see Finding 1's uneven landscape), also issue a second, cheap `GET <base>/metrics` (or, for llama.cpp, `/slots`) call and extract a coarse load signal to use as a **soft pre-filter within the existing healthy set** — deprioritizing, never hard-excluding, a deployment reporting high queue depth or near-saturated KV-cache usage, the exact "soft pre-filter that degrades to full failover, never a hard pin" design constraint `docs/upgrade-research/cache-prompt-caching-aware-routing-2026-09-12.md` Finding 3 already established for a related (billing-cache-affinity) routing question and marked `build_now` as a principle.

**Why it matters for Kelvran specifically:** this is not a speculative "might help" — a real, live, reproducible production failure mode already demonstrates the cost of *not* having it. LiteLLM's own GitHub issue #37622 (filed 2026-08, still open) shows a real operator running two vLLM replicas behind LiteLLM's `least-busy` routing strategy, where LiteLLM's own request-count bookkeeping diverged sharply from ground truth: vLLM's own log line for the overloaded instance read `Running: 31 reqs, Waiting: 48 reqs, GPU KV cache usage: 98.8%, Prefix cache hit rate: 0.0%` at the exact moment a sibling deployment's own log showed `Running: 0 reqs, Waiting: 0 reqs, GPU KV cache usage: 0.0%` — LiteLLM kept routing to the saturated instance because its own in-flight counter (maintained via `litellm.input_callbacks`/`success`/`failure` hooks, entirely client-side bookkeeping, confirmed directly against `litellm/router_strategy/least_busy.py`'s source) never consulted the backend's actual state at all. This is precisely the shape of gap Kelvran's own router — which currently has *no* load-aware selection signal whatsoever, only binary health and static cost-tier/weight — would reproduce identically if an operator ran multiple self-hosted replicas of the same model behind it today. `docs/upgrade-research/gateway-per-deployment-concurrency-2026-09-09.md`'s own Open Questions section names almost exactly this gap prospectively ("Should a deployment nearing its own cap proactively lower its effective weighted-routing share... no source studied described this kind of graduated, pre-emptive load-shedding at the deployment-cap layer specifically") — this research directly answers that open question for the self-hosted-runtime case specifically: yes, and the mechanism (a queue/KV-cache-derived scorer feeding a soft pre-filter) is exactly what GKE Inference Gateway's own "load aware routing" and llm-d's `queue-scorer`/`kv-cache-utilization-scorer` plugins already implement in production, just at Kelvran's own architectural scale (a direct `/metrics` scrape from the existing probe loop, not a ZMQ event bus).

**Consistent with settled decisions?** This must be reconciled with one directly load-bearing prior decision: `DECISIONS.md`'s `[2026-09-07]` entry ("Pre-call TPM reservation for Anthropic + vLLM/openaicompat only — dropped as a candidate") rejected a *different* proposal — an in-band, per-request token-counting HTTP call from inside the `Adapter.ToProvider` path — specifically because `adapter.Adapter`'s own doc comment requires implementations to be "pure functions: no network calls, no hidden state," and a per-request call would violate that for only 2 of 5 adapters. **This finding's proposal does not touch the `Adapter` interface or `openaicompat.go` at all** — it extends `RunHealthProbeLoop`, which is already, today, a background, out-of-band, network-calling mechanism living outside the pure-function `Adapter` boundary (it already calls `ProbeDeployments`, which already issues real HTTP requests on a timer, independent of any live user request). The 2026-09-07 rejection's actual reasoning (adapter purity, not "no network calls anywhere in the codebase") does not apply here, and this finding is careful to make that boundary explicit rather than silently reopening a settled question. Separately, this is a narrower, self-hosted-runtime-specific instance of the general "load-aware/usage-based selection signals" category `gateway/ARCHITECTURE.md`'s router section already names as "still not built, deliberately" pending a real signal — Finding 1 supplies exactly the kind of concrete, sourced signal that section's own deferral was waiting on, for the self-hosted subset of deployments specifically (not the hosted-provider deployments, which expose no equivalent signal at all).

**2026 best practice grounding:**
- GKE Inference Gateway's own docs describe "load aware routing" as one of several named, currently-shipping scoring dimensions: "monitors server load (KV cache utilization and pending queue depth), and gives a higher score to a server with lower load" [docs.cloud.google.com — confirmed, GKE's own canonical description; the underlying open-source llm-d project ships the identical `kv-cache-utilization-scorer`/`queue-scorer` plugin pair independently, corroborating this is llm-d's real mechanism, not a GKE-only reframing, 2-0].
- LiteLLM's own docs (`docs.litellm.ai/docs/routing`, `docs.litellm.ai/docs/proxy/load_balancing`) confirm `least-busy` is real and shipping but is explicitly a client-side in-flight-request-count tracker, not a backend-metrics reader — confirmed directly against `litellm/router_strategy/least_busy.py`'s source, which implements the count via `litellm.input_callback`/success/failure hooks with zero reference to any provider or backend metrics endpoint anywhere in the file [docs.litellm.ai + github.com/BerriAI/litellm — confirmed 2-0, docs and source independently agree]. The GitHub issue (#37622) demonstrating this diverging from vLLM's real state in production is a single, but directly-reproduced, first-party bug report with the operator's own captured logs from both sides (LiteLLM's routing behavior and vLLM's own `/metrics`-adjacent log lines) — treated here as a real, concrete illustration of the failure mode rather than as statistical evidence of its frequency [github.com/BerriAI/litellm/issues/37622 — single source, but primary and directly inspectable, not a paraphrase].
- The precedent for "soft pre-filter over the healthy set, never a hard pin" as the correct way to compose a new preference signal with existing health/failover logic is not re-derived here — it is the same principle `docs/upgrade-research/cache-prompt-caching-aware-routing-2026-09-12.md` Finding 3 already established from LiteLLM's `DeploymentAffinityCheck` test and AWS SageMaker's `ConcurrencyThreshold` overflow behavior, reused directly rather than re-researched, since it applies identically to a load-derived preference as to a cache-affinity-derived one.

**Concrete next step:** a bounded RFC (not a rushed inline addition) scoping: (1) an optional, per-deployment `metrics_url`/`metrics_path` config field on `DeploymentConfig`, defaulting to absent (zero behavior change for any existing config); (2) a small per-runtime scraper reusing the existing probe loop's HTTP client, extracting exactly one normalized "load score" (a documented, explicitly-approximate combination of queue-depth and KV-cache-usage-perc, since the exact metric names and scales differ per Finding 1's table and no universal formula exists across runtimes); (3) wiring that score into `router.Select`'s existing weighted-pick logic as a multiplicative de-weighting factor, never a hard exclusion — reusing the health-set filtering `Select` already performs, not a new selection path; (4) explicitly scoped to `openaicompat` deployments only, since hosted-provider deployments have no equivalent signal and should be entirely unaffected. Per the established "instrument before building" pattern this codebase already applies to the closely related cache-affinity-routing and traffic-derived-health-signal questions, this should be gated on the same kind of concrete trigger those decisions used — e.g., an operator or issue report naming ≥2 self-hosted replicas of the same model behind Kelvran experiencing uneven load — rather than built purely speculatively; the RFC itself, and recording the design now, is the concrete next step, not an immediate merge.

**Effort:** Medium — a new optional config field, a small per-runtime metrics-parsing helper (plain-text Prometheus exposition format, not full PromQL — genuinely simple line-based parsing for ~2-3 known gauge names per runtime), and a `router.Select` weighting change. No new external dependency (Go's stdlib `net/http` suffices for a `/metrics` scrape; a full Prometheus client library is unnecessary for reading 2-3 known gauge lines).

### 4. Speculative decoding and continuous-batching visibility are, correctly, *not* gateway-coordination surfaces at the per-request level — and must not be conflated with the already-settled, distinct question of response-level model cascading (Small — a scope clarification, not a build item)

**What:** The research brief names "speculative decoding" and "continuous batching visibility" as candidate coordination surfaces. Both resolve to "no, correctly" at the per-request API layer, for two different reasons that should not be conflated:
- **Continuous-batching visibility** collapses entirely into Finding 1/3's queue-depth and KV-cache-utilization signals — `num_requests_running`, `tgi_batch_current_size`, `sglang:num_running_reqs` *are* the batching-visibility signal; there is no separate "batching" API surface beyond the aggregate metrics already covered. A per-request API cannot meaningfully expose "which batch was I in" in a way a provider-agnostic gateway could act on differently than it already can via the aggregate load signal.
- **Speculative decoding**, at the token level (a draft model proposing candidate tokens a larger model verifies in one forward pass, within a single inference engine), is a pure server-side config knob (e.g. vLLM's own `--speculative-config`) with **zero wire-visible signal** — the client-facing chat-completion response looks identical whether or not the backend used speculative decoding internally; there is nothing for a gateway sitting in front of the OpenAI-compatible endpoint to coordinate on, because the two models involved share weights/vocabulary/logits inside one process and never appear as separate HTTP-addressable entities. This is confirmed by every source found treating vLLM/SGLang speculative decoding as an engine-internal serving optimization, never as a gateway-facing API.
- A *different*, genuinely gateway-layer concept exists under a similar name — **response-level speculative decoding / model cascading**, where a cheap/fast model and an expensive/capable model are two *separate* HTTP-addressable endpoints, and a proxy layer drafts with the cheap one and verifies with the expensive one (found in this research as a real, live open-source pattern — `acvdoandrew/speculative-inference-proxy`, a Rust/Axum proxy explicitly built for this — and as a recent academic system, "RLM-Cascade," an arXiv preprint describing a proxy-layer draft/verify pipeline deployed in production against Claude Code traffic). **This is not a new finding for Kelvran — it is the same "cost-aware model cascading" question `DECISIONS.md`'s `[2026-09-14]` and `[2026-09-20]` (third entry) already researched twice and correctly left `not_yet`**, most recently via a dedicated RFC (`docs/rfcs/2026-09-20-gateway-cost-aware-model-cascading.md`) that re-verified the LLMRouterBench "model-recall-failure" bottleneck directly against the paper's own PDF. This research found no new evidence in the RLM-Cascade paper or the speculative-inference-proxy project that changes that verdict — both are single/few-data-point demonstrations (RLM-Cascade: 125 production requests; the Rust proxy: a hobby-scale GitHub project with an open "benchmark Rust vs. Python middleware latency" TODO, not a validated-at-scale system) and neither addresses the still-open blocker Kelvran's own prior research already identified (no accurate request-level confidence/refusal signal wired to any decision today).

**Why it matters for Kelvran specifically:** the research brief's phrasing risks a real failure mode this project's own conventions explicitly guard against — re-proposing an already-settled question under a differently-named research angle, rather than engaging with the existing decision directly. ## Caveats

- Every metrics-endpoint-shape claim in Finding 1 was verified against each project's own current documentation/source directly; none were cross-checked against a live, running instance of any of the five runtimes by this research (Kelvran's own repo has no self-hosted runtime deployed anywhere in its CI/dev environment to test against) — a real, disclosed limitation shared with the prior cache-token-field research this finding extends.
- Finding 2's specific numeric claims (69% p90 TTFT improvement, 75-80% cache hit rate) each rest on one primary source (an AWS sample repo's own benchmark; a Google-attributed Snap Inc. quote respectively) — the underlying *mechanism* claim (precise KV-cache-event routing measurably improves TTFT under sustained multi-turn load) is corroborated by both independently, but the exact magnitudes should be treated as illustrative of the pattern's real-world scale, not as numbers Kelvran could expect to reproduce without its own measurement.
- Finding 3's LiteLLM GitHub issue (#37622) is a single first-party bug report, not a statistically-representative sample of how often this failure mode occurs in production LiteLLM deployments — used here as a concrete illustration that the failure mode is real and reproducible, not as evidence of its frequency or typical severity.
- This research did not attempt to independently verify Ollama's own metrics-endpoint behavior beyond what the prior cache-token-field research already disclosed (its coverage gap between the legacy llama.cpp-backed runner and the newer pure-Go engine path) — carried forward as-is, not re-verified, since it was outside this round's own external-search budget to re-confirm a claim the prior round already sourced adequately.
- No live-credentialed test against a real self-hosted runtime was possible in this environment (no vLLM/SGLang/TGI/llama.cpp instance available) — every finding here rests on documentation and source-code reading, the same caveat the prior openaicompat-adapter research rounds have consistently and correctly disclosed for this exact package.
