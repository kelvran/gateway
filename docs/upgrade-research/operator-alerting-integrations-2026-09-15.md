# Operator Alerting & Incident-Response Integrations — Research Synthesis (2026-09-15)

## Kelvran ground truth (read before any external precedent)

- **Real signals that already exist, confirmed by direct code/config read this session:**
  - OTel metrics/counters: `kelvran.ratelimit.fail_open`, `kelvran.budget.threshold_crossed` (`gateway/internal/telemetry/telemetry.go:97,434`), `kelvran.cache.lookup`/`.savings_usd`/`.l3.gate_outcome`, `kelvran.llm.spend_usd`, and the standard `gen_ai.client.operation.duration`/`error.type` pair every request emits unconditionally (`docs/operations/TELEMETRY.md`).
  - A structured audit log: every Admin API mutation and read route logs a JSON line via `logger.Warn`/`Info` (`gateway/internal/admin/admin.go:140` doc comment; e.g. `admin_virtual_key_upserted`, `admin_virtual_key_deleted`, `admin_prompt_upserted`), naming the authenticating credential tier, never the secret itself.
  - Prometheus SLO burn-rate alert rules: `docs/operations/grafana/prometheus/kelvran-slo-rules.yml` — real, hand-authored MWMB (multiwindow multi-burn-rate) recording + alerting rules (`KelvranSLOFastBurn`/`SlowBurn`, overall and per-`gen_ai_provider_name`), loaded into the bundled Prometheus via `rule_files:` in `docs/operations/grafana/prometheus/prometheus.yaml`, per `docs/upgrade-research/slo-error-budget-observability-2026-09-15.md`.
- **Confirmed: no Alertmanager exists anywhere in this repo.** `grep -ril alertmanager .` (excluding this file's own future self) returns nothing outside the SLO report's own prose. `docker-compose.yml`'s only alerting-adjacent service is `observability` (`grafana/otel-lgtm:0.33.0`), and that image's own Dockerfile (fetched live from `grafana/docker-otel-lgtm`) bundles Grafana, Prometheus, Tempo, Loki, Pyroscope, and the OTel Collector — **not** Alertmanager. This directly confirms the task's framing: Kelvran's `KelvranSLOFastBurn`/`SlowBurn` alerts already fire inside Prometheus's own rule evaluator today, populate Prometheus's inert `/alerts` page, and go exactly nowhere — Prometheus has no notification capability of its own by design.
- **Confirmed: every structured log (audit + operational) shares one sink.** `gateway/cmd/gateway/main.go:167`: `slog.New(slog.NewJSONHandler(os.Stdout, nil))` — one JSON-to-stdout handler, no forwarding, no second sink, for the audit log, `budget_threshold_crossed`, `health_probe_deployment_unhealthy`/`_recovered`, everything. Loki ships inside the bundled `observability` image but nothing writes to it — no Docker logging driver, no Promtail/Vector sidecar for `gateway`'s own stdout (Vector in this repo ships only the separate `gatewayevents_v1` business-event stream to S3/GCS, per `docs/operations/vector-gatewayevents-s3-compose.yaml` — a different, narrower pipeline).
- **A real, disconnected webhook sender already exists — in `evals`, not `gateway`.** `evals/evals/cli.py`'s `trend alert --notify-webhook URL` (added per `docs/rfcs/2026-09-14-evals-quality-trend.md`) does a single `urllib.request.Request(...)`/`urlopen(..., timeout=10)` JSON POST when triggered alerts exist — no retry, no HMAC signing, no idempotency key, and the docstring explicitly disclaims scope: *"A plain HTTP POST, not a Slack/PagerDuty-specific integration — no such requirement is scoped here."* Its one real caller, `.github/workflows/evals-judge-nightly.yml`, does **not** pass `--notify-webhook` at all — the feature is real but has never been pointed at a live destination anywhere in this repo.
- **`checkBudgetAlertLadder`/`RecordBudgetThresholdCrossed`** (`gateway/internal/gateway/dataplane/dataplane.go:2378-2400`) already computes exactly the trigger LiteLLM's and Helicone's budget alerting fire on — a fixed 50/75/90/100%-of-cap ladder, crossed-once-per-bucket-per-window — but today it only increments a counter and logs a line; nothing downstream ever turns that into a notification.
- **`gateway/internal/router/router.go`'s own doc comment** confirms a *traffic-derived statistical circuit breaker (Envoy-style outlier detection, LiteLLM-style `allowed_fails` cooldown)* is deliberately deferred pending real production traffic volume — so the only real "provider going bad" signal today is the traffic-independent active health probe, which does fire a real, structured `health_probe_deployment_unhealthy`/`_recovered` log line (`dataplane.go:1880`) with the same "logged, never delivered" fate as everything else here.
- **The `observability` Grafana instance is bound to `127.0.0.1:3000` only** (`docker-compose.yml`), consistent with this pilot's loopback-only posture elsewhere — relevant to every Grafana-UI-driven recommendation below.

## Executive summary

Kelvran's own framing is exactly right: the only alerting mechanism in this repo today is a hand-authored, genuinely correct Prometheus MWMB rule file that fires into a void, because no Alertmanager — and no other notification sink — has ever been wired to receive it. Closing that loop has (at least) three real, independently-verified candidate paths, and the evidence does not converge on one: (1) a standalone `prom/alertmanager` container is the lowest-diff way to make the *already-written* `kelvran-slo-rules.yml` alerts actually notify anyone, since Alertmanager natively supports Slack, PagerDuty, Opsgenie, and a generic webhook receiver out of the box, with zero changes to the existing rule file; (2) Grafana's own embedded alerting engine (already running inside the bundled `otel-lgtm` image) supports the identical contact-point set through Grafana-native file-based provisioning — a better fit for this repo's existing dashboards-as-code discipline, but only for rules re-authored as Grafana-managed alerts, which would leave the existing Prometheus-native alerting group as dead weight unless explicitly retired; (3) a LiteLLM/Helicone-style direct push straight from Go, for the specific signals the gateway *already computes* (budget-ladder crossings, rate-limit fail-open, deployment-health-probe flips), which needs no new infrastructure at all and — critically — still works when the optional `observability` Compose profile is never started. These are complementary, not competing, and the research explicitly does not converge on discarding any of them. A parallel, lower-glamour finding turned out to be just as real: the one nightly GitHub Actions workflow this repo already runs unattended (`evals-judge-nightly.yml`) has a documented, GitHub-confirmed blind spot — scheduled-workflow failure notifications go only to whichever single person last edited the cron line — making a near-zero-cost dead-man's-switch heartbeat a genuine, independent `build_now` alongside the live-traffic-incident story. Finally, a competitor sweep found real texture rather than a uniform "everyone has this, Kelvran doesn't": LiteLLM ships the richest native proxy alerting of any comparator checked; Helicone's is real but simpler; Cloudflare AI Gateway explicitly punts alerting to bring-your-own tooling from its logs, matching Kelvran's current posture exactly; and Portkey's own paywalled budget-alert-threshold feature is documented, in Portkey's own current docs, as writing an audit-log entry and *not yet* sending any actual notification — a directly comparable, verified instance of the same gap this report is about, on a funded competitor's paid tier.

## Findings

### Finding 1 — A standalone Alertmanager is the lowest-diff way to make the already-written MWMB rules notify anyone
**Classification: build_now** · **Confidence: high**

Prometheus's own configuration reference and integrations page (prometheus.io, cross-checked against the `prometheus/alertmanager` GitHub docs) confirm Alertmanager ships native receiver types for `slack_configs`, `pagerduty_configs`, `opsgenie_configs`, `webhook_configs`, plus `discord_configs`, `msteams_configs`, `email_configs`, and (newly) `incidentio_configs` — the generic `webhook_config` exists specifically to cover *"notification mechanisms not natively supported by the Alertmanager."* Wiring this into Kelvran needs: an `alertmanager` service added to `docker-compose.yml` (still gated behind the `observability` profile, matching every other optional dependency's own pattern), one `alerting: alertmanagers: [...]` block added to `docs/operations/grafana/prometheus/prometheus.yaml` (currently absent — confirmed by direct read), and one new `alertmanager.yml` routing `severity: page` (from `KelvranSLOFastBurn*`) to a paging receiver and `severity: warn` (from `KelvranSLOSlowBurn*`) to a lower-urgency one. Zero changes to `kelvran-slo-rules.yml` itself — every label the routing tree needs (`severity`, `gen_ai_provider_name`) already exists on the fired alerts.

Sources: prometheus.io/docs/alerting/latest/configuration/ (primary), prometheus.io/docs/alerting/latest/integrations/ (primary), github.com/prometheus/alertmanager/blob/master/docs/configuration.md (primary).

### Finding 2 — Grafana's own embedded alerting is a real, zero-new-container alternative, but it does not automatically pick up Prometheus's own native alerts — it needs the rules re-authored as Grafana-managed
**Classification: not_yet — real, verified path, but a switching cost this round did not resolve** · **Confidence: high**

Grafana's own alerting docs are explicit and were checked directly: "Grafana includes a built-in Grafana Alertmanager to handle notifications... It can only handle Grafana-managed alerts" (grafana.com/docs/grafana/latest/alerting/set-up/configure-alertmanager/). A separately-running Prometheus's own `rule_files`-evaluated alerts are not automatically forwarded into Grafana's contact points; the only supported bridge is adding that Prometheus as a read-only "Alertmanager data source" for *viewing* an alert state some other Alertmanager already computed — and Grafana's own docs confirm the Prometheus Alertmanager-API implementation is read-only for contact points/notification policies from Grafana's side either way. To get Kelvran's burn-rate alerts through Grafana's own contact points (which do support Slack/PagerDuty/Opsgenie/webhook, confirmed via grafana.com/docs/grafana/latest/alerting/manage-notifications/manage-contact-points/) without a separate Alertmanager container, the burn-rate *comparisons* (not the recording rules, which stay in Prometheus computing `kelvran:slo_errors:ratio_rate*`) would need to be re-expressed as Grafana-managed alert rules querying those same already-computed series. Grafana does support this entirely as file-based provisioning — confirmed live against `grafana/provisioning-alerting-examples` (a Docker-Compose-based GitHub demo repo) and grafana.com's own `provision-alerting-resources/file-provisioning/` doc: alert rules, contact points, *and* notification policies are all provisionable via YAML under `provisioning/alerting/`, matching the exact dashboards-as-code discipline this repo already uses for `docs/operations/grafana/provisioning/dashboards.yaml`. The honest cost: adopting this path and Finding 1 simultaneously would leave `kelvran-slo-rules.yml`'s alerting group (not its recording-rule group) as dead code — still evaluated by Prometheus, still populating an inert UI page, never notifying anyone — a second source of truth this research round surfaces but does not resolve a preference between.

Sources: grafana.com/docs/grafana/latest/alerting/set-up/configure-alertmanager/ (primary), grafana.com/docs/grafana/latest/alerting/set-up/provision-alerting-resources/file-provisioning/ (primary), grafana.com/docs/grafana/latest/datasources/alertmanager/ (primary), github.com/grafana/provisioning-alerting-examples (primary, live-fetched).

### Finding 3 — Grafana OnCall is not a viable answer to this research question at all — it is archived, not merely legacy
**Classification: not_yet (explicitly ruled out, not just deprioritized)** · **Confidence: high**

Grafana OnCall OSS — the obvious "add on-call scheduling/escalation on top of whatever fires the alert" candidate, and Grafana Labs' own comparable answer to PagerDuty/Opsgenie — entered maintenance mode 2025-03-11 and was **archived 2026-03-24**, confirmed directly against the live `grafana/oncall` GitHub repo (`Status: ARCHIVED`, a banner reading *"🚨 Archived: Grafana OnCall OSS 🚨"*) and against grafana.com/docs/oncall/latest/'s own caution box: *"the Grafana OnCall OSS project is archived. The `grafana/oncall` repository is read-only... For a fully supported and actively maintained alternative, Grafana Cloud IRM offers a modern approach"* — a paid, cloud-only successor with no disclosed self-hosted OSS path. This is the same failure mode this repo's own research culture has already named once for MinIO (`docs/upgrade-research/observability-monitoring-maturity-2026-09-13.md` F7): a plausible-sounding OSS tool that looks like an obvious fit until its current repository state is actually checked. Do not build toward Grafana OnCall; it is a dead end as of this research round, not a deferred option.

Sources: github.com/grafana/oncall (primary, live-fetched, `Status: ARCHIVED`), grafana.com/docs/oncall/latest/ (primary, live-fetched).

### Finding 4 — A direct-from-Go push for signals the gateway already computes needs no new infrastructure at all, and has direct, real precedent in the closest comparable competitor
**Classification: build_now** · **Confidence: high**

LiteLLM's own alerting docs (docs.litellm.ai/docs/proxy/alerting, budget-alerts docs, and a live 2026 PR — BerriAI/litellm#31618 — adding webhook budget-threshold alerts) confirm this exact pattern is standard, precedented practice for a close, directly-comparable competitor: `general_settings.alerting: ["slack"]` posts to a Slack Incoming Webhook URL; a separate, generic `alerting_args.budget_alerts_webhook_url` (falling back to a `WEBHOOK_URL` env var) POSTs a plain JSON payload (`{event: "threshold_crossed", spend, max_budget, budget_percentage_used, ...}`) on the exact same 80/85/95%-style ladder Kelvran already computes; `outage_alert_ttl`/`minor_outage_alert_threshold`/`major_outage_alert_threshold` dedup and aggregate provider-outage errors over a rolling window before alerting, specifically to avoid an alert storm — directly relevant prior art for Kelvran's own already-real (but never-delivered) `health_probe_deployment_unhealthy` signal. Helicone's own alerts feature (docs.helicone.ai/features/alerts) independently confirms the same shape (error-rate/cost-threshold alerts routed to Slack or email) from a second competitor. None of this requires the optional `observability` Compose profile to be running at all — a real advantage over Findings 1/2 for an operator who never stands up the Prometheus/Grafana stack. Applied to Kelvran: `checkBudgetAlertLadder` (`dataplane.go:2378`), the rate-limiter's fail-open path, and `probeOneDeployment`'s unhealthy/recovered transitions are the three already-computed trigger points; the delivery mechanism itself (an operator-configured `SLACK_WEBHOOK_URL`/generic webhook-URL env var, reusing this repo's own existing env-var-secret convention) is a small, contained addition to `gateway`, independent of anything in Findings 1-3.

Sources: docs.litellm.ai/docs/proxy/alerting (primary), berriai-litellm.mintlify.app/proxy/budget-alerts (primary), github.com/BerriAI/litellm/pull/31618 (primary, live-fetched), docs.helicone.ai/features/alerts.md (primary).

### Finding 5 — The one webhook sender that already exists in this repo (`evals`' `--notify-webhook`) is real but has none of the reliability/security properties the wider ecosystem treats as baseline for sending a webhook
**Classification: build_now (hardening, honestly scoped)** · **Confidence: high**

Current industry consensus — cross-checked against Stripe's own webhook docs, Svix's published best-practices series, and the vendor-neutral Standard Webhooks specification (backed by Svix and others, `standardwebhooks.com`/`github.com/standard-webhooks/standard-webhooks`) — converges on the same small set of properties for *sending* a webhook responsibly: HMAC-SHA256 signing over `id.timestamp.body` (or an equivalent scheme) with constant-time comparison on the receiving end; a bounded exponential-backoff-with-jitter retry schedule (Svix: ~8 attempts over roughly a day; Stripe: up to 3 days in live mode) ending in a dead-letter/give-up state rather than an unbounded loop; a stable per-event ID so a receiver can deduplicate an at-least-once delivery; and doing the send from a background/async path so a slow or dead receiver never blocks the caller. `evals/evals/cli.py`'s `trend_alert_cmd` (lines ~2991-2999) has none of these: one synchronous `urllib.request.urlopen(..., timeout=10)` call, no signature, no message ID, and its own comment explicitly chooses to let a failed delivery raise as an unhandled exception rather than retry. This is not a bug — the docstring discloses the narrow scope up front, and it has never been pointed at a real destination in this repo (Finding 6's own workflow doesn't pass the flag) — but if this sender (or a close copy of it) becomes the template for the gateway-side pushes in Finding 4, or is ever pointed at a real Slack/PagerDuty-adjacent endpoint, closing this gap first is cheap and well-precedented, and the Standard Webhooks spec specifically was designed to be layered onto an existing unsigned sender without breaking current consumers.

Sources: standardwebhooks.com (primary), github.com/standard-webhooks/standard-webhooks (primary), docs.stripe.com/webhooks (primary), svix.com/resources/webhook-best-practices/retries/ (primary), svix.com/resources/webhook-university/implementation/building-a-webhook-sender/ (primary).

### Finding 6 — GitHub's own documented scheduled-workflow notification model means the one unattended nightly job in this repo has a real, silent blind spot; a dead-man's-switch heartbeat is a near-zero-cost, well-precedented fix
**Classification: build_now** · **Confidence: high**

GitHub's own docs (docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs) state plainly: *"Notifications for scheduled workflows are sent to the user who initially created the workflow... If a different user updates the cron syntax... subsequent notifications will be sent to that user instead."* There is no team/channel routing built in, and — separately, independently confirmed by a live 2026 practitioner writeup (cronalert.com) cross-checked against the GitHub Community forum — GitHub gives no signal at all for the harder failure mode, "the scheduled run never happened" (a disabled-after-60-days-inactivity schedule, a dropped run under load, a broken YAML edit). `.github/workflows/evals-judge-nightly.yml` — the one real, currently-running unattended scheduled job in this repo — has exactly this exposure today: it uses `continue-on-error: true` on its own trend-alert step and never notifies anyone external to a failed run's own GitHub UI page. `healthchecks/healthchecks` (github.com, 10k+ stars, BSD-3-clause, live and actively maintained) is a real, mature, purpose-built answer: a dead-man's-switch service with a self-hosted Docker image *and* a free hosted tier, listening for a "ping" HTTP request from a cron job and alerting the moment a ping doesn't arrive within its configured schedule+grace-period — exactly the "the job didn't run at all" case GitHub's own model cannot cover. Applied to Kelvran: one `if: always()` `curl` step pinging a Healthchecks check URL, added to the existing nightly workflow, closes this for the cost of one HTTP call and one (free-tier-eligible) account — independent of, and orthogonal to, Findings 1-4's live-traffic-incident focus.

Sources: docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs (primary), github.com/healthchecks/healthchecks (primary, live-fetched, 10k+ stars confirmed), healthchecks.io/docs/self_hosted/ (primary), cronalert.com/blog/github-actions-cron-monitoring (secondary, corroborating).

### Finding 7 — A competitor sweep shows real, checked texture, not a uniform "everyone but Kelvran has this" — including one funded competitor's paywalled alert feature that is documented as not yet actually notifying
**Classification: informational (grounds Findings 1-6, no separate build/defer verdict)** · **Confidence: high**

LiteLLM (Finding 4) has the richest native proxy-side alerting of any comparator checked this round. Helicone's is real, if simpler (error-rate/cost alerts to Slack/email). Cloudflare AI Gateway's own marketing copy explicitly frames alerting as the operator's own responsibility — *"Building custom dashboards and alerting systems directly from AI Gateway logs"* — which is functionally the same posture Kelvran is in today, from a competitor with far more production traffic and a much larger team. Portkey is the most instructive data point: its budget-alert-threshold feature is paywalled to Enterprise/select-Pro customers, and Portkey's **own current documentation** (docs.portkey.ai/docs/product/enterprise-offering/budget-policies) states outright: *"If you set an `alert_threshold`... an event is written to audit logs. Email and other proactive alerts for threshold crossings are work in progress and are not sent today."* That is the identical gap this report is about — computed-signal-with-no-delivery — disclosed by a funded competitor on a feature customers are already paying for. Kong AI Gateway and Vercel AI Gateway were not independently checked for a dedicated alerting feature this round (a real gap in this round's own coverage, not a claim either way).

Sources: cloudflare.com/products/ai-gateway/ (primary), docs.portkey.ai/docs/product/enterprise-offering/budget-policies (primary), portkey.ai/docs/product/administration/enforce-budget-and-rate-limit (primary), lushbinary.com/blog/ai-gateway-llm-routing-comparison-litellm-portkey-cloudflare (secondary, corroborating landscape framing only).

### Finding 8 — Security-relevant audit-log events share the exact same "logged, never delivered" fate as operational signals, and a real bridge (the already-bundled but unused Loki) exists but was not verified deep enough this round to call build_now
**Classification: not_yet — open question, not a resolved recommendation** · **Confidence: medium**

An `admin_virtual_key_deleted` or unexpected `admin_prompt_upserted` audit line (`gateway/internal/admin/admin.go`) is exactly the kind of event a real operator would want paged on independent of any SLO/burn-rate math — but per this session's own ground-truth read, it shares the identical single-sink fate (JSON line, stdout, `slog.NewJSONHandler`, nothing downstream) as every operational log line covered above. The bundled `observability` image already ships Loki, and Grafana's alerting engine can evaluate LogQL-based Grafana-managed alert rules against a Loki datasource exactly like the Prometheus-datasource path in Finding 2 — a real, plausible bridge. This research round did not verify the concrete wiring (a Docker logging driver plugin, or a Promtail/Vector sidecar reading the `gateway` container's stdout into that Loki instance) closely enough to call it `build_now` — it is flagged here as a genuinely open, checkable next step rather than asserted either way.

Sources: `gateway/internal/admin/admin.go` (direct repo read), `gateway/cmd/gateway/main.go:167` (direct repo read) — no external source claims this round; flagged as an internal open question deliberately, not dressed up with an unverified web citation.

## Answers to the research question's own framing

1. **How does an operator get notified today?** Confirmed exactly as the task framed it: only via a manually-wired Prometheus Alertmanager — which this repo has never configured (Finding 1's ground-truth check) — plus, separately, a disconnected `evals`-side generic webhook flag that has never been pointed at a real destination (ground truth + Finding 5).
2. **What's missing to close that loop?** Not one thing — three independently real candidates (Findings 1/2/4), each with a different infrastructure/switching cost, plus a distinct and separately real gap for "did the scheduled job even run" (Finding 6) that none of the three touch.
3. **Should this narrow to one delivery mechanism?** No — the evidence explicitly does not converge on one. Alertmanager (Finding 1) is the lowest-diff path for the alerts that already exist in Prometheus-native form; Grafana-native alerting (Finding 2) is a real zero-new-container alternative with its own dead-code cost; a direct Go-side push (Finding 4) is complementary and infrastructure-independent; Grafana OnCall (Finding 3) is confirmed not viable at all.

## Caveats

- Finding 2's "dead code" cost (running both a Prometheus-native alerting group and a Grafana-managed re-authoring of the same math) is a real tradeoff this round surfaces but does not resolve a recommended preference for — an open question below, not an oversight.
- Kong AI Gateway's and Vercel AI Gateway's alerting features specifically were not independently verified this round (Finding 7) — absence of evidence, not evidence of absence, for those two.
- The Standard Webhooks spec (Finding 5) is a relatively young, vendor-neutral effort (backed primarily by Svix); it is real and live-fetched directly from its own spec repository, but "growing adoption" is qualitative, not a hard adoption-count claim.
- Grafana's loopback-only binding (`127.0.0.1:3000`, ground truth) means every Grafana-UI-driven step in Finding 2 assumes local/tunneled access, consistent with this pilot's existing posture everywhere else, but worth restating since it is not repeated inside Finding 2 itself.
- This report deliberately did not re-litigate the MWMB algorithm or the provisional SLO target itself — `docs/upgrade-research/slo-error-budget-observability-2026-09-15.md` already covers that ground in depth; this report starts from "the rules already exist" and researches only the delivery/notification layer on top.

## Open questions

1. Given Finding 1 vs. Finding 2's tradeoff, does this project prefer a new, separately-configured Alertmanager component (more moving parts, zero disruption to already-shipped rule files) or re-authoring the alerting half as Grafana-managed rules (fits existing dashboards-as-code discipline, but orphans the current Prometheus-native alerting group)? No claim this round settles this — it is a real architectural choice, not a research gap.
2. Which of Slack, PagerDuty, Opsgenie, or a plain webhook is the actual target destination for a real human operator at Kelvran's current single-pilot-tenant stage? This report intentionally stayed destination-agnostic per its own instructions; every path above (1, 2, 4) supports all four natively, so this is a choice, not a blocker.
3. Should Finding 4's direct-from-Go push and Finding 1/2's Prometheus/Grafana-routed alerts both exist simultaneously (covering different failure classes — e.g., Go-side push for "this one deployment just failed a health probe," Alertmanager/Grafana for aggregate burn-rate), or would running both be its own source of alert-fatigue/duplication risk? Not settled this round.
4. Finding 8's Loki-bridging path needs its own dedicated verification pass (which Docker logging mechanism actually works cleanly against this repo's exact Compose shape) before it could honestly be called `build_now` — flagged, not answered, here.
