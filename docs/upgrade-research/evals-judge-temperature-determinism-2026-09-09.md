# Kelvran Evals — Does `temperature=0` Actually Fix Judge-Panel Determinism?

**Date:** 2026-09-09
**Scope:** `evals/evals/judge/providers.py`'s `_AnthropicCallModel.__call__`, `_OpenAICallModel.__call__`, `_BedrockCallModel.__call__` — none of which currently set a `temperature` parameter for any judge/panel call, relying instead on each provider's own API default. This research answers the question a prior RFC pass explicitly deferred: is pinning `temperature=0` on these shared call sites the right fix for the judge/panel non-determinism that motivated scheduling the judge-accuracy corpus as a *nightly* CI workflow rather than a gate on every push (`docs/rfcs/2026-09-08-evals-judge-panel-reducer.md`)?
**Method:** Adversarial multi-source research (3-vote verification per claim) against primary sources: a systems-research postmortem on LLM inference nondeterminism (Thinking Machines Lab), two 2024-2026 academic papers measuring "deterministic"-setting non-determinism empirically, a 2026 paper specifically studying temperature's effect on LLM-as-judge behavior (>1M evaluation trials), a 2024 survey of LLM-as-judge methods, official documentation for three real eval frameworks (Inspect AI, DeepEval, OpenAI Evals/Graders), and the G-Eval paper's own implementation details. 19 claims survived adversarial verification; 6 candidate claims were refuted and are excluded below.

---

## Context this research does not re-litigate

Kelvran's own live-measured evidence (verified directly, not assumed) already establishes that the problem is real, not theoretical:

- No call site in `evals/evals/judge/providers.py` sets `temperature` for any judge/panel call — every call runs at whichever default each provider's API applies.
- Re-running the identical 24-case judge-accuracy corpus twice against the same Bedrock-hosted judges (Claude Sonnet 5 + Claude Haiku 4.5), zero code change between runs, produced 2 of 24 different verdicts. A first real CI run of the same corpus measured a *third* different result — a 5/24 quorum-tie/disagreement rate between the two panel judges, vs. 1/24 in the earlier local runs.
- A prior RFC pass explicitly named pinning `temperature=0` on the shared `providers.py` call sites as "a real behavioral change affecting every existing `--llm-judge` caller too, out of scope here," and deferred it as a separate future hardening candidate.

This report's job is to answer that deferred question with evidence rather than intuition: does `temperature=0` deliver the determinism it's assumed to, is it the right lever at all for judge reliability, and if Kelvran does pin it, where should the change land.

---

## Findings, ranked

### 1. `temperature=0` does not guarantee deterministic output in production, for a specific, well-understood systems reason — not the reason most people assume

**What:** Thinking Machines Lab's postmortem states directly: "even when we adjust the temperature down to 0... LLM APIs are still not deterministic in practice." Critically, the paper explicitly investigates and *rejects* the popular explanation (concurrency + floating-point non-associativity from atomic adds) as uninvolved in LLM inference — GPU forward passes for LLMs involve no operations requiring atomic adds. The real mechanism is **lack of batch-invariance** in GPU kernels (matmul, RMSNorm, attention): a given request's numerical output depends on the batch size the server happens to be running it with at that moment, and batch size fluctuates nondeterministically with concurrent server load — "the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies." This was independently corroborated on Hacker News (345 points, 130 comments, no successful technical rebuttal), where one commenter separately raised that MoE models route at the batch level, so expert-choice routing leaks batch-level information across sequences — an independent confirmation of the MoE-routing hypothesis Kelvran's own RFC context already flagged as a candidate cause for its Bedrock-hosted Claude judges' variance.

**Why this matters for Kelvran:** the mechanism (server-side batch-size variance under load, for hosted/multi-tenant inference like Bedrock) is architectural to how providers serve models — pinning `temperature=0` on Kelvran's own call sites cannot reach into Bedrock's serving stack and fix it. This is direct, mechanism-level evidence that `temperature=0` is necessary-but-not-sufficient for judge-panel determinism, not a full fix.

**Confidence:** High — primary source, verified quote, independently corroborated mechanism (Thinking Machines Lab, "Defeating Nondeterminism in LLM Inference"; HN discussion id 45200925).

### 2. This isn't a one-source claim: independent academic measurement puts hard numbers on "deterministic" settings still producing real variance — including on formatting/output-structure, not just final scores

**What:** "Non-Determinism of 'Deterministic' LLM Settings" (Atil et al., Penn State/Comcast AI, arXiv:2408.04667, 5 models × 8 tasks × 10 runs, zero-shot + few-shot) found accuracy varying by up to 15% across "naturally occurring" runs at `temperature=0`, with a best-to-worst-run gap reaching 70%: "none of the LLMs consistently delivers repeatable accuracy across all tasks, much less identical output strings." The paper explicitly frames this as targeting the exact assumption Kelvran's own team held before this research: "Many users of LLM platforms expect model performance to be deterministic when temperature=0... we refer here to this behavior of output variance despite zero temperature as instability." Separately, a 2026 paper specifically on LLM-as-judge ("The Necessity of Setting Temperature in LLM-as-a-Judge," Li et al., U. Luxembourg/ETH Zürich, arXiv:2603.28304, 180,000–360,000 inference calls) found that even at their near-zero setting (T=0.01, not literal 0 — no provider tested exposes a literal-zero option in their test matrix), formatting/output violations remained non-negligible: on one config (Qwen3-Next-80B, pairwise comparison + chain-of-thought, MMLU-Pro) the error rate reached 0.25±0.03. "Output randomness in LLMs is not fully eliminated under low-temperature decoding."

**Why this matters for Kelvran:** this generalizes Finding 1 beyond a single systems postmortem to controlled academic measurement, and the second paper is *specifically about LLM-judge behavior* (not general chat/completion tasks), which is squarely the domain of Kelvran's question. It also surfaces a mechanism the pure-systems paper doesn't: near-zero temperature can still cause output-format breakage (malformed JSON, missing reasoning), which for a structured judge-verdict pipeline is its own separate failure mode from verdict flip-flopping.

**Confidence:** High — both are primary, dated, on-topic academic sources (Atil et al. under review since 2024/revised 2025; Li et al. Mar/Jun 2026), each independently verified against the actual paper text, not summaries. Caveat: the Atil et al. paper does not test LLM-judge/grading tasks specifically (MMLU/BBH accuracy benchmarks, not verdict tasks) — it is corroborating rather than directly-on-point for judge use, unlike the Li et al. paper.

### 3. Real eval-framework documentation already says this out loud: Inspect AI's own docs state `temperature=0` "reduces, but does not always eliminate, run-to-run disagreement," and DeepEval flatly states its flagship LLM-judge metric "is NOT deterministic"

**What:** Inspect AI (UK AISI's actively maintained eval framework) documents this precisely in its Reproducible Grading section: "By default the grader model runs with the provider's default generation settings... grades for borderline answers can change from run to run and across epochs... For more reproducible grading: Set `temperature=0`... Set a seed where the provider supports it. Run multiple epochs and inspect grade variance — setting `temperature=0` reduces, but does not always eliminate, run-to-run disagreement." This is the exact three-part remedy (temperature + seed + repeated-sampling variance inspection) framed as necessary *together*, not `temperature=0` alone. Separately, DeepEval's own docs state about G-Eval, their flagship custom LLM-judge metric: "Although GEval is great in many ways as a custom, task-specific metric, it is **NOT** deterministic," and their documented root cause for run-to-run score inconsistency is *not* temperature — it's that G-Eval "regenerate[s] fresh CoT [chain-of-thought] steps every run when only `criteria` is used." Their fix is to supply fixed, explicit `evaluation_steps` up front. A full-page search of DeepEval's LLM-judge documentation for the word "temperature" returns zero matches — the word is never proposed as a fix at all, anywhere in that documentation.

**Why this matters for Kelvran:** two independent, real, currently-maintained eval frameworks — one from a government AI safety institute, one a widely-used open-source eval library — both explicitly document that `temperature=0` is not a sufficient fix for judge-verdict reproducibility, and one of them (DeepEval) documents that its actual practical fix for the analogous problem is a **prompt-structure change** (fixing what varies in the generation, not the decoding parameter), which is architecturally a different kind of lever than temperature pinning.

**Confidence:** High — both are current, primary, official-vendor documentation, verified by direct fetch (Inspect AI at inspect.aisi.org.uk/model-graded.html; DeepEval at deepeval.com/docs/metrics-llm-evals), not secondhand summary.

### 4. OpenAI's own eval tooling doesn't set temperature for the judge call either, and its newer Evals API can't — reasoning-family judge models explicitly disallow the parameter

**What:** OpenAI's own cookbook example for `getting_started_with_openai_evals` sets `temperature=0.7` only in the unrelated synthetic-data-generation step used to build the eval dataset — the actual `ModelBasedClassify` grader config (the judge call) has no `temperature` field at all. Checking the underlying `openai/evals` framework source confirms this isn't an oversight in one example: neither `ModelBasedClassify` nor the OpenAI completion-function wrapper it uses hardcodes a temperature default anywhere in that judge-call path. Separately, and more structurally significant: OpenAI's current Evals/Graders API documentation states outright that for the `score_model` (LLM-judge) grader, "`temperature` changes not supported for reasoning models" — i.e., if you configure a reasoning-family model (e.g., an `o`-series model) as your judge, the temperature knob simply isn't available to you at all, full stop.

**Why this matters for Kelvran:** even setting aside whether `temperature=0` is a good idea, it is not a *universally available* lever across judge-model choices in the first place. If Kelvran's judge lineup or a future provider swap ever includes a reasoning-family model, a blanket `temperature=0` on the shared `providers.py` call site would either be silently ignored, rejected by the API, or require conditional per-model-family logic — adding real complexity to the "just pin it" option that a first read of the ask doesn't surface.

**Confidence:** High — both claims verified directly against primary sources (developers.openai.com/cookbook and developers.openai.com/api/docs/guides/graders), the latter cross-checked at the framework source-code level (openai/evals GitHub).

### 5. There is documented survey-level consensus that the eval field treats judge non-determinism as a problem to solve via repeated sampling + aggregation, not decoding-parameter tuning alone

**What:** "LLMs-as-Judges: A Comprehensive Survey on LLM-based Evaluation Methods" (arXiv:2411.15594, current through its 2025 revision) names "the inherent generative randomness of LLM black boxes" as a core problem motivating a whole category of documented mitigation techniques it calls "Final Output Optimization Strategy." It cites three concrete, real, named precedents, all of which are repeated-sampling-and-aggregation approaches rather than decoding-parameter fixes: Sottana et al. (2023) averages multiple scores per sample; PsychoBench (Huang et al., 2023) "takes the mean and standard deviation from ten independent runs"; Auto-J (Li et al., 2023) combines critiques across evaluation rounds. This same survey elsewhere reports setting `temperature=0` in its own experiments "to reduce the impact of randomness" — i.e., the field's own literature treats `temperature=0` as a partial, standard hygiene step, while treating post-hoc statistical aggregation over repeated samples as the actual documented mechanism for taming judge-output randomness.

**Why this matters for Kelvran:** this is exactly the shape of Kelvran's own already-partially-existing lever — the 2-judge panel + majority vote (`docs/rfcs/2026-09-08-evals-judge-panel-reducer.md`) is architecturally the same *category* of fix (aggregate over multiple independent judgments) that the broader field's survey literature documents as the real mitigation, not a novel or unusual choice.

**Confidence:** High — primary academic survey, verified directly, all three named precedent papers are real and checkable (not fabricated citations).

### 6. G-Eval — one of the most-cited LLM-judge papers, and a direct architectural ancestor of "set temperature=0 for determinism" — actually used two *different* strategies for its two evaluator backbones, and its stronger backbone used self-consistency sampling, not temperature pinning

**What:** G-Eval (Liu et al. 2023, arXiv:2303.16634) explicitly states, for its GPT-3.5 evaluator: "we set decoding temperature to 0 to increase the model's determinism." But for its GPT-4 evaluator — used because GPT-4 at the time did not expose token log-probabilities — the paper instead sets `n=20, temperature=1, top_p=1` and samples 20 completions to *estimate* the token-probability distribution needed for its probability-weighted scoring formula. This was a self-consistency-style multi-sample approach used as a *substitute* for a feature the model didn't expose (logprobs), not a considered judge-determinism tradeoff — but the outcome is the same as the research question's own framing: one of the field's most influential LLM-judge implementations did not pin `temperature=0` uniformly across its own judge configurations, and its stronger-evaluator configuration used repeated sampling instead.

**Why this matters for Kelvran:** this is real, specific, checkable precedent that "temperature=0 for the judge" is not even a universal norm within the single paper credited with popularizing the LLM-as-judge pattern — the choice was driven by what capability the model exposed, and the higher-capability evaluator used sampling-based aggregation, the same general family of fix as Kelvran's own panel-majority approach.

**Confidence:** High — verified directly against the primary paper PDF (Section 3.1, Implementation Details), which states both configurations explicitly and names the reason (logprob availability) for the split.

### 7. The central tension the research question asked about is real, not hypothetical: low temperature measurably induces "spurious certainty" — high run-to-run consistency without correspondingly better correctness — specifically on ambiguous/boundary cases, which is exactly Kelvran's corpus's hard subset

**What:** The same 2026 LLM-as-judge-specific paper (arXiv:2603.28304) that measured formatting violations at low temperature also directly measured and named this tension. Verbatim: "a low temperature setting (T=0.01) induces a form of 'spurious certainty,' wherein the model produces highly consistent yet not necessarily reliable judgments due to constrained output variability." The paper partitions its corpus into an "Ambiguous" subset (42.6% of items, defined by an entropy criterion — items where judges show high disagreement/uncertainty) and a "Non-ambiguous" subset, and finds the effect is concentrated exactly where you'd expect: ambiguous items show a "flip rate" that "escalates sharply to 40–50%" as temperature rises, while non-ambiguous items stay "largely insensitive to temperature variations." On that same ambiguous subset, the paper's own results table shows a higher-temperature ensemble (10 samples at T=2.0, majority-voted) beating a single low-temperature pass on judge-vs-reference agreement: 0.53 AGR vs. 0.51 AGR for single-pass T=0.01 — i.e., on the hard cases, more sampling at *higher* temperature plus voting outperformed pinning temperature low. A separate, complementary quantitative finding from the same paper's feature-importance analysis: temperature is "the most influential factor" for run-to-run **Consistency** (a dominant, large coefficient), but plays only "a minor role" for **Agreement**/accuracy against ground truth — where judge type and base model dominate instead. The paper's own framing: "temperature should be treated not as a fixed hyperparameter, but as a controllable, task-dependent design choice that mediates the trade-off between reliability and exploration."

**Why this matters for Kelvran:** this is the single most load-bearing finding for the research question as posed. Kelvran's own corpus explicitly includes nuanced/boundary-case grading — exactly the condition class this paper shows is where determinism and quality are *not* aligned, and can trade off against each other. Pinning `temperature=0` would very likely reduce Kelvran's measured run-to-run *consistency* numbers (the nightly workflow's own stated concern), while doing little for, or even measurably hurting, judge *correctness* on the corpus's hardest, most disagreement-prone cases — the ones a judge-accuracy corpus specifically exists to stress-test.

**Confidence:** High — both quotes and the numeric AGR figures independently verified against the primary source's full text and results table (arxiv.org/html/2603.28304v2), not summarized secondhand. Caveat: the paper's judge models are open-weight (Qwen3-Next-80B, Gemma-3-27b), not Claude/Bedrock-hosted judges like Kelvran's — this is real, on-topic, primary evidence of the mechanism, but an analogical (not a direct Claude-Sonnet-5/Haiku-4.5) replication.

## Direct answers to the four research questions

**1. Does `temperature=0` meaningfully reduce judge verdict variance, or do some providers/models remain non-deterministic even at `temperature=0`?**
Both, and they're not in tension: `temperature=0` (or near-zero) demonstrably reduces variance relative to a nondeterministic default, but does not eliminate it. The residual nondeterminism has a real, named systems cause — inference-serving batch-size variance under concurrent load causing floating-point-non-associative reduction-order differences in matmul/RMSNorm/attention kernels (Finding 1) — plus, independently, MoE-routing effects that leak batch-level information into per-token routing decisions (corroborating, not yet as rigorously isolated as the batch-invariance mechanism). This is confirmed by controlled academic measurement (up to 15% accuracy variance, 70% best/worst gap, even at pinned "deterministic" settings — Finding 2) and by two real eval frameworks' own documentation stating the same thing in their own words (Finding 3).

**2. Is `temperature=0` alone considered sufficient in practice, or do serious frameworks layer additional techniques?**
No framework surveyed treats `temperature=0` alone as sufficient. Inspect AI explicitly pairs it with seed-setting (where supported) and multi-epoch variance inspection, and separately ships a first-class multi-model panel with majority-vote as its *default* reducer (Findings 3, and cross-referenced Inspect AI panel-reducer precedent). DeepEval's actual documented fix for its own judge-inconsistency problem is a prompt-structure change (fixed `evaluation_steps`), not temperature (Finding 3). The broader LLM-as-judge survey literature documents repeated-sampling-plus-statistical-aggregation (mean/std across N runs, multi-source score integration) as the standing mitigation category (Finding 5). G-Eval itself — the paper most responsible for popularizing "pin the judge's temperature" — used self-consistency multi-sampling instead of temperature-pinning for its stronger evaluator backbone (Finding 6).

**3. Is there a real documented tradeoff where `temperature=0` worsens judge quality/calibration on nuanced or boundary cases, even as it improves repeatability?**
Yes, and it is directly measured, not inferred. The 2026 LLM-judge-specific paper's "spurious certainty" finding shows low temperature produces high consistency without correspondingly better reliability, with the effect concentrated on exactly the ambiguous/boundary-case subset that Kelvran's own corpus explicitly includes; on that subset, a higher-temperature ensemble with majority voting outperformed a single low-temperature pass on agreement with ground truth (Finding 7). The same paper's feature-importance analysis shows temperature dominates the Consistency metric but is a minor factor for Agreement/accuracy — determinism and correctness are driven by substantially different mechanisms, so "more deterministic" and "more correct" are not the same axis, and can trade off against each other on hard cases.

**4. Concrete recommendation — see below.**

## Concrete recommendation for Kelvran

**Do not pin `temperature=0` on the shared `providers.py` call sites (`_AnthropicCallModel.__call__`, `_OpenAICallModel.__call__`, `_BedrockCallModel.__call__`) as a blanket change.** The research above gives three independent reasons this is the wrong scope for this specific fix, beyond the "affects every existing caller" concern the prior RFC pass already flagged:

1. **It would not fully solve the problem it's aimed at.** Kelvran's own live-measured non-determinism (2/24, then a distinct 5/24, disagreement rate) is consistent with the batch-invariance/serving-load mechanism documented in Finding 1, which is a property of Bedrock's serving stack, not something a client-side `temperature` parameter can override. Expect a real reduction in flip rate, not elimination — Inspect AI's own docs say this explicitly (Finding 3), and would still need the nightly workflow (or an equivalent) to keep watching for the residual variance.
2. **It has a real, documented cost on exactly the case type Kelvran's corpus targets.** The corpus explicitly includes nuanced/boundary-case grading, and Finding 7 shows this is precisely where low temperature trades consistency for correctness ("spurious certainty"), not where the two align. A blanket temperature-0 pin optimizes for the nightly workflow's own reported metric (run-to-run agreement) at a plausible, measured cost to the panel's actual judgment quality on the hardest cases — which inverts the priority a judge-accuracy corpus exists to serve.
3. **It isn't universally available or safe as a blanket default anyway.** If any future judge-model choice is a reasoning-family model (OpenAI's `o`-series being the documented example — Finding 4), `temperature` is not a parameter that provider accepts for that call at all; a shared, unconditional `temperature=0` at the factory level either breaks that call or requires per-model-family branching logic that quietly grows the "just pin it" change into something more invasive than it looks today.

**If Kelvran wants a scoped, lower-risk version of this idea:** pin `temperature=0` (and a fixed `seed`/equivalent where the provider genuinely supports one — check per-provider; this was not separately re-verified per-provider in this pass) only for the nightly judge-accuracy corpus's *own* invocation path, not the shared provider factory functions every `--llm-judge`/`--llm-judge-panel` caller goes through. This narrows the behavioral change to the one workflow whose explicit job is measuring baseline variance, leaves every other caller's behavior untouched (directly respecting the prior RFC's own stated reason for deferring the broader change), and gives the nightly workflow a lower, more stable noise floor to measure real regressions against — while not silently degrading judge quality for Kelvran's production `--llm-judge` callers on nuanced cases, per Finding 7's tradeoff.

**Self-consistency/panel voting is the better lever to invest in, and Kelvran is already most of the way there.** Kelvran's 2-judge panel + majority vote (`docs/rfcs/2026-09-08-evals-judge-panel-reducer.md`) is architecturally in the same family as the mitigation the broader field's own documentation and survey literature actually uses (Finding 5), and the same family of fix G-Eval's own stronger evaluator used instead of temperature-pinning (Finding 6). The highest-leverage next investment based on this research is not tuning a decoding parameter but strengthening what happens on *disagreement* — which is precisely the 1-1 tie case a 2-judge majority vote structurally cannot resolve by count alone (already flagged as the single highest-leverage open design decision in Kelvran's own judge-panel-reducer research, `docs/upgrade-research/evals-judge-panel-reducer-2026-09-07.md`, Finding 6 there). Two concrete, evidence-backed directions, in order of how directly they're supported by primary sources found in this pass:
   - **Prompt/output-structure fixes that reduce the surface area for variance**, independent of temperature — DeepEval's own documented, real-world fix for judge-output inconsistency is exactly this (fixed `evaluation_steps` instead of free-form `criteria`), and it targets a different failure mode (fresh chain-of-thought regeneration every call) than temperature ever could (Finding 3). Worth auditing whether Kelvran's own judge prompts in `providers.py`/`llm_judge.py` regenerate open-ended reasoning steps per call in a way that's structurally similar.
   - **Treating disagreement (not just majority) as signal**, rather than trying to engineer it away at the sampling-parameter level — Finding 7's ambiguous-case ensemble result (higher temperature + more samples + voting beating single low-temperature passes specifically on hard cases) suggests that if Kelvran ever wants a genuinely more accurate judge on its hardest cases, more independent samples at the panel's *existing* temperature (voted), not a lower temperature, is the evidence-backed direction — though note this was only demonstrated at N=10 ensembles in the source paper, a much larger fan-out than Kelvran's 2-judge panel, so this is a documented direction, not a validated drop-in change at Kelvran's current panel size.

**What this recommendation deliberately does not resolve:** whether Bedrock, Anthropic's direct API, and OpenAI's API each expose a `seed` parameter usable in Kelvran's specific call shapes was not independently re-verified per-provider in this research pass (the "where the provider supports one" caveat is Inspect AI's own hedge, not a Kelvran-specific check) — that's a fast, concrete follow-up before implementing the scoped nightly-corpus-only change above.

## Caveats

- The two papers most specific to LLM-as-judge behavior (arXiv:2603.28304, "Necessity of Setting Temperature") and the systems-level nondeterminism postmortem (Thinking Machines Lab) tested open-weight judge models (Qwen3-Next-80B, Gemma-3-27b) or undisclosed/mixed provider infrastructure, not Claude Sonnet 5/Haiku 4.5 on Bedrock specifically. The findings are on-point by mechanism and by domain (judge tasks, not generic chat), but are analogical evidence for Kelvran's exact provider/model pairing, not a direct replication.
- The Atil et al. 2408.04667 "Non-Determinism of Deterministic Settings" paper is strong, controlled, primary evidence for the general "temperature=0 ≠ determinism" claim, but its tasks are MMLU/BIG-Bench-Hard accuracy benchmarks, not LLM-judge/grading tasks — used here as corroborating background, not judge-specific evidence.
- No source found in this pass provides a controlled, apples-to-apples ablation of Kelvran's exact scenario (2-judge Claude panel, Bedrock-hosted, `--llm-judge-panel` majority vote, at `temperature=0` vs. provider default) — every quantitative figure cited above comes from a different model/task/panel-size combination. Directional confidence is high; a precise, Kelvran-specific effect-size prediction is not something this research can respresent as measured fact.
- One candidate claim (that G-Eval's headline Spearman-correlation result was produced by the temperature=1/20-sample GPT-4 config, undercutting temperature=0 as the load-bearing lever in that paper's *best* configuration) was checked and could not be confirmed at the 2-of-3 vote bar in the underlying verification pass — it is directionally plausible given Finding 6, but is not asserted as a confirmed fact above.
- This report did not re-verify whether Kelvran's specific Bedrock endpoint configuration is subject to the same batch-invariance mechanism Thinking Machines Lab documents primarily for OpenAI/generic GPU-serving contexts — it's cited as the best-documented explanation of the general phenomenon, not as a Bedrock-specific measurement.

## Open questions

1. Does Bedrock's InvokeModel API for Claude Sonnet 5/Haiku 4.5 expose a `seed` (or equivalent) parameter Kelvran could pair with `temperature=0` for the scoped nightly-corpus change, and if so, does it come with the same "reduces but doesn't eliminate" caveat Inspect AI documents for temperature?
2. Would auditing Kelvran's actual judge prompts in `evals/evals/judge/llm_judge.py` reveal the same "regenerate fresh reasoning every call" pattern DeepEval identifies as G-Eval's real inconsistency driver — and if so, would fixed/structured evaluation steps be a cheaper, more targeted fix than either temperature pinning or panel-size changes?
3. At Kelvran's actual 2-judge panel size (vs. the 6-9-judge panels tested in the correlated-errors and dependence-aware-aggregation literature referenced in Kelvran's own prior judge-panel-reducer research), does the "spurious certainty" / ambiguous-case ensemble advantage (Finding 7) replicate, or does it require the larger fan-out (N=10) the source paper actually tested?
4. Is there a cost-efficient way to run Kelvran's nightly judge-accuracy workflow at both provider-default and pinned-`temperature=0` settings side by side for a few cycles, to get a Kelvran-specific, not-analogical measurement of how much of the observed 2/24-to-5/24 disagreement rate is attributable to temperature versus other sources (prompt structure, batch-load variance, model version drift)?
