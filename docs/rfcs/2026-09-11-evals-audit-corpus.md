# RFC: Benchmark-corpus static audit tooling

## Status

Accepted, implemented 2026-09-11.

## Context

A 2026 automated-benchmark-auditing tool (`docs/upgrade-research/evals-next-upgrade-round2-2026-09-09.md`'s Finding 3) found >25% major-defect rates (ambiguous task design, wrong ground truth, environment conflicts) across 168 surveyed benchmarks, and filtering flawed tasks moved scores ~10% on the two benchmarks structurally closest to Kelvran's own regression corpus. Confirmed via direct code inspection: `evals run --suite` — what all 6 `regression_corpus_*.json` files (137 cases total) actually use — never produces a `Span` (the only production `Span(` construction site is reached only via `rollout_cmd`'s real sandbox execution path). **Trajectory-mode auditing is out of scope this round** — it would need these corpus cases run through real `rollout` execution first, a materially larger, separate change; this phase is static-mode only.

## Design

New module `evals/evals/audit_corpus.py` (flat, third `.importlinter` layer, added to the existing third-layer `|`-joined bullet), mirroring `judge()`/`llm_judge.py`'s own precedent of staying independent of `evals.judge.providers`: it defines its own local `AuditCallModel = Callable[[str], Awaitable[str]]` type alias rather than importing `llm_judge.py`'s `CallModel`, and imports only `evals.models.EvalCase` (bottom layer). `audit_case` deliberately never calls `judge()` — auditing the design of a corpus with the same mechanism that will later judge cases drawn from it would make the audit's own blind spots identical to the thing being audited.

`AuditFinding` (frozen dataclass, mirroring `llm_judge.ParsedJudgeResponse`'s own value-object precedent): `eval_case_id`, `eval_case_revision`, `severity: Literal["no_defect", "minor", "major"]`, `reason`, `cost_usd: Decimal | None` (always `None` from `audit_case` itself — the CLI fills it in via the existing `_last_judge_call_cost_usd` helper, mirroring `_JudgeOutcome`'s own split). `build_audit_prompt`/`parse_audit_response` mirror `build_judge_prompt`/`parse_judge_response`'s exact labeled-section convention (`REASONING:`/`SEVERITY:` instead of `REASONING:`/`VERDICT:`), including the identical "missing required line is a real parse failure, never silently defaulted" error-handling discipline.

New CLI command `evals audit-corpus --suite PATH [--suite PATH ...] --out PATH [--judge-model TEXT]` (default: Sonnet 5, not the panel's usual Haiku default — a corpus-design audit benefits from the more careful model). Orchestration mirrors `_judge_case`'s existing per-case `asyncio.run(...)` idiom. **Report-only, always**: never exits non-zero based on findings, no matter how many cases are flagged major — only a real tool/IO error (unreadable suite file, an unparseable response) is a hard failure. An LLM auditing the design of the corpus it will later also judge is itself a fallible opinion, not a correctness oracle; findings are for a human to review and act on, mirroring quote-grounding's own "instrument first, act once there's real data" precedent.

## A real, live-discovered gotcha found and fixed during verification

The initial live sanity pass (against the real `cache_adversarial` corpus, with real AWS credentials) crashed immediately: Claude Sonnet 5 spent its **entire** Bedrock service-side default token budget on an internal `reasoningContent` block, returning `stopReason: "max_tokens"` with an empty visible-text response, before ever emitting the required `REASONING:`/`SEVERITY:` answer — surfaced as `_BedrockCallModel.__call__`'s own "no text content block" error. Confirmed by inspecting the raw Converse response directly (not assumed): a long, JSON-heavy audit prompt (a full `EvalCase.task_spec`, materially longer/more complex than a short judge-comparison prompt) is exactly the shape that triggers this. `make_bedrock_call_model`/`_BedrockCallModel` never set `inferenceConfig.maxTokens` at all — a real, pre-existing gap shared by every `--llm-judge`/`--llm-judge-panel` call site too, which have never hit it only because their prompts are short. Fixed by adding an optional `max_tokens: int | None = None` parameter (backward-compatible — omitting it, as every existing panel/judge caller does, leaves today's exact behavior unchanged); `audit_corpus_cmd` passes an explicit, generous `max_tokens=8192`. The broader latent gap (no `maxTokens` control at all for the shared judge/panel path) is named, not fixed, in this pass — disclosed directly in `make_bedrock_call_model`'s own doc comment for a future maintainer.

## Alternatives considered

**Trajectory-mode auditing now** — rejected as out of scope: the regression corpus's cases are scored via `evals run` (baked-in `task_spec.output`, no execution, no `Span`), not `evals rollout`; building trajectory-mode support would require running these cases through real sandbox execution first, a materially larger, separate change than this phase's own scope.

**Wiring audit findings into `--fail-under` or a similar CI gate** — rejected: an LLM's own opinion about corpus design defects is not a correctness oracle the way a Wilson-interval pass-rate check against a fixed ground truth is; gating on it risks blocking CI on a false positive with no human review step. Report-only, by design.

## Verification

New `evals/tests/test_audit_corpus.py` (9 tests): prompt-building (case id/revision/task_spec inclusion, no-reference handling, and a distinguishing assertion that this is genuinely a different prompt shape than `build_judge_prompt` — no `VERDICT` line), response-parsing for all 3 severities plus case-insensitivity plus the missing-`SEVERITY:`-line error case, and `audit_case` end-to-end with a scripted fake (no live AWS call). New CLI integration tests in `test_cli_integration.py` (4 tests): findings are written only for flagged (non-`no_defect`) cases, multiple `--suite` files combine correctly, an unreadable suite raises `click.ClickException`, and — the core report-only guarantee — a scripted fake that flags every single case `major` still exits 0. `uvx --from import-linter lint-imports` confirms the layering design (`evals.audit_corpus` on the third-layer bullet) passes — the actual CI-enforced proof, not just an argued design.

**Live sanity pass** (out of automated CI, real AWS credentials, matching this codebase's existing `RUN_LIVE_LLM_TESTS=1` convention for anything requiring a live provider key): ran the real tool against all 6 corpus files. The first attempt surfaced the `max_tokens` gotcha above (fixed, then re-verified via the full pytest/ruff/import-linter suite). The second attempt, post-fix, successfully processed and correctly parsed 6 real Sonnet 5 responses before the pass's own practical time budget was reached (137 cases at this token budget is a genuinely long-running sequential operation, not a quick check) — all 6 were well-formed, substantively on-target `major` findings correctly identifying real ambiguities in this corpus's own convention of justifying ground truth via an out-of-band, non-embedded "verified directly against the real codebase (a throwaway Go test)" appeal, which the audit correctly flags as unverifiable from the `task_spec` alone. This is sufficient live evidence that the prompt/parser mechanism works correctly against genuine model responses; running the tool to completion across the full corpus is real, disclosed follow-up work for whoever wants the full audit output, not part of this phase's own verification bar.

Full `cd evals && uv run pytest tests/ && ruff check . && uvx --from import-linter lint-imports` clean (352 passed, 11 skipped).
