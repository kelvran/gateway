# RFC: Judge-panel interface — widen `judge()`/`Score.scorer_type` (panel itself stays v2)

## Status

Accepted, implemented 2026-09-07.

## Context

`docs/upgrade-research/evals-2026-09-06.md`'s Finding 2 ("Design the multi-judge-panel *interface* now, even though the panel itself stays v2") is the trigger for this RFC, itself part of the approved Phase 2 upgrade roadmap (see `docs/agents/LOGS.md`'s 2026-09-06/07 entry). `PRD.md`'s "Open Questions Carried Forward" section has, since v1, named the exact question this RFC answers: "Whether the skeptic-panel protocol for Evals should be pairwise-comparison-based or independent-refutation-based (research favors independent refutation; final call deferred to the RFC that accompanies building it)." `evals/ARCHITECTURE.md`'s Data Model sketch has also always shown `Score { ..., scorer_type: deterministic|llm_judge|skeptic_panel|human, ... }` — `skeptic_panel` was in the sketch from day one, but `evals.judge.llm_judge.judge()` accepts exactly one `call_model` callable, and `evals.models.ScorerType` is a closed `Literal["deterministic", "llm_judge"]`. Real code has never had any panel-shaped interface at all.

**Building the panel itself is, and remains, an explicit v2 non-goal** — `PRD.md`'s own "Non-Goals" section lists "adversarial skeptic-panel judging as the default gate" as out of scope for v1. This RFC does not reopen that. What it does is widen the two seams a future v2 panel would need to touch (`judge()`'s signature, `Score.scorer_type`'s `Literal`) *now*, while the only real caller (`evals.cli`'s `_judge_with_cache`) is a single, well-understood call site — retrofitting this later, once more callers depend on the single-`call_model` shape, is strictly more expensive than typing it correctly once, per the research report's own framing.

## Design

### `judge()` accepts `CallModel | list[CallModel]`, not just one callable

Following Inspect AI's `multi_scorer()` prior art (the report's cited concrete shape — `inspect.aisi.org.uk/multiple-scorers.html`, confirmed 3-0 in the research pass): `evals.judge.llm_judge.judge()`'s `call_model` parameter is widened from `Callable[[str], Awaitable[str]]` to `CallModel | list[CallModel]` (a new `CallModel = Callable[[str], Awaitable[str]]` type alias, defined in `llm_judge.py`). Internally, `judge()` normalizes both accepted shapes into one list (`panel = call_model if isinstance(call_model, list) else [call_model]`) and then:

- an empty list raises `ValueError` — there is no judge to call, a real caller error, not a silent no-op;
- a list of exactly one — whether it arrived as a bare callable or as a length-1 list — is scored exactly as `judge()` always has: unwrap, build the prompt, await the one call, parse the one verdict;
- a list of more than one raises `NotImplementedError`, naming the RFC and explaining why: the majority-reducer aggregation across a real panel is not implemented by this function. This is the one deliberate, honest limit that keeps this RFC interface-only — it would be trivial to instead silently score with only `panel[0]` and discard the rest, but that fabricates a "panel" result from a single judge, exactly the kind of dishonest placeholder `evals/models.py`'s own `Run`/`Score` docstrings have repeatedly rejected elsewhere in this codebase ("`None` means not applicable, never a fabricated stand-in"). A real `NotImplementedError` is the equivalent discipline applied to control flow instead of a data field.

**Zero edits to any existing call site.** `evals.cli`'s `_judge_with_cache` — the only real production caller — still passes a bare `call_model` (`await judge(output=output, reference=reference, call_model=call_model, axis=axis)`), unchanged, and is scored identically to before this RFC. Every existing test in `tests/test_llm_judge.py`, `tests/test_llm_judge_integration.py`, and `tests/test_cli_integration.py` also passes a bare callable and needed no changes — verified by actually running the suite (see Verification), not assumed from the type signature alone.

### `Score.scorer_type` gains `"llm_judge_panel"`, not an overload of `"llm_judge"`

`evals.models.ScorerType` widens from `Literal["deterministic", "llm_judge"]` to `Literal["deterministic", "llm_judge", "llm_judge_panel"]`. A new, distinct value — never reusing `"llm_judge"` for a panel result — because `evals.cli`'s `report --scores` groups and gates *by* `scorer_type` (`for scorer_type in sorted({s.scorer_type for s in scores})`), and a future panel's aggregate verdict is a materially different kind of judgment (multiple models, a reducer, disagreement data) than one judge's verdict; conflating the two under one label would silently blend two different reliability profiles into one gate, the exact anti-pattern `report --scores`'s own "never blended across `deterministic` and `llm_judge`" precedent already guards against for the two existing types.

Named `llm_judge_panel`, deliberately diverging from `evals/ARCHITECTURE.md`'s original sketch spelling (`skeptic_panel`) — matching Inspect AI's own `multi_scorer()`/`model_graded_qa()` naming instead. `evals/ARCHITECTURE.md`'s Data Model section is updated in this same pass to describe this rename directly, so the sketch and the real type don't silently diverge in name only (the doc-vs-code staleness class `AGENTS.md`'s own Gotchas section already flags as a recurring problem in this repo).

No scorer in this codebase constructs a `Score` with `scorer_type="llm_judge_panel"` today — `test_score_accepts_llm_judge_panel_scorer_type` proves the type genuinely accepts it (not just that the RFC claims it does), while no production code path produces one, honestly matching this RFC's own "interface, not implementation" scope.

### Panel-size and quorum: reasoned now, not left for the v2 implementer to guess

The research report's own Open Questions section asked this explicitly rather than let it default silently: "What panel size and quorum rule should Kelvran actually pick for v2 if/when it's built — majority-of-2 ... or a 3rd-judge tiebreaker?" This RFC answers it now, as a real decision, even though the panel itself isn't being built:

- **Default reducer: majority (>50% quorum).** Matches Inspect AI's own default and extends naturally from Kelvran's *already-shipped* per-axis verdict logic (`docs/rfcs/2026-09-05-evals-multi-axis-judging.md`'s `--judge-axes`, which AND-combines each axis's independent PASS/FAIL into one case verdict) — a future panel would run majority-reduction *within* one axis's panel of judges, then AND-combine across axes exactly as today, not invent a second aggregation concept.
- **Panel composition starts at 2, disjoint model families.** PoLL (arXiv:2404.18796, confirmed 3-0 in the research pass) found that a panel of smaller, cheaper models from *disjoint* model families beats a single large judge across three judge settings and six datasets — this maps directly onto Kelvran's already-shipped Anthropic+OpenAI dual-provider wiring (`evals/judge/providers.py`'s `make_anthropic_call_model()`/`make_openai_call_model()`, both already producing a `CallModel`-shaped callable). A 2-judge panel already satisfies PoLL's "disjoint families" finding with zero new provider integration work; a 3rd/4th judge from a third family is a stretch goal for whoever builds the real panel, never a v2-launch requirement.
- **Per-judge votes preserved in metadata, not built yet.** Inspect AI's `score.metadata.panel` pattern (preserve every individual judge's vote so disagreement is inspectable after the fact, not collapsed into one bit) is the right shape for whenever the panel is actually implemented — but `Score` has no generic `metadata` field today, and adding one now, with zero producers, would be exactly the "dead code with no consumer" this codebase's own `Span` docstring explicitly rejected ("a stub field here would be dead code with no consumer"). This RFC documents the target shape as a decision for the RFC that builds the panel, rather than adding an unused field speculatively now — unlike `judge()`'s signature and `Score.scorer_type`, which have a concrete, immediate reason to widen now (an existing single-callable caller and a closed `Literal` that would otherwise need a breaking change later), a `metadata` dict with no real writer yet is pure speculation.

## Alternatives considered

**Overload `"llm_judge"` for a panel result instead of adding `"llm_judge_panel"`** — rejected. `report --scores` groups and gates by `scorer_type`; conflating a single-judge verdict and a multi-judge panel verdict under one label would silently blend two different reliability profiles into one pass-rate gate, undermining the exact per-scorer-type isolation `report --scores` already enforces for `deterministic` vs. `llm_judge`.

**Silently score only the first `call_model` when given a list of more than one** — rejected. This would produce a `JudgeResult` indistinguishable from a real single-judge verdict while quietly discarding every other judge in the list — a strictly worse failure mode than a loud `NotImplementedError`, since a caller who genuinely expects panel aggregation would get a wrong-but-plausible-looking result instead of an obvious, immediate signal that panel scoring isn't built yet.

**Add `Score.metadata: dict` now, to hold future per-judge votes** — rejected for this pass; see "Panel-size and quorum" above. Deferred to the RFC that actually builds the panel, once a real writer for the field exists.

**Keep `PRD.md`'s pairwise-vs-independent-refutation question open, resolve it only when the panel is actually built** — considered, since `PRD.md`'s own wording defers "final call" to "the RFC that accompanies building it," and this RFC does not build the panel. Rejected: the research report explicitly asked this RFC to resolve the question with a concrete design (`docs/upgrade-research/evals-2026-09-06.md`'s Finding 2: "directly answers the research brief's open design question ... rather than 'research favors independent refutation' restated"), and Inspect AI's `multi_scorer()` shape (independent per-judge calls, reduced via `majority`) *is* independent-refutation, not pairwise comparison — there's a concrete, evidence-backed answer available now, so restating "still open" would be less honest than committing to it. `PRD.md`'s own bullet is left as the historical record of when this was first raised (matching this project's existing precedent of leaving a resolved RFC's own "Unresolved Questions" bullet untouched, e.g. `docs/rfcs/2026-09-02-virtual-keys-budgets.md`'s soft-budget-cap bullet, resolved by a later RFC without editing the original) — not rewritten in place.
