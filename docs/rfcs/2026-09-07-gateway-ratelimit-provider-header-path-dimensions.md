# RFC: Rate-limit matching on provider/header/path — design only, not scheduled

## Status

Proposed (research/design record only — no implementation authorized by this RFC), 2026-09-07.

## Context

### What already shipped, and what's still named as the gap

`docs/upgrade-research/gateway-2026-09-06.md` Finding 5 named Kong's multi-dimensional rate-limit matching — "consumer × model, provider, header, path, with AND logic" [developer.konghq.com, confirmed 3-0 in that research pass] — as a real capability gap against `internal/ratelimit`. `docs/rfcs/2026-09-07-gateway-multi-dimensional-rate-limits.md` closed exactly one of those dimensions: `KeyConfig.PerModel`, a per-(virtual key, model) RPM override consulted by `KeyLimiter.AllowForModel` before falling back to the key's own default bucket, enforced in both in-memory and Redis mode. That RFC's own Alternatives Considered section named the rest explicitly as scoped-out, not silently dropped: *"Provider/header/path matching would need a materially different integration point than `checkRateLimit`'s current `(vk, model)` view of a request, and no cheap way to add all three without a much larger change was found while implementing the model dimension."* `gateway/ARCHITECTURE.md`'s `/internal/ratelimit` row repeats the same line verbatim as the current, present-tense state of the gap.

This RFC is the "materially different integration point" design that line deferred — worked through concretely, per this item's own scope, with no code change accompanying it.

### Verified: exactly what checkRateLimit sees today, and where the raw request actually lives

Read directly from the current pipeline, not assumed from the prior RFC's summary:

- `dataplane.Pipeline.checkRateLimit(ctx context.Context, vk *identity.VirtualKey, model string) (ok bool, failedOpen bool)` (`gateway/internal/gateway/dataplane/dataplane.go`) takes exactly a `*identity.VirtualKey` and a `model string`. No header map, no path, no `*http.Request` — the doc comment I re-read line-by-line confirms this is deliberate, not an oversight: `AllowForModel` and the RPM/TPM check ordering are the whole decision surface.
- Both call sites — `HandleChatCompletion` (line ~763) and `HandleChatCompletionStream` (`streaming.go`, line ~88) — call `checkRateLimit` with `vk` and `req.Model` only. `req` is `adapter.ChatRequest`, the canonical, provider-agnostic schema (`Model`, `Messages`, `Temperature`, `MaxTokens`, `Tools`, `Stream` — no header/path field of any kind, by design, since it's meant to be identical regardless of which upstream provider eventually serves it).
- The raw `*http.Request` (`r`) exists exactly one layer up, in `gateway/cmd/gateway/main.go`'s `chatCompletionsHandler`/`handleStreamingChatCompletion` — the `net/http` adapter functions that decode the JSON body into `adapter.ChatRequest` and then call `Pipeline.HandleChatCompletion`/`HandleChatCompletionStream`. Today, exactly two things are read off `r` and threaded any further: `r.Header.Get("Authorization")` (passed as a bare string) and `r.Context()` (passed through `telemetry.ExtractContext(r.Context(), r)`, which reads `r`'s headers only to extract a W3C `traceparent` for OTel context propagation — it never surfaces header *values* to the pipeline, only a `context.Context`). Every other header, and `r.URL.Path` itself, is read by `net/http` into `r` but **never passed to `Pipeline` at all** — confirmed by grep across `gateway/internal/gateway/dataplane/*.go` for any `http.Request`/`http.Header` reference: there are none. `Pipeline` has zero `net/http` dependency today, which is itself worth preserving deliberately (see Design's Alternatives-adjacent note below), not an accident to casually reverse.
- **Path matching is, today, vacuous.** `main.go` registers exactly one route: `mux.HandleFunc("/v1/chat/completions", chatCompletionsHandler(pipeline))`. There is no second path to distinguish a request by. Any path-matching design proposed here is necessarily forward-looking — it has zero live discriminating power against Kelvran's current single-endpoint surface, and this RFC says so plainly rather than implying otherwise.
- **Provider is resolved strictly *after* rate-limiting today, not before, and the reason is more than just "convenient ordering."** `checkRateLimit` runs at line ~763, immediately after auth and the `isModelAllowed` check, before the cache-key build, before `p.budget.Allow`. `dep, found := p.nextDeployment(req.Model)` (line ~869) — the call that actually resolves a `Deployment{Provider: ...}` for this request — happens over a hundred lines later, well inside the upstream-call path. `nextDeployment` calls `p.router.Select(model)`, which (`gateway/internal/router/router.go` + `health.go`) is a **stateful smooth-weighted-round-robin selector**: `Router.Select` -> `selectHealthy` -> `ms.next()`, where `ms` (`modelState`) carries a mutable cursor (`i`) advanced on every call. This matters concretely: **calling `Select` twice for the same request — once to "peek" a provider for rate-limiting purposes, and once for real routing — would consume two ticks of the round-robin cursor for what should be one logical request**, silently skewing the weighted distribution every such request touches, and the two calls are not even guaranteed to return the *same* deployment if health state changes between them (a probe result landing mid-request) or if the group has more than one healthy candidate at the current cursor position. `Deployment.Provider` is otherwise only read into a decision/telemetry record (`telemetry.ChatCompletionResult{Provider: dep.Provider, ...}`, built in `finalize`) **after** the full request — including any fallback-chain hop — has already completed. There is currently no code path anywhere that knows "the provider" for a request before routing commits to one, and the one obvious way to make it available earlier (call `Select` early) has a real, non-cosmetic side effect on load-balancing state.

### Grounding on Kong's own matching mechanics — confidence-graded, not re-researched from scratch

Per this item's explicit instruction, Kong is not re-researched here; `docs/upgrade-research/gateway-2026-09-06.md` Finding 5 is cited as-is for *what* Kong matches on (consumer × model, provider, header, path, AND logic) — that claim was confirmed 3-0 against `developer.konghq.com` in the prior pass and is treated as settled. Neither that finding nor `docs/upgrade-research/gateway-competitor-gaps-2026-09-07.md` (which name-checks the same gap at line 29 while scoping a *different* feature, hierarchical budget cascades, away from it) documents *how* Kong resolves ambiguity when a request could match more than one configured rule on the header or path dimension — that mechanism-level detail was never part of either research pass's confirmed claim set. Section "How a request matches a dimension" below is therefore this RFC's own reasoned design, informed by Kong Gateway's generally-documented Route object model (paths matched by longest-prefix by default, with an explicit opt-in to regex; headers matched by exact value against a configured allow-list, with a wildcard `*` special case) — general public API-gateway knowledge, not a claim carried over from the cited internal research's confirmed-claim set. It is flagged as such here so a future reader doesn't mistake it for something already adversarially verified the way Finding 5's top-level claim was.

## Design

**Not built now.** This section is the concrete shape a future implementer should build against once (and if) the Recommendation section's trigger fires.

### (a) What new information needs to flow into checkRateLimit, and the threading change that requires

Two of the three new dimensions need genuinely different data than `checkRateLimit` has today; the third needs nothing new at all:

- **Header matching** needs the raw request headers (or, better, a pre-extracted `map[string]string` of only the specific header names any configured rule actually cares about — see below for why not the full `http.Header`). This data exists only in `main.go`'s handler functions today. Threading it in means widening `HandleChatCompletion`'s and `HandleChatCompletionStream`'s signatures — both call sites, not one — with a new parameter, e.g. `HandleChatCompletion(ctx context.Context, authorizationHeader string, headers map[string]string, req adapter.ChatRequest)`. This is a real, visible signature change to `Pipeline`'s two public entry points, not an internal-only change — every caller (currently just the two `main.go` handlers, but also every existing test in `dataplane`'s own test files that calls these methods directly) needs updating.
- **Path matching** needs `r.URL.Path` — also only available in `main.go` today, and also not currently threaded anywhere. Given today's genuinely single-route surface (see Context above), threading path through has zero live effect until a second route exists; this RFC recommends **not** adding a `path string` parameter to `Pipeline`'s entry points until Kelvran actually has more than one HTTP route to discriminate by — adding a parameter that is a compile-time-constant string literal (`"/v1/chat/completions"`) at every call site for an indefinite period is dead-weight signature noise for a codebase whose own conventions (per `AGENTS.md`'s general discipline and this repo's own YAGNI-adjacent precedent elsewhere, e.g. the Sandbox Pool RFC's "don't build ahead of a real, demonstrated need" reasoning) argues against pre-threading unused plumbing.
- **Provider matching needs no new information at the boundary at all — it needs a reordering, or a duplicate, non-state-mutating lookup, of something already computed downstream.** This is the one dimension where "thread more data through `checkRateLimit`" is the wrong frame entirely; see the dedicated subsection below.

**A cross-cutting note on why headers should be pre-filtered, not passed as the raw `http.Header`:** passing the entirety of `r.Header` into `Pipeline` would be the first time any package under `internal/gateway/dataplane` gained a `net/http` dependency, or exposure to arbitrary caller-supplied header values it has no defined use for (a real, if minor, surface-area increase — an arbitrary header value flowing into a rate-limit bucket-key computation is attacker-influenced input by definition, same class of concern `AGENTS.md`'s "validate input at system boundaries" line already calls out generally). The handler layer (`main.go`) should instead extract only the specific header names any *configured* rate-limit rule references (resolved from `KeyConfig` at request time, or — more likely — from a small, fixed allow-list of header names the config schema itself constrains rule authors to) into a plain `map[string]string`, and pass that narrower value down. This keeps `Pipeline` provider-agnostic and net/http-agnostic in the same spirit `gateway/ARCHITECTURE.md`'s dependency-direction rules already enforce elsewhere (e.g. Cache never importing `internal/adapter`).

### Provider, specifically: peek-without-mutating, or reorder — a real design fork, not a detail

Two candidate designs, both viable, with a real tradeoff between them — this RFC does not pick one, since the right answer depends on router internals a future implementer should re-verify are still accurate at build time (this codebase's router has already changed shape multiple times per its own RFC history — WRR weights, health probing, fallback chains — so "verify against current code, don't assume this RFC's snapshot still holds" applies here as much as anywhere else in this repo):

1. **Add a non-consuming `Router.Peek(model string) (provider string, ok bool)`** that reads the current WRR cursor's *next* candidate (or the first healthy one, if the semantics are defined as "no side effect at all") without calling `ms.next()`. This preserves `checkRateLimit`'s current pipeline position (before cache, before budget) but introduces a real semantic gap: the provider the rate-limiter decided against may not be the provider that ends up serving the request, if `Select` is called for real later and returns a different one (round-robin advancing, a fallback-chain hop, or a health transition in between). A provider-scoped rate-limit bucket keyed off a `Peek` result is therefore an approximation, not a guarantee — this needs to be stated plainly in whatever RFC eventually proposes building this, not discovered as a surprise later the way `dataplane`'s own fallback-chain RFC had to separately reason about "which deployment actually served this" for telemetry purposes.
2. **Move deployment/provider selection earlier in the pipeline**, ahead of `checkRateLimit`, so the *real* `dep` — not a peek — is available for the rate-limit decision. This is more correct (no peek/actual mismatch) but is a materially bigger change: `nextDeployment`'s current position (deep inside the upstream-call path, after cache-miss, after budget-check) exists for real reasons the pipeline's current ordering encodes — routing to a specific deployment is pointless work for a request that's about to be rejected by rate-limit, budget, or served from cache anyway. Moving it earlier means either (i) accepting that wasted-work cost for every request (a real, if probably small, throughput regression, unmeasured), or (ii) doing a *cheap* provider-only lookup separate from full deployment selection (credentials, base URL, adapter wiring) — which starts to look a lot like option 1's `Peek` again, just relabeled.

Both options should be weighed by whoever actually schedules this against option 1's simplicity vs. option 2's correctness, with a real measurement (not a guess) of how often a multi-deployment model group's WRR cursor would actually diverge between a peek and a real select under realistic Kelvran deployment-count configurations (today's own fixture/test configs mostly configure one deployment per model, per a quick grep of `testdata`/example configs — under that common case, peek and real-select are always identical, which may make the whole tradeoff moot in practice and worth confirming with real data before investing in option 2's larger change).

### (b) How a request matches a dimension: exact-match, wildcard, or longest-prefix — and why they shouldn't all be the same rule

This RFC recommends **different** matching semantics per dimension, not one uniform rule, because the three dimensions have genuinely different cardinality and operator intent:

- **Provider: exact-match only.** Providers are a small, closed, code-defined set (`"anthropic"`, `"openai"`, `"bedrock"` — literally the keys of `p.adapters` and `responseUnmarshalers` in `dataplane.go`). There is no meaningful "wildcard provider" or "prefix-of-a-provider-name" concept; exact string equality against `Deployment.Provider` is the whole design space here, and anything fancier would be solving a problem that doesn't exist.
- **Header: exact-match on value, with an explicit wildcard sentinel for "any value, just require presence."** This mirrors the general shape of Kong's own header-condition model (an operator matching against a configured value list) more than it mirrors path matching — headers are typically discrete, enumerable values an operator wants to branch on (e.g. `X-Client-Tier: enterprise` vs. `X-Client-Tier: free`), not prefix-hierarchical data. A wildcard sentinel (e.g. a configured value of `"*"` meaning "any non-empty value for this header name matches") covers the "I just want to know this header was set at all" case without needing a second, parallel "presence-only" rule type.
- **Path: longest-prefix-match, not plain exact-match, and specifically for the reason Kong itself uses prefix matching for paths (per this RFC's own confidence-graded citation above) — path hierarchies are inherently nested, and an operator configuring a rule for `/v1/chat` should reasonably expect it to also govern `/v1/chat/completions` and any future `/v1/chat/*` sibling route, without needing to enumerate every current and future exact path.** Longest-prefix-match (the most specific configured prefix that matches wins) is the standard resolution for ambiguity between two configured rules — a rule on `/v1` and a rule on `/v1/chat/completions` should both be able to exist, with the more specific one taking precedence for a request to `/v1/chat/completions`, exactly analogous to how HTTP routers/CDNs/API gateways generally resolve overlapping path rules. Given today's single real route, this is genuinely speculative design — there is no live ambiguity to resolve yet — but it is the right *shape* to design for now rather than defaulting to exact-match and having to redesign matching semantics later once a second route exists and prefix relationships between routes start to matter.

**AND logic across dimensions**, per Finding 5's own description of Kong's model, composes naturally on top of the above: a configured rule specifies zero or more of {model, provider, header-name+value, path-prefix}, and a request matches that rule only if every dimension the rule specifies is satisfied (an unspecified dimension on a rule imposes no constraint — same "absence means no constraint" convention `KeyConfig.PerModel`'s own nil-map default already establishes for the model dimension). This generalizes `PerModel`'s existing two-dimension (key × model) match to N dimensions without changing that convention.

### (c) Composition with the already-shipped PerModel override

The already-shipped `KeyLimiter.AllowForModel` checks `PerModel[model]` **before** falling back to the key's own default bucket — never both, never in addition. The natural generalization, preserving that same "most-specific-wins, never double-charges" discipline, is: **the new provider/header/path dimensions would be checked as additional, independent match criteria layered onto the same rule-resolution step that currently only considers `(key, model)`** — not as a separate check that runs before or after the model check in sequence, but as part of a single, unified "find the most-specific rule matching this request's full dimension set" resolution that model-only matching (today's `PerModel`) is a special case of. Concretely: today's `AllowForModel(ctx, keyID, model)` would generalize to something like `AllowForRequest(ctx, keyID, dims RequestDimensions)` where `RequestDimensions{Model, Provider, Headers, Path}` carries whatever the caller currently knows (a caller with no header/path threading yet, per (a) above, would construct a `RequestDimensions` with only `Model` set, and the existing PerModel-only behavior falls out as the degenerate case with zero regression — the same backward-compatibility discipline `AllowForModel` itself already applied relative to `Allow`). A request then resolves against whichever configured rule has the most matching dimensions specified (or the most *specific* per the per-dimension matching rules in (b) — e.g. a longer path prefix beats a shorter one), falling through to the key's own plain default bucket only when no rule matches at all — exactly `AllowForModel`'s existing fallback behavior, generalized rather than replaced.

This composition question has one honest open sub-question this RFC does not resolve: **when a request matches two configured rules that are each specific along a different dimension (e.g. a per-model rule and a per-header rule, neither of which subsumes the other), which wins?** Kong's own AND-logic framing (cited in Finding 5) suggests rules are conjunctive predicates over a request, not a strict specificity ordering — meaning two "rules" in Kong's actual model are more like two independently-evaluated policies than one is picked over the other. Whoever implements this should re-verify Kong's real conflict-resolution behavior (not assumed here, since it goes beyond Finding 5's confirmed claim set) before committing to "most dimensions wins" as this RFC's default suggestion above — it is a reasonable starting design, not a verified-correct one.

### (d) Config schema: extend KeyConfig, or a new section?

**Extend, following `PerModel`'s own precedent almost exactly — do not introduce a parallel config section.** The generalization in (c) above (`RequestDimensions`-shaped matching replacing the model-only `PerModel` map) argues for evolving `KeyConfig.PerModel map[string]ModelRateLimit` into something like `KeyConfig.Rules []RateLimitRule` where each `RateLimitRule` carries an optional `Model`, `Provider`, `Header{Name, Value}`, `PathPrefix`, plus its own `Capacity`/`RefillPerSecond` — a list of matchable rules rather than a map keyed by one dimension, since a map can't represent "match on provider AND header" as a single key the way `map[string]ModelRateLimit`'s single string key can for model-only matching. This is a breaking internal shape change to `KeyConfig` (not to its JSON/YAML wire shape necessarily — `rate_limit.per_model.<model>` could still parse into a `RateLimitRule{Model: <model>}` for backward file-format compatibility, with a new, separate `rate_limit.rules` YAML section for the general N-dimension case), and would need the exact same "both static YAML and the live Admin API, both" discipline `docs/rfcs/2026-09-07-gateway-multi-dimensional-rate-limits.md`'s own Design section called out for `PerModel` — `controlplane.VirtualKeyConfig` and `internal/admin`'s `rateLimitRequest` would both need the new shape, not just one. A genuinely new, separate top-level config section (distinct from `rate_limit` entirely) was considered and rejected: these are still fundamentally rate-limit rules, governed by the same `KeyConfig`/`KeyLimiter` machinery, and splitting them into a separate section would fragment one conceptual feature (multi-dimensional rate-limit matching) across two config surfaces for no benefit — the opposite of `PerModel`'s own "extend the existing type" precedent, which this RFC's Alternatives section (below) also reasons about directly.

### Verification a future implementation would need (not run here)

Sketched for whoever eventually builds this, not executed: the same class of proof `PerModel`'s own RFC's Verification section already established a precedent for — a "byte-identical behavior when zero rules configured" test (mirroring `TestAllowForModelByteIdenticalToAllowWhenNoPerModelConfigured`), a "most-specific match wins" test per whatever conflict-resolution rule (c) above settles on, a Redis-mode distinct-key test (the `perModelBackendKey` NUL-byte-separator pattern generalizes directly — a rule's full dimension tuple, not just `keyID+model`, needs an equally collision-proof key construction), and — given the new `net/http`-adjacent header/path plumbing in `main.go` — an integration test proving a header-based or path-based rule actually triggers against a real `httptest` request, matching this project's own "real HTTP server via httptest" integration-test convention already named in `AGENTS.md`'s Testing section.

## Effort and recommendation

### Honest complexity estimate

**Medium-Large**, matching (not exceeding) the estimate the prior RFC's own originating research (`docs/upgrade-research/gateway-2026-09-06.md` Finding 5) already gave this exact scope ("Medium-Large for multi-dimensional rate-limit matching (touches `internal/ratelimit`'s key shape)") — this design pass, having now worked through the concrete mechanics, does not find reason to revise that estimate upward or downward, but can now decompose it into real sub-pieces with materially different risk profiles:

- **Header threading + header-match rules**: genuinely Medium. The data (`r.Header`) already exists at the right layer (`main.go`); the work is a narrow, well-bounded signature change through two call sites plus a straightforward exact-match/wildcard rule evaluator. Lowest risk of the three.
- **Path threading + prefix-match rules**: Small in code, but **currently has zero product justification** — there is exactly one route. Building this ahead of a second route existing would be speculative infrastructure of the exact kind this repo's own precedent (`docs/rfcs/2026-09-07-evals-sandbox-pool-deferred-decision.md`'s explicit "don't build ahead of a real, demonstrated need" reasoning, and the Sandbox Pool RFC's own citation of the distributed-cache Phase 2d gating and the bootstrap/Bayesian-stats verdict) has repeatedly declined elsewhere. This is the strongest single reason not to schedule the *whole* Finding-5 gap as one unit.
- **Provider-dimension matching**: Medium-to-Large and the genuine architectural risk center of this whole RFC — not because the match logic is hard (it's the simplest of the three per (b) above), but because giving `checkRateLimit` an honest, non-approximate answer to "which provider will serve this" requires either accepting the peek/actual-mismatch risk named in the Provider subsection above, or a real pipeline reordering with its own wasted-work and correctness tradeoffs. This is the piece most likely to reveal additional complexity once someone actually starts implementing it — router internals (WRR cursor semantics, health-probe interaction) are exactly the kind of thing that tends to have more edge cases than a design pass surfaces on paper.
- **Config schema generalization (d)**: Medium — mechanical once (b)/(c) are settled, but touches three surfaces (`ratelimit.KeyConfig`, `controlplane.VirtualKeyConfig`, `internal/admin`'s request shape) that all need to move together, per this codebase's own already-established "never ship a rate-limit-adjacent field in only one of the two mutation surfaces" discipline.

### Recommendation: do not schedule this as one unit; the three dimensions have different real justification today

This RFC's own honest recommendation, reasoned from the above rather than restating the prompt's framing: **provider and header matching are worth scheduling as a real, bounded follow-on once there is a concrete operator-facing use case asking for either specifically** (e.g. a real request — from an actual Kelvran deployment scenario, not a hypothetical — to rate-limit one client tier's traffic differently by a header they set, or to give one virtual key a tighter cap specifically against one upstream provider regardless of model, mirroring cost/reliability differences between providers that PerModel's per-model framing doesn't capture). **Path matching should stay explicitly deferred until Kelvran has more than one HTTP route** — building prefix-match plumbing against a single-route surface has no way to be validated as correct today (there's nothing to test "most specific wins" against), and this RFC recommends whoever eventually adds a second route revisit this design fresh at that point rather than building it blind now. This mirrors the Sandbox Pool RFC's own "trigger, not a blanket 'later'" discipline: a vague "someday" is exactly the kind of unresolved fork this repo's own convention (per that RFC's explicit framing) tries to avoid re-opening from scratch — but path-matching's trigger genuinely is "a second route exists," which is a cleaner, more falsifiable condition than trying to invent a synthetic threshold the way the Sandbox Pool RFC had to for CI wall-clock time.

If and when either provider or header matching is scheduled, this RFC's Design section above is the concrete starting shape — but the Provider subsection's peek-vs-reorder fork should be re-decided against the router package's *then-current* code, not assumed from this snapshot, following this repository's own recurring "verify against current code, don't trust a doc's present-tense claim" discipline (`AGENTS.md`'s Gotchas section, promoted there for exactly this class of drift risk).

## Alternatives considered

**Building all three dimensions (provider, header, path) in one implementation pass**, matching Kong's own full breadth in a single change. Rejected as a recommendation (though not as a *design*, which this RFC still provides in full): path matching has no live justification yet (see Recommendation), and bundling a well-justified dimension (header, arguably provider) with an unjustified one (path) would either delay the justified work or ship unused, untestable path-matching code — the same "don't build ahead of a real, demonstrated need" reasoning this repo has applied consistently elsewhere.

**A separate, parallel matching engine outside `internal/ratelimit`** (e.g. a new `internal/gateway/dataplane/ratematch` package that wraps `KeyLimiter` rather than extending it). Considered, and rejected in favor of extending `KeyConfig`/`KeyLimiter` directly, for the same reason `docs/rfcs/2026-09-07-gateway-multi-dimensional-rate-limits.md`'s own Alternatives section rejected a parallel `PerModelLimiter` type: `TokenBucket`'s refill/capacity mechanics and `KeyLimiter`'s existing `configs`/`buckets` maps are exactly the substrate a richer rule set slots into, and a parallel engine would duplicate that machinery for no offsetting benefit while adding a second place bucket state can live.

**Passing the raw `http.Header` (or the raw `*http.Request`) all the way into `Pipeline`**, rather than a pre-filtered `map[string]string`. Rejected in (a) above: it would be the first `net/http` dependency inside `internal/gateway/dataplane`, widens the attacker-influenced-input surface reaching a rate-limit-key computation beyond what's actually needed, and breaks this codebase's own established pattern of keeping `Pipeline` transport-agnostic (mirrors, in spirit, the Cache/`internal/adapter` dependency-direction rule `gateway/ARCHITECTURE.md` already enforces for a different pair of packages).

**Resolving cross-dimension rule conflicts (the (c) open sub-question) inside this RFC rather than leaving it open.** Considered, but rejected as false precision: Kong's actual conflict-resolution semantics for two independently-matching AND-logic rules were not part of Finding 5's confirmed claim set, and guessing an answer now (rather than the honestly-labeled "reasonable starting design, not verified-correct" given in (c)) would risk exactly the kind of doc-vs-reality drift `AGENTS.md`'s own Gotchas section already flags as a recurring, named risk class in this repository.
