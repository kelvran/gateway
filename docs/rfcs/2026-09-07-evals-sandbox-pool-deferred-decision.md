# RFC: Evals Sandbox Pool — asyncio-over-Ray decision, deferred pending a real trigger

## Status

Accepted (decision only — implementation deferred, gated on trigger below), 2026-09-07.

## Context

### The real current model

`evals/evals/rollout/scheduler.py`'s `run_suite` executes every `EvalCase` **sequentially** — one `run_in_sandbox()` call at a time, awaited to completion (success, error, or timeout) before the next case starts. The module's own docstring states the constraint explicitly: "one `EvalCase` maps to exactly one `run_in_sandbox()` call, executed one at a time (no `asyncio.gather`, no worker pool, no Ray)... sequential `asyncio` is the stated v1 posture; concurrency is a later upgrade, not a shortcut taken here." `evals/evals/rollout/sandbox.py`'s `run_in_sandbox()` shells out to `docker run --rm --network=none --read-only --tmpfs=/tmp:rw,exec,nosuid,size=64m`, one fresh container per call, torn down via `--rm` immediately after. Neither file is touched by this RFC — this is a decision record only, per the approved plan text for this item.

`evals/ARCHITECTURE.md`'s own Tech Stack table already names the fork in the road this RFC resolves: "Orchestration | `asyncio` at v1; Ray Core actors once concurrent-rollout count justifies it." That line has stood unresolved (no criterion for "justifies it," no design for what the asyncio path would even look like) since it was written. This RFC gives both: the decision, and the concrete trigger.

### Why this isn't a live problem yet — verified, not assumed

Before proposing a trigger, it's worth being precise about where CI stands today, because the honest answer changes the shape of the trigger: `.github/workflows/ci.yml`'s `evals` job runs `uv run pytest tests/` (fast, in-process) plus a "CI gate smoke test" step that invokes `evals run --suite tests/fixtures/golden_example.json` — **not** `evals rollout`. `evals run`'s `task_spec.output` is a value already baked into the fixture file (per `scheduler.py`'s own docstring, contrasting itself with this exact CLI convention); it never calls `run_in_sandbox()` or touches Docker at all. `golden_example.json` has exactly 3 cases. So today, the PR-blocking CI gate's real wall-clock cost from sandboxed rollouts is not merely small — it is **zero**, because no sandboxed rollout is wired into CI at all yet. The trigger condition below has to account for that precondition explicitly, not just propose a number in the abstract.

### Real prior art — Inspect AI, verified live against current docs (2026-09-07), not restated from the research report's summary alone

`docs/upgrade-research/evals-2026-09-06.md` Finding 5 already identified Inspect AI (built by the UK AI Safety Institute) as the relevant precedent for this exact fork. Before writing this RFC, that claim was re-verified directly against Inspect AI's own current documentation (`inspect.aisi.org.uk`), not trusted from the prior report's summary or from training-data memory:

- **Confirmed, `inspect.aisi.org.uk/parallelism.html` (fetched 2026-09-07):** Inspect's concurrency primitives are built on **AnyIO**, "an async backend independent implementation of async primitives," running on top of **asyncio** by default (**"Inspect uses asyncio and is compatible with user code that uses native asyncio functions"**), with an optional Trio backend via `INSPECT_ASYNC_BACKEND=trio`. No Ray, multiprocessing, or actor/distributed framework is used for ordinary (single-host) concurrency — everything is single-process, cooperative async scheduling.
- **Confirmed, same source:** the real, shipped config knobs, more specific than the research report's summary named: `max_connections` (concurrent model-API connections, default 10, scoped per-provider), `max_tasks` (parallel tasks, default 1, since "most tasks consist of 10 or more samples" so sample-level parallelism already suffices), `max_samples` (concurrent samples within a task, defaulting to `max_connections + 1`), **`max_sandboxes`** (parallel sandbox environments — e.g. Docker containers — with the Docker provider itself defaulting to "twice the number of processors available to the eval"), and `max_subprocesses` (concurrent subprocess calls, defaulting to the number of available processors). `max_sandboxes` is the single most directly on-point precedent for this RFC: it is exactly the "bound how many Docker containers run at once" knob a Kelvran Sandbox Pool would need, already shipped and named almost exactly as proposed below.
- **Confirmed, `inspect.aisi.org.uk/eval-sets.html` (fetched 2026-09-07):** eval-set-level parallelism (`max_tasks`, "the greater of 10 and the number of models being evaluated" by default) is also in-process/single-host, balancing load across model providers — not across compute nodes. **Inspect Flow** is confirmed as a real, separate companion package "for running and managing evaluations at scale, built on top of eval sets," but its documented feature set (specs, sweeps, defaults, a log-indexing "Flow Store") is about *management* at scale, not cluster/distributed *compute*. This is a real, useful correction to the research report's own slightly stronger framing ("true cluster-scale execution is delegated to a separate companion package") — the more precise, currently-verifiable claim is narrower: Inspect's core framework has no Ray/cluster mechanism anywhere, and the one adjacent companion package that exists is not documented as adding one either. Flagged here as **inferred-not-confirmed** (Inspect Flow could plausibly add distributed execution in a way its own docs don't foreground) rather than stated as settled fact, per this project's own confidence-framing discipline.

Net effect on the decision: the research report's core claim — asyncio/AnyIO, not Ray, for a comparable eval framework's rollout concurrency — holds up under direct, current verification, and comes with a more concrete config-knob precedent (`max_sandboxes`) than the original summary cited.

### Non-goal alignment

`PRD.md`'s own v1 non-goal list is explicit: "massively parallel (10K+) eval rollouts" is named, verbatim, as out of scope. Nothing in this RFC reopens that. A Sandbox Pool bounded by a `max_concurrent_sandboxes` knob in the single-digit-to-low-double-digit range (matching Inspect's own defaults, which top out at "twice the processor count" for Docker) is *ordinary* multi-sample parallelism on one host — the same class of concurrency Inspect ships as its default, not the cluster-scale case the PRD non-goal is about. Ray Core's real value proposition (multi-host distribution, actor supervision across a cluster, fault-tolerant scheduling of long-lived stateful workers) has no purchase on that number.

### The trigger — a concrete, reasoned proposal, not left open again

`docs/upgrade-research/evals-2026-09-06.md`'s own Open Questions section asked this explicitly and left it unresolved: *"What concrete, measurable threshold should trigger building the Sandbox Pool — is 'CI wall-clock time exceeds N minutes' the right proxy, or should it be tied to a specific rollout-count-per-PR figure?"* This RFC resolves it, rather than re-parking it, as a compound condition with a precondition:

**Precondition (must be true first):** a real regression-tier suite of genuinely Docker-sandboxed cases (`evals rollout`, not `evals run`) is wired into the PR-blocking `evals report --fail-under` CI gate — i.e., the CI smoke step described above is replaced or supplemented by one that actually exercises `run_in_sandbox()` against real regression cases, per Finding 1's own "default the CI gate to the regression tier" recommendation. Before this is true, "CI wall-clock time from sequential rollouts" is not a measurable quantity at all — there is no real rollout-derived wall-clock time in CI to measure. Building a Sandbox Pool before this precondition holds would have no PR to speed up.

**Trigger (once the precondition holds), either of:**

1. **Wall-clock:** the `evals rollout`-driven CI step's own measured wall-clock time exceeds **5 minutes** on a normal (non-degenerate) PR run of the regression tier, measured directly from CI job logs — not estimated.
2. **Case count:** the regression tier backing that CI step grows past **30 cases**.

Both numbers are grounded in real, already-established project quantities, not picked from thin air:

- **5 minutes** is a reasoned multiple of `docs/testing/TESTING.md`'s own already-declared PR-blocking ceiling for every other integration-test row in its test-pyramid table ("Under a minute"), which that same document names as a deliberate discipline: *"Never let the full sweep block a PR — that's exactly the kind of slow-test-in-CI problem that erodes the discipline of running tests at all."* Docker-sandboxed rollouts are inherently heavier than a Go/pytest integration test (real container start/stop, real command execution, not an in-process assertion), so holding them to the exact same "under a minute" bar isn't realistic — but the existing ceiling is the right anchor to reason from rather than an unrelated number. 5x (5 minutes) is generous enough to absorb real per-container overhead while staying well short of the point where PR turnaround visibly degrades.
- **30 cases** is grounded in `scheduler.py`'s own `DEFAULT_SANDBOX_TIMEOUT_S = 30`: a strictly-sequential 30-case regression suite, even in the fully degenerate case where every single case hits its full 30s timeout, takes exactly 15 minutes — already 3x the wall-clock trigger above. Under a more realistic assumption (a few seconds per case for container start + a trivial command + teardown, not a full timeout), 30 cases lands at roughly 1.5–2.5 minutes — meaning the two thresholds are designed to trip at approximately the same real point under normal conditions, as a cross-check on each other, not two independently-guessed numbers. 30 is also a plausible near-term real figure: the regression tier's only content today is the 3 non-sandboxed fixture cases in `golden_example.json` — 30 represents a realistic order-of-magnitude near-term suite, not a speculative distant one.

Both thresholds are explicitly **starting proposals to be confirmed against a real measured wall-clock time** once the precondition holds and a real regression suite exists — this RFC does not claim false precision, only that a concrete, falsifiable number belongs on record now rather than a re-opened question later. Whoever wires the precondition should re-check both numbers against the first few weeks of real CI runs and adjust in `DECISIONS.md` if the real data disagrees, rather than treating either as sacred.

## Design

**Not built now.** The following is the concrete shape a future implementer should build against once the trigger above fires — specific enough to save a re-derivation pass, without shipping any of it today.

### Config surface

A new keyword-only parameter on `run_suite`, analogous to `cached_runs`/`early_stop`/`span_sink` (all keyword-only, all default to a value that reproduces today's exact behavior):

```python
async def run_suite(
    cases: list[EvalCase],
    *,
    cached_runs: dict[str, Run] | None = None,
    early_stop: EarlyStopConfig | None = None,
    span_sink: list[Span] | None = None,
    max_concurrent_sandboxes: int = 1,
) -> list[Run]:
```

`max_concurrent_sandboxes=1` is the default specifically so that omitting the new parameter reproduces today's fully-sequential behavior byte-for-byte, matching the exact "additive, off-by-default" convention `run_suite`'s own docstring already states for its other three optional mechanisms. Exposed on the CLI as a new `evals rollout --max-concurrent-sandboxes` option (default `1`), living in `cli.py` next to `--early-stop-*`/`--use-cache`, not a new YAML/env-var config file — evals has no gateway-style persistent config file today, and this doesn't need to be the first one to introduce it. Naming deliberately follows Inspect AI's own `max_sandboxes` precedent rather than inventing a new vocabulary.

### Concurrency primitive

`asyncio.Semaphore(max_concurrent_sandboxes)`, acquired immediately before each real `run_in_sandbox()` call and released after it returns (success, exception, or timeout) — the same "throttle a resource-bound operation with a semaphore" pattern Inspect AI's own docs recommend for user-code concurrency (its `concurrency()` context manager) and the standard Python idiom for bounding concurrent I/O-bound work. The suite's cases are launched as `asyncio.create_task` (or fed through `asyncio.gather` over a bounded generator) inside the loop currently in `run_suite`; the semaphore, not the task-launch mechanism, is what actually bounds real concurrent Docker invocations. `sandbox.py`'s own per-call `timeout_s` handling (the `--cidfile`-based real `docker kill` on timeout, fixed 2026-09-04) is completely untouched and orthogonal — the Pool only bounds *how many* concurrent `run_in_sandbox()` calls exist system-wide at once; it must never reach into `sandbox.py`'s own per-call timeout/kill logic, which already does its own job correctly.

Cache hits (`cached_runs`) and early-stopped groups (`stopped_groups`) must **not** consume a semaphore slot — they never call `run_in_sandbox()` today and shouldn't start to. Only a real sandbox launch should acquire the semaphore.

### Preserving `run_suite`'s existing contracts under concurrency — the two real subtleties

Two behaviors of the current sequential implementation are load-bearing and need an explicit answer, not a silent regression, when cases start running concurrently:

1. **Output ordering.** `run_suite` returns `list[Run]` in the same order as its `cases` input today, because the loop is sequential. Under concurrency, tasks complete in whatever order their containers happen to finish, not submission order. **Design decision for the future implementer:** pre-allocate a `list[Run | None]` sized to `len(cases)` and write each completed `Run` into its own case's original index, rather than appending in completion order — this keeps `run_suite`'s output-order contract provably unchanged for every existing consumer (`evals.cli`, every test asserting on `runs[i]`) with zero caller-side changes required. This is a real design decision, not an afterthought: appending in completion order would be a silent, easy-to-miss behavioral break for exactly the callers this change is supposed to be transparent to.

2. **Early-stop tally races.** `_stop_after`/`tally_and_maybe_stop`'s `group_tallies`/`stopped_groups` dicts are mutated once per completed case today, safely, because only one case runs at a time. Under concurrency, two cases from the *same* `(eval_case_id, eval_case_revision)` repeated-trial group can be in flight simultaneously and both attempt to update the same tally entry near-simultaneously. **Design decision for the future implementer:** guard the tally read-modify-write with an `asyncio.Lock` scoped per `group_key` (or one lock covering the whole `group_tallies` dict, given tally updates are cheap, non-blocking, in-memory operations — a single shared lock is simpler and has negligible contention cost relative to a real Docker-bound `run_in_sandbox()` call). Separately, and more importantly to document up front: concurrency necessarily softens the mSPRT's "stop by exactly the Nth trial" ergonomic guarantee — several trials from the same group can already be in flight before a stopping decision is recorded and observed by the scheduling loop, so a concurrent Pool can run a small number of trials *past* the theoretical minimum a strictly sequential run would have stopped at. This does not weaken the mSPRT's actual statistical validity (its anytime-valid guarantee holds pointwise per trial regardless of arrival order — `mixture_sprt_early_stop`'s own math is unaffected), only its resource-savings ergonomics; the future implementer should name this explicitly in that RFC rather than silently discover it, exactly the kind of subtlety this decision-record RFC exists to pre-derive.

### Sandbox isolation model — unaffected, by design

Finding 5 already confirmed Kelvran's per-case isolation posture (`docker run --rm --network=none --read-only --tmpfs=/tmp`, one fresh container per case, torn down immediately) is already correct and matches Inspect AI's own structural pattern. A Sandbox Pool changes nothing about `sandbox.py`'s isolation contract — it is purely a concurrency bound layered on top of `scheduler.py`'s loop. `--network=none` already prevents any cross-container communication, so running N containers concurrently instead of 1-at-a-time introduces no new cross-case isolation surface; the only new operational concern is ordinary Docker daemon capacity (concurrent `docker run` invocations competing for the same daemon and host resources), which is why the config knob exists at all. A reasonable starting default for the eventual implementer to *propose* (not to hardcode blindly) — following Inspect's own Docker-provider default of "twice the number of processors" — would be something conservative and host-aware (e.g. `min(4, os.cpu_count() or 1)`) rather than an unconditional fixed constant; this RFC does not mandate a specific default beyond noting Inspect's own precedent, since the right number depends on the real CI runner's resource profile at build time, not on anything decidable today.

## Alternatives considered

**Ray Core actors**, per `evals/ARCHITECTURE.md`'s own previously-open Tech Stack line. Rejected for the trigger's scope: Ray's real value — multi-host distribution, actor supervision across a cluster, fault-tolerant scheduling of long-lived stateful workers — has no purchase on the ordinary, single-host, single-digit-to-low-double-digit concurrency this RFC's trigger is actually about, and `PRD.md`'s own non-goal explicitly excludes the 10K+-rollout scale where Ray's value proposition would start to matter. It would also be a genuinely new, heavyweight runtime dependency (a Ray cluster to deploy, monitor, and operate) introduced speculatively, ahead of any demonstrated need — the same "don't build ahead of a real, demonstrated need" discipline this project already applied to bootstrap/Bayesian eval stats (Finding 3, reaffirmed not overturned) and to the distributed cache (gated on Phase 2d's own telemetry showing a real cross-instance signal first). Reserved explicitly as the right tool *if* Kelvran ever needs genuine multi-host distribution — which remains a different, larger, and currently out-of-scope problem.

**`multiprocessing`/`ProcessPoolExecutor`.** Rejected: `run_in_sandbox()` is already I/O-bound (waiting on a subprocess and the Docker daemon, not CPU-bound Python computation), so multiprocessing's actual benefit — working around the GIL for CPU-bound work — doesn't apply here; it would only add process-spawn and IPC/pickling overhead for no real gain over `asyncio.Semaphore`-bounded concurrency. `AGENTS.md`'s own Python convention already commits to `asyncio` for I/O-bound orchestration specifically, so this would also be a deviation from an already-stated project convention with no offsetting benefit.

**Building the Sandbox Pool now, ahead of any real trigger.** Rejected: as established in Context above, the CI gate does not exercise a single real sandboxed rollout today — there is no measured wall-clock cost to fix yet. Building this now would be speculative infrastructure exactly of the kind this project has already declined elsewhere for the same reason (Finding 3's bootstrap/Bayesian-stats verdict; the distributed cache's Phase 2d gating).

**Leaving the decision and trigger unrecorded, to be re-derived whenever this comes up again.** Rejected — this is precisely what the approved plan text for this item asks to avoid. Re-deriving the asyncio-vs-Ray argument and re-verifying Inspect AI's precedent from scratch every time Finding 5's open question resurfaces is strictly more expensive than writing this RFC once, now, while both are still fresh and cheap to check.
