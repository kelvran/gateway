# RFC: Anthropic/Bedrock cache-token cost-accounting fix

## Status

Accepted, implemented 2026-09-10.

## Context

A `docs/upgrade-research/gateway-next-upgrade-round2-2026-09-09.md` deep-research pass surfaced a real correctness/cost defect, verified directly against the current code: `gateway/internal/adapter/anthropic/anthropic.go`'s native `Usage{InputTokens, OutputTokens}` and `bedrock/bedrock.go`'s native `Usage{InputTokens, OutputTokens, TotalTokens}` have no fields for either provider's real cache-token usage — `encoding/json` silently drops `cache_creation_input_tokens`/`cache_read_input_tokens` (Anthropic) and `cacheReadInputTokens`/`cacheWriteInputTokens` (Bedrock) on unmarshal. Every downstream consumer of `adapter.Usage` inherits the gap: `costaccounting.Calculate` undercounts real dollar cost and per-key budget spend; the TPM rate-limit dimension (`ReconcileTPM`) undercounts real token usage; and the `gen_ai.usage.input_tokens` OTel attribute undercounts the real figure. This is the *default* path today, not an edge case, since `docs/rfcs/2026-09-07-gateway-cache-control-auto-populate.md` made Anthropic/Bedrock system-prompt caching default-ON.

Two live API-documentation fetches (Anthropic's Messages API, AWS Bedrock's Converse API reference) confirmed the exact field names before implementing, per this codebase's own established discipline of verifying against a live source rather than a plausible guess: Anthropic's own formula is `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens` — i.e. Anthropic's native `input_tokens` already excludes cache tokens, and its own concept of "total input" is cache-inclusive. Bedrock's Converse `TokenUsage.totalTokens` is documented as "the total of input tokens and tokens generated by the model" — i.e. `inputTokens+outputTokens` only; cache tokens are **not** already folded in there, despite the field's name suggesting otherwise.

## Design

Token-counting correctness (unconditional, zero config) is deliberately split from cost-pricing (opt-in, config-gated):

**Canonical `adapter.Usage`** (`gateway/internal/adapter/types.go`): `PromptTokens` becomes cache-inclusive by definition, matching each provider's own "total input tokens" semantics — this is the one design choice that makes the fix automatic at both consumer call sites that matter (`dataplane.go`'s `InputTokens: resp.Usage.PromptTokens` and the `TotalTokens`-driven TPM debit), neither of which needed a single line changed. Two new informational fields, `CacheReadTokens`/`CacheCreationTokens int` (JSON `omitempty`), are a documented subset of `PromptTokens` — used only by `costaccounting` to price that slice separately.

**4 producer sites** (Anthropic buffered `anthropic.go` + streaming `stream.go`; Bedrock buffered `bedrock.go` + streaming `stream.go`) add native cache-token fields with the verified wire names and compute `PromptTokens`/`TotalTokens` per each provider's own confirmed formula. Anthropic's cache fields live in the same `message_start.message.usage` event the existing `input_tokens` capture already reads; Bedrock's live in the single `metadata` event already used for all usage.

**`costaccounting`** (a pure leaf, zero allowed dependency edges) gets its own mirrored `Usage` struct (`CacheReadTokens`/`CacheCreationTokens int`). `ModelPrice` gains `CacheReadPerToken`/`CacheCreationPerToken *decimal.Decimal` — pointers, not bare `decimal.Decimal`: `nil` means "not configured for this model," distinguishable from an operator's explicit `decimal.Zero` (e.g. "cache reads are free"), which a bare-value field could never represent. `Calculate` prices `freshPromptTokens := PromptTokens - CacheReadTokens - CacheCreationTokens` at the base rate, then the two cache slices separately via a new `resolveCacheRate(rate *decimal.Decimal, fallback decimal.Decimal) decimal.Decimal` helper.

**The confirmed fallback decision** (raised to the user via `AskUserQuestion`, given the real cost/business tradeoff — computed $ figures visibly change the moment this ships): both `Calculate` call sites pass `price.PromptPerToken` as the fallback. An operator who hasn't configured an explicit cache rate for a model has that model's cache tokens priced as ordinary prompt tokens — closing the undercounting defect (cache tokens previously contributed $0) immediately, for every existing deployment, with zero config change required. The rejected alternative (default to $0, matching today's behavior, until an operator opts in) would have shipped the fix in code while leaving it inert until someone acted.

**Config** (`controlplane.ModelPriceConfig`): the same two `*decimal.Decimal` fields, parsed from new YAML keys `cache_read_per_token`/`cache_creation_per_token` under `price_table.<model>:`, reusing the existing `getDecimal` helper.

## Alternatives considered

**"Raw + `Calculate` sums separately"** (keep `PromptTokens` non-cache-inclusive, let `costaccounting.Calculate` do the summing) — rejected: this would require an explicit three-field sum inserted at both consumer call sites (`InputTokens`, the TPM debit) that currently read `PromptTokens`/`TotalTokens` verbatim — a second and third place the fix could be forgotten, versus the chosen design's zero required changes at either site.

**Widening `budget`/`ratelimit` to accept the raw `Usage` struct instead of a pre-computed dollar/token figure** — unnecessary: both packages are already downstream of `costaccounting.Calculate`'s/`adapter.Usage`'s output by construction; fixing the two upstream types fixes every consumer automatically, without touching either package.

## Verification

New tests per producer site: `TestFromProviderIncludesCacheTokensInPromptAndTotal` (both `anthropic_test.go`/`bedrock_test.go`), `TestStreamDecoder_UsageIncludesCacheTokens`/`TestDecodeMetadataUsageIncludesCacheTokens` (both `stream_test.go`), and a new golden-fixture pair per provider in `regression_test.go` (`response_{anthropic,bedrock}_native_cached.json` → `response_canonical_cached.golden.json`, via the existing `assertJSONEqual` tree-diff). `costaccounting_test.go`: `TestCalculateCacheTokensPricedAtCacheRate`, `TestCalculateUnsetCacheRateFallsBackToPromptRate`, `TestCalculateCacheReadPlusCreationNeverExceedsPromptTokensInvariant`. `config_test.go`: `TestLoadPriceTableParsesCacheTokenRates`. A new full-pipeline dataplane test, `TestCallDeploymentCacheTokensFoldIntoCostAndTPM`, proves both signals against the SAME cache-bearing response: `budget.Tracker.SpentUSD` reflects the cache-inclusive priced cost, and a TPM bucket sized to survive the pre-fix (6-token) debit but not the post-fix (2054-token) debit correctly rejects a second request. Sanity-checked-by-breaking: temporarily reverted Anthropic's `FromProvider` mapping to the pre-fix 2-field shape, confirmed both assertions in that new test failed for the exact predicted reason (`0.00015` instead of `0.03087`; the TPM rejection never fired), restored. ## Addendum (2026-09-11): extended to OpenAI and openaicompat

The original design above scoped itself to Anthropic/Bedrock — the only two providers with an opt-in, write-side `CacheControl` marker at the time. It never surfaced a fourth, independent signal: OpenAI's Chat Completions API has always returned `usage.prompt_tokens_details.cached_tokens` — real, unconditional, zero-opt-in (live-verified directly against OpenAI's own OpenAPI spec, `openapi.yaml`'s `CompletionUsage` schema, not assumed) — reporting the subset of `prompt_tokens` served from OpenAI's own automatic prompt cache. Kelvran's `openai.go` never parsed it, silently pricing every OpenAI cache hit at the full `PromptPerToken` rate, the exact undercounting defect this RFC's own body already closed for Anthropic/Bedrock.

Closed the same way: `openai.Usage` gains `PromptTokensDetails *PromptTokensDetails{CachedTokens int}`; both producer sites (buffered `FromProvider`, streaming `Decode`, which share the same native `Usage` type) populate `adapter.Usage.CacheReadTokens` from it via a new `cacheReadTokensFromUsage` helper. Unlike Anthropic/Bedrock, `PromptTokens` needed no change — OpenAI's own `prompt_tokens` is already cache-inclusive by definition (`cached_tokens` is described as a subset of it), and OpenAI's automatic caching has no cache-CREATION charge concept at all, so `CacheCreationTokens` stays 0 for every OpenAI response, unconditionally.

`openaicompat` (self-hosted OpenAI-dialect runtimes — vLLM/TGI/Ollama) shares the identical wire shape, so the same fields were added there too — but, unlike the OpenAI case, whether a given self-hosted runtime actually populates `prompt_tokens_details.cached_tokens` is runtime-dependent and was **not** independently verified per-runtime the way OpenAI's own spec was. This is disclosed explicitly in `openaicompat.Usage`'s own doc comment: the read is harmless best-effort — any runtime that never sends the field behaves exactly as it did before this change (`CacheReadTokens` stays 0).

Gemini was investigated and left untouched: its real `cachedContentTokenCount` response field only ever populates for the wholly separate, out-of-band `CachedContent` API (`caches.create()` + a later `generate_content` call referencing it) that `gemini.go` never builds or references — unchanged from the original RFC this document already cited for that finding. Whether Gemini's fully-automatic *implicit* caching (the mechanism Kelvran could actually benefit from without building the separate `CachedContent` flow) also populates that field is genuinely unclear from Google's own docs — named here as an open question, not a confirmed gap, and not built.

New tests: `TestFromProviderExtractsRealCachedTokens`/`TestFromProviderMissingPromptTokensDetailsDefaultsToZeroCacheRead` (both `openai_test.go`/`openaicompat_test.go`), `TestDecodeFinalUsageChunkExtractsRealCachedTokens` (both `stream_test.go`). Sanity-checked-by-breaking: temporarily zeroed the `CacheReadTokens` field in `openai.go`'s `FromProvider`, confirmed `TestFromProviderExtractsRealCachedTokens` failed for the exact predicted reason (`0` instead of `896`), restored. Full gateway verification suite clean (build/vet/test-race/lint/arch-lint/gofmt/mod-tidy) except the same two pre-existing, already-documented rootless-Docker failures.

## Addendum (2026-09-11): Gemini closed; openaicompat disclosure tightened; Fable 5.1/Mythos 5.1 pricing tier

Round-4 upgrade research (`docs/upgrade-research/cache-provider-native-caching-audit-round4-2026-09-11.md`) resolved the open question the previous addendum left about Gemini, and surfaced two further real findings, closed as Phase 2 of the round-4 plan.

**Gemini closed.** Finding 1 confirms Gemini's *implicit* (automatic, on-by-default) caching genuinely populates `usageMetadata.cachedContentTokenCount` on a real cache hit — a real field, distinct from the out-of-band `CachedContent` API the original RFC correctly found `gemini.go` doesn't build. Added `UsageMetadata.CachedContentTokenCount int` (`gemini.go`) and wired it into `adapter.Usage.CacheReadTokens` at both producer sites (buffered `FromProvider`, streaming `usageFromNative` in `stream.go`, which share the same native type) — no `PromptTokens` change needed, since Gemini's own `promptTokenCount` is already cache-inclusive by definition, matching OpenAI's shape. `CacheCreationTokens` stays 0 unconditionally (implicit caching has no creation-charge concept). New tests: `TestFromProviderExtractsRealCachedTokens`/`TestFromProviderMissingCachedContentTokenCountDefaultsToZeroCacheRead` (`gemini_test.go`), `TestDecodeFinalUsageChunkExtractsRealCachedTokens` (`stream_test.go`). Sanity-checked-by-breaking: temporarily zeroed the extraction in `FromProvider`, confirmed the test failed for the exact predicted reason (`0` instead of `896`), restored.

**openaicompat's runtime-support disclosure tightened.** Finding 2's source-level survey of vLLM/Ollama/llama.cpp/TGI found the real support split is uneven, not a uniform "runtime-dependent, unverified" caveat: vLLM, Ollama, and llama.cpp genuinely wire a real prefix/KV-cache-hit count into `prompt_tokens_details.cached_tokens` (vLLM gated behind a default-off `enable_prompt_tokens_details` server flag; Ollama only via its legacy llama.cpp-backed/experimental-MLX runners, not its newer pure-Go engine); TGI has zero cache-token support in its response types at all. `openaicompat.go`'s `Usage` doc comment rewritten to name this explicitly, still disclosing (unlike OpenAI's own live-verified spec) that this remains an assertion about upstream source code, not independently verified against a live runtime by this codebase. No functional code change — the field/extraction logic already shipped in the original addendum above; this is a documentation-accuracy fix only.

**Anthropic Fable 5.1/Mythos 5.1 cache-pricing tier documented.** Finding 5: as of 2026-09-01, Anthropic prices cache reads on Claude Fable 5.1 and Claude Mythos 5.1 specifically at 0.025x base input cost, not the standard 0.1x multiplier every other model uses (cache-write pricing unchanged) — confirmed against two independent, current, official Anthropic documentation pages. Confirmed via Explore that `price_table` parsing (`controlplane/config.go`) is fully generic over YAML keys — this needed **zero Go code changes**, only a new `config.example.yaml` entry for `claude-fable-5-1` demonstrating the correct 0.025x ratio (illustrative base rates, explicitly disclosed as placeholders — only the ratio itself is a verified claim). New test `TestLoadExampleConfig` extension asserts `CacheReadPerToken` is exactly `PromptPerToken * 0.025`. Sanity-checked-by-breaking: temporarily set the example's `cache_read_per_token` to a value that isn't 0.025x, confirmed the extended assertion failed for the exact predicted reason, restored.

Full gateway suite (`go build ./... && go vet ./... && gofmt -l . && go test ./... -race && golangci-lint run ./... && go run github.com/fe3dback/go-arch-lint@v1.18.0 check && go mod tidy`) clean except the two pre-existing, already-documented rootless-Docker failures.
