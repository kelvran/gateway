# RFC: Judge-accuracy metric — Cohen's kappa + confusion matrix against the judge_accuracy corpus

## Status

Accepted, implemented 2026-09-09.

## Context

`docs/upgrade-research/evals-next-upgrade-2026-09-09.md`'s top-ranked finding: `evals/stats.py`/`report_cmd` compute only a Wilson-interval pass rate from raw pass/fail counts — no chance-corrected judge-accuracy metric exists anywhere, so `evals report` can't validate the LLM-judge's own quality against the existing 24-case `regression_corpus_judge_accuracy.json` corpus, only report a raw pass rate. Raw exact-match agreement systematically overstates chance-corrected accuracy — a real 2026 study found a ~38.6 percentage-point mean gap across 21 judges on MT-Bench — so a naive "percent correct on the 24 cases" number would be badly inflated. This is also exactly what the `.github/workflows/evals-judge-nightly.yml` comment already names as a gap: "a meaningful gate needs a real accuracy-vs-designed-label metric, which `evals report` has no concept of today."

The judge_accuracy corpus's 24 cases had no structured ground-truth field before this change — only an `id`-prefix convention (`judgeacc-correct-*`/`judgeacc-incorrect-*`/`judgeacc-boundary-*`) and free-text `corpus_note` prose recording each case's real observed verdict.

## Design

**Ground truth**: a new structured `task_spec.expected_verdict: true | false | null` field, added to all 24 cases in `regression_corpus_judge_accuracy.json`, hand-derived from each case's own existing `corpus_note` prose. `true`/`false` for the 23 cases whose designed intent or live-verified unanimous behavior is unambiguous (all 8 "correct" cases including the flaky `judgeacc-correct-units-2`, whose own note says "Designed as obviously-correct" — the design intent is a stable fact independent of one run's judge variance; all 8 "incorrect" cases; 7 of the 8 "boundary" cases, each explicitly "reclassified after live verification... turned out unanimous"). `null` for exactly one case, `judgeacc-boundary-numeric-3` — the one boundary case that was never reclassified to a resolved value; its own corpus_note documents genuine, real cross-run disagreement (Run 1: fail-closed tie; Run 2: unanimous PASS) with no single stable answer, so forcing a fake binary label would misrepresent it. This avoids fragile `id`-prefix string-parsing in `cli.py` and matches this codebase's established preference for structured data over prose-parsing.

**`evals/stats.py`** gains `ConfusionMatrix` (a `NamedTuple`) and two pure functions, `confusion_matrix(judge_verdicts, human_verdicts) -> ConfusionMatrix` and `cohens_kappa(judge_verdicts, human_verdicts) -> float`, both taking plain `list[bool]` — never a `Score`/`EvalCase` — since `.importlinter`'s layers contract places `evals.models` and `evals.stats` in the same bottom layer, neither may import the other. `cohens_kappa` calls `confusion_matrix` internally (one pairwise pass, not two) and raises `ValueError` when `p_expected == 1.0` (both raters have zero marginal variance in the identical direction — a literal 0/0, not silently `NaN` or a fake `1.0`).

**`evals/cli.py`** gains `_load_expected_verdicts(fixture_path) -> dict[tuple[str, int], bool]` (next to `_load_cases`, reading the same JSON-array fixture shape, mirroring `promote_cmd`'s own `cases_by_key = {(c.id, c.revision): c for c in _load_cases(...)}` precedent exactly) and a new opt-in `--judge-accuracy PATH` option on `report_cmd`, only meaningful together with `--scores`. Inside the existing per-`scorer_type` loop, matched `Score`s (joined by `(eval_case_id, eval_case_revision)`) build parallel `judge_verdicts`/`human_verdicts` lists, then print Cohen's kappa plus the full confusion matrix — **in addition to**, never in place of, the existing pass-rate/CI line, and never affecting `--fail-under`/`--category-fail-under` gate semantics. A case whose `expected_verdict` is `null` is silently excluded from the join (a genuinely unresolved ground truth, not an error); a case whose `task_spec` has no `expected_verdict` key at all is a hard `click.ClickException` (a fixture-authoring bug, not something to silently skip); zero matches across the whole `--scores` file is also a hard error, mirroring `--category-fail-under`'s own "zero matches is a hard error, not a silent no-op" convention.

## Alternatives considered

**Automatic computation whenever a `category:judge`-tagged Score is present, no new flag** — rejected: this codebase's consistent convention is that a new capability is a new, explicit, opt-in flag, never something that silently changes existing report output based on tag presence alone.

**Deriving ground truth from the `id` prefix (`judgeacc-correct-*` → `true`, etc.) instead of a structured field** — rejected: fragile string-parsing tied to a naming convention that was never meant to be machine-parsed, and doesn't handle the one genuinely unresolved case (`judgeacc-boundary-numeric-3`) any better than a structured `null` does.
