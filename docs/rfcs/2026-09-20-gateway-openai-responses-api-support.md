# RFC: OpenAI Responses API support — OpenAI-only passthrough, design only, no code

- **Status**: Design-only, explicitly deferred pending its own named trigger (see Unresolved Questions). Mirrors the exact "designed in full, deferred" precedent already established for the Redis-backed cache (`docs/rfcs/2026-09-11-gateway-redis-backed-cache-design.md`) and the MCP/A2A outbound-credential design (`docs/rfcs/2026-09-11-gateway-mcp-outbound-credential-design.md`): scope the "how" now, without committing to the "when."
- **Date**: 2026-09-20
- **Author(s)**: Session agent (Claude Code), per `docs/upgrade-research/openai-api-surface-gap-tier1-2026-09-20.md` Finding 3/6, whose own verdict is "escalating toward `build_now`-eligible for a scoped RFC specifically."

## Summary

Add an OpenAI-only, largely-passthrough `/v1/responses` route so clients already using OpenAI's `client.responses.create()` SDK surface (a growing population per OpenAI's own steer toward Responses) get Kelvran's centralized auth/budget/rate-limit/guardrail enforcement without Kelvran attempting to normalize Responses' polymorphic output-item schema across every other provider. Follows this codebase's own real, shipped precedent for exactly this shape of decision — `adapter.EmbeddingAdapter` (`internal/adapter/types.go`): a deliberately separate interface, an additive canonical type, its own pipeline function, and selective (not blanket) reuse of existing pipeline primitives.

## Motivation

`docs/upgrade-research/openai-api-surface-gap-tier1-2026-09-20.md` (Finding 3) found a real, dated forward-compatibility pressure point, not just OpenAI's own stated preference: OpenAI's current migration guide states "Chat Completions remains supported, so you can migrate one user flow at a time," but also that starting with GPT-5.4, "Chat Completions does not support tool calling with `reasoning_effort` values other than `none`" — a real, model-version-gated functionality gap that only widens as OpenAI ships newer reasoning models. Any Kelvran customer wanting current-generation tool-calling-plus-reasoning behavior from OpenAI specifically will, at some point, need a request shape `/v1/chat/completions` cannot express at all. Concrete claims backing OpenAI's own steer (same report, Finding 3): a 3% SWE-bench improvement, 40-80% better cache-hit rates, and a fully stateless (`store: false`) mode compatible with Zero Data Retention. Today, `cmd/gateway/main.go` registers exactly `/v1/chat/completions`, `/v1/embeddings`, and `/healthz` as data-plane routes (confirmed by direct code inspection, `openai-api-surface-gap-tier1-2026-09-20.md` Finding 1) — no `/v1/responses` route or Responses-shaped adapter exists anywhere in this codebase.

## Detailed Design

**Scope decision, made explicit rather than defaulted (per the research's own Open Question 2): OpenAI-only passthrough, not cross-provider normalization.** Responses' output is a polymorphic list of item types (message, function_call, tool_call, computer_use action, MCP tool call/approval/list-tools result, code interpreter, image generation) — categorically larger than `EmbeddingResponse.Data`'s flat float64 array. Mirroring the Batch report's own "passthrough-first, cheapest provider first" precedent (`docs/upgrade-research/gateway-batch-api-2026-09-13.md`), this RFC scopes Kelvran's Responses support to the OpenAI provider only, deferring any attempt to translate Anthropic/Bedrock/Gemini calls into the same wire shape as a separate, later RFC if real demand ever appears.

**New canonical types, additive, never a retrofit of `ChatRequest`/`ChatResponse`** (`internal/adapter/types.go`), matching `EmbeddingRequest`/`EmbeddingResponse`'s own established convention:
- `ResponseRequest` — mirrors OpenAI's `input` (either a bare string or an ordered array of typed items: message, function_call_output, etc.), `model`, `store` (bool, default true upstream — Kelvran should default it to `false` in `ToProvider` unless the caller sets it explicitly, since `store: true` implies OpenAI-side state Kelvran has no way to track, invalidate, or account for in `budget`/`costaccounting`), `previous_response_id` (opaque passthrough string, present only when `store` was true on a prior call — see Drawbacks), and `tools`/`tool_choice` (reuse the existing `adapter.Tool`/`ToolChoice` canonical shapes where the schemas actually line up; Responses-specific hosted tools like `web_search`/`code_interpreter` pass through as opaque `any` since Kelvran cannot execute or interpret them).
- `ResponseResult` — mirrors OpenAI's `output` array. Each item's concrete Go type is a **discriminated union by the wire `type` field**, decoded via a custom `UnmarshalJSON` on a wrapper slice type (the same technique `EmbeddingRequest.UnmarshalJSON` already uses for its own dual "string | string[]" wire contract, just applied to a longer list of variants instead of two). A `message`-typed item's `content` decodes into the existing canonical `Message`/`ReasoningBlock` shapes where the fields correspond 1:1 (see below); every other item type (`function_call`, `tool_call`, `computer_use_call`, `mcp_call`, `code_interpreter_call`, `image_generation_call`) is captured as its own thin typed struct holding exactly the fields Kelvran needs to pass the item back to the client byte-for-byte (an id, a status, and the item's own opaque payload) — Kelvran does not attempt semantic understanding of tool-call arguments beyond what it already does for Chat Completions' own `ToolCalls`.
- `ResponseAdapter` — a **third, separate interface** alongside `Adapter` and `EmbeddingAdapter`, not a method added to either: `ToResponseProvider(ResponseRequest) (any, error)` / `FromResponseProvider(any) (ResponseResult, error)`. Only `internal/adapter/openai` implements it in this scope; every other provider package is untouched, exactly matching `EmbeddingAdapter`'s own "Anthropic has no native embeddings model, so it doesn't implement that interface either" precedent — here, no other provider has a Responses API at all, so the "why a separate interface" rationale is even stronger than it was for embeddings.

**Reasoning-content reuse — the one genuine cost mitigation the research found** (Finding 3, medium confidence): Responses' stateless (`store: false`) mode requires the caller to store and replay opaque, provider-issued encrypted reasoning content verbatim on the next turn — mechanically the same round-tripping contract `adapter.Message.ReasoningBlock`'s `Redacted`/`Data`/`Signature` fields already implement today for Anthropic/Bedrock (`docs/rfcs/2026-09-12-gateway-reasoning-content-canonical-schema.md`). `ResponseAdapter.FromResponseProvider` should map an OpenAI encrypted-reasoning output item onto a `ReasoningBlock{Redacted: true, Data: <ciphertext>, Signature: <sig>}` exactly as the Anthropic/Bedrock adapters already do, rather than inventing a second, parallel opaque-blob representation — this is real, already-hardened infrastructure for this one specific slice, not the whole surface.

**New pipeline function, not a `HandleChatCompletion` retrofit** — `Pipeline.HandleResponse(ctx, authorizationHeader, req adapter.ResponseRequest) (adapter.ResponseResult, error)`, its own function in `internal/gateway/dataplane`, matching `HandleEmbeddings`'s exact shape and scoping decision on what to reuse vs. skip:
- **Reused as-is**: auth (`p.verifier.Load().Verify`), `isModelAllowed`, rate-limiting (`p.limiter.AllowForModel`, RPM only — no TPM pre-estimate, same reasoning `HandleEmbeddings` already documents: no character-length-proxy exists for Responses' polymorphic `input` either), budget reserve/reconcile, guardrail `Check` against every plain-text input item, plain (non-sticky) `p.nextDeployment`.
- **Explicitly NOT reused, disclosed rather than silently dropped** (mirroring `HandleEmbeddings`'s own explicit non-reuse list): cache (a `store: true` conversation's `previous_response_id` chain has no cache key Kelvran's existing `cache.Key`/`NormalizedKey` shape can express — the "current turn" alone is not the full conversational context OpenAI holds server-side), idempotency, per-identity concurrency cap, fallback chains (single-provider passthrough has nowhere to fall back to in this scope), and OTel spans (deferred alongside the others; a follow-up RFC territory once this ships, not a blocker to shipping the route itself).
- **`costaccounting` requires zero changes**, mirroring `HandleEmbeddings`'s own "zero changes needed" outcome: a `ResponseResult`'s token usage maps onto the existing `Usage{PromptTokens, CompletionTokens, TotalTokens}` shape with no new fields, priced at the model's ordinary per-token rate.

**New route**: `POST /v1/responses` in `cmd/gateway/main.go`, a new `responsesHandler(p *dataplane.Pipeline) http.HandlerFunc` mirroring `embeddingsHandler`'s exact request-size-limit/decode/error-response shape.

## Drawbacks

- **`previous_response_id` is an accepted, disclosed limitation, not a solved problem.** Kelvran passes it through to OpenAI opaquely (it's just a string in `ResponseRequest`) but has no way to enforce budget/rate-limit/guardrail checks against the *prior* turns a `previous_response_id` chain implies — those checks only ever see the current call's own input. A determined caller could front-load guardrail-triggering content into an OpenAI-stored `store: true` conversation and later reference it via `previous_response_id` with an innocuous-looking follow-up input, bypassing Kelvran's guardrail scan for that content entirely. This is a real, narrower version of the same "Kelvran's checks wrap the outer request/response, gaining no additional guarantee over an unproxied direct call for whatever happens inside OpenAI's own black box" limitation the research (Finding 3) already names for Responses' server-side agentic tool execution generally.
- Schema cost is real and non-trivial — a discriminated-union output-item decoder is closer in shape and maintenance burden to a second, smaller canonical chat schema than to Embeddings' one-line array-of-floats addition.
- OpenAI-only scope means a customer on Anthropic/Bedrock/Gemini gets no equivalent surface; if cross-provider Responses-shaped normalization is ever wanted, it is explicitly a separate, later RFC (Unresolved Questions), not a natural follow-on this design already sets up cleanly — none of the other three providers have anything resembling Responses' shape to normalize from.
- No cache/idempotency/fallback coverage (see Detailed Design) is a real capability gap versus `/v1/chat/completions`, disclosed rather than silently narrowed.

## Alternatives Considered

**Do nothing (status quo, `/v1/chat/completions` only)**: rejected per the research's own escalated verdict — the GPT-5.4 tool-calling-with-`reasoning_effort` gap is a real, dated, model-version-gated functionality wall, not a hypothetical future concern, and it only widens as OpenAI ships newer reasoning models.

**Cross-provider Responses-shaped normalization on day one**: rejected as the more expensive entry point per the research's own recommendation (Finding 3, Open Question 2) — no other provider has a comparable API surface to normalize from, so "normalizing" would mean inventing a translation layer with no real upstream counterpart on the other three providers, pure speculative scope with zero confirmed demand signal for it specifically.

**Extend the existing `Adapter` interface with Responses methods instead of a third interface**: rejected for the same reason `EmbeddingAdapter` was already kept separate — every provider package not implementing Responses (Anthropic, Bedrock, Gemini, OpenAI-compat) would need a dummy/panicking implementation of an operation it fundamentally cannot support.

## Unresolved Questions

1. **The named trigger this RFC is deferred pending**: a confirmed instance of a Kelvran customer's OpenAI usage depending on GPT-5.4+ tool-calling-with-`reasoning_effort` in a way `/v1/chat/completions` literally cannot serve (the research's own Open Question 1) — check directly against Kelvran's own request logs/model-usage telemetry once real production traffic exists, rather than building this speculatively.
2. Whether cross-provider Responses-shaped normalization is ever worth a follow-up RFC once real demand exists — this RFC deliberately does not design it.
3. Whether `previous_response_id`'s guardrail-bypass drawback (above) is severe enough to require Kelvran to reject any request carrying that field until a real mitigation exists, versus accepting it as a disclosed, documented limitation of OpenAI-only stateful passthrough — left for whoever picks up implementation to weigh against the research's own finding that no confirmed customer demand signal exists yet either way.
4. Whether OpenAI's separately-flagged Prompts-object deprecation timeline (`openai-api-surface-gap-tier1-2026-09-20.md` Finding 2) has any bearing on a Responses adapter that might otherwise want to reference stored Prompt objects — not investigated in this pass.
