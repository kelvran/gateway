# RFC: Retry-storm-specific DoS mitigation

## Status

Accepted, implemented 2026-09-07.

## Context

`THREAT_MODEL.md`'s Gateway Denial of Service row, "Retry storms in agentic traffic — many agents retrying on a fixed interval synchronize into a thundering herd," was corrected 2026-09-04 to say plainly what was actually true: zero circuit-breaker, backoff-jitter, retry-budget, or concurrency-cap logic existed anywhere in `gateway/internal/`. The real, existing backstops — `internal/ratelimit`'s per-key RPM/TPM token buckets and `internal/budget`'s per-key USD cap — bound how much damage a retry storm from any single virtual key can do, but neither is retry-storm-*specific*: neither detects, dampens, nor even signals a synchronized retry pattern, and neither tells a well-behaved client anything about how long to wait before trying again. This RFC is that still-undesigned future work, with no prior trigger condition attached — this pass grounds the design in what's actually in the code today before building anything.

**What the code actually does today, verified directly, not assumed:**

- `gateway/internal/gateway/dataplane/fallback.go`'s `attemptFallbackChain` walks a fallback chain's `targets` in a plain `for` loop with **zero delay between hops** — the moment one hop's `call` returns an error, the very next hop is attempted, as fast as the local CPU and network stack allow. There is no backoff of any kind between attempts, chain-internal or client-facing, anywhere in this codebase before this RFC.
- `attemptFallbackChain` resolves each configured chain target via `p.deploymentsByName[name]` **directly** — it does not consult `p.router.IsHealthy(name)` at all. This means the already-shipped active health-probing mechanism (`docs/rfcs/2026-09-07-gateway-active-health-probing.md`) protects `router.Select`'s primary-pick and the pre-existing single-fallback path, but a deployment named explicitly in a `fallback_chains:` list is attempted even if active probing has already marked it unhealthy from real, repeated, cross-request probe failures. This is a real composition gap this RFC closes, not a hypothetical.
- `gateway/internal/ratelimit/limiter.go`'s `KeyLimiter`/`TokenBucket` bound request *rate* (tokens per unit time) and, per the TPM RFC, token *usage* rate — neither bounds how many of a key's requests may be simultaneously outstanding. A key comfortably under its RPM cap can still open an unbounded number of long-running concurrent requests, each one adding real load to a deployment that may already be struggling — exactly the shape a retry storm from many parallel agent workers takes, and exactly what neither existing mechanism catches.
- `gateway/cmd/gateway/main.go`'s `writeErrorResponse` maps every rejection/failure to an HTTP status via `http.Error(w, err.Error(), status)`, but sets **no `Retry-After` header anywhere** — a well-behaved client (including an OpenAI-SDK-compatible one, which does respect `Retry-After` on 429/503) currently has no gateway-provided signal for how long to back off, only its own client-side default.
- `gateway/internal/identity`'s `VirtualKey` is the existing, established tenant-scoping identity every other per-key control (rate limit, TPM, budget, cache-key tenant dimension) is threaded through by ID (`vk.ID`), never by a second identity concept. `telemetry.AgentRunIDFromContext` extracts an `agent_run_id` from W3C Baggage — but, confirmed by reading `ExtractContext`/`AgentRunIDFromContext` directly, this value is **entirely client-supplied and unverified**: any caller can set an arbitrary `agent_run_id` on every request. This matters for design decision (b) below.

## Design

This RFC ships three genuinely new mechanisms, each scoped as narrowly as the motivating gap requires, and explicitly declines to build a fourth (the traffic-derived statistical circuit breaker) that stays out of scope per the user's own instruction.

### (a) Exponential backoff with jitter + `Retry-After`, on the client-facing rejection path

**New `internal/ratelimit/backoff.go`:**

```go
func EqualJitterBackoff(attempt int, base, cap time.Duration, frac float64) time.Duration
```

A pure function implementing AWS's "Exponential Backoff and Jitter" **equal-jitter** variant (not full-jitter): `half := min(cap, base*2^(attempt-1)) / 2; delay := half + frac*half`. Full jitter (`random(0, capped)`) was considered and rejected for this codebase specifically because it has no deterministic floor — a returned value of near-zero is always possible for any attempt count, which makes "prove backoff actually spaces things out" impossible to assert against without a large-sample statistical test. Equal jitter guarantees `delay >= half of the capped exponential value` while still desynchronizing a thundering herd substantially (the other half is fully randomized) — enough floor to write a real, deterministic, real-elapsed-time test against (see Verification), while still solving the actual problem (many clients that would otherwise retry in lockstep on a fixed interval now each wait a materially different amount).

`frac` is caller-supplied (not read from a global `math/rand` source internally) specifically so both call sites below can inject their own randomness source, and so unit tests can pin `frac` to its extremes (0.0 and near-1.0) to assert the exact floor/ceiling bounds.

**`RetryBackoff`** (same file): a per-virtual-key consecutive-rejection streak tracker —

```go
type RetryBackoff struct{ /* mu sync.Mutex; streaks map[string]int; rand func() float64 */ }
func NewRetryBackoff() *RetryBackoff
func (b *RetryBackoff) Record(keyID string) time.Duration // increments streak, returns EqualJitterBackoff(streak, ...)
func (b *RetryBackoff) Reset(keyID string)                // called on every genuine success
```

Base 500ms, cap 30s, streak capped at 10 (2^10 already exceeds the cap many times over). This mirrors two precedents already established in this codebase rather than inventing a third shape: the map-plus-mutex, per-key-state shape of `ratelimit.KeyLimiter` itself, and the "N consecutive" streak-counter idiom `router/health.go` already uses for health-probing (a genuinely different mechanism, deliberately reusing only the *idiom*, not the state).

**New `gateway/internal/gateway/dataplane/retry_after.go`:**

```go
type RetryAfterError struct { /* wraps the original err; RetryAfter time.Duration */ }
func (p *Pipeline) attachRetryAfter(vk *identity.VirtualKey, err error) error
```

`attachRetryAfter` is called from inside `HandleChatCompletion`'s and `HandleChatCompletionStream`'s existing top-level deferred closure (the one that already calls `finalize`), reassigning the named-return `err` before `finalize` runs — so `finalize`'s own `errors.Is`/`errors.As`-based classification (`outcomeFor`, the structured log line) sees the exact same wrapped error the client ultimately receives, never a second, divergent view of what happened.

**Scope of eligibility is deliberately narrow, decided by reusing `outcomeFor`'s existing classification rather than inventing a second error taxonomy:**

- **Eligible** (streak recorded, `Retry-After` attached): `ErrRateLimited`, the new `ErrConcurrencyLimitExceeded` (design (b) below — folded into the same `OUTCOME_RATE_LIMITED` bucket `outcomeFor` already has, deliberately, to avoid a protobuf schema change to `api/gatewayevents/v1`'s `Outcome` enum for a v1 pass — the same "generic bucket" precedent `fallback.go`'s `FallbackClassGeneric` already established for folding rate limits in with other conditions), and the final upstream-call-failed error (`OUTCOME_UPSTREAM_ERROR` — this is exactly the "circuit breaker exhausted, or fallback chain exhausted naturally" case from design (c)).
- **Deliberately NOT eligible, and why:** `ErrBudgetExceeded` is excluded on purpose. A budget cap's real recovery time is either "never" (a lifetime cap) or "whenever `BudgetResetInterval` next elapses," which `internal/budget.Tracker`'s current API does not expose a "time remaining" query for — attaching a short exponential-backoff `Retry-After` here would be actively **misleading**, not merely unhelpful, telling a client to retry in seconds when the real answer might be 30 days or never. Computing an honest value needs `budget.Tracker` to expose reset-time bookkeeping it doesn't today; named explicitly as future work, not silently solved. `ErrModelNotAllowed`, `ErrGuardrailBlocked`, and auth failures are also excluded: none of these are capacity/availability signals a client backing off would ever resolve by waiting — they're request-shape/policy decisions where an identical retry, no matter how long the client waits, fails identically.

`main.go`'s `writeErrorResponse` gains one new step, executed for every error before its existing status-mapping switch statement returns control to `http.Error`: `errors.As(err, &retryErr)` and, if matched, `w.Header().Set("Retry-After", strconv.Itoa(ceilSeconds))`, set before `http.Error` is called (Go's `net/http` requires headers to be set before `WriteHeader`, which `http.Error` calls internally) — this is the concrete "given this codebase's real HTTP response-writing conventions" answer: a plain integer-seconds `Retry-After` header (per RFC 9110 §10.2.3's two allowed forms — a date, or a delay-seconds integer; every real client library, including the OpenAI SDK's own retry logic, expects the integer form), added to the exact same `http.Error` call site every other rejection status already goes through, no new response-writing path.

### (b) Per-virtual-key concurrency cap

**New `internal/ratelimit/concurrency.go`:**

```go
type ConcurrencyConfig struct{ ID string; MaxInFlight int } // <= 0 means unlimited
type ConcurrencyLimiter struct{ /* mu sync.Mutex; limits, inFlight map[string]int */ }
func NewConcurrencyLimiter(keys []ConcurrencyConfig) *ConcurrencyLimiter
func (l *ConcurrencyLimiter) Acquire(keyID string) bool // false = already at cap, no slot reserved
func (l *ConcurrencyLimiter) Release(keyID string)
func (l *ConcurrencyLimiter) Register(cfg ConcurrencyConfig) // live admin-mutation precedent, mirrors KeyLimiter.Register
func (l *ConcurrencyLimiter) InFlight(keyID string) int // test/observability-only read
```

**Location: `internal/ratelimit`, a new file, not a new package.** The task's own candidate framing offered both; this RFC picks the existing package because (1) it is the natural sibling of `KeyLimiter`/`TokenBucket` — same "bound a per-key resource" purpose, same map-plus-mutex shape, same optional-live-`Register` precedent from the admin API RFC; (2) `dataplane` already legitimately depends on `ratelimit` (`Config.Limiter *ratelimit.KeyLimiter`), so this introduces **zero new `go-arch-lint` component and zero new dependency-direction rule** — a brand-new sibling package would need its own component declaration for no real decoupling benefit, since nothing outside `dataplane` needs to consume concurrency-limiting independently of rate-limiting; (3) it avoids the proliferation of single-type packages this codebase has otherwise avoided (`ratelimit` already hosts two genuinely different per-key mechanisms — RPM/TPM token buckets and now in-flight counting — under one roof, exactly like it already hosts both the RPM and TPM dimensions together).

**Scoped to the virtual-key identity, not `agent_run_id` — a deliberate, security-motivated choice, not an oversight.** The task explicitly allows "per virtual-key identity and/or per agent_run_id." This RFC implements *only* the virtual-key dimension, for a concrete reason found by reading the code, not assumed: `telemetry.AgentRunIDFromContext` extracts `agent_run_id` from client-supplied W3C Baggage with **no verification of any kind** — any caller can set an arbitrary, different `agent_run_id` on every single request. Enforcing a concurrency cap keyed on that value would let exactly the adversary this RFC is trying to stop trivially bypass it by rotating `agent_run_id` per request, which would make the control worse than useless (a false sense of protection). The virtual-key ID, by contrast, is authenticated — verified by `identity.Verifier.Verify` against a hashed secret before any per-key state is ever touched — which is why every other per-key control in this codebase (RPM, TPM, budget) is already scoped this same way. A genuine per-`agent_run_id` sub-cap is named explicit future work, contingent on `agent_run_id` first being tied to some verified concept (e.g. signed, or derived server-side rather than client-asserted) — not solved here, and not silently assumed solved.

**Wired at `dataplane.checkRateLimit`'s call site**, per the task's own suggestion, in `HandleChatCompletion` and, identically, `HandleChatCompletionStream` (both currently duplicate the auth/rate-limit/budget check sequence; a concurrency cap that only covered the buffered path would be trivially bypassed by setting `"stream": true`, so both get it): immediately after the existing rate-limit check succeeds, before the budget check —

```go
if !p.checkConcurrency(vk.ID) {
    err = &RetryAfterError{...ErrConcurrencyLimitExceeded...}
    return
}
defer p.concurrency.Release(vk.ID)
```

`dataplane.Config` gains an **optional** `Concurrency *ratelimit.ConcurrencyLimiter` field (nil-safe throughout, exactly like `Config.UpstreamStream`'s existing optionality) rather than a new required dependency — this was a deliberate choice to keep the diff's blast radius small: making it required would force every existing `dataplane.NewPipeline`/bare-`Pipeline{}` test construction across this package's already-large test suite to be updated for a control most of those tests aren't exercising, for no correctness benefit (a nil `Concurrency` correctly behaves as "concurrency limiting not configured," the same "zero/nil means disabled" convention this codebase already applies to Redis rate-limiting, budget persistence, and health-probing).

**A real, named gap:** `Pipeline.UpsertVirtualKey` (the live admin-API virtual-key mutation path) is **not** updated to also register a concurrency cap in this pass — a virtual key added or updated live via `POST /admin/virtual_keys/{name}` gets no concurrency limit (unlimited) until the next process restart re-reads the static config. This mirrors the same "static-config-only in v1" scope-narrowing this codebase's other per-key controls have each started with, but is called out here explicitly rather than left to be discovered later.

### (c) Circuit breaker, precisely defined: per-request, chain-internal, composing with (not duplicating) active health-probing

**What this RFC's "circuit breaker" means, stated exactly, because the term is overloaded in this codebase's own history:** stopping further attempts down an already-failing fallback chain **for the current request only** — a purely local, per-call decision inside `attemptFallbackChain`, with no state that survives past the one request it was computed for. This is explicitly **not**, and does not reintroduce, the traffic-derived statistical circuit breaker (Envoy-style outlier detection, LiteLLM-style `allowed_fails` cooldown) that `docs/rfcs/2026-09-07-gateway-active-health-probing.md` and `gateway/ARCHITECTURE.md` both correctly keep deferred — that mechanism needs a production-traffic volume floor Kelvran does not have yet, and this RFC does not manufacture one. `router.IsHealthy`'s cross-request active-probing state is the traffic-*independent* mechanism that already exists for exactly that "is this deployment known-bad across many requests over time" question; this RFC's breaker answers a narrower, different question — "has *this one request's own* chain-walk already failed enough times in a row that continuing is more likely to hammer additional struggling deployments than to succeed."

Three changes to `attemptFallbackChain`, all additive to its existing "walk targets in order, stop at first success" behavior:

1. **Compose with health-probing, close the real gap found above.** Before attempting a target, check `p.router != nil && !p.router.IsHealthy(name)` — a target already known-unhealthy from real, cross-request probe failures is skipped (never attempted, never charged a backoff delay) rather than being reached only through this chain's own bypass of `router.Select`. The nil-guard preserves this codebase's `internal/router`-optionality convention and, concretely, keeps every pre-existing `fallback_test.go` unit test (which constructs a bare `Pipeline{deploymentsByName: ...}` with no `router` at all) passing unmodified.
2. **A small, fixed per-request threshold — not a config knob.** `maxConsecutiveChainFailures = 3`: once this many *real* (non-skipped) attempts within this one chain-walk have failed consecutively, the walk stops immediately, even if configured targets remain. The number `3` deliberately reuses `router/health.go`'s own `defaultUnhealthyThreshold` value for consistency of "how conservative is 'enough evidence'" across this codebase, but is a **separate, hardcoded, per-request-scoped counter** — it shares no state, and no config surface, with `router.HealthConfig`. Every fallback chain in this codebase's existing test suite tops out at exactly 3 configured hops, so this threshold changes no existing test's observed behavior (verified directly, not assumed — see Verification); it only bounds a hypothetical operator-configured chain longer than that from exhausting every remaining hop once 3 have already failed in a row.
3. **Inter-hop backoff with jitter**, using the same `ratelimit.EqualJitterBackoff` from (a): before the *second* and later real attempts in a chain-walk (never before the first — the common single-fallback case, by far this codebase's most-exercised path, keeps its exact pre-existing latency), sleep `EqualJitterBackoff(hopIndex, 25ms, 400ms, frac)`, honoring context cancellation via a `select` on `ctx.Done()` so a canceled request never blocks on this delay. Deliberately much smaller than (a)'s client-facing backoff (milliseconds to a few hundred milliseconds, not seconds) — this delay happens *inside* one client request's own response-time budget, so it must stay small enough that a chain walk still completes in a reasonable time while still being genuine, measurable spacing rather than an instant re-hammer of the next struggling target.

`attemptFallbackChain`'s signature gains a leading `ctx context.Context` parameter (used only for the backoff sleep's cancellation), updated at both call sites (`dataplane.go`'s `runMissPath`, `streaming.go`'s `streamDeploymentWithFallback` — both already have a `ctx` in scope) and in every existing `fallback_test.go` unit test.

## Alternatives considered

**Full-jitter (`random(0, capped)`) instead of equal-jitter for the backoff formula.** AWS's own "Exponential Backoff and Jitter" article recommends full jitter as the *most effective* desynchronizer of the three variants it names. Rejected specifically for this codebase's testing discipline: a returned delay of near-zero is always a legitimate outcome under full jitter for any attempt count, making a real-elapsed-time test that proves "backoff genuinely grows and spaces things out" fundamentally unable to assert a floor without a large-sample statistical test this project's existing test conventions (fast, deterministic, `go test -race`-friendly) don't otherwise need elsewhere. Equal jitter keeps most of full jitter's desynchronizing benefit (half the delay is still fully randomized) while guaranteeing a deterministic floor to test against.

**Keying the concurrency cap (and/or the retry-backoff streak) on `agent_run_id` instead of, or in addition to, the virtual-key ID.** Rejected for v1, for the concrete, code-verified reason in design (b): `agent_run_id` is entirely client-supplied and unverified today, so using it as an enforcement dimension would let the exact adversary this RFC targets bypass the control by rotating the value per request. Revisit once `agent_run_id` is tied to a verified concept.

**A global (cross-key) circuit breaker on the fallback chain, or a global concurrency cap, instead of per-virtual-key/per-request scoping.** Rejected: this codebase's every existing per-request-cost control (RPM, TPM, budget) is scoped per virtual key, never globally, specifically so one noisy or misbehaving tenant can't degrade service for every other tenant sharing the same gateway process — a global cap would reintroduce exactly the cross-tenant blast-radius problem `internal/cache`'s tenant-isolation discipline (and `THREAT_MODEL.md`'s cross-tenant rows) already treat as a first-class concern elsewhere in this codebase.

**Computing `Retry-After` directly from `TokenBucket`'s own real refill state (seconds until the next token is available) instead of an exponential-streak counter.** Considered as a more "physically accurate" alternative for the rate-limited case specifically. Rejected for v1 scope: it would need a new exported `TokenBucket` method, would only cover the RPM/TPM rejection case (not concurrency-cap-exceeded or the final-upstream-failure case, which have no token-bucket state to query at all), and the task's own framing asks concretely for "exponential backoff with jitter" as the general shape across every gateway-rejection type, not a per-mechanism-accurate value. Worth a future, narrower refinement specifically for the rate-limited case; not built here.

**Extending `Pipeline.UpsertVirtualKey` to also accept a live concurrency-cap update in this same pass.** Rejected for scope: touches `admin.go`'s request struct, its handler, and every admin-API test call site for a control this RFC's own risk assessment already names as a real, acceptable v1 gap (static-config-only) rather than a load-bearing requirement of the mitigation itself.

## Honest effort and risk assessment

**What is real and implemented in this pass:** (1) Exponential-backoff-with-equal-jitter `Retry-After` on every client-facing rejection this codebase can currently classify as a genuine capacity/availability signal (rate-limited, concurrency-cap-exceeded, final-upstream-failure), scoped correctly away from rejections where it would be actively misleading (budget) or pointless (guardrail/model-not-allowed/auth). (2) A genuine, live per-virtual-key concurrency cap, enforced identically on both the buffered and streaming request paths, that a concurrent-N-plus-1st request from the same key really does get rejected by while N are still outstanding (proven by a real HTTP integration test holding N requests open, not a mock). (3) A real per-request fallback-chain circuit breaker that stops early on repeated within-request failure, closes the real "fallback chains bypass active health-probing" gap this RFC's own grounding research found, and adds genuine, measurable inter-hop spacing.

**What is explicitly NOT implemented, named rather than hidden:** No cross-request or cross-instance concurrency enforcement — this is a single-process, in-memory cap, the same "single-instance stepping stone" scope limit this project's rate-limiting/budget/cache-stampede-protection features have each started with; a multi-instance deployment enforces this cap independently per instance, not globally. No live admin-API mutation of the concurrency cap. No `Retry-After` for budget-exceeded rejections (deliberately, not an oversight — see design (a)). No per-`agent_run_id` enforcement dimension (deliberately, not an oversight — see design (b), a genuine unverified-identity security concern, not just a "future work" placeholder). No traffic-derived statistical circuit breaker — correctly, per the task's own explicit instruction, staying out of scope.

**Real risk this pass introduces, weighed honestly:** the inter-hop and client-facing backoff delays add real, if small and bounded, latency to already-failing requests — accepted as the correct tradeoff (a struggling deployment getting hammered faster is strictly worse than a client waiting a few hundred extra milliseconds through an already-degraded path). The per-request circuit-breaker threshold (3) and backoff bounds (25ms/400ms chain-internal, 500ms/30s client-facing) are engineering judgment calibrated against this codebase's own existing conservative-default precedent (`router/health.go`'s N-of-M), not against real production traffic, which does not exist yet for this project — exactly the same calibration-data gap this codebase's own `l3MinSimilarity`/health-probing-threshold RFCs have already named honestly for themselves, not a new problem this RFC introduces silently.

## Verification

`go build ./... && go vet ./...` clean. `golangci-lint run ./...` → `0 issues`. `go run github.com/fe3dback/go-arch-lint@v1.18.0 check` → clean (no new component: `internal/ratelimit` gains two new files, no new package; `dataplane`'s new `Config.Concurrency` field and `retry_after.go` introduce no new cross-package import `dataplane` didn't already have). `gofmt -l .` → empty. `go mod tidy` → empty diff (zero new dependencies; `EqualJitterBackoff`'s jitter source is caller-supplied `float64`, so `internal/ratelimit` still needs no new import beyond the standard library `math`/`math/rand` it can already reach). `go test ./... -race` → every package `ok`, including the two pre-existing, already-documented, environmental rootless-Docker failures unrelated to and unchanged by this pass.

New tests, three layers, following this codebase's own established convention of proving timing-sensitive claims against real elapsed time rather than a mocked clock or a bare "the function returns a plausible number" assertion:

- **`internal/ratelimit/backoff_test.go`**: `TestEqualJitterBackoffFloorAndCeiling` pins `frac` to `0.0` and `0.999...` to assert the exact deterministic floor/ceiling bounds at several attempt counts (pure, no real time needed — this is what proves the *formula* is right). `TestRetryBackoffRecordGrowsWithConsecutiveStreakOverRealElapsedTime` calls `Record` repeatedly for one key with the production, non-injected `rand.Float64` source and *actually sleeps* for each returned duration via real `time.Sleep`, measuring real `time.Now()` deltas between iterations and asserting the observed elapsed time for a later call is never less than the theoretical floor for its streak position (accounting for scheduler slack with a generous but bounded tolerance) — proving the backoff genuinely, measurably spaces out real wall-clock time across repeated rejections, not merely that `Record` returns an increasing number in isolation. `TestRetryBackoffResetClearsStreak` proves a success genuinely resets escalation for that key, and that a different key's streak is never affected by another key's rejections (tenant isolation, matching this codebase's cross-tenant discipline elsewhere).
- **`internal/ratelimit/concurrency_test.go`**: `TestConcurrencyLimiterRejectsNPlusOneWhileNInFlight` acquires exactly `MaxInFlight` slots directly, asserts the next `Acquire` for the same key fails while they're all still held, then releases one and asserts the next `Acquire` now succeeds — the pure, non-HTTP proof of the mechanism. `TestConcurrencyLimiterPerKeyIsolation` proves one key's cap is never affected by a different key's in-flight count. `TestConcurrencyLimiterRegisterLiveUpdateNeverDropsInFlightCount` mirrors `KeyLimiter.Register`'s own test precedent.
- **`cmd/gateway/concurrency_limit_integration_test.go`** (the plan's own required real-HTTP proof, following `cache_stampede_integration_test.go`'s exact pattern: a real `httptest.Server` upstream blocked on a channel until released, real concurrent `net/http` client goroutines, a `sync.WaitGroup` to synchronize "N requests are genuinely in flight before sending the N+1th"): `TestIntegrationConcurrencyCapRejectsNPlusOneWhileNInFlight` configures a virtual key with `max_concurrent_requests: 3`, sends 3 requests that block in the mock upstream, confirms a 4th concurrent request for the *same* key gets `429` with a `Retry-After` header while the first 3 are still outstanding, then releases the upstream and confirms a 5th request (sent only after the first 3 have genuinely completed) succeeds — proving the cap is real, per-key, and self-releasing, not merely that `Acquire`/`Release` exist as functions.
- **`internal/gateway/dataplane/fallback_test.go`** (updated, not replaced): every existing `attemptFallbackChain` test updated for the new leading `ctx` parameter; `TestAttemptFallbackChainSkipsRouterUnhealthyTargetsWithoutAttemptingThem` (new) proves a chain target `router.IsHealthy` reports false for is never passed to `call` at all. `TestAttemptFallbackChainStopsAfterMaxConsecutiveFailuresWithinOneRequest` (new) proves a chain configured with more than 3 targets, all failing, stops calling `call` after the 3rd real failure even though further targets remain configured — the per-request circuit breaker's own load-bearing proof. `TestAttemptFallbackChainInsertsRealMeasurableDelayBetweenHops` (new) measures real wall-clock elapsed time across a 3-hop, all-failing chain walk via `time.Now()` before/after, asserting the total is at least the two inter-hop floors' sum (bounded, not flaky) — proving the delay is a genuine `time.Sleep`/timer-based pause the function actually executes, not a computed-and-discarded value.

Sanity-checked the three most load-bearing lines by temporarily breaking each, confirming the right test failed for the right reason, then reverting and confirming `git diff` showed zero trace: (1) `ConcurrencyLimiter.Acquire`'s `l.inFlight[keyID] >= max` short-circuited to always `true` (never reject) — `TestConcurrencyLimiterRejectsNPlusOneWhileNInFlight` and the real-HTTP integration test both failed with "4th request should have been rejected, got 200"; reverted, both passed again. (2) `attemptFallbackChain`'s new `maxConsecutiveChainFailures` breaker check short-circuited to `false` (never trips) — `TestAttemptFallbackChainStopsAfterMaxConsecutiveFailuresWithinOneRequest` failed with "calls = 5, want 3 (breaker never tripped)"; reverted, passed. (3) `attachRetryAfter`'s `isRetryStormEligible` switch temporarily made to always return `false` — the integration test's `Retry-After` header assertion failed with "header absent, want a positive integer"; reverted, passed.
