# RFC: Gateway inbound Anthropic Messages API — passthrough-first ingress

- **Status**: accepted 2026-10-10 (G8 Option C; owner decisions in `docs/rfcs/2026-10-10-gateway-owner-gate-decisions.md`). Previously: proposed (decision gate G8 of the 2026-10-08 discoverability plan; the owner picks between the three options in "The decision"; no code lands before that)
- **Date**: 2026-10-09
- **Author(s)**: gateway maintainers (plan item 11, RFC-1 of `docs/upgrade-research/kelvran-deep-research-round4-discoverability-2026-10-08.md`; the 2026-10-08 design pass re-verified against `main` at 891e7770 and against Anthropic's Claude Code gateway-protocol page as archived on 2026-10-08)

Every claim about the gateway below was re-read in the code on 2026-10-09 and carries its anchor. Every claim about Claude Code comes from the archived text of `code.claude.com/docs/en/llm-gateway-protocol` (fetched 2026-10-08) and is marked "protocol page"; that page says nothing about the Anthropic SDKs, so claims about the SDKs' header and `base_url` behaviour are SDK behaviour, marked "SDK", and are what the §11 compat matrix verifies rather than this document. Nothing here was taken from the research report's own framing without one of those two checks.

## Summary

Add an Anthropic-Messages-format ingress to the data plane: `POST /v1/messages` (streaming and buffered), `POST /v1/messages/count_tokens`, the already-shipped `GET /v1/models`, and an optional `HEAD /api/hello`. The recommended design is **passthrough-first inside the existing pipeline**: the ingress parses the Anthropic body into a canonical `adapter.ChatRequest` that acts as a *policy shadow* and attaches a *passthrough envelope* holding the raw body, the fields the canonical schema cannot represent, and the `anthropic-*` request headers Anthropic asks gateways to forward. Every policy stage the OpenAI ingress runs today — authentication, model and source-IP allow-lists, RPM/TPM/concurrency, budget reservation, guardrails, routing, fallback, idempotency, the three cache layers, finalize, telemetry — runs on the shadow unchanged. The envelope is consumed at two encoding seams — upstream encoding (an `anthropic` deployment receives the raw body with `model` and `stream` rewritten and the headers forwarded verbatim; any other provider is encoded from the shadow and is therefore lossy) and client encoding (Anthropic Message JSON, Anthropic SSE events, Anthropic error envelopes) — and read, without being re-interpreted, by three policy points: fallback eligibility (§6), the cache key, L3 gate and idempotency fingerprint (§8), and the dropped-fields span attribute (§10). The alternative designs — pure translation through the canonical schema, and a native passthrough with its own enforcement — are laid out with the same evidence so the owner can choose; this RFC recommends the third.

## Motivation

- **The route does not exist and the credential header is not read.** The data mux registers `/v1/chat/completions`, `/v1/embeddings`, `/v1/models`, `/healthz` and `/readyz` and nothing else (`gateway/cmd/gateway/main.go:615-621`). Identity accepts only `Authorization: Bearer <secret>` (`gateway/internal/identity/identity.go:26` for `bearerPrefix`, `:309` for `Verify`'s prefix check). The Anthropic SDKs send their `api_key` as `x-api-key` (SDK). Claude Code sends a bearer for `ANTHROPIC_AUTH_TOKEN` (or, failing that, the `apiKeyHelper` value), `x-api-key` for `ANTHROPIC_API_KEY`, and a helper-only credential in both headers with the same value — "the developer's gateway credential, in one or both headers depending on which credential variable they set" (protocol page, request-header table and model-discovery section); a claude.ai login without a gateway credential variable sends an OAuth bearer Kelvran will reject 401, which the how-to must say. `docs/reference/compatibility.md` lists both the route and the header under what is not available, and marks the `anthropic` SDK and Claude Code as unsupported (rows at lines 394-395, 405).
- **`GET /v1/models` shipped on 2026-10-08 (plan item 6) and is inert for Claude Code without this ingress.** `cmd/gateway/models_handler.go` already answers in the superset shape the Anthropic SDK and Claude Code read, on the exact path, refusing redirects, and its own header comment records that "Claude Code in particular is not made usable by this route today", that Kelvran "never reads `x-api-key`", and that every chat turn is a `POST /v1/messages` Kelvran does not serve (`models_handler.go:31-38`); `docs/reference/compatibility.md:334,395` adds that its discovery "runs only in Anthropic-Messages mode". Per the protocol page the route also stays inert until the developer sets `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` — discovery is off by default so a shared-key gateway does not surface every model to every user.
- **Two blind research lanes named this the P0 independently** (lanes 2 and 4 of the round-4 report; convergence is the report's ranking rule), and Vercel's own gateway page sells the same lever as "only a URL change".
- **The adoption argument is concrete.** With this ingress, Claude Code connects with `ANTHROPIC_BASE_URL` plus one credential variable (protocol page), the `anthropic` Python/TypeScript/Go SDKs connect with `base_url` (SDK), and every one of them inherits Kelvran's virtual keys, budgets, guardrails, fallback and cost attribution — the capabilities that make Kelvran different from a plain proxy. Without it, the whole Claude Code and Anthropic-SDK population is addressable only by rewriting their code to the OpenAI shape.
- **Prior verdicts stand.** The OpenAI Responses API stays `not_yet` (`docs/upgrade-research/openai-api-surface-gap-tier1-2026-09-20.md`, Finding 3). `docs/upgrade-research/gateway-pretoken-counting-2026-09-07.md` looked at `count_tokens` only as an *upstream* call Kelvran might make; it took no position on serving the route and its facts (free, RPM-limited, model-specific) are reused below. No earlier research or decision covers an Anthropic-native inbound surface.

## The decision (gate G8)

Three designs were costed against the same facts. The facts that decide it:

1. **The canonical schema is narrower than the Messages API.** `adapter.ChatRequest` carries `Model`, `Messages`, `Temperature`, `MaxTokens`, `Tools`, `Stream`, `ResponseFormat`, the prompt-reference fields, `ToolChoice` and `ThinkingBindingMode`, plus the operator-only `DisableCacheControlAutoPopulate` (`json:"-"`, `types.go:365`) (`gateway/internal/adapter/types.go:333`, `type ChatRequest`). It has no `thinking{type,budget_tokens}`, `top_p`, `top_k`, `stop_sequences`, `metadata`, `output_config.effort`, `context_management`, server-tool or `anthropic-beta`-paired field. A `tool_result` with array content is rejected by the Anthropic adapter today (`gateway/internal/adapter/anthropic/anthropic.go:525`). The response decoder handles `text`, `tool_use`, `thinking` and `redacted_thinking` blocks and silently skips any other type (`anthropic.go`, `FromProvider`).
2. **Claude Code sends an `ANTHROPIC_BASE_URL` gateway the beta headers and body fields it sends to `api.anthropic.com`, minus a release-varying set of direct-connection defaults, and the protocol page tells gateways to treat those headers and fields as open lists** — "a gateway pinned to an observed list strips the next capability's header or field and breaks it on the release that introduces it" (protocol page, "Forward as open lists"). Capabilities that add body fields pair them with a beta header; stripping the header while passing the body "produces hard 400 errors", and "a gateway that rewrites or redacts request bodies for content inspection breaks the pairing the same way stripping does, so inspect without modifying" (protocol page, "Feature pass-through"). The page's table also lists header-only and body-only features (extended context, adaptive reasoning, prompt caching), so the pairing is not universal.
3. **Claude Code sends `thinking: {"type":"adaptive"}` to any model name it does not recognise, "such as gateway aliases"** (protocol page, feature table). Kelvran's canonical `model:` names are exactly such aliases, so a Claude Code turn through Kelvran carries, by default, a field the canonical schema cannot hold today (the page scopes the field to Claude 4.6 and later and lists `CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1` as a developer switch).
4. **The system array must reach Anthropic unchanged.** The attribution block Claude Code prepends is stripped positionally by `api.anthropic.com` only "when the gateway forwards the system array unchanged"; converting it to a string or reordering it puts the block into the prompt and the prompt-cache key. The page's full conditions: the block must stay the first entry, in its own array entry (a block merged with it is treated as attribution in its entirety and dropped, "including the rest of the system prompt"), with nothing prepended; every non-`api.anthropic.com` upstream receives it as prompt, so the Bedrock translate path always sends it to the model. For a gateway that must reshape system content the page's remedy is `CLAUDE_CODE_ATTRIBUTION_HEADER=0`. The preserved-thinking check rejects a request as "bound to a different conversation" when `system`, `tools` or earlier message content differs from the request that produced the thinking, and "a gateway that rewrites any of that content can cause the rejection itself" (protocol page).
5. **Error wording is load-bearing.** Claude Code's capability-rejection recovery "matches on the upstream's error wording, so forward error response bodies unmodified"; a gateway envelope breaks it "unless the envelope's message carries a stable `capability_rejected:` token" (protocol page, "Automatic retry and error forwarding"). Kelvran redacts every upstream HTTP error body to `upstream provider returned status N` (`gateway/internal/gateway/dataplane/fallback.go:118`) and every transport failure to `upstream call failed for model "<m>"` (`DECISIONS.md` 2026-10-08, sixth entry) for recorded reasons (`THREAT_MODEL.md` line 139: Bedrock error bodies carry the operator's account id and role ARN; `DECISIONS.md` 2026-10-08, sixth entry, item 4: a refused dial carried the deployment's internal base URL — the threat model has no entry for the transport case yet, which §10's amendments add); the §9 exception touches only the former.
6. **Every policy stage is written once, against `dataplane.Pipeline`.** `HandleChatCompletion` (`dataplane.go:3433`) and `HandleChatCompletionStream` (`streaming.go:135`) are the two chat entry points behind which every Gateway-row mitigation in `THREAT_MODEL.md` is implemented (the STRIDE rows name mitigations and regression tests, not entry points; the two handlers are named as entry points only in the 2026-09-26 change-log entry, line 139, alongside `HandleEmbeddings`); a second enforcement path would have to re-argue each row.

### Option A — translate through the canonical schema

Parse the Anthropic body into `ChatRequest`, let the existing adapters encode it for whatever deployment the router picks, decode the provider response into `ChatResponse`, re-encode as an Anthropic Message. One pipeline, every policy applies, cross-format cache hits come free (an OpenAI-ingress request and an Anthropic-ingress request with the same shadow share an entry).

Cost, by facts 1-5: lossy by construction for every field in fact 1 until each is made canonical, and permanently lossy for the open list in fact 2 — each new Claude Code capability is a Kelvran schema change and a release, and between releases the field is dropped (quiet feature loss when the beta header is dropped with it; the protocol page's hard-400 case is the opposite — a body field forwarded without its header, or an Anthropic-format body forwarded to a different-schema upstream — which is what Option A's shadow-encoded body risks on the Bedrock hop for any paired field the schema does carry). Re-encoding the `system` array from `role:"system"` messages (the adapter's current path, `ToProvider`'s `case "system"`, `anthropic.go:504`) defeats the attribution strip and risks the preserved-thinking rejection. Error bodies are re-encoded, so Claude Code's recovery needs the `capability_rejected:` token on every class Kelvran can name. Effort is the smallest to start and the largest to keep.

### Option B — native passthrough with its own enforcement

A separate handler forwards the raw Messages body to `anthropic` deployments only, with its own authentication, limits, budget and guardrail calls. Lossless to Anthropic by construction.

Cost, by fact 6: a second copy of the enforcement sequence, which `THREAT_MODEL.md`'s rows are not written for and which drifts from the first the day one of them changes. No fallback to a non-Anthropic deployment, no cache (the stored canonical response could not be served to it without the re-encoder Option A needs anyway), no cross-format telemetry parity unless re-implemented. It also leaves the Bedrock pilot — the only live configuration today (`/tmp/kelvran-e2e/config-b.yaml`: every deployment is `provider: bedrock`) — without a Claude Code path at all.

### Option C — passthrough-first inside the existing pipeline (recommended)

The ingress produces both a canonical shadow and a passthrough envelope. The pipeline runs on the shadow. Upstream encoding is lossless for `anthropic` deployments (raw body, `anthropic-*` headers forwarded) and lossy-by-declaration for every other provider (encoded from the shadow, with the operator opting in per deployment). Client encoding is Anthropic-shaped at every exit. The canonical schema gains the known fields in fact 1 so that the shadow — and therefore the cache key, the guardrail scan and the Bedrock translation — sees them; the unknown remainder is fingerprinted into the cache key and never silently shared.

What it buys over A: no Claude Code capability is ever lost on the Anthropic path, the system array and error wording reach the client untouched where it matters, and the schema only has to grow for fields Kelvran wants to *reason about*, not for fields it merely has to *carry*. What it buys over B: one enforcement path, fallback and cache intact, and a Bedrock recipe. What it costs: the envelope is a new concept the dataplane has to honour at two encoding seams plus the three read-only policy points named in the Summary, and the lossy hop has to be made visible rather than wished away.

The rest of this RFC designs Option C. If the owner picks A or B, the component list below still names every seam that has to move; only the envelope and the relay tee fall away.

### 1. New leaf package `internal/ingress/anthropicmsgs`

Depends only on `adapter` and `streaming` (new `.go-arch-lint.yml` component `ingress-anthropicmsgs: { in: ingress/anthropicmsgs }`, `mayDependOn: [adapter, streaming]`; add `ingress-anthropicmsgs` to `dataplane`'s `mayDependOn` (`.go-arch-lint.yml:142`); `cmd/gateway` sits outside the lint's `workdir: internal` and needs no entry).

- `Parse(body []byte) (adapter.ChatRequest, *adapter.Passthrough, error)`. Known top-level fields map to the shadow: `model`, `system` (string or block array → `role:"system"` message(s) with `CacheControl` preserved), `messages` (text, image, document, `tool_use`, `tool_result` with string *or* array content, `thinking`/`redacted_thinking` → `ReasoningBlocks` with `Signature`/`Data` byte-for-byte), `max_tokens`, `temperature`, `tools` (`name`, `description`, `input_schema`, `cache_control`, `strict`), `tool_choice` (`auto`/`any`/`none`/`tool` → canonical `ToolChoice`), `stream`, `metadata.user_id`, `stop_sequences`, `top_p`, `top_k`, `thinking{type,budget_tokens}`, `output_config.format`, `output_config.effort` (§3). Every other field, at every depth — the recorder walks the whole document and records every path not consumed into the shadow, including `messages[i].content[j].*`, `system[i].*`, `metadata.*` and `tool_choice.*` members, so nothing the raw body carries is missing from the §8 fingerprint — is recorded by JSON-pointer path in `Passthrough.UnknownFields`. Content blocks: `tool_reference` is a known block (the protocol page says Claude Code "keeps sending the tool-search beta header, defer_loading tool fields, and tool_reference blocks" under MCP tool search, so rejecting it would 400 a normal session on the very path this RFC exists to provide); any other `content[].type` has its string-valued members added to the guardrail scan and passes through to an `anthropic` deployment, and returns an error the handler maps to 400 `invalid_request_error` only when the request resolves to a translate hop (non-`anthropic` deployment), where it cannot be encoded anyway.
- `EncodeResponse(adapter.ChatResponse) []byte`: Anthropic Message JSON (`id`, `type:"message"`, `role`, `model`, `content[]` from `Choices[0].Message` — `ReasoningBlocks` first in `Sequence` order, then text, then `tool_use`), `stop_reason` and `stop_sequence` from new provider-native `ChatResponse.StopReason`/`StopSequence` fields (Anthropic-only, like `InputTransformations`) populated by `anthropic.FromProvider` and the stream decoder and folded into the cached response, falling back when they are absent to a forward table — `stop`→`end_turn`, `length`→`max_tokens`, `tool_calls`→`tool_use`, `content_filter`→`refusal`, any other canonical value passed through verbatim (mirroring `finishReasonFromStopReason`'s own default, `anthropic/stream.go:212-217`). `finishReasonFromStopReason` has no inverse: it is many-to-one (`end_turn`/`stop_sequence`/`pause_turn` all → `stop`, `stream.go:202-203`), so without the native fields a translate or cache-replay turn that hit a stop sequence would be reported as `end_turn` with no `stop_sequence` field, exactly where §3 adds `StopSequences` to the request; the passthrough path relays the raw body and is unaffected. `usage` with `input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens` and `output_tokens_details.thinking_tokens` from `Usage.ReasoningTokens` when non-zero.
- `SSEEncoder`: canonical `streaming.ChatCompletionChunk`s → `message_start`, `content_block_start|delta|stop`, `message_delta`, `message_stop`, with `text_delta`, `input_json_delta`, `thinking_delta` and `signature_delta`; a `ping` injector on a 15 s timer under an injectable clock. Used for every non-`anthropic` upstream and for cache replays.
- `EncodeError(status int, errType, message string) []byte` → `{"type":"error","error":{"type":…,"message":…}}`.

### 2. `adapter.ChatRequest.Passthrough *Passthrough` with `json:"-"`

Set only by the ingress, unreachable from any request body — the same precedent as `DisableCacheControlAutoPopulate` (`types.go:365`). `Passthrough{Format string; RawBody json.RawMessage; UnknownFields map[string]json.RawMessage; ForwardHeaders http.Header}`. `ForwardHeaders` carries every `anthropic-*` request header (the protocol page's "Forward as open lists" rule for Anthropic-format upstreams: "pass anthropic-* request headers and request body fields through unchanged rather than allowlisting the ones you see today"), which today means `anthropic-version`, `anthropic-beta` and, for a Claude-Platform-on-AWS upstream, `anthropic-workspace-id` (the page names it as required there); naming only the first two would itself be the header allow-list the page tells gateways not to keep. `x-claude-code-*` and every other request header are consumed by the attribution carrier (item 13a) and never forwarded, which is what the page allows ("the rest the gateway may consume for routing, attribution, and tracing, and need not forward").

### 3. Canonical gap fills (prerequisite sub-items)

Each is its own tests-first change, lands before the ingress, and folds into L1, L2 and the L3 gate on the day it lands (the 2026-09-24 rule from the reasoning-content RFC: every request-semantic field folds into all three layers, never a subset; `cache.Key`/`NormalizedKey` at `internal/cache/key.go:194,251`, the L3 gates in `checkLexicalCache` at `dataplane.go:2794-2874` — the entity, negation and freshness hard-gates come first and are never weakened; the per-field exact-match gates the new one joins are at `:2833-2874`):

- `ChatRequest.Thinking *ThinkingConfig{Type string; BudgetTokens int}`. The Anthropic adapter's `Request.Thinking` already exists with `Type` and `BlockBinding` (`anthropic.go:117`) and gains `BudgetTokens`; `ToProvider` must not *invent* a `Thinking` on this path (addendum to the reasoning RFC, below). Bedrock's Converse adapter carries it through `additionalModelRequestFields` (`bedrock.go:481`, today used only for structured output). Whether Bedrock accepts `type: "adaptive"` is **unverified** and must be proven live per model before the translate path forwards it; until then the Bedrock path drops `thinking` quietly and records the drop in telemetry. The protocol page does not describe this case (adaptive reasoning has "No beta header", so its "both halves absent" rule is about header-plus-body pairs, not this field); its own alternatives are a 400 naming the thinking field, which Claude Code recovers from by retrying without thinking for the rest of the conversation, or `CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1` on Opus 4.6 and Sonnet 4.6. The quiet drop is a Kelvran choice, to be weighed against returning the matchable 400. *Settled live 2026-10-10 (S2, S4): forward-or-drop by Claude generation, `adapter.BedrockForwardsThinking`; see the "Settled live" blocks under Unresolved Questions.*
- `Effort string` from `output_config.effort`. Needed because `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` leaves `output_config.effort`, the `thinking` field and developer-added `ANTHROPIC_BETAS`/`CLAUDE_CODE_EXTRA_BODY` values in place (protocol page, "Disable pre-release capabilities"), so without a canonical home a Claude Code turn behind a Bedrock-only Kelvran would still carry an unknown field and still hit §6's 400 after following the remedy §6 offers. Whether Bedrock accepts it through `additionalModelRequestFields` is **unverified**, per model, like `thinking`; until proven the Bedrock path drops it with telemetry. *Settled live 2026-10-10 (S2, S5): forward-or-drop by Claude generation, `adapter.BedrockForwardsEffort`; see the "Settled live" blocks under Unresolved Questions.* Developer-added `ANTHROPIC_BETAS`/`CLAUDE_CODE_EXTRA_BODY` residue cannot be canonical and stays in `UnknownFields`; §6's 400 names it so the developer can remove it client-side.
- `TopP *float64`, `TopK *int`, `StopSequences []string` (`stop` is silently dropped on `/v1/chat/completions` today too — fixing that is a side benefit), `Metadata.UserID` → the existing end-user scope (`X-Kelvran-End-User-Id` precedent). *Shipped 2026-10-10 (S5): `top_p` and `stop` are wire fields of `/v1/chat/completions` and reach every provider; `top_k` and `effort` are `json:"-"`, forwarded by anthropic (and gemini for `top_k`), by bedrock per generation (`BedrockForwardsTopK`/`BedrockForwardsEffort`), ignored elsewhere; all four fold into the cache keys (`samplingFingerprint`) and the hidden two into the `Idempotency-Key` fingerprint. `Metadata.UserID` stays for S10a as the `endUserIDHeader` argument.*
- Anthropic `tool_result` content widened to string-or-array (image tool results error today, `anthropic.go:525`). *Shipped 2026-10-10 (S6): `ToolResultContent`, string-or-array, string form byte-identical; bedrock `toolResult.content` image/document blocks; carriability is a routing property (`SupportsToolResultParts`), else `400 tool_result_parts_unsupported`. Settled block below.*
- `anthropic.FromProvider` returns a representability signal (`InputTransformations`-style, or a boolean on the response) when it skipped a block type it cannot carry; the dataplane treats such a response as **not cacheable** — the live client still receives the raw upstream body on the passthrough path, but a cache hit would be re-encoded from the canonical form and would silently lose those blocks. *Shipped 2026-10-10 (S6): `ChatResponse.Unrepresentable` (`json:"-"`) from `FromProvider`'s `default:` arm and the stream decoder's unknown-block and unknown-delta arms; `writeCache` skipped on both paths; anthropic-only. Settled block below.*

### 4. Authentication: `x-api-key` alias

`cmd/gateway`'s `bearerFromRequest(r)` returns `Authorization` when present; otherwise, when `x-api-key` is present, synthesises the string `Bearer <x-api-key>` and passes it as the `authorizationHeader` argument the pipeline already takes. `identity.Verify` is untouched. Precedence is deterministic — a bearer that fails is a 401, never a second attempt with the other header — because Claude Code's discovery request can carry *both* headers with different values ("sending both headers requires Claude Code v2.1.248 or later", protocol page) and two attempts per request would double the guessing surface against `key_hash`. The alias applies to `/v1/messages`, `/v1/messages/count_tokens` and `/v1/models`, the three authenticated Anthropic-format routes (`HEAD /api/hello` takes no credential; the Anthropic SDK lists models with `x-api-key` — SDK); the OpenAI routes keep bearer-only because no OpenAI client sends `x-api-key`. Neither header value may ever be logged. No test pins this today — `bearerFromRequest` is itself new (the four handlers currently call `r.Header.Get("Authorization")` directly: `main.go:2011, 2066, 2105`; `models_handler.go:96`) and no existing test asserts that the `Authorization` value stays out of logs — so a new `TestBearerFromRequestNeverLogs` in `cmd/gateway`, covering both headers, is part of this change and is written red first (Verification).

### 5. Upstream encoding

- `anthropic` deployment with `Passthrough.Format == "anthropic"`: `ToProvider` returns `RawBody` with exactly two rewrites — `model` → `dep.UpstreamModel`, `stream` → the pipeline's value — performed on the parsed JSON object so field order and every unknown field survive. `setUpstreamAuthHeaders` (`dataplane.go:5776`, `case "anthropic"`) copies `ForwardHeaders` verbatim. The case today hardcodes `anthropic-version: 2023-06-01` (`dataplane.go:5812`); on the passthrough path the client's `anthropic-version` from `ForwardHeaders` replaces it when present and the hardcoded value remains the default when absent — one test pins each. Under the recommended decision the thinking-binding beta is not added on this path (the raw body gets no `block_binding` rewrite and the header alone is inert), so the client's `anthropic-beta` is forwarded as-is; the comma-join with `thinkingBindingControlsBeta`, deduplicated, that the existing comment at `:5817-5820` anticipates is needed only if the owner picks the third-rewrite alternative. `Idempotency-Key` stays absent for Anthropic (verified 2026-09-16, same site).
- `bedrock` deployment: encoded from the shadow by the existing Converse adapter. `ForwardHeaders` are stripped (`DeploymentConfig.AnthropicBetaPolicy: strip`, the default). `forward_known` maps an allow-list of beta values into `additionalModelRequestFields.anthropic_beta` only after a live 200 proves each value on the target model, recorded in the allow-list's own comment the way `SupportsStructuredOutput`'s whitelist records its dated verifications. Bedrock stays on Converse; the research's InvokeModel remark is answered by the strip policy, not by a transport change.
- `openai`, `gemini`, `openaicompat`: encoded from the shadow as today. Every field in `UnknownFields` is dropped on these hops.

### 6. Fallback eligibility: lossiness is a routing property

`capabilityOKForRequest` (`dataplane.go:321`) gains a second clause: `len(req.Passthrough.UnknownFields) > 0 && dep.Provider != "anthropic" && !dep.AcceptLossyAnthropicIngress → false`. The flag is a new per-deployment config key, default `false`, so a Claude Code request carrying a beta field reaches a Bedrock-only Kelvran as a **400 `invalid_request_error`** whose message names the dropped fields and the config key (never a deployment name — a client must never learn one) and suggests `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1`, the protocol page's remedy for pre-release betas. The page says that variable leaves `output_config.effort`, the `thinking` field and developer-added `ANTHROPIC_BETAS`/`CLAUDE_CODE_EXTRA_BODY` values in place, which is why `thinking` and `output_config.effort` are canonical (§3) — otherwise a developer who followed the remedy would still get the 400 — and why the message names any developer-added residue explicitly. 400 rather than 502 because the protocol page says Claude Code surfaces non-retried 400s (its context-management and tool-schema rejections) to the developer; the page documents no 5xx policy and defers retry counts and classes to Claude Code's separate automatic-retries page, so nothing here relies on one. The 400 message must avoid the wording Claude Code matches for recovery (`thinking`, `output_config.effort` with `Extra inputs are not permitted`, `Input tag`, `bound to a different conversation`) unless that recovery is the intended outcome. The status diverges from today's 502 for `ErrStructuredOutputUnsupported` (decisions table; plan gate G16). An operator who sets the flag gets the quiet-drop behaviour plus telemetry; the Bedrock recipe in the Claude Code how-to pairs the flag with the client variable.

### 7. Streaming

- `streaming.ChunkSink{WriteChunk(ChatCompletionChunk) error; WriteDone() error}` is satisfied by the existing `*streaming.Writer`; `HandleChatCompletionStream` becomes a thin wrapper over `HandleChatCompletionStreamSink(ctx, …, sink)`. `streamDeployment` (`streaming.go:630`) and `streamDeploymentBedrock` (`:782`) write to the sink. The relay's client leg (next bullet) is itself a `ChunkSink` implementation (adding `WriteRaw([]byte) error`) wrapping the `ResponseWriter`, and sets `*firstChunkSent = true` on the first byte written: today the flag is set only after `sw.WriteChunk` succeeds (`streaming.go:716-719`, `:898`) and gates both `billable = firstChunkSent` (`:375`) and the no-fallback-after-first-byte rule (`if err == nil || firstChunkSent`, `:557`), so a relay writing outside the sink would leave it false and a passthrough stream that failed after bytes reached the client would fall back to another deployment (double delivery, possibly in another format) and be treated as unbilled.
- `anthropic` upstream on the passthrough path: a **raw-relay tee**. A relay driven by the existing `streaming.Reader` (`reader.go:24`): each complete event it returns is written to the client (`Content-Type: text/event-stream`) and flushed before the Anthropic stream decoder consumes it, so the client never receives a partial event and the relay can stop cleanly at an event boundary (an `io.TeeReader` could not — it copies each `Read` buffer verbatim with no event awareness, so a `Read` ending mid-event would be flushed half-written). The decoder consumes the same events for accumulation, usage, mid-stream TPM/budget top-ups (`checkMidStreamReservationTopup`, `streamrunaway.go:194`), the end-of-stream usage fallback (`estimateOrRealUsage`, `streaming.go:952`) and the post-call guardrail. Upstream `ping` events, unknown event types and error-frame wording reach the client byte-for-byte, which is what Claude Code's stall detection and recovery need (protocol page, "Streaming": a gateway that strips or buffers pings "can trip that timeout partway through a response").
- Every other upstream, and cache replays: the `SSEEncoder` sink. The gateway emits its own `ping` during silence because Bedrock's event stream has none (protocol page names this gap). The page does not publish the idle-timeout value; 15 s is Kelvran's choice and must sit well under the value in Claude Code's streaming-idle-timeout documentation, checked before the number is frozen. When the relay or the encoder must abort after a content block has started, it emits an Anthropic `error` event rather than closing cleanly, because the page says a clean end before the final `message_delta` is treated as a dropped connection.
- The streaming post-call guardrail is already audit-only for client delivery (`streaming.go:1029-1035`, per the 2026-09-03 guardrails RFC's accepted residual risk), so the guardrail half of the plan's "overturn" condition (mid-stream budget/guardrail without buffering) needs no buffering layer; the pre-call guardrail runs on the shadow before the upstream call as today. The budget/TPM half is met only if the relay can stop at an event boundary when `checkMidStreamReservationTopup` or the runaway ceiling trips — today both trip by `cancelUpstream()` + `break` (runaway ceiling `streaming.go:732-743`, reservation top-up `:753-763`; the Bedrock twin at `:902` and `:916`) and fall through to `finishStreamedResponse` (`:978`), which writes nothing but the `[DONE]` sentinel via `sw.WriteDone()` (`:1061`) — no terminal chunk and no `finish_reason` is synthesised today, so an OpenAI client sees a stream that simply ends. On this ingress that is not acceptable (the page treats a clean end before the final `message_delta` as a dropped connection), so the Anthropic sinks' `WriteDone` must synthesise `content_block_stop` (if a block is open), `message_delta{stop_reason:"max_tokens"}` and `message_stop` from the accumulator's state. That synthesis is new code on both the `SSEEncoder` and the relay's termination path, specified here and tested (Verification), not a translation of an existing chunk.

### 8. Cache

- `passthroughFingerprint = sha256(canonical JSON of UnknownFields)` becomes a new input to `cache.Key` and `NormalizedKey` (11 parameters each today, `key.go:194,251`; the §3 fields fold in first, each on its own commit, so its ordinal depends on sequencing) and a new exact-match gate in `checkLexicalCache`, placed with `ThinkingBindingMode` and `ToolsFingerprint`. Empty for the OpenAI ingress, so cross-format hits still happen when the shadow matches and the Anthropic request carried nothing unknown. As with every previous fold, every L1/L2 key changes versus an earlier build (hashed even when empty); the in-process caches are empty on every restart, nothing to flush.
- `DisableCacheControlAutoPopulate = true` on every request from this ingress: the client owns `cache_control`, and the attribution block must never be touched (fact 4).
- Cache hits are re-encoded by `EncodeResponse`; `ReasoningBlocks` keep `Signature`/`Data` byte-for-byte so a replayed thinking turn still passes Anthropic's preserved-thinking check. Responses flagged non-representable (§3) are not written.
- Idempotency changes in one place: on this ingress `claimIdempotency` (`dataplane.go:3082-3086`, today `json.Marshal(req)` → `sha256.Sum256`) fingerprints `sha256(RawBody)` (the handler passes the bytes), which covers every field at every depth without depending on what the recorder saw; the OpenAI ingress keeps `sha256(json.Marshal(req))`. A reused `Idempotency-Key` with a body that differs only in an unknown field therefore still yields `ErrFingerprintMismatch` instead of the first response.

### 9. Handlers and routes (`cmd/gateway/anthropic_routes.go`)

- `POST /v1/messages` — exact path, like `/v1/models` (`main.go:617-619`): `ServeMux` matches the path only and ignores the query string, so `?beta=true` (what Claude Code actually posts, protocol page) and any future query are accepted as-is; a subtree pattern (`/v1/messages/`) must not be used, because `ServeMux` would answer the bare path Claude Code posts to with a 301 and the protocol page treats a redirect as failure. `/v1/messages/count_tokens` is its own exact registration. Same 32 MiB body limit (`main.go:184`); `Content-Type: application/json` responses buffered, `text/event-stream` streamed.
- `POST /v1/messages/count_tokens` — authenticates, resolves `model` through the same router, requires an `anthropic` deployment; otherwise 404 `not_found_error`. The protocol page says Claude Code falls back to a character-based estimate when the endpoint is absent; whether it treats a per-model 404 from a served route identically is not on the page and is checked live (Verification step 1). It runs the pre-call guardrail on the shadow (content leaves the gateway), consumes one RPM token, debits no budget, writes no cache, forwards the raw body and headers, returns the upstream body. Anthropic documents the call as free but RPM-limited (pretoken report); the pre-call guardrail's own provider cost (a `bedrockguard`/`embedsim` detector signs a real, paid AWS call per check — `AGENTS.md` gotchas) is incurred per request and never budget-debited, bounded only by RPM, which operators running paid detectors must know before enabling the route.
- `GET /v1/models` — unchanged except for `bearerFromRequest`.
- `HEAD /api/hello` — 204, no auth, no body; `GET` on it is 405.
- `writeAnthropicError` maps three sources to Anthropic types. `errorStatus`'s table (`main.go:2120-2203`; it emits 400, 401, 403, 429, 501, 502 and 503) and `errorTypeAndCode`'s vocabulary (`error_envelope.go:196-257`): 401 `authentication_error`, 403 `permission_error`, 429 `rate_limit_error`, 400 `invalid_request_error`, every 5xx `api_error` (Kelvran keeps its 503 for the `ErrStreamingNotConfigured` class; Anthropic's `overloaded_error` is a 529 condition Kelvran never emits, so the type is not used). The body-limit path's 413 (`main.go:1944, 2044`) → `request_too_large`. This RFC's own `count_tokens` 404 → `not_found_error`. `Retry-After` stays integer seconds (`retryAfterSeconds`, `main.go`; protocol page: "Return integer seconds rather than an HTTP date"). Today it is attached only to rate-limit, upstream-error and deployment-capacity rejections (`isRetryStormEligible`, `retry_after.go:49-57`) — a budget 429 (`insufficient_quota`) carries none — and its value is the larger of the per-key backoff (capped at 30 s, `ratelimit/backoff.go:31`) and the upstream `Retry-After` (capped at 60 s, `maxUpstreamRetryAfter`, `upstream_error.go:59`), so Kelvran never emits a value above 60 and Claude Code never reaches the page's "above 60 stops the retries" path. This RFC changes neither rule and records two consequences for the owner: a Claude Code session on an exhausted budget retries on its own schedule with no `Retry-After` hint, and Kelvran never synthesises `anthropic-ratelimit-unified-*` to tell it the limit is a cap rather than a throttle; an Anthropic 429 asking for more than 60 s is relayed as 60, so Claude Code retries once more after a minute. Lifting `maxUpstreamRetryAfter` on this ingress, or attaching a budget-window `Retry-After`, is a separate decision (plan gate G16 territory), not assumed here. **Cross-reference (2026-10-10, RFC-3 slice (g)):** `kelvran connect claude --check` reads a 400 from `POST /v1/messages` as proof of URL and credential only when the envelope carries `error.code: model_not_found` (Kelvran's own code, `docs/reference/error-codes.md`); Anthropic's envelope has no `code` member, so this ingress must keep Kelvran's `code` on its 400s — an extra member the Anthropic SDKs ignore — or the probe's happy path is updated together with it.
- Upstream error bodies: verbatim only when `dep.Provider == "anthropic"`, status ∈ {400, 422}, and the body parses as `{"type":"error","error":{"type","message"}}` — the classes Claude Code's recovery matches on (thinking field, a mid-conversation system message or its `cache_control` marker, signature "bound to a different conversation", `Input tag`, `output_config.effort`). Anthropic 401/403/429/5xx bodies, every non-Anthropic body and every transport failure keep `ClientSafeMessage` — both `UpstreamHTTPError.ClientSafeMessage` (`fallback.go:118`) and `adapter.UpstreamStreamError.ClientSafeMessage` (`internal/adapter/errors.go:142`; `THREAT_MODEL.md` line 140 names both, and `TestWriteStreamErrorFrameIsInBandAndRedacted` at `error_envelope_test.go:222` pins the stream one). The verbatim exception is applied at both sites with the same three-part scope, so an in-band stream error on an `anthropic` hop reaches the client verbatim too, and the `TestWriteStreamErrorFrame*` family gains the anthropic/400|422/parsed case; the information-disclosure argument in `THREAT_MODEL.md` is about operator-side detail in those classes, and the 400/422 wording is about the client's own request. A Bedrock `ValidationException` whose `UpstreamHTTPError.ErrorType` (`fallback.go:68`) and body name an over-long input is mapped to `capability_rejected: prompt_too_long` (the example token the protocol page shows the Claude apps gateway substituting for cloud providers' wording; that Claude Code's reactive compaction fires on it is not on the page and must be confirmed live).
- Response headers: `NewHTTPUpstreamCaller` and the stream caller capture upstream response headers into an `UpstreamResponseMeta` context value; the handler forwards `x-should-retry` and `anthropic-ratelimit-unified-*` when present (protocol page: "pass the upstream's value through unchanged"). Kelvran never synthesises unified headers from its own budgets — those express Anthropic plan limits, and a fabricated value would mislead Claude Code's usage display.

## Drawbacks

- A second request representation (raw body plus shadow) that two seams must keep consistent. The `model`/`stream` rewrite on the raw body is the one place the two can disagree; one test per field pins it.
- Five new canonical fields and a new fingerprint change every L1/L2 key again (`key.go` already records six such folds — `:97, 108, 135, 149, 165, 185`; these are the seventh and onward, one per commit). Invisible for in-process caches; still a key change.
- The verbatim-error exception is a deliberate, scoped hole in a redaction rule the threat model argued for. The scope (one provider, two statuses, one parsed shape, two redaction sites) is narrow and testable, but it is a hole. More broadly, the Gateway Tampering row's "no raw pass-through of unvalidated provider fields" (`THREAT_MODEL.md` line 12) stops being true for the `anthropic` path and has to be rewritten (§10), not merely appended to.
- Lossy hops are a new failure mode operators must understand: a Claude Code user behind a Bedrock-only Kelvran sees a 400 until the operator opts in or the developer disables experimental betas. The alternative — dropping unknown fields silently by default — is the allow-list behaviour the protocol page warns "strips the next capability's header or field and breaks it on the release that introduces it".
- The `ping` injector, the relay tee and the SSE encoder are three new ways a stream can end badly; each needs its own disconnect and timeout tests.
- `count_tokens` is budget-free traffic a tenant can generate at RPM rate: the Anthropic call is free, but the pre-call guardrail's own provider cost (Bedrock Guardrails, EmbedSim embeddings — a real AWS call per check) is incurred per request and never budget-debited. RPM bounds it, but it is a cost the operator does not see on the budget.
- Claude Code behaviour is taken from one archived page. The page says the lists are open and the defaults vary by release; the compat matrix, not this RFC, is what keeps the ingress honest over time.

## Alternatives Considered

- **Option A, translate** (above). Rejected as the primary design for facts 1-5; kept as the mandatory path for non-Anthropic deployments, which is where its strengths (one schema, cache sharing) apply and its weakness (lossiness) is declared per deployment rather than hidden.
- **Option B, native passthrough with its own enforcement** (above). Rejected for fact 6 and for leaving the Bedrock pilot without a path.
- **Expose the Bedrock InvokeModel format instead of the Messages format.** The protocol page offers this ("you can avoid the bridging by exposing that provider's format instead"), and the pilot is Bedrock. Rejected: Claude Code reads the binary `application/vnd.amazon.eventstream` body and "can't parse it once a gateway converts it to server-sent events" (protocol page), so Kelvran's SSE streaming layer could not sit in the path; it binds the client to one of Kelvran's five providers; and it does nothing for the Anthropic SDKs.
- **Allow-list the `anthropic-beta` values Kelvran has seen.** Rejected: the protocol page says, verbatim, "don't allowlist individual values, because the set changes with Claude Code releases".
- **Accept `x-api-key` on every route, or try both headers.** Rejected: no OpenAI client sends it, and two attempts per request doubles the online guessing surface against `key_hash`.
- **Forward every upstream error body verbatim on this ingress.** Rejected: Bedrock bodies carry operator account ids and role ARNs (`THREAT_MODEL.md`, the 2026-09-26 redaction fix); the scoped exception in §9 covers the classes Claude Code's recovery needs.
- **Do nothing.** Leaves Claude Code and the Anthropic SDKs unable to use Kelvran, which both research lanes ranked as the single largest adoption gap, and leaves `GET /v1/models` serving a picker nobody can reach.

**Settled on 2026-10-11 (item 11 slice S11b2 — the streamed half of §9's response leg).** `streaming.SSEEvent.Raw` carries each event's bytes as read (the reader became a `bufio.Reader` line loop with the same parsed semantics and the same 1 MiB cap) and feeds `streaming.RawRelay.WriteRaw` on the Anthropic encoder before each `Decode`, when the request reached an `anthropic` deployment as a `PassthroughRequest`; the relayable headers travel with the first frame; the first relayed frame is the first byte sent (no fallback after it); the shadow is still decoded for usage, cost, the cache, the post-call audit and the guard cuts, but no canonical chunk is written beside the relay. The encoder mirrors `message_start`, the open block index, a relayed `message_delta` and the terminal frames, so a guard cut still ends with `content_block_stop`/`message_delta{max_tokens}`/`message_stop`, and a relayed `error` frame is the stream's single error event (`WriteError` is a no-op once the message ended); a hop's first frame is decoded before it is relayed and relayed only when the decoder accepted it, so an error frame, garbage or a malformed known event as the first frame is redacted and the hop may fall back exactly as before, while every later frame is relayed before it is decoded so unknown events and in-band error frames reach the client as read (four review rounds, fixed pre-commit: relaying an error-first frame blocked the fallback that used to serve such a turn; a relay-side classifier then disagreed with the decoder in corner cases — the event name, unparsable data, a malformed body — so the decoder became the single judge). An unknown top-level event before `message_delta` marks the response unrepresentable (never cached or replayed; one after it is relayed but not flagged — Anthropic sends `message_delta` last before `message_stop`).
