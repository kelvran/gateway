# RFC: Cache L1/L2/L3 TTL jitter

## Status

Accepted, implemented 2026-09-10.

## Context

A `docs/upgrade-research/cache-next-upgrade-round2-2026-09-09.md` deep-research pass (Finding 3) surfaced a real, checkable eviction-policy gap: `gateway/internal/cache/inprocess/inprocess.go`'s `Put()` computes `expiresAt := now.Add(ttl)` with no randomized jitter, and `inprocess/lexical.go`'s `LexicalCache.Put()` has the identical unjittered pattern. A burst of entries written together (e.g. after a deploy, or a traffic spike) expires in near-lockstep — the textbook thundering-herd pattern AWS's own official caching-best-practices docs (`ttl = base + rand()*jitter`) and Portkey's semantic-caching blog independently name as a standard, trivial-to-implement fix. Kelvran's L2 is a second runtime instance of the exact same `inprocess.Cache` type (`cmd/gateway/main.go`'s `buildPipeline` constructs both via separate calls to the same constructor), so a fix inside `Put()` covers L1 and L2 automatically; L3's structurally separate `LexicalCache` implementation needed the identical fix applied on its own.

## Design

`NewWithClock`'s existing, documented contract ("deterministic TTL testing") is exactly zero jitter — every current TTL-boundary test relies on `expiresAt` being precisely `now.Add(ttl)`. Retrofitting jitter into that constructor directly would make those exact-equality tests flaky. Instead, a new, most-general constructor, `NewWithClockAndJitter(maxEntries, now, jitterFraction, randFn)`, mirrors `ratelimit.RetryBackoff`'s own exact "inject the rand source, not just the clock" split (`NewRetryBackoff` vs. `NewRetryBackoffWithRand`). `Put` becomes `expiresAt := now.Add(ttl + time.Duration(rand()*jitterFraction*float64(ttl)))` — additive only, never shortening the configured TTL. `New` (the real production constructor) delegates to `NewWithClockAndJitter(maxEntries, time.Now, 0.10, rand.Float64)` — jitter on by default, since it only smooths eviction timing and carries no correctness risk. `NewWithClock` stays byte-for-byte unchanged in behavior, delegating to `NewWithClockAndJitter(maxEntries, now, 0, func() float64 { return 0 })`. Identical three-constructor treatment for `LexicalCache`.

Config: `CacheConfig`/`CacheL2Config`/`CacheL3Config` each gain `JitterFraction float64`, parsed from new YAML keys `cache.jitter_fraction`/`cache.l2.jitter_fraction`/`cache.l3.jitter_fraction`. `<= 0` (absent) resolves to the real 10% default — but that resolution deliberately happens in `cmd/gateway/main.go` (a new `resolveJitterFraction` helper), not inside `inprocess` itself: `NewWithClockAndJitter` always jitters by exactly `rand()*jitterFraction*ttl`, whatever it's given, with no `<=0`-means-default special-casing of its own, since that ambiguity only exists for an operator's YAML field (which can't distinguish "not set" from an explicit zero either way) — an internal API call site can always pass the real value it means.

## Alternatives considered

**Retrofitting jitter into `NewWithClock` directly, with `jitterFraction` defaulting to 0** — rejected: this is functionally identical to what shipped (zero jitter for that constructor), but a future maintainer skimming `NewWithClock`'s call sites might expect jitter to apply there and be surprised when a boundary-exact test starts flaking after they change the default. Keeping `NewWithClock` a pure delegate to `NewWithClockAndJitter(..., 0, ...)` makes the "this constructor is jitter-free, on purpose" contract structurally visible, not just documented.

**A configurable "disable jitter entirely" knob** — rejected: jitter only smooths eviction timing and carries no correctness risk, so there's no legitimate operator reason to turn it off in production; `<= 0` in config resolves to the default rather than to zero, deliberately.

## Verification

New tests per cache type, mirroring `inprocess_test.go`'s existing `staticClock` convention plus a deterministic-rand fake (mirroring `backoff_test.go`'s `NewRetryBackoffWithRand` pattern): `TestPutAppliesJitterWithinConfiguredFraction`/`TestLexicalPutAppliesJitterWithinConfiguredFraction` (rand pinned to `1.0`, asserts the exact upper bound), `TestPutZeroRandProducesNoJitter`/`TestLexicalPutZeroRandProducesNoJitter` (rand pinned to `0.0`, asserts the un-jittered floor), and `TestNewWithClockStillHasZeroJitter`/`TestLexicalNewWithClockStillHasZeroJitter` (a regression guard proving the pre-existing constructor's determinism contract survives). Every existing TTL-boundary test using `NewWithClock`/`NewLexicalCacheWithClock` was audited first and confirmed unaffected — all still pass unchanged. New `config_test.go` cases for the three YAML keys, plus an absent-key-defaults-to-zero case (resolution happens in `main.go`, not this package). Sanity-checked-by-breaking: temporarily forced `jitter := time.Duration(c.rand() * 0 * float64(ttl))` inside `Put`, confirmed the max-jitter test failed for the exact predicted reason (`expiresAt` came back at the un-jittered floor instead of the +10% ceiling), restored. Full `cd gateway && go build ./... && go vet ./... && go test ./... -race && golangci-lint run ./... && go run github.com/fe3dback/go-arch-lint@v1.18.0 check && gofmt -l . && go mod tidy` clean except the same pre-existing, already-documented rootless-Docker environmental failures.
