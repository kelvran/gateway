# RFC: OTel GenAI Metrics — gen_ai.client.token.usage + gen_ai.client.operation.duration

## Status

Accepted, implemented 2026-09-07.

## Context

Additive to `docs/rfcs/2026-09-05-gateway-ratelimit-fail-open-metric.md`, which stood up this codebase's only OTel Metrics pipeline and instrument (`kelvran.ratelimit.fail_open`) and explicitly named it as the *first* metric, not the only one. A fresh upgrade-research pass (`docs/upgrade-research/gateway-2026-09-06.md`, Finding 3) confirmed the gap that RFC anticipated: no latency histogram, no token-usage histogram, no request-count metric exists anywhere in this codebase beyond that one counter, despite `PRD.md`'s own stated differentiation thesis being "cost savings attributable and explainable down to the individual agent run" — an observability claim this codebase had almost nothing aggregate to back.

The canonical OTel GenAI semantic-conventions spec defines two Recommended histogram instruments for exactly this: `gen_ai.client.token.usage` (unit `{token}`, with a required `gen_ai.token.type` attribute distinguishing `"input"`/`"output"`) and `gen_ai.client.operation.duration` (unit `s`, with a conditionally-required `error.type` attribute on failure). Envoy AI Gateway v1.1 already ships both, plus a ready-made Grafana dashboard JSON file — concrete precedent that these two specific instrument names are worth building against directly, not a Kelvran-local reinvention.

**Caveat carried forward, not a blocker**: `gen_ai.client.token.usage`'s OTel spec stability badge is explicitly "Development," not "Stable," as of this research. This codebase already has precedent for building against development-stability OTel GenAI conventions — `docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md`'s `gen_ai.*` trace attributes carry the identical caveat and are hardcoded as string constants rather than depending on `go.opentelemetry.io/otel/semconv`'s incubating GenAI module for the same reason (that module's Go API surface itself still shifts as the spec does). The two new instrument name strings are treated the same way: literal constants, not an semconv-package import, so a future spec rename is a one-place string edit, not a dependency-version chase.

## Design

### Reuse `dataplane.finalize`'s existing data capture, not a new one

Both histograms are recorded from the exact same call site `telemetry.RecordChatCompletionResult` already uses: `dataplane.finalize`, shared by `HandleChatCompletion` and `HandleChatCompletionStream`. `finalize` already builds one `telemetry.ChatCompletionResult` literal for the trace-attribute call; that same struct value is now also passed to a new `telemetry.RecordChatCompletionMetrics(ctx, result)` call immediately after `RecordChatCompletionResult(span, result)` — one shared capture point, two consumers, per this item's own "reuse the existing per-request data capture point, don't add a new one" framing. `ChatCompletionResult` gained four fields to carry what only the metrics side needs: `RequestModel` (the `gen_ai.request.model` attribute — the span's own name already encodes this for tracing, so `RecordChatCompletionResult` never needed it as a separate attribute), `Duration`, `Billable`, and `ErrorType`.

### Duration: captured by the caller, not read back from the span

`trace.Span` has no clean, provider-agnostic way to read back its own start time from the OTel API — confirmed by reading the API, not assumed. `HandleChatCompletion`/`HandleChatCompletionStream` each now capture `start := time.Now()` one line before `telemetry.Tracer.Start(...)`, and the deferred `finalize` call is given `time.Since(start)` at the moment it actually runs (computed inside the `defer func() { ... }()` closure, so it reflects the real elapsed time up to that instant, not the time `defer` was registered). This measures the gateway's full request boundary — auth, rate-limit, budget, cache lookup, router/upstream call, guardrails — not narrowly "just the upstream HTTP call." That's a deliberate broadening of the strict GenAI-spec framing (which is scoped to the client-to-model call itself), chosen because it's the same boundary every other per-request signal in this codebase (the span itself, `GatewayDecisionEvent`, the structured log line) already measures — a second, narrower duration measured only around `callDeployment` would be a second, inconsistent notion of "how long did this take" for no offsetting benefit yet.

`gen_ai.client.operation.duration` is recorded **unconditionally** on every call to `RecordChatCompletionMetrics` — success, cache hit, or rejection — mirroring `finalize`'s own "ALWAYS runs, even on error/cancel" framing. `error.type` (the spec's conditionally-required-on-failure attribute) is attached only when `ChatCompletionResult.ErrorType != ""`. `finalize` computes that value via a new `errorTypeFor(outcome)` helper that lowercases and strips the `OUTCOME_` prefix from `outcomeFor(err)`'s own existing, already-shipped classification (e.g. `ErrRateLimited` → `"rate_limited"`) — reusing that single classification for both `GatewayDecisionEvent.Outcome` and the GenAI `error.type` attribute, rather than maintaining two independent error taxonomies that could drift apart.

### Token usage: gated on `billable`, not `CacheHit` — a histogram-specific double-counting hazard `RecordChatCompletionResult`'s span attributes don't have

`gen_ai.client.token.usage` is recorded **only when `ChatCompletionResult.Billable`** — the exact same `billable` parameter `docs/rfcs/2026-09-05-gateway-cost-double-counting.md` already threads through `finalize` to gate `budget.Record` and `limiter.RecordTokens`, for the identical reason. This is a real, considered design decision, not a mechanical copy of an existing gate: `RecordChatCompletionResult`'s span attributes (`AttrGenAIUsageInputTokens`/`OutputTokens`, `AttrKelvranCostUSD`) are deliberately set on *every* request that has a known token count, including cache hits — that's a single, per-request attribute, and reporting "what this would have cost" on a cache hit is explicitly useful (per `CostUSD`'s own doc comment, e.g. for a cache-savings dashboard). A histogram is different: it *accumulates* across many requests for aggregate throughput queries. If every subsequent cache hit for a popular prompt re-emitted the original call's token count into `gen_ai.client.token.usage`, a "total tokens processed" query would be inflated by however many times that entry was served from cache — the same class of bug the cost-double-counting RFC already fixed for budget tracking, just manifesting in a histogram instead of a running balance. Gating on `billable` (true only for a genuine, unshared upstream call this specific request itself paid for — false for every cache hit and every coalesced singleflight follower) closes it the same way.

`gen_ai.token.type` (`"input"`/`"output"`) is a new exported constant pair (`telemetry.GenAITokenTypeInput`/`GenAITokenTypeOutput`), and each token-type data point is only recorded when its own count is `> 0` — mirroring `RecordChatCompletionResult`'s existing `AttrGenAIUsageInputTokens`/`OutputTokens` gating exactly, so the two signals never disagree about what counts as "known."

### Instrument construction and shared attributes follow the existing counter pattern exactly

`tokenUsageHistogram`/`operationDurationHistogram` are built via a new `mustFloat64Histogram` helper, the direct sibling of the existing `mustInt64Counter` — same package-init-time construction, same panic-on-construction-error posture (the instrument name is a fixed, compile-time-known constant; a construction failure can only be a real programming mistake). Both instruments are obtained from the same package-level `meter` var `rateLimitFailOpenCounter`/`cacheL3GateOutcomeCounter` already use, following `otel.Meter`'s documented re-delegation guarantee this codebase already relies on. Shared attributes (`gen_ai.operation.name` = `"chat"`, `gen_ai.provider.name` via the existing `genAIProviderName` remapping helper, `gen_ai.request.model`, `gen_ai.response.model`, `error.type`) are built once per `RecordChatCompletionMetrics` call and reused across both histograms — a fresh copy is taken before appending the per-token-type attribute so the two `tokenUsageHistogram.Record` calls never share (and therefore never risk aliasing) the same backing attribute slice.

## Alternatives considered

**A narrower duration measured only around the upstream call, matching the GenAI spec's strict scope** — rejected: would require a second timer at `callDeployment`'s own call sites (both the buffered and streaming paths, plus the fallback-retry branch), a second, inconsistent notion of "operation duration" alongside the span/event/log line's existing full-request-boundary framing, for a distinction this codebase doesn't yet have a concrete consumer asking for.

**Gating token-usage on `CacheHit` instead of `Billable`** — rejected: `CacheHit` is false for a coalesced singleflight follower (`docs/rfcs/2026-09-05-gateway-cost-double-counting.md`'s other double-counting case), which would still incorrectly replay a real call's token count into the histogram a second time. `Billable` is the correct, already-proven-sufficient gate for this exact class of bug.

**Depending on `go.opentelemetry.io/otel/semconv`'s GenAI module for the instrument name strings** — rejected, matching `docs/rfcs/2026-09-02-otel-tracing-agent-run-id.md`'s own prior decision for the trace attributes: that module's Go API surface tracks the still-Development spec and changes between SDK versions; two more hardcoded string constants cost nothing extra and avoid a second reason to bump the OTel SDK version later.

## Verification

`go build ./... && go vet ./...`, `golangci-lint run ./...` → `0 issues`, `go run github.com/fe3dback/go-arch-lint@v1.18.0 check` → clean, `go mod tidy` → empty diff (no new dependency; the OTel Metrics SDK packages were already direct dependencies as of the fail-open-metric RFC). `go test ./... -race`: every package `ok` except the two already-documented, environmental rootless-Docker failures (`cmd/gateway`'s `TestIntegrationTwoGatewayInstancesShareOneRedisRateLimit`, and `internal/ratelimit/redislimiter`'s own `TestMain` panic) — confirmed unrelated to this change; neither package is touched by this RFC.

`internal/telemetry/result_test.go`'s existing `TestRecordCacheL3GateOutcomeIncrementsPerGateAndOutcome` was extended, in place, to also exercise `RecordChatCompletionMetrics` within its own single `otel.SetMeterProvider`-swap window, rather than adding a second, independent swap-based test function. This was not a stylistic choice: this package's global meter delegates to a real `MeterProvider` exactly once per test binary (`go.opentelemetry.io/otel/internal/global`'s `delegateMeterOnce`, confirmed by reading the SDK source and reproducing empirically with a throwaway experiment) — a second test function swapping `otel.SetMeterProvider` for a *different* instrument in the same package's test binary silently observes nothing, because the delegation had already resolved to the first swap's provider. This is the exact constraint `TestRecordCacheL3GateOutcomeIncrementsPerGateAndOutcome`'s own pre-existing doc comment already documented for the `dataplane`/`telemetry` package split; extending its one already-claimed swap window is the only correct way to add a second global-instrument proof now that both packages that could plausibly own this test (`telemetry`, `dataplane`) had already spent their one delegation on a prior RFC's own test.

New assertions cover three scenarios sharing that one swap: a billable success (both histograms populated: `gen_ai.client.operation.duration` with no `error.type`, `gen_ai.client.token.usage` with both `input`/`output` data points at the correct values), a non-billable cache-hit/coalesced-follower replay (duration still recorded — every operation has one — but token usage is proven absent even though the same non-zero token counts were passed in, the load-bearing double-counting-avoidance proof), and a failure (duration recorded with `error.type = "rate_limited"`, token usage absent). Sanity-checked by temporarily replacing the `billable` gate (`if !r.Billable { return }`) with `if false { return }`: the cache-hit scenario's two "must be suppressed" assertions failed with the exact expected messages ("non-billable cache-hit scenario recorded an input/output token.usage data point — must be suppressed"), then reverted with zero diff remaining.
