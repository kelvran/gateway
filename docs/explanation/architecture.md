# Kelvran architecture: one process, one pipeline, one contract

This page explains why the Kelvran gateway is shaped the way it is: one Go process with a linear per-request pipeline, a cache that is a package rather than a service, a slow control plane kept apart from a fast data plane, and state that stays in memory unless an operator opts a subsystem into durability. It is for operators deciding how to run the gateway and for contributors deciding where a change belongs. It gives reasoning and trade-offs; the facts live in the reference pages linked throughout, and the package-by-package internals live in [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md).

## Two deployables, one shared surface

Kelvran is one repository with two deployables. `gateway/` is a single static Go binary that contains the proxy, the router and the embedded cache. `evals/` is a Python service that scores rollouts offline and samples production telemetry. The two are versioned independently; the current releases are gateway/v0.17.0 and evals/v0.10.1. The only thing they share is `api/`: versioned protobuf for the `gatewayevents` decision event, generated into both languages with `buf`, with `buf breaking` run in CI so that an incompatible schema change fails the build instead of drifting. There is no shared database and no shared library, and `evals` is never in the request path.

The deployable count is forced, not chosen: Go and Python cannot share a runtime. The repository count is the choice. [ADR 0001](../decisions/0001-monorepo-two-deployables.md) weighs the alternatives: a single deployable is impossible, and separate repositories put the one artifact that must be versioned atomically across the language boundary, the contract, in the place most likely to drift. [ADR 0003](../decisions/0003-go-python-split.md) explains the language split itself. The gateway is an I/O-bound proxy holding many concurrent streams, which rewards goroutines and a mature concurrent GC. Evals is a statistics and LLM-judge workload whose ecosystem is Python. Forcing one language would trade a real mismatch for cosmetic uniformity. A narrow Rust FFI island inside the cache remains a permitted later refinement, but only behind a stable interface, only on profiled evidence, and never for auth, routing or spend logic.

Each side polices its own import graph. The Go side uses `go-arch-lint` (`gateway/.go-arch-lint.yml`, in CI since 2026-09-05). The Python side uses `import-linter` (`evals/.importlinter`, one layers contract and two independence contracts). Both stop at `api/`; neither side imports the other's source.

## One process, two planes

Inside the binary, `internal/gateway/controlplane` and `internal/gateway/dataplane` are separate packages because they change at different rates. The control plane is "slow and smart": today it is static YAML parsing and validation, and its only exported function is `Load`. The data plane is "dumb and fast": accept, filter, forward, on every request. Keeping them apart means a change to the config shape never touches the hot path, and the hot path never needs to know how a value was derived. The hot-reload mechanisms that do exist reload credentials and admin-mutable state, never certificates: `dataplane.Pipeline.RunCredentialReloadLoop` re-reads `*_file` deployment credentials; the Bedrock Guardrails and EmbedSim detectors run their own `RunCredentialReloadLoop` over their `*_file` fields (`internal/guardrail/bedrockguard`, `internal/guardrail/embedsim`, started from `cmd/gateway` on the same `credential_reload.interval_seconds`); and the admin API mutates virtual keys and deployment weights, which the config-propagation subscriber replays on other replicas. There is no certificate rotation in the process: deployment client certificates and the admin mTLS material are loaded once at startup.

The client-facing surface is deliberately small: `POST /v1/chat/completions`, `POST /v1/embeddings`, `GET /v1/models`, `GET /healthz` and `GET /readyz`, on one `net/http` mux served by plain `ListenAndServe` with a 10 s read-header timeout. The client-facing listener speaks HTTP/1.1 only and terminates no TLS: whatever a client sees as HTTP/2 or TLS comes from an ingress or load balancer in front of it, and `deploy/k8s/base/` ships no `Ingress` manifest. The one place the process does terminate TLS is the admin listener when `admin.mtls` is configured (`ListenAndServeTLS` with `RequireAndVerifyClientCert`, on which Go's `net/http` also negotiates HTTP/2 over ALPN by default); see the next paragraph. `GET /v1/models` is on main since 2026-10-08, not in gateway/v0.17.0. The routes and bodies are in the [data-plane API reference](../reference/data-plane-api.md).

The admin API is a second `*http.Server` on its own listener, and it does not exist unless `admin.token_env` is set. When it is, it binds `127.0.0.1:8081` by default and authenticates with four static credential tiers (Admin, Viewer, CostViewer, Operator) that never delegate to the virtual-key verifier. A separate port rather than a path prefix is what makes "no admin surface" the default instead of a firewall rule. `GET /admin/config` can return the whole config verbatim for a different reason: `Config` never holds a raw secret. The reasoning is in the [admin API RFC](../rfcs/2026-09-05-gateway-admin-api.md); operation is in [Admin API and RBAC](../how-to/admin-api-rbac.md) and the [admin API reference](../reference/admin-api.md).

## The pipeline is linear on purpose

Every buffered chat completion walks the same stages in the same order, in one function. In code the order is: bearer verification, source-IP allowlist, model allowlist, idempotency claim, prompt resolution, rate-limit reservation (RPM and TPM), per-key concurrency acquire, budget reservation, L1 and L2 key derivation and lookup, L3-lite lookup, then the miss path. A deferred `finalize` always runs, even on error or cancel, because a partial generation still consumed billable tokens. The lifecycle diagram in [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md) is a sketch of this flow and does not show the idempotency claim, the per-key concurrency acquire or the pre-upstream budget reservation (it shows budget only as the mid-stream top-up and the `finalize` record); the order above is the code's.

The order is a cost gradient. Checks that need only the request and the key come first, so an unauthenticated, disallowed or exhausted key is rejected before anything expensive runs. Cache lookup sits before routing so that a hit never touches an upstream. Rate limit and budget are reservations taken before the upstream call and settled afterwards in `finalize`, so concurrent requests on one key compete for capacity before any of them spends it ([TOCTOU fix RFC](../rfcs/2026-09-08-gateway-budget-ratelimit-toctou-fix.md)).

The miss path is where money is spent, so it is deduplicated. `runMissPath` runs under `golang.org/x/sync/singleflight` keyed on the L1 exact-match key: N concurrent byte-identical requests produce one guardrail pre-call, one deployment pick, one upstream call, one guardrail post-call and one write-back to L1, L2 and L3. Coalescing on L1 rather than L2 is deliberate. Two merely normalized-equivalent requests are not coalesced, because serving one execution into two L1 keys is a separate design question. The accepted trade-off is that the leader's context governs the shared call; if the leader cancels, the followers fail too. Followers are also non-billable, which is how one upstream call is never charged twice ([cost double-counting RFC](../rfcs/2026-09-05-gateway-cost-double-counting.md)). Coalescing is in-process only; a distributed version is named as future work in the [stampede-protection RFC](../rfcs/2026-09-05-gateway-cache-stampede-protection.md).

Inside the miss path the post-call guardrail runs before cache write-back, so a blocked response is never cached. Routing is a sticky or weighted-round-robin pick that skips deployments the health prober has marked unhealthy, then an eligibility reroute (`rerouteToCapableDeploymentIfNeeded`) that walks the same model's pool for a deployment that can honour `response_format` and sits inside the key's `allowed_regions`, then an error-classified fallback chain if the deployment configures one ([weighted routing](../rfcs/2026-09-04-weighted-routing.md), [health probing](../rfcs/2026-09-07-gateway-active-health-probing.md), [fallback chains](../rfcs/2026-09-07-gateway-error-classified-fallback-chains.md)). Configuring these is covered in [Routing and failover](../how-to/routing-and-failover.md).

Two routes bend the rule. Streaming runs the same pre-upstream stages in the same order, but its post-call guardrail is audit-only: every chunk is already flushed before a complete response exists to check, so a Block-tier finding is logged at elevated severity but cannot withhold content already delivered. The streaming path also has no singleflight coalescing. `POST /v1/embeddings` is its own, narrower function against its own canonical schema. It reuses authentication (bearer, source-IP and model allowlists), an RPM-only rate-limit check (no TPM reservation, because there is no token estimate for embedding input), budget reservation and the guardrail pre-call, but does not thread through the cache, idempotency, the per-key concurrency cap, fallback chains or telemetry spans. That is a scope decision recorded in its doc comment, not an omission. See [Streaming](../how-to/streaming.md).

## Why the cache is a package, not a service

A cache's natural shape as a standalone service (terminate auth, resolve the tenant, route upstream) is most of a gateway. Running it separately would mean two auth and routing surfaces that drift. [ADR 0002](../decisions/0002-cache-embedded-in-gateway.md) therefore makes the cache a Go package behind a narrow interface. For caching the data plane depends on the `cache` package alone, and on it for two interfaces plus stateless helpers: `cache.Cache` (`Get`, `Put`, `Delete`, each taking a tenant ID) for L1 and L2, `cache.LexicalCache` (`Search`, `Put`) for L3, whose similarity search returns zero or many scored candidates rather than one hit, and the pure `Key`, `NormalizedKey`, `ScopeKey`, `Shingles` and `MinHashSignature` functions that build the lookup keys and L3 signatures. Concrete implementations are constructed only in `cmd/gateway`. The `cache` package imports nothing else in the project: it is keyed on a normalized request, not on which provider served it, so it can never depend on `adapter` or `dataplane`. [THREAT_MODEL.md](../../THREAT_MODEL.md) still treats Gateway to Cache as a trust boundary, because the call crosses tenant-isolation logic even without a network hop.

The extraction seam is real but dormant. `grpcserver` and `grpcclient` satisfy the same interface and return a package-level "not implemented" sentinel error from every method. No cache `.proto` exists; the only protobuf in the repository is `api/gatewayevents/v1`. If one of the ADR's triggers fires (a second caller that bypasses the gateway, a measured resource divergence, a team blocked by release cadence, a profiled CPU bottleneck), extraction means writing the wire contract and swapping the adapter in `cmd/gateway/main.go`, not rewriting the pipeline. "It would be cleaner" is explicitly not a trigger.

Three layers, three jobs. L1 is an exact SHA-256 match. L2 is a normalized match with a deliberately narrow three-operation allowlist, because agent traffic can include pasted code where aggressive normalization risks a wrong answer. L3 is lexical near-duplicate matching (MinHash over word shingles behind a Jaccard floor), never embedding-based semantic similarity, and every candidate is hard-gated on entities, numbers, dates, negation and other fingerprints before it is served. L3 keeps a separate bucket per tenant so isolation is structural rather than a filter applied during search. Why the gates exist, and what they do not catch, is the subject of [The cache gate](./cache-gate.md); the operator view is [Caching](../how-to/caching.md); default TTLs and bounds are in the [configuration reference](../reference/config.md). `Delete` has one live caller, `POST /admin/cache/erase`, which touches L1 and L2 only; L3 has no delete and expires by TTL.

Not available today: a Redis-backed or otherwise shared response cache. Every layer is an in-process instance per gateway. The [Redis-backed cache RFC](../rfcs/2026-09-11-gateway-redis-backed-cache-design.md) is design-only, deferred until its named trigger (organic multi-replica production traffic) fires.

## Where state lives

The default is that nothing survives a restart and nothing is shared between replicas. That follows from shipping one static binary with no mandatory external service, and it is why the gateway runs from a single config file under Docker Compose or systemd. Durability and sharing are opt-in per subsystem, so an operator pays for exactly the state that matters to them. Virtual keys created through the admin API live in memory, or in bbolt via `admin.persist_path`, or in Redis via `admin.redis_addr`; Redis wins if both are set. Budget spend follows the same pattern with `budget.persist_path` and `budget.redis_addr`, where bbolt is single-instance durability (hydrated once at startup, then every change is written through to the file, so a restart resumes where it left off) and Redis is an atomic cross-replica cap-check-and-debit. Prompt versions persist to bbolt via `prompt.persist_path`. Rate limiting is per instance unless `rate_limit.redis_addr` points at a shared Redis limiter (a Lua token bucket for RPM, Lua GCRA for TPM). Admin mutations reach other replicas only when `config_propagation.redis_addr` is set; that channel broadcasts HMAC-signed events over Redis pub/sub and persists nothing, so it is paired with a Redis identity store for a live, shared virtual-key surface. Idempotency records and the response cache are in-process only; no Redis implementation exists for either.

Deployment weight changes made through the admin API are always in memory and revert to the config file on restart. Corruption of any bbolt store is governed by one knob, `admin.on_corrupt_store`, default `fail`. `reset` moves the file aside and recreates it, but only for bbolt's three corruption sentinels (`ErrInvalid`, `ErrVersionMismatch`, `ErrChecksum`), never for a permissions or disk-full error. What each dependency's failure does to traffic is tabulated in [FAILURE-MODES.md](../operations/FAILURE-MODES.md); copying the bbolt files out is in [Backup and restore](../how-to/backup-and-restore.md); the keys themselves are in the [configuration reference](../reference/config.md).

Not available today: a Postgres control-plane store or a ClickHouse event sink. Both are named as targets in [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md); neither dependency is in `gateway/go.mod`. The observability path that exists is OTLP export to a collector, described in [TELEMETRY.md](../operations/TELEMETRY.md).

## Credentials are names, not values

`Config` never contains a secret. A deployment names an environment variable (`api_key_env`, `access_key_id_env`, `secret_access_key_env`, `session_token_env`) or a file (`api_key_file` and the other `*_file` fields); the value is resolved at startup and, for files, re-read by `RunCredentialReloadLoop`. The same rule is what makes `GET /admin/config` safe to return wholesale and keeps secrets out of logs. Admin tokens follow it too: `admin.token_env` names a variable such as `KELVRAN_ADMIN_TOKEN`. The admin mTLS material is loaded once at startup and never re-read. See [Provider credentials](../how-to/provider-credentials.md) and [Rotate credentials](../how-to/rotate-credentials.md).

## Enforced dependency direction

Go's `internal/` visibility only stops code outside `gateway/` from importing these packages; inside the module any package may import any other. `go-arch-lint` is what enforces the direction between them, checking every package's imports (and, with config v3's default `deepScan`, dependencies injected through function parameters) against the declared component graph, which is why it has run in CI since 2026-09-05. Most packages are pure leaves that may import nothing project-internal: `cache`, `adapter`, `identity`, `budget/redisbudget`, `ratelimit`, `router`, `costaccounting`, `guardrail`, `telemetry`, `controlplane`, `backup`, `idempotency`, `configpropagation`, `alerting`, `anomaly`, `credentialstate`, `bench` and `benchupstream`. `dataplane` is the one package allowed to import nearly everything, because it is where the stages are composed. `admin` is a top-level consumer that may import `adapter`, `admin/auditstore`, `controlplane`, `dataplane`, `identity`, `prompt` and `ratelimit`; no `internal/` package imports `admin`, only `cmd/gateway` does.

Several of those rules encode a design choice. `budget` and `ratelimit` do not import `identity`: they track by key-ID string, so each is testable without the other. `router` has its own `Deployment` type rather than importing the data plane's. The Redis implementations (`ratelimit/redislimiter`, `budget/redisbudget`) satisfy an interface that lives in the consumer package, so `ratelimit` and `budget` themselves never import `go-redis`; the Redis packages and `cmd/gateway`, which wires every backend, do, so the one binary always links it whether or not Redis is configured, and configuration rather than a build tag decides which implementation is constructed. The package tree in [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md) is the prose; `gateway/.go-arch-lint.yml` is the enforced list.

## What runs beside the pipeline

One `signal.NotifyContext` on SIGTERM and SIGINT governs the health-probe loop, the credential-reload loop, the config-propagation subscriber and both HTTP servers. Health probing is off unless `health_probe.interval_seconds` is set; the key has no default, and with it omitted `/readyz` reports ready without having probed anything. With probing off, a failing deployment is handled only at request time, by a fallback chain or the same-model fallback.

A second binary, `cmd/kelvran-bench`, drives open-loop load through a gateway and serves a deterministic mock upstream; its packages `internal/bench` and `internal/benchupstream` are pure leaves. It is on main since 2026-10-08, not in gateway/v0.17.0. Methodology and results are in [BENCHMARKS.md](../operations/BENCHMARKS.md).

## What is real in the stack, and what is only a target

The Go toolchain floor is `go 1.26.8`. The direct dependencies that ship in the binary are the standard library's `net/http`, `go-redis/v9`, `bbolt`, the OpenTelemetry SDK with OTLP and stdout exporters, `shopspring/decimal` for cost arithmetic, `automemlimit` for a cgroup-aware `GOMEMLIMIT`, `aws-sdk-go-v2` for Bedrock SigV4 and event streams, `chromem-go` for the embedding-similarity guardrail, `golang.org/x/sync` for singleflight, `golang.org/x/text` for NFC normalization and `google.golang.org/protobuf` for the contract. Upstream calls and the SSE relay are hand-rolled over `net/http`; nothing imports `httputil.ReverseProxy`. The Tech Stack table in [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md) names Postgres and ClickHouse as targets; they are not code.

## Not available today

- Hierarchical identity scope (org, team, user, key, session) and "teams". `identity.VirtualKey` is one flat per-key record, and the rate limiter sees only the key and the model. Deferred in [DECISIONS.md](../../DECISIONS.md) for lack of a demand signal.
- A Postgres control-plane store or a ClickHouse sink.
- A shared or Redis-backed response cache, and distributed singleflight.
- A cache `.proto` or gRPC wire contract for the extraction seam.
- MCP or A2A brokering; no `internal/mcp` package exists. See [MCP and A2A status](./mcp-a2a-status.md).
- A traffic-derived statistical circuit breaker or fleet-wide retry budget; routing health comes from synthetic probes and explicit fallback chains.
- Per-session or per-`agent_run_id` cost roll-up; `finalize` is per request, and aggregation happens downstream from spans or `gatewayevents`.
- An OTel protobuf schema under `api/` (the `otel` placeholder that `api/README.md` names); the gateway exports OTLP directly, and a second schema would duplicate that wire format.
- HTTP/2 or TLS termination on the client-facing listener (`/v1/*`, `/healthz`, `/readyz`); only the admin listener can terminate TLS, via `admin.mtls`.
