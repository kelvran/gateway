# MCP and A2A brokering: what exists, what is designed, and why it waits

This page explains the status of Model Context Protocol (MCP) and Agent-to-Agent (A2A) tool brokering in Kelvran: nothing is built, two design-only RFCs exist, and the work is gated on named triggers that have not fired. It is for operators and evaluators who meet the phrase "MCP/A2A brokering" in [PRD.md](../../PRD.md), [README.md](../../README.md) or the threat model and need to know what it means for a deployment today. For what the gateway does serve, see [data-plane-api.md](../reference/data-plane-api.md) and [compatibility.md](../reference/compatibility.md).

## The short version

Kelvran ships no MCP server, no MCP client, no A2A agent registry and no tool execution of any kind, as of gateway/v0.17.0 and `main` on 2026-10-08. The package that [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md) lists as `/internal/mcp` does not exist on disk. The only occurrences of `mcp` in any case in Go source are three comments: the package comment of `gateway/internal/gateway/dataplane/dataplane.go` and the file comment of `gateway/cmd/gateway/main.go` say it is not built, and a comment in `gateway/cmd/gateway/models_handler.go` names this page. [gateway/config.example.yaml](../../gateway/config.example.yaml) has no `mcp` section, and the data-plane mux in `gateway/cmd/gateway/main.go` registers no `/mcp` route.

Not available today:

- An inbound MCP server: a `gateway/internal/mcp` package, a `POST /mcp` route, an `mcp.enabled` flag. These names come from the inbound RFC and are illustrative. None is a real config key or route.
- An outbound broker: an `OutboundCredential` identity object, per-MCP-server credential registration, on-behalf-of token exchange. These names come from the outbound RFC's shape sketch.
- A2A agent-card registration or operator-registered agent URLs.
- Session or context isolation per concurrent tool call. No tool-call surface exists to isolate.
- Per-tool short-lived scoped credentials.
- Any integration test against a real MCP client.
- An Anthropic Messages-style `POST /v1/messages` ingress. This is not MCP/A2A work: it is item 11 of the 2026-10-08 round-4 discoverability plan (`docs/upgrade-research/kelvran-deep-research-round4-discoverability-2026-10-08.md`), RFC first (the RFC is `docs/rfcs/2026-10-09-gateway-anthropic-messages-ingress.md`, status proposed, decision pending), and the `models_handler.go` comment above points here only because it names this page alongside [compatibility.md](../reference/compatibility.md), which lists what the gateway does accept.

MCP/A2A brokering is not scheduled work. [PRD.md](../../PRD.md) places MCP/A2A tool brokering "explicitly out of scope for v1", tracked as a future `docs/rfcs/` candidate, and makes no v2 promise. [README.md](../../README.md) lists it under "Not built, by recorded decision".

## Reading the other documents correctly

Because the subsystem is named in several places, three documents need a reading note.

[THREAT_MODEL.md](../../THREAT_MODEL.md) carries MCP/A2A threats in its Gateway STRIDE rows (OAuth token-passthrough abuse under Spoofing, guardrail bypass on non-tool operations under Elevation of Privilege), in a Cross-Component table of its own (session leakage across tool calls, auth-passthrough through self-reported agent cards), and in the OWASP LLM03:2026 Excessive Agency row. Every one of these is marked moot or "intended design, not built". The Cross-Component table's preamble says its mitigation cells describe a future subsystem. Read them as design inputs, not as controls a deployment has.

[SECURITY.md](../../SECURITY.md) says the subsystem has no shipped code and enters the vulnerability-report scope when it ships. A report against MCP/A2A behaviour has nothing to target today.

[gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md) keeps a one-paragraph "MCP/A2A Subsystem" section written as intent. The same document's package tree marks `/internal/mcp` NOT BUILT, and the section itself now says so.

## What "brokering" means here

The design intent has been stable since 2026-09-07. It names two directions. Inbound: expose Kelvran's own capabilities as MCP tools so an external MCP client can call into Kelvran. Outbound: broker tool calls from a Kelvran-routed request to a downstream MCP server or A2A agent on the caller's behalf. In both directions the intent is one gateway, not two: the same virtual-key identity, the same cost accounting, the same budget and audit objects, from the same config file. A second gateway with a second config source is the thing the design refuses.

That refusal is the main architectural decision on record, and it is why the two RFCs below are small. Almost everything an MCP surface needs already exists for `/v1/chat/completions`.

## Why it stayed out of v1

The decision rests on four findings from research passes between 2026-09-07 and 2026-09-25 (`docs/upgrade-research/gateway-mcp-a2a-brokering-2026-09-07.md`, `docs/upgrade-research/gateway-mcp-a2a-brokering-2026-09-11.md`, `docs/upgrade-research/mcp-a2a-brokering-tier1-2026-09-20.md`, `docs/upgrade-research/mcp-a2a-ecosystem-maturity-check-2026-09-24.md`, `docs/upgrade-research/mcp-gateway-demand-signal-recheck-2026-09-25.md`). The external facts in them were gathered by those sessions and are cited here as research findings, not as facts about Kelvran.

Brokering is not a differentiator. The 2026-09-07 pass recorded that Kong AI Gateway, Envoy AI Gateway and LiteLLM already route MCP traffic through their own auth, rate-limit and observability stacks. Kelvran's "share the identity and cost objects" framing is the same shape those products chose. Building it would be catching up, not leading. The one dimension the pass found none of them cover is dollar-cost attribution of tool calls, a dimension Kelvran's cost accounting already covers for chat completions, so the intent stands even though the urgency does not. That coverage stops at tokens: `costaccounting.Calculator.Calculate(model, usage)` prices token counts, and a `tools/call` round trip has none to price. The 2026-09-07 pass named this undesigned cost unit as its first reason outbound brokering is premature (building the mechanics first would ship a fourth MCP proxy without the accountability story), and noted that the inbound slice avoids the problem because a completion invoked by tool is still token-priced.

The spec is still moving. The 2026-07-28 MCP revision was a self-described breaking re-architecture: stateless, no `initialize` handshake, no session header. The 2026-09-20 pass found the version string unchanged but the deprecation registry active (SEP-2577, merged 2026-09-15, deprecates Roots, Sampling and Logging; SEP-2640 adds a Skills extension that is orthogonal to brokering). The OAuth 2.1 draft that MCP's authorization model layers on is still an IETF Internet-Draft. Statelessness is good news for Kelvran, whose data plane is already stateless per request, but the spec is not yet a settled target to write a client or server against.

There is no Kelvran-specific demand, and there cannot be yet. The 2026-09-25 recheck found dated GitHub issues asking for gateway-layer MCP brokering on LiteLLM (#7934) and Envoy AI Gateway (#589), both since shipped, and a production friction report against LiteLLM's A2A gateway (#21409). It also found that agent-framework communities (CrewAI, OpenAI Agents SDK, LangGraph) keep MCP in-framework and never ask for it to move to a proxy. So the demand class is real but narrow. Kelvran has no external users, so a Kelvran-specific signal is structurally unobservable today. The RFCs name that as the gating question rather than pretending to answer it.

Designing now is cheap; guessing later is not. Both RFCs exist because the research surfaced a specific wrong shortcut (reusing a virtual key as the downstream credential) and a specific right first slice (one inbound tool). Writing those down while the evidence was fresh costs a document. Discovering them after `internal/mcp` has call sites would cost a rewrite. This mirrors the precedent set by [the Redis-backed cache RFC](../rfcs/2026-09-11-gateway-redis-backed-cache-design.md): design in full, defer the when.

## The outbound RFC: credential delegation

[2026-09-11-gateway-mcp-outbound-credential-design.md](../rfcs/2026-09-11-gateway-mcp-outbound-credential-design.md) scopes the second credential leg that brokering introduces. Today a caller authenticates to Kelvran with a `VirtualKey`; the only other credentials in play are the provider keys `DeploymentConfig` holds for Kelvran's own upstream calls, and neither is delegated to a third party on the caller's behalf. Once Kelvran itself calls a downstream MCP server, that server has its own credential requirement. The RFC's one firm rule is that the caller's `VirtualKey` must never be the credential Kelvran presents downstream. The 2026-09-11 research found that neither LiteLLM (five `auth_type` patterns including RFC 8693 on-behalf-of exchange) nor Portkey (an injected per-server credential) reuses its inbound key outbound, and the 2026-09-24 pass added that the MCP spec's own MUST NOT rule against token passthrough is unchanged across the 2025-06-18, 2025-11-25 and 2026-07-28 revisions. Kelvran's design is therefore not waiting on a rule change.

The RFC sketches, in shape only, an `OutboundCredential` object: registered by an operator per MCP server or A2A agent the way `Deployment`s are registered per provider, resolved by lookup from the already-authorized caller context, with credential material following the `*_env` environment-variable convention `DeploymentConfig` used for provider keys when the RFC was written (that config has since gained `*_file` siblings; see [config.md](../reference/config.md)). It leaves open whether Kelvran needs full on-behalf-of token exchange (which lets the downstream audit trail see the original caller) or Portkey's simpler injected credential, where registration lives in config, how rotation and revocation work, and whether one credential covers a whole server or scopes per tool. What cost unit a brokered tool call carries is a further open question, left so by the 2026-09-07 and 2026-09-11 research passes.

Rejected: reusing `VirtualKey` unchanged (no peer does it, and it leaks Kelvran-internal material toward a party with no relationship to Kelvran's callers); building the full token-exchange flow speculatively (premature while the spec churns and no first integration exists); and doing nothing (a real option, set aside only because recording the finding was cheap).

Two addenda sharpen the picture without changing the status. On 2026-09-24 the RFC recorded that AWS Bedrock AgentCore Gateway, Microsoft Foundry Agent Service and Cloudflare's `workers-oauth-provider` had all shipped per-hop on-behalf-of exchange (RFC 8693 or RFC 7523), to be cited as primary precedent when an implementation RFC is written. The same pass flagged two spec additions a multi-server broker must fold in: Mix-Up attack defences (RFC 9207 issuer binding; PKCE alone is not enough) and the shift from Dynamic Client Registration to Client ID Metadata Documents. On 2026-09-25 the RFC recorded the ecosystem demand evidence above.

## The inbound RFC: one tool, zero new identity

[2026-09-20-gateway-mcp-inbound-design.md](../rfcs/2026-09-20-gateway-mcp-inbound-design.md) scopes the smallest useful inbound surface. One tool, working name `chat_completion`, whose input mirrors `adapter.ChatRequest` and whose output is `adapter.ChatResponse`. Transport is MCP Streamable HTTP, mounted as one more route on the existing data-plane mux, not a new listener or a stdio process. Authentication is the bearer token every other caller already presents, checked by the same `identity.Verifier` and resolving to the same `VirtualKey`. There is deliberately no OAuth 2.1 dependency: the spec recommends OAuth 2.1 for servers exposed to third-party clients, Kelvran's bearer model already is the access control for this surface, and the draft is unratified.

The design's load-bearing property is mechanical. A tool call becomes a call to `dataplane.Pipeline.HandleChatCompletion`, the same function the HTTP handler calls, so budget enforcement, rate limiting, cache lookup and write, guardrail scanning and audit apply without any new code path. Cost accounting is unchanged because a completion invoked by tool is still priced by `costaccounting.Calculator` from the same token usage. The new package would be a leaf, `gateway/internal/mcp`, shaped like `internal/admin` (takes the `*dataplane.Pipeline` plus an auth check and returns an `http.Handler`; the RFC sketches `mcp.NewInboundServer(pipeline, verifier) http.Handler`), but mounted by `cmd/gateway/main.go` as one route on the data-plane mux rather than on the admin server's separate listener, importing `dataplane`, `identity` and `adapter` and imported by none of them, with the boundary enforced by the same `go-arch-lint` check that covers every other package, once an `mcp` component and its `mayDependOn` list are added to `gateway/.go-arch-lint.yml`. It would be off unless an operator enables it. Trace context would cross the tool boundary via SEP-414's `_meta` keys rather than a bespoke mechanism, carrying the `agent_run_id` baggage [the OTel RFC](../rfcs/2026-09-02-otel-tracing-agent-run-id.md) already propagates.

Rejected: exposing admin capabilities as MCP tools now. Read-only spend and prompt lookups are plausible follow-ons, but every mutating admin route (key create, delete and rotate; weight changes; prompt create, delete, promote and rollback; cache erasure; backup; the opt-in pprof scrape) must stay on the HTTP Admin API: that surface gained its `Operator` risk tier the same day the inbound RFC was written ([2026-09-20-gateway-admin-rbac-risk-tiering.md](../rfcs/2026-09-20-gateway-admin-rbac-risk-tiering.md), implemented), and an MCP tool callable by any bearer token would reintroduce an untiered second path to the same destructive routes. Also rejected: reusing `OutboundCredential` for inbound auth (a category error; that object is Kelvran acting as a client), and coupling inbound to outbound (outbound has open credential questions inbound does not share).

Left open: the exact `inputSchema` translation, whether the first slice streams tool results, the flag's real name and default, whether read-only admin tools follow, and the demand signal.

## What an implementation would reuse

Both RFCs are short because the primitives exist and would be used unchanged: the bearer check `identity.Verifier` performs on every request, `Pipeline.HandleChatCompletion`, `costaccounting.Calculator`, the guardrail pre-call scan that already covers `role:"tool"` messages fed back from an earlier turn (regression test `TestHandleChatCompletionPreCallScansToolResultMessagesFedBackFromAnEarlierTurn` in `gateway/internal/gateway/dataplane/guardrail_test.go`), the per-key and per-deployment concurrency caps that bound agentic fan-out today, W3C Baggage tracing of `agent_run_id`, and the handler-registration shape of `internal/admin`. The 2026-09-20 pass checked this against the code and found the canonical schema and adapter registry need no redesign for either direction. Operator-facing descriptions of these pieces live in [config.md](../reference/config.md), [admin-api.md](../reference/admin-api.md) and [metrics-and-logs.md](../reference/metrics-and-logs.md); the request path is in [architecture.md](./architecture.md) and the trust boundaries in [security-model.md](./security-model.md).

## What would start the work

Outbound starts when two conditions hold together: the MCP spec stabilizes, and Kelvran has a first real MCP or A2A integration to build against. The 2026-09-11 research gives the stability test concrete form: either the 2026-07-28 revision's twelve-month deprecation window closes with no further structural change, or a mainstream Go SDK ships two consecutive spec-version bumps with no new removals or deprecations. Inbound starts on a real demand signal. The most recent recheck of these triggers is the 2026-09-25 addendum in the outbound RFC; neither fired.

Starting means an implementation RFC that moves the status line from "Design-only" to "Accepted, implemented", a new `gateway/internal/mcp` package with tests, an integration test against a real MCP client, and for outbound a new identity-object package. Until then, the two RFCs are the whole of the subsystem. [DECISIONS.md](../../DECISIONS.md) records the 2026-09-04 threat-model correction, the 2026-09-12 decision to ship the outbound RFC as design-only, the 2026-09-20 entry that shipped the inbound RFC, and the 2026-09-25 demand recheck.

## Using MCP-capable agents with Kelvran today

Nothing above stops an agent that uses MCP tools from routing its model calls through Kelvran. An agent framework resolves tools on its own side and talks to the model over an OpenAI-compatible endpoint. Point that endpoint at Kelvran and the tool definitions travel as `tools` on the chat-completion request, tool results come back as `role:"tool"` messages, and both are ordinary request content to the gateway: priced, budgeted, rate-limited and scanned by the guardrail pre-call. Kelvran never executes a tool, never holds a tool credential and never sees the MCP transport. That is the division of labour the design keeps until a trigger fires. See [configure-from-a-coding-agent.md](../how-to/configure-from-a-coding-agent.md) and [openai-python.md](../how-to/clients/openai-python.md).

## A related decision that is not a deferral

Kelvran will not build a cross-request agent memory store (the Zep or Mem0 pattern). [gateway/ARCHITECTURE.md](../../gateway/ARCHITECTURE.md) records this as a non-build verdict, not a deferred item: the gateway is stateless per request by design, and memory is a provider-native capability a client opts into on the provider's side. Kelvran does not forward provider memory primitives today either: `chatCompletionsHandler` decodes the body into `adapter.ChatRequest` and drops any field it does not define (OpenAI's `previous_response_id`, Anthropic's `context_management`), and no Responses or Conversations route exists ([compatibility.md](../reference/compatibility.md)). The 2026-09-22 research pass recorded that as a small, unaddressed pass-through gap, distinct from the memory-store non-build. Other decisions of this kind are collected in [design-decisions.md](./design-decisions.md).
