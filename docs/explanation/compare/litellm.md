# Kelvran vs LiteLLM

Kelvran is a self-hosted, OpenAI-compatible LLM gateway: one static Go binary that serves `POST /v1/chat/completions`, `POST /v1/embeddings` and (since `gateway/v0.18.0`) `GET /v1/models` in front of five provider adapters, with virtual keys and budgets, weighted routing with classified failover, a three-layer in-process response cache and OpenTelemetry export, plus a separate Python evals CLI. LiteLLM (BerriAI/litellm) is an open-source AI gateway and Python SDK that describes itself as "Rust core with Python SDK", exposes 100+ providers behind OpenAI-format and Anthropic-format endpoints, and sells an Enterprise licence key for the same image. Both are compared as of 2026-10-09. Every Kelvran cell links the reference page or file that backs it and reflects the repository at commit `0863cb09` (26 commits past `gateway/v0.17.0`, included in `gateway/v0.18.0`); where `gateway/v0.18.0` differs from `gateway/v0.17.0`, the cell says so. Facts about LiteLLM come from its own documentation and repository on that date; verify before relying on them. The source list is at the end of this page.

## TL;DR

- The one differentiator this page claims for Kelvran: the W3C `baggage` member `agent_run_id` is read from every chat request (never fabricated when absent) and written to the request's `chat <model>` span, to the `GatewayDecisionEvent` log record next to `cost_usd`, and to the per-key in-flight breakdown, while per-key budgets are enforced in-process from `config.yaml` with no database ([metrics and logs](../../reference/metrics-and-logs.md), [admin API](../../reference/admin-api.md), `gateway/internal/telemetry/telemetry.go` `AgentRunIDFromContext`). LiteLLM's nearest equivalents are per-session budgets keyed by its own `x-litellm-trace-id` header or `metadata.session_id`, with counters that expire after 1 hour by default (the docs do not say where they are stored) ([a2a_iteration_budgets](https://docs.litellm.ai/docs/a2a_iteration_budgets)), and `litellm_session_id` as a UI grouping ([ui_logs_sessions](https://docs.litellm.ai/docs/proxy/ui_logs_sessions)); whether a session id is a column in `LiteLLM_SpendLogs` is not established from primary sources on 2026-10-09.
- LiteLLM is the older, larger and more featureful product by every measure on this page: repository created 2023-07-27, 1,503 GitHub Releases, 60,411 stars, roughly 100 providers, Anthropic Messages and Responses endpoints, Helm charts, a Prometheus `/metrics` endpoint, teams, an admin UI. Kelvran's repository was created 2026-09-03, has 0 stars and one maintainer, five adapters and five routes.
- The caches are different objects. LiteLLM's semantic cache serves the closest match above a cosine-similarity threshold (example value 0.8) from Redis, Valkey or Qdrant and is shared across replicas; its own docs say it will replay stale responses on multi-turn or agentic traffic. Kelvran's L3 is lexical MinHash/Jaccard at or above 0.9 and every candidate must also pass entity, number, date, negation, freshness, model and policy-version equality gates; it is in-process, per replica, its similarity floor and gates have no configuration knob (only TTL, capacity and jitter are configurable) and it cannot be erased.
- Licensing differs in kind. Kelvran is Apache-2.0 for the whole repository with no paid tier. LiteLLM is MIT outside `enterprise/`, which is under the BerriAI Enterprise License; GitHub reports the repository's SPDX id as `NOASSERTION`; key rotation, model-specific budgets, organisations, SSO beyond 5 users, audit logs and tag budgets require the licence key.
- Both projects pin every GitHub Action to a commit SHA. Kelvran's image carries a keyless cosign signature, a CycloneDX SBOM attestation and SLSA Build Level 2 provenance; its release-asset signing pipeline ships since `gateway/v0.18.0`, and every Release before it carries zero assets. LiteLLM's image is signed with a long-lived cosign key pair and carries an SPDX SBOM attestation but no SLSA provenance; its release build and signing run in a separate repository not visible in the public tree.

## Choose Kelvran if …

- You want a static binary (plus its companion CLI) with no Postgres, no Python runtime and no admin UI, configured from one `config.yaml`, and you can run Redis only when you need more than one replica ([container image](../../reference/container-image.md), [configuration](../../reference/config.md)).
- Your traffic is agentic and you want a near-duplicate cache that refuses a hit on an entity, number, date, negation, freshness or model mismatch rather than on a similarity score alone ([the cache gate](../cache-gate.md)).
- You want `agent_run_id` carried by standard W3C baggage into the span and the decision event, so per-run cost roll-up is a query over your own logs ([metrics and logs](../../reference/metrics-and-logs.md)).
- One licence for everything matters more than feature count: Apache-2.0, no enterprise directory, no licence key ([LICENSE](../../../LICENSE), [NOTICE](../../../NOTICE)).
- Five providers (OpenAI, Anthropic, Gemini, Bedrock, OpenAI-compatible) and the chat and embeddings surface are enough, and you accept a pre-1.0 project with one maintainer, one live pilot and no published performance numbers ([compatibility](../../reference/compatibility.md), [VERSIONING.md](../../VERSIONING.md), [BENCHMARKS.md](../../operations/BENCHMARKS.md)).

## Choose LiteLLM if …

- You need the Anthropic Messages API (Claude Code, the `anthropic` SDK), the Responses API, images, audio, batches, rerank or `/a2a`. Kelvran registers none of these routes ([supported_endpoints](https://docs.litellm.ai/docs/supported_endpoints), [data-plane API](../../reference/data-plane-api.md)).
- You need providers beyond Kelvran's five, or Vertex AI, Azure, Sagemaker or Groq specifically ([README](https://github.com/BerriAI/litellm)).
- You need teams, team-member and end-user budgets, multiple concurrent budget windows on one key, or a fail-closed rate-limit mode when Redis is unreachable ([users](https://docs.litellm.ai/docs/proxy/users), [team_budgets](https://docs.litellm.ai/docs/proxy/team_budgets)). Kelvran has flat per-key budgets only and fails open on Redis error.
- You want a Helm chart, a Prometheus `/metrics` endpoint, an admin UI, a shared Redis response cache, per-request cache controls, or logging to Langfuse, Datadog, S3, Langsmith and the rest of its callback list ([deploy](https://docs.litellm.ai/docs/proxy/deploy), [prometheus](https://docs.litellm.ai/docs/proxy/prometheus), [logging](https://docs.litellm.ai/docs/proxy/logging)).
- You want a vendor with weekly stable releases, a published SOC 2 Type 2 claim, a 30-day enterprise trial and a community of 60,000-plus stargazers behind the project ([release_cycle](https://docs.litellm.ai/docs/proxy/release_cycle), [enterprise](https://www.litellm.ai/enterprise), [GitHub API](https://api.github.com/repos/BerriAI/litellm)).

## Cache semantics

| Aspect | Kelvran | LiteLLM |
|---|---|---|
| Layers and backends | Three in-process layers, always on with no off switch, empty after every restart: L1 exact, L2 normalised (trim, Unicode NFC, strip one trailing `.`/`!`/`?`), L3 lexical near-duplicate; no Redis or shared cache (design RFC only) ([caching](../../how-to/caching.md)) | Backends `redis` (incl. Valkey, ElastiCache, Memorystore), `redis-semantic`, `valkey-semantic`, `qdrant-semantic`, `s3`, `gcs`, `local`, `disk`; Redis is the default and the only one shared across workers and replicas; `local` is per worker process ([caching](https://docs.litellm.ai/docs/proxy/caching), [caching_redis](https://docs.litellm.ai/docs/proxy/caching_redis)) |
| Exact-match key | Virtual key, model, serialised messages, temperature, max_tokens, `guardrails.policy_version`, `response_format`, resolved prompt reference, end-user scope when enabled, `thinking_binding_mode`, and since `gateway/v0.18.0` tools + `tool_choice` ([caching](../../how-to/caching.md), [compatibility](../../reference/compatibility.md)) | Hash of the whole request; by default only standard OpenAI parameters are included, provider-specific params opt in ([caching](https://docs.litellm.ai/docs/proxy/caching), [caching_controls](https://docs.litellm.ai/docs/proxy/caching_controls)); whether exact-match entries are scoped per virtual key is not established from primary sources on 2026-10-09 |
| Semantic or near-duplicate matching | Lexical MinHash/Jaccard: 3-word shingles, 128-value signature, top-5 candidates, similarity floor 0.9, 24-hour staleness budget; all Go constants, no config knob; not embedding-based ([the cache gate](../cache-gate.md), [caching](../../how-to/caching.md)) | Embedding-based on Qdrant, Valkey or Redis; embeds the entire `messages` array including the system prompt; operator-configured embedding model; serves the closest match above `similarity_threshold` (example 0.8; the default when omitted is not established) ([caching_semantic](https://docs.litellm.ai/docs/proxy/caching_semantic), [caching_settings](https://docs.litellm.ai/docs/proxy/caching_settings)) |
| What gates a near-duplicate hit | Volatile-query bypass (`weather\|price\|stock\|score\|today\|current\|currently\|now\|latest` in any user message); entity, number and date fingerprint set equality; negation fingerprint equality; age <= 24 h, similarity >= 0.9 and same model id; exact equality on policy version, `response_format`, prompt, reasoning-blocks, thinking mode and (since `gateway/v0.18.0`) tools fingerprints; any rejection falls through to upstream ([the cache gate](../cache-gate.md)) | Tenant scope (virtual key by default, optionally `end_user`) and the similarity threshold; the prompt is deliberately not part of the key; the docs state semantic caching is for single-shot prompts and will replay stale responses on multi-turn or agentic traffic, recommending exact-match Redis for agents ([caching_semantic](https://docs.litellm.ai/docs/proxy/caching_semantic)); no entity, freshness or staleness gate is described in any fetched page |
| TTLs | L1 300 s, L2 75 s, L3 300 s; `max_entries` 10,000 per virtual key per layer; `jitter_fraction` 0.10 on every TTL and cannot be disabled ([configuration](../../reference/config.md), [caching](../../how-to/caching.md)) | `cache_params.ttl` in seconds; `default_in_redis_ttl` and `default_in_memory_ttl` default to `None` (no expiry unless set) ([caching_redis](https://docs.litellm.ai/docs/proxy/caching_redis)) |
| Client controls | None: no no-cache header, no per-key opt-out, no way to disable a layer ([caching](../../how-to/caching.md)) | Per-request `ttl`, `s-maxage`, `no-cache`, `no-store`, `namespace`; per-key controls in key metadata; `default_off` mode with per-request `use-cache` ([caching_controls](https://docs.litellm.ai/docs/proxy/caching_controls)) |
| Invalidation | Bump `guardrails.policy_version` and restart, or `POST /admin/cache/erase` which removes one request's L1 and L2 entries on one replica; L3 is never erased (`l3_skipped: true` always) ([caching](../../how-to/caching.md), [admin API](../../reference/admin-api.md)) | Hits return `x-litellm-cache-key`; send it to `/cache/delete` ([caching_controls](https://docs.litellm.ai/docs/proxy/caching_controls)) |
| Billing of hits | A hit is never billed and records `kelvran.cache.savings_usd`; responses with `finish_reason: length` or a post-call guardrail block are never written ([caching](../../how-to/caching.md), [metrics and logs](../../reference/metrics-and-logs.md)) | Not established from primary sources on 2026-10-09 |

## Budgets and keys

| Aspect | Kelvran | LiteLLM |
|---|---|---|
| Virtual keys | Operator-generated bearer secrets; `config.yaml` stores only `key_hash` (hex SHA-256); `Authorization: Bearer` only; no server-side secret generation ([virtual keys and budgets](../../how-to/virtual-keys-and-budgets.md)) | Generated by `/key/generate` under a master key; stored and attributed by SHA-256 hash; requires Postgres; `upperbound_key_generate_params` rejects out-of-bound values with `400` ([virtual_keys](https://docs.litellm.ai/docs/proxy/virtual_keys)) |

| Rate limits | RPM token bucket (`burst`/`refill_per_second`, default 20/10), TPM reserve-before-call (Redis path GCRA), `max_concurrent_requests` (per replica even with Redis), `per_model` overrides; `429` with `Retry-After` ([virtual keys and budgets](../../how-to/virtual-keys-and-budgets.md), [configuration](../../reference/config.md)) | `tpm_limit`, `rpm_limit`, `max_parallel_requests`; TPM counts input + output; `model_tpm_limit`/`model_rpm_limit` per key or team; counters in Redis across instances with in-memory sync every 0.01 s; falls back to in-memory on Redis loss, or `503` in fail-closed mode ([users](https://docs.litellm.ai/docs/proxy/users)) |
| Teams and hierarchy | None: flat per-key budgets only; per-agent-run sub-limits rejected by recorded decision; pattern is one key per team, agent or run ([virtual keys and budgets](../../how-to/virtual-keys-and-budgets.md), [security model](../security-model.md)) | Budgets at proxy, team, team-member, internal-user, key and end-user (customer) levels; teams are open source, organisations and team-admin assignment are enterprise ([users](https://docs.litellm.ai/docs/proxy/users), [access_control](https://docs.litellm.ai/docs/proxy/access_control)) |
| Per-agent-run limits | Not available; attribution only, via `agent_run_id` ([security model](../security-model.md)) | `max_iterations` and `max_budget_per_session` keyed by `x-litellm-trace-id` or `metadata.session_id`, `429` when exceeded, counters expire after 1 hour by default; per-session TPM/RPM for Agent Gateway agents ([a2a_iteration_budgets](https://docs.litellm.ai/docs/a2a_iteration_budgets), [users](https://docs.litellm.ai/docs/proxy/users)) |
| Key management | Admin API: 19 routes on its own listener, four bearer tiers (Admin, Viewer, CostViewer, Operator), rotate with grace period, every call audit-logged except `GET /admin/audit` and the pprof routes; mutations persist only with `admin.persist_path` (bbolt) or `admin.redis_addr`; no spend-reset route ([admin API](../../reference/admin-api.md)) | `/key/block`, `/key/unblock`; `/key/{key}/regenerate` with `grace_period` is marked enterprise on the keys page; scheduled auto-rotation carries no badge there but the enterprise feature list names "Key Rotations. Automate rotation for virtual keys" ([virtual_keys](https://docs.litellm.ai/docs/proxy/virtual_keys), [enterprise](https://docs.litellm.ai/docs/enterprise)) |
| Multi-replica state | Redis in four sections (`budget`, `admin`, `rate_limit`, `config_propagation` with HMAC-SHA256-signed events); rate limit and budget fail open on Redis error; known defect in `gateway/v0.17.0` and `gateway/v0.18.0`: with `rate_limit.redis_addr` set, a key with `tpm_capacity` admits one in-flight request at a time ([virtual keys and budgets](../../how-to/virtual-keys-and-budgets.md), [README](../../../README.md)) | Budgets enforced against spend read from Postgres; rate-limit counters in Redis ([users](https://docs.litellm.ai/docs/proxy/users)) |

## Failover and routing

| Aspect | Kelvran | LiteLLM |
|---|---|---|
| Selection | Deployments sharing one `model` form a pool; smooth weighted round-robin over members sorted by name; `weight`, opt-in `cost_tier`, `sticky` canary bucketing by key hash; weight is the only live-changeable field ([routing and failover](../../how-to/routing-and-failover.md)) | Strategies `simple-shuffle` (default, recommended), `least-busy`, `usage-based-routing` (not recommended for production), `latency-based-routing`, `cost-based-routing`, custom; `weight` under simple-shuffle; `order` for priority tiers ([routing](https://docs.litellm.ai/docs/routing), [load_balancing](https://docs.litellm.ai/docs/proxy/load_balancing)) |
| Health checks | Synthetic probes only, off unless `health_probe.interval_seconds > 0`: one synthetic request per deployment per tick (a 1-token chat `ping`; since `gateway/v0.18.0` a one-string embedding for `kind: embedding` deployments); thresholds 3 unhealthy / 2 healthy, 4-step recovery ramp from 20 %; probe-latency EMA de-weights; all-unhealthy fails open; no traffic-derived circuit breaker; `gateway/v0.17.0` mis-probes embedding deployments so `/readyz` returns `503` with probes on ([routing and failover](../../how-to/routing-and-failover.md), [configuration](../../reference/config.md), [README](../../../README.md)) | `/health/liveliness` and `/health/readiness` without LLM calls; `/health` sends a real request to every model; `background_health_checks` every 300 s by default; routing exclusion is reactive (cooldowns) unless `enable_health_check_routing` is on; all-unhealthy bypasses the filter ([health](https://docs.litellm.ai/docs/proxy/health), [health_check_routing](https://docs.litellm.ai/docs/proxy/health_check_routing)) |

## FAQ

**Can I point the OpenAI SDK at either gateway unchanged?** Yes for both. LiteLLM states any client that works with OpenAI works with the proxy ([docs](https://docs.litellm.ai/docs/)). Kelvran honours text chat, tools, `json_schema`/`json_object`, streaming, embeddings and (since `gateway/v0.18.0`) `GET /v1/models`, but rejects content-array multimodal messages, drops several OpenAI fields silently and emits flat streaming tool-call deltas ([compatibility](../../reference/compatibility.md), [OpenAI Python how-to](../../how-to/clients/openai-python.md)).

**Does Claude Code or the `anthropic` SDK work?** With LiteLLM, yes, through `/v1/messages` ([anthropic_unified](https://docs.litellm.ai/docs/anthropic_unified)). With Kelvran, no: the route is not registered and `x-api-key` is not read ([compatibility](../../reference/compatibility.md)).

**Do I need a database?** LiteLLM needs Postgres for virtual keys, budgets and spend tracking, and Redis for any cache or counter shared across workers ([virtual_keys](https://docs.litellm.ai/docs/proxy/virtual_keys), [caching_redis](https://docs.litellm.ai/docs/proxy/caching_redis)). Kelvran needs nothing for one replica; admin mutations persist to a bbolt file or Redis, and multi-replica correctness needs Redis in four config sections ([virtual keys and budgets](../../how-to/virtual-keys-and-budgets.md)).

**Are the "semantic caches" comparable?** No. LiteLLM's is embedding-based with a cosine threshold and its docs warn against it for agentic traffic ([caching_semantic](https://docs.litellm.ai/docs/proxy/caching_semantic)). Kelvran's L3 is lexical, with equality gates on entities, numbers, dates and negation and a hard rule against replacing them with a bare threshold ([the cache gate](../cache-gate.md)).

**Which is cheaper or faster?** Not answerable from primary sources: Kelvran publishes no numbers and this page quotes no competitor benchmarks (see Cost and performance above).

**Is either one offered as a hosted service?** Kelvran: no. LiteLLM: its pricing and enterprise pages describe self-hosting only, while its README and `security.md` still reference a hosted proxy and "LiteLLM Cloud" regions; the current status is not established from primary sources on 2026-10-09 ([pricing](https://www.litellm.ai/pricing), [security.md](https://raw.githubusercontent.com/BerriAI/litellm/main/security.md)).
