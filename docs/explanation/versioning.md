# Why Kelvran versions the way it does

This page explains the reasoning behind Kelvran's versioning, compatibility and support policy: why there are two version lines, why both are still 0.x, which surfaces a version number covers and which it deliberately does not, and why the rules are enforced by a script at release time rather than by convention. It is for operators deciding whether an upgrade is safe, for integrators deciding what they may depend on, and for contributors deciding whether a change is breaking. The policy itself, with its surface tables and current dates, is [`docs/VERSIONING.md`](../VERSIONING.md); this page does not repeat it.

## Two version lines, because there are two deployables

Kelvran ships two independently versioned deployables from one repository: the Go `gateway`, tagged `gateway/vX.Y.Z`, and the Python `evals`, tagged `evals/vX.Y.Z`. Both follow Semantic Versioning 2.0.0. The split is not a style choice. Go and Python cannot share a runtime, so two deployables are forced. The single repository is the separate choice, made so that the one artifact that must stay in lockstep across the language boundary, the protobuf contract in `api/`, cannot drift between repositories. [ADR 0001](../decisions/0001-monorepo-two-deployables.md) records that decision and the premature-split case studies behind it.

Two deployables in one repository means two tag families, two changelog folders and two GitHub Releases per cut. One combined release was rejected in the first release decision ([`DECISIONS.md`](../../DECISIONS.md), 2026-09-03): a GitHub Release wraps exactly one git tag, and the two cadences were expected to diverge. They did. The gateway is at `gateway/v0.17.0` (2026-10-07) and evals at `evals/v0.10.1` (2026-09-22).

The `gateway/` tag prefix is load-bearing, not cosmetic. The Go module is `github.com/kelvran/gateway/gateway`: its `go.mod` lives one directory below the repository root, and Go's nested-module rule requires a `gateway/vX.Y.Z` tag for the module proxy to resolve the real `go.mod` instead of a synthesized empty stub. `DECISIONS.md` records the live reproduction of that failure under the old module path and the fix, which follows the same `gopls/vX.Y.Z` convention the Go team uses. Image tags and release-asset names drop the prefix (`ghcr.io/kelvran/gateway:v0.17.0`, and from the first release after it `kelvran-gateway_<version>_linux_amd64.tar.gz`), and the binary's `-version` prints the bare version.

The `api/` protobuf contract is versioned on its own and is outside the policy. CI runs `buf breaking` against it, so an incompatible schema change fails the build instead of drifting; a deliberate change follows the Contract-Version procedure in [`RELEASE.md`](../../RELEASE.md). [ADR 0003](../decisions/0003-go-python-split.md) explains why a versioned contract, never shared code, is the boundary between the two languages.

## Why both lines are still 0.x

The first release was `0.1.0` for both deployables, following the SemVer FAQ, and explicitly not `1.0.0`, because a 1.0 asserts a stability commitment neither deployable had earned (`DECISIONS.md`, 2026-09-03). That reasoning still holds, and the policy turns it into a checklist rather than a feeling. `gateway/v1.0.0` is cut when all of the following are true: an OpenAPI document for the public routes has been frozen across two consecutive minors; `config.yaml` carries a `schema_version` key; the support window has been operated for two minors; five consecutive releases have carried signed assets; and one external condition, the OpenSSF Best Practices badge at the Passing level, is met. `evals/v1.0.0` follows the same list minus the OpenAPI and `schema_version` items.

Not available today: the OpenAPI document (only the protobuf contract lives in `api/`), the `schema_version` key (the parser in `gateway/internal/gateway/controlplane/config.go` knows no such key), and the five signed releases. The pipeline that signs assets (`.github/workflows/release.yml`, `gateway/.goreleaser.yaml`) is on main since 2026-10-08, not in `gateway/v0.17.0`, whose GitHub Release carries no assets. The count starts with the first release after it.

Staying at 0.x is not a licence to break things. The 0.x rules below are nearly as strict as the 1.x ones. The difference is that a MINOR may carry a documented break; after 1.0 only a MAJOR may.

## What a version number covers, and why the exclusions are where they are

The public-surface tables draw one line. Anything a documented client, config file, dashboard or deployment manifest can depend on is public, and a change that stops an existing documented use from working is breaking. Everything else is implementation and may change in any release. The tables are in [`docs/VERSIONING.md`](../VERSIONING.md) § 2 and the key-by-key detail is in the reference pages. This section explains the exclusions that are not obvious.

**Error `type` and `code` are public; error message text is not.** A client that branches on the message string is coupled to prose that is reworded whenever it is unclear. The stable vocabulary is in [Error codes](../reference/error-codes.md).

**No hand-written Go package is public.** Every hand-written package is `main` under `gateway/cmd/` or lives under `gateway/internal/`, and there is no `pkg/`. The one Go package outside those two trees, the generated protobuf bindings at `gateway/api/gatewayevents/v1` (where `api/buf.gen.yaml` writes them), is importable, but it is the `api/` contract rendered into Go: it is governed with that contract, by `buf breaking` in CI and the Contract-Version procedure, not by the gateway version line. The OpenAI-shaped data-plane routes (`POST /v1/chat/completions`, `POST /v1/embeddings`, `GET /v1/models`) and the two probe routes (`GET /healthz`, `GET /readyz`) are the public data-plane HTTP surface, and the HTTP API is the only supported interface. [Why there is no SDK](why-no-sdk.md) covers the trade-off.

**Cache key derivation is not public, and a cache is never carried across an upgrade.** Keys fold in whatever the gate needs to keep two different requests apart, so each addition changes every key. The latest example is the `tools` and `tool_choice` fingerprint ([RFC 2026-10-08](../rfcs/2026-10-08-gateway-cache-key-tools-fingerprint.md)), which changes every L1 and L2 key even for tool-free requests. The caches `cmd/gateway` builds are in-process and empty on every restart, so there is nothing to flush. See [Caching](../how-to/caching.md).

**The bbolt on-disk format is not public.** The stores behind `persist_path` move only through `POST /admin/backup` and the `-restore-store` flag, which gives the format room to change behind a stable procedure. See [Backup and restore](../how-to/backup-and-restore.md).

**Config keys are public, and the parser is the authority.** [`gateway/config.example.yaml`](../../gateway/config.example.yaml) is the annotated reference, but it omits some keys the parser accepts, so the policy names `gateway/internal/gateway/controlplane/config.go` as the key list and [Config reference](../reference/config.md) as the page that tracks it.

**The admin API is public, with one conditional route group.** The routes, their JSON bodies and the four credential tiers (Admin, Viewer, CostViewer, Operator) are covered. The `/admin/debug/pprof/` routes are mounted only when `admin.enable_pprof` is true (default false), so they are public when enabled. See [Admin API](../reference/admin-api.md) and [Admin API RBAC](../how-to/admin-api-rbac.md).

**The `-version` fields are public; the line's spacing is not.** Version, commit, build date, Go version and platform are stable. Parse fields, not columns.

**The container contract is public; the base image is not.** `ENTRYPOINT ["/gateway"]`, `CMD ["-config", "/config.yaml"]`, port `8080`, UID/GID `65532` and the CA bundle at `/etc/ssl/certs/ca-certificates.crt` are covered. The base image digest and the Go toolchain are build details. Platforms: `gateway/v0.17.0` and earlier images are `linux/amd64` only; the `linux/amd64` + `linux/arm64` index is on main since 2026-10-08, not in `gateway/v0.17.0`. See [Container image](../reference/container-image.md).

**Release-asset names and the package layout are public; the unit's hardening is not.** The deb/rpm/apk packages install `/usr/bin/kelvran-gateway`, the [systemd unit](../../deploy/systemd/kelvran-gateway.service) and `/etc/kelvran-gateway/config.example.yaml`. The unit's hardening directives only ever tighten, so they are outside the promise. See [Release artifacts](../reference/release-artifacts.md).

**OpenTelemetry names are public; log lines are not.** The covered set is what the code registers, described in [Metrics and logs](../reference/metrics-and-logs.md) and [`docs/operations/TELEMETRY.md`](../operations/TELEMETRY.md). Log messages and field names are best effort, not a contract.

For `evals`, the public surface is the CLI commands and their options and the persisted `Run` and `Score` JSONL schemas in `evals/evals/models.py`. Nothing is importable yet; a module becomes public only when `evals/ARCHITECTURE.md` names it as such, and none is named today. The judge prompt text is versioned separately by `JUDGE_PROMPT_VERSION`, because a prompt change makes scores non-comparable without changing any interface.

## Why the 0.x rules are enforced by a script

The rules are short. A PATCH never breaks a public surface. A MINOR may break one only when the dated changelog entry is marked `**BREAKING**`, [`UPGRADE.md`](../../UPGRADE.md) has a table row for that version with migration steps, and, where the old surface can be kept alive meanwhile, a `DEPRECATED.md` row announced it with the lead time described below. A security fix may break a surface in a PATCH if the surface itself is the vulnerability.

The reason the first two conditions are checked by `scripts/release-preflight.sh` rather than by a reviewer is this repository's own record. `UPGRADE.md` said, until it corrected itself on 2026-10-08, that no breaking change had shipped, while `evals/v0.2.0` had already made `--scores` mandatory; that change is now its first row. Documentation that is only promised drifts. So `.github/workflows/release.yml` (and `.github/workflows/release-evals.yml` for `evals/v*` tags) runs the preflight at the pushed tag before building anything, and the preflight fails the release when the dated changelog contains the bold marker and `UPGRADE.md` has no table row of the form `| \`gateway/v0.18.0\` |` for that release. It also fails when the dated changelog file is missing or empty, when `unreleased.md` still holds entries, and for evals when `pyproject.toml` disagrees with the tag or `scripts/check_versions.py` disagrees with the newest changelog file. It warns, as a GitHub Actions annotation, when the support-window table in `docs/VERSIONING.md` does not name the release as the latest minor.

The trade-off is that a textual check sees only what is marked. An unmarked breaking change passes the preflight, and the third condition, deprecation lead time, is a judgement no grep can make. Those halves stay with review: `.github/pull_request_template.md` asks every PR whether it breaks or deprecates a public surface and for the matching `UPGRADE.md` or `DEPRECATED.md` row. The marker's spelling also matters. The match is case-insensitive on the bold text, so `**BREAKING**` belongs only on entries that are breaking.

The record so far: `UPGRADE.md` holds one row, `evals/v0.2.0`. The gateway has shipped no breaking change to a released surface across twenty releases; the one `**Breaking**` note in `gateway/changelog/0.1.0.md` replaced `api_key_env` with `virtual_keys:` before any version existed to migrate from.

## Deprecation: announce, wait, remove

A surface is retired in three steps: a `DEPRECATED.md` row and a `## Deprecated` changelog entry in the release that announces it; a wait of at least two minors or 90 days, whichever is later; then removal with a `**BREAKING**` entry and an `UPGRADE.md` row, the `DEPRECATED.md` row kept with its removal version filled in. After 1.0 the wait becomes at least six months and removal needs a MAJOR.

Where the gateway can detect use of a deprecated surface at runtime, the policy has it log `deprecated_surface_used` at `WARN` once per process per surface and increment a `kelvran.deprecation.used` counter with the surface name as attribute. Not available today: neither the log line nor the counter exists in the gateway source, by design. `DEPRECATED.md` has no rows, so there is nothing for them to report; the first deprecation adds both.

## The support window and why it lives in one place

The latest minor of each deployable receives all fixes as PATCH releases. The previous minor receives security fixes only, for 90 days after the newer minor shipped. Anything older is unsupported. Today that means security fixes for `gateway/v0.16.0` until 2027-01-05 and for `evals/v0.9.0` until 2026-12-20, ninety days after `evals/v0.10.0`, the first release of the newer minor, shipped on 2026-09-21; `evals/v0.10.1` is a PATCH of the latest minor, not a separate line.

The dates live in one table in [`docs/VERSIONING.md`](../VERSIONING.md), and [`SECURITY.md`](../../SECURITY.md) and [`SUPPORT.md`](../../SUPPORT.md) point at it instead of carrying copies. That is the same anti-drift reasoning as the preflight: a date that exists in three files is soon wrong in at least one of them. The preflight's warning when the table does not name the release being cut is what keeps the single copy current.

Pre-releases (`-rc.N` or similar) are outside both the 0.x rules and the support window. The GitHub Release is flagged pre-release, the image tag and assets exist, and the pre-release may change or disappear without an `UPGRADE.md` row. Not available today for `evals`: `.github/workflows/release-evals.yml`'s tag regex forces a hyphenated suffix (`evals/v0.11.0-rc.1`), hatchling writes the sdist and wheel under the normalised PEP 440 form (`0.11.0rc1`), and the workflow's artefact check looks for the hyphenated form in those filenames, so a pushed evals pre-release tag fails before anything is signed; the workflow's own header records this. Until that check changes, an evals pre-release is a policy statement, not a working path.

## Finding out what is running

The build identity is injected at build time through `-ldflags`, so a plain `go build` reports `dev`, `none` and `unknown` instead of a stale number. `kelvran-gateway -version` prints one line, and every start logs the same fields as a `build_info` record so version skew across replicas shows up in logs. The published image carries `org.opencontainers.image.version` as a label and, for images built on or after 2026-10-08, as an index annotation. The exact commands are in [Upgrade](../how-to/upgrade.md) and [Container image](../reference/container-image.md).

Signed assets are part of the 1.0 checklist, and the release pipeline already produces them: one CycloneDX SBOM per archive and package, a `checksums.txt` signed keyless with cosign, and a SLSA build-provenance attestation over every archive, package, SBOM and `checksums.txt` (the signature bundle itself is the one asset not attested). The asset names and the verification recipe are in [Release artifacts](../reference/release-artifacts.md) and [`RELEASE.md`](../../RELEASE.md); the upgrade procedure is in [Upgrade](../how-to/upgrade.md), and what each release pair supports is in [Compatibility](../reference/compatibility.md).
