# Upgrade Guide

**Corrected 2026-10-08**: this file said "no breaking change has shipped in a release yet" while only `gateway/v0.1.0` and `evals/v0.1.0` existed. Twenty gateway and eleven evals releases later (`gateway/v0.17.0`, `evals/v0.10.1`), the gateway has still shipped no breaking change to a released surface (every `api/` change passed `buf breaking`; config keys were only added), but the evals CLI change this file itself flagged as pending did ship — it is the first row below. The support window and what counts as a public surface are defined in `docs/VERSIONING.md` (since 2026-10-08) (in progress per `docs/upgrade-research/kelvran-deep-research-round4-discoverability-2026-10-08.md`); until then the rule is: a `**BREAKING**` changelog entry must have a row here in the same release.

Rows are oldest first and cross-reference the `<deployable>/changelog/<version>.md` entry that introduced the change:

| Version | Breaking Change | Migration Steps |
|---|---|---|
| `evals/v0.2.0` | `evals run` and `evals rollout` require `--scores <path>` (persisted `Score` JSONL); in `evals/v0.1.0` scores were only printed. Introduced by commit `d3e54197` (2026-09-04, "add Score model + persistence"), first shipped in `evals/v0.2.0` (`evals/changelog/0.2.0.md`). | Add `--scores /path/to/scores.jsonl` to every `evals run`/`evals rollout` invocation; feed the same path to `evals report --scores`. |

Config-schema migration notes (virtual keys, budgets, routing rules, cache configuration) will be tracked here as they evolve, once there's a config schema to have opinions about. **Corrected 2026-10-08**: that sentence dates from the 2026-09-02 scaffolding commit; the config schema has existed since `gateway/v0.1.0`. `gateway/internal/gateway/controlplane/config.go` is the authoritative key list — its `Load` reads sixteen top-level `config.yaml` sections (`listen_addr`, `virtual_keys`, `deployments`, `price_table`, `models`, `telemetry`, `budget`, `prompt`, `rate_limit`, `config_propagation`, `cache`, `guardrails`, `admin`, `health_probe`, `alerting`, `credential_reload`; `models` is on main since 2026-10-08, not in `gateway/v0.17.0` (`gateway/changelog/unreleased.md`), so a `gateway/v0.17.0` binary ignores it), which already covers the four areas named above: virtual keys are `virtual_keys:` entries (`VirtualKeyConfig`, each with its own `budget_usd`), budget persistence is `budget:` (`BudgetConfig`), routing rules are `deployments:` entries with `weight`, `fallback_chains`, `sticky` and `cost_tier` (`DeploymentConfig`), and cache configuration is `cache:` (`CacheConfig`). `config.yaml` keys are a public surface under `docs/VERSIONING.md`, so removing or renaming one is a `**BREAKING**` change that needs a row in the table above. Through `gateway/v0.17.0` no key has been removed or renamed, which is why there is still no config row; the two changes in meaning to existing keys are both TPM keys that earlier releases parsed but did not wire: `gateway/v0.14.0` started enforcing `virtual_keys.<name>.rate_limit.tpm_capacity`/`tpm_refill_per_second` when `rate_limit.redis_addr` is set (Redis mode had made per-key TPM a deliberate no-op; `gateway/changelog/0.14.0.md`), and `gateway/v0.17.0` started enforcing `deployments.<name>.rate_limit.tpm_capacity`/`tpm_refill_per_second` (`gateway/changelog/0.17.0.md`). There is no `schema_version` key yet (`docs/VERSIONING.md` lists it as a `gateway/v1.0.0` condition), and the parser ignores top-level keys it does not know (the one strict spot is a `models.<name>` entry, whose unknown fields are a load error), so a config written for a newer release loads on an older binary with the new key silently inactive. The annotated reference is `gateway/config.example.yaml`, the key-by-key page is `docs/reference/config.md`, and the upgrade procedure is `docs/how-to/upgrade.md`.
