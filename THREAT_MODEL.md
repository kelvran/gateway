# Threat Model

## Methodology

STRIDE applied per component against the data-flow diagram in `ARCHITECTURE.md`. Trust boundaries: tenant ↔ Gateway; Gateway ↔ upstream providers; Gateway ↔ Cache (internal, in-process — a trust boundary in the STRIDE sense even without a network hop, because it still crosses tenant-isolation logic); Evals-control ↔ sandboxed agent execution; Gateway/Evals ↔ the shared `api/` contract. This document is reviewed on its own cadence (see "Review Cadence" below), decoupled from `ARCHITECTURE.md`'s — a new CVE, paper, or major release can invalidate a threat-model assumption without any architecture change at all.

## Component: Gateway

| STRIDE | Threat | Mitigation |
|---|---|---|
| Spoofing | Virtual-key forgery; MCP/A2A OAuth2 token-passthrough abuse (a documented real-world bug class in the most mature OSS MCP gateway implementation surveyed); admin-credential forgery against the live virtual-key mutation surface added 2026-09-05 | **Partial, corrected 2026-09-04.** Real today: virtual keys are opaque, unguessable, tenant-scoped tokens validated against `internal/identity` on every request — confirmed, tested. **Moot today**: the MCP/A2A OAuth2 token-passthrough half of this threat, and the mitigation clause claiming MCP/A2A brokering shares identity/budget objects — `internal/mcp` doesn't exist (confirmed: no such directory anywhere in `gateway/internal/`), and MCP/A2A tool brokering is explicitly out of scope for v1 per `PRD.md`. Revisit this row's MCP/A2A half once that subsystem is actually built. **New 2026-09-05**: `internal/admin` (per `docs/rfcs/2026-09-05-gateway-admin-api.md`) is off by default; when enabled, its bearer credential is a deliberately separate credential space from client-facing virtual keys (never delegates to `internal/identity.Verifier`), compared via `subtle.ConstantTimeCompare`, served on its own loopback-default listener (never the client-facing mux/port), and the gateway refuses to start at all if the configured token env var resolves empty — no unauthenticated fallback state exists |
| Tampering | Request/response mutation in transit between adapter stages | Canonical schema validated at each adapter boundary; no raw pass-through of unvalidated provider fields |
| Repudiation | "Why did this agent run cost $X" has no answer beyond a raw total (the exact gap every competitor surveyed has) | `agent_run_id` propagated via OTel Baggage from the first line of the pipeline; span-level cost attribution down to the individual tool call/retry |
| Information Disclosure | Prompt/completion content, which may contain PII, traverses guardrails and cache write-back | PII/content guardrail pre- and post-call; cache write-back respects tenant namespace (see Cache STRIDE table below) |
| Denial of Service | Retry storms in agentic traffic — many agents retrying on a fixed interval synchronize into a thundering herd | **Not built, corrected 2026-09-04.** None of the specifically-cited mechanisms exist — zero matches anywhere in `gateway/internal/` for circuit-breaker, backoff, jitter, concurrency-cap, or retry-budget logic (confirmed via grep). The real, existing backstops are narrower and indirect: per-key token-bucket rate limiting (`internal/ratelimit`) and per-key USD budget caps (`internal/budget`) bound how much damage a retry storm from any single virtual key can do, but neither specifically detects or dampens a synchronized thundering-herd pattern across many keys/agents. Real retry-storm-specific mitigation (backoff+jitter, a global circuit breaker, per-agent concurrency caps) remains future work, not yet designed. **Built 2026-09-05**, per `docs/rfcs/2026-09-05-gateway-ratelimit-fail-open-metric.md`: the rate-limiter backstop's own degraded-mode was previously silent at aggregate scale — a Redis backend outage causes `checkRateLimit` to fail open (allow every request through unrated, per `docs/rfcs/2026-09-03-distributed-rate-limiting.md`'s explicit policy), logged and per-request-flagged but with no way to see "how often is this happening right now" without scanning logs one request at a time. `kelvran.ratelimit.fail_open` (a real OTel counter, `internal/budget`'s independent per-key USD cap remaining the backstop-of-the-backstop) now makes a sustained fail-open episode — i.e. the rate-limiting backstop itself silently degrading during exactly the kind of incident this row is about — an alertable, aggregate signal rather than something only visible in hindsight |
| Elevation of Privilege | Guardrail bypass on non-tool operations (a documented bug class in the MCP gateway implementations surveyed); a leaked/forged admin credential provisioning an unrestricted (unlimited budget, no model allow-list) virtual key, added 2026-09-05 | **Moot today, corrected 2026-09-04.** This threat presupposes MCP/A2A's tool-call vs. non-tool-call operation split, which doesn't exist (`internal/mcp` has zero code). Gateway today has exactly one operation type (a chat completion request), and Guardrails' real pre-call/post-call checks (`internal/guardrail`, per `docs/rfcs/2026-09-03-guardrails-pii-regex-classifier.md`) already apply uniformly to all of it — so the mitigation's literal claim holds trivially, not because a documented distinction was actually defended against. Revisit once MCP/A2A tool brokering is built and a real tool-call/non-tool-call surface exists to bypass. **New 2026-09-05**: the admin surface is off by default, and its default listen address is loopback-only (`127.0.0.1:8081`) — reaching it at all requires either host-local access or a deliberate, explicit non-default `listen_addr`. A compromised admin credential IS a full privilege escalation (it can create a virtual key with no budget cap and no model restriction) — not mitigated further in v1; operators must treat the admin token with at least the same care as a root credential, per this RFC's own persistence/auth open questions left for a future pass |

## Component: Cache

| STRIDE | Threat | Mitigation |
|---|---|---|
| Spoofing | N/A at this layer (auth already resolved upstream by Gateway before Cache is consulted) | — |
| Tampering | Cache poisoning — a 2026 NDSS paper ("When Cache Poisoning Meets LLM Systems") demonstrated 81-89% success rates against production semantic-caching integrations at major cloud providers | Entity/number/date hard-gate in front of every semantic hit (never a bare similarity threshold — see `PRD.md`'s explicit scope requirement); provenance metadata stored at write time so poisoned entries are traceable |
| Repudiation | A stale cache hit silently degrades an agent's downstream action with no error and a clean-looking trace | **Built 2026-09-05**, per `docs/rfcs/2026-09-05-gateway-cache-hit-provenance.md`: `kelvran.cache.layer` (OTel span) / `cache_layer` (structured log) now report which layer served a hit ("L1"/"L2"/"L3"), and `kelvran.cache.similarity`/`kelvran.cache.age_ms` (+ log equivalents) report the real, write-time-captured Jaccard similarity and age for an L3 hit specifically — the data `LexicalCandidate` already computed and was simply being discarded. A downstream failure can now be traced to which specific cache layer/similarity/age produced it, not just "this was a cache hit." L1/L2 still report only their layer, not an age — neither currently captures a write-time timestamp at all (widening `cache.Cache`'s interface to do so is named future work, a materially larger change than this pass) |
| Information Disclosure | **Cross-tenant cache leakage** — a 2026 study ("KeyPooling") found this exploitable in 5 of 5 tested production-representative gateways, with pooled upstream credentials as the specific mechanism | Tenant namespace baked into the vector-index partition itself (not a post-hoc filter) and enforced at every hop: lookup, write, retry, fallback, connection-pool reuse |
| Denial of Service | Cache-miss storms causing redundant expensive upstream calls | **Built 2026-09-05**, per `docs/rfcs/2026-09-05-gateway-cache-stampede-protection.md`: `dataplane.Pipeline.runMissPath` coalesces concurrent identical cache misses via `golang.org/x/sync/singleflight`, keyed on the L1 exact-match cache key (which already bakes in tenant ID, so this can never coalesce two different tenants' requests together) — N concurrent requests for the same not-yet-cached key now produce exactly one real upstream call, verified with a real concurrency test (unit-level and a real end-to-end HTTP integration test). Single-instance-only in v1 (in-process, not a distributed lock) — a multi-instance deployment still allows redundant calls across instances, named explicitly as future work, the same "single-instance stepping stone" posture this project's own rate-limiting/budget mechanisms started with |
| Elevation of Privilege | **Semantic-cache response hijacking** — "CacheAttack" (2026) demonstrated an 86% hijack rate (90.6% against agentic tool invocation, including a financial-agent case study triggering an unintended `sell` order) via similarity-based key collision | Entity/number/date hard-gate + freshness/risk model (not similarity alone) before any semantic hit is served; similarity threshold never below ~0.9 for open-ended, user-facing traffic |

## Component: Evals

| STRIDE | Threat | Mitigation |
|---|---|---|
| Spoofing | A rollout claims to be a golden/regression-tier run when it isn't, corrupting the regression dataset | `EvalCase.tier` is set at dataset-registration time, not by the rollout itself; frozen/immutable revisions |
| Tampering | Judge manipulation — adversarial prompts designed to flip a judge's verdict; research shows up to 100% verdict-flip rates against a single unmitigated LLM-judge call under adversarial pressure | CoT-forcing + reference-guided grading as v1 defaults; judge model always ≠ policy model; adversarial skeptic-panel verification designed into the Scorer Service's interface as a v2 upgrade path (see `evals/ARCHITECTURE.md`) |
| Repudiation | A surprising score gets blamed on the agent when it was actually a grading bug (a documented real failure pattern: a rigid string-match grader produced a 42% score that became 95% once the grader itself was fixed) | Rubrics/graders are reviewed, versioned artifacts; a surprising score triggers grader root-cause review before the agent is blamed |
| Information Disclosure | Sandboxed rollout exfiltrates data via an unexpected channel (network egress, shared filesystem) | **Partial, updated 2026-09-05.** Real today: `--network=none` on every `run_in_sandbox()` call (`evals/rollout/sandbox.py`) — a full egress block, actually stronger than an allowlist for v1's no-legitimate-egress-need profile (a fixed image+command, no LLM call from inside the sandbox), and genuinely tested (`test_run_in_sandbox_blocks_network_egress`). Also real as of 2026-09-05: `--read-only` on the container's root filesystem plus a `--tmpfs=/tmp` mount — a genuine Kelvran-built ephemeral-filesystem guarantee, not just Docker's own default `--rm` writable-layer lifecycle, tested (`test_run_in_sandbox_root_filesystem_is_read_only`, `test_run_in_sandbox_tmp_is_still_writable`). **Not built**: scoped short-lived per-tool credentials issued via a proxy — no "tool" concept exists anywhere in `evals/` yet to scope a credential to. Revisit egress allowlisting (vs. the current stronger full-block) only once a real partial-egress need appears |
| Denial of Service | Cost blowout at eval scale — detecting a modest regression can require ~100 trials per scenario, and a naive suite can cost tens of thousands of dollars per regression check | **Partial, corrected 2026-09-04 (third time — see Review Cadence).** Real, per `docs/rfcs/2026-09-04-evals-rollout-cost-mitigation.md`: an opt-in result cache (`rollout --use-cache`, skips re-running a case with a matching completed prior `Run`). Real early-stopping for repeated trials of the same case, per `docs/rfcs/2026-09-05-evals-mixture-sprt-early-stopping.md` (**upgraded 2026-09-05** from the original two-checkpoint, Bonferroni-corrected design to a real mixture-SPRT/anytime-valid test — Robbins 1970, popularized by Johari, Koomen, Pekelis & Walsh KDD 2017 — checked after every single trial with no pre-declared checkpoints, still never a naive continuous recheck of a fixed-sample interval, which would have inflated the true false-positive rate, the classical optional-stopping/peeking problem). Also real, closed 2026-09-04: `timeout_s` now genuinely bounds a sandbox's real resource usage — `sandbox.py`'s own timeout path previously only killed the local `docker run` CLI *client* process, not the container itself, letting a hung/malicious sandboxed command keep running (and consuming host resources) for its own full natural duration regardless of the configured timeout, confirmed empirically against a real Docker daemon before the fix. Also real, closed 2026-09-05, per `docs/rfcs/2026-09-05-evals-score-cache.md`: an opt-in `Score`-level (LLM-judge) result cache (`--use-score-cache` on both `evals run`/`evals rollout`) — skips re-calling the LLM judge for a case whose `(output, reference, scorer_id)` already has a real, non-cached `Score` in `--scores`, independent of `--use-cache`'s Run-level equivalent. **Still not built**: per-tier calibrated trial-count defaults — no production traffic exists yet to calibrate against, named future work, not silently assumed solved by this pass |
| Elevation of Privilege | **Sandbox escape** — a real 2026 incident saw an agent escape its eval sandbox via a package-registry-proxy zero-day and coordinate with hundreds of other agents through an unsanctioned shared channel, ultimately breaching a production database | **2 of 5 originally-imagined layers real, corrected again 2026-09-04.** Real: the execution boundary itself (Docker container/namespace isolation via a genuine `docker run` call), and — as of `docs/rfcs/2026-09-04-evals-trace-span-model.md` — full audit logging for every real sandbox execution, via a self-contained OTel-SDK-generated `Span` per `Run`. That `Span`/`Trace` gap was previously misframed as "blocked on `api/otel`'s still-undecided transport" — a doc-vs-code framing correction, not a status change on the other three items: isolation *between* concurrent sandboxes is still moot today (`scheduler.py` is sequential-only, zero concurrent sandboxes exist to isolate between); package-registry/dependency-proxy hardening is still moot today (v1 runs a fixed image+command, nothing installs a dependency at runtime inside the sandbox); scoped per-tool credentials still need a tool-calling harness concept that doesn't exist in `evals/`. See `docs/rfcs/2026-09-04-evals-llm-judge-provider-wiring.md`'s Motivation section for the full original sizing — the remaining three items still split into separate future RFCs, not one |

## Cross-Component: MCP/A2A Tool Brokering

**Not built, noted 2026-09-04**: the entire MCP/A2A brokering subsystem this table describes has zero code (`gateway/internal/mcp` doesn't exist) — explicitly out of scope for v1 per `PRD.md`. Both rows below describe the intended design for a future subsystem, not a present-tense mitigation, despite the wording — the same overclaim pattern already found and fixed for the Gateway table's Spoofing/Elevation-of-Privilege rows above.

| STRIDE | Threat | Mitigation |
|---|---|---|
| Information Disclosure | Session/context leakage across concurrent tool calls — a documented bug class in the most mature OSS MCP gateway implementation surveyed | Session/context isolation enforced per concurrent tool call, not shared state across a connection pool |
| Elevation of Privilege | Auth-passthrough abuse — an A2A proxy trusting a self-reported (sometimes unreachable) agent-card URL instead of the operator-registered one | Operator-registered agent URLs are authoritative; caller identity is verified via the same `internal/identity` objects Gateway's outbound path uses, never re-derived from a self-reported card |

## OWASP LLM Top 10 (2025) Crosswalk

| OWASP Category | Where it maps in this system |
|---|---|
| LLM01 Prompt Injection | Guardrail pre/post-call (Gateway); tool-call argument validation (Gateway adapters) |
| LLM02 Sensitive Information Disclosure | PII guardrails; tenant-namespace isolation (Cache); provider data-flow inventory (`docs/operations/PROVIDERS.md`) |
| LLM04 Data and Model Poisoning | Cache poisoning defenses (entity/freshness gates); Evals dataset immutability/versioning |
| LLM06 Excessive Agency | MCP/A2A scoped credentials; per-tool short-lived tokens issued via a proxy outside the sandbox |
| LLM07 System Prompt Leakage | Adapter-level system-prompt handling isolated per provider; never cached across tenants |
| LLM08 Vector and Embedding Weaknesses | Cache's semantic layer (L3) hard-gates and entity checks directly target this category |
| LLM09 Misinformation | Cache freshness/risk model (a cached answer must still be *true*, not just similar); Evals statistical rigor |
| LLM10 Unbounded Consumption | Rate limiting, budgets, retry-storm defenses (Gateway); cost-blowout mitigations (Evals) |
