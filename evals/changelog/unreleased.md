Two real correctness issues were found and fixed *before* any code shipped: the earliest-floated design (recheck a plain confidence interval after every trial, stop at first exclusion of a baseline) is the classical optional-stopping/peeking problem and would have inflated the true false-positive rate well above the nominal level (confirmed empirically via simulation in `tests/test_stats_properties.py`, not just asserted from citation); and the direct, non-log-space mSPRT likelihood-ratio formula overflows `math.exp` for an extreme-enough deviation, caught by this feature's own property-based test suite and fixed by computing entirely in log-space instead. `EarlyStopConfig.score_fn` is async — a third real bug, caught by this feature's own CLI-integration test before shipping: `run_suite` is already executing inside an event loop by the time it calls back into scoring, so a synchronous `--llm-judge` scoring path (which needs to await a coroutine) would raise "cannot be called from a running event loop," previously silently swallowed into a wrong `JUDGE_ERROR` for every early-stopped judged trial. `--early-stop-max-trials` is a plain resource ceiling, not a statistical checkpoint — a group reaching it without the mSPRT itself deciding to stop is force-stopped anyway. Deliberately out of scope: `Score`-level (LLM-judge) caching (shipped separately, see below) and calibrated per-tier trial-count defaults (no production traffic exists yet to calibrate against).

## Fixed

- **Real bug, found only by triggering the nightly workflow for real in CI for the first time**: `make_bedrock_call_model` (`evals/judge/providers.py`) left `region_name=None` for `boto3.client(...)` to resolve on its own, relying on `AWS_REGION`/`AWS_DEFAULT_REGION`'s documented env-var support. The first real CI run failed instantly with `botocore.exceptions.NoRegionError: You must specify a region`, despite `AWS_REGION` being a correctly-set GitHub Actions secret. Reproduced identically on purpose, locally, by pointing `AWS_CONFIG_FILE`/`AWS_SHARED_CREDENTIALS_FILE` at `/dev/null` for one test process — every prior "it works locally" claim this session was silently masked by this machine's own `~/.aws/config` setting a region, unrelated to `evals`. Confirmed directly: this project's pinned botocore (1.43.89) only honors `AWS_DEFAULT_REGION` for a bare `region_name=None` call, not `AWS_REGION` alone — contradicting AWS's own newer-SDK convention and this project's own prior (never actually verified) assumption. Fixed by resolving region explicitly (`region_name` param, else `AWS_REGION`, else `AWS_DEFAULT_REGION`) and passing a real value to `boto3.client(...)`, never `None`. 3 new tests mock `boto3.client` to prove all three inputs resolve correctly; sanity-checked-by-breaking (2 of 3 failed before the fix, restored). No `.env.example`/CLI-help-text change needed — they already said `AWS_REGION`; only the code wasn't honoring it.
- **Real bug, found only by testing against live AWS Bedrock access for the first time**: `BEDROCK_SONNET_5_MODEL_ID`/`BEDROCK_HAIKU_4_5_MODEL_ID` (`evals/judge/providers.py`) used the bare `bedrock-runtime` model id for both Claude Sonnet 5 and Claude Haiku 4.5 — verified against AWS's documentation, but never against a real Converse call, on the unverified assumption that the bare id was "the correct default for a single-region judge workload." A real call fails outright: `ValidationException: Invocation of model ID ... with on-demand throughput isn't supported. Retry your request with the ID or ARN of an inference profile that contains this model.` Neither model supports on-demand invocation by bare id at all. Fixed by switching both constants to their `global.`-prefixed cross-region inference profile id — chosen over a `us.`/`eu.`/`au.`/`jp.` geo-scoped profile so this never needs to track whatever region `AWS_REGION` is set to. Verified live end-to-end (`evals run --llm-judge-panel` against a real, throwaway one-case suite and a real credential) — both judges independently voted, quorum reached, panel PASS — the first time this feature has run against real Bedrock access rather than fakes.
- **Real DoS-relevant bug**: `run_in_sandbox()`'s timeout enforcement only ever killed the local `docker run` CLI *client* process, never the container itself — a killed CLI process does not stop its container, confirmed empirically against a real Docker daemon (`docker ps` still showed a `sleep 30` container `Up` well after a `timeout_s=2` call had already returned `timed_out=True`). Fixed by capturing the real container ID via `--cidfile` and issuing a genuine `docker kill <id>` on timeout, not just killing the CLI wrapper. New load-bearing regression test (`test_run_in_sandbox_timeout_actually_stops_the_container`) asserts the container is genuinely gone via `docker inspect`, not just that the Python call returned — sanity-checked by temporarily reverting the fix and confirming a real orphaned container was left running. Found while implementing an unrelated, smaller backlog item (surfacing `container_id` on `evals`' `Span` model); both are fixed in the same pass since they share the same missing piece.
