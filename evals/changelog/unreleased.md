## Added

- `Span` model + self-contained OTel Python SDK tracing, per `docs/rfcs/2026-09-04-evals-trace-span-model.md`: `evals/evals/tracing.py` wraps every real `run_in_sandbox()` attempt in the Rollout Scheduler with a genuine OTel span (real, spec-compliant `trace_id`/`span_id` via a locally-held `TracerProvider` — never the process-wide `trace.set_tracer_provider()` singleton, and never any OTLP exporter/collector). Closes `THREAT_MODEL.md`'s "full audit logging tied to the trace" gap for the Evals Elevation-of-Privilege row entirely inside `evals` — that gap was previously misframed as blocked on `api/otel`'s still-undecided transport, which was never actually a dependency for auditing evals' own sandbox executions (as opposed to consuming gateway's own spans, a separate, still-undecided capability). New required `--traces <path>` option on `evals rollout` (mirroring `--results`/`--scores`'s existing required convention — a deliberate breaking CLI change); `evals run` is unaffected, since it never touches the Rollout Scheduler. `run_suite` gains an opt-in `span_sink: list[Span] | None = None` keyword parameter, byte-for-byte behavior-identical when omitted; exactly one `Span` is recorded per genuinely-executed trial (success or sandbox-launch exception) — never for a cache hit or an early-stop skip, neither of which represents a real execution. Deliberately no `Trace{spans:[Span]}` wrapper yet — today's harness makes exactly one span per `Run`, the same "don't build the diagram-only box" discipline already applied to `Task/Dataset Registry`/`Sandbox Pool`. A real design mistake in the pre-existing architecture sketch was caught and corrected before any code shipped: `gen_ai.operation.name` (the sketch's own proposed span attribute) is confirmed, via direct inspection of the OTel semantic-conventions registry, to be a namespace for LLM/model-inference operations only — never applied here; real (if experimental/incubating) `process.*`/`container.*` attributes are used instead, only for fields genuinely obtainable from today's `docker run --rm` invocation. New runtime dependency: `opentelemetry-sdk` (pulls in `opentelemetry-api` transitively) — the first non-`anthropic`/`click`/`pydantic`/`protobuf` dependency this project has taken on. `Span.container_id` (the stable `container.id` semantic convention) followed shortly after, once `sandbox.py` gained real `--cidfile` support alongside a DoS-relevant bug fix (see Fixed) — `process_pid` remains deliberately excluded even now that a PID is technically obtainable, since the local `docker run` CLI process's PID is not the containerized command's own process. `evals report` gains a third mode, `--traces <path>` (mutually exclusive with `--scores`/`--successes`+`--total`), resolving the Trace/Span RFC's own named "no consumer needs this yet" gap: an aggregate, never-grouped `ok_rate` line (Wilson-CI-bearing, per `PRD.md`'s "never a bare percentage" convention) plus average sandbox execution duration — deliberately labeled `ok_rate`, not `pass_rate`, since a `Span`'s OK/ERROR status measures sandbox-execution reliability, not eval quality.
- Rollout cost/DoS mitigation, closing `THREAT_MODEL.md`'s Evals Denial-of-Service gap: `evals rollout` gains `--use-cache` (skip re-running a case whose `(task_spec, harness_config)` hash already has a completed `Run` in `--results`; never applied to `tier="drift_sample"` cases, which exist specifically to catch real-world drift, per `docs/rfcs/2026-09-04-evals-rollout-cost-mitigation.md`) and `--early-stop-max-trials`/`--early-stop-baseline-pass-rate`/`--early-stop-relative-mixing-variance` — a real, anytime-valid mixture-SPRT (mSPRT) early-stopping rule for repeated trials of the same case, checked after every single trial with no pre-declared checkpoints (new `evals.stats.mixture_sprt_early_stop`, per `docs/rfcs/2026-09-05-evals-mixture-sprt-early-stopping.md`; an initial two-checkpoint, Bonferroni-corrected design was built first and fully replaced before this line ever shipped in a real release). Both mechanisms are off by default and additive: `run_suite(cases)` called with no new keyword arguments is byte-for-byte identical to before either RFC, and every new `Run`/`RunStatus` field is optional with a default, verified directly (not assumed) to load cleanly from old-shape JSONL. Two real correctness issues were found and fixed *before* any code shipped: the earliest-floated design (recheck a plain confidence interval after every trial, stop at first exclusion of a baseline) is the classical optional-stopping/peeking problem and would have inflated the true false-positive rate well above the nominal level (confirmed empirically via simulation in `tests/test_stats_properties.py`, not just asserted from citation); and the direct, non-log-space mSPRT likelihood-ratio formula overflows `math.exp` for an extreme-enough deviation, caught by this feature's own property-based test suite and fixed by computing entirely in log-space instead. `EarlyStopConfig.score_fn` is async — a third real bug, caught by this feature's own CLI-integration test before shipping: `run_suite` is already executing inside an event loop by the time it calls back into scoring, so a synchronous `--llm-judge` scoring path (which needs to await a coroutine) would raise "cannot be called from a running event loop," previously silently swallowed into a wrong `JUDGE_ERROR` for every early-stopped judged trial. `--early-stop-max-trials` is a plain resource ceiling, not a statistical checkpoint — a group reaching it without the mSPRT itself deciding to stop is force-stopped anyway. Deliberately out of scope: `Score`-level (LLM-judge) caching (shipped separately, see below) and calibrated per-tier trial-count defaults (no production traffic exists yet to calibrate against).
- Real judge-call cost tracking on `Score.cost_usd`. `evals/judge/providers.py`'s `make_anthropic_call_model()` now returns a small callable object (`_AnthropicCallModel`, still satisfying `Callable[[str], Awaitable[str]]`) exposing `last_call_cost` — the real `input_tokens`/`output_tokens` and computed `cost_usd` of the most recent Anthropic call, read from the SDK response's own `usage` field. `judge()`/`llm_judge.py` remain completely untouched, per both prior RFCs' invariant — this is a deliberate, narrow, explicitly-flagged exception to the org-wide "never mutate, always create new objects" rule, the only channel available without widening `judge()`'s contract. A deterministic `Score` gets `cost_usd=Decimal("0")` — an exact, certain fact (no external call is ever made), not an estimate; a `llm_judge` `Score` gets the real computed cost, or `None` if the pinned model has no price-table entry. Pricing (`$1.00`/`$5.00` per MTok input/output for `claude-haiku-4-5-20251001`) is a small, hand-edited, dated-and-sourced constant in `providers.py` — live-fetched and cross-checked against Anthropic's own pricing pages, explicitly flagged for re-verification after 2026-10-15 (Haiku 4.5's earliest possible retirement date).
- `evals report --scores` now sums each `scorer_type` group's `cost_usd` and prints a `total_cost_usd=...` alongside its pass rate — the exact "suite-level cost aggregation" trigger this feature's own RFC named for adopting `Decimal`. `Score.cost_usd` (and `Run`-independent pricing math in `providers.py`) migrated from `float` to `Decimal` in the same pass, built from string literals (`Decimal("1.00")`, never a float intermediate) to avoid reintroducing the exact imprecision `Decimal` exists to prevent — verified pydantic v2 round-trips `Decimal` through the existing JSONL mechanism exactly, as a quoted string, with zero serializer changes needed. A `Score` with `cost_usd=None` (currently unreachable — only one priced judge model exists) is excluded from the sum and counted explicitly (`"(N unknown excluded)"`), never silently treated as zero.
- `evals report --scores <path>` — reads a persisted `Score`s JSONL file (written by `evals run --scores`/`evals rollout --scores`) and prints a pass rate + Wilson CI, mutually exclusive with the existing `--successes`/`--total` raw-counts mode. Every `Score` in the file counts as one trial (no dedup, no `eval_case_id` filtering — the same blunt "count what's there" philosophy `run`/`rollout` already use in-process). Grouped by `scorer_type`, printing one line per distinct value present (`deterministic`/`llm_judge` are never blended into one number — they're different measurement instruments with different failure semantics). Pure CLI-layer wiring over the existing `Score`/`load_scores`/`format_report`/`wilson_interval` — no new model, no new persistence, no new dependency.
- `Score` model + persistence, per `docs/rfcs/2026-09-04-evals-score-model.md`: the last unbuilt entity in `evals/ARCHITECTURE.md`'s Data Model sketch is now real, and every scoring decision across all four call sites (`evals run`/`evals rollout` × deterministic/`--llm-judge`) is a durable, `--scores <path>`-persisted record instead of a `click.echo` line that vanished after the process exited. Closes the most acute instance of the gap: `judge()` already computed a full `rationale`+`bias_mitigations_applied` pair on every successful call, and `cli.py`'s `_judge_output` discarded both, returning only a bare `bool` — that data now survives into a `Score`. `Score.run_id` is `None` for `evals run` (which never touches the Rollout Scheduler) and a real `Run.id` for `evals rollout` — never a fabricated `EvalCase.id` stand-in, mirroring `Run.cost_usd`'s own "`None` means not applicable" convention; the always-real `eval_case_id`/`eval_case_revision` (not in the original sketch) is the join key both commands can honestly supply regardless. `--scores` is a new, required option on both commands, mirroring `--results`'s existing required convention — a deliberate breaking CLI change. A `JUDGE_ERROR` case or a non-`"completed"` `Run` produces zero `Score` rows, exactly mirroring the existing `continue`-before-counting control flow. Deliberately diverges from every framework surveyed while grounding this RFC (promptfoo/Inspect AI/DeepEval/Braintrust all embed scores on their one run/sample record instead of a separate normalized entity) — named explicitly: Kelvran's two-command, two-atomic-unit shape has no single object every score can attach to, so a standalone `Score` is the one shape that honestly serves both.
- Real Anthropic-backed LLM-judge wiring, per `docs/rfcs/2026-09-04-evals-llm-judge-provider-wiring.md`: `evals/judge/providers.py`'s `make_anthropic_call_model()` — the only file in `evals/` that imports `anthropic` — closes the gap where `judge()` could only be exercised against a scripted fake. A pinned, dated default judge model (`claude-haiku-4-5-20251001`, never a bare alias) is constructed lazily, so importing the module never requires `ANTHROPIC_API_KEY`. New `--llm-judge` flag on both `evals run` and `evals rollout`: a case/`Run` is scored by a real, single Anthropic call instead of the deterministic scorer; a missing `reference` fails loudly (`click.ClickException`) before any call is made; a judge-call failure (malformed response, SDK/network error) marks that one case `JUDGE_ERROR` and the suite continues, mirroring the Rollout Scheduler's own "one case's failure never aborts the suite" precedent. `judge()`/`llm_judge.py` are completely untouched — still zero SDK code, still fully unit-testable without a live key. `Run.cost_usd` is deliberately NOT populated by a judge call — it stays `None` for a judged rollout exactly as it does for an unjudged one, since `Run` represents the cost of *producing* an output, not the separate, scoring-time cost of grading it; tracking a judge call's cost is left to a future `Score` record. A new `RUN_LIVE_LLM_TESTS=1`-gated integration test (`llm_integration` pytest marker) proves the real wiring against a live key when one is set — deliberately a separate env var from `RUN_DOCKER_TESTS`, since the two gate different live dependencies and conflating them would either bill API calls on Docker-only runs or skip live-LLM tests for the wrong reason. Default `make verify`/CI never sets it, so no secret is ever required to pass.
- Rollout Scheduler, `Run` model, and JSONL Results Store, per `docs/rfcs/2026-09-04-evals-rollout-scheduler.md`: the first genuinely end-to-end "case → real sandboxed execution → scored, persisted result" path in `evals/`. A new `Run` pydantic model (`evals/models.py`, same `frozen=True` convention as `EvalCase`) records `harness_config` (`{image, command, timeout_s}`), `status` (`completed`/`timed_out`/`error`), `exit_code`/`stdout`/`stderr`, `latency_ms`, and `cost_usd` — deliberately `None` by default, never `0.0`, since v1's sandbox-only harness makes no billed LLM call and reporting zero would falsely claim "measured." A new `evals.rollout.scheduler.run_suite` executes each `EvalCase` sequentially through the existing, unmodified `run_in_sandbox()` (no concurrency/pool this pass, per `evals/ARCHITECTURE.md`'s own stated "asyncio at v1; Ray Core once justified" posture); a launch failure (e.g. a missing `docker` binary) is caught and turned into a `status="error"` `Run` rather than aborting the whole suite. A new `evals.rollout.results_store` (`append_runs`/`load_runs`) persists every `Run` as one line of an append-only JSONL file — no new infrastructure, matching the grounding research's precedent finding that this exact filesystem-only shape is Inspect AI's and promptfoo's real default production mode, not a fallback. A new `evals rollout --suite <path> --results <path>` CLI command wires it together, scoring each completed `Run`'s captured `stdout` against the case's `reference` with the existing deterministic scorer and printing the existing Wilson-CI-bearing report — `evals run`'s own baked-in-`task_spec.output` convention and behavior are completely unchanged.

## Fixed

- **Real DoS-relevant bug**: `run_in_sandbox()`'s timeout enforcement only ever killed the local `docker run` CLI *client* process, never the container itself — a killed CLI process does not stop its container, confirmed empirically against a real Docker daemon (`docker ps` still showed a `sleep 30` container `Up` well after a `timeout_s=2` call had already returned `timed_out=True`). Fixed by capturing the real container ID via `--cidfile` and issuing a genuine `docker kill <id>` on timeout, not just killing the CLI wrapper. New load-bearing regression test (`test_run_in_sandbox_timeout_actually_stops_the_container`) asserts the container is genuinely gone via `docker inspect`, not just that the Python call returned — sanity-checked by temporarily reverting the fix and confirming a real orphaned container was left running. Found while implementing an unrelated, smaller backlog item (surfacing `container_id` on `evals`' `Span` model); both are fixed in the same pass since they share the same missing piece.
