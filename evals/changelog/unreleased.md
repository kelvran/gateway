## Added

- `evals report --scores <path>` — reads a persisted `Score`s JSONL file (written by `evals run --scores`/`evals rollout --scores`) and prints a pass rate + Wilson CI, mutually exclusive with the existing `--successes`/`--total` raw-counts mode. Every `Score` in the file counts as one trial (no dedup, no `eval_case_id` filtering — the same blunt "count what's there" philosophy `run`/`rollout` already use in-process). Grouped by `scorer_type`, printing one line per distinct value present (`deterministic`/`llm_judge` are never blended into one number — they're different measurement instruments with different failure semantics). Pure CLI-layer wiring over the existing `Score`/`load_scores`/`format_report`/`wilson_interval` — no new model, no new persistence, no new dependency.
- `Score` model + persistence, per `docs/rfcs/2026-09-04-evals-score-model.md`: the last unbuilt entity in `evals/ARCHITECTURE.md`'s Data Model sketch is now real, and every scoring decision across all four call sites (`evals run`/`evals rollout` × deterministic/`--llm-judge`) is a durable, `--scores <path>`-persisted record instead of a `click.echo` line that vanished after the process exited. Closes the most acute instance of the gap: `judge()` already computed a full `rationale`+`bias_mitigations_applied` pair on every successful call, and `cli.py`'s `_judge_output` discarded both, returning only a bare `bool` — that data now survives into a `Score`. `Score.run_id` is `None` for `evals run` (which never touches the Rollout Scheduler) and a real `Run.id` for `evals rollout` — never a fabricated `EvalCase.id` stand-in, mirroring `Run.cost_usd`'s own "`None` means not applicable" convention; the always-real `eval_case_id`/`eval_case_revision` (not in the original sketch) is the join key both commands can honestly supply regardless. `--scores` is a new, required option on both commands, mirroring `--results`'s existing required convention — a deliberate breaking CLI change. A `JUDGE_ERROR` case or a non-`"completed"` `Run` produces zero `Score` rows, exactly mirroring the existing `continue`-before-counting control flow. Deliberately diverges from every framework surveyed while grounding this RFC (promptfoo/Inspect AI/DeepEval/Braintrust all embed scores on their one run/sample record instead of a separate normalized entity) — named explicitly: Kelvran's two-command, two-atomic-unit shape has no single object every score can attach to, so a standalone `Score` is the one shape that honestly serves both.
- Real Anthropic-backed LLM-judge wiring, per `docs/rfcs/2026-09-04-evals-llm-judge-provider-wiring.md`: `evals/judge/providers.py`'s `make_anthropic_call_model()` — the only file in `evals/` that imports `anthropic` — closes the gap where `judge()` could only be exercised against a scripted fake. A pinned, dated default judge model (`claude-haiku-4-5-20251001`, never a bare alias) is constructed lazily, so importing the module never requires `ANTHROPIC_API_KEY`. New `--llm-judge` flag on both `evals run` and `evals rollout`: a case/`Run` is scored by a real, single Anthropic call instead of the deterministic scorer; a missing `reference` fails loudly (`click.ClickException`) before any call is made; a judge-call failure (malformed response, SDK/network error) marks that one case `JUDGE_ERROR` and the suite continues, mirroring the Rollout Scheduler's own "one case's failure never aborts the suite" precedent. `judge()`/`llm_judge.py` are completely untouched — still zero SDK code, still fully unit-testable without a live key. `Run.cost_usd` is deliberately NOT populated by a judge call — it stays `None` for a judged rollout exactly as it does for an unjudged one, since `Run` represents the cost of *producing* an output, not the separate, scoring-time cost of grading it; tracking a judge call's cost is left to a future `Score` record. A new `RUN_LIVE_LLM_TESTS=1`-gated integration test (`llm_integration` pytest marker) proves the real wiring against a live key when one is set — deliberately a separate env var from `RUN_DOCKER_TESTS`, since the two gate different live dependencies and conflating them would either bill API calls on Docker-only runs or skip live-LLM tests for the wrong reason. Default `make verify`/CI never sets it, so no secret is ever required to pass.
- Rollout Scheduler, `Run` model, and JSONL Results Store, per `docs/rfcs/2026-09-04-evals-rollout-scheduler.md`: the first genuinely end-to-end "case → real sandboxed execution → scored, persisted result" path in `evals/`. A new `Run` pydantic model (`evals/models.py`, same `frozen=True` convention as `EvalCase`) records `harness_config` (`{image, command, timeout_s}`), `status` (`completed`/`timed_out`/`error`), `exit_code`/`stdout`/`stderr`, `latency_ms`, and `cost_usd` — deliberately `None` by default, never `0.0`, since v1's sandbox-only harness makes no billed LLM call and reporting zero would falsely claim "measured." A new `evals.rollout.scheduler.run_suite` executes each `EvalCase` sequentially through the existing, unmodified `run_in_sandbox()` (no concurrency/pool this pass, per `evals/ARCHITECTURE.md`'s own stated "asyncio at v1; Ray Core once justified" posture); a launch failure (e.g. a missing `docker` binary) is caught and turned into a `status="error"` `Run` rather than aborting the whole suite. A new `evals.rollout.results_store` (`append_runs`/`load_runs`) persists every `Run` as one line of an append-only JSONL file — no new infrastructure, matching the grounding research's precedent finding that this exact filesystem-only shape is Inspect AI's and promptfoo's real default production mode, not a fallback. A new `evals rollout --suite <path> --results <path>` CLI command wires it together, scoring each completed `Run`'s captured `stdout` against the case's `reference` with the existing deterministic scorer and printing the existing Wilson-CI-bearing report — `evals run`'s own baked-in-`task_spec.output` convention and behavior are completely unchanged.

## Changed

- `evals/evals/rollout/results_store.py` moved to `evals/evals/results_store.py` and generalized over any frozen pydantic model — the append/load mechanism was never rollout-specific, only its first caller (`Run`) was; `evals run` (no rollout, no sandbox) is `Score`'s other, equally valid caller. `append_runs`/`load_runs` are behavior-identical thin wrappers; no external consumer of the old path exists (`kelvran-evals` has never published to PyPI).
- `evals/judge/providers.py`'s `_DEFAULT_JUDGE_MODEL` renamed to public `DEFAULT_JUDGE_MODEL` so `cli.py` can cite the real pinned model id as a `Score.scorer_id`.
- `evals/ARCHITECTURE.md`'s Data Model sketch: `Score` moves from "unbuilt" to real (narrowed v1 shape); the Rollout Lifecycle diagram's disambiguating note now reflects that `Scorer Service` covers both deterministic and single-provider `llm_judge` scoring, with every verdict persisted.
- `evals/ARCHITECTURE.md`'s Tech Stack table's `Statistics` row distinguishes what's real today (the Wilson-interval calculator, stdlib-only) from the future target (bootstrap resampling/Bayesian comparison/pass@k via `numpy`/`scipy`/`scikit-learn`) — that package family is still not installed.
- `evals/ARCHITECTURE.md`'s Tech Stack table's `Judge SDKs` row updated a second time this session: from "not yet wired" to naming the real Anthropic wiring this pass ships (pinned default model, second-provider follow-on path).
