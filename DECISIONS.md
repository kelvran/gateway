# Decisions

Lightweight, continuous, one-line-per-decision log. Read before starting new work; append a new line after work is implemented, not during planning. **Never edit past entries** — supersede with a new dated line that says what changed and why.

This is **not** a replacement for `docs/decisions/` (ADRs). ADRs are for the rare, foundational, hard-to-reverse calls, written in full MADR format with context/drivers/alternatives/consequences. This file is the terse, continuous layer for everything smaller — if a decision here recurs or turns out to matter more than expected, promote it to a full ADR rather than letting it grow in place.

- `[2026-09-03]` Decimal-precision cost/budget arithmetic shipped for `gateway` (`docs/rfcs/2026-09-02-decimal-cost-accounting.md`), chosen from the phase-audit workflow's Phase 1 recommendation over distributed rate limiting and budget persistence per the founder's explicit selection. `github.com/shopspring/decimal` — the gateway's second external Go dependency, zero transitive dependencies — replaces `float64` in `costaccounting.ModelPrice`/`Calculate`, `budget.Tracker`, and `identity.VirtualKey.BudgetUSD`. Chosen over `math/big.Rat` (wrong mental model for currency, no decimal-string API), `cockroachdb/apd` (built for SQL-`DECIMAL`-context parity Kelvran has no database to match yet), and hand-rolled `int64` fixed-point (Kelvran's real per-token prices need sub-micro-dollar resolution, defeating any fixed scale factor). The real fix required touching `controlplane`'s hand-rolled YAML parser, not just Go struct types: it previously converted every numeric scalar to `float64` before any caller ever saw it, which would have silently round-tripped every money value through binary floating point regardless of the Decimal type change — numeric scalars now stay as raw source strings, parsed via a new `getDecimal` helper. Found and fixed one real, more severe bug in the same function while researching this (verified via a live test, not asserted): the parser's boolean detection accepted `strconv.ParseBool`'s full grammar, which treats `"0"`/`"1"` as valid booleans — `budget_usd: 1` would silently become the bool `true`, fail the numeric type switch, and fall back to zero, which `budget.Tracker`'s own convention reads as **unlimited**. Fixed by matching only the literal words true/false. `kelvran.cost.usd`'s OTel attribute and `cost_usd`'s JSON log field both changed from `float64`/number to an exact decimal string — a deliberate format change, not an oversight, since converting back to `float64` at that boundary would have reintroduced the exact precision loss this pass removes.

- `[2026-09-03]` Cache L2 (normalized-match) shipped for `gateway` (`docs/rfcs/2026-09-03-cache-l2-normalized-match.md`), picked as Phase 3 after the `api/gatewayevents` contract closed Phase 2 — in-scope v1 work per `PRD.md`'s own line ("exact-match (L1) and normalized-match (L2) layers at v1"), distinct from L3 (semantic, hard-gate-mandatory, still unbuilt). A second `cache.Cache` instance (never a widened `cache.Cache` interface) is checked on an L1 miss, keyed via a new `cache.NormalizedKey` on `dataplane.normalizeMessages`'s output. The v1 normalization allowlist is deliberately narrower than this RFC's own grounding research recommended: the research proposed 6 operations (including internal whitespace collapse and case-folding with fenced-code-span exclusion), reasoning entirely from prose examples; independently extending its own "construct a concrete counterexample" method to pasted code — a realistic message shape for Kelvran's agent traffic, not considered by any of the research's 4 angles — surfaced that both of those operations can collide two different questions (differing Python indentation depth; a capitalized identifier vs. a lowercase reserved word) without ever needing markdown code fences. v1 ships only the 3 operations with no plausible collision risk regardless of content type: outer whitespace trim, Unicode NFC (never NFKC), and a single trailing terminal punctuation strip on the last message only. `internal/cache/inprocess.Cache` gained real LRU eviction (`container/list`) as a direct, causally-connected prerequisite — it had no capacity bound at all before this pass, and doubling its instance count for L2 would have doubled an already-real unbounded-memory risk rather than introducing a new one. No industry precedent exists for this exact three-tier scheme among the products surveyed (Portkey/LiteLLM are strictly two-tier; GPTCache's pre-processing hook does content extraction, not normalization; Redis LangCache's "exact" mode folds in case-insensitivity but isn't a separately named tier) — stated plainly in the RFC, not overstated as proven practice.
- `[2026-09-03]` Cache L3-lite (lexical near-duplicate matching, not real embedding-based semantic matching) shipped for `gateway` (`docs/rfcs/2026-09-03-cache-l3-lite-lexical-hard-gated.md`), picked as Phase 4 after Cache L2 closed Phase 3. Scoped down from the originally-imagined full semantic L3 mid-research, mirroring the L2 RFC's own precedent of narrowing once a real gap surfaced: a real embedding call on every lookup would void `gateway/ARCHITECTURE.md`'s "cache lookup never touches an upstream" guarantee, and no mature, statically-linkable Go ML runtime exists today (official cgo ONNX Go bindings have no tagged release yet; cgo itself breaks the scratch-image static-binary story; pure-Go alternatives are pre-v1/experimental) — real embedding-based semantic L3 is deferred to a later RFC, gated on real miss-telemetry that doesn't exist yet, not a fixed timeline. Ships instead: pure-stdlib MinHash/shingling (`hash/fnv` + a deterministic `splitmix64` bit-mixer, zero new `go.mod` entries) behind a new `cache.LexicalCache` interface (distinct from `cache.Cache`, since a similarity search returns zero-to-many scored candidates) backed by a new `internal/cache/inprocess.LexicalCache` — per-tenant-partitioned structurally (one LRU bucket per tenant, not a shared list filtered post-hoc), per `THREAT_MODEL.md`'s KeyPooling mitigation. Every candidate must clear, in order: a hard bypass for volatile queries (skips L3 entirely, never a soft score), an exact entity/number/date fingerprint match via a new `dataplane.Fingerprint` (regex numbers/dates + capitalized-multi-token-sequences, deliberately over-inclusive — a false positive only costs hit rate, a false negative could serve a wrong cached answer), a 24h staleness budget and exact model-ID match, and a Jaccard similarity floor of 0.9 — explicitly transferred from `THREAT_MODEL.md`'s embedding-cosine floor without independent statistical validation, flagged as an open question, not assumed safe. A search error fails closed exactly like a fingerprint/freshness mismatch — straight to a real upstream call, never an unchecked serve. The three papers `THREAT_MODEL.md`/`PRD.md` cite (CacheAttack, "When Cache Poisoning Meets LLM Systems," KeyPooling) were independently verified as real (one spot-checked directly against its live arXiv abstract) but none of them actually validate entity/number/date extraction as a tested defense — that pattern is industry practice, not paper-proven — stated plainly rather than smoothed over; the one mitigation the papers do validate with a real F1 score (a query↔response consistency classifier) is not implemented here, since it needs the same ML infrastructure this RFC already ruled out. Found one real bug via a load-bearing test during implementation (not a design decision, but worth recording): the entity fingerprint's "skip the sentence-initial word" heuristic didn't exclude the pronoun "I" when it appeared mid-sentence (always capitalized regardless of position), which would have made "How do I reverse a list" and "What's the way to reverse a list" incorrectly fingerprint as different — fixed with a single, narrowly-scoped `alwaysCapitalizedWords` exclusion rather than a broader stoplist.
